Here is the entire interface a Solana program presents to the runtime.

```rust
pub fn process_instruction(
    program_id: &Pubkey,
    accounts: &[AccountInfo],
    instruction_data: &[u8],
) -> ProgramResult
```

A program id, a slice of accounts, a slice of bytes. Nothing else arrives. Nothing else is
promised.

Set that beside the function you would have written on the machine you already know:

```solidity
function deposit(uint256 amount) external {
    balances[msg.sender] += amount;
}
```

Count what the Solidity compiler did before that line ran. It generated a dispatcher that read four
bytes of calldata and jumped to this function. It decoded `amount` from calldata into a `uint256`.
It supplied `msg.sender` as an authenticated fact. It computed the storage slot for
`balances[msg.sender]` by hashing the key with the mapping's slot — a location no caller could
influence. And it refused, at compile time, to let you read that slot as a struct of a different
shape.

On the raw Solana entrypoint, every one of those is your problem. That gap is the whole reason
Anchor exists, and this lesson is about the shape of the gap rather than the syntax that covers it.

## Six jobs that arrive undone

Take the three arguments in order and ask what a program must do with each.

**Which instruction is this?** `instruction_data` is bytes. There is no selector the runtime
understands, no dispatch table, no ABI. You read some agreed prefix and branch on it. What that
prefix is, and how long, is a convention your program invents and your client must match.

**What are the arguments?** The remainder of `instruction_data` is bytes too. You choose a
serialization format, write the decoder, and handle the case where the buffer is short, long, or
garbage.

**Is `accounts[2]` the account you meant?** This is the question with no EVM analogue at all, and it
is worth slowing down on. In Solidity, `balances[msg.sender]` names a location that the *code*
derives. A caller cannot hand you a different slot; there is no argument for that. On Solana the
caller supplies the accounts, all of them, as part of the transaction — that is the tax you met in
[declared access is a tax](/c/declared-access-is-a-tax), and it is not merely inconvenient. It means
the state your program operates on is chosen by the party calling you.

**Is the data inside it the type you think it is?** An account holds a byte buffer. Two of your own
account types, both 72 bytes long, are indistinguishable as bytes. Deserializing a `Vault` buffer
into a `Config` struct succeeds. It does not fault, it does not revert, it produces a `Config` whose
fields are somebody else's numbers.

**Did anybody actually authorise this?** Each `AccountInfo` carries an `is_signer` flag. The runtime
sets it truthfully. It does not require you to look at it.

**How does state get written back?** You serialize into the account's data buffer yourself, having
first checked that the account is writable, that it is large enough, and that you are permitted to
write it at all.

Six jobs. A raw Solana program is mostly these six jobs, and the interesting part of your program is
the small remainder. That ratio is the thing Anchor changes.

<Aside kind="note">
Notice what the runtime *does* still guarantee, because it is easy to over-correct into thinking
Solana checks nothing. Only the owning program may modify an account's data or reduce its lamports;
`is_signer` is set by signature verification and cannot be forged by the caller; the declared account
list is enforced for locking and for writability. The runtime is sound. What it does not do is
interpret your bytes or know your intentions, and every one of the six jobs above lives in that
second category.
</Aside>

## Anchor is a code generator, and that is the whole claim

An Anchor program is a Rust program that compiles to the same SBF ELF as a hand-written one, deploys
the same way, and is loaded by the same loader. The runtime has never heard of Anchor. There is no
Anchor node, no Anchor precompile, no Anchor opcode.<Cite src="anchor-docs" /><Cite src="solana-docs-anchor" />

What Anchor is, is a set of Rust macros that expand — at compile time, on your machine — into the
deserialization and validation code you would otherwise write by hand.<Cite src="anchor-docs-program-structure" />

That single sentence has three consequences worth carrying through the rest of the module.

**Everything Anchor adds executes on chain.** It is code in your program. It runs inside the
invocation, in front of your logic, and it consumes compute units. The declarative syntax reads like
configuration, and it is not configuration.

**Everything Anchor adds is readable.** `anchor expand` prints the generated source, which means
every claim in this module is checkable rather than folkloric.<Cite src="anchor-docs-cli" />

**Everything Anchor adds can be absent.** A field with no constraints gets no checks. This is why
the pedagogy in this module runs manual-first: if you only ever learn the macro, you cannot look at
a program and notice the check that *isn't* there. That noticing is the entire skill.

## The three macros, each shown against the code it replaces

Anchor's surface is three macro layers plus `declare_id!`, which records the program's own
address.<Cite src="anchor-docs-program-structure" /> Take them in the order the six jobs appear.

### `#[program]` — dispatch and argument decoding

By hand, dispatch is a prefix read and a match. Something in this shape, with the prefix length and
encoding chosen by you:

```rust
// manual: you invent the convention and you enforce it
let (tag, rest) = instruction_data.split_at(8);
match tag {
    DEPOSIT => {
        let args = DepositArgs::try_from_slice(rest)?;   // your decoder
        deposit(program_id, accounts, args)
    }
    WITHDRAW => { /* ... */ }
    _ => Err(ProgramError::InvalidInstructionData),
}
```

With `#[program]`, the module's public functions *are* the instructions. Each becomes a handler
whose first parameter is a `Context<T>` and whose remaining parameters are the decoded
arguments.<Cite src="anchor-docs-program-structure" />

```rust
#[program]
mod vault {
    use super::*;

    pub fn deposit(ctx: Context<Deposit>, amount: u64) -> Result<()> {
        ctx.accounts.vault.total += amount;
        Ok(())
    }
}
```

The generated dispatcher compares the first eight bytes of the instruction payload against a
discriminator derived from a hash of the instruction's name, which is the next lesson's
subject.<Cite src="anchor-docs-idl" /> `Context<T>` carries the deserialized accounts, the executing
`program_id`, the accounts passed but not declared (`remaining_accounts`), and the bump seeds found
during validation.<Cite src="anchor-docs-program-structure" />

The comment on `remaining_accounts` in Anchor's own source is worth reading as written: accounts
given but not deserialized or validated, and be very careful when using this
directly.<Cite src="anchor-docs-program-structure" /> That field is where the framework hands the
raw problem back to you, and it is the first place to look in an unfamiliar program.

### `#[derive(Accounts)]` — the account list and its validation

By hand, every account is an index into a slice followed by a stack of assertions:

```rust
// manual: three checks before you can trust one account
let vault_info = &accounts[0];
if vault_info.owner != program_id { return Err(/* wrong program owns this */); }
let data = vault_info.try_borrow_data()?;
if data[..8] != Vault::DISCRIMINATOR { return Err(/* not a Vault */); }
let mut vault = Vault::try_from_slice(&data[8..])?;

let authority_info = &accounts[1];
if !authority_info.is_signer { return Err(/* nobody authorised this */); }
if vault.authority != *authority_info.key { return Err(/* wrong owner */); }
```

With `#[derive(Accounts)]`, that becomes a struct in which the *type of each field* and the
attributes on it carry the assertions:<Cite src="anchor-account-constraints" /><Cite src="anchor-docs-account-types" />

```rust
#[derive(Accounts)]
pub struct Deposit<'info> {
    #[account(mut, has_one = authority)]
    pub vault: Account<'info, Vault>,
    pub authority: Signer<'info>,
    pub system_program: Program<'info, System>,
}
```

Read those two blocks against each other and the framework's actual proposition becomes visible.
Nothing was added. The manual version's five `if`s are the generated version's five checks. What
changed is that the checks are now impossible to omit *silently*: the shape of the struct is the
shape of the validation, and a missing check shows up as a missing word rather than as an absent
line somewhere in a function body.

**The Accounts struct is the security specification of the instruction, in one place.** That is the
single most useful sentence in this module. When you open an unfamiliar Anchor program, you read the
`Accounts` structs first and the handler bodies second, because the handler cannot defend an account
the struct already let through.

### `#[account]` — on-chain state

By hand, an account type is a struct, a serialization choice, and a type tag you invent and remember
to check. With `#[account]`, the struct gets Borsh serialization, an owner check against the
declaring program, and an eight-byte discriminator, all
generated.<Cite src="anchor-docs-program-structure" /><Cite src="anchor-docs-idl" />

```rust
#[account]
pub struct Vault {
    pub authority: Pubkey,
    pub total: u64,
}
```

Two of the six jobs disappear here — the encoding and the type tag — and one appears that has no EVM
counterpart: you must size the account at creation, because Solana accounts are allocated with a
fixed length rather than growing as a mapping does.

## What it does not remove

A framework's marketing is about what it handles. Your reading of a program has to be about what it
leaves.

**Accounts you declare as unchecked.** `UncheckedAccount` and `AccountInfo` assert nothing. Anchor
makes you write a `CHECK` doc comment justifying it, which converts an invisible omission into a
visible sentence — and a sentence is only as good as its author.<Cite src="anchor-docs-account-types" />

**Relationships you did not state.** A `Vault` that passes every type check can still be somebody
else's `Vault`. Nothing in `Account<'info, Vault>` says *whose*.

**Arithmetic.** Rust's release profile wraps on overflow unless overflow checks are enabled; the
framework has no opinion about your `+`.

**Programs you call.** A cross-program invocation goes to whatever program id you pass it. Anchor
will not tell you that the token program you were handed is a program somebody wrote yesterday.

**Everything about your business logic.** Anchor validates accounts. It does not know that a
withdrawal should be capped, that a price is stale, or that an admin instruction should not be
callable during a pause.

Anchor maintains its own catalogue of these — the Sealevel Attacks reference, kept as insecure /
secure / recommended triples so you can see the flawed code, the fix, and the idiomatic-Anchor
fix.<Cite src="anchor-docs-security-exploits" /><Cite src="sealevel-attacks" /> The framing in
Anchor's own words is the right one: the framework uses a lot of magic to eliminate footguns, and if
you are shipping to mainnet you need to understand every bit of that magic and the motivation behind
it.<Cite src="anchor-docs-security-exploits" />

## Read the version yourself, every time

This is a fast-moving framework and any version number written into a lesson is wrong by the time
you read it. So the durable skill is the lookup, not the number.

Three places, in descending order of authority. `anchor --version` on the machine you are actually
building on, which is the only answer that describes your build. The published crate versions, which
tell you what exists.<Cite src="anchor-crate-versions" /> The release list and CHANGELOG, which tell
you what changed.<Cite src="anchor-releases" /><Cite src="anchor-repo-changelog" />

What that lookup returned on 26 August 2026, purely as a worked example of reading it: `anchor-lang`
1.0.0 was published on 2 April 2026, ending roughly five years of 0.x; 1.1.2 followed on 26 June
2026 and is the newest non-prerelease; and a 2.0.0-rc.1 pre-release was published on 12 August
2026.<Cite src="anchor-crate-versions" /> A release candidate at the top of the list is exactly the
situation where quoting "the current version" without saying which channel you mean produces two
people talking past each other.

Two more artefacts of the 1.0 transition that will bite you in older material. The repository moved
namespace — `github.com/solana-foundation/anchor` now resolves to `github.com/otter-sec/anchor`, and
the crates are published by OtterSec.<Cite src="anchor-repo-changelog" /><Cite src="anchor-lang-error-docsrs" />
And the TypeScript package was renamed away from `@coral-xyz/anchor`; the CHANGELOG's own breaking
entry and its feature entries do not agree on the replacement name, listing both
`@anchor-lang/anchor` and `@anchor-lang/core`.<Cite src="anchor-repo-changelog" /> Resolve that one
from the package registry against the version you are installing rather than from any prose,
including this prose.

<Aside kind="warn">
The practical consequence: a tutorial that says `0.29` or `0.30` is not merely a point release
behind. Between there and now the IDL format changed, the default local network changed, the default
test template changed, the TypeScript package name changed, and several constraint behaviours became
stricter.<Cite src="anchor-repo-changelog" /><Cite src="anchor-changelog" /> Treat pre-1.0 material
as being about a related framework.
</Aside>

<Check type="explain" concept="anchor-purpose">
A colleague coming from Solidity reviews your first Anchor program and says: "This is fine, but I
don't see where you check anything. In our Solidity code every function starts with
`require(msg.sender == owner)`. Anchor seems to just declare the accounts and get on with it — where
did the checks go, and what is stopping someone passing in the wrong account?"

Answer them, and say what you would show them to make the answer concrete.

<Answer>
**The checks did not go anywhere; they moved from the function body to the account declaration, and
they still run on chain.** `#[derive(Accounts)]` is a procedural macro. It expands at compile time
into Rust that executes inside the program, before the handler body, and returns a specific error
when an assertion fails.<Cite src="anchor-account-constraints" /><Cite src="anchor-docs-program-structure" />
The syntax is declarative; the runtime behaviour is a stack of `if` statements. Nothing about it is
evaluated by a client, a compiler-time prover, or the Solana runtime.

**What is stopping the wrong account is a specific check, and it is worth naming them separately
because they answer different questions.** The type `Account<'info, Vault>` asserts that this
program owns the account and that its first eight bytes are `Vault`'s discriminator before any field
is read.<Cite src="anchor-docs-account-types" /><Cite src="anchor-docs-idl" /> The type
`Signer<'info>` asserts the account signed the transaction.<Cite src="anchor-docs-account-types" />
A `has_one = authority` constraint asserts that the pubkey stored *inside* the vault equals the key
of the `authority` account in the same
instruction.<Cite src="anchor-account-constraints" /> Only all three together reproduce what
`require(msg.sender == owner)` gives you in Solidity, and the reason it takes three is that Solidity
was answering an easier question: its storage location was derived by the code, so "is this the
right object" never came up.

**The honest half of the answer is that nothing stops an account you did not constrain.** A field
typed `UncheckedAccount` asserts nothing at all; Anchor requires a `CHECK` doc comment explaining
why, and that comment is prose, not a check.<Cite src="anchor-docs-account-types" /> A `Vault` with
no `has_one` is any valid `Vault`, including the attacker's — or including the victim's, passed by
the attacker.

**What to show them, in this order.** First, `anchor expand` on the program, so they can read the
generated validation as ordinary Rust and stop treating the attributes as
magic.<Cite src="anchor-docs-cli" /> Second, a failing test: call the instruction with a vault the
signer does not own and show the transaction failing with a named constraint error rather than
succeeding quietly. Third, delete the `has_one` and re-run the same test, so they watch the exploit
land. That third step is the one that converts the explanation into a belief, and it is why this
module's practice exercises are built around removing constraints rather than adding them.

**The sentence to leave them with.** In Solidity you ask "did the caller have permission to do
this". On Solana you ask that *and* "is this the object the caller has permission to act on", because
the caller chose the object. Anchor gives you a place to write the second question down; it does not
notice when you leave it blank.
</Answer>
</Check>

## What this unlocks

The next six lessons walk the generated checks one layer at a time, and each of them is a case of
the same move: here is the manual version, here is the macro, here is what the macro does *not*
cover.

- **The eight-byte discriminator and the three checks inside `Account<'info, T>`** come next, and
  they are the two mechanisms that close the classic
  [type confusion](/c/account-type-confusion) and [missing owner check](/c/missing-owner-check)
  vulnerability classes.<Cite src="anchor-lang-error-docsrs" />
- **Constraints as generated code** turns the declarative syntax back into the `if` statements it
  compiles to, which is what makes error codes readable and costs predictable.
- **Binding an account to its seeds and its owner** is the part with no Solidity counterpart, because
  a Solidity mapping never needed to prove that a key belonged to a caller.
- **The IDL** is Solana's ABI, and unlike an ABI it can be incomplete in ways that produce a silently
  wrong client.
- **Cost and testing** close the module: what the convenience is measured in, and why the next module
  exists at all.

Before moving on, do the one thing that makes the rest of this concrete. Take any Anchor program you
can find, run `anchor expand`, and read the generated `try_accounts` for a single
instruction.<Cite src="anchor-docs-cli" /> Everything in the remaining lessons is a description of
what you will find there.
