Open any ERC-20 you have ever read and find the two lines that make a transfer happen. They are a
subtraction and an addition against a `mapping(address => uint256)`. Everything you believe about
that token — that the balances sum to the total supply, that nobody printed themselves a billion of
it, that the transfer function did not silently create value — is a belief about those two lines and
about every other line in the contract that can reach that mapping.

The EVM does not know a token is a token. It knows that some contract writes numbers into some
storage slots. `_mint` is `_balances[to] += amount; _totalSupply += amount;` and the machine has no
opinion about whether the caller was entitled to run it. That is why the vulnerability class you
ranked first by realised loss in the security track is access control, not arithmetic: the arithmetic
is easy, and the guard around the arithmetic is what fails.

Move starts from the other end. It asks: what if the *value* were the thing the machine understood,
and the compiler simply refused to emit code that duplicates or discards it?

This lesson is about what that buys, and — more usefully for someone arriving from Solidity — about
exactly what it does not.

## Where Move came from, and why the origin explains the design

Move was built at Meta for the Diem payments project. Its own technical paper describes an executable
bytecode language for implementing custom transactions and smart contracts, whose central feature is
the ability to define custom resource types "with semantics inspired by linear logic: a resource can
never be copied or implicitly discarded, only moved between program storage
locations".<Cite src="move-diem-paper" /> The same paper reports that Diem used it for the things
that mattered most — the Diem coin itself, transaction processing, and validator
management.<Cite src="move-diem-paper" /> It is explicit that the goal was not only safe digital
assets but "correct business logic for wrapping assets and enforcing access control
policies".<Cite src="move-diem-paper" />

That context is not trivia. It tells you what the language was optimised for and therefore where its
guarantees are concentrated. Diem was a permissioned payments system built by a company with
regulators watching. The requirement that dominated everything else was *representing money
correctly*: no accidental issuance, no accidental destruction, no path by which a bug in an unrelated
module quietly changes the supply. A team with that requirement and a blank sheet of paper does not
put its safety story in a library of well-audited base contracts. It puts it in the type system,
because the type system is the only place a guarantee gets checked on every line of every program
anybody ever writes, including the ones written after you leave.

Diem was wound down. The language outlived it. Two teams took it in different directions, and Aptos
and Sui are both descendants of that lineage.<Cite src="aptos-move-docs" /><Cite src="sui-docs-concepts" />
The third lesson in this module is about how far apart they have moved since; for now, treat the
resource model as the shared inheritance, because it is the part that genuinely transfers.

<Aside kind="note">
The original reference repository, `move-language/move`, is now a **public archive** on
GitHub.<Cite src="move-language-repo" /> There is no single upstream that both chains track. If you
are looking for the current compiler, verifier or standard library, you want whichever chain's
repository you are actually targeting — and you should read the version off that repository rather
than off any tutorial, including this one.
</Aside>

## A resource is a value the compiler will not let you lose

The peer-reviewed account of the design states the rule in the form that matters for a compiler
writer: "when a resource value is assigned to a new memory location, the location previously holding
it must be invalidated".<Cite src="move-resources-paper" /> That single sentence produces both halves
of the guarantee.

**Subgoal: derive "cannot duplicate" from the rule.** If assigning a resource invalidates the source
location, then after `let b = a;` the name `a` no longer holds anything. There is now exactly one
live handle to that value. Writing `a` again is not a runtime failure or a silent aliasing bug; it is
a compile error, in the same category as a type mismatch.

**Subgoal: derive "cannot silently destroy" from the same rule.** A resource that goes out of scope
has to have gone *somewhere* — stored, returned, passed on, or explicitly destructured by code
allowed to destructure it. There is no path where the value simply stops existing because a function
returned. Dropping a resource on the floor is, again, a compile error.

Put those together and you get the property the module title is about. In Solidity you write a
`_transfer` that decrements one balance and increments another, and the conservation of supply is a
consequence of you having written both halves correctly. In Move you take a resource in as a
parameter and you must do something with it; the conservation is a consequence of the code you were
*permitted to write*.

Here is the shape of the difference, stripped to the minimum.

```solidity
// Solidity: the asset is a number. Conservation is a property of this function's body.
function _transfer(address from, address to, uint256 amount) internal {
    _balances[from] -= amount;   // if you forget this line, supply inflates
    _balances[to]   += amount;   // if you forget this line, supply deflates
}
```

```move
// Move: the asset is a value. Conservation is a property of the type.
public fun deposit(account: &mut Wallet, coin: Coin) {
    // `coin` was moved in. It is now yours and you must dispose of it.
    // Returning without storing it, or storing it twice, does not compile.
    vector::push_back(&mut account.coins, coin);
}
```

The second version has no line you can forget. There is no subtraction to omit, because nothing was
subtracted: a value moved from one place to another and the language tracked the move.

That misconception is worth sitting with, because you arrive from a track that ranked vulnerability
classes by realised loss. Re-run that ranking against Move's guarantee and ask which rows it removes.
Accidental double-credit of a balance: removed. A refund path that credits without debiting: removed.
Access control on a privileged mint: **not** removed. Oracle manipulation: not removed. A lending
market that misprices its collateral: not removed. The class at the top of that ranking survives Move
entirely, because "who is allowed to call this" is not a question a linear type system asks.

## The four abilities: read them first, the way you read an Anchor `Accounts` struct

Move does not have a `resource` keyword sitting beside `struct`. It has something more granular and,
once you get used to it, more informative: every type carries a set of **abilities**, and the set
determines which operations the compiler will permit on values of that type. The Move Book defines
exactly four.<Cite src="move-book-abilities" />

- **`copy`** — "Allows values of types with this ability to be copied."<Cite src="move-book-abilities" />
- **`drop`** — "Allows values of types with this ability to be popped/dropped."<Cite src="move-book-abilities" />
- **`store`** — "Allows values of types with this ability to exist inside a value in
  storage."<Cite src="move-book-abilities" />
- **`key`** — "Allows the type to serve as a 'key' for storage", meaning the value can be a top-level
  value in storage.<Cite src="move-book-abilities" />

An asset is not a special construct. It is a struct that has `store` and `key` and does **not** have
`copy` or `drop`.<Cite src="move-book-abilities" /> That is the whole encoding. The absence of two
abilities is what makes a type behave like money.

```move
// A plain data type: freely copied, freely discarded.
public struct Config has copy, drop, store {
    fee_bps: u64,
}

// An asset: no `copy`, no `drop`. The two omissions are the entire safety story.
public struct Coin has store, key {
    id: UID,
    value: u64,
}
```

**Subgoal: learn to read the declaration line as a threat model.** When you open unfamiliar Move
code, the ability list on each struct tells you, before you read a single function, what the author
believed about that type. `has copy, drop` means the author considers it data — configuration,
parameters, a computed result. No `copy`, no `drop` means the author considers it a thing that must
be conserved. If you find a type that holds value and carries `drop`, you have found either a
deliberate design decision worth understanding or a bug, and it took you one line to find it. This is
the same reflex the Solana module trains around the `Accounts` struct: the declaration carries the
security-relevant information, so read declarations before bodies.

**Subgoal: understand why this is finer-grained than a keyword.** Generic types make the four-ability
encoding earn its keep. The Move Book notes that abilities can be *conditional*: a generic type may
not possess all of its declared abilities depending on what its type parameters
carry.<Cite src="move-book-abilities" /> A container of a droppable type is droppable; the same
container holding a `Coin` is not. You get that propagation for free, and it is the mechanism by
which "you cannot put a coin in a struct and then throw the struct away" holds without anyone writing
a rule about coins-inside-structs.

**Subgoal: notice which of the four is chain-specific.** Three of the abilities are about the value.
`key` is about *storage*, and storage is the exact place the two Move chains diverge. In the Aptos
lineage, `key` marks a type that can be published under an account address and reached with the
global-storage operators.<Cite src="aptos-move-book-global-storage" /> On Sui there is no global
storage to reach into at all, and `key` instead carries a requirement that the struct's first field
be an `id: UID`.<Cite src="sui-docs-move-differences" /> Same keyword, different meaning, because the
storage model underneath it is different. Hold that observation; the third lesson in this module is
built on it.

This is the most important correction in the lesson. **Move does not prevent minting.** A module that
declares `Coin` can construct `Coin` values inside its own body, because within the defining module
the struct's fields are accessible and the value can be built. Whether that constructor is guarded by
a capability, a signer check, or nothing at all is an authorization decision the author makes, and it
is exactly as fallible as the `onlyOwner` modifier you would have written in Solidity.

What linearity gives you is different and still valuable: once a coin exists, the number of coins in
the world changes only where someone deliberately wrote code to change it. There is no accidental
path. The set of places that can alter supply is small, syntactically identifiable, and lives inside
one module.

## What the type system actually promises across module boundaries

The guarantee has a second half that is easy to miss and is arguably the more useful one in a system
where you will call code you did not write.

Move was "designed to support strong encapsulation and static verification in the service of secure
smart contract programming".<Cite src="move-robust-safety-paper" /> A struct's fields are private to
its defining module. A `Coin` handed to your module is opaque: you can move it, store it, return it,
pass it on — and you cannot reach inside and change `value`, because that field belongs to the module
that declared the type. Combined with linearity, this means a third-party module you call cannot
inflate your balance, cannot silently keep a copy of the coin you passed it, and cannot make the coin
disappear without the type system noticing.

Compare that with what an ERC-20 balance is. Your balance is a number in *someone else's* mapping.
Every guarantee you have about it is a guarantee about the correctness and the intentions of the
contract that owns the mapping — which is why the token-standards module spends so much of its time
on weird ERC-20 behaviour: fee-on-transfer tokens, rebasing tokens, tokens that do not return a bool.
Each of those is a case where the number in someone else's mapping did not behave the way your code
assumed. In Move, "the amount I received" is a value in your hands with a type, not a number you have
to re-read from a mapping and hope did not move.

The formal work here is honest about its limits, and so should we be. The robust-safety analysis
pairs a program verifier for closed-world invariants with a separate check for whether those
invariants still hold in an open world where arbitrary other modules exist, and reports certifying
more than 99% of the Move modules in its benchmark.<Cite src="move-robust-safety-paper" /> Note both
halves of that: the property is strong enough to be worth formalising, and the number is not 100%.

You are reviewing a Move module that implements a simple escrow. Four things appear in it. For each,
say whether the type system will catch the problem, and if not, what would have to catch it instead.

1. A function takes a `Coin` parameter, checks a condition, and returns early with no value stored.
2. The `release` function transfers the escrowed coin to whoever calls it, with no check on the
   caller.
3. A struct `Receipt` is declared `has copy, drop, store` and is used as proof that a deposit
   occurred.
4. A helper computes a fee and constructs a new `Coin` for it by calling the coin module's `mint`

<Answer>
**1 — the compiler catches it.** A `Coin` has no `drop`, so a path that lets it go out of scope
without storing, returning or destructuring it does not compile.<Cite src="move-book-abilities" />
This is the accidental-loss case, and it is the case the design exists for. Note what the error is
*not*: it is not "you forgot to update a balance", it is "this value has nowhere to go". The compiler
does not know what an escrow is; it knows a value with no `drop` must be disposed of.

**2 — the compiler does not catch it.** Linearity says the coin moves somewhere; it has no opinion
about *who* it moves to. This is an [access-control failure](/c/access-control-failure), which
[outweighs reentrancy in every published count](/c/access-control-is-top-loss), and Move's guarantee
does not touch it. What catches it is a review, a test, a capability pattern that makes the authority
to release a value you must hold, or a specification checked by a prover. In other words: exactly the
same set of things that would catch it in Solidity.

**3 — the compiler does not catch it, and the declaration is the tell.** `Receipt` carries `copy`, so
anyone holding one can make as many as they like, and it carries `drop`, so one can be discarded
without trace. A value used as *proof* of anything should almost never have `copy`. This is the
ability line functioning as a threat model: you found the design flaw by reading one line, before
looking at any logic.<Cite src="move-book-abilities" />

**4 — the compiler does not catch it, and this is the misconception made concrete.** Creating new
`Coin` values is what the defining module is for. Linearity governs what happens to a coin after it
exists; it places no bound on issuance. An unguarded public `mint` is an unbounded inflation bug in
Move for precisely the same reason it is in Solidity.

**The pattern.** One of four. The type system removed the class of bug that comes from *handling*
value carelessly, and left every bug that comes from *deciding* who may do what. That ratio is the
honest summary of what this language buys you.
</Answer>
</Check>

## What you should take from this into the rest of the module

**The comparison that pays off immediately.** An ERC-20 balance is a number in a mapping owned by a
contract, and every safety property about it is a property of that contract's code. A Move resource
is a value with a type, and two safety properties about it — it cannot be duplicated, it cannot be
silently discarded — are properties of the language, checked on every module anyone ever
publishes.<Cite src="move-resources-paper" /><Cite src="move-book-abilities" /> That is a real
difference in where safety lives, and it is not a difference in how much safety there is overall.

**The reading habit.** Ability lists first, then function signatures, then bodies. `has copy, drop`
on something that represents value or authority is a finding. The absence of `drop` on a type
explains why a function has a return value you did not expect. This habit costs nothing and is the
fastest way for someone fluent in Solidity to start reading Move code productively.

**The limit, stated once more because it is the thing people get wrong.** Move makes a specific class
of accident impossible. It does not make authorization correct, does not price your collateral, and
does not stop you from writing a mint function anyone can call.

**What this unlocks.** The next lesson takes the guarantee one layer down. Everything above is a
statement about what the *compiler* accepts — and a compiler is something you run on your own
machine, on source code, before you deploy. That would be worth very little on a public network where
anybody can publish bytecode nobody compiled. Move's answer is a bytecode verifier that re-checks
resource, type and reference safety at publish time, so the guarantee holds against modules the
honest toolchain never touched.<Cite src="move-language-repo" /> The EVM has no equivalent, and the
consequences of that asymmetry run through everything you know about verifying deployed contracts.
