You want to know whether a deployed contract does what its team says it does, so you open the
explorer, click through to the source tab, and read. Sometimes the tab says "unverified" and you
shrug, or you decompile, or you decide not to integrate.

Sit with what that workflow actually is. Somebody recompiled a source tree with a specific compiler
version and specific settings, the resulting bytecode matched what is on chain, and now you are
reading source that is *evidence about* the bytecode. The chain itself has no opinion. The EVM
accepted that bytecode without asking where it came from, and it will execute it whether or not any
source exists anywhere in the world.

Every guarantee from the last lesson — a coin cannot be duplicated, a resource cannot be silently
dropped — was described as something the *compiler* enforces. If Move stopped there, it would be
worth almost nothing on a public network. Anyone can skip the compiler.

## The verifier is a second checker, and it runs on the bytecode

Move's answer is that the compiler is not the last line. The bytecode itself is checked, by a
component whose own documentation describes it as "a static analysis tool for rejecting invalid Move
bytecode" that "checks the safety of stack usage, types, resources, and
references".<Cite src="move-bytecode-verifier-readme" /> This check happens on the module being
published, not on any source that may or may not accompany it. A recent paper on the Move VM states
the same property from the runtime's side: the VM "statically verifies foundational safety properties
like type safety and reference safety at code loading time".<Cite src="move-runtime-safety-paper" />

The unit of work is a function body. Each function in a compiled module is verified separately, while
trusting the correctness of the function signatures declared in that module; checking that each
signature matches its definition is described as a separate
responsibility.<Cite src="move-bytecode-verifier-readme" /> Then each body goes through a sequence of
phases.

**Subgoal: control flow first, because everything else depends on it.** The instruction sequence is
decomposed into basic blocks, each a contiguous run of instructions ending in a branch or a return,
with the decomposition guaranteeing that branch targets land only at the beginning of some
block.<Cite src="move-bytecode-verifier-readme" /> That last guarantee alone rules out the family of
jump-into-the-middle-of-an-instruction tricks that the EVM's flat bytecode and dynamic `JUMP` force
you to reason about with jumpdest analysis.

**Subgoal: stack discipline, checked as an invariant.** If the stack height is *n* when a function
starts, valid bytecode must maintain the invariant that execution arrives at the beginning of any
basic block with stack height *n*, and at a return instruction with height *n* plus *k*, where *k* is
the number of return values.<Cite src="move-bytecode-verifier-readme" /> The analysis computes the
effect of each instruction on the height and rejects anything that violates
this.<Cite src="move-bytecode-verifier-readme" />

**Subgoal: types, inferred rather than trusted.** The types of local variables are already present in
the bytecode, but the types of stack values are *inferred* — modelled as a stack of types pushed and
popped as the block's instruction stream is processed — and every operation is checked to be invoked
with arguments of appropriate types.<Cite src="move-bytecode-verifier-readme" /> The bytecode does
not get to assert its own type correctness; the verifier reconstructs it.

**Subgoal: resource safety, which is the lesson's payload.** The rules are concrete enough to quote.
The instructions that copy a local (`CopyLoc`) or store into one (`StLoc`) require that the local's
type is not of resource kind; `WriteRef`, `Eq` and `Neq` require the same of the referenced type; and
at a return instruction, any local whose type is of resource kind must be empty — the value must have
been moved out.<Cite src="move-bytecode-verifier-readme" /> That last rule implies the resource was
either moved to global storage via `MoveTo` or destroyed via `Unpack`, and **both of those are
internal to the module in which the resource is declared**.<Cite src="move-bytecode-verifier-readme" />

Read that last clause twice. It is the bytecode-level restatement of the encapsulation property from
the previous lesson. Not "the compiler will not let you write code that destroys someone else's
coin", but "there is no instruction sequence that destroys someone else's coin", checked before the
module is allowed to exist on chain.

**Subgoal: reference safety, the intricate one.** The goal is that there are no dangling references,
and the README enumerates the shapes: a reference to a local that is then moved or rebound, a
reference to an uninitialised local, a reference to a local returned out of the function, a reference
to a globally published value that is then unpublished.<Cite src="move-bytecode-verifier-readme" />
References are exclusive or shared, the latter read-only, and the analysis constrains how references
may extend one another.<Cite src="move-bytecode-verifier-readme" /> That is a borrow checker
operating on bytecode rather than on source.

## Why this is a different security model, not a better compiler

The comparison worth making is not "Move's compiler is stricter than solc". It is about where the
trust anchor sits.

On Ethereum, [verification is bytecode matching](/c/verification-is-bytecode-matching): a claim that
this source, compiled these ways, produces those bytes. It is genuinely useful and you should keep
doing it. But it is a claim about provenance made by a third party after the fact, it is optional,
and its absence does not stop anything from being deployed or executed. The properties you care about
are properties of source code that may or may not be published.

On a Move chain, a specific set of properties is checked on the artifact that will actually run,
before it is allowed to run, by the network itself.<Cite src="move-bytecode-verifier-readme" /> A
module hand-assembled by an attacker who never touched the Move compiler is subject to the same
checks as one produced by the honest toolchain. The guarantee survives the absence of source entirely
— which is the only condition under which a guarantee about a public chain is worth much.

## The limits, stated by the people who build it

This is where an honest lesson has to slow down, because the strongest version of the claim is not
true and the Move community itself says so.

**The verifier is software.** A 2026 paper from the Aptos side puts it directly: static verification
is complex and evolving, and "like any software, it is not immune to bugs. In a live blockchain
setting, a missed rule violation can translate directly into loss of assets, forged authority, or
unrecoverable corruption of on-chain state."<Cite src="move-runtime-safety-paper" /> Their response
is not to assert harder. It is defence in depth: Aptos "relies on defense-in-depth runtime safety
checks that independently verify the critical invariants during execution, providing protection
against latent verifier bugs and malicious bytecode".<Cite src="move-runtime-safety-paper" />

That is the correct engineering posture and it is also the correct thing for you to internalise. A
static gate in front of execution is a very good idea and it is not a proof. The systems that take it
most seriously are the ones that put a second, independent check behind it.

**The scope is narrow by design.** Function bodies are verified while *trusting* signatures, with
signature-to-definition matching handled separately.<Cite src="move-bytecode-verifier-readme" /> The
verifier is a set of safety properties, not a specification checker. Reasoning about what a module
means — invariants, authorization, economics — is the job of a prover, and the formal work on Move
treats closed-world verification and open-world encapsulation as two separate problems requiring two
separate tools.<Cite src="move-robust-safety-paper" />

<Aside kind="warn">
The verifier is part of a chain's implementation, not a fixed artifact you can pin. The original
reference repository is archived,<Cite src="move-language-repo" /> and each chain ships and evolves
its own copy alongside its own VM.<Cite src="aptos-move-docs" /> When a specific rule matters to you
— exactly which instructions are restricted, exactly what a given ability implies at the bytecode
level — read it from the repository of the chain you are deploying to, at the release you are
deploying against.
</Aside>

An attacker skips the Move compiler entirely and hand-assembles a module. Its bytecode contains a
`CopyLoc` on a local holding a `Coin` — a type declared with `store` and `key` but neither `copy` nor
`drop` — intending to duplicate a coin it was passed. What happens, at which point, and what is the
equivalent story on an EVM chain?

<Answer>
**On the Move chain: rejected at publish, not at execution.** `CopyLoc` requires that the local's type
is not of resource kind, and a struct without `copy` is exactly that.<Cite src="move-bytecode-verifier-readme" /><Cite src="move-book-abilities" />
The module never becomes publishable code. There is no transaction that exploits it, no incident, and
nothing for a monitoring system to detect, because the state where the exploit exists is never
reached. Note also what did *not* protect you: nobody read the attacker's source, because there was
no source.

**On an EVM chain: nothing happens, because there is nothing to reject.** There is no notion of a
resource for the bytecode to violate. An attacker who wants to duplicate a token writes a contract
that increments a balance in a mapping it controls; that is ordinary, valid, deployable bytecode. The
defence is entirely at the application layer — the token contract's own access control on `_mint` —
and if that access control is wrong, the chain executes the exploit exactly as instructed. This is
the [access-control failure](/c/access-control-failure) class, and it is a class only because the
machine has no concept the code could violate.

**The honest caveat.** "Rejected at publish" holds as long as the verifier itself is correct on this
input, which is precisely why Aptos added independent runtime checks against latent verifier bugs and
malicious bytecode.<Cite src="move-runtime-safety-paper" /> The right claim is that an entire class of
attack has to get through a mandatory network-side check first, not that the class is impossible.
</Answer>
</Check>

## Where this pays off

**When you evaluate a chain's security story**, you have a sharper question than "is the language
safe". Ask what is checked *by the network* on the artifact that runs, what is checked by tooling the
developer chose to run, and what is checked by nobody. On the EVM the first bucket is nearly empty.
On a Move chain it holds stack, type, resource and reference safety — and the second bucket still
holds everything else.

**When you read Move code**, the verifier explains ergonomics that would otherwise look arbitrary —
why functions return values you did not expect, why a resource must be explicitly destructured, why
references behave the way they do. These are not conventions. They are the shape of code that passes
an admission check.

**What this unlocks.** The verifier operates on modules, and modules live in storage — and storage is
where the two Move chains stopped agreeing. The next lesson is about the fact that "Move" names a
family rather than a target: Aptos kept Diem's account-rooted global storage with `MoveTo` and
`BorrowGlobal` as first-class instructions,<Cite src="move-bytecode-verifier-readme" /> and Sui
removed global storage outright. The resource model you have just learned transfers between them. The
code that touches storage does not.
