You find a Move package that does something you need — a vesting schedule, a simple order book — and
the README says it is written in Move. You are targeting a Move chain. You clone it, point your
toolchain at it, and it does not build.

Not "it needs a dependency bump". The storage primitives it calls do not exist on your chain.

This is the single most expensive misunderstanding available in this ecosystem, and it comes from a
naming accident. "Move" is a family, in roughly the way "Lisp" is a family. Two production chains
descend from the Diem work, they share the resource model you learned two lessons ago, and they made
opposite decisions about the one thing every non-trivial program touches: where state lives.

## The lineage, and why there is no upstream to point at

Both chains inherit from the same Diem-era language. Neither is a fork of the other, and neither
tracks a common upstream any more: the original `move-language/move` reference repository is a
**public archive** on GitHub.<Cite src="move-language-repo" /> Each chain ships its own compiler, its
own verifier, its own standard library and its own VM, and each documents Move as its own
language.<Cite src="aptos-move-docs" /><Cite src="sui-docs-concepts" />

The practical consequence is that there is no such thing as "the Move docs". There is the Move
Book,<Cite src="move-book" /> which is excellent for the language core — abilities, modules,
generics, references — and is written in the flavour of one chain. There are the Aptos
docs.<Cite src="aptos-move-docs" /> There are the Sui docs.<Cite src="sui-docs-concepts" /> When a
question is about types and values, any of them will do. When a question touches storage, you must be
reading the one for your chain, and a search result that does not tell you which chain it is about is
worse than no answer.

<Aside kind="note">
This extends to versions, and it is why this lesson pins none. The two projects do not even publish
releases in the same *shape*: the Sui repository cuts a continuous stream of CI-tagged builds
alongside named testnet and mainnet tags,<Cite src="sui-releases" /> while the Aptos repository tags
mainnet node releases, testnet node releases and CLI releases as separate
lines.<Cite src="aptos-core-releases" /> Any single version number you carry around in your head is
ambiguous before it is stale. Read the releases page of the chain you are targeting, and read
`--version` off the binary you actually installed.
</Aside>

## Aptos: state lives inside accounts, and the program reaches for it

The Aptos lineage kept Diem's model, and the Move Book's description of it is worth quoting exactly
because the shape is the whole idea: "Structurally, global storage is a forest consisting of trees
rooted at an account address."<Cite src="aptos-move-book-global-storage" />

Two rules fall out of that.

**Addressing is by the pair (address, type).** A resource is not at a slot number and not at a
pointer. It is found by saying *whose* it is and *what type* it is. That is a semantic address, and
it is a large ergonomic difference from anything you have used: on Ethereum you compute
`keccak256(abi.encode(key, slot))` to find a mapping entry, and the result is a number that means
nothing until you know the layout.

**At most one of each type per address.** "Each address can store at most one resource value of a
given type and at most one module with a given name."<Cite src="aptos-move-book-global-storage" />
This makes "does this user have a vault" a direct question with a direct answer, and it makes "this
user has three vaults" a design you must express some other way — typically by putting a collection
inside the single resource.

The operators are five instructions: `move_to`, `move_from`, `borrow_global_mut`, `borrow_global`,
and `exists`.<Cite src="aptos-move-book-global-storage" /> Note the signature shapes. `move_to` takes
a `&signer` — the capability that proves the account authorised this publication — while
`borrow_global` and `exists` take a bare address.<Cite src="aptos-move-book-global-storage" /> The
authorisation to *place* something under an account is a value you must hold; reading is not gated
the same way.

```move
// Aptos-lineage global storage: the module reaches into state by (address, type).
public fun open_vault(owner: &signer) {
    move_to(owner, Vault { balance: 0 });          // publish under the signer's address
}

public fun balance_of(addr: address): u64 acquires Vault {
    borrow_global<Vault>(addr).balance             // fetch by (address, type)
}
```

**How this sits relative to the two models you already know.** It is closer to the EVM than to Solana
in one respect and closer to Solana in the other, and holding both halves is what makes the
comparison useful.

Like the EVM: the program *reaches* for state. The caller does not hand it in. `borrow_global` is a
fetch, in the same sense that `SLOAD` is a fetch, and a function that performs one must declare it
with `acquires`.

Like Solana: the state is [externalised](/c/state-externalized) from the module that defines the
type. A `Vault` does not live "inside the vault contract". It lives under a user's account, and the
module is code that knows how to manipulate values of that type. The mental model where a contract
owns a private heap — which is exactly what a Solidity contract's storage is — does not survive here.

## Sui: there is no global storage, and objects are passed in

Sui went the other way, and its own documentation states the removal outright: "Move on Sui addresses
the scaling issue by not having global storage or its related
operations."<Cite src="sui-docs-move-differences" /> There is no `move_to` to call. There is nothing
to `borrow_global` from.

What replaces it is objects. When objects and packages are stored on Sui they are each given unique
identifiers,<Cite src="sui-docs-move-differences" /> and the `key` ability — the fourth of the four
abilities — now carries a structural requirement: a struct with `key` must have an `id: UID`
field.<Cite src="sui-docs-move-differences" /><Cite src="move-book-abilities" /> The documentation
lists other divergences in the same place: 32-byte addresses for objects and accounts, module
initialisers that run once at publication, and `entry` functions with specific rules for use in
transactions.<Cite src="sui-docs-move-differences" />

```move
// Sui: state is an object with an id, handed to the function by the transaction.
public struct Vault has key {
    id: UID,
    balance: u64,
}

public fun balance_of(vault: &Vault): u64 {
    vault.balance          // no fetch: the caller supplied the object
}
```

**Subgoal: notice what that signature change buys.** Because the objects a transaction touches are
its explicit inputs, the transaction's read and write set is visible *before* execution. That is the
same property Solana obtains by making the client submit a list of accounts with the transaction —
[declared access](/c/sealevel-declared-access) — but reached from an entirely different direction.
Solana gets it from the transaction *format*; Sui gets it from the language and the type system,
because you cannot operate on an object you were not given. The next lesson is about what both chains
do with that property, and it is not the same thing.

### Ownership is a property of the object, and it has five values

This is the part where most secondary material is out of date, so read it from the source. The Sui
docs currently name five kinds of ownership: address-owned, shared, immutable, wrapped, and
consensus-address owned (also called "party").<Cite src="sui-docs-object-ownership" />

The reason ownership belongs in a lesson about the storage model, rather than only in a lesson about
access control, is that it is also a *performance class*. The documentation is explicit: "Address-
owned objects skip consensus, so transactions against them have the lowest latency", while "Shared
objects go through consensus, which adds latency but enables concurrent
access."<Cite src="sui-docs-object-ownership" />

Read that as an architecture constraint rather than a footnote. On Ethereum, whether a piece of state
is shared between users changes your gas costs and your MEV exposure but not the code path the
network runs. Here it changes which protocol handles your transaction. A design that routes every
user action through one shared object has opted into consensus for every action; a design that keeps
per-user state in address-owned objects has opted out of it. That choice is made in your data model,
early, and it is expensive to reverse.

### Why one of them removed global storage at all

It is worth asking why a team would delete the storage model it inherited, because the answer tells
you what the whole design is for. Sui's own framing is that removing global storage "addresses the
scaling issue".<Cite src="sui-docs-move-differences" />

**Subgoal: reconstruct the scaling problem from the Aptos model.** If a module can call
`borrow_global` on an address it computed at runtime,<Cite src="aptos-move-book-global-storage" /> then
nothing outside the execution of that function knows which state it will touch. A scheduler wanting
to run two transactions at the same time has no way to prove in advance that they do not collide. It
can guess, run them, and check afterwards — but it cannot know.

**Subgoal: see the removal as buying a property, not as subtraction.** Taking away the ability to
fetch arbitrary state forces every touched value to arrive as an input. Now the collision question is
answerable by inspection: two transactions conflict exactly when their input object sets overlap on
something mutable. The chain gave up a convenience and bought a static property. That is the same
trade Solana made when it required the client to submit the account list — and it is why the Solana
module frames declaration as [a tax the developer pays](/c/declared-access-is-a-tax) rather than as a
free win.

**Subgoal: notice what it costs.** Sharing becomes expensive by construction. Any state several users
must mutate has to be a shared object, and shared objects go through
consensus.<Cite src="sui-docs-object-ownership" /> A single global counter, a single pool, a single
order book: each is a design decision with a protocol-level price tag that a Solidity developer has
never had to think about, because on the EVM every storage slot is equally shared and equally
sequential and there is no cheaper alternative to compare against.

Two observations that are easy to miss when the chains are studied one at a time.

**The split is not EVM-versus-the-rest.** It runs down the middle of the Move family. Aptos is on the
same side of this line as the EVM; Sui is on the same side as Solana. A reader who learned "alt-VMs
declare their state up front" as a rule of thumb has learned something false.

**Neither column is the safe one.** Fetching gives you flexible, composable code and an execution
engine that must discover conflicts by running. Passing in gives you a schedulable workload and an
application layer that has to plumb every touched object through the call graph and out to the client
that builds the transaction. You met the second cost already in the Solana module; the Move family
lets you see both costs charged on the same language.

## What ports, and what does not

Keep this list. It is the whole practical content of the "two dialects" idea.

**Ports cleanly.** The resource model. Abilities, and the discipline of reading them
first.<Cite src="move-book-abilities" /> Modules, generics, references, and the borrow-style
restrictions the verifier enforces. The habit of treating an asset as a value you must dispose of
rather than a number you must adjust. Everything, in other words, that the first two lessons of this
module were about.

**Does not port.** Every storage operator. The meaning of the `key` ability. The shape of a
transaction and therefore every entry point signature. Standard libraries and framework modules.
Anything about ownership, because one chain has no such concept at the protocol level and the other
has five.<Cite src="sui-docs-object-ownership" /><Cite src="aptos-move-book-global-storage" />

**Diverges further over time.** Both projects extend their dialect independently, and the docs each
describe their own language rather than a shared standard.<Cite src="aptos-move-docs" /><Cite src="sui-docs-move-differences" />
Treat "which chain is this written for" as the first question about any Move code you find, and treat
any answer older than a year with suspicion.

<Aside kind="warn">
**On the size of these ecosystems, stated as a ratio because the counts are not trustworthy.** A
comparison published on 31 January 2026 reports Sui at 954 monthly active developers against Aptos's
465 — roughly two to one — and attributes the figures to Electric
Capital.<Cite src="ambcrypto-move-developer-comparison" /> Treat the *ratio* as the signal and the
absolute numbers as unreliable: the article does not date the underlying snapshot, and
monthly-active-developer counts vary substantially with the counting method and the window. Both
figures are in the hundreds, which is one to two orders of magnitude below the EVM ecosystem on any
published ranking. If a decision of yours turns on this, read the current dashboards
directly<Cite src="developer-report-ecosystems" /> rather than trusting any figure quoted in a lesson,
including this one.
</Aside>

You are designing a per-user savings position — a balance, a lock-until timestamp, and an owner — and
you want it to work on an Aptos-lineage chain and on Sui. Describe the state design on each, then say
what an attacker or an integrator can observe about a transaction *before* it executes in each case.

<Answer>
**On Aptos.** Declare a `Position` struct with `key` and publish it under the user's account with
`move_to`, which requires the user's `&signer`.<Cite src="aptos-move-book-global-storage" /> Functions
that read it call `borrow_global` with the user's address and declare `acquires Position`. Because at
most one value of a given type lives under an address,<Cite src="aptos-move-book-global-storage" />
one position per user comes free — and if the product later needs several per user, the fix is a
collection inside the single `Position`, not a second one beside it. Existence checks are `exists`,
which is a direct answer to a direct question.

**On Sui.** Declare `Position` with `key` and an `id: UID` field, because Sui requires
it.<Cite src="sui-docs-move-differences" /> There is nowhere to publish it *to*; the object is
created and transferred, and it is then address-owned by the user. Functions take `&Position` or
`&mut Position` as a parameter — the transaction supplies it. Several positions per user is the
default rather than an extension, because objects are individually identified rather than keyed by
type.

**What is observable before execution — the interesting half.** On Sui, everything: the transaction
names the objects it operates on, so the read/write set is available to anyone watching, before
execution.<Cite src="sui-docs-move-differences" /> On Aptos, much less: the function may compute the
address it borrows from, so the touched state is a consequence of running the code, not a declaration
in the transaction.

**Why that difference matters more than it looks.** It is the same axis Solana sits on with
[declared access](/c/sealevel-declared-access), and it decides what the scheduler can know in
advance. An engine that can see conflicts before executing can plan around them; an engine that
cannot must discover them by running. That is exactly the fork in the road the next lesson is about,
and you have just derived which side each chain is on from its storage model alone.

**And the ownership consequence.** On Sui, if this position must be touched by anyone other than its
owner — a keeper, a liquidator — it probably has to become a shared object, which routes it through
consensus and gives up the low-latency path.<Cite src="sui-docs-object-ownership" /> On Aptos there is
no such protocol-level distinction to give up. That is not one chain being better; it is a cost that
is visible and payable on one chain and invisible and unavailable on the other.
</Answer>
</Check>

## Where this pays off

**Immediately, in how you read.** Before you evaluate any Move claim, code sample, audit report or
tutorial, establish which chain it targets. If it cannot be established, discard it. The core
language material is shared; the storage material is not, and storage is where the bugs and the
architecture decisions live.

**In how you scope a port.** "We will move our Move code from one chain to the other" is not a
dependency upgrade. The resource logic survives; the storage layer, the entry points and the client
are rewrites. Scope it that way from the start.

**What this unlocks.** You now have three storage models side by side: Solana's externalised accounts
declared by the client, Aptos's account-rooted global storage reached by the program, and Sui's
objects handed in as transaction inputs. The next lesson uses exactly this to explain why three
chains that all claim "parallel execution" mean three genuinely different mechanisms by it — declare
and lock, execute and retry, or partition by ownership and skip consensus — and what each one does to
your users when a single piece of state gets hot.
