Here is the first sentence of EIP-7928's motivation section:

> Transaction execution cannot be parallelized without knowing in advance which addresses and
> storage slots will be accessed.<Cite src="eip-7928" />

Now here is the equivalent line from the Solana design note published in 2019: the reason Solana can
process transactions in parallel is that its transactions describe all the states a transaction will
read or write while executing.<Cite src="solana-sealevel-note" />

Same claim. Same reasoning. Roughly seven years apart, in ecosystems that are usually written about
as rivals.

This lesson is about that convergence, and about being precise regarding what actually converged —
because the two designs put the declaration in different places, get different second-order benefits
from it, and enforce it by completely different means. The point is not that Ethereum is copying
Solana. It is that there is a constraint underneath both, and once you can see the constraint you can
predict what any chain claiming parallel execution must have paid for it.

## What a block-level access list is

A BAL records all accounts and storage locations accessed during block execution, along with their
post-execution values.<Cite src="eip-7928" />

Mechanically: a new header field `block_access_list_hash` holds the Keccak-256 hash of the
RLP-encoded list. The list itself is *not* in the block body — execution clients store BALs
separately and transmit them as a field in the `ExecutionPayload` over the engine
API.<Cite src="eip-7928" />

The encoding follows the pattern address, then field, then block access index, then change. Per
account it records storage changes, storage reads, balance changes, nonce changes and code changes,
and the block access index is a `uint32` where 0 means pre-execution, 1 through n identify
transactions, and n+1 means post-execution.<Cite src="eip-7928" />

The inclusion rules are strict in a way that repays reading. The list must include addresses touched
by `BALANCE`, `EXTCODESIZE`, `EXTCODECOPY` and `EXTCODEHASH`; the targets of `CALL`, `CALLCODE`,
`DELEGATECALL` and `STATICCALL` even if they revert; senders and recipients even for zero-value
transfers; `SELFDESTRUCT` beneficiaries; withdrawal recipients regardless of amount; and precompiles
when called. Addresses with no state changes must still appear, with empty change
lists.<Cite src="eip-7928" />

And one negative rule that says everything about how the two mechanisms relate: entries from an
EIP-2930 access list must **not** be included automatically — only addresses and slots actually
touched during execution are recorded.<Cite src="eip-7928" />

Read that as the spec quietly disowning the older mechanism. [The 2930 access list](/c/access-list)
is a statement of intent and is allowed to be wrong; the BAL is a statement of fact and is not.

## Three places the two designs differ

### Who declares, and when

On Solana the declaration is an **input**. The person building the transaction writes the account
array, orders it into the four permission groups, and signs over it; the runtime reads the read/write
set straight off the wire before executing anything.<Cite src="solana-docs-transaction-structure" />
The user's wallet is party to it.

On Ethereum the declaration is an **output**. Nobody constructing a transaction declares anything
new. The block builder executes the block, observes what was touched, and emits the BAL; every other
client re-derives it and checks the hash in the header. The BAL is a *consequence* of execution
that is then published so that the *next* execution of the same block can be planned.

That difference is the reason this can ship at all. Requiring every user to declare their read/write
set would break every wallet, every dapp and every contract that decides where to write based on what
it computes — which is most of them. Moving the declaration to the block asks nothing of users and
everything of proposers, and proposers are a small set of sophisticated operators who can absorb it.

It also caps what the mechanism can deliver. A transaction-level declaration lets you reject a
transaction before executing it. A block-level one only tells you how to schedule a block you have
already been handed.

### What gets carried

Solana's account list carries keys and permission flags. Nothing else — the permissions are the
positions in the array, and the payload is 32 bytes per account.<Cite src="solana-docs-transaction-structure" />

A BAL carries post-execution *values*. The EIP is explicit that this is deliberate: storing
post-execution values for writes enables state reconstruction during sync without individual proofs
against the state root.<Cite src="eip-7928" /> That is a completely different second-order benefit
from anything Solana gets out of its account list, and it is the one worth noticing — the EIP lists
parallel disk reads, parallel transaction validation, parallel post-state root calculation, and
"executionless state updates" as what BALs enable.<Cite src="eip-7928" />

Executionless state updates means a syncing node can apply a block's effects by reading the BAL
rather than by re-running the block. Ethereum is not only buying parallelism here. It is buying a
sync mode.

### How it is enforced

Solana enforces by **expressibility**. An instruction references accounts by index into the message's
account array, so an account that is not in the array cannot be
named.<Cite src="solana-docs-transaction-structure" /> Under-declaring is not a violation; it is a
sentence you cannot write.

Ethereum enforces by **validity check**. Contracts may still touch whatever they like at runtime.
What is checked is that the published list matches what execution actually did, via the header hash —
a mismatch makes the block invalid.<Cite src="eip-7928" />

The spec also has to defend against a proposer who declares reads that never happen, in order to
force other clients into wasteful prefetching. Because storage reads are not mapped to specific
transaction indices, their validity is only confirmable after executing everything, so clients are
advised to run a gas-budget feasibility check at transaction boundaries:

```text
G_remaining  >=  R_remaining * 2000
```

where `R_remaining` is the number of declared reads not yet accessed and 2000 is the minimum gas
cost of a storage read via an access list — 1900 upfront plus 100 warm. If the invariant fails, the
block can be rejected immediately, and the check is suggested every eight
transactions.<Cite src="eip-7928" />

There is no equivalent problem on Solana, because there is no proposer-authored list to lie in.
Different enforcement point, different attack surface.

## The numbers, and what they are worth

The EIP publishes its own overhead analysis, and the figures are worth carrying because they set the
scale of what is being traded.

**Size.** The rationale cites roughly 70 KiB average BAL size from historical data, and gives a
compressed breakdown at a 60 million block gas limit totalling about 72.4 KiB: storage writes 40.3%,
storage reads 25.8%, account addresses with diffs 10.7%, balance diffs 9.2%, RLP overhead 6.1%,
touched-only addresses 4.8%, code diffs 1.6% and nonce diffs 1.5%. It notes this is smaller than
current worst-case calldata blocks.<Cite src="eip-7928" />

**Headroom.** The list is bounded by the block gas limit rather than a fixed item count:

```text
bal_items  <=  block_gas_limit // ITEM_COST     where ITEM_COST = 2000
```

with `bal_items` being total storage keys plus unique addresses. The constant is set deliberately
below the cheapest way to add an item — a cold `SLOAD` at `COLD_SLOAD_COST`, 2100 — so that a buffer
exists.<Cite src="eip-7928" /><Cite src="eip-2929" />

**The payoff estimate.** This is the number to actually think about: 60-80% of transactions access
disjoint storage slots, and the remaining 20-40% can be parallelised through the post-transaction
state diffs.<Cite src="eip-7928" />

Hold that against the Solana side, where the equivalent statistic is not "how many transactions
happen to be disjoint" but "how many transactions were *built* to be disjoint" — and where the
scheduler's constraint is a 12 million compute unit cap on any single writable account against a
100 million CU block, so that one contended account can consume 12% of a block and no
more.<Cite src="solana-100m-cu-blocks" />

Those are not comparable numbers, and resisting the urge to compare them is part of the lesson. One
is an empirical property of existing traffic on a chain that never asked for disjointness. The other
is a designed ceiling on a chain that did. What they share is the direction of the mechanism.

## There is no third option, and that is the actual claim

Step back from both chains and the general statement is short: **a runtime cannot execute two
transactions concurrently unless it knows, before running them, whether they conflict.** Everything
else is where you put the cost of finding out.

There are four answers in production, and every one of them pays somewhere:

The fourth row is worth a moment, because you already met it. [UTXO parallelism](/c/utxo-parallelism)
gets concurrency for free — two transactions spending different outputs cannot conflict, and no
declaration is needed, because the model has no shared mutable object to contend over. That is the
cleanest solution to this problem anyone has, and the reason it is not the universal answer is that
"no shared mutable object" is also a description of what a smart contract platform is for.

Which reframes the account model in a useful way. Ethereum's account model was chosen partly *because*
it gives shared mutable state, and shared mutable state is what forces the declaration question in
the first place. Solana kept the account model and answered the question up front. Ethereum kept the
account model, deferred the question for a decade, and is now answering it at the block.

<Check type="explain" concept="parallelism-requires-declaration">
A team is designing a new L1 and wants parallel execution. They propose: keep the EVM exactly as it
is, keep per-transaction access lists optional as EIP-2930 defines them, and have the client run
transactions concurrently whenever their access lists are disjoint.

Say what breaks, then say which of the four approaches above they have accidentally chosen, and what
they would have to change to make their original idea sound.

<Answer>
**What breaks: the lists are not binding.** EIP-2930's own summary says accesses outside the list
are possible, they merely become more expensive.<Cite src="eip-2930" /> So two transactions with
disjoint declared lists can still collide on undeclared state — a cold `SLOAD` of a slot nobody
mentioned is a legal operation costing 2,100 gas, not an error.<Cite src="eip-2929" /> Schedule them
concurrently and you get a race between two executions writing the same slot, resolved by whichever
finished last. On a blockchain that is not a performance bug. Two clients can resolve the race
differently, produce different state roots, and split the network — a consensus failure with a
data-race as its root cause.

**Which approach they actually chose: none, cleanly.** They picked the ergonomics cost of declaration
— developers now have to write access lists to get scheduled — while keeping the discovery semantics
that make declaration meaningless. The worst square of the matrix: they pay for the guarantee and
do not receive it.

**What would fix it, and each fix names a row in the table.**

*Make the list binding.* Touching state outside the declared list becomes an error rather than a
surcharge. This is Solana's answer, and it costs exactly what Solana pays: contracts can no longer
choose at runtime which storage to touch, so every existing contract that branches on state breaks.
That is why nobody proposes it for an existing EVM chain.

*Move the declaration to the block and check it after the fact.* This is EIP-7928. Users declare
nothing, the proposer publishes what execution actually touched, and the header hash makes a wrong
list an invalid block.<Cite src="eip-7928" /> It costs proposer work and around 70 KiB of
bandwidth per block, and it requires the new defence against proposers declaring phantom
reads.<Cite src="eip-7928" />

*Keep discovery and add conflict detection.* Execute optimistically, detect read/write conflicts as
they occur, and re-execute the losers. This asks nothing of developers and pays for it in wasted
execution precisely when contention is highest — [Block-STM](/c/aptos-block-stm) is the
production example.

**The one-line rule to carry.** Concurrency is bought with knowledge of the access set, and knowledge
is bought from the developer, from the proposer, or from wasted work. A design that names no seller
is a design that has not paid.
</Answer>
</Check>

## What this unlocks

You have finished the module that the rest of Track 12 rests on, and it is worth stating what
actually changed.

**You can read the account model as a chain of consequences rather than a list of facts.** State
lives outside the program, so state objects are individually addressed. Individually addressed
objects can be enumerated, so a transaction can declare its read/write set. A declared read/write
set can be scheduled, so transactions can run concurrently. Every awkwardness — program derived
addresses instead of mappings, rent deposits instead of free permanent storage, client-side account
resolution, ceilings on the account list — is a payment against that last line.

**You have a test for any chain that claims parallel execution.** Ask who supplies the access set and
what they were charged for it. The answer is always one of four, and if a project cannot name theirs,
either the parallelism is not real or the cost has not been found yet.

**And the EVM should look different now.** Private contract storage is not the shape execution
naturally takes; it is a decision, and its consequences run all the way from "you cannot enumerate
token holders without an indexer" to "the L1 cannot schedule two transactions at once". EIP-7928
exists because that second consequence became expensive enough to pay to undo.<Cite src="eip-7928" />

The rest of this track puts the model to work. The next module takes the scheduler, the compute
budget and the fee market apart in detail; after that come Anchor and the constraint system that
generates the account checks this module kept gesturing at, the low-level frameworks that strip them
away again for compute, the token programs, and the vulnerability taxonomy that exists entirely
because the caller picks the accounts. Then Move and Cosmos, which answer the same questions with
different machinery — including the one answer that removes shared mutable state rather than
scheduling around it.
