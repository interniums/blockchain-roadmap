Pull apart a Solana transaction on the wire and the first surprise is how little of it is
instructions.

A transaction is an array of 64-byte signatures and a message. The message is a three-byte header, an
array of 32-byte account addresses, a 32-byte recent blockhash, and an array of compiled
instructions.<Cite src="solana-docs-transaction-structure" /> Each compiled instruction is startlingly
thin: an index into the account array naming the program, a list of *indices* into the same array
naming its accounts, and the instruction data.<Cite src="solana-docs-transaction-structure" />

Not addresses. Indices. One byte each.

That encoding decision is the whole subject of this lesson, because it forecloses something. An
instruction cannot name an account that is not already in the message's account array — there is no
syntax for it. The set of accounts a transaction can touch is fixed before a single instruction runs,
and it is fixed by the person who built the transaction, not by the code that will execute.

## Permissions live in the ordering

Look at the header. It has exactly three `u8` fields: `num_required_signatures`,
`num_readonly_signed_accounts`, and `num_readonly_unsigned_accounts`.<Cite src="solana-docs-transaction-structure" />

Three bytes. That is the entire permission model for a transaction that may reference dozens of
accounts. It works because the account array must be in a strict
order:<Cite src="solana-docs-transaction-structure" />

1. Signer and writable
2. Signer and read-only
3. Non-signer and writable
4. Non-signer and read-only

The three counts partition the array into those four groups, so every account's permissions are
determined by its position — no per-account metadata flags are stored at
all.<Cite src="solana-docs-transaction-structure" />

Sit with the shape of that. Whether an account is *writable* is not an assertion your program makes,
or a property the runtime discovers, or a flag on a field. It is where the address sits in a sorted
list, decided by the client, signed over by the user, and readable by anyone holding the raw bytes
without executing anything. When the program finally runs, the runtime hands it that answer as a
single byte per account in the serialized parameter buffer: `is_signer`, then
`is_writable`.<Cite src="solana-docs-account-runtime" />

The consequence the runtime cares about: **the complete read/write set of a transaction is known
before execution begins.** Not estimated. Not usually correct. Known, because it is the only way the
transaction can refer to anything.

## This is not an access list, and the difference is the whole point

You have met a list of accounts and storage keys attached to a transaction before. It is worth being
precise about why [the EVM access list](/c/access-list) is a different mechanism wearing similar
clothes.

EIP-2930 adds a transaction type carrying a list of addresses and storage keys the transaction
*plans* to access, and those entries are added to the accessed sets that EIP-2929
introduced.<Cite src="eip-2930" /><Cite src="eip-2929" /> The summary sentence in the EIP is the one
to memorise: accesses outside the list are possible, but become more
expensive.<Cite src="eip-2930" />

Possible. The list is a prepayment, priced at `ACCESS_LIST_ADDRESS_COST` of 2,400 and
`ACCESS_LIST_STORAGE_KEY_COST` of 1,900 per entry, and its stated motivation was to let transactions
pre-specify and pre-pay for accounts and slots so that the repricing in EIP-2929 would not break
contracts that had become stuck.<Cite src="eip-2930" /> It is a gas mechanism. A transaction with an
empty access list may touch a thousand slots; it just pays 2,100 rather than 100 for each cold
one.<Cite src="measured-gas-constants" />

So the EVM still *discovers* what a transaction touched by running it. The access list changes the
price of discovery, not the fact of it.

On Solana there is nothing to discover. Omit an account from the list and the instruction cannot
reference it; there is no index that points to it. The declaration is not a hint that earns a
discount — it is the only naming mechanism that exists.

## What the runtime does with the knowledge

The original design note explains the idea by analogy to an operating system call you may have used.
`readv` and `writev` tell the kernel ahead of time all the memory the caller wants to read or write,
which lets the OS prefetch, prepare the device, and execute the operation concurrently if the device
allows it. On Solana each instruction tells the VM which accounts it wants to read and write ahead
of time, and the stated optimisation is: sort millions of pending transactions, then schedule all the
non-overlapping ones in parallel.<Cite src="solana-sealevel-note" />

The conflict rule is ordinary reader/writer locking over account keys. Many transactions may hold a
read lock on the same account at once; a write lock excludes everything else. So two transactions
conflict when one writes an account the other reads or writes, and transactions over disjoint
accounts — or that only read the same account — may
proceed together.<Cite src="solana-sealevel-note" /><Cite src="gridplus-accounts-sealevel-spl" />

Note what is doing the work and what is not. Nothing in the program says "run me in parallel". There
is no annotation, no async keyword, no shard id. Parallelism is a *scheduling* result computed from
the account lists, and a developer's only influence over it is which accounts they declare and which
of those they declare writable.

### Pessimistic, not optimistic — and why the distinction matters

This is the single most common way the model gets mis-taught, so name the alternative explicitly.

There is a second family of parallel execution engines that runs transactions optimistically:
execute them concurrently, watch for read/write conflicts as they happen, and re-execute the ones
that conflicted. [Aptos's Block-STM](/c/aptos-block-stm) is the well-known example, and it needs no
declaration from the developer at all — it discovers conflicts by executing and pays for mistakes
with re-execution.

Solana does the opposite. It takes locks derived from the declared account list and does not
co-schedule conflicting transactions in the first place. Anza's description of the scheduler is
built around exactly that vocabulary: worker threads placing locks — reserving for read or write —
and the redesign was motivated by threads that had no context of what other threads were doing,
producing lock conflicts and stalls.<Cite src="anza-central-scheduler" /> Conflicting transactions
are always processed in priority order, probably on the same execution
thread.<Cite src="anza-central-scheduler" />

Both families get described as "parallel execution" in marketing copy and both deliver concurrency,
but they fail differently and they cost differently. Optimistic execution wastes work under
contention and needs no cooperation from the developer. Pessimistic execution wastes no work and
taxes the developer with a declaration. If you carry one sentence out of this section, carry: on
Solana a state conflict is *avoided before execution*, never *discovered during it*.

<Aside kind="warn">
Be careful with the phrase "Solana's scheduler". The scheduler is client software, not protocol.
Agave's default scheduling algorithm has already been replaced once since the design the blog above
describes, and Firedancer implements its own. Claims of the form "Solana's scheduler does X" are
really "this client's scheduler currently does X" — the account-lock semantics are the durable part,
the packing algorithm is not.
</Aside>

## Declaration is not free

Three separate bills arrive with the account list, and all three shape real designs.

**Bill one: writability is metered.** The validator's pre-execution cost model sums five components —
signature cost, write-lock cost, instruction data cost, program execution cost, and loaded accounts
data size cost — and the write-lock component is charged per writable account at `WRITE_LOCK_UNITS`
of 300 compute units.<Cite src="solana-docs-compute-budget" /><Cite src="solana-docs-constants-reference" />
Marking an account writable "just in case" costs compute units before your program runs, and costs
you concurrency on top.

**Bill two: the list has a hard ceiling.** A transaction may lock at most 64 accounts. The hard
encoding ceiling is 256, since indices are one byte, and a feature raising the enforced limit to 128
exists but is not active.<Cite src="solana-docs-constants-reference" /><Cite src="solana-docs-transactions" /> Separately, the whole
serialized transaction must fit in 1,232 bytes — the IPv6 minimum MTU of 1,280 minus 48 bytes of
network headers.<Cite src="solana-docs-transaction-structure" /> In the legacy format every account
is written out as a full 32-byte key, which bounds a transaction to roughly 32 accounts before it
runs out of bytes, well before the lock limit.<Cite src="solana-docs-versioned-transactions" />

### Counting the bytes yourself

The "roughly 32 accounts" figure is worth deriving rather than accepting, because the derivation
tells you which knob to turn when a transaction will not fit.

**Subgoal 1 — bill the fixed parts.** A single-signer legacy transaction spends a compact-u16
signature count, one 64-byte signature, the three header bytes, a compact-u16 account count, the
32-byte blockhash and a compact-u16 instruction count. Every variable-length array carries that
compact-u16 prefix, which is one byte for counts up to 127.<Cite src="solana-docs-versioned-transactions" />
Call the fixed overhead a little over 100 bytes.

**Subgoal 2 — bill the accounts.** Each one is a full 32-byte public key written out
inline.<Cite src="solana-docs-versioned-transactions" /> Thirty accounts is 960 bytes on its own.

**Subgoal 3 — bill what is left.** Instructions still need their program index, their account-index
list at one byte each, and their data. Against a 1,232-byte
ceiling<Cite src="solana-docs-transaction-structure" /> that leaves room for around thirty-something
keys once a realistic instruction payload is included — which is the "roughly 32" the documentation
quotes.<Cite src="solana-docs-versioned-transactions" />

**Subgoal 4 — read off which knob helps.** Adding a second signer costs 64 bytes, or two accounts'
worth. Adding an account costs 32. So the expensive dimension is *keys*, and that is exactly the
dimension address lookup tables compress.

That byte pressure is why the v0 format exists. An address lookup table is an on-chain account
storing up to 256 public keys; a v0 transaction references entries by one-byte index instead of
spelling out 32 bytes, and the validator resolves the references into full keys before execution
begins.<Cite src="solana-docs-versioned-transactions" /> Two details are worth holding: the resolved
addresses are appended to the static keys and follow the same writable-before-read-only ordering,
and resolution happens *before* execution — so an ALT changes how accounts are spelled, never when
they are known.<Cite src="solana-docs-versioned-transactions" />

<Aside kind="note">
A third format is in the pipeline and it moves in the opposite direction: v1 raises the size limit to
4,096 bytes, carries up to 64 accounts inline, sets resource limits in a message config rather than
through ComputeBudget instructions, and **removes** address lookup
tables.<Cite src="solana-docs-versioned-transactions" /> It is not active on any cluster, activation
is targeted with Agave v4.2, and the underlying proposal, SIMD-0296, is in Review
status.<Cite src="solana-docs-versioned-transactions" /><Cite src="simd-0296" /> Treat it as a
direction of travel, not a thing to build against — and notice that ALTs turn out to have been a
workaround for a size limit rather than a feature.
</Aside>

**Bill three: your program loses a degree of freedom.** This is the expensive one, and it is not
denominated in anything. Because the accounts are fixed before execution, a program cannot decide at
runtime which account to touch — every account it might need must be passed in, which pushes account
resolution into the client and makes dynamic data structures awkward. That is
[the tax on declared access](/c/declared-access-is-a-tax), and it is the reason a Solidity design
that branches into different mappings depending on state does not survive the port.

## Contention is per account, which is the payoff

The last piece: because conflict is decided per account, so is congestion.

A single writable account may consume at most 12,000,000 compute units within one block, a cap that
sits far below the block ceiling.<Cite src="solana-docs-compute-budget" /> When the block limit was
raised from 60M to 100M CU — activated on mainnet at the start of epoch 1009 on 29 July 2026 — that
per-account cap deliberately did **not** move.<Cite src="solana-100m-cu-blocks" /> The upgrade page
draws out the consequence: one hot account could previously take 20% of a block and can now take
12%, so the added capacity is *parallel* capacity. A congested program hits its own ceiling at the
same point, but the block has room for far more unrelated activity
alongside it.<Cite src="solana-100m-cu-blocks" />

<Aside kind="warn">
Two first-party pages disagree here, and the disagreement is instructive. The core docs' compute
budget page still lists `MAX_BLOCK_UNITS` as 60,000,000 and describes SIMD-0286 as a
proposal;<Cite src="solana-docs-compute-budget" /> the upgrade page states the raise activated on
mainnet, names the epoch and date, and gives the feature-gate
pubkey.<Cite src="solana-100m-cu-blocks" /> The upgrade page is the more specific and more recent
claim, and this lesson follows it — but the habit to take away is to check both a constants page and
an activation record before quoting a limit, because reference pages lag feature gates.
</Aside>

That per-account framing is what people mean by local fee markets, and it is where this module hands
off. Whether locality actually holds in practice is a genuinely contested question — the scheduler
orders one global priority queue over shared worker threads and shared block space, and practitioners
disagree about how much a fee war on one account degrades everyone else. The
[local fee markets](/c/local-fee-market) lessons in the next module take that argument apart with
both sides' evidence. What is not contested is the mechanism underneath it: contention is per
account because *conflict* is per account, and conflict is per account because the account list said
so.

<Answer>
**T1 and T2 conflict.** Both take a write lock on `pool_vault`, and a write lock excludes every
other lock.<Cite src="solana-sealevel-note" /> They serialise, in priority order, probably on the
same execution thread.<Cite src="anza-central-scheduler" /> Note that they share `pool_config` and
`token_program` too, and *that* sharing is harmless: both hold read locks, and read locks are
compatible with each other.

**T3 runs alongside either of them.** Its writable set — `carol_token`, `dave_token` — is disjoint
from everything else, and its only shared account, `token_program`, it reads. Note what
`token_program` being read-only buys: if programs had to be write-locked to be invoked, every
transaction touching SPL tokens would serialise against every other one, and the chain would have
roughly one lane. Programs are read-only accounts, which is why they are not a global bottleneck.

**T4 conflicts with T1 and T2, but only because of `pool_vault`.** T4 holds a read lock on
`pool_vault`; T1 and T2 want write locks on it. Read and write are incompatible in either direction,
so T4 cannot run with either of them — though T4 and T3 are fine together.

**So the achievable schedule is:** T1 and T3 together, then T2 — or T4 and T3 together, then T1,
then T2. Which one the leader picks is a packing decision made by client software, not something the
protocol specifies.

**On the developer's question: yes, declaring it read-only matters, in three ways.** First, it is the
difference between T4 conflicting with only the writers of `pool_vault` and T4 conflicting with
every transaction that so much as reads it — read locks are shared, write locks are
exclusive.<Cite src="solana-sealevel-note" /> Second, it is billed: the pre-execution cost model
charges `WRITE_LOCK_UNITS`, 300 CU, per writable
account.<Cite src="solana-docs-compute-budget" /><Cite src="solana-docs-constants-reference" />
Third, it is counted against the 12M CU any single writable account may consume in one
block.<Cite src="solana-docs-compute-budget" /> Marking an account writable when you will not write
it is the Solana equivalent of taking a table lock you never needed: it costs you compute, costs the
account's block budget, and removes concurrency you were entitled to.

**The habit worth exporting.** On the EVM you tune gas after the fact by profiling. Here the biggest
performance lever is a declaration you make in the client before the transaction is signed, and the
question "which of these accounts do I actually write" is a design question with a measurable
throughput answer.
</Answer>
</Check>

## What this unlocks

The claim this module has been building toward can now be stated flat: **externalising state into
addressable accounts is not an aesthetic preference. It is the precondition for declaring a
read/write set, and declaring a read/write set is the precondition for running two transactions at
once.** Every awkwardness in the model — client-side address resolution, the 64-account ceiling, the
inability to iterate — is the price of that one property.

Three doors open from here.

**The engineering door.** The next module takes the scheduler apart properly: how the leader buffers
and packs, why the default algorithm has already changed once and differs by client, what compute
units actually cost, and what "my transaction failed" means on a chain where the common failure is
never being included at all rather than reverting.

**The security door.** You now know that the caller picks every account and marks each one's
permissions. The runtime checks the signatures and the ownership rule and nothing else. Which
account is *the right one* is a question only your program can answer, and
[the three questions to ask of every account](/c/three-questions-per-account) is where that
discipline gets systematic.

**The convergence door.** Ethereum has the same problem — its clients also cannot parallelise
execution without knowing what each transaction touches — and it is arriving at the same requirement
from the other side, with a declaration attached to the block instead of the transaction. That is the
last lesson in this module, and it is the one that stops this track from being a comparison and makes
it an argument.
