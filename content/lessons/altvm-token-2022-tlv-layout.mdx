Search any mature Solana codebase for the number 165 and you will find it. In a helper called
`is_token_account`. In a rent calculation. In an indexer's filter. In a comment explaining why the
filter is safe. For roughly four years that number was not a magic constant but a *fact*: a token
account was 165 bytes, a mint was 82, a multisig was 355, and the length of an account was a complete
and reliable statement of its type.

Token-2022 ends that, and it ends it in a way designed not to break the accounts that already exist.
The base layouts are unchanged — a token account has the same representation in both programs for its
first 165 bytes, and a mint for its first 82.<Cite src="solana-program-token-2022" /> What changes is
that there can now be *more after that*, a variable amount of it, structured as a chain of
type-length-value records. So the old check is not wrong about the accounts it was written for. It is
wrong about the ones it will meet next.

This lesson is the layout, the correct way to read it, and the reason the layout is also the feature:
because the extension records are on the chain, "what can this mint do" is a question you can answer
by reading, before you accept the mint.

## Why the size is a first-class fact here and was not on Ethereum

Notice first how strange this problem would be in the EVM.

Adding a field to a Solidity contract's storage costs nothing structural. Storage is a sparse map
from a 256-bit key to a 256-bit word; every slot already exists, conceptually, and writing to a new
one is an `SSTORE` at the same price as any other. There is no "size of the contract's state" to
allocate, no reason for a caller to know it, and no way to derive the contract's type from it.

A Solana account is the opposite: a buffer of a **fixed allocated length**, chosen when the account
is created, whose lamport balance must cover the [rent-exemption](/c/rent-exemption) deposit for
exactly that length. Because state is [externalised into accounts](/c/state-externalized) rather than
hidden inside a program, the length is public, it costs money, and — before extensions — it was
unique per type. That combination is what made length-based typing so attractive: it was free, it was
correct, and it needed no deserialisation.

The extension model has to add per-mint state without breaking any of that. Its answer is to append.

## The layout

Extension data is written **after the end of a Token-program account, which is the byte at index
165**, and the documentation states the consequence directly: it is therefore always possible to
differentiate mints from accounts.<Cite src="solana-program-token-2022" />

A mint's own data is 82 bytes,<Cite src="solana-program-token-2022" /> but its extensions still begin
past the 165-byte mark, which is why an extended mint and an extended token account can never be
confused for one another by offset alone.

Three details in that picture repay attention, because each is a place where a plausible
implementation goes wrong.

**The account-type byte is not always there.** This is the detail almost every summary omits, and it
is stated flatly in the program's own crate documentation: the `Mint`, `Account` and `Multisig` types
are determined *exclusively by the size of the account* and are **not** included in the account data;
`AccountType` is only included once extensions have been
initialised.<Cite src="spl-token-2022-docsrs-extension" /> The variants are `Uninitialized = 0`,
`Mint = 1`, `Account = 2`.<Cite src="spl-token-2022-docsrs-extension" /> So a Token-2022 mint with no
extensions is 82 bytes with no discriminator, exactly like a legacy mint. Any detector that expects a
type byte at offset 165 will fail on precisely the accounts that look most ordinary.

**The record type is a `u16`, and the enumeration is the menu.** `ExtensionType` is declared
`#[repr(u16)]` and its variants run from `Uninitialized = 0` through `PermissionedBurn = 28` in the
crate documentation read for this lesson, covering `TransferFeeConfig = 1`, `MintCloseAuthority = 3`,
`DefaultAccountState = 6`, `ImmutableOwner = 7`, `NonTransferable = 9`, `CpiGuard = 11`,
`PermanentDelegate = 12`, `TransferHook = 14`, `TokenMetadata = 19`, `ScaledUiAmount = 25` and
`Pausable = 26` among others.<Cite src="spl-token-2022-docsrs-extensiontype" /><Cite src="solana-docs-token-extensions" />
Some variants are mint extensions, some are account extensions, and the documentation is explicit
that mint extensions must only be applied to mints and account extensions only to token-holding
accounts.<Cite src="spl-token-2022-docsrs-extensiontype" />

**There is one deliberate hole in the numbering, and it exists to protect the last length check.**
Multisig accounts are still guaranteed to be 355 bytes, and Neodyme notes the obvious worry — could a
mint or token account with extensions happen to land on 355 and be mistaken for one? It cannot,
because Token-2022 checks for that edge case and adds an additional byte to the
account.<Cite src="neodyme-token-2022" /> The mechanism is visible in the enumeration itself:
`ExtensionType::Uninitialized = 0` is documented as **used as padding if the account size would
otherwise be 355, same as a multisig**.<Cite src="spl-token-2022-docsrs-extensiontype" /> A zero
type-tag exists solely so a size collision cannot happen.

## Reading it correctly

The replacement is not a smarter length check. It is to stop guessing and unpack.

Neodyme's version is three lines and is the whole answer: hand the account data to the program's own
unpacker for the type you expect, and let it fail if the data is not that
type.<Cite src="neodyme-token-2022" />

```rust
use spl_token_2022::{extension::PodStateWithExtensions, pod::PodMint};

pub fn unpack_mint(account_data: &[u8]) -> PodStateWithExtensions<'_, PodMint> {
    PodStateWithExtensions::<PodMint>::unpack(account_data).unwrap()
}
```

Substitute `PodAccount` for `PodMint` for a token account.<Cite src="neodyme-token-2022" /> The point
is not the ergonomics; it is that the type test and the parse are the same operation, so they cannot
disagree. A length check is a claim about the data that nothing verifies.

Once unpacked, the extension list is one call away — the mechanism the rest of the module depends on:

```rust
use spl_token_2022::{extension::{ExtensionType, PodStateWithExtensions}, pod::PodMint};

const ALLOWED_EXTENSION_TYPES: [ExtensionType; 1] = [ExtensionType::DefaultAccountState];

fn assert_mint_extensions(account_data: &[u8]) -> Result<()> {
    let mint = PodStateWithExtensions::<PodMint>::unpack(account_data).unwrap();
    let mint_extensions = mint.get_extension_types().unwrap();
    if !mint_extensions.iter().all(|item| ALLOWED_EXTENSION_TYPES.contains(item)) {
        return err!(Error::InvalidMint);
    }
    Ok(())
}
```

That is Neodyme's own allowlist sketch, published with the recommendation that you should support
mints only with certain extensions.<Cite src="neodyme-token-2022" /> Note the direction: the check is
an **allowlist of extensions you have handled**, not a denylist of ones you have heard of. A denylist
is wrong on the day a new variant is added to the enumeration, and variants have been added — the
newer entries are exactly the ones that older tutorials do not
mention.<Cite src="spl-token-2022-docsrs-extensiontype" />

<Aside kind="note">
Client-side, the same information is available without writing Rust. Offside Labs points to
`getExtensionTypes`, which returns the extensions on a mint, and
`getMinimumBalanceForRentExemptAccountWithExtensions`, which sizes the rent for a token account
carrying them.<Cite src="offside-token-2022-part1" /> The corresponding Rust helper,
`ExtensionType::try_calculate_account_len`, computes the required data length for a set of extension
types — and **fails if any of them has a variable length**, which is a useful signal in itself that
not every extension has a size you can compute up
front.<Cite src="spl-token-2022-docsrs-extension" />
</Aside>

## The second consequence: rent is no longer a constant

The 165-byte assumption has a financial twin, and it is the one that shows up as a production
incident rather than a wrong balance.

Offside Labs's worked example is a helper that returns the cost of opening a token account as a
hardcoded `0.00203928` SOL — the rent for the 165 bytes a Token-program token account
needs.<Cite src="offside-token-2022-part1" /> Point that helper at a Token-2022 mint whose accounts
carry extensions and the amount is **insufficient to cover the extra space**, so account creation
fails outright. Their second observation is the sharper one: if the space is determined by the user
and a backend keeper pays for creation, the keeper can be made to **overpay rent**, which is a
financial loss with a user-controlled magnitude — and their recommendation is to avoid having a
keeper create token accounts for users at all.<Cite src="offside-token-2022-part1" />

Notice why the size is user-influenced rather than fixed per mint. Some mint extensions **require**
matching state on every token account of that mint: the crate exposes
`ExtensionType::get_required_init_account_extensions`, which takes the mint's extension types and
returns the account extension types required at `InitializeAccount`.<Cite src="spl-token-2022-docsrs-extension" />
That is why the enumeration contains paired variants — `TransferFeeConfig` on the mint and
`TransferFeeAmount` on the account, `TransferHook` and `TransferHookAccount`, `NonTransferable` and
`NonTransferableAccount`, `Pausable` and `PausableAccount`.<Cite src="spl-token-2022-docsrs-extensiontype" />
The mint's configuration reaches into the size of every account you create for it.

And some account extensions can be added *after* creation, which makes the size mutable over the
account's life. The Token-2022 extension guide documents `Reallocate`, an instruction that lets an
owner grow their token account to fit room for more extensions, using required-memo-on-transfer as
the worked example of an extension enabled after `InitializeAccount`.<Cite src="solana-token-2022-extensions-ref" />
Offside Labs adds the operational consequence: reallocation charges additional rent for the
additional bytes, so the `payer` parameter on `createReallocateInstruction` and `reallocate` is a
decision about **who absorbs an unbounded cost**, not a plumbing
detail.<Cite src="offside-token-2022-part1" />

## Which extensions are fixed at creation, and what that does and does not guarantee

Here is the property that makes the whole extension model tractable for an integrator — stated
carefully, because the confident one-line version of it is not true.

The Solana documentation's phrasing is that each extension adds state generally initialised during
mint or token account creation, and that **most extensions cannot be added after an account is
initialized** — which it calls an important consideration when designing a token, since you have to
plan ahead for the features you want.<Cite src="solana-docs-token-extensions" /> Neodyme splits it by
side: mint extensions must be applied during mint initialisation and cannot be changed afterwards,
while account extensions can be required by the mint or enabled by the user, and *some* can be added
after account initialisation though most cannot.<Cite src="neodyme-token-2022" /> Offside Labs states
the mint half most strongly: all extensions for a mint account must be initialised before the mint is
created, and once created it is not possible to add new
extensions.<Cite src="offside-token-2022-part1" />

Read those three together and take the honest version: **on the mint side the rule is effectively
firm; on the account side it is per-extension and you must check the specific one.** The practical
consequence for an integrator is the good news of this module — a mint's capability set is readable
at listing time and will not sprout a transfer hook next Tuesday.

Two riders, both of which matter more than they look.

**Extensions constrain each other.** Some combinations are simply not allowed: the documentation gives
`NonTransferable` together with `TransferFeeConfig` as an example of extensions with conflicting
behaviours that cannot be enabled on the same mint,<Cite src="solana-docs-token-extensions" /> and the
crate exposes `check_for_invalid_mint_extension_combinations` for exactly this
purpose.<Cite src="spl-token-2022-docsrs-extension" /> Others are mutually *required*: Offside Labs
records that enabling confidential transfer fee requires both transfer fee and confidential transfer,
and that enabling transfer fee together with confidential transfer requires confidential transfer
fee.<Cite src="offside-token-2022-part1" /> Extension sets are not free combinations, which slightly
shrinks the space you have to reason about.

**Fixed at creation is not the same as immutable.** A mint carrying `MintCloseAuthority` can be
closed, and a new mint initialised at the same address with a different set. That is the subject of
lesson six, and it is the reason the reading you do at listing time has an expiry date. Hold the
thought; do not let "set at creation" harden into "permanent" in the meantime.

<Check type="spot-bug" concept="extensions-are-tlv-state">
An indexer written in 2023 classifies accounts owned by either token program with this function, and
has run without incident for two years.

```rust
fn classify(owner: &Pubkey, data: &[u8]) -> Kind {
    if owner != &TOKEN_PROGRAM && owner != &TOKEN_2022_PROGRAM {
        return Kind::Other;
    }
    match data.len() {
        82  => Kind::Mint,
        165 => Kind::TokenAccount,
        355 => Kind::Multisig,
        n if n > 165 => match data[165] {
            1 => Kind::Mint,
            2 => Kind::TokenAccount,
            _ => Kind::Other,
        },
        _ => Kind::Other,
    }
}
```

Three things are wrong with it. Find them, and say which one produces silently wrong data rather than
an obvious gap.

<Answer>
**Wrong thing 1 — the `355` arm can swallow a mint or a token account, except that it cannot, and the
author did not know why.** The arm is accidentally safe: Token-2022 checks for the case where an
extended account's size would otherwise be 355 and adds an additional byte, so no mint or token
account ever lands there.<Cite src="neodyme-token-2022" /> The mechanism is
`ExtensionType::Uninitialized = 0`, documented as padding used when the size would otherwise equal a
multisig's.<Cite src="spl-token-2022-docsrs-extensiontype" /> The defect is that the code depends on a
property it never states; the correct version does not need the special case because it does not
classify by length at all.

**Wrong thing 2 — `n > 165` reads `data[165]` as an account type on accounts that do not have one.**
`AccountType` is present only once extensions have been
initialised.<Cite src="spl-token-2022-docsrs-extension" /> An account longer than 165 bytes for any
other reason — including a non-token account that slipped past a weaker owner check, or a future
layout — has an arbitrary byte at that offset, and the `1`/`2` match will occasionally hit by chance.
One in 128 such accounts is misfiled as a mint or a token account rather than falling into
`Kind::Other`.

**Wrong thing 3, and the one that silently corrupts data — the `82` and `165` arms are checked
first.** These arms encode "length is type", and the premise is now false: the base layouts are shared
for the first 165 and 82 bytes,<Cite src="solana-program-token-2022" /> so any account of one of those
lengths is classified without a single byte of its contents being validated. Compare the failure
modes: arms 1 and 2 produce records that are absent or obviously junk, which someone eventually
notices. This one produces records that look *entirely normal* and are attached to the wrong entity.

**The fix is not a fourth arm.** Drop the length matching and unpack:
`PodStateWithExtensions::<PodMint>::unpack` for a mint and `PodStateWithExtensions::<PodAccount>::unpack`
for a token account, treating a failed unpack as "not that type".<Cite src="neodyme-token-2022" />
That makes the type test and the parse a single operation, and it gives you
`get_extension_types()` on the same value — which is the thing the indexer actually wants and cannot
get from a length.<Cite src="neodyme-token-2022" />
</Answer>
</Check>

## What this unlocks

**A detector you can trust, and a rule that generalises past tokens.** Unpack, do not measure. The
[account-type-confusion](/c/account-type-confusion) class you met in the security material is the
same defect one level up, and Token-2022 is where it stops being a theoretical concern and becomes an
everyday one, because the ecosystem now routinely produces accounts whose length carries no type
information.

**A rent discipline.** Never hardcode a size or a rent-exempt amount for an account you create on
behalf of somebody else, and know who pays when an account grows. Compute the length from the
extension set,<Cite src="spl-token-2022-docsrs-extension" /> and treat a keeper that creates accounts
for users as a cost surface with a user-controlled input.<Cite src="offside-token-2022-part1" />

**And the capability that the rest of the module is built on.** `get_extension_types()` on an
unpacked mint is a complete, on-chain, enumerated answer to "what will this token do inside my
transfer" — the question ERC-20 cannot answer at all. Every remaining lesson is a specific entry in
that list: what it lets an issuer do, what it does to your integration, and what you would have to
write to support it.

The next one takes the entry that has already cost the most money on the other chain. With
`TransferFeeConfig` enabled, the amount that leaves the sender and the amount the recipient can spend
are different numbers, and the difference sits inside the recipient's own account.
