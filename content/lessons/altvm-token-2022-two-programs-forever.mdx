A support ticket, of the kind that arrives about six weeks after a listing. A user says the deposit
screen shows zero. Their wallet shows 4,000 of the token. Your indexer agrees with the wallet; your
program agrees with the deposit screen. Nothing reverted, no transaction failed, and the address your
code is reading is a real, well-formed program-derived address that exists in the sense that you can
derive it — it simply has nothing in it and never will.

The bug is one line, and it is a line nobody reviews: your code derived the user's token account
using the token program id it has hardcoded since 2022. The mint the user holds belongs to a
different program. Same wallet, same mint, different program id in the seed list, different address.
Both addresses are correct. Only one holds money.

This module is about that second program and the behaviours a mint under it can turn on. This lesson
is about the fact that there are two programs at all, and why that structural fact — not any
individual extension — is where most integration bugs start.

## The inversion you are walking into

**On Ethereum, a token is an interface.** ERC-20 specifies function signatures and event shapes.
Anyone can deploy a contract that satisfies them, and what happens inside `transfer` is entirely up
to the author. That is precisely why the [weird-token taxonomy](/c/weird-erc20-taxonomy) exists and
why it can never be finished: it is an empirical catalogue of what implementers actually did, and a
new entry can be deployed tomorrow. You cannot enumerate the behaviours of a thing defined by its
interface, only observe them.

**On Solana, a token is a row in a program's state.** The mint and token accounts are owned by a token
program, and that program contains all the transfer logic there is. Creating a token is not deploying
code; it is calling `InitializeMint` on a program that already exists. There is no per-token
`transfer` implementation to audit, because there is no per-token implementation at all.

That is the setup for Token-2022's interesting move. If behaviour lives in one program, adding
behaviour means either changing that program for everyone or letting each mint declare which of a
**fixed menu** it wants. Token-2022 does the second, and the menu is an enumerated Rust type —
`ExtensionType`, variants numbered as a `u16` — so the set of things a mint can do is finite, listed,
and readable off the chain.<Cite src="spl-token-2022-docsrs-extensiontype" /> That is a real
improvement, and the module will spend seven lessons on why it is smaller than it sounds.

## Why there are two programs and not one upgraded program

The Token program's own documentation states the motivation plainly. Developers arriving with new
ideas had been **forking** the Token program — easy to do, hard to get adopted, because Solana's
programming model requires programs to be named in transactions alongside accounts, which makes
transactions spanning multiple token programs awkward to construct. On top of that, wallets and
on-chain programs have to trust any token program they choose to
support.<Cite src="solana-program-token-2022" />

The stated goal was to add functionality **with minimal disruption to users, wallets and dApps, while
preserving the safety of existing tokens**, and the answer was a new program deployed to a different
address.<Cite src="solana-program-token-2022" /> Note what that does *not* say. The Token program's
own status page says it is considered complete, with no plans to add functionality and changes only
to fix important or breaking bugs;<Cite src="solana-program-token-legacy" /> Token-2022's
documentation adds the matching line — there are no plans to ever add new instructions to
Token.<Cite src="solana-program-token-2022" />

Both programs are finished, in different senses, and both are live. Write the addresses down, because
they are the only reliable way to tell which universe an account belongs to:

```text
Token            TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA
Token-2022       TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb
Assoc. Token     ATokenGPvbdGVxr1b2hvZbsiqW5xWH25efTNsLJA8knL
```

The first two come from the programs' own documentation.<Cite src="solana-program-token-2022" /><Cite src="offside-token-2022-part1" />
The third is the Associated Token Account program, and there is only one of those — it creates
accounts for either token program.<Cite src="solana-program-token-2022" /><Cite src="solana-program-ata" />
Hold that asymmetry; it is the source of the bug in the opening scene.

## The compatibility that makes this dangerous

Here is the part that turns a clean architectural decision into an integration hazard.

Token-2022's functionality and structures are a **strict superset** of Token's, and the instruction
layouts are identical byte for byte. The documentation's worked example: transferring 0.75 tokens in
UI amount on a mint with 2 decimals means an amount of 75, and the `TransferChecked` instruction data
is `[12, 75, 0, 0, 0, 0, 0, 0, 0, 2]` — discriminator 12, then 75 as a little-endian `u64`, then the
decimals byte. That byte string means the same thing to both programs; **to target one program over
the other you change only the `program_id`**.<Cite src="solana-program-token-2022" />

The account layouts line up the same way. A token account has the same representation in both
programs for its first 165 bytes, and a mint for its first 82.<Cite src="solana-program-token-2022" />
Token has 25 unique instructions at indices 0 through 24; Token-2022 supports all of them and adds
new functionality starting at index 25.<Cite src="solana-program-token-2022" />

Now say what that means for a program written against the original.

**Subgoal: identify what breaks loudly.** Almost nothing. Your instruction encoding is already
correct, and your struct offsets are correct for the fields you read. The failure modes you are used
to — a decode error, a panic, an obviously wrong discriminator — mostly do not fire.

**Subgoal: identify what breaks quietly.** The program id. It appears in your derivations, your CPI
target, your owner checks, and the default arguments of the SDK you use. Each is a place where the
code is not wrong so much as *narrowed*: it silently means "the subset of tokens under one program."

**Subgoal: state the consequence.** A partially-compatible interface is worse than an incompatible
one. Neodyme's auditors put it in exactly those terms: the program id differs, the ATA derivation
differs, account sizes are variable, and plain `transfer` fails on several extension sets, which
together make "my code already handles SPL tokens" a trap rather than an
approximation.<Cite src="neodyme-token-2022" />

## The program id is a seed

This is the mechanism behind the opening scene, and it deserves to be spelled out at the level of the
derivation, because it is the one place where two correct-looking answers exist.

The associated token account for a wallet is a program-derived address off the Associated Token
Account program, and the documentation gives the derivation directly: the seeds are the **wallet
address, the token program id, and the mint address**, in that order, and the deriving program is
`ATokenGPvbdGVxr1b2hvZbsiqW5xWH25efTNsLJA8knL`.<Cite src="solana-program-ata" />

Everything you know about [PDAs](/c/pda) applies. Change any seed and you get a different address —
deterministically, immediately, and without any error, because deriving an address is pure arithmetic
that does not consult the chain. So for one wallet and one mint there are two derivable ATAs, one per
token program, and the runtime has no opinion about which one you meant.

Trace the failure precisely:

**Subgoal: what your code computes.** You pass the legacy program id as the second seed because your
constant is named `TOKEN_PROGRAM_ID` and has been correct for years. You get address *A*.

**Subgoal: what actually holds the balance.** The mint is a Token-2022 mint, so the wallet and every
wallet-side tool derived address *B* using the Token-2022 program id. The tokens are in *B*.

**Subgoal: what the runtime tells you.** Nothing. *A* is a valid address. Reading it returns an
account that does not exist, which most client code renders as a balance of zero. Nothing about *A*
is malformed, so there is no error to surface.

**Subgoal: what happens if you write.** Worse. If your code creates *A* on demand — a vault, an
escrow, a "make sure the user has an account" convenience path — you have paid rent to create an
account under the wrong program that will never receive a transfer, and your accounting believes it
has a place to put the user's funds.

The SDK makes the wrong branch the easy one. Offside Labs points out that where an interface serves
both programs, the SPL Token program id is typically the **default parameter**: in the JS
`createAssociatedTokenAccountInstruction`, the `programId` argument defaults to
`TOKEN_PROGRAM_ID`.<Cite src="offside-token-2022-part1" /> An omitted argument is not a decision
anyone reviewed, and it silently picks a universe.

<Aside kind="warn">
The same shape catches DeFi teams specifically. Wrapped SOL exists in both universes: the familiar
`So11111111111111111111111111111111111111112` under SPL Token, and a distinct Token-2022 wSOL at
`9pan9bMn5HatX4EJdBwg9VgCa7Uz5HL8N1m5D3NdXejP`. Offside Labs recorded the second as having very little
trading activity as of September 2024 and recommended that platforms giving SOL and wSOL special
significance **blacklist the Token-2022 wSOL address outright**.<Cite src="offside-token-2022-part1" />
What is stale there is the activity level, not the existence of two addresses; check current usage
before leaning on the "nobody uses it" half of the argument.
</Aside>

## How to ask the question correctly

The fix is not "add Token-2022 support" as a feature flag. It is to stop treating the token program as
a constant and start treating it as **a property of the mint you were handed**.

Every Solana account carries an owner field naming the program that controls it, and for a mint that
owner *is* the answer: it decides which instructions to build, which program to CPI into, and which id
goes into the ATA seed list. So the first thing a token-touching code path does is read the mint
account's owner and carry it forward — not compare a name, not check a symbol, not read a config file.

```text
given: mint address M supplied by a caller

1. read M; take owner(M)                     -> the token program for this mint
2. reject unless owner(M) is Token or Token-2022
3. every derivation for M uses owner(M) as the program-id seed
4. every CPI for M targets owner(M)
5. every account you validate for M must itself be owned by owner(M)
```

Step 5 is the one that gets skipped, and it is the [account-substitution](/c/account-substitution)
check you already met, arriving with a new value to substitute. If you validate the mint's owner but
not the token account's, a caller can hand you a Token-2022 mint alongside a legacy token account, or
the reverse, and your two checks each pass against a different program's state.

Anchor names the distinction for you. Offside Labs's summary is worth memorising as a rule: types
under `anchor_spl::token_interface` are compatible with both programs, types under `anchor_spl::token`
are for the SPL Token program only, and types under `anchor_spl::token_2022` are exclusively
Token-2022. Their recommendation is explicit — use `token_interface` when you intend to support both,
and `token::Token` when you deliberately do not, because using the interface types in a program that
does not actually intend to support Token-2022 produces ambiguity rather than
safety.<Cite src="offside-token-2022-part1" />

## The evidence that the old program is not going anywhere

If you want one fact that settles the "surely everyone migrates eventually" instinct, it is that the
ecosystem spent a major protocol upgrade making the **original** program dramatically cheaper.

SIMD-0266 proposes replacing the implementation behind
`TokenkegQfeZyiNwAJbNbGKPFXCWuBvf9Ss623VQ5DA` with `p-token`, a like-for-like re-implementation that
is `no_std` and uses zero-copy access to instruction and account data. Because it keeps the same
instruction and account layouts, it is a drop-in replacement requiring no client
changes.<Cite src="simd-0266-proposal" /> Solana's upgrade page reports it live on mainnet and is dated
April 2026.<Cite src="solana-upgrades-p-token" />

The measured effect, from that page's own table:

<Aside kind="stop">
**Those are compute units, not gas, and no EVM intuition transfers to them.** Solana meters a
transaction's work in compute units against a per-transaction limit and a per-block budget: no
storage-write price dominating the bill, no cold/warm access distinction, no relationship to the
constants in the EVM gas track. Do not convert, do not compare ratios across the two machines, and do
not carry a CU figure anywhere without the instruction name and the source it was measured under —
including the ones above, which are the Token program's numbers and say nothing about Token-2022's.
</Aside>

The proposal's motivation explains why anyone bothered: about **10% of block compute units** is
consumed by Token program instructions, so cutting that to a fraction returns most of it to other
transactions — the proposal works the arithmetic as 10% of block CUs becoming 0.5%, a 9.5%
block-space gain.<Cite src="simd-0266-proposal" /> The upgrade page frames the outcome as roughly 10%
more total block space.<Cite src="solana-upgrades-p-token" />

<Aside kind="note">
Two cautions. Other write-ups quote the impact against a different denominator — a share of all chain
compute *including votes* — producing a number that is not comparable and must not be merged with
this one. And the precise activation moment is reported inconsistently across secondary sources (an
epoch in one, a month in another, a specific day in a third); the upgrade page's own framing, April
2026 with mainnet activation completed, is the anchor used here.<Cite src="solana-upgrades-p-token" />
</Aside>

Read the shape of that upgrade. The improvement was delivered by **swapping the implementation behind
an existing address**, so every application got it without changing a line. That is the strongest
available signal about the original program's future: it is being invested in, not retired — which
makes "which program owns this?" a permanent question in your code rather than a migration you can
schedule.

<Check type="spot-bug" concept="token-program-id-is-a-seed">
A teammate opens a PR adding Token-2022 support to a vault program. The client-side change is this,
and the test suite passes.

```ts
const TOKEN_2022 = new PublicKey('TokenzQdBNbLqP5VEhdkAS6EPFLC1PHnBqCXEpPxuEb');

async function depositAddressFor(wallet: PublicKey, mint: PublicKey) {
  const mintInfo = await connection.getAccountInfo(mint);
  const isToken2022 = mintInfo.data.length > 82;

  const [ata] = PublicKey.findProgramAddressSync(
    [wallet.toBuffer(), TOKEN_PROGRAM_ID.toBuffer(), mint.toBuffer()],
    ASSOCIATED_TOKEN_PROGRAM_ID
  );

  return { ata, programId: isToken2022 ? TOKEN_2022 : TOKEN_PROGRAM_ID };
}
```

Name every defect, and say why the tests passed anyway.

<Answer>
**Defect 1 — the program id is detected but never used in the derivation.** The seed list hardcodes
`TOKEN_PROGRAM_ID` regardless of what `isToken2022` decided. Because the token program id is one of
the three ATA seeds,<Cite src="solana-program-ata" /> this returns the legacy-universe address for
every mint, then pairs it with the *Token-2022* program id — so downstream code builds a Token-2022
instruction pointed at an account that program does not own. Silent for reads, and expensive for
writes: rent paid to create an account permanently unreachable by transfers of this mint.

**Defect 2 — the type test is a length comparison.** A Token-2022 mint with no extensions is not
longer than a legacy mint, so `data.length > 82` misclassifies it as legacy. The next lesson shows why
length-based typing is broken in general; Neodyme names it as an assumption a decade of correct code
has to unlearn.<Cite src="neodyme-token-2022" />

**Defect 3 — the question was asked of the wrong field.** The mint account's **owner** already states
which program controls it, with no inference. Reading `mintInfo.owner`, rejecting anything that is
neither known program address, and threading that value through the derivation, the CPI target and
every other account check replaces both the heuristic and the branch. There is also no rejection path
at all: an arbitrary account still returns data and the code proceeds.

**Why the tests passed.** They use legacy mints, extension-free Token-2022 mints, or both. Under a
legacy mint defect 1 is invisible because the hardcoded seed is right; under an extension-free
Token-2022 mint defect 2 sends control down the legacy branch, making it right again. The suite
exercises exactly the inputs on which the two bugs cancel. Add one Token-2022 mint with a single
extension and both appear at once.
</Answer>
</Check>

## What this unlocks

You now have the frame the rest of the module needs, and it is deliberately narrow.

**A rule for every token-touching entry point.** The token program is not a constant your codebase
owns; it is a property of the mint a caller handed you, read from that account's owner field and
threaded through every derivation, CPI and account check downstream. Applied consistently, that one
discipline removes the entire class of failure the opening ticket described, at the cost of one field
read.

**The reason the extension model is worth studying rather than avoiding.** Because behaviour lives in
one program and each mint declares which of an enumerated set of extensions it
enabled,<Cite src="spl-token-2022-docsrs-extensiontype" /> "what can this token do to me" is a
question with a readable answer — more than ERC-20 has ever offered. The Solana documentation is
blunt that most extensions cannot be added after an account is initialized, which is what makes the
answer worth reading at listing time.<Cite src="solana-docs-token-extensions" />

**And the reason that is not the end of the story.** The menu includes fees withheld inside the
recipient's account, third-party code invoked on every transfer, an address that can drain any holder
of that mint, and a path by which a mint's rules change after you read them. Each gets a lesson, and
each is a capability and a hazard at once.

The next lesson takes the first structural consequence: if extensions are extra state appended to the
account, Token-2022 accounts are variable-length, and the 165-byte assumption a decade of correct code
was built on stops holding — including in the length check you just found in the
review.<Cite src="solana-token-2022-extensions-ref" />
