Two users open the same screen in the same product and see the same offer: batch your next three
actions into one confirmation, and stop needing ETH to play.

The first user made their address last week. Accepting costs them nothing.

The second user's address is four years old. It is a signer on a treasury multisig. It holds an ENS
name that resolves to it. It sits in three protocols' allowlists that were written by other teams and
cannot be edited. It has token approvals that took a dozen transactions to set up. For this user, "we
will create you a smart account" is not an upgrade. It is a request to abandon an identity.

That difference — not elegance, not gas, not which standard is newer — is the decision this lesson is
about.

## What each road actually changes

**ERC-4337 gives you a different account.** The smart account is a contract at its own address,
deployed by a factory or referenced counterfactually before it exists via `initCode`. When `initCode`
is specified, the operation is aborted if the `sender` address already points at an existing contract,
or if the `sender` address still does not exist after the `initCode` runs.<Cite src="eip-4337" /> The
user's old address is not involved. Everything the new account can do, it does through the
UserOperation pipeline.

**EIP-7702 gives you the same account with code.** The account's code field holds a delegation
designator — `0xef0100` followed by a 20-byte address — and calls to it run the named code in the
account's own context.<Cite src="eip-7702" /> The address does not change. The history does not
change. The approvals do not change. You met the mechanics in the EVM track and the app-layer flow in
[the previous module](/c/detect-delegated-eoa); what matters here is the one-line summary: nothing the
account already had is disturbed.

So the axis is migration cost. Enumerate what is welded to an address before you decide it is cheap to
leave one behind:

- **[ERC-20 allowances](/c/erc20-allowance-model)**, which are stored per owner address and do not
  travel.
- **Membership in other people's contracts** — multisig signer sets, DAO membership, vesting
  beneficiaries, allowlists — most of which you cannot edit and some of which nobody can.
- **Names and reputation** that resolve to the address, on chain and off it.
- **Positions** already open under that address in lending markets, vaults and staking contracts.
- **Every off-chain record** your compliance, support and analytics systems keyed on it.

If that list is empty for your users, a fresh smart account is the simpler thing to build. If it is
not empty, the standard that keeps the address is not a preference — it is the only one that ships.

## They compose, and the specification says so out loud

The most common framing in circulation treats these as rivals waiting for a winner. The ERC-4337
specification does not, and the evidence is structural rather than rhetorical.

**7702 is a dependency of 4337.** The spec's `Requires` header lists EIP-712 and
EIP-7702.<Cite src="eip-4337" />

**There is a reserved factory value for delegated EOAs.** The account creation field is described as
an "Account Factory for new Accounts OR `0x7702` flag for EIP-7702 Accounts", and the rule is explicit:
if the `factory` address is `0x7702`, then the sender MUST be an EOA with an EIP-7702 authorization
designation.<Cite src="eip-4337" /> At the packed level, this is an `initCode` field starting with
`0x7702` right-padded with 18 zeros.<Cite src="eip-4337" />

**The RPC surface carries authorizations.** On networks with EIP-7702 enabled, `eth_sendUserOperation`
accepts an extra `eip7702Auth` parameter.<Cite src="eip-4337" /> A user can be delegated and served in
the same flow.

**And there is a safety rule that only exists because of the combination.** All EIP-7702 delegated
smart-contract-account implementations MUST check that all calls to the initialization function
originate from the `entryPoint.senderCreator()` address.<Cite src="eip-4337" /> That is the fix for a
hazard the EVM track already taught: installing a designator runs no constructor, so initialisation is
a separate call, and a separate call can be front-run. Requiring the caller to be a specific
EntryPoint-derived address closes the window.

Read together: a delegated EOA can point at ERC-4337-compatible account code, be named as the `sender`
of a UserOperation, be validated by the same EntryPoint, be sponsored by the same paymaster, and be
carried by the same bundlers. Same address, same pipeline.

## Where they genuinely differ

Composition is not identity, and two differences survive it.

**A delegated EOA still has a key that outranks its code.** The authority whose signature installed
the designator can sign another authorization pointing at the zero address and clear
it.<Cite src="eip-7702" /> Whatever policy the delegate code enforces, that key can remove the code
enforcing it. A 4337 smart account has no such external override: its rules are the only path in,
because there is no private key that corresponds to a contract address. If your threat model includes
"the user's key is compromised", the two roads give materially different answers, and 7702's answer is
weaker by construction.

**4337's stated ambition is to need no EOA at all.** One of the spec's own goals is to completely
remove any need for users to also have EOAs, as required by both status-quo smart contract accounts
and EIP-7702.<Cite src="eip-4337" /> A delegated EOA is, definitionally, still an EOA with a
secp256k1 key behind it. For a passkey-first or recovery-first product where the user should never hold
a seed phrase, that is a real distinction and not a philosophical one.

Neither point makes one road correct. They mean the comparison has two axes — migration cost and key
model — and that reading either one alone gives a confident wrong answer.

### The third difference is when the code shows up

Both roads break the same check, in opposite directions, and the breakage lands in your backend rather
than in your contracts.

A 4337 account has an address before it has code. The `initCode` field in the UserOperation carries
the factory call that will deploy it<Cite src="erc-4337-docs" />, and the spec's rule around it is
precise: with `initCode` specified, the operation aborts if the `sender` already points at an existing
contract, or if the `sender` still does not exist after the `initCode` runs.<Cite src="eip-4337" /> So
between "the user has an address you can show them" and "the address has code" there is a real
interval, and it can last weeks if the user does nothing. During it, anything that inspects the address
sees an empty account: your analytics, a third-party allowlist, an exchange's withdrawal-address check,
a contract that refuses to send to non-contracts.

A delegated EOA is the mirror image. The address has 23 bytes of code where every historical record
says it had none.<Cite src="eip-7702" /> Anything that concluded "no code, therefore an EOA, therefore
safe to push value to" reaches the opposite wrong answer.

You have met both halves of this already — the
[blurred line between an EOA and a contract](/c/eoa-contract-line-is-blurred) and the
[detection routine that survives it](/c/detect-delegated-eoa). What is new here is that the two
standards put your product on *both* sides of it at once: some of your users are addresses with code
that should not have code, and some are addresses without code that will have code later. A single
`code.length` branch is wrong for both populations, and it is wrong silently.

## The feature neither of them defines

Now the correction that this module exists to deliver, because it is stated wrongly in most
introductory material including material published by people who know better.

**ERC-4337 does not define session keys.**

The ERC-4337 documentation says it in the same breath as the demo: these patterns unlock new UX for
games, dApps and mobile wallets, "though they are not yet standardized and are implemented
wallet-by-wallet."<Cite src="erc-4337-session-keys-docs" />

What 4337 defines is the question: the EntryPoint calls `validateUserOp` and asks the account whether
this operation is acceptable. A session key is one answer an account may choose to give. The
documentation describes two shapes — static delegation, granting a key ongoing permission to act on
the account, which must be explicitly revoked; and dynamic delegation, signing a session token with
constraints such as `validUntil` and `targetContract` — and is direct about where they are enforced:
in `validateUserOp()`, by wallet-specific logic, through plugins or auth modules rather than natively
by the standard.<Cite src="erc-4337-session-keys-docs" />

Three consequences follow, and each one costs somebody a sprint when it is discovered late.

**It is not portable.** A session-key grant that works with one account implementation means nothing
to another. Switching your smart-account vendor is not a config change; it is a re-implementation of
your permission model.

**You cannot feature-detect it by name.** "Supports ERC-4337" tells you nothing about whether scoped
permissions exist, what dimensions they constrain, or whether the constraints are enforced on chain at
all.

**It inherits the validation fence.** Whatever the policy checks, it must survive ERC-7562 — no
`TIMESTAMP`, no reading arbitrary contract storage unstaked, no calling codeless
addresses.<Cite src="erc-7562" /> This is exactly why the time bound shows up as `validUntil` inside
the returned `validationData` rather than as an `if` statement in the validator: the account states
the window, and the EntryPoint checks it.<Cite src="eip-4337" />

### The standards that are trying to fix this are drafts

Two ERCs are the convergence point, and both are worth knowing by shape rather than by detail.

**ERC-7715** defines a JSON-RPC method by which an application asks the wallet for a scoped permission
instead of a signature, with optional constraints expressed as rules, and a response carrying
delegation-manager information. Its status is **Draft**, it was created 2024-05-24, and the method is
named `wallet_requestExecutionPermissions`.<Cite src="erc-7715" />

**ERC-7710** is the on-chain half. Its status is **Draft**, created 2024-05-20, and its interface is
`redeemDelegations(bytes[] permissionContexts, bytes32[] modes, bytes[] executionCallData)`, where the
execution modes come from ERC-7579.<Cite src="erc-7710" /><Cite src="erc-7579" />

Draft means the shape can change and implementations diverge. Build against them by all means; do not
put "supports ERC-7715" in a product commitment, and feature-detect rather than assume.

### And the same pattern works on a delegated EOA

Because a session key is a property of the account's code, and 7702 is a way of giving an existing
address account code, the pattern is equally available without moving addresses. Point the designator
at ERC-7579-style modular account code, install a validator module with the policy you want, and the
account answers `validateUserOp` the same way a factory-deployed smart account
would.<Cite src="erc-7579" /><Cite src="eip-7702" />

This is the whole thesis of the module in one sentence: the capability lives in the account's code,
and both standards are ways of getting code onto an account.

## Talking to either one from the app

The layer that lets your application stop caring which road a user took is ERC-5792.
`wallet_getCapabilities` lets wallets indicate their support for various capabilities including atomic
execution, and `wallet_sendCalls` processes a batch of calls, executing them atomically when
`atomicRequired` is set to true.<Cite src="eip5792-getting-started" />

One detail in the capability response is worth carrying: a wallet can report that it is able to
upgrade to `supported` pending user approval — for example via EIP-7702.<Cite src="eip5792-getting-started" />
The answer to "can you batch?" is not a boolean. It can be "not yet, but ask the user". Any capability
check you write as a two-way branch will mishandle the most interesting case.

<Check type="explain" concept="7702-vs-4337">
Your product has 40,000 existing users on plain EOAs, most with open positions and token approvals.
You want: batched approve-and-act in one confirmation, sponsored gas for the first action of new users,
and a scoped key so a game loop does not prompt on every move.

A teammate proposes shipping ERC-4337 smart accounts for everyone and migrating existing users by
prompting them to move their funds.

Say what you would do instead, and name the one thing your plan does not get you.

<Answer>
**Split the population, because the migration cost is not uniform.**

*Existing users* get EIP-7702. The address, the approvals, the positions and the third-party allowlist
entries stay exactly where they are, because a designator changes the code field and nothing
else.<Cite src="eip-7702" /> A migration prompt sent to 40,000 users with open positions is not a
migration plan; it is a churn event with a support queue attached.

*New users* can go either way, and the deciding question is the key model rather than the standard.
If you want a passkey-first account with no seed phrase, a 4337 smart account is the road that matches
— one of the spec's stated goals is removing the need for users to have EOAs at
all.<Cite src="eip-4337" /> If you want one code path for the whole user base, delegate their EOA too.

**Batching and sponsorship do not force the choice, because they are shared.** A 7702-delegated EOA can
be the `sender` of a UserOperation: the spec reserves the `0x7702` factory value for exactly this and
adds an `eip7702Auth` parameter to `eth_sendUserOperation`.<Cite src="eip-4337" /> Same EntryPoint,
same paymaster, same bundlers, same scoping arithmetic from the previous lesson. Batching can also come
from ERC-5792 without 4337 at all, and the capability response will tell you which wallets can do it —
including the ones that can become able to with user approval.<Cite src="eip5792-getting-started" />

**What the plan does not get you: a portable session key.** Neither road defines one. ERC-4337's own
documentation says these patterns are not yet standardized and are implemented
wallet-by-wallet.<Cite src="erc-4337-session-keys-docs" /> The convergence standards, ERC-7715 and
ERC-7710, are both **Draft**.<Cite src="erc-7715" /><Cite src="erc-7710" /> So the scoped game key is
real work against one account implementation's validator module, and switching implementations later
means writing it again. Budget it as a feature you own, not a capability you adopt.

**The sentence to take to the planning meeting.** The standard choice is decided by whether your users
can afford a new address; the session-key work is decided by nobody, because nobody has standardised
it yet.
</Answer>
</Check>

## Where this pays off

**The session-key module** is next, and it starts exactly where this lesson stops: if the policy lives
in the account's validation logic, then the policy's dimensions — target, selector, value cap, rate,
expiry — are a design you produce rather than a menu you pick from. It also covers the two things this
lesson only gestured at: that expiry is free while revocation is a transaction with a front-running
window, and that where the key material physically sits usually matters more than the policy design.

**The passkey module** is the concrete case of "the signature means whatever the account says". A
P-256 assertion cannot be an EOA key on any curve Ethereum verifies natively, so it can only control
funds through an account that verifies it — which is either a 4337 smart account or a delegated EOA,
which is to say: one of the two roads you just chose between.

**The reflection prompt for this module** is the paymaster arithmetic, and it is worth doing with the
population split above in mind. Sponsoring the first action of a brand-new smart account and
sponsoring the first action of a four-year-old delegated EOA are different risks, because one of those
senders has a history you can price and the other one was created ninety seconds ago.
