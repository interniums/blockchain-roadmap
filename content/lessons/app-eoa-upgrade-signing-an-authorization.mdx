Two products shipped an EIP-7702 upgrade in the same quarter.

The first is a game with its own embedded wallet. It generates a key in the browser, holds it in
process, and when a new player finishes onboarding it signs an authorization pointing that address at
a batch-executor contract the team deployed and audited. The player never sees the word "delegation".

The second is a DeFi front end whose users arrive with MetaMask. It wants the same thing — one
confirmation instead of three — and it cannot do any of the above. It does not hold the key, there is
no standard JSON-RPC method for asking a wallet to sign an authorization on an application's behalf,
and the delegate contract the team would have nominated is not a contract that wallet will install.

Both are EIP-7702. They are not variants of one flow; they are two different products with two
different consent problems, and confusing them is the most common way this feature gets designed
wrong. This lesson covers what your code does in the first case, and what your interface owes the
user in both.<Cite src="eip-7702" />

## The API, and the constraint hiding inside it

viem exposes the tuple through `signAuthorization`. Give it an account and a `contractAddress` and,
by default, it signs over the account's next available nonce and the current chain id:

```ts
const authorization = await walletClient.signAuthorization({
  account: eoa,
  contractAddress: '0xFBA3912Ca04dd458c843e2EE08967fC04f3579c2',
})
// { chainId: 1, contractAddress: '0xFBA…', nonce: 1, r: '0x…', s: '0x…', yParity: 0 }
```

The signed object then rides on a transaction as `authorizationList`, on either `sendTransaction` or
`writeContract`.<Cite src="viem-sign-authorization" /><Cite src="viem-eip7702-contract-writes" /> If
you want the filled-but-unsigned object first — to show a user what they are about to sign, or to
inspect the nonce viem chose — `prepareAuthorization` fills `chainId` and `nonce` and returns the
tuple without a signature.<Cite src="viem-prepare-authorization" />

Now the constraint. The `account` parameter on both actions is documented as accepting a **Local
Account** — a private key, mnemonic or HD account that signs inside your
runtime.<Cite src="viem-sign-authorization" /><Cite src="viem-prepare-authorization" /><Cite src="viem-local-account-doc" />
It is not documented as accepting a [JSON-RPC account](/c/viem-account-kinds), where the key lives in
an external wallet and viem only asks.<Cite src="viem-jsonrpc-account-doc" />

That single line in a parameter list is the boundary between the two products above. If you hold the
key, you can build an authorization. If the user's wallet holds the key, you cannot — and no
amount of library archaeology changes it, because the missing piece is a wallet RPC method that does
not exist, not a viem feature that was overlooked.

So what does the second product do? It asks for the capability and lets the wallet decide how to
provide it. Send a batch with `atomicRequired: true` to an account whose `atomic` capability is
`ready`, and the wallet is obliged to upgrade before submitting — where `ready` means precisely that
the account is an EOA the wallet can upgrade via an EIP-7702 delegation, pending the user's
approval.<Cite src="eip-5792" /><Cite src="eip5792-atomic-capability" /> MetaMask's own walkthrough
of this flow is a wagmi app calling `useSendCalls` with two ordinary calls; the upgrade prompt
appears because the wallet raised it, not because the tutorial requested
one.<Cite src="metamask-7702-upgrade" /> Your app never names a contract.

## Who signs and who pays are different questions

The property that makes 7702 useful for onboarding is that the authorization's signer and the
transaction's sender need not be the same account.<Cite src="eip-7702" /> viem's own overview lists
sponsorship as a headline application: account X pays for a transaction on behalf of account Y,
possibly for free as an application operator including its users'
transactions.<Cite src="viem-eip7702-overview" />

In code, that is a wallet client whose account is your relayer, signing a transaction that carries an
authorization signed by someone else:

```ts
// walletClient.account is the relayer. `eoa` is the user.
const authorization = await walletClient.signAuthorization({ account: eoa, contractAddress })

const hash = await walletClient.writeContract({
  abi,
  address: eoa.address,
  authorizationList: [authorization],
  functionName: 'initialize',
})
```

<Cite src="viem-eip7702-contract-writes" />

Note the target: the transaction is sent *to the user's own address*, which is what makes the
freshly-installed delegate code run in the user's account. And note that this is one transaction —
the authorization list is processed before the execution portion begins, so the delegate is already
installed when the call executes.<Cite src="eip-7702" />

### The nonce, and the one case where it is not obvious

The authorization commits to a nonce belonging to the *authorizing* account. When the relayer and the
user are different accounts, the default is correct and you can stop thinking about it.

When they are the same account — a user sponsoring their own upgrade — the arithmetic shifts by one,
and the reason is a single clause in the specification: the authorization list is processed before
execution begins, **but after the sender's nonce is incremented**.<Cite src="eip-7702" /> The
transaction has already consumed nonce N by the time the authorization is checked, so an
authorization signed over N is now stale and will fail its nonce check, silently, while the rest of
the transaction proceeds.

viem encodes this as a parameter rather than leaving it to you: pass `executor: 'self'` when the
account that signed the authorization will also execute the transaction, and viem accounts for the
difference. Leave it unset and viem assumes a separate relayer.<Cite src="viem-sign-authorization" />

<Aside kind="warn">
Get this wrong and nothing throws. A failed authorization tuple is skipped — processing stops for
that tuple and continues to the next one — while the transaction's own call executes
normally.<Cite src="eip-7702" /> You get a successful receipt, an account that was not upgraded, and
a call that ran against whatever code was there before. Assert on the account's code after the
upgrade; do not assert on `status: 'success'`.
</Aside>

## What the consent screen owes the user

Everything above is mechanism. This half is the part that decides whether shipping it was
responsible.

A 7702 upgrade is not a per-transaction approval. The designator stays in the account until an
authorization naming the zero address clears it, which means one signature changes what the address
can do indefinitely, and reverting it costs a transaction and requires the
key.<Cite src="eip-7702" /> There is no expiry, and no third party who can retire a delegation on the
user's behalf.

Four things a consent surface has to carry, and each one is there because of a specific property of
the protocol rather than because it reads well.

**Name the delegate, and say what it is.** Code reached through the designator executes with the
user's account as `address(this)`, spends that account's balance, and reads and writes that account's
storage — [there is no scope at the protocol level](/c/delegate-is-total-control).<Cite src="eip-7702" /><Cite src="oz-eoa-delegation" />
An address on a screen is not meaningful to a user, but its *absence* is a tell: an interface that
will not say what it is delegating to is asking for consent it has not earned.

**Say what capability it adds.** "Upgrade your account" is not a description of anything. "Lets this
app submit your approval and your deposit as one confirmation" is, and it is also the sentence the
user can check afterwards.

**State the way back.** Revocation is an authorization pointing at the zero address, which resets the
account's code and its code hash to the empty-code hash.<Cite src="eip-7702" /> Two things are worth
saying plainly rather than in a footnote: it is a transaction, so it costs gas and takes time; and it
clears the code field only — [storage written by the old delegate remains](/c/delegate-storage-collision)
and will be visible to whatever is installed next.<Cite src="eip-7702" />

**Name the chain, or admit that you did not.** An authorization's `chain_id` may be the current chain
or zero, and [zero is a deliberate wildcard](/c/chain-id-scoping) that makes the same signed tuple
valid on every EVM chain.<Cite src="eip-7702" /> That is a real feature — one signature, the same
account behaviour everywhere — and it is also a consent problem, because the code living at that
address may differ per chain unless it was deployed deterministically. A user who agrees to a
delegation on one chain and receives it on chains they have never used has consented to a set they
were never shown.

### The clause that ruins the obvious mental model

Most people, told that the upgrade and the first use happen in one transaction, conclude that they
therefore succeed or fail together. They do not.

> if transaction execution results in failure (e.g. any exceptional condition or code reverting), the
> processed delegation indicators is not rolled back.<Cite src="eip-7702" />

The delegation survives the failure of the transaction that installed it. So the sequence "user
approves an upgrade in order to do X, X reverts" ends with the user upgraded and X not done. If your
interface framed the upgrade as a step *within* an action, you have just told them that action
failed, while leaving behind the permanent part of it.

This is a UI requirement, not a trivia item. After any transaction carrying an `authorizationList`,
read the account's code before you decide what to render — the next lesson is entirely about doing
that correctly — and if the delegation landed while the action did not, say both.

### Why this screen is heavier than a token approval

Your reader knows the [ERC-20 allowance model](/c/erc20-allowance-model) and has probably shipped an
approval flow. The instinct is to reuse its language, and the comparison is worth making explicitly
because it fails in the user's disfavour on every axis.

An approval names one token contract and one spender, bounds an amount, and can be reduced to zero by
calling the same function again. A delegation names code that executes as the account, bounds
nothing, and is limited only by whatever restrictions that code chose to impose on
itself.<Cite src="eip-7702" /><Cite src="oz-eoa-delegation" /> Choosing a delegate is a trust
decision of the same order as sharing the private key, which is why the standing advice is to
delegate only to audited wallet infrastructure rather than to application-controlled
code.<Cite src="nethermind-7702-attack-surfaces" /> Research on real 7702 activity has found
delegate contracts reused across incidents and a meaningful share of delegations associated with
criminal activity, which is one team's measurement rather than a settled figure, but it is the right
prior for how this consent gets abused.<Cite src="arxiv-7702-phishing" />

So: a screen that borrows an approval's visual weight has understated its subject by a wide margin,
and the "approve" verb your design system already has is the wrong one. This is the
[blind-signing](/c/blind-signing) problem with a larger blast radius than usual.

<Aside kind="note">
If you *are* the first product — you hold the key and you chose the delegate — two implementation
duties come with it. The delegate must verify that its initial setup calldata was signed by the EOA's
key, because the protocol runs no initcode during delegation and an observer could otherwise
front-run the initialisation with values they control.<Cite src="eip-7702" /> And it should root its
storage layout at a slot derived from a unique identifier, [ERC-7201 style](/c/erc-7201-namespaced-storage),
so a later migration to a different implementation does not collide with what this one
wrote.<Cite src="eip-7702" /><Cite src="slowmist-7702-practices" />
</Aside>

## Worked example: the same upgrade, sponsored and self-paid

The module's practice exercise asks for both. Here is the reasoning that makes the second one work.

**Subgoal 1 — establish which account holds the key.** If it is yours, `signAuthorization` is
available and everything below applies. If it is the user's wallet, stop: the flow is a capability
request and the wallet owns the rest.<Cite src="viem-sign-authorization" /><Cite src="metamask-7702-upgrade" />

**Subgoal 2 — sponsored case, and why the default is right.** Relayer sends, user signs. viem's
default assumption is a separate executor, so the authorization is signed over the user's next
available nonce and nothing about the relayer's nonce is involved.<Cite src="viem-sign-authorization" />
The user needs no ETH, which is the entire onboarding argument for doing it this way.

**Subgoal 3 — self-paid case, and the off-by-one.** Same account signs and sends. The transaction
consumes the sender's nonce *before* the authorization list is processed, so the authorization must
commit to the value after that increment.<Cite src="eip-7702" /> Pass `executor: 'self'` and let viem
do the arithmetic.<Cite src="viem-sign-authorization" />

**Subgoal 4 — prove the upgrade rather than the transaction.** Read the account's code and check it
is the designator naming your delegate. A successful receipt proves the transaction executed; it does
not prove the tuple was accepted, because a rejected tuple is skipped rather than
fatal.<Cite src="eip-7702" />

**Subgoal 5 — exercise the new capability in the same test.** Send a two-call batch through the
delegated account. This is the step that catches a delegate installed at the wrong address, or one
whose initialisation never ran.

**Subgoal 6 — clear it, and check what clearing did not do.** Sign an authorization naming the zero
address, confirm the code is empty and the code hash is back to the empty-code
hash.<Cite src="eip-7702" /> Then read one storage slot the delegate wrote, and observe that it is
still there. That observation is the point of the step.

<Check type="explain" concept="7702-upgrade-consent">
Your team ships an embedded-wallet flow that upgrades a new user's account and, in the same
transaction, calls `initialize` on the delegate to register the user's session policy. The
transaction reverts inside `initialize` because a parameter was malformed.

Say what the on-chain state is afterwards, what your UI is probably showing, what the user's account
can now do, and what the correct recovery step is.

<Answer>
**On-chain state: upgraded, uninitialised.** The authorization list is processed before the execution
portion of the transaction begins, and processed delegation indicators are *not* rolled back when
execution fails.<Cite src="eip-7702" /> So the designator is written and the `initialize` call's
effects are not. The account's code is now `0xef0100` followed by your delegate's address; its
storage is untouched.

**What the UI is probably showing: "setup failed, try again".** That message is true about the call
and false about the account, and the retry button behind it is now doing something different from
what it did the first time — the account is already delegated, so a fresh authorization is redundant
work rather than the operation the user thinks they are repeating.

**What the account can do: whatever your delegate does before it is initialised.** This is the
interesting half and it is entirely your problem, not the protocol's. The delegate is live and
callable by anyone, in the account's context, with no session policy recorded. If its functions do
not gate on an initialisation flag, an uninitialised account is an open account. This is the same
shape as the front-running-initialisation hazard the EIP names: no initcode runs during delegation,
so any setup must be a separate, authenticated call — which means there is always a window in which
the account is delegated and not yet set up.<Cite src="eip-7702" />

**Correct recovery: retry the initialisation, not the upgrade.** Read the account's code first,
recognise the designator, and branch. If the delegate is already the one you wanted, send
`initialize` alone. If the delegate is unexpected — a different address, or one from a previous
version — clearing to the zero address and starting over is the safe path, remembering that clearing
leaves storage behind for the next
implementation.<Cite src="eip-7702" /><Cite src="oz-eoa-delegation" />

**The design lesson.** "Upgrade and use in one transaction" is a gas optimisation, not an atomicity
guarantee, and the specification says so in one sentence that is easy to read past. Any flow built on
it needs a state for *upgraded but the rest failed*, and the only way to know you are in it is to
read the account's code.
</Answer>
</Check>

## Where this pays off

**The next lesson** is the detection half. Every branch above began with "read the account's code",
and doing that correctly is neither `code.length === 0` nor anything you can infer from a receipt.

**The capability module you just finished** is the other route to the same outcome, and it is the one
most products will actually take: ask for atomic execution, let the wallet decide whether to offer
its user an upgrade, and never name a delegate at all.<Cite src="eip-5792" />

**Session keys**, later in this track, are where the delegate's own code starts mattering to you as a
product surface rather than as a dependency. A delegated EOA can point at code that scopes a
secondary key, so the old claim that session keys require moving to a new smart-account address no
longer holds.<Cite src="eip-7702" /> What has not changed is that the scoping is the *account's*
logic: the ERC-4337 documentation states plainly that these patterns are not yet standardised and are
implemented wallet-by-wallet, which is another way of saying you cannot assume a delegate supports
them because it is a smart account.<Cite src="erc-4337-session-keys-docs" />

**Every consent screen you design after this one.** The transferable question is not "is this
signature safe" but *what is still true tomorrow because of it*. A transaction is over when it
lands. A delegation is not, and neither is an unbounded approval — which is why the two belong in the
same category in your interface even though the wallet presents them very differently, and why the
copy you write here is reusable in a way the mechanism is not.
