A note on where this table came from, because it matters for how much you should trust it.

During the research sweep for this curriculum, `docs.soliditylang.org` returned HTTP 403 to
automated fetches, so the panic code table had to be recovered from a secondary aggregation — and
that aggregation was missing `0x00` entirely and worded `0x22` and `0x51` differently from the
normative text. That is the ordinary way this table degrades: blog posts, cheat sheets and answer
sites copy from other copies, and entries fall out.

Re-checked on 26 August 2026 while writing this lesson, the page serves HTTP 200 to a plain `curl`
with no user agent at all — the 403 was transient. So the table below was read directly from the
normative page,<Cite src="solidity-error-handling" /> and then cross-checked line by line against
the file that page is generated from, `docs/control-structures.rst` in the compiler
repository.<Cite src="solidity-docs-src-control-structures" /> Both carry all ten entries, in the
same order, with the same wording — including a stray semicolon after `0x12` in place of a colon,
which is a useful marker that what follows was transcribed rather than remembered.

Ten entries, and at least two of them are missing from most secondary versions:

```text
0x00: Used for generic compiler inserted panics.
0x01: If you call assert with an argument that evaluates to false.
0x11: If an arithmetic operation results in underflow or overflow outside of
      an unchecked { ... } block.
0x12; If you divide or modulo by zero (e.g. 5 / 0 or 23 % 0).
0x21: If you convert a value that is too big or negative into an enum type.
0x22: If you access a storage byte array that is incorrectly encoded.
0x31: If you call .pop() on an empty array.
0x32: If you access an array, bytesN or an array slice at an out-of-bounds or
      negative index (i.e. x[i] where i >= x.length or i < 0).
0x41: If you allocate too much memory or create an array that is too large.
0x51: If you call a zero-initialized variable of internal function type.
```

<Cite src="solidity-docs-src-control-structures" />

`0x00` is the one worth noticing. It is in the normative list and absent from the aggregation the
research pass recovered — and, as the next section shows, absent from at least one shipping client
library's lookup table as well. If you have ever seen a decoder print `Panic` with no explanation,
this is very likely why.

You met [the panic codes](/c/sol-panic-codes) as a compiler behaviour in Track 04. This lesson is
about the two things a client has to do with them, which are unlike what it does with every other
revert shape.

## Panics decode for free, and that is the easy half

Measured on solc 0.8.36, captured through a low-level-call prober so nothing had a chance to
reformat them:<Cite src="measured-revert-surfaces-1-7-1" />

```text
assert(1 == 2)              0x4e487b71 … 01
1 - 2                       0x4e487b71 … 11
1 / 0                       0x4e487b71 … 12
arr.pop() on empty array    0x4e487b71 … 31
arr[3] on a length-0 array  0x4e487b71 … 32
```

Selector `0x4e487b71`, one 32-byte word, the code in the low byte. Because `Panic(uint256)` is a
built-in signature, no ABI is required: viem's decoder appends the `Error` and `Panic` definitions
to whatever ABI you hand it, and Solidity's own `catch Panic(uint errorCode)` clause exists for the
same reason.<Cite src="viem-src-panic-reasons" /><Cite src="solidity-docs-src-control-structures" />

So classification is free and identification is free. What is not free — and this is the part
worth measuring rather than assuming — is the mapping from code to sentence, because that mapping
lives in your tooling and your tooling's copy may be incomplete.

**viem's table has nine entries, not ten.** Its `panicReasons` constant maps 1, 17, 18, 33, 34, 49,
50, 65 and 81 — that is `0x01` through `0x51` in decimal — to English descriptions. There is no
key `0`.<Cite src="viem-src-panic-reasons" /> When `ContractFunctionRevertedError` decodes a panic,
it looks the first argument up in that map and assigns the result to
`reason`.<Cite src="viem-src-contract-errors" /> A `Panic(0)` therefore decodes correctly —
`errorName` is `'Panic'`, `args` is `[0n]` — and produces `reason === undefined`. The generic
compiler-inserted panic, the one entry your secondary sources probably never showed you, is also
the one your error renderer will most likely print as a blank.

**`cast` does not map codes at all.** On cast 1.7.1, `cast decode-error` prints the signature and
the raw argument and stops:<Cite src="measured-revert-surfaces-1-7-1" />

```text
$ cast decode-error 0x4e487b71…0011
Panic(uint256)
17

$ cast decode-error 0x4e487b71…0000
Panic(uint256)
0
```

Both decode. Neither says what happened. That is defensible for a CLI and a trap for anyone who
pipes its output into an incident report, because `17` is a code and `0x11` is how every table
writes it — the tool prints decimal, the documentation prints hex, and reconciling the two is one
more place to be wrong at 3am. OpenZeppelin's `Panic.sol` is a useful second copy of the constants
if you want the mapping inside a contract.<Cite src="oz-panic-sol" />

## The hard half: a panic is never a message for the user

The normative wording is unusually blunt for a language reference. `assert` "should only be used to
test for internal errors, and to check invariants"; "properly functioning code should never create
a Panic, not even on invalid external input"; and if one happens "then there is a bug in your
contract which you should fix".<Cite src="solidity-docs-src-control-structures" />

Read the middle clause again, because it is the one that decides your client behaviour. *Not even
on invalid external input.* A contract that panics when someone sends it a stupid number has not
correctly rejected bad input; it has failed to validate it and then tripped over its own arithmetic.
So the inference from a panic is not "the user did something wrong". It is "somebody in this call
path shipped a defect", and the only open question is who.

That yields a rule with no exceptions worth teaching:

**A panic is routed to your alerting system, and the user gets a generic apology.** Not
"arithmetic overflow". Not "array index out of bounds". Not the raw code. Those strings tell a
non-expert nothing they can act on, and they tell an expert that your product is broken — which is
true, and which you would rather learn from your own alerts than from a screenshot on social media.

What the user sees is some variant of "Something went wrong on our side. Nothing was charged and
your funds have not moved. We have been notified." What your alert carries is everything the user
does not need: the panic code in both hex and decimal, the contract address, the function and
arguments, the chain id, the block number the simulation ran against, and the account. That set is
enough to reproduce; anything less turns an alert into a scavenger hunt.

<Aside kind="warn">
"Nothing was charged" is only true for a *simulated* failure. If the panic came back from
`eth_call` or from `eth_estimateGas`, nothing was signed and nothing was spent. If it came back
from a mined receipt with a reverted status, the transaction was included and the gas was consumed.
Those are different sentences to a user who is about to check their balance, and a triage function
that cannot tell them apart will eventually tell someone a comforting lie.
</Aside>

## Which panic tells you which kind of defect

The rule is uniform for the user; the rule is not uniform for you. Six of the ten codes point at
recognisably different failures, and knowing which is which cuts triage time sharply.

**`0x11`, overflow or underflow — usually a missing validation, occasionally a real logic error.**
The most common single cause in application-facing contracts is subtracting a user-supplied amount
from a balance without first checking the amount is not larger. Since 0.8.0 the check is automatic
and the failure is a panic instead of a silent wrap, which is a large improvement and also the
reason this code shows up in support queues. If you can produce it from ordinary user input, the
contract is missing a `require` and the client is missing a pre-flight check.

**`0x32`, index out of bounds — an off-by-one or an unvalidated index parameter.** If the index
came from calldata, the function should have bounded it. If it came from internal state, two pieces
of state have gone out of sync, which is the more serious of the two readings.

**`0x12`, division by zero — almost always a denominator that is a supply, a total, or a price.**
The characteristic shape is a share calculation on an empty pool, or a rate computed against a
`totalSupply` of zero. It tends to appear on the first interaction with a freshly deployed
contract and then never again, which is exactly the profile of a bug that survives a test suite.

**`0x01`, a failed `assert` — a broken invariant, and the most serious entry on the list.** The
author wrote down a condition they believed could not be false, and it was false. Everything else
on this list is a language-level check the compiler inserted; this one is a human claim that has
just been refuted. Escalate it above the others.

**`0x21`, invalid enum conversion — a client bug more often than a contract bug.** An enum
parameter is a `uint8` on the wire with a valid range the ABI does not encode. If your interface
sends `3` for a three-variant enum, you get this. Fix it on the client and add a bound on chain.

**`0x22`, incorrectly encoded storage byte array — rare, and when it appears, look at storage
layout.** A `bytes` or `string` in storage has an encoding that depends on its length, and reaching
this code means a slot holds something that is not a valid encoding of either form. In practice
that means something wrote to a slot that belongs to a different variable, which is a storage
collision. If the contract sits behind [a proxy](/c/proxy-storage-slots), that is where to look
first.

The remaining codes — `0x00` generic, `0x31` pop on empty, `0x41` over-allocation, `0x51`
zero-initialised internal function pointer — are rarer in application call paths and should be
treated as "read the trace" rather than pattern-matched.

<Aside kind="note">
There is a historical detail that still shows up in old runbooks. Before Solidity 0.8.0, panics
used the `INVALID` opcode, which consumed **all** the gas available to the call rather than
returning the remainder.<Cite src="solidity-docs-src-control-structures" /> If you are reading a
2019 postmortem that treats a failed `assert` as catastrophically expensive, that is why, and it is
no longer the behaviour.
</Aside>

## The absence of a panic is not evidence of correctness

One asymmetry is worth carrying into incident response. `0x11` fires for arithmetic "outside of an
`unchecked { ... }` block".<Cite src="solidity-docs-src-control-structures" /> Inside one, the same
overflow wraps silently and execution continues with a wrong number.

For a client that means the panic surface is a partial view of the arithmetic surface. A gas-tuned
contract that wraps its hot loop in `unchecked` has not removed the possibility of overflow; it has
removed the *report*. So "we have never seen `0x11` from this contract" is weak evidence, and it is
weakest exactly where the contract has been optimised hardest. When a contract produces a result
that is absurd rather than a failure that is loud — a balance that grew, a fee larger than the
principal, a share count with more digits than the supply — the first hypothesis is a wrapped
subtraction inside an `unchecked` block, and no error shape will ever tell you that.

This is also the cleanest argument for the invariant checks you built in the security track running
against production data and not only in the test suite. The panic channel reports the failures the
compiler was willing to insert a check for. Everything the author opted out of is yours to detect.

## When the panic is not yours

You will also see panics from contracts you did not write and cannot fix: a token with a broken
`transferFrom`, a periphery contract doing arithmetic on a fee-on-transfer token it was not
designed for, an oracle returning zero into somebody's denominator. The classification is unchanged
— it is still a defect, still not a business rule, still not a message for the user — but the
action changes. It stops being "file a bug against our contracts" and becomes a routing decision:
this counterparty, this token, this pool is unsafe for this path, and your interface should stop
offering it.

That is worth building deliberately. A triage function that reports *which contract* produced the
panic, not merely that one occurred, lets you disable a single market rather than an entire
feature. Getting the contract address requires either a trace or a call structure where you know
which sub-call you were in — which is one of several reasons the next lesson's advice about
assembling ABIs by call path pays for itself.

<Check type="spot-bug" concept="panic-means-bug">
An interface shows this to users, and the copy was written deliberately by someone who thought it
was helpful:

> **Transaction failed: arithmetic underflow or overflow.** Try entering a smaller amount.

The failure it renders is a `Panic(0x11)` from a staking contract's `unstake(uint256 amount)`,
which computes `staked[msg.sender] - amount` without a prior check. Users who follow the advice do
often succeed.

Say what is wrong with this, given that the advice works. Then say what the interface should do
instead — all of it, not only the string.

<Answer>
**The advice works, and it is still wrong, for three separate reasons.**

*It leaks an implementation detail as a diagnosis.* "Arithmetic underflow or overflow" is a
category of compiler-inserted check.<Cite src="solidity-docs-src-control-structures" /> It is not
the failure the user experienced, which is "I tried to unstake more than I have staked". The user
has to perform the translation, and most cannot.

*It is only sometimes true.* `Panic(0x11)` from this contract means an unchecked subtraction
underflowed, and the same code will arrive from a reward calculation, an index arithmetic bug, or
a fee computation on a large amount — none of which are fixed by entering a smaller number. The
message hard-codes one cause for a code that covers a class. When the other causes arrive, the
interface confidently sends the user down a dead end.

*It suppresses the alert.* This is the expensive one. The contract reaches a panic on ordinary
user input, which per the documentation means properly functioning code should not have done
that — the contract is missing a bound check.<Cite src="solidity-docs-src-control-structures" /> By
rendering the panic as a business message, the team converted a standing defect into a UX quirk
that nobody escalates. It will sit there until it appears somewhere it cannot be worked around.

**What the interface should do instead.**

*Prevent it.* The amount field should be bounded by the staked balance the interface already reads.
A panic reachable from a form input is a validation gap in two places at once.

*Simulate before signing.* Run the call as a simulation, catch the failure before the user is asked
for a signature, and never let a panic reach a signing prompt.

*Classify, then render.* The four-way branch says shape three. Shape three routes to the app-bug
bucket: a generic apology to the user, plus an alert carrying `0x11`/17, the contract address, the
function, the arguments, the chain id and the block. Not the code, not the phrase "underflow", to
the user.

*Fix the contract.* `require(amount <= staked[msg.sender], InsufficientStake(staked[msg.sender], amount))`
turns the panic into a typed business error with the two numbers the interface needs to say "you
have 40 staked; you asked to unstake 50" — which is the sentence the original copy was trying and
failing to approximate.

**The tell to remember.** If a panic code is reachable by a user filling in a form, the argument is
over: it is a bug in the contract, whatever the message says.
</Answer>
</Check>

## What this unlocks

**Next**, the shape with no selector at all. Zero bytes has at least five unrelated causes,
measured, and none of them can be distinguished from the data — which makes it the only shape
triaged by context rather than content. The same lesson takes apart the assumption that four bytes
identify anything, with 83 signatures that all hash to `0x00000000`.

**Then the client machinery**: how viem gets from a thrown action error down to these bytes, what
its decoder does when the selector is not in your ABI, and why the contract that produced the panic
is so rarely the contract you called.
