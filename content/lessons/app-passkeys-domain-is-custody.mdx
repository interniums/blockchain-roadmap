A product decision that takes ninety seconds in a kickoff meeting: the wallet will live at
`app.example.com`, because marketing owns the apex and the landing page is already there.

Eighteen months later the company rebrands. The apex moves to a new name, `app.example.com` is
decommissioned along with everything else on the old domain, and a migration ticket says "update DNS,
redirect old URLs". Every user who registered a passkey in those eighteen months now holds a credential
that exists, is perfectly healthy, sits in their phone's secure hardware — and will never produce another
assertion for that wallet, because the authenticator will not offer a credential whose relying party
identifier does not match where the request came from.

There is no cryptographic failure in that story. Nobody lost a key. The custody model included a DNS name,
and nobody wrote that down.

## What the credential is actually bound to

The binding is the relying party identifier, and the specification is precise about how it is chosen and
what it scopes.

By default, the RP ID for a WebAuthn operation is the caller origin's effective domain. The caller may
override that default, but only to a value that is a **registrable domain suffix of, or equal to**, the
caller origin's effective domain.<Cite src="webauthn-l3" /> An RP ID is based on a host's domain name and
does not itself include a scheme or a port, unlike an origin.<Cite src="webauthn-l3" />

The specification's own worked example is the fastest way to internalise the rule. For a relying party whose
origin is `https://login.example.com:1337`:<Cite src="webauthn-l3" />

| Candidate RP ID | Valid? | Why |
|---|---|---|
| `login.example.com` | yes | equal to the effective domain — this is the default |
| `example.com` | yes | a registrable domain suffix of the effective domain |
| `m.login.example.com` | no | more specific than the caller's own domain |
| `com` | no | not a registrable domain |

And the scope it buys, stated as three conditions: the RP ID must equal the origin's effective domain or be
a registrable domain suffix of it; the origin's scheme must be `https`, or the host must be `localhost` with
scheme `http`; and the origin's **port is unrestricted**.<Cite src="webauthn-l3" />

Three consequences fall out immediately, and they are the whole of this lesson's practical content.

**You can widen at registration time, never afterwards.** A credential created with RP ID `example.com` works
from `app.example.com`, `wallet.example.com`, and any other subdomain. One created with RP ID
`app.example.com` works from `app.example.com` and nowhere else — not even from `example.com`. The RP ID is
fixed for the life of the credential: no rotation ceremony, no migration path, no re-signing.

**The port does not matter and the scheme does.** `https://app.example.com` and
`https://app.example.com:8443` share credentials. `http://app.example.com` gets nothing, and that is not a
browser warning you can dismiss.

**Your staging environment is a decision, not an accident.** With RP ID `example.com`, `staging.example.com`
can obtain assertions from production credentials. With RP ID `app.example.com` it cannot, and your team
cannot test with their real accounts. Neither answer is wrong. Choosing by default is.

## Choose the RP ID as carefully as a contract address

Because the choice is permanent, run it as an architecture decision with a written record. Four questions
settle it:

**1. What is the widest registrable domain you will plausibly ever serve this wallet from?** That is almost
always the answer — the apex. Registering at the apex costs nothing today and preserves every subdomain you
have not thought of. Registering at a subdomain saves nothing and forecloses all of them.

**2. Do you need to keep environments apart?** If production credentials must never be usable from staging,
you need distinct RP IDs, which means distinct registrable domains — a separate apex for non-production, not
a subdomain of the same one.

**3. Who controls that domain's registration and DNS, and what happens if they leave?** Write down the
registrar account, who can reach it, whether transfer and registrar locks are on, and the renewal term. If
the answer involves one person's email address, you have found the account's single point of failure.

**4. Does the account contract pin the RP ID?** From lesson four, the cheap strong check is a 32-byte
comparison of `authenticatorData[0:32]` against a constant fixed at
deployment.<Cite src="webauthn-l2" /><Cite src="certik-passkey-wallets" /> If you pin it, the account will
only ever accept assertions for that identifier — good for security, and a constraint you cannot revise later
without an upgrade path. If you do not pin it, you have delegated the entire binding to the authenticator,
which is a defensible choice with a name.

<Aside kind="note">
`webauthn-sol` takes the unpinned option, and documents exactly why, which makes it a good model for how to
write down this kind of decision. Its header states that it does **not** verify that the `rpIdHash` in
`authenticatorData` is the SHA-256 hash of the expected RP ID, relying instead on the authenticator to enforce
that credentials are used only by the correct relying party, generally through Apple App Site Association and
Google Asset Links. It then adds the caveat that matters: to protect against edge cases in which a
previously-linked RP ID is removed from the authorised RP IDs, they recommend that messages signed by the
authenticator include some expiry mechanism.<Cite src="webauthn-sol" /> That is a security argument with a
stated assumption and a stated residual risk. Copy the format even if you make the opposite choice.
</Aside>

## What a domain takeover buys an attacker

Be precise about the threat, because the vague version ("don't lose your domain") leads people to the wrong
mitigations.

The authenticator binds a credential to an RP ID. It does not bind it to your TLS key, your bundle hash, your
company, or your code. If someone else comes to control an origin that matches the RP ID — through an expired
registration, a registrar account compromise, a subdomain takeover of a dangling DNS record, or a hijacked
hosting account — then a page they serve is, as far as the authenticator is concerned, you. It can call
`get()` with a challenge of its choosing, and the user's device will offer the credential and produce an
assertion for it.

The user's experience of that is the same biometric prompt they see every day. There is no second signal.

That makes domain control a custody-grade dependency, and it is a sharper risk than the equivalent for a
seed-phrase wallet, where a hijacked website still has to persuade the user to sign something through an
independent wallet prompt. Here the credential itself will sign, and the only thing between the attacker and
an authorisation is what your *contract* checks.

Which is exactly why the on-chain checks from lesson four are not belt-and-braces. Two of them do work here:

- **The challenge is the operation.** If the challenge is a [UserOperation hash](/c/user-operation), the
  attacker's page can only obtain assertions over operations the account would recognise, and those still have
  to satisfy every policy the account enforces — spending limits, value thresholds, timelocks on high-value
  actions.
- **Policy is on-chain.** A limit the account enforces cannot be reconfigured by whoever is serving the
  frontend, which is the property that separates a validation rule from a UI affordance.

CertiK's boundary statement is the one to hold onto, and it cuts both ways: once an attacker can execute in
the target origin, the RP ID and origin binding no longer protect the flow, because the malicious call comes
from the correct domain.<Cite src="certik-passkey-wallets" /> Phishing resistance is resistance to being
*elsewhere*. A domain takeover moves the attacker to *here*.

### Related Origin Requests: the escape hatch, and its price

Level 3 adds a mechanism for the case the rule above makes painful — one brand, many registrable domains.

By default, WebAuthn requires the RP ID to equal the origin's effective domain or be a registrable domain
suffix of it, and the specification acknowledges this makes deployment challenging for large environments with
country-specific domains, alternative or brand domains, and platform-as-a-service providers supporting mobile
apps.<Cite src="webauthn-l3" /> Relying parties can opt in to allowing a credential to be created and used
across a limited set of related origins, and MUST choose a common RP ID to use across all ceremonies from
those origins.<Cite src="webauthn-l3" />

The mechanism is a JSON document hosted at the WebAuthn well-known URL for the RP ID — that is,
`https://<rpId>/.well-known/webauthn` — served over HTTPS with content type `application/json`, whose top-level
object contains an `origins` key holding an array of web origins.<Cite src="webauthn-l3" /> Clients supporting
the feature MUST support at least five registrable origin labels, and client policy SHOULD define an upper
limit to prevent abuse.<Cite src="webauthn-l3" /> Requests to that endpoint are made without credentials,
without a referrer, and over HTTPS, and clients MUST require all redirects to also use
HTTPS.<Cite src="webauthn-l3" />

Read what that does to your dependency list. **A static JSON file on a web server is now part of the
authentication path for a wallet.** If it 404s, if a CDN serves the wrong content type, or if a redirect drops
to HTTP, the validation procedure throws a `SecurityError` and the ceremony fails.<Cite src="webauthn-l3" />
And the file is an *authorisation list*: whoever can write it can add an origin from which assertions can be
obtained.

Use it when the alternative is worse — genuinely separate brand or country domains that must share accounts.
Do not use it as a substitute for having chosen the apex in the first place.

## Synced or device-bound, and how the credential tells you

Two credentials, both called passkeys, with opposite failure modes. The specification gives you two bits in
`authenticatorData` that say which one you are holding, and they are the most product-relevant bits in the
whole structure.

Level 3 defines flag bit 3 as **Backup Eligibility (BE)** and bit 4 as **Backup State
(BS)**.<Cite src="webauthn-l3" /> Their semantics:

- Backup eligibility is whether the credential source is **allowed** to be backed up. It is a credential
  property and is **permanent** for a given credential — set during the registration operation and MUST NOT
  change.<Cite src="webauthn-l3" />
- A backup-eligible credential is called a **multi-device credential**; one that is not is a **single-device
  credential**.<Cite src="webauthn-l3" />
- Backup state is the *current* state, as determined by the managing authenticator, and it can change over
  time.<Cite src="webauthn-l3" />

The specification then does something unusual for a web standard: it tells relying parties what to *do* about
each. It RECOMMENDS storing the most recent value of these flags with the user account for future evaluation,
and gives three uses.<Cite src="webauthn-l3" /> Two of them are your product's recovery prompts, written by
the W3C:

**BE = 0 — require additional authenticators.** A single-device credential is not resilient to single-device
loss, and relying parties SHOULD ensure that each user account has additional authenticators registered
and/or an account recovery process in place — for example by prompting the user to set up an additional
authenticator.<Cite src="webauthn-l3" />

**BS changes 1 → 0 — add a factor.** The authenticator is signalling that the credential is no longer backed
up and no longer protected from single-device loss, which could result from user action such as disabling the
backup service, or from errors in the backup service. When this transition occurs, the relying party SHOULD
guide the user through validating their other authentication factors, and if the user has no other credential,
SHOULD guide them through adding one.<Cite src="webauthn-l3" />

For a login service, ignoring those is a support cost. For a wallet, BS dropping to 0 on a single-credential
account is the account moving from "recoverable" to "one dropped phone from permanent loss", and it is
observable, in a signed structure, on every single assertion. **Read those two bits on every operation and
store them.** They are already in the calldata you are paying for.

<Aside kind="warn">
Two limits on how far you should push this. First, the flags describe eligibility and state, not vendor
behaviour: exactly how a given platform credential manager syncs, exports, or restores passkeys in 2026 is
vendor policy that changes, and this curriculum has not verified current behaviour for any specific platform.
Verify per platform, per release, and date the note. Second, `webauthn-sol` explicitly does not verify credential
backup state, on the stated assumption that backup state is not used as part of relying-party business
logic.<Cite src="webauthn-sol" /> If you decide to use these flags in *policy* rather than in product prompts —
"this account requires a multi-device credential" — you are outside that assumption and you must check them in
your own verification path.
</Aside>

<Check type="explain" concept="passkey-rp-id-binding">
A wallet has shipped for a year at `https://wallet.example.com`, RP ID `wallet.example.com`. Two changes land
in the same quarter:

1. The company acquires `examplepay.com` and wants the wallet reachable from both domains.
2. The infrastructure team proposes moving the wallet to `https://app.example.com` behind a new load balancer,
   with a permanent redirect from the old host.

For each, say what happens to existing users' credentials and what the least-bad path is.

<Answer>
**Change 2 first, because it is the one that destroys accounts.** A credential with RP ID
`wallet.example.com` can only be exercised from origins whose effective domain is `wallet.example.com` or a
subdomain of it.<Cite src="webauthn-l3" /> `app.example.com` is neither. An HTTP redirect changes where the
browser ends up; it does not change which credential the authenticator will offer, because the RP ID is
compared against the origin the request finally comes from. Every existing user is locked out on the day the
old host stops serving.

There is no migration ceremony for an RP ID. The only path that preserves accounts is:

- **Keep `wallet.example.com` serving indefinitely** — not redirecting, serving — as the origin from which
  assertions are obtained. It can be a thin page whose only job is to run the WebAuthn ceremony.
- **Or run a dual-credential migration while the old origin still works**: from `wallet.example.com`, ask each
  user to register a *second* credential, carrying the new RP ID, and record its public key on-chain through
  an operation authorised by the first. That is an on-chain state change per user, it costs gas, and every
  user has to come back and do it. Budget it as a campaign with a completion rate below 100%, and decide in
  advance what happens to the tail.

The general rule: **an RP ID change is a per-user, per-account migration that requires an authorised
transaction from a working credential, and it can only happen while the old domain still works.** Which means
it has to be started before the decommissioning date, not after.

**Change 1 has a real mechanism.** `examplepay.com` is a different registrable domain, so no suffix
relationship exists and the default rule cannot cover it. Related Origin Requests is the sanctioned answer:
choose one common RP ID for all ceremonies and host the well-known JSON listing both
origins.<Cite src="webauthn-l3" /> Two costs to price before agreeing:

- The RP ID must be common across all related origins, so if existing `wallet.example.com` credentials are to
  work from `examplepay.com`, the common RP ID is the one those credentials already carry — which puts a
  `.well-known/webauthn` file on `wallet.example.com` and makes that host a dependency of the *other* brand's
  wallet.
- The origins array is an authorisation list. Whoever can deploy to that path can add an origin that may
  request assertions for these credentials. It belongs under the same change control as the account
  implementation, not under the marketing site's deploy pipeline.

**The decision that would have avoided both.** RP ID `example.com` at launch. It costs nothing on day one,
covers every subdomain the infrastructure team will ever invent, and leaves Related Origin Requests as the
answer only to genuinely separate brands. This is why the RP ID belongs in the same document as the account
implementation address: both are chosen once, both are permanent for everyone already using them, and only one
of them looks like a configuration value.
</Answer>
</Check>

## Where this pays off

**The next lesson** is the one this module has been walking toward. You now have every state that can strand a
user: a credential bound to a domain that changed, a single-device credential on a phone in a river, a
multi-device credential behind an OS account whose password is gone. The account is a contract, and it will
listen only to the parties its own code names — so the exits have to exist before the user needs them.

**Your architecture decision record** gains an entry with two fields nobody currently writes down: the relying
party identifier this product will use forever, and whether the account contract pins it. Both are permanent
for every user already registered.

**Your monitoring** gains the BE and BS bits. They arrive free, in every assertion, in the same
`authenticatorData` you already hash to build the digest.<Cite src="webauthn-l3" /><Cite src="eip-7951" /> An
account whose credentials are all BE = 0, or whose BS just dropped to 0, is a support ticket that has not been
filed yet.
