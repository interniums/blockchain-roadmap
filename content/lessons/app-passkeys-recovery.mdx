The ticket says: *new phone, old one went in a lake, I can see my balance on the website, please help.*

On the call are a support lead, a backend engineer with production database access, the CTO, and the
person who deployed the account factory. Between them they can read every row in every table, rotate any
secret the company owns, and deploy new contracts. Not one of those capabilities can add a credential to
that user's account, because the account's validation logic names the parties it will listen to, and
every one of those parties is at the bottom of a lake.

This is the lesson the whole module has been walking toward, and it is the one that decides whether your
product is shippable. The earlier lessons were about getting a signature verified. This one is about the
state where there is no signature to verify, and about the fact that the fix has to have been applied
months earlier.

## Why there is no back door, stated precisely

Two facts you already have, put together.

**The verifier verifies; it does not recover.** `ecrecover` takes a digest and a signature and *derives*
an address, which is why an Ethereum account can recognise a signer it has never stored. `P256VERIFY`
takes the public key coordinates `qx` and `qy` as two of its five input words.<Cite src="eip-7951" /> The
EIP states the design choice directly: verification rather than recovery, because most secp256r1
implementations verify signatures directly and NIST FIPS 186-5 specifies verification, not
recovery.<Cite src="eip-7951" />

So the account must already hold the public key of any credential it will ever accept. There is no
"present a signature and we will work out who you are". The account either knows your key or it does not,
and if it does not, your signature is a valid signature over the right message from a stranger.

**Registering a key is a state change.** Writing a new public key into the account's storage is a write,
and every write to a smart account goes through the account's own authorisation. Under ERC-4337 that means
an operation whose `validateUserOp` returns success — which means a signature from a party the account
already accepts.<Cite src="eip-4337" />

Compose them: **to add a credential you must already have one.** Not as a policy that could be relaxed,
not as a default someone could override — as the shape of the code. A user holding zero accepted
credentials has zero ways to obtain one, and the contract is indifferent to how sympathetic the case is.

## Every recovery design is the same move

Once you see it, the design space collapses to one axis. Recovery means **widening the set of parties the
account's validation logic will accept**, and every mechanism in circulation is a different way of choosing
who goes in that set and under what conditions. Which tells you two things: the mechanisms **trade against
each other rather than stack**, because every party added is a party who can take the account; and the design
doc should contain *the list*, with what it takes for each entry to move the money — not the phrase "social
recovery".

Two rows deserve emphasis before the mechanisms, because they are the ones teams discover late.

**The multi-device row is not a recovery design; it is somebody else's recovery design.** A credential that
syncs survives device loss because the platform credential manager restores it — so the user's OS or cloud
account is an authority over the wallet, and the account contract has no visibility into that authority at
all. Level 3 gives you the flag that says whether you are relying on it, and the specification RECOMMENDS
storing the most recent value of both backup flags with the user account.<Cite src="webauthn-l3" /> An account
whose only credential reports BE = 0 has no cloud safety net, and the specification says so in its own
guidance: a single-device credential is not resilient to single-device loss, and relying parties SHOULD ensure
each account has additional authenticators registered and/or a recovery process in place.<Cite src="webauthn-l3" />

**The RP ID row is the zero-credential row for everyone at once.** From the previous lesson: if the relying
party identifier stops resolving to something you control, no user can obtain a new assertion, and every
account simultaneously enters the state whose only exits are the ones configured in advance. Whatever
recovery mechanism you choose has to work without a passkey, because the scenario that takes out one user's
device and the scenario that takes out the domain both end in the same row.

### Several credentials, on separate authenticators

Register a second credential at account creation — a second device, or a roaming authenticator such as a
security key — and store both public keys in the account.

*Who can take the account:* whoever holds any registered credential.

*What it costs:* the least new trust of any option — no new party, no new contract, no timelock. The
weaknesses are practical rather than structural. The second credential is often on a device in the same OS
account as the first, which makes the two failures correlated rather than independent. And it depends on the
user possessing a second authenticator at the moment they create the account, which is exactly when they
have the least patience.

### An EOA or hardware wallet as co-owner

Add a secp256k1 address to the set of accepted signers. The account's validation accepts either a WebAuthn
assertion or an ordinary ECDSA signature from that address. OpenZeppelin's account layer models this
directly — the abstract signer family and the ERC-7913 multi-signer machinery exist to let one account
accept several signer kinds.<Cite src="oz-changelog" /><Cite src="erc-7579" />

*Who can take the account:* whoever holds that private key.

*What it costs:* the seed phrase comes back. That is the honest description, and products avoid saying it
because it contradicts the pitch. It is still frequently the right answer, because the phrase moves from the
daily path to the cold path: the user never types it and only touches it when the alternative is losing
everything. A phrase used once in five years is a very different risk from one used weekly.

*The variant that is not this:* an EOA whose key your onboarding generated and emailed, or held in your
backend "temporarily". That is a custodial fallback wearing this mechanism's clothes, and it belongs in the
fourth row with the trust properties of the fourth row. CertiK's checklist asks the equivalent question for
EIP-7702-style smart EOAs: whether the delegation-revocation path remains under the user's control, and
what happens if the delegated contract is upgraded.<Cite src="certik-passkey-wallets" /><Cite src="eip-7702" />

### A guardian set with a timelock

`N` addresses; `M` of them can, together, rotate the account's signer after a delay.

*Who can take the account:* any `M` guardians who collude, after the delay elapses.

*What it costs:* two parameters that pull against each other, and one implementation constraint people meet
late.

The threshold `M` trades availability against capture: low `M` means fewer guardians need to be reachable
in an emergency and fewer need to collude to steal. The timelock trades the same way in time — it is the only
defence against a guardian set quietly compromised, because it gives the real owner a window to cancel, and it
is a delay imposed on a user who has just lost their phone.

The implementation constraint: a recovery that becomes valid *after* a delay is a time condition, and inside
an ERC-4337 account you do not express it by reading the clock during validation. The standard gives you the
mechanism. `validateUserOp`'s return value is packed from an
aggregator/authorizer field, a `validUntil` timestamp and a `validAfter` timestamp, both six bytes, with
`validUntil` zero meaning infinite; and a validity range can be expressed in block numbers instead by
setting the high bit of both.<Cite src="eip-4337" /> The operation is valid only inside that window, checked
as `validAfter <= block.timestamp`.<Cite src="eip-4337" /> A recovery operation that returns a `validAfter`
of "request time plus the delay" *is* the timelock, enforced by the EntryPoint rather than by a `require` in
your validation path.

*The part nobody designs:* guardian churn. A guardian set assembled at account creation decays — people
change phones, lose interest, fall out with the user, or die. If there is no path to rotate guardians, the
threshold silently rises over time until it is unreachable, and the account arrives back in the
zero-credential row by attrition rather than by accident.

### A custodial fallback held by the product

Your company holds a key that can rotate the account's signer, and support uses it when a user is stranded.

*Who can take the account:* you. Anyone who compromises you. Anyone who compels you.

*What it costs:* the best user experience in the list, and the largest change to what your company is. Say it
in those words in the design document, because the alternative is a diagram where this appears as "emergency
access" and nobody notices the product became a custodian. It is also the highest-value target you operate: a
single key that can take any account is worth more than any account.

*When it is defensible:* with a timelock and a loud user-visible notification, so a fallback used maliciously
is observable and cancellable by a user who still holds a credential. That converts "we can take any account"
into "we can take any account belonging to a user who is not paying attention" — materially different, and
honest enough to write down.

## Why it has to be at account creation

The behavioural argument is familiar: a settings screen labelled "set up recovery" is visited by a small
fraction of users, and the people who skip it are exactly the people the product was built for. The
structural argument is stronger and less well known.

An ERC-4337 account is usually addressed counterfactually — the address is derived before any code exists,
and the operation that first uses the account carries the factory call that deploys it.<Cite src="eip-4337" />
That address is a [CREATE2 derivation](/c/create2-address) over the init parameters, and **the owner set is
one of those parameters**. So for an account that has not yet been deployed, adding a guardian or a co-owner
is not a transaction — it is a different address. Funds already sent to the original address are not
governed by the account you would deploy with the new configuration.

That gives you a hard ordering constraint:

- **Before deployment**, the recovery configuration is part of the account's identity. Change it and you have
  a different account.
- **After deployment**, the recovery configuration is state, changeable by an authorised signer — which
  requires a working credential, which is precisely what the user has lost by the time they care.

There is no window in which recovery is easy to add. It is either baked into the address or it needs an
authorisation the stranded user does not have.

### What to actually ship

Three moves, in order of how much they cost the funnel:

**Make the second factor part of account creation, not a follow-up.** The cheapest version is a roaming
authenticator or a second device registered in the same session. The next cheapest is a co-owner address the
user generates and stores — one screen, and it is the screen passkeys were supposed to remove, so put it
after the account is usable rather than before.

**Enforce it with the account instead of asking for it.** The account is a contract, so "this account is
capped until a second party is authorised" is a rule it can hold. A wallet that works fully for small
balances and requires a recovery configuration before it will execute above a threshold converts an ignorable
prompt into a blocking one at the moment the user has something to lose. That is a policy your validation
logic enforces, which means it cannot be skipped by a modified frontend.

**Use the flags the assertion already carries.** Read BE and BS on every operation, store the latest values as
the specification recommends, and drive prompts from them: BE = 0 means no cloud safety net; BS falling from 1
to 0 means the account just lost one. Both are the specification's own recommended triggers for guiding a user
to add another credential.<Cite src="webauthn-l3" />

## The second database nobody syncs

One failure mode that is specific to this architecture and is missed in almost every implementation.

Your account's storage holds a set of accepted public keys. The user's authenticator holds a set of
credentials scoped to your RP ID. These are two databases, they drift, and only one of them is under your
control.

Remove a compromised credential from the account and it does not disappear from the user's device. The
authenticator keeps offering it — at a fresh sign-in with an empty `allowCredentials`, the picker shows a
credential the account will now reject. The user selects the one they remember, gets a rejection with no
explanation, and files a ticket.

Level 3 adds the fix, and it is a client-side call rather than a transaction. `PublicKeyCredential` gains
three static signal methods: `signalUnknownCredential`, `signalAllAcceptedCredentials`, and
`signalCurrentUserDetails`.<Cite src="webauthn-l3" />

- `signalUnknownCredential({ rpId, credentialId })` signals that a credential id was not recognised — for
  example because it was deleted — and the authenticator then removes or hides it from future authentication
  ceremonies.<Cite src="webauthn-l3" />
- `signalAllAcceptedCredentials({ rpId, userId, allAcceptedCredentialIds })` signals the complete list, and
  the specification says relying parties SHOULD prefer it when the user is authenticated, since there is then
  no privacy leak risk and the list is a full snapshot that may reflect changes not yet reported to attached
  authenticators.<Cite src="webauthn-l3" />

The reason to prefer the second when you can is stated as a privacy property: signalling a single unknown
credential avoids leaking credential ids to an *unauthenticated* caller, which is the situation the first
method is designed for.<Cite src="webauthn-l3" />

The engineering instruction is short. **Any operation that changes the account's set of accepted credentials
should be followed, on the client, by a signal call reflecting the new set.** Put it in the same code path as
the transaction confirmation, not in a settings screen — the on-chain write and the device-side signal are
two halves of one change, and shipping only the half you can see in a block explorer is how the ghost
credential survives.

<Aside kind="warn">
Do not build authorisation on this. Signal methods are a hint to authenticators, not a revocation mechanism —
they keep the user's picker honest. Revocation is the on-chain write, and the account rejecting the removed
key is what makes the credential powerless. If the signal call fails, or the user's other devices never
receive it, the account is still safe and the user is merely confused. Reverse those two and you have built a
wallet whose security depends on a browser API succeeding.
</Aside>

<Aside kind="note">
The counterfactual state has one more edge worth naming. A contract signer answers through
`isValidSignature`, which is a call — so the contract has to exist.<Cite src="eip-1271" /> An account that has
been addressed but never deployed cannot answer, and ERC-4337's factory field solves the execution side
without solving the signature-checking side for third parties.<Cite src="eip-4337" /> So an undeployed account
that has received funds has a recovery configuration fixed by its address, signers that cannot be changed, and
no way to prove anything to an external protocol. The exit is to deploy it with the original init parameters,
which needs whatever that configuration named. If nothing it named still exists, the funds sit at an address
whose only possible governing code is one nobody can now authorise.
</Aside>

## Where this pays off

**The module closes here**, and the reflection prompt is the deliverable: every state your accounts can be
in, and the exit from each. Any state whose only exit is "unrecoverable" must either gain an exit or be
written down as an accepted risk in the words "the user loses everything". A design document without that
sentence has not made the decision; it has deferred it to whoever reads the support queue.

**What you now have** is the full shape of an authentication system whose verifier has no operator. The curve
forced the account to be a contract. The payload forced the contract to rebuild what a browser wrote. The
precompile made it affordable and then declined to canonicalise the signature. The domain turned out to be
custody. Every one of those ends in the same place: the account listens to exactly the parties its code
names — the property you wanted, priced honestly.

**The next thing to reach for** is scope rather than recovery. An account that prompts for a biometric on
every action is safe and exhausting, and the answer is not a weaker credential but a narrower authority:
[session keys](/c/session-key-definition), enforced by the account's own validation — commonly as a validator
module under ERC-7579.<Cite src="erc-7579" /> A different trust decision, built on the same sentence: the set
of parties the account accepts, and what each of them is allowed to do.
