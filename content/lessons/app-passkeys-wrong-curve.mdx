viem's documentation for a WebAuthn account is unusually blunt. It lists four differences from a local
account, and two of them are refusals:

> cannot sign transactions (transactions do not support **secp256r1** signatures)
>
> does not have an Ethereum `address`<Cite src="viem-webauthn-account" />

A library that could paper over this would have papered over it. The type has no `address` field
because there is no address to compute, and it has no transaction signer because there is no
transaction it could produce that a node would accept. Neither is a gap in the library. Both are the
same fact about arithmetic, showing up in a type system.

This lesson is that fact, and the design consequence that follows from it — which is not "use a
different library" but "the account is a contract, and it always was".

## Two curves that share a name and nothing else

You know ECDSA on [secp256k1](/c/ecdsa-secp256k1) in detail. P-256 is ECDSA too. The algorithm is
identical; the group it runs in is not.

Both are short Weierstrass curves over a prime field, `y² = x³ + ax + b (mod p)`. The parameters
differ in every position. SEC 2 defines secp256k1 as a Koblitz curve with `a = 0` and `b = 7`, and
secp256r1 as a verifiably random curve with `a = p − 3` and `b` derived from a seed.<Cite src="sec2-curve-params" />
EIP-7951 lists P-256's parameters in full: base field modulus
`p = 0xffffffff00000001000000000000000000000000ffffffffffffffffffffffff`, subgroup order
`n = 0xffffffff00000000ffffffffffffffffbce6faada7179e84f3b9cac2fc632551`, cofactor 1, with NIST
SP 800-186 as the normative source.<Cite src="eip-7951" /><Cite src="nist-sp-800-186" />

Different `p`. Different `n`. Different base point. A point on one curve is, with overwhelming
probability, not a point on the other, and a scalar that is a valid private key for one is a valid
private key for the other only in the trivial sense that both are 256-bit integers below their
respective orders.

The security level is comparable — EIP-7951 states P-256 provides approximately 128 bits of security,
equivalent to secp256k1 — which is exactly why the confusion survives.<Cite src="eip-7951" /> They are
equally good curves. They are not the same curve.

## What `ecrecover` does with a P-256 signature

`ecrecover` is not a signature verifier. It is a *recovery* function: given a digest, a parity bit and
`(r, s)`, it reconstructs the point that must have been the ephemeral `R`, solves for the public key
that would make the equation hold **on secp256k1**, and returns that key's address.

Hand it `(r, s)` from a P-256 signature and it does not detect an error, because there is no error to
detect at its level. It performs the same arithmetic in the wrong group. Either the inputs fall
outside the ranges it checks and it returns the zero address, or it returns the address of a key that
nobody holds — a perfectly well-formed 20 bytes with no relationship to the passkey, to the user, or
to anything else.

That failure mode is worth sitting with, because it is the shape of the whole class. **Nothing
raises.** You get an address. It is simply the wrong one, every time, and it is a different wrong one
for each signature. A test that asserts "recovery returned a non-zero address" passes. A test that
asserts "recovery returned the expected signer" is the only one that fails, and it fails identically
whether the cause is a wrong curve, a wrong digest, or a corrupted byte.

### A second mismatch, in the encoding

The curve is the mismatch that forces the architecture. There is a smaller one that will cost you an
afternoon, and it is worth naming here so it does not read as a bug later.

Ethereum signatures arrive as 65 raw bytes: `r`, `s`, `v`. WebAuthn assertion signatures do not.
For COSE algorithm -7 (ES256) and other ECDSA-based algorithms, the specification requires the
signature to be encoded as an **ASN.1 DER `Ecdsa-Sig-Value`**, and gives a worked example of the
tagged, length-prefixed form.<Cite src="webauthn-l2" /> The specification even records mild regret
about it, recommending that new attestation formats represent signatures as fixed-length byte arrays
without internal structure, and explaining that the DER form persists because CTAP1/U2F authenticators
already produced it.<Cite src="webauthn-l2" />

Two practical consequences. First, you have to parse DER somewhere to recover `r` and `s` as 32-byte
words, and the sane place is off-chain, before the values ever reach a contract. Second — the part
that produces the afternoon — DER integers are signed, so an `r` or `s` whose top bit is set is emitted
with a **leading zero byte** to keep it positive. Roughly half of all values are affected. Code that
slices a fixed offset works on most signatures and fails on the rest, which is the worst possible
failure distribution: it passes your tests, it passes your staging soak, and it rejects a fraction of
your users' transactions in production with no pattern they can describe.

The corollary is the one viem's type encodes. An Ethereum externally owned account *is* a secp256k1
key: the address is the last twenty bytes of the hash of the public key, and the only way to move
value from it is a signature the protocol can recover to that address. A P-256 key has no such
address, because the derivation is defined over the other curve and the protocol would not check it if
it did. A passkey therefore cannot be an EOA key. Not "is awkward as"; cannot be.

## So the account is a contract

If a passkey cannot be an EOA key, then anything a passkey controls must sit behind code that can
verify P-256 signatures. There are three shapes in production, and they differ in what the *address*
is, which turns out to be the thing that matters for custody.

**An ERC-4337 smart account.** The account is a deployed contract. It implements `IAccount`, whose
single required function is:

```solidity
function validateUserOp(
    PackedUserOperation calldata userOp,
    bytes32 userOpHash,
    uint256 missingAccountFunds
) external returns (uint256 validationData);
```

The EntryPoint calls it, hands it the hash of the operation, and the account decides. ERC-4337 is
**Final**.<Cite src="eip-4337" /> The account "MUST validate that the signature is a valid signature of
the `userOpHash`", and — this detail matters in two later lessons — it "SHOULD return
`SIG_VALIDATION_FAILED` (1) without reverting on signature mismatch", where any *other* error must
revert.<Cite src="eip-4337" /> Validation in this world is a returned value, not an exception.

**An ERC-1271 contract signer.** A contract exposes `isValidSignature` and answers questions about
arbitrary messages, returning a magic value when it approves.<Cite src="eip-1271" /> This is the route
for "log in with your passkey account" and for any protocol that accepts contract signatures. It has
one structural limitation worth knowing before you design around it: `isValidSignature` is a call to a
contract, so the contract has to exist. An account that has been counterfactually addressed but never
deployed cannot answer, because there is no code at the address to answer with. ERC-4337 addresses the
same problem from the other side, by carrying the factory call that first deploys the account inside
the operation the user signs.<Cite src="eip-4337" /><Cite src="certik-passkey-wallets" />

**An EOA delegated under EIP-7702.** The address stays an EOA. A delegation designator points its code
at an implementation that verifies P-256, so calls into that address execute validating
code.<Cite src="eip-7702" />

That third route deserves a warning, because it is the one whose custody model is most often
misdescribed in product documentation.

<Aside kind="warn">
Under [EIP-7702 delegation](/c/delegation-designator) the passkey does not replace the EOA key. It is
*added* authority. The underlying secp256k1 key still exists, still controls the address, and can still
sign a new authorisation pointing the delegation somewhere else — or clear it. So "the user's account is
secured by their passkey" is only true if the EOA key is under control: freshly generated and discarded,
held by the user deliberately as a co-signer, or otherwise accounted for. CertiK's audit checklist asks
this directly for 7702-style smart EOAs: does the delegation-revocation path remain under the user's
control, and what happens if the delegated contract is upgraded?<Cite src="certik-passkey-wallets" /> A
passkey layered on an EOA whose key was emailed to the user during onboarding is a passkey-shaped
interface over a private-key wallet.
</Aside>

The three routes are not interchangeable, and the axis that separates them is what the address *is*:

| Route | The address is | Exists before first use | Who else can move it |
|---|---|---|---|
| ERC-4337 smart account | a contract, usually CREATE2-derived | counterfactually, code deployed on first use | whoever the account's validation logic accepts |
| ERC-1271 contract signer | a deployed contract | only once deployed | same, but the contract must exist to answer at all |
| EIP-7702 delegated EOA | an EOA, with code pointed at an implementation | yes, as a plain EOA | the passkey **and** the EOA's secp256k1 key |

Read the last column downward. Two of the three rows have one answer; the third has two, and the second
one is invisible in the product's own description of itself.

## Where the signature actually enters

Abstract routes are easy to nod at. Trace one concretely, because the trace names the four places the
next four lessons live.

**Subgoal — turn the user's intent into one hashable object.** The wallet assembles the operation:
sender, nonce, calldata, gas fields, paymaster data, and the factory call if the account does not exist
yet.<Cite src="eip-4337" /> Nothing is signed yet.

**Subgoal — collapse it to a single fingerprint the contract can recompute.** `userOpHash` is a hash
over the operation excluding the signature, plus the EntryPoint address and the chain
id.<Cite src="eip-4337" /> Recomputable by the account during validation, and it changes if any field
changes — which is what makes it usable as a challenge.

**Subgoal — get the authenticator to commit to that fingerprint.** The wallet passes `userOpHash` into
the WebAuthn call as the challenge. This is where lesson three begins, because what comes back is not a
signature over `userOpHash`.

**Subgoal — ship the proof somewhere a contract can re-derive it.** The assertion travels on-chain as
several separate fields rather than a bare `(r, s)` pair, precisely because the contract has to rebuild
the signed bytes.<Cite src="certik-passkey-wallets" /> That is lesson four.

**Subgoal — verify the P-256 signature.** The account calls the secp256r1 verifier and reads the
result. That is lesson five, and it has a trap in it.

**Subgoal — decide.** The account returns a validation result rather than reverting, and only then does
execution proceed.<Cite src="eip-4337" />

Note what is absent from every step: `ecrecover`, transaction signing, and the user's private key. The
user's device produced one assertion. Everything else was your infrastructure and your contract.

## The building blocks already exist

You do not have to write the signer from scratch, and knowing what the standard libraries call things
saves a day of searching.

OpenZeppelin Contracts added a `P256` library for verification and public-key recovery of secp256r1
signatures in **5.1.0 (17 October 2024)**.<Cite src="oz-changelog" /> **5.4.0 (17 July 2025)** added the
account layer — `Account`, `AccountERC7579`, and an `AbstractSigner` family including `SignerP256` —
alongside the ERC-7913 multi-signer machinery.<Cite src="oz-changelog" /><Cite src="erc-7579" />
**5.5.0 (31 October 2025)** added the WebAuthn-specific pieces: a `WebAuthn` library for verifying
authentication assertions, a `SignerWebAuthn` abstract signer, and an `ERC7913WebAuthnVerifier` for
P-256 identities.<Cite src="oz-changelog" />

Two changes since then are worth carrying, because both are corrections to how the earlier versions
behaved.

In **5.6.0 (25 February 2026)**, `SignerWebAuthn` had its P-256 fallback **removed**: it now returns
false when the signature is not a valid WebAuthn assertion, and developers who want the fallback must
override the function to add it back.<Cite src="oz-changelog" /> The fallback let a signer accept two
different things — a full WebAuthn assertion, or a bare P-256 signature over the digest — under one
public key. If your account accepts both, then every check that lives inside the assertion (the
ceremony type, the flags, the relying-party binding) is optional from an attacker's point of view,
because they can simply present the bare form instead.

Also in 5.6.0, `Account`'s default ERC-4337 EntryPoint version moved to **v0.9**.<Cite src="oz-changelog" />
Treat that as a fact about the library's default, not as a statement about the network: EntryPoint v0.7
is the version most commonly described as the production deployment, v0.8 and v0.9 also exist, and which
one actually dominates mainnet traffic in August 2026 is not something this curriculum established. Pin
the EntryPoint your account is built against explicitly and verify the deployment on the chain you ship
to, rather than inheriting a default.

<Check type="predict" concept="passkey-needs-smart-account">
A team ships a passkey wallet on one chain. It works. They then "deploy to three more chains" by
running the same factory script, and route users by chain id in the frontend. A user registers a passkey
on chain A, receives funds on chain C, and cannot move them.

Predict the two most likely causes, and say which one is a bug and which one is a design decision that
was never made.

<Answer>
**Cause one — the account does not exist at that address on chain C.** The address came from a
[CREATE2 derivation](/c/create2-address), so it is the same on every chain, but sameness of address is
not deployment. Funds sent to an undeployed address sit at an address with no code. This is recoverable:
deploy the account with the same init parameters and the funds are under the control of the code that
appears. ERC-4337 anticipates exactly this by letting the operation that first uses an account also
deploy it through the factory field.<Cite src="eip-4337" /> A wallet that does not implement the
deploy-on-first-use path has a bug, and it is a bug with a fix.

**Cause two — the secp256r1 verifier the account calls is not present on chain C.** This is the one that
is not a bug, because nobody decided it. The account's validation logic calls a verifier. If that
verifier is the precompile, it exists only on chains that have activated it. If it is a deployed Solidity
contract, it exists only where someone deployed it. If it is a library that falls back from one to the
other, the fallback has its own dependencies — and the fallback in wide use depends on the ModExp
precompile at `0x05`, which is itself absent on some chains.<Cite src="webauthn-sol" /> The account's code
is identical on all four chains and its behaviour is not, because it depends on the chain's own
capabilities.

**Which is which.** The first is an implementation gap in a flow the standard defines. The second is an
unmade design decision: "which verification path does this account use, and on which chains is that path
available" is a question with a per-chain answer that has to be settled before the factory script runs,
because it is baked into the account's implementation address.

**The general lesson.** A passkey account is portable only as far as its verifier is. That is a
deployment-topology question, not a cryptography question, and it is the first place where "the account
is a contract" stops being a pedantic correction and starts costing a user access to their money.
</Answer>
</Check>

## Where this pays off

**Lesson three** answers the question this lesson deferred: you passed a hash in as the challenge, so
what came back? Not a signature over that hash. The gap between what you handed the authenticator and
what it signed is the reason on-chain verification is a lesson rather than a line.

**Lesson five** is about the verifier this lesson kept calling "the P-256 verifier" without pricing it.
For most of Ethereum's history the price was the argument against this entire design, and it is not any
more.

**Your threat model** gains a component it did not have. In a seed-phrase wallet, one question covers
most of the risk: was the phrase exposed? Here, the authority to move assets runs as a chain through the
authenticator, the application, the challenge, the account-abstraction infrastructure, the on-chain
validator, and the sync and recovery paths — and attackers route around the strongest link rather than
attacking it.<Cite src="certik-passkey-wallets" />
