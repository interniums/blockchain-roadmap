Search for the JSON-RPC method that grants a session key and you will find `wallet_grantPermissions`
in a hundred blog posts, three SDK wrappers and at least one conference talk.

Open the specification. The method is called `wallet_requestExecutionPermissions`.<Cite src="erc-7715" />

The old name has not gone into hiding, either: the Ethereum Magicians discussion linked from the
ERC's own header is still titled *erc-7715-grant-permissions-from-wallets*, and the ERC's title today
is "Request Permissions from Wallets".<Cite src="erc-7715" /> Nothing broke. A draft changed a name,
the ecosystem's writing did not follow, and the search results are now a mixture of two vocabularies
describing one method.

Treat that as the lesson's opening fact rather than as trivia. **ERC-7715 has been Draft since 24 May
2024, and the interface is not stable enough that the method name survived unchanged.**<Cite src="erc-7715" />
Everything below is worth learning because the *shape* is converging. None of it is worth hardcoding.

## Four methods, and only one of them is famous

ERC-7715 specifies four methods, and applications that use only the middle one are missing the two
that make the flow survivable.<Cite src="erc-7715" />

**`wallet_getSupportedExecutionPermissions`** — the wallet reports which permission types it
supports, per chain, and which rule types can be applied to each. The response is keyed on the
permission type, with `chainIds` and `ruleTypes` for each.<Cite src="erc-7715" /> This is the
feature-detection step, and it exists because the ERC deliberately does **not** enumerate the
permission types: it says it does not specify an exhaustive list of rule or permission types, since
more are expected as wallets get more advanced, and that a type is valid as long as both the dapp and
the wallet are willing to support it.<Cite src="erc-7715" /> The only structural constraints are that
no two permission types or rule types may share a type name, that new types should be specified in
additional ERCs, and that in all cases they MUST inherit from `BasePermission` or
`BaseRule`.<Cite src="erc-7715" />

If you have used [wallet capability detection](/c/wallet-capabilities) from EIP-5792, this is the
same discipline applied one layer up, and for the same reason: branching on the wallet's vendor breaks
on every release, branching on what it says it can do does not.<Cite src="eip-5792" />

**`wallet_requestExecutionPermissions`** — the request itself. The parameter is an *array* of
`PermissionRequest` objects, each with:<Cite src="erc-7715" />

```ts
type PermissionRequest = {
  chainId: Hex          // hex-encoded uint256, EIP-155
  from?: Address        // whose account — optional, lets the user pick
  to: Address           // the dapp session account
  permission: {
    type: string              // enum defined by ERCs
    isAdjustmentAllowed: boolean
    data: Record<string, any> // shape defined by the permission's own ERC
  }
  rules?: { type: string; data: Record<string, any> }[]
}[]
```

Note where the two halves of a policy live. `permission` is *what the session account may do on behalf
of the user's account*; `rules` are *restrictions or conditions the session account MUST abide by when
using it*.<Cite src="erc-7715" /> The only rule type the ERC spells out is expiry, and it defines it
tersely: it constrains a permission so that it is only valid until a specified timestamp, carrying a
`timestamp` which is the unix timestamp at which the permission becomes
invalid.<Cite src="erc-7715" />

**`wallet_getGrantedExecutionPermissions`** — the wallet MUST return all granted permissions that are
not yet revoked.<Cite src="erc-7715" /> This is your reconciliation endpoint, and building without it
means your app's belief about what it may do drifts from the wallet's.

**`wallet_revokeExecutionPermission`** — takes a `permissionContext` and, on success, the wallet
responds with an empty response.<Cite src="erc-7715" /> Its place in the lifecycle is the next
lesson's subject.

<Aside kind="warn">
Read the draft's own text on that fourth method before you design against it. The request type is
`RevokeExecutionPermissionRequestParams` with a `permissionContext` field, and the response type
printed directly beneath it is named `GetPermissionsInfoResultParams` and carries a list of
`chainIds` — a name and a shape that belong to a different method.<Cite src="erc-7715" /> That is not
a subtlety to reason about; it is an editing artifact in a draft. It is also the most honest possible
demonstration of what "Draft" means in the status field, and a good reason to drive revocation
through the on-chain path you control rather than through an interface whose response type has not
been settled.
</Aside>

## What comes back is not what you asked for

The response type is the request type plus three fields:<Cite src="erc-7715" />

```ts
type PermissionResponse = PermissionRequest & {
  context: Hex
  dependencies: { factory: `0x${string}`; factoryData: `0x${string}` }[]
  delegationManager: `0x${string}`
}
```

And then the sentence that should govern how you write the handler: the response contains all of the
parameters of the original request, and **it is not guaranteed that the values received are
equivalent to those requested**.<Cite src="erc-7715" />

That is not a hedge. It is the deliberate consequence of `isAdjustmentAllowed`, which the ERC defines
as allowing the wallet to attenuate — **reduce or increase** — the authority of a permission to meet
the user's terms for approval.<Cite src="erc-7715" /> The example the ERC gives for setting it false
is a payment that requires a specific allowance and must not be adjusted.<Cite src="erc-7715" />

So the first rule of writing this integration: **the request is a proposal, the response is the
contract.** Every cap, every expiry and every address your product logic depends on must be read out
of the response, not remembered from the request. A UI that displays "you granted 50 USDC" because
that is what it asked for will be wrong the first time a user drags the slider down to 10.

The other two fields are the plumbing.

`dependencies` is an array of `factory` and `factoryData` entries as defined by ERC-4337, describing
accounts that are not yet deployed but MUST be deployed for the permission to be redeemed. Either both
fields are specified in an entry or neither; if any involved account is undeployed the wallet MUST
return the corresponding dependencies, and if all are deployed it MUST return an empty array. The dapp
MUST deploy each account by calling the factory with `factoryData` as the
calldata.<Cite src="erc-7715" /> This is counterfactual deployment showing up in your happy path: the
user's account may not exist on-chain at grant time, and shipping the redemption before the deployment
gives you a failure that looks like a permission problem and is not.

`delegationManager` is required as defined in ERC-7710, and it is the address you will send the
redemption to.<Cite src="erc-7715" />

## ERC-7710 is the on-chain half, and it is deliberately separate

ERC-7715 grants off-chain. ERC-7710 — Smart Contract Delegation, also Draft, created 20 May 2024,
requiring EIP-1271 and EIP-7579 — is what redeems on-chain.<Cite src="erc-7710" />

Its vocabulary is worth adopting because it disambiguates a conversation that otherwise runs on
"the account" and "the app":<Cite src="erc-7710" />

- A **delegator** is a smart contract that can create a delegation.
- A **delegation manager** validates delegation authority and calls on the delegator to execute an
  action. Multiple managers can exist with different implementations, and **a contract account can be
  its own delegation manager.**
- A **delegation** is an authority given to another address to perform a specific action.
- A **delegate** is a contract, smart account or EOA that has authority to redeem a delegation.
- A **redeemer** is a delegate that is using one.

The interface is a single function:<Cite src="erc-7710" />

```solidity
interface ERC7710Manager {
  function redeemDelegations(
    bytes[] calldata _permissionContexts,
    bytes32[] calldata _modes,
    bytes[] calldata _executionCallData
  ) external;
}
```

The three arrays MUST be interpreted as a list of tuples — `(_permissionContexts[i], _modes[i],
_executionCallDatas[i])` — the function MUST revert if the arrays have different lengths, and
implementations MUST enforce atomicity of the batch.<Cite src="erc-7710" /> The `_modes` and
`_executionCallDatas` are the mode and execution calldata defined in ERC-7579's Execution Behavior
section: mode encodes the behaviour of the execution such as a single call or a batch, and the
execution calldata encodes target, value and data.<Cite src="erc-7710" /><Cite src="erc-7579" />

**Why it looks like that** is documented, and the history is instructive. A previous iteration defined
an `Action` as a simple `(target, value, data)` tuple and required the delegator to implement
`executeDelegatedAction(Action)`. That was dropped for two reasons: existing smart accounts would not
be compatible unless they happened to implement the interface, and a single `Action` could only encode
one call, making batching, delegatecall and CREATE2 impossible.<Cite src="erc-7710" /> The fix was to
require no interface on the delegator at all — relying on the manager to call it correctly, and on the
fact that a delegator would only create permission contexts for a manager that knows how to call it —
and to adopt ERC-7579's execution encoding for the second problem.<Cite src="erc-7710" />

So the awkward-looking three-array signature is what "work with accounts that already exist" costs.

**And the separation is intentional.** ERC-7710 states that the process by which a delegate obtains a
delegation is deliberately out of scope, that it focuses solely on the interface for redeeming and on
validating delegation authority, and that the mechanism for requesting and granting may be implemented
in various ways such as through ERC-7715 or other protocols.<Cite src="erc-7710" /> The two halves are
independently useful and independently replaceable — which is also why a wallet can ship one without
the other and still be standards-compliant about it.

## What the flagship implementation actually grants

Specifications describe a space. Implementations pick a corner of it, and the corner is the thing
your product ships on.

MetaMask implements ERC-7715 under the product name **Advanced Permissions**, and its documentation
describes the mechanism in the ERC's terms: `wallet_requestExecutionPermissions`, a session account
that is created solely to request and redeem permissions and holds no tokens, redemption as specified
in ERC-7710, and a hard prerequisite that the MetaMask user whose permissions are being requested must
be upgraded to a MetaMask smart account.<Cite src="metamask-advanced-permissions-concept" />

Now read the list of what it will actually grant:<Cite src="metamask-supported-permissions" />

| Permission type | MetaMask extension floor |
|---|---|
| ERC-20 allowance | ≥ v13.32.1 |
| ERC-20 periodic | ≥ v13.23.0 |
| ERC-20 stream | ≥ v13.23.0 |
| Native token allowance | ≥ v13.32.1 |
| Native token periodic | ≥ v13.23.0 |
| Native token stream | ≥ v13.23.0 |
| Token approval revocation | Smart Accounts Kit only, no extension support listed |

Seven types. Every one of them is about **moving value**: a total allowance, a per-period budget, a
linear stream, or the revocation of an existing approval. The applicable rules are three: `expiry`
with a unix timestamp, `redeemer` restricting redemption to specific addresses, and `payee`
restricting payments to specific receiver addresses.<Cite src="metamask-permission-rules-reference" />
The permission parameters are token address, amounts, periods, an optional `startTime`, and a
`justification` — a human-readable explanation of why the permission is being
requested.<Cite src="metamask-permissions-reference" />

**There is no "call this contract's `move(uint8)` function up to a thousand times" permission type in
that list.** The game example that motivates every session-key article — including the motivation
section of ERC-7715 itself, which names highly interactive applications such as games — is not
something the standard's most complete public implementation grants today through this
interface.<Cite src="erc-7715" /><Cite src="metamask-supported-permissions" />

That capability exists one layer down. The same framework's delegation layer has `allowedTargets`,
`allowedMethods`, `allowedCalldata` and `limitedCalls` as caveat
enforcers.<Cite src="metamask-caveats-reference" /> But those go into a delegation the dapp constructs
and the user signs — and the documentation is direct about why that path is not offered through the
extension's consent screen: regular delegations are not human-readable, so it is the dapp's
responsibility to provide context, and they cannot be signed through the MetaMask extension, because
if a dapp requests a delegation without constraints the whole wallet can be exposed to the
dapp.<Cite src="metamask-advanced-permissions-concept" />

Read that as the industry's current position, stated by a participant: **a permission gets a
first-class consent screen when the wallet can describe it in a sentence.** "Up to 10 USDC per day"
can be rendered. "Whatever `0x9a3f…` does when you send it these bytes" cannot, and so it does not get
the screen.

<Aside kind="note">
One concrete divergence to plan for. The ERC's `PermissionRequest` names the session account in the
`to` field.<Cite src="erc-7715" /> MetaMask's own description of the same call says the method
requires a `signer` parameter identifying the entity requesting or managing the permission, and that
the kit supports multiple signer types — wallet signers, single-key and multisig signers, and account
signers.<Cite src="metamask-advanced-permissions-concept" /> Two vocabularies for the same slot in the
same flow. This is precisely what the ERC's own text warns about when it declines to enumerate types,
and it is why `wallet_getSupportedExecutionPermissions` plus reading the response back is not defensive
programming here — it is the intended usage.
</Aside>

## Worked example: the grant-to-redeem round trip

**Subgoal — establish what the wallet can do before you show the user anything.** Call
`wallet_getSupportedExecutionPermissions` and intersect its permission types with the ones your
feature can express. If the intersection is empty, your feature does not exist for this wallet, and
the honest UI is a fallback to per-transaction prompts rather than an error.

**Subgoal — request the narrowest permission that still ships the feature.** ERC-7715's security
considerations say dapps should only request the permissions they need, with a reasonable expiration
time.<Cite src="erc-7715" /> Set `isAdjustmentAllowed` deliberately: `true` when the user tightening
the cap is fine, `false` when a smaller cap silently breaks the flow — and remember that `true` also
permits an increase.<Cite src="erc-7715" />

**Subgoal — persist the response, not the request.** Store `context`, `delegationManager`, the
returned `permission.data` values and the returned rules. These are what you are actually holding.

**Subgoal — settle the dependencies before you promise the feature works.** If `dependencies` is
non-empty, the user's account is not deployed and you MUST deploy it by calling each `factory` with
its `factoryData`.<Cite src="erc-7715" /> Do this at grant time, when the user is present and
expecting a wait, not at the moment the first automated action is due.

**Subgoal — redeem through the manager the response named.** Encode the execution — ERC-7715's own
example builds a single-call execution as `(target, value, callData)` packed, with the single-call
execution mode — and call `redeemDelegations([context], [mode], [executionCallData])` on the returned
`delegationManager`.<Cite src="erc-7715" /><Cite src="erc-7710" /> The delegate can be any account
type, using whatever payment or relay infrastructure it prefers, which is why the same context works
whether you send an ordinary transaction or a UserOperation.<Cite src="erc-7715" />

**Subgoal — simulate before every redemption, permanently.** ERC-7710 makes this a requirement rather
than a nicety: dapps MUST NOT assume that having received a delegation in the past guarantees future
execution rights, because delegations can be revoked, expire, or become invalid due to state changes.
Its guidance is to always simulate redemptions before submitting them, handle simulation failures
gracefully by requesting new permissions, consider retry logic with escalating permission requests,
and **be prepared for delegations to become invalid between simulation and
execution**.<Cite src="erc-7710" /> You already have the habit from
[simulate before send](/c/tx-simulate-before-send); here it is normative, and the last clause is the
one the next lesson is entirely about.

<Check type="spot-bug" concept="erc-7715-grant-permissions">
A team ships this grant handler. Name what will break, in the order it will break.

```ts
const [granted] = await provider.request({
  method: 'wallet_grantPermissions',
  params: [{
    chainId: '0x1',
    to: sessionAccount.address,
    permission: {
      type: 'erc20-token-periodic',
      isAdjustmentAllowed: true,
      data: { tokenAddress: USDC, periodAmount: parseUnits('10', 6), periodDuration: 86400 },
    },
  }],
})

await db.savePermission({
  user: userAddress,
  context: granted.context,
  dailyCap: parseUnits('10', 6),
})
showToast('You can now spend up to 10 USDC per day')
```

<Answer>
**It breaks immediately, on the method name.** The current spec defines
`wallet_requestExecutionPermissions`; a wallet implementing the current draft has no
`wallet_grantPermissions` handler, and ERC-7715's backwards-compatibility section says wallets that
do not support the method SHOULD return an error.<Cite src="erc-7715" /> So the first failure is a
JSON-RPC error, which is the *good* outcome — it is loud.

**Then it breaks on the missing feature detection.** There is no
`wallet_getSupportedExecutionPermissions` call, so the app does not know whether this wallet supports
`erc20-token-periodic` on this chain, and the type string is a guess. The ERC does not enumerate
types; support is a per-wallet, per-chain fact you are required to ask for.<Cite src="erc-7715" />

**Then it breaks quietly, and this is the expensive one: `dailyCap` is stored from the request.**
`isAdjustmentAllowed` is `true`, and the wallet MAY attenuate the permission in either
direction.<Cite src="erc-7715" /> The specification states outright that it is not guaranteed the
received values equal the requested ones.<Cite src="erc-7715" /> If the user drags the cap to 2 USDC,
your database says 10, your toast says 10, and your scheduled charge fails on-chain for a reason your
logs will attribute to the chain rather than to the grant. Read `granted.permission.data.periodAmount`
and store that.

**Then it breaks at redemption, because `delegationManager` was never stored.** It is a required field
of the response and is the address redemption is sent to.<Cite src="erc-7715" /><Cite src="erc-7710" />
Holding the `context` without it is holding half a credential.

**Then it breaks for new users, because `dependencies` was ignored.** If the user's account is not yet
deployed, the wallet returns factory entries that MUST be used to deploy it before any redemption can
succeed.<Cite src="erc-7715" /> This failure arrives days later, on the first automated charge, for the
subset of users who granted from a fresh account.

**And there is no expiry.** No `rules` array, so no `expiry` rule, so nothing bounds the permission in
time. ERC-7715's security considerations ask for a reasonable expiration time, and the absence of one
is the difference between a session key and a standing authority.<Cite src="erc-7715" />

**The shape of the fix.** Detect, request, then treat the response as the source of truth for
everything you display, store or schedule against — and re-read it with
`wallet_getGrantedExecutionPermissions` rather than trusting your own copy.<Cite src="erc-7715" />
</Answer>
</Check>

## What this unlocks

**The next lesson** takes ERC-7710's warning — that a delegation can become invalid between simulation
and execution — and turns it around: what happens when *you* are the one trying to invalidate it, and
someone else is racing you.

**The blast-radius lesson** returns to the seven shipping permission types with a different question:
given that they all describe value movement, what is the largest sentence you would have to tell a user
if the grant leaked?

**And the last lesson** is about the screen the wallet renders on your behalf — the one place where the
entire consent for hundreds of future actions is presented, once, by software you do not control.
