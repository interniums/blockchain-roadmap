Three products, three teams, the same complaint written three different ways in three different
issue trackers.

The game: a turn takes about four seconds and produces one on-chain move. A session is forty
minutes. That is roughly six hundred wallet prompts, and the second one is where the player leaves.

The subscription: the charge is due on the fourteenth of each month whether or not the user has a
browser open. There is no moment at which they can be asked.

The limit order: the whole point is that it fires when the price crosses, which is exactly when
nobody is watching.

ERC-7715's motivation section names the same two problems in the same order — that it gets tedious
for a user to manually approve every transaction, especially in highly interactive applications such
as games, and that it is impossible to send transactions for users without an active wallet
connection, which invalidates subscriptions, passive investments and limit
orders.<Cite src="erc-7715" />

The answer the ecosystem converged on is called a session key. This lesson is about what that
actually is, what has to be true before one can exist, and why the name is the most misleading part
of it.

## The word is borrowed, and it borrowed the wrong half

You have shipped web sessions. A user signs in, the server issues a token, the browser sends it back
on every request. The token is not authority — it is a **pointer to** authority that lives on the
server. Delete the row and the token is confetti. The server decides, on every single request,
whether this token still means anything, and it decides for free, instantly, unilaterally.

A blockchain session key inverts every one of those properties. It is not a pointer to authority; it
*is* authority, in the same way your primary key is. There is no server in the request path with a
veto. The only thing standing between the holder of that key and your user's account is code that
was configured in advance and now runs without anybody's supervision.

So the useful reading of the word "session" is: **bounded in time**. That is the only property it
carries over. Everything else that makes a web session feel safe — the central authority, the
instant revocation, the per-request re-check — is absent, and the mechanisms in this module exist to
build approximations of them.

## The definition, said precisely

A **session key** is a keypair — usually generated by your application, not by the user's wallet —
which the user's account has been configured to accept as an authorised signer for a restricted set
of actions over a bounded period.

Unpack the four load-bearing clauses.

**"Generated by your application."** Nothing in any specification requires this, and the wallet
generating it is a legitimate design. But in the common shape, your code calls something like
viem's `generatePrivateKey`, feeds it to `privateKeyToAccount`, and now holds a fresh secp256k1
keypair that has never existed anywhere else.<Cite src="viem-private-key-to-account" /> That
matters because it decides who is responsible for the private half, which is the subject of a later
lesson in this module and is usually a bigger risk than the policy.

**"The account has been configured to accept."** This is the whole trick, and it is why the next
section exists. Acceptance is not a property of the key. It is a property of the account, expressed
as code that the account runs when deciding whether to authorise something.

**"A restricted set of actions."** The restriction is the product. A session key with no restriction
is a copy of the user's account. MetaMask's own documentation says this about its delegation layer
without softening it: without caveat enforcers, a delegation has infinite and unbounded authority to
make any execution the original account can make.<Cite src="metamask-caveat-enforcers" /> The
default is total authority. Every bound you get is one you added.

**"Over a bounded period."** Bounded is doing work. The bound is enforced by the account's
validation, evaluated against a block's timestamp — not by your code noticing the clock ran out.

And one clause that is not in the definition but is the reason anybody wants this: **the user's
primary key is used exactly once, at grant time, and never leaves the wallet.** The session key is
what signs the six hundred moves. If the game's frontend is compromised, the attacker holds a key
that can play the game. That is a categorically different outcome from holding a key that can do
anything, and the entire engineering effort in this module is about making sure the first sentence is
actually true rather than aspirational.

## This is not an ERC-4337 feature, and the docs say so

There is a sentence in the ERC-4337 documentation's own session-keys page that should shape how you
read every tutorial you find: these patterns are **not yet standardized and are implemented
wallet-by-wallet**.<Cite src="erc-4337-session-keys-docs" /> The same page describes the dynamic
form — signing a session token with constraints such as `validUntil` and `targetContract` — as
enforced in `validateUserOp()` by wallet-specific logic, a plugin or auth module, and says plainly
that it is **not natively supported by ERC-4337**.<Cite src="erc-4337-session-keys-docs" />

The one that is finished is the one that does not define session keys. Everything that does define
some part of them is a draft, and ERC-7715 has been a draft since 24 May 2024.<Cite src="erc-7715" />

That is not a reason to avoid the topic. It is a reason to learn the **shape of the problem** —
which dimensions a policy can constrain, where enforcement has to live, what expiry and revocation
each cost — and to treat every library you pick up as one vendor's answer rather than as the answer.
Vendor implementations here are real and shipping: MetaMask's Smart Accounts Kit implements ERC-7715
under the product name Advanced Permissions, with per-permission-type minimum extension
versions.<Cite src="metamask-advanced-permissions-concept" /><Cite src="metamask-supported-permissions" />
They are just not interchangeable, and nothing yet guarantees they will become so.

## Why a plain EOA cannot have one

Try to design a session key for a plain externally owned account and watch it fail in one step.

An EOA's validity rule is a protocol rule. A transaction from that account is valid if the ECDSA
signature over it recovers to that address and the nonce is right. There is no code. There is no
place to put a condition. Whoever holds the private key can do everything the account can do, and
whoever does not holds nothing. Authority is one bit.

You could try to fake it off-chain: keep the real key on your server, have it sign only what your
policy allows. This is not a session key, it is custody with extra steps, and the "policy" is a
property of your codebase rather than of the account. Anyone who reaches that key — including you,
including a compromised deploy — has the whole account, and there is no artifact on-chain that
disagrees.

So scoping requires **code in the validation path**. Two routes exist, and the choice between them
is the first architectural decision in this module.

**Route one: an ERC-4337 smart account.** The account is a contract. Its `validateUserOp` runs when
an operation arrives, and it can implement any rule the validation restrictions allow. The
[EntryPoint](/c/entrypoint) and the [UserOperation](/c/user-operation) machinery you already know is
the delivery mechanism. The cost is that this is a *different address* from the user's EOA, so
assets and history have to move — which for an existing user is not a technical problem so much as a
product one.

**Route two: an EIP-7702-delegated EOA.** The user signs one authorization; their account gains a
[delegation designator](/c/delegation-designator) pointing at smart-account code; and that code runs
with the account as `address(this)`, against the account's storage, at the account's original
address.<Cite src="eip-7702" /> Same address, same assets, same history. Validation logic now exists
where before there was none.

Route two is why the commonly repeated line "session keys require a smart account" is now wrong. It
was true, and the thing that changed is not a library.

<Aside kind="warn">
Route two comes with a constraint from the EIP itself that is easy to skip past. EIP-7702 states
that it is **not possible** to implement a system of permissions at the delegation level, and that
applications needing custom wallet behaviour must use standardised extension or module systems built
on top of the delegated code.<Cite src="eip-7702" /> The delegate is wallet infrastructure, audited
once and reused. Your application's permission lives in a module the wallet's code admits — which is
exactly the layer ERC-7579, ERC-7710 and ERC-7715 are trying to standardise. If you find yourself
designing a delegate contract *for your dapp*, you are operating at the wrong layer. See
[what a delegation actually grants](/c/delegation-designator) for why that layer has no bounds to
offer you.
</Aside>

## One action, traced end to end

Abstractions about "authority" get slippery. Trace a single move in the game and name who holds what
at each step.

**Subgoal — enumerate the keypairs, because the count is the whole story.** There are two. The
user's primary key, inside their wallet, which has never been in your process and will not be. The
session key, generated in your app, whose private half is somewhere you chose — a JavaScript
variable, an IndexedDB record, a server HSM. Two keys, two custody stories, and only one of them is
your problem.

**Subgoal — find the single moment the user's key is used.** Grant time. The user approves a
permission; their wallet signs something that configures the account to accept the session key's
address under a policy. That is the last time the primary key participates in this feature. If your
design has the user re-signing later for anything other than a re-grant or a revocation, the feature
did not do what it claims.

**Subgoal — follow move number thirty-seven.** Your app builds the call — `move(uint8 direction)` on
the game contract — and signs it with the session key. Depending on the route, that signature travels
as a UserOperation to a [bundler](/c/bundler) and then to the EntryPoint, or as an ordinary
transaction to a delegation manager. Either way it reaches the user's account, and the account runs
validation logic that asks one question: **does the policy attached to this signer permit this
call?**

**Subgoal — name the thing that answers that question.** Not your frontend. Not your API. Not the
SDK. A contract, executing on-chain, reading the policy that was stored at grant time. If the answer
is yes, the account executes the move. If no, the operation is rejected and the move does not happen.

**Subgoal — ask what stops move thirty-eight from being `transfer(attacker, everything)`.** The
answer is: only the policy, and only if the account enforces it. Nothing else in the picture is
looking. There is no rate limiter, no fraud team, no server that noticed something odd. If the
policy does not name the target contract, the selector and a cap, then the session key is a copy of
the account with a countdown on it.

That last subgoal is the one to carry forward. Every remaining lesson in this module is an
elaboration of it.

<Check type="explain" concept="session-key-definition">
A team tells you their game "uses session keys, so it's safe — the key only lasts an hour and it's
generated fresh for every play session." Their implementation registers the session key's address on
the user's smart account as an additional owner, with a `validUntil` one hour in the future.

Say what they have built, in one sentence, and name the largest thing that could go wrong.

<Answer>
**What they have built is an hour-long copy of the account.** Registering a key as an *owner* grants
whatever owners can do, which on a typical smart account is everything: transfer the native balance,
move every token, spend every allowance the account has ever granted, and — if the account allows
owner management — add a second owner with no expiry at all.

That last clause is the largest thing that could go wrong, and it is the one that survives the hour.
An attacker who obtains the session key inside its window does not need to hurry: their first action
is to use the owner authority to install a permanent one. The expiry then fires on a key nobody
cares about. **A time bound on a key that can modify the account's authority set is not a time
bound.**

The two words doing the false work are "session key". What makes something a session key is not that
it is temporary and not that it is freshly generated — it is that the account's validation logic
constrains what it may do. This implementation has a temporary key and no policy, which is the
`validUntil` field of a session key with none of the rest of it.

**The rewrite.** Register the key through a validator that constrains the target contract, the
function selectors, a value cap and the window — never as an owner. The sentence you want to be able
to say at the end is "if this key leaks, an attacker can play the game as this user until the hour
is up", and that sentence is only true when owner-level authority was never granted.
</Answer>
</Check>

## What this unlocks

**The next lesson** takes "the policy" from a placeholder to a list. There are eight or nine
dimensions a real policy constrains, each omission hands an attacker a choice, and the omissions are
invisible once the happy path works.

**The lesson after that** goes underneath the SDK, into ERC-7579's module types and ERC-7562's
validation rules, and answers the question that makes session-key modules look so awkward: why can a
validator not simply read `block.timestamp` and compare?

**The wallet-facing half** — ERC-7715 and ERC-7710 — is where you stop generating the policy
yourself and ask the user's wallet to grant one. It is also where you learn how much of what you
requested you actually got.

**And in the security track**, the artifact this module produces is an
[actor-capability row](/c/capability-not-role): your app is now an actor with a named, bounded,
time-limited capability against the user's account. Writing that row honestly is the deliverable.
The rest of this module is about making it a short sentence rather than a long one.
