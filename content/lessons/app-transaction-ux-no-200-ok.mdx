The ticket said: *"Your app told me my deposit failed. My wallet says the ETH is gone. Which one is
lying?"*

Neither was. The transaction had been mined, had reverted, and had been charged for the gas it burned
getting to the revert. The app's deposit flow had been written by someone competent, in the shape every
competent web engineer writes:

```ts
try {
  await sendDeposit(amount)
  toast.success('Deposit confirmed')
} catch (e) {
  toast.error('Deposit failed')
}
```

Four outcomes exist. This code has two branches. The other two — *it was mined and it reverted*, and
*it was never mined at all* — land wherever the shape of the promise happens to put them, which is
usually the success branch and the error branch respectively, both wrong.

This module is about building the missing states. This lesson builds the frame: what the chain actually
tells you, when, and what each answer does and does not mean.

## The API returns an identifier, not a result

Broadcasting is one JSON-RPC call. `eth_sendRawTransaction` "Creates new message call transaction or a
contract creation for signed transactions", and returns "DATA, 32 Bytes - the transaction hash, or the
zero hash if the transaction is not yet available."<Cite src="ethereum-org-json-rpc" />

That is the entire response. Not a status. Not a receipt. A 32-byte identifier and an implicit "a node
took these bytes".

viem is direct about what that implies for the library call on top of it. `writeContract` "internally
sends a transaction – it **does not** validate if the contract write will succeed (the contract may
throw an error)", it returns a transaction hash, and — unlike `readContract` — it does not return the
function's output data at all.<Cite src="viem-write-contract" /> The recommendation on the same page is
to pair it with `simulateContract`, which is [lesson five](/c/tx-simulate-before-send) and the single
biggest lever in this module.<Cite src="viem-write-contract" /><Cite src="viem-simulate-contract" />

You already know why the call cannot answer more than this from
[the mempool as a broadcast](/c/mempool-is-a-public-broadcast): the node you spoke to is one node,
holding one view, with no authority over what any block contains. It is not a server that will do your
work. It is a peer you handed a signed message to.

## The state machine, and the observation that moves you along it

Here is the whole thing. What matters is not the list of states — it is that every transition is driven
by *an observation you have to go and make*, not by a message the chain pushes at you.

And the three edges that leave the happy path, each of which the rest of this module gives a lesson to:

- **Replaced** — a different transaction from the same sender at the same nonce got there first.
- **Dropped** — evicted from pools, never mined, no announcement.
- **Included and reverted** — mined, charged, accomplished nothing.

Notice the asymmetry in the *how you learn* column. Everything up to "broadcast" is synchronous and
local. Everything after it is you polling, and the thing you are polling for is *absence turning into
presence*. That asymmetry is the source of nearly every bug in this area.

## "Not yet" and "never" have the same shape

`eth_getTransactionReceipt` takes a hash and returns the receipt — and the documentation notes plainly
that "the receipt is not available for pending transactions", returning `null` when none was
found.<Cite src="ethereum-org-json-rpc" />

So a `null` receipt means one of:

- The transaction is in a pool and will be mined in twenty seconds.
- The transaction is in a pool and cannot be mined at the moment, because the base fee is above the
  cap the sender authorised (the [next lesson](/c/tx-stuck-from-fee-cap)).
- The transaction was dropped from every pool that had it, hours ago.
- The transaction was replaced, and a *different* hash carries the user's action now.
- The node you are asking has simply not caught up.

One value. Five situations. Three of them are terminal for this hash and two are not, and no amount of
waiting distinguishes them — which is the reason the rest of this module exists.

### What the client library does with that, and what it leaves to you

viem's `waitForTransactionReceipt` is the polling loop written out. Its documented defaults are worth
memorising because they are product decisions you are inheriting by not changing them:
`confirmations: 1`, `timeout: 180_000` milliseconds, `retryCount: 6`, and a `retryDelay` of
`({ count }) => ~~(1 << count) * 200` — exponential
backoff.<Cite src="viem-wait-for-transaction-receipt" /> wagmi's `useWaitForTransactionReceipt` wraps
the same action, taking `hash`, `confirmations` and `pollingInterval`, with polling defaulting to the
config's interval.<Cite src="wagmi-use-wait-for-transaction-receipt" />

Three minutes is a long time to hold a spinner and a very short time in the life of a transaction whose
fee cap is under the current base fee. When that timeout fires you get a
`WaitForTransactionReceiptTimeoutError` — a distinct exported class, alongside `TransactionNotFoundError`
and `TransactionReceiptNotFoundError`, all extending `BaseError`.<Cite src="viem-errors-glossary" />

**That the library gives these three different names is the whole point.** They are not severities of
one failure. `TransactionNotFoundError` says the node cannot find the transaction at all. The timeout
says the library gave up after three minutes. Neither says the transaction failed, and neither says it
will not be mined. If your `catch` block treats them the same as a revert, you have collapsed the
distinction the library went to the trouble of preserving — and you already know from
[the viem error hierarchy](/c/viem-error-hierarchy) that the way to keep it is to walk the `cause`
chain and branch on the class, never on the message string.

<Aside kind="note">
A timeout on the client is not a timeout on the chain. Nothing expires. Under
[EIP-1559](/c/eip-1559-fee-fields) the validity rule is
`transaction.max_fee_per_gas >= block.base_fee_per_gas`,<Cite src="eip-1559" /> and a base fee that
falls tomorrow makes today's parked transaction includable tomorrow. Meanwhile the node-side pool has
its own, unrelated clocks: go-ethereum's `--txpool.lifetime` default is `3h0m0s`, and it governs the
"maximum amount of time non-executable transaction are queued" — one client's default, for one
category of transaction, configurable by whoever runs the node.<Cite src="geth-cli-options" />
</Aside>

## Mined is not succeeded

The receipt exists. The transaction is in a block. It is in the receipts trie, its gas was charged, and
its `status` field says it reverted.

You have the mechanism from [fees charged on failure](/c/fees-charged-on-failure) and
[receipt contents](/c/receipt-contents). What is new here is only the interface consequence, and it is
blunt: **a "confirmed" toast fired on receipt arrival is wrong exactly as often as your contract
reverts.** For a well-simulated flow that is rare. For anything touching allowances, slippage bounds,
deadlines or another protocol's state, it is not rare at all.

The pattern to look for in a codebase is any place a receipt is awaited and then used without reading
`status`:

```ts
// The bug, in its usual habitat.
const hash = await walletClient.writeContract(request)
const receipt = await publicClient.waitForTransactionReceipt({ hash })
await creditUser(userId, amount)   // <- fires on reverted receipts too
```

`waitForTransactionReceipt` resolves on *inclusion*. Reverting is a normal, fully-included outcome. The
awaited value carries the answer; the code above never opens it.

<Misconception
  belief="If the transaction had failed, awaiting the receipt would have thrown."
  reality="It resolves. A reverted transaction is an included transaction, and the receipt is a successful response describing an unsuccessful execution. The status lives in the resolved value, not in the rejection path."
  why="Promise rejection is how every other client signals failure, so the success path feels like it has already been filtered. Here the filter is a field you have to read."
  src="viem-wait-for-transaction-receipt"

## Worked example: the type that makes the bug unrepresentable

The fix is not a longer `if`. It is a type where the four outcomes cannot be collapsed, so the compiler
asks you about the ones you forgot.

**Subgoal: name the states, so that "pending" stops being a single thing.** The point of writing them
out is that each of the three off-path states gets a place to live, and each carries the data the UI
needs to say something specific.

```ts
type TxState =
  | { kind: 'idle' }
  | { kind: 'simulating' }
  | { kind: 'simulation-failed'; reason: string }
  | { kind: 'awaiting-signature' }
  | { kind: 'declined' }
  | { kind: 'pending'; hash: `0x${string}`; nonce: number; broadcastAt: number }
  | { kind: 'replaced'; nonce: number; reason: 'repriced' | 'cancelled' | 'replaced'; hash: `0x${string}` }
  | { kind: 'likely-dropped'; nonce: number }
  | { kind: 'reverted'; hash: `0x${string}`; blockNumber: bigint }
  | { kind: 'confirmed'; hash: `0x${string}`; blockNumber: bigint; confirmations: number }
```

Two details in there are the whole module in miniature. `pending` carries a **nonce**, not just a hash,
because the hash stops identifying the user's action the moment a replacement happens
([lesson four](/c/tx-replacement-changes-the-hash)). And `likely-dropped` is hedged in its name, because
dropping is an inference you draw rather than an event you receive
([lesson two](/c/tx-dropped)).

**Subgoal: map each observation onto exactly one transition, so no observation lands in two places.**

```ts
const hash = await walletClient.writeContract(request)
setState({ kind: 'pending', hash, nonce, broadcastAt: Date.now() })

try {
  const receipt = await publicClient.waitForTransactionReceipt({
    hash,
    confirmations: 1,
    onReplaced: (r) =>
      setState({ kind: 'replaced', nonce, reason: r.reason, hash: r.transaction.hash }),
  })
  setState(
    receipt.status === 'success'
      ? { kind: 'confirmed', hash: receipt.transactionHash, blockNumber: receipt.blockNumber, confirmations: 1 }
      : { kind: 'reverted', hash: receipt.transactionHash, blockNumber: receipt.blockNumber },
  )
} catch (e) {
  // Timeout is not failure. It is the end of this library call, not of the transaction.
  setState({ kind: 'likely-dropped', nonce })
}
```

The `onReplaced` callback is not decoration. It fires with a `reason` of `'replaced'`, `'repriced'` or
`'cancelled'`, plus the replacing transaction and its receipt, and replacement is detected because
"Transactions are replaced when they are sent from the same
nonce".<Cite src="viem-wait-for-transaction-receipt" /> Three lessons from now that callback is the
difference between an order that settles and an order that hangs forever.

**Subgoal: decide what each state renders, because a state machine nobody can see is just a
refactor.** The test of this design is whether a human can write one sentence per state that is true
and actionable. `reverted` is "it ran and was rejected — here is why, and here is what to change".
`likely-dropped` is "we have stopped watching; it may still land — here is how to check".
`replaced` is "you replaced this from your wallet; we are following the new one now". If a state has no
distinct sentence, you did not need it. If two states share a sentence, you have a bug hiding in the
merge.

<Aside kind="warn">
The `catch` above is deliberately crude — it treats every throw as "probably dropped", which is wrong
for a network error and wrong for a node that is behind. The honest version branches on the error class
from the errors glossary and only reaches `likely-dropped` after checking the account's nonce, which is
the procedure the next lesson builds.<Cite src="viem-errors-glossary" />
</Aside>

## The state machine outlives the tab

There is one more consequence of "everything after broadcast is polling", and it is the one that most
often gets discovered in production rather than in design.

A request/response call is scoped to the page that made it. If the user navigates away mid-request,
nothing was going to happen anyway. A transaction is not scoped to anything. It was signed, it was
broadcast, and it will be included or not entirely independently of whether your component is still
mounted, whether the tab is open, whether the laptop is awake, or whether your app was deployed over
five minutes ago.

So the state above cannot live only in a component. It has to live somewhere that survives:

- **A local store keyed per account and chain**, so a returning user sees the transaction they left
  behind rather than a clean slate. `localStorage` is enough; what matters is that the key includes the
  address and the chain id, because the same browser is used by several accounts and the same nonce
  exists on every chain.
- **A server-side record, if anything off-chain depends on the outcome.** If a confirmation causes you
  to credit a balance, ship an item or send an email, the browser is the wrong place for the watcher —
  it is a client that can close. The chain does not need your app to be running; your *reaction* to the
  chain does.
- **A reconciliation job**, because both of the above can miss. The chain is the only durable record,
  and reconstructing from it means asking about an account and a nonce, not replaying your own
  in-memory events.

This is also where the two halves of a product's transaction handling meet and usually diverge. The
front end is optimising for a spinner that resolves quickly. The backend is optimising for never
crediting something twice and never missing a credit. They will disagree about how long to wait, and
they should — that disagreement is the subject of
[the confirmation-policy lesson](/c/tx-confirmation-policy-is-a-product-decision), where the answer
turns out to depend on what each side does next rather than on a number either of them can look up.

<Aside kind="note">
There is a small ordering hazard worth designing around now rather than debugging later. Your server
and your browser can observe the same transaction in either order, and neither observation is
authoritative about the other. If the browser writes "confirmed" to your API and the server's own
watcher also writes "confirmed", both paths must be idempotent on the same key. That key is not the
hash — a point lesson four makes at length — and building the write path around
`(address, chainId, nonce)` from the start costs nothing today and saves a migration later.
</Aside>

## The primitive that looks like it deletes all of this

There is a newer path worth knowing about precisely so you do not over-read it. EIP-7966 specifies
`eth_sendRawTransactionSync`, and viem ships `sendTransactionSync` and `writeContractSync` on top of
it, which block until a receipt rather than returning a hash.<Cite src="eip-7966" /><Cite src="viem-send-transaction-sync" />

That is a genuine improvement in ergonomics on the chains it suits, and viem's own documentation is
explicit that those are chains with low block times and fast finality — not
mainnet.<Cite src="viem-send-transaction-sync" />

More importantly: it changes where the waiting happens, not whether the states exist. A synchronous
send still returns a receipt whose `status` can be reverted. It still sits behind a nonce that can be
blocked. It can still return nothing because the transaction was never included. Collapsing broadcast
and wait into one call hides the pending state from your code; it does not remove it from the world,
and a UI written as though it did will have no vocabulary for the cases where the call comes back
empty-handed.

<Answer>
**Moment 1 — a hash exists.** Correct: "submitted", with the hash and an explorer link, and no claim
about the outcome. The naive version says nothing different from what it will say at moment 4, because
it only has "loading" and "done".

**Moment 2 — repeated `null`.** Correct: "waiting for inclusion", and after a while a second line that
distinguishes *parked* from *gone* — which requires the nonce check, not more waiting. The naive version
shows the same spinner for three minutes with no change, and the user, reasonably, refreshes the page.
On refresh the in-memory state is lost and the app now believes nothing is happening at all.

`null` is not an error here: the documentation states the receipt is not available for pending
transactions and returns `null` when none was found.<Cite src="ethereum-org-json-rpc" /> Polling
`null` is the expected behaviour of a transaction that is proceeding normally.

**Moment 3 — the timeout throws.** Correct: "we have stopped watching; this may still be mined", plus a
way to resume watching. The naive version shows "Deposit failed", which is the single most damaging
error message in this module, because it is false in a way that causes the user to act — they submit
again, from a nonce that is now behind a stuck one, and make the queue worse.

The throw is a `WaitForTransactionReceiptTimeoutError`, and it is a different class from
`TransactionNotFoundError` and from `TransactionReceiptNotFoundError` precisely so you can tell these

default you inherited, not a property of the chain.<Cite src="viem-wait-for-transaction-receipt" />

get one, the gas that was charged, and the action to take. The naive version has two failure modes
here, and both are common: if it only checks receipt existence it says "confirmed", which is the
original support ticket; if it never rechecks after the timeout it says "failed" for a wrong reason and
never learns the real one.

**The field available at moment 1.** The **nonce** of the transaction you sent. With it you can compare
against `eth_getTransactionCount` for your address — a call whose block parameter accepts `latest` and
`pending` among others<Cite src="ethereum-org-json-rpc" /> — and that comparison distinguishes "the
slot is still open, so this may yet land" from "the slot has been consumed by something else, so this
hash will never appear". Nothing else you hold at moment 1 can make that distinction, which is why the
state type above carries the nonce and not only the hash.
</Answer>
</Check>

## What this unlocks

**The next two lessons split "pending" apart.** Parked because the base fee is above the fee cap, and
dropped from the pools entirely, are the two situations that produce identical silence and need
opposite messages. The nonce is the instrument that tells them apart.

**Lesson three replaces the Cancel button with what it really is** — a race you can lose, at a price.

**And the type above is the module's spine.** Every lesson from here adds a state to it or adds a
transition into one. By the end it also carries a confirmation policy per action, because "confirmed"
turns out to be a product decision rather than a chain event — which is the question the second half of
this module is built around.
