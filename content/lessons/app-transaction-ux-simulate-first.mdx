Count the states the previous four lessons built. Awaiting signature, pending, parked, dropped,
replaced with three reasons, reverted, confirmed. Each needs copy, a test, and a decision about what
your backend does.

Now notice that a large fraction of the traffic through those states never had any chance of
succeeding. The allowance was not set. The deadline had passed. The balance was short by dust. The
pool had moved past the slippage bound. Every one of those transactions was signed by a user, paid for
by a user, occupied a block, and returned nothing.

Running the call first turns all of them into a sentence shown *before* the wallet prompt. No
signature, no gas, no pending state, no reverted receipt to explain afterwards. One read call, and the
most expensive states in your interface stop being reachable.

## What the two calls actually do

`writeContract` "internally sends a transaction – it **does not** validate if the contract write will
succeed (the contract may throw an error)", and it returns a transaction hash rather than the
function's output.<Cite src="viem-write-contract" /> Its own documentation recommends pairing it with
simulation.<Cite src="viem-write-contract" />

`simulateContract` "**simulates**/**validates** a contract interaction", and it is described as useful
for retrieving return data and revert reasons of contract write functions.<Cite src="viem-simulate-contract" />
It returns two things: `result`, the value the function would have returned, and `request`, which you
hand straight to `writeContract`.<Cite src="viem-simulate-contract" />

```ts
const { result, request } = await publicClient.simulateContract({
  address, abi, functionName: 'deposit', args: [amount], account,
})
const hash = await walletClient.writeContract(request)
```

Two properties of that pairing matter more than the ergonomics.

**You get the return value.** `writeContract` cannot give you one — a transaction's return data is not
in the receipt — so `result` is the only way to know what the call would produce. For a deposit that
returns shares minted, or a swap that returns amount out, this is the number your confirmation screen
should be showing, and simulation is where it comes from.<Cite src="viem-simulate-contract" />

**You get the revert reason, decoded, before signing.** The failure arrives as a thrown viem error with
the reverting error in its `cause` chain, which is the machinery you already have from
[the error hierarchy](/c/viem-error-hierarchy) and [typed reverts](/c/viem-typed-revert). A custom
error with named arguments becomes "you need 4.2 more USDC" instead of "execution reverted", and it
becomes that at a moment when the user can still do something about it.

## The correction: which state are you simulating against

Almost every description of this technique, including the one in this module's own concept summary,
says you simulate against *pending* state. Check the default before you rely on it.

viem's `simulateContract` accepts `blockNumber` and `blockTag`, and `blockTag` **defaults to
`'latest'`**.<Cite src="viem-simulate-contract" /> `latest` is the most recent mined block. It does not
include anything sitting in a mempool.

`pending` is a real option — the JSON-RPC default block parameter accepts a block number or the tags
`latest`, `earliest`, `pending`, `safe` and `finalized`<Cite src="ethereum-org-json-rpc" /> — and it
means something narrower than it sounds. "Pending" is a block a node has speculatively assembled from
its own pool. You already know from [the node-local mempool view](/c/mempool-view-is-node-local) that
this pool is one node's opinion, so a pending simulation is an opinion about an opinion. It is
sometimes more accurate than `latest` and sometimes less, and providers differ in what they will build.

The honest statement is therefore narrower than the folklore: **simulation checks the call against a
recent state, and the default is the last mined block.** If your own application has just sent a
transaction that this one depends on — an approval, then a swap — `latest` will not see it, and the
simulation will fail for a reason that has already been fixed. That case wants an explicit tag, or a
wait, or a batch.

viem's own documentation is explicit about the sharper version of this with state overrides: simulating
"based on a fake state" means "making a transaction based on the returned `request` object might fail
regardless of the simulation result".<Cite src="viem-simulate-contract" /> Overrides are a debugging
instrument, not a pre-flight check.

## What simulation removes, and what it does not

The value of this technique is a specific, enumerable list, and being precise about the boundary is what
stops it being oversold.

**Removed — deterministic failures of the current state.** Missing allowance. Insufficient balance.
Paused contract. Caller not on the allowlist. Expired deadline. Wrong function arguments. Zero address.
Anything the contract checks that depends only on state that is not about to change. This is the
majority of reverts in most applications by a wide margin, and it is the reason the technique is worth
its round trip.

**Not removed — anything competitive or time-sensitive.** A slippage bound that was fine when you
simulated and is not when you land. A liquidation someone else got to first. An oracle update between
the two moments. A deadline that expires while the wallet prompt is open. This is the
[simulation is not a guarantee](/c/viem-simulation-is-not-a-guarantee) boundary, and it is why the
reverted state stays in your state machine no matter how good your pre-flight is.

**Not removed — gas.** Simulation is not estimation, and the distinction has teeth you already know:
[estimation is a search](/c/estimategas-is-a-search) with its own
[failure modes](/c/estimategas-failure-modes), and [EIP-150's 63/64 rule](/c/estimategas-63-64) means a
correctly estimated top-level limit can still starve a deep sub-call.<Cite src="eip-150" /> A
simulation that succeeds says nothing about whether the limit you send will be enough.

<Aside kind="note">
There is a newer failure mode in this area that older material does not mention. EIP-7825 caps the gas
a single transaction may use, independently of the block limit,<Cite src="eip-7825" /> so a very large
transaction can be well-formed, simulate correctly at that gas, and still be rejected for exceeding the
per-transaction ceiling. Batching work into one enormous call is no longer bounded only by what fits in
a block.
</Aside>

**Not removed — the user declining.** Which is worth saying out loud because it is the most common
"failure" in most funnels and it is not a failure at all. Simulation moves it earlier: the user now
declines a prompt they have been given a reason to trust, instead of declining one that appeared with
no explanation.

## Worked example: the pre-flight, and where its output goes

**Subgoal: make simulation the only path to `writeContract`, structurally rather than by convention.**
If the write helper accepts raw parameters, someone will eventually call it with raw parameters. Give
it a signature that only accepts a simulated `request`, and the invariant is enforced by the type
system rather than by review.

**Subgoal: turn the thrown error into the one sentence the user needs.** The chain of work here is
already yours: walk the `cause` chain to find the reverting error rather than matching on message
strings,<Cite src="viem-errors-glossary" /> decode it against the ABI, and map it through the
[four-bucket triage](/c/error-triage-taxonomy) so that
[the message names the next action](/c/error-message-must-name-the-next-action). Simulation is what
makes that machinery worth building, because it is what delivers the error at a moment when there is a
next action to name.

**Subgoal: use `result`, do not throw it away.** This is the step most implementations skip. The
simulation already computed what the call returns; put it on the confirmation screen. "You will receive
1,204.31 shares" is a different product from "Confirm", and it costs nothing extra because you have
already paid for the call.<Cite src="viem-simulate-contract" />

**Subgoal: decide what a *stale* simulation means for this action.** The result was computed against a
block that is no longer the head. For a deposit into a quiet vault, staleness is irrelevant. For a swap
with a tight bound, a simulation from thirty seconds and three blocks ago is close to worthless. The
design question is whether you re-simulate on new blocks, and the honest answer differs per action —
which is the same shape of question as the confirmation policy the next lesson is about, arriving from
the other end of the lifecycle.

An exchange interface simulates every swap before prompting, and shows the decoded revert reason when
simulation fails. Their reverted-transaction rate falls sharply but does not reach zero. The remaining
reverts cluster into three groups:

1. Swaps submitted during periods of rapid price movement
2. Swaps by users who had approved the token in a transaction sent moments earlier
3. A handful with no obvious pattern, all from one integration partner

For each group, say whether simulation should have caught it, why it did not, and what change would.

<Answer>
**Group 1 — simulation could not catch these, and no change to simulation will.** The revert is a
slippage bound failing against state that changed between the simulated block and the included block.
Simulation ran against one block; other people traded in the blocks after
it.<Cite src="viem-simulate-contract" /> This is the residual the technique cannot remove, and the
correct responses are product responses rather than technical ones: re-simulate when the head advances
and update the quote, shorten the window between quote and signature, make the slippage bound an
explicit user choice with its consequence stated, and keep the reverted state in the UI with copy that
explains price movement rather than implying a bug.

**Group 2 — simulation should have caught these, and the default block tag is why it did not.**
`blockTag` defaults to `'latest'`, the last mined block.<Cite src="viem-simulate-contract" /> The
approval was sent moments earlier and is not mined yet, so the simulated state still shows no
allowance — and the interface, seeing a simulation failure it does not expect on a flow it just
completed, either blocks a valid swap or the team disables the check for this path and ships the revert
instead.

Three fixes, in increasing order of quality. Simulate at `'pending'` for this specific step, accepting
that the answer is one node's speculative view.<Cite src="ethereum-org-json-rpc" /> Or wait for the
approval's receipt before enabling the swap, which is correct and slow. Or make the two calls one
user-visible action so the ordering is the wallet's problem rather than yours — which is
[the last lesson in this module](/c/tx-one-intent-many-transactions), and is the answer that also fixes
the double prompt.

**Group 3 — this is not a simulation problem, it is a reporting problem.** One partner, no pattern,
means either a different code path that skips the pre-flight, or a different RPC endpoint whose view
disagrees, or errors arriving in a shape the triage does not recognise and being silently dropped into
a generic bucket. The first move is not to change the simulation; it is to record, per reverted
transaction, whether a simulation ran, against which block, and what it returned. Without that field
you cannot tell "the check was skipped" from "the check passed and the world moved", and those need
opposite fixes.
</Answer>
</Check>

## What this unlocks

**The states you kept are the ones worth designing.** After this lesson, `reverted` is rare and
genuinely informative rather than routine — which makes it worth the copy, the alert and the
investigation it will now get.

**The next half of the module is about the other end.** Simulation shrinks the failures before
inclusion. Everything after this is about what "confirmed" means once inclusion has happened, how sure
you need to be before acting on it, and what happens when the chain changes its mind.

**And one measurement is worth taking this week:** count how many of your reverted transactions in the
last month would have been caught by a simulation against `latest`. In most applications the number is
uncomfortable, and it is the strongest argument you will ever have for spending one round trip.
