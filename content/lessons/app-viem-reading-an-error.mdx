Here is a viem error as it arrives in a console. A version of this was posted to the viem repository by
someone whose contract was full of custom errors, who knew one of them had fired, and who could not
find its name anywhere in the output.<Cite src="viem-discussion-1789" />

```text
ContractFunctionExecutionError: RPC Request failed.

Raw Call Arguments:
  from:  0x6A83…2D3F
  to:    0x37fF…C2d2
  data:  0xd21c1215…

Contract Call:
  address:   0x37fF…C2d2
  function:  book(uint256 roomId, uint128 checkInDate, uint128 checkOutDate, …)
  args:      (1, 1708038000, 1708210800, …)
  sender:    0x6A83…2D3F

Docs: https://viem.sh/docs/contract/simulateContract
Details: VM execution error.
Version: viem@2.7.3
```

The class is `ContractFunctionExecutionError`. It is not `ContractFunctionRevertedError`. There is no
error name, no arguments, no selector. The reflex at this point is to reach for
`error.message.includes(...)`, and that reflex is what this lesson exists to replace.

Three things are true of that block at once, and each is a section below. Not one line of it is a
string viem composed for you to read back — every line is a field, printed. The outer class name is
nearly uninformative, because *every* failure of a contract action arrives wearing it. And whether the
error name was recoverable was decided by an argument you passed before the call, not by anything the
chain sent back.

## The message is assembled, which is exactly why you must not parse it

viem's errors glossary opens with the sentence that carries the whole design: all errors in viem
extend `BaseError`.<Cite src="viem-errors-glossary" /> It then lists them by area — ABI, Account,
Chain, Contract, Encoding, Estimate Gas, Node, Request, RPC, Transaction, Transport and more — roughly
a hundred exported classes.<Cite src="viem-errors-glossary" /> That list is the interface. The text is
not.

`BaseError` carries five fields beyond the standard `Error` surface: `shortMessage`, `details`,
`metaMessages`, `docsPath` and `version`. Its constructor builds `message` by joining them in a fixed
order — short message, meta messages, a `Docs:` line, a `Details:` line, a `Version:`
line.<Cite src="viem-base-error-source" /> The console output above decomposes against that list
exactly:

| Line in the output | Field it came from |
|---|---|
| `RPC Request failed.` | `shortMessage` |
| `Raw Call Arguments:` … `Contract Call:` … | `metaMessages` |
| `Docs: …` | derived from `docsPath` |
| `Details: VM execution error.` | `details` |
| `Version: viem@2.7.3` | `version` |

So a regular expression over `error.message` is a parser recovering structure that existed in typed
form one function call earlier. It breaks when a `metaMessage` is added, when a provider changes its
wording, when the short message is reworded in a patch release — and viem ships a lot of patch
releases, with `latest` on the npm registry at 2.55.19 on 26 August 2026.<Cite src="npm-viem-dist-tags" />

One detail from the constructor explains a confusing case later. `details` is not the error's own
text: if the cause is itself a `BaseError`, `details` is copied from *that* error's `details`,
otherwise it is the cause's `message`.<Cite src="viem-base-error-source" /> `Details: VM execution
error.` above is therefore the node's own words, hoisted up through however many wrappers. It is the
most useful line in the block and the one furthest from the class name.

## The cause chain, and what `walk` actually does

Errors nest. A revert arrives as a JSON-RPC error; viem lifts that into a typed node error, wraps it in
a contract-level error, and wraps that in a per-action error, each layer keeping the one beneath it in
the standard `cause` property. `BaseError.walk` traverses the resulting list, and its two overloads
behave very differently:

```ts
walk(): Error                                  // deepest link in the chain
walk(fn: (err: unknown) => boolean): Error | null   // first link matching fn, else null
```

The implementation is a four-line recursion: if a predicate was supplied and it matches, return that
link; otherwise, if the error has a defined `cause`, recurse into it; otherwise return `null` when a
predicate was supplied, and the current error when one was not.<Cite src="viem-base-error-source" />
Both overloads get misused.

**`walk()` with no argument returns the *bottom* of the chain, not the top.** That is the root cause —
often an `RpcRequestError` holding the raw provider payload — good to log, bad to branch on, because
its class depends on which provider you happened to hit.

**`walk(fn)` returns the first match from the outside in, and `null` when there is no match.** The
`null` is the part people forget: it comes back on every failure that was not a decodable revert — a
timeout, a rate limit, a rejected prompt — so the result needs a second `instanceof` check before you
touch `.data`, which is what the canonical answer in the viem discussion
does.<Cite src="viem-discussion-1789" />

```ts
if (error instanceof BaseError) {
  const revert = error.walk(e => e instanceof ContractFunctionRevertedError)
  if (revert instanceof ContractFunctionRevertedError) {
    // revert.data?.errorName, revert.data?.args
  }
}
```

That second check looks redundant and is not: `walk` returns `Error | null`, so the narrowing has to
happen in your code.<Cite src="viem-base-error-source" />

## Why the outer class tells you almost nothing

viem builds contract errors in a single function whose logic is short enough to state
completely.<Cite src="viem-get-contract-error-source" /> First it locates the interesting link: the
first error in the chain with a `data` property, falling back to the deepest link if none
does.<Cite src="viem-get-contract-error-source" /> Then it decides whether that link is a revert. It is
one if the JSON-RPC error code is `3` — viem names that constant `EXECUTION_REVERTED_ERROR_CODE` — or
`-32603` (internal error) with some payload attached, or `-32000` (invalid input) whose details are the
literal string `execution reverted` and which carries
data.<Cite src="viem-get-contract-error-source" /><Cite src="viem-rpc-errors-source" />
Only then does it construct a `ContractFunctionRevertedError`; otherwise the original error is kept
unchanged as the cause. And then, in every case without exception, it wraps whatever it has in a
`ContractFunctionExecutionError` carrying the ABI, args, address, function name and
sender.<Cite src="viem-get-contract-error-source" /><Cite src="viem-contract-errors-source" />

That last sentence answers the opening puzzle. A DNS failure during `readContract`, a 429 from your
provider, a dismissed wallet prompt, a genuine `InsufficientBalance` — all four surface as
`ContractFunctionExecutionError`, because that class is a context wrapper, not a diagnosis. In the dump
above, the node returned an error satisfying none of the three revert conditions, so no
`ContractFunctionRevertedError` was constructed and there was nothing to decode: the provider said `VM
execution error` in a field viem could not map, which is
[a whole category](/c/provider-error-shape-drift) the error-surfaces module takes apart.

## `ContractFunctionRevertedError`, field by field

When the revert *is* constructed, four properties matter, and they are not
interchangeable.<Cite src="viem-contract-errors-source" />

**`data`** holds the decoded result: the ABI item, the `errorName`, and the `args`. This is the typed
prize — a custom error's name and its actual parameters, in the types the ABI declared.

**`raw`** holds the original hex the chain returned, kept whether or not decoding succeeded. It is the
escape hatch: if the selector was not in the ABI you passed, you still have the bytes and can try
[`decodeErrorResult`](/c/viem-decode-error-result) against a different ABI
later.<Cite src="viem-contract-errors-source" /><Cite src="viem-decode-error-result-doc" />

**`reason`** is a string, populated for exactly two of the
[four shapes revert data can take](/c/four-revert-shapes). If the decoded error name is `Error`, the
reason is the string argument — the legacy `require("...")` form. If it is `Panic`, viem looks the
numeric code up in its own table and puts the human phrase there.<Cite src="viem-contract-errors-source" />
For a custom error `reason` stays undefined and the information lives in `data`, so a handler that
reads only `reason` silently handles old contracts and drops everything written since
[custom errors](/c/sol-custom-error) became normal.

**`signature`** is populated only in the failure case: viem tried to decode, the selector was not in
the ABI, and it recorded the four bytes instead, along with meta messages telling you the signature was
not found on the provided ABI.<Cite src="viem-contract-errors-source" /> If `signature` is set, your
ABI is wrong or incomplete — the chain did its job.

A fifth outcome is not a revert at all and is constantly mistaken for one.
`ContractFunctionZeroDataError` says the function returned no data, and its meta messages name the
three causes: the contract does not have that function, the parameters may be invalid, or the address
is not a contract.<Cite src="viem-contract-errors-source" /> The third is the common one — usually an
address from the wrong chain, or a proxy never deployed where you think.

## Decoding stops at the ABI you passed

Decoding runs `decodeErrorResult` against the ABI supplied to the action — the same ABI whose
[`as const` declaration](/c/viem-abi-const-inference) gave you the argument
types.<Cite src="viem-contract-errors-source" /><Cite src="viem-decode-error-result-doc" /> No registry
of selectors is consulted on your behalf and no lookup crosses the network.

So the errors you can decode are the ones defined in the interface you are calling, and "anything else"
covers a great deal of ordinary code: a revert raised inside a linked library, a token's own error
[bubbled up](/c/revert-bubbling) through the contract you called, an error defined on an implementation
when your ABI is the proxy's, an error from a router two hops down. The four bytes are correct and your
dictionary does not contain the word. The fix is unglamorous: concatenate the ABIs you might need into
the one you pass, or keep `raw` and re-decode against a wider ABI later.
[Which ABI you need is itself a question with a wrong intuitive answer](/c/decode-needs-the-right-abi),
and the error-surfaces module answers it properly.

## The string matching viem does so that you do not have to

There is an honest complication in "never match on strings" that would surprise you the first time you
read viem's source. Node-level errors — `InsufficientFundsError`, `NonceTooLowError`, `IntrinsicGasTooLowError`,
`FeeCapTooLowError` and the rest — are classified by regular expression. Each class carries a static
`nodeMessage` pattern, and the mapping function lowercases the error's `details` and tests it against
each one in turn, returning `UnknownNodeError` when nothing
matches.<Cite src="viem-node-errors-source" /><Cite src="viem-get-node-error-source" /> Execution
reverts take a different route: that function first walks the chain for a link whose `code` equals
`ExecutionRevertedError.code`, which is `3`.<Cite src="viem-get-node-error-source" /><Cite src="viem-node-errors-source" />

The point is not that string matching is fine after all. The point is where it lives. viem does it
once, in one file, against a maintained set of patterns, and hands you back a class — so the fragile
part is centralised and fixed for everyone when a client changes its wording. Your handler matching on
`error.message` is the same fragility, in your repository, discovered in production. And when the
patterns miss you get `UnknownNodeError`, an honest "I do not know" rather than a confident wrong
branch.<Cite src="viem-get-node-error-source" />

<Aside kind="warn">
One pattern is worth flagging rather than trusting. `ExecutionRevertedError` matches both `execution
reverted` and `gas required exceeds allowance`.<Cite src="viem-node-errors-source" /> Those are not
obviously the same event, and the research behind this curriculum records a live disagreement over
whether the second indicates a revert at all rather than a balance check failing before execution.
Treat an `ExecutionRevertedError` from gas estimation as "the node refused", not "the contract
reverted", and read [the four reasons estimation fails](/c/estimategas-failure-modes) before writing a
message for it — which is also why
[estimation is not simulation](/c/estimategas-is-not-simulation).
</Aside>

## Worked example: a triage function, in the order the checks must happen

The output of this function is a decision your product can act on, not a string to print. Order matters
more than any individual branch, so each subgoal names why its check comes where it does.

**Subgoal 1 — establish that this is a viem error before assuming any structure.** Your `try` block
contains your own code too, and a `TypeError` from a null dereference has no `walk`. Gate everything on
`error instanceof BaseError`.<Cite src="viem-base-error-source" />

**Subgoal 2 — separate refusal from failure, first.** A dismissed wallet prompt is
`UserRejectedRequestError`, whose static code is `4001` — the code EIP-1193 assigns to "User Rejected
Request".<Cite src="viem-rpc-errors-source" /><Cite src="eip-1193" /> It comes before the revert check
because a user changing their mind is not an error condition: close the modal, log nothing.

**Subgoal 3 — walk for the revert, and narrow the result.** `error.walk(e => e instanceof
ContractFunctionRevertedError)` returns `null` when there was no decodable revert, so narrow before
reading `data?.errorName` and `data?.args`.<Cite src="viem-discussion-1789" /><Cite src="viem-contract-errors-source" />
Switch on `errorName` and map each known custom error to a sentence naming the next action. If
`errorName` is absent but `signature` is set you have an undecoded selector: log it, and treat the
missing ABI entry as your bug rather than the user's.

**Subgoal 4 — check node errors, which are refusals with a remedy.** `InsufficientFundsError`,
`NonceTooLowError`, `FeeCapTooLowError` and their siblings each imply a different next
step.<Cite src="viem-node-errors-source" /> "You need more ETH for gas" and "this transaction reverted"
must never reach the user as the same sentence, and here you can separate them without reading a
character of text.

**Subgoal 5 — treat what remains as transport, and make it retryable.** `HttpRequestError`,
`TimeoutError`, `RpcRequestError` and the rate-limit RPC errors are the residue, and they share a
property none of the branches above have: retrying the identical call may
succeed.<Cite src="viem-errors-glossary" /> This is where a retry button belongs; putting one on a
revert invites the user to pay twice for the same refusal.

**Subgoal 6 — log the bottom of the chain, display the top.** `walk()` with no argument gives your logs
the root cause: the provider's own payload, which is what you need when you open a ticket with
them.<Cite src="viem-base-error-source" /> Show the user the classification instead.

You write this once per application, and every screen that sends a transaction calls it — one place
where a failure becomes a decision, so adding a custom error to a contract means adding a case rather
than auditing every catch block.

```ts
try {
  const { request } = await publicClient.simulateContract({ ...params, abi: vaultAbi })
  const hash = await walletClient.writeContract(request)
  await publicClient.waitForTransactionReceipt({ hash })

  } else {

```

<Answer>
**1. The rejection check matches on text, and it is the check that most needs not to.** Whether a
dismissed prompt produces a message containing `User rejected` depends on the wallet, the connector and
the viem version. The stable fact is the class and its static code `4001`, assigned by EIP-1193 to User
Rejected Request.<Cite src="viem-rpc-errors-source" /><Cite src="eip-1193" /> When the wording drifts,
this branch stops firing and the user who cancelled deliberately gets a red banner and a retry button.

**2. `instanceof ContractFunctionExecutionError` is read as "the contract reverted", and it is not
that.** viem wraps every failure of a contract action in that class, revert or
not.<Cite src="viem-get-contract-error-source" /> A timed-out simulation, a 429 from the provider and a
real `InsufficientBalance` all land here and all produce the words "Transaction reverted" — two of them
false, and one describing a transaction that was never sent.

**3. Nothing walks the chain, so the decoded revert is discarded at the moment it exists.** The
`ContractFunctionRevertedError` one link down holds `data.errorName` and `data.args`, ready to become
"you tried to withdraw 4.2 ETH and your position holds
3.8".<Cite src="viem-contract-errors-source" /><Cite src="viem-discussion-1789" /> Instead
`shortMessage` is printed, which for an undecoded revert is a bare "the contract function reverted".

**4. `showRetryButton()` runs unconditionally, including on reverts.** A revert against unchanged state
reverts again; the retry is only sound for the transport branch, which this handler never
identifies.<Cite src="viem-errors-glossary" /> Quieter version of the same bug: this `catch` also wraps
`waitForTransactionReceipt`, so a transaction that was broadcast, mined and reverted lands here too,
where "retry" means paying for a second revert.

**The structural fix:** the handler branches on the *outermost* class because that is the object it was
handed, and every useful distinction lives further down the chain, where only `walk`
reaches.<Cite src="viem-base-error-source" /> Reordering the branches as the worked example does fixes
all four at once, because each defect is a specific failure handled by a branch meant for a general
one.
</Answer>
</Check>

## Where this pays off

**The next lesson** closes the module on an action that changes which of these errors you can receive
at all: a synchronous send collapses broadcast and receipt into one call, turns a reverted receipt into
a thrown error by default, and gives you a timeout that means "still pending", not "failed".

**The error-surfaces module** is the full treatment of what sits underneath `data` and `raw`: the four
shapes revert bytes can take, why zero bytes has several unrelated causes, why
[a panic is your bug rather than the user's](/c/panic-means-bug), and how to reach a triage taxonomy
whose output [names the next action](/c/error-message-must-name-the-next-action).

**The transaction-UX module** takes the branch this lesson only pointed at — broadcast, then failed or
never arrived — and builds the state machine a `try`/`catch` around one `await` cannot express.
