Three files. The middle line of each is the same character-for-character; the line above it is not.

```ts
// server.ts — a Node process on your infrastructure
const client = createPublicClient({ chain: mainnet, transport: http(RPC_URL) })
const balance = await client.getBalance({ address })

// stream.ts — a long-lived socket, same process
const client = createPublicClient({ chain: mainnet, transport: webSocket(WS_URL) })
const balance = await client.getBalance({ address })

// browser.ts — running inside the user's tab, no RPC URL of your own at all
const client = createPublicClient({ chain: mainnet, transport: custom(window.ethereum!) })
const balance = await client.getBalance({ address })
```

In the third file, the bytes for that balance query leave the page through a browser extension you did
not write, get relayed to a node you have never configured, and come back. Your code does not know
that. It calls `getBalance` and receives a `bigint`.

This is not a convenience. It is the single structural decision viem makes, and once you can see it,
a whole category of "why is this not working" questions stops being ambiguous. You already know from
[the RPC lesson](/c/rpc-is-the-only-door) that everything a program can learn about a chain arrives
through a JSON-RPC method. viem splits the job of *deciding which method to call and what to do with
the answer* from the job of *getting the bytes there and back*, and gives them two different names.

## Client and Transport are two objects, not one

viem's own definition is one sentence: a **Client** provides access to a subset of
**Actions**.<Cite src="viem-clients" /> There are three of them — a Public Client for read-only
actions like `getBlockNumber` and `getBalance`, a Wallet Client for actions that produce signatures
like `sendTransaction` and `signMessage`, and a Test Client for actions like `mine` and
`impersonate` that only a development node will honour.<Cite src="viem-clients" /> The next lesson is
entirely about the boundary between the first two.

A **Transport** is defined just as narrowly: the intermediary layer responsible for executing
outgoing requests.<Cite src="viem-clients" /> viem names three — `http()` over an HTTP JSON-RPC API,
`webSocket()` over a WebSocket JSON-RPC API, and `custom()`, which wraps an
[EIP-1193](https://eips.ethereum.org/EIPS/eip-1193) `request`
function.<Cite src="viem-clients" /><Cite src="eip-1193" /> `fallback()` and `ipc()` are transports
too, but they are composed out of the same interface rather than being new kinds of wire; the
fallback lesson later in this module takes that apart.

Notice what is *not* in either definition. The Client does not hold a socket. The Transport does not
know what `getBalance` means. Neither of them is "the connection to Ethereum", because there is no
such object in viem — there is a request function and a set of functions that call it.

## The action does not care, because the action is a function

The reason the three files above can share a line is that viem's actions are not methods that live on
a client. They are standalone functions that take a client as their first argument, and the client
object you normally use is a convenience wrapper over them.

viem documents this directly, because it is also the escape hatch for bundle size. `createClient`
builds a bare client with no decorated actions at all; you then import the actions you actually use
from `viem/actions` and pass the client in:<Cite src="viem-build-your-own-client" />

```ts
import { createClient, http } from 'viem'
import { mainnet } from 'viem/chains'
import { getBlock, sendTransaction } from 'viem/actions'

const client = createClient({ chain: mainnet, transport: http() })

const block = await getBlock(client, { blockTag: 'latest' })
const hash = await sendTransaction(client, { /* ... */ })
```

`createPublicClient` and `createWalletClient` are not special-cased in the library. Both are
`createClient` followed by `.extend(...)` with a set of actions — viem's docs say so in as many
words, and offer `.extend` to you for the same purpose.<Cite src="viem-build-your-own-client" /> Here
is a client that speaks a namespace viem does not ship, built the same way:

```ts
const debugClient = createClient({ chain: mainnet, transport: http() })
  .extend(client => ({
    async traceCall(args: CallParameters) {
      return client.request({
        method: 'debug_traceCall',
        params: [formatTransactionRequest(args), 'latest', {}],
      })
    },
  }))
```

That example is from the documentation, and it is worth sitting with for a moment.<Cite src="viem-build-your-own-client" />
`debug_traceCall` is a geth namespace, not a standard one. viem has no opinion about it. But
`client.request` is the transport's request function, exposed, so an action you write yourself is
indistinguishable in kind from `getBalance` — it is a function that takes a client, calls
`client.request`, and shapes the result. There is no privileged inner ring.

<Aside kind="note">
This is also why "does viem support X" is usually the wrong question. If X is a JSON-RPC method your
node exposes, you can call it today through `client.request`. What viem supplies on top is
argument formatting, result parsing, and types — real work, but work you can do without waiting for a
release.
</Aside>

## What the split tells you when something breaks

Here is the practical payoff, and it is the reason this lesson comes first.

**An action that returns the wrong answer is a chain or ABI problem.** The transport did its job: a
request went out, a response came back, the response was well-formed enough to parse. The value is
wrong because you asked the wrong node about the wrong contract at the wrong block, or because the
ABI you handed viem does not describe the code at that address. No amount of transport configuration
will change it.

**An action that never returns is a transport problem.** Timeouts, socket closures, a provider
rate-limiting you, a browser extension that is waiting on a human. Nothing about your ABI or your
arguments is implicated.

Those two failure modes have almost disjoint fixes, and conflating them is how afternoons disappear.
The transports give you instrumentation on exactly the second one. `http()` takes `onFetchRequest`
and `onFetchResponse` callbacks, plus `retryCount` (default `3`) and `retryDelay` (default `150`ms,
with exponential backoff).<Cite src="viem-http-transport-doc" /> `webSocket()` takes `keepAlive` and
`reconnect`, both enabled by default.<Cite src="viem-websocket-transport-doc" /> None of these
options exist on the action, because none of them are the action's business.

A third failure mode hides between the two, and it is worth naming now because it costs people real
money: **the request went somewhere you did not intend.** If you call `http()` with no URL, the
transport falls back to a public RPC URL taken from the chain object, and viem's own documentation
flags this with a warning recommending an authenticated URL to avoid
rate-limiting.<Cite src="viem-http-transport-doc" /> The same warning appears on
`webSocket()`.<Cite src="viem-websocket-transport-doc" /> So `http()` with empty parentheses is
valid, compiles, runs, and quietly sends your production traffic to a shared endpoint. The chain
object made that possible, which brings us to what the chain object actually is.

## The chain is a record, not a connection

`chain: mainnet` looks like it selects a network. It selects a *description* of a network: the chain
id, the native currency, a set of RPC URLs, block explorer metadata, and the addresses of well-known
contracts on that chain. Every use of it is local. The chain supplies the default URL when the
transport has none.<Cite src="viem-http-transport-doc" /> On a Wallet Client, viem uses it to assert
that the chain you are targeting matches the wallet's currently active chain before it sends
anything.<Cite src="viem-wallet-client-doc" /> Later in this module, the multicall lesson leans on
the contract addresses it carries.

The thing to internalise is that swapping `mainnet` for `optimism` changes a data structure. It does
not open anything, close anything, or validate anything against a live node. If the transport still
points at a mainnet URL, you now have a client that believes it is on Optimism and is talking to
Ethereum, and nothing in the type system objects — a failure mode we will meet again, in a sharper
form, when we get to type inference.

<Misconception
  belief="Passing a chain to createPublicClient means viem will use that chain."
  reality="The chain is metadata used for defaults, assertions and contract lookups. Which node you reach is decided by the transport's URL. A mismatched pair is a valid, compiling, silently wrong client."
  why="Every argument named after a network in every other kind of SDK is a selector. Here it is a record, and the selector is the URL you may not have passed."
  src="viem-http-transport-doc"

## Worked example: one action, three wires, three different meanings of "who answers"

Take `readContract` — internally an `eth_call` with ABI-encoded data, restricted at the type level to
`view` and `pure` functions.<Cite src="viem-read-contract-doc" /> Trace the identical call over each
transport and name what changes.

**Subgoal 1 — establish what is constant.** The JSON-RPC method is `eth_call` in all three cases. The
params are the same encoded calldata you could produce by hand from
[the ABI rules](/c/abi-encoding) and [the selector](/c/abi-function-selector). The decoding of the
returned word into a `bigint` is the same code. Everything above the transport is one path.

**Subgoal 2 — name who chose the node, over `http()`.** You did, in the URL string. You know the
provider, the region, and whether it is archive or pruned. If the answer is stale you can say which
machine was stale.

**Subgoal 3 — name who chose the node, over `webSocket()`.** Still you, but the connection is
long-lived, so its failure mode is different in kind: not "this request failed" but "the socket
dropped and everything after it is affected until reconnect". viem reconnects by default, which turns
a hard error into a latency spike you have to look for rather than trip over.<Cite src="viem-websocket-transport-doc" />

**Subgoal 4 — name who chose the node, over `custom(window.ethereum)`.** The user's wallet did. The
`custom` transport accepts an EIP-1193 `request` function and nothing more — injected extensions,
WalletConnect, a Coinbase SDK provider, or a function you wrote
yourself.<Cite src="viem-custom-transport-doc" /><Cite src="eip-1193" /> You do not know the URL. You
do not know the provider. You do not control the caching, and you cannot audit the answer's
provenance.

**Subgoal 5 — state the rule the trace produces.** *The action determines what is true if the answer
is honest; the transport determines who you are trusting for honesty.* This is why serious
applications read through a transport they control and only write through the user's wallet — a
split that is trivial to express here, because it is two clients with two transports and one shared
set of action calls.

<Check type="explain" concept="viem-client-vs-transport">
An engineer reports two bugs from the same React app on the same afternoon.

**Bug A:** `readContract` for an ERC-20 `balanceOf` returns `0n` for an address that the block
explorer clearly shows holding tokens. It returns `0n` every time, instantly, with no error.

**Bug B:** `getBlockNumber` hangs for about thirty seconds and then throws. It works about half the
time.

For each, say which half of the split is implicated, what you would look at first, and one specific
thing that cannot possibly be the cause.

<Answer>
**Bug A is above the transport.** A response came back, it parsed, and it decoded to a valid
`bigint`. The wire worked perfectly; the disagreement is about *what was asked*. Look at, in order:
the chain the transport's URL actually points at versus the chain in the client (they can differ
freely, and nothing checks<Cite src="viem-http-transport-doc" />); the contract address; whether the
ABI describes the code at that address; and the block being read against.

What it cannot be: a transport misconfiguration in the sense of connectivity. A broken connection
does not return `0n` — it throws or hangs. An instant, consistent, well-typed wrong answer is
positive evidence that the wire is fine.

**Bug B is the transport.** No answer arrived. Look at `onFetchRequest`/`onFetchResponse` to see
whether the request left at all, then at the provider's rate limits, then at `retryCount` and
`retryDelay` — because with a default of 3 retries at a 150 ms base delay with exponential backoff, a
"thirty second" symptom may be four failed attempts rather than one slow
one.<Cite src="viem-http-transport-doc" /> Intermittency at roughly half is the signature of a limit
being hit, not of a wrong argument.

What it cannot be: your ABI or your arguments. `getBlockNumber` carries neither.

**The thing worth noticing:** you sorted both of these before reading a single line of application
code, using only the shape of the symptom. That is what the split buys you.
</Answer>
</Check>

## A note on which viem this is

Everything in this module is viem 2.x. As of 26 August 2026 the npm registry lists `latest` at
**2.55.19** and `next` at **3.0.0-next.10**.<Cite src="npm-viem-dist-tags" /> A 3.0 prerelease exists;
it is not what `npm install viem` gives you, and this module does not teach its API shapes. Where a
default value is quoted in these lessons, it is quoted from the 2.x documentation and named as a
default rather than as a law — defaults are the part of a library most likely to move under you.

## Where this pays off

**The next lesson** takes the Client half seriously: which of the two clients can spend money, why
that is enforced by the type system rather than by discipline, and the difference between a key that
lives in your process and a key that lives in a wallet that can say no.

**The fallback lesson** takes the Transport half seriously, and shows that "one URL" is a
single point of failure you can remove without touching a single action call — which is only possible
because of the separation you just learned.

**The wagmi module**, later in this track, is a React layer over exactly these objects. When you meet
[wagmi's config](/c/wagmi-is-viem-plus-query) and find it asking for `chains` and `transports` as two
separate fields, you will already know why they are separate.
