Here is a line of TypeScript that will not compile, and the reason it will not compile is the whole
first half of this lesson:

```ts
const balance = await client.readContract({
  address: token,
  abi: erc20Abi,
  functionName: 'transfr',   // Type '"transfr"' is not assignable to ...
  args: [user],
})
```

No code generation ran. No build step produced a `Token.ts`. The compiler knows that `transfr` is not
a function on this contract because the ABI *value* carried that information into the type system, and
viem's action signature was written to read it.

Here is a second line, in the same file, which compiles cleanly and is wrong:

```ts
const balance = await client.readContract({
  address: proxyDeployedLastYear,
  abi: erc20Abi,
  functionName: 'balanceOf',
  args: [user],
})
```

Nothing in the type system knows what code is at `proxyDeployedLastYear`. The first check is real and
worth having. The second gap is the one that costs money. Both come from the same design, so learn
them together.

## Inference comes from the value, not from a generator

viem infers types from ABI and EIP-712 typed-data definitions, powered by
ABIType.<Cite src="viem-typescript" /><Cite src="abitype-docs" /> For this to work, viem's own
documentation states the requirement flatly: you must either add const assertions to specific
configuration parameters or define them inline.<Cite src="viem-typescript" />

```ts
const abi = [{
  type: 'function',
  name: 'balanceOf',
  stateMutability: 'view',
  inputs: [{ type: 'address' }],
  outputs: [{ type: 'uint256' }],
}] as const
```

Without `as const`, TypeScript widens `name` to `string` and `type` to `string`, and the array becomes
a list of shapeless objects. With it, the array is a *literal* type — a type that remembers the exact
strings — and ABIType can walk it. What falls out is a chain of narrowings: `functionName` becomes a
union of the real names, `args` becomes the tuple those inputs describe, and the return value becomes
the type those outputs describe.<Cite src="viem-typescript" /> viem's documentation says exactly where
to look when it stops working: if type inference is not working, it is likely you forgot the const
assertion or did not define the parameter inline.<Cite src="viem-typescript" />

The mechanism carries a second, quieter guarantee. `readContract` is documented as calling read-only
functions — those marked `view` or `pure` — and viem's own example annotates the narrowed union with
the observation that `transfer` is *not* in it, because it is not a read
function.<Cite src="viem-read-contract-doc" /><Cite src="viem-typescript" /> You have now seen this
rule enforced three times in three places: [the Solidity keyword](/c/sol-view-pure),
[the `STATICCALL` opcode](/c/staticcall-is-the-enforcement), and an autocomplete list. Only the third
one fires before you run anything.

The inference is not limited to `readContract`. viem lists the surface it covers: `readContract`,
`writeContract`, `simulateContract`, `estimateContractGas`, `multicall`, `deployContract`, the event
filter and watch actions, and a shelf of encode/decode utilities including `decodeEventLog`,
`encodeFunctionData` and `encodeErrorResult`.<Cite src="viem-typescript" /> `multicall` is the
interesting member: each entry in the array carries its own `abi` and `functionName`, so the result
array is typed *per entry*.<Cite src="viem-multicall" /><Cite src="viem-typescript" /> That is only
possible because the types come from values, which can differ per element.

### Why your JSON import gets you nothing

The habit from every other kind of API client is to write `import abi from './Token.json'`. It
compiles. It produces no inference at all.

viem's documentation names the cause and links the upstream issue: TypeScript does not support
importing JSON as `const`.<Cite src="viem-typescript" /><Cite src="ts-issue-32063" /> The import
resolver types the file structurally and widens every literal, so `name: "balanceOf"` becomes
`name: string` and the whole apparatus above has nothing to grip. There is no error. You get
`functionName: string`, arguments typed loosely, and a return value you have to assert. The symptom is
always the same and always misread: *"it compiles but I have no autocomplete."*

The documented remedy is `@wagmi/cli`, which can fetch ABIs from block explorers and resolve them from
Foundry or Hardhat projects, and which emits TypeScript with the const assertions
in place.<Cite src="viem-typescript" /> On a Foundry project — and you have one — that means your ABIs
regenerate from `forge build` output rather than being copied by hand into a JSON file that drifts.

### Two footnotes that will bite you exactly once

**Strictness is required.** viem's documentation asks for `strict: true` in `tsconfig.json` to ensure
everything works correctly, and states that types currently require TypeScript v5.0.4 or
greater.<Cite src="viem-typescript" />

**Type changes are shipped as patch releases.** This one is genuinely surprising, and viem states it
outright: changes to types in the repository are considered non-breaking and are usually released as
patch semver changes, and it is highly recommended that you lock your `viem` package version to a
specific patch release.<Cite src="viem-typescript" /> The non-type public API still follows semver
strictly.<Cite src="viem-typescript" /> So a caret range on viem is a range over *type* behaviour, and
a CI failure after `npm update` with no code change is expected rather than mysterious. Pin the patch.
With `latest` at 2.55.19 as of this writing, that means the exact version, not
`^2.55.19`.<Cite src="npm-viem-dist-tags" />

## Where the guarantee stops

Now the important part, and the reason this lesson exists in an elective rather than a tutorial.

**What the compiler checks:** that the call you wrote is consistent with the ABI you handed it.

**What nothing checks:** that the ABI you handed it describes the code at that address, on that chain,
at that block.

That second sentence has no enforcement anywhere in the stack. An ABI is a description a human
attached to an address. The chain stores bytecode. The only thing that connects them at runtime is
[four bytes of a hash](/c/abi-function-selector) matching a jump target in
[the dispatcher](/c/abi-dispatch) — and four bytes is a space small enough that
[collisions exist and no registry resolves them](/c/abi-selector-collision-risk).

Three ordinary ways to end up green and wrong:

**The proxy moved.** The address is a proxy; the implementation behind it was upgraded. Your ABI
describes what used to be there. You already know
[what an upgrade actually replaces](/c/delegatecall-is-the-proxy-primitive) and that the
[implementation slot](/c/erc-1967-slots) is a storage value someone can change. The address is stable
precisely so that clients do not have to notice, which is the feature and the hazard.

**The chain moved.** Same address, different chain. The transport's URL and the client's `chain` are
independent, as the first lesson established. On the other chain that address may hold different code
or none.

**The address was never right.** A config typo, a testnet address in a production environment
variable, a checksummed address someone re-typed.

All three produce green builds. Two of the three produce the same runtime error, and it is worth
recognising on sight. viem raises `ContractFunctionZeroDataError` — its message is *the contract
function "…" returned no data ("0x")* — and it attaches a list of causes: the contract does not have
that function, the parameters may be invalid, or the address is not a
contract.<Cite src="viem-contract-errors-source" /><Cite src="viem-errors-glossary" /> That error is
the type system's silence becoming audible. When you see it, stop debugging your arguments and go
verify what is at the address.

  why="In every other typed client — OpenAPI, gRPC, GraphQL — the schema is fetched from or negotiated with the server. Here it is a file you keep, and the server never sees it."

<Aside kind="note">
The practical countermeasure is small and worth doing: on start-up, read the code size at each
configured contract address and fail loudly if it is empty, and where a proxy is involved read the
implementation slot and compare it to what your ABI was generated from. That is two reads at boot,
which is nothing, and it converts a class of silent wrongness into a startup error. It is the same
instinct as verifying deployment state rather than trusting the repository.
</Aside>

## Every EVM integer arrives as a bigint

The second half of the lesson is a different kind of type guarantee: one the language gives you, that
you can only lose on purpose.

Chain integers cross into JavaScript as `bigint`, never `number`. The reason is arithmetic, not
style. `Number.MAX_SAFE_INTEGER` is **9007199254740991** — a little over nine
quadrillion.<Cite src="mdn-max-safe-integer" /> MDN's own demonstration is the one to remember:

```js
Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2   // true
```

Two different integers, both representable as doubles, comparing equal.<Cite src="mdn-max-safe-integer" />
Now put a chain amount next to it. One ether is 10^18 wei — about a hundred times larger than that
ceiling. A `uint256` maximum is around 1.16 × 10^77. `number` is not marginally unsuitable here; it
runs out before the smallest interesting amount.

JavaScript's `BigInt` is the arbitrary-precision integer type, written with an `n` suffix
(`9007199254740991n`) or produced by the `BigInt()` function.<Cite src="mdn-bigint" /> Two of its
behaviours matter daily:

**Mixed arithmetic throws.** Subtracting or multiplying a `BigInt` and a `Number` raises a
`TypeError: can't convert BigInt value to Number value`.<Cite src="mdn-bigint" /> This is the good
news, and it is doing more work for you than you notice: the most dangerous version of this bug —
silent coercion to a double — is not available.

**Comparison does not throw.** Relational comparison across `BigInt` and `Number` works, which is why
`amount > 0` is fine while `amount * 1.05` is a type error.<Cite src="mdn-bigint" /> The boundary is
sharper than "bigints are contagious"; know which side of it you are on.

**`JSON.stringify` throws.** Using `JSON.stringify()` with any `BigInt` value raises a `TypeError`,
because BigInt values are not serialized in JSON by default — though `stringify` will call a `toJSON`
method if you define one.<Cite src="mdn-bigint" /> Any API response, cache key, log line, or
`localStorage` write that touches a chain amount hits this. Decide once, in one serializer, whether
amounts cross your process boundary as decimal strings or as hex, and never as numbers.

### The two conversions, and their exact signatures

viem's sanctioned crossings are narrow on purpose. `parseUnits(value: string, exponent: number)`
multiplies a **string** representation by 10^exponent and returns a
`bigint`.<Cite src="viem-parse-units-doc" /> `formatUnits(value: bigint, exponent: number)` divides by
10^exponent and returns a **string**.<Cite src="viem-format-units-doc" />

```ts
parseUnits('420', 9)          // 420000000000n
formatUnits(420000000000n, 9) // '420'
```

Read the signatures as a rule about direction. `parseUnits` takes a string because a decimal typed by
a human is text; converting it to a `number` first would round it before viem ever saw it.
`formatUnits` returns a string because the result is for display, and the moment you do arithmetic on
it you have re-entered floating point through the back door — `Number(formatUnits(x, 18)) * price` is
the canonical version of that mistake, and it compiles.

`parseEther` and `formatEther` are the same pair with the exponent fixed at 18.

### Worked example: a value computation that stays in integers

Convert a balance of token A into a quote currency B, where A has 18 decimals, B has 6, and the price
of A in B arrives from an oracle as an integer scaled by 10^8.

**Subgoal 1 — write down every scale before writing any code.** `balanceA` is scaled 10^18. `price` is
scaled 10^8, in units of B per A. The answer must be scaled 10^6, because that is B's base unit. Three
different exponents, none of them interchangeable. Most bugs in this shape are a missing line in
exactly this inventory.

**Subgoal 2 — get the decimals from the chain, not from a constant.** `decimals()` is a function on
the token, and it is the token's answer, not yours. Read it and cache it per address per chain. A
hard-coded `18` is a claim about a contract you did not deploy, and the
[weird-ERC-20 taxonomy](/c/weird-erc20-taxonomy) exists because that claim is sometimes false.

**Subgoal 3 — do the multiplication before any division.** In integer arithmetic the order determines
how much you throw away. `(balanceA * price) / 10n ** 20n` and `(balanceA / 10n ** 20n) * price` are
not the same computation: the second truncates first and then scales the truncation up.

**Subgoal 4 — derive the scale factor rather than guessing it.** The product `balanceA * price` is
scaled 10^(18+8) = 10^26. The target is 10^6. So divide by 10^20. Writing the exponent arithmetic as a
comment next to the line is not decoration; it is the only place that reasoning survives.

```ts
const valueB = (balanceA * price) / 10n ** BigInt(18 + 8 - 6)
```

**Subgoal 5 — decide the rounding direction on purpose.** BigInt division truncates toward
zero.<Cite src="mdn-bigint" /> For a display value that is fine. For anything that
[decides who is owed what](/c/precision-rounding-bug), truncation always favours one party, and which
party it favours is a product decision that belongs in a comment and a test. You have seen where the
alternative ends.

**Subgoal 6 — format only at the boundary.** `formatUnits(valueB, 6)` produces the string the user
reads.<Cite src="viem-format-units-doc" /> Nothing downstream of that string does arithmetic. If
something needs to, it needs `valueB`.

<Check type="spot-bug" concept="viem-bigint-boundary">
Review this helper. It compiles, its unit test passes, and it is wrong in more than one way. Name each
defect and say which ones the compiler or the runtime would have caught if the code were written
differently.

```ts
export async function quote(client: PublicClient, token: Address, user: Address) {
  const [balance, price] = await Promise.all([
    client.readContract({ address: token, abi: erc20Abi, functionName: 'balanceOf', args: [user] }),
    fetchPriceUsd(token),                   // returns a JS number, e.g. 2431.77
  ])
  const human = Number(formatUnits(balance, 18))
  const usd = human * price
  await cache.set(`quote:${user}`, JSON.stringify({ balance, usd }))
  return usd.toFixed(2)
}
```

<Answer>
**Defect 1 — `Number(formatUnits(...))` re-enters floating point deliberately.** `formatUnits` returns
a string precisely so the value stays exact.<Cite src="viem-format-units-doc" /> Wrapping it in
`Number` converts to a double, and above 9007199254740991 doubles stop representing consecutive
integers.<Cite src="mdn-max-safe-integer" /> A large balance loses its low digits here, silently. The
compiler cannot object: `Number(string)` is a legal, ordinary call.

**Defect 2 — the decimals are asserted, not read.** `18` is hard-coded. For a token whose `decimals()`
returns 6, this understates the balance by a factor of 10^12 — and it will look plausible rather than
absurd, which is worse. Read `decimals` alongside `balanceOf`; in the previous lesson you saw how to
do that in one round trip.<Cite src="viem-multicall" />

**Defect 3 — `JSON.stringify` on an object containing `balance` throws.** `balance` is a `bigint`, and
`JSON.stringify` raises a `TypeError` on any BigInt value.<Cite src="mdn-bigint" /> This is a *runtime*
catch, and it is the one piece of good news in the function: the language refuses rather than writing
something lossy to your cache. Note the test presumably passes because it never exercises the cache
write.

**Defect 4 — the test passing proves very little.** A fixture balance small enough to survive the
double, and a token that happens to have 18 decimals, makes every defect above invisible. Property
tests over the amount — you know how to write them — would kill defects 1 and 2 immediately. This is
the same lesson as fuzzing a contract: the example that was easy to write is the example that does not
discriminate.

**How to write it instead.** Take the price as an integer with an explicit scale rather than a
`number`, read `decimals` from the chain, keep the whole computation in `bigint`, and call
`formatUnits` exactly once, at the return.<Cite src="viem-parse-units-doc" /><Cite src="viem-format-units-doc" />
The function then has no floating-point operation in it at all, which is the property you actually
want to be able to assert in review.
</Answer>
</Check>

## Where this pays off

**The next lesson** puts these two halves together under pressure. `simulateContract` returns
`{ result, request }` where `result` is typed from the ABI and `request` is a prepared argument object
for `writeContract` — the handoff only type-checks because of the `as const` mechanism you just
learned, and the value it protects is a user's signature.

**The error lesson** is the other side of the ABI guarantee. When a contract reverts with a custom
error, viem decodes it *only* against the ABI you supplied — the same document, with the same gap
between it and the chain — and hands you [raw hex](/c/decode-needs-the-right-abi) when the definition
is missing.<Cite src="viem-decode-error-result-doc" />

**The wagmi module** inherits the bigint boundary wholesale, and adds a wrinkle: query keys have to be
hashed, hashing usually means serialisation, and serialisation of a `bigint` is the `TypeError` you
just met.<Cite src="mdn-bigint" />
