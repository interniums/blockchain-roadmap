Open a file you did not write and answer one question about it before you read anything else: which
lines can move money?

```ts
const pub = createPublicClient({ chain: mainnet, transport: http(RPC_URL) })
const wallet = createWalletClient({ chain: mainnet, transport: custom(window.ethereum!) })

const decimals = await pub.readContract({ ...token, functionName: 'decimals' })
const balance  = await pub.readContract({ ...token, functionName: 'balanceOf', args: [user] })
const fee      = await pub.estimateContractGas({ ...token, functionName: 'transfer', args: [to, amount], account: user })
const logs     = await pub.getLogs({ address: token.address, fromBlock: 0n })

const hash     = await wallet.writeContract({ ...token, functionName: 'transfer', args: [to, amount], account: user })

const receipt  = await pub.waitForTransactionReceipt({ hash })
```

Exactly one line: the one whose first token is `wallet`. Every other line is a read, and no read can
change anything, no matter what arguments you pass it or how badly you get them wrong.

That is not a naming convention you have to remember. It is a property of the two objects, and it is
checked by the compiler.

## The public client is defined by what it cannot do

`createPublicClient({ chain, transport })` returns a client carrying the Public Actions — viem
describes it as an interface to the "public" JSON-RPC methods: retrieving block numbers,
transactions, reading from smart contracts.<Cite src="viem-public-client-doc" /><Cite src="viem-clients" />
`getBlockNumber`, `getBalance`, `readContract`, `call`, `estimateGas`, `getLogs`,
`waitForTransactionReceipt`. There is no `account` in that constructor, no private key anywhere in
its object graph, and no action on it that produces a signature.

The narrowness is the feature. `readContract` is restricted to `view` and `pure` functions, and viem
enforces that at the type level: pass an ERC-20 ABI and `functionName` autocompletes to the read
functions only, with `transfer` absent from the
union.<Cite src="viem-read-contract-doc" /><Cite src="viem-clients" /> You met
[the `view`/`pure` distinction](/c/sol-view-pure) as a Solidity keyword and
[`STATICCALL`](/c/staticcall-is-the-enforcement) as the opcode that enforces it. The type union here
is a third enforcement of the same rule, in a third place, and unlike the other two it fires before
the code runs.

<Aside kind="note">
"Public" in `createPublicClient` means *the public JSON-RPC namespace* — the standard `eth_*` methods
any node exposes — not "safe to expose publicly" and not "no authentication". The transport it wraps
usually carries an API key in its URL or headers, and that key is as secret as any other. The name
describes the method set, not the security posture.
</Aside>

## The wallet client is defined by whose signature it gets

`createWalletClient` carries the actions that produce signatures and broadcast transactions:
`sendTransaction`, `writeContract`, `signMessage`, `signTypedData`. viem states its scope precisely —
the Wallet Client supports signing over **JSON-RPC Accounts** (browser extension wallets,
WalletConnect, and so on) and **Local Accounts** (private key or mnemonic
wallets).<Cite src="viem-wallet-client-doc" />

Both produce a client with the same shape. `walletClient.writeContract({ ... })` is one line either
way. What differs is the entire chain of custody underneath it, and the difference is not cosmetic.

### Local Account: the key is in your process

A Local Account performs signing of transactions and messages with a private key **before**
broadcasting over JSON-RPC.<Cite src="viem-local-account-doc" /> viem ships three kinds —
`privateKeyToAccount`, `mnemonicToAccount`, and `hdKeyToAccount`.<Cite src="viem-local-account-doc" />

```ts
import { privateKeyToAccount } from 'viem/accounts'

const account = privateKeyToAccount(process.env.DEPLOYER_KEY as `0x${string}`)
const wallet = createWalletClient({ account, chain: mainnet, transport: http(RPC_URL) })
```

The transport here is `http()`, not `custom()`. There is no wallet software in the picture at all.
viem builds the transaction, signs it in your runtime, and submits the resulting bytes with
`eth_sendRawTransaction`.<Cite src="viem-send-transaction-doc" /> The node receives a signed blob and
has no idea a library was involved.

Say the consequence out loud, because it is the part people skip: **that private key is in the memory
of the process running this line.** Anything that can read process memory, read your environment, or
inject a dependency can sign as this account, with no prompt and no second factor. You spent a whole
module on [the mapping from capabilities to the parties who hold them](/c/capability-not-role) and on
[the surfaces that are not the contract](/c/offchain-attack-surface). `privateKeyToAccount` is that
mapping, expressed as one line of TypeScript. Deployer keys, relayer keys and bot keys are local
accounts, and they are exactly the class of credential that shows up in incident write-ups.

### JSON-RPC Account: the key is somewhere you cannot reach

A JSON-RPC Account is an account whose signing keys are stored on the external wallet; it **defers**
signing to that wallet over JSON-RPC.<Cite src="viem-jsonrpc-account-doc" /> Its representation in
your code is startlingly thin — viem's documentation is explicit that a JSON-RPC Account can just be
initialised as an address string.<Cite src="viem-jsonrpc-account-doc" />

```ts
const [address] = await window.ethereum.request({ method: 'eth_requestAccounts' })
const wallet = createWalletClient({ account: address, chain: mainnet, transport: custom(window.ethereum!) })
```

`account` here is twenty bytes of hex. It carries no key material, no signing capability, and no
authority. It is a *name for whom to ask*. When you call `sendTransaction`, viem emits
`eth_sendTransaction` through the [EIP-1193 provider](/c/rpc-endpoints-aliases) and the wallet does
everything else.<Cite src="viem-send-transaction-doc" /><Cite src="eip-1193" />

### A Local Account is an interface, not a private key

The phrase "the key is in your process" describes `privateKeyToAccount`, not the category. viem
exports `toAccount`, which builds an Account from a custom signing implementation: you supply an
`address` and three functions — `signMessage`, `signTransaction` and
`signTypedData`.<Cite src="viem-to-account-doc" /> That is the entire contract. Nothing in it says
where the key lives or who performs the maths.

```ts
const account = toAccount({
  address: '0xa0b8...eb48',
  async signMessage({ message }) { /* ... */ },
  async signTransaction(transaction, { serializer }) { /* ... */ },
  async signTypedData(typedData) { /* ... */ },
})
```

Three async functions and an address. Each of them can call a cloud KMS, a hardware security module,
a signing service behind an internal API, or a multi-party computation network. To the rest of viem
this is a Local Account: it signs before broadcasting, and the result goes out as
`eth_sendRawTransaction`.<Cite src="viem-local-account-doc" /><Cite src="viem-send-transaction-doc" />

This matters for the review conversation more than for the code. "Is this a local account?" and
"where does the key material live?" look like the same question and are not. `privateKeyToAccount`
answers both at once, which is why it is the version everyone reaches for and the version that ends
up in a repository. `toAccount` separates them, and the separation is what lets a key custody
decision change without any call site changing — the same decoupling the transport gave you for
network access.

<Aside kind="note">
Signing over EIP-712 typed data is a first-class member of that interface rather than an add-on. You
already know why the structured format exists: a wallet cannot show a user what an opaque digest
authorises, and [a signature over bytes with no domain](/c/eip-712-typed-data) is a
[blind-signing](/c/blind-signing) surface. When you get to relayed and sponsored flows, `signTypedData`
is the action doing the real work, and `sendTransaction` is not involved at all.
</Aside>

## Four things you lose with a JSON-RPC account, and why each one matters

The two account kinds are not "the same thing, hosted differently". Here is the difference expressed
as capabilities your code no longer has.

**1. You cannot guarantee the fields.** `eth_sendTransaction` hands the wallet a partial transaction.
The wallet decides the nonce, and it decides the fee fields — the
[`maxFeePerGas` and `maxPriorityFeePerGas`](/c/eip-1559-fee-fields) your interface displayed are a
suggestion. If the user opens the wallet's advanced panel and edits them, or if the wallet has its own
fee oracle, the transaction that lands is not the transaction you composed. Any UI that shows a
precise fee before a JSON-RPC-account send is showing a forecast.

**2. You cannot pre-compute the hash.** The transaction hash is a hash of the signed bytes, and the
signed bytes do not exist until the wallet has produced them. With a local account you could, in
principle, sign and derive the hash before broadcasting. With a JSON-RPC account there is nothing to
hash until the wallet responds. Your UI cannot show a "pending" row keyed by hash until the promise
resolves, which is precisely why every well-built flow has a state between "user clicked" and "we
have a hash".

**3. There is a human in the loop, and the human can refuse.** viem exports
`UserRejectedRequestError` for exactly this.<Cite src="viem-errors-glossary" /> A rejection is not a
failure — nothing went wrong, a person declined — and the error-handling lesson later in this module
treats it as its own category rather than as an exception to log. It also means the latency is
unbounded. There is no timeout that distinguishes "the wallet is broken" from "the user went to make
coffee".

**4. The wallet has its own idea of which chain it is on.** viem uses the client's `chain` in
`sendTransaction` and `writeContract` to assert that it matches the wallet's active
chain.<Cite src="viem-wallet-client-doc" /> When it does not, you get `ChainMismatchError` rather than
a transaction on the wrong network.<Cite src="viem-errors-glossary" /> This check exists because the
wallet's network selector is global to the wallet and completely independent of your app's intent —
and it is a check you get only on the write path.

<Aside kind="warn">
That last asymmetry is worth writing down. Writes are asserted against the wallet's chain; **reads
are not**. Your Public Client reads through the transport *you* configured, at whatever chain that URL
serves, regardless of what the user's wallet is doing. An app whose reads and writes silently address
two different chains is a completely ordinary bug, and neither the compiler nor viem will mention it.
</Aside>

## Hoisting, and the error that tells you it did not happen

Both account kinds can be passed per-action or **hoisted** onto the client, so you stop threading it
through every call.<Cite src="viem-wallet-client-doc" /> Hoisted:

```ts
const wallet = createWalletClient({ account, chain: mainnet, transport: http() })
await wallet.sendTransaction({ to, value: parseEther('0.001') })
```

Per-action:

```ts
const wallet = createWalletClient({ chain: mainnet, transport: http() })
await wallet.sendTransaction({ account, to, value: parseEther('0.001') })
```

Forget both and you get `AccountNotFoundError`, which viem defines as being thrown when no account is
provided to an action that requires one.<Cite src="viem-errors-glossary" /> It is a good error: it
names the missing input rather than failing at the node.

## Worked example: one call site, traced twice

Take the single line that can move money from the file at the top, and follow it to the node under
each account kind. The purpose is to be able to say, for any transaction your app produces, exactly
which party decided each field.

```ts
await wallet.writeContract({ ...token, functionName: 'transfer', args: [to, amount], account: user })
```

**Subgoal 1 — establish what viem does before either path diverges.** `writeContract` ABI-encodes the
call and hands it to `sendTransaction`, viem's documentation says as
much.<Cite src="viem-write-contract" /> So the `data` field — the selector plus the two
[encoded arguments](/c/abi-encoding) — is produced locally, from the ABI you supplied, in both cases.
This half is yours regardless.

**Subgoal 2 — trace the local-account path to the wire.** viem needs a complete, signable
transaction, so the missing fields get filled: the nonce, the fee fields, the gas limit, the chain id.
It signs, and submits the serialised bytes with
`eth_sendRawTransaction`.<Cite src="viem-send-transaction-doc" /><Cite src="viem-local-account-doc" />
Every field in the transaction that lands is one your process chose. If the fee was too low, that is
your bug. If the nonce collided, that is your bug. The node accepted bytes and had no opinion.

**Subgoal 3 — trace the JSON-RPC-account path to the wire.** viem emits `eth_sendTransaction` through
the EIP-1193 provider with the fields it has.<Cite src="viem-send-transaction-doc" /><Cite src="eip-1193" />
The wallet now owns completion: it fills or overrides what it likes, renders a confirmation screen,
waits for a human, signs with a key you cannot address, and broadcasts through a node you did not
pick. What returns to you is a hash.

**Subgoal 4 — identify the one field that is checked rather than chosen.** The chain. viem asserts
the client's `chain` against the wallet's active chain and raises `ChainMismatchError` when they
disagree.<Cite src="viem-wallet-client-doc" /><Cite src="viem-errors-glossary" /> This is the only
place in the flow where your intent and the wallet's state are reconciled, and it exists precisely
because they are otherwise independent.

**Subgoal 5 — state the rule.** *With a local account you author the transaction and the node
executes it. With a JSON-RPC account you author a request and a third party authors the transaction.*
Every difference in this lesson — fee accuracy, hash timing, rejection handling, unbounded latency —
falls out of that one sentence. When you cannot remember the details, re-derive them from it.

## When one client is the right answer

The two-client rule has a documented exception, and it is common enough to be worth stating. When you
are using a local account, your Wallet Client and your Public Client would be constructed from the
same transport and the same chain — two objects describing one connection. viem's answer is to extend
one:<Cite src="viem-wallet-client-doc" /><Cite src="viem-local-account-doc" />

```ts
const client = createWalletClient({ account, chain: mainnet, transport: http(RPC_URL) })
  .extend(publicActions)

const { request } = await client.simulateContract({ /* ... */ })  // a Public Action
const hash = await client.writeContract(request)                  // a Wallet Action
```

This is the same `.extend` from the previous lesson: actions are functions, and a client is a bag you
can add functions to.<Cite src="viem-build-your-own-client" /> Note what it does *not* change — the
account is still local, the key is still in the process, and `simulateContract` still reads while
`writeContract` still writes.<Cite src="viem-simulate-contract" /><Cite src="viem-write-contract" />
You merged two holders, not two capabilities.

In a browser, do not do this. The reason is the transport, not the client: extending a
`custom(window.ethereum)` client with public actions routes your *reads* through the user's wallet
too, which means a node you did not choose, a cache you do not control, and rate limits set by
someone else. Keep reads on a transport you own.

  reality="The split is what makes 'which lines can spend money' answerable by reading the receiver of each call. Merge them and every line becomes a candidate, which is precisely the review property you were trying to buy."
  why="Two objects feels like more setup than one, and the cost of the merge is paid later, by someone auditing the file under time pressure."

A team ships a "gasless-feeling" flow: the user signs in the browser, and a server-side relayer pays
for and submits the transaction. Here is the shape of it. Name every distinct problem you can see,
and say which of them the type system catches.

```ts
// browser.ts
const wallet = createWalletClient({ chain: mainnet, transport: custom(window.ethereum!) })
const [user] = await wallet.getAddresses()
const hash = await wallet.writeContract({
  ...vault, functionName: 'deposit', args: [amount], account: user,
  nonce: expectedNonce, maxFeePerGas: quotedFee,
})
await db.insert({ id: hash, status: 'pending' })

// server.ts
const relayer = createWalletClient({
  account: privateKeyToAccount(process.env.RELAYER_KEY),
  chain: mainnet, transport: http(RPC_URL),
})
const balance = await relayer.readContract({ ...vault, functionName: 'totalAssets' })
```

<Answer>
**Problem 1 — the flow is not what it claims.** `writeContract` from a JSON-RPC account sends
`eth_sendTransaction`, so the *user* pays and the user's wallet
broadcasts.<Cite src="viem-send-transaction-doc" /> The relayer is never involved. Nothing here is
gasless; the server is decoration. A relayed flow requires the user to produce a *signature over an
intent* — a typed-data signature the contract verifies — not a transaction. Same library, entirely
different action.

**Problem 2 — `nonce` and `maxFeePerGas` are suggestions.** Both are being passed to a wallet that
owns those decisions.<Cite src="viem-send-transaction-doc" /> A hard-coded `expectedNonce` from a
server round-trip is a race against the user's own pending transactions, and
[a nonce gap or a duplicate](/c/account-nonce-eoa) is a stuck queue rather than an error you will see
here.

**Problem 3 — the hash is being used as a primary key.** It is stored as `id` at the moment of
broadcast, and the user can speed up or cancel that transaction, which
[produces a different hash for the same nonce](/c/tx-replacement-changes-the-hash). The row orphans
silently. Key on `(address, chainId, nonce)` and treat the hash as mutable.

**Problem 4 — `readContract` on the relayer client compiles and is a real design smell.** It compiles
only because the client was never extended with public actions — so in fact this line does *not*
compile, which is the type system doing its job. If someone "fixes" it by adding
`.extend(publicActions)`, the code will work while quietly routing reads through the same object that
holds the relayer key. Reads belong on a keyless client.

**Problem 5 — the relayer key is in an environment variable.** Not wrong on its own; incomplete.
`privateKeyToAccount` signs with whatever it is handed, with no prompt and no
policy.<Cite src="viem-local-account-doc" /> Anything that can read that variable is the relayer.
Whether that is acceptable is a threat-model question about
[the capability that key confers](/c/capability-not-role), and it deserves an answer written down
somewhere, not an implicit one.

**What the type system caught:** exactly one of the five — problem 4, and only in its literal form.
Types enforce which *action set* a client carries. They have nothing to say about who pays, whether a
nonce is racing, whether a hash is stable, or who can read your environment.
</Answer>
</Check>

## Where this pays off

**The next lesson** takes the transport under the Public Client and removes its single point of
failure, then shows how to collapse a screenful of reads into one round trip — both without touching
the action code, because of the split from the first lesson.

**The simulate lesson** is where the two clients meet properly: the read client answers "would this
work" and hands a prepared request to the write client, so the human is only interrupted for
transactions that have already passed a check.<Cite src="viem-simulate-contract" />

**The wagmi module** turns the JSON-RPC-account path into hooks — connectors, chain switching, and the
connect button. Everything you just learned about who signs and who can refuse is what those hooks are
wrapping, and the wallet is still the one holding the key.
