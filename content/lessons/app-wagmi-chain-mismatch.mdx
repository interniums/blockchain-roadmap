Put these two lines in a debug corner of any multi-chain app and leave them there:

```tsx
const configChainId = useChainId()
const walletChainId = useConnection().chainId
```

They are different pieces of state, they are allowed to disagree, and when they do, every read hook
in your app that did not name a chain explicitly is answering a question about
`configChainId` while the user is looking at a wallet showing `walletChainId`.

Nothing throws. Nothing logs. The balance renders, formatted, with the right number of decimals, from
a chain the user is not on. This is the last lesson of the module because it is the failure mode with
no symptom — every other bug in wagmi shows you something missing, and this one shows you something
wrong.

## Three chain ids, and only one of them is the wallet's

**The wallet's active chain.** Whatever network the user has selected in their extension or their
phone. `useConnection().chainId` reports it, as the connected chain id **from the
connector**.<Cite src="wagmi-use-connection" />

**The Config's chain.** `config.state.chainId`, which `useChainId()` returns, and which
`useSwitchChain` manipulates when nothing is connected.<Cite src="wagmi-use-chain-id" /><Cite src="wagmi-src-use-chain-id" /><Cite src="wagmi-use-switch-chain" />
This is the value that selects a transport, which is why it is the one your reads actually use.

**The chain id on the hook call.** `useReadContract({ ..., chainId })`. Optional, and when omitted,
`useReadContract` substitutes `useChainId({ config })` — the source is
`chainId: parameters.chainId ?? chainId`.<Cite src="wagmi-src-use-read-contract" />

`syncConnectedChain` defaults to `true` and exists to keep the second in step with the
first.<Cite src="wagmi-create-config" /> Most of the time it does, which is exactly why the times it
does not are so expensive. The subscription in `createConfig` carries an explicit guard:

```ts
// If chain is not configured, then don't switch over to it.
const isChainConfigured = chains.getState().some((x) => x.id === chainId)
if (!isChainConfigured) return
```

<Cite src="wagmi-src-create-config" />

So the Config follows the wallet **only onto chains you listed in `chains`**. Switch to a chain your
config does not know and the sync silently declines, leaving `config.state.chainId` on whatever it
was. The documentation states the resulting behaviour from the other side: `useChainId` only returns
chain ids for chains configured via `createConfig`'s `chains` parameter, and if the active
connection's chain id is not one of them, it returns the **last configured chain
id**.<Cite src="wagmi-use-chain-id" />

Read that as a user story. Your config lists Ethereum and Base. Your user switches MetaMask to
Arbitrum. `useConnection().chainId` is `42161`. `useChainId()` is `8453`. Every unqualified read in
your app now describes Base.

## Why the wrong answer looks right

A read against the wrong chain does not error because there is nothing wrong with it. viem encodes
the call, picks the transport registered for that chain id, and the node answers
honestly.<Cite src="wagmi-src-create-config" /> The result is real data about a real chain.

The reason it is *plausible* data rather than obvious nonsense is two facts you already have.

**An address is a key, not a location.** An EOA exists on every EVM chain simultaneously, because
"existing" means nothing more than being derivable from a key. `balanceOf(user)` on the wrong chain
is a well-formed question about an account that genuinely exists there.

**Contract addresses collide on purpose.** [CREATE2 deployment](/c/create2-address) puts the same
token at the same address on many chains, deliberately. So the wrong-chain call usually reaches a
contract, usually with the same ABI, and returns a number.

The common outcome is a confident zero, which reads as "you have no tokens" rather than "I asked the
wrong chain". The dangerous outcome is a non-zero number, which happens whenever the user genuinely
holds the asset on both chains — and now your UI is off by whatever the difference is, with a Send
button next to it.

### The wallet is not in the read path at all

One more reason the divergence goes unnoticed: your reads never touch the wallet. `getClient` looks
up `rest.transports[chainId]` and builds a viem Client from it, so a read goes straight to the RPC
endpoint you configured for that chain.<Cite src="wagmi-src-create-config" /> The wallet is consulted
for accounts, chain switching and signatures — never for `eth_call`.

That is the right design. It means your reads keep working while the wallet is locked, are not
rate-limited by a wallet vendor's node, and are as fast as the transport you chose. It also means
there is no moment at which the wallet could object to a question about a chain it is not on, because
it is never asked. The only thing standing between a user's dropdown and your RPC endpoint is
`config.state.chainId`, and you have just seen the guard that stops it moving.

## The rule for reads: name the chain, always

Passing `chainId` explicitly is not defensive style. It converts a silent substitution into a loud
one. Compare the two paths through `getClient` in the Config's source:<Cite src="wagmi-src-create-config" />

```ts
const chainId = config.chainId ?? store.getState().chainId
const chain = chains.getState().find((x) => x.id === chainId)
// chainId specified and not configured
if (config.chainId && !chain) throw new ChainNotConfiguredError()
```

**Explicit and unconfigured throws.** You get `ChainNotConfiguredError` at the call site, in
development, the first time you run it. **Implicit and unconfigured cannot throw**, because by the
time it is read it has already been replaced by a configured value.

That asymmetry gives you a rule you can enforce mechanically:

> Every read hook names its chain. A read that does not name a chain is a read whose answer depends
> on the user's wallet dropdown.

Where the chain genuinely is the user's choice, make that explicit too — `chainId: selectedChainId`,
from your own state, rather than by omission. Omission does not mean "follow the user"; it means
"follow a value that follows the user conditionally, and silently falls back when the condition
fails".

<Aside kind="note">
The same argument applies to `scopeKey`'s neighbours in the query key. `chainId` is part of the key,
so naming it also means two components reading the same value for two different chains no longer
share a cache entry by accident.<Cite src="wagmi-use-read-contract" /> The cache correctness and the
answer correctness have the same fix, which is unusual and worth taking.
</Aside>

## Writes fail in the opposite direction

A read on the wrong chain returns a wrong answer. A write on the wrong chain either goes to the wrong
chain or is refused — and it will not be silently redirected, because the wallet signs with the
[EIP-155 chain id inside the payload](/c/eip-155-chain-id-replay). A transaction built for one chain
is not valid on another.

That protects you from replay. It does not protect you from the user being on Arbitrum while your
button expected Base, because in that case the wallet happily signs a perfectly valid Arbitrum
transaction — against the address your Base-shaped code told it to call.

The gate is `useSwitchChain`, and its behaviour depends on connection state in a way the docs state
plainly: when connected, it switches the target chain for the **connector**; when not connected, it
switches the target chain for the **Config**.<Cite src="wagmi-use-switch-chain" /> One hook, two
different subjects.

Underneath, for an injected wallet, the sequence in wagmi's source is:<Cite src="wagmi-src-injected-connector" />

1. Reject immediately if the requested chain is not in `config.chains` —
   `SwitchChainError(ChainNotConfiguredError)`.
2. Send `wallet_switchEthereumChain` with the chain id as a hex string.<Cite src="eip-3326" />
3. If that returns error code `4902`, or a MetaMask-mobile-wrapped `4902`, build an
   `addEthereumChain` payload and send `wallet_addEthereumChain`.<Cite src="eip-3085" /><Cite src="wagmi-src-injected-connector" />
4. Resolve only when the `change` event carrying the new chain id arrives.

Three things in that list are worth internalising.

**Both RPC methods are Stagnant EIPs.** EIP-3326 and EIP-3085 are the universally implemented,
never-finalised interface every wallet exposes.<Cite src="eip-3326" /><Cite src="eip-3085" /> Wallet
behaviour around them varies, and wagmi's source carries a comment about one such divergence: during
`wallet_switchEthereumChain`, MetaMask makes a `net_version` call to the target chain, and if that
call fails it does not emit `chainChanged` but **still switches the chain** — so wagmi re-reads and
emits the change itself.<Cite src="wagmi-src-injected-connector" />

**`switchChain` is optional on the Connector interface.**<Cite src="wagmi-src-create-connector" /> A
connector may not have one. Your UI needs a path for a wallet that cannot switch, and that path is
instructions, not a spinner.

**WalletConnect may refuse rather than prompt.** WalletConnect v2 requires chains to be pre-approved
at session time, so switching to a chain the session never approved throws — and depending on
`isNewChainsStale` it may instead disconnect the user on auto-connect.<Cite src="wagmi-connector-walletconnect" />

  why="Awaiting a promise usually establishes a fact that stays true, and here the fact is under the control of a person with a different UI open."

The shape that survives contact with users is a gate rather than a step: read the connection's chain
id, and if it is not the one this action requires, render a **Switch network** button instead of the
action. The user performs the switch as a deliberate act, the component re-renders on the connector's
`change` event, and the real button appears. No handler holds a stale assumption across an `await`,
because no handler spans the switch.

<Check type="spot-bug" concept="wagmi-chain-mismatch">
An app supports Ethereum and Base. Its config lists both. A portfolio page renders

```tsx
const { data } = useReadContract({ abi: erc20Abi, address: USDC, functionName: 'balanceOf', args: [address] })
```

and a Bridge button does

```tsx
async function onBridge() {
  await switchChain.mutateAsync({ chainId: base.id })
  bridge.mutate({ address: BRIDGE, abi, functionName: 'deposit', args: [amount] })
}
```

Three reports arrive. Diagnose each.

1. A user on Arbitrum sees a USDC balance of zero and insists they hold USDC.
2. A user reports the Bridge button "did nothing", then later found a failed transaction on
   Ethereum.
3. A WalletConnect user is disconnected every time they open the app, since the team added a third
   chain to the config last week.

<Answer>
**1 — the read fell back to a configured chain.** Arbitrum is not in `chains`, so
`syncConnectedChain` declined to follow it and `useChainId()` returned the last configured chain
id.<Cite src="wagmi-src-create-config" /><Cite src="wagmi-use-chain-id" /> The hook passes no
`chainId`, so it inherited that value.<Cite src="wagmi-src-use-read-contract" /> The app read USDC on
Ethereum or Base and reported a real balance for a chain the user is not on — zero, in their case.
Two fixes, and both are needed: pass `chainId` explicitly so the question is unambiguous, and detect
`useConnection().chainId` not being in your configured set so you can say "unsupported network"
rather than showing a number.<Cite src="wagmi-use-connection" />

**2 — a race across the `await`.** `switchChain.mutateAsync` resolved, and then something changed the
chain back before the write was signed: the user declined and a stale resolution slipped through, the
user switched manually in the wallet, or the wallet's own switch reported success without emitting
the event wagmi waits for — the exact case wagmi's source works around for
MetaMask.<Cite src="wagmi-src-injected-connector" /> The write was then signed on Ethereum with
Base-shaped calldata, which is a valid Ethereum transaction that fails. Restructure as a gate: if the
connection's chain is not Base, render Switch network; only render Bridge when it is. Passing
`chainId` on the write hook as well makes the mismatch an error instead of a wasted fee.

**3 — `isNewChainsStale`, working as documented.** Adding a chain to the config after a WalletConnect
session was established makes it a chain the session has no approval relationship with. With the
default of `true`, wagmi treats it as stale and disconnects on auto-connect so the user is forced to
reconnect and approve.<Cite src="wagmi-connector-walletconnect" /> Setting it to `false` keeps them
connected at the cost of a throw if they later try to switch to that chain, which your code must
handle. There is no setting that removes the problem; the honest fix is to prompt for reconnection
with an explanation when the configured chain set changes.

**The through-line.** Each report is a place where the wallet's chain and the app's chain were
allowed to differ without anyone being told. The first is a read that did not name its chain, the
second is a write that trusted a moment that had passed, and the third is a session whose chain set
was decided before your config changed.
</Answer>
</Check>

## What this unlocks

**Two lines in your debug corner, permanently.** `useChainId()` beside `useConnection().chainId`, and
an "unsupported network" state for when the second is not in your configured
set.<Cite src="wagmi-use-chain-id" /><Cite src="wagmi-use-connection" />

**A review rule with no judgement in it.** Every read names a chain; every write is gated on the
connection's chain rather than preceded by a switch.

**And the module is done.** wagmi is [viem plus TanStack Query](/c/wagmi-is-viem-plus-query) with
connectors bolted on; reads are cached questions that nothing invalidates for you; the key you
invalidate must be built rather than guessed; a connector hides the wallet but not its failure modes;
a connected address is a claim, not a login; the server cannot know your wallet unless you put it in
a cookie; and the chain in the wallet is not the chain in your hook. The reflection prompt asks you
to write down a staleness budget for your three most important reads — do it now, while the whole
stack is still in your head, because the three you cannot answer without guessing are the ones that
will page you.
