Open a terminal against a running dapp's backend and send this:

```bash
curl 'https://app.example/api/portfolio?address=0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045'
```

If it returns that account's portfolio, the application has no authentication. Not weak
authentication — none. The address in the query string is a string the client chose, and there is
nothing anywhere in the request that ties it to a person.

The uncomfortable part is that the frontend of such an app usually looks correct. It has a Connect
button, it shows an avatar and a truncated address, it gates the whole UI behind
`useConnection().status === 'connected'`, and it looks exactly like every product you have logged
into.<Cite src="wagmi-use-connection" /> That resemblance is the bug. **Connecting is a UI event.
Authentication is a server-verified proof.** They are placed together, styled together, and named
similarly, and they have nothing to do with each other.

## What "connected" actually asserts

Strip the hook away and connecting is one EIP-1193 request that returned an array of
addresses.<Cite src="eip-1193" /> The connector wrapped it, wagmi put it in the Config's store, and
`useConnection()` reads it back.<Cite src="wagmi-use-connection" />

Notice what never happened. No challenge was issued. Nothing was signed. No private key was
exercised. The wallet **claimed** that the user controls the address, and there was no reason for it
to lie, because the wallet is on the user's side. It is a claim from a cooperative party, and it is
appropriate for what it is used for on the client: deciding what to render.

Now move that claim across the network and it changes character completely. On the server it arrives
as bytes in a request — a query parameter, a JSON body field, a header — put there by whatever
software is speaking HTTP, which need not be your frontend at all. Anyone can send any address. That
is not a vulnerability with a CVE; it is the absence of a mechanism.

The rule to carry:

> The client may use a connected address to decide what to draw. The server may never use a
> client-supplied address to decide what to return.

## Proof is a signature over something your server chose

Control of an address is provable in one way: [an ECDSA signature](/c/ecdsa-secp256k1) that recovers
to it. The interesting design work is not the cryptography — you have that — it is what gets signed.

A signature over a constant string proves nothing useful. Capture it once and it is a bearer token
with no expiry, replayable against you forever, and replayable against every other site that asks
users to sign the same friendly sentence. The message therefore needs three properties.

**Freshness, so a captured signature is spent.** A random nonce your server issued and will accept
exactly once.

**Origin binding, so the signature is only good at your site.** The domain must be inside the signed
bytes, or a phishing site can relay a signature it collected to your backend.

**A lifetime, so a leaked signature stops working.** An issue time and an expiry.

[EIP-4361](/c/wagmi-connection-not-authentication), Sign-In with Ethereum, is the standard message
format for exactly this. It defines an ABNF grammar for a plaintext message and names the
fields:<Cite src="eip-4361" />

| Field | Required | What it is for |
|---|---|---|
| `domain` | yes | The authority requesting the signature — the origin binding |
| `address` | yes | The signing account, in ERC-55 checksummed form |
| `uri` | yes | The resource that is the subject of the signing |
| `version` | yes | Must be `1` |
| `chain-id` | yes | The EIP-155 chain the session is bound to, and where contract accounts are resolved |
| `nonce` | yes | Random, chosen by the relying party, at least 8 alphanumeric characters |
| `issued-at` | yes | RFC 3339 datetime |
| `expiration-time` | no | When the signed message stops being valid |
| `statement`, `not-before`, `request-id`, `resources` | no | Human-readable assertion, validity window, correlation id, requested scopes |

Two of those rows are load-bearing in ways the table understates. **`chain-id` is where a contract
account must be resolved**, which matters the moment a smart account signs.<Cite src="eip-4361" />
And **`domain` is what the wallet checks against the request origin** — the spec requires wallets to
prevent phishing by verifying that a message beginning "example.com wants you to sign in" actually
came from `https://example.com`.<Cite src="eip-4361" /> That is a wallet obligation, not a courtesy,
and it is the reason the domain belongs in the message rather than in a header.

viem ships both halves: `createSiweMessage` and `generateSiweNonce` from `viem/siwe` build the
message, and `publicClient.verifySiweMessage` verifies it, taking optional `nonce`, `domain` and
`time` parameters so the checks that matter are done for you rather than by
you.<Cite src="viem-create-siwe-message" /><Cite src="viem-verify-siwe-message" /> On the wagmi side
the prompt is `useSignMessage`, a mutation like every other write hook —
`signMessage.mutate({ message })` in v3.<Cite src="wagmi-use-sign-message" /><Cite src="wagmi-migrate-v2-v3" />

<Aside kind="note">
SIWE signs a plaintext string through `personal_sign`, which is ERC-191 version byte `0x45`. The
leading `0x19` byte exists to guarantee the signed payload **cannot be valid RLP**, which is what
stops a message signature from ever being a transaction signature.<Cite src="eip-191" /> Version
`0x01` of the same registry is [EIP-712](/c/eip-712-typed-data) structured data.<Cite src="eip-191" />
Both are legitimate for login. SIWE chose plaintext so the user can read the exact bytes they are
signing, which is a deliberate trade against EIP-712's typed field rendering.
</Aside>

## The login prompt trains a habit you will need later

A SIWE signature is, by construction, one of the safest things a user can sign. The `0x19` prefix
means the payload cannot be valid RLP, so it can never be a transaction, and the message is plaintext
the user can read.<Cite src="eip-191" /> Nothing they sign at your login screen can move a token.

That is exactly why the login prompt is worth designing carefully, and the reason is behavioural
rather than cryptographic. The same wallet dialog, in the same position, with the same buttons, is
also how a user approves [an off-chain permit](/c/erc2612-permit) or a
[Permit2 allowance](/c/permit2) — messages that do move tokens, and that a user cannot distinguish
from a login by the shape of the interaction. Every app that asks for a signature on page load, on
every navigation, or "to refresh your session" is teaching its users to dismiss the dialog without
reading it, and [blind signing](/c/blind-signing) is the precondition for the losses that follow.

So the operational rule is not only "one prompt per session" for the sake of UX. **Signature prompts
are a budget your product spends against a user's attention**, and the balance is drawn down by
whoever asks last — usually not you. Sign once, at a moment the user initiated, with a
`statement` that says what signing does.<Cite src="eip-4361" />

## Verification is not `ecrecover` any more

The naive server-side check — recover the address from the signature, compare to the claimed address
— is correct only for externally owned accounts. viem is explicit about this: the `verifyMessage`
**utility** can only verify a message signed by an EOA, and you should use the public client
**Action** instead.<Cite src="viem-verify-message-util" />

The Action covers the cases the utility cannot, because a contract has no private
key:<Cite src="viem-verify-message-action" />

- **Deployed smart accounts** via ERC-1271, whose `isValidSignature` returns a magic value rather
  than recovering anything.<Cite src="eip-1271" />
- **Pre-deployed (counterfactual) accounts** via ERC-6492, for an account whose address is known but
  whose code is not on chain yet.<Cite src="eip-6492" />
- **Pre-delegated accounts** via ERC-8010, the case that matters for an EOA that is about to become
  [a delegated account](/c/delegation-designator).<Cite src="viem-verify-message-action" />

Choosing the utility because it is synchronous and needs no RPC is choosing to reject every smart
account and every passkey wallet at your login screen, with an error message that says the signature
is invalid. EIP-4361 states the requirement directly: EOAs use ERC-191, contract accounts SHOULD use
ERC-1271, and the verifying contract must be resolved from the message's
`chain-id`.<Cite src="eip-4361" />

<Aside kind="warn">
ERC-1271 verification reads chain state, and the spec warns that implementations **are not required
to be pure functions** — the same message and signature can validate today and fail tomorrow if the
account's owner set changes. It recommends invalidating affected sessions when that
happens.<Cite src="eip-4361" /><Cite src="eip-1271" /> A multisig that removes a signer has revoked
a login your database still considers valid. If you support smart accounts, session invalidation is
a feature you owe, not an edge case.
</Aside>

## The flow, with each step named by its purpose

**Subgoal — connect, purely to learn which address to challenge.** No trust is extended here. The
address is an input to the next step and nothing else.

**Subgoal — get a nonce from the server, so freshness is not the client's decision.** The server
generates it, stores it against the session, and will accept it once. A client-generated nonce
proves nothing, because an attacker replaying a captured message controls the client.

**Subgoal — build the message with the fields that bind it.** `domain` from your own configuration
rather than from `window.location`, which an attacker's page controls; `chainId` from the connection;
the server's `nonce`; an `expirationTime` short enough that a leaked signature is worthless — minutes,
not days.<Cite src="viem-create-siwe-message" />

**Subgoal — prompt once, with `useSignMessage`.** One wallet interaction. If your design signs on
every request you have built something users will click through blind, which is the precondition for
every signature-phishing loss.<Cite src="wagmi-use-sign-message" />

**Subgoal — verify server-side, against values the server already knows.** Send message and signature
to your backend and call `verifySiweMessage` with the expected `nonce` and `domain`, using a public
client so contract accounts work.<Cite src="viem-verify-siwe-message" /><Cite src="viem-verify-message-action" />
Never verify on the client. A client that verifies a signature has verified a signature for itself.

**Subgoal — convert the proof into a session, and bind that session to the address.** Issue your
ordinary session cookie. EIP-4361 is explicit that sessions MUST be bound to the address and not to
further resolved resources that can change.<Cite src="eip-4361" /> From here your app is a normal
authenticated web app, and every API route reads the address from the session, never from the
request.

**Subgoal — invalidate on the events that end the session.** Account changed in the wallet, chain
changed if your session is chain-bound, disconnect pressed, expiry reached. The
[connector callbacks](/c/wagmi-connector-abstraction) are where the first two arrive.

<Check type="explain" concept="wagmi-connection-not-authentication">
A team adds SIWE. The client calls `createSiweMessage` with `domain: window.location.host`, a nonce
from `crypto.randomUUID()`, and no `expirationTime`. It signs, then calls `verifyMessage` from
`viem` in the browser, and on `true` sets `localStorage.authed = address`. The API reads the address
from a request header. Name every defect and rank them.

<Answer>
**1 — the API still trusts a client-supplied address. Nothing else matters until this is fixed.**
The header is chosen by the caller; the entire SIWE flow is decoration on top of an unauthenticated
API. The only fix is a server-issued session, with the address read from it.<Cite src="eip-4361" />

**2 — verification happens on the client.** A check performed by the party being checked is not a
check. Message and signature must go to the server, and the server must verify.

**3 — the nonce is client-generated, so replay is unaffected.** A nonce exists so the *relying party*
can insist on freshness; the spec says it is typically chosen by the relying
party.<Cite src="eip-4361" /> An attacker replaying a captured message supplies whatever nonce is in
it, and a server that never issued one has nothing to compare against.

**4 — `verifyMessage` from `viem` is the EOA-only utility.** Every smart account and passkey wallet
is rejected with "invalid signature".<Cite src="viem-verify-message-util" /> The public client Action
handles ERC-1271, ERC-6492 and ERC-8010.<Cite src="viem-verify-message-action" />

**5 — no `expirationTime`, so a captured signature never expires.** It is optional in the grammar
and mandatory in practice.<Cite src="eip-4361" />

**6 — `domain` comes from `window.location.host`.** On your own page this is right and harmless. In
the threat model it is worthless, because the attacker's page sets it to whatever it likes; the value
that matters is the one the *server* compares against, which must be your configured
domain.<Cite src="viem-verify-siwe-message" /> The wallet performs its own origin check against this
field, which is where the anti-phishing value actually lives.<Cite src="eip-4361" />

**7 — `localStorage.authed` is a flag the user can set.** It is a UI hint being used as a
credential.

**The ranking matters more than the list.** Defects 2 through 7 are refinements of one mistake, and
defect 1 is the mistake: authority was never moved to the server. A reviewer who fixes the nonce
generation and calls the PR done has improved the ceremony around an API that still answers to
anyone.
</Answer>
</Check>

## What this unlocks

**A login you can describe to a security reviewer in four sentences.** Server issues a nonce, user
signs a domain-bound message with an expiry, server verifies it in a way that admits smart accounts,
server issues a session bound to the address.

**Honest product language.** "Connect" means the page can see an address. "Sign in" means your
backend has proof. A single button labelled "Connect wallet" that also creates a server session is
lying about one of the two.

**Two lessons left, both about state that disagrees with itself.** Why server-rendered HTML cannot
know about a wallet at all — and why the chain in the wallet is not the chain your hooks are reading.
