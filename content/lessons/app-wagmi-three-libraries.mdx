Here is the entire body of `useReadContract`, the hook most people think of as "wagmi reading the
chain". This is the source at the `wagmi@3.7.6` tag, reformatted only to fit the
column:<Cite src="wagmi-src-use-read-contract" />

```ts
export function useReadContract(parameters = {}) {
  const config = useConfig(parameters)
  const chainId = useChainId({ config })
  const options = readContractQueryOptions(config, {
    ...parameters,
    chainId: parameters.chainId ?? chainId,
  })
  return useQuery(options)
}
```

Four statements. None of them opens a socket, encodes calldata, or knows what a contract is. The
hook reads a config out of React context, decides which chain id to use, asks another package to
build a query descriptor, and hands that descriptor to a cache library.

That is not a simplification of wagmi. That *is* wagmi. The library you are about to spend a module
on is a coordination layer over three other things, and almost every hour you will lose to it is an
hour spent debugging one of the three while reading the documentation of the wrong one.

## Three responsibilities, none of them wagmi's

wagmi's own documentation states the division without hedging: **wagmi Core is essentially a wrapper
over viem** that provides multi-chain functionality via the wagmi Config and automatic account
management via connectors, and **all of the core hooks are friendly wrappers around viem actions**
that inject a multi-chain and connector-aware Config.<Cite src="wagmi-viem-guide" /> The other half
of the sentence is on the caching page: wagmi hooks utilise TanStack Query to enable fetching,
caching, synchronising and updating of asynchronous data.<Cite src="wagmi-tanstack-query" />

Put concretely, for any hook you call:

**viem does the chain I/O.** Encoding the call, choosing the transport, sending the JSON-RPC
request, decoding the response, and throwing a typed error when it fails. Everything you learned in
the [viem client and transport](/c/viem-client-vs-transport) module is still exactly what is running
— wagmi did not wrap it in a new abstraction, it passed it a Client.

**TanStack Query v5 does everything between the component and the request.** Deduplication, the
cache, staleness, retries, `isPending` versus `isFetching`, garbage collection, refetch-on-focus.
Every one of those behaviours is TanStack's, configured by TanStack's options, documented on
TanStack's site.<Cite src="wagmi-tanstack-query" />

**wagmi supplies the three things neither of the others has.** A connector abstraction so a wallet
can be swapped without touching call sites; chain switching and a notion of "the current chain"; and
a Config object that persists connection state across page loads.<Cite src="wagmi-viem-guide" /><Cite src="wagmi-create-config" />

The practical payoff of holding that split in your head is a routing rule for questions, and it is
worth writing on the wall of any team adopting this stack:

> A caching question is a TanStack Query question. A chain question is a viem question. Only
> connectors, chain switching and config are actually wagmi questions.

**A caching question** sounds like: why did this fire twice, why is it stale, why did it refetch when
I focused the tab, what is the difference between `isPending` and `isFetching`. Searching wagmi's
docs for those answers wastes an afternoon; they are one page deep in TanStack's.

**A chain question** sounds like: why is this argument the wrong type, why does the revert come back
as hex, why did the RPC batch these together, what is a `bigint` doing in my formatter. Those are
viem's, and you have already answered most of them.

**A wagmi question** sounds like: why did the wallet not appear in my list, why did the chain switch
silently not happen, why does the page render disconnected on the server. Those are the four
remaining lessons of this module, and they are wagmi's alone precisely because nothing underneath
knows a browser extension exists.

## The config is the object, the provider is furniture

`createConfig` takes `chains`, `connectors`, `transports` and `storage`, plus a handful of flags, and
returns the one object that defines which chains exist, how to reach each of them, which wallets may
connect, and where connection state persists.<Cite src="wagmi-create-config" /> `chains` and
`transports` are required; `connectors` defaults to undefined; `storage` defaults to `localStorage`
when a window exists and a no-op store otherwise.<Cite src="wagmi-create-config" />

`WagmiProvider` does one job: it puts that object into React context. It is not a client, it holds
no state of its own, and every hook's `config` parameter exists so you can bypass the provider
entirely and pass the object directly.<Cite src="wagmi-use-read-contract" /> The same object is what
the vanilla `@wagmi/core` actions take as their first argument, which is why a utility function in
a non-React file can read exactly the same state your components see.

Three consequences follow, and the third is the one that bites.

**There is no per-component client to construct.** If you are used to instantiating a provider or a
signer near the code that uses it, unlearn it here. The Config is a singleton for the app.

**Configuration is not React state.** Which chains exist and how they are reached is decided once, at
module evaluation or inside a `useState` initialiser, and changing it means rebuilding the object.
Anything you want to vary per render is a hook argument, not a config field.

**Two configs is a bug that looks like a race condition.** Build a second Config anywhere — a test
helper, a lazily-imported module that calls `createConfig` again, a Storybook decorator — and you now
have two independent stores of connection state reading the same wallet. One reports connected, the
other disconnected, and which one a component sees depends on which provider it happens to be under.
The symptom is intermittent; the cause is structural.

<Aside kind="note">
Two of `createConfig`'s defaults are worth knowing now because they explain behaviour you will
otherwise attribute to magic. `multiInjectedProviderDiscovery` defaults to true, which turns on
[EIP-6963](/c/wagmi-eip6963-discovery) wallet discovery.<Cite src="wagmi-create-config" /><Cite src="eip-6963" />
And `syncConnectedChain` defaults to true, which makes the Config's idea of the current chain follow
the connected wallet — with an exception that is the entire subject of this module's last
lesson.<Cite src="wagmi-create-config" /><Cite src="wagmi-src-create-config" />
</Aside>

## The v3 rename, and the more useful version of that warning

Every wagmi tutorial, answer and code sample written before v3 uses names v3 has moved on from.
The migration guide lists them under a heading titled **Deprecations**:<Cite src="wagmi-migrate-v2-v3" />

| Was | Is |
|---|---|
| `useAccount` | `useConnection` |
| `useAccountEffect` | `useConnectionEffect` |
| `useSwitchAccount` | `useSwitchConnection` |
| `useConnect().connect` / `.connectAsync` | `.mutate` / `.mutateAsync` |
| `useWriteContract().writeContract` | `.mutate` |
| `useConnect().connectors` | `useConnectors()` |
| `useSwitchChain().chains` | `useChains()` |

The reasoning behind the first three is stated plainly: at the core of wagmi are *connections*
between apps and Ethereum providers, and the account hooks were renamed to represent that more
accurately.<Cite src="wagmi-migrate-v2-v3" /> The mutate rename is about ergonomics — it lets you
name the hook result whatever you want without renaming destructured keys, so two `useWriteContract`
calls in one component become `transfer.mutate` and `approve.mutate` instead of a pile of
aliases.<Cite src="wagmi-migrate-v2-v3" />

Now the part the summaries get wrong, and it changes what you should worry about. **Those old names
still exist.** At the `wagmi@3.7.6` tag, the React package's export barrel exports
`useConnection as useAccount` with an `@deprecated` tag on it; `useWriteContract` returns `mutate`
*and* a `writeContract` alias marked deprecated; `useConnect` still returns `connect`, `connectAsync`
and `connectors`; `useSwitchChain` still returns `chains`.<Cite src="wagmi-src-react-exports" /><Cite src="wagmi-src-use-write-contract" /><Cite src="wagmi-src-use-connect" /><Cite src="wagmi-src-use-switch-chain" />

So a v2 component pasted into a v3 app compiles and runs. What it does not do is survive the removal
that a deprecation announces, and it teaches every reader of your codebase a vocabulary the docs no
longer use. Treat the table above as a lint rule, not as a crash you are waiting for.

**What actually breaks on upgrade is not a name.** The guide's own overview says v3's purpose is to
give you total control over connector dependencies: every connector's SDK is now an optional peer
dependency you install yourself.<Cite src="wagmi-migrate-v2-v3" /> `walletConnect` needs
`@walletconnect/ethereum-provider`; `coinbaseWallet` needs `@coinbase/wallet-sdk`; `metaMask` needs
`@metamask/connect-evm`; `safe` needs both `@safe-global/safe-apps-provider` and
`@safe-global/safe-apps-sdk`; `baseAccount` needs
`@base-org/account`.<Cite src="wagmi-migrate-v2-v3" /> A v2 app that upgraded and did not install
them builds fine and fails when a user presses Connect — the worst possible place, because it is the
one path your smoke test probably stubs.

## Tracing one call through all three layers

Take a single `useReadContract` for an ERC-20 balance and follow it down. The point of the exercise
is not the trace; it is that each step belongs to a different owner with a different failure mode.

**Subgoal — establish which config and which chain the question is asked against.** The hook calls
`useConfig`, then `useChainId({ config })`, then sets `chainId: parameters.chainId ?? chainId`.<Cite src="wagmi-src-use-read-contract" />
If you passed a `chainId`, that wins. If you did not, the Config's current chain is substituted
silently. **Owner: wagmi.** Failure mode: the answer is about a chain you did not mean.

**Subgoal — turn the arguments into a cache identity.** `readContractQueryOptions` produces a query
key, a query function and a `structuralSharing` setting. The key is a two-element tuple: the literal
string `'readContract'` and a filtered copy of the options.<Cite src="wagmi-src-query-read-contract" />
**Owner: wagmi, on TanStack's behalf.** Failure mode: two questions you thought were different share
one identity, or two you thought were identical do not.

**Subgoal — hand the descriptor to the cache.** wagmi's own `useQuery` wrapper forwards to TanStack's
and adds one option: `queryKeyHashFn: hashFn`, commented in the source as *for bigint
support*.<Cite src="wagmi-src-react-query-utils" /> From here, whether a request happens at all is
TanStack's decision, made from the key, the cached entry and the staleness settings. **Owner:
TanStack Query.** Failure mode: no request when you wanted one, or five when you wanted one.

**Subgoal — actually ask the chain.** Only if TanStack decides to fetch does the query function run,
and only then does viem encode the call, pick the transport for that chain id, and issue JSON-RPC.
**Owner: viem.** Failure mode: transport errors, decode errors, typed reverts.

**Subgoal — get the answer back into the component.** TanStack stores the result and returns
`data`, `error`, `isPending`, `isFetching`, `refetch` and the rest of its result object, which wagmi
passes through unchanged apart from re-attaching `queryKey`.<Cite src="wagmi-src-react-query-utils" /><Cite src="wagmi-use-read-contract" />
**Owner: TanStack Query.**

Five steps, three owners, and exactly one of them touches the network. When something is wrong, name
the step before you name the library.

<Check type="explain" concept="wagmi-is-viem-plus-query">
A teammate files four bugs against "the wagmi integration". For each, say which of the three layers
owns it, whose documentation you would open, and what the first diagnostic move is.

1. Five components on a dashboard each render `useReadContract` for the same token's `decimals`, and
   the Anvil log shows five requests.
2. A `uint256` returned by a contract arrives as a `bigint` and crashes a chart component that
   expected a number.
3. After a user switches network in MetaMask, one panel keeps showing the old chain's balance and
   never refetches.
4. The balance shown after a successful transfer is the pre-transfer figure, indefinitely.

<Answer>
**1 — TanStack Query, then wagmi.** Deduplication is entirely a function of the query key: identical
keys share one cache entry and one in-flight request.<Cite src="tanstack-query-keys" /> Five requests
means five distinct keys, so the diagnostic move is to print `queryKey` from all five hooks and diff
them. The usual culprit is one component passing an extra argument, a different `chainId`, or a
`scopeKey`, all of which are part of the key. Only if the keys are genuinely identical does this
become a wagmi bug.

**2 — viem, and it is not a bug.** Every EVM integer crosses into JavaScript as a `bigint`, which is
viem's contract with you and the reason `formatUnits` exists.<Cite src="viem-clients" /> wagmi
returns whatever viem returned; TanStack stores it unexamined. The fix lives at the presentation
boundary, and the search term is viem's, not wagmi's.

**3 — wagmi, and it is the module's last lesson.** Which chain a read targets is decided by wagmi
before TanStack or viem is involved: `parameters.chainId ?? useChainId({ config })`.<Cite src="wagmi-src-use-read-contract" />
A panel that keeps answering about the old chain is a panel whose effective chain id did not change,
either because it pins one explicitly or because the Config's chain id did not follow the wallet. The
first move is to render `useChainId()` next to `useConnection().chainId` and see whether they agree.

**4 — TanStack Query, and it is the module's second lesson.** A read hook is a cached question with
no subscription to the chain. Nothing in the stack observes that a balance changed, so nothing marks
the entry stale.<Cite src="wagmi-tanstack-query" /> The fix is invalidation, and it is your code that
has to do it. Note that this bug and bug 1 have opposite shapes but the same root: the cache does
precisely what the key and the staleness settings say, and neither of those is about the chain.

**The pattern.** Three of the four never touch wagmi's own code, and two of the four are answered by
printing something you can print in thirty seconds — the query key, or the two chain ids side by
side. Layer attribution is not pedantry here; it is the difference between reading the right page and
reading four wrong ones.
</Answer>
</Check>

## What this unlocks

**The next two lessons are the TanStack half**, because that is where the time goes. Reads are
cached questions and writes are mutations, nothing invalidates anything for you, and the query key
you have to invalidate has a shape you should build rather than guess.

**Then the wagmi half**: what a connector actually is and why four wallets fail four different ways,
why a connected address is not an authenticated user, why the server cannot know your wallet, and
why the chain in the wallet is not the chain in your hook.

**The viem half you already have.** Nothing in this module re-teaches encoding, simulation, typed
errors or the `bigint` boundary — when a lesson here needs one, it links to it and keeps going.
