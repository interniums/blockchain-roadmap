Here is a function that shipped, worked for eight months, and then started producing support
tickets:

```ts
function supportsBatching(connectorId: string) {
  return connectorId === 'coinbaseWalletSDK' || connectorId === 'safe'
}
```

Nothing about it broke. The wallets it names still exist and the string comparison still evaluates.
What happened is that a wallet it does *not* name shipped batching, so those users kept getting two
prompts where everyone else got one — and then a wallet it *does* name shipped a release where
batching was available on one chain and not another, and this function, which has no chain parameter,
started returning `true` where the answer was no.

This is the last mile of everything the core tracks gave you. You can read the account record, you
know what a delegation designator does, you can encode a call by hand. None of that tells you what
the software on the other end of the JSON-RPC pipe is willing to do for this user, on this chain,
today. That is a negotiation, and ERC-5792 is where it was standardised.<Cite src="eip-5792" />

## The shape of the mistake

The function above is user-agent sniffing with a different variable name, and the failure mode is
unusually gentle at first: a vendor check is correct on the day you write it, correct against the two
wallets you have installed, and correct in production until a release you did not schedule. Three
properties make it worse here than it was on the web.

**The feature set moves per release, not per major version.** A wallet that could not batch in March
can batch in April without changing its connector id or anything else you could branch on.
[EIP-6963 discovery](/c/wagmi-eip6963-discovery) gives you a stable, honest identity for each
injected provider — which is exactly what makes it tempting, and identity is not
capability.<Cite src="eip-6963" />

**The feature set moves per chain.** ERC-5792 nests its capability response inside per-chain objects
for precisely this reason: a wallet may support different capabilities across the several chains
authorised in one session.<Cite src="eip-5792" /> A boolean with no chain in scope cannot represent
the truth.

**You cannot enumerate the wallets.** The standard's own ecosystem page lists the wallets known to
implement it and states plainly that the list is not exhaustive, inviting additions by pull
request.<Cite src="eip5792-wallets-ecosystem" /> Any branch keyed on membership in a registry
maintained by pull request degrades to the worst path for every wallet nobody has added yet — which,
for a new wallet, is all of its users on day one.

## What the query actually returns

`wallet_getCapabilities` takes an address and an optional array of chain ids, and returns
key-value pairs where the key names a capability, nested inside an object keyed by the EIP-155 chain
id in hexadecimal.<Cite src="eip-5792" /> Four details in that sentence carry weight.

**It is keyed by address, not by wallet.** You are asking what *this account* can do — and after the
next module you will know why those can differ for the same wallet software.

**It is keyed by chain.** Capabilities supported on every chain SHOULD appear once under the special
chain id `"0x0"` and SHOULD NOT be repeated in the per-chain objects, so a correct reader merges the
wildcard entry with the specific one rather than reading only the specific one.<Cite src="eip-5792" />

**An unsupported chain is an omission, not an error.** If the wallet does not support a chain you
asked about, it MUST NOT respond with an error, and MUST instead leave that chain's key out of the
response.<Cite src="eip-5792" /> So the absence of a key is a real answer, and your code must read it
as one.

**It requires an authorised connection.** The method SHOULD return a `4100 Unauthorized` error if the
user has not already authorised a connection between the application and the requested
address.<Cite src="eip-5792" /> Capability discovery is therefore *after* connection in your flow,
never before it — you cannot use it to decide which connect button to show.

A response looks like this:

```json
{
  "0x2105": {
    "atomic": { "status": "supported" },
    "paymasterService": { "supported": true }
  },
  "0x14A34": {
    "atomic": { "status": "unsupported" }
  }
}
```

<Aside kind="note">
Capabilities may also reach you out of band, cached by a provider abstraction. Where an out-of-band
expression is contradicted by a live wallet RPC response, the live response SHOULD be taken as
canonical.<Cite src="eip-5792" /> That is your cache-invalidation rule, written down for you.
</Aside>

## The one capability the spec defines itself

Almost every capability is deliberately left to its own separate ERC. One is not: `atomic` is built
into ERC-5792, and its only property, `status`, takes exactly three values.<Cite src="eip-5792" />

- **`supported`** — the wallet will execute the calls atomically and contiguously.
- **`ready`** — the wallet is able to upgrade to `supported`, pending user approval.
- **`unsupported`** — the wallet provides no atomicity or contiguity guarantees, and will not
  suggest an upgrade to the user.<Cite src="eip-5792" /><Cite src="eip5792-getting-started" />

And the fourth case, which is not a value: **if the `atomic` capability is absent for a chain, the
wallet does not support batching on that chain at all.**<Cite src="eip-5792" /> Absent and
`unsupported` mean different things, and both mean "do not send a batch here".

`ready` is the interesting one, and it is the seam between this module and the next. A wallet reports
`ready` when the account is an EOA that the wallet can upgrade to a smart account supporting atomic
execution, via an EIP-7702 delegation, with user approval.<Cite src="eip5792-atomic-capability" />
The capability response is telling you that an account upgrade is available and has not happened
yet. Your app does not perform that upgrade and does not choose what it upgrades to. It asks for
atomicity, and the wallet decides whether to offer the user the upgrade that would provide
it.<Cite src="metamask-7702-upgrade" />

## Reading it from React

wagmi exposes the query as `useCapabilities`, a normal TanStack query with `account`, `config`,
`connector` and `scopeKey` parameters plus the standard `query` options object.<Cite src="wagmi-use-capabilities" />
Note what is *not* in that list: there is no `chainId` parameter. The hook returns everything the
wallet reports, grouped by chain, and picking your chain out of it is your job. viem's underlying
`getCapabilities` action does take a `chainId`, if you are working below React.<Cite src="viem-get-capabilities" />

```tsx
import { useCapabilities, useChainId } from 'wagmi'

const CHAIN_UNKNOWN = 'unknown'

function useAtomicStatus() {
  const chainId = useChainId()
  const { data, status } = useCapabilities()

  if (status !== 'success') return CHAIN_UNKNOWN

  const forChain = { ...(data?.[0] ?? {}), ...(data?.[chainId] ?? {}) }
  return forChain.atomic?.status ?? 'absent'
}
```

Two things in nine lines are worth naming.

The merge of the wildcard entry over the per-chain entry implements the "SHOULD appear once under
`0x0`" rule.<Cite src="eip-5792" /> Read only `data[chainId]` and you will miss capabilities a wallet
declared globally — the failure is silent and looks exactly like a wallet that lacks the feature.

The early return on `status !== 'success'` is the part most implementations get wrong, and it is the
subject of the rest of this lesson.

## The state your user sees first is "I do not know yet"

`useCapabilities` is a query, so it has the [full query lifecycle](/c/wagmi-read-hooks-are-queries):
`status` is `'pending'`, `'error'` or `'success'`.<Cite src="wagmi-use-capabilities" /><Cite src="wagmi-tanstack-query" />
On a cold load the user's sequence is: page renders, wallet connects, capability request goes out,
answer arrives. Every frame before the last one is `pending`. That produces four states, not two, and
the last two are where the bugs live:

| State | What you know | What the button should do |
|---|---|---|
| `pending` | Nothing yet | Render the safe path, or a disabled control — never the optimistic one |
| `error` | The query failed | Treat as absent; the wallet may not implement the method at all |
| `success`, capability present | The real answer | Branch on it |
| `success`, capability absent | Also a real answer | Take the fallback path deliberately |

**Treat an unknown capability as absent, never as present.** The asymmetry is not stylistic. Assume
absent and be wrong, and the user gets the longer flow once and the better one after — a mild
regression. Assume present and be wrong, and you have already rendered "one signature to finish"
while the wallet is about to ask for three, or to reject the request outright with error `5700`,
*unsupported non-optional capability*.<Cite src="eip-5792" /> The first mistake costs a render; the
second costs the user's trust in a sentence your interface just showed them.

An `error` result reads the same way. A wallet that has never heard of `wallet_getCapabilities`
returns an error rather than an empty object, because the EIP says wallets that do not support these
methods SHOULD return error responses when they are called.<Cite src="eip-5792" /> "The query failed"
and "the wallet is old" are frequently the same event, and both mean: take the fallback path.

## Worked example: replacing the sniff

Take the eight-month-old function from the top and derive its replacement, naming what each step is
for.

**Subgoal 1 — recover the property the branch was protecting.** `supportsBatching` gated a decision
between "submit approve and deposit as one action" and "submit them as two". The property being
tested was never *which wallet is this*. It was *can this account, on this chain, accept several
calls in one request*. That sentence names an address and a chain, and the old signature had neither.

**Subgoal 2 — place the query after authorisation.** Because the method returns `4100 Unauthorized`
without an existing connection, the query belongs in the connected part of the tree, not in the
landing page.<Cite src="eip-5792" /> In wagmi v3 the hook that tells you whether you are connected is
`useConnection` — v2's `useAccount`, renamed along with `useAccountEffect` and `useSwitchAccount` to
reflect that wagmi models connections rather than accounts.<Cite src="wagmi-migrate-v2-v3" /> Every
tutorial written before v3 opens with the old name, including tutorials published by wallet vendors,
so expect to translate as you read.

**Subgoal 3 — make the unknown state explicit in the return type.** The replacement does not return a
boolean, because a boolean has no room for "not yet".

```ts
type BatchSupport = 'unknown' | 'none' | 'sequential' | 'atomic'
```

`unknown` is the pending or errored query. `none` is a successful query with no `atomic` key for this
chain. `sequential` is `status: 'unsupported'`. `atomic` covers `supported`, and — with a decision
you now have to make deliberately — possibly `ready`, which means atomicity is available if the user
accepts an account upgrade.<Cite src="eip5792-atomic-capability" />

**Subgoal 4 — check that every state has a rendering.** Four values, four branches. `unknown` and
`none` may share a visual treatment; they must not share it by accident.

**Subgoal 5 — delete the vendor list, and assert that it stays deleted.** A grep in CI for connector
ids in your components is a cheap regression test, and the exercise at the end of this module asks
for exactly that assertion.

## The cost of asking

One counterweight. The EIP's privacy section warns that exposing capabilities to more callers than
necessary lets a wallet's client software be fingerprinted or probabilistically identified, which —
combined with the web platform's other deanonymisation vectors — can contribute to deanonymising an
individual user, or all users of a client in aggregate. It names applications that over-query
capabilities, or incentivise capability oversharing, as an anti-pattern to be
avoided.<Cite src="eip-5792" />

Concretely: query the capabilities you will act on, where you will act on them. A startup sweep
across every configured chain to populate an analytics event is the behaviour that section describes.
It is also why the design deliberately blurs the difference between a feature the wallet lacks and
one it has not granted you — the occlusion is a privacy feature, not an ambiguity to work
around.<Cite src="eip-5792" />

Your app runs on two chains. The connected wallet returns this from `wallet_getCapabilities`:

```json
{
  "0x0": { "paymasterService": { "supported": true } },
  "0x2105": { "atomic": { "status": "ready" } }
}
```

The user is currently on chain `0xa` (chain id 10), which your app supports and which is not in the
response. Answer four questions: can you batch on the current chain; can you use a paymaster on the
current chain; what does `ready` on `0x2105` commit the wallet to; and what should your primary
button say right now.

<Answer>
**Batching on chain `0xa`: no.** The chain is absent from the response, and the EIP says a wallet
that does not support a requested chain MUST omit the key rather than error — so the omission is the
answer, not a missing answer.<Cite src="eip-5792" /> Even if the chain had been present, an absent
`atomic` capability for a chain means no batching on that chain.<Cite src="eip-5792" /> Two
independent reasons, same conclusion.

**Paymaster on chain `0xa`: yes, as far as this response goes.** `paymasterService` appears under the
special chain id `0x0`, which is how a wallet declares a capability it supports on all chains, and
which SHOULD NOT then be repeated in the per-chain objects.<Cite src="eip-5792" /> A reader that
looks only at `data["0xa"]` sees nothing and concludes wrongly. This is the merge step, and it is the
most common quiet bug in a first implementation.

**What `ready` commits the wallet to on `0x2105`: nothing yet.** It means the account is an EOA and
the wallet can upgrade it — via an EIP-7702 delegation — to a smart account that executes batches
atomically, and that the upgrade requires user approval.<Cite src="eip5792-atomic-capability" /> The
wallet has told you a path exists, not that it has been taken. If you send a batch requiring
atomicity and the user declines the upgrade, the specification gives that its own error code, `5750`
— *atomic-ready wallet rejected upgrade*.<Cite src="eip-5792" /> Your UI needs a state for that, and
it is not the same state as "this wallet cannot batch".

**What the button should say: the sequential copy.** There is no honest way to promise one
confirmation on a chain with no batching, and the fact that the same wallet could batch elsewhere
does not change what happens when the user presses the button now. If you want to offer the better
path, the offer is a chain switch — a separate, explicit thing to ask for, not something to imply by
leaving a one-step label on screen.
</Answer>
</Check>

## Where this pays off

**The next lesson** spends the capability you just learned to read. It submits several calls as one
action with `wallet_sendCalls`, and shows the option that keeps the same code path working against a
wallet that has never heard of the method.

**The lesson after that** takes the single most dangerous inference available from a successful
batch — that its calls succeed or fail together — and shows the on-chain state left behind when that
inference is wrong.

**The EOA-upgrade module** is what `ready` was pointing at. It is the product half of EIP-7702: how
an authorization is signed from TypeScript, what the consent screen owes a user whose account is
about to change indefinitely, and why the delegate address is the wallet's choice and not
yours.<Cite src="eip-7702" />

**Session keys and paymasters**, later in this track, arrive through this same door: both are
capabilities in the ERC-5792 sense — things you ask for and adapt to, rather than features you
assume — and the [permission standards](/c/erc-7715-grant-permissions) that would formalise the
first of them are still drafts.
