Run the approve-and-deposit batch from the last lesson against an account that does not execute
atomically, and arrange for the deposit to fail. Then read the chain.

The allowance is set. The vault balance is unchanged. Your interface, which was written on the
assumption that a batch is a unit, shows "deposit failed" and offers a retry button — while the
user's token contract now carries a standing approval to a vault they have never deposited into. The
retry, if they press it, sends the approval again.

Nothing malfunctioned. Every component did what it promised. The defect is a word: **batch**, which
every engineer reads as *transaction* in the database sense, and which ERC-5792 deliberately does not
define that way.

## The specification refused to promise it

The rationale section says so directly. The authors initially proposed that multiple calls must
execute atomically, and after debate decided that was too opinionated; instead they specified an
`atomic` capability, so that EOA wallets could accept multiple calls while developers retained the
option to submit a batch *only* when it will be executed atomically.<Cite src="eip-5792" />

So atomicity is a property of the account executing the batch, negotiated per chain, not a property
of the method you called. The negotiation has two halves and you must use both.

**On the way out**, the request carries `atomicRequired`, a top-level boolean.<Cite src="eip-5792" />

- With `atomicRequired: true`, the wallet MUST execute all calls **atomically** — either all execute
  successfully or no material effects appear on chain — and **contiguously**, meaning no other
  transactions or calls may be interleaved with the batch. A wallet whose atomicity is `ready` rather
  than `supported` MUST perform that upgrade before submitting.<Cite src="eip-5792" />
- With `atomicRequired: false`, the wallet MAY execute the calls sequentially with no atomicity or
  contiguity guarantee at all — and MAY execute them atomically anyway if it is
  able.<Cite src="eip-5792" />

Read the second bullet again. With `false`, both outcomes are permitted. You do not get to predict
which one you received; you get to *observe* it afterwards.

**On the way back**, that observation is a field. `wallet_getCallsStatus` returns an `atomic` boolean
alongside the status code, and the wallet MUST be explicit about it: `true` when the calls were
executed atomically, `false` when they were not.<Cite src="eip-5792" /> viem surfaces it at the top
level of the status object, next to `statusCode`, `status` and
`receipts`.<Cite src="viem-get-calls-status" />

## Contiguity is a second promise, not a restatement

`atomicRequired: true` buys two things, and conflating them costs you a class of bug that atomicity
alone does not cover.

**Atomicity** says: all of the effects, or none of them.

**Contiguity** says: nothing else runs in between.<Cite src="eip-5792" />

A batch could in principle be all-or-nothing while other transactions interleave with its
constituent parts, and the difference is exactly the surface that [MEV](/c/mev-definition) lives on.
If a price you read in call one is acted on in call three, atomicity guarantees you will not be left
half-applied; only contiguity guarantees that nobody moved the price between them. When you write
"the whole thing succeeds or the whole thing does not" in a design document, check whether the
sentence you actually needed was about interleaving.

## The receipts shape tells you which world you are in

The status response's `receipts` array is shaped differently depending on the answer, and the
difference is the most useful diagnostic the API gives you.

If the wallet executed atomically, it MAY return a `receipts` field containing a single receipt *or*
an array, according to how the calls were included on chain — and it MUST return `atomic: true`.
If it executed non-atomically, it MUST return an array of receipts for all transactions containing
batch calls that were included on chain — **including the batch calls that were included on chain but
eventually reverted** — and MUST return `atomic: false`.<Cite src="eip-5792" />

That inclusion clause is the whole lesson in one line. A reverted call still has a receipt, because
it was still a transaction that was still included and still burned gas. So the non-atomic failure
mode is not "some calls are missing". It is "every call is present, and some of them are
[receipts with a failure status](/c/tx-receipt-status-zero)". Code that counts receipts to decide
whether the batch worked gets the wrong answer; code that reads each receipt's status gets the right
one.

The status codes complete the picture. `500` means the batch reverted completely, with only
gas-related changes possibly on chain. `600` means the batch **reverted partially, with some changes
related to the batch calls possibly included on chain**.<Cite src="eip-5792" /> A `600` is the wire
representation of the state described at the top of this lesson, and if your error handling collapses
everything above `400` into "it failed", you have thrown away the only signal that distinguishes
"nothing happened" from "something happened and it was not what you told the user".

## The fallback path is never atomic

The sequential fallback is the case where none of this is negotiable. When viem's
`experimental_fallback` engages, the calls go out as separate `eth_sendTransaction`
requests.<Cite src="viem-send-calls" /> Separate transactions, separate inclusion, separate
opportunities to fail, and every intervening block open to anyone else's transactions.

This means the fallback trades away precisely the property that made the batch valuable, and it does
so silently, because your call site looks identical either way. It is still the right default —
degraded is better than broken — but it makes the pairing explicit: **if you enable the fallback, you
have committed to writing UI for the half-applied state**, because you have guaranteed that path
exists for some of your users.

And if you cannot write that UI — if the flow genuinely has no coherent half-state — then the
fallback is the wrong choice for that particular flow, and `atomicRequired: true` with a clean
refusal is the right one. The specification gives that refusal two distinct error codes so you can
tell the two rejections apart: `5760` *atomicity not supported*, when the wallet cannot do it at all,
and `5750` *atomic-ready wallet rejected upgrade*, when it could have but the user declined the
account upgrade that would have enabled it.<Cite src="eip-5792" /><Cite src="eip5792-atomic-capability" />
Those are different messages to a user. One is about their wallet; the other is about a choice they
just made and can un-make.

## Atomic does not mean each call did what you wanted

One more layer, and it is the one that survives everything above.

`status: 200` means the batch was included on chain **without reverts**.<Cite src="eip-5792" /> It
does not mean every call achieved its purpose, because [a low-level call returns a
boolean](/c/call-returns-a-boolean) rather than aborting its caller. A contract that ignores that
boolean proceeds with its own state updated as though the inner call had worked — and from outside,
the transaction succeeded. Atomicity binds *reverting*. It has nothing to say about a failure that
was swallowed before it could revert anything.

So the strongest guarantee available here — `atomic: true`, `statusCode: 200` — still leaves you
needing to verify the outcome you actually cared about. Read the balance. Read the allowance. Check
the log you expected to be emitted. The receipts are evidence about execution; your invariant is a
statement about state, and only one of those is the thing you promised the user.

<Check type="spot-bug" concept="batching-is-not-atomicity">
This handler ships in an app that enabled `experimental_fallback`. Name every incorrect assumption,
and say which one produces the worst user-visible outcome.

```ts
const { id } = await walletClient.sendCalls({
  account,
  calls: [approveCall, depositCall],
})

const result = await walletClient.waitForCallsStatus({ id })

if (result.receipts?.length === 2) {
  markDepositComplete(account.address, amount)
  return { ok: true, hash: result.receipts[1].transactionHash }
}
return { ok: false, retry: true }
```

<Answer>
**Assumption 1 — that omitting `atomicRequired` means atomic.** The field is not set here. With
`atomicRequired` false, a wallet MAY execute the calls sequentially with no atomicity or contiguity
guarantee.<Cite src="eip-5792" /> The code never reads the `atomic` field the response is required to
return, so it never learns which execution it got.<Cite src="viem-get-calls-status" />

**Assumption 2 — that receipt count implies success.** In a non-atomic execution the wallet MUST
return receipts for all transactions containing batch calls that were included on chain, *including
those that eventually reverted*.<Cite src="eip-5792" /> Two receipts is therefore entirely consistent
with "the approval succeeded and the deposit reverted". The check that was needed is each receipt's
own status, which is a hex `1` or `0` in the response.<Cite src="eip-5792" />

**Assumption 3 — that the status code is not worth reading.** `waitForCallsStatus` resolves on any
non-pending code by default, its predicate being `statusCode >= 200`.<Cite src="viem-wait-for-calls-status" />
A `600`, partial revert, resolves the promise exactly like a `200` does.<Cite src="eip-5792" /> The
one code that names this lesson's failure is the one this handler discards.

**Assumption 4 — that `receipts[1]` is the deposit.** The receipts are ordered by on-chain inclusion,
not by position in your calls array.<Cite src="eip-5792" /> For an atomic execution the wallet may
legitimately return a *single* receipt covering both calls, in which case `receipts[1]` is
`undefined` and the property access throws — inside a success branch, which is the worst place for an
exception to appear.

**The worst outcome is assumption 2.** Three and Four produce a visible failure — a wrong-looking
retry, a thrown error — and someone will notice. Two calls `markDepositComplete` for a deposit that
reverted: the off-chain record now disagrees with the chain, the user is told they are done, and
nothing in the system will ever revisit it. That is the shape of every incident where the code did
not crash.

**The fix is not a bigger condition.** It is to stop inferring: read `result.atomic` to know which
execution happened, read `result.statusCode` to distinguish `200` from `600` from `500`, read each
receipt's status individually — and then verify the state you promised, because a batch that reverted
nothing can still contain a swallowed inner-call failure.<Cite src="eip-5792" />
</Answer>
</Check>

## Where this pays off

**The module's practice exercise** is this lesson made concrete: run the same failing batch through an
atomic account and through the sequential fallback, capture the chain state after each, and write the
copy for the state the sequential run leaves behind. If your interface has no message for "the
approval went through and the deposit did not", that absence is the finding.

**The EOA-upgrade module** answers the question `atomicRequired: true` raises for an ordinary user:
where does an EOA get atomic execution from? It gets it from EIP-7702, from a delegate the wallet
chooses, through a consent screen that is doing more work than it looks like it is.<Cite src="eip-7702" />

**Error surfaces**, later in this track, is where the `500` / `600` distinction joins the wider
problem of turning chain-level outcomes into sentences a person can act on. The batch codes are an
unusually well-specified case, and most of what you will meet is far less legible than this.

**Every design review from here.** The question to bring is not "does this wallet support batching".
It is: *if half of this lands, what does the user see, and what does my database believe?* Ask it
before you write the batch, because the answer sometimes changes what the calls should be.
