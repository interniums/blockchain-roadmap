Reviewing a lending market's pricing path. Collateral is a yield-bearing wrapper, and the valuation
is two lines:

```solidity
uint256 rate = IERC4626(vault).convertToAssets(1e18);
uint256 usd  = rate * underlyingUsdFeed.latestAnswer() / 1e18;
```

Nothing in that fires the [spot-price reflex](/c/orac-spot-price-is-not-an-oracle) the last three
lessons installed. There is no pool. There is no
`getReserves`. There is no market anyone can trade against. The rate comes from the asset's own
contract — the most authoritative source that exists for what a share of that vault is worth. If the
vault does not know its own exchange rate, nobody does.

Which is exactly the argument that makes this the dominant oracle attack surface of 2026, and why
protocols that carefully avoided spot prices are still losing money.

## Promoting a function to an oracle

When a protocol values something by calling a function on another contract, that function becomes a
price feed. It acquires all the properties from the first lesson — an author, an age, a cost to
falsify — regardless of whether its authors intended it to have them.

And they usually did not. `convertToAssets`, an LST's exchange rate, an LP token's virtual price:
these were written to report internal accounting. Their job is to make the vault's own arithmetic
consistent, to render a number in a user interface, and to let a depositor estimate a redemption.
Their job was never to resist an adversary who has read the function and is now choosing its inputs.

The generic question, and it is the only one that matters, is two clauses long:

> **What is this value a pure function of, and who can change those inputs inside one transaction?**

Answer it for the two-line snippet above. A typical implementation computes `totalAssets() * shares /
totalSupply()`. So the value is a function of two storage-derived quantities. `totalSupply` moves when
anyone mints or burns. `totalAssets` moves when anyone deposits or withdraws — and, in most
implementations, when anyone simply **transfers the underlying asset to the vault address**, because
`totalAssets` is a balance query.

That is a permissionless, unmetered, one-transaction write to a number your lending market treats as
a price.

## The specification anticipated this, and the anticipation is routinely misread

The ERC-4626 standard's security considerations address this directly, and the passage repays reading
in full because its structure is subtle.

It separates two families. The `preview` methods — `previewMint`, `previewRedeem` and the rest —
return values as close as possible to exact, and **for that reason they are manipulable by altering
the on-chain conditions and are not always safe to be used as price
oracles**.<Cite src="eip-4626" /> The `convert` methods are different in a specific way: the
specification **allows them to be inexact and therefore they can be implemented as robust price
oracles** — for example, it would be correct to implement the convert methods using a time-weighted
average price when converting between assets and shares.<Cite src="eip-4626" />

Read the modal verbs. `preview` methods **are** manipulable. `convert` methods **can be implemented**
robustly. One is a statement about what the functions do; the other is a permission granted to
implementers.

The specification also says, one line earlier, that `totalAssets`, `convertToShares` and
`convertToAssets` are **estimates useful for display purposes** and do not have to confer the exact
amount of underlying assets their context suggests.<Cite src="eip-4626" />

So the standard's actual position is: convert methods are the ones a vault *may* implement as a
robust oracle, and a vault that does so is conforming. It does not say that any given vault has.
Almost none do — the overwhelmingly common implementation is the direct ratio, which is exactly as
manipulable as the preview methods the standard warns about.

The other clauses are worth knowing precisely because they sound like protections and are not.
`convertToAssets` MUST NOT vary depending on the caller, and MUST NOT reflect slippage or other
on-chain conditions **when performing the actual exchange**.<Cite src="eip-4626" /> Neither says the
value cannot be moved by state changes. The first forbids per-caller answers; the second is about the
gap between a quote and an execution. A vault whose rate triples because somebody sent it tokens
violates neither.

## The same bug, from both sides

You met the [ERC-4626](/c/erc-4626-vault) inflation attack in the token-standards module: an attacker
front-runs the first depositor, [donates assets directly to the vault](/c/donation-attack), and inflates the share price so that the victim's
deposit rounds down to zero shares. OpenZeppelin's implementation defends against it with virtual
shares and virtual assets, which make the attack economically
unprofitable.<Cite src="oz-erc4626-inflation-defense" />

Note what that defence is *for*. It protects **depositors** against a distorted share price at
deposit time. It does not promise that the share price cannot be distorted; it makes the distortion
expensive relative to what an attacker gains from the rounding.

A protocol using the same rate as a collateral price is a different victim, with different
economics. The attacker is not trying to steal a depositor's rounding dust — they are trying to
inflate their own collateral's valuation on a lending market. The value at stake is the borrow cap,
which can be orders of magnitude larger than the vault. A defence sized to make one attack unprofitable
says nothing about the other.

**One rate, two consumers, two independent economic analyses.** That asymmetry is the thing to
carry: a vault can be perfectly safe for its depositors and a catastrophic oracle for a protocol that
prices against it, and neither team has done anything wrong by their own lights.

## The families, and what moves each

**ERC-4626 shares and their conversion rate.** Moved by donations to the vault address, by
unpermissioned deposits, by anything that changes `totalAssets` or `totalSupply` in one transaction.
The vault's own accounting is correct throughout.

**Liquid-staking and restaking exchange rates.** Moved by whatever mechanism updates the rate. Some
are governance-set, some are oracle-set, some are computed from a balance that a permissionless
function updates. The failure mode is not always inflation: a rate that updates in a discrete step
after a long pause is a different problem, and one that updates continuously from a manipulable
balance is the problem in this lesson.

**LP token virtual prices.** Moved by anything that changes the pool's invariant relative to its
share supply, and observable mid-update by anything that reads it during a callback. This is where
the read-only reentrancy from the security track lands: the rate function is correct, and it is being
observed at the one moment its inputs disagree.

**Anything a protocol publishes about itself.** Redemption rates, net asset values, reserve values.
Chainlink's own documentation treats this class as its own risk category: single-source feeds bottom
out in one underlying source or provider — a protocol-published NAV, reserve value, redemption rate
or exchange rate — and if that source publishes incorrect data, omits data, changes its methodology,
suffers an outage or is compromised, the feed reflects that.<Cite src="chainlink-selecting-data-feeds" />
Its instruction for such feeds is unusually direct: users **MUST** implement additional safeguards —
value bounds, caps, circuit breakers, freshness checks, fallback behaviour, monitoring against
independent references, and manual pause or kill-switch controls — and such feeds may be classified as
high or very high market pricing risk depending on the asset and the intended
use.<Cite src="chainlink-selecting-data-feeds" /> Wrapping a manipulable rate in a professional feed
does not launder it.

## The 2026 case, reported carefully

The incident that made this the industry's live concern rather than a theoretical one is the March
2026 sDOLA market on LlamaLend. Per the post-mortem published in Curve's governance forum, a flash
loan was used to force positions into soft liquidation via a large swap, and an unpermissioned
`stake()` call was then used to inflate the savings-vault exchange rate that the market consumed as a
price — hard-liquidating a set of borrowers who were not, on any honest valuation, insolvent.<Cite src="gov-curve-sdola-postmortem" />

<Aside kind="warn">
Two honesty notes about that paragraph. First, the post-mortem is a governance-forum document written
by parties with an interest in the framing, and the forum returns errors to automated retrieval, so
this account rests on the source as recorded rather than on a fresh reading of it today. Treat the
mechanism as the transferable part and the specific figures as something to check before quoting.
Second, "unpermissioned" here is the load-bearing word: the call that moved the rate was a normal
function of the savings contract, available to anyone, behaving as designed.
</Aside>

The transferable shape has three steps and none of them involve a defect:

1. A protocol function exists whose return value is a deterministic function of mutable state.
2. Some caller-reachable path changes that state.
3. A second protocol consumes the return value as a price.

Each participant is correct in isolation. The composition is the vulnerability, and neither team owns
it — which is precisely why it survives audits of both.

## Auditing a rate function used as a price

A checklist, ordered so that the cheap disqualifying answers come first.

**Read the implementation, not the interface.** An `IERC4626` type in the consumer tells you nothing.
Open the deployed source of the vault and find the body of `convertToAssets`. If it is
`totalAssets * shares / totalSupply`, you have your answer already.

**Enumerate the writers of every input.** For each storage variable the function reads, list every
external function that can change it and every access control on those functions. Include the
implicit one: if any input is a token balance of the contract, then `transfer` is a writer and there
is no access control at all.

**Ask whether it can move within a single transaction.** A rate that can only change once per block,
or once per epoch, or only by governance, is a different security object from one any caller can push
now. It may still be exploitable across blocks — the whole previous lesson applies — but the atomic
attack is closed.

**Ask whether it can be observed mid-update.** If any state-changing path in the source protocol
makes an external call between the writes that the rate function reads, the value is manipulable
without moving anything.

**Ask which direction is monotone.** Many of these rates are supposed to only increase, because they
accrue yield. That is a strong structural property and it is the basis of the cheapest effective
defence: cap the rate of increase and reject anything faster. Aave's price cap adapters do exactly
this for liquid-staking tokens, capping the price by a maximum allowed yearly growth rate against a
stored snapshot ratio and timestamp.<Cite src="aave-price-cap-adapters" /> The next lesson builds it.

**Price the attack, as you now can.** Cost to move the rate by the distortion your protocol cares
about, against the value that distortion unlocks.<Cite src="arxiv-manipulation-cost-2026" /> For a
donation-driven rate the cost may literally be the donated amount, recovered on redemption — which is
to say, near zero.

<Check type="spot-bug" concept="orac-lp-token-and-rate-oracles">
A team prices a restaking token as collateral. They tell you they deliberately avoided both spot
prices and TWAPs, and instead use the two sources that are hardest to argue with: a professional
feed for the underlying, and the token contract's own rate.

```solidity
function collateralUsd(uint256 shares) external view returns (uint256) {
    uint256 assets = IRestakingToken(lrt).convertToAssets(shares);
    (, int256 p, , uint256 t, ) = ethUsdFeed.latestRoundData();
    require(p > 0 && block.timestamp - t <= MAX_AGE, "bad feed");
    return assets * uint256(p) / 1e8;
}
```

The ETH leg is checked properly. Say what is wrong, and what would make this design defensible.

<Answer>
**The ETH leg is not the risk, and checking it thoroughly makes the code look more careful than it
is.** The two legs multiply, so the composite price inherits the weaker one. All the diligence has
been spent on the leg that has a professional feed behind it and none on the leg that does not.

**Defect one: `convertToAssets` is an unaudited price feed with no checks at all.** No bound, no
staleness notion, no plausibility test, no cross-check. Whatever the vault's implementation returns
flows straight into a solvency comparison.

**Defect two: the standard does not promise what the team thinks it promises.** ERC-4626 says the
convert methods are estimates useful for display, permitted to be inexact, and therefore *capable of
being implemented* as robust oracles — for instance using a time-weighted average.<Cite src="eip-4626" />
That is a permission to the vault's author, not a property of this vault. Somebody has to open the
deployed source and check which option was taken.

**Defect three: if `totalAssets` is a balance query, `transfer` is the setter.** No access control
exists on sending tokens to an address. The attacker's cost is the donated amount, most of which is
recoverable by redeeming their own shares afterwards at the price they created.

**Defect four: no monotonicity assumption is being enforced even though one exists.** A restaking
token's rate is supposed to grow with yield, slowly and in one direction. Nothing in this function
would notice a 40% jump in one block, which no legitimate yield mechanism produces.

**Defect five: the failure is silent and one-directional.** An inflated rate produces an over-valued
position that borrows successfully and is never liquidated. There is no revert, no event, and no
metric that moves until the bad debt appears.

**What would make it defensible.**

*Bound the rate's growth.* Store a snapshot ratio and timestamp, derive a maximum allowed ratio from a
configured yearly growth rate and the elapsed time, and return the cap when the current ratio exceeds
it — the CAPO construction.<Cite src="aave-price-cap-adapters" /> This closes the atomic attack
entirely, because no donation can produce a rate above a line that only moves with wall-clock time.

*Treat the rate as a source in the trust inventory.* Owner, monitoring rule, documented failure mode,
and an alert on any single-block movement beyond a threshold.

*Decide what happens when the cap binds.* A capped rate is a deliberate under-valuation, and the next
lesson is about what that costs when the growth is real rather than an attack.

*Read the vault.* If its `convertToAssets` is already a time-weighted implementation, some of this is
redundant — and knowing which case you are in requires reading the source, which is the whole point.
</Answer>
</Check>

## What this unlocks

**The next lesson** builds the defences named here: bounds, cross-checks with an explicit divergence
policy, and the growth cap that turns a one-transaction rate attack into a multi-block one.

**The liquidation and lending lessons** are where the damage lands. An inflated collateral rate does
not break anything visibly; it produces a position that borrows more than it should and is never
liquidated, and the loss surfaces later as bad debt with no obvious cause.

**Your own review checklist.** Add one line to it permanently: *for every external call whose return
value enters a valuation, open the callee's source and list who can move its inputs in one
transaction.* That sentence, written out for each call site, is most of this class of finding.
