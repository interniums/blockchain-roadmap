Open a block explorer on a liquidation you have seen before. A keeper calls `liquidationCall`, the
position is seized, the borrower loses a discount's worth of collateral, and the transaction succeeds.
Now walk backwards through the trace and ask a narrower question than usual: at what point did this
chain learn that the collateral was worth less than the debt?

It did not. Nowhere in that trace is there a step where the network observed a market. There is a
`STATICCALL` into an aggregator contract, which reads a storage slot, which contains an integer that
an off-chain process wrote there some minutes earlier.<Cite src="chainlink-data-feeds-api-reference" />
Every subsequent step — the health factor, the comparison against one, the seizure — is arithmetic on
that integer. The chain verified the arithmetic perfectly and had no opinion whatsoever about the
integer.

That gap is the subject of this module.

## Consensus settles ownership, not worth

You have spent six tracks on machinery that establishes, to a very high standard, *who owns what*. A
signature proves authorisation. A nonce prevents replay. The state root commits to every balance.
Finality means two conflicting histories were never both accepted. All of it is about custody and
sequence.

None of it is about value. There is no opcode that returns a price. There is no field in the block
header, no precompile, no consensus rule that references any market anywhere. A blockchain can tell
you with cryptographic certainty that an address holds 41.7 units of some token, and it has no
mechanism at all for telling you what those units are worth. The state transition function does not
have that concept.

This is not an oversight to be fixed in a future hard fork. Price is a fact about the world outside
the machine, and the machine's entire security model rests on every node computing the same answer
from the same inputs. Any rule that made a node reach out to a market would break determinism at the
root. So the chain does the only consistent thing available: it treats a price as data that somebody
wrote, exactly like any other data somebody wrote.

## Where the price enters, and how far it reaches

[Health factor](/c/lend-health-factor) is a ratio of *values*, and both sides of it are denominated in
a unit the chain cannot produce. Collateral value is a quantity multiplied by a price. Debt value is a
quantity multiplied by a price. The quantities are on-chain facts with proofs behind them. The prices
are inputs.

Follow that through a lending market and the reach is larger than it looks. The same number decides:

- whether a borrow is allowed at open time, through the loan-to-value cap;
- whether a position is seizable, through the liquidation threshold;
- how much collateral a liquidator receives, through the bonus applied to a value;
- whether a liquidation leaves the protocol whole or leaves it with bad debt;
- what the protocol reports as its own solvency.

Aave's pool documentation is explicit that price is consulted at each of these points rather than
cached once at open time.<Cite src="aave-v3-pool-docs" /> The consequence is worth stating flatly:
**an attacker who can move the price controls every one of those decisions simultaneously.** They do
not need to find a bug in the liquidation maths. The liquidation maths will work correctly on their
number.

Nor is lending special. A perpetual futures venue marks positions against a price. A stablecoin
decides redemption against a price. A vault reports share value against a price. An insurance pool
decides whether a peg broke against a price. In each case there is a single integer, written by a
process outside consensus, that the entire mechanism obeys.

<Aside kind="note">
The security track already showed you this from the attacker's side: a `getPrice()` whose every line
was correct, fed reserves from a pool the attacker could move, losing roughly $2M without a single
defect in the contract.<Cite src="uniswap-v2-oracles-docs" /> This module is the constructive half —
where prices actually come from, what each delivery model guarantees and does not, and how to compute
whether the number is expensive enough to be worth trusting.
</Aside>

## The oracle is a trust boundary, so treat it like one

In the threat-modelling module you learned to draw a boundary wherever data crosses from a party you
do not control into logic you do — a [trust-assumption inventory](/c/trust-assumption-inventory) entry. A price read is exactly that crossing, and it is the one teams most
reliably fail to draw, because calling a `view` function on another contract *feels* like computation
rather than like accepting a message from a stranger.

It is not computation. It is an input, and it has all the properties of an input:

**It has an author.** Some set of parties decided this value. Name them. For an aggregator feed it is
an off-chain oracle network reaching consensus and one transmitter landing the result; for a pool
read it is whoever traded last.

**It has an age.** The value was true at some moment, which is not this moment. Every serious feed
returns a timestamp alongside the answer precisely so the consumer can decide whether the age is
acceptable.<Cite src="chainlink-data-feeds-api-reference" /> A design that reads the answer and drops
the timestamp has thrown away the feed's own statement about itself.

**It has a cost to falsify.** This is the property that makes the whole subject tractable rather than
vibes-based. Manipulation is not a bug in the oracle; it is a purchase. Somebody pays something to
move the number, and the useful question is always whether that price is smaller than what the moved
number unlocks. The 2026 formalisation of AMM-based oracles defines that cost precisely — as the
minimal mark-to-market loss an attacker must incur to move the reported price by a given
factor — which turns "is this oracle safe" from an opinion into a
computation.<Cite src="arxiv-manipulation-cost-2026" />

That third property is the module's spine. By the end you will be able to take a pool, a window
length and a target distortion, and produce a number in dollars.

**And it has a unit.** A feed answers in its own fixed-point scale, and the scale is a property of
the feed rather than of the asset — the aggregator exposes a `decimals()` function because there is
no universal convention to assume.<Cite src="chainlink-data-feeds-api-reference" /> Multiplying a
token amount in wei by an eight-decimal USD answer and comparing the result against an
eighteen-decimal debt figure produces a number that is wrong by ten orders of magnitude and reverts
nothing. This is the least interesting failure in the module and it has cost real money, so it is
worth naming once: the units are part of the interface, and the interface is not self-describing.

## The ceiling this places on your protocol

Here is the uncomfortable corollary. If moving your price by 30% costs an attacker $4M, and a 30%
distortion lets them borrow $40M against collateral that is not worth it, then no amount of care
elsewhere in the codebase matters. Your formal verification is sound. Your invariant tests pass. Your
audit found nothing. The protocol will still lose $36M, because the specification it satisfies is a
specification about the wrong number.

**A protocol's security is bounded above by the cost of making its price wrong.** This is
[attacker economics](/c/attacker-economics) applied to the one input the protocol cannot verify. Everything else —
reentrancy guards, access control, careful rounding — is work below that ceiling. It is necessary
work, and it cannot raise the ceiling by a single dollar.

This reframes what "auditing a lending market" means. A review that reads `Pool.sol` line by line and
never opens the oracle configuration has audited the half of the system that is cheap to get right,
and skipped the half that decides the loss.

It also reframes what a *parameter change* is. Raising a collateral factor from 70% to 80% looks like
a governance tuning decision about capital efficiency. It is not only that. It shrinks the distortion
an attacker needs, which lowers the cost of the attack, which lowers the ceiling — and the amount by
which it lowers it is computable rather than a matter of taste. Listing a new collateral asset is the
same move at a larger scale: it does not modify one line of the protocol, and it can move the
protocol's true security ceiling by an order of magnitude, downward, in a single vote.

<Check type="explain" concept="orac-price-feed">
A team presents a new isolated lending market. The collateral is a mid-cap token; the debt asset is a
major stablecoin. They tell you the contracts are a fork of an implementation that has been audited
four times and has never been exploited, and that they changed only the risk parameters.

Name the questions that decide whether this market is safe, and say why reading the diff against the
audited fork does not answer them.

<Answer>
**The diff is the wrong artefact, because the fork's safety was never a property of the fork alone.**
The audited implementation was safe *given prices with some cost of manipulation*. Change the
collateral asset and you change that cost, without touching a line of the code that was audited.

**Question one: where does the price of the collateral come from?** Name the mechanism and the
parties. An aggregator feed maintained by an off-chain network, a pool read, a rate function on the
token's own contract — these have completely different failure modes and the code that consumes them
looks identical.<Cite src="chainlink-data-feeds-docs" />

**Question two: what does it cost to move that price by the amount that matters?** The amount that
matters is derived, not guessed: take the liquidation threshold, and compute the distortion at which
a borrow becomes profitably under-collateralised. Then price the mark-to-market loss of producing that
distortion.<Cite src="arxiv-manipulation-cost-2026" /> Compare against the market's borrow cap. If the
cost is smaller, the market is unsafe at any code quality.

**Question three: how old may the answer be?** The feed returns a timestamp; somebody has to choose a
maximum acceptable age and act on it.<Cite src="chainlink-data-feeds-api-reference" /> "The audited
fork handles that" is not an answer until you have read which value it compares against and confirmed
that value suits *this* asset's volatility.

**Question four: what happens when the source is unavailable?** Reverting, pausing, or falling back to
a second source are three different products with three different attack surfaces, and the choice is
usually made accidentally.

**Why the diff misleads.** Forking preserves the code and discards the context. The original market's
parameters encoded a judgement about a specific asset's liquidity and a specific feed's behaviour.
Copying the code and changing the parameters copies the judgement's *form* without any of its
content — and the security ceiling moved the moment the collateral changed.
</Answer>
</Check>

## What this unlocks

**The next two lessons** take the two ways a price actually arrives: push, where an operator writes
on its own schedule and you read a slot, and pull, where you attach a signed update to your own
transaction. They fail differently, and the difference decides which one belongs in your design.

**Then the manipulable sources.** Reading a pool you can trade against, why time-weighting converts a
free attack into a priced one, and how to compute that price from pool depth and window length.

**Then the 2026 surface.** Not spot prices any more, but protocol functions — vault conversion rates,
liquid-staking exchange rates, LP virtual prices — quietly promoted to oracles by whoever called
them.

**Then defence.** Bounds, cross-checks, rate limits, and the part almost always skipped: writing down
what happens when two sources disagree.

**Reviewing anything, starting now.** For every value a contract treats as a price, write three lines:
who authored it, how old it may be, and what it costs to make it wrong. Most oracle findings are that
list, filled in.
