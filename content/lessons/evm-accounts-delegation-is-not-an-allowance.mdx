Two confirmation dialogs, screenshotted side by side, both from wallets people trust.

The first says: *this application is requesting permission to spend your USDC.* The second says:
*this application is requesting to upgrade your account.* Both are one signature. Both are
described, in the copy underneath, as letting a contract act on your behalf. Both are revocable.

The first bounds one asset at one contract at one amount, and the bound is enforced by the token
contract, which will refuse to move more. The second bounds nothing at all, and there is no
contract anywhere that will refuse anything.

This lesson is about the distance between those two dialogs, which is roughly the distance between
a spending limit and a spare key.

## What "in your context" adds up to

You know the execution rule from two lessons ago: code reached through a delegation designator runs
with the delegating account as `address(this)`, against that account's storage, spending that
account's balance.<Cite src="eip-7702" />

Enumerate what that actually reaches, because the abstract statement understates it.

- **Every wei of ETH the account holds.** The delegate can send it anywhere.
- **Every token the account holds.** The delegate calls `transfer` as you; the token contract sees
  its rightful owner.
- **Every allowance the account has ever granted.** Approvals you made years ago to contracts you
  have forgotten are reachable, because the delegate is the approver.
- **Every NFT, every position, every governance vote, every role** keyed to your address anywhere
  on that chain.
- **The account's own storage**, which the delegate can write freely.
- **New contracts**, because a delegated account can execute a create instruction — one of the
  invariants the EIP records as broken is that an EOA's nonce may now increase after execution has
  begun.<Cite src="eip-7702" />

At the protocol level there is no scope, no expiry, no per-asset cap and no rate limit. Any
restriction that exists at all exists because the delegate's own code chose to impose it on itself.

The EIP does not hedge about this. Its security considerations state that a poorly implemented
delegate can allow a malicious actor to take near complete control over a signer's
EOA.<Cite src="eip-7702" />

## The spec tells wallets not to build the obvious feature

There is a passage in the rationale that reads unusually for a specification, and it is worth
sitting with because it settles a product question you will otherwise have to argue about.

Applications must not expect that they can suggest a user sign an authorization, and it is the
wallet's duty not to provide an interface for doing so. The reasoning given is that there is no
safe way to provide such an interface: the code named by an authorization has unrestricted access
to the account and must always be closely audited by the wallet, and few users have the
sophistication to verify the code they are delegating to.<Cite src="eip-7702" />

And then the part that answers the natural follow-up: it is **not possible** to implement a system
of permissions at this level. Applications needing custom wallet behaviour must use standardized
extension or module systems built *on top of* the delegated code, where permissions can actually be
expressed.<Cite src="eip-7702" />

So the architecture the spec is asking for is: the delegate is wallet infrastructure, audited once
and reused; anything application-specific is a module the wallet's own code admits, under rules the
wallet enforces. An application that wants users to delegate to *its* contract has misread which
layer it is operating at.

## What a broken delegate looks like

The failure does not require malice. Here is the shape, reduced to nothing:

```solidity
// Deliberately unsafe. Do not deploy.
contract NaiveBatcher {
    function execute(address target, uint256 value, bytes calldata data) external {
        (bool ok, ) = target.call{value: value}(data);
        require(ok);
    }
}
```

Read it as a normal contract and it looks harmless: a helper that forwards a call, holding no funds
of its own, guarding nothing because there is nothing to guard.

Now read it as a delegate. Every account delegated to it has a public function that executes an
arbitrary call, with arbitrary value, to an arbitrary address — callable by anyone. There is no
`msg.sender` check because as a standalone contract there was no reason for one. Nethermind's
write-up of EIP-7702 attack surfaces builds exactly this case: a delegate without access control
lets attackers execute arbitrary logic on behalf of every EOA delegated to it, including
transferring the tokens out.<Cite src="nethermind-7702-attack-surfaces" />

The EIP enumerates what a delegate must require a signature over from the account's authority, and
each item names a distinct attack:<Cite src="eip-7702" />

- **A replay nonce** — without it, a valid signature can be resubmitted and its effect repeated.
- **`value`** — without it, a malicious sponsor can attach unexpected value to the call.
- **`gas`** — without it, a malicious sponsor can starve the call so it runs out of gas and fails,
  griefing the person being sponsored.
- **`target` and `calldata`** — without them, a malicious actor can call arbitrary functions in
  arbitrary contracts.

That list is a review checklist. A delegate that signs over three of the four has a specific,
namable hole.

## The empirical picture

A December 2025 measurement study frames the class precisely: rather than deceiving a user into
signing individual transactions, an attacker induces a single authorization signature that grants
unconditional and persistent execution control over the account.<Cite src="arxiv-7702-phishing" />
The study reports identifying three reliable trigger pathways — user-driven, attacker-driven and
protocol-triggered — each capable of full account takeover, and reports that the authorizations it
measured were heavily concentrated in a small number of contract families it links to criminal
activity and repeated reuse across incidents.<Cite src="arxiv-7702-phishing" />

Treat the counts in any single study as one team's measurement rather than a settled number. The
structural claim is what transfers: the phishing target moved from "a transaction" to "a
signature", and the signature is worth strictly more than any transaction the same user could have
been tricked into sending.

## Clearing a delegation

Revocation is a fresh authorization whose `address` field is the zero address. Processing it does
not write a designator — it clears the account's code by resetting the code hash to the empty code
hash, `0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`.<Cite src="eip-7702" />

That constant is worth a moment. It is `keccak256` of the empty byte string, which is what a
never-coded account's `codeHash` has always been, and it is the value that makes a cleared account
read as identical to an account that was never delegated. It is stated in the spec and it
recomputes correctly.

Note the shape of revocation, because it is not what the word suggests:

- **It costs a transaction.** Clearing is not free and not instant.
- **It requires the key.** Nobody else can retire your delegation for you — not the delegate, not
  the wallet vendor, not a guardian.
- **There is no expiry.** A delegation persists until something replaces it. This was deliberate:
  the first draft of the EIP cleared code at the end of each transaction, and persistence was
  chosen specifically to create enough friction that users would not treat delegation as a
  scripting facility.<Cite src="eip-7702" />

The zero-address special case exists for a reason that is a nice illustration of how carefully the
gas schedule is watched. The authors initially resisted adding it, since special cases are costly.
But an account delegated to the zero address is indistinguishable from a plain EOA for most
purposes *except* that operations touching it would still pay an extra cold account read on first
touch, from attempting to load the code at address zero.<Cite src="eip-7702" /><Cite
src="eip-2929" /> The special case exists so a user can restore their account fully rather than
almost.

## Storage outlives the code that wrote it

This is the consequence people discover late, and it is the one with the sharpest edges.

Delegated code writes to *your* storage. That storage belongs to your account, not to the delegate.
Clear the delegation and the slots remain. Delegate to a different implementation and the new code
reads those slots as its own.

If the two implementations assign different meanings to the same slot, the new delegate inherits
data it did not write and will misinterpret it. Nethermind's illustration is minimal and exact: an
implementation whose slot 0 is a `bool`, followed by an implementation whose slot 0 is a `uint`.
The value written as a boolean is then read as an integer, and behaviour is undefined in the
practical sense — not the compiler's.<Cite src="nethermind-7702-attack-surfaces" />

If you have worked through [storage collisions in proxies](/c/storage-collision), this is the same
failure, arrived at by a different route. A proxy collides with its implementation because both
write to one account's storage at the same time. A delegated account collides with *itself over
time*, because successive implementations write to one account's storage in sequence.

The spec's guidance is direct. Changing an account's delegation is security-critical and should not
be done lightly, particularly when the new code was not designed and tested as an upgrade to the
old one. Contracts intended as delegates should root their storage at a slot derived from a unique
identifier — the [ERC-7201 namespaced layout](/c/erc-7201-namespaced-storage) pattern — so that
independently written implementations do not land on the same slots by accident. And where there is
any doubt, the recommendation is to first clear all account storage, an operation the protocol does
not offer natively but which a special-purpose delegate can be written to
perform.<Cite src="eip-7702" /><Cite src="erc-7201" />

<Check type="explain" concept="delegate-is-total-control">
A user is phished into signing one authorization pointing at an attacker-controlled contract. They
notice within a minute and immediately sign a clearing authorization to the zero address, which
lands in the next block.

Say what the attacker could have taken in that window, and say what remains true after the
clearing lands.

<Answer>
**In the window, everything reachable from the account.** The delegate executes as the account:
native ETH, every token balance, every NFT, and — the part people forget — every allowance the
account has ever granted to any contract. The attacker does not need the account to hold assets
directly; an old unlimited approval to a router is enough to move whatever that router can move.

The window is also not "one minute" in the way the user thinks. It is whatever block the attacker's
transaction landed in, and the attacker was watching for the delegation to appear. In practice the
draining transaction is prepared before the signature is even collected.

**After clearing, the code is gone and the storage is not.** The code hash returns to the empty
code hash, `EXTCODESIZE` reads zero again, and no further calls execute the attacker's code. But
anything the attacker's delegate wrote into the account's storage is still there, waiting to be
reinterpreted by whatever the account delegates to next.

**And the allowances are still granted.** Clearing a delegation revokes nothing at the application
layer. Every approval the attacker created while acting as the account — a fresh unlimited approval
to a contract they control is the obvious move — survives clearing, because it lives in the token
contract's storage, not the user's.

That last point is the one to carry into an incident runbook. "Revoke the delegation" is the first
step and not the whole remediation; the account has to be treated as compromised in the same way it
would be after a key leak, because for the duration of the window it was.
</Answer>
</Check>

## What a defensible delegate looks like

Pulling the guidance together, the shape the ecosystem converged on:

**Delegate to wallet infrastructure, not to applications.** The audited-once, reused-widely
implementation is the only version of this that scales, and it is what the EIP's interface
guidance implies.<Cite src="eip-7702" />

**Prefer standardized execution interfaces.** ERC-7821 defines a minimal batch executor interface
for delegations precisely so that multiple vendors' delegates can be driven the same way, and its
motivation states the operating principle plainly: EIP-7702 delegation is a risky procedure that
should be done sparingly, and should not be performed each time a user switches
websites.<Cite src="erc-7821" />

**Put permissions in a layer above.** Scoped, expiring, per-application authority is what
applications actually want, and it belongs in a module system on top of the delegate. ERC-7710 and
ERC-7715 are the drafts working that space; treat them as a direction of travel rather than as
something to build a product on today.<Cite src="erc-7710" /><Cite src="erc-7715" />

**Design for migration from the first line.** Namespaced storage is cheap to adopt before your
first user and impossible to retrofit after.<Cite src="erc-7201" />

## Where this pays off

**The outside and inside views** in the next lesson explain why a contract cannot defend itself by
checking what code a caller has: the thing it can observe is not the thing that runs.

**Proxies and upgrades** on the Solidity track are the same storage problem with a different actor
holding the upgrade key, and ERC-1967's fixed slots are the older answer to the question ERC-7201
answers generally.<Cite src="erc-1967" /><Cite src="erc-7201" />

**Account abstraction** picks up where the permission gap here leaves off: smart-account
standards, session keys and paymasters exist because "unconditional control or nothing" is not a
usable permission model for real products.
