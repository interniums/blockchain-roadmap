Run two greps across any Solidity codebase written before 2025.

```text
require(msg.sender == tx.origin
.code.length == 0
```

You will find both. They are one line each, they appear in audit checklists, they are in code that
has held real money for years, and they are usually uncommented — because for a decade what they
meant was obvious to everyone reading.

Both are now wrong. Not "deprecated", not "discouraged in modern style". Wrong, in the sense that
they return an answer that does not correspond to the question their author was asking. One of them
was already wrong before Pectra and nobody noticed, because its failure case was rare enough to
stay theoretical.

This lesson is about what each one was actually protecting, why the proxy stopped tracking the
property, and what you put in its place.

## The claim that both checks inherit

The two idioms are downstream of a single claim, which is stated in some form in nearly every
introduction to Ethereum written before 2025. Paraphrased:

> Every account is either externally owned — controlled by a private key, holding no code — or a
> contract, holding code and controlled by that code. Whether the code is empty tells you which.

That sentence organised everything: how explorers label addresses, how wallets categorise
counterparties, how tutorials introduce the state, and how a large body of deployed Solidity
reasons about its callers.

It is still there. Fetch ethereum.org's accounts page today and you get the two-kinds framing, the
four fields, and the claim that `codeHash` cannot be changed unlike the other account
fields.<Cite src="ethereum-docs-accounts" /> As of this writing that page does not mention EIP-7702
or delegation anywhere.

Since Pectra, an account may be key-controlled *and* code-bearing at once, and the same address may
be plain, delegated, re-delegated and cleared over its lifetime.<Cite src="eip-7702" /> The binary
survives as an artefact — worth learning precisely because it is baked into the code you will
review, not because it describes the state.

## `code.length == 0`, broken in two directions

Start with the direction that was always broken, because it changes how you should feel about the
second one.

OpenZeppelin shipped an `Address.isContract` helper for years, and documented its own failure modes
in the source. Its comment states that it is unsafe to assume that an address for which the
function returns false is an externally owned account and not a contract, and then enumerates the
cases: an externally owned account, a contract in construction, an address where a contract *will*
be created, and an address where a contract lived but was destroyed.<Cite
src="oz-address-iscontract" />

The same comment says the quiet part about intent: relying on it against flash loans is
unsupported, and preventing calls from contracts is highly discouraged because it breaks
composability, breaks support for smart contract wallets, and provides no security since it can be
circumvented by calling from a contract constructor.<Cite src="oz-address-iscontract" /> The helper
is gone from OpenZeppelin Contracts 5.x.

So the check has always produced **false negatives**: contracts that pass a "not a contract" gate,
by calling during construction.

EIP-7702 added **false positives**. An ordinary key-controlled user who has delegated to a wallet
implementation has 23 bytes of code.<Cite src="eip-7702" /> A gate reading `code.length == 0` now
rejects exactly the users who upgraded their wallet — which, if your gate exists to keep bots out
and let people in, is close to the opposite of the intended selection.

Put both together and the check is unsound in both directions at once. It admits some contracts and
rejects some people. There is no threshold you can tune, because the quantity it measures is not
the quantity you care about.

## `msg.sender == tx.origin`, and what it still proves

This one deserves more care than it usually gets, because the common summary — "7702 broke it" —
is imprecise in a way that leads people to fix the wrong thing.

The EIP itself works through the three purposes the idiom served, and reaches three different
verdicts:<Cite src="eip-7702" />

**Purpose one: proving `msg.sender` is an EOA.** *Not affected.* `tx.origin` must still be an
account that can originate a transaction. EIP-3607 forbids transactions from senders with deployed
code, and EIP-7702 relaxed that restriction *only* for accounts whose code is a valid delegation
designator; accounts with any other code still cannot originate.<Cite src="eip-3607" /><Cite
src="eip-7702" /> So the equality still proves the immediate caller is key-controlled.

**Purpose two: protecting against atomic sandwich attacks such as flash loans.** *Broken.* A
delegated account originates a transaction and then runs arbitrary code, so an attacker can arrange
state before and after your call within one transaction while the equality holds. The EIP adds a
detail worth carrying: relying on `tx.origin` this way is considered bad practice and could already
be circumvented by conditionally including transactions in a block.<Cite src="eip-7702" /> The
protection was porous before it was broken.

**Purpose three: preventing reentrancy.** *Broken*, and the most severely affected of the three —
though the EIP's authors report finding no examples of this usage in their (non-exhaustive)
search.<Cite src="eip-7702" />

The distribution they found on mainnet was many instances of purpose one, some of purpose two, and
none of purpose three.<Cite src="eip-7702" />

So the precise statement is this: **the check still proves key control, and has stopped proving
that no code is executing.** Those were the same claim for ten years. Code that used the equality
to mean "this address is a person's wallet" is fine. Code that used it to mean "nothing
programmable is happening in this frame" is not.

<Aside kind="note">
The EIP records three invariants it knowingly breaks, and each is a place a downstream assumption
may be hiding: an account's balance can now fall without a transaction originating from that
account; an EOA's nonce can now increase after execution has begun, because a delegated account can
execute a create instruction; and `tx.origin == msg.sender` can now be true outside the topmost
frame.<Cite src="eip-7702" /> If a system you maintain depends on any of the three, the dependency
is now a bug regardless of which idiom expressed it.
</Aside>

## Re-deriving the property behind the proxy

Both checks are proxies. The repair is never a better proxy — it is naming the property and asking
whether it was ever obtainable.

**"Nothing executes when I send ETH to this address."** This was the assumption behind push
payments, refund loops and `transfer`-based payouts. It is gone: a value transfer to a delegated
account invokes its code, with whatever gas the sending helper forwards. The property you wanted
was *the recipient cannot re-enter me or make my loop fail*, and the way to get it has not changed
since long before Pectra: pull over push. Let recipients withdraw; do not iterate over
counterparties inside a state-changing function.

**"This call cannot be composed inside one transaction with other state changes."** That is the
flash-loan property, and no on-chain check has ever provided it — a block proposer can compose
transactions even where a contract cannot. What actually addresses it is design: price from sources
an attacker cannot move within a block, cap per-block movement, or accept composability and make it
uneconomic rather than forbidden.

**"This function cannot re-enter."** Use a guard. This one has a measured answer: on forge 1.7.1
and solc 0.8.36 with the optimizer off, a transient-storage guard costs a flat ~284 gas of
overhead, while a storage guard's overhead is cold/warm dependent and ranges from about 3,100 to
about 7,100 — the low end measured directly at 3,104 on an already-warm slot.<Cite
src="measured-gas-constants" /><Cite src="eip-1153" /> The circulating "7,100 versus 200" pairing
overstates the ratio, because it silently compares a cold storage slot against transient storage.
Worth pairing with ChainSecurity's point that making guards cheap also makes *attempting*
reentrancy cheaper to probe, which shifts the economics rather than removing the
class.<Cite src="chainsecurity-tstore" />

**"The caller is a human, not a bot."** This was never on-chain. Address count is free, delegation
is cheap, and a bot with a key satisfies every test that a person with a key satisfies. If your
airdrop, fee discount or rate limit rests on this, the honest move is to price the behaviour rather
than to classify the actor: charge for the resource, cap per-address over time, or accept that the
distribution is what it is.

**"I want to exclude smart contract wallets."** Ask why. If the reason is that they cannot receive
your callback, fix the callback. If the reason is a gas limit assumption, state it. Excluding
contracts excludes real users with real funds, and now excludes delegated EOAs too — a population
that grows every time a wallet vendor ships an upgrade prompt.

## An audit pass you can actually run

Concretely, for a pre-2025 codebase:

**Find every use.** Grep for `tx.origin`, `.code.length`, `extcodesize`, `isContract`, and
`codehash`. Include tests and scripts — a test that constructs its scenario with plain EOAs is a
test that cannot fail on this.

**Classify each hit by intended purpose**, not by syntax. Authorisation, contract exclusion,
reentrancy, flash-loan protection, or something the author never articulated. The last category is
the most common and the most dangerous, because there is nothing to re-derive from.

**For contract exclusion, ask who it now excludes.** Delegated EOAs fail a `code.length == 0` gate.
If that gate sits in a claim, a mint, a fee tier or a referral, you are penalising upgraded
wallets.

**For flash-loan and reentrancy hits, replace rather than repair.** A guard for reentrancy;
economic design for atomicity. Neither replacement mentions the caller's code at all, which is the
sign that the property has finally been named.

**Write the test that would have caught it.** Foundry's delegation cheatcodes make this
short: `signAndAttachDelegation` attaches a signed delegation to the next transaction, so a test
can drive your guard from an account that is simultaneously `tx.origin` and running attacker
code.<Cite src="foundry-cheatcode-sign-delegation" /> A regression test that delegates is now part
of a complete suite for anything that reasons about callers.

<Check type="spot-bug" concept="code-length-check-broken">
A rewards contract contains this gate on its claim function:

```solidity
require(msg.sender == tx.origin, "no contracts");
require(msg.sender.code.length == 0, "no contracts");
```

The team's reasoning: the first line catches contracts calling through, the second catches
contracts calling from their own constructor, so together they are complete.

Say what each line now does, whether the combination achieves the team's goal, and what you would
replace it with if the goal is "one claim per real person".

<Answer>
**Line one now proves key control and nothing more.** It still guarantees that `msg.sender` is an
account that can originate a transaction, which after EIP-3607 and its EIP-7702 relaxation means an
account with empty code or a valid delegation designator.<Cite src="eip-3607" /><Cite src="eip-7702" /> It no longer guarantees that no code is
executing in that frame, because a delegated account is `tx.origin` while running arbitrary
delegate code.

**Line two now excludes delegated users.** Any account with a designator has 23 bytes of code and
fails. The people it turns away are ordinary users who accepted a wallet upgrade prompt; the
contract-in-constructor case it was added for is unaffected by it, because that case is exactly the
one where code length reads zero.

**The combination is worse than either line alone.** It does not block an attacker: line two only
catches an account that chose to delegate, so an attacker declines to delegate and calls from a
constructor exactly as before. Meanwhile it blocks a growing population of legitimate users. The
gate has inverted — it filters honest upgraded wallets and admits the attacker it was written for.

**The replacement, if the goal is one claim per person.** There is no on-chain answer, and that is
the finding rather than a failure to find one. Sybil resistance is not a property of the account
model — addresses are free and delegation is cheap. The available moves are all off-chain or
economic: an allowlist committed to as a Merkle root, an attestation from something that did the
identity work, a cost that makes many claims unprofitable, or accepting the distribution.

Say the honest version out loud before you write any code: the contract can enforce *one claim per
address*. Turning addresses into people was always somebody else's job, and the two idioms above
were a decade-long way of not noticing that.
</Answer>
</Check>

## Where this pays off

**The module's reflection prompt** is exactly this exercise on something you have shipped. It asks
what the "is this a human wallet" category was protecting, and what a delegated EOA does to that
protection.

**Reentrancy and [access control](/c/access-control-is-top-loss)** on the security track are the
two failure classes that inherit most directly from here. A gate built on a caller-classification
heuristic is access control with an unstated assumption inside it, which is why it fails quietly
rather than loudly.

**Account abstraction** across the app track starts from the position this lesson arrives at:
"caller is an EOA" is not a useful product category, and the standards that replaced it — batching,
sponsorship, session permissions — are all built for callers that run code.

**Reading pre-2025 code** in general. The specific skill is noticing when a one-line check encodes a
claim about the world rather than about the code, and asking when that claim was last true.
