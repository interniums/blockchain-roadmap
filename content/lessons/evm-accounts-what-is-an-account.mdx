Paste three addresses into a block explorer and watch what it does with them.

The first gets a plain balance page. The second gets a tab bar — Contract, Read, Write, Events —
and a green tick next to some verified source. The third gets the plain balance page, plus a small
badge the explorer added at some point in 2025 that most people scroll past.

The explorer is not reading a field. There is no field. It is running a heuristic over the one
record the protocol actually stores, and the badge on the third address is there because in May
2025 that heuristic stopped being able to answer the question it had been answering since
2015.<Cite src="eip-7702" />

This lesson is about what is genuinely in the record, and about which of the words you already use
for accounts describe the data and which describe a habit.

## One map, one shape of value

Ethereum's world state is a single map. The key is a 20-byte address. The value is an account
record, and every account record has exactly four fields.<Cite src="yellow-paper" />

- **`nonce`** — for a key-controlled account, how many transactions it has originated; for an
  account that creates contracts, how many it has created.<Cite src="ethereum-docs-accounts" />
- **`balance`** — an unsigned integer count of wei.<Cite src="ethereum-docs-accounts" />
- **`storageRoot`** — the root of a separate trie holding that account's own storage.
- **`codeHash`** — the hash of the account's code, with the code itself held outside the record and
  fetched by hash.<Cite src="ethereum-docs-accounts" />

You have already built the machinery underneath this. The map is
[a committed key-value store](/c/key-value-state), the two roots are
[hashes](/c/hash-function) standing in for whole structures, and the address is the *key* rather
than a field of the record — nothing in the account says what its own address is.

Now notice the three things that are not in the list, because each one is a place where an
assumption tends to live.

**There is no type tag.** Nothing in the record says "this is a wallet" or "this is a contract".
Every claim of that kind, everywhere — in explorers, in wallets, in your own code — is inferred
from the four fields, and the inference is somebody's choice of rule.

**There is no owner, no admin, no creator.** An account does not know who deployed it or who can
act for it. If a contract has an owner, that owner is a number in its storage, put there by its own
code and protected by its own rules.

**There is no creation timestamp and no existence flag.** An address you have never heard of has
the same reading as an address whose four fields all happen to be zero. EIP-161 makes this
explicit in the other direction: an account whose nonce is zero, balance is zero and code is empty
is *empty*, and a touched empty account is deleted from the trie rather than persisted.<Cite
src="eip-161" /> Sending nothing to a fresh address leaves nothing behind.

## What "externally owned" actually names

An externally owned account is one whose authority to act comes from a secp256k1 private key: the
key whose public key hashes to that address. That is the whole definition, and it has a sharp
operational consequence.

**Only a key-controlled account can originate a transaction.** A transaction carries a signature,
and the sender is not a field you set — it is [recovered from the signature](/c/ecrecover). There
is no way to produce a transaction that claims to come from an address you cannot sign for, because
"comes from" *is* "recovers to".

That is why the top of every call stack on Ethereum is an EOA. Not by policy — by the arithmetic of
signature recovery.

## What "contract account" actually names

A contract account is one that came into existence through a CREATE-family instruction. Its address
is computed rather than derived from a key — from the creator and its nonce in the case of `CREATE`,
or from the creator, a salt and the initcode hash in the case of `CREATE2`, which is what makes a
`CREATE2` address knowable before deployment.<Cite src="eip-1014" /> No private key exists for
either, so nobody can sign for it, so it cannot originate anything. It acts only because something
called it.

Its record has the same four fields as any other. "Contract" is not a type in the state. It is a
description of two facts — how this account came to hold code, and that no key can produce a
signature recovering to its address.

## The definition that broke

Here is the version most engineers carry, and it is worth writing out because the failure is
precise rather than vague.

> An EOA is an account with no code. A contract is an account with code. `codeHash` tells you which.

Every clause of that held for a decade. Since EIP-7702 shipped with Pectra in May 2025, an account
controlled entirely by a private key may hold 23 bytes of code — a *delegation designator*, the
byte sequence `0xef0100` followed by an address — and still originate transactions, still be signed
for by its key, still be in every meaningful sense the wallet it was the day before.<Cite
src="eip-7702" />

Two properties that used to move together have come apart. Sort accounts by both at once and there
are now three populations, not two:

- **Plain EOA** — key-controlled, no code.
- **Delegated EOA** — key-controlled, *and* code-bearing. This one is new.
- **Contract account** — code-bearing, no key.

## The canonical documentation has not caught up

This is not a hypothetical staleness problem. Fetch ethereum.org's own accounts page today. It
gives the four fields correctly, and it says of `codeHash` that it cannot be changed, unlike the
other account fields.<Cite src="ethereum-docs-accounts" /> As of this writing the page does not
mention EIP-7702 or delegation anywhere.

That sentence was a reasonable approximation before Pectra — code was written once at creation, and
the only way to change a code hash afterwards was `SELFDESTRUCT`, which since Cancun only has an
effect in the same transaction that created the account.<Cite src="eip-6780" /> It is now plainly
false: a delegation designator is written into the code field of a live account by an ordinary
transaction, and can be rewritten or cleared later.

The point is not that the docs are bad. The point is that "the reference says so" is not a date
stamp, and the specific claim that broke is the one your code is most likely to depend on.

<Aside kind="note">
There is one restriction that did survive, and it is worth carrying from here on: EIP-3607 forbids
transactions from senders with deployed code, and EIP-7702 relaxed it *only* for accounts whose
code is a valid delegation designator.<Cite src="eip-3607" /><Cite src="eip-7702" /> An account with
ordinary contract code still cannot originate a transaction. So "the sender of a transaction is
key-controlled" remains true. It is "the sender is not running code" that stopped being true.
</Aside>

## Reading a record without guessing

Given an address and nothing else, here is what the four fields support and what they do not.

**`balance`** — how much ETH the protocol says this account holds. Note that this is the only asset
the protocol itself knows about; every token balance you have ever displayed is a number in some
contract's storage.

**`nonce`** — a counter whose meaning depends on what has been acting. It counts originated
transactions for a key-controlled account and created contracts for a creating one, and since
Pectra a signed authorization also consumes it, so transactions are no longer the only thing that
moves it.<Cite src="eip-7702" />

**`storageRoot`** — non-empty means something has written storage under this address. That includes
a key-controlled account whose delegate wrote to it, which is a case worth remembering when you
next assume storage implies "contract".

**`codeHash`** — the hash of the code that the *outside* sees. Empty-string hash means no code.
Anything else means there are bytes, and reading those bytes is the only way to learn whether they
are a contract's runtime code or a 23-byte pointer at somebody else's.

<Check type="explain" concept="account">
You query an address and get: nonce 41, balance 0.3 ETH, a non-empty `storageRoot`, and a
`codeHash` that is not the hash of the empty string. Name everything you can conclude, and name the
two questions this does not answer.

<Answer>
**What you can conclude.** The account has code of some kind, and something has written to its
storage. The nonce of 41 means 41 nonce-consuming actions have occurred — transactions originated,
contracts created, authorizations processed, or a mixture.

**What you cannot conclude: whether a private key controls it.** Both a contract account and a
delegated EOA present as "has code, has storage, has a nonce". The `codeHash` alone does not
separate them; you have to fetch the code and look at whether it is 23 bytes beginning `0xef0100`.

**What you cannot conclude: whether the nonce counts transactions.** A contract's nonce counts
contracts it created. A delegated EOA's nonce counts transactions *and* the authorizations it has
signed. Reading 41 as "this person sent 41 transactions" is an inference, not a reading.

The general shape is worth keeping: the record is four numbers, and every sentence you say about an
account that is not one of those four numbers is a rule you chose. The rest of this module is about
which of those rules stopped holding.
</Answer>
</Check>

## Where this pays off

**The designator itself** is the next lesson: the exact 23 bytes, the transaction type that writes
them, and what the EVM does when a call lands on an account holding them.

**Every "is this a contract" check** in the last lesson of this module is the payoff for taking the
type-tag point seriously. If there is no type in the state, then every check is a proxy for a
property somebody chose not to write down — and once you can name the property, you can ask whether
the proxy still tracks it.

**Storage and code as separate structures** carries straight into proxies and upgrades. The reason
an upgradeable proxy can swap behaviour without moving state is the same reason a delegated account
can: `storageRoot` and `codeHash` are independent fields, and the EVM will happily run one
account's code against another account's storage.
