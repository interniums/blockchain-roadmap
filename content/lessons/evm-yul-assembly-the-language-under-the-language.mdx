Take a contract with no `assembly` block anywhere in it. A token, a vault, something ordinary. Ask
the compiler for its intermediate representation rather than its bytecode, and read what comes out.

Near the top of the object is this:

```yul
mstore(64, memoryguard(0x80))
```

<Cite src="ottersec-memory-safety" /> Then a `switch` on the function selector, then your functions,
rendered as generated Yul functions built out of `let`, `if`, `for` and a single value type. You did
not write any of it. It is not bytecode either — it is a program in a language, with a grammar, that
the compiler then optimises and lowers.<Cite src="solidity-yul" />

That language is Yul, and it is the same language your inline `assembly` blocks are written in. The
useful reframing of this module starts here: dropping into assembly does not move you to a different
layer of the machine. It moves you into the layer the compiler was already using, minus the part of
the compiler that knew what your code meant.

## What Yul actually is

Yul is an intermediate language designed to be compiled to bytecode for different backends, used
both in stand-alone mode and as "inline assembly" inside Solidity.<Cite src="solidity-yul" /> Two of
its design decisions explain most of what it feels like to write.

**It has one type, because the EVM has one type.** Yul is statically typed, but a dialect supplies
the types, and the only specified dialect — the EVM dialect — defines exactly one: `u256`, the
native 256-bit word.<Cite src="solidity-yul" /> That is why nothing in an assembly block carries a
type annotation, and why [the 256-bit word](/c/word-is-256-bits) stops being a machine detail and
becomes the only thing you can say.

**It hides the stack on purpose.** There are no statements for `SWAP`, `DUP`, `JUMPDEST`, `JUMP` or
`JUMPI`. The documentation is explicit about why: the first two obfuscate the data flow and the last
two obfuscate control flow, so Yul supplies `if`, `switch`, `for` and user-defined functions
instead, and states as a goal that the programmer or auditor should not have to worry about the
stack.<Cite src="solidity-yul" /> Functional-style nesting — `mul(add(x, y), 7)` — is preferred over
`7 y x add mul` for the same reason.<Cite src="solidity-yul" />

So an inline `assembly` block is not a hole in the compiler through which you emit bytes. Inside it
the compiler still resolves identifiers, still allocates stack slots for your `let` bindings, still
counts stack height for variable access, still removes those slots when the block ends, and still
runs the Yul optimizer over what you wrote.<Cite src="solidity-inline-assembly" /> What it stops
doing is checking anything about meaning. That distinction is the whole module.

<Misconception
  belief="Inline assembly is raw bytecode."
  reality="It is Yul. Stack management, name resolution, jump generation and optimisation all still happen. Only the semantic guarantees are gone."
  why="The word 'assembly' implies one instruction per line and one line per instruction. Yul deliberately breaks that correspondence — it has loops, named functions and structured branches, and the docs list hiding the stack as a design goal rather than an accident."
  src="solidity-yul"
/>

The practical consequence of that misconception is a wrong risk model. Engineers who believe they
are writing bytecode assume the output is what they typed, and therefore that reviewing the source
is reviewing the artefact. It is not. The optimizer transforms your block along with everything
else, and — as the next lessons develop — how it transforms the code *around* your block depends on
claims you make about your block.

## Two pipelines, and which one you are on

The compiler can reach bytecode two ways.

**Legacy codegen.** Parse, analyse, emit EVM assembly directly from the Solidity AST, run the
`evmasm` optimizer, emit bytecode.<Cite src="solidity-via-ir-closer-look" />

**Via-IR.** Parse, generate Yul IR from the Solidity AST, run the Yul optimizer repeatedly, transform
Yul to EVM assembly, then run the same `evmasm` optimizer, then emit
bytecode.<Cite src="solidity-via-ir-closer-look" /> Four optimisation-relevant stages instead of
two, and — importantly for lesson four — each stage happens in isolation and retains no information
about the previous one.<Cite src="ottersec-memory-safety" />

Which one runs is not a detail you can leave to folklore, because it changes both gas and behaviour.
In standard-JSON the setting is `viaIR`, and the compiler's own documentation of it reads: "This is
false by default."<Cite src="solidity-using-the-compiler" /> On the command line it is `--via-ir`;
in a Foundry project it is `via_ir` in the profile.<Cite src="foundry-solc-config" />

<Misconception
  belief="via-IR is the default now."
  reality="It is opt-in. The standard-JSON reference for solc 0.8.36 still documents viaIR as false by default, and legacy codegen is what you get from an unconfigured compile."
  why="The team announced the intention to make it default at Solidity Summit 2023, and the July 2024 explainer says the original plan was June 2024 — so 'it's the default now' has been plausible-sounding for three years. The plan was then tied to the EOF upgrade, which was rejected for Fusaka."
  src="solidity-using-the-compiler"
/>

That last point is worth stating plainly, because it is the reason the timeline slipped and stayed
slipped. The 2024 explainer gives two reasons for tying the via-IR default to EOF: EOF's unlimited
swaps and dups would make the Yul-to-EVM transformation simpler and remove additional stack-too-deep
cases, and since both changes carry minor semantic differences, shipping them together would reduce
the upgrade burden.<Cite src="solidity-via-ir-closer-look" /> EOF was rejected for inclusion in
Fusaka, and the experimental EOF backend was removed from the compiler in 0.8.36 as
obsolete.<Cite src="solidity-0836-release" /> The plan that anchored the default did not survive its
anchor.

### What replaced it, and what that does not mean

The current work is a third path. A from-scratch SSA-based Yul code generator shipped as an
experimental opt-in in 0.8.35, exposed as `--via-ssa-cfg` on the command line and `viaSSACFG` in
standard JSON.<Cite src="argot-roadmap-2026" /> In 0.8.36 it gained stack-to-memory spilling, which
the release announcement describes as effectively solving stack-too-deep **on that
backend**.<Cite src="solidity-0836-release" /> The maintainers' stated focus for the rest of 2026 is
stabilising that pipeline and moving it out of `--experimental`.<Cite src="argot-roadmap-2026" />

<Aside kind="warn">
Read the qualifiers before you carry this forward as "stack-too-deep is fixed". `viaSSACFG` implies
`viaIR` and is itself documented as false by default.<Cite src="solidity-using-the-compiler" /> It
sits behind the `--experimental` flag, and the compiler's documentation of that mode says
experimental features are often not adequately tested, are not yet intended for production use, and
carry no backwards-compatibility guarantees — they may change in breaking ways in non-breaking
releases.<Cite src="solidity-using-the-compiler" /> For a project on the default pipeline,
[stack-too-deep](/c/stack-too-deep) is still exactly what it was: the compiler failing to reach a
live value within [the 16-slot DUP/SWAP window](/c/stack-reach-16), worked around with block scopes,
structs and fewer live locals.
</Aside>

## via-IR is not a gas switch

The most expensive misreading of the pipeline is that it is an optimiser and therefore
semantics-preserving. The compiler maintains a dedicated page listing observable differences,
which is the strongest available evidence that it is not.<Cite src="solidity-ir-breaking-changes" />
Four of them are worth carrying:

- **State variable initialisation order under inheritance changed.** Legacy initialises every state
  variable in the hierarchy from most-base to most-derived and only then runs constructors; via-IR
  interleaves, initialising and constructing each contract in turn. The documented example returns
  0 under one pipeline and 42 under the other.<Cite src="solidity-ir-breaking-changes" />
- **`delete` on a storage struct now zeroes the whole slot**, including padding that legacy left
  untouched — which matters precisely when an upgrade has parked data in that padding.<Cite src="solidity-ir-breaking-changes" />
- **Modifiers are implemented as real functions.** If a modifier evaluates its placeholder more than
  once, parameters and return variables are re-initialised per evaluation instead of persisting in a
  fixed stack slot. The documented example returns 1 under legacy and 0 under
  via-IR.<Cite src="solidity-ir-breaking-changes" />
- **Evaluation order differs in kind, not just in outcome.** For legacy codegen the evaluation order
  of expressions is unspecified; for via-IR the compiler tries source order, left to right, but does
  not guarantee it.<Cite src="solidity-ir-breaking-changes" /> Neither is a promise you may build on.

<Misconception
  belief="via-IR only changes gas, so switching is a benchmark decision."
  reality="It changes observable behaviour in documented ways. Switching a production project means re-running the full test suite and re-reading the IR-based codegen changes page, not just re-running the gas report."
  why="Everything else labelled 'optimizer' in a build system is semantics-preserving by contract, so the word carries that guarantee across even when the change is a different code generator rather than an optimisation pass."
  src="solidity-ir-breaking-changes"
/>

## verbatim: the floor below assembly

There is one construct below Yul, and it is worth knowing mostly so you can recognise it in a diff.

The `verbatim` family lets you embed a literal byte sequence, including opcodes the compiler does
not know. The functions are named `verbatim_<n>i_<m>o("<data>", ...)`, where `n` is the number of
input stack slots, `m` the number of outputs, and `data` a string literal holding the
bytes.<Cite src="solidity-yul" /> Doubling a value without letting the optimizer touch the constant
looks like this:

```yul
let x := calldataload(0)
let double := verbatim_1i_1o(hex"600202", x)
```

What matters is not the syntax but what it costs you.

**The compiler stops reasoning.** The optimizer treats verbatim bytecode as an opaque block: it
always assumes the block modifies all aspects of state, so it can do very few optimisations across
it. It will not split the block, though it may move, duplicate or merge it with identical
blocks.<Cite src="solidity-yul" />

**The rules are unchecked.** The documentation gives a non-exhaustive list of restrictions that the
compiler does not verify — control flow must not jump into or out of the block, reverting or
returning from it is not allowed, stack contents other than the declared inputs and outputs must not
be touched, and the stack height difference must be exactly outputs minus inputs. Violations are
undefined behaviour.<Cite src="solidity-yul" /> Even with the optimizer off, the code generator
still has to determine a stack layout, so using verbatim to change the stack height is undefined
regardless of settings.<Cite src="solidity-yul" />

**It is outside the ecosystem's compatibility promises.** The docs carry an explicit warning that in
discussions about whether EVM changes might break existing contracts, features used inside
`verbatim` cannot receive the same consideration as those the compiler itself
emits.<Cite src="solidity-yul" />

<Misconception
  belief="verbatim is just a faster or lower-level way to write assembly."
  reality="It removes the compiler's ability to reason about the block, and with it every downstream tool's. The optimizer treats it as opaque state-modifying code, and the compatibility promises that cover compiler-emitted opcodes do not extend to it."
  why="It appears in the same list as every other Yul built-in and reads like one more instruction, so it looks like a peer of mstore rather than an exit from the language."
  src="solidity-yul"
/>

Treat its appearance in a pull request as the review trigger, not the implementation detail.

<Check type="explain" concept="via-ir-pipeline">
A colleague opens a pull request that adds `via_ir = true` to the Foundry profile. The description
reads: "Enables the optimizer's IR pipeline. Gas report attached: every function is cheaper or
unchanged. No behaviour change, so no new tests needed."

Name the two claims in that description that are wrong, and say what evidence would have to be in
the pull request before you approve it.

<Answer>
**Claim one: "no behaviour change".** The compiler publishes a page of observable differences between
the pipelines precisely because there are some.<Cite src="solidity-ir-breaking-changes" /> Four
concrete ones are in this lesson: inheritance initialisation order, `delete` clearing struct
padding, modifiers with a repeated placeholder, and expression evaluation order moving from
unspecified to attempted-but-unguaranteed source order. Whether any of them touch *this* codebase is
an empirical question the pull request has not asked.

**Claim two: the framing of via-IR as "the optimizer's IR pipeline".** It is a different code
generator, not an optimisation setting. The Yul optimizer is a stage inside it and only runs when
optimisation is also enabled.<Cite src="solidity-via-ir-closer-look" />

**Evidence that would make this approvable:** the full test suite green under the new setting rather
than a gas report; a read of the IR-based codegen changes page against this codebase's actual use of
inheritance, `delete` on storage structs, and modifiers with repeated placeholders; and a compile
time measurement, since longer compilation is the documented cost of the extra Yul optimisation
stages.<Cite src="solidity-via-ir-closer-look" />

**A trap worth naming:** if the gas report shows a *large* improvement in a contract containing
inline assembly, that is not necessarily via-IR being clever. It may be that the block is annotated
in a way that lets the optimizer do things it previously could not — which is lesson four, and which
is only safe if the annotation is true.
</Answer>
</Check>

## Where this pays off

**Everything Solidity was doing for you** is the next lesson, and it now has a sharper statement:
the compiler inside an assembly block is still doing the mechanical work — names, slots, jumps,
optimisation — and has stopped doing the semantic work. Knowing exactly which half went away is the
difference between writing assembly and gambling with it.

**The memory-safe annotation** is a claim addressed to the Yul optimizer specifically, which is a
stage that only exists on one of the two pipelines. The pipeline fork you just learned is why the
same assembly block can be harmless under legacy codegen and wrong under via-IR.

**Gas profiling and optimizer settings** on the toolchain track inherit the same rule this lesson
established for behaviour: a gas number belongs to a pipeline and an optimizer configuration, not to
a piece of source. A benchmark that does not name both is not reproducible.

And when the SSA CFG backend does leave `--experimental`, the thing to re-check is not whether
stack-too-deep is gone. It is which pipeline your project actually compiles with, and whether the
semantic differences page grew.
