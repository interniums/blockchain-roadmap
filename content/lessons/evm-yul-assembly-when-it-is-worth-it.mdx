Two pull requests arrive in the same week.

The first replaces a Solidity loop in a rewards calculation with fourteen lines of annotated
assembly. The gas report shows 380 gas saved on a function that runs perhaps two hundred times a day.
The author is the only person on the team who can read it.

The second adds a proxy fallback: `calldatacopy`, `delegatecall`, `returndatacopy`, `return` or
`revert`. It cannot be written in Solidity at all, because there is no type for "whatever bytes
arrived" returning "whatever bytes came back".

Both are "assembly PRs" in a standup. They are not the same decision, and the thing that separates
them is not difficulty or line count. This lesson is about which question actually separates them,
and about the cost that shows up on neither gas report.

## Four categories, and why each one qualifies

The defensible cases share a property: the reason for the assembly is that the language cannot
express the operation, not that it expresses it slowly.

### Fixed storage slots the layout cannot reach

ERC-1967 standardises three storage slots for proxies, each derived as
`bytes32(uint256(keccak256(<label>)) - 1)`: the implementation at
`0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc`, the admin at
`0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103`, and the beacon at
`0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50`.<Cite src="erc-1967" /> The
point of the derivation is that no compiler will ever allocate a variable there, so the proxy's own
bookkeeping cannot collide with the implementation's state.<Cite src="erc-1967" />

ERC-7201 generalises the idea for namespaced storage.<Cite src="erc-7201" /> Its formula is now
available to you as a compile-time built-in: `erc7201(string memory id)` returns the base slot, defined as
`keccak256(keccak256(id) - 1) & ~0xff`, and it accepts arbitrary
strings.<Cite src="solidity-global-variables" />

**The compiler has narrowed this category, and it is worth knowing by exactly how much.** A contract
can now declare where its storage starts, with a `layout at <base-slot-expression>` specifier whose
expression may use the `erc7201` built-in; the slots assigned to static storage variables shift
accordingly.<Cite src="solidity-custom-storage-layout" /> The specifier is placed on the most derived
contract and shifts the whole inheritance tree.<Cite src="solidity-layout-storage" /> For a single
upgradeable contract that wants one namespace, that is the assembly-free answer.

The limits are equally specific, and they are what leaves the category alive. The specifier may
appear at most once and only on the topmost contract of an inheritance tree; it cannot be used on
abstract contracts, interfaces or libraries; and it does not affect transient state
variables.<Cite src="solidity-custom-storage-layout" /> So a contract composing several independent
namespaces — the case ERC-7201 was written for — still needs a storage pointer whose `.slot` is
assigned, which is assembly. So does a proxy that must reach three unrelated fixed slots rather than
one contiguous region. And so does the library that wraps the pattern for everyone else.

<Aside kind="note">
This is the shape of the whole module's argument in miniature. The justified categories are not a
fixed list handed down in 2019; they shrink as the compiler grows. A team that adopted an
assembly-based namespaced-storage helper before the specifier existed and has not revisited it is
carrying review cost for a capability the language now has.
</Aside>

### Forwarding calls that have no type

A proxy fallback receives arbitrary calldata for an unknown function and must return arbitrary return
data, unchanged, including reverting with the callee's exact revert bytes. Solidity has no type for
that. [`delegatecall` as the proxy primitive](/c/delegatecall-is-the-proxy-primitive) is reachable
from the language, but the copy-in and copy-out are not, and the "terminating block" case from the
previous lesson is precisely what makes taking over memory legitimate
here.<Cite src="solidity-inline-assembly" />

This is the cleanest possible justification: the assembly is not an optimisation of a Solidity
version, because there is no Solidity version.

### Hot paths in libraries many projects depend on

The economics change when the code is written once and read by auditors many times over. A signature
library, a fixed-point maths library, a Merkle proof verifier vendored into a hundred protocols
amortises its review cost across all of them, and the reviewers are specialists who chose that work.
Solady exists as the reference corpus for this — production-grade, heavily reviewed assembly to read
as an example of what annotation discipline looks like when it is done
seriously.<Cite src="solady" />

The trap is inferring the wrong lesson from it. That a library written by assembly specialists,
audited repeatedly, is written in assembly is not evidence that your application contract should be.
It is evidence that the amortisation worked for them.

### Operations the language cannot express

Everything else in this category is small and specific: reading `codesize`, `msize`, or `gas()`
semantics directly; constructing initcode; addressing return data as bytes. If the answer to "how
would I write this in Solidity" is "I could not", the category is satisfied by construction.

## What is not on the list

Ordinary application logic. Loops, accumulators, comparisons, struct manipulation — anything with a
plain Solidity spelling.

The folk knowledge here is genuinely out of date. The via-IR pipeline was built to enable
optimisation passes spanning functions and complex control flows; the Yul optimizer operates across
arbitrary control flow rather than only within basic blocks, retains knowledge about memory and
storage across complex flows in certain cases, and provides more opportunities for inlining. The
compiler team's own summary is that it generates better gas-optimised code than the default
pipeline.<Cite src="solidity-via-ir-closer-look" /> Meanwhile `mcopy` has removed one of the classic
reasons to hand-write a memory loop.<Cite src="eip-5656" />

Two caveats keep this honest. The Yul optimizer only runs when optimisation is actually enabled
alongside via-IR, and via-IR is opt-in.<Cite src="solidity-via-ir-closer-look" /><Cite src="solidity-using-the-compiler" />
And "generated code is often competitive" is a claim about a distribution, not about your function.

Which is the actual rule: **measure, on your contract, on your pipeline, and publish the number in
the pull request.** A benchmark that does not name the compiler version, the optimizer settings and
the pipeline is not a benchmark, and this is the same discipline the toolchain track applies to
[gas folklore](/c/gas-folklore) generally.<Cite src="foundry-gas-optimization-guide" />

## The price that is not on the gas report

Suppose the 380 gas is real. It is still the smaller of the two prices.

**Readers.** After the merge, a subset of the team can no longer review that function. Not "finds it
harder" — cannot, in the sense that they cannot answer the three memory-range questions from the
previous lesson, and their approval carries no information. That subset grows over time as people
leave.

**Tools.** [Static analysis](/c/static-analysis) and [formal verification](/c/formal-verification)
understand Solidity better than Yul and Yul better than opaque bytes. `verbatim` is the extreme case:
the optimizer treats it as an opaque block that modifies all aspects of state, and every downstream
consumer inherits that blindness.<Cite src="solidity-yul" /> Each step down the ladder removes a
class of automated finding you were previously getting for free.

**Compiler dependence.** A Solidity function's correctness is the compiler's problem. An assembly
block's correctness is partly yours and partly the optimizer's, and — as the memory-safety analysis
puts it — memory safety is a promise between IR generation and optimisation, with each stage
retaining no information about the previous one.<Cite src="ottersec-memory-safety" /> You have taken
on a dependency that upgrades without asking.

Now set that against where losses actually come from. Systematic mapping of real-world smart-contract
attacks to root causes puts access-control failure far ahead of reentrancy by value
lost.<Cite src="sok-root-cause-losses" /> Counts that also take in operational compromise rank stolen
keys and phishing above it, so the ordering at the very top depends on what a study admits — but the
gap over reentrancy survives either framing.<Cite src="arxiv-audit-gap-2026" /> The concrete bugs are
mundane: a missing modifier, an unprotected initialiser, an over-privileged key.
[Access control dwarfs the bug classes curricula lead with](/c/access-control-is-top-loss), and
assembly addresses none of it.

<Aside kind="warn">
Be careful with annual totals here, including ones you will see quoted confidently. Different
trackers scope incidents differently — smart-contract-only, DeFi-protocol-only, all-crypto including
exchange compromises — and their published figures for the same year do not reconcile. The *ranking*
by root cause is the robust finding and the one worth acting on.<Cite src="sok-root-cause-losses" />
A single headline dollar figure is not.
</Aside>

## A rule that survives contact with a codebase

Three tests. A block that fails any one of them should be Solidity.

**A named category.** Which of the four, stated in the pull request. Not "for gas" — that is the
thing being tested, not a category. If the category is "hot path in a widely reused library", the
next question is whether this repository is that library.

**A measured benefit.** Numbers from a run, with compiler version, optimizer settings and pipeline
recorded, and the Solidity baseline compiled the same way. If the category is "the language cannot
express this", the measured benefit is waived and the justification is the impossibility instead.

**A named reviewer.** A person who has answered the memory-range questions and says so in the review.
If nobody can, the block does not merge — the correct outcome is deletion, not a comment saying
`// TODO: review this assembly`.

To that, three habits that make the rule enforceable rather than aspirational:

- **Comment each block with the memory range it touches**, so a re-review is a check rather than a
  rediscovery.<Cite src="solidity-inline-assembly" />
- **Compile CI the same way production compiles**, and if the project supports both pipelines, put
  both in the matrix — a false annotation can be inert under one and fatal under the
  other.<Cite src="solidity-using-the-compiler" />
- **Re-examine old blocks when the compiler moves.** The `layout at` specifier and the `erc7201`
  built-in each retired a reason that used to be
  good.<Cite src="solidity-custom-storage-layout" /><Cite src="solidity-global-variables" />

<Check type="explain" concept="assembly-cost-is-review-cost">
You inherit a codebase with four inline assembly blocks. Classify each, and say what you would do.

1. A `fallback()` that copies calldata, `delegatecall`s an address read from an ERC-1967 slot, and
   returns or reverts with the return data.
2. A `_sum(uint256[] memory)` helper that loops in assembly to skip bounds checks, unannotated,
   saving a measured 24 gas per element on the current pipeline.
3. A storage-pointer helper that assigns `.slot` from a constant derived with `keccak256`, used by
   three separate namespaces in one upgradeable contract.
4. A block using `verbatim_1i_1o` with a hex literal, with a comment reading "faster than shl".

<Answer>
**1 — keep, and check one thing.** Category: forwarding calls that have no type. This is the case
where Solidity has no expression for the operation, and the block terminates on every path, which is
what makes taking over memory legitimate.<Cite src="solidity-inline-assembly" /> The thing to check
is the one the previous lessons set up: does it verify the implementation address has code? A
`delegatecall` to an empty address succeeds having executed nothing, so a proxy without that check
accepts every call and silently does nothing.

**2 — remove it, and do not agonise.** No category applies; "skip bounds checks" is ordinary
application logic. The measured 24 gas per element is real and is the smaller price. It is also
unannotated, so if it touches memory — and reading through a `uint256[] memory` parameter does — the
whole compilation unit has lost stack-to-memory movement and related memory
optimisations.<Cite src="solidity-inline-assembly" /> That means the block may be costing gas
elsewhere by more than it saves here, which nobody measured because the measurement was scoped to the
function. Rewrite in Solidity, re-measure the *unit*, and expect a surprise.

**3 — keep, and record why.** Category: fixed storage slots. Three independent namespaces in one
contract is exactly the case the `layout at` specifier does not cover, since it may appear at most
once and only on the most derived contract.<Cite src="solidity-custom-storage-layout" /> Add a
comment naming the ERC-7201 derivation and the reason the specifier is not sufficient here, so the
next reviewer does not re-derive the argument — and so that if the constraint is ever lifted, the
block is findable.

**4 — delete, or escalate.** "Faster than shl" is not a category, and the cost is severe:
the optimizer treats verbatim as opaque, assumes it modifies all state, and can therefore optimise
very little across it, while the restrictions on its content are documented as unchecked and their
violation as undefined behaviour.<Cite src="solidity-yul" /> A comment claiming a micro-optimisation
cannot justify that. If the real reason turns out to be an opcode the compiler does not know, that is
a genuine category-four case — but then the comment is wrong and needs to say so.

**The pattern across all four.** Three of the four decisions were made by asking which category
applies, before anyone opened a gas report. That ordering is the rule. Gas is the tie-breaker inside
a category, never the argument for entering one.
</Answer>
</Check>

## Where this pays off

**Upgradeable proxies** on the Solidity track are the single largest legitimate consumer of the
techniques in this module, and the storage-slot standards are why. You now have the tools to read
`ERC1967Utils` and say which of the four ranges each block touches and why the annotation holds.

**Security review** inherits the classification directly: an assembly block is a finding location by
default, and the three-test rule is a review checklist rather than a style opinion.

**Gas profiling** on the toolchain track supplies the measurement half. This lesson only claims that
a number is required; that track is where you learn to produce one that survives someone else running
it.

**Formal verification and static analysis** on the security track will keep meeting the ceiling
described here. Knowing which of your contract's regions the tools can see is what makes their
silence interpretable — and a tool that says nothing about a `verbatim` block is not reassurance.

The reflection prompt for this module asks you to write your team's rule and then apply it to real
assembly you have seen. Do it in that order. A rule written after looking at the code is a
description of the code.
