Your indexer hashes a string with `sha3-256`. Your contract hashes the same string with `keccak256`.
The digests do not match, and no amount of re-checking the input will make them.

Nothing is broken. You are calling two different functions that share a lineage and, for a while,
shared a name.

## Where the split happened

Keccak won NIST's SHA-3 competition, and NIST then spent time turning the winning submission into a
published standard.<Cite src="nist-fips-202" /> FIPS 202 says outright that the result is not the
submission: the SHA-3 hash functions append a two-bit suffix to the message before the sponge's own
padding rule runs.<Cite src="nist-fips-202" />

The standard writes it as `SHA3-256(M) = KECCAK[512](M || 01, 256)`. Read that line
carefully, because three separate things are named in it and only one of them is the difference.

**Subgoal — identify the engine.** `KECCAK[c]` is the sponge: a fixed 1600-bit permutation, run over
a state split into a *rate* portion that absorbs message bytes and a *capacity* portion `c` that the
message never touches directly.<Cite src="nist-fips-202" /> For SHA3-256 the capacity is 512 bits,
which leaves 1088 bits — 136 bytes — of rate. FIPS 202 publishes that 136 as SHA3-256's HMAC block
size, and it is the number of message bytes consumed per permutation
call.<Cite src="nist-fips-202" /> Ethereum's `keccak256` uses the same permutation and the same
512-bit capacity.

**Subgoal — identify the output.** The trailing `256` is the digest length in bits. Also identical.

**Subgoal — identify what actually differs.** `M || 01`. Two bits, appended to the message before
anything else happens. That is the entire divergence, and its stated job is domain separation — it
keeps inputs arriving from the SHA-3 hash functions distinct from inputs arriving from the SHAKE
extendable-output functions, and from any variant defined later.<Cite src="nist-fips-202" />

Ethereum had already shipped with the pre-standardisation function, which appends nothing, and never
migrated. Ethereum's hash is `keccak256`, written `KEC` in the Yellow Paper.<Cite src="yellow-paper" />

<Aside kind="note">
The suffix is a small registry, not a one-off. FIPS 202 defines
`SHAKE128(M, d) = KECCAK[256](M || 1111, d)` and `SHAKE256(M, d) = KECCAK[512](M || 1111, d)`, and
an inner pair `RawSHAKE128`/`RawSHAKE256` that append `11` instead, reserved so that a future tree
hashing mode can extend the scheme without colliding with anything already
defined.<Cite src="nist-fips-202" />

`SHAKE256(M, 256)` therefore shares the permutation, the 512-bit capacity **and** the output length
with `SHA3-256`. Only the suffix differs — `1111` against `01` — and on the empty string the two
disagree completely: `46b9dd2b…` against `a7ffc6f8…`, computed with Python's `hashlib` on
26 August 2026. That is what a domain separator is for, demonstrated on the two functions the
separator was invented to keep apart.
</Aside>

## What the divergence looks like in bytes

For byte-aligned messages, FIPS 202 gives the padding SHA-3 appends. When exactly one byte of
padding fits, the appended byte is `0x86`; when two fit, `0x0680`; when more fit, `0x06`, then zero
bytes, then a final `0x80`.<Cite src="nist-fips-202" /> The same table gives the XOF row: `0x9F`,
`0x1F80`, and `0x1F … 0x80`.<Cite src="nist-fips-202" />

The Keccak side is usually quoted as `0x01` and `0x81`: the same `pad10*1` rule with no suffix in
front of it. FIPS 202 does not state those bytes, because it describes only its own functions, so
treat that pair as reported by secondary write-ups rather than read out of the
standard.<Cite src="sha3-vs-keccak" />

Two bits of difference in one padding byte produce no relationship at all between the outputs.
Computed here with `cast` 1.7.1 and Python's `hashlib` on 26 August 2026:

```text
input: "" (the empty string)
keccak256   c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470
SHA3-256    a7ffc6f8bf1ed76651c14756a061d662f580ff4de43b49fa82d80a4b80f8434a

input: "abc"
keccak256   4e03657aea45a94fc7d47ba826c8d667c0d1e6e33a64a036ec44f58fa12d6c45
SHA3-256    3a985da74fe225b2045c172d6bd390bd855f086e3e9d525b46bfe24511431532
```

No shared prefix, no partial agreement. This is the expected behaviour of a hash function under a
one-bit input change, and it is exactly why the bug is hard to spot by eye: a wrong digest looks the
same as a right one.

## What does *not* differ, and why that matters

It is worth being precise that Ethereum is not running a weaker function. The guarantees from the
previous lesson are unchanged by the missing suffix, because they come from the sponge's capacity and
its output length, neither of which the suffix touches. FIPS 202 scores SHA3-256 at 128 bits of
collision resistance, 256 bits of preimage resistance and 256 bits of second-preimage
resistance.<Cite src="nist-fips-202" />

One entry in that table repays a second look. SHA-256 is listed at `256 − L(M)` bits of
second-preimage resistance — its strength decays with the length of the message under attack — while
every SHA-3 hash function is listed at a flat number with no message-length term at
all.<Cite src="nist-fips-202" /> That is a property of the sponge rather than of the standardisation,
so Ethereum inherits it. The suffix is a naming decision. The security is structural, and the fork
did not touch it.

## The naming trap, and how deep it goes

The practical consequence is a naming problem rather than a cryptographic one, and it is worth
seeing how many layers of the stack the wrong name reached.

**The opcode.** The EVM instruction at `0x20` was originally called `SHA3`. EIP-1803 proposed
renaming it to `KECCAK256` "for clarity", alongside `GAS` → `GASLEFT` and `NUMBER` →
`BLOCKNUMBER`.<Cite src="eip-1803" /> The EIP is stagnant and changes no behaviour — but its
existence is the record that the mnemonic was wrong, at the bottom of the stack, for years.

**The language.** Solidity shipped a `sha3` builtin that computed Keccak. It was renamed, then
removed: the v0.5.0 breaking-changes list states plainly that `sha3` is disallowed in favour of
`keccak256`.<Cite src="solidity-050-breaking" /> Any snippet older than that release uses the
misleading name.

**The libraries.** Go's `golang.org/x/crypto/sha3` exposes both, and its documentation for the
Ethereum-compatible one is a warning rather than a description: `NewLegacyKeccak256` says to use it
only if you require compatibility with an existing cryptosystem that uses non-standard
padding.<Cite src="go-x-crypto-sha3" /> Of the two functions used in the vectors above, Python's
`hashlib.sha3_256` is the FIPS function and Foundry's `cast keccak` is Ethereum's.

So the check when an off-chain digest refuses to match an on-chain one is not "is my input right".
It is: *which of the two functions is the thing I imported actually computing?*

<Aside kind="warn">
Ethereum does ship a second hash function, but it is not SHA-3 either: the precompile at address
`0x02` is SHA2-256, priced with a base cost plus a per-word cost.<Cite src="execution-specs-osaka-gas" />
So the EVM has SHA-256 and Keccak-256 available and no SHA3-256 at all. If a spec you are
implementing calls for SHA3-256 — some non-Ethereum protocols do — there is no opcode for it, and
you are writing it in Solidity.
</Aside>

<Check type="predict" concept="keccak-vs-sha3">
A team ships a claims contract. Off-chain, their Node service builds a commitment with a library
imported as `sha3`; on-chain, Solidity's `keccak256` recomputes it and compares. Everything passes in
their unit tests, which compute both sides in Node. It fails on the first real claim.

What do you check first, why did the tests pass, and what test would have caught it?

<Answer>
Check which function the `sha3` import actually is. If it is the FIPS function, every commitment the
service produced is a SHA3-256 digest and the contract's `keccak256` will never reproduce it.

The tests passed because both sides of the comparison were computed with the *same* wrong function.
A test that hashes in Node and asserts against a value also hashed in Node cannot detect this class
of bug — it is self-consistent by construction, which is precisely what makes it useless here.

Two tests can catch it. Pin a **known vector**: assert that the library returns
`c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470` for the empty string, which is
Keccak's answer and not SHA-3's. Or pin a digest **computed by the chain** — call the contract's own
hashing path in a fork test and compare. Either way the rule is the same one that ends the previous
lesson: when two systems must agree on a hash, at least one side of the assertion has to come from
outside the code under test.
</Answer>
</Check>

## Where this pays off

Almost every identifier in Ethereum is a `keccak256` output, which means every one of them is
unreachable if you have the wrong function. Function selectors are the first four bytes of
`keccak256` of a canonical signature.<Cite src="solidity-abi-spec" /> The storage slot of a mapping
entry, the address produced by `CREATE2`, every node of the Merkle Patricia Trie, event topics, and
the ENS namehash are all the same primitive. There is no layer below this where an approximately
right hash function still works: a digest either matches the chain's or it is noise.

The habit to carry forward is smaller than the fact, and it generalises past hashing. When two
systems must agree on a value, the agreement is over a *named, versioned* function applied to an
*exact byte string* — never over "the hash of the data". You will meet the same requirement three
more times in this module, each time with a sharper failure attached: EIP-712's domain separator
pins which contract and chain a signature was meant for, EIP-191's `0x19` prefix pins whether a blob
is a message or a transaction, and the Merkle-tree lesson at the end of the module pins whether 64
bytes are a leaf or an internal node. Same idea as NIST's two bits, escalating consequences.
