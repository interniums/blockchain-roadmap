A wallet shows you 32 bytes of hex and a button that says Sign. You already know from the previous
lessons that those 32 bytes are the entire meaning of what you are about to authorise. So the
product question is unavoidable: **how does a wallet show a human what a digest means, when a digest
means nothing by itself?**

EIP-712 is the answer, and it is worth being clear about what kind of answer it is. It adds no new
cryptography. The signature underneath is still ECDSA over secp256k1. What it changes is the *rule
for building the digest*, so that the rule can be run backwards into a display.

## First, the prefix byte

Before structure comes safety. EIP-191 fixes a format for anything that is signed but is not a
transaction: `0x19`, then a one-byte version, then version-specific data, then the data to
sign.<Cite src="eip-191" />

The leading `0x19` is chosen for a specific reason. In RLP, a single byte in the range `0x00` to
`0x7f` encodes as itself, so a byte string starting with `0x19` cannot be one well-formed RLP
structure — at best it is a one-byte RLP payload followed by something else, which means EIP-191
signed data can never also be a valid Ethereum transaction.<Cite src="eip-191" /> Without that, a
multisig accepting presigned blobs would accept a raw transaction as a blob, or the reverse.

The version byte is a small registry: `0x00` for data with an intended validator, `0x01` for
structured data as defined by EIP-712, and `0x45` for the familiar `personal_sign`
messages.<Cite src="eip-191" />

<Aside kind="note">
Two details in that registry are more than trivia.

`0x45` is the ASCII code for `E`. The prefix that predates the standard is
`"\x19Ethereum Signed Message:\n" + len(message)`, and EIP-191 retrofits it by declaring that the
`E` *is* the version byte, leaving `thereum Signed Message:\n` + length as the version-specific
data.<Cite src="eip-191" /> The standard was reverse-engineered onto a convention already in the
wild, which is why it looks odd.

Version `0x00` is the minimal fix for the problem EIP-712 later solves properly: its version-specific
data is a single **intended validator address**, and in a multisig that address is the multisig
itself.<Cite src="eip-191" /> One field, hashed into the digest, and a signature stops being valid
anywhere else.
</Aside>

<Aside kind="note">
EIP-191's motivating example is worth reading as a product story, not a crypto one. Users A, B and C
run a 2-of-3 wallet X. Users A, B and D run a 2-of-3 wallet Y. A and B presign an action for X. The
attacker replays that same presigned payload against Y, which also has A and B as signers, and it is
accepted.<Cite src="eip-191" /> Nothing was forged. The signatures never said which wallet they were
for.
</Aside>

## The EIP-712 digest, built in three subgoals

**Subgoal 1 — pin the schema, so field names are part of the hash.** The struct's type is written
out canonically as `name ‖ "(" ‖ member₁ ‖ "," ‖ … ‖ memberₙ ")"`, each member being `type ‖ " " ‖ name`
— for the spec's example, `Mail(address from,address to,string contents)`. If the struct references
other struct types, those are collected, **sorted by name**, and appended, giving strings like
`Transaction(Person from,Person to,Asset tx)Asset(address token,uint256 amount)Person(address wallet,string name)`.
`typeHash` is the `keccak256` of that whole string, and the spec notes it is a constant per type
that never needs computing at runtime.<Cite src="eip-712" />

**Subgoal 2 — hash the instance against that schema.**
`hashStruct(s) = keccak256(typeHash ‖ encodeData(s))`, where every member becomes exactly 32
bytes.<Cite src="eip-712" /> The per-type rules are specific and worth knowing, because they are
where implementations diverge: booleans become `uint256` 0 or 1; addresses become `uint160`; `bytes`
and `string` are replaced by the `keccak256` of their contents; arrays become the `keccak256` of the
concatenated `encodeData` of their members; nested structs recurse into their own
`hashStruct`.<Cite src="eip-712" /> Cyclical data is undefined.<Cite src="eip-712" />

**Subgoal 3 — bind the whole thing to one place.** The final digest is
`keccak256(0x19 ‖ 0x01 ‖ domainSeparator ‖ hashStruct(message))`.<Cite src="eip-712" />

Because the type string is inside the digest, the wallet can be handed the schema, the domain and
the values, recompute the digest itself, and render field names and values to the user knowing that
what it displays is what will be signed. That is the whole trick.<Cite src="cyfrin-signature-standards" />

<Aside kind="note">
An obvious question: why not just `abi.encode` the struct and hash that? The EIP considered it and
rejected it. Its rationale states that the ABIv2 standard by itself **fails the determinism security
criteria**, because there are several valid ABIv2 encodings of the same
data.<Cite src="eip-712" /><Cite src="solidity-abi-spec" /> Tight packing was rejected too, and for
a reason you have already met — `abi.encodePacked` drops lengths, so two dynamic arguments can be
re-cut into the same bytes.<Cite src="nethermind-encodepacked-collisions" />

There is a third rejected alternative that shows what the design is protecting. Merging `typeHash`
into the domain separator instead of into `hashStruct` would be cheaper, and the EIP declines it
because then the hash function is no longer **injective** over structured
values.<Cite src="eip-712" /> Injectivity — distinct meanings never share a digest — is the property
this whole standard exists to buy. It is the same property the Merkle lesson at the end of this
module loses, and with the same consequence.
</Aside>

## The domain separator is the load-bearing part

`domainSeparator = hashStruct(eip712Domain)`, where `EIP712Domain` carries whichever of these fields
make sense for your protocol.<Cite src="eip-712" /> Each is doing a specific job:

- **`name`** and **`version`** — the human-readable protocol name, and its major version. The spec is
  explicit that signatures from different versions are not compatible, which is the point: bumping
  the version invalidates every outstanding signature at once.<Cite src="eip-712" />
- **`chainId`** — the EIP-155 chain id, and the spec says the user-agent *should refuse to sign* if
  it does not match the currently active chain.<Cite src="eip-712" /><Cite src="eip-155" />
- **`verifyingContract`** — the address of the contract that will verify the
  signature.<Cite src="eip-712" />
- **`salt`** — described by the spec as "a domain separator of last resort", for disambiguating cases
  the other four fields cannot.<Cite src="eip-712" />

Fields are optional and the ones you omit are left out of the struct type entirely, so the type
string itself differs between protocols. The spec fixes their order, and requires that any future
field be added alphabetically after the existing five.<Cite src="eip-712" />

Mix that hash into every digest and cross-domain replay stops being something you defend against and
becomes something that cannot typecheck. The same struct, signed for contract A on chain 1, produces
a different digest than for contract B or on chain 2 — so it recovers to a different address there,
and the check fails.

Two consequences follow directly, and both have bitten real deployments:

- **A separator computed once at deploy time is wrong after a chain fork.** The fork changes
  `chainId`; a cached separator does not. OpenZeppelin's `EIP712.sol` handles this by caching the
  separator as an immutable *together with the chain id it was built for*, and rebuilding it whenever
  `block.chainid` no longer matches — its own comment says the design exists to protect against
  replay on an eventual fork of the chain.<Cite src="oz-eip712-source" />
- **Omitting `verifyingContract` makes a signature valid at every deployment of the same code.**
  Fine for a singleton. Not fine for a factory that deploys one vault per customer.

<Aside kind="warn">
Read this line from the abstract before you rely on any of it: EIP-712 "does not include replay
protection".<Cite src="eip-712" /> Its Security Considerations say the same thing at length — the
standard is only about signing and verifying, and making the application behave correctly when it
sees the same signed message twice is out of scope and application-specific.<Cite src="eip-712" />

There is a second warning beside it that is easy to miss. Because anyone holding a signature can
submit it, the EIP tells implementers to be secure against **frontrunning**: an attacker intercepts
the signature and submits it before the intended use, and the application must either reject that or
produce exactly the effect the signer intended.<Cite src="eip-712" /> A domain separator does not
help — the attacker is submitting it in the right domain.
</Aside>

## Worked example: the `permit` digest

ERC-2612 is the smallest complete instance of everything above, and it is worth assembling once by
hand.

**Subgoal — declare the schema.** The type string is
`Permit(address owner,address spender,uint256 value,uint256 nonce,uint256 deadline)`, and its
`keccak256` is the `typeHash`.<Cite src="eip-2612" />

**Subgoal — bind the domain.** ERC-2612's suggested domain is the four-field one:
`EIP712Domain(string name,string version,uint256 chainId,address verifyingContract)`, hashed with the
token's name, its version, `chainid`, and `address(this)`.<Cite src="eip-2612" /> The token address
is in there, so a permit for USDC does not verify at DAI.

**Subgoal — bind the instance and assemble.** The digest is
`keccak256(0x19 ‖ 0x01 ‖ DOMAIN_SEPARATOR ‖ keccak256(abi.encode(typeHash, owner, spender, value, nonce, deadline)))`.<Cite src="eip-2612" />

Now read what each field of the struct is *for*, because between them they close the gaps the
previous two lessons opened:

- `nonce` is the replay key, derived from contract state rather than from the signature bytes, and
  the spec requires it to equal `nonces[owner]` before the update and to increment
  afterwards.<Cite src="eip-2612" />
- `deadline` bounds the window. ERC-2612's rationale is blunt about why: a relayer holding a permit
  has "a free option to submit or withhold" it, and the deadline is how the owner prices that
  option.<Cite src="eip-2612" /> That is the same free-option problem the commitment lesson meets
  later in this module.
- `owner` is in the struct, and the spec notes that nowhere in the definition does `msg.sender`
  appear — the caller of `permit` can be any address.<Cite src="eip-2612" />

Five fields, and four of them exist because a signature by itself proves less than it looks like it
proves.

<Aside kind="note">
One piece is still missing: how does a wallet learn what your domain *is*? EIP-712 never specified
it, and ERC-5267 says that omission likely limited adoption of the whole scheme — including of
`permit`, which applications had to build custom support for one token at a
time.<Cite src="eip-5267" /> ERC-5267 fixes it with a single view function, `eip712Domain()`,
returning a `fields` bitmap plus name, version, chain id, verifying contract, salt and
extensions.<Cite src="eip-5267" /> OpenZeppelin's `EIP712.sol` implements that
interface.<Cite src="oz-eip712-source" />

The pattern generalises: a hashing convention is only half a standard. The other half is publishing
enough for a third party to reconstruct the hash without reading your source.
</Aside>

<Check type="explain" concept="domain-separator">
A vault factory deploys one vault contract per customer, all from identical bytecode. Each vault
verifies withdrawal authorisations with EIP-712, using a domain of
`name: "Vault", version: "1", chainId: block.chainid` — and a per-signer nonce, correctly
incremented.

An auditor flags it. What is the finding, and why does the nonce not save it?

<Answer>
`verifyingContract` is missing from the domain, so every vault deployed by the factory computes the
same domain separator, and therefore the same digest for the same withdrawal struct. A signature
authorising a withdrawal from vault A verifies identically at vault B.

The nonce does not help because nonces are per-contract state. Vault B has its own mapping, and the
signer's nonce there is still zero — the signature is, from B's point of view, entirely fresh. The
nonce answers "has this been used *here*?"; nothing in the digest ever answered "was this meant for
here?".

Adding `verifyingContract: address(this)` fixes it, and it fixes it structurally: no check has to
run, because the digests simply differ.<Cite src="eip-712" />

Two follow-ups worth carrying. The domain type string changes when you add the field, so every
outstanding signature is invalidated by the fix — which is the correct outcome, not a migration
problem. And if the vaults are clones deployed behind proxies, a domain separator cached in the
implementation's constructor would be the implementation's address, not the clone's; the caching
strategy has to key on `address(this)` as well as on the chain id.<Cite src="oz-eip712-source" />
</Answer>
</Check>

## Where this pays off

ERC-2612 `permit`,<Cite src="eip-2612" /> Permit2, order signing on every intent-based exchange, and
cross-chain message authorisation are all this construction with a different struct in the middle.
Smart accounts extend it one step further: an ERC-1271 contract signer decides for itself what a
valid signature is, and the payload it is handed is usually an EIP-712
digest.<Cite src="eip-1271" /><Cite src="eip-712" />

When you later read a bridge's message format and find a chain id and a contract address hashed into
it that nobody seems to check at runtime, you will recognise the shape: they are not being checked,
they are being made impossible to get wrong. That is the highest form of the pattern this module
keeps returning to — the check you never have to write is the one the encoding already made
unrepresentable.
