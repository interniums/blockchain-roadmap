You need to stop an approval being used twice. The obvious move, and one that reads as airtight, is
to remember the signature you already honoured:

```solidity
bytes32 key = keccak256(sig);
require(!used[key], "replayed");
used[key] = true;
```

This does not work. The same approval, by the same signer, over the same digest, has a second valid
byte string — and the attacker can compute it from the first without knowing any secret.

## The symmetry

Recall the signing operation from the previous lesson: `r` is the `x` coordinate of the point `k·G`
reduced modulo the curve order `n`, and `s = k⁻¹(e + r·d) mod n`.<Cite src="sec1-ecc" />

Now negate the ephemeral point. `−(k·G)` is `(−k)·G`, and negation on this curve mirrors a point
across the horizontal axis: the `y` coordinate flips sign, the `x` coordinate does not. So `r` is
untouched. Substituting `−k` into the second equation flips the sign of the whole expression,
turning `s` into `−s mod n`, which is `n − s`.

The result is a second pair `(r, n − s)` that verifies over the same digest under the same key. What
changes is which of the two mirrored candidate points recovery must pick — so the recovery
identifier flips with it, 27 to 28 or back. EIP-2's own rationale spells the transformation out in
exactly those terms: flip `s` to `secp256k1n - s`, flip `v`, and the resulting signature is still
valid.<Cite src="eip-2" />

This is not a quirk of Ethereum's usage. SEC 1's signing operation says it in a single sentence
immediately after outputting the signature: the signer may replace `(r, s)` with `(r, −s mod n)`,
"because this is an equivalent signature".<Cite src="sec1-ecc" /> The specification treats the two
forms as the same object. Only your code treats them as two.

Both forms are genuine signatures by the same key over the same digest. Neither is forged. They have
different bytes, so they have different `keccak256` digests, so the replay guard above sees two
different approvals.

## This is older than Ethereum

Bitcoin met the same property first and catalogued it more thoroughly, which makes its documents the
better map. BIP-62 lists **nine** distinct sources of transaction malleability. Inherent ECDSA
malleability — "taking the negative of the number S inside (modulo the curve order) does not
invalidate it" — is source number five; the others are encoding-level, such as non-DER signature
serialisation and redundant script push operations.<Cite src="bip-62" />

The sentence in BIP-62 worth carrying away is not about ECDSA at all. It says the first six sources
and part of the seventh can be fixed by extra consensus rules, and the last two
**cannot**.<Cite src="bip-62" /> The two that cannot: a script that ignores one of its inputs, and
the fact that whoever holds the key can always produce a fresh signature over the same
spend.<Cite src="bip-62" /> Malleability is not a bug with a patch. It is a property of "the same
authorisation can be written down more than one way", and the best a protocol can do is narrow the
set, never empty it.

Bitcoin narrowed it in BIP-146, whose LOW_S rule requires `s` to lie in the lower half of the curve
order — and which prints the attack in the same breath, noting that a high `S` "could be trivially
replaced by `S' = curve_order − S`".<Cite src="bip-146" />

<Aside kind="note">
Malleability is also a case study in blaming the right thing. When Mt. Gox collapsed in February
2014 it publicly attributed the loss to malleability attacks draining its accounts. Decker and
Wattenhofer then measured the Bitcoin network across the year preceding the filing and concluded
that while the problem is real, there was **no widespread use** of malleability attacks before the
closure.<Cite src="mtgox-malleability-arxiv" />

Both halves are worth holding. The primitive is genuine and the exchange's accounting really could
be confused by it. The headline explanation was still not supported by the data. When you read an
incident report that names a cryptographic property as the cause, the useful follow-up question is
whether anyone measured.
</Aside>

## What EIP-2 fixed, and what it did not

EIP-2 is a Homestead-era bundle of four unrelated changes — contract-creation gas, the low-`s` rule,
out-of-gas behaviour for code deposit, and a difficulty-adjustment
formula.<Cite src="eip-2" /> The one that concerns us made a transaction invalid at the protocol
level if its `s` value is greater than half the curve order. In the very same sentence, it says the
ECDSA recover precompile is deliberately left unchanged and will keep accepting high `s`
values.<Cite src="eip-2" />

That is not an aside. It is the whole shape of the problem, and the executable spec still shows both
halves side by side today. Transaction validation rejects `s` above
`SECP256K1N // 2`.<Cite src="execution-specs-osaka-transactions" /> The `ecrecover` precompile checks
only that `s` lies in `0 < s < n` — the full range, both halves.<Cite src="execution-specs-ecrecover" />

So the rule protects transactions and nothing else. Any signature you hand to a contract and recover
with `ecrecover` is accepted in either form.

<Aside kind="note">
Why fix it that way? EIP-2's stated motivation is narrow, and notably *not* theft. The EIP says the
malleability is "not a serious security flaw, especially since Ethereum uses addresses and not
transaction hashes as the input to an ether value transfer" — the damage is that an attacker can
cause the transaction confirmed in a block to have a different hash from the one the user sent,
breaking user interfaces that track transactions by hash.<Cite src="eip-2" />

Choosing low-`s` rather than, say, dropping `v` was debated at the
time.<Cite src="eip-2-malleability-thread" /> The design worth noticing is that the fix was applied
at the layer that had the problem and deliberately withheld from the precompile, because a contract
may legitimately need to recover from signatures made outside Ethereum's rules — the EIP's own
example is a contract recovering old Bitcoin signatures.<Cite src="eip-2" /> A protocol-level
canonicalisation would have foreclosed that, permanently, for every future contract.
</Aside>

## A third byte string for the same approval

Even with low-`s` enforced, "the signature" still has more than one encoding. ERC-2098 defines a
**compact** 64-byte representation: keep `r` as one word, and pack the parity bit into the top bit
of `s` as a combined `yParityAndS` word.<Cite src="eip-2098" /> The saving is real — 65 bytes
word-align to 96, while 64 stay 64.<Cite src="eip-2098" />

Notice what makes it possible. The top bit of `s` is free *precisely because* the low-`s` constraint
already forbids the upper half of the range, which ERC-2098 attributes to the Homestead
change.<Cite src="eip-2098" /><Cite src="eip-2" /> One canonicalisation created room for a second
encoding.

And note the parity convention: ERC-2098 records that `yParity` is 0 or 1, while the values used
historically are 27 and 28 because those did not collide with binary prefixes used in
Bitcoin.<Cite src="eip-2098" /> So the same approval can reach your contract as 65 bytes with
`v ∈ {27, 28}`, 65 bytes with `v ∈ {0, 1}` from a library that normalises differently, or 64 bytes
compact — before anyone has done anything adversarial at all.

Any of those hashes to a different `keccak256`. The replay key was never keyed on the approval.

<Check type="predict" concept="signature-malleability">
A payments contract accepts an off-chain authorisation and guards it with
`require(!used[keccak256(sig)])`, exactly as above. An attacker holds one valid signature authorising
a 10 ETH withdrawal, already submitted and honoured.

Walk through what they do, and say what stops working if the contract instead rejects high-`s` values
but keeps the same replay key.

<Answer>
They take the honoured signature, compute `s' = n - s`, flip `v` between 27 and 28, and resubmit.
`ecrecover` returns the same signer, the digest is the same, and `keccak256` of the new 65 bytes is
a value the `used` mapping has never seen. The withdrawal executes a second time.

Rejecting high-`s` does close *this* door: only one of the two forms survives the check, so the pair
collapses to one canonical byte string. But the replay key is still wrong in principle, and the
previous section is the proof — a compact 64-byte ERC-2098 signature carries the same `r` and the
same low `s` and hashes to something else entirely.<Cite src="eip-2098" /> So does the same signature
with `v` written as 0 rather than 27. Freshness was tied to a representation, and representations
multiply.

The correct key is derived from the *message*: a per-signer nonce, or the EIP-712 digest itself,
which is a value both parties computed independently from the thing being
authorised.<Cite src="eip-712" /> OpenZeppelin's ECDSA source states the rule directly — do not use
signatures as unique identifiers; use hash invalidation or nonces.<Cite src="oz-ecdsa-source" />
</Answer>
</Check>

## What to do instead

Two independent habits, and you want both:

- **Derive replay state from the message, never from the signature.** A per-signer nonce, or a
  `mapping(bytes32 => bool)` keyed on the digest you actually verified. This is the load-bearing one,
  because it is the only one that survives a change of signature format — including a change to a
  scheme that is not ECDSA at all.
- **Normalise before you accept.** Reject `s` in the upper half of the curve order, and reject `v`
  outside 27 and 28. OpenZeppelin's ECDSA library does exactly this — it rejects malleable
  signatures by requiring low-`s` and a `v` of 27 or 28 — and hand-rolled verification usually does
  not.<Cite src="oz-ecdsa-source" /> The threshold is a constant of the curve, not of your protocol:
  half of the published order `n`.<Cite src="sec2-curve-params" />

Order matters between the two. Normalisation makes the byte string canonical; only the nonce makes
the *approval* single-use. A contract with normalisation and no nonce still honours the same
authorisation twice if the signer's counterparty submits it twice.

## How common is this, really

Not a museum exhibit. A 2025 empirical study of signature replay vulnerabilities read 1,419 audit
reports from 37 blockchain security companies, found 108 containing detailed descriptions of the
bug, and classified five distinct variants of it.<Cite src="arxiv-signature-replay" /> Running their
detector over 15,383 contracts that perform signature verification, drawn from an initial set of
918,964 across four chains, they report that **19.63% of Ethereum contracts using signatures contain
a signature-replay vulnerability**, with affected contracts holding $4.76 million in active
assets.<Cite src="arxiv-signature-replay" />

Roughly one in five. This is not an exotic finding class; it is close to the base rate for contracts
that touch signatures at all.

## Where this pays off

The next lesson adds the missing half of replay protection: a nonce answers "has this approval been
used?" but says nothing about "was this approval meant for *this* contract, on *this* chain?" That
is a scoping problem, and its answer is the EIP-712 domain separator.<Cite src="eip-712" /> Note that
the two failures compose — a contract with a nonce and no domain, or a domain and no nonce, is
vulnerable in a different direction each way.

Malleability also comes back in a place you would not expect. The passkey lesson later in this
module verifies signatures on a different curve, where there is no EIP-2 to have partly cleaned up
after you and no protocol-level canonicalisation of the kind Bitcoin eventually
adopted.<Cite src="bip-146" /> Everything above applies there in full, with nothing switched on by
default.

The habit generalises past Ethereum. Any time you use a credential's serialisation as its identity —
a JWT string, a signed URL, a webhook signature header — you are making the assumption this lesson
breaks. Identity belongs to the claim, not to its encoding.
