Here is a claim worth taking seriously: given a normal Merkle airdrop, an attacker can produce a
proof that your verifier accepts, for an entry that was never in the tree. No collision is found. No
hash is broken. `keccak256` behaves exactly as specified throughout.

The bug is in the encoding contract between the prover and the verifier, and it is worth working
through slowly, because the shape of it recurs everywhere hashed data has more than one meaning.

## The mechanism

Take a tree where leaf 1 and leaf 2 hash into an internal node. Write the leaf hashes as `h(ℓ₁)` and
`h(ℓ₂)`, and the internal node's pre-image as their concatenation, `a = h(ℓ₁) ‖ h(ℓ₂)`. The node
itself is `h(a)`. A legitimate proof for `ℓ₂` supplies `h(ℓ₁)` and then the siblings above:
`[h(ℓ₁), h(b), h(f)]`.<Cite src="rareskills-merkle-second-preimage" />

Now the attack. The attacker submits `a` itself as their leaf data, and supplies the *shortened*
proof `[h(b), h(f)]`. The verifier hashes the leaf data, obtaining `h(a)` — which is precisely the
internal node — folds in `h(b)` and `h(f)`, and arrives at the
root.<Cite src="rareskills-merkle-second-preimage" />

It verifies. The attacker has proven membership of a value that is not a leaf, and they did it by
starting the fold one level up.

**Subgoal — notice what the attacker had to know.** Only the tree's published contents. Airdrops
publish them by definition, so this is not a secret.

**Subgoal — notice what the attacker did not have to do.** No search, no collision, no grinding. Two
concatenations and one hash, all of it deterministic.

**Subgoal — notice what the verifier could have checked and did not.** Nothing in the proof said how
long the path should be. The fold ran one iteration short and terminated on a match, which is the
only success condition the function has.

<Aside kind="note">
The usual name for this — "second-preimage attack" — is misleading, and one of the clearest
write-ups says so directly: no second preimage of any hash is found. Better names are **node-as-leaf**
or **shortened-proof**.<Cite src="rareskills-merkle-second-preimage" /> What is exploited is that the
root is built incrementally, so a fold that begins partway up the path still lands on the same value.

It earns its usual name at the level of the *tree*, though. Read the tree as a single function from
a leaf set to a root, and the attacker has found a second input producing the same output — which is
exactly the property RFC 6962 says domain separation exists to
provide.<Cite src="rfc-6962" /><Cite src="nist-sp-800-107" />
</Aside>

## Why 64 bytes is the number everyone quotes

For this to work, the attacker must pass the internal node's **pre-image**, not its hash. Two 32-byte
child hashes concatenated is 64 bytes, so the leaf data has to be permitted to be 64 bytes long. If
your leaf pre-image can never have that length, the substitution cannot be expressed at
all.<Cite src="rareskills-merkle-second-preimage" />

That is why OpenZeppelin's `MerkleProof.sol` carries a warning to "avoid using leaf values that are
64 bytes long prior to hashing", and points instead at a hash function other than `keccak256` for
leaves.<Cite src="oz-merkleproof-source" />

<Aside kind="warn">
Be precise about your own encoding here, because the 64-byte rule is a proxy, not the condition.

`abi.encode(address, uint256)` is exactly 64 bytes — two padded words — which sounds immediately
fatal. But the first word of a valid claim must be a left-padded address, meaning 12 leading zero
bytes, and a `keccak256` output has those only by luck. The shapes that are *directly* constructible
are the ones where the attacker chooses both words freely: leaves built from two `bytes32` fields,
leaves taken as raw `bytes` from calldata, or any path where attacker-influenced entries let them
grind the tree into a usable shape.

The library states the rule by length because a library cannot see your field types.<Cite src="oz-merkleproof-source" />
You can, so reason about both: length *and* whether an attacker can choose the bytes.
</Aside>

## Sorted pairs are not a neutral optimisation

The previous lesson used sorted-pair hashing — order the two 32-byte values, then concatenate — so
proofs need not carry a left/right bit. It is smaller and simpler, and OpenZeppelin's verifier is
built on it.<Cite src="oz-merkleproof-source" />

The cost is that the tree keeps no positional information whatsoever. There is nothing in a node that
says which side it came from or how deep it sits, so there is nothing for a verifier to cross-check
against when a node is presented as a leaf. Sorting is what turns the confusion from a theoretical
overlap into an exploitable one.<Cite src="rareskills-merkle-second-preimage" />

Contrast the two conventions from the previous lesson and the interaction is visible. Certificate
Transparency's node hash is `SHA-256(0x01 ‖ MTH(left) ‖ MTH(right))` — the operands are not sorted,
because the prefix byte and the position both carry meaning.<Cite src="rfc-6962" /> Sorting is what
you do once you have decided position carries nothing; the prefix is what you must then add back to
keep *kind* carrying something.

## The fix, and why it is the same fix as the rest of this module

Make it impossible for one byte string to be read as two kinds of object. Any of these achieves it:

**Domain separation by prefix.** Hash a leaf as `H(tag_leaf ‖ data)` and an internal node as
`H(tag_node ‖ left ‖ right)`, with different tags. Certificate Transparency does this with `0x00` for
leaves and `0x01` for nodes, and RFC 6962 states it in a parenthesis next to the definition: the hash
calculations for leaves and nodes differ, and "this domain separation is required to give second
preimage resistance".<Cite src="rfc-6962" /> Nethermind's write-up of the Solidity case uses `0x01`
and `0x02` instead.<Cite src="nethermind-merkle-second-preimage" /> The specific bytes carry no
meaning; distinctness is the entire content of the idea.

**Double-hash the leaves.** Define the leaf as `H(H(data))`. The outer hash's input is then always 32
bytes, while internal nodes always take 64, so the two input domains cannot
overlap.<Cite src="nethermind-merkle-second-preimage" /> This is what OpenZeppelin's JavaScript tree
builder does by default, and it is why trees built with it are safe against this out of the
box.<Cite src="oz-merkle-tree-js" /> Run it on the forgery above and the 64-byte leaf data hashes to
`6ec3f0db…dc974276`, which is not a node in the tree and folds to nothing.

**Use a different hash function for leaves.** Same effect, more gas.<Cite src="oz-merkleproof-source" />

You have now seen this exact move four times in one module: NIST's two-bit suffix separating SHA-3
from SHAKE<Cite src="nist-fips-202" />, EIP-191's `0x19` separating signed data from
transactions<Cite src="eip-191" />, EIP-712's domain separator separating one contract's messages
from another's<Cite src="eip-712" />, and this. A hash means nothing until you have fixed what its
input is allowed to represent.

## The multiproof has its own version of this

Batch verification is where the same confusion reappears in a form the 64-byte rule does not catch,
and it has a CVE.

OpenZeppelin's advisory for `verifyMultiProof` and `processMultiProof` states the impact plainly: it
is possible to construct Merkle trees that allow forging a valid multiproof for an **arbitrary set of
leaves**.<Cite src="oz-multiproof-advisory" /> The precondition is specific — the tree must include a
node with value zero at depth 1, just below the root — and the advisory notes this can happen
*inadvertently* for balanced trees with three leaves or fewer when the leaves are not hashed, or
deliberately when a malicious party builds the tree.<Cite src="oz-multiproof-advisory" /> It is
tracked as CVE-2023-34459 and was patched in 4.9.2.<Cite src="oz-multiproof-advisory" />

Three things in the workaround list are worth reading as general advice rather than as OpenZeppelin
guidance:<Cite src="oz-multiproof-advisory" />

- Hash the leaves, and do not insert empty nodes into your trees.
- **Do not accept user-provided Merkle roots without reconstructing at least the first level of the
  tree.**
- Single-leaf proving is not affected.

The middle one is the deep one. Every other defence in this lesson constrains what a *claimant* can
submit. That one constrains what a *root publisher* can submit — and it is the answer to the question
the previous lesson ended on, about who gets to set the root.

## A review checklist

When you meet Merkle verification in a codebase, four questions settle it, in this order.

**Subgoal — can a leaf pre-image be 64 bytes?** Read the exact expression that produces `leaf`, not
the library call underneath it. `abi.encodePacked(bytes32, bytes32)` is the vulnerable shape in its
purest form; `keccak256(bytes.concat(keccak256(abi.encode(...))))` is not.

**Subgoal — can the attacker choose those bytes?** Two attacker-controlled words is fatal; a
left-padded address plus an amount is far less reachable. Length is the proxy, control is the
condition.

**Subgoal — do leaves and nodes hash the same way?** If yes, the tree is one leaf-encoding change
away from the forgery, whatever today's field types happen to be.

**Subgoal — do the builder and the verifier agree?** They live in different repositories and
different languages, and they are one commit apart from disagreeing. A verifier and a builder that
disagree about leaf hashing produce a contract that rejects every honest claim — which at least fails
loudly. The dangerous version is the builder being changed to match a verifier that was wrong.

<Check type="spot-bug" concept="merkle-second-preimage">
A rewards contract:

```solidity
function claim(bytes32 idHash, bytes32 amountWord, bytes32[] calldata proof) external {
    bytes32 leaf = keccak256(abi.encodePacked(idHash, amountWord));
    require(MerkleProof.verify(proof, root, leaf), "bad proof");
    _pay(msg.sender, uint256(amountWord));
}
```

The library is the audited one and the root is correct. What goes wrong, what does the attacker need
to know, and what is the smallest fix?

<Answer>
The leaf pre-image is `abi.encodePacked(bytes32, bytes32)` — exactly 64 bytes, both words fully
attacker-chosen. That is the vulnerable shape in its purest form.

The attacker needs only the tree's published contents, which airdrops publish by definition. They
compute any internal node's two children, pass them as `idHash` and `amountWord`, and supply that
node's own remaining path as the proof. The verifier folds from one level up and reaches the root.
`amountWord` is the right-hand child hash reinterpreted as a number, so the payout is whatever that
hash happens to be — which is to say, enormous.

Smallest fix: `bytes32 leaf = keccak256(bytes.concat(keccak256(abi.encode(idHash, amountWord))));`
The outer hash now takes 32 bytes and can never coincide with an internal node's 64-byte
input.<Cite src="oz-merkle-tree-js" /> The tree generator must be changed to match, in the same
commit.

Two extensions worth thinking through before you move on. First, `_pay` sends
`uint256(amountWord)` — an unbounded value read straight out of the proof, with no cap and no
per-claimant "already claimed" flag, so even the honest path is one duplicate submission away from
paying twice. Second, notice that the fix does nothing about *who set `root`*; if the root is
mutable, everything above is decoration.<Cite src="oz-multiproof-advisory" />
</Answer>
</Check>

This is not a museum piece. The same family shows up in competitive audit findings against deployed
Merkle verification, including proof implementations vulnerable to tree-extension
manipulation<Cite src="c4-merkle-tree-extension" />, and it has been studied systematically as a
class in the specific context of Merkle-proof-based airdrops.<Cite src="fsa-merkle-airdrop-study" />
The OpenZeppelin issue that documents it on their own library has been open, as a documentation and
guidance matter rather than a code fix, precisely because the vulnerable half lives in the caller's
tree builder.<Cite src="oz-merkleproof-issue-3091" />

## Where this pays off

When you reach Ethereum's Merkle Patricia Trie, one of the questions worth carrying in is how it
keeps its node kinds apart — leaf, extension and branch nodes are different shapes with different
encodings — and what it would take to present one kind as another. The same question applies to SSZ
merkleisation on the consensus side, and to every bridge that authorises a message by proving it
against a remote root, where the "leaf" is a message and the payout is whatever the message says.

The general form is the durable takeaway, and it is the sentence this whole module has been building
toward. Whenever a system hashes more than one kind of thing with one function, its security depends
on those input spaces being disjoint — and the moment that stops being true, a correct verifier will
cheerfully accept a lie.
