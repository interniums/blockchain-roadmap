Three lines from the same codebase. Each is one call to the same hash function.

```solidity
bytes32 id = keccak256(payload);                  // the primary key for a submitted document
require(keccak256(voucher) == issuedDigest);      // a voucher is valid if it reproduces its digest
emit Committed(keccak256(bid));                   // a sealed bid, revealed after the auction closes
```

All three are correct uses of a hash function, in the narrow sense that the function does exactly
what it advertises. One is broken by anybody with a laptop and an afternoon. The other two rest on
guarantees that differ from each other by a factor of 2¹²⁸.

Which is which is not a fact about `keccak256`. It is a fact about **who gets to choose the
inputs**, and that is the subject of this lesson.

## What the function is, before what it promises

A hash function maps an input of any length to a fixed-length output, deterministically. The same
bytes always produce the same digest; any change to the input produces a digest with no visible
relationship to the previous one. It is cheap to compute forward. Ethereum's is `keccak256`, written
`KEC` in the Yellow Paper, producing 32 bytes.<Cite src="yellow-paper" /> The family it comes from
was standardised by NIST as SHA-3 in 2015<Cite src="nist-fips-202" />, and the relationship between
Ethereum's function and that standard is the next lesson — it is less straightforward than the
shared name suggests.

Start with the part people skip. There are unboundedly many possible inputs and exactly 2²⁵⁶
possible outputs.<Cite src="yellow-paper" /> Collisions do not merely happen to exist: with an
unbounded set mapped into a finite one, some digests must have unboundedly many inputs producing
them. That is counting, and no cleverness in the design changes it.

So no hash function promises that two inputs never collide. It promises something weaker and far
more useful — that **you cannot find** a pair that does. Every guarantee below is a statement about
the cost of a search, never about the absence of an answer.

## Three promises, and the only thing that varies between them

The three properties get listed as three phrasings of "no two inputs hash the same". They are not.
Read each as a game, and watch what the attacker is *handed* versus what they get to *choose*.

**Preimage resistance.** Given a randomly chosen digest `h`, it is infeasible to find any `x` with
`hash(x) = h`. NIST calls this the one-way property.<Cite src="nist-sp-800-107" /> The attacker
chooses nothing about the target; the value they must hit was fixed before they arrived.

**Second-preimage resistance.** Given a specific input `x`, it is infeasible to find a different `x'`
with `hash(x') = hash(x)`.<Cite src="nist-sp-800-107" /> The attacker now chooses *one* of the two
messages. The other is handed to them, and it is usually something already published, already
signed, or already recorded on chain.

**Collision resistance.** It is infeasible to find *any* pair `x ≠ x'` with equal
digests.<Cite src="nist-sp-800-107" /> The attacker chooses both. Nothing is fixed in advance, and
neither message has to mean anything to anyone but them.

Nothing varies across those three except the quantifier — what is given, and what is free. That is
also the only place the cost varies, and the difference is not a rounding error.

## Why collisions cost half, and why that is counting rather than weakness

NIST scores each property separately. For an `L`-bit hash the expected strengths are `L` bits against
preimage, `L` bits against second preimage, and `L/2` bits against collisions — for SHA-256, 256,
256 and 128.<Cite src="nist-sp-800-107" /> Reconstruct the halving rather than memorising it.

**Subgoal: count what a search buys when the target is fixed.** Hunting a preimage, each guess hits
or misses with probability 2⁻ⁿ. After 2^(n/2) guesses you have had 2^(n/2) chances. You are nowhere.

**Subgoal: count what the same search buys when nothing is fixed.** Hunting any collision, each new
digest pairs with every digest you already hold. After 2^(n/2) computations you hold roughly 2ⁿ
*pairs*, each matching with probability 2⁻ⁿ. Same work, squared payoff.

**Subgoal: notice what that argument never assumed.** Nothing about Keccak, SHA-2, or structure in
any real function — only that digests are drawn from a set of size 2ⁿ. This is the **birthday
bound**; an ideal random function obeys it exactly, and no design removes it, because it is
arithmetic about how fast pairs accumulate.

The halving is not a defect being tolerated, then. It is why output sizes are chosen at double the
security level actually wanted: 256 bits of digest is what you pick to buy 128 bits against an
adversary who controls both messages.

<Aside kind="note">
NIST's own table refuses a single second-preimage number: SHA-256 is listed at 201–256 bits, not a
flat 256, because for some constructions the strength also depends on the length of the message
under attack.<Cite src="nist-sp-800-107" /> Treat "L bits" as a headline rather than a constant. The
*ordering* is the durable part, and it never inverts.
</Aside>

One more sentence from that document belongs in every design review. When an application needs more
than one property, the strength of the hash *for that application* is the strength of the weakest
property it relies on: digital signatures need collision resistance and second-preimage resistance,
so their strength is `L/2`, the smaller one.<Cite src="nist-sp-800-107" /> Your design's strength is
not the digest length in the documentation. It is whichever property your attacker gets to attack.

<Check type="recall" concept="collision-resistance">
A protocol lets users register a name by submitting `keccak256(name)`. An attacker wants to claim a
name someone else already registered. Which property must break for the attack to work — and does
the attacker get to choose both messages?

Then change one thing: the protocol is first-come-first-served, and the attacker can register names
of their own before anyone else shows up. What changes?

<Answer>
**Second-preimage resistance.** The victim's name is already fixed on chain, so the attacker is
handed `x` and must find a different input matching its digest. They do *not* choose both sides, so
the birthday bound does not help them — the cost is 2ⁿ, not 2^(n/2).

**In the second setup, collision resistance.** The attacker registers a name they constructed
themselves, having already found a second string that collides with it. Both messages were theirs,
nothing was fixed before they started, and pairs accumulate: 2^(n/2).

Same function, same protocol shape, a factor of 2¹²⁸ apart at 256-bit output — decided entirely by
whether the attacker could act before the value was pinned. The question to ask about a design is
therefore not "is this hash strong" but "what was already fixed when the attacker arrived".
</Answer>
</Check>

## The properties fall in that order, and they have

This is the recorded history of the two hash functions the industry used before this one.

**MD5** produces a 128-bit digest. By the time the IETF published its updated security
considerations in 2011, finding a collision was reported at ten seconds or less on a 2.6 GHz
Pentium 4, and the conclusion was that MD5 must not be used where collision resistance is
required.<Cite src="rfc-6151" /> The very next section of that document reports the best known
*preimage* attack at about 2¹²³·⁴ — faster than exhaustive search, and still entirely out of
reach.<Cite src="rfc-6151" /> One property gone; another intact enough to publish a number for.

**SHA-1** produces a 160-bit digest, so the birthday bound puts its expected collision strength at
80 bits. NIST's table listed it below even that, at "< 80", while listing its preimage resistance at
the full 160.<Cite src="nist-sp-800-107" /> In 2017 a team produced the first collision for the full
function: two PDF files with the same digest and deliberately different visible content, at 2⁶³·¹
compression-function calls — roughly 6,500 CPU years and 100 GPU years, and more than 100,000 times
faster than brute force.<Cite src="sha1-first-collision" /> NIST retired SHA-1 in December 2022,
naming collision attacks as the cause, with a phase-out deadline of 31 December
2030.<Cite src="nist-sha1-retirement" />

Both died of the cheapest property, the one where the attacker chose both messages — and note what
the SHA-1 authors needed to make a collision *useful*: control of the prefixes, so the colliding
files displayed different content.<Cite src="sha1-first-collision" /> A collision between random
blobs is a curiosity. A collision between two documents that both mean something is a forgery, and
reaching it needs exactly the freedom that only collision resistance grants.

<Aside kind="note">
The implication runs one way: anyone who finds a second preimage has thereby found a collision, so
collision resistance is the stronger claim, and the reverse does not hold. That asymmetry is the MD5
story in one line — the function lost collision resistance completely while staying serviceable for
detecting accidental corruption, where nobody chooses anything. "Is this hash broken?" is the wrong
question. "Broken for which property, and is it the one I am leaning on?" is the question.
</Aside>

## The failure that needs no broken function

Everything above attacks the function. The most common real failure attacks the assumption around it
instead.

<Misconception
  belief="Hashing is a way of encrypting data."
  reality="Hashing destroys information; encryption preserves it. There is no key and no inverse — a digest cannot be decrypted even by the person who computed it, because the input is not in there any more."
  why="Both live under 'cryptography' and both turn readable data into unreadable data, so they get filed together. The confusion stays harmless right up until someone concludes that a digest of a secret is therefore safe to publish."
/>

Look at how NIST states preimage resistance: given a **randomly chosen** digest, it is infeasible to
find an input producing it.<Cite src="nist-sp-800-107" /> That phrase is load-bearing. The property
is a claim about the function across its whole input space, not a claim about your input.

Your input is almost never randomly chosen. A bid in whole pounds, a phone number, a postcode, a
salary band, a vote for one of four options, an address from a published list — each is a set an
attacker can enumerate. They never invert anything. They run the function forward over every
candidate and compare, which is the same work you did to produce the digest.

<Misconception
  belief="Publishing the hash of a secret keeps the secret, because hashes cannot be reversed."
  reality="Nobody reverses it. If the value comes from a small set, the attacker hashes every element of that set and compares. The function's preimage resistance is untouched — it simply was never the thing protecting you."
  why="Preimage resistance is defined over the full input space, and applications live in a tiny corner of it. The guarantee is real; the reasoning that inherits it is not."
  src="nist-sp-800-107"
/>

The repair is to commit not to the value but to the value mixed with something an attacker cannot
enumerate. That construction has requirements of its own and a lesson of its own later in this
module.

## Which property is your design leaning on?

One question separates the cases, and it is not a question about cryptography.

**Who chooses the inputs, and what was already fixed when the attacker arrived?**

- **Attacker chooses nothing and must match a digest that already exists** — preimage resistance,
  full `L` bits.<Cite src="nist-sp-800-107" /> The risk here is almost never the function; it is how
  much entropy your input actually had.
- **Attacker is handed one input and must produce a second that matches** — second-preimage
  resistance, full `L` bits.<Cite src="nist-sp-800-107" /> Ask what pinned the first input, and
  whether the attacker could have influenced it beforehand.
- **Attacker chooses both** — collision resistance, half the bits<Cite src="nist-sp-800-107" />, and
  historically the first to fall. Any design treating a digest as a *name* — a key, an identifier, a
  deduplication token — is in this row, because the attacker supplies the thing being named.

The three lines at the top now resolve. The primary key is the collision row: two submitters, two
chosen payloads, one row. The voucher check is the second-preimage row — unless the attacker
supplied the voucher text at issue time, in which case it was quietly the collision row all along.
The sealed bid is the preimage row and it is the broken one, not because preimage resistance failed
but because bids are enumerable. Cryptographic strength did not order these by practical risk.

## Where this pays off

**Function selectors** are the first four bytes of `keccak256` of a function's canonical
signature.<Cite src="solidity-abi-spec" /> Four bytes is 32 bits, and the `L/2` rule puts collisions
at roughly 2¹⁶ work<Cite src="nist-sp-800-107" /> — seconds, on anything. Not a weakness in
`keccak256`: the birthday bound applied to a deliberately truncated digest, and the reason selector
collisions are a design consideration rather than a thought experiment.

**Storage slots** behind a mapping, **`CREATE2` addresses** and **transaction hashes used as
identity** all name something a caller supplied, so all three sit in the collision row at half the
bits — which is exactly why the digest is 256 bits wide and not 128.

**Merkle roots** compress a set into one 32-byte commitment, and the proofs built on them depend on
second-preimage resistance holding *at the application level*, not merely at the function level. Two
lessons later in this module take that apart and then break it, with no weakness in `keccak256` at
all. **Commitments** — the sealed bid above, done properly — are preimage resistance applied with
the entropy problem handled rather than assumed.

The next lesson narrows the question from "what does a hash guarantee" to "*which* hash". Getting
that wrong costs you every guarantee on this page at once, for a reason that has nothing to do with
any of them.
