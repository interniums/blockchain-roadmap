Thousands of machines, run by people who have never met and have no particular reason to trust
each other, are asked what one account's balance is. They all answer the same number.

The intuitive mechanism — take a poll, majority wins — is not what happens, and working out why it
is the wrong mechanism is most of what this module is for.

## Voting on outcomes is the expensive design

Picture the poll actually running. What is being voted on?

Not one balance. A node cannot vote on a single account in isolation, because a transaction that
touched that account probably touched others, and a vote that ratifies one field while leaving the
rest unratified ratifies nothing. So the ballot is the whole state — every account, every contract's
storage — and it has to be re-run every time anything changes.

That design has three problems, and they compound.

**Nothing is checkable.** If one node reports 40 and another reports 41, a third node counting votes
has no way to tell which is right. It can count heads. It cannot evaluate the claim. Majority becomes
a popularity contest among peers who were selected by nobody.

**Everyone must trust everyone's arithmetic.** A node accepting a vote is accepting the result of a
computation it did not perform, from a machine it cannot inspect.

**The cost scales with the state, not with the change.** A single token transfer would trigger
agreement over a data set that grows without bound.

There is a design that avoids all three, and it predates blockchains by decades.

## Agree on the inputs; compute the outputs alone

The technique is **state machine replication**. Model the service as a deterministic state machine.
Run identical copies on independent machines. Feed every copy the same sequence of requests, in the
same order. Each copy then produces the same outputs and passes through the same states, with no
further coordination required.<Cite src="schneider-smr-tutorial" />

Three things have to hold for that to work:

1. Every replica starts from the same state.
2. Every replica processes the same inputs in the same order.
3. The transition function is deterministic — same state, same input, same result, always.

Given those, agreement on outcomes is not something the replicas negotiate. It is a consequence.
They agree because they cannot do otherwise.

Notice what this does to the problem. The expensive, unbounded, uncheckable question — *what is the
state?* — has been replaced by a cheap, bounded question: *what comes next?* Ordering is the only
thing left to argue about, and an ordering can be argued about compactly because it is a list of
identifiers, not a database.

This is the single most useful sentence to carry through the rest of the track: **consensus in a
blockchain is about sequence, never about outcome.** Every time a later lesson says validators
"agree" on something, the thing they agree on is which block comes next.

## Ethereum's instantiation

The pieces map directly.

- **The input log** is the chain of blocks. Each block carries an ordered list of transactions and a
  pointer to its parent, so the whole history is one totally ordered sequence.
- **The transition function** is the protocol's state transition rules — the EVM plus the block-level
  bookkeeping around it — specified as a deterministic function of the previous state and the new
  block.<Cite src="yellow-paper" />
- **The state** is the set of accounts, balances, contract code and contract storage that the
  function reads and writes.

Nobody transmits state. A node that has the genesis state and every block since can compute the
current state for itself, and two nodes that do so arrive at the same answer or one of them is
broken.

### A worked trace

Two nodes, run by strangers, receive the same block. Follow what each of them does with it.

**Subgoal: establish a common starting point.** Both nodes already hold the state produced by the
parent block, and both hold the parent's root. The new block names its parent, so each node knows
exactly which state it is extending. If a node does not have that parent, it cannot apply the block
at all — it has to fetch the gap first. Ordering is enforced by the structure, not by etiquette.

**Subgoal: apply the inputs in the given order.** Each node runs transaction one against its local
copy of the state, then transaction two against the result of that, and so on. There is no messaging
between the nodes during this phase, and no timing dependence. Transaction two sees exactly what
transaction one left behind, on both machines, because that is what "in order" means.

**Subgoal: compare a fingerprint, not a database.** Each node hashes its resulting state into a
single root and compares it with the root the block claims. Equal: the block is valid and becomes the
new tip. Unequal: the block is invalid and is discarded, along with everything built on it.

**Subgoal: notice what never happened.** Neither node asked the other what the balances came out as.
Neither node's answer was weighted by stake, reputation, or uptime. The only cooperative act in the
whole trace was accepting the same ordered list of transactions, which happened before any execution
began.

That last observation is the design. Everything the consensus protocol does — attestations,
checkpoints, fork choice, the whole apparatus of the next four lessons — exists to produce that
ordered list. Execution is a local matter afterwards.

## Then why does a block publish a state root?

If the state is derivable from the inputs, publishing a fingerprint of it looks redundant. It is not,
and the reason is worth pausing on, because it is a pattern you will meet again.

**Subgoal: make divergence detectable rather than silent.** Two nodes that quietly disagree about a
balance will keep operating, serving different answers to different users, for as long as nobody
compares them. Two nodes that disagree about a single root hash discover it on the next block.

**Subgoal: make the check cheap.** Comparing two states means walking two databases. Comparing two
roots is one equality test on one word.

**Subgoal: make the resolution mechanical.** A node whose computed root differs from the root in the
block does not enter a negotiation. It rejects the block. If the rest of the network accepted that
block, this node has left the network, and the correct conclusion is that this node is wrong.

That last point is worth stating plainly, because it inverts an instinct trained by ordinary
distributed systems. There is no quorum here that makes a minority result acceptable. A client that
computes a different state root from the same inputs is, by definition, buggy — and if that client is
running on a large fraction of the network, the network splits into two chains, each internally
consistent and mutually unrecognisable. Correctness of the transition function is not one property
among many. It is the thing the whole arrangement rests on.

<Check type="explain" concept="state-machine-replication">
A new client implementation joins the network. It syncs from genesis, replays every block, and
arrives at a state root that differs from the one in the latest block by a single bit. Its authors
argue that since the difference is tiny and their implementation is more standards-compliant, the
network should accept their root.

What is wrong with that argument, in terms of what the network is actually agreeing on?

<Answer>
The network is not agreeing on which state is *correct* in any external sense — it is agreeing on an
ordered list of inputs, and the state root is a checksum over the result of applying the agreed
transition function to that list.

"More standards-compliant" describes a different transition function. Running a different function
over the same inputs produces a different state, which is not a better answer to the same question;
it is an answer to a different question. There is no forum in which that root can be accepted,
because acceptance is not a vote — every other node recomputes and rejects.

The practical resolution is the reverse of what the authors propose: either the specification is
wrong and every client changes together at a scheduled fork, or this client is wrong and fixes
itself. A one-bit difference is not a small disagreement. It is a chain split.
</Answer>
</Check>

## Determinism stops being a matter of taste

Requirement three above — the transition function is deterministic — sounds like a mild engineering
preference. In this setting it is a hard constraint with teeth, and it explains a list of EVM
omissions that otherwise look arbitrary or primitive.

Any quantity that can differ between two machines running the same code is a fork waiting to happen.
So the design removes the whole category rather than trying to police it.

**No floating point.** The EVM's word is a 256-bit unsigned integer and arithmetic is modular.<Cite
src="yellow-paper" /> Floating point is specified precisely enough on paper, but the result of an
expression in practice depends on intermediate precision, on whether the compiler contracted a
multiply and an add into one instruction, and on which library supplied the transcendental functions.
Those vary by compiler, flags and hardware. Excluding the type is cheaper than proving that every
client's toolchain agrees.

**No clock.** A contract reading the host machine's time would read a different value on every node.
On Ethereum today the execution payload's timestamp is not a reading at all: the consensus rules
require it to equal the time computed from the slot number, derived from the genesis time and a fixed
slot duration, and a payload whose timestamp differs is invalid.<Cite src="consensus-specs" /> The
value is part of the schedule, agreed before execution begins, and every node executing that block
sees the identical number.

**No ambient randomness.** A contract cannot ask the operating system for entropy, because entropy is
by construction different on every machine. What exists instead is `PREVRANDAO`, which took over
opcode `0x44` from the old `DIFFICULTY` instruction and returns a value produced by the beacon
chain.<Cite src="eip-4399" /> That value is consensus data — it was agreed before the block executed,
so every node reads the same bytes. Whether it is *unpredictable* enough for a given use is a
separate question, and a harder one; determinism is satisfied either way.

**No I/O.** No filesystem, no sockets, no environment variables, no calls out to anything the
protocol did not put in front of the machine.

**No undefined ordering.** This one reaches above the EVM. Encoding is part of the transition
function's surface: if two clients can serialize the same value two different ways, they hash it two
different ways, and their roots diverge without either one having made an arithmetic error. That is
why the encodings this track covered earlier are specified as canonical — exactly one byte string per
value — rather than merely as "a format".

### The transition function has several implementations

Here is the part that unsettles most engineers when it lands. The transition function is written down
as a specification, but the specification is not what runs. What runs is a handful of independent
implementations, in different languages, written by different teams, each of which has to agree with
all the others on every input anyone will ever submit.

Ordinary software treats an implementation difference as a bug of some severity to be triaged.
Here, a difference in the transition function is a network partition with extra steps. Two clients
that disagree on one obscure edge case will agree on billions of blocks and then, on the block where
that case first appears, produce different roots and stop recognising each other's chains.

Two consequences follow, and they explain a lot of behaviour that looks paranoid from outside:

- **Bug-compatibility beats correctness.** If the specification and the dominant implementation
  disagree, the implementation usually wins, because changing it unilaterally is the thing that
  splits the network. Corrections get scheduled into coordinated upgrades instead.
- **How many nodes run each client is a live risk number, not trivia.** If one client has a defect
  and a small share of the network, its nodes fall off the chain and their operators fix them. If it
  has most of the network, the defective behaviour becomes what the majority chain does, and the
  correct nodes are the ones that appear to have failed. That asymmetry is why client-diversity
  figures are tracked at all.

None of this is Ethereum-specific. It is what requirement three costs when the replicas are operated
by people who do not answer to you.

## Where the real world gets in

The obvious objection: real products need prices, weather, sports results, timeouts. None of that is
deterministic. How does any of it reach a contract?

It arrives as an input that was itself ordered by consensus. An oracle does not give a contract a
capability to look outward; it submits a transaction. Once submitted, the value in that transaction
is what every node sees, in the position the block gave it, forever.

Two consequences fall out immediately, and both matter more than they look:

- **The contract reads a reported value, not a true one.** Determinism guarantees that every node
  agrees on what was reported. It guarantees nothing about whether the report was accurate.
- **Position in the sequence is part of the semantics.** A price update placed before a liquidation
  produces a different world from the same update placed after it. Because ordering is the thing
  consensus decides, whoever influences ordering influences outcomes — which is where a large part of
  this ecosystem's adversarial economics lives.

<Check type="spot-bug" concept="determinism-requirement">
Someone proposes a new EVM opcode, `RANDOM`, which returns 32 fresh bytes from the node's operating
system entropy pool. The argument for it: contracts need randomness, `PREVRANDAO` is influenceable by
the block proposer, and the OS entropy pool is not.

Name the failure, and be specific about what breaks first.

<Answer>
Execution diverges on the first block that contains a call to it.

Every node executing the transaction gets different bytes, so every node computes a different result,
a different state, and a different state root. The proposer's block carries the proposer's root. Every
other node recomputes, gets its own root, finds a mismatch, and rejects the block as invalid.

The chain does not fork into two viable branches — it fails to make progress at all, because no
block containing that opcode can ever be accepted by anyone other than the machine that produced it.

The proposed cure also misreads the disease. `PREVRANDAO`'s weakness is *predictability and
influence*, which is a security property. The opcode's requirement is *agreement*, which is a
correctness property. An unpredictable value that nobody else can reproduce fails the correctness
requirement outright, and no amount of extra entropy repairs that. Randomness usable here has to be
agreed first and unpredictable second — which is why the mechanisms that get proposed for it are all
some form of commit-then-reveal, carried through the ordered input log like everything else.
</Answer>
</Check>

## Where this pays off

You now have the frame the rest of the protocol hangs on.

The **Merkle Patricia trie** is the data structure that makes the state root of this lesson cheap to
compute incrementally and cheap to prove pieces of — it exists because the root has to be recomputed
every block.

The **two-process node** — an execution client and a consensus client running side by side, talking
over a narrow API — is this lesson's split made physical: one process decides the order, the other
applies the transition function.

An **indexer** is a deterministic fold over the same ordered log, which is why a well-built one can
be rebuilt from scratch and land on identical output, and why the parts of it that are not
deterministic are exactly the parts that break during a reorg.<Cite src="eth2book-consensus" />

And the module's real question is now in view. Replication works when every replica follows the
rules. The next lesson asks what happens when one of them does not.
