Most serialization libraries you have used are graded on round-tripping: encode a value, decode it,
get the value back. By that standard a decoder that accepts more inputs is a better decoder, and
being strict is just being unfriendly.

Ethereum inverts this. Here a decoder that accepts a second encoding of the same value is a defect,
and the strictness is the feature. This lesson is about why, and it is the one that makes the
previous three matter.

## The property

An encoding is **canonical** when every value has exactly one valid byte representation, and decoders
reject every other representation of it.

Two halves, and the second is the one that gets forgotten. It is not enough that your *encoder*
produces one form. Every decoder in the network must refuse the alternatives — otherwise the
alternatives exist, and something will eventually produce one.

## What RLP rejects

RLP's rules from the earlier lesson looked like a compact encoding scheme. Read the reference
decoder and they are better described as a list of things that are illegal to write down.

- **A single byte below `0x80` wrapped in a length prefix.** `0x8105` decodes structurally to the
  one-byte string `0x05`, and it is rejected: `0x05` must be written as
  itself.<Cite src="ethereum-rlp-reference" />
- **The long form used where the short form fits.** A length-of-length header whose decoded length
  comes out below 56 is rejected, because that length had a one-byte encoding
  available.<Cite src="ethereum-rlp-reference" />
- **A leading zero in a length.** The first byte of a length-of-length may not be zero — a padded
  length would give one payload size several spellings.<Cite src="ethereum-rlp-reference" />
- **A leading zero byte in an integer.** Positive integers are big-endian with no leading zeros, so
  in a field the schema types as an integer, `0x820005` is not a long-winded five — the reference
  decoder raises "non-canonical integer".<Cite src="ethereum-rlp-reference" /> ethereum.org pushes
  the requirement outward: a decoded positive integer with leading zeroes **must be treated as
  invalid by any higher-order protocol using RLP**.<Cite src="ethereum-org-rlp" />
- **Trailing bytes.** An item whose declared length ends before the input does is rejected rather
  than truncated.<Cite src="ethereum-rlp-reference" />

You can watch this happen. `cast from-rlp 0x8105` and `cast from-rlp 0xb80161` both fail, and both
are structurally parseable — the decoder knows what they were meant to say and refuses to say
it.<Cite src="ethereum-rlp-reference" />

None of these rules exists to save bytes; the saving is one or two bytes on an item. They exist to
make the map from values to encodings injective in both directions.

## What ABI does not reject

The third format in this module is the interesting one, because it is *not* canonical and says so.

The ABI specification defines a **strict encoding mode**: offsets as small as possible while still
not overlapping, and therefore no gaps. It then records the actual state of affairs — the Solidity
encoder always produces strict output, and the Solidity decoder **does not enforce
it**.<Cite src="solidity-abi-spec" /> A decoder that follows offset pointers wherever they point
accepts encodings with dead space between payloads, or with two offsets aimed at the same bytes, and
hands back plausible arguments.

EIP-712's authors reached the same conclusion from the other direction. Considering ABI encoding for
their structured-data scheme, they rejected it in one line: the standard by itself fails the
determinism criterion, because there are several valid encodings of the same
data.<Cite src="eip-712" /> Two independent specifications, same finding.

Why is that survivable when a non-canonical RLP decoder would not be? Because calldata is not itself
a consensus object. What the chain hashes is the *transaction*, and a transaction is RLP — the
calldata rides inside it as one opaque byte string, hashed exactly as it arrived rather than
re-encoded.<Cite src="eip-1559" /> Two spellings of the same arguments are two different transactions
with two different hashes, both valid; no client has to decide which is real.

So the failure moves rather than disappearing. It lands wherever an application treats decoded
*arguments* as the identity of a call: an idempotency key hashed from calldata, a signature checked
against a re-encoding of arguments, a replay guard that hashes what it decoded rather than what it
received. In each, the same call has more than one name.

## What SSZ rejects

SSZ removes most of the opportunity by construction. A fixed-size field has one layout because its
type says so; there is no length to spell two ways.<Cite src="ssz-specs-container" />

The freedom that remains is in offsets, and it is closed explicitly. A container decoder requires
that the **first offset equals the width of the fixed part** — the heap starts where the fixed part
ends, not one byte later — and that offsets are **monotonic**, so payloads cannot overlap or be
reordered behind the scenes.<Cite src="ssz-specs-container" /> Without those two checks the same
container value would have many valid serializations differing only in dead space between payloads —
precisely the freedom the ABI decoder leaves open.

SSZ then enforces the property a second time, one level up, because it has a second identity to
protect: the hash tree root must be unique to a value too. So a variable-length list mixes its
element count into its root, and a progressive container mixes in which fields are active — the
latter specifically because a removed field and a zero-valued field both leave a zero leaf, and
without the mix-in the two would root identically.<Cite src="ssz-specs-merkleization" /> Same rule
applied to a tree instead of a byte string.

<Check type="spot-bug" concept="canonical-serialization">
A team writes an RLP decoder for a tool that reads block data. To be robust against "slightly odd"
producers, they add a fallback: if a length prefix has a leading zero byte, strip it and carry on.
Every test round-trips. Name the failure this introduces, and say what class of failure it is.

<Answer>
**The tool now accepts two distinct byte strings as the same value — and it will disagree with the
network about which is real.**

A padded length is not a bug in a producer, it is a different byte string, and byte strings are what
get hashed. Feed the tool a block whose header carries a padded length and it reports a valid header
with some root; every conforming client rejects that block outright.<Cite src="ethereum-rlp-reference" />
The tool is not being lenient about formatting. It is computing over data the chain does not contain.

**The class is consensus divergence, not data corruption.** Nothing is malformed in the ordinary
sense: no hash is broken, no signature is forged, the bytes parse. Two implementations simply
disagree on whether a given byte string is a valid encoding, and therefore on what the chain is.

That is also why the fix is not "make the strict clients lenient". Leniency is not a superset of
strictness here — a rule that some participants enforce and others do not is precisely the thing that
splits a network. The fallback has to be deleted.

One refinement worth carrying: the tool's authors were not wrong to think leniency is sometimes safe.
It is safe exactly where the bytes are not the identity — an ABI decoder that tolerates gaps is
survivable because calldata is hashed as received rather than
re-encoded.<Cite src="solidity-abi-spec" /> It is fatal here because an RLP structure's bytes *are*
what gets hashed into a header. Knowing which of the two situations you are in is the whole skill.
</Answer>
</Check>

## Why the strictness is load-bearing

Follow the chain of consequences once, slowly.

**Step 1 — the encoded bytes are what get hashed.** A block header is hashed as encoded bytes, and so
is every node of the trie that holds state.<Cite src="ethereum-org-rlp" /> A beacon object's root is
derived from its typed layout instead, but the principle is the
same.<Cite src="ssz-specs-merkleization" />

**Step 2 — the hash is the identity.** Blocks refer to parents by hash. State is committed to by a
root. Validators sign roots, not objects.

**Step 3 — a second encoding is a second identity.** If a value can be written two ways, it has two
hashes. Two participants doing everything correctly, each producing a legal encoding, would commit to
different roots for identical data.

**Step 4 — disagreement on validity is a fork.** One client accepts a block; another rejects it. They
are now building on different heads. No cryptography failed and no rule was broken by anyone; the
specification simply admitted two answers.

A fifth step runs through signatures rather than blocks, and it is the one most likely to reach your
own code. A legacy transaction's signature covers a nine-element RLP list that is never transmitted,
rebuilt from the fields that are.<Cite src="eip-155" /> A type-2 signature covers
`keccak256(0x02 || rlp([...]))` over a list assembled the same way.<Cite src="eip-1559" /> Signer and
verifier construct those bytes independently and must arrive at the same ones. A decoder that admits
a second encoding of some field hands the verifier a different digest, which recovers a different
address — not an error, but a valid signature by somebody else.

<Misconception
  belief="Serialization is a boring implementation detail — as long as it round-trips, the format is fine."
  reality="In a system where encoded bytes are hashed and the hash is the shared identity, the encoding rules are consensus rules. A decoder that accepts a non-canonical form has changed what the chain is, for whoever runs it."
  why="In ordinary software, round-tripping really is the whole requirement, and generous parsers are a virtue — Postel's law. That advice inverts when multiple independent implementations must agree bit-for-bit on the result, because every accepted variant is a way for two correct-looking programs to reach different answers."
/>

<Aside kind="note">
This is why "be liberal in what you accept" is dangerous advice in a consensus system, and why
strictness is worth the developer friction of a decoder that refuses your hand-written test vector.
The friction is the mechanism working.
</Aside>

## The same shape in your own systems

You have almost certainly built something with this property and not noticed. Any signature over a
concatenation of fields, any cache or idempotency key assembled from parts, any digest of a JSON
document — each asks the same two questions: can two different inputs produce the same bytes, and can
one input produce two different byte strings?

The first direction is the packed-encoding collision from earlier in this module. The second is this
lesson: a value with more than one encoding has more than one identity, so a signature over one
spelling does not cover the other, and a cache keyed on one spelling misses the other.

JSON is the everyday offender, because key order, whitespace and number formatting are all free
variables. Hashing a JSON document without pinning those three is this lesson's mistake written in
another language, and the repair is the one EIP-712 chose: a fixed field order, a fixed width for
every field, and the schema hashed alongside the data.<Cite src="eip-712" />

## Where this pays off

The Merkle Patricia Trie is the immediate beneficiary: its nodes are RLP, its root is the hash of
those bytes, and the structure only functions as a commitment because the encoding underneath it is
canonical.<Cite src="ethereum-org-rlp" /> The trie's own structural rules — no branch node with
exactly one non-empty child, extension nodes required rather than optional — are the same idea one
layer up: rules whose only purpose is to give one set of key–value pairs one root.

That is also what makes a state root comparable across independent client implementations, and why
client diversity is a safety property rather than a nice-to-have: several teams implementing one
specification only helps if the specification admits one answer.

More broadly, this is the first place the curriculum states a principle that recurs everywhere in
protocol work: determinism is a security property, not tidiness. Every remaining lesson about
consensus assumes it, and the first question to ask of any new format — including the ones your own
team invents — is which of the two halves it actually has.
