The ABI is a calling convention: it describes how one contract talks to another. It is not how a
transaction is stored, how a block header is hashed, or how two nodes exchange data.

That job belongs to RLP — Recursive Length Prefix — and it is small enough to hold in your head. The
whole format has two types.

## Two types, and nothing else

RLP encodes a **byte string**, or a **list of items where each item is itself RLP
encoded**.<Cite src="ethereum-org-rlp" /><Cite src="yellow-paper" />

That is the entire type system. There is no boolean, no map, no field name, no version tag. A
decoder that reads RLP bytes recovers a tree of byte strings and learns nothing about what any of
them mean. Meaning comes from the schema the reader already holds.

The design goal is narrow on purpose: RLP standardises the *structure* of data so that two nodes
agree byte-for-byte on what they are hashing, and delegates the encoding of specific data types —
strings, floats — to higher-order protocols.<Cite src="ethereum-org-rlp" />

There is exactly one exception, and it is worth stating precisely rather than filing under "two
types and nothing else". Positive integers are not delegated: they must be represented in big-endian
binary form with no leading zeroes, which makes the integer zero equivalent to the empty byte array,
and a decoded integer carrying leading zeroes must be treated as invalid by any higher-order
protocol using RLP.<Cite src="ethereum-org-rlp" /> One type rule, stated normatively, and the last
lesson in this module is about why that one is there.

## The five rules

Encoding a byte string:

| Input | Encoding |
|---|---|
| A single byte in the range `0x00`–`0x7f` | that byte, unchanged |
| 0 to 55 bytes | `0x80 + length`, then the bytes |
| More than 55 bytes | `0xb7 + (bytes needed for the length)`, then the length big-endian, then the bytes |

Encoding a list — encode every item, concatenate the results into a payload, then:

| Payload | Encoding |
|---|---|
| 0 to 55 bytes | `0xc0 + payload length`, then the payload |
| More than 55 bytes | `0xf7 + (bytes needed for the length)`, then the length big-endian, then the payload |

That is all of it.<Cite src="ethereum-rlp-reference" /> The first byte of any RLP item tells you
which of the five cases you are in, and therefore how many bytes of header to skip. Note the range
split that falls out: any first byte below `0x80` is a bare single byte, `0x80`–`0xbf` is a string,
and `0xc0` and above is a list. Both boundaries become load-bearing before this lesson ends.

### Real encoder output

```text
0x7f                    ->  0x7f                    single byte below 0x80, encodes as itself
0x80                    ->  0x8180                  one byte, but not below 0x80, so it needs a prefix
(empty string)          ->  0x80                    length 0, prefix only
0x646f67   "dog"        ->  0x83646f67              0x80 + 3
["cat", "dog"]          ->  0xc88363617483646f67    payload is 8 bytes: 0xc0 + 8
(empty list)            ->  0xc0
55 bytes of 0x61        ->  0xb7 6161…              still the short form: 0x80 + 55
56 bytes of 0x61        ->  0xb8 38 6161…           long form: one length byte, holding 0x38 = 56
```

The `0x7f` case is the one that surprises people. A one-byte value below `0x80` is its own encoding —
no prefix at all — because a prefix would be pure overhead on the most common item in the format.
The consequence is that `0x80` itself, one byte above the line, costs two bytes to encode.

### Nesting is free

Lists contain items; items can be lists. The classic example is three nested empty structures:

```text
[ [], [[]], [ [], [[]] ] ]   ->   0xc7 c0 c1c0 c3c0c1c0
```

Read it left to right: `0xc7` is a list with a 7-byte payload. Inside, `0xc0` is the empty list,
`0xc1c0` is a one-byte-payload list containing the empty list, and `0xc3c0c1c0` is a three-byte-payload
list containing the previous two. Recursion costs one byte per level of depth.

## Numbers, booleans, and the schema that decides

RLP has no integer type in the sense of a tag, so a number is encoded as its big-endian bytes with
leading zeros stripped, and then encoded as a byte string.<Cite src="ethereum-rlp-reference" />

This produces a distinction that catches people out exactly once:

```text
the integer 0        ->  0x80    the empty byte string
the byte string 0x00 ->  0x00    a one-byte string that happens to be zero
the integer 1024     ->  0x820400
```

Zero as a number is *nothing* — an empty string. Zero as a byte is a byte. Both are valid RLP and
they are different encodings, because they are different values. It is the schema that decides which
one a given field is.

Booleans make the point harder to argue with. The reference encoder maps `True` to the single byte
`0x01` and `False` to the empty byte string — that is, to `0x80` — which is exactly what it produces
for the integers one and zero.<Cite src="ethereum-rlp-reference" /> Two Python types, four
conceptual values, two byte strings. Nothing in the output distinguishes the boolean from the
integer, and no decoder can, because the distinction was never encoded.

## The surprising rule is a security mechanism

Return to the `0x00`–`0x7f` case, the one that looked like a byte-saving quirk. It is the foundation
of the way Ethereum keeps signed messages from being replayed as transactions.

EIP-191 specifies that signed data is framed as `0x19 <version byte> <version-specific data> <data
to sign>`, and gives the reason for the leading byte outright: **the initial `0x19` byte is intended
to ensure that the signed data is not valid RLP**. Because a single byte in the range `0x00`–`0x7f`
is its own RLP encoding, any such payload can only ever be a one-byte RLP item followed by something
else — never one RLP structure — so an EIP-191 signed message can never be an Ethereum
transaction.<Cite src="eip-191" />

Read that as an engineering pattern rather than a fact about one EIP. A prefix is only a safe
domain separator if something *outside* the convention guarantees it cannot appear in the data being
separated. Here the guarantee comes from RLP's grammar: every legacy transaction is a list, so it
begins with a byte of `0xc0` or above,<Cite src="eip-2718" /> and no framing that starts below
`0x80` can be mistaken for one. The quirk you were tempted to skim is the whole proof.

## What is actually RLP

On the execution layer: transactions, receipts, block headers, the nodes of the Merkle Patricia Trie
that holds state, and the devp2p messages nodes exchange.<Cite src="ethereum-org-rlp" />

A legacy transaction is exactly `rlp([nonce, gasPrice, gasLimit, to, value, data, v, r, s])` — nine
byte strings in a list. A legacy receipt is
`rlp([status, cumulativeGasUsed, logsBloom, logs])`.<Cite src="eip-2718" /> The transaction and
receipt tries are keyed by `rlp(Index)` — the transaction's position in the block, RLP-encoded —
rather than by a hash.<Cite src="eip-2718" />

A block header is likewise an RLP list of header fields, but the field list has grown across forks
and the count depends on which fork you are encoding for. If you are going to hash a header yourself,
read the header definition out of the execution specs for that fork rather than any published list.

### Worked example: the nine fields you send are not the nine fields you sign

Take the legacy transaction above and ask what `r` and `s` are a signature *over*. The answer is not
"the other six fields", and has not been since 2016.

**Subgoal: notice that the signature cannot cover itself.** `v`, `r` and `s` are three of the nine
list items, so whatever gets hashed for signing must be a different structure — the six
pre-signature fields, at most.

**Subgoal: read what EIP-155 substituted for those six.** Instead of hashing six RLP-encoded
elements `(nonce, gasprice, startgas, to, value, data)`, a conforming signer hashes **nine**:
`(nonce, gasprice, startgas, to, value, data, chainid, 0, 0)`.<Cite src="eip-155" /> Three extra
items, none of which is transmitted.

**Subgoal: find where the chain id went.** It is not sent as a field either. It is folded into `v`,
which must be set to `{0,1} + CHAIN_ID * 2 + 35`, where the `{0,1}` is the parity of the signature's
curve point.<Cite src="eip-155" /> A verifier reads `v`, recovers the chain id, rebuilds the
nine-element signing list, and checks the signature against that.

**Subgoal: name the property this buys.** A transaction signed for one chain id cannot be replayed
on another, because the digest the signature covers includes the chain id even though the wire format
has no field for it.<Cite src="eip-155" />

**Subgoal: extract the general shape.** Two RLP structures, one transmitted and one only ever
constructed in memory, and the security of the scheme lives entirely in the second. Which means both
sides must build that second structure byte-identically — a requirement with no error path, since a
mismatch produces a signature that verifies against a different address rather than an exception.

<Aside kind="warn">
Modern transactions are **not** plain RLP. EIP-2718 wraps them in an envelope: a transaction is
`TransactionType || TransactionPayload`, where the type is a single byte from 0 to `0x7f` and the
payload is an opaque byte array whose interpretation depends on the
type.<Cite src="eip-2718" /> The upper bound is chosen so that a type byte can never be confused
with a legacy transaction, which is an RLP list and therefore always begins with a byte of `0xc0` or
higher.<Cite src="eip-2718" />

So `cast from-rlp` on a raw modern transaction fails, and correctly. Strip the leading type byte
first; the payload behind it is usually itself an RLP list, defined by the EIP that introduced that
type.
</Aside>

The type-2 transaction is the concrete case. Its payload is
`rlp([chain_id, nonce, max_priority_fee_per_gas, max_fee_per_gas, gas_limit, destination, amount,
data, access_list, signature_y_parity, signature_r, signature_s])`, and its signature covers
`keccak256(0x02 || rlp([...]))` over the same list minus the three signature
items.<Cite src="eip-1559" /> Note the `0x02` inside the hash: EIP-2718 recommends that every future
type include the type byte as the first byte of the signed data, so that a signature for one
transaction type cannot be reused as a signature for another.<Cite src="eip-2718" /> That is the
same domain-separation move as EIP-191's `0x19`, applied to a different namespace.

## Why it looks the way it does

Three design choices are worth naming, because each is the opposite of what a general-purpose format
would do.

**No type information.** Self-describing formats let a reader parse data it has never seen. RLP
refuses, which costs flexibility and buys the smallest possible encoding of a known-shape structure —
one byte of overhead for anything up to 55 bytes.

**Length-prefixed, never delimited.** There is no terminator byte and no escaping. A reader always
knows the exact byte count before it reads content, so nested structures can be skipped without
parsing them, and no byte value is ever special inside a payload. It is the same property that made
ABI encoding decodable, arrived at from a different direction.

**The envelope is deliberately not RLP.** EIP-2718's rationale states why the payload is an opaque
byte array rather than an RLP list: so that future transaction payloads can use a different encoding
format entirely — it names SSZ, LEB128 and fixed-width layouts as
possibilities.<Cite src="eip-2718" /> The format that has encoded every execution-layer object since
2015 has a documented exit hatch built into its own successor, and the next lesson is about what is
waiting on the other side of it.

## Where this pays off

Hand-decoding a raw transaction is now a tractable exercise rather than a wall of hex — strip the
type byte, split the RLP list, apply the schema for that transaction type, and remember that the
signing structure is a different list from the transmitted one.<Cite src="eip-155" /><Cite src="eip-1559" />

RLP is also the encoding of every node in the Merkle Patricia Trie, so the way state roots are
computed is built directly on the rules above, and the transaction and receipt tries are keyed by an
RLP-encoded index rather than by a hash.<Cite src="eip-2718" /> When state and tries come up, this
lesson is the layer underneath them.

And the two boundaries you were asked to notice turn out to be load-bearing outside the format that
defines them. `0xc0` bounds the transaction type byte, because every legacy transaction is a list and
so begins above it.<Cite src="eip-2718" /> `0x80` is what makes EIP-191 framing unforgeable as a
transaction, because a byte below it is a complete RLP item on its own.<Cite src="eip-191" /> Neither
mechanism has a fallback if a decoder is sloppy about those ranges — which is the subject of the last
lesson in this module.
