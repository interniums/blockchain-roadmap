A peer hands you a byte string and says it is a trie node. You have never seen this trie, you have
no schema, and there is no type tag in front of it. **How do you know what you are holding?**

This is not a contrived question. It is the exact situation a proof verifier is in: it gets a list
of opaque byte strings and has to walk them.<Cite src="eip-1186" /> Whatever answers it must be
carried inside the encoding itself, and the answer turns out to be small enough to memorise.

## Four kinds, and the count gives most of it away

Every node in a Merkle Patricia Trie is exactly one of four things.<Cite src="ethereum-org-mpt" /><Cite src="yellow-paper" />

| Kind | Shape | What it means |
|---|---|---|
| NULL | the empty byte string | nothing here |
| Branch | a 17-item list | sixteen child slots plus one value slot |
| Extension | a 2-item list | a shared path fragment and a child reference |
| Leaf | a 2-item list | the rest of a key and its value |

There is no fifth kind. No optional variant, no version byte, no extensibility hook. That closedness
is the point: a decoder can classify almost everything by counting.

RLP-decode the bytes.<Cite src="ethereum-org-mpt" /> If you get an empty string, it is NULL. If you
get a list of 17 items, it is a branch — nothing else in the structure has 17 items, so the count
alone settles it. If you get a list of 2 items, it is either an extension or a leaf, and one nibble
at the front of the first item tells you which.

That last case is the whole of lesson 4 and lesson 5. What matters right now is the shape of the
answer: **the entire structure is decidable from the RLP shape plus one nibble.** No external
schema, no context from the parent, no negotiation.

<Aside kind="note">
The count of four is a teaching count, and the specification counts differently in a way worth
seeing. Its type union is `InternalNode = LeafNode | ExtensionNode | BranchNode` — described as *any
of the three node types making up a Merkle Patricia Trie* — and absence is modelled not as a fourth
dataclass but as `Optional[InternalNode]` being `None`, encoded as
`b""`.<Cite src="execution-specs-mpt" /> Three types that carry data, plus one representation of
nothing. Both counts are right about the same structure; the specification's version is the one that
tells you NULL has no fields to get wrong.
</Aside>

<Aside kind="note">
go-ethereum makes the family resemblance explicit in its type names: branches are `fullNode`,
while extensions and leaves share a single type called `shortNode`.<Cite src="geth-trie-package" />
Production code does not treat them as two structures, because on the wire they are not two
structures. Its in-memory representation adds two kinds that are not wire node types at all —
`hashNode`, a not-yet-loaded child standing in for a subtree, and `valueNode`, a resolved value — and
its proof verifier switches on exactly those.<Cite src="geth-trie-proof" /> Four types in the wire
format, four different types in one client's memory, and the two sets do not line up. Read the file
you are in.
</Aside>

## The empty node, and the constant it produces

NULL is represented as the empty byte string. The executable specification encodes an absent node as
`b""` and nothing else.<Cite src="execution-specs-mpt" /> RLP encodes the empty string as the single
byte `0x80`.<Cite src="yellow-paper" />

Follow that through. An empty trie has no nodes, so its root node is the empty string, so its root
hash is `keccak256` of the RLP encoding of the empty byte string — the hash of one byte. The
executable spec pins this as the named constant `EMPTY_TRIE_ROOT`, and documents it as exactly that:
the keccak256 hash of the RLP encoding of an empty byte string, used in block headers when the
corresponding trie has no entries, regardless of whether that trie would have been
secured.<Cite src="execution-specs-mpt" />

The value is `0x56e81f171bcc55a6ff8345e692c0f86e5b48e01b996cadc001622fb5e363b421`. It is worth
knowing how firmly that is pinned, because it is the sort of constant that circulates without
provenance: it is a literal in the specification file,<Cite src="execution-specs-mpt" /> and it
appears independently as the `storageHash` of a storage-free account in EIP-1186's own worked
example response.<Cite src="eip-1186" /> Two primary sources, and one line of local code — `keccak256`
of the single byte `0x80` — reproduces it.

<Aside kind="warn">
**Derive it anyway.** A 32-byte hex literal is the easiest thing in this domain to transcribe
wrongly, and the same constant circulates in write-ups whose provenance you cannot check. It is two
lines of code from a keccak library and one byte of input. Put the derivation in a test and let the
test be the thing you trust; the literal above is then a cross-check rather than an input.
</Aside>

You will meet this value constantly once you know it is there. Every account that has never written
a storage slot carries it as its `storageRoot`,<Cite src="eip-1186" /> and so does every account that
has cleared its last remaining slot — the specification deletes an emptied storage trie outright, so
the account falls back to the same constant.<Cite src="execution-specs-state-mpt" /> Every block whose
trie of some kind is empty carries it in that header field. It is one of a handful of hex constants
worth *recognising*, which is not the same as worth memorising.

It has a sibling worth recognising at the same time. An account with no code carries
`keccak256` of the empty byte string as its `codeHash` — the specification names it
`EMPTY_CODE_HASH`<Cite src="execution-specs-state" /> and EIP-1186 spells the value out for an
account without code.<Cite src="eip-1186" /> Same idea, one layer up: the empty thing hashes to a
perfectly ordinary-looking digest rather than to zeros.

/>

There is a second reason zeros would be wrong. The root is supposed to be a hash of the trie's
contents. If emptiness were special-cased to zero, then "hash of contents" would have an exception
in it, and every piece of code that verifies a root would need to know about the exception. Deriving
the empty root by the normal rule keeps the rule exceptionless.

## How absence is written down

One detail that looks like an implementation choice and is not: what goes in a branch slot with no
child under it.

The answer is the empty byte string — the same representation as a NULL node. The specification's
branch node documents each of its sixteen entries as *the encoded form of another internal node, or
`b""` if no key descends through that nibble*, and its seventeenth item as *the value for a key that
terminates at this node, or `b""` if no such key exists*.<Cite src="execution-specs-mpt" /> Not a zero
hash, not a null marker, not a shorter list. Every branch node is 17 items whether it has one child
or sixteen, and the unused slots are `0x80` each.<Cite src="yellow-paper" />

That has a size consequence you can see. A branch with sixteen hash children carries sixteen 33-byte
references; a branch with two children carries two references and fourteen single bytes. Both are
17-item lists, and lesson 5 shows how to read which is which straight off the RLP header.

It also removes an ambiguity. If empty slots were omitted, a decoder would have to be told which
nibbles the remaining children correspond to, and that mapping would need its own encoding — one
more thing two implementations could do differently. Fixed positions cost bytes and buy the property
the whole structure exists for.

There is a consequence of using `b""` for absence that is easy to trip over when you build a trie
rather than read one: **the empty string is reserved and cannot be a value.** The specification
asserts outright that an encoded value is never `b""` before the trie is
built.<Cite src="execution-specs-mpt" /> If a stored value could encode to the empty string, a branch
slot holding it would be indistinguishable from a slot holding nothing, and the structure would stop
being decodable from shape alone. The reservation is what keeps the previous section's rule
exceptionless.

## Why exactly these four

Two of the four kinds carry data you asked for; two of them exist to keep the structure honest.

The **leaf** is the obvious one. A key's walk has to end somewhere, and where it ends you want the
value. The specification's leaf holds *nibbles of the key not yet consumed by ancestor nodes*, which
is the phrase to keep — a leaf stores the remainder, never the whole
key.<Cite src="execution-specs-mpt" />

The **branch** is the fan-out point: sixteen slots, one per possible next nibble of the key.<Cite src="ethereum-org-mpt" />
Lesson 3 explains why sixteen. Its seventeenth item is a value, for the case where a key terminates
at exactly this node rather than continuing into a child.

The **extension** exists because without it the structure would be unusably tall. Keys in the state
trie are 64 nibbles long,<Cite src="ethereum-org-mpt" /> and after the first few levels there is
typically only one key left down a given branch — which would mean a long chain of branch nodes each
having a single non-empty slot and sixteen empty ones. The extension collapses that entire run into
one node holding the shared fragment and a single child reference.<Cite src="execution-specs-mpt" />
That collapse is not an option a builder may decline: go-ethereum's own proof code records, in
passing, that a `fullNode` with only one child *is disallowed*.<Cite src="geth-trie-proof" />

And **NULL** is what an unused branch slot holds, and what an empty trie is.

<Check type="spot-bug" concept="mpt-four-node-types">
You are writing a proof verifier. Your node classifier looks like this:

```python
def classify(raw):
    decoded = rlp.decode(raw)
    if decoded == b"":
        return "null"
    if len(decoded) == 17:
        return "branch"
    if len(decoded) == 2:
        return "leaf"          # 2 items means a leaf
    raise ValueError("not a trie node")
```

It passes every test you wrote. It will still let an attacker fool your verifier. What is wrong, and
what is the consequence?

<Answer>
**A 2-item node is not necessarily a leaf.** It is a leaf *or* an extension, and the classifier has
no way to tell — it never looks at the flag nibble at the front of item 0.

The consequence is worse than a mislabel. The type determines how you read item 1. In a leaf, item 1
is **the value**. In an extension, item 1 is **a reference to a child
node**.<Cite src="execution-specs-mpt" /> Treat an extension as a leaf and you will return a child
reference — a 32-byte hash — to your caller as though it were the stored value.

Now think about what that gives an attacker. They want you to believe an account holds some
particular 32 bytes. They do not need to break keccak256; they need to find a place in a real,
honestly-constructed trie where an extension node sits at the point your verifier stops walking, and
hand you a proof that terminates there. Your verifier hashes every node correctly, matches every
reference correctly, and returns an attacker-chosen value.

Two smaller faults in the same six lines, both of which matter once the input is hostile rather than
your own encoder's output:

*It accepts any 2-item list.* Item 0 has to hex-prefix-decode to a legal flag — only four of the
sixteen nibble values are legal — and a classifier that never reads it cannot reject the other
twelve.<Cite src="execution-specs-mpt" />

*It treats "is this a trie node" as a local question.* Even a perfectly classified node means nothing
until it is checked against the reference its parent held. Classification tells you how to read
bytes; it never tells you the bytes belong in this trie.

The fix for the headline bug is one line — read the first nibble of item 0 and branch on it — and it
is the reason lesson 4 spends its whole length on a single nibble.
</Answer>
</Check>

## Where this pays off

You now have the vocabulary the rest of the module is written in, and one habit worth keeping: when
you meet a trie node anywhere — in an `eth_getProof` response,<Cite src="eip-1186" /> in a client's
database, in a test fixture — the first two questions are always *how many items* and *what is the
first nibble*.

The four kinds are also the yardstick for the successor design. When lesson 10 gets to the binary
tree proposed in EIP-7864, the first thing worth noticing is that it also defines four node
kinds<Cite src="eip-7864" /> — different ones — and that every difference is an argument about what
made the MPT expensive to prove.
