Two clients. Different languages, different teams, different databases, no communication between
them. Both execute the same block and both must produce the same 32 bytes — not a compatible value,
not a value that verifies, the *same* 32 bytes, or the network splits.

Nothing about a tree data structure makes that automatic. A red-black tree's shape depends on
insertion order. A hash map's iteration order depends on its seed. Most structures you have built
are free to represent the same contents several ways, and it never mattered because you only ever
compared contents.

Here, structure *is* contents, because the structure gets hashed. So the question worth asking is:
where did all the freedom go?

## The audit

Walk the construction and check every point where an implementer might reasonably have made a
choice.

**Which node type goes here?** Determined by the data. The specification's build procedure has four
cases and they are mutually exclusive: no keys gives NULL, one key gives a leaf, a shared non-empty
prefix gives an extension, and anything else gives a branch.<Cite src="execution-specs-mpt" /> No
tie to break.

**Should I bother compressing this run of nibbles?** Not optional. Where a prefix is shared, an
extension node is what the procedure produces, so an implementation that emits a chain of
single-child branch nodes instead is producing different bytes and a different root — lesson 5. The
invariant has a name in client code: a branch with a single child is
disallowed.<Cite src="geth-trie-proof" />

**How do I encode this path fragment?** One way. Hex-prefix encoding gives exactly one byte string
per (path, is-leaf) pair, with the parity handled by a rule rather than a
preference<Cite src="execution-specs-mpt" /> — lesson 4.

**Hash this child or embed it?** Fixed at 32 bytes of RLP.<Cite src="ethereum-org-mpt" /><Cite src="execution-specs-mpt" />
Not a tuning parameter, not a per-client heuristic — lesson 6.

**How do I serialise the node?** RLP, which is canonical: one encoding per value, with the
short-form and long-form boundaries pinned by the specification.<Cite src="yellow-paper" />

**What about a key whose value is zero — is it in the trie or not?** Answered too, and this one is
easy to miss. The specification's trie carries a `default` value representing absence, and storing
that default at a key is defined as equivalent to omitting the key: the underlying structure
represents missing keys by leaving them out entirely.<Cite src="execution-specs-mpt" /> So "written
then zeroed" and "never written" are the same trie and the same root. There is no ghost entry.

**What about an account whose entire storage is gone?** Also answered, one level up. When a storage
trie's last entry is removed, the state object deletes the trie rather than keeping an empty one, and
the account's storage root falls back to the empty-trie constant.<Cite src="execution-specs-state-mpt" />
An emptied map and a map that never existed are the same 32 bytes.

Seven places where an ordinary data structure would offer a choice, seven places where this one does
not. That is the whole argument.

## The consequence

**A root hash is a function of the key-value set alone.**

Not of insertion order. Not of deletion history. Not of which client, which version, which
database, or which language. Feed two correct implementations the same set of pairs and they must
produce byte-identical nodes at every position, and therefore the same root.

<Misconception
  belief="Two tries holding the same data could legitimately differ in shape, the way two balanced trees can."
  reality="They cannot. The shape is fully determined by the contents, which is exactly what lets the root serve as a consensus object."
  why="Almost every tree structure engineers work with does depend on insertion order — that is the normal case, so it reads as the general case. Here it would make the root meaningless, so the design removed it."
/>

<Aside kind="note">
Worth separating two ideas that sound alike. *Canonical serialization* means one encoding per value
— RLP's job.<Cite src="yellow-paper" /> *Canonical structure* means one shape per data set — the
trie's job.<Cite src="execution-specs-mpt" /> You need both. A canonical encoding of a non-canonical
structure still gives you two valid roots for one set of facts.
</Aside>

## The map, the commitment, and the database

Lesson 1 planted the distinction; this is where it earns its place, because it is what stops
"canonical" from being over-read.

The executable specification now separates the two physically. `state.py` defines the state model and
says of itself that it is **commitment-agnostic: it defines what state *is*, not how it is committed
to**, exporting a `PreState` protocol that an in-memory dictionary, an on-disk database or a witness
may all implement.<Cite src="execution-specs-state" /> The Merkle Patricia Trie lives in a different
file, `state_mpt.py`, which describes itself as the implementation used on Ethereum mainnet — where
accounts and storage live in tries and the state root is the MPT commitment — and names other
commitment schemes as separate implementations of the same protocol.<Cite src="execution-specs-state-mpt" />

Even inside that implementation, the trie is not a storage layout. The specification's `Trie` holds
its contents in a plain dictionary and builds the Merkle Patricia structure **only when `root` is
called**, with a comment saying so: storing intermediate nodes is not needed for the spec's
outputs.<Cite src="execution-specs-mpt" /> The nodes you spent five lessons decoding are produced on
demand, by a pure function of the dictionary.

That is the cleanest available statement of what canonicity actually asserts. It is a claim about a
function — set of pairs to 32 bytes — and about nothing else. Two clients must agree on the output.
They are free to disagree about every representation on either side of it.

## The state root

Now the payoff. Each block header carries a `stateRoot`: the root of the world-state trie **after**
that block's transactions have executed.<Cite src="ethereum-org-mpt" /><Cite src="yellow-paper" />

Thirty-two bytes committing to every account and every storage slot in existence.

Two things that buys, and they are different things.

**Verification without the state.** A party holding only the header can be handed a claim about any
account or slot, plus a short proof, and check it. They do not need the state, or a copy of the
chain, or trust in whoever gave them the proof. That is lesson 9.

**Agreement.** Two clients that executed the same block identically will have identical state and
therefore identical roots. Two that did not, will not. The state root is where a divergence in
execution becomes a divergence in a single comparable value.

The specification models exactly that shape: a root is computed by taking the pre-state, copying its
tries, applying a whole block's diff, and hashing — the pre-state itself is never
mutated.<Cite src="execution-specs-state-mpt" /> A state root is a snapshot function, not an
accumulator.

<Misconception
  belief="The state root commits to the changes the block made."
  reality="It commits to the entire world state after the block — every account, whether or not the block touched it. There is no changes-only root in the header."
  why="Headers are small and blocks are described as containing changes, so a small root sounds like it must summarise a small thing. It does not: a 32-byte hash commits to an arbitrarily large structure, which is the point of hashing."
/>

The header carries other roots built the same way. The transactions and receipts tries produce
`transactionsRoot` and `receiptsRoot`,<Cite src="ethereum-org-mpt" /> and the current fork's
specification also computes a withdrawals root and checks it against the header before accepting a
block.<Cite src="execution-specs-osaka-fork" /> Same machinery, different key scheme — lesson 7.

## What canonicity does not give you

Four limits, because "the root is determined" is easy to over-read.

**It does not make the database canonical.** Two clients must agree on the nodes and the root. They
are free to disagree about everything below that: how nodes are laid out on disk, whether historical
nodes are pruned, whether the trie is stored path-indexed or hash-indexed, what is cached. The
specification's own architecture licenses this explicitly, by defining state through a protocol that
several providers may implement.<Cite src="execution-specs-state" /> Those choices are where client
implementations differ most, and none of them touch consensus.

**It does not commit to everything a client holds.** The root commits to accounts' **code hashes,
never to code contents** — the specification says so in as many words, and draws the consequence that
account diffs alone determine the root.<Cite src="execution-specs-state-mpt" /> Bytecode, preimage
tables and receipts of past execution all sit outside. Lesson 10 is partly about a proposal to move
one of those inside.

**It does not make execution canonical.** The root is a function of the resulting key-value set. What
produced that set — transaction ordering, gas accounting, every EVM rule — is a separate agreement,
and a much larger one. Reorder two transactions that touch the same account and you get a different
*set*, and therefore legitimately a different root. Canonicity says: given the same set, the same
root. It says nothing about how you arrived at the set.

**It does not timestamp anything.** A root commits to a state, not to a moment. The same state
reached twice would produce the same root twice, and nothing in the value says which block it came
from. That is why lesson 9's proofs are always proofs *at a block* — the binding between a root and
a position in the chain lives in the header, not in the trie.

<Aside kind="warn">
There is one place where ordering genuinely is part of the rules, and it is worth knowing because it
looks like a counterexample and is not. The specification's block diff carries a `storage_clears`
set — addresses whose pre-existing storage was wiped during the block by a pre-EIP-6780
`SELFDESTRUCT` — and requires those storage tries to be dropped **before** the block's storage writes
are applied, so any post-wipe write starts from empty storage.<Cite src="execution-specs-state-mpt" /><Cite src="eip-6780" />
That is not the trie being order-sensitive. It is the *set* being defined by a rule about how the
block's effects compose. Get the composition wrong and you compute the correct root of the wrong set.
</Aside>

## What a mismatch tells you

Because the root is a pure function of the data, a root mismatch is one of the most precise signals
in the system. It says: *the key-value set you built differs from the one the reference built, or
the structure over it does.* It does not say where. But it says the difference is real and
reproducible, which is more than most bugs offer.

The technique that follows is bisection on the key set, not on the code.

**Subgoal 1 — get a failing set.** Any set of keys where your root differs from a reference. The
purpose of this step is to convert an intermittent report into a deterministic input; until it
reproduces on demand, nothing below works.

**Subgoal 2 — shrink it.** Remove keys and re-test, keeping any removal that preserves the mismatch.
The purpose is to strip away every key that is not load-bearing, so that what remains is small enough
to hold in your head. Two or three keys is a typical floor.

**Subgoal 3 — encode by hand.** The purpose here is to obtain a second opinion that shares no code
with the first. At that size you can write out the nibble paths, decide the node types yourself using
the four-case procedure,<Cite src="execution-specs-mpt" /> and hex-prefix-encode the fragments on
paper.

**Subgoal 4 — diff at the node level.** The purpose is to localise: compare your nodes with the
reference's, item by item, top down. The first node that differs bounds the fault, and everything
above it is exonerated.

That fourth step is where the diagnosis appears, and it is nearly always one of the same short list:
a dropped padding nibble, an omitted extension node, or an unconditional hash where a child should
have been inlined. All three are lessons 4 through 6, and all three produce exactly this signature —
a root that is right on some inputs and wrong on others.

Two implementations build a storage trie from the same three slots.

Implementation A inserts them in the order they appear in the source, and never deletes.
Implementation B inserts them in reverse order, then additionally writes slot `0x07` with the value
`0`, then leaves it there.

Do their roots match? Answer for each difference separately.

<Answer>
**Yes, the roots match. Both differences are non-differences by construction.**

*Insertion order.* The build procedure looks only at the set of keys present and their remaining
nibbles at each level.<Cite src="execution-specs-mpt" /> There is no rebalancing step, no rotation,
nothing that carries a trace of the order things arrived. Reverse the order and every node comes out
identical. The specification makes this structurally obvious rather than merely true: the trie holds
a plain dictionary and only patricializes it when the root is asked
for,<Cite src="execution-specs-mpt" /> so there is no incremental structure in which an order could
be recorded.

*The zero write.* Storing the default value at a key is defined as equivalent to omitting that
key,<Cite src="execution-specs-mpt" /> and a storage trie's default is the 256-bit
zero.<Cite src="execution-specs-state-mpt" /> Slot `0x07` set to zero is not a key holding zero — it
is a key that is not in the trie. B's set is the same set as A's.

Both answers are the same answer wearing different clothes: the root is a function of the key-value
set, and neither operation changed the set.

The zero case is worth dwelling on because it has a consequence you will meet in the next lesson. At
the RPC layer, an unset slot and a slot holding zero both read back as zero — indistinguishable. In
the trie they are not merely indistinguishable, they are *the same thing*: there is no entry either
way. Which means proving "this slot is zero" and proving "this slot was never written" are the same
proof, and it is an exclusion proof.

One extension of the same question, since it is the version that shows up in practice: if B's three
slots had been the *only* entries and B then zeroed all three, B would not hold an empty storage trie
— it would hold no storage trie at all, and its account's storage root would be the empty-trie
constant.<Cite src="execution-specs-state-mpt" /> A contract that clears itself out is byte-identical
in the state root to one that never wrote anything.
</Answer>
</Check>

## Where this pays off

Canonicity is the property that makes the next lesson possible. A proof works by recomputing hashes
and comparing against a root — and comparing is only meaningful if there was exactly one correct
answer to compare against.

It is also why a state root mismatch is the canonical symptom of a consensus bug in client
development, and why the first question after one is never "which client is right" but "what is the
smallest input on which they disagree".

And it is the frame to keep for lesson 10. What a successor design replaces is the *commitment* —
the function from the map to 32 bytes — while the map itself, address to account and slot to value,
is the part the specification has now deliberately factored out of the
question.<Cite src="execution-specs-state" />
