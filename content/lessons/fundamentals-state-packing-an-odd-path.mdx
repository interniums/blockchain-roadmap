An extension node holds a run of nibbles that every key below it shares. That run can be five
nibbles long. RLP stores byte strings. **Five nibbles is two and a half bytes.**

You could shrug at this — pad it and move on — except that whatever you do here is hashed into the
root, so "pad it and move on" has to mean exactly the same thing in every client written by every
team in every language, forever. This lesson is about the rule they all follow, and about the one
place where a reasonable-looking implementation quietly disagrees with all of them.

## The ambiguity, stated precisely

Take the nibble sequence `[1]` and the nibble sequence `[0, 1]`. Pack each into bytes the obvious
way and both come out as the single byte `0x01`.<Cite src="ethereum-org-mpt" /> One path fragment is
one step long, the other is two, and the encoding has lost the difference.

That is fatal here. Path length is not decoration — it is how many nibbles of the key this node
consumes, and getting it wrong sends the walk to the wrong place.

There is a second thing the encoding has to carry. A 2-item node is either a leaf or an extension,
and the two are the same shape (lesson 2). Something has to say which, because it decides whether
item 1 is a value or a child reference.<Cite src="execution-specs-mpt" />

Two bits of information, then: **is this a leaf**, and **is the nibble count odd**. Hex-prefix
encoding carries both in a single nibble stuck on the front.

## The flag nibble

The first nibble of an encoded path is one of exactly four values.<Cite src="ethereum-org-mpt" />

| Flag | Bits | Node type | Path length |
|---|---|---|---|
| `0` | `0000` | extension | even |
| `1` | `0001` | extension | odd |
| `2` | `0010` | leaf | even |
| `3` | `0011` | leaf | odd |

Read the bits and the table stops needing to be memorised. The specification draws the nibble as a
four-bit field and says which bit is which: the lowest bit encodes the parity of the nibble-list
length, the next bit distinguishes leaf from extension, and the two highest bits are
unused.<Cite src="execution-specs-mpt" /> Which is to say:

## The padding nibble

The flag occupies one nibble. A path of even length added to one flag nibble gives an odd total,
which does not pack into whole bytes. So:

- **Even length** — insert a single zero nibble after the flag. Flag, zero, then the payload.
- **Odd length** — put the first real nibble in that position instead. Flag, first nibble, then the
  rest.

Either way the total nibble count is even and the packing is exact. The specification states the odd
case as the operative one: when the length is odd the first nibble is packed into the same byte as
the flag, *leaving an even number of remaining nibbles to pair off*.<Cite src="execution-specs-mpt" />
And notice the elegance of it: the same half-byte slot is either padding or data, and the flag you
already read tells the decoder which.

## The vectors

Four worked examples, from the canonical documentation.<Cite src="ethereum-org-mpt" /> Learn to read
these and the rule is yours; they are also the test set your implementation must reproduce byte for
byte.

```text
[1, 2, 3, 4, 5]              extension, 5 nibbles, odd    ->  11 23 45
[0, 1, 2, 3, 4, 5]           extension, 6 nibbles, even   ->  00 01 23 45
[0, f, 1, c, b, 8, T]        leaf,      6 nibbles, even   ->  20 0f 1c b8
[f, 1, c, b, 8, T]           leaf,      5 nibbles, odd    ->  3f 1c b8
```

`T` is the terminator marker. The documentation's reference implementation signals "this is a leaf"
by appending the sentinel value 16 to the nibble array and stripping it before
encoding;<Cite src="ethereum-org-mpt" /> the executable specification instead takes an explicit
`is_leaf` boolean argument.<Cite src="execution-specs-mpt" /> Same output, two calling conventions,
and it is worth knowing both exist because you will read code written in each style. go-ethereum uses
the sentinel: its in-memory hex encoding carries *an optional trailing terminator byte of value
`0x10`* — decimal 16 — and its encoder strips that byte and turns it into the flag
bit.<Cite src="geth-trie-encoding" />

There is a fifth vector nobody prints, and it is the one that breaks implementations first. **The
empty path.** Feed a zero-length nibble list to the specification's encoder and the even branch runs
with nothing to pair: the output is one byte, the flag alone — `0x00` for an extension and `0x20` for
a leaf.<Cite src="execution-specs-mpt" /> A leaf with an empty remaining path is exactly what you get
when the key is fully consumed by the time you arrive, and a one-byte path item is a perfectly legal
thing to meet in a proof. An encoder that assumes at least one nibble will index past the end of the
array instead.

### Working one through

Take `[f, 1, c, b, 8]` as a leaf — the fourth vector.

**Subgoal 1 — establish the two bits.** It is a leaf, so `isLeaf = 1`. It has five nibbles, so
`isOdd = 1`.

**Subgoal 2 — derive the flag.** `flag = 2 * 1 + 1 = 3`.

**Subgoal 3 — decide what shares the flag's byte.** The count is odd, so no padding: the first real
nibble `f` goes in the low half of the first byte. First byte is `0x3f`.

**Subgoal 4 — pack the remainder.** Four nibbles left, `1 c b 8`, which pair into `0x1c` and `0xb8`.

**Result:** `3f 1c b8`. Three bytes for a five-nibble leaf path.

Now change one thing — make it an extension instead. `flag = 2 * 0 + 1 = 1`, so the first byte is
`0x1f` and the rest is unchanged: `1f 1c b8`. **One nibble apart, and the two nodes mean completely
different things.**

### Working one backwards

Encoding is the trie builder's job. Reading a proof runs the other direction, so run the same vector
in reverse — this is the operation your verifier performs on every 2-item node it is handed.

Given the three bytes `00 01 23 45`, with no context at all:

**Subgoal 1 — recover the flag before anything else.** High nibble of byte 0 is `0`. That is the
whole type decision: bit 1 clear means extension, so **item 1 of this node is a child reference, not
a value**. Everything downstream of this node depends on getting this nibble right, and it is the
first four bits you read.

**Subgoal 2 — read the parity bit to know where the payload starts.** Bit 0 clear means even, so the
low nibble of byte 0 is padding. The payload begins at byte 1, not at the second nibble of byte 0.

**Subgoal 3 — check the padding rather than skipping it.** The flag claims even, so that padding
nibble must be zero. It is. A node where it is not was produced by no honest builder, and the
question of whether you reject it is yours to answer deliberately.

**Subgoal 4 — expand the remaining bytes.** `01 23 45` splits into `0 1 2 3 4 5`. Six nibbles, which
agrees with the parity bit. If it had disagreed — an odd count under an even flag — the node is
malformed, and that consistency check is free.

**Result:** an extension consuming `[0,1,2,3,4,5]`, whose second item is a child reference to follow.
Compare with `3f 1c b8`: high nibble `3` means leaf and odd, the low nibble `f` is *data*, the path is
`[f,1,c,b,8]`, and item 1 is a value to return rather than a pointer to chase.

<Aside kind="note">
go-ethereum's decoder does the same job with a piece of arithmetic worth recognising when you meet
it: it expands the compact bytes to nibbles, then chops `2 - base[0]&1` nibbles off the front — two
when the flag says even, one when it says odd.<Cite src="geth-trie-encoding" /> Same rule, expressed
as an offset rather than a branch.
</Aside>

## The implementation

The spec's version, which is short enough to read in full:<Cite src="execution-specs-mpt" />

```python
def nibble_list_to_compact(x, is_leaf):
    compact = bytearray()

    if len(x) % 2 == 0:                        # even: flag nibble, then a zero padding nibble
        compact.append(16 * (2 * is_leaf))
        for i in range(0, len(x), 2):
            compact.append(16 * x[i] + x[i + 1])
    else:                                      # odd: flag nibble shares its byte with x[0]
        compact.append(16 * ((2 * is_leaf) + 1) + x[0])
        for i in range(1, len(x), 2):
            compact.append(16 * x[i] + x[i + 1])

    return bytes(compact)
```

`16 * n` is "put nibble `n` in the high half of a byte". The even branch writes the flag with an
empty low half — that is the padding — and the odd branch writes the flag with `x[0]` in the low
half. Everything after that is pairing nibbles two at a time.

Now the same function in go-ethereum, because seeing one algorithm in two dialects is the fastest way
to stop reading either as magic:<Cite src="geth-trie-encoding" />

```go
func hexToCompact(hex []byte) []byte {
	terminator := byte(0)
	if hasTerm(hex) {
		terminator = 1
		hex = hex[:len(hex)-1]      // strip the 0x10 sentinel
	}
	buf := make([]byte, len(hex)/2+1)
	buf[0] = terminator << 5        // the flag byte
	if len(hex)&1 == 1 {
		buf[0] |= 1 << 4            // odd flag
		buf[0] |= hex[0]            // first nibble shares the first byte
		hex = hex[1:]
	}
	decodeNibbles(hex, buf[1:])
	return buf
}
```

Line them up. `terminator << 5` is `0x20` — the leaf flag in the high nibble — and the spec writes
the same value as `16 * (2 * is_leaf)`. `1 << 4` is `0x10`, the odd bit in the high nibble, and the
spec writes it as the `+ 1` inside `16 * (2*is_leaf + 1)`. `buf[0] |= hex[0]` is the spec's `+ x[0]`.
Two languages, one arithmetic, no room between them — which is exactly the property a consensus
encoding needs and the reason this lesson exists.

## Decoding, which is what a verifier actually does

```python
def compact_to_nibbles(encoded):
    flag = encoded[0] >> 4                       # high nibble of the first byte
    is_leaf = bool(flag & 2)                     # bit 1
    is_odd  = bool(flag & 1)                     # bit 0

    nibbles = []
    if is_odd:
        nibbles.append(encoded[0] & 0x0F)        # first real nibble shares byte 0
    # if even, the low nibble of byte 0 is padding and is discarded

    for byte in encoded[1:]:
        nibbles.append(byte >> 4)
        nibbles.append(byte & 0x0F)

    return is_leaf, nibbles
```

Three things to notice, because each is a place implementations go wrong.

**The padding nibble is discarded, not validated.** A strict decoder should check that it is zero
when the flag says even, and reject the node otherwise. A permissive one accepts a node that no
honest builder would produce — which is the sort of gap that lets two implementations disagree about
whether a proof is valid.

**Flags 4 through 15 are not legal.** The two high bits of the flag nibble are unused,<Cite src="execution-specs-mpt" />
so only 0, 1, 2 and 3 are meaningful. A decoder that masks with `& 3` instead of rejecting the node
will silently accept malformed input.

**The return value is two things, and both matter.** `is_leaf` decides whether item 1 of the node is
a value to return or a reference to keep walking. Dropping it on the floor is the bug from lesson 2.

<Aside kind="note">
**Two codecs, not one.** Hex-prefix encoding turns a nibble list into a byte string. RLP then
encodes that byte string as one item of the node's list, alongside the value or child reference.
They are applied in that order and they are independent — you can implement, test and break either
one without touching the other.<Cite src="yellow-paper" /> The specification's node encoder shows the
composition literally: it builds the pair `(nibble_list_to_compact(path, is_leaf), payload)` and
hands that to RLP.<Cite src="execution-specs-mpt" />
</Aside>

<Check type="spot-bug" concept="hp-even-padding">
An implementation handles the odd case correctly but writes the even case like this:

```python
if len(x) % 2 == 0:
    compact.append(16 * (2 * is_leaf))
    compact.append(0)                     # padding as a whole byte
    for i in range(0, len(x), 2):
        compact.append(16 * x[i] + x[i + 1])
```

Its own decoder is written to match, so `decode(encode(p)) == p` for every path the author tried,
odd and even, leaf and extension. Ten thousand random round-trips pass.

Why is it still wrong, and what will the author actually observe?

<Answer>
**The padding is half a byte, not a whole one.** This version emits one extra byte for every
even-length path, so `[0,1,2,3,4,5]` as an extension encodes to `00 00 01 23 45` instead of
`00 01 23 45`.<Cite src="ethereum-org-mpt" />

The round-trip test cannot catch it. A wrong-but-self-consistent codec round-trips perfectly — the
decoder was written to undo whatever the encoder does, so the pair agrees with itself and disagrees
with the world. Round-trip equality is the standard correctness property for a codec and it is the
wrong property when the output is going to be hashed into a consensus value. The property you
actually need is agreement with a reference: **reproduce the published vectors byte for
byte.**<Cite src="ethereum-org-mpt" />

What the author observes is the nastiest kind of bug report. Not a crash, not a parse error — a root
hash that matches the reference implementation on some inputs and not others. Tries where every path
fragment happens to be odd are fine. Add one key that produces an even-length fragment and the root
diverges, along with every hash on the way up to it.

There is a nastier variant of the same failure hiding in the extra byte, worth seeing because it is
not about the root at all. A one-byte-longer path item makes the whole node's RLP one byte longer,
and node length is not cosmetic here: the threshold at 32 bytes decides whether a parent stores a
hash or embeds the child verbatim (lesson 6), and go-ethereum's proof builder uses the same threshold
to decide which nodes even enter a proof.<Cite src="geth-trie-proof" /> A single stray padding byte
can therefore push a node across that line and change the *shape* of a proof, not merely its
contents.

The way in is a minimal failing pair: shrink the key set until removing any key makes the mismatch
disappear. Two keys is usually enough, and two keys is small enough to encode by hand.
</Answer>
</Check>

## Where this pays off

This nibble is the first thing a proof verifier reads about any 2-item node, before it decides
whether item 1 is a value it should return or a hash it should keep walking. Get it wrong in the
permissive direction and you have the vulnerability from lesson 2; and every node in an
`eth_getProof` response arrives as exactly this problem.<Cite src="eip-1186" />

It is also the specific place where from-scratch trie implementations fail. When lesson 8 argues
that a root hash is a pure function of the key-value set, this encoding is one of the reasons that
is true — there is exactly one hex-prefix encoding of any given path, and no implementation gets a
choice.
