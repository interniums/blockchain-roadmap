You have written a contract. It stores balances. Where does that data actually live, and what
questions can you ask it?

The first half of the answer is comfortable: it is a key-value map, and you already know how to
think about those. The second half is the part that reshapes your intuitions, because this
particular map has to satisfy a constraint no map in your own systems has ever had to satisfy —
**a stranger who holds none of the data must be able to check any single entry in it.**

## Two maps, nested

Ethereum's state is two levels of mapping.

The **world state** maps a 20-byte address to an account record. The record is four fields —
nonce, balance, storage root, code hash — and nothing else.<Cite src="ethereum-org-mpt" /><Cite src="yellow-paper" />

The third of those fields, `storageRoot`, is the entry point to the second map. Every contract
account owns a **storage trie** of its own: a map from a 32-byte slot key to a 32-byte value.<Cite src="ethereum-org-mpt" />
That is where `balances[alice]` ends up. Not in the account record — the account record only holds a
32-byte commitment to the whole of it.

Worth one level of precision on "four fields", because it explains a discrepancy you will hit in
client code. The executable specification's `Account` type holds **three** fields — nonce, balance
and code hash. The storage root is not part of the record; it is passed in separately at encoding
time, and the four-item list `rlp([nonce, balance, storageRoot, codeHash])` is assembled only when
an account is about to become a trie value.<Cite src="execution-specs-mpt" /><Cite src="execution-specs-state" />
So the fourth field is a property of the *encoding*, not of the account: it is the point where the
two maps are stitched together.

Two things follow immediately, and both surprise people.

**The address is not stored in the account.** It is the key you look the account up under. A record
pulled out of the state in isolation cannot tell you whose it is.

**Storage is not inside the contract.** The account holds a root hash; the storage lives in a
separate structure. This is why writing one slot changes the storage root, which changes the account
record, which changes the world state root. One `SSTORE` propagates all the way up.

An account with no storage at all does not carry a null or a zero here — it carries the root of the
empty trie, a fixed 32-byte constant the specification names `EMPTY_TRIE_ROOT`.<Cite src="execution-specs-mpt" />
And the relationship is symmetric: when a contract's last remaining slot is cleared, the
specification drops that account's storage trie entirely, so its storage root reverts to the same
constant.<Cite src="execution-specs-state-mpt" /> Lesson 2 derives the value.

## What you cannot ask

Here is where the model stops resembling a database. There are no tables, no secondary indexes, and
**no iteration**. You can look up a slot if you know its key. Nothing in the protocol lets you
enumerate the keys a contract has written.

<Misconception
  belief="You can iterate a contract's storage, or ask the chain for every holder of a token."
  reality="State is a map with no enumeration primitive. Every holder list, balance history and portfolio view you have ever seen was reconstructed off-chain by indexing event logs."
  why="Block explorers present holder lists beside on-chain data with the same styling, so they read as if they were queried from the chain. They were not — and a token that never emits Transfer events has no holder list anywhere."
  src="ethereum-org-mpt"
/>

This is not an oversight, and later in this module you will see the precise mechanism that makes
enumeration impossible: the structure does not store your key at all, only a hash of it.

There is a third thing the map does not contain, and it is easy to miss because the account record
mentions it by name. **Contract code is not in the trie.** The record holds `codeHash`; the
bytecode itself lives in a separate store keyed by that hash, and the specification is explicit that
the trie commits to accounts' code hashes and never to code contents.<Cite src="execution-specs-state-mpt" />
File that away — lesson 9 shows what it costs a proof, and lesson 10 shows that putting code
*inside* the state is one of the headline changes in the proposed successor.

## Why a plain hash map is not enough

Suppose you were designing this. A hash map gives you the lookups. What it does not give you is the
thing the protocol actually needs: **one short value that commits to the entire map**, such that any
change anywhere changes it.

You have already seen the standard answer to "commit to a lot of data with one hash" — a Merkle
tree. Hash the leaves, hash the pairs, keep going, publish the root. Anyone can then be convinced
that a particular leaf is in the tree by being handed the sibling hashes along one path.

That solves commitment. It does not solve the map. A Merkle tree commits to a **list**: leaf 0, leaf
1, leaf 2. Nothing about a leaf's contents determines where it sits. So:

- Two clients that insert the same key-value pairs in different orders build different trees and get
  different roots. For a consensus object, that is fatal.
- To prove a key is *absent*, you would have to reveal every leaf and let the verifier check that
  none of them match. There is no short proof of absence.

Both problems have the same root cause: position is unrelated to key.

The clearest evidence that this is a real limitation rather than a pedagogical one is Certificate
Transparency, the most widely deployed Merkle log outside this domain. RFC 6962 defines exactly two
proof types over its tree: a **Merkle audit path**, proving one leaf is in the tree, and a **Merkle
consistency proof**, proving one version of the tree is an append-only extension of an earlier
one.<Cite src="rfc-6962" /> Both are useful and neither answers "is this certificate absent from
the log?". A monitor that wants that answer has to download the log and look. The structure below is
what buys the third proof type.

## What a trie fixes

A trie inverts that relationship. You find a value by consuming the key one symbol at a time and
descending accordingly. Take the first symbol, follow that edge; take the second, follow that one;
stop when the key runs out. **The path you walked is the key.**

That single change buys three things at once.

**Position is determined by content.** Same key, same place, regardless of when it was inserted.
Insertion order stops mattering, which is the precondition for two independent clients agreeing on a
root hash.

**Prefix sharing is free.** Keys beginning with the same symbols share the top of their path, so the
structure compresses runs of common prefix instead of duplicating them.

**Absence becomes provable.** Walk as far as the key takes you and show that the structure ends
there — or veers off in a different direction. A verifier who trusts the root can follow the same
walk and conclude, from a handful of nodes, that the key is not present.<Cite src="eip-1186" /> A
plain Merkle tree cannot do this at all.

<Misconception
  belief="The trie stores keys at its nodes, the way a B-tree or a hash map does."
  reality="No node stores the key. Nodes store structure, fragments of path, and values; the key is reconstructed by remembering which edges you took to arrive."
  why="Every tree structure most engineers have implemented keeps the key in the node so it can be compared. Here the comparison has already happened — it is the descent itself."
  src="lambdaclass-mpt"
/>

<Aside kind="note">
Ethereum's structure is a *Merkle Patricia Trie*: a trie whose edges are hash references rather than
pointers. Both ideas are load-bearing. The trie half gives key-addressed lookup and exclusion
proofs. The Merkle half gives the single committing root. Neither one alone is sufficient, which is
why the name is a mouthful.
</Aside>

## The map and the commitment are two separate things

This distinction is worth installing now, because almost every explainer blurs it and the blur
causes real confusion later about what clients store on disk.

The executable specification separates them physically. `state.py` defines the state model and
describes itself as **commitment-agnostic: it defines what state *is*, not how it is committed
to**.<Cite src="execution-specs-state" /> What it exports is a `PreState` protocol — get an account,
get a storage value, get code by hash, compute a state root — with the note that any provider may
implement it: an in-memory dictionary, an on-disk database, or a
witness.<Cite src="execution-specs-state" /> The Merkle Patricia Trie appears in a *different* file,
`state_mpt.py`, described as the in-memory implementation used on mainnet, where accounts and
storage live in tries and the state root is the MPT commitment — with other commitment schemes named
as separate implementations of the same protocol.<Cite src="execution-specs-state-mpt" />

Read that architecture and two claims separate cleanly:

- **The map is the semantics.** Address to account, slot to value. That is what a transaction reads
  and writes, and it does not mention hashing.
- **The trie is one commitment over that map.** It fixes a 32-byte summary and a proof format. It is
  not the only conceivable one, and the specification is now shaped to say so out loud.

Hold both. When lesson 8 argues that a root is a pure function of the key-value set, this is the
sentence it is really making precise. And when lesson 10 discusses replacing the structure, notice
that what is being replaced is the commitment, not the map.

## What one write actually touches

The nesting has a cost structure, and it is worth seeing before you meet it as a gas number.

Writing one storage slot changes a leaf in that contract's storage trie. Changing a leaf changes its
hash, which changes the parent node that referenced it, and so on to the storage root. The storage
root is joined into the account record when the account is encoded,<Cite src="execution-specs-mpt" />
so the account's leaf in the world-state trie changes too, which cascades again to the state root.

Two chains of node updates for one write. The reads work the same way in reverse: getting a value
means walking down to the account, then down again into its storage.

This is the structural reason storage writes are the expensive operation in the EVM rather than an
arbitrary pricing decision, and it is also why touching *many* slots in one contract costs less per
slot than touching one slot each in many contracts — the second walk is shared in the first case and
repeated in the second.

<Aside kind="note">
The two-chain picture is the *semantics*, not the execution strategy. The specification's own state
object computes a root by copying the tries, applying a whole block's diff, and taking the root
once.<Cite src="execution-specs-state-mpt" /> No client rehashes after every `SSTORE`. Keep the
logical picture for reasoning about proofs and the batched one for reasoning about cost.
</Aside>

## Not every trie in Ethereum works the same way

One more thing to file away now, because it explains apparent contradictions later. Ethereum builds
several tries, and they do not all behave alike. The executable specification is blunt about it: a
trie may be *secured*, meaning its keys are hashed with keccak256 before insertion to stop
adversarial keys producing a deeply unbalanced trie — and the state and storage tries are secured
while the transaction and receipt tries are not.<Cite src="execution-specs-mpt" />

That is a real behavioural difference, not a detail — and lesson 7 is about why it exists. For now,
when you read "the trie", ask which one.

<Check type="explain" concept="trie">
A colleague proposes storing the world state as a sorted array of `(address, account)` pairs, built
into a Merkle tree over that array. Sorting, they argue, removes the insertion-order problem — two
clients sorting the same set get the same array and the same root.

They are right about that. Name the thing this design still cannot do, and say why the trie can.

<Answer>
**It cannot produce a short proof that an address is absent — at least not without extra machinery
the design does not have.**

Sorting does fix determinism. But the proof a Merkle tree yields is "leaf *i* is in the tree", and
what a verifier needs for absence is "no leaf anywhere matches this address". With a sorted array
you can get partway there by proving two *adjacent* leaves that bracket the missing address, which
means the verifier must also be convinced the array is globally sorted and that these two leaves are
genuinely adjacent. That is a second invariant to enforce, and enforcing it is exactly the kind of
thing that has broken real implementations.

In a trie, absence needs no extra invariant. Position is forced by the key, so walking the key's
path and finding it ends early *is* the proof — which is why the RPC that serves proofs specifies
absence and presence as the same response shape walked the same way.<Cite src="eip-1186" /> The same
nodes, checked the same way, serve both.

The second cost of the sorted array is worse in practice: inserting one account shifts the index of
every account after it, so every cached proof in the world is invalidated by a single write.
</Answer>
</Check>

## Where this pays off

Everything in this module is an unpacking of the two claims above: state is a key-addressed map, and
one 32-byte number commits to all of it.

The immediate payoffs are concrete. The four-field account record is the value stored at a leaf of
the world-state trie, so the account model is not a separate topic — it is this structure's payload,
assembled at the moment of encoding.<Cite src="execution-specs-mpt" /> The reason blockchain products
need indexers at all is the missing enumeration primitive, and now you know it is missing by
construction rather than by omission. And `eth_getProof`, which lesson 9 takes apart, is the RPC that
hands you the nodes along one of these paths so that a party holding only a block header can verify a
single entry for themselves.<Cite src="eip-1186" />
