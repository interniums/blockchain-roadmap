You now have the node kinds and the path encoding. This lesson puts them together on real bytes:
what each node actually contains, why the shapes are what they are, and how a complete four-key trie
looks when you dump every node in it.

By the end you should be able to take a node out of an `eth_getProof` response and say what it is,
what it consumes, and what it points at.<Cite src="eip-1186" />

## Branch: seventeen items

A branch node is the RLP list `[v0, v1, ..., v15, value]`.<Cite src="ethereum-org-mpt" />

Slots 0 through 15 are child references, indexed by the next nibble of the key. If no key descends
through nibble *k*, slot *k* holds the empty string.<Cite src="execution-specs-mpt" /> The
seventeenth item is a value.

That seventeenth item is the one people get wrong.

<Misconception
  belief="The seventeenth slot is padding, a version marker, or a leftover from an earlier design."
  reality="It holds the value of a key whose path terminates at exactly this node — a key that has run out of nibbles while other keys continue past it. It is the entire reason a branch is 17 items and not 16."
  why="Sixteen slots matches the nibble intuition so cleanly that the extra one looks vestigial. It only becomes visible when one key is a strict prefix of another — a case the trie definition must handle and Ethereum's own key schemes happen not to produce, so you can inspect mainnet data indefinitely without seeing it populated."
  src="ethereum-org-mpt"
/>

Hold on to the condition: **the seventeenth slot is used when one key is a strict prefix of
another.** In the world-state and storage tries every key is a 32-byte hash, so every path is 64
nibbles and no key can be a prefix of another — the slot is present in the encoding and permanently
empty.<Cite src="execution-specs-mpt" /> In the transaction and receipt tries, keys are short and
variable-length, which is the only setting where the slot could carry anything. Lesson 7 is about
that split, and the arithmetic below is about how much room the split actually leaves.

<Aside kind="note">
**How hard is it to find a populated seventeenth slot?** Harder than "variable-length keys" suggests,
and the reason is worth working out because it is a property of RLP rather than of the trie. The
index-keyed tries use `rlp(index)` as the key.<Cite src="execution-specs-osaka-fork" /> RLP encodes a
single byte below `0x80` as itself, the empty string as `0x80`, and anything longer behind a length
prefix of `0x81` or above.<Cite src="yellow-paper" /> So every one-byte index key lies in
`0x00`–`0x80`, and every multi-byte index key *starts* at `0x81` or higher — no short key is a byte
prefix of a longer one. Since a key's nibble path always has even length, a nibble-level prefix would
require a byte-level prefix, and there is none to have.

Which means: if you want to watch the seventeenth slot hold a value, build the four-key
`do`/`dog`/`doge` trie below, where the keys are arbitrary strings. Sampling real block data is not
going to show you one. The slot is not vestigial — the branch node's definition needs it and the
build procedure populates it whenever a key ends mid-trie<Cite src="execution-specs-mpt" /> — but
Ethereum's own two key schemes, fixed-length hashes and prefix-free RLP integers, both happen to
avoid the case.
</Aside>

## Extension: skip a shared run

An extension node is the 2-item list `[hexPrefix(sharedNibbles, isLeaf=false), childRef]`.<Cite src="ethereum-org-mpt" />

Its only job is compression. When every key below a point shares the next several nibbles, the
alternative is a chain of branch nodes each with a single occupied slot and fifteen empty ones. The
extension replaces that chain with one node carrying the whole run.<Cite src="execution-specs-mpt" />

<Misconception
  belief="Extension nodes are an optimisation, so a simple implementation can leave them out and still be correct."
  reality="They are mandatory. Where a run of shared nibbles exists, the canonical form is an extension node, and an implementation that emits a chain of single-child branches instead produces a different root hash for the same data."
  why="In ordinary tree code, path compression genuinely is optional — it changes performance, not results. Here the structure is hashed, so structure is result."
  src="ethereum-org-mpt"
/>

The rule this produces is worth stating in the form you will use when debugging: **in the secure
tries, no branch node ever has exactly one non-empty child.** If you build one, you have skipped an
extension somewhere, and your root will not match. go-ethereum states the same invariant flatly in a
comment on its range-proof code — a `fullNode` with only one child is disallowed — which is a good
sign that it is load-bearing rather than stylistic.<Cite src="geth-trie-proof" /> (The qualifier
matters — see the worked example below, where a branch with one child is legitimate because a key
terminates at it.)

## Leaf: the rest of the key, and the value

A leaf node is the 2-item list `[hexPrefix(remainingNibbles, isLeaf=true), value]`.<Cite src="ethereum-org-mpt" />

Item 0 is however much of the key has not yet been consumed by ancestors — the specification's own
phrasing is *nibbles of the key not yet consumed by ancestor
nodes*.<Cite src="execution-specs-mpt" /> Item 1 is the value: `rlp([nonce, balance, storageRoot,
codeHash])` in the world-state trie,<Cite src="ethereum-org-mpt" /><Cite src="execution-specs-mpt" />
the stored 32 bytes in a storage trie.

And structurally it is the same thing as an extension: a 2-item RLP list.

<Aside kind="note">
In go-ethereum, branches are `fullNode` and both extensions and leaves are `shortNode`.<Cite src="geth-trie-package" />
When you read client code and cannot find a leaf type, that is why. Its proof walker makes the
consequence explicit: it switches on `*shortNode` and checks whether the remaining key has the node's
key as a prefix, and on `*fullNode` and indexes by the next nibble — two cases, not
three.<Cite src="geth-trie-proof" />
</Aside>

## How a node's kind gets decided

The executable specification builds the trie recursively, and the decision procedure at each level
is four cases in order.<Cite src="execution-specs-mpt" />

1. **No keys remain** — the subtree is empty. Return NULL.
2. **Exactly one key remains** — return a leaf holding that key's unconsumed nibbles and its value.
3. **Every remaining key shares a non-empty prefix at this level** — return an extension consuming
   that prefix, and recurse below it.
4. **Otherwise** — partition the keys by their next nibble into up to sixteen groups, recurse into
   each, and assemble a branch. A key that has run out of nibbles here supplies the seventeenth
   item.

Read case 3 and case 4 together and the "no single-child branch" rule falls out. You only ever reach
case 4 when the shared prefix is empty — when the keys genuinely disagree about the next nibble, or
when one of them has ended. There is no path through this procedure that produces a branch whose
only content is one child.

Two things about the procedure that are easy to miss and both change what you expect on the wire.
The prefix search takes the *minimum* common prefix length across every key at this level, so a
single key that diverges immediately collapses the extension case to zero and forces a
branch.<Cite src="execution-specs-mpt" /> And the branch case initialises its value item to `b""` and
overwrites it only if some key's length equals the current level — which is the seventeenth slot's
entire population rule, in one line.<Cite src="execution-specs-mpt" />

## A complete trie, every node

The canonical documentation works a four-entry example, and it is worth walking in full because it
exercises every case above.<Cite src="ethereum-org-mpt" /> The entries:

```text
'do'     -> 'verb'          key bytes 64 6f           nibbles 6 4 6 f
'dog'    -> 'puppy'         key bytes 64 6f 67        nibbles 6 4 6 f 6 7
'doge'   -> 'coins'         key bytes 64 6f 67 65     nibbles 6 4 6 f 6 7 6 5
'horse'  -> 'stallion'      key bytes 68 6f 72 73 65  nibbles 6 8 6 f 7 2 7 3 6 5
```

These are raw keys, not hashes — an illustration trie, not a state trie. That is deliberate on the
documentation's part and it is what makes the seventeenth slot visible.

The resulting nodes:

```text
root : [ <16>, hashA ]
hashA: [ <>, <>, <>, <>, hashB, <>, <>, <>,
         [ <20 6f 72 73 65>, 'stallion' ],
         <>, <>, <>, <>, <>, <>, <>, <> ]
hashB: [ <00 6f>, hashC ]
hashC: [ <>, <>, <>, <>, <>, <>, hashD, <>, <>, <>, <>, <>, <>, <>, <>, <>, 'verb' ]
hashD: [ <17>, [ <>, <>, <>, <>, <>, <>, [ <35>, 'coins' ],
                 <>, <>, <>, <>, <>, <>, <>, <>, <>, 'puppy' ] ]
```

Now decode it, node by node. Every path byte below is hex-prefix encoded, so lesson 4's table is the
tool.

**root** is a 2-item node whose path byte is `0x16`. Flag nibble `1`: extension, odd length. Odd, so
the low nibble `6` is the first real nibble. Shared path is `[6]` — and indeed all four keys start
with nibble 6.

**hashA** has 17 items, so it is a branch. Slot 4 holds `hashB`; slot 8 holds a node written inline.
That matches the keys: after consuming `6`, the three `do…` keys continue with `4` and `horse`
continues with `8`.

The inline node at slot 8 is `[<20 6f 72 73 65>, 'stallion']`. Flag nibble `2`: leaf, even length,
so the next nibble is padding and the real path starts after it — `6 f 7 2 7 3 6 5`. Which is
exactly what remains of `horse` once `6` and `8` are consumed.

<Aside kind="warn">
Notice that this leaf appears **inside** its parent rather than as a hash reference. That is not a
notation shortcut. It is a rule of the structure, and lesson 6 is entirely about it.
</Aside>

**hashB** is `[<00 6f>, hashC]`. Flag nibble `0`: extension, even length, so the second nibble is
padding and the path is `6 f`. All three `do…` keys share that run after `6 4`.

**hashC** is a branch — and here is the seventeenth slot doing its job. Slot 6 holds `hashD`, and the
value item holds `'verb'`. Why? Because `do`'s path is `6 4 6 f`, which has been fully consumed by
the time we arrive: the root's `6`, hashA's branch on `4`, hashB's `6 f`. The key ends *at* this
node. `dog` and `doge` continue with nibble `6`.

This is also the branch with exactly one non-empty child that the rule earlier seemed to forbid.
It is legal precisely because it is not carrying only a child — it is carrying a terminating value
too, which no extension node can hold. Case 4 of the decision procedure was reached because the
shared prefix was empty, and it was empty because one key had run out.

**hashD** is `[<17>, ...]`. Flag `1`: extension, odd, first nibble `7`. Both `dog` and `doge` have
`7` next. Its child, again inline, is a branch: slot 6 holds the leaf `[<35>, 'coins']` and the
value item holds `'puppy'`. Flag `3` on that leaf: leaf, odd, first real nibble `5`, so the
remaining path is `[5]` — the last nibble of `doge`.

## Reading a node's first three bytes

Once you have seen a few real proofs you stop decoding them fully, because the RLP header alone
tells you most of what you want. EIP-1186's worked example shows account-proof entries beginning
`0xf90211a0…` and `0xf90151a0…`.<Cite src="eip-1186" /> Both prefixes are worth taking apart, because
you can read a node's whole shape out of them.

`0xf9` is RLP's long-form list prefix with a two-byte length following,<Cite src="yellow-paper" /> so
`f9 02 11` announces a list whose payload is `0x0211` = 529 bytes. Now count what a branch node
costs. A 32-byte hash reference RLP-encodes as `a0` plus 32 bytes — 33 bytes. Sixteen of those is
528. Add one byte for an empty seventeenth item, encoded as `0x80`, and the payload is 529 exactly.

So `f90211` is a **completely full branch node**: all sixteen slots occupied by hash references, no
terminating value. The `a0` immediately after is the start of the first child hash. You see this
prefix constantly near the top of a state-trie proof, which makes sense — the upper levels of a trie
holding hundreds of millions of accounts are saturated.

Run the same arithmetic backwards on `f90151`. Payload `0x0151` = 337 bytes. With *n* occupied slots
the payload is `33n + (16 - n) + 1`, which is `32n + 17`. Set that equal to 337 and `n = 10`. Ten
children, six empty slots, no terminating value — a branch from further down, where the trie has
begun to thin out.

The formula also tells you when a header is lying to you. A branch node in a *secure* trie always has
an empty seventeenth item, so its payload must satisfy `32n + 17` for some `n` between 2 and
16 — every legal payload is odd and congruent to 17 modulo 32. A payload of 369 works out to
`n = 11`; a payload of 370 does not correspond to any branch of that shape at all, and the node you
are holding either carries a terminating value (which cannot happen in a secure trie) or is not a
branch.<Cite src="execution-specs-mpt" />

### The other half: spotting a 2-item node from its header

Branches announce themselves with a long-form header because they are always large. The 2-item nodes
often do the opposite, and that asymmetry is itself a tell.

RLP's list prefix is `0xc0` plus the payload length while the payload is 55 bytes or fewer, and only
switches to the `0xf7`-plus-length-of-length form above that.<Cite src="yellow-paper" /> So work out
a typical storage leaf: a two-byte hex-prefix path RLP-encodes to 3 bytes, a 32-byte value to 33, for
a payload of 36 — under the limit, so the node begins `0xe4`. An extension pointing at a hashed child
lands in the same neighbourhood: a short path plus a 33-byte reference is a payload in the thirties,
so the first byte is somewhere in `0xe0`–`0xef`.

The practical rule, then, for a node you have not decoded yet:

- **`0xf9…`** — a long-form list of a few hundred bytes. A branch, and the next two bytes give you
  the occupancy through `32n + 17`.
- **`0xe…`** — a short-form list of 32 to 47 bytes. A 2-item node with a compact payload: a storage
  leaf or an extension. Read the next byte's high nibble for which.
- **`0xf8…`** — a long-form list with a one-byte length, 56 to 255 bytes. In a state proof this is
  almost always an account leaf, for the reason the next section derives.

None of that is a substitute for decoding. It is a way to look at twelve hex strings and know which
one to decode first.

### Why an account leaf is never small

One more piece of arithmetic, because it settles a question lesson 6 turns into a rule.

Take the emptiest account there is: nonce 0, balance 0, the empty storage root and the empty code
hash. Its value encodes as `rlp([nonce, balance, storageRoot, codeHash])`.<Cite src="execution-specs-mpt" />
Zero RLP-encodes to the single byte `0x80`; each of the two 32-byte hashes encodes to 33
bytes.<Cite src="yellow-paper" /> Payload: `1 + 1 + 33 + 33 = 68` bytes, which is over the 55-byte
short-form limit, so the list takes a two-byte header — 70 bytes in total.

That 70-byte string is then item 1 of the leaf node, so it gets a *second* RLP header as a byte
string: 72 bytes. Add item 0 — a hex-prefix path of at least one byte, encoded as at least one more —
and the leaf's payload is at least 74 bytes, so the node itself is at least 76.

**Every account leaf in the world-state trie is comfortably over 32 bytes, for every account that
exists, including the emptiest one.** No arithmetic about balances or nonces changes that, because
the two 32-byte hashes dominate. Which means account proofs never exercise the rule in lesson 6, and
testing only against account proofs proves nothing about it.

<Aside kind="note">
This is a genuinely useful field skill. Given a proof as an array of hex strings, the prefixes alone
sketch the path: a run of `f90211` at the top, thinner branches below, then a short 2-item node at
the bottom whose first content byte starts with `2` or `3` — a leaf. If the last node's flag nibble
is `0` or `1` instead, you are looking at an extension, and the walk did not end where you thought.
</Aside>

<Check type="recall" concept="mpt-branch-node">
In the trie above, `hashC` holds `'verb'` in its seventeenth item.

Now suppose the same four entries were inserted into the **world-state trie**, where the key walked
is `keccak256` of the original key rather than the key itself. What happens to that seventeenth
item, and why?

<Answer>
**It goes permanently empty — in that node and in every other branch node in the trie.**

Hashing makes every key exactly 32 bytes, so every path is exactly 64 nibbles.<Cite src="ethereum-org-mpt" /><Cite src="execution-specs-mpt" />
Two paths of identical length: neither can be a strict prefix of the other unless they are equal.
Since the seventeenth slot exists only to hold the value of a key that terminates while others
continue, the situation it handles cannot arise.

The prefix relationship between `do` and `dog` is destroyed by hashing, which is the point.
`keccak256('do')` and `keccak256('dog')` share no meaningful prefix — the same reason the trie stays
shallow and balanced.

Three things worth taking from this. First, the slot is still there in the encoding: a branch node in
the state trie is still 17 items, with the last one an empty string. The structure does not shrink
because the case does not occur — which is exactly what makes the `32n + 17` arithmetic above hold
for every branch in a state proof. Second, this is why the seventeenth slot looks vestigial to anyone
who has only ever inspected mainnet data: the state and storage tries rule the case out by
fixed-length keys, and, as the aside above derives, the index-keyed tries rule it out by RLP's
prefix-free integer encoding.<Cite src="yellow-paper" /> The slot is defined and
populated by the build procedure,<Cite src="execution-specs-mpt" /> and neither of Ethereum's key
schemes exercises it.

Third, and most useful when you are debugging: this gives you a cheap sanity check on any state or
storage proof. Sum the nibbles consumed by every node in the walk — one per branch, the fragment
length per extension, the remainder at the leaf. If it does not come to exactly 64, you are not
looking at a secure-trie proof, whatever the response envelope said.
</Answer>
</Check>

## Where this pays off

Every node in the next four lessons is one of these three shapes. Lesson 6 explains why two of the
nodes above were written inline instead of as hashes — and the account-leaf arithmetic above is why
that rule is invisible until you leave the state trie. Lesson 8 argues that this whole layout is
forced — that the decision procedure has no free choices in it<Cite src="execution-specs-mpt" /> —
which is what lets a root hash function as a consensus object. And lesson 9 walks a real proof, where
the work is precisely the decoding you just did four times by hand.
