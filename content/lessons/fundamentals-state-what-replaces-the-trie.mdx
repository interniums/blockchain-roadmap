If you have read anything about Ethereum's roadmap written between roughly 2021 and 2024, you have
read that Verkle tries are what comes after the Merkle Patricia Trie. Conference talks, roadmap
diagrams, explainer threads — the name is everywhere.

**As of August 2026 that is not the live direction**, and a lesson that repeated it would be
teaching you a design that is not being built. What follows is what is actually in front of the
protocol, what is genuinely undecided about it, and how to hold the difference.

## Why replace the trie at all

Start with the complaint, because it has changed.

The original framing was **witness size**. A stateless client executes a block without holding the
state, using a witness supplied alongside it, and that witness is a bundle of Merkle proofs. Lesson
3's arithmetic explains why they are large: a hexary node forces fifteen sibling references per
level, and EIP-7864 puts the expected cost of proving a single branch in a `2^32`-entry tree at
`15 * 32 * log_16(2^32) = 3840` bytes.<Cite src="eip-7864" />

The current framing is **proving cost**. The goal EIP-7864 names is having blocks provable with
validity proofs, and it lists what makes the MPT unfriendly to that: RLP node encoding, keccak256 as
the hash, being a tree of trees rather than one tree, and contract code not being part of the state
at all.<Cite src="eip-7864" /> It also gives a worst case that is not about witnesses being
inconvenient: a block spending its gas touching one byte each of many different contracts' code,
which the EIP puts at roughly 330 MB under current rules because code is not
chunked.<Cite src="eip-7864" />

Same structure, different question asked of it. That shift is most of the story of why the answer
changed too.

## What is actually proposed

EIP-7864, *Ethereum state using a unified binary tree*, created 20 January 2025 and still
**Draft**.<Cite src="eip-7864" />

The differences from what you have spent this module learning are large and all deliberate.

**One tree, not a tree of trees.** Account headers, contract code and storage live in a single
logical tree, so there is no `storageRoot` field pointing into a nested structure and no second walk
in a proof.<Cite src="eip-7864" />

**Binary, not hexary.** Arity two: lesson 3's trade-off re-run against a cost model where node width
dominates.<Cite src="eip-7864" />

**No RLP.** Removed as unnecessary complexity, particularly inside a proving circuit.<Cite src="eip-7864" />

**No extension nodes.** The design deliberately avoids extension nodes injected into the middle of
branches, using instead the minimum number of internal nodes needed to separate stems that share a
prefix.<Cite src="eip-7864" />

**Four node kinds again, but different ones**: `InternalNode` with a left and right hash, `StemNode`
carrying a stem plus two hashes, `LeafNode` holding a 32-byte value or empty, and
`EmptyNode`.<Cite src="eip-7864" />

**Prefix-free keys with deliberate locality.** The first byte of a key denotes storage type — headers
versus code versus storage, so subtrees can be synced separately — the middle bytes are the stem,
and the last byte is a subindex within it. Keys sharing the first 31 bytes share a stem and are
co-located in groups of 256, so data accessed together is proved together.<Cite src="eip-7864" />

**Code is in the state.** Contract code is chunked and stored in the tree, which is what removes the
330 MB worst case above.<Cite src="eip-7864" /> Measure that against what the current commitment
does: the executable specification's MPT-backed state says outright that it commits to accounts'
**code hashes, never to code contents**.<Cite src="execution-specs-state-mpt" /> A proof today
establishes a hash and leaves you to fetch the bytes and check them yourself (lesson 9). The proposal
closes that specific gap, which is why "code is in the tree" is a change to what a proof *means*, not
only to where bytes live.

## What is not decided

This is the part to hold most carefully, because it is the part most likely to be reported as
settled.

**The hash function is explicitly undecided.** The draft uses BLAKE3 to reduce friction for
execution-layer clients experimenting with the EIP, and says in as many words that the final
decision remains TBD, with Keccak and Poseidon2 as other candidates — Poseidon2 pending an Ethereum
Foundation cryptography assessment. The EIP's own instruction is: do not assume BLAKE3 is a final
decision.<Cite src="eip-7864" />

**The schedule is not a schedule.** The EIP is Draft.<Cite src="eip-7864" /> This project's research
found it attached to no named fork as of this lesson's verification date. No date should be inferred
from anything here — including from the fact that this lesson exists.

**The migration story points at Verkle-era documents.** EIP-7864 delegates its fork mechanics to
EIP-7612 and its later state conversion to EIP-7748.<Cite src="eip-7864" /> The model is
freeze-and-start-empty: the binary tree starts empty, only new state changes go into it, and the MPT
continues to exist frozen, with a migration of the old data left to a future
fork.<Cite src="eip-7864" /> But EIP-7612 is titled for a Verkle state transition and is
Stagnant,<Cite src="eip-7612" /> and EIP-7748 is titled for conversion to a Verkle
tree.<Cite src="eip-7748" /> Whether those have been retargeted, superseded, or simply not yet
rewritten is not something this project resolved. Read them before relying on either.

**State expiry is not settled either.** The draft discusses state-expiry strategies as something that
*could* still be applied, and sketches two ways the node layout would have to change to accommodate
one.<Cite src="eip-7864" /> That is a description of open design space, not a plan.

**The breaking changes are named but not resolved.** The EIP lists two: gas costs for code-chunk
access change, which affects application economics, and the tree-structure change means in-EVM
proofs of historical state stop working.<Cite src="eip-7864" /> The second is worth pausing on if
you build anything that verifies storage proofs on-chain — the mitigation offered for the first
(raise the gas limit) has no counterpart for the second.

## What the specification has already changed

Here is a piece of evidence with no press release attached, which is the kind worth more than a
roadmap post: the executable specification has been reorganised so that the state model and its
commitment are separate things.

`state.py` now describes itself as **commitment-agnostic — it defines what state *is*, not how it is
committed to** — and exports a `PreState` protocol that an in-memory dictionary, an on-disk database
or a witness may each implement.<Cite src="execution-specs-state" /> The Merkle Patricia Trie sits in
a separate file as *the* implementation used on mainnet, with other commitment schemes named as
separate implementations of the same protocol.<Cite src="execution-specs-state-mpt" /> And the
protocol's own `compute_state_root` is documented for two cases: a commitment over code hashes alone,
which can ignore the block's new bytecode, and **a commitment over code contents**, which has to
resolve each account's bytecode through its code hash.<Cite src="execution-specs-state" /> The
MPT-backed implementation is the first case.<Cite src="execution-specs-state-mpt" /> The second is the
shape EIP-7864 asks for.<Cite src="eip-7864" />

Read that carefully for what it is and is not. It is not a schedule, not an adoption, and not a
commitment to any particular successor. It is a specification being made pluggable at exactly the
seam a state-format change would run along — which is weak evidence about *when* and reasonably
strong evidence about *what kind of thing* is being prepared for.

## What happened to Verkle

Verkle tries replace hash-based branching with polynomial vector commitments, so that proving a set
of openings costs a small constant rather than a sibling per level per key. That is a real and
elegant answer to *witness size*, which was the question being asked. It has a specification of its
own: EIP-6800, *Ethereum state using a unified verkle tree*, created 17 March
2023.<Cite src="eip-6800" /> Read it if you want to know what Verkle actually proposed rather than
what the diagrams said.

Two facts about that document are worth putting side by side with EIP-7864, because together they
say more than any commentary. **EIP-6800 is Stagnant.**<Cite src="eip-6800" /> And EIP-7864 —
*Ethereum state using a unified binary tree*, one word different in the title — carries a heavily
overlapping author list.<Cite src="eip-7864" /><Cite src="eip-6800" /> This is not one camp
displacing another. It is largely the same people re-answering their own question after the question
changed.

EIP-7864's rationale argues against it on two grounds, both stated in the EIP.<Cite src="eip-7864" />

**Post-quantum exposure.** Verkle's commitments rely on elliptic curves, which are not post-quantum
secure. The EIP cites expert estimates putting practical quantum computers in the 2030s and NIST
guidance to stop using elliptic-curve cryptography by 2030. A hash-based tree depends only on hash
functions, which remain safe under that assumption.<Cite src="eip-7864" />

**Proving systems moved.** The EIP's argument is that progress in proving systems has been fast
enough that pre-state and post-state proofs may be achievable directly — which erodes the advantage
Verkle's small proofs were bought for.<Cite src="eip-7864" />

<Aside kind="warn">
**On the strength of this claim.** What is verifiable is the above: EIP-7864 exists, is the active
proposal for a state-format change, and argues explicitly against the Verkle approach. This
project's research did **not** locate a single authoritative Ethereum Foundation announcement
cancelling Verkle. The honest reading is direction of travel evidenced by a draft specification,
not a decision with a citable date. Independent quantitative comparison of the two designs under
SNARK proving does exist and is worth reading directly.<Cite src="stateless-benchmarks-arxiv" />
</Aside>

A colleague reads a 2023 roadmap post, then this lesson, and asks the reasonable question: "So the
protocol people were wrong for three years?"

Give the better answer.

<Answer>
**No — the target moved, and the design that was best for the old target is not best for the new
one.**

Verkle was designed against *witness size*: make stateless clients practical by making the proof
that accompanies a block small. On that criterion it is genuinely strong, because a vector
commitment gives a constant-size opening instead of a sibling per level.

Two things then changed the criterion.

*Proving became the point.* The goal became blocks provable with validity proofs, which asks a
different question of the state format — not "how many bytes is the proof" but "how expensive is
this structure to reason about inside a circuit". Against that question, RLP, keccak256 and a
tree-of-trees layout are all costs, and Verkle's elliptic-curve arithmetic is one too.<Cite src="eip-7864" />

*Post-quantum moved from distant to schedulable.* A structure whose security rests on elliptic
curves is a liability on a horizon where NIST guidance is to stop using them by 2030, and a
hash-based tree simply does not have that exposure.<Cite src="eip-7864" />

The transferable lesson is about how to read roadmaps at all. A roadmap item is a bet on a
criterion, and criteria in this domain have a half-life of a few years. The right habit is to hold
the *problem* firmly — proofs of state need to be small and cheap to verify — and the *named
solution* loosely. Someone who learned "Verkle is next" has to relearn. Someone who learned "the
MPT's proofs are large because a hexary node forces fifteen siblings per level, and something will
address that" already understands EIP-7864 before reading it.
</Answer>
</Check>

## Where this pays off

Two things to carry forward. The first is a fact with a date attached: the hexary Merkle Patricia
Trie with keccak256 is Ethereum's live state commitment as of August 2026,<Cite src="ethereum-org-mpt" />
and everything in the previous nine lessons describes what is running now, not history.

The second is a habit. Volatile claims need a verification date and a status attached — Draft, not
scheduled, hash function TBD — and a claim that arrives without them should be treated as unverified
regardless of how confidently it is stated. Statelessness, and the question of whether proving the
state or shrinking the proof is the right lever, is where this module hands off.
