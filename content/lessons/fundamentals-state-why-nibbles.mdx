A branch node has sixteen child slots. Not two, not 256. **Why sixteen?**

The question sounds like trivia and is not. The answer is a single design parameter — how many bits
of the key you consume per level — and once you see what it controls, several other facts about the
trie stop being arbitrary: the width of a branch node, the length of a path, the existence of the
hex-prefix flag, and the entire argument for replacing the structure.

## The unit

A **nibble** is four bits: one hexadecimal character, sixteen possible values. It is the atomic step
of Ethereum's trie — the amount of key consumed by descending one level.<Cite src="ethereum-org-mpt" />

That is the whole of the definition, and it produces the sixteen slots directly. If one step of the
walk consumes a value in the range 0 to 15, an internal node needs one child slot per value, which
is sixteen slots.<Cite src="execution-specs-mpt" /> The seventeenth item you will keep seeing is a
value, not a child, and lesson 5 deals with it.

The specification's key preparation is equally plain: a byte string is expanded into a sequence of
nibbles by splitting each byte into its high and low half, producing a sequence of bytes each holding
a value from 0 to 15 inclusive — so a key of *n* bytes becomes a path of *2n*
steps.<Cite src="execution-specs-mpt" />

<Aside kind="note">
That expansion is not a mental model, it is a representation clients hold in memory. go-ethereum
names three encodings of a trie key and converts between them explicitly: **keybytes**, the actual
key and nothing else; **hex**, one byte per nibble with an optional trailing terminator byte of value
`0x10`; and **compact**, the Yellow Paper's hex-prefix form. Its own comment records which is used
where — hex for nodes held in memory, because it is convenient to index, and compact for nodes stored
on disk.<Cite src="geth-trie-encoding" /> One nibble per byte wastes half of every byte and is worth
it while you are walking.
</Aside>

## The trade you are actually making

Call the number of children per node the **arity**, *r*. Two quantities move in opposite directions
as you change it.

**Depth** is `log_r(N)` for *N* keys. Larger arity, shallower trie, fewer nodes to fetch and hash
when you walk a path.

**Node width** is *r*. Larger arity, fatter nodes — and node width is not free, because a Merkle
proof has to hand the verifier every sibling in every node along the path so it can recompute that
node's hash. Each sibling is a 32-byte reference, which RLP-encodes to 33 bytes on the
wire.<Cite src="yellow-paper" />

So the sibling bytes in a proof go roughly as `(r - 1) * 32 * log_r(N)`, and that expression has a
minimum somewhere. EIP-7864 states the hexary case for a tree of `2^32` entries directly:
`15 * 32 * log_16(2^32) = 3840` bytes to prove a single branch.<Cite src="eip-7864" />

Put `r = 2` into the same expression and you get `1 * 32 * 32 = 1024` bytes — smaller, at the cost of
thirty-two levels of descent instead of eight. That is arithmetic on the EIP's own formula rather
than a figure from the EIP, and it is precisely the trade EIP-7864 argues should now be made
differently.<Cite src="eip-7864" /> Lesson 10 takes that argument apart.

Sixteen was chosen when the binding constraint was different: a node small enough to store and
transmit conveniently, and a path short enough that a lookup is a handful of database reads rather
than dozens. Under those constraints it is a reasonable answer. Under "how expensive is this to
prove inside a zero-knowledge circuit", it is a much less obvious one.

<Aside kind="note">
Notice that the argument never reaches for a nibble being "natural" because it is half a byte.
Convenient, yes — nibbles pack two to a byte and print as hex. But the reason there are sixteen
slots is the arity choice, and the convenience is a consequence, not a cause.
</Aside>

## Path length is fixed, and that is deliberate

A 32-byte key produces a path of exactly 64 nibbles; a 20-byte key, 40.<Cite src="ethereum-org-mpt" />

In the world-state and storage tries you never actually walk a raw address or a raw slot number.
Both are hashed first,<Cite src="execution-specs-mpt" /> so the key being walked is always a 32-byte
keccak256 digest and **every path is exactly 64 nibbles long**.<Cite src="ethereum-org-mpt" /> Uniform,
and — the part that matters — not chosen by anybody. Lesson 7 is about why that property is worth
buying.

The uniformity has a second consequence that is easy to miss and shows up in lesson 5: with every
path the same length, **no key can be a strict prefix of another**. Every branch node in a secure
trie therefore carries an empty seventeenth item, permanently.

## The mistake this invites

Sixty-four steps sounds like sixty-four nodes, and a proof of sixty-four nodes would be a serious
cost. It is not what happens.

<Misconception
  belief="A 64-nibble path means a proof has to contain 64 nodes."
  reality="Path length and node count are different quantities. Extension nodes collapse every run of nibbles that all keys below them share, so real proofs are a handful of nodes deep."
  why="The path is the only length anyone quotes, so it becomes the number people reason with. But most of those 64 steps are traversed inside a single extension node, not one node at a time."
/>

The reason is a counting argument. A branch node only survives at a level where at least two keys
actually diverge — the specification reaches its branch case only when the keys share no common
prefix at all at that level.<Cite src="execution-specs-mpt" /> With *N* keys distributed uniformly —
and hashing the key is what makes them uniform — divergence stops happening after roughly `log16(N)`
levels, and everything below that point is one key going its own way, which is exactly what an
extension node compresses into a single node.

You do not have to take this on faith. EIP-1186's own worked example of an `eth_getProof` response
shows an account proof of five nodes.<Cite src="eip-1186" /> Five, against a path length of 64.

<Check type="predict" concept="mpt-nibble-path">
Someone proposes a change: keep everything about the trie, but consume a whole **byte** per level
instead of a nibble. Paths for a 32-byte key drop from 64 steps to 32.

Two questions. What happens to the width of an internal node, and what happens to the size of a
proof? Use the sibling-bytes expression from earlier.

<Answer>
**Node width goes from 16 slots to 256.** One slot per possible value of the consumed symbol, and a
byte has 256 values.

**Proof size roughly doubles.** Substituting `r = 256` into `(r - 1) * 32 * log_r(N)` for `N = 2^32`
gives `255 * 32 * 4 = 32,640` bytes, against 3,840 for the hexary case.<Cite src="eip-7864" /> The
depth did fall — four levels instead of eight — but each level now costs 255 sibling references
instead of 15, and that dominates by a wide margin.

This is the shape of the whole trade-off, and it runs the other way too: dropping to binary shrinks
proofs further still. The reason nobody proposes a 256-ary trie is the same reason the binary
proposal is now being taken seriously — proof size is dominated by node width, not by depth.

Worth noticing separately: with byte-wide steps there would be no odd-length path problem, because
every fragment would already be a whole number of bytes. The entire hex-prefix encoding in lesson 4
exists only because the unit is half a byte — and go-ethereum's own encoding comment says as much
when it describes the compact form as carrying "the oddness of the
length".<Cite src="geth-trie-encoding" />
</Answer>
</Check>

## Depth in practice

Two numbers describe a proof and they behave differently as the state grows.

**Node count** tracks `log16(N)`, which grows glacially. Going from a million entries to a billion
adds roughly two and a half levels — the logarithm base 16 of a thousandfold increase is under
three. A proof does not get meaningfully longer as Ethereum gets bigger, which is the property that
makes the whole light-client story viable.

**Bytes per node** does not shrink. Every branch node on the path contributes its siblings whether
or not you care about them, and that per-level cost is fixed by the arity. So a proof's size is
roughly `constant * depth`, with the constant set by the fan-out and the depth barely moving.

Which is why the successor design attacks the constant rather than the depth. Nobody proposes making
the trie shallower; the proposal is to make each level cheaper, and to accept more levels in
exchange.<Cite src="eip-7864" />

<Aside kind="note">
A useful check when you are reasoning about a proof: the top of the path is dense and the bottom is
sparse. Near the root, every branch node is full because millions of keys pass through it. Near the
leaf, you are usually in an extension node covering a long run that only your key walks. The
expensive part of a proof is the first few levels.
</Aside>

## Arity is not the only knob

One refinement, because it changes what "smaller arity" costs and is the thing most summaries drop.

Going binary makes each node cheap and the path long, which would ordinarily mean many more nodes
per proof. EIP-7864 buys most of that back with a second decision that has nothing to do with arity:
key *locality*. Its keys are prefix-free and structured — a first byte denoting storage type, a
middle **stem**, and a final subindex — so that keys sharing the first 31 bytes sit in one group of
256 leaves under a common stem, and data accessed together is proved
together.<Cite src="eip-7864" />

The contrast with what you have learned here is exact and worth holding. Ethereum's current tries
deliberately destroy locality by hashing the key, because locality is what an adversary would grind
for (lesson 7). A design that wants locality back has to make keys unchooseable some other way —
which is what the prefix-free structure is for. Two answers to the same threat, arrived at fifteen
years apart.

## Where this pays off

The nibble is the reason for three things you are about to meet. Sixteen slots in a branch node,
which lesson 5 decodes byte by byte. Odd-length path fragments, which do not fit in whole bytes and
force the encoding in lesson 4. And a uniform 64-step path, which lesson 7 shows is bought
deliberately by hashing the key.

It is also the number under negotiation in the successor design. When you read that a binary tree
gives shorter Merkle branches, the claim is this arity trade being re-run against a different cost
model — one where the expensive operation is proving the walk inside a circuit rather than
performing it on a disk.<Cite src="eip-7864" />
