There is no RPC method that lists a contract's storage slots. Not a slow one, not a paid one, not
one behind an archive node. **Why not?** The data is public, the node has all of it on disk, and
every other question about a contract is answerable.

The answer is a single line in the trie's construction, and it was put there for a completely
different reason.

## The path is not the key

For the world-state trie and every storage trie, the sequence of nibbles walked is not the key you
supplied. It is `keccak256` of that key.

The specification states the split without hedging: a trie may be *secured*, meaning keys are hashed
with keccak256 before insertion to prevent adversarial keys from producing a deeply unbalanced trie;
the state and storage tries are secured, and the transaction and receipt tries are
not.<Cite src="execution-specs-mpt" /> It is a field on the trie itself — `secured: bool` — and the
one place it is consulted is a two-line branch during key preparation: hash the preimage if the trie
is secured, otherwise use the key as given, and expand the result into
nibbles.<Cite src="execution-specs-mpt" /> Ethereum's state object constructs its main trie and every
storage trie with that flag set.<Cite src="execution-specs-state-mpt" />

So looking up an account walks `keccak256(address)`,<Cite src="ethereum-org-mpt" /> and looking up a
storage slot walks `keccak256(slotKey)`. The RPC specification says the same thing in its own
vocabulary without ever calling it a design decision: an account proof follows the path of the
`SHA3` of the address, and each storage proof follows the path of the `SHA3` of the
key.<Cite src="eip-1186" />

## What hashing buys: a depth nobody can choose

The stated reason is adversarial balance,<Cite src="execution-specs-mpt" /> and it is worth
following the attack it prevents.

Suppose the path were the raw address. Addresses are not assigned — they are derived, and an
attacker can generate as many as they like and keep the ones they like the look of. Grinding for a
20-byte value with a chosen 8-nibble prefix is a small amount of work.

Now generate a few thousand addresses that all share a long prefix and put state at each. The trie
below that prefix becomes a deep, narrow tower. Every read of any account in that region walks the
whole tower, and every proof about one of them carries a node per level. The attacker has not broken
anything; they have made a region of the state structurally expensive for everyone who touches it,
and they chose how expensive.

Storage slot keys are worse, because there the grinding is a normal API call rather than a mining
loop. Solidity places the value for `mapping(K => V)` at `keccak256(pad32(key) ++ pad32(p))`, where
*p* is the declared slot,<Cite src="solidity-layout-storage" /> and the caller supplies the key. An
attacker who wants slot numbers sharing a prefix tries keys until they get them.

Hashing removes the choice at the point where it would matter. To place a key at a chosen path you
would have to find a preimage for a chosen keccak256 output, which is the property that entire
discipline rests on. Paths land uniformly whether an attacker likes it or not, so depth is a
function of *how many* keys exist, not *which* keys exist. Every path is exactly 64
nibbles<Cite src="ethereum-org-mpt" /> and the tree stays roughly `log16(N)` deep, as lesson 3
argued.

<Aside kind="note">
Notice which property of the hash is being spent. It is not secrecy — addresses are public and slot
derivations are documented.<Cite src="solidity-layout-storage" /> It is that the *output is
unchooseable*. The trie needs a function from keys to paths that no participant can steer, and a
preimage-resistant hash is the cheapest such function available.
</Aside>

## What hashing costs: the preimages are gone

Here is the side effect, and it answers the question this lesson opened with.

A trie node stores a fragment of *path*. The path is a hash. Walk the entire state trie, decode
every node, and what you reconstruct is a set of 64-nibble hashes with values attached. You learn
that some account exists at `keccak256(address)` for some address you cannot name.

**The node serving your RPC request does not know what the keys were.** It is not withholding them.
Clients that want reverse lookups keep a separate preimage table, populated as keys pass through
during execution — an extra database, not part of consensus, and not something you can rely on being
present.

The exception proves the rule rather than breaking it. go-ethereum does expose a way to page through
an account's storage, `debug_storageRangeAt` — and its cursor parameter is documented as the *hash*
of the storage key, not the key.<Cite src="geth-ns-debug" /> Even the debug path walks in hash order,
because hash order is the only order the structure has. It also sits in the `debug` namespace, which
is not enabled on public endpoints and is not part of the standard API.

That is the whole reason blockchain products need indexers. The enumeration you want is not slow, it
is absent, and it is absent because of a decision made to bound trie depth.

## Two hashes, not one

For mapping storage this compounds, and the compounding trips people up.

Solidity places `mapping(address => uint256) balances` at some declared slot *p*. The storage
position for a particular key is `keccak256(pad32(key) ++ pad32(p))` — the key and the slot number,
each left-padded to 32 bytes, concatenated and hashed.<Cite src="solidity-layout-storage" />

Then that 32-byte position is itself the key of the storage trie, so the path walked is
`keccak256` of *it*.<Cite src="execution-specs-mpt" />

Two hashes with different jobs, and — the part worth holding — **different owners**. The first is
Solidity's storage layout, a language convention documented by the compiler; a contract written in
raw assembly may lay its storage out any way it likes.<Cite src="solidity-layout-storage" /> The
second is the protocol's, fixed by the trie definition and not negotiable by any
contract.<Cite src="execution-specs-mpt" /> Conflate them and your hand-verified proof will not
verify; the symptom is a walk that diverges at the first branch and gives you a perfectly valid
exclusion proof for a slot you did not mean to ask about.

## Absence, and what it means at each level

One consequence of hashing that shows up in the specification's types rather than its prose, and
that lesson 9 will need.

A trie carries a `default` value, and storing that default at a key is defined as deleting the key:
the structure represents the default by omitting the key entirely.<Cite src="execution-specs-mpt" />
Ethereum's two secure tries pick different defaults. The main trie's default is `None` — an address
with no account is simply not there. Each storage trie's default is the 256-bit zero, so writing zero
to a slot removes it.<Cite src="execution-specs-state-mpt" />

The nesting goes one step further than most people expect. When a contract's last remaining slot is
cleared, its storage trie is not left empty — the specification deletes the trie from the state
object outright, and the account's storage root falls back to the empty-trie
constant.<Cite src="execution-specs-state-mpt" /> Absence is recursive: an empty map has no
representation at any level, only a root that says so.

## What clients keep, and why it is not a guarantee

If the preimages are gone from the trie, how does a node answer `eth_getProof` for an address at
all? It does not need to. You supply the address; the node hashes it and walks.<Cite src="eip-1186" />
The direction that is lost is the other one — from a path back to the address — and nothing in normal
operation needs it.

Some clients do maintain a separate preimage table, mapping a hash back to the key that produced it,
populated as keys pass through during execution. Two things about it are worth knowing.

It is **not part of consensus**. No block, header or root commits to it. Two clients with identical
state can hold completely different preimage tables, or none, and both are correct — the
specification's state model does not have a field for one.<Cite src="execution-specs-state" />

It is **not complete**. It contains what that node happened to observe. A node that synced from a
snapshot rather than replaying history may have very little in it, and it can be turned off to save
disk.

So "can I enumerate this contract's storage?" has a precise answer: not from the state, and not
reliably from any node. What you can do is watch execution — which is what an indexer does, and why
its coverage starts at the block it was switched on rather than at genesis.

## Not every trie is secured

Ethereum builds more tries than the two that persist, and the others follow different rules.

The transaction trie, the receipt trie and the withdrawals trie are keyed by the RLP encoding of the
item's index within the block, with no hashing applied. The executable specification for the current
fork inserts transactions under `rlp(index)`, receipts under `rlp(index)`, and withdrawals under
`rlp(i)` as it iterates them.<Cite src="execution-specs-osaka-fork" />

Which makes sense once you ask what hashing was protecting against. The key set here is not
attacker-supplied; it is `0, 1, 2, …` up to the number of items in the block, assigned by the
protocol. There is no grinding to prevent, and short dense keys make the trie shallow and cheap to
build.

Three consequences follow, and all three are visible.

**Keys are short and variable-length.** Unlike the fixed 64-nibble secure tries, paths here differ in
length from one another, which is the precondition for the seventeenth branch slot from lesson 5
mattering at all.<Cite src="execution-specs-mpt" /> Lesson 5 works out how much of that precondition
RLP actually delivers, and the answer is less than it looks.

**Order is preserved.** The trie path is derived from the index, so position in the trie tracks
position in the block. That is what makes a receipt's index meaningful in a proof.

**They are not state.** These tries are derived from a block's contents, committed to in the header,
and thrown away.<Cite src="execution-specs-osaka-fork" /> Nothing persists them between blocks. The
world state trie is the only one that carries forward.

<Check type="explain" concept="mpt-secure-trie">
A team is designing an application-specific chain and proposes dropping the key hashing from their
state trie. Their argument: "our addresses are issued by us, sequentially, so nobody can grind for a
prefix. We get shallower tries, cheaper proofs, and — this is the real win — we can enumerate all
accounts by walking the trie, which kills our need for an indexer."

Is the argument sound? What are they actually trading?

<Answer>
**The argument is internally consistent, and the trade is real. Both of their claimed wins are
genuine, and both of the costs are structural.**

Taking it apart:

*The security premise holds only as long as issuance stays centralised.* Sequential issuance means
they control the key set, exactly as Ethereum's protocol controls transaction
indices.<Cite src="execution-specs-osaka-fork" /> The moment any path exists for a user to influence
their own identifier — a vanity scheme, a counterfactually-derived address, a migration that imports
foreign keys — the grinding attack is back, and it is back against a structure with no defence in it.

*They have only secured half the key space.* Addresses are one thing; storage keys are another, and
the same proposal leaves those unhashed too. A user calling a mapping-heavy contract chooses the
mapping key, and a chosen mapping key becomes a chosen slot number by a documented, public
formula.<Cite src="solidity-layout-storage" /> Sequential *account* issuance says nothing about that,
so the grinding attack survives the premise entirely — it just moves one level down, into a storage
trie.

*The enumeration win is real and is the mirror image of the cost.* If the path is the key, then
walking the trie recovers every key, and no separate index is needed. It is worth being explicit
that this is the same property viewed from the other side: Ethereum did not lose enumeration by
accident, and this chain does not gain it by cleverness. One decision, two names.

*The proof cost claim is the shakiest part.* Sequential keys are short and dense, so paths are short
and the trie is shallow — genuinely cheaper. But clustered keys mean that inserting a new account
often restructures nodes many existing proofs depend on, and short paths make it far more likely that
nodes fall under the 32-byte inlining threshold, so proof *shape* varies with data in a way uniform
64-nibble paths do not. Uniformly distributed paths spread that churn out.

*And there is a privacy consequence they did not mention.* A secure trie does not hide anything from
someone who knows the address — they can hash it and look. What it does is prevent bulk recovery of
the key set from the structure alone. Dropping it publishes the complete list of every account
identifier that has ever held state, forever, to anyone who syncs. For an application chain that may
be exactly what they want. It should be a decision rather than a side effect.
</Answer>
</Check>

## Where this pays off

This lesson is where several loose facts snap together. The missing enumeration primitive from
lesson 1 is now explained by a mechanism rather than asserted. The uniform 64-nibble path from
lesson 3 is now something bought deliberately. And the seventeenth branch slot from lesson 5 turns
out to be a case the definition must cover that neither of Ethereum's key schemes actually
produces — one hashes every key to the same length, the other inherits prefix-freeness from
RLP.<Cite src="execution-specs-osaka-fork" />

It also sets up the verification work in lesson 9. When you hand `eth_getProof` an address and try
to check the returned nodes yourself, the first step — before any hashing of nodes — is hashing the
address to get the path you are supposed to be walking.<Cite src="eip-1186" /> Skipping it is the
single most common reason a first hand-verification attempt fails, and the failure is silent: you get
a valid-looking exclusion proof rather than an error.
