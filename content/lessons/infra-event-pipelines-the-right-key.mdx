The ticket said: "I sent two transfers and only one shows up." It was wrong in a way that took a
morning to see. She had not sent two transfers. She had sent one transaction, which routed through a
pool, which moved the token twice — one `Transfer` to the pool and one out of it — and the product's
activity feed showed one row.

The pipeline had a primary key of `transaction_hash`. The second `Transfer` had been written, found a
row with that key already present, and been discarded by an `ON CONFLICT ... DO NOTHING` clause that
somebody had added specifically to make ingestion idempotent. The idempotency was real. The key was
wrong, so the idempotency was deduplicating distinct events.

That is the failure this lesson exists to prevent, and it is worth stating in its most uncomfortable
form: **an idempotent write on the wrong key is worse than no idempotency at all**, because it deletes
data confidently and silently, and every retry makes the table look more stable rather than less.

## Why the transaction hash is not a key

Two independent reasons, and each is sufficient on its own.

**One transaction emits many logs.** You know this from
[the shape of a log record](/c/log-record-shape) — a transaction's receipt carries an array, and a
single call frame can emit up to four topics per log across as many logs as it likes. A router swap
routinely produces six or more. The JSON-RPC log object even tells you so structurally: it carries
both a `transactionHash` and a separate `logIndex`, described as the integer of the log index
position **in the block**.<Cite src="ethereum-org-json-rpc" /> If the hash identified the event, the
second field would not need to exist.

**The same transaction can appear on two branches.** A transaction that was in a block which gets
replaced may be re-included in the replacement, at a different position, producing logs with different
positional identifiers. The hash is the same in both cases, because it is a hash of the transaction,
not of where the transaction landed. So the hash is stable across branches in exactly the way that
makes it useless: it does not distinguish the version of history you are looking at.

An event is identified by where it sits in the ordered stream:

Ponder's engine uses precisely this ordering: for each chain, indexing functions are called according
to EVM execution order — block number, transaction index, log index.<Cite src="ponder-indexing-overview" />
That is not a coincidence of implementation. It is the only total order the chain actually defines
over events, so it is the only thing that can serve as both a sort key and an identity.

### The honest detail about `transaction_index`

`log_index` is already scoped to the block, not to the transaction — the JSON-RPC definition says
position in the block.<Cite src="ethereum-org-json-rpc" /> So `(chain_id, block_number, log_index)` is
already unique, and `transaction_index` is redundant *for uniqueness*.

Include it anyway, for two reasons that are not about uniqueness:

1. **It is half the sort key.** Any query that orders events the way the chain does needs it, and
   putting it in the primary key gets you the index for free.
2. **It is the join to the transaction.** Without it, going from a row to "what else happened in the
   same transaction" is a second lookup.

Being precise about which columns are load-bearing and which are convenient is worth the sentence,
because someone will eventually ask why the key has four columns when three would do, and "it is the
execution order" is a better answer than "that is what the blog said".

### The block-hash variant

```
(chain_id, block_hash, log_index)
```

is equally correct and carries one extra piece of information: which branch the row came from. During
reorg handling that is exactly the fact you want, and it is exactly the fact `block_number` throws
away — two competing blocks share a number and differ in hash. The detection signal every streaming
product uses is built on this: QuickNode's Streams identifies a reorg when a new block's parent hash
does not match the hash of the previous block that was streamed.<Cite src="quicknode-streams-reorgs" />

The trade is that block-number keys sort and range-scan naturally and block-hash keys do not. The
common resolution is to key on the number form and carry `block_hash` as a non-key column, so you can
still ask "which of my rows came from a block that is no longer canonical" with a single query. Do
that from day one; adding the column later means backfilling it, and you cannot backfill a hash for a
branch that no longer exists.

### Chain id is not optional, even when you have one chain

Ponder's isolated ordering mode makes this structural: every table must have a composite primary key
that includes a column named `chainId`, and the build step fails if any table does
not.<Cite src="ponder-isolated-indexing" /> Under the hood that lets Ponder partition tables by chain,
which removes contention between concurrent writers and speeds up single-chain
queries.<Cite src="ponder-isolated-indexing" />

You may have one chain today. The cost of the column now is four bytes; the cost of adding it later is
a migration of every row, every index and every query in the product. This is the cheapest decision in
the module.

### From a viem log to a row, without losing anything on the way

The key is four columns; getting them out of the client without a silent narrowing is worth doing
once, carefully. viem's `Log` type is generic over two parameters — `quantity`, defaulting to
`bigint`, and `index`, defaulting to `number` — so `blockNumber` arrives as a `bigint` while
`logIndex` and `transactionIndex` arrive as plain numbers, and `blockHash`, `blockNumber`,
`logIndex`, `transactionHash` and `transactionIndex` are all typed as `null` when the log is
pending.<Cite src="viem-src-log-type" /> The block-range parameters are bigints too: the documented
scoping example passes `fromBlock: 16330000n`.<Cite src="viem-get-logs" />

```ts
// viem 2.x
const rows = logs.map((log) => {
  if (log.blockNumber === null || log.logIndex === null) {
    throw new Error("pending log reached the ingester");   // never write these
  }
  return {
    chainId,
    blockNumber: log.blockNumber,        // bigint -> SQL bigint
    transactionIndex: log.transactionIndex,
    logIndex: log.logIndex,
    blockHash: log.blockHash,            // keep it, non-key
    transactionHash: log.transactionHash,
    amount: log.args.value,              // bigint -> SQL numeric, NOT bigint
  };
});
```

**Subgoal: refuse pending logs at the boundary rather than defaulting them.** Those `null`s are not
hypothetical — they are what the type says a pending log looks
like.<Cite src="viem-src-log-type" /> A `?? 0` anywhere near this mapping writes a row whose key is
`(chain, 0, 0, 0)` and whose second occurrence is silently swallowed by your own `DO NOTHING`.

**Subgoal: keep the two bigints in different SQL types, because they are different sizes.**
`blockNumber` fits comfortably in a 64-bit `bigint`. A `uint256` token amount does not — it needs
`numeric` (arbitrary precision) or a text column, and the moment anything in the path turns it into a
JavaScript `number` you have lost the low digits of every large balance in the system. This is the one
type error in the module that produces plausible numbers rather than errors.

**Subgoal: treat `removed` as a signal, not as a field to store.** The JSON-RPC log object carries
`removed`, defined as true when the log was removed due to a chain reorganization and false if it is a
valid log.<Cite src="ethereum-org-json-rpc" /> Logs returned by a plain range query are canonical as of
that query, so the interesting case is filter-based and subscription-based delivery. Storing the flag
tempts you into keeping non-canonical rows around and filtering them at read time in every query
forever; acting on it belongs in the reorg path, which is the fourth lesson.

## The write: one clause

PostgreSQL's `INSERT` accepts an `ON CONFLICT` clause with a conflict target and a conflict action; the
target can be a list of index columns or expressions with an optional `WHERE` index predicate, or a
named constraint, and the action is either `DO NOTHING` or `DO UPDATE SET ...`.<Cite src="postgres-insert" />

```sql
INSERT INTO transfer_event
  (chain_id, block_number, transaction_index, log_index,
   block_hash, transaction_hash, from_addr, to_addr, amount)
VALUES (...)
ON CONFLICT (chain_id, block_number, transaction_index, log_index)
DO NOTHING;
```

**Subgoal: make the conflict target and the unique index the same object.** `ON CONFLICT` with a
column list requires an inference match against a unique index or
constraint.<Cite src="postgres-insert" /> If your primary key is those four columns, the clause infers
it. If someone later adds a surrogate `id BIGSERIAL PRIMARY KEY` and demotes the natural key to a
plain index, the clause stops matching and inserts start duplicating. **The natural key must be the
constraint, not a comment about intent.**

**Subgoal: choose `DO NOTHING` or `DO UPDATE` on the basis of whether the row can legitimately
change.** For a raw log row, nothing about it can change — a given position in a given block emitted
exactly one log with exactly that payload — so `DO NOTHING` is correct and cheaper. For a *derived*
row (a balance, a position, an aggregate), the replay must recompute, so `DO UPDATE` is correct.
Ponder's documented example takes the second shape, inserting a row and specifying
`onConflictDoUpdate` with the new value.<Cite src="ponder-indexing-overview" />

**Subgoal: verify idempotency the only way that means anything.** Run the same block range twice into
an empty database and once into a database that already has it, and compare a checksum over the whole
table, not a row count. A row count catches duplicates; it does not catch a `DO UPDATE` that writes a
different value on the second pass because it read something time-dependent.

<Aside kind="warn">
`ON CONFLICT DO UPDATE` cannot affect the same row twice within one statement — PostgreSQL raises an
error rather than silently picking one.<Cite src="postgres-insert" /> A batch insert of 1,000 events
that contains the same natural key twice will therefore fail the whole batch. That is the correct
behaviour and it is also a signal: if it fires, your fetch produced a duplicate inside a single chunk,
which means an overlapping range, not a redelivery.
</Aside>

## At-least-once is the floor, not a vendor's shortcoming

Every mechanism that can deliver an event to you can deliver it twice, because every one of them can
crash between handing you the message and recording that it did so. This is not a defect list. It is
the honest guarantee, and each transport documents it in its own vocabulary.

**Webhooks retry on your failure.** Alchemy's webhook documentation states that webhooks have built-in
retry logic with exponential backoff for non-200 response codes when it fails to reach your server,
with the backoff extending up to 10 minutes for Free and Pay-As-You-Go teams and up to 1 hour for
Enterprise.<Cite src="alchemy-notify-webhooks" /> A 200 that your process emitted and then died before
committing is indistinguishable, from the sender's side, from a 200 that worked.

**Streams redeliver on reorg by design.** QuickNode's Streams re-delivers affected blocks with updated
data when a reorg occurs, exposes `reorgs` and `blocks_reorged` metadata fields in the payload, and —
this is the sentence worth pinning to the wall — tells PostgreSQL users directly that re-streamed
blocks may conflict with existing rows and that you should implement an upsert strategy such as
`ON CONFLICT ... DO UPDATE` in your ingestion logic.<Cite src="quicknode-streams-reorgs" /> A vendor
whose product handles reorgs still requires your write to be idempotent. That is not a gap in their
product; it is where the responsibility genuinely sits.

**Subscriptions replay from a point.** A dropped socket that re-establishes has to resume from
somewhere, and whatever it picks is either behind where you were, which duplicates, or ahead, which
loses.<Cite src="geth-pubsub" /> Bilinear's write-up recommends running polling alongside subscriptions
precisely because the subscription's failure is silent.<Cite src="bilinear-indexing-events" />

**Cursor resumes reprocess.** A crash mid-chunk leaves the last range partially written, and the
restart re-runs it. That is the next lesson's subject, and it is only harmless because of this one.

**And your own retries are a transport too.** The retry middleware that keeps a backfill alive across
a provider blip — Bilinear recommends configuring one with exponential backoff rather than writing it
yourself<Cite src="bilinear-indexing-events" /> — will happily re-issue a request whose response you
already partially consumed. That is the same at-least-once shape arriving from inside your own process,
which is worth noticing because it is the one case where "the vendor should fix it" is not available.

  why="'Exactly-once' appears on the marketing page while the redelivery behaviour appears in the reorg-handling page, which is three clicks deeper and read by fewer people."
  src="quicknode-streams-reorgs"
/>

The framing that survives contact with production: **the transport's job is to deliver at least once;
your job is to make the second delivery a no-op.** Split that way, nobody is at fault and the fix is
one clause.

## Worked example: migrating a table that keyed on the hash

This is the repair for the opening scene. Four subgoals, each with a purpose.

**Subgoal: measure the damage before changing anything, because the old table cannot tell you what it
discarded.** The rows that were dropped are not in the table; they are only in the chain. So you
cannot count them from the database. You re-fetch a bounded historical window with
`eth_getLogs`<Cite src="execution-apis-getlogs-method" />, count the logs the chain reports, and
compare against the rows you hold for that window. The difference is your loss rate, and it is the
number that gets the migration prioritised.

**Subgoal: build the new table alongside, so the cutover is a read switch rather than a rewrite.**
Create `transfer_event_v2` with the four-column natural key, plus `block_hash` as a non-key column.
Backfill it from the chain — not from the old table, which is missing the rows you are trying to
recover.

**Subgoal: gate the cutover on a diff, not on the backfill finishing.** Dual-run: both tables ingest
for a period, and a scheduled query compares them over a window that is safely below finality, since
finalized history cannot be re-orged outside of manual intervention driven by community
coordination<Cite src="execution-apis-block-tags" /> and therefore both sides should agree exactly.
Cut over when the diff is empty for a stated duration, not when the job says done.

**Subgoal: keep the transaction hash, demoted.** It is still the right thing to link to an explorer
and the right thing to group by when a user asks "what happened in this transaction". It was never
useless — it was misfiled as an identity.

<Check type="spot-bug" concept="idempotency-via-upsert">
An engineer is fixing a double-counting bug in a pipeline that ingests `Transfer` events and
maintains a `holder_balance` table. Their patch:

```sql
-- raw events: idempotent
INSERT INTO transfer_event (chain_id, block_number, transaction_index, log_index, from_addr, to_addr, amount)
VALUES (...)
ON CONFLICT (chain_id, block_number, transaction_index, log_index) DO NOTHING;

-- derived balance: apply the delta
INSERT INTO holder_balance (chain_id, address, balance)
VALUES ($1, $2, $3)
ON CONFLICT (chain_id, address) DO UPDATE
  SET balance = holder_balance.balance + EXCLUDED.balance;
```

Both statements have an `ON CONFLICT` clause on a correct natural key. The double counting continues.
Explain why, and give the smallest fix.

<Answer>
**The second statement is idempotent as a statement and not idempotent as an operation.** `ON CONFLICT`
guarantees that running the *insert* twice does not create two rows. It says nothing about the
*effect*. `SET balance = holder_balance.balance + EXCLUDED.balance` accumulates: run it twice with the
same event and the balance is wrong by exactly one transfer amount, with no duplicate row anywhere to
find it by.

**Why the first statement is genuinely safe and the second is not.** A raw log row is a fact about a
fixed position — nothing about it changes on replay, so `DO NOTHING` is a true no-op. A balance is a
fold over facts. Replaying an increment is not a no-op, because addition is not idempotent.

**The smallest fix: make the derived update conditional on the event being new.** Do both writes in
one statement so the raw insert decides whether the derived update happens at all:

```sql
WITH ins AS (
  INSERT INTO transfer_event (chain_id, block_number, transaction_index, log_index, from_addr, to_addr, amount)
  VALUES ($1, $2, $3, $4, $5, $6, $7)
  ON CONFLICT (chain_id, block_number, transaction_index, log_index) DO NOTHING
  RETURNING to_addr, amount
)
INSERT INTO holder_balance (chain_id, address, balance)
SELECT $1, to_addr, amount FROM ins
ON CONFLICT (chain_id, address) DO UPDATE
  SET balance = holder_balance.balance + EXCLUDED.balance;
```

`RETURNING` on an `ON CONFLICT DO NOTHING` insert returns rows only for insertions that actually
happened<Cite src="postgres-insert" />, so a redelivered event produces an empty CTE and the increment
never runs. Both writes are in one statement, therefore one
transaction<Cite src="postgres-transactions" />, therefore there is no window where the event exists
and the balance does not.

**The structural version of the same answer.** There are two families of ingestion write and they need
different treatments: **facts**, keyed on the event's position, safe under `DO NOTHING`; and
**folds**, which must either be recomputed from the facts rather than incremented, or be guarded by
the fact's insertion. Frameworks resolve this by owning both sides — Ponder rolls the whole database
back through a transaction log rather than trying to make every derived update
commutative.<Cite src="ponder-indexing-overview" /> If you are hand-rolling, the guarded-CTE shape
above is the version that fits in one screen.

**And the trap the opening scene fell into.** Notice that neither statement here keys on
`transaction_hash`. If the first one did, the `DO NOTHING` would discard the second `Transfer` of a
two-hop route, the guarded increment would correctly not fire, and the balance would be consistently,
reproducibly, idempotently wrong.
</Answer>
</Check>

## What this unlocks

The natural key is the load-bearing decision in the module, and almost everything after this depends
on it.

- **Retries and parallelism.** A chunk is independently retryable only because re-writing it is a
  no-op, which is only true keyed on position.
- **Crash recovery.** The next lesson can resume from a cursor without checking what it already wrote,
  because rewriting is free.
- **Reorg reconciliation.** When a branch is replaced, "which rows came from the abandoned branch" is
  answerable only if you kept `block_hash`. Envio's rollback covers the entities in your
  schema<Cite src="envio-reorgs" /><Cite src="envio-indexing-and-reorgs" />; if you replicate
  downstream, the hash column is how your replica answers the same question.
- **Cross-chain.** The `chain_id` in the key is what stops two chains' events from being silently
  merged, which is the last lesson in this module.

The thing to do this week is smaller than a migration: run `SELECT count(*)` against your event table
for one busy day, then re-fetch the same day's logs from the chain and count those. If the two numbers
differ, you already know which of them is right.
