Two engineers each say "we need to migrate our indexer". One of them is describing an afternoon. The
other is describing six weeks. Both are correct, and the sentence does not distinguish them.

This lesson prices both, and then closes the module with the axis that no comparison table contains:
what you give up, in neutrality, by choosing whichever option is fastest — and for which products that
loss is the whole architecture rather than a footnote.

## Migration A: the same artifact, a different host

If your fold is a subgraph and it works, moving it is a deploy-target change.

Goldsky documents a one-step migration from a subgraph on The Graph's decentralised network, keyed on
the IPFS hash shown on that subgraph's Explorer page:<Cite src="goldsky-migrate-from-the-graph" />

```bash
goldsky subgraph deploy your-subgraph-name/your-version \
  --from-ipfs-hash <your-subgraph-ipfs-hash>
```

The vendor frames this as a drop-in replacement offering the same subgraph API your apps already use,
for a zero-downtime migration.<Cite src="goldsky-migrate-from-the-graph" /> Take the marketing framing
as marketing framing, and the structural claim as the durable part: **the artifact travelled, so the
work is a deployment rather than a rewrite.** That is only possible because the manifest, schema and
mappings are a portable document and the receiving host runs the same WASM processing
layer.<Cite src="goldsky-subgraphs-docs" />

This is why the previous module insisted the subgraph format's portability is an asset separate from
any host's existence. When Alchemy sunset its subgraph service on 8 December 2025 and directed users to
Goldsky,<Cite src="alchemy-subgraphs-sunset" /> the affected teams had a bad week rather than a bad
quarter. Other operators accept the same
files.<Cite src="ormi-labs" /><Cite src="envio-docs" /><Cite src="protofire-indexer-comparison" />

What still costs you something, even here:

- **Endpoint churn.** URLs change, authentication changes, and every consumer — frontend, backend jobs,
  partner integrations, that one internal dashboard — has to be repointed.
- **Behavioural differences under the same API.** Different infrastructure means different latency,
  different rate limits and different behaviour under load. The query language is identical; the
  service is not.
- **Re-indexing time.** The new host starts from your start block. You are still waiting for a
  backfill, which is the same clock as any other migration.

Call it days, dominated by the backfill and the repointing.

## Migration B: the same intent, a different framework

Now the case people mean when they are worried. Moving a subgraph to Ponder, or Envio, or the reverse.
It is neither a port nor a rewrite; it is both, unevenly, and the parts are not the ones people
estimate.

**What carries over almost mechanically.** The entity schema — your tables are your tables, and the
field types translate. The event set — the same contracts, the same signatures, the same start blocks.
The intent of each derived field, which is the part that took the original design work.

**What is rewritten.** The mapping logic, because the languages and the entity APIs differ:
AssemblyScript with `new Entity(id)` and `.save()` becomes TypeScript with an insert-and-conflict-update
against a typed schema.<Cite src="ponder-docs" /> The configuration format. Factory registration, which
sits in a different place in each framework. Contract reads inside handlers, which have different
batching and caching stories.<Cite src="envio-docs" />

Both of those are estimable. A team can look at fifteen handlers and say "two weeks", and be roughly
right.

**And neither of them is where the time goes.**

### The time goes into the backfill and the diff

The expensive part of any framework migration is running the fold twice and explaining every place the
two results differ.

**Re-run the full historical backfill on the new system.** Not a sample. The full range, because the
purpose is to produce a dataset comparable to production. This is the wall-clock cost the benchmarks
are actually about, and it is the one place a speed difference between platforms converts directly into
project duration.

**Dual-run both systems against live data.** Old and new, side by side, both writing, for long enough
to cover the workload's variety — a month-end, a governance action, a volatile day, whatever your
protocol's unusual events are.

**Diff row by row, and explain every difference.** This is the work.

The diff query is a full outer join on the natural key — [the composite
key](/c/log-natural-key), never the transaction hash, because one transaction emits many logs:

```sql
SELECT COALESCE(o.chain_id, n.chain_id)         AS chain_id,
       COALESCE(o.block_number, n.block_number) AS block_number,
       COALESCE(o.log_index, n.log_index)       AS log_index,
       o.amount AS old_amount,
       n.amount AS new_amount
FROM   old_transfers o
FULL OUTER JOIN new_transfers n
  ON   o.chain_id = n.chain_id
 AND   o.block_number = n.block_number
 AND   o.log_index = n.log_index
WHERE  o.log_index IS NULL
   OR  n.log_index IS NULL
   OR  o.amount IS DISTINCT FROM n.amount;
```

Three kinds of row come back, and each means something different. Rows only in the old table: either
the new system is missing data, or the old system had fossils from a mishandled reorg. Rows only in the
new table: either the new system is over-counting, or the old one was silently dropping records. Rows
in both with different values: a semantic difference in the transition, which is the interesting case.

### Most diffs are not bugs in the new system

This is the part that catches teams by surprise, and the previous two lessons already gave you the
evidence for it.

On the factory-template workload, six platforms indexing the same contracts over the same block range
reported 35,039, 75,951, 33,972, 182,767, 75,951 and 35,039 records — against 35,039 expected. The
benchmark's authors are explicit that this is not a bug in any platform: there is no industry standard
for what counts as a template event, with some platforms counting only events from dynamically created
contracts, others including factory events, and others counting differently when one transaction fires
events across several related contracts.<Cite src="sentio-obib" />

A five-fold difference in row count, produced by a definitional disagreement nobody wrote down.

Now imagine meeting that difference during a migration diff rather than in a benchmark table. You would
spend days assuming one system was broken. Neither is. The old system encoded a semantic your product
has been consuming for two years, and the new one encodes a different one — and your dashboards,
alerts, and anything downstream were calibrated against the old semantic.

The same shape shows up in more mundane places: the benchmark records that Subsquid's
`.addTransaction()` silently skips blocks with no transactions, dropping roughly 87% of an early-history
range without a warning.<Cite src="sentio-obib" /> A diff between a system using it and one using
`.includeAllBlocks()` would show an enormous discrepancy with no error anywhere to point at.

**So the real deliverable of a migration is not the new indexer. It is the written list of every
semantic difference you found and what you decided to do about each one.** That document is also, not
coincidentally, the first honest specification your derived data has ever had.

### The cutover criterion

A migration without a stated cutover criterion ships its own bugs. State it as a predicate, in advance:

> Zero row-level differences on the reconciliation query across the last 10,000 blocks, sustained for
> 24 hours of dual-running, with every historical difference either resolved or recorded in the
> semantic-differences document with an accepted rationale.

Three properties make that usable. It is **falsifiable** — you run a query and get a number. It is
**bounded** — 10,000 blocks and 24 hours, not "until we feel good". And it has an **escape hatch that
requires writing something down**, because some differences are genuinely acceptable and the cost of
accepting one should be a paragraph explaining why.

<Aside kind="note">
One thing the diff cannot cover, and it belongs in the plan explicitly: anything downstream that keyed
on the old system's identifiers. If the old indexer generated entity ids in its own format and your
analytics warehouse, your partner exports or your support tooling stored those ids, the new system's
ids will not match, and no row-level diff on the natural key will tell you. Inventory the consumers
before cutover, not after — this is the same reasoning as the reorg lesson's downstream boundary,
applied to a different kind of change.
</Aside>

## What you give up by choosing the fastest thing

Now the axis nobody prices, and the one that matters for a specific and small class of product.

Every performance-competitive option in this field is a centralised service. Envio's hosting, Goldsky,
Ormi, Sentio, a Ponder instance on your own cluster — each has exactly one operator, and that operator
can deprecate the product, reprice it, or be compelled to stop serving a particular consumer. That is
not a hypothetical risk in this market: The Graph's own hosted service stopped serving queries in June
2024,<Cite src="thegraph-sunsetting-hosted-service" /> and Alchemy Subgraphs was sunset on 8 December
2025 with all endpoints discontinued.<Cite src="alchemy-subgraphs-sunset" />

The Graph's decentralised network is the one option in the query layer with a credible neutrality
claim, and the mechanism is worth stating precisely rather than as a slogan. Publishing a subgraph is
an on-chain action. It makes the subgraph indexable by the network's independent indexers, removes the
rate limits of the development environment, makes it searchable and queryable in Graph Explorer, and
makes it available for curators to signal on.<Cite src="thegraph-quick-start" /> Curation is the
incentive mechanism that gets independent operators to index your data at all, and the documentation
recommends 3,000 GRT or more.<Cite src="thegraph-quick-start" />

Read that as an architecture rather than as a product: **the thing serving your queries is a set of
independent operators paid to do so, rather than one company that agreed to.** Removing any one of them
does not remove your data.

The honest accounting has three entries on the other side.

**It is not free, and the free tier is a development allowance.** Subgraph Studio offers 100,000
queries per month,<Cite src="thegraph-sunsetting-hosted-service" /> and a Studio deployment is
rate-limited, not publicly visible, and served by a single indexer operated by Edge &
Node.<Cite src="thegraph-quick-start" /> Production is the network, and the network is a cost with an
unusual shape — a transaction, plus a signal denominated in a volatile asset.

**It is not the fastest.** The open benchmark's slowest entry on the events-only case was the subgraph
path at 188.79 minutes against 6.94 for the fastest platform.<Cite src="sentio-obib" /> Neutrality is
purchased with sync time, among other things.

**And it is neutrality of exactly one layer.** Your frontend is hosted somewhere. Your domain has a
registrar. Your users reach you over a network path someone operates. An unstoppable query layer
underneath a takedown-able everything else is a partial claim, and the useful version of this argument
is always about which specific component is the weakest link.

**Who should actually care.** For most products, this axis does not decide anything, and pretending
otherwise is how teams end up paying for a property they do not use. Ship the thing that fits the
first four gates.

For one class it decides everything: a protocol whose proposition is that its interface cannot be shut
down. For that protocol, a centralised indexer is the component that quietly makes the claim false —
and the honest version of its architecture diagram says so, in writing, where users can read it. That
is not a technical requirement. It is a truthfulness requirement, and the engineering follows from it.

<Check type="explain" concept="migration-cost-shape">
A team runs a subgraph on a third-party host. Two things happen in the same month: the host announces
a price increase, and the product adds a requirement to account for ETH received through internal
contract calls.

An engineer proposes: *"Both problems, one migration. Move to a trace-capable framework, two sprints,
and we get off the host at the same time."*

Price the proposal honestly, and say what you would change about the plan without changing the
destination.

<Answer>
**The destination is probably right and the estimate is probably wrong, for a specific reason.**

**The two problems have very different natural solutions.** The price increase alone is a Migration A —
the artifact is portable, another host accepts the same files, and the cost is repointing consumers
plus a re-index.<Cite src="goldsky-migrate-from-the-graph" /> Days. The trace requirement is not
solvable that way at all: subgraph-style indexing measured 58% completeness on traces with sender
attribution broken,<Cite src="sentio-obib" /> so no change of host fixes it. That one requires a
different framework, which is a Migration B.

**So the bundling is sound.** If you must do B anyway, doing A for free inside it is correct. The
engineer's instinct is right.

**The two-sprint estimate is the problem, and predictably so.** Two sprints is a plausible number for
the part that is visible: rewriting fifteen handlers from AssemblyScript into
TypeScript.<Cite src="ponder-docs" /> It contains no allowance for the full historical backfill, none
for a dual-run period, and none for reconciling the diff — and the diff is where the surprises live,
because a trace-capable system will legitimately produce *more rows than the old one for the exact
reason you are migrating.* Those extra rows are the deliverable, and every one of them will look like a
discrepancy until someone proves it is not.

**What I would change without changing the destination.**

*Split the timeline, not the destination.* Handler rewrite: two sprints, fine. Backfill: measured, not
guessed — run it once on a bounded range first and extrapolate. Dual-run and reconcile: its own phase
with its own exit criterion.

*Write the cutover criterion before starting.* Zero unexplained row-level differences on the natural
key over a bounded range for a bounded period, with a document listing every accepted difference and
why. Without it, "done" is a feeling.

*Expect the diff to be large and to be right.* Pre-agree with whoever consumes this data that fee
totals will move upward at cutover, that this is the bug being fixed rather than a new one, and that
historical reports will restate. Discovering that conversation during the dual-run is how migrations
lose a month.

*Handle the price increase separately if the timeline slips.* The host migration is days and
independent. Coupling a cheap urgent fix to an expensive careful one gives you the worst schedule of
both.

**And one thing to check before any of it.** Does the target framework support traces on every chain in
scope — including at the provider level, which is a separate question from framework
support.<Cite src="sentio-obib" /> A migration that lands on a platform that cannot satisfy the
requirement on your second chain has spent two sprints to arrive at the same problem.
</Answer>
</Check>

## What this unlocks

You have finished the two modules that turn "we need an indexer" from a shopping question into an
engineering one.

You can state what an indexer is — a deterministic fold over a rewritable ordered stream — and derive
its hard parts from that definition rather than memorising them. You can read a subgraph, and you know
which host still exists and how to check on the day. You can separate catching up from keeping up and
say which of them a published number describes. You can force a reorg on purpose and say exactly where
the framework's rollback stops. You can place any framework you have never seen on the declarative
dial, the data-source axis and the operating-model axis in five minutes. You can read a benchmark's
methodology section and name three ways it could still mislead you without anyone lying. You can run
four capability gates that eliminate candidates before speed is consulted. And you can price a
migration in both directions, which is the only thing that makes a dependency decision reversible.

**Next, the event pipelines module** takes the boundary this module kept pointing at. The indexer's
rollback covers the indexer's tables and nothing beyond them — so natural keys, idempotent writes,
cursors committed in the same transaction as the rows they describe, gap detection, and the discipline
of gating every irreversible action on finality are what stand between a correct indexer and a correct
product.

**And the monitoring module** turns the invariants you learned to write in Foundry into predicates
evaluated against mainnet state, which is the same skill pointed at a system that is already
live.
