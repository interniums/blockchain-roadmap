Three teams are asked to do the same thing: turn a token's `Transfer` events into a balances table.
All three produce a deterministic fold. All three end up with the same rows. The artifacts they write
look almost nothing alike, and the differences between them are not stylistic — each one makes a
different trade about who declares what, who runs the process, and where the data comes from.

This lesson is that comparison, done properly. By the end you should be able to look at any indexing
framework you have never seen and place it on three axes within about five minutes of reading its
quick start.

## The same fold, three ways

### Model one: declarative manifest plus sandboxed mapping

You met this in the previous module. Three files: a manifest naming contracts, events and start
blocks; a GraphQL schema naming the entities; and handlers in AssemblyScript compiled to WebAssembly
and executed by the runtime.<Cite src="thegraph-quick-start" />

The defining property is that **two thirds of the definition is declarative**. A host can read your
manifest and schema without executing anything, which is what makes it safe and tractable to run
somebody else's subgraph on shared infrastructure. That property is the reason multiple independent
operators accept the format, and the reason the format outlived its original host.

The cost is at the handler. The mapping language is a constrained subset, the execution environment is
a sandbox rather than Node, and the ergonomics of debugging follow from both.

### Model two: everything in TypeScript, against Postgres

Ponder inverts the split. It is an open-source TypeScript framework for EVM data indexing: you write
TypeScript that transforms on-chain data into your application's schema, and it fetches the data, runs
your logic, and writes the result to Postgres. Once indexed, you query through GraphQL, SQL over HTTP,
or directly in Postgres.<Cite src="ponder-docs" />

There is no manifest in another language and no schema in another language. The configuration is
TypeScript, the schema is TypeScript, and the handlers are TypeScript.

```ts
// ponder.config.ts — the input specification
import { createConfig, factory } from "ponder"
import { parseAbiItem } from "viem"
import { PoolAbi } from "./abis/Pool"

export default createConfig({
  chains: { mainnet: { id: 1, rpc: process.env.PONDER_RPC_URL_1 } },
  contracts: {
    Pool: {
      abi: PoolAbi,
      chain: "mainnet",
      address: factory({
        address: "0xb16c1342e617a5b6e4b631eb114483fdb289c0a4",
        event: parseAbiItem("event NewPair(address poolAddress)"),
        param: "poolAddress",
      }),
      startBlock: 12369621,
    },
  },
})
```

The `factory()` helper is worth pausing on, because it is the clearest example of what "everything in
TypeScript" buys and what it costs. Ponder describes it as returning a list of addresses that updates
whenever a log matching the configuration is found — you give it the factory's address, the event that
announces a child, and the name of the parameter carrying the child's address.<Cite src="ponder-factory" />
It is a *declaration expressed as a function call*: the framework can still see it before running your
handlers, because it is evaluated at config time and not inside a handler.

Note also `process.env` in the config. That is a genuine convenience — and it is the reason the
configuration cannot be shipped to a third party as a document. The declarative-versus-programmatic
trade is not free in either direction.

The handler is ordinary code with ordinary tooling around it:

```ts
import { ponder } from "ponder:registry"
import { account } from "ponder:schema"

ponder.on("Token:Transfer", async ({ event, context }) => {
  await context.db
    .insert(account)
    .values({ address: event.args.to, balance: event.args.value })
    .onConflictDoUpdate((row) => ({ balance: row.balance + event.args.value }))
})
```

Two things follow from this shape and they are the whole pitch. **Your debugger works.** It is Node;
breakpoints, `console.log`, the profiler and your test runner all behave normally. And **the output is
a database your team already knows how to query** — the docs list direct SQL access as a first-class
query path alongside GraphQL.<Cite src="ponder-docs" /> That matters more than it sounds: a data team
can join your indexed tables against your product's own tables without an API in between.

The trade is that you are running it. Ponder's production documentation covers deploying to Railway
and self-hosting, and ships a status endpoint and metrics separately from a liveness
check.<Cite src="ponder-docs" /><Cite src="ponder-observability" /> A stateful service with a database
is now yours.

### Model three: declarative config, familiar handlers, different data source

Envio HyperIndex looks like a hybrid at the surface. There is a `config.yaml` naming chains, contracts
and events — a manifest in all but name — a `schema.graphql`, and handlers in the TypeScript
family.<Cite src="envio-docs" />

```yaml
name: nftindexer
chains:
  - id: 1337
    start_block: 0
    contracts:
      - name: NftFactory
        abi_file_path: abis/NftFactory.json
        address: "0x4675a6B115329294e0518A2B7cC12B70987895C4"
        events:
          - event: SimpleNftCreated(string name, string symbol, uint256 maxSupply, address contractAddress)
      - name: SimpleNft
        abi_file_path: abis/SimpleNft.json
        # no address — instances are discovered at runtime
        events:
          - event: Transfer(address from, address to, uint256 tokenId)
```

Factory support is expressed as a registration handler rather than a config helper: a
`contractRegister` callback fires on the factory's creation event and adds the child address, after
which the child's events flow into normal handlers.<Cite src="envio-dynamic-contracts" />

```ts
indexer.contractRegister(
  { contract: "NftFactory", event: "SimpleNftCreated" },
  ({ event, context }) => {
    context.chain.SimpleNft.add(event.params.contractAddress)
  },
)
```

Compare that with Ponder's `factory()` for a moment. Ponder's version is a pure declaration the
framework evaluates up front; Envio's is code that runs during indexing. Envio's is more flexible —
you can branch, filter, or derive the address — and Ponder's is more inspectable. Same capability, two
places on the declarative/programmatic dial, and the dial is the actual subject of this lesson.

## The part that is not at the handler

Now the difference that matters, and it is underneath all three models rather than inside any of them.

HyperIndex's backfill does not read from a JSON-RPC endpoint by default. It reads from **HyperSync**, a
purpose-built data retrieval layer for on-chain data written in Rust, presented as an alternative to
traditional JSON-RPC that lets you filter and select exactly the fields you
need.<Cite src="envio-hypersync-overview" /> Envio's supported-networks documentation states the
selection rule plainly: if a network is supported on HyperSync, HyperSync is used by default as the
data source; if it is not, you configure RPC as the data source
instead.<Cite src="envio-supported-networks" />

That single architectural choice is where the backfill performance difference comes from, and
understanding it explains two otherwise puzzling things.

**Why tuning a subgraph's mappings cannot close the gap.** The mappings are not the bottleneck. Bulk
historical retrieval over JSON-RPC is bounded by a protocol designed for point queries: each log query
names a range, providers cap that range per plan and per chain, responses are capped by size —
Alchemy publishes a hard 150MB ceiling and advises splitting wide queries<Cite src="alchemy-eth-getlogs" /> —
every request carries protocol overhead, and
[the concurrency limit](/c/rate-limit-two-axes) caps how many you can have in flight. Halve your chunk
size and you double your request count. You are optimising inside a box whose walls are the transport.
A columnar bulk-read API is not in that box.

**Why the coverage question changes shape.** For an RPC-based indexer, "can I index chain X" means "is
there an archive node for X". For HyperIndex the fast path means "is X on HyperSync", which is a
strictly smaller and differently-shaped list.<Cite src="envio-supported-networks" /> The fallback to
RPC exists, so the chain is not unusable — but the property you selected the platform for does not
apply there, which is a much subtler failure than an unsupported chain.

### About the multipliers

You will see very large numbers attached to this mechanism. Handle them carefully, because they do not
agree with each other — including on the same page.

Envio's HyperSync overview describes retrieving and processing data "up to 1000x faster than
traditional RPC methods" in its benefits list, and in an information box on the same page describes
HyperSync as "delivering up to 2000x faster data access".<Cite src="envio-hypersync-overview" /> Both
are that vendor's own characterisation of its own product, published together, differing by a factor
of two.

That is not a reason to dismiss the mechanism, which is real and well explained. It is a reason to
treat every specific multiplier as a claim about a particular workload on particular hardware against
a particular baseline, and to measure your own. The next lesson takes two published benchmarks apart
and shows exactly how numbers this far apart get produced without anyone lying.

<Aside kind="note">
There is a related trap in reading these comparisons at all. HyperSync is a raw data extraction engine
— no schema management, no database, no GraphQL. The benchmark discussed in the next lesson makes the
point explicitly: comparing a raw extraction time against a full indexer's time is comparing a data
dump against a system that parses, transforms, stores and serves.<Cite src="sentio-obib" /> When you
see a number, the first question is not "how fast" but "how much of the job did that number cover".
</Aside>

### A fourth dial you only notice on the second chain

There is one more difference that stays invisible until a product spans two networks, and then becomes
the whole conversation: **what ordering guarantee the framework gives you across chains.**

Within one chain the answer is obvious and universal — handlers run in EVM execution order, by block
number, then transaction index, then log index.<Cite src="ponder-indexing-overview" /> Across chains
there is no such order to inherit, because there is no shared clock, and each framework has to invent
a policy. Ponder documents the cross-chain case separately and notes that the ordering guarantee across
multiple chains is more complex than the single-chain one, with isolated indexing as its own
topic.<Cite src="ponder-indexing-overview" /><Cite src="ponder-isolated-indexing" />

The reason to check this before you commit is that the policy determines whether a handler on chain A
may read state derived from chain B, and that determines whether an entire class of cross-chain
derived field is expressible at all. It is not a performance question and it will not appear in any
benchmark.

## The query surface is a product decision, not a detail

Comparisons treat "how you read the data back" as a footnote. It is not; it decides which teams in
your company can use the indexer without asking you for anything.

**A subgraph gives you GraphQL.** One endpoint, one schema, entity queries with filters and pagination
derived from the entity types you declared. It is a good API and it is the only API. Anything your
consumers want that the query language does not express — a window function, a group-by across
entities, a join against a table that is not on the chain — has to be built as another service in
front of it.

**Ponder gives you three surfaces over the same Postgres**: a GraphQL endpoint, SQL over HTTP, and
direct access to the database.<Cite src="ponder-docs" /> There is also a client library and a React
binding shipped alongside the framework, so the frontend path is a first-party
concern.<Cite src="ponder-docs" />

Consider what "direct access to the database" actually unlocks, because it is the item on that list
that changes the org chart rather than the code. Your analytics team can point their existing warehouse
tooling at it. Your finance reconciliation job can join indexed transfers against your own invoices
table in one query. Someone can answer an ad-hoc question in a psql session at 9pm without deploying
anything. None of that is possible through a fixed GraphQL surface, and all of it is a thing teams end
up building badly when it is not available.

The corresponding cost is the same one as always: that Postgres is yours, including its backups, its
disk, its connection limits and the day someone runs a sequential scan against it during an incident.

## The development loop, which you will feel every day

The last structural difference is the one you experience most often and see in comparisons least.

Ponder is plain Node.js — `create-ponder` scaffolds a project, `pnpm dev` starts a local server that
connects to the database, starts an HTTP server and begins indexing, with a terminal UI and structured
logs.<Cite src="ponder-docs" /> The open benchmark that measured all these platforms characterises it
the same way from the outside: a local Node.js framework, and in its recommendations it singles Ponder
out for self-hosting with minimal setup — plain Node, no Docker.<Cite src="sentio-obib" /> The same
benchmark characterises Envio HyperIndex as a local, Docker-based framework.<Cite src="sentio-obib" />

That difference sounds trivial and is not, for two reasons. A Docker requirement is a constraint on
every machine that runs the project, including CI runners and the laptop of the engineer who joins in
six months. And the inner loop — change a handler, see the result — is the single activity you will do
a thousand times while building a fold, so its latency compounds in a way that a one-off backfill
number never does.

## Placing any framework in five minutes

Three questions, in this order, will locate anything you meet.

**Where does the declaration/execution boundary sit?** How much of your definition can the platform
read without running your code? A manifest-based system can be hosted by strangers and inspected by
tooling. A code-based system can express things a manifest cannot, and requires an execution
environment rather than a document. Watch specifically for how factories are handled — it is the
feature that forces every framework to pick a side, and you have now seen both sides.

**What is the data source during backfill?** JSON-RPC, or something else. This is the throughput
question and the coverage question at the same time, and it is almost never in the comparison table.
Read the docs page that says which chains are supported *by the fast path*, not the one that says which
chains are supported.

**Where does the output land, and who runs it?** A managed GraphQL endpoint, or a Postgres database
you own. This decides whether your data team can join against your indexed tables, and it decides
whether you have a new on-call rotation. It is the subject of the next lesson.

## Worked example: reading a framework you have never seen

Take the three questions and apply them to a hypothetical framework's quick start, naming what each
step is for.

**Subgoal — find the artifact list and count the languages.** If the quick start produces a `.yaml`
plus a `.graphql` plus a handler file, you are looking at a manifest system, and you should expect
portability, sandboxing, and a constrained handler language. If it produces three TypeScript files,
expect ordinary tooling and a configuration that cannot travel.

**Subgoal — search the docs for the word "factory" or "dynamic".** Whatever you find tells you where
the dial sits. A config-time helper means declarations the platform can pre-resolve. A registration
callback means code that runs during indexing. If you find *neither*, stop — you have discovered a
capability gap, and the next lesson but one explains why that is a harder disqualification than any
timing.

**Subgoal — find out what the backfill talks to.** Look for a page named for the data source, or for
an RPC URL in the quick-start config. An RPC URL in the config is not a defect; it tells you the
performance envelope is the transport's envelope, which you can already price from the RPC module.

**Subgoal — find the contract-read story.** Every non-trivial fold eventually needs state the event did
not carry. Envio documents accessing contract state in handlers as its own topic, with caching and
multicall as the efficiency mechanisms.<Cite src="envio-contract-state" /> Ponder documents reading
contract data inside indexing functions.<Cite src="ponder-indexing-overview" /> Whether a platform has
this at all, and what it costs when you use it, is one of the sharpest differentiators there is —
partly because it is where the determinism question from the first module resurfaces.

**Subgoal — find the reorg page and read its limits, not its promise.** Every serious framework now
says "automatic". The information is in the retained window, the detection guarantee, and the list of
things not covered.

**Subgoal — check the repository, not just the docs.** Recent commits, open issue count, how questions
get answered. HyperIndex is developed in the open.<Cite src="hyperindex-repo" /> Ponder is open
source.<Cite src="ponder-docs" /> "Open source" is a licence; "actively developed" is an observation
you make yourself, and the next lesson explains why it deserves its own axis.

<Check type="explain" concept="hypersync-not-rpc">
A team runs a subgraph whose backfill takes eleven hours. They are considering two changes:

**(a)** Rewrite the mappings — batch the entity writes, remove three redundant lookups, and replace a
loop with a single pass.

**(b)** Move to a platform whose backfill reads from a columnar bulk-data API instead of JSON-RPC.

Their mappings genuinely are inefficient; the rewrite would cut handler CPU time roughly in half.
Which change has the larger effect on the eleven hours, and what would have to be true for the answer
to flip?

<Answer>
**(b), and usually by a lot — but the reasoning matters more than the verdict.**

Split the eleven hours into two components: **time acquiring the data**, and **time executing your
transition over it**. The mapping rewrite only touches the second. If acquisition dominates — which it
does for a log-heavy backfill over JSON-RPC, because every chunk is a request bounded by range caps,
response-size caps, per-request overhead and a concurrency limit<Cite src="alchemy-eth-getlogs" /> —
then halving the handler cost halves a small share of the total. Amdahl's law, applied to an indexer.

**A columnar bulk-read data source attacks the dominant component.** It is not a faster RPC; it is a
different protocol shape, built for exactly this access pattern.<Cite src="envio-hypersync-overview" />
That is why "just optimise your subgraph" cannot close the gap and why the handler language is close
to irrelevant to it.

**What would flip the answer.** Three things, each real:

*The handler does per-event network calls.* If each event triggers a contract read, execution is no
longer cheap — it is a serialised round trip per event, and now the transition genuinely dominates. In
that case the mapping rewrite (specifically: batching those reads, or declaring them so the runtime can
prefetch them per block) is the higher-leverage change. Envio documents caching and multicall for this
reason.<Cite src="envio-contract-state" />

*The workload is not events.* The bulk-data advantage is measured on historical retrieval of logs and
similar records. It says nothing about a fold whose cost is elsewhere.

*The chain is not on the fast path.* If the target chain falls back to RPC as the data source, the
platform's headline property does not apply to this migration at all.<Cite src="envio-supported-networks" />
You would have paid a rewrite to arrive at the same transport.

**And the thing neither change touches.** Eleven hours is a backfill number. Neither option is
evidence about live-tail lag, which is the regime the product runs in for the other 364 days of the
year.
</Answer>
</Check>

## Where this goes

You can now describe what actually differs between these platforms without reaching for a speed claim.

**The next lesson takes the axis nobody puts on the comparison grid**: who runs the process, and who
decides where the project goes. Two of the options in this field changed steward between late 2025 and
early 2026, and one of those changes is routinely misread as an obituary.

**Then the benchmarks**, including the two published sets of numbers for the same platforms that differ
by two orders of magnitude — and the mechanism by which that happens without any dishonesty. Envio's
own benchmarks page is one of them.<Cite src="envio-hyperindex-benchmarks" />

**Then capability**, which is the axis that actually eliminates candidates: traces, transactions,
blocks, contract reads inside handlers, and factories — with measured completeness rather than
feature-matrix ticks.
