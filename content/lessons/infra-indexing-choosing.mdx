Everything in this module so far has quietly assumed a log. A record with an address, up to four
topics, a data blob, and a position in a block. That assumption is doing more work than it looks like,
because it is the reason the whole EVM indexing ecosystem shares one shape: consume logs, decode with
an ABI, fold into tables.

Take the log away and the shape does not survive. This lesson covers what indexing looks like when the
event model differs, and then closes the module with the thing the module has been building towards:
a selection procedure that starts somewhere other than a benchmark headline.

## When the source has a different event model

Three quick contrasts, because the differences are structural rather than cosmetic.

**Substrate chains emit runtime events**, produced by pallets during block execution. There is no ABI
in the Solidity sense — the decoding metadata comes from the runtime itself, and it changes when the
runtime is upgraded, which happens on a governance schedule rather than a deployment schedule. An
indexer for these chains has to track metadata versions as a first-class concern.

**Cosmos chains emit typed events attached to transactions**, with attributes as key-value pairs
rather than positional ABI-encoded arguments. Cross-chain activity is carried by IBC packets, whose
lifecycle spans two chains and does not appear as a single record on either.

**Bitcoin has no event model at all.** There is nothing to subscribe to. Indexing means reading
transaction outputs and reconstructing the meaning yourself, which is a different program from
"decode a log against an ABI".

So a framework that reaches these ecosystems is not an EVM indexer with more endpoints configured. It
needs a different source abstraction, and the frameworks that have one advertise it in their project
initialisation: SubQuery's CLI asks you to choose a **network family** before it asks you to choose a
network.<Cite src="subquery-quickstart" /> That prompt is the architecture leaking through the
interface, and it is a useful thing to notice — a tool whose first question is "which family" has been
built for more than one.

<Aside kind="note">
It is worth being precise about why the UTXO case is the hardest of the three. On an account chain,
"who owns what" is a value you can read. On Bitcoin it is a set you must *maintain*: the unspent
outputs, which change with every transaction, and which nothing publishes as a whole. An indexer there
is not folding events into a derived view of state — it is reconstructing the state itself, and the
[UTXO model](/c/utxo-model) you met in the ledgers track — and its
[absence of global state](/c/no-global-state) — is the reason the two jobs are not the same job. Any comparison table that puts a tick in a "Bitcoin" column is compressing a very
different program into the same cell as an EVM log subscription.
</Aside>

### What a genuinely multi-chain project buys, and what it costs

SubQuery's multi-chain support is the clearest documented example of the payoff. One project, with the
same GraphQL schema and the same mapping files, indexes several networks into the **same database**,
served from a single query endpoint; the documentation gives capturing XCM transaction data across
Polkadot parachains, or monitoring IBC messages across Cosmos zones, as the motivating
cases.<Cite src="subquery-multichain" />

The costs are documented alongside it, and they are instructive because they generalise to any
cross-chain read model:

**It is not retrofittable.** The `--multi-chain` argument must be set from the start; adding it later
means deleting and resetting the database.<Cite src="subquery-multichain" /> A decision that must be
made before the first block is indexed is a decision worth making deliberately.

**Every chain gets its own indexing node**, all pointed at one shared schema and one shared Postgres
schema.<Cite src="subquery-multichain" /> Which means the failure modes are per chain — one network
can stall while the others advance, and your single query endpoint will happily serve the mixture.

**The documentation's own tip list names the traps**: ID collisions across networks, handled with
network prefixes; network-specific logic inside shared handlers; and cross-chain race
conditions.<Cite src="subquery-multichain" /> That third one is the deep one. There is no global
ordering across chains, so "the state of the system at time T" is not a well-defined query unless you
define it — the event-pipelines module treats this as
[multichain clock skew](/c/multichain-clock-skew), and it is a design decision rather than a
configuration.

### The other non-EVM route

SQD is the other project with reach beyond the EVM, and it is worth looking at because its shape has
changed. Its documentation now presents a **Portal HTTP API** for raw blockchain data with arbitrary
ranges, streaming and finality handling, two TypeScript SDKs — Squid SDK and Pipes SDK — for decoding,
transforming and persisting, managed hosting as SQD Cloud, and a decentralised data lake behind the
Portal.<Cite src="sqd-docs-home" /> The product site describes the network as a data lake with 2,000
or more worker nodes.<Cite src="sqd-site" />

One small thing to notice, because it is a habit worth having. The documentation home advertises
"140+ networks" while the product site advertises "130+ indexed networks" on the same
day.<Cite src="sqd-docs-home" /><Cite src="sqd-site" /> Neither is a lie; they are almost certainly
counting different things or updated at different times. It is a reminder that a coverage number on a
marketing surface is not the artifact you should be checking — the supported-network *list* for the
version you would actually run is.

## Coverage tables go stale faster than anything else

Here is the evidence for that last point, laid out so you can see the drift.

The open indexer benchmark published a chain-support table for the five platforms it measured: EVM
everywhere; Sui and Aptos only on Sentio; Fuel on Sentio, Envio and Subsquid; Solana on Subsquid, with
Sentio and Subgraph marked limited; Bitcoin on Subgraph with Sentio limited; Envio and Ponder
EVM-only.<Cite src="sentio-obib" /> Its data was collected in January 2026 and it was published in May
2026.<Cite src="sentio-obib" />

Envio's own documentation, read today, describes HyperIndex as supporting any EVM chain plus Solana and
Fuel.<Cite src="envio-docs" /><Cite src="envio-supported-networks" /> That is not the same row as the
one in the benchmark table, and the gap is a matter of months, not years.

Neither source is wrong. The benchmark is a dated measurement of a pinned version; the vendor
documentation describes the current one. The lesson is procedural: **read coverage off the
supported-networks page of the version you would run, on the day you decide, and never off a
comparison article.** Third-party comparisons are useful for discovering that an option exists — one
such survey is where most people first encounter the full field.<Cite src="protofire-indexer-comparison" />
They are not a source for whether a specific chain is supported, and one host they listed was
discontinued before the year they were published ended.<Cite src="alchemy-subgraphs-sunset" />

## The selection procedure

The rest of this track's material about picking an indexer is in the next module, in depth and with
data. What belongs here is the *order of operations*, because the order is what makes the decision
tractable — and because getting the order wrong is the single most common way teams end up with a
platform they have to leave in eight months.

Run the axes as a sequence of eliminations. Speed is last, and it is a tiebreaker.

**One — which chains.** A platform that does not reach a chain your product touches is not slow at it.
It is absent. This gate removes more candidates than any other and takes ten minutes with the
supported-networks page open.

**Two — which data types.** Logs are the easy case and everybody does them. Ask separately about
blocks, transactions, internal traces, and whether a handler can read contract state at all. The
benchmark's own results include N/A rows and a timeout, which are categorically different from a slow
time — and the next module makes the case that these are the questions that actually decide
selections.<Cite src="sentio-obib" />

**Three — the shape of the fold you have to write.** Can it follow contracts created at runtime by a
factory? Does it express the transition in a language your team debugs with normal tools? Ponder's
answer is ordinary TypeScript against Postgres, queryable over GraphQL, SQL over HTTP, or directly in
the database.<Cite src="ponder-docs" /> A subgraph's answer is a manifest plus AssemblyScript. Neither
is better in the abstract; one of them is better for the people who will maintain it.

**Four — migration effort, in both directions.** Not just how you get on, but what leaving costs. The
subgraph format is portable across several hosts; a framework's mapping logic is not portable at all.
That asymmetry is worth pricing before you commit, not after.

**Five — the operating model.** Self-hosted means you own a stateful service, its database, its
backups and its on-call. Managed means you own a bill and a dependency. The right answer usually
follows from whether your team already runs stateful infrastructure.

**Six — who steers the project.** Two of the main options changed steward between late 2025 and early
2026, and a data layer you cannot replace is a dependency worth understanding before you build on it.
The next module gives this its own lesson.

**Seven — and only now, minutes.** Among the candidates that survived the first six gates, backfill
duration is a real cost, for the reason the first lesson established: it is the deploy latency of every
change to your data model.

<Check type="explain" concept="indexer-choice-axes">
A team is building a cross-chain lending dashboard. It must show, in one view, positions on an EVM L2
and positions on a Cosmos-based chain, with the ETH each position has actually received — including
transfers made by contracts rather than by users. The team is four frontend engineers with no
infrastructure background. They have found a benchmark showing platform X finishing an events-only
workload in under seven minutes.

Run the gates in order and say where the decision is actually made.

<Answer>
**Gate one eliminates most of the field immediately.** The product spans EVM and Cosmos. Any
EVM-only platform is out, regardless of every other property — the benchmark's own chain table has two
of five platforms in that category.<Cite src="sentio-obib" /> This is the gate that should have been
run first, and it is the one the seven-minute number cannot speak to at all.

**Gate two eliminates most of what survives.** "ETH each position has actually received, including
transfers made by contracts" is a trace requirement, not a log requirement — value moving through
internal calls does not necessarily emit an event. A platform that indexes only logs will produce a
dashboard that looks complete and under-reports. The next module has the measured version of this gap;
here it is enough that this is a yes-or-no gate and a "no" ends the conversation.

**Gate three is where the team's own shape matters.** Four frontend engineers will maintain handlers.
A TypeScript-against-Postgres model is materially easier for them to debug than an AssemblyScript
mapping compiled to WASM, and that difference will show up in every incident for the life of the
product.

**Gate five is where the real decision is made, and it is not a technical one.** A team with no
infrastructure background is being asked to take on a stateful service with a database that must be
backed up, migrated, resynced and watched — plus, because the product is cross-chain, per-chain
failure modes where one network stalls while the others advance.<Cite src="subquery-multichain" /> For
this team, managed hosting is not a convenience, it is the difference between shipping and acquiring a
new competence mid-project. Paying for it is the correct trade and should be argued for explicitly
rather than discovered in the first outage.

**Gate seven never runs.** By the time the first five gates have been applied, the candidate set is
small enough that a two-minute difference in backfill time changes nothing. The seven-minute number
that started the conversation turns out to be a fact about a workload this product does not have, on
chains this product cannot use.

**The meta-point.** The team did not make a bad decision by preferring speed. They made a bad decision
by starting with the axis that had a number on it. The gates are ordered by how many candidates they
eliminate and by how expensive the mistake is to reverse — and both orderings put speed last.
</Answer>
</Check>

## Where this goes

This module gave you the definition — a deterministic fold over a rewritable ordered stream — and then
its four consequences: the artifact the field standardised on, the host that no longer exists, the two
regimes, and the unwind that nothing warns you about.

The next module is the decision itself, with the numbers. Three programming models for the same fold
and what actually differs between them. Who owns each project and what changed in the last eighteen
months. Why the speed ranking inverts between workloads, told from a benchmark whose configurations
are public. Which capability gaps eliminate candidates before speed is consulted. And what a migration
costs — in both directions — alongside the one thing you give up by choosing whichever option is
fastest.
