Search for how to index a contract's events and you will land, within two results, on a tutorial with
eight steps. Steps one through five still work. Step six is a deploy command aimed at a service that
stopped answering years ago, and the tutorial has no way of telling you that, because from its side
nothing changed.

This lesson does two things. It takes apart the artifact those tutorials are teaching — which remains
the most portable thing in indexing and is worth understanding even if you never deploy one. And it
gives you the map of where that artifact can actually run in 2026, along with the habit that keeps
the map from going stale on you.

## Three files, and why the split matters

A subgraph is not a program. It is three declarations that a runtime executes.<Cite
src="thegraph-subgraph-overview" /> The Graph's own quick start names them in the order you edit
them.<Cite src="thegraph-quick-start" />

**The manifest, `subgraph.yaml`.** Which contracts, which events on them, which chain, and from which
block. This is the *input specification* of the fold from the previous lesson.

```yaml
dataSources:
  - kind: ethereum/contract
    name: Vault
    network: mainnet
    source:
      address: "0x1f98431c8ad98523631ae4a59f267346ea31f984"
      abi: Vault
      startBlock: 12369621
    mapping:
      kind: ethereum/events
      apiVersion: 0.0.9
      language: wasm/assemblyscript
      entities: [Position]
      abis:
        - name: Vault
          file: ./abis/Vault.json
      eventHandlers:
        - event: PositionOpened(indexed address,indexed uint256,uint256)
          handler: handlePositionOpened
      file: ./src/vault.ts
```

Two details to notice. The event signature is written out in full including which parameters are
indexed, because that is what determines the topic layout the runtime filters on — the same
[topic semantics](/c/getlogs-topic-semantics) you already know, restated declaratively. And
`startBlock` is not an optimisation, it is a correctness-adjacent decision: set it too late and you
silently omit history, set it to zero and you pay for scanning years of blocks in which your contract
did not exist.

**The schema, `schema.graphql`.** The *accumulator*. Entities here become both the tables the fold
writes and the GraphQL types consumers query.

```graphql
type Position @entity {
  id: Bytes!
  owner: Bytes!
  size: BigInt!
  openedAt: BigInt!
  status: String!
}
```

**The mappings, historically `mapping.ts` in AssemblyScript.** The *transition*. One exported function
per handler named in the manifest, translating an event into entity writes.<Cite
src="thegraph-quick-start" />

```ts
export function handlePositionOpened(event: PositionOpened): void {
  let p = new Position(event.params.id.toString())
  p.owner = event.params.owner
  p.size = event.params.size
  p.openedAt = event.block.timestamp
  p.status = "open"
  p.save()
}
```

The language is the part that surprises people coming from the rest of this curriculum. AssemblyScript
is a TypeScript-shaped subset compiled to WebAssembly, which is what the runtime executes. It looks
like TypeScript and is not: no closures over mutable captures in the shapes you expect, no `any`,
nullable handling that is stricter and noisier, and a standard library that is a fraction of Node's.
Your instinct about how to write a helper will be wrong roughly a third of the time, and the compiler
will tell you so in messages that take some getting used to.

  src="thegraph-quick-start"
/>

This is not an argument against the format — the constraint is what makes the artifact portable and
sandboxable across operators. It is an argument for knowing which of your habits transfer before you
budget the work.

<Aside kind="note">
The three-file split is doing something more interesting than organisation. Two of the three files are
*declarative*, which means a host can read them without executing your code — it can know which
contracts and which events you need before it runs anything. That is exactly what makes remote hosting
of somebody else's subgraph tractable, and it is the structural reason this format, and not a
general-purpose framework, became the thing multiple independent operators agreed to accept.
</Aside>

## The declaration that makes the runtime fast

There is one more manifest feature that is worth meeting early, because it is the clearest example of
why the declarative half of the format earns its keep.

A mapping handler frequently needs something the event did not carry — a token's decimals, a pool's
current reserve, an owner's tier. The obvious way to get it is to bind to the contract inside the
handler and call it. That works, and it is the single largest cause of slow subgraphs, because each
call is a synchronous round trip to a node in the middle of processing one log, and there are millions
of logs.

Declared `eth_calls` move the call from the handler into the manifest. Goldsky's documentation
describes the resulting workflow precisely: before processing a block's events the indexer identifies
all declared calls for that block, executes them in parallel, caches the results in memory, and then
when your handler binds to the contract and makes the call it gets the cached value instead of issuing
a request.<Cite src="goldsky-declared-eth-calls" /> The handler code is unchanged. The declaration is
what lets the runtime batch.

The feature requires `specVersion: 1.2.0` or higher in the manifest, and Goldsky quotes a reduction in
indexing time of up to ten times for subgraphs that call contracts
frequently.<Cite src="goldsky-declared-eth-calls" /> Treat the multiplier as a vendor figure and the
mechanism as the durable part: **the runtime can only prefetch what you declared, and it cannot read
your handler to find out.** That sentence is the whole argument for a declarative input specification,
and it comes back in the next module when a framework with no manifest has to solve the same problem a
different way.

<Aside kind="note">
The same reasoning explains a product category you will run into: no-code subgraphs. Goldsky's wizard
takes a contract address, fetches the ABI from a block explorer, and generates the manifest, schema
and mappings for you.<Cite src="goldsky-no-code-subgraph" /> That is only possible because a
"transcribe every event into a table" subgraph is fully determined by the ABI — there is no transition
logic to infer. It is genuinely useful for exploration and for feeding a warehouse, and it is not what
you want when the accumulator's shape should be driven by your queries rather than by the contract's
event list. Which, as the previous lesson argued, is the usual case.
</Aside>

## The portability is the point

Nothing above is technically remarkable. What makes the format matter in 2026 is that *several
independent operators accept the same three files*.

Goldsky describes its offering as a completely backwards-compatible subgraph indexing solution using
exactly the same WASM processing layer, with its own RPC layer, query layer and storage underneath.<Cite
src="goldsky-subgraphs-docs" /> Ormi Labs lists subgraphs as a product alongside its data
APIs.<Cite src="ormi-labs" /> Envio, whose own framework is not subgraph-shaped at all, nonetheless
lists subgraph hosting among its services.<Cite src="envio-docs" />

So a subgraph is the one indexer definition that is not the property of a single operator. Every other
option in this field — including the good ones you will meet in the next module — ties your mapping
logic to one project's API. That is not an argument that subgraphs are better. It is an argument that
the *format* is an asset, separate from any host's continued existence. Which is convenient, because
the default host stopped existing.

## The step that no longer works

The Graph's hosted service was, for roughly four years, the free place a subgraph went. The sunset was
announced at Graph Day and executed in three phases: stop new deployments, stop upgrades from hosted
accounts, then phase out hosted subgraphs entirely.<Cite src="thegraph-sunsetting-hosted-service" />
The Graph's own announcement page now carries a banner at the top stating that as of 12 June 2024 the
hosted service is no longer active and all queries are served by The Graph Network.<Cite
src="thegraph-sunsetting-hosted-service" />

A detail from that same page is worth carrying, because it explains why the "when did it die" question
gets inconsistent answers across the internet. The published end-of-Q1-2023 date applied only to
chains the network already supported; a note added to the post says non-mainnet chains would have their
hosted equivalents sunset gradually as network support arrived.<Cite
src="thegraph-sunsetting-hosted-service" /> The service therefore did not stop on one day for
everybody. It stopped in waves, over roughly two years, ending in the 2024 banner — and by 2026 there
is nothing left to deploy to.

### What The Graph offers instead

Two distinct things that get conflated, and the conflation causes real cost surprises.

**Subgraph Studio** is the development target. A deployed subgraph there is indexed by the Upgrade
Indexer — a single indexer owned and operated by Edge & Node — and is free to use, rate-limited, not
publicly visible, and explicitly meant for development, staging and testing.<Cite
src="thegraph-quick-start" /> The sunset banner quantifies the free allowance as 100,000 subgraph
queries per month.<Cite src="thegraph-sunsetting-hosted-service" />

Read that list again as a production checklist and it fails three items. Rate-limited. Not public.
Single operator. Studio is not a smaller version of production; it is a different thing.

**Publishing to the network** is the production target, and it is an on-chain action. Publishing makes
the subgraph indexable by the network's independent indexers, removes the rate limits, makes it
searchable and queryable in Graph Explorer, and makes it available for curators to signal on.<Cite
src="thegraph-quick-start" /> The docs recommend adding curation in the same transaction to save gas,
and recommend curation of 3,000 GRT or more to incentivise indexing.<Cite src="thegraph-quick-start" />

That last number is the one that catches teams out. Publishing is not a deploy command with a
credit-card page attached; it is a transaction, plus an economic act whose purpose is to make indexers
want to serve your data. If nobody indexes your subgraph, it is published and useless. The recommended
signal is how you avoid that, and it is denominated in a volatile asset, which is a cost shape most
product teams have no process for.

## The third-party route, and its own half-life

If the mapping logic is written and works, the cheapest move is a host that runs it unchanged.

Goldsky publishes a one-command path from a subgraph already on the network, keyed on the IPFS hash
visible on that subgraph's Explorer page:<Cite src="goldsky-migrate-from-the-graph" />

```bash
goldsky subgraph deploy your-subgraph-name/your-version \
  --from-ipfs-hash <your-subgraph-ipfs-hash>
```

Goldsky frames this as a drop-in replacement offering the same subgraph API your apps already use, for
a zero-downtime migration.<Cite src="goldsky-migrate-from-the-graph" /> Take the framing as vendor
framing, and the *shape* of the claim as the durable lesson: because the artifact is portable, moving
hosts changes a deploy target rather than a codebase. That is a genuinely different kind of migration
from moving to another framework, which rewrites the mapping logic — the last lesson of the next
module prices both.

Now the part that keeps this honest. The set of hosts is itself volatile, and the proof is recent and
first-party: **Alchemy Subgraphs was sunset on 8 December 2025, with all subgraph and query endpoints
discontinued and users directed to Goldsky.**<Cite src="alchemy-subgraphs-sunset" /> A host that a
2025 comparison article listed as a live migration target was gone before the article's year
ended.<Cite src="protofire-indexer-comparison" />

check on the day you choose, not a thing you learn once.

### Reading a tutorial's vintage in ten seconds

You will meet dozens of these pages, most of them undated, several of them ranking above the official
docs. Four tells, in the order they appear in a typical article:

**A deploy step aimed at the hosted service.** `graph deploy --product hosted-service`, or a
`--node https://api.thegraph.com/deploy/` flag, or the phrase "no wallet required". Any of them dates
the page before mid-2024 and means nothing after step five can be followed.<Cite
src="thegraph-sunsetting-hosted-service" />

**No `specVersion`, or one below 1.2.0, in a manifest that also binds contracts inside handlers.** Not
wrong, but it means the article predates the declared-call feature and its performance advice is
stale.<Cite src="goldsky-declared-eth-calls" />

**A named third-party host with no date attached.** The host list churns; one entry on it was
discontinued in December 2025.<Cite src="alchemy-subgraphs-sunset" /> A recommendation without a
retrieval date is a recommendation about a market that has since moved.

**A speed claim with a multiplier and no methodology link.** Park it. The third lesson of the next
module is entirely about what those numbers are measuring, and the short version is that the ranking
depends on the workload.

None of these tells require you to know the answer in advance. They require you to notice that the
page has a *vintage*, which is the habit this whole track is trying to build.

<Check type="spot-bug" concept="hosted-service-retired">
A teammate sends you a plan for indexing your protocol's events. It reads:

> 1. `graph init` against our Vault contract, `startBlock: 0` so we get everything.
> 2. Write mappings, `graph build`, deploy to the hosted service — free, no wallet needed.
> 3. Point the frontend at the hosted endpoint.
> 4. If we outgrow it later, we can always move to the decentralised network.

Four lines, at least four problems. Name them, and say which one is a correctness bug rather than an
operational one.

<Answer>
**Line 1 — `startBlock: 0` is a cost bug and a slow-release bug.** The runtime will walk every block
from genesis looking for a contract that did not exist until block twelve million or so. It produces
correct data eventually, so nothing fails; it just makes every re-index of a schema change take hours
it did not need to take. Set it to the deployment block.

**Line 2 — the hosted service is not a deploy target.** It has not been active since 12 June 2024.<Cite
src="thegraph-sunsetting-hosted-service" /> The plan's step two does not exist.

**Line 2 again — "no wallet needed" is a tell.** Subgraph Studio requires connecting a wallet, and
publishing to the network is an on-chain action.<Cite src="thegraph-quick-start" /> The absence of a
wallet in a 2026 subgraph plan means the plan was copied from a pre-2024 source, which is worth saying
out loud because everything else in it inherits that vintage.

**Line 3 — pointing production at a Studio endpoint is the operational bug.** Even if you substitute
Studio for "hosted service" and the deploy succeeds, a Studio deployment is rate-limited, not publicly
visible, and served by a single indexer operated by Edge & Node — the docs say plainly it is for
development, staging and testing.<Cite src="thegraph-quick-start" /> Your frontend would work in
staging and rate-limit in production.

**Line 4 — "we can always move later" understates one thing and overstates another.** Moving to
another *subgraph host* really is cheap, because the artifact is portable; Goldsky's path is a single
command against the IPFS hash.<Cite src="goldsky-migrate-from-the-graph" /> But publishing to the
network is not a bigger version of a deploy — it is a transaction plus a curation decision, with 3,000
GRT or more recommended to attract indexers.<Cite src="thegraph-quick-start" /> That is a budget
conversation, not a config change, and it belongs in the plan now rather than in the quarter you
outgrow the free tier.

**Which is the correctness bug?** None of them corrupt data — and that is the useful observation.
Three are cost or availability failures and one is a plan that cannot execute. Indexing's genuine
correctness bug is the one this module has not reached yet, and it does not appear in any deploy step.
</Answer>
</Check>

## Where this goes

You now have the artifact and the map. Three things follow from here.

**The two regimes.** A subgraph, like every indexer, catches up and then keeps up, and those are
different engineering problems with different failure modes. The next lesson separates them, and shows
why the number every vendor publishes describes only the first.

**The unwind.** Nothing in the three files above says what happens when the blocks a handler already
processed are replaced. That is the correctness bug the check above was pointing at, and it is the next
lesson but one.

**The alternatives.** Ponder's model is the same fold expressed as ordinary TypeScript against
Postgres, with no manifest and no WASM step.<Cite src="ponder-docs" /> Envio's differs underneath
rather than at the handler.<Cite src="envio-docs" /> The whole of the following module is that
comparison — and by then you will know why "which is fastest" is the wrong opening question.
