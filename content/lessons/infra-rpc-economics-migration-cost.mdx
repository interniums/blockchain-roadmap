The migration was scoped at two hours: change an environment variable, redeploy, watch the graphs.

It took eleven days. The activity feed came back empty because it had been built on a transfer-history
endpoint that exists at one company. The internal-transactions view threw a parse error, because the
new endpoint answered with a flat list of actions where the old one had returned nested call frames.
The backfill job started failing on ranges that had worked for a year, because the block-range cap was
different. And the alerting pipeline stopped entirely, because it had been a webhook the old provider
delivered and the new one has a different product with a different payload.

Not one of those is a bug. Every one is a decision somebody made — quickly, sensibly, for good local
reasons — without recording that a decision had been made.

That is the whole lesson. **Migration cost is not paid at migration time; it accumulates one
convenient endpoint at a time and is then presented as an invoice on the worst possible day.**

## The line the standard draws

The boundary is crisp for something so often ignored: either a method is in the execution API
specification or it is not.

Inside is a small, fixed set — the `eth_` namespace, the six raw-data getters in `debug_`, `txpool_`,
`net_`.<Cite src="execution-apis-spec" /> Ethereum.org states the property that makes it valuable:
every client implements the specification, "so there is a uniform set of methods that applications can
rely on regardless of the specific node or client
implementation".<Cite src="ethereum-org-json-rpc" />

Outside it, nothing is guaranteed by anyone — and "outside" is much larger than the
`alchemy_`-prefixed methods people picture. Four layers, in increasing order of how well they hide.

**Layer one: named namespaces.** `alchemy_getTokenBalances` and `alchemy_getTokenMetadata` are real
methods with a quickstart guide.<Cite src="alchemy-token-api" /> QuickNode publishes its own —
`qn_getBlockWithReceipts`, `qn_getTokenMetadataByContractAddress`, `qn_resolveENS`,
`qn_sendRawTransactionWithWebhook` and others.<Cite src="quicknode-ethereum-rpc" /> These are the
honest ones: the prefix is a warning label you can grep for.

**Layer two: separate products.** Webhooks, streams, token and NFT APIs, portfolio and price
endpoints — delivered over HTTP rather than JSON-RPC, so they never appear in a call inventory built
by reading RPC method names.<Cite src="alchemy-token-api" />

**Layer three: standard-looking methods that are not standard.** `eth_subscribe` carries the `eth_`
prefix, is near-universally implemented, and is not in the specification's `eth_` namespace at all —
it exists because Geth added publish/subscribe over JSON-RPC notifications in
v1.4.<Cite src="execution-apis-spec" /><Cite src="geth-pubsub" /> Nothing about the name says so.

**Layer four: behaviour rather than API.** No method name changes here — only the limits and semantics
behind one. A block-range cap, a response-size ceiling, a billing boundary, a namespace your provider
happens to enable. Invisible to every audit that greps for prefixes, and where most of the eleven days
went.

## The trade is real in both directions

It would be easy to read this as "never use enhanced endpoints", and that is wrong. Look at what one
of them does.

`qn_getBlockWithReceipts` "returns information about the specified block and the transaction receipts
within it" in a single call, and requires the Single Flight RPC add-on on your
endpoint.<Cite src="quicknode-single-flight" /> For an indexer that would otherwise issue one block
fetch plus one receipt fetch per transaction, that is a large and real saving — the exact N+1 pattern
the previous lessons priced.

Now notice the specific thing about this example: the standard set already contains
`eth_getBlockReceipts`.<Cite src="execution-apis-spec" /> On one provider's table it costs 20 compute
units against volume and 500 against throughput, so it is not free
either.<Cite src="alchemy-compute-units" /> But it is portable and the provider-specific method is
not. **That is the shape of the decision every time: a measurable saving now against an unmeasured
liability later.**

Either answer is legitimate. What is not legitimate is answering without noticing — which is what
happens when the enhanced call goes to the same base URL, in the same JSON-RPC envelope, through the
same client, differing from a standard one by the string in the `method`
field.<Cite src="alchemy-token-api" /> There is nothing at the call site to trip over.

## Two APIs for the thing you actually needed

Tracing deserves separate treatment because it is where portability stops being a spectrum and becomes
a binary.

There is no `trace_` namespace in the specification, and the `debug_` namespace it does define
contains six raw-data getters and no tracer at all.<Cite src="execution-apis-spec" /> The two
conventions that fill the gap came from different clients: Geth's `debug_` API, described by its own
documentation as "several non-standard RPC methods" for inspection and
debugging,<Cite src="geth-ns-debug" /> and the OpenEthereum-lineage `trace_` namespace that lives on
in Erigon as a module "for getting a deeper insight into transaction
processing".<Cite src="erigon-trace-namespace" /> You met the semantic differences in the lesson on
expensive methods. The migration consequences are three.

**Availability is the provider's choice, not the protocol's.** Erigon exposes namespaces via
`--http.api`, whose list includes `eth`, `debug`, `trace`, `erigon`, `txpool`, `ots` and `overlay`,
with `overlay` marked archive-nodes-only.<Cite src="erigon-rpc-namespaces" /> A commercial endpoint on
a comparable plan may enable a different subset than the one you developed against — QuickNode, for
instance, documents an Erigon API, a Trace API and a Debug API as separate reference
sections.<Cite src="quicknode-ethereum-rpc" />

**There is no adapter.** A flat list of actions with a `traceAddress` path and a nested object are
different data structures, and the trace-filtering API has no counterpart to translate
into.<Cite src="erigon-trace-namespace" /> Code that walks one does not walk the other.

**Depth is bounded differently.** Erigon's ad-hoc tracing works "as long the blocks have not yet been
pruned", and replaying a mined transaction needs the node "in archive mode, or the transaction must be
within the most recent 1000 blocks".<Cite src="erigon-trace-namespace" /> Two endpoints can both offer
your namespace and disagree about how far back it works.

## Layer four: the constants you did not know you had

"Behaviour differs" is not actionable, so here is one concrete example of each kind.

**Block-range caps.** Alchemy's `eth_getLogs` supported range is unlimited on Ethereum and several
major chains at Pay As You Go, 10,000 on most other chains, 1,000 on Berachain at that tier, and 10
everywhere on the free tier — with all responses capped at
150MB.<Cite src="alchemy-eth-getlogs" /> Your backfill's chunk size is a constant tuned against one
provider on one chain. It is not a property of Ethereum.

**Billing boundaries.** Under Chainstack's rule a request costs 1 request unit at latest state and 2
at archive, archive meaning data "127 or more blocks behind" the tip on most EVM chains, with an
`eth_getLogs` charge evaluated at `fromBlock` if set.<Cite src="chainstack-request-units" /> Move a
log-heavy backfill onto that model and the *same code* has a different cost curve.

**Product lifecycle.** Sometimes the migration is not your decision. Alchemy Subgraphs "was sunset on
December 8, 2025. All subgraph and query endpoints have been discontinued", with a partner named as
the migration path.<Cite src="alchemy-subgraphs-sunset" /> Anything outside the standard can be
withdrawn on the vendor's schedule; the standard set is the only part of the surface for which that is
structurally impossible.

## The portability audit, in an hour

This is a checklist rather than a project, and it produces a document rather than a change.

**Subgoal — enumerate every method your code sends, not every method you remember.** Grep for RPC
method strings and for your client's action names; a viem client's transport is a swappable object, so
the call sites are where the truth lives.<Cite src="viem-clients" /> Include CI, deploy scripts and
monitoring — the inventory rows nobody paid for.

**Subgoal — sort each into standard or not by checking the specification, not the prefix.** The `eth_`
prefix is not evidence: `eth_subscribe` carries it and is not in the
spec.<Cite src="execution-apis-spec" /><Cite src="geth-pubsub" /> Then add the things that are not
method calls at all — webhooks, streams, dashboards, alerts that fire from the provider's console
rather than yours.

**Subgoal — write each non-standard item's replacement cost in hours, not in a label.** "Token
balances: rebuild on multicall, one day." "Internal transfers: no replacement on `debug_`-only
providers; three days plus a re-index." A list of dependencies is not a decision input; a list with
hours beside it is.

**Subgoal — write down the constants and where they came from.** Chunk size, retry budget, polling
interval, block range. Each is an unrecorded assumption about one provider until it is written next to
that provider's name.

**Subgoal — decide the standard-only core.** Name the subset that must run against any compliant
endpoint — usually the write path and whatever the failover transport has to serve — and defend that
boundary in review. Everything outside it can use whatever is convenient, with the cost of the
convenience already priced.

<Check type="explain" concept="enhanced-apis-lock-in">
A team is picking how to build a "your activity" tab: the connected user's token transfers for the
last ninety days, with token symbols and USD values at the time of transfer.

Option A: the provider's transfer-history and token-metadata endpoints, plus its price API. Estimated
three days.

Option B: chunked `eth_getLogs` over `Transfer` topics filtered by the user's address, a cached
`decimals()` and `symbol()` per token, and prices from a separate price source. Estimated three weeks,
plus ongoing indexer maintenance.

Argue for a decision, and say what you would write down either way.

<Answer>
**Take option A, and buy it deliberately.** Three days against three weeks is not a close call for a
feature whose value is unproven, and the enhanced endpoints genuinely do work. The argument is not
against A; it is against A arriving undocumented.

**What A actually costs, stated in advance.** Three non-standard dependencies, not one: transfer
history, token metadata, and prices. Each is a separate product with its own lifecycle — and a
provider can retire a whole product line on its own schedule, as the December 8, 2025 sunset of one
subgraph service shows.<Cite src="alchemy-subgraphs-sunset" /> The replacement cost is roughly option
B's three weeks, which means **you have not avoided three weeks of work; you have bought an option to
defer it**, with a premium payable at a time you do not choose.

**What to write down before merging.** One paragraph in the repository, next to the code:

- Which endpoints, which provider, which are standard (none of these) and which are its own products.
- The replacement plan in hours — here, option B's estimate, which you already have.
- The trigger for revisiting: the tab becoming load-bearing, a chain the provider does not cover, or
  the plan price crossing whatever number makes a second provider attractive.
- Explicitly: **this feature is out of the standard-only core and the failover transport does not
  cover it.** If the second provider cannot answer these calls, the tab has no fallback and should
  degrade to an empty state rather than an error.

**What would change the recommendation.** If the activity tab *is* the product — a portfolio tracker,
a tax tool — its data path is your core competency and option B is not a cost, it is the thing you are
building. And if an indexer already exists for other reasons, option B's three weeks are mostly paid:
the marginal work is a query, not a pipeline.

**The part worth carrying.** Lock-in is not a moral failure, it is a *position*. Positions are fine
when they are sized and recorded, and dangerous when they accumulate by accident across four sprints
and surface during an outage. The audit is not a way to avoid taking positions; it is a way to know
what you are holding.
</Answer>
</Check>

## What this unlocks

**Next**, the last question in this module: whether to run the node yourself. Notice that the audit
you just built is also the input to that decision — the non-standard column tells you exactly which
capabilities a self-hosted node would have to reproduce, and which of them no node can give you
because they were never chain data in the first place.

**And a habit worth more than the audit.** The two-hour estimate at the top of this lesson was not
careless; it was made by someone who had never seen the list. Put the list in the repository, add to
it in the pull request that adds the dependency, and the estimate becomes arithmetic. The list will
always grow — the point is never zero non-standard dependencies, only never being surprised by the
count.
