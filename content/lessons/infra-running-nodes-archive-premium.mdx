Somebody on your team is sizing a disk. They open the hardware page of the client you picked, read a
number, double it for headroom, and put a line in the budget.

There are at least four numbers they could have read, all of them published by the same project, and
they differ by more than an order of magnitude. Some are about a data set that stopped growing in
2022. Some are about one that grows every twelve seconds. One of them describes a storage engine the
client is in the middle of replacing. Every one of them is correct about the thing it describes, and
none of them is the answer to "how big is my node".

This lesson is about the structure underneath those numbers, because the structure is stable and the
numbers are not. Once you can name which of four categories a byte on your disk belongs to, you can
read any client's documentation and know which figure applies to you — and you can stop repeating the
one claim about archive nodes that is wrong in a way that costs money.

## Four categories, and only one of them is the premium

Everything in an execution client's data directory falls into one of four buckets. Say them out loud
once, because the whole lesson is the consequences of their sizes being wildly unequal.

1. **Headers.** One per block, small, and the thing that lets you verify everything else. Every node
   keeps every header, forever, and this is not up for negotiation.
2. **Block bodies and receipts.** The transactions themselves and their outcomes. Large. Grows with
   usage. Never re-derivable from anything else you have.
3. **Recent state.** One current state plus enough recent history to survive a reorg. This is what
   `eth_call` at `latest` reads.
4. **Historical state.** Every intermediate value the chain ever passed through, or a representation
   from which those values can be recovered. Only an archive node keeps this.

A full node holds categories 1, 2 and 3. An archive node holds all four. **The archive premium is
category 4 and nothing else** — the blocks, the receipts, the peers and the JSON-RPC surface are
identical.<Cite src="eth-archive-nodes" /><Cite src="quicknode-full-vs-archive" />

That is worth dwelling on because the folk explanation gets the cause exactly backwards. The folk
explanation is that an archive node is enormous because it stores the whole history of transactions.
It does not store any transaction a full node does not also store. Ethereum.org is explicit that the
network does not depend on archive nodes for historical *data*: all historical interim states can be
derived on a full node, and the transactions themselves are stored by any full node and can be
replayed to build the whole archive.<Cite src="eth-archive-nodes" /> An archive node is a node that
performed that derivation in advance and kept the results.

### Why outputs dwarf inputs

The arithmetic is worth doing once by hand, because it explains the whole cost shape.

A block modifies some accounts and some storage slots. In a [Merkle Patricia trie](/c/merkle-patricia-trie),
changing one leaf changes every node on the path from that leaf to the root — and because the paths are
hashes of keys, those paths are scattered rather than shared, so a block rewrites the whole interior of
every path it touches. That is many more nodes than slots modified. A full node writes the new ones,
drops the old ones, and moves on. **An archive node in the classic design keeps the old ones. Forever.
For every block.**

So the input for a block is the transactions it carries, and the output is a multiple of that in
superseded trie nodes — and the multiplier compounds across every block since 2015. That is the whole
story of why the number is large. It is also why the number is a **property of
the storage engine rather than of Ethereum** — a design that does not keep superseded interior nodes
does not pay that multiplier, and that is the fault line the published figures fall along.

## The same client, two archives, and why they are not comparable

Geth's own documentation now describes two archive designs side by side, and reading it is the fastest
cure for treating "archive node size" as a single fact.

**Hash-based archive (the legacy design).** It stores the entire historical state using Merkle Patricia
tries, retaining every account and storage slot including all corresponding trie nodes at every
block.<Cite src="geth-archive-mode" /> Because it holds every trie node that ever existed, it fully
supports historical Merkle proofs through `eth_getProof`.<Cite src="geth-archive-mode" /> It is also
the design behind the largest published figures, and geth's page says syncing one from genesis is
resource-intensive and may take months.<Cite src="geth-archive-mode" />

**Path-based archive (the current recommendation).** Introduced in geth v1.16.0, it keeps exactly one
full state in the database — the persistent state sits 128 blocks behind head, with forward diffs held
in memory for newer blocks — plus **reverse key-value state diffs**, one per historical block,
containing the previous values of every account and storage location that block
modified.<Cite src="geth-archive-mode" />

The trick is in how a historical query is answered from that. To get the balance of account X at block
B, the client searches *forward* through the diffs starting at B until it finds a block where X was
modified; that diff contains the pre-value, which is the balance at B.<Cite src="geth-archive-mode" />
An index of which blocks touched which account makes the search fast, and geth's page notes the index
takes on the order of thirty hours to build for mainnet, with historical state unavailable until it is
complete.<Cite src="geth-archive-mode" />

Notice what changed and what did not. Both designs answer the same questions. One stores every version
of every node; the other stores one version plus the deltas needed to walk backwards. **Same
capability, different representation, radically different size** — and one capability genuinely lost
in the transition: on v1.16.x, historical `eth_getProof` is not supported, because that needs the
historical trie nodes; from v1.17.x it comes back if you configure trie-node retention
explicitly.<Cite src="geth-archive-mode" />

<Aside kind="warn">
That proof caveat is the kind of thing that sinks a project quietly. If your product verifies
historical storage proofs — a bridge checking an old balance, an airdrop proving a snapshot — "we run
an archive node" is not sufficient. Historical flat state and historical *proofs* are two separate
retention settings, and the default is to keep the first and not the second.<Cite src="geth-archive-mode" />
Test the exact call you depend on at the exact block depth you depend on, before the disk is bought.
</Aside>

## Why the published numbers disagree, and why none of them is yours

Now the part this lesson refuses to resolve for you, and the reasoning behind the refusal.

Geth's hardware page states that a full archive node keeping all state back to genesis requires more
than 12 TB.<Cite src="geth-hardware" /> The same site's archive page says a hash-based archive database
for mainnet can exceed 20 TB, and that a path-based archive with full flat state history requires
around 2 TB — rising to roughly 6.5 TB if it also stores historical trie
data.<Cite src="geth-archive-mode" /> Secondary write-ups quote a range of other figures again, for
other clients.

Every one of those is honest. They disagree because **they are answers to different questions**, and
you can see the differences from the pages themselves:

- The hardware page carries a "last edited" date of September 2023 and prefaces its disk section with
  "at the time of writing (September 2022)".<Cite src="geth-hardware" /> It is describing the
  hash-based world, correctly, for a chain that was three years and one gas-limit increase younger.
- The archive page is dated February 2026 and gives three numbers, not one, because the size depends
  on which of two schemes you run and whether you retain trie nodes.<Cite src="geth-archive-mode" />
- Other clients are different software. Erigon's modes — `archive`, `full`, `blocks`, `minimal` —
  differ precisely in retention,<Cite src="erigon-pruning-modes" /> and Erigon 3's release notes lead
  with an initial sync that does not re-execute from zero.<Cite src="erigon-readme" /> A figure
  measured against one storage engine says nothing about another.

**So no figure in this lesson is the number to plan against, including the ones just quoted.** The
research sweep behind this curriculum recorded the geth hardware page and the newer path-based
material as an unresolved contradiction, and it should stay unresolved in your head too, because
resolving it in favour of either number is how people buy the wrong disk.

What replaces the number is a procedure, and it is short:

1. Name the **client and version** you will actually run. Not "an archive node".
2. Name the **state scheme and retention flags** for that version. In geth's path-based mode this is
   `--history.state` for how many recent states to keep and `--history.trienode` for whether historical
   proofs work at all.<Cite src="geth-archive-mode" />
3. Read that client's **current** documentation, and cross-check against a dated practitioner table.
   The eth-docker resource-usage page is the most useful of these because it publishes a client
   version and a measurement date next to every figure, and breaks the disk column out by retention
   policy rather than giving one number per client.<Cite src="eth-docker-resource-usage" />
4. Measure your own after a week. Every number you read was measured on somebody else's workload.

## What a node is now allowed to forget

Everything so far has been about category 4. Now categories 1 and 2, where the 2026 material genuinely
differs from the 2022 material.

Since July 2025, execution clients may drop **pre-Merge block bodies and receipts** while continuing to
serve every header. The Ethereum Foundation's announcement states that as of that date all execution
clients support partial history expiry in accordance with EIP-4444, and that removing block data prior
to the Merge reduces the disk required by 300–500 GB.<Cite src="ef-partial-history-expiry" />

Read the pieces separately, because the naming is a trap.

**EIP-4444 is the vision, and it is not what shipped.** Its specification sets `HISTORY_PRUNE_EPOCHS`
to 82,125 epochs — one year — and says clients should not serve headers, bodies and receipts older than
that on the p2p network.<Cite src="eip-4444" /> That is a *rolling* window over all history. The EIP is
marked Stagnant.<Cite src="eip-4444" />

**EIP-7639 is the narrower step.** It defines eth/70, on which clients must not make or respond to p2p
queries about block bodies or receipts before block 15537393 — the Merge block — affecting exactly four
protocol messages.<Cite src="eip-7639" /> Its motivation gives the reason the pre-Merge segment was
chosen first: of roughly 500 GB of historical data in 2024, nearly 400 GB of it predated the Paris
upgrade.<Cite src="eip-7639" /> It is also marked Stagnant.<Cite src="eip-7639" />

**EIP-7927 is the rollout meta-EIP**, documenting activation shortly after Pectra — delayed so that all
pre-fork deposit logs would be processed before clients began dropping history — with Sepolia as the
testing ground.<Cite src="eip-7927" /> Also Stagnant.<Cite src="eip-7927" />

<Aside kind="note">
Three Stagnant EIPs describing a change that is live in every production client is a good reminder of
what EIP status tracks. Status describes the document's progress through the standards process, not the
software's. A Stagnant networking EIP that all five clients implemented is a document nobody kept
editing, not a feature nobody shipped. Read the client release notes for what runs; read the EIP for
what it means.
</Aside>

### What "allowed to forget" costs you, concretely

The pre-Merge segment being droppable is not an abstraction — it changes which JSON-RPC calls a random
peer can answer. EIP-7927 lists the endpoints an execution client that dropped history can no longer
serve for pre-Merge blocks without an alternate data source, and the list is longer than people
expect: `eth_getBlockByHash`, `eth_getBlockByNumber`, `eth_getTransactionByHash`, the by-index
variants, `eth_getTransactionReceipt`, the block-transaction-count methods and the uncle
methods.<Cite src="eip-7927" />

Two things follow for anyone building on top.

**Historical data from an arbitrary peer is now a weaker assumption than it used to be.** The
Foundation's announcement is direct about the security model this rests on: a 1-of-N assumption, where
if at least one entity provides the historical blocks, nodes can retrieve them by out-of-protocol
means.<Cite src="ef-partial-history-expiry" /> The header chain is still served in full, which is what
lets you cryptographically verify anything you fetch from elsewhere.<Cite src="ef-partial-history-expiry" />

**The data moved rather than vanished, and the retrieval path is a real command.** Pre-Merge data lives
in the e2store archival format, listed on a community-maintained endpoints page, with the Portal
Network and EIP-7801 as peer-to-peer routes.<Cite src="eip-7927" /> That page carries magnet links,
torrent files and HTTP mirrors for the mainnet era1 range from genesis to merge block 15537393, plus
checksums for verification.<Cite src="eth-clients-history-endpoints" /> Geth exposes
`geth download-era` to fetch a block or epoch range from such a server, verify it against known
checksums, and place it into the ancient store.<Cite src="geth-download-era" />

So the operational answer to "we dropped it and now compliance wants it" is not a resync. It is a
targeted range download, and it is worth rehearsing before you need it.

## Reading a real disk breakdown

Categories are easier to trust once you have seen them itemised. Geth's history-pruning page prints the
output of `geth db inspect` on mainnet before and after running `geth prune-history`, and the shape of
that table teaches more than any summary figure.<Cite src="geth-history-pruning" />

**Subgoal: separate the chain data from the state data.** The ancient store holds bodies, receipts,
headers and hashes — categories 1 and 2. The key-value store holds trie nodes, snapshots, the
transaction index and the log index — category 3 plus the indexes built over categories 1 and 2. In
geth's printed example the ancient-store chain data is the larger of the two by a wide
margin.<Cite src="geth-history-pruning" />

**Subgoal: notice what pruning moves and what it does not.** After `prune-history`, the bodies and
receipts rows shrink by roughly the fraction of the chain that predates the Merge and the item counts
drop to the post-Merge block count, while every trie and snapshot row is
byte-for-byte unchanged.<Cite src="geth-history-pruning" /> The page states the invariant directly:
the state trie and all headers are preserved, and the node remains fully functional for
consensus.<Cite src="geth-history-pruning" />

**Subgoal: notice what is neither chain nor state.** Two substantial key-value rows in that example are
the transaction index and the log index, each of them larger than the contract-code
row.<Cite src="geth-history-pruning" /> Those are *your*
categories — they exist so that `eth_getTransactionByHash` and `eth_getLogs` are fast. They are derived,
they are optional in principle, and they are a meaningful fraction of the disk. When the next module
argues that a provider's `eth_getLogs` pricing reflects real work, this row is part of the reason.

**Subgoal: date the observation.** That example was published in June 2025, before the default block
gas limit rose to 60M.<Cite src="geth-history-pruning" /><Cite src="eip-7935" /> A larger gas limit
means more transactions, more receipts and more state churn per block, so every disk figure measured
before that increase understates the current growth rate. This is the general form of the trap: a disk
number is a measurement of a moving system at an instant, and the instant is usually printed on the
page if you look for it.

<Answer>
**Four defects. Two are sizing errors, and two would take down a product.**

**1 — The 12 TB figure is real and is not this node's figure.** Geth's hardware page does state that a
full archive keeping all state back to genesis requires more than 12 TB,<Cite src="geth-hardware" />
but that page's disk section is prefaced "at the time of writing (September 2022)" and describes the
hash-based scheme.<Cite src="geth-hardware" /> The same project's archive page, dated February 2026,
gives materially different figures for the path-based design and a larger one again for
hash-based.<Cite src="geth-archive-mode" /> Consequence: the budget is wrong, and it is not even wrong
in a predictable direction — it over-provisions for one configuration and under-provisions for another.
The fix is procedural: name the client, the version and the retention flags, read that version's
documentation, cross-check a dated practitioner table,<Cite src="eth-docker-resource-usage" /> and
measure after a week.

**2 — The saving is real and does not apply to the number it is being subtracted from.** Partial
history expiry drops pre-Merge block bodies and receipts, saving 300–500 GB.<Cite src="ef-partial-history-expiry" />
The archive premium is historical state. These are disjoint parts of the disk, so the saving does not
offset the archive cost — it offsets the block-data cost the node was paying anyway. Consequence: an
arithmetic error of a few hundred gigabytes presented as a rationale for a multi-terabyte decision.
Worth doing anyway; worth doing for its own reasons.

**3 — Historical proofs are a separate retention setting, and this is the one that breaks a product.**
On geth v1.16.x the path-based archive does not support historical `eth_getProof`, because that
requires historical trie nodes; from v1.17.x it works only if `--history.trienode` is configured to
retain them.<Cite src="geth-archive-mode" /> Consequence: the analytics queries succeed, the node
reports healthy, and the bridge's proof verification fails at exactly the block depths it exists to
handle. "An archive node has all historical state" is true of the flat values and false of the
structure that proves them. Decide this before syncing, because it is a retention choice, not a flag
you flip afterwards.

**4 — "If the disk fills, we prune" is the instruction that cannot be followed here.** Geth's pruning
documentation states the rule plainly: do not try to prune an archive node, because archive nodes need
to maintain all historic data by definition.<Cite src="geth-dbpruning" /> The same page adds that
pruning needs at least 40 GB free and cannot rescue a disk that is already
full.<Cite src="geth-dbpruning" /> Consequence: the escape hatch the plan depends on does not exist,
and it will be discovered at the moment the disk is full — which is also the moment the node stops
following head. Note also that changing what a node retains is not adjustable in place: Erigon requires
deleting `chaindata` and re-syncing to change mode.<Cite src="erigon-pruning-modes" />

**The corrected plan.** Split the workloads. The analytics requirement is a *dataset* question —
build it once against an archive source, store it, serve it from your own database, and stop paying
for an archive node to answer the same queries repeatedly. The bridge requirement is a *proof*
question with a specific retention setting attached; size and configure for it explicitly, and test
the exact call at the exact depth. Enable history expiry on everything because it is free, not because
it funds anything. And write the disk figure into the plan as "measured on our client and version at
this date", so the next person knows what they are allowed to reuse.
</Answer>
</Check>

## What this unlocks

You can now decompose a node's disk into headers, block data, recent state and historical state, say
which of them each 2026 mechanism touches, and read any client's published figure with the two
questions that make it meaningful — which storage engine, and measured when.

That is also the skeleton of a build-versus-buy conversation. The next module prices RPC access, and
the archive line is where self-hosting looks most attractive on paper: the queries are expensive to buy
and the hardware is a one-off. The argument you now have is that the hardware is not the cost line —
the *retention decision* is, because it is made once, cannot be changed without a resync, and determines
whether the node can answer the question at all.

Before that, two lessons remain here, and both are about resources the archive conversation quietly
assumes. The next one is about a category of bytes that is not in the four above at all, because it
does not live on the execution client: blob data, which arrives at a rate, expires on a clock, and
belongs to the other half of your node. And the last is about the constraint that decides whether any
of this works — not how much disk you bought, but how fast it answers.
