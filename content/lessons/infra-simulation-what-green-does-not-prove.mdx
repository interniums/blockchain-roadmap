The confirmation screen says you will receive 0.1 ETH. You sign. You lose everything in the wallet.

Nothing malfunctioned. The contract detected that it was being simulated, behaved harmlessly for the
preview, and behaved differently when it actually executed. MetaMask's own documentation names this
pattern — a **red pill attack** — and describes the mechanism plainly: a contract detects it is being
simulated, shows a benign outcome, and once executed on chain switches behaviour and drains funds
after the approval.<Cite src="metamask-tx-simulations" /> The preview looks legitimate; the
transaction is not. The documentation is explicit that this tricks both the user reading the safe
preview and the wallet provider relying on the controlled environment to produce
warnings.<Cite src="metamask-tx-simulations" />

That is the sharpest version of this lesson's claim, and there are three softer versions underneath
it. A green simulation is a conditional statement with the conditions stripped off. This lesson is
about putting them back.

## Simulation became a product surface

Wallets now simulate before they ask you to sign. MetaMask describes the feature as predicting the
estimated balance changes to your account so you understand the outcome of the transaction you are
about to submit — a preview of how much ETH you will receive or which tokens will move — and states
that it is an added safety feature enabled by default, with a toggle under Settings, Security &
Privacy.<Cite src="metamask-tx-simulations" /> Simulations are available for contract interactions,
covering balance changes involving ERC-20 tokens and ERC-721 and ERC-1155 transfers in and out of the
account.<Cite src="metamask-tx-simulations" />

The pattern is not MetaMask's alone. Vendor simulation documentation describes the same product
shape from the other side: dapps and wallets use single simulations to give users a way to dry-run
transactions before committing real assets, previewing the execution along with the detailed balance
and asset changes, on the argument that this helps users approve only successful transactions and
prevent costly failures.<Cite src="tenderly-simulations" />

This is the main practical defence against [blind signing](/c/blind-signing), because it turns
calldata nobody can read into a claim a user can evaluate. Two consequences follow for anyone
shipping on chain, and neither is optional any more.

**Your transactions have to be legible to a simulator that does not know your protocol.** The wallet
is not going to read your docs. It reads logs and balance deltas. A flow whose effects are
expressible as token transfers and approvals gets summarised; a flow that moves value through
internal accounting with no corresponding events gets shown as "unknown" or gets a warning, and users
learn to click through warnings or learn to leave. Emitting the events that describe what actually
happened is now a UX feature as well as an indexing one.

**Simulation is a dependency with its own failure modes.** MetaMask notes that enabling the
estimated-balance-changes feature involves using a centralised MetaMask server to simulate the
transaction and obtain the necessary data, and advises leaving it disabled if you do not want
transaction data or your IP address exposed.<Cite src="metamask-tx-simulations" /> So the safety
feature is also a disclosure: every transaction a user is about to send is seen, pre-broadcast, by a
third party. Some of your users will and should turn it off, and your product should not assume the
preview exists.

## The escalation: enforcing the simulation on chain

The red-pill attack works because standard simulations run off chain, and MetaMask states the
assumption they rest on directly — that contracts behave the same way in simulation and in on-chain
execution — and that this is not always true.<Cite src="metamask-tx-simulations" /> Its documentation
goes further: when simulations are conducted off chain only, as almost all transaction simulations
today are, they are vulnerable to this class of attack, and for simulations to be genuinely helpful
they must be enforced on chain.<Cite src="metamask-tx-simulations" />

The described mechanism is three steps: the transaction is simulated before signing; the same
simulation conditions are enforced on chain; and if real execution does not match the simulation, the
transaction automatically reverts.<Cite src="metamask-tx-simulations" /> The documented consequence is
that what appears on the confirmation screen is guaranteed to match what happens on chain, because a
mismatch means the transaction does not go through and the user pays only the network
fee.<Cite src="metamask-tx-simulations" /> The feature is described as available by default when
interacting with a non-trusted contract for MetaMask smart accounts on the extension, across a listed
set of networks including Ethereum, Base, Arbitrum, Optimism, Polygon, Avalanche and
Linea.<Cite src="metamask-tx-simulations" /> It costs more gas, because it adds an on-chain
verification step and the additional computation that implies.<Cite src="metamask-tx-simulations" />

Sit with the shape of that fix for a moment, because it generalises well beyond wallets. The
off-chain simulation could not be trusted, so the guarantee was moved into the transaction itself:
**the prediction became a precondition**. That is the same move as a slippage bound, a deadline, or a
`require` on a balance delta at the end of a batch — and it is the move available to you as a
protocol author whenever a simulation result is load-bearing. If a rehearsal's conclusion matters, an
assertion in the executed calldata is worth more than an assertion in the rehearsal.

## The gap between the state you simulated and the state you get

Set malice aside; the ordinary case is bad enough. Your simulation ran against a specific block.
Your transaction will execute against a different one. Everything that happens in between is outside
the result you are holding.

**Prices move, and the movement can be caused by you.** A swap simulated against the pool as it
stands is not a swap executed after someone has traded the pool against you. This is not an edge
case; it is [an attack surface with a name](/c/mev-sandwich), and
[slippage tolerance is the parameter that decides how much of it you are exposed to](/c/mev-slippage-is-the-attack-surface).
A simulation showing an excellent rate is a simulation of the best case.

**Allowances get spent.** An approval you observed at simulation time may have been consumed by
another transaction of the user's own — a common failure with wallets that batch, retry or replace.

**Nonces advance.** A rehearsed sequence of transactions from one account assumes an ordering that a
replacement or a stuck earlier transaction can break.

**Roles get revoked and parameters get changed by people who are not you.** This is the one that
matters most for the rehearsals in the rest of this module: the admin who could execute your upgrade
last Tuesday may not be the admin today, and nothing about your simulation will notice.

And a gap that is entirely of your own making: **with `validation` false, `eth_simulateV1` behaves
like `eth_call`**,<Cite src="execution-apis-execute-schemas" /> which means no nonce ordering check
and, as measured in the previous lesson, a simulated block with a zero base
fee.<Cite src="measured-simulation-2026-08-26" /> A green result under those settings has not
established that the sender could pay for the transaction, only that the code path works. If your
pre-send check is the thing standing between a user and a failed send, turn validation on and supply
real fee fields, or accept that you are checking a narrower claim than you think.

## Four things a simulation cannot see at all

The drift above is about *when*. This is about *what* — categories of fact that are simply not
present in the execution being simulated, no matter which block you pin or which overrides you apply.

**Ordering, and who controls it.** A simulation executes your calls in the order you wrote them,
alone. It has no model of the other transactions competing for the same block, of what a builder will
choose to include, or of the fact that submitting through a public mempool advertises your intent to
everyone who wants to act on it first. The result answers "does this work", never "will this be
included, and in what company".

**Anything that has to happen off chain.** An oracle push that has not arrived. A keeper that has not
run. A sequencer that has not posted. A bridge message that has not been relayed. Rehearsals that
warp time forward are especially exposed here, because time passing on a fork does not cause any of
the off-chain actors to act — you fast-forwarded the clock and nobody else moved. If your flow
depends on somebody else doing something during the interval, you have to simulate them doing it, and
then say so.

**Whether the participants would consent.** Covered in the previous lesson from the mechanical side;
it belongs here too. A rehearsal that impersonates five multisig signers has proved something about
the calldata and nothing about the signers.

**Everything outside the calls you wrote.** Your bundle is not the block. A rehearsal that hands
control to an external contract — a callback, a hook, a token with transfer logic, a router — is
rehearsing that contract's *current* implementation. If it is upgradeable, you have rehearsed a
snapshot of somebody else's code, and their governance can change it between your rehearsal and your
send without asking you.

### The failure that is hardest to see: your own size

There is one distortion that hides inside an otherwise perfect simulation, and it catches
sophisticated teams. Simulating an action against real state includes your action's effect on that
state — that is the point — but only *your* action's effect, once.

Move 4 million dollars through a pool in a rehearsal and the rehearsal will faithfully show the price
impact of moving 4 million dollars through that pool. What it will not show is that in production you
will do it while three other people react, that the liquidity you consumed was provided by a market
maker who will withdraw when they see the first tranche, or that your own second transaction meets
the market your first one created plus everyone else's response to it.

The tell is a rehearsal that comes out *better* than production. If your simulated slippage is
consistently and comfortably lower than what you actually get, you are not looking at a bug in the
simulator. You are looking at the difference between an execution alone in a block and an execution
in a market.

## The EOA that runs code

There is one more wrinkle, and it is recent enough that most simulation tooling was designed before
it.

Under [EIP-7702](/c/delegation-designator), an externally owned account can carry a delegation
designator in its code field and execute the delegate's code when it is
called.<Cite src="eip-7702" /> The account is still an EOA — it still signs transactions, it still
has a nonce — but "this address is an EOA, therefore calling it cannot run arbitrary logic" stopped
being true.

Two places this shows up in simulation work.

**Simulating a send "from a user's wallet" may execute contract code.** The transaction originates
from an EOA, and the EOA runs the delegate's implementation. Anything your rehearsal assumed about
the simplicity of the sender no longer holds automatically.

**Any logic that branches on whether an address has code is now branching on something else.** You
know this asymmetry from the core track. What is new here is that a *simulator* — yours or your
wallet's — may be making the same branch internally when it decides how to summarise a transaction,
and a delegated EOA is exactly the input that classification was not built for.

<Aside kind="stop">
Be careful how far you take this. That EIP-7702 delegation *can* make an EOA execute code is in the
EIP.<Cite src="eip-7702" /> How any particular wallet's simulator, indexer or asset-diff renderer
behaves when it meets a delegated EOA was **not** established for this lesson, and no source was
found documenting it. Treat it as a question to ask of the specific tool you depend on — send a
delegated account through your own pre-send path and look at what comes out — rather than as a known
behaviour you can design around.
</Aside>

The practical version of everything above is a discipline about wording. Compare two sentences an
engineer might put in a pull request:

> We simulated the migration and it works.

> Against mainnet at block 25,839,000, with the treasury's balance overridden and validation off, the
> five-call migration bundle completed with all calls at status 0x1, moved 4.2M USDC as expected, and
> left the vault's `totalAssets` unchanged. It has not been run with realistic fees, and it assumes
> the timelock admin is still `0x807a…95d2`.

The second one is not longer because it is more cautious. It is longer because it contains the four
things a reader needs to evaluate it: **the block, the overrides, the validation setting, and the
assumptions that are not encoded anywhere in the result.** A simulation without those is a screenshot
of a green tick.

Adopt the habit now, because from the next lesson onward the stakes rise sharply: the rehearsals in
this module end with somebody sending a transaction they cannot take back, on the strength of exactly
this kind of sentence.

<Check type="explain" concept="simulation-is-not-a-guarantee">
Your team ships a "preview" panel: before the user confirms a deposit into your vault, you call
`eth_simulateV1` and render the asset changes — "you send 10,000 USDC, you receive 9,981 vault
shares". Product wants to add copy that says **"Guaranteed outcome"** next to the preview, because
"the simulation proves it".

Write the response you would give, and describe what you would build instead.

<Answer>
**The copy is a claim the tool cannot support, and I would not ship it.** Three separate reasons,
each sufficient on its own.

**The state moves.** The simulation ran against one block. By inclusion, the vault's share price has
moved — that is what a vault *does* — and another deposit or a large withdrawal in between changes
the number. A share count computed at simulation time is an estimate of a quantity that is defined by
the state at execution time.

**The settings decide what was checked.** If we ran with `validation` false, the simulation behaved
like `eth_call`<Cite src="execution-apis-execute-schemas" /> — no nonce ordering, and a simulated
block whose base fee came back as zero in measurement.<Cite src="measured-simulation-2026-08-26" />
The preview says nothing about whether the user can pay for the transaction.

**Off-chain previews are attackable in principle.** MetaMask's documentation states outright that
off-chain simulations rely on the assumption that contracts behave the same way in simulation and on
chain, that this is not always true, and names the red-pill pattern where a contract detects the
simulated environment and switches behaviour.<Cite src="metamask-tx-simulations" /> Our own vault is
not adversarial, but any contract in the call path could be, and "guaranteed" is a word about the
whole path.

**What I would build instead, in three parts.**

*Change the copy to a bounded claim.* "Estimated — based on the vault at block N" with the block
number visible. Users forgive an estimate that moved. They do not forgive a guarantee that did not
hold.

*Make the guarantee real where it matters, by moving it into the transaction.* If the user must not
receive fewer than some number of shares, that is a `minSharesOut` argument enforced by the contract,
and the transaction reverts if the world moved. This is the same shape as MetaMask's enforced
simulations: the prediction becomes a precondition, and a mismatch costs a fee instead of a
loss.<Cite src="metamask-tx-simulations" /> It is the only version of "guaranteed" that is true, and
it is enforced by the EVM rather than by our copywriting.

*Re-simulate close to signing, and re-render.* A preview computed when the panel opened and shown
a minute and a half later is stale by several blocks of other people's transactions. Refresh it, and if the number has moved by
more than the user's tolerance, say so before they sign rather than after.

**And one thing to check rather than assume:** whether our preview path does anything sensible when
the sender is an EOA carrying an EIP-7702 delegation, which can execute the delegate's
code.<Cite src="eip-7702" /> That is not a known bug in our stack — it is an untested input, and
"untested input on the path between the user and their money" is how I would raise it.
</Answer>
</Check>

## What this unlocks

You now have the honest frame: simulation reduces uncertainty and never removes it, the gap between
simulated state and included state is where an entire class of failures lives, and off-chain
prediction is itself an attack surface that the ecosystem is actively hardening against.

That frame is what makes the rest of this module worth doing rather than reassuring. **A rehearsal is
valuable exactly in proportion to how honestly you state its conditions.**

**Next**: four environments to rehearse in — a fork test, a local forked node, a hosted shared fork,
and the standardised method you already know — and precisely what each one adds and costs. After
that, the two rehearsals that justify the entire practice: an upgrade executed against live storage,
and a governance action rehearsed end to end before anybody votes.
