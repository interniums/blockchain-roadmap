A support ticket, lightly disguised.

An onboarding job sends every new user two things at signup: zero USDC and zero wei. Both calls
return a transaction hash. Both transactions succeed. The reconciliation job that runs the next
morning finds a storage entry in the token contract for every new user, and finds nothing whatsoever
for the ETH side — the addresses are simply not in the state, as though the transactions had never
happened.

Nothing failed. The two transfers are not two instances of one operation, and the difference between
them is not a quirk of the token contract. It is the second field of the account record, and a rule
from 2016 about what the protocol does with accounts that hold nothing.

## `balance` is a protocol field

The second of the four fields is an unsigned integer: the number of wei owned by this account,
stored directly in the record.<Cite src="yellow-paper" /><Cite src="ethereum-docs-accounts" /> Wei is
the smallest unit of ether, at 10<sup>18</sup> wei to one ether, and it is the unit the protocol
actually works in — the value field of every transaction is denominated in wei, and querying a
balance means inspecting this field.<Cite src="ethereum-docs-intro-to-ether" />

There is no ledger contract behind that number. No `transfer` function ran. No event was emitted.
When a transaction moves ether, the state transition function decrements one integer and increments
another, and the only reason anybody believes it is that every node computed the same two integers
and hashed them into the same state root.

**ETH is the only asset the protocol itself knows about.** Every other balance a user sees is a
number in some contract's storage trie, moved by that contract's own code according to that
contract's own rules. ERC-20 fixes the shape of those rules — `balanceOf(address)` returning a
`uint256`, `transfer`, `approve`, `transferFrom` — but the standard is an interface convention, not a
protocol feature.<Cite src="eip-20" /> Nothing in consensus knows a token exists.

### Where the seam shows

**There is no allowance model for ether.** `approve` and `transferFrom` are ERC-20's, and ether has
neither.<Cite src="eip-20" /> A contract cannot be granted permission to pull ether from you later; it
can only be handed ether now. Any protocol that wants one uniform code path over "an asset" has to
represent ether as a token to get one, which is the entire reason a wrapped-ether contract exists —
it is an adapter that buys interface uniformity by moving ether into a storage mapping where it obeys
the token rules.

**They arrive by different mechanisms.** Sending ether is a call carrying value, and the recipient's
code — if it has any — runs. An ERC-20 transfer is a call to the *token* contract; the recipient may
learn nothing about it unless the token or the sender goes out of its way to tell them.

**They fail differently.** Track 04 covers this properly, because it is the source of an entire class
of production bugs: a token that returns `false` instead of reverting, a recipient that reverts on
receiving ether, a fixed gas stipend that used to be enough and now is not. The reason to notice the
asymmetry here is that it is not an accident of any particular token — it is the gap between a
protocol operation and a call into somebody's code.

## The account that vanishes

Now the other half of the ticket.

EIP-161 defines an account as **empty** when it has no code, zero nonce and zero balance, and requires
that at the end of a transaction, any account that was touched during it and is now empty becomes
non-existent — deleted from the state.<Cite src="eip-161" /> "Touched" is broad on purpose: it
includes being the recipient of a transfer of zero value.<Cite src="eip-161" />

So the zero-wei transfer did exactly what the protocol says. It touched an address with no code, no
nonce and no balance; at the end of the transaction that account was empty; the account was deleted.
There is nothing left to reconcile because there is nothing there.

The same EIP removed the incentive to do it anyway: where `CALL` previously charged 25,000 gas for a
non-existent destination, the charge is now levied only when the operation transfers more than zero
value.<Cite src="eip-161" /> A zero-value poke at a fresh address is cheap *and* inert. It buys
nothing.

### Why this rule exists

It is worth knowing where the rule came from, because it explains why it is shaped the way it is.

Spurious Dragon, at block 2,675,000 in November 2016, was the second of a two-round hard-fork response
to the denial-of-service attacks on Ethereum in September and October of that year. The Ethereum
Foundation's own announcement describes EIP-161's job plainly: to make it possible to remove a large
number of empty accounts that had been put into the state at very low cost as a result of those
attacks — and it notes that the actual removal would begin after the fork, by systematically issuing
`CALL`s to the empty accounts the attacks had created.<Cite src="ethereum-blog-spurious-dragon" />

The original proposal puts a price on how cheap "very low cost" was. EIP-158 acknowledges that
repeatedly zero-value-calling already-existing empty accounts produced a state change at about 700
gas per account, against a usual minimum around 5,000 — and less again once suicide refunds were
applied.<Cite src="eip-158" /> Cheap state writes are a denial-of-service vector against every node
that has to store the result, which is a theme you will meet again under a different name every time
this curriculum touches state growth.

The same EIP also settled the conceptual question underneath: from the EVM's point of view, emptiness
and nonexistence became the same thing.<Cite src="eip-158" />

<Aside kind="note">
One edge worth knowing exists. EIP-158 defines emptiness for gas purposes as zero balance, empty code
and zero nonce — and says explicitly that emptiness of *storage* does not matter, on the grounds that
an account with empty balance, code and nonce but non-empty storage is pathological and has no real
use value.<Cite src="eip-158" /> It is a small hole in the tidy story that an account is exactly its
four fields, and it is the kind of hole worth remembering the shape of, because "the pathological case
has no real use value" is a sentence that ages differently on a chain with adversaries than it does in
a design document.
</Aside>

## What this changes about your code

**An existence check on an address is not an existence check on a user.** There is no operation you
can perform for free that registers an address in state. If your product needs to know that an address
is one of yours, that fact belongs in your database, not in a poke at the chain.

**Existence is not monotonic in the direction you expect — but it is in the other one.** An account can
appear and then be gone again in the same transaction. But the moment an account originates a single
transaction its nonce becomes non-zero, and the nonce never decreases. An account that has ever sent
anything can never again be empty, and therefore can never again be cleared. Every EOA that has ever
transacted is a permanent entry in the state trie.

**Holding ether is enough to persist.** A non-zero balance disqualifies an account from being empty,
so the one-wei version of the onboarding job would have worked — at the cost of creating a state entry
for every user who never comes back, forever.

**Delegation now creates a third way to become permanent.** Since EIP-7702, an authorisation writes a
delegation indicator into an account's code field and increments its nonce, and a delegation left in
place is non-empty code.<Cite src="eip-7702" /> That is the sixth lesson's territory; the point here is
only that the set of ways an account becomes permanent grew in 2025 and the "empty" definition did
not change to match.

<Check type="explain" concept="empty-account-clearing">
A signup flow does three things for a brand-new address that has never appeared on chain. For each,
say whether an account record exists afterwards, and what an observer holding only the state root can
conclude.

1. Send it 0 wei.
2. Send it 1 wei.
3. Have the user sign a login message with the corresponding private key.

Then: after (2), the user sends one transaction that spends their entire balance on gas, ending at
exactly zero. Is the account cleared?

<Answer>
**1 — no record exists.** The transfer touched the address; at the end of the transaction the account
had no code, zero nonce and zero balance, so it was deleted.<Cite src="eip-161" /> The observer can
conclude nothing at all — the state is byte-identical to a state in which the transaction was never
sent. Note that the transaction itself is still in a block with a receipt; it is the *state* that
retains nothing.

**2 — a record exists**, with nonce 0, balance 1, and the empty-storage and empty-code hashes from the
first lesson. The observer can prove the account exists and holds exactly one wei, and can prove it
has never originated a transaction, because the nonce is zero. They cannot tell who controls it, and
they cannot tell whether anyone does.

**3 — nothing on chain whatsoever.** A signature is produced and verified off-chain; the public key is
recovered from it by whoever checks it. This is the cleanest illustration of the point from lesson
one: the account's relationship to its key is not stored, it is re-derived. A wallet can prove control
of an address that does not exist.

**And the tail: no, the account is not cleared.** Sending a transaction incremented the nonce to 1
before anything else happened, and an account with a non-zero nonce is not empty by
definition.<Cite src="eip-161" /> The balance can go to zero; the nonce cannot come back down. So the
record persists with nonce 1, balance 0 — permanently, and visibly, which is a small privacy fact as
well as a state-growth one.
</Answer>
</Check>

## Where this pays off

**The next lesson** is the field that just saved this account from deletion. The nonce turns out to be
doing three separate jobs, only one of which is counting.

**In Track 04**, the ETH/token asymmetry becomes a design constraint: pull versus push payments,
reentrancy on value transfer, the wrapped-ether adapter, and the reason `SafeERC20` exists at all.

**In Track 07**, empty-account clearing is the first appearance of a much larger argument. State
growth is the constraint that shapes statelessness, expiry proposals and the binary-tree work — and
the 2016 fix on this page is the earliest example of the protocol deciding that some state is not
worth keeping.
