Two requests that sound like the same request.

**"What is the ETH balance of `0xd8dA…6045`?"** One call. Any node on earth answers it in milliseconds,
and can hand you a proof against the state root that a laptop verifies without trusting the node.

**"List every address on Ethereum holding non-zero ETH."** Not slow. Not expensive. Not available. A
node holding the complete, fully verified world state cannot produce that list, and no amount of
hardware changes it.

The gap between those two is not a gap in the RPC surface. It is a direct consequence of the shape of
one small record — specifically, of what that record deliberately does not contain. This lesson takes
the record apart.

## The record

You already have the machinery from Track 01: the world state is a
[Merkle-Patricia trie whose keys are hashed before insertion](/c/mpt-secure-trie), producing one root
that commits to every entry. What that module left as "the value at the end of the path" is what this
lesson is about.

The Yellow Paper defines the world state as a mapping from an address to an *account state* of
exactly four fields, and lists them in this order: `nonce`, `balance`, `storageRoot`,
`codeHash`.<Cite src="yellow-paper" /> ethereum.org's accounts page gives the same four with the same
meanings — a counter of transactions sent or contracts created, the number of wei owned, a 256-bit
hash of the root of a storage trie, and a hash referring to the account's EVM
code.<Cite src="ethereum-docs-accounts" />

Note that the docs page presents them in a different order from the encoding: it lists `codeHash`
before `storageRoot`. Reading fields off an explorer is order-free. [RLP](/c/rlp) is not — it is
positional, with no field names on the wire, so the order above is the only one that produces a
matching hash.

<Aside kind="note">
Four fields is the whole record. Not four fields plus metadata, not four fields plus a type tag
distinguishing a wallet from a contract. There is no field anywhere in the state that says "this is
an EOA". The distinction people draw between account types is inferred entirely from the values of
these four, which is exactly why it turned out to be fragile — the last lesson in this module is
about the day that inference broke.
</Aside>

## Building one by hand

Abstract field lists are easy to nod at. Encode one.

**Subgoal: choose something concrete to represent.** A key-controlled account that has sent three
transactions and holds one ether. Nothing else has ever happened to it.

**Subgoal: pin the two constants.** The two hash fields of an account with no code and no storage are
not zero — they are the hashes of empty structures, which are specific 32-byte values.

The empty code hash is `keccak256` of the empty byte string. You do not have to take that on trust:
EIP-3607 states it normatively as `EMPTYCODEHASH = 0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`,
and EIP-7702 restates the same constant when specifying how a cleared delegation restores an
account.<Cite src="eip-3607" /><Cite src="eip-7702" /> ethereum.org says only that for externally
owned accounts the field is "the hash of an empty string", which is the same claim without the
bytes.<Cite src="ethereum-docs-accounts" />

The empty storage root is the root of a trie with nothing in it — the hash of RLP's empty string,
`keccak256(0x80)`. Computed here with `cast` 1.7.1 on 26 August 2026, that is
`0x56e81f171bcc55a6ff8345e692c0f86e5b48e01b996cadc001622fb5e363b421`.

**Subgoal: encode the four values positionally.** One ether is `10**18` wei, which is
`0x0de0b6b3a7640000`.<Cite src="ethereum-docs-intro-to-ether" /> The RLP of the four-item list, again
computed with `cast` 1.7.1:

```text
f8 4c                                                              list, 76-byte payload
   03                                                              nonce = 3
   88 0de0b6b3a7640000                                             balance = 10^18 wei
   a0 56e81f171bcc55a6ff8345e692c0f86e5b48e01b996cadc001622fb5e363b421   storageRoot
   a0 c5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470   codeHash
```

Seventy-eight bytes total. The nonce is a single byte below `0x80`, so RLP writes it as itself. The
balance gets an `0x88` prefix — a string of eight bytes. Each hash gets `0xa0` — a string of
thirty-two.

**Subgoal: notice what is not there.** Seventy-eight bytes, and not one of them says whose account
this is.

## The address is the key, not a field

The address is not stored in the account because the address is what you used to find the account.
The path into the state trie is `keccak256(address)`, and the record is the value at the end of that
path.<Cite src="yellow-paper" />

For `0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045`, that path is
`0x06e120c2c3547c60ee47f712d32e5acf38b35d1cc62e23b055a69bb88284c281` — sixty-four nibbles of trie
descent, computed with `cast` 1.7.1.

You met the reason keys are hashed in Track 01: an unhashed trie lets an adversary mine addresses
sharing long prefixes and grow the tree's depth on purpose. Hashing the key makes path shape a
property of keccak's output rather than of anything an attacker chooses.

The cost of that defence is the thing this lesson opened with. Going from a path back to an address
means inverting keccak, and keccak is [preimage-resistant](/c/preimage-resistance). Walk the entire
state trie of a fully synced node and you collect every account record on Ethereum together with
sixty-four-nibble paths that identify none of them.

  reality="The address is the trie key; the stored record is only the four fields. Enumerating accounts from a state root is therefore impossible without a separately maintained table of keccak preimages."
  why="Every database table any of us has designed has an id column, and every explorer UI shows the address sitting at the top of the account page as though it were the first field of the row. It is the row's location, not its content."

Three consequences worth carrying out of here.

**Every "all accounts" view you have ever seen is an index.** Somebody replayed the chain, recorded
each address as it appeared in a transaction, and stored the mapping themselves. That index is not
committed to by any state root, no two providers are obliged to agree on it, and nothing in consensus
maintains it.

**A proof is a proof about a path.** `eth_getProof` returns the node list along the path for a given
address plus the account values found there.<Cite src="eip-1186" /> The verifier does the hashing
themselves — they take the address they care about, hash it, and check that the returned nodes really
do spell out that path from the root. Nothing in the proof asserts an address; the address is the
question, not the answer.

**An unknown address and a non-existent one look identical.** Both are simply a path with nothing at
the end of it.

## What you thought was in there

The mental model most people arrive with is a user row. Take the four things that row would obviously
contain and find each one's actual home.

**Transaction history.** Not in the state at all. Transactions live in blocks; the state holds only
their cumulative effect. "Every transaction sent by this address" is not a state query, it is a scan
of every block ever produced — which is why every wallet UI on earth sits in front of an indexer, and
why that indexer is a product dependency rather than an implementation detail.

**Token balances.** A number in some *other* account's storage trie, governed by that contract's
code. Nothing about your account changes when a token moves to you. The next two lessons are about
each half of that sentence.

**A human-readable name.** A record in a naming contract's storage, resolvable in one direction by
whoever knows how to query it, and reversible only if someone bothered to set the reverse record.

**The private key.** Nowhere. It has never been on chain and never will be. The account's connection
to a key is not stored anywhere — it is re-derived from a signature every single time the account
originates a transaction. Track 01 called this [ECDSA public-key recovery](/c/ecrecover); the account
model is where it pays off, because it means the state does not have to hold a public key per
account.

## Absence is not a record of zeroes

An address nobody has ever touched has no path in the trie. It is not a record of four zeroes sitting
there waiting; there is no node, no leaf, no bytes.

When you call `eth_getBalance` on a fresh address and get `0`, that zero was produced by the client
rendering an absence. This is deliberate: EIP-158 specified that whenever the EVM checks whether an
account exists, emptiness is treated as equivalent to nonexistence, so that "once this change is
enabled, there is no longer a meaningful difference between emptiness and nonexistence from the point
of view of EVM execution".<Cite src="eip-158" /> The third lesson in this module is about what that
rule does to accounts you can watch disappear.

## The shape is stable; one field's meaning is not

Four fields is what the Yellow Paper specifies and what ethereum.org still
documents.<Cite src="yellow-paper" /><Cite src="ethereum-docs-accounts" /> Nothing in this module will
add a fifth.

Two pressures on that are worth knowing exist, and both get their own treatment later.

The first is that `codeHash` stopped meaning what it used to mean. Since EIP-7702 shipped in Pectra in
May 2025, an account controlled by a private key can carry a non-empty code
hash.<Cite src="eip-7702" /> ethereum.org's accounts page, retrieved for this lesson on 26 August 2026,
still describes `codeHash` as the one field that "cannot be changed, unlike the other account
fields".<Cite src="ethereum-docs-accounts" /> Both statements are on the record; only one of them is
still true. The sixth lesson in this module is about which application code that broke.

The second is that the four-field record is itself a candidate for replacement. EIP-7864 proposes
merging account fields, storage and code into a single binary tree, which would dissolve
`storageRoot` and `codeHash` as separate committed sub-structures.<Cite src="eip-7864" /> It is Draft
and scheduled into no fork. Track 07 handles it; the reason to know the name now is that it tells you
which parts of this lesson are consensus rules and which are a data-layout choice.

<Check type="explain" concept="account-address-not-stored">
You are handed a state root and a node database that verifiably matches it. Three requests arrive.
For each, say whether you can serve it, and what the answer actually requires.

1. Prove that address `A` held balance `B` at that root.
2. Produce every address holding non-zero ETH at that root.
3. Prove that address `C` did not exist at that root.

<Answer>
**1 — yes, and this is the case the design is optimised for.** Hash `A` to get its path, walk the
trie collecting the nodes along it, and return that node list together with the four field values at
the leaf.<Cite src="eip-1186" /> The verifier repeats the hash themselves and re-derives the root from
the node list. Note the division of labour: you supply the path evidence, they supply the address.
Nothing in the proof has to be trusted to be about the right account, because they computed which
path the right account lives on.

**2 — no, and the obstruction is cryptographic rather than operational.** You can enumerate the trie
perfectly. What you get is a complete set of four-field records indexed by sixty-four-nibble keccak
images. Recovering the addresses means inverting keccak once per account. A client that answers this
question is answering it from a preimage table it chose to keep, and that table is not part of
consensus state and is not committed to by the root — so two providers can legitimately return
different answers while agreeing on every byte of the state.

**3 — yes, with an exclusion proof, and the interesting part is what it proves.** Hash `C`, walk as
far down its path as the trie goes, and return the nodes ending in one that demonstrates the path
does not continue — a branch with an empty slot at the next nibble, or a leaf holding a different
remaining path. Re-deriving the root from those nodes proves no account sits at `C`.

The subtlety: that proves the *path is absent*, which is only the same thing as "the account does not
exist" because the protocol made emptiness and nonexistence indistinguishable.<Cite src="eip-158" />
Before that rule there were two different states here — present-but-empty and absent — and a proof of
one was not a proof of the other.
</Answer>
</Check>

## Where this pays off

**The next lesson** takes the two hash fields seriously. `storageRoot` and `codeHash` are 32 bytes
each and neither contains what it names — they are pointers, and the indirection is what makes a
contract possible at all.

**Lesson three** is the `balance` field: why ETH sitting in a protocol field rather than a contract's
mapping is an asymmetry every product eventually trips over, and why an account with a zero balance
can be deleted out from under you.

**Lesson four** is the `nonce`, which is doing considerably more than counting.

**In Track 03**, `eth_getProof` stops being a curiosity and becomes the tool you reach for whenever
you need one chain to believe a fact about another, or a light client to believe a fact at
all.<Cite src="eip-1186" />

And when you reach statelessness in Track 07, the question "what exactly does a state root commit to"
becomes load-bearing. The answer is on this page: four fields per account, under a hashed key, with
the code and the storage held at arm's length.
