Two current, canonical documents, both wrong about the same field.

The Yellow Paper lists the intrinsic validity tests every transaction passes before anything executes.
Test four: **the sender account has no contract code deployed**, citing EIP-3607 for the
rule.<Cite src="yellow-paper" /> The edition serving from `ethereum.github.io` today is the Shanghai
version, which is to say it predates the fork this lesson is about.

ethereum.org's accounts page, last updated 6 August 2026 and retrieved for this lesson on 26 August
2026, describes `codeHash` as the account field that "cannot be changed, unlike the other account
fields", and states that contract accounts do not have private keys while externally owned accounts
do.<Cite src="ethereum-docs-accounts" />

Every one of those sentences was true from 2015 until May 2025. Each of them is now false in a
specific way, and one of the falsehoods took a security check with it — a check that appears in a
great deal of code written before 2025 and still deployed today.

## Why "has code" and "sends transactions" were mutually exclusive

Start with the rule that broke, because its reason is not the one most people assume.

EIP-3607 forbade transactions from any sender with code. Its motivation was **address collisions**.
Ethereum addresses are 160 bits, so finding a collision between a contract address and an
externally-owned address is a birthday problem at roughly 2<sup>80</sup> operations — and the EIP's
authors estimated that with cycle-finding algorithms this could be done in about a year for
approximately US$10 billion in hardware and electricity.<Cite src="eip-3607" />

The attack that buys is precise. Deploy a safe-looking contract — the EIP suggests a token wrapper or
an AMM — at an address for which you also hold the private key. Attract deposits. Then spend the
contract's balance directly with the key, bypassing the contract's own logic
entirely.<Cite src="eip-3607" /> The EIP's own framing is that a contract's behaviour is supposed to be
constrained by its code, and that the account's funds should not suddenly be spendable by some private
key.<Cite src="eip-3607" />

The fix is one line: reject any transaction whose sender has a code hash other than
`EMPTYCODEHASH = 0xc5d2460186f7233c927e7db2dcc703c0e500b653ca82273b7bfad8045d85a470`, and treat any
block containing one as invalid.<Cite src="eip-3607" />

That line is what made "has code" and "can originate transactions" mutually exclusive, and therefore
what made the EOA/contract binary a real thing rather than a naming convention.

## What actually changed

EIP-7702, final and shipped in Pectra, introduces a transaction type carrying a list of signed
authorisations. Processing one writes a **delegation indicator** — the 23 bytes
`0xef0100 || address` — into the authorising account's code field, and all code-executing operations
then load and execute the code at that address.<Cite src="eip-7702" />

And then, explicitly: the EIP **modifies the restriction put in place by EIP-3607** to allow accounts
whose code is a valid delegation indicator to originate transactions. Accounts with any other code
value still may not.<Cite src="eip-7702" />

So the account now has all three at once: a private key, non-empty code, and the ability to be
`tx.origin`. Every pairwise exclusion that defined the binary is gone.

Three mechanical details are worth having, because they are what your code will actually observe.

**The code hash looks like any other code hash.** It is `keccak256` of those 23 bytes. Computed with
`cast` 1.7.1 on 26 August 2026, an account delegated to
`0x1111111111111111111111111111111111111111` carries
`codeHash = 0xdfe7c7677e3d245aaff2e3e94db902f5fb37475eb611959c71ee641508dcf49a`. Nothing about the
32-byte value's shape distinguishes it from a contract's. You have to fetch the code to know.

**The `0xef` prefix is deliberate and unforgeable.** `0xef` is the byte EIP-3541 banned from the start
of new contract code, precisely so that a marker like this could be introduced later without ambiguity
with real bytecode.<Cite src="eip-3541" /><Cite src="eip-7702" /> The empirical study of delegation
activity spells out the encoding: `0xef` is the deliberately banned opcode, and the following two bytes
`0x0100` identify the format version.<Cite src="arxiv-7702-phishing" />

**It is reversible, and persistent until reversed.** Authorising the zero address clears the
delegation and resets the code hash to the empty code hash.<Cite src="eip-7702" /> Absent that, the
delegation survives every subsequent transaction — the specification chose persistence over
per-transaction scope on purpose, to create enough friction that delegation is treated as a wallet
upgrade rather than a scripting facility.<Cite src="eip-7702" />

## The check that stopped working, precisely

`require(msg.sender == tx.origin)` appears in mints, claims, reward gates and anti-sandwich guards
across the pre-2025 corpus. EIP-7702's security considerations enumerate the three things people meant
by it, and — this is the part worth reading carefully — rate the damage differently for each.

**Purpose one: "`msg.sender` is an EOA."** The EIP says this invariant does not depend on execution
depth and is therefore *not affected*, since `tx.origin` still always has to be an
EOA.<Cite src="eip-7702" />

**Purpose two: protection against atomic sandwich attacks such as flash loans.** The EIP says this
protection *would be broken*. It adds that relying on `tx.origin` this way was already considered bad
practice and could already be circumvented by block producers choosing what to include and when.<Cite src="eip-7702" />

**Purpose three: preventing reentrancy.** The EIP says this use is *more severely affected*, while
noting the authors found no real examples of it in a non-exhaustive search.<Cite src="eip-7702" />

Now the honest reading, because purpose one is where people stop and declare the check fine.

The invariant the EIP names as broken is stated one sentence earlier: allowing `tx.origin` to set code
and execute its own delegated code **breaks the property that `msg.sender == tx.origin` only happens in
the topmost execution frame of a transaction**.<Cite src="eip-7702" /> A delegated EOA runs code in its
own context, in the top frame, and calls your contract from there. Inside your contract, `msg.sender` is
that EOA and `tx.origin` is that same EOA. The equality holds, one frame down, with arbitrary code
having just run and about to run again on the way back.

So the literal claim survives and the useful claim does not:

- The check still proves **"the caller is the account that originated this transaction"**, and it always
  will, because only a key-holding account can originate one.
- The check no longer proves **"the caller has no programmable behaviour"**, **"nothing composed this
  call with other calls atomically"**, or **"this is the outermost frame"**. Those are what almost every
  deployed use of the check actually meant.

Anyone who wrote the guard meaning the first thing is fine. Everyone who wrote it meaning any of the
others has an unsound guard, and the guard will keep passing.

<Aside kind="warn">
The sibling check `address.code.length == 0` deserves the same treatment and gets it less often. It has
always had a false negative: an account under construction has its code hash set to the hash of the
empty string until the initialisation code finishes and the runtime code is deposited, so a constructor
calling out looks code-free to whatever it calls.<Cite src="yellow-paper" /> EIP-7702 added the error in
the other direction — `EXTCODESIZE` on a delegated account returns 23, the size of the indicator, not
the size of the code that will actually run.<Cite src="eip-7702" /> `EXTCODEHASH` behaves the same way,
reporting the indicator rather than following the delegation, and the specification is explicit that
this was chosen so an account could not temporarily masquerade as having a particular
codehash.<Cite src="eip-7702" /><Cite src="arxiv-7702-phishing" /> One check, wrong in both directions,
for two unrelated reasons.
</Aside>

## What to reach for instead

**If you meant "prevent reentrancy", use a reentrancy guard.** The EIP says so itself: there are many
direct and flexible ways to prevent reentrancy — it names a transient storage variable — and
`msg.sender == tx.origin` would be an obscure tool for the job.<Cite src="eip-7702" /> Transient storage
is EIP-1153's `TSTORE`/`TLOAD`, both measured at 100 gas on this repository's
harness.<Cite src="eip-1153" /><Cite src="measured-gas-constants" /> Measured end to end, a transient
guard adds about 284 gas per guarded call, while a storage guard's overhead is **cold/warm dependent
and ranges from roughly 3,100 to 7,100** — the low end when the lock slot is already warm, the high end
on the first guarded call in a transaction, which is EIP-2929's
split.<Cite src="measured-gas-constants" /><Cite src="eip-2929" /> Quote the range, not a single number;
the widely circulated single figures are the extremes of it presented as constants.

**If you meant "no atomic composition with other calls", accept that you cannot test for it.** The EIP
is clear that block producers could already defeat that guard by choosing inclusion, so the property was
never enforceable from inside a contract.<Cite src="eip-7702" /> Design so the invariant does not depend
on being uncomposed — price the operation, bound it, or make it idempotent.

**If you were gating rewards on "is a human", you were never testing that.** A key can be scripted, a
key can be rented, and now a key can carry code. That gate needs a different mechanism entirely.

**Detection is possible, but it is not a security boundary.** You can observe delegation: fetch the
code, check for the `0xef0100` prefix, read the 20 bytes after it. What you cannot do is treat the
answer as durable. Delegation persists until explicitly changed and any transaction can change
it.<Cite src="eip-7702" /> An answer obtained in one transaction says nothing about the next.

<Aside kind="note">
One framing to carry into Track 03, from a security team who audited the surface: the delegate contract
executes *as* the account, and the account's private key retains full control
throughout.<Cite src="nethermind-7702-attack-surfaces" /> Delegation is therefore not an approval with
a scope. It is closer to handing over the key than to granting an allowance — which is why the
specification insists that choosing a delegate is a wallet's job and that there is no safe way for an
application to offer that interface.<Cite src="eip-7702" />
</Aside>

## What this module is deliberately not covering

The mechanism has a lot more surface: authorisation tuple construction, sponsorship and relayer
griefing, storage collisions across successive delegates, the asymmetry between `CODESIZE` during
delegated execution and `EXTCODESIZE` from outside, and what a safe delegate contract looks
like.<Cite src="eip-7702" /> All of that is Track 03's accounts and delegation module, where it belongs
with the EVM machinery it depends on.

What belongs here is the account-model conclusion, and it is a small, durable one. The four-field record
did not change. The set of values one of its fields can hold did, and every inference anyone had built
on top of that field's range had to be re-derived. **`codeHash` was never a type tag.** It was a hash of
some bytes, and a great deal of code was reading it as a type tag and getting away with it for ten
years.

<Check type="spot-bug" concept="eoa-contract-line-is-blurred">
A rewards contract, written in 2023 and still deployed, gates its claim function like this:

```solidity
function claim() external {
    require(msg.sender == tx.origin, "no contracts");
    require(block.timestamp > lastClaim[msg.sender] + 1 days, "too soon");
    _payout(msg.sender);
}
```

The team's threat model, written at the same time, says the guard "ensures claims come from real user
wallets and prevents a contract from composing a claim with a swap in one transaction".

Say which half of that threat model still holds and which does not, and what the attacker actually
does.

<Answer>
**The first half holds in a useless form; the second half is gone.**

"Claims come from real user wallets" — the guard does still establish that `msg.sender` is the
transaction's originator, and only an account with a private key can be that.<Cite src="eip-7702" /> It
never established that the entity behind that key was a person, and it now does not establish that the
caller has no code either.

"Prevents composing a claim with a swap in one transaction" — this is exactly the invariant EIP-7702
names as broken: `msg.sender == tx.origin` no longer implies the topmost execution
frame.<Cite src="eip-7702" />

**What the attacker does.** They sign an authorisation delegating their own EOA to a contract that
batches calls. Their EOA now carries the 23-byte indicator in its code field and can still originate
transactions, because the delegation indicator is the one code value EIP-3607's amended rule
permits.<Cite src="eip-7702" /> They send one transaction from that EOA. The delegate's code runs in
the EOA's context and calls `claim()`, then the swap, then whatever else, all atomically. Inside
`claim()`, `msg.sender` and `tx.origin` are both the EOA, the `require` passes, and arbitrary composed
logic is running on both sides of the payout.

**Two things worth noticing about the fix.** First, the daily rate limit on the second line is
untouched and still does its job — it is a rule about the account, not about the frame, so nothing here
weakens it. Second, there is no drop-in replacement for line one. If the payout must not be composable,
that has to become a property of `_payout` — a bound, a price, a delay — because no in-contract test for
"nothing else is happening in this transaction" exists any more, and the EIP points out block producers
could already defeat the old one.<Cite src="eip-7702" />
</Answer>
</Check>
