"The nonce prevents replay attacks" is the sentence every introduction uses, and it is true of exactly
one of the three ways a signature can be used more than once.

Line the three up, because they have three different mechanisms and one of them is *deliberately*
switched off by default in the newest of them.

1. **The same signed transaction, submitted twice to the same chain.** The nonce handles this.
2. **The same signed transaction, submitted to a different chain.** The nonce does nothing here. A
   chain id, folded into the signature, handles it.
3. **The same signed authorisation, applied on a different chain.** EIP-7702 carries its own chain id
   and its own nonce — and setting the chain id to zero opts out on purpose.

Everything else in this lesson is those three, in order, with the reason each one is shaped the way it
is.

## Layer one: the nonce makes a transaction single-use

A transaction is valid only when its nonce is exactly equal to the sender's current
nonce.<Cite src="yellow-paper" /> Execution consumes that value irrevocably, as the first thing it
does.<Cite src="yellow-paper" /> Put those together and the consequence is immediate: **a signed
transaction can be included at most once on a given chain.** Re-broadcast it an hour later and every
node rejects it, because the value it names has moved on and never comes back.

Notice what is *not* happening. There is no set of seen signatures anywhere. No node keeps a bloom
filter of executed transaction hashes for replay purposes. Nothing grows. The protection is a side
effect of a counter that exists for sequencing, and it costs eight bytes per account rather than a
structure proportional to history. ethereum.org states the property directly, describing the nonce as
protecting "against replay attacks where signed transactions are repeatedly broadcast and
re-executed".<Cite src="ethereum-docs-accounts" />

<Aside kind="note">
The alternative design is instructive. Before chain ids existed, the Morden testnet gave every new
account a starting nonce of 2<sup>20</sup> specifically so that its transactions could not be confused
with mainnet ones — replay protection built out of the counter itself. EIP-2681 records that this
approach went "out of fashion since EIP-155 introduced a more elegant way using chain
identifiers".<Cite src="eip-2681" /> A counter can be made to carry domain information; it just makes a
poor job of it.
</Aside>

### What it protects, and what it does not

The nonce protects **the ledger**. It does not protect **your database**.

Track 01's work on [signature malleability](/c/signature-malleability) is the reason. A secp256k1
signature has a second valid encoding with the same meaning, so before EIP-2 required the low-`s` form
the same authorisation could be presented as two different byte strings — and therefore as two
different transaction hashes.<Cite src="eip-2" /> That never let anyone spend twice; both forms name
the same nonce, and the second is rejected the moment the first lands. What it did was let the
transaction appear on chain under a hash that nobody was watching for.

The general shape is worth keeping: **consensus-level replay protection tells you nothing about whether
your own identifiers are stable.** Systems that key on a transaction hash they computed before
broadcast are relying on a different property from the one the nonce provides.

## Layer two: the chain id, folded into the signature

Now the case the nonce cannot touch.

An account has a nonce *per chain*. The same address on two chains has two independent counters that
happen to start at the same place. So a transaction signed for one chain, carrying nonce 7, is a
perfectly well-formed transaction for any other chain on which that account is also at nonce 7 — same
signature, same fields, same recovered sender.

EIP-155 closed this by changing what gets hashed. Before it, the signing payload was six RLP elements:
`nonce, gasprice, startgas, to, value, data`. After it, nine: the same six plus `chainid, 0, 0` — and
the signature's `v` is set to `{0,1} + CHAIN_ID * 2 + 35` rather than `{0,1} + 27`.<Cite src="eip-155" />

The EIP's worked example makes the change visible. For a transaction with nonce 9, gas price
20 gwei, start gas 21,000, one ether of value and empty data, the signing hash becomes
`0xdaf5a779ae972f972197303d7b574746c7ef83eadac0f2791ad23db92e4c8e53`, and the resulting `v` is 37
instead of 27.<Cite src="eip-155" /> That is where the strange large `v` values in legacy transactions
come from: the chain id is not a separate field on the wire at all, it is arithmetic hidden inside the
recovery byte.

Two consequences of that hiding are worth knowing.

**Modern transaction types stopped hiding it.** Every typed transaction carries `chain_id` as an
ordinary first field of the payload. EIP-7702's type-4 payload, for example, begins
`rlp([chain_id, nonce, max_priority_fee_per_gas, ...])`.<Cite src="eip-7702" /> The protection is the
same; it is simply legible now.

**The old form never went away.** EIP-155 was deployed as a backwards-compatible change: the existing
scheme using `v = 27` and `v = 28` "remains valid and continues to operate under the same rules as it
did previously".<Cite src="eip-155" />

That second point produced a real, documented, still-live hazard, and it is the best illustration in
this module of why a protocol's compatibility decisions are a security surface. The Ethereum
Foundation's own Spurious Dragon announcement spells it out: because the old format is still accepted,
transactions created on alternative Ethereum-based chains that have not implemented EIP-155 — Ethereum
Classic is the example it names — can still be replayed on Ethereum
mainnet.<Cite src="ethereum-blog-spurious-dragon" /> EIP-155's own rationale describes the intended
outcome as a way to send transactions that work on Ethereum without working on ETC or the Morden
testnet, and encourages other chains to adopt it with their own unique
value.<Cite src="eip-155" /> Adoption is the operative word. The defence works when both sides
implement it.

## Layer three: the authorisation, with a wildcard

EIP-7702's authorisations are signed objects that are not transactions, so they need their own answer
to both questions. They have one.

An authorisation tuple is `[chain_id, address, nonce, y_parity, r, s]`, and the authority is recovered
from `keccak(MAGIC || rlp([chain_id, address, nonce]))` with `MAGIC = 0x05`, requiring `s` to be at most
`secp256k1n/2` exactly as EIP-2 does for transactions.<Cite src="eip-7702" /><Cite src="eip-2" /> Both
protections are present: a nonce that must equal the authority's current value and is incremented on
success, and a chain id that is verified against the current chain.<Cite src="eip-7702" />

And then the wildcard. The chain id is required to be either the current chain's id **or zero**, where
zero means the authorisation is valid on any chain.<Cite src="eip-7702" />

This is deliberate, and the specification explains the trade honestly. The concern it names is what the
code at the delegate address does on *some other* chain: a deterministic deployment can put identical
code at the same address everywhere, but verifying that "may not always be desirable", so a specific
chain id narrows the authorisation's scope — and "when universal deployment is preferred, simply set
chain ID to 0".<Cite src="eip-7702" />

Read that as a product engineer and the risk is plain. A chain-id-zero authorisation is a signature
that grants control of your account to whatever code sits at one address, on every chain that supports
the mechanism, whether or not you have ever used those chains and whether or not the code there is the
code you looked at. The first empirical study of delegation activity treats exactly this as one of two
amplifying attack surfaces, describing chain-agnostic authorisation as permitting replay-like
compromise across independent networks.<Cite src="arxiv-7702-phishing" />

Track 03 builds the delegation machinery properly. What belongs here is the shape: **the newest layer
of replay protection ships with a documented opt-out, and the opt-out is a single field set to zero.**

## The pattern underneath all three

Step back and the three layers are one idea applied at three scopes.

A signature is dangerous exactly when it can be used in a context its signer did not have in mind. So
bind it to two things: **a domain** — which chain, which contract, which purpose — and **a value that
can be consumed exactly once**.

- Transactions: domain is the chain id; the single-use value is the account nonce.
- Authorisations: domain is the chain id, optionally waived; the single-use value is the account nonce
  again.
- Application-level signatures: neither is provided for you. An [EIP-712 typed-data](/c/eip-712-typed-data)
  signature that a contract consumes has no nonce unless that contract maintains one, and it applies to
  whatever contract accepts it unless the [domain separator](/c/domain-separator) pins the chain and the
  verifying address.<Cite src="eip-712" />

That last bullet is where product engineers actually get hurt, because it is the only one of the three
that is your job. The protocol gave you both halves of the pattern for transactions. For anything your
own contract verifies, both halves are yours to build, and leaving either one out produces a signature
that works somewhere you did not intend or works more times than you intended.

<Check type="explain" concept="eip-155-chain-id-replay">
Four signed artefacts, all produced by the same private key. For each, say where and how many times it
can be used, and which mechanism decides.

1. A type-2 transaction on mainnet, nonce 7, already included in a block.
2. A pre-EIP-155 legacy transaction, nonce 3, never broadcast.
3. An EIP-7702 authorisation with `chain_id` set to 1.
4. An EIP-712 signature authorising "withdraw 100 units", verified by a contract you wrote, with no
   nonce in the struct.

<Answer>
**1 — used once, everywhere, permanently.** Both layers are working. The nonce is consumed on mainnet,
so it cannot be re-included there.<Cite src="yellow-paper" /> The chain id is inside the signed payload
of a typed transaction, so it is not a valid transaction anywhere else.<Cite src="eip-7702" /> This is
the fully protected case and it needed no thought from you.

**2 — valid on every EIP-155-era chain where that account is at nonce 3.** The signature commits to six
elements and none of them is a chain id, and the old scheme is still accepted by
mainnet.<Cite src="eip-155" /><Cite src="ethereum-blog-spurious-dragon" /> Each chain consumes its own
counter, so it can be included once per chain, not once in total. This is the historical hazard that
EIP-155 was written for, and it survives because the fix was backwards-compatible rather than a
break.

**3 — once, on chain 1 only.** The chain id is verified against the current chain and the nonce must
equal the authority's current value, and is incremented on success.<Cite src="eip-7702" /> Had that
field been zero instead of one, the same signature would be a valid delegation on every chain
implementing EIP-7702 — the one place in this lesson where correct protocol behaviour is to accept a
replay.<Cite src="eip-7702" />

**4 — unbounded, and this is the only one that is your bug.** The protocol layers do not apply: this
signature is never a transaction, so no account nonce is consumed by verifying it. Anyone holding the
bytes can present them to your contract again, and again. If the domain separator pins the chain id and
the verifying contract, the damage is confined to that contract on that chain; if it does not, the same
signature is also good against any other deployment that accepts the same struct.<Cite src="eip-712" />
The fix is to supply both halves of the pattern yourself: a domain in the separator, and a per-signer
counter or a consumed-digest set that the contract actually checks.
</Answer>
</Check>

existing application code: what an account with code is allowed to be, and which security check stopped
working the day that changed.

itself.

**In Track 06**, signature replay is a vulnerability class with its own taxonomy — cross-chain,
cross-contract, cross-function, and the same signature accepted twice. The three layers here are the
reference model that makes those four look like variations rather than four separate things to
memorise.

signed for one chain that is *meant* to be acted on somewhere else. The mechanisms are the same; only
the intent is inverted.
