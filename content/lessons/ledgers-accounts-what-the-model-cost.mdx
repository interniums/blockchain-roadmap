Read this module back as an invoice.

Lesson three: accounts get deleted when they hold nothing, because entries in a shared global map are
expensive to keep and somebody had to clean up after an attack that made millions of
them.<Cite src="ethereum-docs-accounts" /> Lesson four: one key is one strictly ordered stream, and a
gap in it is a wall. Lesson five: single-use had to be *constructed* out of a counter, and
cross-chain scoping had to be added years later in a second fork.<Cite src="eip-155" /> Lesson six: a
security check that a decade of code depended on turned out to rest on a rule about what a long-lived
identity is allowed to be.

None of those are accidents of implementation. They are line items on one architectural decision, and
this lesson is that decision with both columns showing.

## One asymmetry generates the whole bill

Strip both models to a single sentence each.

**In UTXO, a transaction declares its own dependencies before anything runs.** Each input names the
exact output it spends. Two transactions are independent when neither consumes an output the other
consumes and neither spends an output the other creates — and both of those are visible from the
transactions' own fields, without executing
anything.<Cite src="bitcoin-programming-survey" /> [You worked this out in the previous module](/c/utxo-parallelism):
the dependency graph is known in advance, which is what makes the model naturally partitionable.

**In the account model, what a transaction touches is discovered by executing it.** A call to one
address may reach any address. There is no field in the transaction that bounds the set, and no
analysis short of running it produces one. Two transactions that look completely unrelated may collide
on a storage slot four calls deep.

Everything below follows from that one difference.

## What UTXO charges

The whitepaper's complaint is titled "Lack of state" and is specific: a UTXO is spent or unspent, and
"there is no opportunity for multi-stage contracts or scripts which keep any other internal state
beyond that", so the model supports "simple, one-off contracts and not more complex 'stateful'
contracts".<Cite src="ethereum-whitepaper" />

Long-lived state shared between strangers is the thing it makes painful. Expressing an ongoing
obligation means encoding it as a chain of outputs, each spend recreating the state as a new output —
which means some specific party has to hold the current one and keep advancing it, and two unrelated
strangers cannot both write to it whenever they like.<Cite src="utxo-debt-representation" />

There is a second charge people notice sooner. The protocol never computes anyone's balance. A balance
is a wallet-side sum over the outputs that wallet can spend, so answering "what is this identity worth"
requires an index consensus does not
maintain.<Cite src="bitcoin-programming-survey" /> [That was the previous module's point](/c/no-global-state),
and it is the mirror image of lesson three in this one: Ethereum has a `balance` field precisely
because it decided that question should be answerable from state.

## What accounts charge

Four items, and they are not independent of each other.

**A required global ordering.** Because the protocol cannot know what a transaction touches until it
runs it, every transaction has to be executed in one agreed sequence. Not "usually", not "when they
conflict" — always, because conflict cannot be established in advance. The Yellow Paper's state
transition is a fold over an ordered list, and there is no version of it that is a set
operation.<Cite src="yellow-paper" />

**Per-sender sequencing.** The nonce, and everything lesson four spent 2,000 words on. Note where it
comes from: a mutable account can be mutated between the moment you sign and the moment your
transaction executes, so the protocol needs a way to pin *which* state your signature was meant for. A
UTXO transaction has no equivalent problem — the outputs it names either still exist or they do not.

**Contention over hot state.** When strangers mutate one slot in place, they serialise on it. The
account model's greatest strength — a pool, a registry, a market that anyone can write to — is a
single point of contention by construction. The performance question and the design question are the
same question.

**Value in choosing the order.** This is the item people meet last and feel first. If ordering changes
outcomes, and someone gets to choose the ordering, then choosing it is worth money. Extractable value
is not a defect that better software removes; it is the shadow that a globally ordered log of
operations on shared mutable state casts. Track 05 prices it.

### And replay had to be built

Compare the two models on the question lesson five was about, because the difference is clean.

Re-submitting a UTXO transaction is a double-spend attempt against outputs that no longer exist, and it
is rejected by exactly the rule that rejects any double spend.<Cite src="bitcoin-programming-survey" />
Single use is a *property of the object being consumed*. Nothing was added to get it.

Re-submitting an Ethereum transaction has to be caught by a counter that exists for a different reason,
maintained per account, on the account.<Cite src="yellow-paper" /> And when chains split, the counter
turned out not to be enough, so a chain id had to be folded into the signed payload in a hard
fork.<Cite src="eip-155" />

Neither approach is cleverer. One model gets a property for free from its data structure; the other has
to spend a field and a fork on it.

## The axis is still live, in both directions

Two current pieces of work make the point better than any argument.

**Solana kept the account model and made declaration mandatory.** A transaction carries an explicit
list of the accounts it will touch, flagged for writability, so the runtime knows the complete
read/write set before executing an instruction and can schedule non-conflicting transactions
together.<Cite src="solana-sealevel-note" /> That is UTXO's *property* — dependencies known in advance
— obtained by asking the developer rather than by changing what the state is. Track 09 builds it
properly, including where the analogy stops.

**Ethereum is chasing the same property at block granularity.** EIP-7928's motivation is one sentence
long and could serve as this lesson's thesis: transaction execution cannot be parallelised without
knowing in advance which addresses and storage slots will be
accessed.<Cite src="eip-7928" /> It notes that EIP-2930 introduced optional per-transaction access
lists but that they are not enforced — a pricing hint, not a
declaration.<Cite src="eip-7928" /><Cite src="eip-2930" /> Block-level access lists record every
account and storage location accessed during a block's execution, along with post-execution values,
which enables parallel disk reads, parallel transaction validation, parallel state-root computation and
state reconstruction without executing the transactions at
all.<Cite src="eip-7928" /> As of this writing the EIP is in Review status and names no activation
fork.<Cite src="eip-7928" />

Notice the shape of that solution, because it is the account model's constraint showing through. The
declaration cannot come from the sender — by the time you know what a transaction touched, you have run
it. So it comes from whoever builds the block, who ran everything anyway, and ships the answer along
with the block so that everyone else does not have to.

<Aside kind="note">
The generalisation worth keeping: **parallelism is bought with declaration.** Every system that
executes transactions concurrently gets the read/write set before execution, from somebody. UTXO gets
it from the transaction's structure. Solana gets it from the developer. Ethereum would get it from the
block builder. There is no fourth option where you get it for nothing, and any claim that a chain is
"parallel" is really a claim about who was made to declare what.
</Aside>

## Neither one is a mistake

It is tempting to score this. Do not.

The account model bought exactly what Ethereum said it was buying: state that many unrelated parties
mutate in place under a stable identity, which is the substrate every application in Tracks 05 and 06
is built on.<Cite src="ethereum-whitepaper" /> The invoice above is the honest cost of that substrate,
and every item on it is a design constraint rather than a defect to be engineered away.

The productive question is never "which model is better". It is: **for this operation, is the shared
mutable state doing work?** If a payment only needs to move value between two parties who each know
what they hold, the ordering, the contention and the extractable value are all pure cost. If it needs
a pool's price, a registry's current owner or a market's depth, the shared state is the entire product
and the cost is what it costs.

Two payments, in the same second. Alice pays Bob 3 and Carol 2 out of a balance of 10. Separately and
unrelatedly, Dave pays Erin 1.

1. Under UTXO, which of these can be validated concurrently, and how is that decided?
2. Under the account model, which can be validated concurrently?
3. Alice sends her two payments as two separate transactions from one key. What is true of their
   ordering, and does it depend on whether they conflict?
4. What single change would make the account-model version parallelisable?

<Answer>
**1 — Alice's and Dave's can run concurrently, and it is decided by reading the transactions.** Each
input names the specific output it spends, so the two transactions' input sets are visibly disjoint
before either is executed.<Cite src="bitcoin-programming-survey" /> Alice's transaction is one
transaction with two outputs to Bob and Carol plus a change output back to herself, so her two payments
are not two things to order in the first place.

**2 — neither, and not because they conflict.** The account model cannot establish that they *don't*.
Alice's transaction might be a call into a contract that touches Dave's balance, or a slot that Dave's
transaction reads. Nothing in either transaction bounds what it reaches, so both must be placed in the
one global sequence and executed in it. The cost here is paid by transactions that never conflict —
which is most of them.

**3 — strictly ordered, and no, it does not depend on conflict at all.** Nonce N cannot execute before
N−1, whatever the two transactions touch.<Cite src="yellow-paper" /> Two payments to two unrelated
strangers are as strictly sequenced as two writes to the same slot. This is the sharpest single
illustration in the module: the ordering constraint is a property of the *sender's identity*, not of
the work.

**4 — a binding declaration of the read/write set.** That is the whole answer, and it is what both live
proposals supply from different directions. Solana requires the transaction to carry its account list
with writability flags.<Cite src="solana-sealevel-note" /> EIP-7928 has the block carry the accounts and
storage locations its transactions accessed, so validators can parallelise even though no sender
declared anything — and it says plainly that parallelisation is impossible without knowing the accessed
set in advance.<Cite src="eip-7928" /> Note what *doesn't* work: EIP-2930's optional access list is a
gas hint the EVM does not enforce, so it cannot be relied on for
scheduling.<Cite src="eip-7928" /><Cite src="eip-2930" />
</Answer>
</Check>

## Where this pays off

**In Track 05**, extractable value stops being a piece of folklore about bots and becomes the fourth
line item on this page. Every MEV mechanism — private order flow, order-flow auctions, builder markets
— is a response to the fact that ordering shared-state mutations is valuable.

**In Track 07**, block-level access lists are the concrete engineering, and the thing to carry into it
is the constraint they exist to work around rather than the data structure they
use.<Cite src="eip-7928" />

**In Track 09**, Solana's account model is the natural next comparison: same word, different object,
and the declared-access requirement is the reason it can schedule what Ethereum cannot.<Cite src="solana-sealevel-note" />

And immediately after this module, blocks and the mempool are where the global ordering stops being an
abstraction. Somebody assembles that sequence, from a set of candidate transactions they chose. The
next two modules are about who, and how.
