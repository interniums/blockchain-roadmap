Write a header encoder and you will, at some point, stop and reread the specification, because three
of the fields you are being asked to serialise appear to be constants.

The difficulty is zero. The nonce is eight zero bytes. The ommers hash is a fixed 32-byte value that
is the same in every block. You are not misreading it, and they are not optional. A client validating
your header will *check* all three and reject the block if any of them is anything else. You are
required to transmit forty-odd bytes of guaranteed-zero information in every block, forever, and to
verify that someone else did too.

That is not sloppiness. It is a decision, and reading the modern header field by field is largely an
exercise in reading which decisions the protocol was willing to make and which it was not.

## Three fields that are enforced constants

Precision first, because "these fields are ignored" is a common and wrong summary. They are not
ignored. They are pinned.

The header-validation routine contains these checks, among others:<Cite src="execution-specs-osaka-fork" />

```python
if header.difficulty != 0:
    raise InvalidBlock
if header.nonce != b"\x00\x00\x00\x00\x00\x00\x00\x00":
    raise InvalidBlock
if header.ommers_hash != EMPTY_OMMER_HASH:
    raise InvalidBlock
```

`EMPTY_OMMER_HASH` is defined as `keccak256(rlp.encode([]))` — the hash of the RLP encoding of the
empty list.<Cite src="execution-specs-osaka-fork" /> Its value,
`0x1dcc4de8dec75d7aab85b567b6ccd41ad312451b948a7413f0a142fd40d49347`, is printed verbatim in the
header illustrations of both EIP-4895 and EIP-4788.<Cite src="eip-4895" /><Cite src="eip-4788" />

Body validation adds a fourth check in the same spirit: a block whose ommers list is non-empty is
invalid outright.<Cite src="execution-specs-osaka-fork" />

The distinction between "ignored" and "pinned" is not academic. An ignored field is a place you could
smuggle data. A pinned field is not. There is exactly one field in the modern header where a proposer
may write arbitrary bytes, and it is `extra_data`, capped at 32 bytes by the same validation
routine.<Cite src="execution-specs-osaka-fork" />

### Why they were kept

Because the header is an RLP list, and [RLP lists carry no field names](/c/rlp) — only order.

Deleting a field from the middle of an ordered list changes the encoding of every field after it,
which changes every header hash, which changes every parent hash, which means every piece of software
that reads a header — clients, explorers, indexers, wallets, bridges, hardware wallets, an
unbounded set of contracts holding hard-coded offsets — has to change simultaneously at a block
boundary. That is a flag day, and a flag day across an ecosystem nobody controls.

EIP-3675 chose the alternative: freeze the fields at constants, keep the layout, and pay the bytes
forever.<Cite src="eip-3675" />

The bill, if you want it concretely. Under RLP, the integer zero encodes as a single byte; eight zero
bytes encode as a one-byte prefix plus eight; a 32-byte hash encodes as a one-byte prefix plus
thirty-two.<Cite src="yellow-paper" /> That is forty-three bytes per block, in perpetuity, for
information content of exactly zero. Multiply by however many blocks you think Ethereum will produce.
The ecosystem looked at that number and at the cost of a coordinated flag day and did not hesitate.

<Aside kind="note">
This is worth generalising, because you will meet it in your own systems. The cost of a schema change
is not the change; it is the coordination. Once a format is read by software you do not control, dead
fields become permanent, and the correct engineering response is usually to accept the dead weight
and move on. Ethereum's header is a public, well-documented instance of a decision every long-lived
protocol makes privately.
</Aside>

## Ommers: gone, not rare

The most misleading of the three fields is the ommers hash, because unlike difficulty and nonce — the
words alone tell you they are proof-of-work residue — "uncle blocks" are still described in a great
deal of current-sounding material as an occasional occurrence.

They are not occasional. They are impossible.

**What they were for.** Under proof of work, block production was a race. Two miners could solve the
same height within the network's propagation delay of each other, and one of them would lose: valid
work, valid block, no reward. That penalty falls hardest on the worst-connected miners, because
propagation delay is what decides the race, which hands a structural advantage to whoever sits
closest to the network's centre. Ommers were the countermeasure — a mechanism to reference and
partially reward blocks that were valid but lost, blunting the centralising pull of low
latency.<Cite src="yellow-paper" />

**Why proof of stake removes them.** There is no race to nearly win. Each slot has exactly one
assigned proposer, chosen in advance. Nobody else is entitled to propose in that slot, so there is no
second valid block competing for the same position and nothing to reward. The mechanism does not
become rare; its precondition disappears.<Cite src="eip-3675" />

Two things that are *not* ommers, and get called ommers by people reaching for the nearest word:

**A missed slot** produces no block at all. Nothing is orphaned because nothing was made. The next
lesson is about how much product code breaks on that fact alone.

**A reorged-out block** was a real block that lost the fork choice. It is not referenced by the
canonical chain, earns nothing, and leaves no trace in any header. There is no field for it and no
reward for it. The finality module treats reorgs properly; the point here is only that the
compensation mechanism that once existed for losing a race is not the mechanism that handles losing
a fork choice, and that neither is alive in the header.

## prevRandao: a field that was recycled rather than retired

Now the interesting one, because it is the counter-example. When the Merge needed somewhere to put
the beacon chain's randomness, the protocol did not append a field. It repurposed one.

EIP-4399 redefined `mixHash` — the field at index 13, zero-indexed, formerly holding a proof-of-work
artefact — to carry `prevRandao`, the latest RANDAO mix from the previous block's post beacon state,
and changed the `DIFFICULTY` opcode at `0x44` to return that value instead.<Cite src="eip-4399" />
Both the field and the opcode were renamed to match.

The design notes are instructive, and each answers a question you would actually ask:

**Why reuse a field rather than append one?** No encoding change, and the header is already available
inside the EVM's execution context, so exposing the value costs nothing new. It also keeps the
execution layer fully executable from the block alone, without additional inputs from the consensus
client.<Cite src="eip-4399" />

**Why `mixHash` and not `difficulty`, which is the field that went dead?** Because client software
implementing pre-Merge logic leaned heavily on `difficulty` for total-difficulty computation, which
was the basis of the proof-of-work fork choice. Putting a large random number there risked a class of
hidden fork-choice bugs.<Cite src="eip-4399" /> Freezing `difficulty` at zero was the safer move
precisely because zero is inert.

**A side effect worth knowing.** Since the returned value is now a random 256-bit quantity rather
than a difficulty, a value greater than `2**64` is a reliable signal that execution is happening in a
post-Merge block — a trick both contracts and decompilers use.<Cite src="eip-4399" />

### It is not safe randomness, and the EIP says so first

`block.prevrandao` is reachable from Solidity in one expression, looks random, and is free. It is
also biasable by the one party best placed to exploit it, and EIP-4399's own security-considerations
section is the clearest statement of how.<Cite src="eip-4399" />

**One bit per slot, by refusal.** The proposer for a slot sees what the RANDAO mix would become if
they propose. If they do not like it, they can decline to propose. The mix is then not updated for
that slot. That is a one-bit choice, and its cost is the proposer's forgone rewards — the block
reward and the priority fees they would have collected.<Cite src="eip-4399" />

**Colluding proposers get more bits, but not durable ones.** Proposers of `n` consecutive slots
working together get `n` bits of influence. The influence lasts only until the first honest RANDAO
reveal afterwards: one honest proposal is enough to unbias the mix, even if it was biased for several
slots running.<Cite src="eip-4399" />

**A second bit, almost free.** A proposer can also censor the transaction that reads the randomness,
forcing it into the next block and therefore onto a mix the proposer already knows. The EIP notes the
opportunity cost of this variant is negligible.<Cite src="eip-4399" />

Put the economics together and the conclusion is uncomfortable but simple: **whenever the prize
exceeds what a proposer forgoes by skipping a slot, biasing the draw is the rational move for the
proposer.** For a lottery, an NFT mint allocation, a liquidation ordering or any other mechanism with
a payoff larger than a block's rewards, the attacker you should model is not an outside adversary. It
is the validator who happens to be assigned the slot your draw lands in — a party who needs no
exploit, no capital and no coordination, only the decision not to act.

The EIP's own advice for applications that must use it is to rely on *future* randomness with a
substantial lookahead — its worked suggestion is at least four epochs between the moment inputs are
locked and the moment the mix is read, so that the set of proposers who could bias the draw is not
yet known to the people with something to win.<Cite src="eip-4399" /> That helps. It does not make
the source unbiasable, and for a large enough prize the right answer remains a commit-reveal scheme
or an external verifiable random function.

<Aside kind="warn">
The same EIP quotes the usual rate of missed proposals on mainnet as about one
percent.<Cite src="eip-4399" /> Treat that as a figure from a document written years before you read
it, not as a current measurement — the module's second practice has you sample real slots and produce
your own number, with a date attached. Any argument that depends on how often proposers skip needs a
figure you measured, because the whole point of the attack is that the skip rate is a *choice*.
</Aside>

## Reading the header as a stratigraphy

Once you know what to look for, the header records its own history. Grouping by the fork that
introduced or froze each field:

- **Frontier-era core.** Parent hash, ommers hash, coinbase, state root, transactions root, receipt
  root, logs bloom, difficulty, number, gas limit, gas used, timestamp, extra data, mix hash, nonce.
  Fifteen fields, and the header stayed at fifteen for years.<Cite src="yellow-paper" />
- **London.** `baseFeePerGas`, the first structural change in a long time, arriving with the fee
  market.<Cite src="eip-1559" />
- **Paris (the Merge).** No new field. Instead: `difficulty`, `nonce` and `ommersHash` frozen at
  constants,<Cite src="eip-3675" /> and `mixHash` repurposed as
  `prevRandao`.<Cite src="eip-4399" />
- **Shanghai.** `withdrawalsRoot`.<Cite src="eip-4895" />
- **Cancun.** `blobGasUsed` and `excessBlobGas` for the blob fee market,<Cite src="eip-4844" /> and
  `parentBeaconBlockRoot` for the consensus-layer window.<Cite src="eip-4788" />
- **Prague.** `requestsHash`.<Cite src="eip-7685" />

Which yields a compact statement of the shape of the whole thing: **three of twenty-one fields carry
no information, and one more carries information that arrived by recycling a dead field rather than
adding a new one.** Roughly a fifth of the header is archaeology.

And the layer is still accumulating. The in-development Amsterdam fork directory in execution-specs
declares a 23-field header, adding a block access list hash and a slot
number.<Cite src="execution-specs-amsterdam-blocks" /> Unshipped, unscheduled, and subject to change
— but the direction is clear enough: fields get added, fields get frozen, and nothing ever gets
removed.

<Aside kind="note">
Two fields in that Frontier-era list deserve a footnote because they are alive but often
misdescribed. `coinbase` is the fee recipient: it collects priority fees, while the base fee is
burned and reaches nobody.<Cite src="execution-specs-osaka-blocks" /><Cite src="eip-1559" /> And
`timestamp` is set by the proposer with only a weak execution-layer constraint — the specification
requires nothing more than that it be strictly greater than the parent's.<Cite src="execution-specs-osaka-fork" />
The next lesson is about what follows from that.
</Aside>

A colleague reviewing your header encoder makes three claims. Assess each, and where a claim is
wrong, say what the correct version is and what code would break if you believed the wrong one.

1. "The fossil fields are ignored by clients, so we can leave them out of the RLP encoding and save
   forty-odd bytes on our internal representation."
2. "Since the difficulty field is dead, we could use it as a channel to tag blocks our own builder
   produced."
3. "Uncle rate is a useful health metric for the network, so let us chart the ommers count per block
   over time."

<Answer>
**Claim 1 — wrong, and wrong in the most expensive possible way.** The fields are pinned, not
ignored: validation rejects any header whose difficulty is non-zero, whose nonce is not eight zero
bytes, or whose ommers hash is not the constant. More importantly, this confuses the *internal
representation* with the *encoding*. You may store whatever you like internally, but the moment you
compute a block hash you must RLP-encode the full list in the fork's declared order. Omit three
fields and every subsequent field shifts position, so the encoding is different, so the keccak is
different, so your hash matches nothing. The failure has no diagnostic: you get 32 wrong bytes, not
an error naming a missing field.

**Claim 2 — wrong, and it is the interesting one.** "Dead" and "writable" are different properties.
`difficulty` is dead in the sense of carrying no protocol meaning, and pinned in the sense that any
value other than zero makes the block invalid. There is no smuggling channel there. The one field
where a proposer may write arbitrary bytes is `extra_data`, and even that is capped at 32 bytes by
validation. If you want to tag your own blocks, that is the field, and its size limit is the reason
the tags you see in practice are short strings rather than structured data.

**Claim 3 — the metric does not exist any more.** The ommers list is always empty and the ommers hash
is a constant, so the chart is a flat zero line by protocol rule rather than by network health. Under
proof of work an uncle rate genuinely measured something — how often propagation delay cost someone a
block — but proof of stake assigns one proposer per slot, so there is no near-miss to count.

The health metric your colleague actually wants is the **missed-slot rate**: how often the assigned
proposer produced nothing. That is a real, varying quantity, it is measured on the consensus layer
rather than in execution headers, and it is not visible in the field they were about to chart —
because a missed slot leaves no block at all, not an orphaned one. Chasing that distinction is the
next lesson.
</Answer>
</Check>

## Where this pays off

**The block-hash practice** in this module asks you to print the three fossils and assert their
constant values. That assertion is the cheapest possible regression test for a header encoder, and it
fails loudly on the exact mistake most encoders make.

**Reading any protocol specification.** The habit this lesson builds — asking of each field "when did
this arrive, is it still doing anything, and what would breaking it cost" — transfers directly to
every versioned format you will maintain.

**Randomness in contracts** is a security topic the Solidity and security tracks return to. The
argument is already complete here: the party with the cheapest attack is the one the protocol
schedules, and the fix is not a better hash but a different mechanism.

**The next two lessons** take the two live consensus-layer fields seriously — one that says what time
it is, and one that opens a window from the EVM into the beacon chain.
