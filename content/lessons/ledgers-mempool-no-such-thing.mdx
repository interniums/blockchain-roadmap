Same transaction hash. Same second. Two RPC providers.

Provider A returns a full transaction object with a null `blockNumber` — pending. Provider B returns
`null` — as far as it is concerned, this transaction does not exist. Nobody is lying, nothing is
misconfigured, and neither provider is behind. Both answers are correct, and they will stay
correct.

Track 01 established that a pool is a per-node cache rather than a shared structure. This lesson
takes the next step, which is the one that changes code: **there is no observer anywhere that sees
the union of those caches**, so every question you can ask about unconfirmed state is a question
about one machine. Once you accept that, a whole category of transaction-monitoring bug stops being
mysterious and starts being predictable.

## The protocol declines to define it

The `eth` wire specification is the closest thing to a normative description of transaction
exchange, and what it says about the pool is deliberately thin: client implementations keep track of
the set of pending transactions in the transaction pool, and that pool "is subject to client-specific
limits".<Cite src="devp2p-eth-wire" /> The current protocol version is
eth/72.<Cite src="devp2p-eth-wire" /> Across all of it there is no message that reads a pool, no
message that reconciles two pools completely, and no object that any block commits to.

Read the validity rules and the abdication becomes explicit. The spec fixes the parts consensus needs
— signature, intrinsic gas, balance, and a nonce equal to or greater than the account's current nonce
— and then hands the rest to the implementer: it is "up to implementations to determine how many
'future' transactions with nonce greater than the current account nonce are valid, and to which
degree 'nonce gaps' are acceptable".<Cite src="devp2p-eth-wire" />

Then it goes further, in a sentence worth reading twice. Implementations must not disconnect peers
for sending invalid transactions and should discard them instead, "because the peer might be
operating under slightly different validation rules".<Cite src="devp2p-eth-wire" />

The wire protocol is written on the assumption that honest nodes disagree about what belongs in a
pool. Divergence is not a degraded mode the network recovers from. It is the operating condition the
protocol was designed around.

## Four independent reasons two honest nodes differ

"Nodes disagree" is easy to nod at and hard to reason with. Name the mechanisms, because each one
produces a different signature in your logs.

**Admission.** A pool applies a price floor and a size ceiling before anything else. go-ethereum's
default minimum tip for pool acceptance is 1 wei, and it is a configurable field
(`PriceLimit`).<Cite src="geth-legacypool" /> The spec notes that rejecting encoded transactions
larger than 128 kB is common practice rather than a rule.<Cite src="devp2p-eth-wire" /> An operator
running a higher floor holds a strictly smaller pool than its neighbour, permanently.

**Capacity.** go-ethereum's defaults, read from the source, are `GlobalSlots` of 4096 plus 1024
executable slots, `GlobalQueue` of 1024 non-executable slots, `AccountSlots` of 16 executable slots
guaranteed per account, and `AccountQueue` of 64.<Cite src="geth-legacypool" /> Roughly five thousand
executable slots, shared by every account on Earth transacting through that node. Two nodes under the
same load with different capacity settings evict different transactions.

**Time.** A queued transaction has a `Lifetime` — three hours by default — and the pool runs an
eviction ticker once a minute to enforce it.<Cite src="geth-legacypool" /> A node that started an
hour later than its neighbour is holding a different age distribution.

**Reachability.** A node learns of a transaction only if some peer announced it, and announcements
are filtered: a node should announce hashes the remote peer probably does not already
have.<Cite src="devp2p-eth-wire" /> Whether a particular hash crossed a particular link is a
question about topology and timing, and nothing retries it to completion.

None of these are failures. All four are correct behaviour, and all four are configured
per-operator.<Cite src="geth-cli-options" />

## Every unconfirmed query answers for one machine

Now make that concrete at the API boundary, because this is where the abstraction leaks into your
code.

`txpool_content` returns two associative arrays, `pending` and `queued`, each mapping sender address
to nonce to transaction.<Cite src="geth-rpc-txpool" /> `txpool_status` returns two counts.
`txpool_inspect` returns a textual summary.<Cite src="geth-rpc-txpool" /> All three are documented as
inspecting "the transaction pool" — meaning the pool of the process answering the call.

The same is true of methods that do not look pool-shaped at all. `eth_getTransactionByHash` on a hash
that has not been mined is a pool lookup wearing chain-query clothing. A pending-transaction
subscription is a firehose of one node's admissions. `eth_getTransactionCount` with the `pending` tag
is the account nonce advanced by that node's view of that account's in-flight transactions, which is
why it disagrees with `latest` and with other providers.

The geth documentation includes one detail that will matter for the next two lessons, so notice it
now: in `txpool_content`, "there may be multiple transactions associated with the same account and
nonce".<Cite src="geth-rpc-txpool" /> A pool does not hold a sequence. It holds candidates, and some
of them are mutually exclusive.

### The load-balancer trap

Here is the specific shape this takes in production, and it is worth internalising because it looks
like a bug in your code and is not.

An RPC endpoint is a hostname, not a node. Behind it sits a fleet. You submit through the endpoint and
land on node 7. You poll the endpoint four seconds later and land on node 12. Node 12 may not have
received the announcement yet, may have rejected it on price, or may not be running the same client.
Your two observations are of two different pools, and you have no way to tell from the response which
node answered.

Private submission makes the gap total rather than probabilistic. A transaction sent to a private
endpoint is never gossiped, so it is absent from every public pool by construction, and operators
treat even the derived nonce as sensitive: Flashbots Protect includes such transactions in
`eth_getTransactionCount` results only for the `pending` tag, and only when the request is signed by
the sender's own key and carries the signature in an `X-Flashbots-Signature`
header.<Cite src="flashbots-protect-nonce-management" /> An unsigned query to that endpoint returns a
nonce that accounts only for public-mempool transactions.<Cite src="flashbots-protect-nonce-management" />

## What you may and may not conclude

The practical value of all this is a short table of valid inferences. Everything else is a guess.

**A node returned your transaction as pending.** Valid conclusion: this node held it when asked.
Invalid: that it is widely propagated, that it will be included, or that any other node has it.

**A node returned `null`.** Valid conclusion: this node did not hold it when asked. Invalid — and
this is the expensive one — that it was rejected, dropped, or never existed. Absence of evidence is
the default condition of a gossip overlay.

**Two nodes disagree.** Valid conclusion: nothing at all is wrong. Invalid: that one is stale.

**A receipt exists.** Valid conclusion: it was included, at a stated block, and the account nonce
moved. This is the only observation in the list that is about the chain rather than about a cache,
and it is therefore the only one a product decision should ever rest on.

The rule that falls out: **use pool state to explain, never to decide.** Pool observations are
excellent for telling a user *why* something is slow. They are worthless as the trigger for anything
irreversible.

<Check type="spot-bug" concept="mempool-view-is-node-local">
A team builds a dashboard for their relayer service. It subscribes to pending transactions from two
providers, computes the symmetric difference of the two hash sets every 30 seconds, and pages
on-call when the difference exceeds 5% of the union — reasoning that a healthy network should have
converged pools and a large divergence means one provider is degraded.

They also add a rule: if their own submitted transaction appears in provider A's pending set but not
provider B's after 60 seconds, mark the submission as "partially propagated" and re-broadcast the
same signed bytes to three more endpoints.

What is wrong with each half, and what should replace them?

<Answer>
**The alert is measuring the wrong thing, and it will fire forever.** Pools are bounded caches with
per-operator admission policy, capacity limits and lifetimes.<Cite src="geth-legacypool" /> Two
providers with different `PriceLimit` settings, different capacity, different peer sets and possibly
different clients will always hold materially different sets, and the wire protocol explicitly
anticipates peers "operating under slightly different validation
rules".<Cite src="devp2p-eth-wire" /> A 5% threshold on the symmetric difference is a threshold on a
quantity with no target value. The predictable outcome is the one every team reaches: the alert fires
constantly, gets muted, and is therefore silent when something real happens.

What to measure instead: something with a defined correct value. Head block number advancing.
Provider-reported head lagging the consensus head. Your own submitted transactions reaching a receipt
within a latency budget you chose. Each of those has a known-good state; pool overlap does not.

**The re-broadcast is harmless but useless, and the label is a lie.** Re-sending identical signed
bytes cannot produce a second transaction — the signature and nonce are the same, so any node that
already has it responds "already known"<Cite src="geth-txpool-errors" /> and any node that does not
treats it as a first sighting. So the action costs nothing except an incorrect internal state name.

"Partially propagated" implies a measurable coverage fraction. Nothing measures that. The union of
pools is not held anywhere, so the denominator does not exist. If the transaction was submitted
through a private endpoint, the correct coverage number is zero and the transaction may still land in
the next block.<Cite src="flashbots-protect-nonce-management" />

The replacement rule for both halves: stop treating divergence as an error signal, and stop
inferring propagation from observation. The two states that exist are "we have a receipt" and "we do
not have a receipt yet", and the second one is not further decomposable from outside.
</Answer>
</Check>

## Where this pays off

**Pending and queued** are the next lesson, and they are the reason a single node's answer is still
worth reading carefully — the two states have different causes and different fixes.

**Replacement** only makes sense once you accept there is no single pool: your replacement has to
clear an acceptance rule at every node that holds the incumbent, independently, and some nodes will
have neither transaction.

**Private order flow** is this lesson taken to its limit. If a transaction is sent to a builder
rather than gossiped, its coverage of the public pools is exactly zero, and every analytics pipeline
built on pool observation is sampling a biased subset without knowing it.

**Inclusion lists** are the sharpest confirmation that this is a permanent property rather than a
defect. EIP-7805 has each committee member build its list "according to their subjective view of the
mempool", and the mechanism's censorship resistance comes precisely from those views being
independent — an adversary would have to corrupt many of them at
once.<Cite src="eip-7805" /> The design does not try to fix the subjectivity. It is built on it.
