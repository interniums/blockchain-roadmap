The ticket is one line: *show the user their balance.*

In an account ledger this is a `SELECT`. On Ethereum it is `eth_getBalance`, one RPC call, one
number, answered from state the protocol maintains for exactly this purpose. On Bitcoin there is
nothing to select and no method to call, because the number does not exist until somebody computes
it — and *who* computes it turns out to determine what it says.

This lesson is the consequences lesson. One structural fact from the first two — every check a
transaction needs is local to that transaction — produces three results that look unrelated and are
not: there is no balance anywhere, the dependency graph between transactions is knowable before
execution, and no long-lived identifier accumulates history by default.

## Balance is a client-side fold

The developer guide states it without ceremony. When your wallet tells you that you have a 10,000
satoshi balance, what it means is that 10,000 satoshis are sitting in one or more unspent
outputs.<Cite src="bitcoin-devguide-transactions" />

So "balance" is a fold: scan the UTXO set, keep the entries whose locking scripts this wallet can
satisfy, sum the amounts. Every part of that sentence is wallet-side. The protocol maintains the
set; the filter and the sum are yours.

Which means the answer depends on what the wallet knows how to satisfy — and that is not a fixed
quantity.

A modern wallet does not store a bag of keys. It derives a whole tree of them from one seed, per
BIP-32.<Cite src="bip-32-hd-wallets" /> Restoring from a seed phrase therefore does not restore a
list of your outputs; it restores the *ability to generate* the keys, after which the wallet must go
looking for outputs that match. That search cannot run forever, so BIP-44 specifies where it stops:
the address gap limit is 20, and on hitting twenty unused addresses in a row the software concludes
there is nothing beyond that point and stops scanning the chain.<Cite src="bip-44-account-hierarchy" />

Now the failure mode writes itself. A user receives payments at addresses beyond a run of twenty
unused ones — because a script generated addresses in a loop, because two devices derived in
parallel, because they exported and used keys outside the wallet. Restore that seed and the balance
comes back short. Nothing is lost and nothing is corrupt. The funds are exactly where they were; the
fold stopped early.

## Asking about an address is a scan, not a lookup

Press further: forget wallets, ask the node directly. What is this address worth?

Bitcoin Core does have an answer, and its shape is the point. `scantxoutset` **scans** the unspent
transaction output set for entries matching an output descriptor — `addr(...)` for a given address,
`pkh(...)` for a given public key, or an extended public key with a derivation range.<Cite src="bitcoin-rpc-scantxoutset" />
Its result reports how many unspent outputs were scanned and the total amount found.<Cite src="bitcoin-rpc-scantxoutset" />
The call takes a `start`/`abort`/`status` action, with `status` returning progress as a
percentage.<Cite src="bitcoin-rpc-scantxoutset" /> An RPC with a progress bar is telling you what
kind of operation it is. The reference page also carries an explicit warning that the call is
experimental and may be removed or changed.<Cite src="bitcoin-rpc-scantxoutset" />

The aggregate view is the same story. `gettxoutsetinfo` reports statistics over the whole set —
`txouts`, the number of unspent transaction outputs, and `total_amount` — with no per-address
breakdown anywhere in the result.<Cite src="bitcoin-rpc-gettxoutsetinfo" />

There is no address-keyed index, because there is no address-keyed *anything*. The consensus state
is a set of outputs keyed by the outpoint that created them, and "which of these belong to a given
address" is a predicate you evaluate over all of them.

This should land as a familiar conclusion reached by an unfamiliar route. Track 01 established that
Ethereum's state is a map with no enumeration primitive, which is why every holder list and portfolio
view is reconstructed off-chain by indexing logs. Bitcoin gets to the same operational place —
**every product needs an indexer** — from the opposite direction. Ethereum has the identity and lacks
the iteration; Bitcoin has the iteration and lacks the identity.

<Aside kind="warn">
The practical consequence for anyone integrating: an address balance served by an explorer API is a
number computed by that explorer's index, from that explorer's interpretation of which outputs count
and which chain tip is current. Two providers can disagree, and neither is lying. This is the same
class of hazard as two Ethereum RPC providers disagreeing about pending transactions, and it wants
the same defence — decide which source is authoritative for money-moving decisions and do not
average.
</Aside>

## Every dependency is declared before execution

Now the property that makes this model interesting to systems people.

An input names the exact output it spends, by txid and index, and it does so in the transaction's own
fields.<Cite src="bitcoin-devguide-transactions" /> Nothing is discovered by running the transaction.
Read the bytes and you know the complete set of state entries it will remove and the complete set it
will add.

So take two transactions and ask when their order matters. Exactly two situations impose one.

**They consume the same output.** Each output may be used as an input only once; any subsequent
reference is a double spend and is rejected.<Cite src="bitcoin-devguide-block-chain" /> Note this is
not an ordering constraint that can be satisfied by picking the right sequence — it is a conflict.
Whichever the network orders first is valid and the other is permanently invalid, in either
direction.

**One spends an output the other creates.** Here order is real and the Ethereum whitepaper spells it
out while describing Bitcoin: if two transactions A and B are in a block such that B spends a UTXO
created by A, the block is valid if A comes before B and not
otherwise.<Cite src="ethereum-whitepaper" />

Everything else is independent. Two transactions that touch neither the same inputs nor each other's
outputs produce the same final set applied in either order, or concurrently. And crucially, **which
case you are in is visible from the transaction's fields before anything executes.** The dependency
graph is static.

Compare what has to happen on Ethereum. Whether two transactions conflict depends on which storage
slots their execution ends up touching, and that depends on control flow, which depends on state,
which depends on execution. You cannot know without running them — and if you run them and they
conflict, you have to unwind.

<Aside kind="note">
Be precise about what this claim is. It is a property of the *model*: the dependency graph is
statically knowable, so the work is partitionable in principle. It is not a claim that any particular
Bitcoin implementation executes transactions in parallel, or that Bitcoin is fast. Throughput is
governed by block size and block interval, which is a separate set of decisions entirely. Confusing
"parallelisable in principle" with "parallel in production" is the most common way this property gets
oversold.
</Aside>

The reason this matters far beyond Bitcoin is that the industry has spent a decade trying to buy the
property back. Solana kept an account model but requires each transaction to declare, up front, every
account it will read or write, which is what lets the runtime schedule non-overlapping transactions
concurrently.<Cite src="solana-sealevel-note" /> Ethereum's own draft work on block-level access
lists is chasing the same thing: making the set of state a block touches explicit rather than
emergent.<Cite src="eip-7928" />

Both are recovering, with extra machinery, something the UTXO model has for free — because in that
model there is nothing to declare, since naming the state you touch *is* how you write a transaction.

## Identity does not accumulate — by default, and only by default

The third consequence is the one most likely to be overstated, including by people who should know
better, so hold two things at once.

Outputs are independent. Nothing in the protocol links two of them beyond the public transaction
graph, so the natural practice is to receive each payment to a fresh script, and the developer guide
recommends exactly that, including for change outputs.<Cite src="bitcoin-devguide-transactions" />
It goes further: if each public key is used exactly twice — once to receive, once to spend — the user
gains a significant amount of financial privacy, whereas reusing an address as a static payment
identifier lets anyone track that person's receiving and spending habits, including how many satoshis
they control in known addresses.<Cite src="bitcoin-devguide-transactions" />

So the default is genuinely different from an account model, where one address is your permanent
handle and everything it has ever done is queryable forever by anyone.

And now the other half. The transaction graph is fully public, and public graphs get clustered.

The reference result here is Meiklejohn and colleagues' 2013 study, which built its analysis on two
heuristics that both exploit the mechanics from lesson one. **Heuristic 1: if two or more addresses
are inputs to the same transaction, they are controlled by the same user** — a spender must hold the
private key for every input, so the alternative would require independent parties to share private
keys.<Cite src="meiklejohn-fistful" /> This is transitive, so observing A and B together and later B
and C together merges all three.<Cite src="meiklejohn-fistful" />

**Heuristic 2 targets change.** Because outputs are indivisible, the only way to spend part of one is
to produce a change output — which is why most Bitcoin transactions generate
change<Cite src="bitcoin-programming-survey" /> — and in the common wallet idiom that change address is generated
internally and never reused — so a user is unlikely to have given it out to anyone, and might not
know it exists.<Cite src="meiklejohn-fistful" /> The paper's rule identifies an output as change when
it is the first appearance of that key, the transaction is not a coin generation, no output address
also appears among the inputs, and no *other* output is also a first appearance.<Cite src="meiklejohn-fistful" />

Applying the first heuristic alone, the authors partitioned the network into 5,579,176 clusters,
starting from 12,056,684 public keys.<Cite src="meiklejohn-fistful" /> The authors are careful about
the second one, noting it exploits a habit of use rather than a property of the protocol, and that
falsely linking even a small number of change addresses can collapse the graph into superclusters
that no single user controls.<Cite src="meiklejohn-fistful" /> Treat those figures as what that study
reported about the chain it studied, not as a current measurement.

The structure of the finding is what transfers: **the privacy property is a default of usage, and
usage leaks.** Heuristic 1 works because of an unavoidable feature of the model — you must sign for
every input you spend. Heuristic 2 works because of change, which lesson one showed is structurally
forced.

<Check type="explain" concept="utxo-parallelism">
Four transactions are broadcast at roughly the same time. Using only the fields of the transactions
themselves — no execution — classify each pair as independent, ordered, or conflicting, and say what
a validator must do about it.

- **T1** spends outputs `(a,0)` and `(b,1)`; creates `(T1,0)` and `(T1,1)`.
- **T2** spends output `(c,0)`; creates `(T2,0)`.
- **T3** spends output `(T1,1)`; creates `(T3,0)`.
- **T4** spends output `(b,1)`; creates `(T4,0)`.

Then answer the part that matters: why could you do this without running anything, and what would
the equivalent exercise require on Ethereum?

<Answer>
**T1 and T2 — independent.** Disjoint inputs, and neither spends anything the other creates. Applied
in either order or concurrently they yield the same set. A validator may process them in any order.

**T1 and T3 — ordered.** T3 spends `(T1,1)`, an output T1 creates, so T1 must come first. Within a
single block this is a hard rule: a block containing both is valid only if T1 precedes
T3.<Cite src="ethereum-whitepaper" /> Before T1 is applied, `(T1,1)` is not in the set and T3 fails
the first validity check.

**T1 and T4 — conflicting.** Both name `(b,1)`. Each output may be spent only once, and any
subsequent reference is a forbidden double spend.<Cite src="bitcoin-devguide-block-chain" /> There is
no ordering that makes both valid; whichever is ordered first survives and the other becomes
permanently invalid. Note this is not a scheduling problem for the validator to solve — it is a
decision the consensus layer makes, and it is precisely the decision the whole chain exists to make.

**T2 and T3, T2 and T4 — independent.** No shared inputs, no producer-consumer relationship.

**Why you could do this statically:** every state entry each transaction removes is named in its
inputs and every entry it adds is named in its outputs.<Cite src="bitcoin-devguide-transactions" />
There is no path by which a transaction touches an entry it did not name, so reading the fields is
sufficient.

**On Ethereum:** you could not answer at all from the transaction fields. Two transfers to the same
token contract may or may not touch the same storage slots depending on the addresses involved, the
contract's logic, and the current state; a call may branch into a different contract entirely. The
conflict set is a property of execution, which is why the ecosystem has had to *add* declaration —
Solana by requiring every account access up front,<Cite src="solana-sealevel-note" /> and Ethereum,
in draft form, by publishing the state a block touched at the block level.<Cite src="eip-7928" />
</Answer>
</Check>

## Where this pays off

**The next lesson** turns the three consequences into a decision. If dependencies must be declared,
then a piece of state that many strangers want to modify concurrently is a piece of state that many
strangers must fight over one at a time — and that is the whole argument for the account model, in
one sentence.

**On the account model**, "there is no balance" flips into "there is exactly one place a balance
lives", and [account-four-fields](/c/account-four-fields) will read as a deliberate answer to this
lesson rather than as a definition to memorise.

**On mempools and ordering**, the double-spend framing above is worth keeping: what the consensus
layer fundamentally decides is which of several conflicting attempts to remove the same state entry
wins. Every fee market, replacement policy and reordering game you meet later is a fight over that
decision.

**On the alternative-VM track**, [sealevel](/c/sealevel) is this lesson's parallelism property
retrofitted onto accounts, with the costs of the retrofit visible — declared access is a tax paid by
every developer, and getting the declaration wrong is a new class of bug that does not exist here.

**And on privacy**, the shape of the Meiklejohn result generalises past Bitcoin: a system with a
public graph leaks through structure, so any privacy claim that rests on the absence of names rather
than on the absence of links is a claim to check rather than accept.
