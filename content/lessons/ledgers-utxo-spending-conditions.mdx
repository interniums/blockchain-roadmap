Your product needs a rule: this pot of money moves only if two of three named people approve it.

In every system you have built, that rule lives somewhere *outside* the money. A policy row, an
approvals table, an IAM statement, a multi-sig service in front of a treasury wallet. The funds sit
in an account, the account has an owner, and a separate subsystem decides whether a given request is
allowed to touch it. Ownership is an identity; authorisation is a lookup against that identity.

Bitcoin does not work like that, and the difference is not cosmetic. There is no owner field on an
output. The rule *is* the money's location. Each output carries a small program stating what a
future spender must supply, and "owning" that output means nothing more or less than being able to
supply it.

The previous lesson treated that program as an opaque predicate. This lesson opens it.

## Two halves, written at different times by different people

Every output carries a **locking script** — `scriptPubKey` in the serialisation, also called the
pubkey script. It is placed there by whoever created the output, and it expresses the condition
under which the output may later be consumed.<Cite src="bitcoin-devguide-transactions" />

Every input carries an **unlocking script** — `scriptSig`, also called the signature script. It is
written by whoever is spending, and it supplies the data that satisfies the referenced output's
condition.<Cite src="bitcoin-devguide-transactions" />

Two consequences follow immediately, and both are load-bearing.

**The condition is fixed at receive time, not at spend time.** Whoever pays you decides the bytes of
the locking script, which is why the receiver has to communicate the condition they want — and why,
historically, that communication was limited to what a short address could express.<Cite src="bitcoin-devguide-transactions" />

**Authorisation lives inside the spending transaction.** There is no account record anywhere holding
a public key. The full public key is not even revealed until the moment of spending — the output
commits only to a hash of it, and the spender presents the preimage in the signature
script.<Cite src="bitcoin-devguide-transactions" /> That should sound familiar: it is a
[commitment](/c/commitment) in exactly the Track 01 sense, opened at spend time.

Validation runs the two halves in sequence over one shared stack, starting with the spender's
signature script and continuing to the end of the output's pubkey script; if the stack does not end
in a false value, the spend is accepted.<Cite src="bitcoin-devguide-transactions" />

## Walking the common case

Pay-to-Public-Key-Hash is the canonical form, and it is five tokens:

```text
scriptPubKey:   OP_DUP OP_HASH160 [PubkeyHash] OP_EQUALVERIFY OP_CHECKSIG
scriptSig:      [Sig] [PubKey]
```

Run it with the purpose of each step named rather than just the step.<Cite src="bitcoin-devguide-transactions" /><Cite src="bitcoin-p2pkh-scripts" />

**Subgoal one — the spender supplies evidence.** The signature script pushes two pieces of pure
data: a signature, then the full uncompressed-or-compressed public key. No logic has run yet.

**Subgoal two — bind the presented key to the committed hash.** `OP_DUP` copies the public key so
that one copy survives the check. `OP_HASH160` replaces the top copy with its hash. The pubkey
script then pushes the hash the payer committed to. `OP_EQUALVERIFY` compares the two and aborts
validation outright if they differ.

**Subgoal three — bind the key to the transaction.** `OP_CHECKSIG` verifies the signature against
the now-authenticated public key and the transaction data. Passing step two proved *which* key is
allowed; step three proves the holder of that key authorised *this* spend.

**Subgoal four — read the verdict.** If a false value is not on top of the stack at the end, the
spend is valid.<Cite src="bitcoin-devguide-transactions" />

Notice that the script never learns whose money it is. It learns that a hash matched and a signature
verified. That is the entire notion of ownership at the protocol level, and it is why the module
concept is phrased as a *satisfiable condition* rather than an identity.

<Aside kind="note">
The address you paste into a wallet is not an account and does not appear in the ledger. It is the
pubkey hash — or, for pay-to-script-hash, a script hash — wrapped with a version byte and a checksum
so that a human can transcribe it without silent corruption.<Cite src="bitcoin-devguide-transactions" />
What is actually stored on chain is the locking script. The address is a transport encoding for one
parameter of it.
</Aside>

## What the signature covers, and why that is a design surface

You know from Track 01 that a signature is only meaningful relative to what it commits to. Bitcoin
makes that explicit and, unusually, makes it a per-input choice.

The data signed for a normal spend includes the txid and index of the output being consumed, that
output's pubkey script, the pubkey scripts and amounts of the outputs being created — in essence the
entire transaction *except* the signature scripts themselves.<Cite src="bitcoin-devguide-transactions" />

`OP_CHECKSIG` reads a flag attached to each signature, the **signature hash type**, which selects
how much of the transaction that signature covers. Three base types exist. `SIGHASH_ALL`, the
default, signs all inputs and all outputs. `SIGHASH_NONE` signs the inputs but none of the outputs,
so anyone may redirect the funds unless some other signature protects them. `SIGHASH_SINGLE` signs
only the output at the same index as this input. Each base type may be combined with
`SIGHASH_ANYONECANPAY`, which restricts the signature to this one input and lets anyone add or
remove others.<Cite src="bitcoin-devguide-transactions" />

Because every input is signed separately, one transaction can carry several different coverage
choices at once.<Cite src="bitcoin-devguide-transactions" />

Sit with how different that is from what you have seen. On Ethereum, one signature authorises one
whole transaction; [eip-712-typed-data](/c/eip-712-typed-data) exists precisely because signing
anything *narrower* than that had to be invented on top, in application code, with a domain
separator to keep the scopes apart. Here, partial coverage is a protocol primitive, and the domain
separation problem is handled by the fact that each signature also commits to the specific outpoint
it is spending.

Selectable coverage is what makes multi-party transactions constructible without a coordinator you
have to trust. The guide's CoinJoin example is the clean case: several mutually distrusting people
who want to move funds among themselves face the question of who goes first, and they answer it by
building one transaction that does all the spending simultaneously, so none of them can take the
others' satoshis and no outside observer can reliably tell who ends up controlling
what.<Cite src="bitcoin-devguide-contracts" /> Building the equivalent in an account model means one
party constructing and the others trusting, or a contract holding everyone's funds in escrow.

## Malleability, structurally

Track 01 taught you signature malleability as an algebraic fact about ECDSA and
[low-s-normalisation](/c/low-s-normalisation) as the fix. Bitcoin's version of the problem is worse
than that, and the reason is architectural rather than cryptographic.

None of the signature hash types protect the signature script, because a signature cannot sign
itself. So a third party who sees a broadcast transaction can make non-functional modifications to
the signature script — padding it with data that is dropped before the pubkey script runs, for
instance — without invalidating it.<Cite src="bitcoin-devguide-transactions" />

The modification changes nothing about which outputs are consumed or created. But it changes the
transaction's hash. And in this model, **the txid is the pointer**: every input identifies its
prior output by the txid of the transaction that created it.<Cite src="bitcoin-devguide-block-chain" />
Change the txid and every child transaction that was built on it now references something that does
not exist.

For a payment destined straight for a block, this is a nuisance — the funds move, the tracking
breaks, and a system watching for a specific txid reports that the transaction vanished.<Cite src="bitcoin-devguide-transactions" />
For anything that chains spends *before* confirmation it is fatal, which is why the developer guide
tells you not to build on unconfirmed transactions absent SegWit, and why the recommended way to
track a payment is by the outputs it consumes rather than by its hash — those cannot be changed
without invalidating the transaction.<Cite src="bitcoin-devguide-transactions" />

BIP-141, Segregated Witness, is the structural fix, activated in August
2017.<Cite src="bitcoin-devguide-transactions" /> It splits the identifier in two: the `txid` stays
the double-SHA256 of the traditional serialisation, which no longer contains the witness data, while
a new `wtxid` is the double-SHA256 of the serialisation *with* it.<Cite src="bip-141-segwit" /> Move
the malleable bytes outside the thing the pointer hashes, and third-party mutation stops moving the
pointer.

There is a general lesson here worth carrying past Bitcoin: **if an identifier is a hash, everything
inside the hash preimage is part of your API.** Anything a third party can change inside it, they can
use to change your identifiers.

## The machine is deliberately small

Bitcoin Script is a Forth-like, stack-based language, and the developer guide names both of its
constraints as intentional: it is stateless, which ensures that once a transaction is on the chain
no later condition can render it permanently unspendable, and it is not Turing-complete —
specifically, it has no loops or gotos — which makes it less flexible but more predictable and
greatly simplifies the security model.<Cite src="bitcoin-devguide-transactions" /> The survey
literature reads the outcome the same way: Bitcoin's long record without major consensus-level
failures is attributed largely to the non-Turing-complete script language and its limited opcode set,
which significantly reduce the system's attack surface.<Cite src="bitcoin-programming-survey" />

The Ethereum whitepaper reads the same choice from the outside and agrees about the mechanism while
disagreeing about the price: loops are missing to avoid infinite loops during transaction
verification, and although any bounded loop can be unrolled, doing so produces very space-inefficient
scripts.<Cite src="ethereum-whitepaper" />

Now connect it to something you already know. [determinism-requirement](/c/determinism-requirement)
says every validating node must compute the same result. A language with unbounded loops threatens
that from a resource angle: a node cannot know, before running a script, whether running it will
finish. Ethereum's answer was to meter execution and charge for each step, which is what gas is.
Bitcoin's answer was to remove the possibility, which is why **there is no gas in Bitcoin and no need
for any.** The cost of validating a script is bounded by its own size before it runs.

That is the trade in one sentence: Bitcoin pays in expressiveness for a validation cost it can bound
statically; Ethereum pays in a metering system for expressiveness it can bound only dynamically.

## What the predicates actually look like

Four shapes are worth recognising, because between them they cover most of what people build.

**Threshold signatures.** An m-of-n multisig pubkey script lists n public keys and requires m
matching signatures before the output can be spent.<Cite src="bitcoin-devguide-transactions" /> Note
one wart worth knowing about, because it is a good example of consensus code being frozen by
compatibility: `OP_CHECKMULTISIG` consumes one more stack item than m indicates, an off-by-one in the
original implementation that must be preserved forever, so the signature list is prefixed with a
dummy value that is consumed and discarded.<Cite src="bitcoin-devguide-transactions" />

**Commit to a script instead of a key.** Pay-to-Script-Hash puts a hash of a second program, the
redeem script, in the output. The spender supplies the satisfying data *and* the full redeem script;
the network checks the hash matches and then executes the redeem script as if it had been the pubkey
script all along.<Cite src="bitcoin-devguide-transactions" /> This is the same commit-then-reveal
structure as P2PKH, one level up: the payer does not need to know or transmit the condition, only its
hash, so an arbitrarily complicated policy fits behind an ordinary-looking address.

**Escrow with an arbitrator.** The guide's worked example is a 2-of-3 between customer, merchant and
arbitrator: the customer can pay the merchant, the merchant can refund the customer, or the
arbitrator can break a tie — and because the arbitrator alone is one of three, they cannot take the
money.<Cite src="bitcoin-devguide-contracts" /> If the arbitrator misbehaves, the other two can move
the funds to a fresh 2-of-3 with a different arbitrator.<Cite src="bitcoin-devguide-contracts" />
There is no contract holding custody here — the policy is the output.

**Time.** A transaction's `nLockTime` says the earliest point at which that *transaction* may enter
a block, expressed as a block height below 500 million and as a Unix timestamp at or above
it.<Cite src="bitcoin-devguide-transactions" /> BIP-65 adds `OP_CHECKLOCKTIMEVERIFY`, which moves the
constraint into the locking script: the *output* itself becomes unspendable until the specified time
or height.<Cite src="bip-65-cltv" /> That relocation is what makes the difference between a delay you
have to be trusted to honour and one enforced by the network.

Stack those and you get payment channels: the guide's micropayment channel has the payer lock funds
into a shared output and the two parties repeatedly re-sign a settlement transaction, with a time
lock guaranteeing the payer gets a refund if the counterparty disappears.<Cite src="bitcoin-devguide-contracts" />
Hold on to that structure — lesson four shows it is the general shape of every stateful thing built
in this model, and the reason that shape is limiting.

## Consensus-valid is not the same as relayed

One more gate exists, and it will feel familiar from the mempool lesson in Track 01.

After several dangerous bugs in early versions, nodes added a check that only accepts transactions
whose scripts match a small set of believed-safe templates. That is the standardness test, and
transactions passing it are called standard.<Cite src="bitcoin-devguide-transactions" /> Non-standard
transactions are not invalid — they may be accepted by nodes not running the default settings, and
once in a block they are processed normally.<Cite src="bitcoin-devguide-transactions" />

Two of the standardness rules matter to anyone designing a spending policy. A signature script may
only push data onto the stack; it cannot push opcodes, other than opcodes that solely push
data.<Cite src="bitcoin-devguide-transactions" /> And bare multisig requiring more than three public
keys is non-standard — which is a large part of why real multisig is deployed as P2SH, where the
network sees only a hash and accepts the output regardless of what the redeem script
says.<Cite src="bitcoin-devguide-transactions" />

The product lesson is the same one the Ethereum mempool taught: **there are two rule sets, and the
one that decides whether your transaction propagates is the looser, more mutable, node-configurable
one.** A policy that is consensus-valid but non-standard is a policy you cannot broadcast normally,
and that is a shipping problem, not a theory problem.

<Check type="spot-bug" concept="script-vm">
A team is designing a two-party channel. Their plan: Alice funds an output that requires both
signatures, Bob countersigns a refund transaction returning the funds to Alice after a time lock,
and Alice broadcasts the funding transaction. Only once Bob has handed over the signed refund does
Alice consider the channel safe to use.

They test it on a local network, everything works, and they ship. Payments start getting stuck.
Name the defect, and name the two independent fixes.

<Answer>
**The defect is that the refund transaction references the funding transaction by txid, and the
funding transaction's txid is not stable until it is in a block.**

Bob signs a refund that spends output zero of funding transaction `T`. Alice broadcasts `T`. Anyone
watching can modify `T`'s signature script in a way that does not invalidate it — the signature
cannot sign itself, so that data is unprotected — and the modified copy hashes to a different
txid.<Cite src="bitcoin-devguide-transactions" /> If the modified copy is the one that gets mined,
Alice's funds are in an output nobody has a signed refund for. She needs Bob's signature to move
them, and Bob has no obligation to co-operate.

The guide names this exact hazard for micropayment channels: if someone uses malleability to break
the link between the two transactions, one party can hold the other's funds hostage without doing
any work.<Cite src="bitcoin-devguide-contracts" />

**Fix one — do not sign over an unconfirmed txid.** Wait for the funding transaction to confirm
before treating the refund as valid. This is correct and it is also the reason the guide advises
against depending on unconfirmed transactions at all when large amounts are at stake.<Cite src="bitcoin-devguide-transactions" />
It costs you a confirmation delay at channel open, which for a payments product is a real UX cost.

**Fix two — remove the malleability instead of waiting it out.** Under SegWit the txid is computed
over a serialisation that excludes the witness data, so third-party mutation of that data no longer
changes the txid.<Cite src="bip-141-segwit" /> The chain of unconfirmed transactions becomes stable
by construction. This is the fix that made production payment channels practical, and the ordering
is not an accident: the structural fix had to land before the product could exist.

The transferable version of the lesson: **the test passed because a local network had no adversary in
it.** The failing input is not a value, it is a participant.
</Answer>
</Check>

## Where this pays off

**The next lesson** takes the fact that authorisation lives entirely inside the spending transaction
and derives three consequences from it: nobody can be asked for a balance, dependencies between
transactions are declared rather than discovered, and identity does not accumulate by default.

**Lesson four** revisits the payment channel above and asks the general question it raises — if the
only way to hold evolving state is a chain of outputs that a specific party must advance, what
happens when the state is a lending pool that ten thousand strangers need to update?

Beyond the module, two threads continue. When you meet the EVM's gas metering, you now have the
counterfactual: the alternative to metering is a language that cannot loop, and it was chosen on
purpose.<Cite src="bitcoin-devguide-transactions" /> And when you write your first signature-gated
contract, the SIGHASH design is worth remembering as the road not taken — a protocol where the scope
of a signature is a first-class field rather than something an application standard bolts on.
