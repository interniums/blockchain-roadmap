Pick the least exotic on-chain product you can think of. Not a derivatives protocol — a shared pot.
Ten thousand unrelated people deposit into it, it accrues interest, and each of them can withdraw
their share at any time. One number that everyone reads, that many people write, that nobody owns.

In the account model that is four lines of Solidity and you already know what it compiles to: a
persistent key-value store hanging off one stable address, mutated in place. The whole apparatus you
spent Track 01 on — the storage trie, the state root, the account record — exists to make that store
verifiable.

Now build it out of unspent outputs.

This lesson is why you cannot, cheaply, and why Ethereum said so in writing before it shipped.

## The only way to hold state is a thread of outputs

There is exactly one construction available. Put the state in an output: the amount is the pot, and
the locking script encodes the rules. To change the state, spend that output and create a new one
carrying the updated state. The pot advances by being destroyed and recreated, one transaction at a
time.

You have already seen this shape. The developer guide's micropayment channel is precisely it: funds
locked into a shared output, and a settlement transaction the two parties re-sign as the balance
between them shifts, with a time lock as the escape hatch if one side disappears.<Cite src="bitcoin-devguide-contracts" />
A channel is a two-party state machine implemented as a chain of transactions, and it works.

Now scale the participant count and watch three things break.

**Someone has to hold the thread.** The current state exists as one specific unspent output, and
advancing it requires a transaction that satisfies its locking script. In the channel, the two
parties hold each other's signatures. With ten thousand strangers, either every update needs
everyone's signature, or a designated party is trusted to hold and advance the state on everyone's
behalf — which is a custodian with extra steps.

**Concurrency becomes exclusion, not contention.** Two people trying to deposit at the same time both
build transactions spending the same state output. One lands. The other does not merely execute
second — it becomes permanently invalid, because the output it names is gone. In an account model a
losing race costs you a worse price or a failed require. Here the transaction cannot be included at
all, and the client has to rebuild it against the new state and try again. Lesson three called this
property "every dependency is declared"; from this side it reads as "every shared object is a
mutex", and the pot is one object.

**Value and logic are welded together.** The state lives in an output, and an output is money. There
is no way to keep a registry, a counter or a permission bit that is not also a spendable amount that
somebody must keep alive by paying fees to move it.

The research that set out to fix this names the gap exactly. The Extended UTXO model was designed to
support "a substantially more expressive form of validation scripts, including scripts that implement
general state machines and enforce invariants across entire transaction chains" — an extension,
proposed because the base model does not do that.<Cite src="extended-utxo-model" /> Work on
representing debt in UTXO ledgers reaches the same conclusion from the finance side: the model is
ordinarily used to represent credit only, and representing credit and debt together is what the
account model's support for balances is for.<Cite src="utxo-debt-representation" />

## Ethereum wrote its reasons down

The unusual thing about this design decision is that the argument is on the record. The Ethereum
whitepaper devotes a section to Bitcoin's scripting language before proposing an alternative, and
lists four limitations.<Cite src="ethereum-whitepaper" />

**Lack of Turing-completeness.** A large subset of computation is supported, but not everything, and
the main missing category is loops — omitted to avoid infinite loops during transaction
verification. Any loop can in principle be unrolled, but doing so produces very space-inefficient
scripts; the whitepaper's example is that implementing an alternative signature algorithm would need
256 repeated multiplication rounds written out individually.<Cite src="ethereum-whitepaper" />

**Value-blindness.** A script cannot exercise fine-grained control over the amount withdrawn, because
outputs are all-or-nothing. The whitepaper's worked case is a hedging contract that should pay one
party a fixed dollar value and the other the remainder; the only way to approximate it is the
inefficient hack of pre-creating many outputs of varying denominations and having an oracle choose
which to send where.<Cite src="ethereum-whitepaper" />

**Lack of state.** An output is spent or unspent; there is no room for anything else. That rules out
multi-stage contracts and two-stage commitment protocols, and it means the model can express simple
one-off contracts but not stateful ones such as decentralised organisations.<Cite src="ethereum-whitepaper" />
Combined with value-blindness it also makes withdrawal limits impossible.<Cite src="ethereum-whitepaper" />

**Blockchain-blindness.** Scripts cannot see chain data such as the nonce, the timestamp or the
previous block hash, which cuts off a whole category of applications.<Cite src="ethereum-whitepaper" />

Read the third one again. "Lack of state" is not a complaint about ergonomics. It is the observation
that the only state a UTXO carries is one bit — spent or not — and everything else has to be
smuggled through the thread construction above.

The answer the whitepaper proposes is direct. State is made of objects called accounts, each with a
20-byte address, and an account has four fields: a nonce that ensures each transaction is processed
only once, an ether balance, contract code if present, and storage, empty by
default.<Cite src="ethereum-whitepaper" /> Contract accounts are described as autonomous agents that
execute code when poked, with direct control over their own balance and their own key-value store for
persistent variables.<Cite src="ethereum-whitepaper" />

That is the whole move: **give state a stable identity, and let it be mutated in place by anyone the
code permits.** Everything you know about Ethereum falls out of it.

## And here is the bill

The whitepaper is equally explicit about the immediate cost, in the same document. Turing-completeness
reintroduces the halting problem that Bitcoin's language removed, so every transaction must cap the
computational steps it may consume: `STARTGAS` and `GASPRICE` exist to require an attacker to pay
proportionately for every resource consumed.<Cite src="ethereum-whitepaper" /> Gas is not an
optimisation. It is the price of admission for a language with loops.

The larger cost is the one you have been circling all module. Once state is shared, mutable and
addressed by a stable identity, the protocol can no longer tell from a transaction's fields what it
will touch. Ordering stops being a per-object question and becomes a global one, and everything that
follows is downstream of that:

- **Nonces.** A transaction is processed once, in strict per-sender order, because there is no
  outpoint pinning it to a specific prior state.
- **Contention.** Two users hitting the same pool do not conflict at the protocol level, so both
  transactions execute — and the second one gets a different result than it simulated.
- **MEV.** When the outcome of a transaction depends on where it sits in a shared sequence, the right
  to choose that sequence is worth money.

None of those exist in the model you spent three lessons in. They are not defects that better
engineering removes; they are the invoice for mutable shared state, and Ethereum decided the state
was worth the invoice.

Solana's design requires a transaction to declare, in advance, every account it will read or write,
which is what lets non-overlapping transactions run concurrently.<Cite src="solana-sealevel-note" />
Ethereum's draft block-level access lists make the state a block touched explicit rather than
emergent.<Cite src="eip-7928" /> Both are buying back, with added machinery and added developer
burden, the thing that in the UTXO model is simply what a transaction *is*.

## The boundary is not where it was in 2014

One honesty check before you leave this module. The whitepaper dates from January
2014<Cite src="ethereum-whitepaper" /> and was written by an interested party.

The limits it describes are limits of Bitcoin Script as it stood, not laws about UTXO ledgers. The
Extended UTXO work demonstrates a UTXO model supporting general state machines with invariants
enforced across whole transaction chains, and it is careful to say that Bitcoin chose UTXO for good
reasons — including that its semantics stay simple in a concurrent, distributed
setting.<Cite src="extended-utxo-model" /> More recent work targets Bitcoin directly: Bithoven is a
2026 language with a type checker and a resource-liveness analyser that compiles to Bitcoin Script,
built on the argument that the model's rigorous security has been paid for in developer usability,
and that the trade is not
inevitable.<Cite src="bithoven-utxo-contracts" /> Bitcoin's own upgrades have moved the line too —
the Taproot upgrade in 2021 brought Schnorr signatures and a new output type, improving privacy and
programming capability.<Cite src="bitcoin-programming-survey" />

So the honest summary is not "UTXO cannot do contracts". It is: **base Bitcoin Script makes long-lived
mutable state expensive enough that a system aimed at contracts had a strong reason to choose
otherwise, and that reason was stated at the time.**

<Check type="explain" concept="why-ethereum-chose-accounts">
Design the same escrow in both models and be specific about what each one makes easy and hard.

*Requirement:* a buyer pays, a seller ships. If both agree, funds go to the seller. If they disagree,
a named arbitrator decides. If nobody acts within 30 days, the buyer gets an automatic refund.

<Answer>
**In UTXO.** The buyer creates one output whose locking script is satisfied either by two of the three
keys — buyer, seller, arbitrator — or, after the deadline, by the buyer alone. The 2-of-3 half is a
standard multisig; the refund half is a time-locked branch, which `OP_CHECKLOCKTIMEVERIFY` supports
directly by making an output unspendable until a given point.<Cite src="bitcoin-devguide-contracts" />

*Easy:* there is no custodian. The arbitrator holds one key of three and cannot take the funds; if
they misbehave, the other two can move to a fresh 2-of-3 with a different
arbitrator.<Cite src="bitcoin-devguide-contracts" /> The whole policy is one output, so nothing can
touch it except a transaction that satisfies it, and the state space is small enough to reason about
exhaustively.

*Hard:* anything that is not a single terminal payout. Partial release of half the funds needs a
second construction, because outputs are all-or-nothing and a script cannot express fine-grained
control over the amount withdrawn.<Cite src="ethereum-whitepaper" /> A dispute history, a reputation
score for the arbitrator, or a fee that varies with elapsed time all require state the output cannot
hold.<Cite src="ethereum-whitepaper" /> And every escrow is a separate output — there is no shared
object that a marketplace could keep statistics in.

**In accounts.** One contract, a mapping from escrow id to a struct, and functions to release, refund
and arbitrate. Partial release, per-escrow history, dynamic fees and a global counter are all
trivial, because the contract owns persistent storage under a stable
identity.<Cite src="ethereum-whitepaper" />

*Easy:* expressiveness and composition. Another contract can call yours.

*Hard:* everything that follows from custody and shared mutable state. The contract *holds* the
money, so a bug in any function threatens every escrow at once — the blast radius is the whole
mapping rather than one output. Upgrade keys, if present, are a trust assumption the UTXO version
does not have. Two arbitration calls in the same block both execute against state neither simulated
against. And the deadline is not enforced by anything: somebody must send a transaction to trigger
the refund, whereas the UTXO version's time lock is enforced by the network refusing the spend until
the deadline passes.<Cite src="bitcoin-devguide-contracts" />

**The sentence worth keeping:** the UTXO version is harder to write and easier to audit, because the
complete set of ways the money can move is written on the money. The account version is easier to
write and harder to audit, because the complete set of ways the money can move is every reachable
path through a program that also holds nine thousand other people's escrows.
</Answer>
</Check>

## Where this pays off

**Immediately next**, the account model stops being a definition and becomes an answer. When you meet
[account-four-fields](/c/account-four-fields) and
[accounts-enable-stateful-contracts](/c/accounts-enable-stateful-contracts), you will be reading a
design that was chosen against a specific alternative for stated reasons, and you will be able to
name what it gave up.

**Then the bill arrives, in instalments.** [nonce-replay-protection](/c/nonce-replay-protection)
exists because there is no outpoint pinning a transaction to a specific prior state.
[mempool-is-a-public-broadcast](/c/mempool-is-a-public-broadcast) and everything about ordering
matter because shared mutable state makes sequence valuable. Each of those lessons is easier if you
read it as a consequence rather than as a fact.

**Later**, on the scaling and alternative-VM tracks, you will meet designs that deliberately sit
between the two poles — declared access lists, per-object ownership, systems that partition state so
that most transactions do not contend.<Cite src="solana-sealevel-note" /><Cite src="eip-7928" /> You
now have both endpoints and can place any new design between them by asking one question: *can I tell
what this transaction touches before I run it?*

**And the module's reflection prompt is worth doing properly.** Take one thing your own product does
with money and write it out in both models. If the answer to "which would I rather implement in" and
"which would I rather audit" is different, you have found the trade-off in its most useful form —
not as a comparison of two chains, but as a property of your own risk tolerance.
