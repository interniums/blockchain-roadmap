Two engineers disagree in a review thread. The question is narrow: **if a slot passes with no block, does
epoch processing still run at the epoch boundary?**

One says no — epoch processing happens when a block is processed, and if there is no block there is no
processing. The other says yes — the beacon chain has to advance whether or not anyone proposes, or a
missed slot at an epoch boundary would leave justification permanently stuck.

They are about to spend an afternoon on this. In most protocol ecosystems, that afternoon is the only
option: read the prose again, read a client's source, ask someone. Here it takes four lines, because the
specification is a program and you can run it.

That is the idea this lesson is built around. Not "the specification is precise" — lots of specifications
claim that. **The specification executes**, and a question you can phrase as a program is a question you
can answer yourself.

## What "executable" actually means here

The specification documents are markdown containing Python code blocks, and tooling extracts those blocks
into a real, importable Python package.<Cite src="consensus-specs" /><Cite src="pyspec-readme" /> The
document and the reference implementation are not two artifacts that have to be kept in agreement. They
are the same artifact.

Two consequences are worth internalising, and they are different in kind.

**The first is negative and it is the underrated one.** The specification cannot silently contain code
that does not run. Prose specifications accumulate a particular kind of rot: a sentence that seemed
unambiguous, a pseudocode fragment with an off-by-one, an edge case nobody thought to state. Every one of
those survives indefinitely in a document nobody executes. Here, the repository's own tests exercise the
extracted code, which the pyspec README describes as testing the spec itself, to verify consistency and
provide feedback on modifications of the spec.<Cite src="pyspec-readme" /> A change that breaks
consistency fails in CI.

**The second is positive.** You can execute it. Construct a state, apply a block, read the result. When
you do not know what a rule means, you are one session away from finding out rather than one email away.

This is also where the [determinism requirement](/c/determinism-requirement) you met in fundamentals stops
being an abstract property and becomes a build artifact. Six client teams in six languages produce
identical state roots because there is one function they are all reimplementing, and it is written down in
a form that runs.

## Building it, in 2026

The build has modernised, and instructions written even eighteen months ago will send you down the wrong
path.

**The prerequisite is `uv`.** The repository uses the `uv` package manager to manage its dependencies and
virtual environment, and it can download a suitable Python — the required versions are 3.10 to 3.13 — if
one is not available natively.<Cite src="consensus-specs-readme-v161" /> The Makefile's dependency-sync
step checks for it and errors out with the install command if it is
missing.<Cite src="consensus-specs-makefile-v161" /> Instructions telling you to create a virtualenv and
`pip install -r requirements.txt` describe a build that no longer exists.

**The entry point is `make help`.**<Cite src="consensus-specs-readme-v161" /> That is not a formality;
the target list has changed and the one most tutorials name is not on it. At v1.6.1 the public targets
are:<Cite src="consensus-specs-makefile-v161" />

```text
make clean      -- delete all untracked files
make comptests  -- generate compliance tests
make coverage   -- run pyspec tests with coverage
make lint       -- run the linters
make reftests   -- generate reference tests
make serve_docs -- start a local docs web server
make test       -- run pyspec tests
```

Notice what is absent. **There is no public `pyspec` target.** Extraction happens in an internal target,
`_pyspec`, which every other target depends on. It runs
`uv run python -m pysetup.generate_specs --all-forks`.<Cite src="consensus-specs-makefile-v161" /> So the
way you build the spec is to ask for something that needs it — running `make test` builds it as a side
effect, and the repository's own getting-started document simply says to run
`make`.<Cite src="consensus-specs-tests-readme" />

**The output is one module per fork per preset.** The package lands under `tests/core/pyspec/eth2spec/`,
and the Makefile's coverage scope names the modules as `eth2spec.<fork>.<preset>` — `eth2spec.phase0.minimal`,
`eth2spec.fulu.mainnet`, and so on.<Cite src="consensus-specs-makefile-v161" /> That module, not the
markdown, is what you read when you want a fork's complete behaviour in one place, and it is what you
import.

**Running a specific test is a set of flags, not a pytest invocation.** The pyspec README documents
`make test`, `make test preset=minimal`, `make test k=<test-name>`, `make test fork=<name>`, and
combinations.<Cite src="pyspec-readme" /> The Makefile shows two defaults worth knowing: the preset
defaults to `minimal`, and the BLS implementation defaults to
`fastest`.<Cite src="consensus-specs-makefile-v161" />

<Aside kind="note">
The list of executable specs the build produces includes more than forks. At v1.6.1 it is phase0, altair,
bellatrix, capella, deneb, electra, fulu and gloas — plus `eip6800`, `eip7441`, `eip7805` and
`eip7928`.<Cite src="consensus-specs-makefile-v161" /> Individual features get their own executable
specification, developed in parallel and consolidated into a fork later, exactly as the README describes
the process.<Cite src="consensus-specs-readme-v161" /> You can build and run FOCIL's specification today.
It is still not scheduled.
</Aside>

### What the extraction step actually does

It is worth knowing that this is a real compiler pass rather than a copy-paste script, because the design
explains why the specification can be written the way it is.

The `pysetup` package that `generate_specs` lives in contains, among other modules, `md_to_spec.py` for
turning a markdown document into spec source, `md_doc_paths.py` for knowing which documents belong to which
fork, `constants.py`, `typing.py`, and a `spec_builders` package.<Cite src="consensus-specs" /><Cite src="consensus-specs-makefile-v161" />
That is a pipeline with a notion of fork inheritance built into it — which is exactly what a specification
written as a stack of diffs requires, and the subject of the next lesson.

The `--all-forks` flag on the generation command is the default the Makefile
passes.<Cite src="consensus-specs-makefile-v161" /> You get every fork's module in one pass, which is why
the build feels slow the first time and instant afterwards.

Two other targets earn their keep once the package exists. `make lint` runs the linters over the
*extracted* code, which is how the repository enforces that the specification is code that would pass
review rather than code that merely parses. And `make serve_docs` starts a local documentation server
built from the same source, so you can browse the specification with the code blocks rendered in
place.<Cite src="consensus-specs-makefile-v161" />

These are not type aliases for readability, though the document says they are for type hinting and
readability.<Cite src="consensus-specs-beacon-chain-v161" /> They are [SSZ](/c/ssz) types, and every
container built from them has a canonical serialization and a
[`hash_tree_root`](/c/ssz-merkleization).<Cite src="ssz-specs" />

That is the join between this module and the encoding track, and it is load-bearing in both directions.
`state_transition` ends by asserting `block.state_root == hash_tree_root(state)` — a comparison between a
value in the block and a Merkleization of the entire post-state, computed by rules specified
elsewhere.<Cite src="consensus-specs-beacon-chain-v161" /> Change how a container is Merkleized and every
state root on the network changes. It is also why the reference test vectors are SSZ-encoded rather than
JSON: the format the spec is defined over is the format the tests are shipped in, and no lossy conversion
sits between them.

## The function at the centre

Everything the beacon chain does reduces to one function, and it is short enough to read in
full:<Cite src="consensus-specs-beacon-chain-v161" />

```python
def state_transition(
    state: BeaconState, signed_block: SignedBeaconBlock, validate_result: bool = True
) -> None:
    block = signed_block.message
    # Process slots (including those with no blocks) since block
    process_slots(state, block.slot)
    # Verify signature
    if validate_result:
        assert verify_block_signature(state, signed_block)
    # Process block
    process_block(state, block)
    # Verify state root
    if validate_result:
        assert block.state_root == hash_tree_root(state)
```

Five things are visible in twelve lines.

**It mutates in place and returns `None`.** The specification is written imperatively over a `BeaconState`
object. Conceptually it is a pure function from state and block to state; mechanically you pass a state in
and it is different afterwards.

**Time is advanced before the block is applied.** `process_slots(state, block.slot)` catches the state up
to the block's slot, and the comment says explicitly: *including those with no
blocks*.<Cite src="consensus-specs-beacon-chain-v161" />

**The signature check is optional.** `validate_result` gates both the block-signature verification and the
state-root check. That flag is why the spec can be driven in test harnesses that do not want to construct
valid BLS signatures.

**The state root is checked at the end, not computed.** The block asserts what the post-state root will
be, and the transition verifies it — the same [`hash_tree_root`](/c/ssz-merkleization) machinery from the
encoding track.<Cite src="ssz-specs" />

**Failure is an assertion.** Invalid blocks are rejected by an `assert` blowing up. There is no error
type, no result enum. The specification's notion of "invalid" is "this program raised".

### The three phases

`process_slots` is the one to read closely, because it contains the answer to the argument at the top of
this lesson:<Cite src="consensus-specs-beacon-chain-v161" />

```python
def process_slots(state: BeaconState, slot: Slot) -> None:
    assert state.slot < slot
    while state.slot < slot:
        process_slot(state)
        # Process epoch on the start slot of the next epoch
        if (state.slot + 1) % SLOTS_PER_EPOCH == 0:
            process_epoch(state)
        state.slot = Slot(state.slot + 1)
```

**Per-slot processing** is `process_slot`, and it is pure bookkeeping: cache the state root into
`state.state_roots`, backfill the latest block header's state root if it is empty, cache the block
root into `state.block_roots`.<Cite src="consensus-specs-beacon-chain-v161" /> It runs for every slot,
whether or not a block existed.

**Epoch processing** fires inside that loop, on the condition `(state.slot + 1) % SLOTS_PER_EPOCH == 0` —
the last slot of an epoch, before the counter increments. It runs the expensive
accounting:<Cite src="consensus-specs-beacon-chain-v161" />

```python
def process_epoch(state: BeaconState) -> None:
    process_justification_and_finalization(state)
    process_rewards_and_penalties(state)
    process_registry_updates(state)
    process_slashings(state)
    ...
```

**Block processing** is `process_block`, and at phase0 it is four
calls:<Cite src="consensus-specs-beacon-chain-v161" />

```python
def process_block(state: BeaconState, block: BeaconBlock) -> None:
    process_block_header(state, block)
    process_randao(state, block.body)
    process_eth1_data(state, block.body)
    process_operations(state, block.body)
```

`process_operations` is where attestations, deposits, slashings, exits and the rest are applied.

So the review-thread argument is settled by the loop structure. Epoch processing lives in the **slot**
phase, not the block phase, and its trigger is the slot counter reaching an epoch boundary. Missed slots
do not skip it: the next block's `state_transition` calls `process_slots` up to its own slot, and every
boundary crossed on the way fires `process_epoch`. Justification and finalisation cannot be starved by
missing proposers, and the spec makes that structural rather than remedial.

### Why knowing the phase is the first debugging move

Ask which phase a rule lives in and you have already narrowed *when it can possibly fire*.

A rule in **block processing** fires only when a block containing the relevant operation is applied. If
nobody includes that operation, the rule never runs.

A rule in **slot processing** fires every slot regardless of proposer behaviour.

A rule in **epoch processing** fires once per 32 slots, in a fixed order, on state that has already
absorbed everything from the epoch.

When two clients disagree about a state root, the phase tells you the search space. A divergence that
appears only at epoch boundaries is in `process_epoch` and almost certainly in ordering or rounding — the
sub-functions run in a specified sequence and each sees the previous one's
output.<Cite src="consensus-specs-beacon-chain-v161" /> A divergence that appears on a specific block is
in the operations. A divergence that appears on empty slots is in the caching.

There is a bisection hiding in that structure, and it is the reason phase placement is worth memorising
rather than looking up. Given two clients that disagree about a post-state root, you can localise the
divergence without reading either client's code:

**Does it appear on empty slots?** Then it is in `process_slot` — root caching, or the backfill of
`latest_block_header.state_root`, which is the one piece of `process_slot` with a
conditional.<Cite src="consensus-specs-beacon-chain-v161" />

**Does it appear only on the last slot of an epoch?** Then it is in `process_epoch`, and the ordered list
of sub-functions is your candidate set. Each one runs on state the previous one already
modified<Cite src="consensus-specs-beacon-chain-v161" />, so ordering bugs and rounding bugs both surface
here and look identical from outside.

**Does it appear on a block containing a particular operation?** Then it is in `process_operations`, and
you can narrow further by which operation the block carried.

**Does it appear on every block regardless of contents?** Then it is in `process_block_header` or
`process_randao`, both of which run unconditionally.<Cite src="consensus-specs-beacon-chain-v161" />

Four questions, each answerable from the chain itself, and each one cuts the search space by an order of
magnitude before anybody opens a debugger. This is the practical payoff of the spec being decomposed the
way it is: the decomposition is a diagnostic tree.

## What the executable specification is not

This is where enthusiasm for the idea usually overshoots, so it is worth naming the limits precisely.

**It is not a client, and it will not follow the chain.** The pyspec is the state transition and its
helpers. It does not gossip, does not maintain peers, does not talk to an execution client, does not
persist anything. You cannot point it at mainnet.

**It is not a performance model.** It is Python written for clarity, with no attempt at the caching and
incremental hashing that make a real client viable. Timings tell you nothing about how long a real client
takes, and the specification's own design goals say so in spirit: minimize complexity, even at the cost of
some losses in efficiency.<Cite src="consensus-specs-readme-v161" />

**The cryptography is swappable, and the default is not the point.** The test target passes a BLS type,
defaulting to `fastest`.<Cite src="consensus-specs-makefile-v161" /> Test runs are not evidence about
signature-verification behaviour unless you have chosen the implementation deliberately.

**It does not tell you why.** `process_epoch` calls its sub-functions in a specific order and the code does
not say what would break if you reordered them. Rationale lives in EIPs, research posts and All Core Devs
notes. The specification tells you what, exactly; it is nearly silent on why.

**And executability is not correctness.** The specification can be wrong. It has been wrong. What
executability removes is *ambiguity* — the gap between what a document says and what a reader thinks it
says. It does not remove the gap between what the document says and what the designers intended. Those are
different failures, and only one of them is addressed here.

<Aside kind="warn">
The most common overclaim about the pyspec is that it proves clients are correct. It cannot. It is the
thing clients are compared *against*, which makes agreement with it checkable — an enormous practical win,
and a completely different claim from correctness. The next lesson but one takes that distinction apart,
because it is the whole reason the reference test vectors have the coverage properties they do.
</Aside>

## Answering your own question

Here is the shape of the workflow, using the review-thread question as the worked example.

**Subgoal 1 — get a build, by asking for something that needs one.** `make test` triggers the internal
extraction step before it runs anything.<Cite src="consensus-specs-makefile-v161" /> If `uv` is missing,
the sync step tells you so and gives you the install
command.<Cite src="consensus-specs-makefile-v161" />

**Subgoal 2 — import the fork and preset you mean.** The module is `eth2spec.<fork>.<preset>`, so a
question about current mainnet behaviour and a question about how the tests run are answered by different
imports.<Cite src="consensus-specs-makefile-v161" /> Under `minimal`, `SLOTS_PER_EPOCH` is
8<Cite src="consensus-specs-minimal-preset-phase0" />; under `mainnet` it is
32<Cite src="consensus-specs-mainnet-preset-phase0-v161" />. Choosing the wrong one gives you a correct
answer to a different question.

**Subgoal 3 — reduce the question to a call.** "Does epoch processing run without a block" becomes: build
a genesis state, call `process_slots` far enough to cross a boundary, and look at whether
`state.current_justified_checkpoint` or the epoch-processing side effects moved. No block is constructed
at all, which is exactly the condition under argument.

**Subgoal 4 — read the answer off the state, not off the code.** The point of running it is that you stop
reasoning about what the code would do. Print the field. If the epoch counters advanced with no block
applied, epoch processing ran.

**Subgoal 5 — turn the finding into a citation.** The answer is `process_slots`, and the specific line is
the `(state.slot + 1) % SLOTS_PER_EPOCH == 0` condition inside the
loop.<Cite src="consensus-specs-beacon-chain-v161" /> A review comment that names the function beats one
that reports an experiment, because the next reader can check it without running anything.

The whole loop is minutes, and the reason to internalise it is not this particular question. It is that
after doing it once, "I am not sure what the spec means here" stops being a place where you stop.

validator registry and by signature work, both of which scale with the active set — a quantity the minimal
preset deliberately shrinks. Measure it on a client, on the network you care about, at an epoch boundary.
The specification will tell you *what* is computed there, in order, which is genuinely useful input to that
measurement.<Cite src="consensus-specs-beacon-chain-v161" /> It will not tell you what it costs.

## What this unlocks

- **The next lesson** explains why the markdown looked so sparse when you opened it, and why the built
  module is the thing to read: each fork's document is a diff over the previous one, and the build step is
  what composes the stack.<Cite src="consensus-specs" />
- **It also formalises the preset distinction** that just bit your colleague — presets versus configs,
  compile-time versus runtime, and why the minimal preset lets justification and finalisation happen inside
  a REPL session.<Cite src="consensus-specs-minimal-preset-phase0" />
- **The module's practice** is this lesson performed: build, import, advance a state, and explain where
  each field you printed came from in the markdown.<Cite src="eth2book-running-the-spec" /><Cite src="devcon-pyspec-talk" />

The habit worth forming: when a specification is executable, stop arguing about what it means. Reduce the
disagreement to a call, run it, and then go find the line that explains the result — so the answer you
bring back is a citation rather than an anecdote.
