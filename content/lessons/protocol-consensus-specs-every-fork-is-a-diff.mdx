Somebody opens `specs/fulu/beacon-chain.md` to find out how attestations are processed in the current
fork. They scroll. There is a blob schedule, a modified `process_execution_payload`, an extended
`BeaconState`, some proposer-lookahead helpers. There is nothing about attestations at all.

Two conclusions are available. The first is that Fulu removed attestation processing, which is absurd. The
second is that they are reading the wrong kind of document — and that is correct, though nothing about the
file announces it except one line in the introduction:

> *Note*: This specification is built upon Electra.<Cite src="consensus-specs-fulu-beacon-chain-v161" />

Every fork's specification is a **patch**. This lesson is about what that means for reading it, how the
build turns a stack of patches back into something complete, and the second place the same idea shows
up — in the two directories of constants that get conflated constantly.

## The layer cake

The fork documents are written over one another in sequence. Altair over Phase0, Bellatrix over Altair,
and so on down to Fulu over Electra, with Gloas and Heze under construction on top of
that.<Cite src="consensus-specs" /><Cite src="consensus-specs-readme-v161" />

The convention is visible in three places at once.

**In the introduction.** Fulu's beacon-chain document states outright that it is built upon
Electra.<Cite src="consensus-specs-fulu-beacon-chain-v161" />

**In the headings.** Fulu's table of contents reads *Modified `process_execution_payload`*, *New
`BlobParameters`*, *Modified `compute_fork_digest`*, *New `get_beacon_proposer_indices`*, *Modified
`process_epoch`*.<Cite src="consensus-specs-fulu-beacon-chain-v161" /> The prefixes are the diff markers.

**Inside the code.** Altair's document annotates individual container fields and function lines with
comments like `# [New in Altair]` and `# [Modified in
Altair]`.<Cite src="consensus-specs-altair-beacon-chain-v161" /> Fulu goes further and attributes changes
to the EIP that caused them — its blob schedule is marked *[New in
Fulu:EIP7892]*.<Cite src="consensus-specs-fulu-beacon-chain-v161" />

So the absence of attestation processing in Fulu's file is a statement, not an omission: **Fulu did not
change it.** `process_attestation` is still whatever the most recent fork that touched it says it is, and
you find that by walking back down the stack.

### Why the flattened module is what core developers read

This is the practical reason the build step from the previous lesson exists.

The extraction produces one importable module per fork per preset, named
`eth2spec.<fork>.<preset>`.<Cite src="consensus-specs-makefile-v161" /> That module is the **composition of
the whole stack** — every function from Phase0 that nothing later overrode, plus every override, resolved.
It is the artifact that answers "what does Fulu actually do", and the markdown is not.

The reading discipline that follows:

**To find out what a fork changed**, read its markdown. That is exactly what the document is for, and the
diff markers make it fast.

**To find out how something behaves right now**, read the built module for the current fork — or grep it.
One file, complete, no walking.

**To find out when a rule last changed**, walk the markdown backwards through the fork stack looking for
the most recent *Modified* heading that names it. The layering makes that a short search, which is the
compensating benefit of the design.

<Aside kind="note">
Notice that the execution layer solved the same problem the other way. `ethereum/execution-specs` keeps one
complete directory per fork — `frontier` through `amsterdam` — so each is standalone and the diffs are
implicit in the version history.<Cite src="execution-specs" /> Neither choice is wrong. Layering makes
"what changed" trivial and "what is the current rule" require tooling; snapshotting makes the opposite
trade. Knowing which repository made which choice is what stops you looking for a diff that is not written
down, or walking a stack that does not exist.
</Aside>

### Walking the stack: one worked search

Take the opening question seriously and answer it properly. **What are the rules for processing an
attestation in Fulu?**

**Subgoal 1 — check whether the current fork touched it.** Fulu's beacon-chain document has no
`process_attestation` heading of either kind.<Cite src="consensus-specs-fulu-beacon-chain-v161" /> Fulu did
not change it. That is one grep and it is the most common outcome, because most forks change very little.

**Subgoal 2 — walk backwards until something did.** Electra's beacon-chain document carries a *Modified
`process_attestation`* heading. So does Deneb's. So does Altair's. Bellatrix and Capella do
not.<Cite src="consensus-specs" />

**Subgoal 3 — stop at the first hit going backwards, because later overrides earlier.** The most recent
fork before Fulu to modify the function is Electra. **Electra's version is the live rule.** Deneb's and
Altair's are history — useful for understanding how the rule got here, and not what runs.

**Subgoal 4 — get the surroundings from the flattened module.** Electra's markdown shows the function in
isolation. What it calls, and what calls it, is resolved in `eth2spec.fulu.<preset>`, where the whole stack
has been composed.<Cite src="consensus-specs-makefile-v161" />

Four steps, a couple of minutes, and the answer is precise enough to cite. Compare that with searching a
client's source tree, where you would find one team's structuring of the same rule and no indication of
which parts are protocol and which are engineering.

### The file that makes the layering executable

A fork directory holds more than `beacon-chain.md`. Fulu's contains `fork-choice.md`, `validator.md`,
`p2p-interface.md`, two data-availability documents — and `fork.md`, which is the one that turns the
metaphor into code.<Cite src="consensus-specs" />

`fork.md` defines the upgrade function. Fulu's has the signature
`upgrade_to_fulu(pre: electra.BeaconState) -> BeaconState`, and its body constructs the new state field by
field from the old one, carrying most fields across unchanged and marking the ones it alters — the fork
version among them — with `# [Modified in Fulu]`.<Cite src="consensus-specs" /> It runs once, at the
boundary, as what the document calls an irregular state change.<Cite src="consensus-specs" />

Two things are worth taking from that. The layering is not just an editorial convention for humans: the
type signature names the previous fork's state type, so the dependency is checked by the same tooling that
checks everything else. And a fork boundary is a *function application*, not a restart — one deterministic
transformation from the last state of the old protocol to the first state of the new one, which is why
clients can cross a fork without resyncing.

### Fork versions: the layering, encoded on the wire

The layering has a runtime counterpart, and it is why a fork boundary does not simply split the network in
half by luck.

Each fork gets a version constant. Mainnet's config runs `GENESIS_FORK_VERSION: 0x00000000`,
`ALTAIR_FORK_VERSION: 0x01000000`, up through `FULU_FORK_VERSION: 0x06000000`, with
`GLOAS_FORK_VERSION: 0x07000000` marked *temporary
stub*.<Cite src="consensus-specs-mainnet-config-v161" /> Feature specs get their own —
`EIP7441`, `EIP7805` and `EIP7928` each hold a fork version of their
own.<Cite src="consensus-specs-mainnet-config-v161" />

Those versions feed `compute_fork_digest`, a function Fulu itself
modified.<Cite src="consensus-specs-fulu-beacon-chain-v161" /> The digest scopes networking: nodes on
different sides of a fork boundary derive different digests and therefore stop talking on the affected
topics rather than exchanging messages neither can validate. The layer stack in the documents and the
version constants in the config are the same sequence, expressed once for readers and once for peers.

## Presets and configs: the same idea, applied to constants

Every constant in the beacon chain lives in one of two directories. They are both YAML full of numbers,
they sit next to each other, and the distinction between them is the single most conflated thing in this
repository.

### Presets change the shape of the specification

Presets are described in the repository's own words as more extensive than runtime configurations, and
generally only applicable during compile-time.<Cite src="consensus-specs-presets-readme" /> Each preset is
a directory, with one YAML file per fork.

There are two standard presets. `mainnet/` is used in mainnet, mainnet-like testnets such as Hoodi, and
spec-testing. `minimal/` is used in low-resource local dev testnets and
spec-testing.<Cite src="consensus-specs-presets-readme" />

A configuration declares which preset it extends by setting `PRESET_BASE`, and an implementation may
choose to support only one preset per build target and should validate that the config's `PRESET_BASE`
matches the running build.<Cite src="consensus-specs-presets-readme" /> That is the compile-time part made
explicit: **the preset is baked into the binary, and mixing them is a build error rather than a runtime
misconfiguration.**

### Configs change which network you are on

Configs hold the values that differ between networks at runtime: fork activation epochs, the deposit
contract address, genesis parameters, chain identity. The standard ones are `mainnet.yaml` and
`minimal.yaml`, the latter used in spec-testing alongside the minimal
preset.<Cite src="consensus-specs-configs-readme" />

The configs README also draws a boundary worth knowing: not all network configurations are in scope for
the specification, and common networks and testnet assets live in a separate
repository.<Cite src="consensus-specs-configs-readme" /> The specs repo carries mainnet and the test
configuration; everything else is somebody else's file.

Open `configs/mainnet.yaml` and the first lines make the relationship
concrete:<Cite src="consensus-specs-mainnet-config-v161" />

```yaml
# Extends the mainnet preset
PRESET_BASE: 'mainnet'
CONFIG_NAME: 'mainnet'
```

A config is not a standalone description of a network. It is a delta over a preset, in the same way a fork
document is a delta over the previous fork.

### The rule that governs both: extend, never overwrite

Here is the unifying idea, and it is stated independently in both READMEs.

The presets README says that like config forking, the preset extends with every fork instead of
overwriting previous values.<Cite src="consensus-specs-presets-readme" /> The configs README gives the
reason: variables are not replaced but extended with forks, in order to support syncing from one state to
another over a fork boundary without hot-swapping a config. For forks that change a variable, the variable
name is suffixed with the fork name — `INACTIVITY_PENALTY_QUOTIENT_ALTAIR` is the example the document
itself gives.<Cite src="consensus-specs-configs-readme" />

Once you know that, several things that look like clutter turn out to be the design.

**`MAX_EFFECTIVE_BALANCE` is still 32 ETH in the phase0
preset**<Cite src="consensus-specs-mainnet-preset-phase0-v161" /> **while
`MAX_EFFECTIVE_BALANCE_ELECTRA` is 2,048 ETH in the electra
preset.**<Cite src="consensus-specs-mainnet-preset-electra-v161" /> Both exist because a client replaying
history needs the old value for old states.

**`SECONDS_PER_SLOT`, value 12, is present and marked
deprecated**<Cite src="consensus-specs-beacon-chain-v161" /> alongside `SLOT_DURATION_MS`, value
12,000.<Cite src="consensus-specs-mainnet-config-v161" /> The configs README anticipates exactly this: a
constant that is genuinely replaced goes through a deprecation phase, and only when old state is no longer
supported does the old name disappear.<Cite src="consensus-specs-configs-readme" />

**Constants exist for features that have never activated.** `configs/mainnet.yaml` carries fork versions
and epochs for `EIP7441`, `EIP7805` and `EIP7928`, each set to
`18446744073709551615`.<Cite src="consensus-specs-mainnet-config-v161" />

Read that way, the config file is not a settings file. It is an append-only log of every parameter the
network has ever had, with the retired ones still readable because somewhere a client is syncing from
genesis and needs them.

## The minimal preset, and what it is for

The minimal preset shrinks the protocol so that behaviour taking hours at mainnet parameters happens in
seconds. Comparing the two phase0 files side by

Some constants do not move. `MAX_VALIDATORS_PER_COMMITTEE` is 2,048 in both, and `MAX_EFFECTIVE_BALANCE`
is 32 ETH in both.<Cite src="consensus-specs-minimal-preset-phase0" /><Cite src="consensus-specs-mainnet-preset-phase0-v161" />
Minimal is not "everything divided by eight". It is a deliberate selection of the parameters that make
tests slow.

**Why it matters that the code paths are identical.** Minimal changes constants, not logic. The same
`process_epoch` runs, the same justification rules apply, the same containers are Merkleized. A behaviour
you observe under minimal is the same behaviour mainnet has, at a scale you can watch — which is exactly
why the reference test vectors are generated under both presets rather than only one.

**What it makes possible.** With `SLOTS_PER_EPOCH` at 8, an epoch is eight slots rather than
thirty-two.<Cite src="consensus-specs-minimal-preset-phase0" /> Justification requires crossing epoch
boundaries, and finalisation requires crossing several. Under mainnet constants, watching a checkpoint
finalise means simulating dozens of slots with committees of 128. Under minimal, it is a loop you can run
in a REPL and print the checkpoint after each pass. Finality stops being something you read about and
becomes something you watch happen.

**And it is the default for the tests.** The Makefile's test target passes `--preset=minimal` unless you
say otherwise.<Cite src="consensus-specs-makefile-v161" /> The pyspec README documents
`make test preset=minimal` as the way to be explicit about
it.<Cite src="pyspec-readme" /> Either way, an unqualified `make test` has not told you anything about
mainnet-scale behaviour.

<Aside kind="warn">
Two failure modes follow from the preset being compile-time, and both are quiet.

The first is measuring under minimal and reporting about mainnet — anything scaling with committee size or
validator count is off by more than an order of magnitude, and the run still passes.

The second is a config and a build that disagree. An implementation should validate that the config's
`PRESET_BASE` matches the running build.<Cite src="consensus-specs-presets-readme" /> "Should", not
"must" — so a stack that skips the check will start, run, and compute state roots nobody else agrees with,
which is a consensus failure produced entirely by a configuration mistake.
</Aside>

<Check type="spot-bug" concept="presets-vs-configs">
A teammate is setting up a private devnet for load testing. Their plan: "I'll copy `configs/mainnet.yaml`,
change `CONFIG_NAME`, set all the fork epochs to 0 so everything is active from genesis, and drop
`SLOTS_PER_EPOCH` to 8 so we cycle through epochs faster and see finality quickly. All the clients read
the config file, so they'll pick it up."

Find the error, and say what the corrected plan is.

<Answer>
**One line of that plan is in the wrong file, and it is the one they care most about.**

**`SLOTS_PER_EPOCH` is not a config value. It is a preset value.** It lives in
`presets/<preset>/phase0.yaml`, and presets are described as generally only applicable at
compile-time.<Cite src="consensus-specs-presets-readme" /><Cite src="consensus-specs-mainnet-preset-phase0-v161" />
Adding it to a config file does not change it. Depending on the client, it will be ignored as an
unrecognised key or rejected — and the ignoring case is the dangerous one, because the devnet starts, runs,
and has 32-slot epochs while the plan says 8.

**Why the "clients read the config file" reasoning fails.** Clients read both, at different times. The
preset is compiled in; the config is loaded at startup. That is the whole distinction, and it is enforced
by the `PRESET_BASE` field: a config declares which preset it extends, and an implementation should
validate that the running build matches.<Cite src="consensus-specs-presets-readme" /> Their copied file
still says `PRESET_BASE: 'mainnet'`.<Cite src="consensus-specs-mainnet-config-v161" />

**The parts of the plan that are correct.** `CONFIG_NAME` is a config value.<Cite src="consensus-specs-mainnet-config-v161" />
So are the fork activation epochs — the configs README lists fork epochs as exactly the kind of value that
differs per network.<Cite src="consensus-specs-configs-readme" /> Setting them to 0 to start post-Fulu
from genesis is the intended use of that file.

**The corrected plan.**

*Pick the preset first, because it is a build-time decision.* If you want 8-slot epochs, that is the
`minimal` preset, where `SLOTS_PER_EPOCH` is 8, `TARGET_COMMITTEE_SIZE` is 4 and `SHUFFLE_ROUND_COUNT` is
10.<Cite src="consensus-specs-minimal-preset-phase0" /> Every client on the devnet must be built or
launched for that preset, not just configured for it.

*Then write the config against that preset.* Set `PRESET_BASE: 'minimal'`, a distinct `CONFIG_NAME`, the
fork epochs you want, and your own genesis parameters and deposit contract
address.<Cite src="consensus-specs-mainnet-config-v161" />

*Do not set the epoch for anything you are not actually running.* The max-uint64 value is the convention
for a disabled fork, and it is the safest default for anything you have not deliberately
enabled.<Cite src="consensus-specs-mainnet-config-v161" />

*Check the trade before committing to minimal.* Minimal changes constants, not code paths — the behaviour
is genuinely the same protocol — but committee sizes of 4 and a 10-round shuffle mean anything you measure
about propagation, aggregation load or signature-verification cost is not transferable to
mainnet.<Cite src="consensus-specs-minimal-preset-phase0" /> For a *load* test specifically, that is close
to fatal: they wanted fast epochs for observability and a realistic scale for measurement, and those are
opposite settings of the same knob.

**The one-line version.** Fork epochs are config. Slots per epoch is preset. One you can change by editing
a file; the other you change by building a different specification.
</Answer>
</Check>

## What this unlocks

- **The next lesson** follows the presets into the test corpus. Reference vectors are generated under both
  presets, arranged in a directory tree whose first level is the config name — and they are produced by
  running the specification, which has a consequence for what they can and cannot
  catch.<Cite src="consensus-specs-makefile-v161" />
- **Reading any fork's changes** is now a mechanical procedure: open its markdown, read the *Modified* and
  *New* headings, and stop. That is the complete list of what the fork
  did.<Cite src="consensus-specs-fulu-beacon-chain-v161" />
- **The module's practice** has you build a genesis state under minimal and run epochs until something
  finalises. The preset is what makes that a coffee-break exercise rather than an overnight
  job.<Cite src="eth2book-running-the-spec" />

The habit worth forming: when a specification is versioned, find out whether each version is a snapshot or
a patch before you read one. Everything about how you search it, and about what an absence means, depends
on that answer — and in this repository the two normative repos give opposite answers.
