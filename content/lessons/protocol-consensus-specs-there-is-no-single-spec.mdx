A colleague asks what looks like a simple question: **does Ethereum enforce that a block proposer include
transactions from the mempool?**

Four people answer it from four documents.

The first opens the EIPs repository, finds EIP-7805 — fork-choice enforced inclusion lists — reads that a
committee of validators can force-include transactions in every block, and says yes.<Cite src="eip-7805" />
The second opens the consensus specifications, finds no such mechanism in any stable fork, and says no.
The third opens the Glamsterdam hardfork meta EIP, sees EIP-7805 under **Declined for Inclusion**, and
says no and it was considered and rejected.<Cite src="eip-7773" /> The fourth opens the Engine API
directory, finds a `bogota.md` defining `engine_getInclusionListV1`, and says it is coming.<Cite src="engine-api-bogota" />

All four read a real document. Three of them are wrong about the question asked, and each is wrong in a
different, characteristic way. This lesson is about which repository answers which question, so that you
stop being any of those four people.

## There is no "the Ethereum specification"

There are at least four normative repositories, owned by different groups, moving at different cadences,
answering different questions.

**`ethereum/consensus-specs`** defines beacon-chain behaviour: the state transition, fork choice,
networking, validator duties.<Cite src="consensus-specs" /> Its documents are markdown containing Python,
and the Python is the specification.

**`ethereum/execution-specs`** defines execution-layer behaviour: the EVM, transaction processing, gas,
block validity.<Cite src="execution-specs" /> Also executable Python, arranged one complete package per
fork.<Cite src="execution-specs-osaka-fork" />

**`ethereum/execution-apis`** defines the interfaces: the JSON-RPC surface applications use, and the
Engine API between the two clients.<Cite src="engine-api-spec" />

**`ethereum/EIPs`** holds proposals. A proposal is the *intent* behind a change and the argument for it —
not its definition, and not evidence that it happened.

Two more you will meet quickly: `ethereum/execution-spec-tests` generates execution-layer conformance
tests<Cite src="execution-spec-tests-repo" />, and `ethereum/hive` runs cross-client integration tests in
containers.<Cite src="hive-repo" />

That last one matters more than its position suggests. Inclusion is decided in All Core Devs calls, whose
agendas and notes live in `ethereum/pm`.<Cite src="ethereum-pm" /> If you want to know *why* something was
declined rather than *that* it was, that is where the conversation is.

### Inside consensus-specs, in the order you will need it

The repository is small enough to hold in your head, and knowing the top-level layout is most of the
navigation.

- **`specs/<fork>/`** — the fork documents. `beacon-chain.md` is the state transition, `fork-choice.md` is
  head selection, `validator.md` is what a validator is supposed to do and when, `p2p-interface.md` is
  networking.
- **`presets/`** and **`configs/`** — the constants, split into two kinds for reasons the third lesson is
  about.<Cite src="consensus-specs-mainnet-config-v161" />
- **`ssz/`** — the SimpleSerialize specification and the Merkle proof formats, linked from the README as
  accompanying documents.<Cite src="consensus-specs-readme-v161" />
- **`sync/`** — behaviours that are not part of the state transition but that clients must agree on,
  including optimistic sync.
- **`tests/`** — the reference test format, the generators, and the pyspec
  itself.<Cite src="consensus-specs-readme-v161" />

The README also names four external specifications that are deliberately *not* in this repository: Beacon
APIs, Engine APIs, Beacon Metrics and Builder Specs.<Cite src="consensus-specs-readme-v161" /> That list is
worth reading as a boundary statement. The consensus specification defines what the network agrees on. How
you *talk to* a client, how a client reports metrics, and how it negotiates with an out-of-protocol block
builder are all somebody else's documents, because none of them is consensus — and clients can differ
about them without forking the chain.

That distinction resolves a whole class of confusion. "Why isn't the beacon API in the consensus specs" has
the same answer as "why isn't MEV-Boost in the protocol": because agreement is not required for it, and
things that do not require agreement are kept out of the artifact whose entire purpose is agreement.

## For consensus behaviour, the spec outranks the EIP

This is the ordering that trips people up, because it is the reverse of how standards usually work.

In most ecosystems the standards document is authoritative and implementations follow it. Here, for
consensus-layer behaviour, the merged consensus-specs pull request is normative and the EIP frequently
lags it — sometimes by months, sometimes permanently, because an EIP's job ends once the idea has been
argued and the specification's job is only beginning.

The consequence is concrete. When an EIP and a spec file disagree about a consensus-layer detail, the spec
file is what clients implement, and therefore what the network does. An EIP describing an earlier design
revision is not an error in the EIP; it is the EIP doing its job, which was to capture intent at the time.

<Misconception
  belief="An EIP being merged means the change is happening."
  reality="Merging an EIP means it is formatted, numbered and assigned. Inclusion is decided on All Core Devs calls, specified in the specs repositories, and then shipped by clients — and proposals with merged EIPs do get cut."
  why="In ordinary open source, 'merged' means 'accepted'. Here the EIPs repository is a document registry, not a decision log."
  src="eip-7723"
/>

There is a specification for the decision process itself, which is unusually helpful. EIP-7723, "Network
Upgrade Inclusion Stages", defines the vocabulary: **Proposed for Inclusion**, **Considered for
Inclusion**, **Declined for Inclusion**, **Scheduled for Inclusion**.<Cite src="eip-7723" /> Each network
upgrade then gets a hardfork meta EIP that sorts every candidate into those buckets.

For Glamsterdam that is EIP-7773, and reading it takes ninety seconds and settles arguments. Scheduled for
Inclusion: EIP-7732 (enshrined proposer-builder separation) and EIP-7928 (block-level access lists),
among others. Declined for Inclusion: EIP-7805 (FOCIL) and EIP-7782 (reduce block latency, the
six-second-slot proposal), among others.<Cite src="eip-7773" /> Its own status is **Draft**, and it
contains no activation date — because there is not one.<Cite src="eip-7773" />

<Aside kind="warn">
"Declined for Inclusion" means declined *for this upgrade*. EIP-7805 and EIP-7782 both remain
Draft<Cite src="eip-7805" /><Cite src="eip-7782" />, and the Engine API's `bogota.md` — a file for the
fork after Amsterdam — defines `engine_getInclusionListV1`, which is the shape FOCIL takes over the
wire.<Cite src="engine-api-bogota" /> The idea is alive and being specified. That is not the same as being
scheduled, and nothing in any of those documents carries a date.
</Aside>

## Reading the fork tables

The single most useful page in consensus-specs is its README, because it carries two tables that tell you
what is live and what is being built.

The stable table at tag v1.6.1 lists Phase0 at epoch 0, Altair at 74,240, Bellatrix at 144,896, Capella at
194,048, Deneb at 269,568, Electra at 364,032 and Fulu at
411,392.<Cite src="consensus-specs-readme-v161" /> The in-development table at that tag lists one entry:
Gloas, fork epoch TBD.<Cite src="consensus-specs-readme-v161" /> On the repository's default branch there
are now two — Gloas and Heze, both TBD.<Cite src="consensus-specs" />

The README also states the design philosophy that explains why those tables look the way they do:
features are researched and developed in parallel, then consolidated into sequential upgrades when
ready.<Cite src="consensus-specs-readme-v161" /> Forks are release trains, not design units.

You can see that literally in the mainnet configuration file. Alongside the fork epochs for shipped forks
it carries `GLOAS_FORK_VERSION: 0x07000000` marked *temporary stub*, plus separate fork versions for
`EIP7441`, `EIP7805` and `EIP7928` — individual features with their own activation slots, each set to
`18446744073709551615`.<Cite src="consensus-specs-mainnet-config-v161" /> That number is 2⁶⁴ − 1, and the
file's own comment gives the convention: forks that are disabled are temporarily set to the max uint64
value.<Cite src="consensus-specs-mainnet-config-v161" />

**This is the most reliable "has it shipped" test available.** Open `configs/mainnet.yaml`, find the fork
epoch. A real number means it activated and you can compute when. `18446744073709551615` means the
specification exists and the network will never reach it as configured. No blog post, no conference talk
and no roadmap graphic outranks that line, because it is the line the clients read.

### The two spec repos made opposite structural choices

Both consensus-specs and execution-specs are executable Python. They organise it in opposite ways, and
knowing which is which saves you from reading the wrong file.

**consensus-specs layers.** Each fork's document contains only what that fork changed. Fulu's beacon-chain
document opens with a note that the specification is built upon Electra, and its headings are prefixed
*Modified* and *New*.<Cite src="consensus-specs-fulu-beacon-chain-v161" /> Altair's marks changes inline
with comments like `# [New in Altair]` and `# [Modified in Altair]` against individual
fields.<Cite src="consensus-specs-altair-beacon-chain-v161" /> Open one fork's file and you are reading a
patch, not a program.

**execution-specs snapshots.** Its source tree carries one complete directory per fork —
`src/ethereum/forks/` holds `frontier` through `amsterdam`, plus `bpo1` to `bpo5` for the blob-parameter-only
forks.<Cite src="execution-specs" /> Each is a full implementation. Osaka's `fork.py` is not a diff against
Prague; it is the whole entry point to the specification for that
fork.<Cite src="execution-specs-osaka-fork" />

The practical consequence: on the execution side, one directory answers your question completely. On the
consensus side, one file never does — which is the subject of this module's third lesson, and the reason
its build step exists.

### And they move on different clocks

Cadence differs too, and the release page shows it plainly. As of 26 August 2026 the consensus-specs
release line stands at `v1.7.0-alpha.14`, published 19 August 2026, and every tag in the `v1.7.0` line
back to March 2026 is marked pre-release.<Cite src="consensus-specs-releases" /> The `v1.6.x` line — the
stable line this lesson cites throughout — is what carried Fulu.

So "the current spec" is two different things depending on which fork you care about. For shipped
behaviour you want the latest stable tag. For a fork under construction you want the alpha line, which
will change under you between one week and the next. Citing an unversioned link to a development branch is
how references rot: paths move, files get renamed, and a URL that resolved last quarter returns a 404 or,
worse, a different document. Prefer a tag.

## Star names and city names

The naming confusion is a real tax on newcomers and it dissolves in one paragraph.

**The consensus layer names its forks after stars.** Phase0, Altair, Bellatrix, Capella, Deneb, Electra,
Fulu, Gloas, Heze.<Cite src="consensus-specs" />

**The execution layer names its forks after cities** — the Devcon host cities. Shanghai, Cancun, Prague,
Osaka, Amsterdam.<Cite src="engine-api-spec" /><Cite src="execution-specs" />

**A network upgrade ships both at once, and is referred to by the two names welded together.** Prague plus
Electra is Pectra. Fulu plus Osaka is Fusaka. Gloas plus Amsterdam is Glamsterdam — the portmanteau the
meta EIP is titled for.<Cite src="eip-7773" />

So when you read that something "landed in Fulu" and elsewhere that it "landed in Fusaka", those are the
same event described from two layers. And when a change is purely consensus-layer, it has a star name and
no city name at all — which is why searching the execution specs for it returns nothing and feels like a
contradiction.

  belief="The star name and the city name are two names for the same fork."

  why="They activate simultaneously and are always spoken about together, so they look interchangeable."

/>

That last detail is worth holding on to, because it is the one that produces real bugs: the two layers do
not even activate on the same *kind* of clock. The consensus layer schedules by fork epoch, in the beacon
config.<Cite src="consensus-specs-mainnet-config-v161" /> The Engine API talks about payload
timestamps — Osaka's rules are written in terms of whether a payload's `timestamp` falls at or after
activation.<Cite src="engine-api-spec" /> Two representations of one moment.

### The next pair, and what can honestly be said about it

After Gloas, consensus-specs lists **Heze**.<Cite src="consensus-specs" /> After
`amsterdam.md`<Cite src="engine-api-amsterdam" />, execution-apis carries a
**bogota.md**.<Cite src="engine-api-bogota" /> Both files exist and both are being written against.

The pattern says those are the two halves of the upgrade after Glamsterdam. What this lesson will not do
is print a combined name for it, because the concatenation is a convention rather than something either
repository states, and there is no fork epoch, no timestamp and no meta EIP scheduling it. "Heze on the
consensus side, Bogota on the execution side, both unscheduled" is the whole of what the primary sources
support.

## The four wrongnesses

Return to the opening question, and name what each of the four people did.

**The EIP-only reader** described a design as though it were behaviour. EIPs contain proposals at every
stage of life, including ones that were revised, deferred or killed. Reading an EIP tells you what someone
wanted.

**The spec-only reader** was right about today and had no view of what is coming or why. Specifications
describe mechanism without motivation; nothing in a spec file explains why a rule exists or what it
replaced.

**The meta-EIP reader** was the closest to correct and still missing something, because "declined for
Glamsterdam" is a statement about one upgrade and gets read as a verdict.

**The Engine-API reader** saw a file for an unshipped fork and inferred a schedule. Specification work
running ahead of deployment is how the process is *supposed* to look; the existence of the artifact says
nothing about the date.

The composite answer — and the one a colleague can act on — needs all four: *no, not today; it was
proposed as EIP-7805, declined for Glamsterdam, and is being specified for a later upgrade with no
activation scheduled.*<Cite src="eip-7773" /><Cite src="eip-7805" /><Cite src="engine-api-bogota" />

<Answer>
**Four claims, three of them wrong, and each one is checkable in under a minute.**

**"Arriving later this year" — cut the date entirely.** The Glamsterdam meta EIP is status Draft and
schedules no activation.<Cite src="eip-7773" /> The consensus config sets `GLOAS_FORK_EPOCH` to
`18446744073709551615`, the max-uint64 value the file's own comment defines as disabled — the encoding for
"no date".<Cite src="consensus-specs-mainnet-config-v161" /> *Check: `configs/mainnet.yaml`, then the meta
EIP.* If the fork epoch is max uint64, no date is publishable, whatever anyone has said in a talk.

**"Introduces enshrined proposer-builder separation" — keep, with the tense fixed.** EIP-7732 is listed
under Scheduled for Inclusion in the meta EIP.<Cite src="eip-7773" /> "Is scheduled to introduce" is the
accurate verb. *Check: the meta EIP's Scheduled list.*

**"Alongside inclusion lists" — remove.** EIP-7805 (FOCIL) is listed under **Declined for
Inclusion**.<Cite src="eip-7773" /> It remains a Draft EIP<Cite src="eip-7805" /> and is being specified
for a later fork — the Engine API carries a `bogota.md` defining
`engine_getInclusionListV1`<Cite src="engine-api-bogota" /> — but it is not part of this upgrade. *Check:
the meta EIP's Declined list.* The trap here is that the EIP exists, is merged, and is actively worked on;
none of those facts imply inclusion.

**"Six-second slots" — remove.** EIP-7782, "Reduce Block Latency", is also Declined for
Inclusion.<Cite src="eip-7773" /><Cite src="eip-7782" /> Mainnet slots remain 12 seconds, and the
attestation deadline remains a fraction of that.<Cite src="consensus-specs-mainnet-config-v161" />
*Check: the meta EIP, then the config's `SLOT_DURATION_MS`.*

**The missing item worth adding.** EIP-7928, block-level access lists, is Scheduled for Inclusion and is
the other headline of the upgrade.<Cite src="eip-7773" /> A post that lists inclusion lists and omits BALs
has the scope roughly inverted.

**The general method, which is the actual answer.** For any claim of the form "upgrade X does Y", read
three documents in this order: the **hardfork meta EIP** for whether Y is scheduled, declined or merely
proposed<Cite src="eip-7723" />; the **specs repository** for what Y actually does; and the **config file**
for whether X has an activation at all.<Cite src="consensus-specs-mainnet-config-v161" /> Secondary
coverage is where the errors in this draft came from, and every one of them is contradicted by a primary
document that takes a minute to open.

**And the framing to give your teammate.** A draft that says "scheduled for a future upgrade, no date
announced" ages gracefully. A draft that says "arriving later this year" is a hostage to a schedule nobody
controls, and Ethereum upgrades have moved before.
</Answer>

## What this unlocks

- **The next lesson** takes the claim that the Python *is* the specification literally: you build the
  package, import a fork, construct a state and apply a block. The point is not the exercise. It is that a
  question you cannot answer from prose becomes a REPL session.<Cite src="eth2book-running-the-spec" />
- **Lesson three** explains why the fork documents look so thin when you open
  them — Fulu's beacon-chain document opens by saying it is built upon
  Electra<Cite src="consensus-specs-fulu-beacon-chain-v161" /> — and what the build step does about it.
- **The release notes** are the real changelog for each fork, and they are attached to tags rather than
  written as prose elsewhere.<Cite src="consensus-specs-releases" />

The habit worth forming: before answering a protocol question, name the artifact you are answering from
and what kind of question it can settle. "The EIP says" and "the spec says" and "the meta EIP says" are
three different claims, and confusing them is how confident, well-read people end up wrong in public.
