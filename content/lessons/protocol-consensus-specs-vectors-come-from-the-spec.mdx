Six independent implementations, in six languages, written by six teams who do not share code and mostly
do not share a timezone, produce byte-identical state roots for every block on Ethereum. That is not
normal. Independent reimplementation of anything nontrivial usually produces divergence, and here
divergence is a chain split.

The thing that makes it work is not shared review, not a reference client everyone quietly copies, and not
unusual discipline. It is a corpus: a pile of generated files containing a starting state, an input, and
the exact state that must result. Every client runs it in CI. Agreement is manufactured by making
disagreement mechanically detectable.

This lesson is how that corpus is built, what it can prove, and — the part that matters most and gets
taught least — what it structurally cannot.

## What a vector is

`ethereum/consensus-spec-tests` publishes generated test vectors, attached to releases, that every
consensus client consumes.<Cite src="consensus-spec-tests" /> They are SSZ-encoded, snappy-compressed
files laid out in a directory tree, and the tree is the schema.

The general test format specifies the path structure
exactly:<Cite src="consensus-specs-test-formats" />

```text
tests/<config name>/<fork or phase name>/<test runner name>/<test handler name>/<test suite name>/<test case>/<output part>
```

Each level is doing a job. The config name is at the top so a client can run minimal first, which is
useful during development.<Cite src="consensus-specs-test-formats" /> The fork name comes next because
each fork introduces new tests and modifies existing ones — some earlier-fork tests repeat with updated
state data.<Cite src="consensus-specs-test-formats" /> The runner is the category, and the format
document names the well-known ones: `bls`, `epoch_processing`, `genesis`, `operations`, `sanity`,
`shuffling`, `ssz_generic`, `ssz_static`.<Cite src="consensus-specs-test-formats" />

Cases are split into individual directories deliberately: it enables diffing parts of a case and tracking
changes per part, and it means a suite's size does not change the memory a runner needs, because cases
load one at a time.<Cite src="consensus-specs-test-formats" />

### The shape of one case

The `operations` runner is the clearest, and its format is three
files:<Cite src="consensus-specs-test-formats-operations" />

- `pre.ssz_snappy` — an SSZ-encoded `BeaconState`, before.
- `<input-name>.ssz_snappy` — the operation object: an `Attestation`, a `Deposit`, a `ProposerSlashing`.
- `post.ssz_snappy` — the `BeaconState` after. **No value if operation processing is aborted.**

That last clause carries as much weight as the rest of the format. An absent `post` file is the encoding
for *this input must be rejected*. The document states the condition plainly: the resulting state should
match the expected post state, or if post is left blank, the handler should reject the input operation as
invalid.<Cite src="consensus-specs-test-formats-operations" /> Negative tests need no separate machinery.

The runner also publishes a table mapping each operation name to the function that must process
it — `attestation` to `process_attestation`, `deposit` to `process_deposit`, `voluntary_exit` to
`process_voluntary_exit`, `withdrawals` to `process_withdrawals` (new in Capella), `consolidation_request`
to `process_consolidation_request` (new in Electra), `payload_attestation` to
`process_payload_attestation` (new in Gloas).<Cite src="consensus-specs-test-formats-operations" /> The
corpus does not just say what the answer is; it says which function is supposed to produce it.

<Aside kind="note">
One entry in that table shows the boundary between the layers being drawn inside a test. The
`execution_payload` handler normally requires verifying the execution state transition, which is the
responsibility of an external execution engine — so during testing that call is **mocked**, and an
`execution.yml` file supplies a dict with an `execution_valid`
boolean.<Cite src="consensus-specs-test-formats-operations" /> The consensus test corpus does not run an
EVM. It asserts what the consensus layer does *given* a verdict, which is precisely the interface the
Engine API carries.
</Aside>

### The runners, and what each one is for

The runner names look arbitrary until you notice they carve the specification along the same seams the
state transition does.

**`sanity`** sets the baseline of what really needs to pass — the essentials. It has two handlers: `slots`,
covering transitions of one or more slots including epoch transitions within them, and `blocks`, covering
transitions triggered by one or more blocks.<Cite src="consensus-specs" /> If a client fails sanity, none
of the finer-grained results are worth reading.

**`operations`** isolates one operation at a time against a pre-state, as described
above.<Cite src="consensus-specs-test-formats-operations" />

**`epoch_processing`** isolates each epoch sub-transition. Its own format document makes a nice
observation about why it can be simpler than the operations format: there is no "change" factor, because
the sub-transitions are pure functions with just the pre-state as
input.<Cite src="consensus-specs" /> Its cases carry `pre`/`post` for the sub-transition and
`pre_epoch`/`post_epoch` for the whole epoch transition around it, so a failure can be attributed to one
sub-function rather than to the epoch as a whole.<Cite src="consensus-specs" />

**`ssz_static`** instantiates the known Ethereum SSZ types from binary data, based on the spec-maintained
SSZ implementation.<Cite src="consensus-specs" /><Cite src="ssz-specs" /> This is the layer everything else
rests on: a client that Merkleizes a container differently produces different state roots for every case
in every other runner, so an `ssz_static` failure usually explains a cascade elsewhere.

**`shuffling`**, **`genesis`** and **`bls`** cover committee selection, genesis-state construction and the
signature primitives respectively.<Cite src="consensus-specs-test-formats" />

Every case may carry a `meta.yaml` with an optional description and a `bls_setting`, and the format
document is emphatic that tests should be identified by their directory name rather than by that
description.<Cite src="consensus-specs-test-formats-operations" /> Report failures by path.

## Nobody writes these by hand

Here is the fact that reframes the whole corpus.

The vectors are produced by executing the specification. The Makefile's `reftests` target depends on the
spec-generation step and then runs
`python -m tests.generators.main --output ../consensus-spec-tests/tests`, with optional filters for
runners, cases, forks and presets.<Cite src="consensus-specs-makefile-v161" /> The README says it in one
sentence: reference tests are built from the executable Python
specifications.<Cite src="consensus-specs-readme-v161" />

So the pipeline runs end to end like this:

**Markdown code block → extraction → `eth2spec` module → generator script → SSZ vector → client
CI.**<Cite src="consensus-specs-makefile-v161" /><Cite src="consensus-specs-readme-v161" />

### What follows, stated bluntly

**The vectors cannot catch a bug in the specification.** If `process_attestation` contains a mistake, the
generator runs that mistake over its inputs and records the mistaken outputs as expected. Every client
that faithfully implements the flawed rule passes. The corpus is green and the protocol is wrong.

**What the vectors do catch is divergence between a client and the spec.** That is the failure mode that
splits chains, and making it mechanically detectable across six implementations is an enormous
achievement. It is simply a different achievement from correctness.

**So what catches spec bugs?** Three things, none of them the corpus.

*Review.* Humans reading the pull request, in a repository whose diffs are small because each fork is a
patch.

*Executability itself.* The repository's own tests exercise the spec to verify consistency and provide
feedback on modifications of it.<Cite src="pyspec-readme" /> That catches incoherence — a rule that
cannot run, a transition that does not terminate, an invariant the spec asserts about itself and then
violates. It does not catch a rule that runs perfectly and is the wrong rule.

*Devnets.* Running the thing, with real clients, at scale, before mainnet. This is why devnet cycles are
long and why an upgrade that has passed every test still spends months on test networks.

<Aside kind="warn">
There is a counterintuitive consolation. A bug in the specification that every client implements
identically does not split the chain — everyone is wrong in the same way, and the network stays in
consensus about an incorrect rule. That is a governance and economics problem, potentially a severe one,
but it is not a liveness or safety failure of the kind client divergence
produces.<Cite src="ethereum-org-client-diversity" /> The corpus is aimed squarely at the failure that
breaks the chain, and it is aimed there on purpose.
</Aside>

### The coverage frontier is where the bugs are

Passing the corpus means a client agrees with the spec on everything the corpus covers. That sentence has
a load-bearing clause at the end.

The format document is candid about the corpus being a scoped deliverable rather than an exhaustive one:
it describes the aim as providing clients with a well-defined scope of work to run a particular set of
test suites, notes that clients incomplete in functionality can choose to ignore suites using certain
runners or handlers, and asks complete clients to contribute to testing and seek better resources for
conformance.<Cite src="consensus-specs-test-formats" /> That is a document describing a growing corpus,
not a finished one.

**Consensus bugs live outside coverage, by definition.** Anything inside is caught before merge. The
interesting cases are the state shapes nobody generated: unusual validator-set configurations, rare
operation combinations, boundary conditions at fork transitions, interactions between two features that
were tested separately.

Which is why the corpus is not the only harness. `ethereum/hive` runs cross-client integration tests,
putting real client binaries in containers and making them interact<Cite src="hive-repo" />, and
`ethereum/execution-spec-tests` does the equivalent generation job for the execution
layer.<Cite src="execution-spec-tests-repo" /> The consensus vectors test one client against the spec;
Hive tests clients against each other. Different questions, and you want both.

There is also a second generated corpus for fork choice. The Makefile's `comptests` target produces
compliance tests into a separate `compliance-spec-tests` directory, with its own generation
configuration.<Cite src="consensus-specs-makefile-v161" /> Fork choice is not a pure state transition —
it depends on message arrival order and timing — so it needs a different kind of test than
pre-state-plus-input-equals-post-state.

## Which vectors, though?

"Run the spec tests" is an ambiguous instruction, and the ambiguity is a release-channel question.

The README describes both channels in one paragraph: reference tests built from the executable Python
specifications are available in the release assets for each release, and there are also **nightly**
reference tests built from the latest version of the
specifications.<Cite src="consensus-specs-readme-v161" />

**Stable channel.** Vectors attached to a tagged release. Pinned, reproducible, and matching a spec
version you can name. This is what you want for a shipped fork, and what a client's release CI should be
running.

**Nightly channel.** Vectors generated from the development branch by a scheduled workflow. This is what
you want for a fork under construction — it lets client teams implement against Gloas before Gloas
stabilises — and it will move under you between one run and the next.

The practical rule: **name your channel whenever you report a result.** "Our client passes the spec tests"
means one of two very different things. Against a release asset it is a claim about conformance to a
version. Against nightly vectors it is a claim about conformance to a moving target, valid for about a
day, and a regression tomorrow may be somebody editing the spec rather than anybody editing your client.

The release line makes this concrete. As of 26 August 2026 the head of the consensus-specs releases is
`v1.7.0-alpha.14`, published 19 August 2026, and the entire `v1.7.0` line is marked
pre-release.<Cite src="consensus-specs-releases" /> A fork whose spec line is still in alpha has no stable
vectors, because there is no stable release to attach them to.

Two consequences for anyone wiring this into CI. **Pin the tag, and treat a bump as a change to review.**
Because vectors are regenerated whenever the spec changes, moving from one release's assets to the next
can change expected outputs — which is the system working correctly, and is indistinguishable from your
own regression unless the version moved deliberately. **And keep the two channels in separate jobs.** A
nightly job that goes red is information about a spec under construction; a pinned job that goes red is
information about your code. Merging them into one signal destroys the only thing that made them useful
separately.

Say what that claim establishes, what it does not, and how you would strengthen it.

<Answer>
**It establishes something real and narrower than "verified correct", and the gap has three parts.**

**What it does establish.** For every case in the corpus, their implementation produces the same
post-state as the specification — including rejecting every input whose case has an empty `post`
file.<Cite src="consensus-specs-test-formats-operations" /> Across six implementations, that is the
property that keeps the chain in one piece, and it is the strongest routinely-checkable claim available.

**Gap one — "correct" is the wrong word, because the vectors are the spec's own output.** They are
generated by running the specification.<Cite src="consensus-specs-makefile-v161" /><Cite src="consensus-specs-readme-v161" />
A bug in the spec is baked into the expected outputs, and a client that reproduces it passes. The claim
they have earned is *agreement with the specification*, which is exactly what is wanted from a client and
is not the same claim.

**Gap two — "100%" is a proportion of the corpus, not of the behaviour space.** The format document treats
the corpus as a scoped set of suites that grows, explicitly allowing incomplete clients to skip runners
and asking complete ones to help improve conformance
resources.<Cite src="consensus-specs-test-formats" /> Consensus bugs live outside coverage by
construction: everything inside it is caught before merge. A team reporting 100% is reporting that they
are at the frontier, not past it.

**Gap three — which vectors, and from when?** Stable release assets and nightly-generated vectors are two
channels.<Cite src="consensus-specs-readme-v161" /> If this is the current stable fork, the answer should
name a release tag. If it is a fork under development, the vectors were generated from a moving branch and
the claim has a shelf life of about a day.<Cite src="consensus-specs-releases" />

**And one thing the corpus deliberately does not touch.** The `execution_payload` handler mocks the
execution engine with an `execution.yml` supplying an `execution_valid`
boolean.<Cite src="consensus-specs-test-formats-operations" /> Everything about how their client behaves
when a real execution client answers slowly, inconsistently, or not at all is untested here.

**How I would strengthen the claim.**

*State it precisely.* "Agrees with consensus-specs vX.Y.Z on every case in the release's vector set, both
presets." That is checkable, dated, and does not overclaim.

*Add cross-client integration.* Hive runs real client binaries against each other in
containers<Cite src="hive-repo" />, which covers the interaction failures a per-client vector run cannot
see.

*Add differential testing beyond the corpus.* Generate state and operation pairs the corpus does not
contain and compare against the pyspec directly — the specification is importable, so it can serve as an
oracle for inputs nobody generated a vector for.

*Fuzz the deserialization boundary.* `ssz_generic` and `ssz_static` cover the encoding<Cite src="consensus-specs-test-formats" /><Cite src="ssz-specs" />,
but malformed and adversarial input arriving over the network is a different population from
well-formed containers the generator produced.

*Say what happens on a devnet.* Spec bugs and integration bugs are found by running the thing at scale
before mainnet. A team that has passed vectors and not yet run a devnet has completed the cheap half.

**The one-line version.** They have shown their client agrees with the specification everywhere anyone has
looked. That is the right goal and worth celebrating; "verified correct" claims something no corpus
generated from the spec can deliver.
</Answer>

## What this unlocks

- **The next lesson** assembles the whole picture into a reading procedure. A protocol change is four
  artifacts — the EIP, the specs pull request, the vectors it added, the client pull requests — and the
  vectors are the layer that tells you what a client must *observably*
  produce.<Cite src="consensus-spec-tests" />
- **The module's practice** has you mutate one line in the built pyspec and run the suite, so that the
  relationship between a spec edit and a set of failing vectors stops being theoretical. Which cases fail,
  and why they are consensus failures rather than unit-test failures, is the whole
  exercise.<Cite src="consensus-specs-tests-readme" />
- **Downloading a release asset and counting cases by runner** takes ten minutes and gives you a
  quantitative feel for where the corpus is dense and where it is
  thin.<Cite src="consensus-spec-tests" />

The habit worth forming: whenever someone shows you a green test suite, ask where the expected values came
from. If they were derived from the same artifact under test, the suite is measuring reproduction rather
than correctness — which is often exactly what you want, as long as nobody in the room thinks it is the
other thing.
