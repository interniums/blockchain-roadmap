Clone both of the consensus clients most newcomers land on, and check what you just checked out.

```text
sigp/lighthouse        default branch: stable
OffchainLabs/prysm     default branch: develop
```

Neither is `main`. Neither is `master`.<Cite src="lighthouse-repo" /><Cite src="prysm-repo" /> And in
Lighthouse's case the default branch is explicitly *not* the one you should base work on: the book
states that the project maintains two permanent branches — `stable`, which always points at the
latest release and is what most users want, and `unstable`, which carries the latest pull requests
and is the branch developers should base theirs on.<Cite src="lighthouse-contributing" />

A first pull request opened against `stable` is not rejected on the merits. It is a diff against a
release tag, full of changes that already landed, and the reviewer has to ask you to redo it. That is
the cheapest possible mistake to avoid and it is invisible from anywhere except the project's own
contributing page.

This lesson reads those two clients as *processes* rather than as codebases. They implement the same
[consensus specification](/c/consensus-specs-repo), run the same
[reference vectors](/c/consensus-spec-tests), and perform the same
[consensus-client role](/c/consensus-client-role) in a node. Everything that differs is language,
tooling and review culture — which is the whole of what you are choosing between.

## Lighthouse: Rust, and a written philosophy about crashing

Lighthouse is written in Rust by Sigma Prime. On 26 August 2026 the repository shows 3,465 stars,
1,050 forks and 519 open issues.<Cite src="lighthouse-repo" /> The book that documents it is generated
from the `unstable` branch, which is worth noticing: the published documentation describes the
development branch, not the release you are running.<Cite src="lighthouse-book" />

The contributing page gives a five-step opening move, and step three and step four are the ones
newcomers skip:

1. Read the how-to-contribute document.
2. Set up a development environment.
3. Browse the open issues, looking for the `good first issue` tag.
4. **Comment on an issue before starting work.**
5. Share your work via a pull request.<Cite src="lighthouse-contributing" />

Step four is a norm, not a courtesy. Curated newcomer lists accumulate issues that were solved
elsewhere, superseded by a refactor, or quietly claimed in a Discord thread. A comment costs you a
minute and buys you the difference between a weekend of work and a weekend of wasted work.

The Rust conventions are two commands — `cargo clippy --all` and `cargo fmt --all --check` — and one
rule that tells you something real about the domain:<Cite src="lighthouse-contributing" />

> Generally, panics should be avoided at all costs.

The reasoning given is not stylistic. Lighthouse "operates in an adversarial environment (the
Internet) and it's a severe vulnerability if people on the Internet can cause Lighthouse to crash via
a panic".<Cite src="lighthouse-contributing" /> The concrete guidance follows from it: prefer
`array.get(1)?` over `array[1]`, prefer returning a `Result` or `Option`, and where you know a panic
cannot happen but cannot express that to the compiler, use `.expect("Helpful message")` rather than
`.unwrap()`, with the reasoning written in a nearby comment.<Cite src="lighthouse-contributing" />
There is also a hard rule that every `TODO` must be accompanied by a linked GitHub
issue.<Cite src="lighthouse-contributing" />

Take that seriously as a description of the job. A crash in a web service is an incident. A crash in
a consensus client that a stranger can trigger over the network is a liveness attack on a share of
the validator set, and if the client is above a third of the network it is a
[finality stall](/c/client-diversity-thresholds). The style rule is the threat model wearing a lint
config.

<Aside kind="note">
**The label list is a map of the roadmap.** Lighthouse maintains 100 issue labels. Beyond the ordinary
ones there are fork labels — `bellatrix`, `capella`, `deneb`, `electra`, `fulu`, `gloas`, `heze` —
devnet labels such as `fusaka-devnet-0` through `fusaka-devnet-3` and `peerdas-devnet-4`, and feature
labels including `das`, `focil`, `execution-proofs`, `light-client`, `lean` and
`tree-states`.<Cite src="lighthouse-labels" />

Filtering issues by a devnet label is one of the fastest ways to see what an in-flight fork actually
broke in one implementation, in that implementation's own words. It is the same information the
All Core Devs record carries, at a different resolution.
</Aside>

There are four newcomer-adjacent labels rather than one: `good first issue`, `help wanted`,
`low-hanging-fruit` and `good for bounty`.<Cite src="lighthouse-labels" /> And there is an `epf`
label, which means this team tags work specifically for Ethereum Protocol Fellowship
participants.<Cite src="lighthouse-labels" /> Keep that in mind for the last two lessons in this
module: the relationship between the fellowship and the client teams is concrete enough to have
shipped as GitHub metadata.

## Prysm: Go, a different owner, and a build system that is the real barrier

Prysm is the Go consensus client. Its repository is `OffchainLabs/prysm`, and the older
`prysmaticlabs/prysm` address redirects there silently.<Cite src="prysm-repo" /> Its documentation
portal is at `prysm.offchainlabs.com`, showing version 7.1.8 on 26 August
2026.<Cite src="prysm-docs" /> The repository shows 3,775 stars, 1,348 forks and 594 open
issues.<Cite src="prysm-repo" />

For the very large population of engineers who already write Go and do not want to learn Rust first,
this is the natural consensus-layer entry point. The layer you can reach is identical to
Lighthouse's; only the language and the process differ.

The contributing guide opens with a prohibition rather than an invitation, in a call-out block:

> Please, **do not send pull requests for trivial changes**, such as typos, these will be rejected.
> These types of pull requests incur a cost to reviewers and do not provide much value to the
> project.<Cite src="prysm-contributing" />

That is the second client team in this module to write that rule down explicitly — Reth has its own
version refusing spelling-and-grammar-only contributions. Two independent teams closing the same door
is a signal about what has been arriving in their inboxes, and it should permanently retire "fix a
typo" as first-contribution advice.

The rest of the guide is a fourteen-step git walkthrough, and its substantive instruction is the same
as Lighthouse's: pick an issue, then "leave a comment to let the development team know that you would
like to work on it".<Cite src="prysm-contributing" />

**The real friction for a Go engineer is not the Go.** The repository root carries `BUILD.bazel`,
`MODULE.bazel`, `MODULE.bazel.lock`, `WORKSPACE`, `.bazelrc`, `.bazelversion`, `deps.bzl` and a
`bazel.sh` wrapper, alongside an ordinary `go.mod`.<Cite src="prysm-repo" /> Prysm builds with Bazel.
If your entire Go career has been `go build ./...`, the first hour of this project is a build system
you have never used, and that is where people quit. Budget for it deliberately instead of discovering
it at 11pm.

<Aside kind="warn">
**Contributor guides go stale, including good ones.** Step 13 of the Prysm contribution steps says to
run `git pull origin master`.<Cite src="prysm-contributing" /> The repository's default branch is
`develop`.<Cite src="prysm-repo" /> The guide also points at `docs.prylabs.network` for the
most up-to-date documentation, an address that now redirects to the Offchain Labs
domain.<Cite src="prysm-contributing" /><Cite src="prysm-docs" />

Neither is a criticism of the project; both are what happens to any document that outlives an
acquisition and a branch-naming change. The lesson for you is procedural: read the guide for
*intent*, and read the repository for *facts*. Where they disagree, the repository is right.
</Aside>

## The label trap, stated plainly

Prysm maintains 55 issue labels. `good first issue` is not one of them; the closest is
`help-wanted`.<Cite src="prysm-labels" />

Now recall the cross-repository aggregator from the previous lesson, which watches the `good first
issue` label across 31 Ethereum core repositories. On 26 August 2026 its entry for Prysm reads "No
Current Good First Issues".<Cite src="gfi-ethereum-aggregator" />

Both of those statements are true and the obvious inference from them is false. The aggregator is
reporting the absence of a *label*, not the absence of *work*. A repository with 594 open issues has
work.<Cite src="prysm-repo" />

The habit to build: before concluding that a project has nothing for you, open its label list — the
plain `/labels` page of the repository — and read it. It takes a minute, it tells you the project's
own vocabulary, and in every case in this module it revealed something a search did not.

## The other four, briefly

Lighthouse and Prysm are the two most newcomers reach for, which is why they get the detail. That is
a statement about where attention goes, not a ranking — the community diversity dashboard publishes
consensus-layer datasets that disagree with each other badly enough that one places Lighthouse above
half the network and another at a fifth, so no ordering here is derived from
share.<Cite src="clientdiversity-org" /> They are also not the field. Teku is Java at `Consensys/teku`, Nimbus is Nim at `status-im/nimbus-eth2`, Grandine is
Rust at `grandinetech/grandine`, and Lodestar is TypeScript at
`ChainSafe/lodestar`.<Cite src="teku-repo" /><Cite src="nimbus-repo" /><Cite src="grandine-repo" /><Cite src="lodestar-repo" />

Two of those are worth a second look for reasons that have nothing to do with size.

**Lodestar is TypeScript**, which makes it the only consensus client a front-end or Node engineer can
read on day one. Its label scheme includes both `good first issue` and a dedicated `good EPF
issue`.<Cite src="lodestar-labels" /> On 26 August 2026 it showed 13 open good-first-issues, the
largest count of any consensus client in the aggregator, though 8 of them already had someone
assigned.<Cite src="gfi-ethereum-aggregator" />

**Ream is a lean client in Rust**, and a reminder that the list of consensus clients is not
closed.<Cite src="ream-repo" /> New implementations start small, which means their issue trackers are
comprehensible in an afternoon and their maintainers are reachable — the inverse of the trade-off
Geth presents.

## The one seam that is identical in every one of them

There is a part of each of these codebases that is the same problem in six languages, and it is the
most useful place for a newcomer to start reading: the harness that downloads the reference test
vectors and replays them against the client's own state-transition code.

Every consensus client consumes the [generated reference vectors](/c/consensus-spec-tests) in CI.
That is the mechanism — not shared code, not shared review — that makes six independent
implementations agree.<Cite src="consensus-specs" /> Each client therefore needs the same three
things: something that fetches the vectors for the right release, something that decodes SSZ
pre-state and post-state, and something that runs the transition and diffs the result.

The consequence for you is that this harness is where genuinely tractable, genuinely useful issues
accumulate. Prysm keeps a dedicated `spec-tests` label.<Cite src="prysm-labels" /> Lodestar's open
newcomer list on 26 August 2026 included both "Improve experience of `download-spec-tests`" and
"Lazily load spec tests for beacon-node and validator".<Cite src="gfi-ethereum-aggregator" /> Those
are ordinary software problems — fetching, caching, lazy loading, developer ergonomics — sitting at
the exact point where the protocol's correctness guarantee is enforced.

They are also portable. Understanding how one client consumes the vectors means understanding what
every other client must also do, which makes this the cheapest possible way to build a mental model
that survives changing clients. And when a
[fork under development moves to nightly vectors](/c/spec-release-channels), the harness is the code
that has to cope with a moving target — so it changes every upgrade cycle, and it is never finished.

## What this unlocks

**The next lesson** answers the question these two have been circling: given that typo fixes are
explicitly refused and consensus-critical code is the slowest thing to review, what *does* a
mergeable first contribution look like? The answer has moved recently — the repository most guides
name for this is now archived — and the replacement has a branch layout worth learning.

**Right now**, you have the four artefacts that decide where you start, and you can read all of them
for any client before dinner: the default branch and which branch pull requests target, the
contributing guide's prohibitions, the label list in the project's own vocabulary, and the open issues
that are actually unassigned.

**And the durable habit**: when a tool reports zero across a set of repositories, ask what the tool
measured. The answer is almost never what the column header says.
