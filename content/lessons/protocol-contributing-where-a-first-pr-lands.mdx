The single most repeated piece of advice about entering Ethereum core development is: start in
`ethereum/execution-spec-tests`, because the tests are written in Python and the repository is
unusually approachable for a core project.

On 26 August 2026, that repository is **archived**. Its issue count is zero because it accepts no
issues. Its last push was 2 July 2026.<Cite src="execution-spec-tests-repo" /> Its documentation site
serves one page, headed "Archived (Welded)", which says the project has merged into
`ethereum/execution-specs` and that the site is no longer
maintained.<Cite src="eest-archived-notice" />

Nothing was cancelled. The work is more active than ever — it simply lives somewhere else, under a
branch layout that does not resemble any repository you have contributed to before. Anyone following
the standard advice today forks a read-only repository and finds out later.

This lesson is the map of where a first contribution actually lands in 2026: the merge that moved
the tests, what the entry-point statistics look like when you count them rather than assume them, and
the two kinds of contribution that client teams are short of and nobody competes for.

## The Weld: why the tests moved into the specs

The Ethereum Foundation's STEEL team — Specifications and Testing for the Ethereum Execution Layer —
announced on 4 November 2025 that "The Weld" was complete: `ethereum/execution-spec-tests` had been
merged into `ethereum/execution-specs`, and the unified repository was accepting
contributions.<Cite src="steel-weld-complete" />

The stated reasons are all developer-experience problems, and they are worth reading because they
describe what it was like to write a spec test before:<Cite src="steel-weld-complete" />

- New spec developers had to clone and manage two separate repositories.
- Test developers had to manually configure which branch and fork of the Python execution specs to
  generate vectors against, in an `eels_resolutions.json` file.
- Getting test coverage of the spec was non-trivial.
- You could not step from a test into the spec code in a debugger, because the spec source was fetched
  over HTTP by a resolver rather than being present locally.

That last one is the tell. The specification and its tests were coupled in every way that mattered
and separated in the one way that made debugging impossible.

What changed for anyone writing a test:<Cite src="steel-weld-complete" />

- **Pull requests no longer target `main`.** They target the appropriate fork branch or EIP branch —
  `forks/osaka`, `forks/amsterdam`, or `eips/amsterdam/eip-7928`.
- **No resolver configuration.** The reference EVM implementation in your current branch is used.
- **Environment setup is `uv sync` from the repository root**, where it used to be
  `uv sync --all-extras`.
- **Line length dropped from 99 to 79** across test and framework source, for consistency with the
  Python specs.
- **Imports collapsed into one package.** Where a test file used to import from
  `ethereum_test_tools`, `ethereum_test_forks`, `ethereum_test_vm` and `ethereum_test_checklists`
  separately, the commonly used objects now come from a single top-level `execution_testing` import.
- **For client developers, nothing changed**: releases continue to come from the same location.

Line coverage of the Python specs now falls out of the fill command itself, with a
`--cov=src/ethereum` flag producing an HTML report — which means "did my test actually exercise the
spec code I think it did" is now a question you can answer
locally.<Cite src="steel-weld-complete" /> The documentation moved to the STEEL
docs.<Cite src="steel-execution-specs-docs" />

## The branch list is the work in progress

The unified repository does something unusual with branches, and reading them is the fastest survey
of execution-layer work that exists.

On 26 August 2026 `ethereum/execution-specs` carries 79 branches and its **default branch is
`forks/amsterdam`** — not `main`, not `master`.<Cite src="execution-specs-branches" /><Cite src="execution-specs" />
They fall into five families:

Among the EIP branches on that date: `eips/amsterdam/eip-7928`, `eips/amsterdam/eip-8024`,
`eips/amsterdam/eip-7843`, `eips/amsterdam/eip-8304`, `eips/amsterdam/eip-7805` and roughly thirty

`projects/zkevm`.<Cite src="execution-specs-branches" />

<Aside kind="warn">
**A branch is not a decision.** `eips/amsterdam/eip-7805` exists in that
list.<Cite src="execution-specs-branches" /> EIP-7805 is FOCIL, and the research baseline this
curriculum is built on records it as declined for inclusion in Glamsterdam and moved to the following
upgrade. A branch means somebody is implementing something so it can be evaluated; it does not mean
the evaluation concluded, and it does not mean the reverse either.

Where an EIP stands in an upgrade is answered by the All Core Devs record, which the next lesson
covers. Never infer inclusion from the existence of code.
</Aside>

The practical use of the branch list is targeting. If you want to write a test for a specific EIP, the
branch it belongs on already exists and tells you which fork it is being considered for. If you want
to know what is being actively exercised, the devnet branches with the highest numbers are the answer.
And the EIP champion guide confirms the intended flow from the other direction: EIP authors are
encouraged to implement their own changes in the execution specs, with maintainers stepping in to
polish, and to add test cases in a subfolder of `tests/unscheduled/` before an EIP is
scheduled.<Cite src="pm-eip-champion-guide" />

## Counting the entry points instead of assuming them

"Every major client maintains good first issues" is the kind of claim that is repeated because it
sounds obviously true. Here is what it looks like counted.

A community aggregator watches the `good first issue` label across 31 Ethereum core repositories. On
26 August 2026 it listed **113 open issues in total**, distributed like
this:<Cite src="gfi-ethereum-aggregator" />

| Repository | Open | With an assignee |
|---|---|---|
| ethereum/execution-specs | 30 | 14 |
| lambdaclass/lambda_ethereum_consensus | 19 | 0 |
| NethermindEth/nethermind | 14 | 10 |
| ChainSafe/lodestar | 13 | 8 |
| sigp/lighthouse | 11 | 0 |
| ethereum/EIPw | 7 | 3 |
| paradigmxyz/reth | 6 | 5 |
| ethereum/execution-apis | 4 | 0 |
| ethereumjs/ethereumjs-monorepo | 3 | 1 |
| ethpandaops/ethereum-package | 3 | 0 |
| Consensys/teku, grandinetech/grandine, kurtosis-tech/kurtosis | 1 each | 1 total |

And the repositories showing **zero**: `ethereum/go-ethereum`, `OffchainLabs/prysm`,
`besu-eth/besu`, `erigontech/erigon`, `status-im/nimbus-eth2`, `ethereum/consensus-specs`,
`ethereum/hive`, `ethereum/tests`, `ethereum/execution-spec-tests`, `ethereum/beacon-apis`,
`erigontech/silkworm`, `lightclient/rpctestgen`, `ethpandaops/assertoor`, `ethpandaops/tracoor`,
`ethpandaops/checkpointz`, `ethpandaops/dora`, `ethereum/retesteth` and
`eth-protocol-fellows/protocol-studies`.<Cite src="gfi-ethereum-aggregator" />

Three things fall out of that table, and none of them is the thing the table appears to say.

**One: the actionable count is much smaller than the total.** Of the 113 open issues, 42 already carry
an assignee.<Cite src="gfi-ethereum-aggregator" /> An assigned issue is claimed. Starting one without
asking is how two people spend a weekend on the same diff.

**Two: several zeros are label artefacts, not absences.** Prysm has no `good first issue` label at
all.<Cite src="prysm-labels" /> Reth files newcomer issues under
`D-good-first-issue`.<Cite src="reth-labels" /> Its six entries appear in the table only because
that aggregator happens to look for both. Any zero in this table needs to be checked against the
repository's own label list before it means anything.

**Three: the largest single pool is the specs repository, not a client.** Thirty of the 113 are in
`ethereum/execution-specs` — which, post-Weld, is the specification *and* the test
framework.<Cite src="gfi-ethereum-aggregator" /><Cite src="steel-weld-complete" /> The Python-friendly
entry point survived the merge; only its address changed.

  belief="A first contribution to Ethereum means writing consensus-critical code."
  reality="The highest-acceptance first pull requests are tests, tooling, documentation that matches the current release, benchmarks and bug reproductions. Consensus-critical changes get the deepest scrutiny from the people with the least spare time, which makes them the slowest possible thing to land."
  why="The phrase 'core developer' implies core code, and the visible output of the role is protocol changes rather than the test and tooling work that surrounds them."

The structural reason is worth stating rather than asserting. A test case is objectively right or
wrong: it either encodes the specified behaviour or it does not, and a reviewer can decide in
minutes. A change to consensus behaviour is right or wrong relative to a network of independent
implementations and an adversary, and deciding costs a specialist an afternoon. Review capacity is
the scarce resource in this ecosystem, and the contributions that consume the least of it per unit of
value are the ones that get merged.

## The contributions nobody competes for

Here the advice usually degrades into "write docs", which — as the previous two lessons established —
is precisely the advice two client teams have written rules against. Reth will not accept
contributions that only fix spelling or grammar.<Cite src="reth-contributing" /> Prysm rejects
trivial changes such as typos outright, on the stated grounds that they cost reviewers more than they
give.<Cite src="prysm-contributing" />

So be specific about what the short-staffed work actually is.

**Bug reproductions.** Reth's bug report form asks for four things: the version you are on and that
it is current, the platform, code snippets, and concrete steps to
reproduce.<Cite src="reth-contributing" /> The guide points at the standard minimal-complete-verifiable-example
technique and asks that snippets be as small as possible so the bug can be ruled out of your own
code.<Cite src="reth-contributing" /> Turning a vague report into that shape is real engineering, it
requires reading exactly the parts of the codebase that matter, and it is the fastest route to being
known by the people who review code — before you have submitted any.

**Reviewing.** Reth states that any community member is welcome to review any pull request, and
devotes more of its contributing guide to how to review well than to how to
contribute.<Cite src="reth-contributing" /> The guidance — focus on whether the change makes sense
and improves things, request changes rather than demanding them, mark nits explicitly as
non-blocking, do not assume the submitter knows how to add a test — is a description of a job that is
open to you today with no permission required.

**Test and tooling work at the seams.** The specs repository's own newcomer issues on 26 August 2026
were things like replacing a slow hash call in the test framework, making a CLI command produce
useful stack traces, formatting generated code correctly, and documenting commit
prefixes.<Cite src="gfi-ethereum-aggregator" /> Ordinary software problems, in the repository where
the protocol's behaviour is defined.

**Cross-client integration testing.** `ethereum/hive` is the end-to-end harness that runs clients
against each other, and it has a review culture unlike any other repository in this module. It follows
the Collective Code Construction Contract, under which "any patch that successfully solves an issue
(bug/feature) and doesn't break any existing code/contracts must be optimistically merged by
maintainers", with follow-up patches used for polish and reverts available if a change turns out
badly.<Cite src="hive-repo" /> The README calls this "a different approach to code contributions than
your usual FOSS project" and "an experiment".<Cite src="hive-repo" />

Hold that against Geth's `status:merge-at-meeting` label from the first
lesson.<Cite src="geth-labels" /> Two repositories in the same ecosystem, one merging optimistically
by policy and one deciding in a meeting. Both are correct for their blast radius. Choosing where to
put a first pull request is partly choosing which of those you want to meet.

<Aside kind="note">
**Hive keeps a trophy list.** The README carries a section of bugs found in real clients because of
hive, linked to the fixing pull requests: a Geth data race between remote block import and local
mining, a Nethermind CREATE/CREATE2 behaviour when an account already has the maximum nonce, a Besu
gas estimation bug where a transaction with no gas params was estimated as a legacy rather than a
1559 transaction.<Cite src="hive-repo" />

That list is the argument for integration testing as a contribution, made in the only currency that
counts. It is also a reading list: each entry is a real cross-client divergence with the diff that
fixed it attached.
</Aside>

**And the wiki.** The community protocol wiki is built from a public repository, and its own
contributing document is explicit that it is not trying to duplicate existing documentation — the ask
is to connect topics into a bigger picture and to write from what slowed *you* down as a
learner.<Cite src="protocol-studies-repo" /> That is a different instruction from "fix the docs", and
it is one a person six months into learning the protocol is unusually well placed to follow.

## What a first pull request actually looks like

Strip away the mystique and a first core contribution is seven steps, six of which are the same in
every repository in this module. The step that differs is the local gate, and it is the one people
skip.

**Subgoal: pick something that is still wanted.** Filter the repository's own newcomer label — in its
own vocabulary, not GitHub's default — and exclude anything with an assignee. Then read the issue
thread to the end. An issue with a six-month-old comment saying "I'll take this" and nothing since is
available; an issue with a linked draft pull request is not.

**Subgoal: claim it in public before writing code.** Lighthouse puts this in its five-step
instructions; Prysm's guide says to leave a comment saying you would like to work on
it.<Cite src="lighthouse-contributing" /><Cite src="prysm-contributing" /> If the issue turns out to
be stale or already solved, saying so on the thread is itself a contribution: it saves the next
person the same fortnight.

**Subgoal: get the build green before you change anything.** This is the single highest-value hour and
almost nobody logs it. Whatever fails — a toolchain version mismatch, a missing system library, a
build system you have never used — is undocumented friction, and the notes you take fixing it are the
raw material for a documentation contribution that is emphatically not a typo fix.

**Subgoal: branch from what the project actually merges into.** Lighthouse: `unstable`, not the
default `stable`.<Cite src="lighthouse-contributing" /> Geth: `master`, with website changes going to
a separate `website` branch.<Cite src="geth-readme" /> Execution-specs: the fork or EIP branch the
change belongs to.<Cite src="steel-weld-complete" />

**Subgoal: make the change small enough to review in one sitting.** Reth's stated bar is that a pull
request need only be an *incremental* improvement over the status quo, with follow-ups for the
rest.<Cite src="reth-contributing" /> That cuts both ways: it means your change does not have to be
complete, and it means a sprawling change will be asked to become several.

**Subgoal: run the project's own gate, not your own.** This is the step that differs, and running it
is the difference between a review about your change and a review about your formatting:

```text
Reth              make pr
Lighthouse        cargo clippy --all  &&  cargo fmt --all --check
execution-specs   uv sync
                  uv run fill --fork=Osaka --clean tests/<your-path>/ --cov=src/ethereum
                  uv run ruff format tests/
```

Those are the projects' own commands, from their own guides.<Cite src="reth-contributing" /><Cite src="lighthouse-contributing" /><Cite src="steel-weld-complete" />
The execution-specs coverage flag deserves particular attention: it produces an HTML report showing
which lines of the Python spec your test actually executed, which converts "I think this covers the
edge case" into something you can look at.<Cite src="steel-weld-complete" />

**Subgoal: treat review as the work, not as the verdict.** Reth's guide says plainly that any
community member may review, so you may get conflicting feedback, and to watch for comments from code
owners to resolve it.<Cite src="reth-contributing" /> Expect requested changes. Expect nits marked as
non-blocking. Expect, in a consequence-heavy repository, to wait — Geth has a label whose name means
the decision happens when the team is next in a room.<Cite src="geth-labels" />

One more norm worth internalising early, because it will happen to you: if your pull request stalls,
someone may ask whether they can pick it up. Reth's guide describes the polite version of that
exchange and asks that the original contributor be credited via `Co-authored-by:` in the
commit.<Cite src="reth-contributing" /> An abandoned branch is not a failure. It is a change that
found a different author.

## What this unlocks

**The next lesson** supplies the thing that stops all of this being busywork: how to find out what the
core developers have actually said they need. Picking a good first issue makes you a contributor;
reading the All Core Devs record is how you stop picking at random.

**Immediately**, you have a target list with the current addresses attached:
`ethereum/execution-specs` for spec and test work, `ethereum/hive` for cross-client integration under
an optimistic-merge policy, the client repositories for reproductions and reviews, and the protocol
wiki for the connective writing only a recent learner can do well.

**And the discipline that generalises**: when a repository moves, the advice that names it does not
move with it. Before acting on any on-ramp recommendation — including this one — open the repository
and check that it still accepts pull requests, on the branch the advice assumes.
