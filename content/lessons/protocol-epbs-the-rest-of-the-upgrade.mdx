Open EIP-7773 — the hardfork meta EIP for Glamsterdam — and you find three lists and an empty table.

The first list, *EIPs Scheduled for Inclusion*, has eighteen entries. The second, *Other EIPs*, holds
networking and informational proposals. The third, *Declined for Inclusion*, is longer than the first
two combined.<Cite src="eip-7773" />

The empty table is the activation schedule: three rows for Sepolia, Holešky and Mainnet, with a note
saying they will be filled in as activation times are decided by client
teams.<Cite src="eip-7773" />

That document is the most useful single artifact for understanding how Ethereum upgrades actually
work, and this lesson reads it. Along the way it covers the upgrade's other headline change, the
proposal that was cut, and the discipline that decides which list a proposal lands in.

## The other headliner: block-level access lists

ePBS takes execution validation off the attestation critical path. EIP-7928 makes the execution
itself faster. Together they are the upgrade's argument for how blocks get bigger safely.

You already know [per-transaction access lists](/c/access-list): an optional list attached to a
transaction, naming
addresses and storage slots it expects to touch, which pre-warms them and changes the gas
arithmetic.<Cite src="eip-7928" /> A block-level access list is a different object with a different
purpose. It is not optional, not per-transaction, and not a gas hint. It is an **enforced record of
every account and storage location the block touched, plus the post-execution values**.

The motivation in the EIP is one sentence: transaction execution cannot be parallelised without
knowing in advance which addresses and storage slots will be
accessed.<Cite src="eip-7928" /> Per-transaction access lists exist and are not enforced, so a client
cannot rely on them.

The four things a BAL is claimed to enable:<Cite src="eip-7928" />

- Parallel disk reads and parallel transaction execution.
- Parallel post-state root calculation.
- State reconstruction without executing transactions.
- Execution time reduced to parallel IO plus parallel EVM.

### Where it lives, which is not where you would guess

```python
class Header:
    # Existing fields
    ...
    block_access_list_hash: Hash32 = keccak256(rlp.encode(block_access_list))
```

The header gains a hash.<Cite src="eip-7928" /> The list itself is **not in the block body**. The
execution layer stores BALs separately and transmits them as a field in the `ExecutionPayload` over
the engine API.<Cite src="eip-7928" />

That placement is worth pausing on, because it is a design decision with a visible cost and a clear
reason. Keeping the list out of the body means a header stays small and a client that does not want
the BAL need not carry it; putting the hash in the header means the list is still committed to and
still consensus-critical. The empty case is spelled out precisely — an empty BAL hashes to
`keccak256(rlp.encode([]))`, and the field itself is the empty RLP list
`0xc0`.<Cite src="eip-7928" />

The encoding follows one pattern throughout: address, then field, then block access index, then
change.<Cite src="eip-7928" />

```python
BlockAccessIndex = uint32  # 0 for pre-execution, 1..n for transactions, n+1 for post-execution

StorageChange = [BlockAccessIndex, StorageValue]
BalanceChange = [BlockAccessIndex, Balance]
NonceChange   = [BlockAccessIndex, Nonce]
CodeChange    = [BlockAccessIndex, Bytecode]

AccountChanges = [
    Address,
    List[SlotChanges],   # storage_changes
    List[StorageKey],    # storage_reads (read-only)
    List[BalanceChange],
    List[NonceChange],
    List[CodeChange],
]
```

Two things to notice. **Reads and writes are separated** — `storage_reads` is a bare list of keys with
no values, while `storage_changes` carries post-transaction values. And **the index space includes
slots 0 and n+1** for pre-execution and post-execution system work, so system-contract activity and
withdrawal recipients are inside the same structure as transaction
activity.<Cite src="eip-7928" />

### What must be in it, and one rule that will surprise you

The inclusion rules are long and worth skimming in the original, but three carry the design's
character:<Cite src="eip-7928" />

- Addresses accessed with **no state change** must still be present, with empty change lists. Touching
  is enough.
- Targets of `CALL`, `DELEGATECALL` and friends are included **even if the call reverts**, subject to
  the gas-validation rules.
- Entries from an EIP-2930 access list **must not** be included automatically. Only what was actually
  touched during execution is recorded.

That last rule is the one that catches people. The two mechanisms share a name and are semantically
opposite: EIP-2930 is a *declaration of intent* supplied by the sender before execution; EIP-7928 is a
*record of fact* produced by execution. Copying one into the other would corrupt the record with
things that never happened.

### The size bound, and where its constant comes from

BALs are bounded by the block gas limit rather than by a fixed item count:<Cite src="eip-7928" />

where `bal_items` is storage keys plus unique addresses. The reasoning behind 2000 is the interesting
part. The cheapest way to add an item to a BAL is a cold `SLOAD`, and the cold storage-read cost is
2100 — a figure this curriculum measured directly rather than taking from
memory.<Cite src="measured-gas-constants" /><Cite src="eip-7928" /> `ITEM_COST` is set *below* that
minimum on purpose, creating a buffer of roughly `block_gas_limit / 42000` extra items to absorb BAL
entries that consume no block gas at all: system-contract execution and withdrawal
recipients.<Cite src="eip-7928" />

A constant chosen to be deliberately wrong in a known direction, to leave room for the things outside
the accounting, is a good example of what specification reading gets you that a summary does not.

On actual size, the EIP reports an average around 72.4 KiB compressed at a 60 million gas limit, with
storage writes at about 29.2 KiB and storage reads about 18.7 KiB of that, and argues this is smaller
than current worst-case calldata blocks.<Cite src="eip-7928" /> Those are the EIP's own figures from
its own analysis, at its own stated gas limit — quote them with all three qualifiers attached or not
at all.

There is also a denial-of-service consideration with a neat shape. Because `storage_reads` entries are
not mapped to specific transaction indices, their validity can only be confirmed after executing
everything — so a malicious proposer could declare phantom reads that force clients into pointless
prefetching. The mitigation is a running feasibility check at transaction boundaries: remaining block
gas must be at least the number of not-yet-accessed declared reads times 2000, checked periodically,
allowing early rejection.<Cite src="eip-7928" />

## Why declaring access is what buys parallelism

Take the abstract claim apart, because "declared access enables parallelism" is repeated far more
often than it is explained.

To run two transactions concurrently you must know they do not conflict. Two transactions conflict if
one writes state the other reads or writes. On Ethereum today, the set of state a transaction touches
is discovered *by executing it* — the information you need to schedule is produced by the thing you
were trying to schedule.

A BAL breaks the circularity by supplying the information up front. Once you have it, you can:

**Fetch state in parallel before executing anything.** Disk reads are latency-bound and independent;
knowing every key in advance turns a serial chain of lookups into one batch.

**Schedule disjoint transactions across cores.** The EIP cites 60–80% of transactions accessing
disjoint storage slots, with the remaining 20–40% made parallelisable by the post-transaction state
diffs the BAL carries.<Cite src="eip-7928" />

**Compute the post-state root in parallel**, and **reconstruct state without executing**, because the
post-execution values are in the list.<Cite src="eip-7928" />

### The convergence worth noticing

This is the same structural insight Solana adopted at the start. [Sealevel](/c/sealevel)'s parallel runtime works
because every Solana transaction must declare the accounts it reads and writes, which lets the
scheduler group non-conflicting transactions and run them across
cores.<Cite src="solana-sealevel-note" />

Ethereum arrives at the same requirement about a decade later, and at a different granularity: per
block rather than per transaction, produced by execution rather than declared by the sender.

That difference in granularity is not cosmetic. Solana pushes the burden onto the developer, who must
know statically what an instruction touches — which constrains what programs can do. Ethereum's
version imposes nothing on the transaction author; the block producer records what happened. The cost
lands as block size and as work for the builder, and the benefit lands on every verifying node.

Two chains usually presented as opposite design choices reached the same requirement from opposite
ends. It is worth carrying, because it is a fact about the problem rather than about either chain:
**you cannot parallelise execution over shared mutable state without knowing the access set in
advance.** Every design that claims parallel execution has answered that question somehow, and asking
how is the fastest way to evaluate one.

A colleague argues: "We already have EIP-2930 access lists. If wallets just started attaching accurate
ones to every transaction, clients could parallelise today without a new EIP." Explain why this does
not work, in terms of what the client can rely on.

<Answer>
It fails on enforcement, on completeness, and on who produces the information.

**Enforcement.** EIP-2930 access lists are optional and not enforced — a transaction may declare a
list that is wrong, incomplete, or absent, and it executes anyway.<Cite src="eip-7928" /> A scheduler
that assumed a declared list was the complete access set would produce incorrect results whenever it
was not, and would have no way to detect this before executing. A BAL is validated against actual
execution, so a block whose list is wrong is invalid.

**Completeness.** Even a perfectly honest sender cannot always know what their transaction will touch.
Anything with dynamic dispatch, a call whose target depends on state, or a path that varies with
current prices has an access set the sender cannot compute in advance. The BAL is produced *by*
execution, so this problem does not arise.<Cite src="eip-7928" />

**Scope.** A per-transaction list says nothing about the block's system-level access: pre- and
post-execution system contract work and withdrawal recipients, which the BAL carries at indices 0 and
n+1.<Cite src="eip-7928" /> A client scheduling the whole block needs the whole block's access set.

**And the values.** Parallel state-root computation and executionless state reconstruction need the
post-execution *values*, not merely the keys. EIP-2930 has no values at
all.<Cite src="eip-7928" />

The general principle: a hint you cannot verify before you need it is not a hint you can schedule on.
Turning an optional declaration into an enforced record is the entire change, and it is why the
mechanism had to be at the block level, where a producer that already executed everything can attest
to what happened.
</Answer>
</Check>

## The part that got cut

Now the third list.

FOCIL — EIP-7805, fork-choice-enforced inclusion lists — is a censorship-resistance mechanism that
does not depend on who builds the block. A committee of validators each builds an inclusion list from
its own view of the mempool and gossips it; the next proposer's block must include those transactions;
and attesters vote only for blocks that satisfy the
constraint.<Cite src="eip-7805" /> The enforcement is in fork choice, which is why the name says so:
a block that ignores the lists does not become canonical.

The parameters are small. `IL_COMMITTEE_SIZE` is 16 and `MAX_BYTES_PER_INCLUSION_LIST` is 8,192 bytes
— eight kibibytes of RLP-encoded transactions per member.<Cite src="eip-7805" /> The design's stated
core properties are that it is committee-based rather than single-proposer (reducing bribery surface),
fork-choice enforced (so no actor can bypass it), same-slot rather than forward (so a transaction
submitted during slot N can be constrained into slot N+1's block), and conditionally enforcing —
blocks that are full, or where a listed transaction cannot validly be appended, are still
accepted.<Cite src="eip-7805" />

Its motivation is worth reading beside the previous lesson: it opens by observing that auctioning
block building to specialists led to a few sophisticated builders dominating block production, and a
deterioration of censorship resistance.<Cite src="eip-7805" /> FOCIL is the response to precisely the
problem ePBS does not address.

**And it was declined.** EIP-7805 appears under *Declined for Inclusion* in the Glamsterdam meta
EIP.<Cite src="eip-7773" /> The recorded reasoning is that combining enshrined PBS with inclusion
lists in one upgrade would create too much untested interaction at mainnet
scale.<Cite src="ethereum-pm" /> EIP-7732 itself notes it is fully compatible with fork-choice-enforced
inclusion lists — compatibility was never the issue; simultaneity
was.<Cite src="eip-7732" />

### Where it went, with primary evidence

The consensus-layer configuration carries a small, decisive piece of evidence about the destination.
Under a section heading naming the fork after Gloas:<Cite src="consensus-specs-mainnet-config-gloas" />

```yaml
# Heze
# 6667 basis points, ~67% of SLOT_DURATION_MS
INCLUSION_LIST_DUE_BPS: 6667
```

An inclusion-list deadline, defined, sitting under **Heze** — with `HEZE_FORK_EPOCH` set to the
far-future sentinel, exactly as `GLOAS_FORK_EPOCH` is.<Cite src="consensus-specs-mainnet-config-gloas" /> The
consensus-layer fork after Gloas is where the mechanism is being specified.

One caution about naming, and it is the kind of thing worth being pedantic about. Heze is the
*consensus-layer* codename from the specification repository. Community coverage pairs it with an
execution-layer codename for the same upgrade, and that pairing is inferred from ordering rather than
confirmed by a primary source.<Cite src="consensus-specs" /><Cite src="ethereum-pm" /> Use the
consensus-layer name, which you can read from a file, and say "the upgrade after Glamsterdam" for the
combined thing.

### The second declination, which almost nobody mentions

FOCIL is the famous cut. It was not the only one in its class.

EIP-7782 proposes reducing Ethereum's slot time from twelve seconds to six — halving on-chain latency
and epoch duration, doubling slot throughput while keeping block and blob sizes
unchanged.<Cite src="eip-7782" /> Its motivation list reads like a catalogue of everything people want
from the protocol: faster confirmations, faster finality, halved settlement delay for rollups, better
economics for liquidity providers through reduced loss-versus-rebalancing, and bandwidth smoothed
across more, smaller slots.<Cite src="eip-7782" /> Its own framing of the trade is sharp: increasing
block sizes beyond a certain point is impractical without substantial networking changes, whereas
decreasing slot time achieves a similar effect and improves the user experience at the same
time.<Cite src="eip-7782" />

It is in the declined list.<Cite src="eip-7773" />

Two large, popular, well-specified changes to how a slot works, in the same upgrade as a third large
change to how a slot works, and two of the three did not make it. That is the pattern, and it is more
informative than either individual decision. The scarce resource is not developer time or consensus
about value; it is **tolerance for untested interaction on mainnet**, and every large change consumes
the same pool of it.

Notice also how the previous lesson's observation about basis-point deadlines fits here. The
configuration now expresses every deadline as a fraction of `SLOT_DURATION_MS` rather than as a count
of seconds.<Cite src="consensus-specs-mainnet-config-gloas" /> A proposal to change slot duration would once
have required touching every deadline. It no longer does. Declining a change and making it cheaper to
revisit later are not contradictory acts.

## What else is actually in the upgrade

The two headliners get the coverage; the scheduled list has eighteen entries, and several of them will
touch your work sooner than ePBS
will.<Cite src="eip-7773" /> A tour of the ones with visible consequences, all read from the meta
EIP's own list at the retrieval date:

- **EIP-7688, forward compatible consensus data structures.** The retyping of beacon containers as
  progressive containers that you met inside `BeaconBlockBody` — it is why the Gloas container
  definitions carry annotations from more than one
  EIP.<Cite src="eip-7773" /><Cite src="consensus-specs-gloas-beacon-chain" />
- **EIP-7708, ETH transfers emit a log.** A change with a large blast radius for indexers and
  accounting: value movement becomes observable through the log pipeline rather than only through
  traces.<Cite src="eip-7773" />
- **EIP-8282, builder execution requests.** The predeploy contracts and request types that carry
  builder deposits and exits — the plumbing behind the builder registry from the earlier
  lesson.<Cite src="eip-7773" />
- **A cluster of gas-cost changes**, including reduced intrinsic transaction gas, increased access list
  cost, state-creation and state-access cost increases, and block gas accounting without
  refunds.<Cite src="eip-7773" /> Repricing is where the capacity argument gets settled in practice,
  and it is the least glamorous part of every upgrade.
- **EIP-8045, exclude slashed validators from proposing**, which shows up in the merged specification
  as a modification to how proposer indices are
  computed.<Cite src="eip-7773" /><Cite src="consensus-specs-gloas-beacon-chain" />

There is also a separate networking group — new `eth` protocol versions, one of them specifically for
exchanging block access lists, and a `snap` extension for BAL-based state healing — which is where the
BAL design turns into wire formats.<Cite src="eip-7773" />

The point of the tour is not the individual items. It is that "the Glamsterdam upgrade" is eighteen
scheduled changes plus a networking programme, of which two get named in headlines, and the
proportion of the upgrade you have heard about is small.

## Upgrade scoping, read from the record

FOCIL is not an anomaly. Look at what else is in that third list, at the retrieval date for this
lesson: EOF, the EVM Object Format meta; SSZ transactions and SSZ receipts; removing the bloom filter
and the trustless log index that would replace it; six-second slots; delayed execution; the `PAY`
opcode.<Cite src="eip-7773" />

Several of those had specifications, implementations, years of discussion and vocal support. All of
them are, for this upgrade, not happening.

Three lessons follow, and they are the practical core of this lesson.

**A merged EIP is not a shipped feature.** Merging an EIP means the proposal is correctly formatted
and assigned a number. Inclusion is decided separately, on [All Core Devs calls](/c/acd-process), then specified in
`consensus-specs` or `execution-specs`, then implemented by
clients.<Cite src="ethereum-pm" /><Cite src="consensus-specs" /> Every stage can reject.

**Scope shrinks as the date approaches, and the usual reason is interaction risk rather than merit.**
FOCIL was not cut for being a bad design; it was cut because its interaction with another large change
would be untested at mainnet scale.<Cite src="ethereum-pm" /> That is a reason that has nothing to do
with the proposal's quality, which is why "but it is a good idea" never predicts inclusion.

**The upgrade's own records are the only reliable list.** The meta EIP names what is scheduled,
declined and merely proposed; the All Core Devs notes record why; the specification repositories
record what has actually been written down.<Cite src="eip-7773" /><Cite src="ethereum-pm" /> Trackers
that aggregate this are useful for orientation and are a step removed from the
source.<Cite src="eipsinsight-upgrades" />

<Aside kind="note">
A three-line procedure for checking any upgrade claim, in order of authority. **One:** open the fork's
meta EIP and find which of the three lists the proposal is in. **Two:** open the configuration file in
the relevant specification repository and read the fork epoch — a far-future sentinel means
unscheduled, whatever anyone has announced.<Cite src="consensus-specs-mainnet-config-gloas" /> **Three:** if
the two disagree, or the proposal is not in either, go to the All Core Devs notes and find the call
where it was discussed.<Cite src="ethereum-pm" /> Anything you cannot resolve in those three places is
not yet a fact.
</Aside>

## How to read a change like this, mechanically

The habit this module has been practising is [worth writing down as a procedure](/c/reading-a-spec-change),
because it is the transferable part.

**Know which file answers which question.** The consensus specification splits into three kinds of
file and confusing them produces most of the wrong numbers in circulation. A **spec** file — say
`specs/gloas/beacon-chain.md` — holds the containers and the state transition functions. A **preset**
file holds values that are properties of the design and differ between mainnet and minimal test
configurations, like `PTC_SIZE`. A **config** file holds values that are properties of *this network*
and can change without a design change: fork epochs and the deadline basis
points.<Cite src="consensus-specs-mainnet-config-gloas" /> "Has it shipped" is a config question. "How big
is the committee" is a preset question. "What does the committee vote on" is a spec
question.<Cite src="consensus-specs-gloas-beacon-chain" />

**Pin the tag.** Every specification link in this module points at `v1.7.0-alpha.14` rather than at a
branch. Paths under an in-development branch are rewritten between one reading and the next, and a
lesson citing a moving path is citing nothing.<Cite src="consensus-specs" />

**Read the annotations.** Merged spec files mark each changed line with the fork and EIP responsible —
`# [Modified in Gloas:EIP7732]`, `# [New in Gloas:EIP7732]`. That is how you separate two independent
changes landing on the same container, and how you tell a rename from a new
field.<Cite src="consensus-specs-gloas-beacon-chain" />

**Prefer containers and code to prose.** You saw the note about where blob commitments live contradict
the container three screens above it. Prose in an in-development spec drifts; the executable
definitions are the thing clients implement.<Cite src="consensus-specs-gloas-beacon-chain" />

**Diff the EIP against the merged spec, and expect the EIP to be behind.** EIP-7732's container list
and the merged one differ in field membership; the EIP's rationale and the merged fork-choice rules
differ on a threshold.<Cite src="eip-7732" /><Cite src="consensus-specs-gloas-beacon-chain" /> Neither
is wrong; they are snapshots at different times. When they disagree, clients follow the specification.

**Then, and only then, read the commentary.** Secondary writing is good for motivation and for
noticing what changed; it is unreliable for constants, container shapes and
dates.<Cite src="eipsinsight-upgrades" />

## What this module leaves you with

Across nine lessons the module made one argument and then refused to overstate it.

**The argument.** Nearly every mainnet block is built by someone other than its proposer, the exchange
between them is escrowed by a handful of trusted services, and that escrow has failed in production in
ways that cost real money. EIP-7732 moves the exchange into the state transition: builders become
staked registry entries, the proposer commits to a bid rather than a payload, payment is enforced
independently of delivery, and a 512-seat committee votes on nothing but whether the payload
arrived.<Cite src="eip-7732" /><Cite src="consensus-specs-gloas-beacon-chain" />

**The refusals.** No activation date, because neither the meta EIP nor the configuration file carries
one.<Cite src="eip-7773" /><Cite src="consensus-specs-mainnet-config-gloas" /> No single figure for how much
the validation window widens, because the disagreement is about the baseline. No builder-concentration
percentage, because the published measurements name different firms. No claim that this decentralises
building, because it does not. And no pretence that the free option is solved, because the evidence is
a preliminary simulation and the mitigation would have to punish behaviour the honest builder guide
prescribes.<Cite src="eip-7732" /><Cite src="ethresearch-epbs-threads" />

What this unlocks is the ability to read an in-development protocol change the way its implementers
do: from the merged specification at a pinned tag, checking the EIP text against it, treating every
constant as a draft and every date as absent until a file says otherwise. That habit outlasts this
particular upgrade, which is fortunate, because by the time you need it the constants above will have
moved.
