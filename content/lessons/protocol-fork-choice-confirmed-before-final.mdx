A risk meeting, and a question nobody in the room can answer.

"How many blocks before we credit a deposit?" The answer is twelve. Twelve was chosen years ago by
someone who has left. Asked what twelve protects against, the room produces three incompatible
stories: it is roughly a minute, it is more than any reorg anyone remembers, and a competitor uses
twelve.

That is not a policy. It is a number with no adversary attached, and this lesson is about what
replaces it — not a better number, but a sentence you can defend.

## What a confirmation rule is, and what Ethereum has

Start with the definition, because it is more precise than the everyday use of the word.

A confirmation rule is an algorithm run by network nodes to determine whether a block will remain
permanently in the canonical chain.<Cite src="fc-fast-confirmation-paper" /> Not "probably". Not "after
enough blocks". An algorithm, run locally, that returns a decision — and whose guarantee is stated
along with the conditions under which it holds.

The only confirmation rule currently available in Gasper is FFG finalization, and while it tolerates
asynchronous network conditions, it is slow: in the best case a transaction takes 13 to 19 minutes to
confirm, depending on when it is submitted.<Cite src="fc-fast-confirmation-paper" /> That range comes
from the same structure as the 64-to-95-slot figure you met in lesson seven: a transaction submitted
early in an epoch waits longer for its checkpoint than one submitted late.<Cite src="3sf-paper" />

Everything else the industry uses — depth counting, "twelve blocks", "wait a minute" — is not a
confirmation rule under this definition. It is a heuristic whose guarantee has never been written
down, which is exactly why the room cannot state it.

## The fast confirmation rule, stated with its conditions

The Fast Confirmation Rule for Gasper, under synchrony and the assumptions stated in the paper,
achieves a best-case confirmation time of **12 seconds — a single slot** — which the authors describe as
an order-of-magnitude improvement over FFG
finalization.<Cite src="fc-fast-confirmation-paper" /> The paper is Saltini, Kalinin, Zanolini,
D'Amato, Asgaonkar and Zhang, first posted May 2024 with a revised version online in July
2026.<Cite src="fc-fast-confirmation-paper" />

Four properties of the design matter more than the headline number.

**It is complementary to finalization, not a replacement.** Users who trust synchrony obtain fast
confirmations, while finalization remains available as a fallback that tolerates
asynchrony.<Cite src="fc-fast-confirmation-paper" /> Both mechanisms run. You choose which guarantee
you are relying on, per decision.

**It advances monotonically.** Each newly confirmed block is a descendant of the previous one, so users
are never worse off than under finalization alone.<Cite src="fc-fast-confirmation-paper" /> The paper
proves safety — confirmed blocks remain canonical — and, under an additional assumption,
monotonicity.<Cite src="fc-fast-confirmation-paper" />

**It runs every slot, as a predicate over the data you already have.** The core is a per-block safety
predicate checking whether observed attestation support for a block exceeds a threshold ensuring no
other block can receive more support, applied to every block between the last confirmed block and the
candidate.<Cite src="fc-fast-confirmation-paper" /> That predicate accounts for the proposer boost, the
Byzantine stake bound, and equivocation evidence from slashed
validators<Cite src="fc-fast-confirmation-paper" /> — which is to say, it is built out of exactly the
three mechanisms this module has spent six lessons on.

**The hard part is the interaction with FFG, not the weight arithmetic.** The paper names it: the
checkpoint filter means a block with overwhelming weight support can still be removed from the
fork-choice tree, for instance if a conflicting checkpoint becomes justified at an epoch
boundary.<Cite src="fc-fast-confirmation-paper" /> You met that filter in lesson one as
`filter_block_tree`.<Cite src="fork-choice-spec" /> A confirmation argument therefore has to reason
jointly about LMD-GHOST weight comparisons and FFG justification dynamics — two layers operating on
different time scales under different fault-tolerance
thresholds.<Cite src="fc-fast-confirmation-paper" /> The rule handles it with additional predicates: one
checks whether justification of the current-epoch checkpoint can be guaranteed so the confirmed branch
survives the filter, another checks whether a conflicting checkpoint can still be justified — in which
case **confirmation is frozen** until the situation resolves — and at epoch boundaries a reconfirmation
step re-checks previously confirmed blocks, so the safety argument does not depend on synchrony having
held since an arbitrarily distant past.<Cite src="fc-fast-confirmation-paper" />

### The two assumptions, because using the rule means adopting them

This is the part a product team must read, and it is the part that makes the rule worth having.

**Assumption 1 — a static validator set.** The only change that can occur to the validator set and
effective balances is Byzantine validators potentially getting slashed: no new validator is ever added,
no rewards are incurred, and honest validators never exit or incur
penalties.<Cite src="fc-fast-confirmation-paper" /> That is an idealisation of the analysis window, not
a claim about the chain.

**Assumption 2 — a known adversarial bound.** There exists a constant β, **known to anyone using the
Confirmation Rule**, bounding the fraction of Byzantine validators in any set of consecutive committees
weighted by the relevant checkpoint.<Cite src="fc-fast-confirmation-paper" />

Read the emphasis in the paper's own phrasing. β is not a protocol parameter the network agrees on; it
is an input *you* supply, and the guarantee you receive is conditional on it. The paper is careful to
place the cost in context: any party relying on Gasper's finality guarantee already assumes a Byzantine
fraction below some bound at most 1/3.<Cite src="fc-fast-confirmation-paper" /> So the rule does not
introduce trust from nothing — it makes the parameter explicit and lets you choose it more
conservatively than the protocol's own.

The paper also argues why the bound over a short window is tighter than the global one: by the
Chernoff–Hoeffding inequality, with Ethereum's validator set of approximately one million and epoch
length 32, the probability that the local fraction is below the global bound minus a margin is
overwhelming even for moderate margins.<Cite src="fc-fast-confirmation-paper" /> A short window of
committees is a random sample from a very large set, and random samples of a very large set are close
to the mean.

<Aside kind="note">
Notice what a product actually gains here, because it is not primarily speed. It is the ability to
write a falsifiable sentence in a risk register: *we credit deposits on a rule that is proven safe
provided the Byzantine fraction over the relevant committees stays below β, and we have chosen β = X.*
A reviewer can argue about X. Nobody can argue about "twelve", because "twelve" makes no claim. The
confirmation rule's contribution is that it converts an unstated assumption into a stated parameter,
and it happens to be fast as well.
</Aside>

## The measured behaviour, with its provenance attached

The paper reports an empirical evaluation, and it is worth reproducing with every qualifier intact —
both because the numbers are useful and because this is the shape a performance claim should take.

**Workload and date.** Approximately 26 hours of Ethereum mainnet data starting from block 12,607,808,
17 September 2025.<Cite src="fc-fast-confirmation-paper" />

**Data source.** Attestations from two channels: the aggregate gossip topic as observed by Xatu sentry
nodes, and attestations included in blocks.<Cite src="fc-fast-confirmation-paper" />

**Result.** 94.67% of blocks were confirmed within a single slot, at most 12 seconds; 98.87% within two
slots, at most 24 seconds; and 100% within eight slots, at most 96
seconds.<Cite src="fc-fast-confirmation-paper" />

**What determines the tail.** Single-slot confirmation requires the fraction of committee weight not
attesting in support of the block to be below 1/20 = 5%; the paper attributes the roughly 5.33% of
blocks needing more than one slot to blocks with empty slots between themselves and their parents, or
to blocks sent late that did not accrue enough weight within one
slot.<Cite src="fc-fast-confirmation-paper" /> Note that the non-attesting fraction covers Byzantine
withholding, offline validators, and attestations that simply arrived after the
check.<Cite src="fc-fast-confirmation-paper" />

**And the limitation, stated by the authors.** During the observation period no adversary was employing
strategies aimed at delaying confirmation; a strategic adversary aware of the rule could withhold or
mistime attestations to increase confirmation latency up to the theoretical maximum, so the empirical
results do not capture the impact of adversarial strategies targeting the
rule.<Cite src="fc-fast-confirmation-paper" />

**The safety guarantee does not degrade with the delay.** It is identical whether confirmation occurs
in one slot or in several; only the latency experienced by users
changes.<Cite src="fc-fast-confirmation-paper" /> That is the property that makes it usable in a
product: an adversary targeting your confirmation rule makes you slower, not wrong.

## Is it available on the client you run?

There is no confirmation-rule endpoint in the consensus specification — the fork-choice spec defines
`get_head`, the proposer-reorg helpers and the store, and nothing about
confirmation.<Cite src="fork-choice-spec" /> This is a client feature, not a protocol one, so its
availability is a matter of implementation and configuration.

One concrete data point. Lighthouse merged an implementation of the fast confirmation rule on 13 July
2026, gated behind an `--enable-fast-confirmation` flag, with the author noting that the implementation
touches no production code path and that if it were incorrect it would affect only consumers of the
`safe` tag running with that flag.<Cite src="fc-lighthouse-confirmation-pr" /> The pull request also
records that it passes spec tests written by one of the rule's
authors.<Cite src="fc-lighthouse-confirmation-pr" />

Two things follow, and both are operational rather than theoretical.

**The delivery vehicle is the `safe` tag.** You know the
[unsafe / safe / finalized](/c/unsafe-safe-finalized) triple from the execution API. If a client wires
the confirmation rule to `safe`, that field means different things depending on which client you query
and how it was launched — which belongs in your infrastructure documentation, not in an assumption.

**Which release first carries it has to be read from your own client's notes.** A merge date is not a
version.<Cite src="fc-lighthouse-confirmation-pr" /> Check the tag your nodes actually run, and check
each client separately — nothing obliges two clients to expose the same rule under the same name.

the rate of attacks.<Cite src="ethereum-org-pos-attack-defense" />

each tier names the assumption it rests on — and the only thing wrong with twelve was never its value,
it was that it named nothing.

## What this unlocks

This closes the module, so the payoff is a way of reading and a way of deciding.

- **Every consensus guarantee comes with a precondition; find it before you use it.** Finality assumes
  a Byzantine bound and tolerates asynchrony. The confirmation rule assumes synchrony and a β you
  supply.<Cite src="fc-fast-confirmation-paper" /> Proposer boost assumes a proposer's timeliness is
  observed consistently.<Cite src="fork-choice-spec" /> None of them is unconditional, and the condition
  is the interesting part of each.
- **The three-tier shape generalises past deposits.** Reversible-and-instant, conditional-and-fast,
  unconditional-and-slow. Bridges, payment flows, liquidation engines and settlement rails all face the
  same choice, and picking a depth is a way of not making it.
- **You can now read a performance claim properly.** The paper's own numbers arrive with a workload, a
  starting block, a date, a data source and a stated limitation about
  adversaries.<Cite src="fc-fast-confirmation-paper" /> Any consensus latency figure lacking those is
  not comparable to any other, and this module's habit is to refuse to quote one that does.
- **The module's reflection prompt has a home now.** Proposer boost cannot be set to a value that
  prevents both ex-ante and ex-post reorgs; the shipped setting is
  40.<Cite src="fc-config-mainnet-v161" /> Which failure you would err towards is a question about who
  is harmed: an honest proposer losing a block it earned, or a user whose transaction lands in a block
  someone else takes. Both parties are real, and the current value picks one.
- **And the operational habit worth carrying out of the whole module.** When someone tells you what
  Ethereum's fork choice does, open `specs/phase0/fork-choice.md` at the tag your client targets and
  read the function.<Cite src="fork-choice-spec" /> Constants change, mitigations get replaced rather
  than accumulated, and several widely read explanations describe rules that no longer exist. The spec
  is short. Read it.
