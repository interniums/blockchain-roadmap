Here is the sentence the whole security story is built on, quoted rather than paraphrased because
every summary of it drops something:

> At each slot, a node advertising `custody_group_count` downloads a minimum of
> `sampling_size = max(SAMPLES_PER_SLOT, custody_group_count)` custody groups, selected by
> `groups = get_custody_groups(node_id, sampling_size)` […] The custody groups to custody […] are
> then in particular a subset of those to sample. Sampling is considered successful if the node
> manages to retrieve all selected columns.<Cite src="consensus-specs-fulu-das-core" />

Read it twice, because it says three things that the usual gloss — "each node samples eight random
columns per slot" — gets wrong.

The selection function is `get_custody_groups(node_id, …)`. That is the same deterministic function
from the previous lesson, seeded on the same node id. **A node's sample set does not change from slot
to slot.** Custody is a *subset* of the sample set, not a separate thing alongside it. And success is
all-or-nothing: retrieve every selected column or the slot's sampling failed.

You already did the probability arithmetic for DAS in Scaling — why extension turns a 93.75% attacker
success rate into roughly 1 in 370 at eight draws. This lesson is the other half: what the shipped
procedure actually is, what the number 8 is a bound *on*, and three substitutions that quietly change
what is being claimed.

## The procedure, unpacked

### Sampling is at least custody, and often exactly custody

`sampling_size = max(SAMPLES_PER_SLOT, custody_group_count)` with `SAMPLES_PER_SLOT` = 8 and
`CUSTODY_REQUIREMENT` = 4.<Cite src="consensus-specs-fulu-das-core" /><Cite src="consensus-specs-v161-mainnet-config" />
Work the cases:

| node | `custody_group_count` | `sampling_size` | groups sampled beyond custody |
| --- | --- | --- | --- |
| plain full node | 4 | 8 | 4 |
| node with validators, floor | 8 | 8 | **0** |
| node with 512 ETH attached | 16 | 16 | **0** |
| supernode | 128 | 128 | **0** |

The surplus exists only at the bottom. For every node with `custody_group_count` ≥ 8 — which is every
node with validators attached, since `VALIDATOR_CUSTODY_REQUIREMENT` is
8<Cite src="consensus-specs-fulu-validator" /> — the maximum is its own custody count, so the set it
samples *is* the set it custodies. "Sampling beyond custody" is a real activity for exactly one class
of node: the plain full node at the 4-group floor, which checks four groups it does not keep.

This is not a flaw; it is a consequence of what sampling is for. A node that already downloads and
retains a larger slice has, by downloading it, performed a stronger check than eight probes would
have been. But it changes how you should read the phrase "thousands of nodes sampling
independently" — a large share of them are not running an extra check at all, they are attesting on
the strength of their custody download.

The containment works because of the prefix property: increasing the count *extends* the returned
list rather than reshuffling it, so `get_custody_groups(node_id, 4)` is genuinely a subset of
`get_custody_groups(node_id, 8)`.<Cite src="consensus-specs-fulu-das-core" /> The spec's "in
particular a subset" is a statement about that function's construction, not a coincidence.

### The sample unit is a whole column, not a cell

EIP-7594 is explicit: PeerDAS defines a sample as a column — a cross-section across all blobs —
rather than a row, which would be a full blob.<Cite src="eip-7594" /> The das-core FAQ says how it is
fetched: in the one-dimensional construction, a node samples its peers by requesting the whole
`DataColumnSidecar`.<Cite src="consensus-specs-fulu-das-core" />

So "8 samples" is 8 column sidecars, each carrying one cell per blob in the block. At the config's
`MAX_BLOBS_PER_BLOCK` of 21, that is 8 × 21 = 168 cells and 168 proofs, not 8
cells.<Cite src="consensus-specs-v161-mainnet-config" /><Cite src="consensus-specs-fulu-preset" /> A
"sample" in PeerDAS is a few tens of kilobytes, and it grows with blob count like everything else.

Two numbers reconcile here and it is worth doing the reconciliation once. Eight of 128 columns is
1/16 of the *extended* matrix. The extended matrix is twice the original blob data. So a sampling
node moves 1/8 of the blob data — the figure EIP-7594 quotes for current
parameters,<Cite src="eip-7594" /> and the same arithmetic ethereum.org spells
out.<Cite src="ethereum-org-peerdas" /> If you ever see 1/16 and 1/8 quoted for the same thing,
neither is wrong; they are denominated differently.

### All the columns, or none of the value

Sampling is considered successful only if the node retrieves *all* selected
columns.<Cite src="consensus-specs-fulu-das-core" /> There is no "seven of eight, good enough".

That rule collapses two very different events into one outcome. A column can be missing because an
adversary is withholding it, or because the two peers you asked were slow, or busy, or had just
restarted. The node cannot tell the difference, and the specification does not ask it to. From the
availability check's point of view, an unresponsive peer and a withholding proposer produce the same
verdict.

This is what makes DAS a networking problem rather than a cryptography problem, and it is why the
peering strategy carries as much of the security weight as the sampling arithmetic does. EIP-7594
says so in the rationale: a focus on peers allows redundancy in the mechanism, which helps both
theoretical security and practical security of the implementation — if a single peer fails, a node
can likely use another peer for the same sampling task.<Cite src="eip-7594" />

## What eight samples is a bound on

### The per-node number, and why it is not the security claim

For a single node, the standard computation applies: an adversary who wants the data unrecoverable
must keep the network from assembling any 64 of 128 columns, so it can serve at most
63,<Cite src="consensus-specs-fulu-das-core" /> and a node whose eight columns all fall inside a
63-column served set is fooled. That is the arithmetic you worked in
[checking without downloading](/c/erasure-coding-for-da), and it lands near 1 in 370.

One in 370 is not a security parameter anybody would accept for a single machine's decision. It is
not meant to be. EIP-7594's security section states the real object: it bounds the probability of
convincing a **fraction ε of the nodes** that withheld data is available, as a product of three
terms — the number of ways to choose the nε nodes to be tricked, the number of ways to choose a
maximally large subset of samples to serve without allowing reconstruction, and the probability that
all chosen nodes' queries fall inside that subset.<Cite src="eip-7594" />

At one per cent the bound is 1 — the analysis rules out nothing. From two per cent it collapses
completely. So the precise claim is: **fooling a hundred nodes is not excluded; fooling a meaningful
fraction is astronomically unlikely.** EIP-7594 concludes from this table that PeerDAS is secure
against withholding attacks,<Cite src="eip-7594" /> and it is — for the property the table is about.

### Why the determinism makes that table matter more, not less

Here is where the shipped procedure and the security model have to be read together.

The bound counts "ways to choose the nε nodes to be tricked". If sample sets were freshly randomised
each slot, an attacker could not know in advance which nodes it was about to trick — it would choose a
column subset and see who happened to fall inside. Because sample sets are derived from node ids by a
public function,<Cite src="consensus-specs-fulu-das-core" /> the attacker can compute, before
producing the block, exactly which of the network's known nodes would be satisfied by any given
served subset, and pick the subset that maximises that count.

This is not a break, and it is important to be precise about why. The combinatorial bound already
takes the worst case over that choice — the second term is the number of ways to choose a maximally
large subset of samples to serve, and the first is the number of ways to choose which nodes to
satisfy.<Cite src="eip-7594" /> The analysis assumes the attacker chooses optimally. What determinism
removes is any *additional* safety margin from unpredictability, and what it adds is that the same
nodes are fooled every time rather than a fresh draw each slot.

EIP-7594 describes the scheme as a "(pseudo)randomized sampling
scheme".<Cite src="eip-7594" /> Hold both readings: pseudorandom **across** the node population,
fixed **for** each node. The parenthesis is carrying real weight.

### What the lever is worth, in one table

Because `sampling_size` follows `custody_group_count` one-for-one above 8, the per-node lever has a
computable payoff. An adversary keeping the block unrecoverable can serve at most 63
columns;<Cite src="consensus-specs-fulu-das-core" /> a node sampling *k* distinct columns is fooled
only if all *k* land inside that set, with probability C(63, k) / C(128, k):

Three readings, in order of usefulness.

**Sixty-four is qualitatively different.** A node sampling 64 distinct columns cannot be fooled at
all: 64 columns retrieved *is* the reconstruction threshold, so if its check passes it holds enough
to rebuild the matrix itself.<Cite src="consensus-specs-fulu-das-core" /> Above that line the
probabilistic argument stops being needed. A node with 2,048 ETH of attached effective balance sits
at 64 groups by the balance rule.<Cite src="consensus-specs-fulu-validator" />

**The floor of 4 is much weaker than 8, and that is why 8 exists.** A node checking only its four
custodied groups would be fooled roughly one time in eighteen. `SAMPLES_PER_SLOT` = 8 is the
protocol declining to let the minimum-custody node's check be that
weak.<Cite src="consensus-specs-fulu-das-core" />

**The rightmost column is the one the network cares about.** At 8 samples, an adversary serving a
*fixed, non-optimised* 63-column set fools about 27 of every 10,000 nodes — 0.27%, comfortably below
the ε = 0.01 row where EIP-7594's bound is
1.<Cite src="eip-7594" /> An adversary who *optimises* the served set against publicly derivable
sample sets does better than that, and how much better is precisely what the EIP's first two
combinatorial terms are there to bound.<Cite src="eip-7594" /> Do not read 27 as the answer; read it
as the floor.

### The substitution that is actually dangerous

Of the three, this is the one that shows up in design documents: treating "my node's samples passed"
as "the data is available".

The spec's own framing of the availability check is deliberately narrow, and the next lessons take it
apart. For now, hold the shape: eight successful column retrievals mean *the columns you asked for
were served to you*. They do not mean the block is recoverable, they do not mean any other node saw
anything, and they do not mean the data will still be reachable in an hour. A node acts on them
because the protocol only ever needed the fraction-level guarantee — each node's own vote is what its
own check feeds.

<Aside kind="note">
There is a fourth, smaller substitution worth flagging because it appears on a foundation page.
ethereum.org describes a default node as participating in at least 8 randomly chosen column subnets,
and receiving data from 8 of 128 subnets.<Cite src="ethereum-org-peerdas" /> The spec sets custody at
4 groups and sampling at 8, joins gossipsub subnets for *custodied* groups, and allows the request/
response protocol for columns not received on subnets — with the p2p spec also acknowledging
subscriptions taken on "additional
sampling".<Cite src="consensus-specs-fulu-das-core" /><Cite src="consensus-specs-fulu-p2p" /> Both
land on 8 groups' worth of data per slot; they differ on whether those 8 arrive by subscription or by
request, and the spec permits either. If you are sizing subnet load, use the spec's split, not the
summary's.
</Aside>

## Where the samples come from

The spec separates *which* columns to sample from *how* to get them, and the split matters for
anyone reasoning about load.

Custodied groups arrive by subscription. To custody the columns in a particular custody group, a node
joins the respective gossipsub subnets.<Cite src="consensus-specs-fulu-das-core" /> Those columns are
pushed to it as a side effect of block propagation; nothing is requested.

Columns that do not arrive that way are pulled. If a node fails to get columns on the column subnets,
it can use the request/response protocol to query the missing columns from other
peers.<Cite src="consensus-specs-fulu-das-core" /> For a minimum-custody node that is the four
sampled-but-not-custodied groups, plus anything its subscriptions dropped.

The p2p spec also acknowledges a third case in passing: a client may be subscribed to a subnet
"either due to custody requirements **or additional
sampling**".<Cite src="consensus-specs-fulu-p2p" /> So subscribing to sampled subnets is permitted
rather than mandated, and a node that does so trades steady inbound gossip for not having to make
requests under time pressure. That is a client policy decision, and it is one place where two
correct implementations will show different network profiles.

The consequence to carry into the deadline lesson: for the surplus groups, sampling is a
**request-response round trip to a peer that might not answer**, and the all-or-nothing rule means
one such peer failing costs the whole slot's check.<Cite src="consensus-specs-fulu-das-core" />

## What raises assurance, and what only looks like it does

**More samples per node: yes, in direct proportion to cost.** The lever is `custody_group_count`,
because `sampling_size` is `max(SAMPLES_PER_SLOT, custody_group_count)` and a node may advertise up
to 128.<Cite src="consensus-specs-fulu-das-core" /> Every extra group is one more column an attacker
must serve to keep this node fooled — and one more column of bandwidth and storage, permanently,
because the custody ratchet means you should not later reduce
it.<Cite src="consensus-specs-fulu-validator" />

**More nodes: yes, and this is the term the design actually leans on.** EIP-7594 puts it as a
property of the scheme: PeerDAS resolves withholding attacks with a randomised sampling scheme that
decreases the probability of a successful attack **as the size of the network grows**, for a
sublinear amount of data that must be downloaded.<Cite src="eip-7594" /> Population is the security
parameter.

**More peers per node: yes, but for a different reason.** Peers do not change the probability that a
withholder is detected. They change the probability that a *legitimately available* column is
retrieved before the deadline — which matters because the all-or-nothing rule turns a slow peer into
a failed check.<Cite src="consensus-specs-fulu-das-core" /><Cite src="eip-7594" />

**Sampling more often within a slot: no.** There is one sample set per node per slot and it is the
same set. Re-requesting the same columns from different peers is a retry, not an additional sample,
and it improves availability of the answer rather than the strength of the inference.

<Check type="explain" concept="das-security-argument">
A team is writing the threat model for a service that reacts to L2 state as soon as the batch's
availability check passes on their own node. Their draft says:

> Our node samples 8 of 128 columns each slot at random. The chance of being fooled by a withholding
> proposer is at most (1/2)⁸ ≈ 0.4%, and since sampling is re-randomised every slot, an attacker
> cannot target us specifically. Across the network's thousands of nodes the probability of a
> successful withholding attack is negligible.

Three of those four sentences are wrong or misleading. Identify them, and say what the threat model
should assert instead.

<Answer>
**Sentence 1 — "at random" is wrong.** The sample set is
`get_custody_groups(node_id, sampling_size)`, a deterministic function of the node
id.<Cite src="consensus-specs-fulu-das-core" /> Their node samples the same 8 groups every slot, and
has done since the key was generated.

**Sentence 2 — the bound is the wrong bound, and it is stated in the wrong direction.** (1/2)⁸ is the
loose form; the tighter per-node figure for 8 distinct columns drawn against a maximally-served
63-column set is about 1 in 370, roughly 0.27%.<Cite src="consensus-specs-fulu-das-core" /> More
importantly it is a bound on *this node being fooled*, which is a per-machine risk they are about to
act on, not a network-security property. For a service that triggers on its own node's verdict, the
per-node number is exactly the right one to worry about and 0.27% is not small.

**Sentence 3 — "an attacker cannot target us specifically" is exactly backwards.** Because the
derivation is public and their node id is in their ENR, an attacker can compute their sample set and
construct a withholding pattern that serves precisely those 8 columns and no more than 63 in total.
Targeting one known node is the *easy* case; EIP-7594's bound is trivially 1 at ε =
0.01.<Cite src="eip-7594" />

**Sentence 4 is the one that is right, and it is right about something else.** Network-wide, the
probability of convincing a meaningful fraction collapses fast — 10⁻²⁰·⁰⁴ at ε = 0.02 and 10⁻³⁰⁶·³⁴ at
ε = 0.05 for mainnet parameters at 10,000 nodes.<Cite src="eip-7594" /> The chain will not finalise
unavailable data. Their service, acting alone and early, is not protected by that.

**What the threat model should assert.**

*Distinguish the two guarantees explicitly.* "The network will not finalise a block whose data was
withheld" is strong and inherited. "Our node's local availability verdict at attestation time is
correct" is weak, per-node, and roughly 1-in-370 against an adversary willing to withhold — plus
whatever probability their peers simply failed to answer, since the all-or-nothing success rule does
not separate the two causes.<Cite src="consensus-specs-fulu-das-core" />

*Name the mitigation that actually applies.* If they need a stronger local verdict, the lever is
`custody_group_count`: raising it raises `sampling_size` one-for-one, up to 128, at linear cost and
subject to the ratchet.<Cite src="consensus-specs-fulu-das-core" /><Cite src="consensus-specs-fulu-validator" />
Running at 32 groups instead of 8 makes their node far more expensive to fool, and it is the only
lever they control.

*Or wait.* If the reason to act early is latency, the honest trade is stated as latency versus a
per-node probabilistic check — and waiting for justification, then finality, replaces a 1-in-370
local inference with a network-level guarantee. That is a product decision, and it should appear in
the threat model as one rather than as an assumption.
</Answer>
</Check>

## What this unlocks

You now know what a node does each slot, why the number 8 appears, and — the part most treatments
skip — that a node's eight are *its* eight, permanently, and that for anything above the minimum
custody floor sampling and custody are the same
download.<Cite src="consensus-specs-fulu-das-core" /><Cite src="consensus-specs-fulu-validator" />

**Next: what happens when the columns do not all arrive.** Sampling is a test, and a test that fails
does not fix anything. The repair mechanism is a threshold, a deliberately randomised delay, and an
obligation to republish what you rebuilt — and it is what makes partial withholding a bad attack
rather than merely a detectable one.

**Carry the all-or-nothing rule.** It is the single sentence that converts a cryptographic scheme into
a real-time networking deadline, which is where this module ends up.
