Every mechanism in this module funnels into eight lines of Python. Here they are, whole:

```python
def is_data_available(beacon_block_root: Root) -> bool:
    # `retrieve_column_sidecars` is implementation and context dependent, replacing
    # `retrieve_blobs_and_proofs`. For the given block root, it returns all column
    # sidecars to sample, or raises an exception if they are not available.
    # The p2p network does not guarantee sidecar retrieval outside of
    # `MIN_EPOCHS_FOR_DATA_COLUMN_SIDECARS_REQUESTS` epochs.
    column_sidecars = retrieve_column_sidecars(beacon_block_root)
    return all(
        verify_data_column_sidecar(column_sidecar)
        and verify_data_column_sidecar_kzg_proofs(column_sidecar)
        for column_sidecar in column_sidecars
    )
```

<Cite src="fulu-fork-choice" />

The whole of "Ethereum guarantees data availability", as [fork choice](/c/fork-choice-purpose) sees
it. It is worth reading slowly, because three separate things in it are narrower than the phrase they
implement.

## Three narrowings, in the order they matter

### It is over the columns *to sample*, not over the data

`retrieve_column_sidecars` returns "all column sidecars **to sample**" for the block
root.<Cite src="fulu-fork-choice" /> Not all sidecars. Not the blobs. The node's own sample set, which
from lesson five is `get_custody_groups(node_id, max(SAMPLES_PER_SLOT, custody_group_count))` — eight
groups at the minimum, out of 128.<Cite src="consensus-specs-fulu-das-core" />

So a passing check means: *the eight columns this particular node was going to ask for were obtained
and verified.* It does not mean the node has the block's data. At the minimum setting the node has
one-eighth of it and will keep one-sixteenth.

Compare what the same function meant before Fulu. The modification note in the spec says the only
change to `on_block` is that `is_data_available` no longer takes `blob_kzg_commitments` as
input.<Cite src="fulu-fork-choice" /> That input was the list of every blob the block committed to,
and the pre-Fulu check ran over all of them. Removing the parameter is the entire semantic shift,
expressed as a signature change: the function no longer needs to know what the block's full data was,
because it is no longer checking against it.

### It is a per-node conclusion, and the protocol knows that

Nothing in the function consults other nodes. There is no quorum, no aggregation, no threshold across
peers. Each node runs this against its own retrieved sidecars and gets its own answer.

That is deliberate and it is why the security argument in EIP-7594 is stated over a *fraction* of
nodes rather than over any individual one — the bound is on convincing a fraction ε, and at ε = 0.01
it is 1.<Cite src="eip-7594" /> The protocol never needed each node to be right. It needed most nodes
to be right, because what each node's check actually gates is that node's own vote.

### It verifies structure and proofs, not inclusion — that happened earlier

The two helpers named are `verify_data_column_sidecar` and
`verify_data_column_sidecar_kzg_proofs`.<Cite src="fulu-fork-choice" /> The binding of the
commitments to the block body — `verify_data_column_sidecar_inclusion_proof` — is a gossip validation
condition, applied on arrival, along with the proposer signature and the correct-subnet
check.<Cite src="consensus-specs-fulu-p2p" />

That layering is worth internalising: by the time fork choice asks, a sidecar has already been
established as belonging to this block by this proposer. The fork-choice check is asking a different
question — did I get them, and do the cells open correctly against the commitments.

## What fork choice does with a "no"

Here is the line in `on_block`:

```python
# [Modified in Fulu:EIP7594]
# Check if blob data is available
# If not, this payload MAY be queued and subsequently considered when blob data becomes available
assert is_data_available(hash_tree_root(block))
```

<Cite src="fulu-fork-choice" />

Read the comment as carefully as the code. A block failing the check is **not rejected as invalid**.
It MAY be queued and considered later, once the data turns up.<Cite src="fulu-fork-choice" /> The
assertion stops the block entering the store *now*; it does not brand it.

That distinction is the availability-finality dilemma showing up as an implementation detail. An
unavailable block is not provably bad — nobody can produce evidence that data does not exist, only
that they did not receive it. Punishing it would punish victims of a slow network, and rejecting it
permanently would let a transient failure fork the node off from a chain everyone else accepts.
Deferral is the only honest response, and it is what the spec chose.

Two consequences follow immediately.

**Availability failures are recoverable, and the repair mechanisms have somewhere to land.** A block
queued at second four can be accepted at second seven when a supernode's reconstruction and
cross-seeding put the missing columns back on the
wire.<Cite src="consensus-specs-fulu-das-core" /> The healing loop from lesson six is only useful
because fork choice defers rather than rejects.

**But the vote is already gone.** `on_block` computes timeliness *after* the availability assertion,
comparing the time into the slot against the attestation
deadline,<Cite src="fulu-fork-choice" /> and `ATTESTATION_DUE_BPS` is 3,333 bps of a 12,000 ms
slot.<Cite src="consensus-specs-v161-mainnet-config" /> A block that becomes available at second
seven cannot be timely and cannot receive proposer boost. It can still win the fork choice on
accumulated weight later; it has simply lost the head-vote race for its own slot.

## The boundary at eighteen days

The comment inside `is_data_available` carries the limit that ends the guarantee:

> The p2p network does not guarantee sidecar retrieval outside of
> `MIN_EPOCHS_FOR_DATA_COLUMN_SIDECARS_REQUESTS` epochs.<Cite src="fulu-fork-choice" />

That constant is 2¹² = 4,096 epochs, roughly 18
days.<Cite src="consensus-specs-fulu-p2p" /><Cite src="consensus-specs-v161-mainnet-config" /> The
validator spec states both halves of the obligation: a validator MUST hold sidecars for
`MIN_EPOCHS_FOR_DATA_COLUMN_SIDECARS_REQUESTS` epochs and serve when capable, to ensure the data
availability of these blobs throughout the network — and after that period, nodes MAY prune the
sidecars and/or stop serving them.<Cite src="consensus-specs-fulu-validator" />

Three things this settles.

**The availability check is a check on the recent window.** Outside `data_column_serve_range` there is
no retrieval guarantee to check against,<Cite src="consensus-specs-fulu-p2p" /> which is why a node
syncing history does not re-establish availability for every block it downloads. It accepts history
on the strength of a weak subjectivity checkpoint and the fork choice, not on the strength of a data
availability sample it can no longer perform.

**"Data availability layer" is not "data storage layer".** Ethereum guarantees a window during which
the data can be obtained. Anything beyond it is somebody running an archive — the rollup, a third
party, or you.

**The obligation is to *serve*, and it is bounded by capability.** "Serve when
capable"<Cite src="consensus-specs-fulu-validator" /> is not a promise of availability on demand; a
peer that cannot answer within `data_column_serve_range` should return `3: ResourceUnavailable` and
may be descored.<Cite src="consensus-specs-fulu-p2p" /> Descoring is the enforcement mechanism, and
descoring is not retrieval.

### What a syncing node has to do about it

The window has a second consequence that catches people bringing new nodes online.

A node bootstrapping from a recent weak subjectivity checkpoint has no column history at all. The
spec is direct about the obligation: nodes that start from a recent weak subjectivity checkpoint MUST
backfill the local data columns database to at least `data_column_serve_range` to be fully compliant
with `DataColumnSidecarsByRange` requests.<Cite src="consensus-specs-fulu-p2p" /> And while they have
not, other peers MAY disconnect or temporarily ban such an un-synced or semi-synced
client.<Cite src="consensus-specs-fulu-p2p" />

Meanwhile the node advertises where it stands. `earliest_available_slot` in `Status` v2 is the slot
from which it can serve,<Cite src="consensus-specs-fulu-p2p" /> and it may be lowered progressively
as a backfill advances.<Cite src="consensus-specs-fulu-validator" /> A node syncing is a node saying
"my window is shorter than the protocol's, and here is where it starts".

Two operational readings. **Bringing up a node is now a bandwidth event sized by the retention
window, not by the state.** Backfilling four custody groups across 131,072 slots is a fixed cost that
scales with blob capacity, and it is separate from state sync. **And a fleet rotated too aggressively
never leaves that state** — which is the concrete version of the objection to weekly key rotation
from lesson four, now visible in the peering rules rather than only in the custody derivation.

<Check type="explain" concept="is-data-available">
A team is designing the dispute path for a system that settles on an L2. Their design document says:

> Batch data is posted to Ethereum as blobs. Ethereum's consensus verifies data availability before
> finalising, so any party can reconstruct the batch from L1 and prove fraud. We therefore do not
> need to run our own data retention.

Take the three clauses in order and say what each one actually gets from the protocol. Then state
what the design needs that PeerDAS does not supply.

<Answer>
**Clause 1 — "posted to Ethereum as blobs" — is true and weaker than it sounds.** What is permanently
on Ethereum is the versioned hash of each blob's commitment. The blob bytes are not in the block, are
not in state, and are not readable by any contract.

**Clause 2 — "consensus verifies data availability before finalising" — is true of the network and
false of any node.** Each node runs `is_data_available` over *its own sample set* and gets its own
answer;<Cite src="fulu-fork-choice" /> the guarantee that emerges is statistical and stated over
fractions of the node population, with EIP-7594's own bound trivial at ε =
0.01.<Cite src="eip-7594" /> So the correct version is: the network will not finalise a block whose
data was withheld from most of it. That is genuinely strong. It is a statement about *the time of
finalisation*, not about the future.

**Clause 3 — "any party can reconstruct the batch from L1" — is the one that fails, and it fails in
two independent ways.**

*It expires.* Nodes must serve sidecars for 4,096 epochs, about eighteen days, and may prune
afterwards.<Cite src="consensus-specs-fulu-validator" /><Cite src="consensus-specs-fulu-p2p" /> A
dispute window longer than that — and most fraud-proof windows are seven days, so a delayed
challenge, a paused chain, or a governance timelock easily pushes past it — has no data behind it.

*It is a gather even inside the window.* No ordinary node holds any blob whole; recovering one row
needs 64 of its cells, which means collecting columns from many
peers.<Cite src="consensus-specs-fulu-das-core" /> "Any party can reconstruct" is true only of a
party that is peered into the network, running the right protocols, inside the window. It is not true
of a user with an RPC endpoint and a laptop, three months later.

**What the design needs that PeerDAS does not supply.**

*Retention past eighteen days*, from someone. The rollup, a dedicated archive, or the team. This is
exactly the "run our own data retention" the document says is unnecessary, and it is necessary.

*A retrieval path, not just an availability claim.* Availability sampling establishes that the data
*could* be assembled by the network during the slot. It does not hand anyone the bytes. The design
needs a named source with a stated retention period and a way to verify what it returns — and the
versioned hashes on L1 are exactly the right verifier, which is the part of clause 1 that is worth
keeping.

*A dispute window sized against the availability window, or explicitly decoupled from it.* If the
challenge period can outlast eighteen days, the design must state where the data comes from during
the overhang, and that source becomes a trust assumption in the system whether or not it is written
down as one.
</Answer>
</Check>

## What is still unsettled

Four things this module deliberately did not close, listed so you know they are open rather than
missing.

**The delay and give-up policies are client decisions.** The spec raises, as inline notes, both the
question of at what point a node considers samples missing and chooses to reconstruct and cross-seed,
and the anti-DoS and quality-of-service question of how samples are sent and
considered.<Cite src="consensus-specs-fulu-das-core" /> Behaviour will diverge across clients here
and will keep changing.

**The supernode population is unmeasured, here and in the spec.** "At least one" is the requirement;
"many (hundreds)" is the expectation.<Cite src="consensus-specs-fulu-p2p" /> Reconstruction margins
depend on the actual number, and the inputs are public in every ENR, so it is measurable by anyone
willing to crawl.

**The current blob cap is a moving target and this module quotes a dated reading.** The config read on
26 August 2026 lists `MAX_BLOBS_PER_BLOCK` 15 from epoch 412672 and 21 from epoch
419072.<Cite src="consensus-specs-v161-mainnet-config" /> Whether a further blob-parameter fork has
since been agreed is not something a checked-in file can tell you. Re-read the schedule before you
quote a number.

**Whether a blob's field elements are coefficients or evaluations has no current spec file behind
it.** The tagged spec says evaluation form in Lagrange basis; a widely-read foundation page says
coefficients; and both polynomial-commitments files are gone from master. Cite the tag, name the
convention.

None of these makes the mechanism uncertain. The constants are fixed, the functions are written, and
the thing has been running on mainnet since epoch
411392.<Cite src="consensus-specs-v161-mainnet-config" /> What is open is timing policy, network
composition and documentation — which is exactly the profile of a system that shipped recently and is
still being tuned.

## What this unlocks

You can now read the sentence "Ethereum guarantees the data was available" and decompose it without
hesitating: a per-node check over that node's sample set, deferring rather than rejecting on failure,
inside a window that ends after 4,096
epochs.<Cite src="fulu-fork-choice" /><Cite src="consensus-specs-fulu-validator" />

**The trade, stated once more in full.** Before PeerDAS, a node saying "the data is available" had
downloaded it. Now it means the node holds its custodied columns and its samples passed. That is
strictly less individual knowledge, bought deliberately, in exchange for capacity that a
download-everything rule could never have reached. The network as a whole knows more than it used to,
because there is more data in it; each participant knows less about any of it.

**Where to take this next.** Two directions are natural. Toward capacity: the next lever is the
column count, and EIP-7594 names it —
1/8 to 1/16 or 1/32 by increasing the number of columns,<Cite src="eip-7594" /> which is a preset
change with new cell sizes and a new transaction wrapper, not a blob-parameter fork. Toward timing:
the open notes in the spec about when a node considers samples missing and when it reconstructs are
where client behaviour is still being decided.<Cite src="consensus-specs-fulu-das-core" />

**And the question to carry into your own systems.** For each thing you build on blob data, write down
which of the three meanings of "published" you actually need — reconstructable by someone during the
slot, retrievable by you now, or retrievable by you in eighteen months — and which of them this
protocol gives you. It gives you the first, conditionally the second, and never the third.
