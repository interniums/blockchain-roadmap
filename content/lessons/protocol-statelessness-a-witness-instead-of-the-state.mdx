You have already produced a witness. Every time you called `eth_getProof`, the node handed you an
account's fields plus the sibling hashes along its path, and optionally the same for named storage
slots.<Cite src="eip-1186" /> Hand that response to somebody who has the state root and nothing
else, and they can check that those values were really in that state.

A block witness is that, for every state item a block touched, bundled with the block.

That is the entire idea, and it is old. What has never been true is that the bundle is small enough
to send. This lesson is about the bytes: what has to be in a witness, why the number is what it is,
and why four published worst-case figures spanning **18 MB to 1.8 GB** are not four readings of one
quantity.

## What a verifier is missing, precisely

Take a block with one transaction: account A sends 10 ETH to account B. To verify it you need A's
balance, to check the transfer and the fees. To verify it *without holding state*, you also need
proof that the balance you were handed is the one the parent block's state root committed to.

The Stateless Book makes the sharp version of the point. When a block arrives, the client cannot
predict which account will be A — so a stateful client must hold every account against the
possibility. But *given the block*, the state a verifier needs is orders of magnitude smaller than
the whole state.<Cite src="stateless-fyi-stateless-clients" /> The whole design is an exchange of
"be ready for anything" for "be told what you need".

So a witness has two parts, and it is worth keeping them separate because they behave completely
differently:

- **Values.** The actual contents of everything read or written: balances, nonces, code hashes,
  storage slots, executed code.
- **Proof material.** Whatever it takes to show each of those values was in the state committed by
  the parent's state root. In today's tree, that is the sibling hashes along every path.

Given the block and a valid witness, a verifier executes, computes the resulting state root, and
compares it to the header. It never held state. The Stateless Book calls such a client a **secure
light client**, and the distinction it draws from an ordinary light client is the whole point:
trustlessness, rather than believing whatever an external provider says the state
is.<Cite src="stateless-fyi-stateless-clients" />

<Aside kind="note">
**A stateless client is a smaller program, not just a lighter one.** The Stateless Book's
architecture sketch requires an EVM implementation, because the block must be executed, and a tree
implementation, because the new state root must be computed. The Engine API and the transaction pool
become partial or optional, and the rest of a full node is not strictly
required.<Cite src="stateless-fyi-stateless-clients" /> Fewer components is a maintainability
argument as much as a hardware one, and it is a large part of why client teams want this.
</Aside>

## Weak statelessness, which is the actual target

The pure form — nobody holds state — is not what anybody is building.

Somebody must hold state, because somebody has to build the block and produce the witness, and you
cannot produce a proof about state you do not have. The Stateless Book states this as a limitation
rather than a design goal: a stateless client cannot be a block builder, "since generating the proof
indirectly requires having access to the state".<Cite src="stateless-fyi-stateless-clients" />

What it *can* be is a validator. The book's argument is that many validators already delegate block
construction to external parties through MEV-Boost, so a stateless validator receives a candidate
block with its proof, verifies it, and proposes it.<Cite src="stateless-fyi-stateless-clients" />
You have already met the [role split](/c/pbs-problem) that makes this possible, which is why this
sentence lands so differently after the consensus track than before it.

That is **weak statelessness**: builders hold full state, everyone else verifies with witnesses. It
is worth being exact about what that buys and what it concedes. It does not eliminate the cost of
holding state. It relocates it onto the parties already specialising in block production — the same
parties the PBS literature already worries about concentrating. The book itself flags the
implications for network topology and security as an open research area rather than a solved
one.<Cite src="stateless-fyi-stateless-clients" />

## Everything the block reads must be in the tree

Before the size problem, there is a completeness problem: a witness can only prove things the state
root commits to. Anything a block reads that is not in the tree is a hole.

`BLOCKHASH` was exactly such a hole. Executing it needed the last 256 block hashes, which clients
kept outside the state tree, because a full node has the blockchain anyway. Proving one from the
chain instead would take up to 256 block headers, which the Stateless Book calls
prohibitive.<Cite src="stateless-fyi-blockhash" />

The fix arrived in two parts. **EIP-2935**, which is Final, has each block store the previous block
hash in a system contract, so the value is *available* from the state
tree.<Cite src="eip-2935" /> **EIP-7709**, which is Draft, then makes `BLOCKHASH` actually resolve
from the tree — a storage read, priced like one, from the EIP-2935 contract's
slots.<Cite src="eip-7709" /> The book notes the compatibility constraint: EIP-2935 stores 8191
historical hashes but `BLOCKHASH` still serves only the last 256, so older queries keep returning
zero rather than quietly starting to work.<Cite src="stateless-fyi-blockhash" />

Notice the pattern, because it is how a lot of statelessness work looks: a small, unglamorous EIP
that moves one input into the tree, shipped years before the thing that needs it.

## The size problem, and the code half of it

Now the bytes.

Two structural facts about today's tree make witnesses large, and they are separable.

**Arity.** The state trie is hexary. Proving a path means publishing up to fifteen sibling hashes at
every level. EIP-7864 gives the expected branch for a single item in a 2^32-element tree as
`15 * 32 * log_16(2^32)` = **3,840 bytes**.<Cite src="eip-7864" /> EIP-8297 gives it against the
observed shape instead: the account trie today reaches a maximum depth of about 12, so a branch at
that depth is `15 * 32 * 12` = **5,760 bytes**.<Cite src="eip-8297" />

**Code.** The tree commits to `keccak(code)`, not to code. To prove any single byte of a contract's
bytecode you must reveal the entire contract.<Cite src="stateless-fyi-trees" /> Dedaub puts the
consequence plainly: a 2,600-gas `CALL` against a 24 kB contract drags the whole bytecode into the
witness.<Cite src="dedaub-locality" /> Compare that against the cold-account-access cost of 2,600
gas measured on this project's own toolchain and the arithmetic is uncomfortable — 2,600 gas buys up
to 24 kB of witness.<Cite src="measured-gas-constants" /><Cite src="eip-2929" />

That is the asymmetry an adversary attacks. Not "make the block expensive to execute", but "make the
block expensive to *transmit* while paying execution prices".

### Enumerating one, by hand

Abstractions about "everything the block touched" are easy to nod at. Walk one transaction and the
inventory becomes concrete. Take a plain ERC-20 `transfer` from Alice to Bob.

**Subgoal: list the accounts whose headers get read.** The sender's account, for nonce and balance.
The token contract's account, because a `CALL` to it is a cold account access. The coinbase, because
fees land there. Three account paths, three sets of siblings.

**Subgoal: list the storage the EVM actually touches.** Alice's balance slot and Bob's balance slot
in the token's balances mapping. Both live at `keccak256(h(address) . p)`, so they are two unrelated
locations in the slot space with nothing between them — two independent paths from the storage root,
which itself hangs off the token account's leaf.<Cite src="dedaub-locality" />

**Subgoal: add the part that has no analogue in your gas intuition.** The token's bytecode. Under
today's tree the witness must carry all of it, because the commitment is over the whole thing and
the verifier has to run `transfer` — which means it must be able to check that the byte at the jump
destination really is a `JUMPDEST` and not a `PUSH` immediate, and that check needs the full code
for the analysis.<Cite src="stateless-fyi-data-encoding" /> An ERC-20's deployed code is commonly a
few kilobytes. That single item is usually larger than every hash in the witness put together.

**Subgoal: notice what is *not* in it.** No history. No receipts. No other account's anything. The
witness is exactly the slice this block read, which is why the average measured witness sits in the
hundreds of kilobytes while the state it is drawn from is hundreds of gigabytes.

**Subgoal: multiply.** A block is not one transfer. EIP-6800's bound assumes up to **6,000 state
accesses per block**, derived as 15M gas divided by 2,500 gas per access.<Cite src="eip-6800" /> Six
thousand paths, each dragging its siblings, plus a code reveal for every distinct contract entered.

That is the object that has to cross the network before the slot ends.

<Aside kind="note">
**Code chunking is the fix, and it needs a chunker with a strange requirement.** Both proposed trees
put chunked bytecode *in* the tree so a slice can be proved. The chunk boundary cannot be a simple
32-byte cut, because a verifier holding one chunk cannot tell whether its first byte is an opcode or
the tail of a `PUSH` immediate that began in the chunk before — and getting that wrong means
accepting an invalid `JUMP`. Both EIPs use 31 bytes of code plus one leading byte recording how many
of the chunk's opening bytes are PUSHDATA.<Cite src="eip-7864" /><Cite src="eip-8297" /> A whole
byte in thirty-two, spent on a problem that exists only because a verifier no longer sees the whole
program.
</Aside>

## Four worst-case numbers, and why they are four different quantities

Here is where the discipline this module needs starts. Every one of these figures is published, each
by people who did the arithmetic, and averaging them or watching them as a trend would be a mistake.

| Figure | What it assumes | Source |
|---|---|---|
| ~**18 MB** per block | 15M gas, 6,000 accesses at 2,500 gas each, average ~3 kB account witness | EIP-6800, 2023<Cite src="eip-6800" /> |
| ~**330 MB** per block | 30M gas spent touching one byte each of distinct unchunked account codes, 24 kB code limit | EIP-7864, 2025<Cite src="eip-7864" /> |
| ~**1.8 GB** per block | 60M gas, depth-12 branches, 64 KiB code limit | EIP-8297, 2026<Cite src="eip-8297" /> |
| ~**3 kB** average, worst case ~3× | One account witness, hexary trie | EIP-6800, 2023<Cite src="eip-6800" /> |

**Subgoal: separate the terms that moved.** Between the first and third rows the gas limit doubled
twice (15M → 30M → 60M), the assumed per-access price fell from 2,500 to 2,400 — the latter being
the EIP-2930 access-list address cost rather than the 2,600 cold access
cost<Cite src="eip-8297" /><Cite src="eip-2930" /> — and the code size limit in the calculation went
from 24 kB to 64 KiB.

**Subgoal: check the code-limit term is even live.** That 64 KiB comes from EIP-7954, which raises
the contract code limit from 24 KiB to 64 KiB and the initcode limit from 48 KiB to 128 KiB. It is
in **Review** status, not shipped.<Cite src="eip-7954" /> So the 1.8 GB figure is a worst case
against a *proposed* limit, computed to argue for a design. Read as "the problem got a hundred times
worse in three years", it is nonsense. Read as "here is the bound under the parameters we expect to
be defending against", it is exactly right.

**Subgoal: notice the term that did not move.** All three are dominated by code. Take the code term
out of EIP-7864's expression and you are left with `30M/2400 * 5*480` — the branch material — which
is roughly 30 MB against 330 MB total.<Cite src="eip-7864" /> Ninety percent of the worst case is
bytecode that had to be published whole because the tree cannot commit to a slice of it.

## The measured witness, which is the number nobody quotes

Worst cases argue for designs. What a network actually carries is an average, and there is exactly
one place in this material where someone measured it.

The Stateless Consensus team replayed **~200k historical blocks around the Shanghai fork** with a
Verkle tree in place, tried four witness encodings, and published sizes for the blocks produced
after the whole state was converted — about 134k blocks, with the conversion blocks
skipped.<Cite src="stateless-fyi-verkle-replay" />

| Encoding | Median | Max |
|---|---|---|
| type 1 | 425 KB | 1,285 KB |
| type 2 | 383 KB | 928 KB |
| type 3 | 380 KB | 928 KB |

<Cite src="stateless-fyi-verkle-replay" />

The spec's own encoding — type 0, using an SSZ `Optional[T]` — was so much worse than the others
that it was dropped from the rest of the analysis.<Cite src="stateless-fyi-verkle-replay" /> Which
is worth a beat on its own: a serialisation choice, not a cryptographic one, was the largest single
effect anyone measured here.

Then the breakdown, averaged over those ~134k blocks, for the best encoding:<Cite src="stateless-fyi-verkle-replay" />

**Read the first and third rows together.** The cryptographic proof — the part a better commitment
scheme shrinks — is about **12%** of the witness on average. The *values*, which no commitment
scheme touches, are about **78%**.

This is the single most load-bearing fact in the module, and almost nothing written about
statelessness says it. The tree change does not shrink witnesses by an order of magnitude in
practice, because the thing it shrinks was never the majority of the bytes. What it does is remove
the *worst case* — the code-reveal cliff and the sibling blowup — and make the remaining cost
proportional to what a block actually touched.

<Aside kind="note">
**The fourth row is a design note, not a rounding error.** Post-state values average 0.1% but reach
47% in the worst case. The team's own takeaway is that they should probably be removed entirely,
since validating them requires executing the block
anyway.<Cite src="stateless-fyi-verkle-replay" /> That is a good example of what measurement buys
over reasoning: nobody would have prioritised a field that is one part in a thousand on average.
</Aside>

## Why it has to fit inside a slot

A witness is not merely large, it is large *on a deadline*. It has to reach every verifier inside
the same seconds that are already carrying the block, the blob data columns, and the sampling
traffic. You have met that budget from the [data-availability side](/c/das-timebound); this is the
same seconds, spent again.

EIP-6800 puts the constraint in one sentence: ~18 MB "is too large to safely broadcast through a p2p
network within a 12-second slot".<Cite src="eip-6800" /> Note the two conditions welded together —
a size *and* an interval. Either one alone is meaningless.

This is why the ordering of work in this module is what it is. Statelessness is not blocked on
cryptography, or on client architecture, or on anybody being convinced. It is blocked on bytes
arriving in time. **The state commitment has to change before statelessness is possible, because the
tree shape is the size and the size is the blocker.**

## Gas has to change too, and for a reason worth stating

One consequence follows immediately and catches people out. Once a block carries a witness, every
state access a transaction makes adds bytes that the whole network must transmit — so gas has to
price witness growth, or an attacker constructs a transaction whose witness saturates the network
without paying for the bandwidth.<Cite src="dedaub-locality" />

EIP-4762 is the proposal that does it, and its constants make the model visible: `WITNESS_BRANCH_COST`
1,900 charged the first time a transaction touches a group, `WITNESS_CHUNK_COST` 200 for the first
touch of a leaf inside a group already paid for, and edit-side costs of 3,000, 500 and 6,200 for
first write to a group, first write to a leaf, and writing a previously-empty
leaf.<Cite src="eip-4762" />

Compose the read side and the shape appears: **1,900 + 200 = 2,100** for the first read in a fresh
group, which is deliberately comparable to today's cold storage read; **200** for a different leaf
in a group you already paid for; and **nothing further** at the witness layer for re-reading a leaf
you already have.<Cite src="dedaub-locality" /><Cite src="eip-4762" /> Against the measured cold
`SLOAD` of 2,100 gas, that first figure is a match by
construction.<Cite src="measured-gas-constants" />

The part with no analogue today is code. Under EIP-2929, once you have paid for the `CALL`,
executing bytecode is free. Under a witness model, every 31-byte code chunk the EVM enters is a leaf
that has to be proved and therefore paid for.<Cite src="dedaub-locality" /> Lesson five is about
what that does to code people have already deployed.

There is a second-order effect here that is easy to miss and matters for how you read the rest of
this module. Once gas prices witness bytes, the gas limit and the witness size stop being
independent quantities: raising the limit raises the bound on the witness, and every worst-case
figure in the table above has a gas limit as one of its terms. The Stateless Book states the causal
direction explicitly — the IO bottleneck is the principal hindrance to raising the gas limit, and
removing the requirement to hold state is what decouples verification cost from
it.<Cite src="stateless-fyi-intro" /> Statelessness is pitched as a decentralisation measure, and it
is, but the argument that gets it prioritised is throughput.

And one nearer-term relative deserves a name, because it does something adjacent without changing
anything about the tree. **EIP-7928** has a block declare, up front, every account and storage
location it will touch along with post-execution values — which lets clients read state in parallel
and validate transactions in parallel.<Cite src="eip-7928" /> That is not a witness: it carries no
proof material and a verifier still needs the state to check it. But it is the same insight arriving
by a cheaper route — say what you will touch — and the last lesson in this module shows the state
tree's own migration design has been written to ride on it.

<Answer>
**What it buys: less than the pitch implies, and against the wrong term.**

On the measured Verkle replay, proof material averaged about 12% of a witness and keys about 13%,
while raw values averaged about 78%.<Cite src="stateless-fyi-verkle-replay" /> Sibling hashes are
uniformly-distributed 32-byte digests, which is the least compressible data there is; and hexary
witnesses carry more of them, so the share is larger than 12% here — but the values are still the
majority and they are the balances and slot contents the verifier must actually receive. Compressing
the compressible quarter of the smaller half is a single-digit-percentage win.

**Cross-block dictionaries do not survive contact with the delivery model.** A verifier must be able
to check a block from the block plus its witness. A dictionary built from previous blocks is state —
smaller state, but state — and a verifier that must hold it to decode is no longer stateless. It is
also a synchronisation liability: a node that missed the block your dictionary was primed from
cannot decode yours.

**What it does not fix, and this is the decisive part.** Roughly 90% of EIP-7864's worst case is
bytecode revealed in full, because the tree commits only to `keccak(code)` and there is no way to
prove a slice.<Cite src="eip-7864" /><Cite src="stateless-fyi-trees" /> No encoder helps: an
adversary picks contracts with high-entropy code and pays 2,600 gas per cold account access to drag
each one in whole.<Cite src="measured-gas-constants" /> The fix is structural — put chunked code in
the tree so a slice can be proved — and that is a tree change, not an encoding change.

**The honest concession.** Encoding is not nothing, and the same replay proves it: switching from
the spec's `Optional[T]` encoding to a grouped one was the largest single effect measured, and the
best encoding beat the next by a further 357 KB at the
maximum.<Cite src="stateless-fyi-verkle-replay" /> Worth doing. Not a substitute for the tree.
</Answer>

## What this unlocks

**The next lesson** answers the question this one leaves open: if the tree has to change, change it
to what? The answer for roughly four years was Verkle trees, and understanding why they were the
obvious answer is what makes their cancellation comprehensible rather than arbitrary.

**Lesson five** takes the gas model seriously. Once locality is priced, storage layout stops being
a style question and becomes a cost decision, with measured consequences for contracts already
deployed.

**In diligence on any "we made it succinct" claim**, the transferable move is the breakdown table.
Ask what fraction of the object the succinct part actually is. A 10× improvement on 12% of the bytes
is an 11% improvement, and the person quoting the 10× is usually not being dishonest — they are
quoting the term they worked on.

**And when you meet a worst-case number**, ask for its four parameters before you compare it to
anything: the gas limit, the assumed per-access price, the size limit on whatever gets revealed
whole, and the year. Three published figures in this lesson differ by two orders of magnitude and
every one of them is correct.
