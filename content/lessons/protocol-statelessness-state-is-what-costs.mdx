Two proposals, both of which get summarised in a newsletter as "Ethereum stops keeping old data
around".

The first bounds how much chain history an execution client is required to serve. It has a number,
EIP-4444, it has been discussed since 2021, and its direction is broadly settled.<Cite src="eip-4444" />

The second makes state nobody has touched for a period stop counting as active state until somebody
revives it. It has been proposed repeatedly since before 2018, it has never been assigned to a fork,
and the version with a number attached is marked Stagnant.<Cite src="eip-7736" />

They are not two speeds of the same idea. They address different data, with different access
patterns, sitting in different parts of a node's database, and only one of them is the reason your
node needs the disk it needs. This lesson makes that split precise and then puts real numbers on the
half that matters, because every proposal in this module — witnesses, binary trees, expiry,
real-time proving — exists as a response to those numbers.

## What state actually is, counted

State is the set of all accounts, plus every contract's storage. Per account: balance, nonce, code
hash, storage root. Per contract: its storage, which today lives in
[its own trie](/c/per-account-storage-trie) hanging off the account record. The state root in the
block header commits to all of it, and holding it is what lets a node execute the next block.

You have met that structure. What you probably have not met is its shape at mainnet scale. The
Stateless Consensus team publishes a static analysis of mainnet state at **block 22284325**, around
16 April 2025:<Cite src="stateless-fyi-tree-shape" />

Two of the distributions in that same analysis are more instructive than the totals. Code length has
an **average of 676 bytes and a median of 45**, with a 99th percentile of 11,293 and a maximum of
24,576 — the old contract size limit, sitting exactly where you would expect a limit to
sit.<Cite src="stateless-fyi-tree-shape" /> Storage slots per contract have an **average of 26 and a
median of zero**, a 99th percentile of 47, and a maximum of
**68,794,129**.<Cite src="stateless-fyi-tree-shape" />

Read that median. Half of all contracts on Ethereum have no storage at all. The average is dragged
to 26 by a tail, and the tail's far end is one contract holding nearly 69 million slots. State is
not 288 million evenly-sized things; it is a very large number of tiny things and a small number of
enormous ones, which is precisely the distribution that makes capacity planning and gas pricing
hard.

<Aside kind="note">
**Why "hundreds of gigabytes" is the honest unit.** EIP-8037 reports that as of **January 2026**,
the database a Geth node dedicates to state was **~390 GiB**.<Cite src="eip-8037" /> The Stateless
Book, writing about conversion, uses **~300 GiB**.<Cite src="stateless-fyi-state-conversion" />
EIP-8347 budgets **~300 GB** of extra disk for a node holding two trees at
once.<Cite src="eip-8347" /> These are not contradictions: they are different dates, different
clients, different database layouts, and in one case GiB against GB. Carry the order of magnitude
and the date it came from, never a single figure with no provenance.
</Aside>

## The split that changes every conclusion

**History** is the record of what happened: old blocks, old receipts, old transactions. It is
append-only. It is read sequentially, if it is read at all. Nothing in it is needed to execute the
next block — you need it to answer questions about the past, which is what an archive node and an
indexer are for. EIP-4444 is about bounding how long execution clients are obliged to serve
it.<Cite src="eip-4444" />

**State** is what is true now: balances, nonces, code, storage. It is random-access. Every one of
those 288 million accounts is a candidate for the next transaction, and a node cannot know in
advance which. It must be able to answer for any of them, immediately, before the slot ends.

That difference in access pattern is the whole story of node cost. Sequential reads are what cheap
disks are good at. Random reads across hundreds of gigabytes are what they are worst at, and the
gap widens as the working set stops fitting in page cache.

**And the randomness is manufactured, not incidental.** Solidity places a mapping's values at
`keccak256(h(key) . p)`, which spreads two adjacent users' balances uniformly across the slot
address space by construction. The same analysis that gives the account counts finds the
consequence: grouping mainnet state into the 256-value groups both proposed trees use, **about 92%
of storage-slot groups hold exactly one non-zero value**, which is about **71% of all groups** —
and it attributes that directly to Solidity mapping usage.<Cite src="stateless-fyi-tree-shape" />
Nearly three quarters of the tree's leaf-level groups exist to hold a single 32-byte word, in a
location chosen by a hash function specifically so that nothing near it is related. That is not a
storage layout anyone would design for a disk. It is what falls out of pricing every slot the same
regardless of where it lands, which is the thread lesson five picks up.

### The shape of the tree is part of the cost

One more property of today's state belongs here, because three later lessons turn on it.

Ethereum's state commitment is not one structure. It is an account trie whose leaves each carry a
`storageRoot`, and hanging off each of those roots is that contract's own storage trie. Reaching one
storage slot means descending one trie to find the account and a second to find the slot. The
Stateless Book calls this a "tree of trees", and EIP-7864 lists it among the reasons the current
design is unfriendly to validity proofs, alongside RLP encoding and
Keccak.<Cite src="stateless-fyi-trees" /><Cite src="eip-7864" />

The second property is about code. The account trie stores only `keccak(code)`, not the code itself.
That keeps 32 GB of bytecode out of the tree, which is a real saving — and it means that proving one
byte of a contract's code requires producing **all** of it, because the only commitment available is
over the whole thing.<Cite src="stateless-fyi-trees" /> A node that holds the state does not care;
it has the code. A verifier that holds nothing cares enormously, and the next lesson is where that
bill arrives.

Neither property is a bug. Both were reasonable given what clients did in 2015. Hexary branching was
chosen to make the tree shallow, because disk lookups cost more than hashing — and clients have
since moved to flat key-value storage in which intermediate nodes are recomputed rather than stored,
which removes most of the benefit that justified the choice.<Cite src="eip-3102" /> That pattern —
a design decision that was correct against a client architecture that no longer exists — is worth
naming now, because it recurs three more times in this module.

## Monotonic is the word that matters

State grows with every new account and every newly-written storage slot. It shrinks almost never.

The mechanisms that could shrink it have been narrowed deliberately. `SELFDESTRUCT` no longer erases
a contract's code and storage unless the contract was created in the same
transaction.<Cite src="eip-6780" /> Clearing a storage slot to zero does remove its leaf — in the
current tree and in both proposed replacements, zero and absent are the same
state<Cite src="eip-8297" /> — but the slot is written once, cleared once, and the account, the code
and the contract's other slots stay.

The measured growth rate is where this stops being abstract. EIP-8037 reports that after the block
gas limit rose from 30M to 60M, the average size of new state created each day **more than tripled,
from ~105 MiB to ~326 MiB**, an annual rate of **~116 GiB**.<Cite src="eip-8037" />

Sit with the shape of that. A 2× increase in gas limit produced roughly a 3× increase in daily state
creation. The EIP says so explicitly and declines to treat it as a steady-state ratio, reading it
instead as a one-off shift in user behaviour.<Cite src="eip-8037" /> It then extrapolates
proportionally to a 200M gas limit and gets **~387 GiB per year**, which starting from 390 GiB would
cross a **650 GiB** threshold in under a year.<Cite src="eip-8037" />

That 650 GiB figure is not arbitrary. It comes from BloatNet, a dedicated test network for
stress-testing Ethereum under state growth, which identified a critical threshold around **650 GB**
past which memory consumption grows exponentially, validator performance degrades significantly, and
state access times increase by **40%**.<Cite src="stateless-fyi-active-projects" />

<Aside kind="warn">
**Two numbers, one project, and they do not match.** The Stateless Book's summary of EIP-8037 says
it targets an average state growth of **100 GiB/year**.<Cite src="stateless-fyi-active-projects" />
The EIP's own abstract says it introduces a cost-per-state-byte variable "targeting an average state
growth of **120 GiB per year** at a reference block gas limit of 150M gas
units".<Cite src="eip-8037" /> A summary page and the document it summarises, both current, one of
them out of date. When a number matters, read the spec.
</Aside>

## The gas schedule is the load-bearing part

State growth is a pricing failure before it is an engineering problem. Every new account and every
new slot is created by somebody who paid gas for it — and then imposes a cost on every node, for
ever, that nobody pays again.

The prices are legible. Measured on this project's own toolchain, forge 1.7.1 with solc 0.8.36 and
the optimizer off, a **cold SLOAD costs 2100 gas** and a **warm one 100**; a cold account access via
`BALANCE` or `EXTCODESIZE` costs **2600**, warm **100**; an `SSTORE` writing zero to non-zero costs
**20000** and non-zero to non-zero **2900**, each plus 2100 when the slot is
cold.<Cite src="measured-gas-constants" /> Those access constants are EIP-2929's, set in the Berlin
fork.<Cite src="eip-2929" />

EIP-8038 makes the argument bluntly: EIP-2929 landed in Berlin in **March 2021**, and the state has
grown significantly since, degrading the performance of exactly the operations that EIP priced.
Its benchmarks were run on a snapshot the size of mainnet in **March 2026** against a performance
target of **100 Mgas/s**, up from a stated current **20 Mgas/s**.<Cite src="eip-8038" />

Its proposed repricing is worth reading as a diagnosis rather than as a table of numbers, because
what moves tells you where the mispricing is:<Cite src="eip-8038" />

| Parameter | Current | Proposed | Change |
|---|---|---|---|
| `COLD_ACCOUNT_ACCESS` | 2,600 | 3,000 | +15% |
| `COLD_STORAGE_ACCESS` | 2,100 | 2,100 | 0% |
| `WARM_ACCESS` | 100 | 100 | 0% |
| `ACCOUNT_WRITE` | 6,700 | 9,000 | +34% |
| `STORAGE_WRITE` | 2,800 | 10,000 | +257% |
| `CREATE_ACCESS` | 7,000 | 12,000 | +71% |

Read that "current" column carefully: only the first three rows are constants the EVM charges today.
The other three are EIP-8038's own *decomposition* of costs that the existing schedule fuses into
composites — `ACCOUNT_WRITE` is pulled out of `CALL_VALUE`, `STORAGE_WRITE` out of `SSTORE`'s reset
cost, `CREATE_ACCESS` out of `CREATE` — so those figures are the EIP's arithmetic on today's
schedule, not opcode prices you can measure.<Cite src="eip-8038" /> The measurable ones agree:
2,100, 2,600 and 100 are exactly what this project's own harness records for cold storage access,
cold account access and a warm touch.<Cite src="measured-gas-constants" />

Reading costs barely move. **Writing costs move enormously.** The proposal decomposes state-touching
operations into three independent components — access, write, and state creation — and puts the
increases on the last two.<Cite src="eip-8038" /> Its companion EIP-8037 does the state-creation
half, observing that contract deployment costs about **200 gas per new byte** while new storage
slots cost about **313 gas per new byte**, for the same permanent
obligation.<Cite src="eip-8037" />

Both are in Review status and neither is assigned to a fork. What they are, right now, is the
clearest available statement of where the current gas schedule and the current state disagree.

<Answer>
**Right:** history is genuinely bounded work with a known direction of travel, and pruning it is a
real, one-time saving on the sequential half of the database.<Cite src="eip-4444" />

**Wrong:** the plan sizes the box against the half that stops growing and ignores the half that does
not. State is what must be held to execute the next block, it is random-access, and it grows
monotonically. As of January 2026 the state portion of a Geth database was reported at ~390 GiB,
growing at roughly 116 GiB/year at a 60M gas limit — a rate that itself tripled when the limit
doubled.<Cite src="eip-8037" /> A box sized with no state headroom is a box that has to be replaced
on a schedule set by other people's storage writes.

**And wrong in a second way:** the failure mode is not "disk full". BloatNet's finding is that past
roughly 650 GB, memory consumption grows exponentially, validator performance degrades and state
access times rise about 40%.<Cite src="stateless-fyi-active-projects" /> The node gets slow and
starts missing duties before it runs out of space, which is a much harder incident to diagnose.

**The measurement:** not free disk. Measure the state directory specifically, separated from history
and from the consensus client, and record its growth rate over a few weeks. That gives you a date
rather than a percentage — the date on which this box stops being adequate — which is the only form
of the answer a capacity plan can use.
</Answer>

## Why this is the constraint and not merely a cost

An engineer meeting this for the first time reasonably asks why any of it is a protocol problem.
Disks get cheaper. Buy a bigger one.

The answer is that the hardware requirement to run a node is the practical limit on how many people
can run one, and how many people run one is what the security argument rests on. The Stateless Book
puts the causation the other way round from how it is usually told: the reason the gas limit is
where it is, is that IO is the principal hindrance to raising it — so state cost is not only a node
cost, it is a **throughput ceiling**.<Cite src="stateless-fyi-intro" />

That gives you the shape of every proposal in this module. Each one attacks the same relationship
from a different side:

- **Reprice it.** Make creating state cost what it actually costs. EIP-8037 and
  EIP-8038.<Cite src="eip-8037" /><Cite src="eip-8038" />
- **Stop requiring most nodes to hold it.** Send a verifier the slice of state a block touched,
  proved. That is statelessness, and it is the next lesson.
- **Change what the state commits with**, so that slice is small enough to
  send.<Cite src="eip-7864" />
- **Stop counting untouched state as active.** State expiry.<Cite src="eip-7736" />
- **Prove the block instead**, so a verifier needs neither the state nor a large witness.

And one that is further along than any of them: **declare in advance what a block will touch**, so
clients can read state in parallel rather than serially. That is EIP-7928, Block-Level Access
Lists.<Cite src="eip-7928" /> It changes no tree and expires nothing, which is a large part of why
it is the one moving fastest — and, as the last lesson shows, the migration design for the new state
tree has already been written to depend on it.<Cite src="eip-8347" />

## What this unlocks

**The next lesson** replaces the question "how does a node hold all this" with "what is the smallest
thing you could send a node instead". The answer is a witness, and the whole difficulty is its size.

**The lesson after that** explains why the plan to shrink witnesses — Verkle trees, taught as
Ethereum's future for roughly four years — is no longer the plan, and why the stated reasons have
nothing to do with whether it worked.

**In your own systems**, the transferable move is the one this lesson opened with: when two things
get described with the same sentence, check whether they have the same access pattern before you
believe they have the same solution. Sequential and random are different databases wearing one word.

**And in capacity planning**, notice which number the sources put their confidence behind. Not a
state size, which is stale the day it is written, but a **growth rate measured against a stated gas
limit**, and a **threshold at which behaviour changes**. Those two together give you a date. A size
gives you nothing.
