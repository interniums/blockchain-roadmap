There is a runbook in your wiki. Near the top, in a table someone made when the chain launched, is a
row that reads "blob target 3, max 6". It has been correct, then quietly wrong, then wrong by a factor
of several, and nobody has edited it because nothing about a wiki page changes when the network does.

Those two numbers have since been superseded three times, by two different mechanisms, and the second
mechanism was designed specifically so that it could keep superseding them without anyone shipping a
client release. This lesson is about that mechanism, what it does to your infrastructure that
"config-only" does not suggest, and how to write software that does not need the runbook row at all.

## What a BPO fork is allowed to change, and why the list is that short

EIP-7892 defines a blob-parameter-only hardfork as an upgrade that modifies only blob-related
parameters through configuration, without requiring any client-side code changes, taking effect
immediately at the specified activation time.<Cite src="eip-7892" /> The complete list of what it may
touch is three entries: **target**, **max**, and **baseFeeUpdateFraction**.<Cite src="eip-7892" /> The
EIP adds a constraint that keeps the registry honest: when a *regular* hardfork changes any of these,
it MUST do so by adding an entry to the same blob schedule.<Cite src="eip-7892" /> One place, always.

The rationale section is worth reading as an argument about release engineering rather than about
blobs. Full hard forks require extensive coordination, testing and implementation changes beyond
parameter adjustments — the EIP cites Lighthouse, where a typical hard fork implementation requires
thousands of lines of boilerplate before any protocol change
occurs.<Cite src="eip-7892" /> Externalising the parameters into node configuration lets testing teams
investigate different values with minimal involvement from client implementers.<Cite src="eip-7892" />
And the case against putting it on-chain instead is stated in one line that should be pinned above
every governance discussion: Ethereum's gas limit increase to 36M "took nearly a year to
coordinate."<Cite src="eip-7892" />

Optimism's account from the rollup side names the same motive from the other end: BPO is the mechanism
that lets Ethereum safely increase blob capacity **between** hardforks.<Cite src="optimism-fusaka-is-live" />

### "Config-only" does not mean "invisible to your node"

This is the part that surprises operators, and it is in the specification in plain sight.

A BPO fork changes the network's identity. `compute_fork_digest` is modified to bitmask the applicable
`max_blobs_per_block` into the four-byte digest, so the fork digest changes at every BPO even though
no code did.<Cite src="eip-7892" /> Consensus-layer ENRs gain a new entry, `nfd` — "next fork digest"
— which nodes MUST evaluate alongside the existing `ENRForkID` fields to form an accurate view of a
peer's intended next fork.<Cite src="eip-7892" /> And because gossip topic names contain the
`ForkDigestValue`, **all topics automatically rotate at a BPO fork.**<Cite src="eip-7892" />

Read that as an operational fact: a node whose configuration lacks the upcoming BPO entry will, at the
activation timestamp, compute a different fork digest from its peers, subscribe to the wrong gossip
topics, and partition itself off the network — with no error at build time, no failed upgrade, and no
code change to blame. The specification also requires that execution and consensus clients share
consistent BPO schedules, that the EL `blobSchedule` slot align with the CL epoch, and that the EL
`max` equal the CL's `MAX_BLOBS_PER_BLOCK`.<Cite src="eip-7892" /> Three consistency requirements,
each of which is a way to be misconfigured.

<Aside kind="warn">
"No client release needed" is true for the protocol and false for you. A BPO fork is a scheduled
network event with a hard timestamp, a changed fork digest and rotating gossip topics. It belongs on
the same on-call calendar as a named upgrade, and the check to run before it is that your node's
configuration contains the new schedule entry — which, conveniently, is a single RPC call the next
section covers.<Cite src="eip-7892" /><Cite src="eip-7910" />
</Aside>

## Why raising the count became safe: the causal order

Blob capacity was not held at 3/6 and then 6/9 out of caution about the fee market. It was held there
by bandwidth. Before PeerDAS, every node downloaded every blob, so the data each node had to move grew
linearly with the blob count, and upload bandwidth is one of the most sensitive
knobs.<Cite src="ethereum-org-peerdas" />

[PeerDAS](/c/peerdas) breaks that linearity. It lets nodes verify blob data availability through
**sampling** rather than downloading whole blobs, using erasure coding so that sampling small portions
still gives a cryptographic guarantee that the full data is available across the
network.<Cite src="fusaka-mainnet-announcement" /><Cite src="eip-7594" /> The EF's framing of the
consequence is precise: this directly benefits rollups by supporting higher blob throughput **without
proportionally increasing bandwidth requirements for individual
nodes**.<Cite src="fusaka-mainnet-announcement" />

So the chain of causation, in the order it actually happened:

1. PeerDAS made a higher blob count safe to carry.<Cite src="eip-7594" />
2. BPO forks raised the count.<Cite src="eip-8134" /><Cite src="eip-8135" />
3. The extra supply is what moved the price, by making it easier to stay under target.

### What changed for the rollup, and what did not

**Unchanged: the interface.** A rollup still submits whole blobs in a type-3 transaction. Column
splitting happens on the consensus network, downstream of anything a batcher
does.<Cite src="eip-7594" /> If you find yourself asking how many columns to post, the model has
drifted.

**Changed: the proof structure inside the transaction.** EIP-7918's analysis of node compute states it
as a matter of fact about the current specification — under PeerDAS, execution-layer nodes
batch-verify `CELLS_PER_EXT_BLOB` (128) cell proofs for each blob before including a transaction
carrying that blob in their pool.<Cite src="eip-7918" /> Per-cell proofs, not one proof per blob. Any
library or tooling written against an EIP-4844-era one-proof-per-blob assumption is producing the
wrong wrapper.

**Changed: what nodes retain and serve.** The retained unit on the network is the data column sidecar
rather than the whole blob, which is why a rollup that needs its own history back cannot assume the
beacon network is a place to get it.<Cite src="eip-7594" /><Cite src="eip-4844" />

**Unchanged, and worth restating: the per-transaction blob limit.** Six, enforced at submission, on
receipt from the network, and during block production and processing.<Cite src="eip-7594" /> Raising
the per-*block* max does not raise it.

## Where the numbers live now, and how to read them

EIP-7840 moved target, max and the update fraction into a per-fork `blobSchedule` object in execution
client configuration.<Cite src="eip-7840" /> EIP-7892 then linked each entry to an activation
timestamp via a top-level `<fork_name>Time` field, with BPO forks named by the convention
`bpo<index>` starting at 1.<Cite src="eip-7892" />

That means the values are in a config file — yours, and everyone else's, possibly disagreeing. So
EIP-7910 added the method that reads them back out of a running node. `eth_config` takes no parameters
and returns three configuration objects: **current**, **next**, and **last**, where `next` and `last`
are null if the client is not configured for a future fork.<Cite src="eip-7910" /> Each object
contains `activationTime` as a Unix timestamp and `blobSchedule`, a JSON object with exactly three
members — `baseFeeUpdateFraction`, `max`, and `target`.<Cite src="eip-7910" /> BPO forks are
interpreted as new forks taking the parent fork as base, recursively, and updating only the
blobSchedule values.<Cite src="eip-7910" />

**This is the answer to the runbook row.** Not a better table — a call. Your batcher's cost model
should read `target`, `max` and `baseFeeUpdateFraction` from `eth_config().current.blobSchedule`, and
your on-call check before a scheduled BPO should confirm that `next` is non-null and that its
`activationTime` matches the announced one. EIP-7910's stated purpose is exactly this: letting nodes
advertise, before a fork, that they have the correct configuration loaded, because past mainnet and
testnet forks revealed clients with wrong precompile sets, chain IDs and other configuration
errors.<Cite src="eip-7910" />

## Why this lesson prints no current pair

You have every parameter through BPO2 above, with dates. You will not get one for today, and the
reason is instructive rather than evasive.

**The registry EIP for the next step exists and its table is empty.** EIP-8138, "Hardfork Meta —
BPO3", was created in January 2026 and, when fetched for this lesson on 2026-08-26, carried the status
**Draft** with a parameters table whose Activation Time, Blob Target, Blob Max and Base Fee Update
Fraction rows had no values in them.<Cite src="eip-8138" /> Its predecessors, EIP-8134 and EIP-8135,
are both marked Final and both carry complete tables.<Cite src="eip-8134" /><Cite src="eip-8135" />
That contrast is the finding: the registry is being maintained, and it does not yet record a third
step.

**It does document the rule the step would follow.** EIP-8138 states that for BPO3 the blob target is
set to the previous upgrade's blob maximum, and the blob maximum is calculated as 1.5 × the blob
target, rounded up.<Cite src="eip-8138" /> That rule reproduces the shipped history: Prague 6/9,
BPO1 10/15, BPO2 14/21 all satisfy `max = 1.5 × target`.<Cite src="eip-8135" /> You can therefore
compute what the next step *would* be. You still may not hard-code it, because a documented rule with
a blank activation time is a plan, and plans get paused on telemetry.

**And the sources genuinely disagree about the destination.** ethereum.org's PeerDAS page — last
updated 6 June 2026 — describes PeerDAS as delivering roughly an order-of-magnitude increase in DA
capacity and says the number of blobs "will begin doubling every few weeks until it reaches a maximum
of 48", while developers monitor for adverse effects on nodes.<Cite src="ethereum-org-peerdas" /> The
registry EIPs record two steps, ending at 21.<Cite src="eip-8135" /> Both are first-party Ethereum
sources. One describes an intention, the other records what shipped, and this curriculum's research
sweep could not resolve the gap between them. **Sources disagree; no current pair is stated here.**

<Aside kind="stop">
This is the shape of the disagreement to expect for the rest of this parameter's life, and it is not a
defect in anybody's documentation. A roadmap page describes where the mechanism is heading; a registry
EIP records what activated; a client config holds what your node believes. Those three will diverge
routinely, precisely because BPO forks were designed to be scheduled, paused and rescheduled on
telemetry rather than on a release train.<Cite src="eip-7892" /> Treat the roadmap as intent, the
registry as history, and `eth_config` as truth.<Cite src="eip-7910" />
</Aside>

## Worked example: making the runbook row unnecessary

You are removing every hard-coded blob constant from a batcher. Work it in the order that produces
software rather than a better spreadsheet.

**Subgoal 1 — enumerate what actually varies, which is fewer things than you think.** Three values:
`target`, `max`, `baseFeeUpdateFraction`.<Cite src="eip-7892" /> `GAS_PER_BLOB` at 2<sup>17</sup>,
`MIN_BASE_FEE_PER_BLOB_GAS` at 1 wei and the six-blobs-per-transaction limit are not on the schedule
and have not moved.<Cite src="eip-4844" /><Cite src="eip-7594" /> Distinguishing the two sets is most
of the work; a codebase that treats every blob number as volatile becomes unreadable, and one that
treats them all as constant becomes wrong at a timestamp.

**Subgoal 2 — fetch the varying three at startup and on a schedule.** `eth_config().current
.blobSchedule` gives all three in one call.<Cite src="eip-7910" /> Refresh it, because a BPO takes
effect at a timestamp with no restart involved.

**Subgoal 3 — use `next` as an alarm, not as data.** If `next` is non-null, you have an
`activationTime` and the parameters that follow it.<Cite src="eip-7910" /> Two useful behaviours fall
out. Warn when `activationTime` is within your on-call horizon. Warn *louder* when a BPO has been
publicly announced and your node's `next` is null — that is the misconfiguration that ends in a gossip
partition, and it is detectable days ahead.<Cite src="eip-7892" />

**Subgoal 4 — recompute the derived quantities rather than storing them.** Everything from the fee
lesson is a function of these three: the maximum upward multiplier is
`e^((max − target) × GAS_PER_BLOB / baseFeeUpdateFraction)`, the downward one uses `target` in place of
`(max − target)`.<Cite src="eip-4844" /><Cite src="eip-7892" /> Store the inputs, compute the rates.
A rate cached across a BPO boundary is a silently wrong number that no test will catch.

**Subgoal 5 — recheck the decisions that depend on `max`, not just the ones that depend on price.**
Your target frames per transaction is sized against blob economics, and your fill ratio moves the
blob-versus-calldata crossover linearly.<Cite src="op-docs-configure-batcher" /><Cite src="op-docs-tune-batcher-costs" />
A capacity increase changes how much room there is at a given price, which changes how full your blobs
should be, which moves your crossover. The parameter that looks like someone else's protocol detail
propagates into your own posting policy in two hops.

**Subgoal 6 — delete the runbook row and replace it with the call.** The row's replacement is not a
number, it is `eth_config`, plus a sentence saying that anyone who needs the current values runs it
against the node the chain actually uses.<Cite src="eip-7910" /> A wiki cannot be stale if it does not
contain the answer.

## Data stopped being the expensive part

One consequence deserves stating carefully, because it is the most-repeated claim in this subject and
the most-quoted-with-fabricated-numbers.

The direction is not in doubt. EIP-4844 introduced blobs as the preferred method of data
availability;<Cite src="eip-7623" /> two BPO forks then raised per-block capacity from 6/9 to
14/21;<Cite src="eip-8134" /><Cite src="eip-8135" /> and the blob base fee's floor is 1
wei.<Cite src="eip-4844" /> For a chain whose blobs are well filled, in a regime where the fee sits at
or near that floor, the L1 data bill is small in absolute terms — the six-blob arithmetic from the fee
lesson puts it under a picoether of blob gas.

You can see the same conclusion encoded in a live chain's own configuration rather than inferred. An
OP Stack transaction's total fee has three components — L2 fee, L1 fee, operator fee — and the L1 fee
is the one that exists to recover batcher spend.<Cite src="op-docs-fee-parameters" /><Cite src="op-docs-tune-batcher-costs" />
OP Mainnet runs `operatorFeeScalar` and `operatorFeeConstant` at 0, and a `basefeeScalar` of 5,227
against a `blobbasefeeScalar` of 1,014,213.<Cite src="op-docs-fee-parameters" /> The economic health
check the documentation prescribes is not a per-transaction fee figure at all: compare the batch
submitter's L1 spend against L1-fee revenue arriving in your fee vaults over a representative window,
and expect revenue at or above spend by your target margin.<Cite src="op-docs-tune-batcher-costs" />
That is a measurement you can run on your own chain and nobody can run on yours from outside — which
is exactly why the published figures are unreliable.

<Aside kind="stop">
**Figures this module refuses to print, and why.** Post-Fusaka per-transaction L2 fee medians: found
only in secondary sources, unverified, and volatile enough that a monthly figure misleads. Blob
utilisation percentages after BPO2: a single unverified secondary source. Any multiple describing how
far the blob base fee "surged" relative to its floor: unverified, and arithmetically unremarkable
against a 1 wei baseline in any case. Peer-reviewed measurement of the blob fee market
exists;<Cite src="ieee-4844-impact" /> its specific findings were not read for this curriculum and are
therefore not quoted. If you need any of these numbers, measure them on the chain you operate, over a
window you state.
</Aside>

**So what dominates instead?** It depends on the chain, and naming the candidates honestly is more
useful than ranking them. [Proving cost](/c/proving-cost) for validity rollups, which is a compute bill
that scales with execution rather than with bytes. Node, RPC and monitoring operations, which scale
with users rather than with either. And above all whether there is enough transaction demand to cover
fixed costs at all — the term that decides
[gross versus net revenue](/c/l2-gross-vs-net-revenue) and the one no protocol upgrade addresses.

The practical consequence for you: rollup economics diagrams built around data cost are describing
2023, and a chain differentiating itself on squeezing bytes is optimising a line item that stopped
being the largest one.

<Answer>
**Ranked: 3 is an outage, 2 is a silently wrong number, 1 is a stale dashboard.** The ranking is the
point — the least visible item is the dangerous one.

**Item 3 — the split configuration. Severity: the node leaves the network at a timestamp.** EIP-7892

the EL's `blobSchedule` align with the epoch in the CL configuration, and that the EL's `max` equal
the CL's `MAX_BLOBS_PER_BLOCK`.<Cite src="eip-7892" /> Two repositories maintained by two people is

topics nobody else is on.<Cite src="eip-7892" /> It looks like a peering problem, it happens at a

**Item 1 — the dashboard's capacity constant. Severity: misleading, not operational.** `6` was

network is fuller than it is. Easy to spot, because it goes visibly wrong rather than subtly wrong.

**What you fix in all three, once.** None of these is a wrong number problem; they are all a *pinned
number* problem. The three values that move are `target`, `max` and `baseFeeUpdateFraction`, and

record.<Cite src="eip-8138" /><Cite src="ethereum-org-peerdas" /><Cite src="eip-8135" /> A number you
would have to caveat that heavily is a number your code should be asking a node for.

## What this unlocks

**This module closes here**, and the piece it hands to the rest of the track is a habit rather than a
fact. You can now price a batch on both paths, predict the blob market's next move exactly, and read
the capacity parameters out of a live node instead of a document.

**Next in this track**, data availability that is not Ethereum. Everything in this module assumed the
data goes into L1 blobs; alternative DA layers and validium designs move it somewhere else, and the
comparison you have just learned to do in gas stops applying — because the thing you are buying stops
being the same thing.<Cite src="ethereum-org-fusaka" />

**And the reflex to keep.** Whenever a lesson, a blog post or a runbook hands you a blob parameter,
ask which fork's schedule it came from and when that page was last edited. Two of the three sources
consulted for this lesson disagree about where capacity is heading, and both are official. The one
that cannot disagree with itself is the node you are pointed at.
