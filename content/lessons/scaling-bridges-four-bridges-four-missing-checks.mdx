Four of the largest thefts in the history of this industry were carried out against systems whose
cryptography was working perfectly at the time.

That is not a rhetorical framing. It is the finding, and it is unusually well documented, because the
bridge failures of 2021 and 2022 were analysed to a level of detail that most incidents never
receive. In each case the elliptic curve was fine, the hash function was fine, the Merkle proofs were
fine — and the contract released the escrow anyway, because the check that mattered was somewhere
else and was not being made.

This lesson is the record, organised by the missing check rather than by the incident. Four bridges,
four checks, and a review sheet at the end that you can run against any bridge you are about to
depend on.

## Why the value concentrates behind one boolean

Start with the structure, because the structure is what makes bridges different from every other
category of exploit.

**Subgoal: describe what a bridge accumulates.** Every asset that crosses leaves its original behind
— in an escrow, in a lock, in the custody of a validator set. The escrow therefore holds the
*integral* of everything that ever crossed, not the flow. It grows with adoption and it does not
shrink when usage does.

**Subgoal: describe what defends it.** One contract, or one signer set, or one verification function.
That number does not grow with adoption. A bridge with a hundred times the volume has a hundred times
the payoff and the same number of things to break.

**Subgoal: state the consequence.** The attacker's expected return scales with the bridge's success
while the defender's surface stays fixed. This is why bridges dominate the largest-exploit lists, and
why the useful security question about a bridge is never "is the code audited" but **"how many keys,
held by whom, guard how much".**

The 2022 figures make the concentration concrete. One audit firm's review of that year counts five
major cross-chain bridge exploits totalling $1,317,000,000 — 57% of all Web3 losses that
year.<Cite src="certik-bridge-exploits-2022" /> A vendor education page, written later against a
different denominator, gives more than $2.8 billion hacked from cross-chain bridges, almost 40% of
the entire value hacked in Web3, attributing the figure to a public
dashboard.<Cite src="chainlink-bridge-vulns" />

<Aside kind="warn">
Those two numbers are not comparable and must not be added, averaged or presented as a trend. They
cover different periods, different denominators and different methodologies, and even single
incidents carry meaningfully different figures across write-ups — the Ronin loss appears as $624
million in one analysis<Cite src="certik-bridge-exploits-2022" /> and $625 million in
another,<Cite src="zealynx-bridge-checklist" /> and Wormhole appears as $326
million<Cite src="certik-bridge-exploits-2022" /> and $320 million.<Cite src="zealynx-bridge-checklist" />
Quote a scope with every figure or quote no figure. The mechanisms below are not in dispute; the
totals are.
</Aside>

## Missing check 1 — the verifier's trusted input came from the caller

**Wormhole, 2 February 2022.** The verification code ran. It returned success. It checked nothing
binding.

The Solana-side verifier used a deprecated command, `load_instruction_at`, to establish that
`Secp256k1` had been called — and that command does not check the value of the system address, the
Instructions sysvar.<Cite src="wormhole-postmortem" /> The attacker created a counterfeit Instructions
sysvar as a previously-created account referencing `Secp256k1`, and passed that fake account instead
of the legitimate one; the verification then validated a fraudulent
context.<Cite src="wormhole-postmortem" /> With that in hand they created a validator action approval
through `post_vaa`, used it in a `complete_wrapped` call to mint 120,000 wETH, and extracted
it.<Cite src="wormhole-postmortem" /><Cite src="certik-bridge-exploits-2022" />

You have already built the tool that finds this. In the storage-proof lesson you sorted a verifier's
inputs into two piles: the ones that are self-checking, and the one that is the axiom. Run it again
here.

**Subgoal: enumerate what the verifier consumes.** A message, a set of signatures, and — implicitly —
*the identity of the thing that is allowed to say the signatures are valid.* On Solana that identity
is an account; on the EVM it is usually an address in storage.

**Subgoal: sort by whether the value is self-checking.** The message and the signatures are
self-checking: change either and the recovered signer changes and the check fails. The verifier's own
identity is not self-checking. Nothing in the verification validates it, because it is what
validation is measured *against*.

**Subgoal: find who supplies the axiom.** This is the whole exploit. The axiom was an account
supplied by the caller, and the deprecated helper did not compare it against the known
address.<Cite src="wormhole-postmortem" /> Once the caller supplies the axiom, "did the guardians
sign this" becomes "did the thing I nominated agree with me", which is always yes.

**Subgoal: state the general shape.** *Any verifier one of whose trusted inputs can be influenced by
the caller is not a verifier.* The EVM versions look like this:

```text
verify(msg, sigs, address signerSet)      -- signer set is a parameter
verify(msg, proof, bytes32 root)          -- root is a parameter
require(IOracle(oracleAddr).check(...))   -- oracleAddr read from calldata
require(chainId == m.chainId)             -- chainId taken from the message
```

Each reads as a verification and each is a request for the caller's opinion. The fix is mechanical:
**bind every trusted input to `immutable`, to a constant, or to storage the caller has no path to
write.** If a trusted value must be updatable, the update path is the security boundary and belongs
in the same review as the verification itself.

### The same missing check without a signature anywhere

The class is broader than signature verification, which is why it is worth naming by the missing
check rather than by the mechanism.

**Qubit, 27 January 2022, $80 million.** The attacker called `deposit()` without attaching any ETH,
and faked the ETH deposit event using an ERC-20 event; roughly 77,162 qxETH were minted on the
strength of it.<Cite src="certik-bridge-exploits-2022" />

No signature was forged. The authorising artefact was an *event*, and the attacker was permitted to
produce it. Same missing check, different costume: the thing the destination side treated as
authoritative was under the attacker's control.

  src="wormhole-postmortem"
/>

Note the shape of the outcome, because it decides who absorbs the loss. The Ethereum-side escrow was
never touched. 120,000 unbacked wETH appeared on the other
chain.<Cite src="certik-bridge-exploits-2022" /> Nothing was stolen from the bridge; something was
*created* beside it — and everyone holding or lending against that wrapper became the counterparty
without being consulted.

## Missing check 2 — the keys, and what a threshold actually measures

**Ronin, March 2022.** Nothing in the contract was wrong.

The bridge ran nine validator nodes and required five signatures. Spear phishing gave the attacker
the private keys to the four validators Sky Mavis ran. The fifth signature did not come from a fifth
stolen key: Sky Mavis still held a temporary permission to sign on behalf of the third-party Axie DAO
validator, granted earlier to absorb a load spike and never
revoked.<Cite src="sok-cross-chain-bridge-security" /> Four keys and one stale delegation moved
173,600 ETH and 25.5 million USDC, reported at $624
million.<Cite src="certik-bridge-exploits-2022" />

Read the composition of the five, not the number. **The fifth signature belonged to a different
organisation on paper only.** That third-party validator is precisely the thing that made a
five-of-nine set look distributed: an outside party in the set means the operator cannot act alone.
Except that a permission nobody revoked had already collapsed the two organisations into one, so the
attacker never had to breach the second. The distribution was organisational, and a social attack
crosses organisational boundaries far more cheaply than it crosses cryptographic ones.

So the arithmetic that matters is not k out of N. It is:

**Harmony Horizon, 23 June 2022, approximately $97 million.** The attacker controlled a
`MultiSigWallet` owner and called `confirmTransaction()` directly, across twelve attack transactions
from three addresses.<Cite src="certik-bridge-exploits-2022" /> The threshold on that wallet is
widely reported as two-of-five; the analyses cited here describe the owner compromise rather than the
threshold, so treat the specific number as reported rather than verified. The mechanism does not
depend on it.

The published checklists put the same point as a hard rule: a two-of-three multisig is not sufficient
for a bridge holding $100M or more, and validators should face defined economic penalties for signing
invalid messages or double-signing.<Cite src="zealynx-bridge-checklist" /> The vendor taxonomy of
bridge vulnerabilities opens with unsecure private key management and includes unproven validator
sets — operators lacking the requisite operational security
expertise — as a separate entry.<Cite src="chainlink-bridge-vulns" />

This is the [upgrade key](/c/upgrade-key-risk) question one level down, and the module's reflection
prompt is exactly it: for the bridge your product would use, name every party who could act alone or
in collusion of size k to mint unbacked supply or move the escrow. **State k. Then state what you
believe k' to be, and why.**

## Missing check 3 — a value set once, at deployment, and never re-derived

**Nomad, 2 August 2022.** An upgrade left `committedRoot` initialised as zero, which allowed message
verification to be bypassed entirely; total value locked went from around $190 million to roughly
$12,000, with at least 41 wallets participating in the
exploitation.<Cite src="certik-bridge-exploits-2022" />

Take the mechanism at the level that generalises. A message-verification path asks a question of the
form *has this message been proven?* and answers it by looking up stored state. If the stored state's
default value happens to satisfy the acceptance test, then **every message that was never proven
passes** — because "never seen" and "approved" are the same bit pattern.

That is not a bridge bug. It is a class of bug that bridges make catastrophic:

- A `mapping(bytes32 => Status)` where `Status(0)` is a meaningful accepted state rather than
  `Unknown`.
- A `trustedRoot` that is zero until an initialiser runs, in a contract whose verification accepts a
  proof against the current root.
- A threshold or quorum variable that is zero until configured, in a check written as
  `require(signatures.length >= threshold)`.
- Any proxy whose implementation was upgraded without re-running the initialisation that the new
  storage layout expects.

The control that catches all four is the same and it is boring: **a post-deployment and post-upgrade
assertion pass that reads the deployed state and checks every security-critical variable against an
expected value, run as a gate rather than as a habit.** Not a test against the constructor — a read
against the chain, after the transaction that changed anything.

Nomad's other property — that the exploit became copy-pasteable and a crowd of unrelated wallets
joined within hours — is the [copycat window](/c/copycat-window), and the security track treats it as
its own subject with the incident-response consequences worked through. What matters here is the
narrow point: the security-critical value was set outside the code, and nothing downstream re-derived
it.

## Missing check 4 — the message path could reach the bridge's own controls

**Poly Network, 10 August 2021, $600.3 million.**<Cite src="halborn-poly-network" /> The largest of
the four, and the one whose shape is most likely to be present in code you review this year.

The `putCurEpochConPubKeyBytes` function in the `EthCrossChainData` contract can update the keeper
role, and it can be executed with a call to `verifyHeaderAndExecuteTx` in the `EthCrossChainManager`
contract.<Cite src="halborn-poly-network" /> The attacker sent a specially crafted command to
`verifyHeaderAndExecuteTx`, reassigned the keeper role to their own address, and then drained the
protocol with the elevated permission they had just granted
themselves.<Cite src="halborn-poly-network" />

Say what the missing check was in one sentence. **The set of targets a verified message could call
was not restricted to exclude the contracts that decide which messages are verified.** The bridge's
executor was, by construction, the owner of its own configuration — so a message that the current
keeper authorised could change who the keeper is, and from there every subsequent message was
self-authorised.

You met the small version of this in the native-bridge lesson. A contract on the receiving side must
check both that `msg.sender` is the messenger and that `xDomainMessageSender()` is the party it
expects, because checking only the first authorises every address on the other
chain.<Cite src="op-docs-bridging-messaging" /> Poly Network is that omission at the protocol layer:
the executor was trusted absolutely, so anything the executor could reach was inside the trust
boundary, including the boundary's own definition.

This is [access control](/c/access-control-failure) evaluated across a domain hop, and the review
question is a set-difference:

```text
T  = every address a verified message may call
A  = every address that can change the verifier set, the keeper,
     the threshold, the roots, or the proxy implementations

the required invariant:   T ∩ A = ∅
```

If that intersection is non-empty, the bridge's security is a fixed point rather than a property, and
one authorised message anywhere in its history can move it. Check the intersection at review time,
and re-check it after every upgrade — because a proxy added later is a new member of `A` that nobody
compared against `T`.

The aftermath is worth one line because it explains why the totals in this lesson disagree with the
ones you will read elsewhere: the attacker claimed the exploit was a demonstration and returned some
of the funds, though the majority was not returned at the time of that
write-up.<Cite src="halborn-poly-network" /> Loss figures for incidents with partial recovery are a
moving target for months.

## The review sheet

The published checklists organise this into seven domains and more than a hundred individual checks —
architecture and trust model, message-passing security, asset-transfer mechanisms, oracle and
validation security, economic security, emergency mechanisms and operations, and chain-specific
considerations.<Cite src="zealynx-bridge-checklist" /> Read it in full before an engagement. The
short version, in the order the four failures suggest, is:

1. **Name every trusted input to the verifier, and prove none of them is caller-influenced.** Signer
   set, root, threshold, chain identifier, oracle address. Bind them to immutable storage or to
   state with an explicit, separately reviewed update path.
2. **Compute k and then k'.** Threshold, holder identities, and the correlations between them —
   employer, infrastructure, signing tooling, and any temporary arrangement. Confirm slashing exists
   if the design claims it.<Cite src="zealynx-bridge-checklist" />
3. **Read the deployed state, not the source.** Every security-critical variable, on chain, after the
   most recent upgrade, compared to an expected value. This is minutes of work and it is the only
   thing that catches the Nomad class.
4. **Compute the intersection of "callable by a verified message" with "can change the
   verification".** It must be empty, and it must stay empty across upgrades.
5. **Prove replay protection in both dimensions.** A message valid on one chain must not be
   replayable on another, which means chain identifiers inside the signed payload; and a historical
   message must not be re-executable, which means per-sender nonces and a consumed
   set.<Cite src="zealynx-bridge-checklist" />
6. **Confirm mint authority is held only by the verified message receiver.** Only the bridge contract
   should be able to mint the wrapped token.<Cite src="zealynx-bridge-checklist" />
7. **Ask what happens with no verification at all.** Rate limits and active transaction monitoring
   are separate entries in the vendor taxonomy for a reason — they bound the damage from a
   verification failure you did not find.<Cite src="chainlink-bridge-vulns" />

Items 1 to 4 are the four incidents. Items 5 to 7 are what the incidents' write-ups agreed should
have been present anyway.

<Check type="spot-bug" concept="signature-verification-failure">
A team hands you this for review, minutes before deployment. It has an audit report attached. Find
every one of the four missing checks that is present, and say which incident each corresponds to.

```solidity
contract Bridge {
    address public signerSet;
    bytes32 public trustedRoot;
    mapping(bytes32 => bool) public executed;

    struct Message { address target; bytes data; uint256 nonce; }

    function initialize(address _signerSet) external {
        signerSet = _signerSet;
    }

    function executeMessage(
        Message calldata m,
        bytes calldata sigs,
        address verifier
    ) external {
        bytes32 h = keccak256(abi.encode(m));
        require(IVerifier(verifier).verify(h, sigs, signerSet), "bad sigs");
        (bool ok, ) = m.target.call(m.data);
        require(ok, "call failed");
    }

    function setSignerSet(address s) external {
        require(msg.sender == address(this), "only self");
        signerSet = s;
    }
}
```

<Answer>
All four, plus a replay hole. In order of how quickly each one ends the review:

**1 — `verifier` is a caller-supplied parameter. This is the Wormhole class and it is total.**
`IVerifier(verifier).verify(...)` calls a contract the attacker chose. They deploy one that returns
`true` and the entire authorisation model evaporates; `signerSet` being correctly stored is
irrelevant, because the code that consults it is also the attacker's. This is exactly the missing
comparison in the deprecated Solana helper — the trusted reference was never checked against a known
value.<Cite src="wormhole-postmortem" /> Fix: `verifier` becomes `immutable`, set in the constructor,
and is not a function argument.

**2 — `initialize` has no access control and no one-time guard. This is the Nomad class.** Anyone can
call it, at any time, including after deployment and after every upgrade, and set `signerSet` to an
address they control. Note the second half of the same class: `trustedRoot` is declared and never
assigned anywhere in this contract, so it is zero. Any future code path that validates a proof
against `trustedRoot` will validate against zero, which is the Nomad shape
precisely — `committedRoot` initialised as zero, allowing verification to be
bypassed.<Cite src="certik-bridge-exploits-2022" /> Fix: an initialiser guard, an authorised caller,
and a post-deploy assertion that reads both variables on chain and compares them to expected values.

**3 — `setSignerSet` is reachable from `executeMessage`. This is the Poly Network class, in seven
lines.** The `require(msg.sender == address(this))` looks like a hardened self-call restriction, and
it is the opposite: `m.target` is unrestricted, so a verified message can set `m.target` to the
bridge itself and `m.data` to `setSignerSet(attacker)`. `msg.sender` during that inner call *is* the
bridge, so the check passes. One authorised message rewrites who is allowed to authorise messages,
which is what `putCurEpochConPubKeyBytes` reachable through `verifyHeaderAndExecuteTx` did for
$600.3 million.<Cite src="halborn-poly-network" /> The intersection of "callable by a verified
message" and "can change the verification" is non-empty. Fix: exclude `address(this)` and every
admin-bearing contract from the permitted target set, and move `setSignerSet` behind a role that no
message path can assume.

**4 — the key-compromise class is not visible in this file, which is the point.** There is nothing
here to read. `signerSet` is an address; how many keys it represents, what threshold it enforces, who
holds them and what those holders share is entirely outside the repository. That is the Ronin
lesson — nothing in the contract was wrong. Spear phishing took the four validators Sky Mavis ran,
and the fifth signature came from the Axie DAO validator because a temporary permission for Sky Mavis
to sign on its behalf had never been revoked.<Cite src="certik-bridge-exploits-2022" /><Cite src="sok-cross-chain-bridge-security" /> The finding to
write is that the contract's security parameter is unauditable from the contract, and the review must
therefore include the deployed verifier's composition and its custody model, against a rule like "a
two-of-three multisig is not sufficient for a bridge holding $100M or
more".<Cite src="zealynx-bridge-checklist" />

**5 — `executed` is declared and never written.** Every message is infinitely replayable: same
calldata, same signatures, same result, as many times as the escrow allows. And `Message` carries a
`nonce` but no chain identifier, so a message signed for one deployment is valid on every other
deployment of this contract with the same signer set. Both are named checklist requirements —
historical message replay must be prevented with per-sender nonces, and chain identifiers must be
included in signed payloads so that a message valid on one chain is not replayable on
another.<Cite src="zealynx-bridge-checklist" /> Fix: `require(!executed[h]); executed[h] = true;`
before the call, and put `block.chainid` and the contract address inside the hashed struct — the same
domain-separation reasoning as [signature replay](/c/signature-replay) protection.

**And the audit report attached to it?** Worth reading, and worth nothing on its own. Three of these
five findings live in deployment state and operational structure rather than in the code an audit was
scoped to, which is the recurring conclusion of the incident record rather than a complaint about
auditors.
</Answer>
</Check>

## Where this pays off

**Immediately, on anything already in production.** Items 1, 3 and 4 of the review sheet are queries
against chain state, not code reading, and each takes minutes. Read the deployed verifier address and
confirm it is immutable. Read every security-critical storage slot and compare it to what you expect.
List the addresses a verified message can call and intersect that list with the addresses that can
change the verification. If any of the three surprises you, that surprise is the finding.

**In the module's own exercise.** The two practices attached here are reproductions rather than
readings: build a minimal bridge with an uninitialised trusted root and prove an arbitrary message
against it, and build a verifier that reads its signer set from a caller-supplied argument and forge
a message through it. Both are short. Both are more convincing than any write-up, because you will
watch a correct-looking `require` return true for a message nobody sent.

**In the ranking the whole module was building.** You now have the complete ladder and its evidence.
The native bridge adds nothing to the rollup's own assumptions. A liquidity bridge adds an operator
and a pool. A storage-proof bridge adds a source of foreign headers. An intent bridge adds a solver
and a settlement gap. Externally verified message passing adds a set of size N with a threshold k —
and that bottom rung is where every loss in this lesson happened, for reasons that are structural
rather than accidental: it is the only rung where a small, fixed number of parties can release
