Send one ETH from Ethereum to OP Mainnet through the official bridge. It arrives in roughly one to
three minutes.<Cite src="op-docs-bridging-messaging" />

Send it back. That takes approximately seven days, and it is not one transaction but three: one on
L2 to initiate, one on L1 to prove, and one on L1 to finalise once the challenge period has
elapsed.<Cite src="op-docs-bridging-messaging" />

Same protocol. Same repository. Same audits. Same team. A factor of roughly three thousand in
latency, and a factor of three in the number of times the user has to sign something.

Nothing in that asymmetry is an implementation shortcoming, and every third-party bridge you will
meet in this module exists because of it. So it is worth deriving rather than accepting — because
once you can derive it, you can tell which of the "fast bridge" products are removing the wait and
which are merely selling it to you.

## The token bridge is the top of a stack, not the whole thing

Start with what is actually deployed, because the vocabulary matters later.

On the OP Stack the L1 side is three layers. `OptimismPortal` is the low-level deposit entry point
and withdrawal exit. `L1CrossDomainMessenger` sits on top of it and adds replayable message passing.
The token bridges — `L1StandardBridge` for ETH and ERC-20s, `L1ERC721Bridge` for
NFTs — sit on top of the messenger.<Cite src="op-docs-smart-contracts" /> The documentation is
explicit that messages sent directly to `OptimismPortal` are not replayable, and that users and
application developers should prefer the messenger or bridge
interfaces.<Cite src="op-docs-smart-contracts" />

Scroll arranges the same idea with different names. Arbitrary messages go through
`L1ScrollMessenger`; enforced transactions bypass the messenger and go straight to `L1MessageQueue`;
the standard token gateways encode a deposit into a message and hand it to the
messenger.<Cite src="scroll-cross-domain-messaging" />

Two stacks, one shape. **The token bridge is an application built on a general message-passing
layer.** A "bridge" that moves USDC and a contract on L1 calling a contract on L2 are the same
machinery with different calldata — the messenger's `sendMessage` takes a target address, a message
body and a minimum gas limit, which the OP Stack documentation notes is essentially
`address(_target).call...` with the gas limit, except the target is on a different
network.<Cite src="op-docs-bridging-messaging" />

That framing is the one to carry. When lesson five asks what a bridge exploit actually broke, the
answer is almost never "the token logic". It is the message layer underneath it.

<Aside kind="note">
The messenger being general is also why "we only bridge tokens, so message-passing bugs do not apply
to us" is not a defence. Your token bridge's authorisation is the messenger's authorisation. You
inherited every property of it, including the ones nobody on your team has read.
</Aside>

## Why the two directions cannot be symmetric

Now the derivation. Four subgoals, and the third is where the whole module turns.

**Subgoal: establish what each side is already allowed to believe.** A rollup derives its own state
from data published on L1. The L2 must read L1 to exist at all — that is what makes it a rollup
rather than a separate chain. So L1 is already inside the L2's trust base; the L2 believes L1 by
construction. The reverse is not true. Ethereum has no view of the L2 whatsoever, and no capacity to
acquire one: if an L1 contract could execute the L2, there would be no reason for the L2 to exist.
You met this in [rollup](/c/rollup) and it is the load-bearing asymmetry here.

**Subgoal: price a deposit under that asymmetry.** Going in, nothing has to be proven. An L1
transaction emits an event; the rollup's node software watches for it and turns it into an L2
transaction. On the OP Stack, `OptimismPortal.depositTransaction` runs sanity checks and emits
`TransactionDeposited`; `op-node` watches L1 for those events and converts them into deposit
transactions, which in most cases call `relayMessage` on
`L2CrossDomainMessenger`.<Cite src="op-docs-deposit-flow" /> Scroll's sequencer runs a watcher over
`L1MessageQueue` and appends the resulting `L1MessageTx` transactions to a local queue, which must be
included in L2 blocks in the queue's order, ahead of ordinary L2
traffic.<Cite src="scroll-cross-domain-messaging" />

There is no verification step anywhere in that paragraph, because there is nothing to verify. The L2
was going to read L1 anyway.

**Subgoal: account for the minutes that are still there.** If a deposit needs no proof, why is it one
to three minutes rather than one block? The OP Stack documentation gives the reason directly: the
sequencer waits for a certain number of L1 blocks before including L1-to-L2 transactions, to avoid
reorgs.<Cite src="op-docs-bridging-messaging" /> That is a [reorg](/c/reorg) safety margin, not a
verification cost — the same reasoning your indexer uses when it refuses to treat a one-block-old L1
event as settled. Halve Ethereum's reorg risk and that number moves. No amount of bridge engineering
moves it.

**Subgoal: price a withdrawal.** Coming out, an L1 contract has to be convinced of an L2 fact, and it
has exactly the two options the rollup itself has: wait out a challenge window, or verify a validity
proof. The OP Stack's withdrawal is three transactions for that reason, and each one exists for a
different party's benefit:<Cite src="op-docs-withdrawal-flow" />

Read step 2 closely, because you have already built this machinery. The output root commits to the
state of the `sentMessages` mapping in `L2ToL1MessagePasser`'s storage, and the proving transaction
verifies a Merkle-Patricia proof that a particular entry in that mapping is
set.<Cite src="op-docs-withdrawal-flow" /> That is a [storage proof](/c/storage-proof) against a
[Merkle-Patricia trie](/c/merkle-patricia-trie) — the same object EIP-1186's `eth_getProof` returns
for any account and slot.<Cite src="eip-1186" />

**The native bridge is already a storage-proof bridge.** It is just one whose root arrives through
the rollup's own settlement contract instead of through a third party. Hold that thought; lesson
three is that sentence with the root arriving from somewhere else.

### Two consequences most people meet as bugs

**The proof can be re-proven, and re-proving restarts the clock.** A withdrawal may be proven more
than once — for example against a different dispute game if the original game turns out to be
invalid — and re-proving resets the proof timer.<Cite src="op-docs-withdrawal-flow" /> If your
product tracks "withdrawal initiated at T, therefore finalisable at T plus seven days", that model is
wrong in exactly the case where it matters most: the case where the first proof's game was bad. The
correct model keys off the proof timestamp currently recorded on chain, not off your database.

**The costs are not where users expect.** The L1 proving transaction is expensive because it verifies
a Merkle trie inclusion proof on L1, and both L1 transactions are typically far more expensive than
the L2 transaction that started the whole thing.<Cite src="op-docs-bridging-messaging" /> A
withdrawal is an L1 operation with an L2 prologue, priced accordingly.

### What the withdrawal hash commits to, and why each field is there

The thing proven in step 2 is a hash, and the fields hashed are a small, deliberate set. Reading them
as a design rather than a list is worth two minutes, because every one of them is a check that a
worse bridge does not make.

`L2ToL1MessagePasser.initiateWithdrawal` hashes the raw withdrawal fields — nonce, sender, target,
value, gasLimit, data — records the hash in `sentMessages`, and emits those fields with the hash in a
`MessagePassed` event.<Cite src="op-docs-withdrawal-flow" /> Take them in turn:

- **nonce** — a single-use value whose stated purpose is to stop two otherwise identical withdrawals
  from hashing to the same value.<Cite src="op-docs-withdrawal-flow" /> Without it, "Alice withdraws
  1 ETH to her own address" is the same message every time, and proving it once would be proving it
  forever. This is [replay protection](/c/signature-replay) by construction rather than by a separate
  spent-set, and it is the exact property the Nomad and Wormhole failures in lesson five did not have
  in the place they needed it.
- **sender** — the L2 address that initiated the transfer, typically `L2CrossDomainMessenger` — and
  **target**, the L1 address to call.<Cite src="op-docs-withdrawal-flow" /> Both are inside the hash,
  so a proven withdrawal cannot be re-aimed. The message is bound to its destination the way an
  [EIP-712](/c/eip-712-typed-data) payload is bound to its domain.
- **gasLimit** — the system guarantees at least this much gas is available on L1. The documentation
  is careful here: if the gas is insufficient, the finalising transaction *returns a failure, it does
  not revert*.<Cite src="op-docs-withdrawal-flow" /> A failure that does not revert is a state change
  that looks like nothing happened. Your monitoring has to read the outcome, not the receipt status.

Nothing in that list is exotic. What is notable is that the *bridge* does not choose any of it — the
fields are fixed by the protocol, and the escrow releases against a hash of all of them together. In
lesson two you will meet designs where the equivalent commitment is chosen by whoever operates the
bridge, and the difference between those two situations is most of the module.

### Two stacks, two proof structures, one job

Scroll solves the same problem with a different data structure, and the contrast is instructive.
Where the OP Stack proves an entry in a mapping inside the general state trie, Scroll's
`L2MessageQueue` maintains a dedicated **Withdraw Trie**: an append-only, dense binary Merkle tree
whose leaves are message hashes, whose internal nodes are the keccak digest of their two children's
concatenated hashes, and whose depth grows with the number of messages, padding incomplete levels
with a zero hash.<Cite src="scroll-cross-domain-messaging" /> After the batch containing the message
is finalised on the L1 rollup contract, the user calls `relayMessageWithProof` on `L1ScrollMessenger`
with a Merkle proof against that trie.<Cite src="scroll-cross-domain-messaging" />

Two design points fall out. First, Scroll's docs describe the finalisation as trustless *because of*
the Merkle proofs, and note it can be submitted by the user or by a third party on their
behalf.<Cite src="scroll-cross-domain-messaging" /> The proof is what makes the relayer role
permissionless — anyone can push your withdrawal through, because nobody is being trusted to say it
happened. Second, generating that proof requires having watched the whole message stream, so Scroll
runs a Bridge History API that monitors `SentMessage` events, maintains its own copy of the Withdraw
Trie and serves proofs.<Cite src="scroll-cross-domain-messaging" />

That second point is the one to file away. **A trustless verification step can still have a
convenience service in front of it, and the service is not trustless — it is just falsifiable.** If
the API serves you a bad proof, the contract rejects it; you lose time, not money. Compare that to a
design where an off-chain service's word *is* the authorisation, which is lesson two's whole subject.

## The other direction has its own hazards, and they are not latency

A deposit that arrives is not a deposit that succeeded. Deposit transactions can fail on L2 —
usually because not enough gas was supplied, or because L2 state did not allow the call to succeed —
and when that happens the `L2CrossDomainMessenger` records the message as failed and it can be
replayed later, optionally with more gas.<Cite src="op-docs-deposit-flow" /> Scroll does the same on
its side: a message whose gas limit was set too low on L1 can be replayed with a higher
one.<Cite src="scroll-cross-domain-messaging" />

This is the replayability the messenger buys you over the raw portal, and it is the reason the OP
Stack documentation steers you away from calling `OptimismPortal` directly.<Cite src="op-docs-smart-contracts" />
Skip the messenger and a failed message is simply gone — the L1 side succeeded, the L2 side did not,
and there is no record to retry against.

The gas accounting is worth one more sentence because it explains a whole category of support ticket.
`OptimismPortal` charges for the L2 execution by burning a dynamic amount of L1 gas during the L1
transaction, and the amount rises when more people are sending L1-to-L2 traffic; the documentation
recommends adding a buffer of at least 20% to the requested L2 gas
limit.<Cite src="op-docs-bridging-messaging" /> So an L1-to-L2 call can become more expensive between
your simulation and your broadcast for reasons that have nothing to do with your transaction.

### The sender changes identity at the boundary

Because messages are shuttled by the messenger contracts, `msg.sender` on the receiving side is the
messenger, not the originator. Each messenger exposes `xDomainMessageSender()` so the receiving
contract can recover who actually sent the message, and an `onlyOwner` modifier on L2 has to check
both that the caller is the messenger and that `xDomainMessageSender()` is the
owner.<Cite src="op-docs-bridging-messaging" /> Scroll's arbitrary-message path expresses the same
constraint differently: the L2 sender for an arbitrary message is the *aliased* `L1ScrollMessenger`
address, while an enforced transaction submitted through `EnforcedTxGateway` uses the EOA from the
function parameters as the sender.<Cite src="scroll-cross-domain-messaging" />

You already know why the naive version of this check is dangerous. A contract that only checks
`msg.sender == messenger` has authorised *every* address on the other chain, because anyone can ask
the messenger to deliver a message. A contract that only checks `xDomainMessageSender()` without
checking the caller is the messenger has authorised anyone who can fake that call. Both halves, every
time — this is [access control](/c/access-control-failure) with an extra hop in it, and the extra hop
is where the omissions live.

That misconception matters beyond bridging. The deposit path is the mechanism underneath
[forced inclusion](/c/forced-inclusion) and therefore underneath the
[escape hatch](/c/escape-hatch): the same contract that accepts your bridged ETH is the one that
accepts your transaction when the sequencer refuses to. Scroll says this in as many words — enforced
transactions let users bypass `L1ScrollMessenger` and send directly to `L1MessageQueue`, which the
docs describe as a censorship-resistance mechanism ensuring users can always force inclusion on
L2.<Cite src="scroll-cross-domain-messaging" />

## What the native bridge actually asks you to trust

Here is the whole point of starting here rather than with the interesting bridges.

Using the native bridge adds **no trust assumption you were not already making by using the chain**.
Conduit's framing of the rollup builder's decision says it plainly: the native bridge requires no
security assumptions beyond the ones the development framework already imposes — no extra validators,
no liquidity providers, no external consensus
mechanism.<Cite src="conduit-native-vs-third-party" /> ethereum.org classifies bridges the same way
along the axis that matters: who verifies the system, with bridges secured by external validators
being typically less secure than bridges verified locally or natively by the underlying chain's own
validators.<Cite src="ethereum-org-bridges" />

That is the baseline. It is not "safe" in the absolute — it is exactly as safe as the rollup, which
you already know is a serious qualification. The rollup's upgrade authority can change the bridge
contracts; the [upgrade key](/c/upgrade-key-risk) sits above the proof system, and at
[Stage 0](/c/l2beat-stage-0) that is a small group of humans. But it adds nothing *on top of* that.
Every bridge in the next four lessons does add something, and the module's whole method is to name
the addition.

Conduit is equally clear about the two things the native bridge cannot do: withdrawals wait out the
seven-day challenge period, and it connects your rollup to Ethereum and to nothing
else.<Cite src="conduit-native-vs-third-party" /> Those two sentences are the entire commercial
existence of the third-party bridge industry. Lesson two starts there.

<Check type="predict" concept="deposit-is-fast-withdrawal-is-slow">
You are the engineer on a treasury system that keeps working capital on an OP Stack chain and sweeps
to an Ethereum address. Four proposals land in your inbox. For each, say whether it removes the
seven-day wait, and name the mechanism that decides.

1. "Switch to a validity rollup — proofs are verified on L1, so there is no challenge window."
2. "Run our own `op-challenger` so we can defend the withdrawal ourselves."
3. "Use a bridge that pays us on Ethereum in two minutes and claims the native withdrawal itself."
4. "Prove the withdrawal on day one instead of day seven, so the clock starts earlier."

<Answer>
**1 — yes, and it is the only one of the four that removes the wait rather than moving it.** The
window exists because an L1 contract is not convinced; a verified validity proof convinces it, so
there is nothing left to wait for. What replaces the wait is proving latency and a recurring proving
cost, which are real and which this module does not put a number on. Note also that this changes the
chain, not the bridge.

**2 — no, and the reason is the useful part.** The challenge window is not a queue you can jump by
participating. It is a fixed period during which *anyone* may dispute the root your withdrawal is
proven against. Running a challenger improves the chance that a bad root gets challenged; it does
nothing to shorten the period, because the period's length is set against a censorship adversary, not
against your responsiveness.

**3 — no. It sells you the wait.** The seven days still elapses; somebody else sits through them.
That somebody has capital on Ethereum, has taken the risk that the withdrawal fails or the root is
invalidated, and has charged you a fee that prices both. This is the [liquidity
bridge](/c/liquidity-bridge) and it is lesson two's subject. It is a perfectly reasonable purchase —
as long as you are aware you made one.

**4 — no wait removed, but this one is not empty.** Proving early does start the seven days early,
so end to end it is faster than proving on day seven. The catch is the one above: a withdrawal can be
re-proven, and re-proving resets the proof timer.<Cite src="op-docs-withdrawal-flow" /> Proving
against a dispute game that later resolves badly means starting over. Early proving is a latency
optimisation with a tail risk, not a way out of the window.

**The pattern.** Of four proposals, exactly one changes the guarantee, one is a purchase, one is a
scheduling tweak, and one is a misunderstanding of what the window is for. That ratio holds across
the whole bridge market, which is why the question to ask a bridge is never "how fast" but "who
waits, and what happens to them if the root is bad".
</Answer>
</Check>

## Where this pays off

**In lesson two**, every third-party design gets measured against the baseline you just established.
The honest comparison is not "which bridge is safer" but "what did this one add to the rollup's own
trust assumptions, and what did the addition buy". Lock-and-mint adds a minting authority; a
liquidity bridge adds a pool and an operator; both are answers to the two limitations Conduit
names.<Cite src="conduit-native-vs-third-party" />

**In lesson three**, the storage proof in step 2 of the withdrawal comes back as the whole design. A
storage-proof bridge is that Merkle-Patricia proof pointed at a chain that is not your settlement
layer — which immediately raises the question the native bridge never has to answer, because its root
arrives from a contract it already trusts.

**In your own systems, immediately.** Two things from this lesson are worth checking today in any
codebase that receives cross-domain messages. First, that every authorisation check on a receiving
contract tests both the messenger identity and `xDomainMessageSender()`.<Cite src="op-docs-bridging-messaging" />
Second, that your withdrawal state machine reads the on-chain proof timestamp rather than assuming
seven days from initiation.<Cite src="op-docs-withdrawal-flow" /> Both are cheap. Both have shipped
wrong in production code.
