The transaction is still there. That is the part that makes the ticket confusing.

Somebody is rebuilding a rollup's history from L1. They pull a batcher transaction from eighteen
months ago, decode it, read its `blob_versioned_hashes` field, and get back a clean list of 32-byte
values — the same list the chain has carried since the day it landed. Then they ask a beacon node for
the blobs behind those hashes and get nothing. Not a malformed response, not a timeout. The
commitment is permanent and the thing it commits to is gone.

Their first instinct is that something broke. It did not. This is the system operating exactly as
specified, and the specification says so in a sentence that is easy to read past: rollups need data
to be available once, long enough to ensure honest actors can construct the rollup state, but not
forever.<Cite src="eip-4844" />

You know [blobs](/c/blob) and [blob pruning](/c/blob-pruning) from the EVM track. This lesson is
about what that pruning means for a *guarantee* — where the line between "available" and "still
around" actually falls, how wide the window is and why that width was chosen, and what property you
are relying on the moment you step past it. That second property has a name, a much weaker security
argument, and no consensus behind it at all.

## Ethereum's native DA, stated precisely

A rollup posting to blobs gets availability with no additional trust assumption and no additional
bridge, because the chain enforcing publication is the chain settling the rollup. L2BEAT records this
as an *enshrined* bridge: full nodes download the full data for both execution-layer transactions and
consensus-layer blobs, a block is only valid if all that data is available and passes the
`is_data_available()` check, and therefore from the rollup's perspective Ethereum's canonical chain
cannot contain unavailable data commitments.<Cite src="l2beat-ethereum-da" /> No committee attests
anything. Each node checks for itself.

The on-chain footprint is small on purpose. What the execution layer stores is the versioned hash,
computed as the version byte `VERSIONED_HASH_VERSION_KZG` — `0x01` — followed by
`sha256(commitment)[1:]`.<Cite src="eip-4844" /> The blob itself is `FIELD_ELEMENTS_PER_BLOB` = 4,096
field elements of `BYTES_PER_FIELD_ELEMENT` = 32 bytes, and it lives on the consensus
layer.<Cite src="eip-4844" />

So there are two different objects with two different lifetimes, and this is the crux of the whole
lesson. The versioned hash is execution-layer state, and execution-layer state is permanent. The blob
is a consensus-layer sidecar, and sidecars have an expiry.

<Aside kind="note">
Post-Fusaka the object that is actually stored and served on mainnet is not a whole blob but a
`DataColumnSidecar`. PeerDAS extends each blob with a one-dimensional erasure code, subdivides the
result into cells, and defines a column as the cells at one index taken across every
row.<Cite src="eip-7594" /> Nodes custody columns, not blobs — which means "does the network still
have that blob" and "can this particular node hand it to me" have come apart in a way pre-2025
material does not describe.
</Aside>

## Deriving the window instead of quoting it

"About eighteen days" gets repeated everywhere. Work out where it comes from, because the derivation
tells you what would change it.

**Subgoal 1 — find the constant the spec actually states, since that is what clients implement.** The
Fulu p2p interface defines `MIN_EPOCHS_FOR_DATA_COLUMN_SIDECARS_REQUESTS` as `Epoch(2**12)`, that is
4,096, described as the minimum epoch range over which a node must serve data column
sidecars.<Cite src="consensus-specs-fulu-p2p" /> EIP-4844's equivalent for the pre-PeerDAS object,
`MIN_EPOCHS_FOR_BLOB_SIDECARS_REQUESTS`, is the same 4,096.<Cite src="eip-4844" />

**Subgoal 2 — convert epochs into slots, because the retention constant is in epochs and the clock is
in slots.** `SLOTS_PER_EPOCH` is 32.<Cite src="consensus-specs-phase0-preset" /> So 4,096 epochs is
4,096 × 32 = 131,072 slots.

**Subgoal 3 — convert slots into seconds using the live slot duration.** The mainnet config sets
`SLOT_DURATION_MS` to 12,000, one slot every twelve seconds.<Cite src="consensus-specs-mainnet-config" />
131,072 × 12 = 1,572,864 seconds.

**Subgoal 4 — put it in human units and keep the remainder, because rounding is where the myth
starts.** 1,572,864 ÷ 86,400 = 18.2 days. Not "about two weeks", not "roughly three weeks". Just over
eighteen days, and the phrase EIP-4844 itself uses is "around 18 days".<Cite src="eip-4844" />

**Subgoal 5 — notice which direction the constant binds, because this is the part that changes what
you may conclude.** The spec calls it a *minimum* range over which a node **must**
serve.<Cite src="consensus-specs-fulu-p2p" /> It is a floor on obligation, not a ceiling on
behaviour. Nothing forbids a node from keeping sidecars for a year. Equally, nothing entitles you to
one that does. Any product built on "the data will still be there at day 25 because that node kept it
last time" is built on an operator's disk policy.

That derivation also shows you what would move the number. Shortening the slot would move it: the
retention constant is denominated in epochs, so halving `SLOT_DURATION_MS` would halve the wall-clock
window without anyone editing the retention line.<Cite src="consensus-specs-mainnet-config" /> A
change to `SLOTS_PER_EPOCH` would move it.<Cite src="consensus-specs-phase0-preset" /> Blob capacity
changes, which arrive through EIP-7892 blob-parameter-only forks, would not: they alter how much data
rides in each block, not how long it lives.<Cite src="eip-7892" />

### Why 4,096 and not more

EIP-4844's rationale gives the reasoning outright. Its sustained-load argument is that there is no
expectation blobs need to be stored as long as an execution payload, which makes it possible to
implement a policy that they be kept for at least a certain period — and the specific value chosen is
around 18 days, a much shorter delay than the proposed one-year rotation times discussed for
execution payload history.<Cite src="eip-4844" />

The window is sized against the deadlines that need the data: long enough for an honest party to
reconstruct state and mount a challenge, and no longer.<Cite src="eip-4844" /> Fraud proofs need the
inputs only while a challenge can be raised. Validity proofs need them only until the proof is
produced and verified. Once both deadlines have passed, the protocol's interest in those bytes ends.

Yours does not. That is the gap.

## What you are relying on after day eighteen

The property has a name — [retrievability](/c/retrievability) — and it is worth keeping separate in
your vocabulary, because its security argument is of a completely different kind.

Celestia's documentation draws the line as sharply as anyone: data storage concerns keeping and
retrieving historical transaction data, the security assumption for storage is 1-of-N honesty — only
one honest keeper of history is needed — while data availability is about new blocks being
publishable and verifiable.<Cite src="celestia-da-faq" /> Their FAQ also names the failure precisely:
if historical data cannot be retrieved, users may lose access to history and nodes cannot sync from
genesis, and this is a retrieval problem, not an availability
problem.<Cite src="celestia-da-faq" />

Unpack the 1-of-N framing, because the shape of the assumption is what makes it both reassuring and
unreliable.

**It is weak in the good sense.** You need one honest party, not a majority, not a threshold. Any
single archive node, indexer, block explorer, rollup operator or ordinary user who kept a copy
suffices. Celestia's FAQ lists exactly those categories as the likely
keepers.<Cite src="celestia-da-faq" /> In practice, for a chain anyone cares about, someone has the
data. The hackmd write-up that popularised the framing makes the same point: this is a reasonable bet
and a materially different guarantee from the one consensus provides.<Cite src="da-retrievability-faq" />

**It is weak in the bad sense too.** Nobody is obligated. There is no slashing for failing to serve
history, no protocol rule violated by deleting it, and no way to prove that data was retrievable
yesterday and is not today. Celestia states the design intent explicitly: guaranteeing permanent
storage is not the DA layer's role, and third parties store history based on their own
incentives.<Cite src="celestia-da-faq" />

**And it degrades quietly.** A 1-of-N assumption holds until the last N fails, and there is no signal
as it thins from a thousand to three. You discover the number was one when it becomes zero.

### The same line, drawn by a DA layer that markets on DA

If you suspect this is Ethereum apologising for a limitation, look at what a purpose-built DA network
does with the same problem. Celestia's own retrievability page states that as of celestia-app v6,
celestia-node implements a light-node sampling window of seven days per CIP-36; light nodes sample
only inside that window rather than from genesis, and blobs older than the recency window are pruned
by default on light nodes while archival nodes retain
them.<Cite src="celestia-retrievability-pruning" />

Their guidance to rollup developers is blunter than anything in the Ethereum documentation: once data
has been published on Celestia and guaranteed to have been made available, rollups and applications
are responsible for storing their historical data, and developers should not rely on free archival
nodes as their only access method because archival nodes serving requests for free is not
guaranteed.<Cite src="celestia-retrievability-pruning" /> The recommended alternatives are paid
archival providers, shared snapshots, peer-to-peer historical block sync between rollup nodes, and a
future namespace-pinning mechanism.<Cite src="celestia-retrievability-pruning" />

Read those two windows next to each other — around eighteen days on Ethereum, seven for a Celestia
light node — and the conclusion is not that one layer is better. It is that **no DA layer is a
storage layer**, and every one of them says so in its own documentation.

## The wrinkle inside the window

Here is the part that surprises people who assumed the only cliff is at day eighteen.

The beacon API's blobs endpoint retrieves blobs for a given block id, optionally filtered by
versioned hash.<Cite src="beacon-apis-get-blobs" /> Its own description carries a post-Fusaka caveat:
after the Fulu fork, only supernodes — which custody all data columns — are required to return blobs,
and clients *may* implement blob reconstruction logic for non-supernodes.<Cite src="beacon-apis-get-blobs" />

That is a real behavioural change, and it follows directly from column custody. An ordinary node
custodies `CUSTODY_REQUIREMENT` = 4 custody groups and samples
`sampling_size = max(SAMPLES_PER_SLOT, custody_group_count)` groups per slot, with `SAMPLES_PER_SLOT`
= 8.<Cite src="consensus-specs-fulu-das-core" /> Out of `NUMBER_OF_COLUMNS` = 128 columns, that node
holds a small fraction and no complete row.<Cite src="consensus-specs-fulu-das-core" /> It cannot
hand you a blob because it does not have one. It could reconstruct — the spec says a node obtaining
50% or more of all columns SHOULD reconstruct the full matrix via
`recover_matrix`<Cite src="consensus-specs-fulu-das-core" /> — but an ordinary node is nowhere near
that threshold, and the API says reconstruction is optional anyway.<Cite src="beacon-apis-get-blobs" />

The practical consequence for anything you build: **"can I fetch this blob" is a question about the
endpoint, not only about the age of the data.** Two providers, same block, same versioned hash, two
different answers, both correct. Test against the endpoint you will actually use, and treat a
successful fetch on one provider as evidence about that provider.

## What this changes in a product

Four places where the eighteen-day line shows up as a real decision.

**Backfill has a horizon, so treat it as a migration rather than a query.** Any pipeline that
reconstructs L2 history from L1 blobs can only reach back as far as somebody's retained sidecars. If
your indexer needs 2024 data, that data comes from an archive service or from the rollup's own node
snapshots, not from the beacon API. Budget for it during design, because discovering it during an
incident is expensive.

**Syncing a rollup node from genesis is not a DA question.** It is a retrievability question, and
Celestia's guidance to rollup teams — own your history, use paid archival access, share snapshots,
implement peer-to-peer block sync — applies equally to a chain posting to Ethereum
blobs.<Cite src="celestia-retrievability-pruning" />

**Proof and challenge deadlines are inside the window by construction, and that is the only reason
the window is safe.** The protocol sized 4,096 epochs against exactly those
deadlines.<Cite src="eip-4844" /> If your product's dispute or reconciliation process has a longer
horizon than the chain's, you are outside the protocol's design assumption and need your own copy.

**Your own archival copy is cheap next to the alternative.** A rollup's blob throughput per day is
small compared to the cost of not being able to answer a regulator, a user, or an auditor about
something from last year. Store the batches you care about at post time, when you already have them
in memory.

<Check type="explain" concept="da-is-not-storage">
Your team indexes an L2 that posts batches to Ethereum blobs. A tester reports that historical
reconstruction "works for recent blocks and silently produces gaps for old ones", and proposes
raising the beacon client's retention setting to one year so the gaps stop.

Say whether that fixes it, and what the actual design should be.

<Answer>
**It fixes nothing that has already happened, and only partly helps going forward.** Retention is a
policy on the node you run. Raising it means your own node keeps sidecars it received from now on. It
does not conjure sidecars from before the change, because nobody is obliged to serve them: the
protocol's obligation is a minimum of 4,096 epochs, around 18
days.<Cite src="consensus-specs-fulu-p2p" /><Cite src="eip-4844" /> Your node cannot backfill what
the network no longer has to give it.

**Name what is actually happening.** Two different properties, one code path. Inside roughly eighteen
days you are exercising a consensus-backed availability guarantee, and Ethereum's own validators
enforced publication at the time via the availability check every node
runs.<Cite src="l2beat-ethereum-da" /> Outside it you are exercising retrievability, whose security
assumption is 1-of-N honest keepers with nobody obligated.<Cite src="celestia-da-faq" /><Cite src="da-retrievability-faq" />

**Why the failure is silent, which is the more serious half of the report.** A missing sidecar is not
an error state your pipeline recognises. The execution-layer transaction still exists, its
`blob_versioned_hashes` still decode, and the beacon request comes back without the payload. Nothing
in that sequence looks like a fault, so the row is skipped and the gap appears downstream. The
diagnostic that resolves the confusion in one step is checking whether the execution-layer transaction
is still present — it will be, permanently, because the commitment is execution-layer state and the
blob never was.<Cite src="eip-4844" />

**And it may not even be an age problem.** Post-Fulu, only supernodes are required to return blobs at
all; other nodes may reconstruct from their custodied columns but are not required
to.<Cite src="beacon-apis-get-blobs" /><Cite src="consensus-specs-fulu-das-core" /> Before concluding
the data is gone, ask a supernode-class endpoint for a recent blob you know is inside the window and
compare. If that fails too, the problem is your provider, not the calendar.

**The design.**

*Archive at post time.* Your batcher, or your indexer at the head, already has the batch bytes. Write
them to your own object store keyed by versioned hash the moment you see them. This is the only step
that turns a 1-of-N bet into a guarantee you control.

*Verify what you archive.* Recompute `0x01 || sha256(commitment)[1:]` and check it against the
versioned hash from the execution layer.<Cite src="eip-4844" /> An archive nobody validated is a
liability, because you will find out it drifted at the moment you most need it.

*Make the boundary explicit in the pipeline.* One flag per record: reconstructed from consensus data
inside the availability window, or read from an archive. They carry different confidence and belong
in different tables.

*Fail loudly past the boundary.* A fetch miss for a block older than the window is expected and should
be routed to the archive path; a fetch miss inside the window is either a provider problem or a real
incident, and those two cases must not share an alert.

**The one-line version for the tester.** The gaps are not a bug and cannot be configured away — they
are the difference between a guarantee the chain made about a moment in the past and a favour someone
is doing you today.<Cite src="l2beat-glossary" />
</Answer>
</Check>

## What this unlocks

- **The next lesson** goes underneath the guarantee itself: how a node that downloads a tiny fraction
  of a block can nonetheless make a defensible claim about all of it, why erasure coding is what
  makes that claim possible, and why the naive version of the probability argument is not the one the
  specification makes.<Cite src="eip-7594" />
- **Lesson four** takes this lesson's distinction somewhere sharper. If availability is enforced by
  whichever consensus set holds the data, then choosing a different holder changes who can freeze
  your users — and it changes the chain's classification, because without a DA bridge Ethereum has no
  proof of data availability for the project at all.<Cite src="l2beat-celestia-no-bridge" />
- **The module's practice** is this lesson made empirical: fetch one blob successfully, fail to fetch
  an old one, and capture the exact difference between the two responses. The write-up asks you to
  name the property you were relying on in the second case, and the answer is the word this lesson
  spent its length separating from the first.

The habit worth forming: any time a system hands you a hash of something, ask who is holding the
something, for how long, and under what obligation. On Ethereum the answers are the consensus layer,
4,096 epochs, and a `MUST` in the p2p spec.<Cite src="consensus-specs-fulu-p2p" /> After that, the
answers are whoever felt like it, indefinitely, and nothing.
