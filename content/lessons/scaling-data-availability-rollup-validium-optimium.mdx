Two teams deploy the same stack in the same week. Same contracts, same client binaries, same version
tags, same sequencer software, same fault proof program. One of them appears on L2BEAT under
"Rollups". The other appears under "Validiums and Optimiums".<Cite src="l2beat-da-scaling" />

The difference is a configuration choice about where the batcher sends its bytes.

That is not a quirk of one framework. The OP Stack ships alt-DA as a documented mode of the
protocol: switching to it means switching to an off-chain data availability provider, with the
batcher uploading data to the DA layer and submitting only a commitment as the batcher inbox
transaction's calldata.<Cite src="op-specs-alt-da" /> Everything else in the derivation pipeline
stays where it was. So "is this chain a rollup" stopped being a property of the stack somebody built
on and became a per-deployment question, answerable only by reading that deployment's
configuration — a specific instance of [configurability not being freedom](/c/configurability-is-not-freedom).

This lesson turns that one question into a taxonomy you can apply, then goes underneath the labels to
the machinery: what a committee actually signs, what a DA bridge actually verifies, and what happens
on the OP Stack when someone challenges an availability claim on L1.

## One question, three labels

L2BEAT's definition is a single sentence and it does all the work. A rollup must choose a DA layer
that guarantees any node can retrieve its data permissionlessly under any circumstance, and if data
is stored somewhere other than a permissionless L1, then the project is not a rollup but rather a
validium or an optimium.<Cite src="l2beat-glossary" />

The two off-chain labels split on proof type, and only on proof type:

- **Validium** — an off-chain solution that uses validity proofs for settlement and publishes the
  data off-chain, therefore requiring an additional trust
  assumption.<Cite src="l2beat-glossary" />
- **Optimium** — an off-chain solution that uses fraud proofs for settlement and publishes the data
  off-chain, therefore requiring an additional trust assumption.<Cite src="l2beat-glossary" />

There is a fourth entry worth knowing because it dissolves the idea that a chain has one answer.
**Volition** is a hybrid data availability mode where the user can choose whether to place data
on-chain or off-chain.<Cite src="l2beat-glossary" /> StarkEx implements it concretely for spot
trading: two vault ranges in the same deployment, one ZK-Rollup and one validium, and a user moves an
asset between them by transferring it into a vault on the other
tree.<Cite src="starkex-data-availability" /> On such a chain, "what is my DA guarantee" is a
per-position question.

### A second axis the label does not capture

"Where" is the sorting question, but L2BEAT's per-chain rows also record *what kind* of data goes
there, and the column separates rollups that post transaction data from rollups that post state
diffs, with most rows additionally marked compressed.<Cite src="l2beat-da-scaling" /> The distinction
is not cosmetic. Transaction data lets anyone re-execute and derive the state independently. State
diffs let anyone apply the changes and arrive at the same state without being able to re-derive how
it got there — cheaper per transaction, and it means the published data is only as trustworthy as the
proof system that vouched for the transition. Both count as a rollup under the taxonomy. They give a
reconstructing party different starting material, which matters the day you are the reconstructing
party.

### Why the axis is availability rather than proofs

The taxonomy could have been built on proof type. Everyone's instinct says it should be — proofs are
the thing that sounds like security. L2BEAT built it on DA instead, and the reason is worth stating
because it is the module's thesis in one line.

**A proof failure and an availability failure are not the same kind of event.** If a proof system is
broken or dormant, an incorrect state can be committed — and that is a violation, detectable in
principle, and something an L1 contract or a watcher can be built to catch. If data is withheld, no
rule has been broken. Every contract behaves as designed. There is nothing to detect and nothing to
challenge, and the users are nonetheless unable to compute their own balances.

Note also which way this cuts. The label says nothing about proof strength: an optimium and a
validium differ only in proof type and sit in the same bucket, while a chain using the weakest live
proof system on Ethereum blobs is still a rollup. That is deliberate, and it pairs with the stage
framework, which measures governance rather than either axis. Three independent questions, three
frameworks, [no averaging](/c/proof-type-is-not-trust-level).

## Alt-DA: what you buy and what you sign up for

Alternative DA means publishing a chain's data to a network other than Ethereum, and having the
chain's L1 contracts accept some attestation that publication happened. AltLayer's integration
documentation is a fair picture of how mundane this is in practice — a rollup framework wires a DA
adapter and the batches go elsewhere.<Cite src="altlayer-celestia-da" />

The saving is real. So is the substitution: availability is now enforced by that network's validator
set or committee rather than by Ethereum's validators running their own availability
check.<Cite src="l2beat-ethereum-da" />

L2BEAT scores this on two groups of risks, and the split is the most useful thing in the framework
because the two groups fail independently. **DA layer risks** are economic security and fraud
detection. **Bridge risks** are committee security, upgradeability and relayer
failure.<Cite src="l2beat-da-risk" />

Reading the live rows tells you what the labels mean in practice. As of this writing, the risk table
records Celestia and Avail as "Staked assets" for economic security and "DAS" for fraud detection,
while EigenDA is recorded as "No slashing" and "None"; on the bridge side, Blobstream and Vector are
"Validator set / No delay / No mechanism", and EigenDA's DACert Verifier is "Permissioned / No delay /
Self propose".<Cite src="l2beat-da-risk" /> Those are live classifications on a page that updates, so
treat the shape as the lesson and re-read the page for the values.

<Aside kind="warn">
**EigenDA's slashing status is genuinely contested and should not be taught either way.** L2BEAT's
project page records economic security as "No slashing", noting that operators stake a minimum in the
relevant quorums and that although slashing is enabled at the EigenLayer protocol level, individual
services like EigenDA must activate it.<Cite src="l2beat-eigenda" /> Other write-ups describe
restaked economic security as the design's central pitch. The research pass behind this module
recorded the question — whether EigenDA slashing is live and enforced — as unresolved. Check the
current L2BEAT row and EigenDA's own release notes before repeating either claim.
</Aside>

### The comparison that is not worth making

Throughput. Every alt-DA layer publishes a bigger number than Ethereum's blob capacity, and the
number is close to irrelevant for a decision, because a chain with meaningful value is not usually
DA-capacity-bound and because the numbers move with every parameter change.

The comparison that *is* worth making is the shape of the trust. Celestia is its own proof-of-stake
chain whose light nodes verify availability by sampling an erasure-coded matrix, and it commits to
publishing data rather than to storing it.<Cite src="celestia-da-101" /><Cite src="celestia-da-faq" />
Avail is its own chain combining erasure coding, KZG commitments and DAS, with a block reconstruction
protocol L2BEAT records as still under development.<Cite src="l2beat-avail-vector" /> EigenDA is a
service on restaked collateral rather than a standalone chain, which is a different failure surface
before any number is compared.<Cite src="l2beat-eigenda" />

## The DA bridge is the distinction that matters

Here is the part most comparisons skip entirely, and it is sharper than the choice of layer.

A **DA bridge** is an L1 contract that verifies an external DA layer's claim that data was published.
Its presence or absence decides what your rollup's L1 contracts can do about a false claim. With a
bridge, they can at least reject a commitment that carries no valid attestation. Without one, they
accept the operator's word and there is nothing on L1 that even represents the question.

L2BEAT states the consequence flatly on the no-bridge configuration: without a DA bridge, Ethereum
has no proof of data availability for this project.<Cite src="l2beat-celestia-no-bridge" />

This is why the same DA layer appears more than once in L2BEAT's listing — the entry is not the
layer, it is the *layer plus bridge* pair. Celestia is listed both with no bridge and with Blobstream;
EigenDA both with its DACert Verifier and with no bridge; Espresso with a light client and with a TEE
bridge; Avail with Vector.<Cite src="l2beat-da-summary" /><Cite src="l2beat-da-risk" /> Two chains
can both say "we use Celestia" and be in different risk categories, and the sentence "we use
Celestia" does not distinguish them.

Bridges come in recognisable shapes, and each shape names what your L1 contract is actually checking:

**A committee threshold.** The contract verifies k-of-n signatures over a data commitment. What it
checks is that k keys signed, which is a statement about key custody rather than about bytes existing
anywhere.

**A light client.** The contract verifies the DA chain's consensus — headers, signatures, sometimes a
proof — and thereby inherits that chain's own availability conclusion. Stronger, and now your L1
contract's correctness depends on a second chain's fork choice being correctly implemented in
Solidity.

**A challenge game.** The contract holds no attestation at all and instead lets anyone force
publication on L1. This is the OP Stack's design, below.

**Nothing.** The commitment is recorded and accepted.<Cite src="l2beat-celestia-no-bridge" />

## What a data availability committee actually does

Strip the acronym. A **DAC** is a named, fixed set of members who sign attestations that they hold a
chain's data, and an on-chain verifier checks that a threshold of those signatures is reached before
a data commitment is considered available and therefore valid to use in the
system.<Cite src="l2beat-glossary" />

StarkEx's documentation describes the working version of exactly this. In validium mode users'
balances are not published on-chain; they are sent to several well-known and trusted parties who are
members of the DAC, and a state update is valid and accepted on-chain only if at least a quorum of
committee members sign it — signing specifically that they know all the new vault balances
determining the new state, as enforced by the availability
verifiers.<Cite src="starkex-data-availability" /> Members run a Committee Service that validates the
data availability of a batch and sends a signed approval, and StarkEx does not submit a new on-chain
state without that approval.<Cite src="starkex-data-availability" />

Read that closely and the security property falls out.

**The signature attests to knowledge, not to publication.** A member signs that it *has* the data.
Nothing in the mechanism makes that member give the data to you. The committee is a set of custodians
whose honesty you are trusting, and StarkEx says so in one line: using a DAC requires trust in the
committee members.<Cite src="starkex-data-availability" />

**The threshold is where the whole guarantee lives.** If enough members collude or are compromised
they can attest to data that was never published, and the L1 verifier will accept the corresponding
commitment because from its position the signatures are all that exist. Three parameters decide how
plausible that is: how many members, what threshold, and how independent the members really are —
distinct organisations, distinct jurisdictions, distinct key custody, distinct infrastructure. A
seven-member committee where five run on the same cloud account under one company's IAM is a
one-member committee with extra steps.

**"Well-known and trusted" is doing load-bearing work.** The construction's honesty is social. That
is not automatically bad — it is how a great deal of finance operates — but it is a different
category of assurance from "every Ethereum validator independently refused to attest until it could
sample the data",<Cite src="l2beat-ethereum-da" /> and a product's risk disclosure should not use one
sentence for both.

## The OP Stack's alt-DA mode, concretely

The most instructive middle case is the one where L1 gets a mechanism rather than an attestation.

**What gets posted.** Batching and compression are unchanged. When a batch is ready, the data is
uploaded to the DA storage layer instead of the inbox, and a commitment is submitted as the batcher
inbox transaction's calldata.<Cite src="op-specs-alt-da" /> Commitments are encoded as a commitment
type byte followed by the commitment bytes: type 0 is `keccak256(tx_payload)`, type 1 is a
`da-service` commitment consisting of a DA layer byte followed by a
payload.<Cite src="op-specs-alt-da" /> The spec's own examples assign distinct DA layer bytes to
EigenDA, Avail and Celestia commitments.<Cite src="op-specs-alt-da" />

**How availability is enforced.** Not by verifying an attestation — by a permissionless challenge
contract on L1. Challenging an input commitment means forcing providers to submit the input data
on-chain to prove it is available within a time period. The period during which any party can
challenge is the `challenge_window`, the period during which any party can submit the data to resolve
a challenge is the `resolve_window`, and if a challenge is not resolved by the time `resolve_window`
L1 blocks have passed, chain derivation must be reset, omitting the input data and therefore causing
a reorg.<Cite src="op-specs-alt-da" />

**Why the economics are designed the way they are.** The contract requires a payable bond making a
challenge at least as expensive as submitting the data on-chain to resolve it, which mitigates a
denial-of-service vector; the reward is deliberately not net positive for the challenger who forced
the release, preventing a money pump while keeping challenges affordable to altruistic fishermen and
to users who want to pay for on-chain availability.<Cite src="op-specs-alt-da" /> A challenger is
someone spending money to make data appear, not someone farming a bounty.

**What it costs users.** Latency, in a place that is easy to miss. Under alt-DA the engine queue
receives finality signals from the L1 RPC *and* from a DA manager tracking challenges. Commitments
are only "optimistically safe" when found in an L1 block and become safe only when they can no longer
be invalidated, so the queue maintains a longer buffer of L2 blocks waiting for the DA window to
expire before signalling finality.<Cite src="op-specs-alt-da" /> The specification also warns
directly that although blocks are labelled safe, the chain might still reorg in the case of a faulty
DA provider, and users must use the finalized label for a guarantee their state cannot
revert.<Cite src="op-specs-alt-da" />

<Aside kind="note">
The OP Stack's own specification labels alt-DA a Beta feature that has received initial review from
core contributors, is still undergoing testing, and may have bugs or other
issues.<Cite src="op-specs-alt-da" /> That sentence belongs in any risk write-up about a chain
running this mode, quoted rather than paraphrased.
</Aside>

## Worked example: classifying a chain from primary sources

Somebody hands you a chain and asks what it is. Five subgoals, each naming what the step is for.

**Subgoal 1 — find the batcher's destination, because that single fact decides the label.** Look at
what the L1 inbox transaction carries. Blob versioned hashes, or calldata containing the batch, mean
the data is on a permissionless L1 and the chain is a rollup.<Cite src="l2beat-glossary" /> A short
commitment means it is not, and on the OP Stack the commitment's type byte and DA layer byte tell you
which provider.<Cite src="op-specs-alt-da" />

**Subgoal 2 — identify the proof type, because that picks which of the two off-chain labels
applies.** Validity proofs make it a validium; fraud proofs make it an
optimium.<Cite src="l2beat-glossary" /> This step is second, not first, and doing it first is the
error the whole taxonomy exists to prevent.

**Subgoal 3 — find the DA bridge, because this is the sharpest risk difference and it is not implied
by the layer.** What contract on L1, if any, verifies that publication happened? A signature
threshold, a light client, a challenge contract, or nothing. Without a bridge, Ethereum has no proof
of data availability for the project at all.<Cite src="l2beat-celestia-no-bridge" />

**Subgoal 4 — score the layer and the bridge separately, because they fail separately.** Economic
security and fraud detection for the layer; committee security, upgradeability and relayer failure
for the bridge.<Cite src="l2beat-da-risk" /> A staked, sampling DA layer behind an instantly
upgradeable bridge is not a strong configuration, and averaging the two hides that.

**Subgoal 5 — write the freeze sentence, because that is what the analysis was for.** One sentence
naming who would have to misbehave for a user to be unable to withdraw. For a rollup that sentence is
awkward to write, which is informative. For a validium it is short: the operator, or the committee,
by declining to hand over data no rule requires them to hand over.

<Answer>
**Classification: not a rollup.** Under L2BEAT's definition, if data is stored somewhere other than a
permissionless L1 then the project is a validium or an optimium, not a
rollup.<Cite src="l2beat-glossary" /> Which of the two depends on the proof system: validity proofs
make it a validium, fraud proofs an optimium.<Cite src="l2beat-glossary" /> The paragraph says
"proofs" without saying which, and that is the second thing to find out.

**What "settlement and proofs on Ethereum" does and does not buy.** It buys verification that each
transition was legal. It does not buy the ability to reconstruct the state those transitions produced,
because the verifier contract consumes a proof and public inputs rather than the batch. Availability
is enforced by whichever consensus set holds the data — here Celestia's validators, not
Ethereum's.<Cite src="l2beat-ethereum-da" />

**The omission, and it is the whole finding: no DA bridge is mentioned.** L2BEAT lists Celestia as
two separate entries, one with no bridge and one with Blobstream, precisely because the pair is what
determines risk.<Cite src="l2beat-da-summary" /> If this chain has no bridge, Ethereum has no proof
of data availability for it, and the L1 contracts accept the sequencer's word that publication
happened.<Cite src="l2beat-celestia-no-bridge" /> Naming the DA layer and not the bridge describes
the stronger half of the arrangement.

**Question one: which Celestia configuration — bridged or not?** If bridged, what does the L1 contract
verify, and can a state commitment be rejected when the corresponding attestation is absent? If not
bridged, say so plainly in the user-facing disclosure, because that is the configuration where the L1
has no representation of the availability question at all.<Cite src="l2beat-celestia-no-bridge" />

**Question two: what is the withdrawal path when the sequencer stops cooperating?** A withdrawal
requires a proof against the chain's state, which requires the state, which requires the data. Ask
where a user obtains the data in that scenario, from whom, and under what obligation — and note that
Celestia itself commits to publishing data rather than storing it, with historical retrieval resting
on a 1-of-N honest-archiver assumption.<Cite src="celestia-da-faq" /> "Ask the sequencer" is not an
answer to a question about the sequencer failing.

**On the cost claim.** Take it as true and irrelevant to classification. Blobs made L1 data a minor
line item for most rollups, so a large multiple on a small number is a small
saving<Cite src="eip-4844" /> — and price is precisely the axis L2BEAT's framework declines to sort
on.<Cite src="l2beat-da-summary" />

**The honest one-liner for a product's docs.** "Transactions are proven on Ethereum. The data needed
to compute your balance and build a withdrawal lives on Celestia, and if it becomes unavailable your
funds cannot be moved even though every proof remains valid." If the team resists that sentence, the
resistance is the risk assessment.
</Answer>

## What this unlocks

- **You can read a DA risk page as five independent questions** rather than one impression: where the
  data goes, what proves the state, what bridge exists, how the layer and bridge score separately,
  and who has to misbehave for a user to be stuck.<Cite src="l2beat-da-risk" />
- **You can read a chain's configuration rather than its stack.** Alt-DA is a mode of the OP Stack,
  not a different product, so the answer for a given chain lives in its deployment config and its
  batcher inbox transactions.<Cite src="op-specs-alt-da" />
- **The next lesson is the failure this taxonomy exists to isolate.** A valid proof over data nobody
  has: every contract behaving correctly, no rule broken, no misbehaviour provable on L1, and users
  who cannot construct the one thing a withdrawal requires.

Before that, one exercise worth ten minutes: open the L2BEAT DA summary, pick a project using an
external layer, and follow it through to its bridge row. Then find a second project on the same layer
with a different bridge. Those two chains describe their DA identically in their own documentation,
and they are not in the same risk category.<Cite src="l2beat-da-summary" />
