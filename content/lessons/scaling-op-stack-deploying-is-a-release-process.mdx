The deployment tutorial ends well. Contracts are on L1, the genesis file is written, the node comes
up, a transaction lands. It feels finished.

It is not a finish; it is an enrolment. What you have actually done is put a chain onto a version, and
versions move. From here the recurring work is adopting releases on somebody else's calendar,
keeping five components' versions mutually compatible, and living with a set of configuration choices
that quietly determined what your chain will be called by everyone who classifies chains for a living.

This lesson is about that shape: the deployment tool, the contract that owns your contracts, the
release calendar, and the knobs that cost you a classification.

## The tool exists to make deployments comparable

`op-deployer` is declarative. You define the chain's desired configuration in a configuration file and
the tool makes the minimum number of smart contract calls required to make the deployment match that
configuration, abstracting away the implementation details of the
deployment.<Cite src="op-docs-op-deployer-overview" /> The design goal is stated as making doing the
right thing easy and doing dangerous things hard — the configuration and API are optimised for
deploying and upgrading Standard OP Chains, with lower-level primitives available for more complex
configurations.<Cite src="op-docs-op-deployer-overview" />

Two commands carry the flow. `op-deployer init` takes an L1 chain ID, a list of L2 chain IDs, an
output directory and an `--intent-type` of `standard`, `custom` or `standard-overrides`, and writes
two files: `intent.toml`, where you specify the configuration, and `state.json`, where the tool
outputs the current state of the deployment after each stage.<Cite src="op-docs-op-deployer-init" />
`op-deployer apply` then performs the deployment against that
intent.<Cite src="op-docs-op-deployer-apply" />

The intent file is where the interesting decisions live, and it is short enough to read in one screen.
It carries a `configType`, an `l1ChainID`, `useInterop`, and — the part that matters most — an
`l1ContractsLocator` and `l2ContractsLocator` in the form `tag://op-contracts/vX.Y.Z`, plus a
`[chains.roles]` block naming `l1ProxyAdminOwner`, `l2ProxyAdminOwner`, `systemConfigOwner`,
`unsafeBlockSigner`, `batcher`, `proposer` and `challenger`.<Cite src="op-docs-op-deployer-init" />

**Subgoal: notice that the version is an input, not a consequence.** Your chain is not "deployed with
the OP Stack". It is deployed at a tag, and that tag is a line in a file you wrote. Everything later
in this lesson is a consequence of that line changing over time.

**Subgoal: notice that the security posture is also an input.** The docs split the roles by key
handling: cold-wallet multisigs such as Gnosis Safes are recommended for the fee vault recipients,
`l1ProxyAdminOwner`, `l2ProxyAdminOwner` and `systemConfigOwner`, while HSMs are recommended for the
hot wallets — `unsafeBlockSigner`, `batcher`, `proposer` and
`challenger`.<Cite src="op-docs-op-deployer-init" /> The key-management guide makes the same division
from the operational side: batcher and proposer addresses need their private keys online somewhere for
a component of the system to work, and if these addresses are compromised the system can be
exploited.<Cite src="op-docs-key-management" /> A dev deployment where every role is the same EOA is
fine, and the docs say so; the warning is that all the zero values must be replaced with something
appropriate before you use the intent for a real deployment.<Cite src="op-docs-op-deployer-init" />

### Four deployment targets, and the useful one

`apply` takes a `--deployment-target`, defaulting to `live`:<Cite src="op-docs-op-deployer-apply" />

- `live` — sends transactions to a real L1; requires an RPC URL and a private key.
- `genesis` — deploys to an L1 genesis file, for testing or local development.
- `calldata` — deploys to a calldata file, useful for generating inputs to multisig wallets for
  future execution.
- `noop` — deploys nothing; a dry run before another target.

`calldata` is the one that reveals the intended shape of a production deployment. It exists because
the entity that should authorise your chain's contracts is a multisig that cannot hold a hot key and
run a CLI. So the tool produces the transaction, the humans produce the signatures, and the two are
separated in time. That separation is what an audited deployment looks like.

The docs also close one worry directly: ownership over each L2 is transferred to the proxy admin owner
specified in the intent after the deployment completes, so it is acceptable to use a hot key for the
deploying signature itself.<Cite src="op-docs-op-deployer-apply" />

<Aside kind="warn">
Development status is published and worth quoting rather than paraphrasing: OP Deployer is under
active development, has been used for several mainnet deployments and is considered production-ready —
and it has not been audited, so chains deployed with it should be checked thoroughly for correctness
prior to launch.<Cite src="op-docs-op-deployer-overview" /> "Production-ready and unaudited" is an
unusual pair of words to see together, and it belongs in your launch checklist rather than in a
footnote.
</Aside>

### Why it is mandatory rather than recommended

The registry's operations document is blunt: if you are deploying a standard chain, it *must* be
deployed with `op-deployer` to be considered standard in the Superchain
Registry.<Cite src="superchain-registry-ops" /> If you do not use it, you will need to manually create
your config file and follow the custom-chain path.<Cite src="superchain-registry-ops" />

The mechanism explains the mandate. Registry onboarding runs `just create-config <shortname> <path to
your state file>` against the `state.json` that `op-deployer`
produced.<Cite src="superchain-registry-ops" /> The registry does not validate your chain by reading
your prose; it validates a machine-readable artefact your deployment emitted. A bespoke script can
produce a perfectly good chain and cannot produce that artefact, which means it cannot be checked
mechanically against the charter — and a deployment nobody can check is indistinguishable, from the
outside, from a subtly non-standard one.

## The contract that owns your contracts

`op-deployer` is the operator-facing half. The on-chain half is the **OP Contracts Manager**.

OPCM deploys and upgrades an OP Stack chain's L1 contracts, and the version it deploys is always a
governance-approved contract release — the set of releases named
`op-contracts/vX.Y.Z`.<Cite src="op-docs-opcm" /> There is a new OPCM instance for each smart contract
release, and it addresses three deployment aspects: shared contracts, which are used between many OP
chains and are deployed only occasionally; shared implementation contracts, deployed once per contracts
release; and the per-chain contracts, deployed for every OP chain
deployment.<Cite src="op-docs-opcm" /> After the Upgrade 13 network upgrade, OPCM instances are also
used to upgrade existing OP Stack chains.<Cite src="op-docs-opcm" /> The fault proof system OPCM
deploys uses the `PermissionedDisputeGame`.<Cite src="op-docs-opcm" />

That last clause is the sentence to underline. **A newly deployed chain does not have permissionless
fault proofs.** It has a permissioned dispute game and a named proposer, and moving beyond that is a
separate project with its own guide: configure the dispute components, deploy the contracts with OPCM,
test the off-chain agents, and switch the respected game type — four phases, with a recommended
minimum contracts version of `v5.0.0` and a requirement to be already operating `op-challenger` and
`op-dispute-mon`.<Cite src="op-docs-migrating-permissionless-current" /> The docs describe permissioned
games as previously relying on a single trusted validator, typically the proposer configured in the
`PermissionedDisputeGame` and usually the network's only
sequencer.<Cite src="op-docs-migrating-permissionless-current" />

Hold that against the registry census from the last lesson: 20 of 31 mainnet entries record
`faultProofs.status` as `permissioned` and 8 record `none`, against 3
`permissionless`.<Cite src="superchain-registry-chainlist" /> That distribution is not a mystery. It is
what happens when the default deployment produces a permissioned system and the migration to
[permissionless challenging](/c/permissionless-challenging) is a deliberate, staffed piece of work that
somebody has to schedule.

The specification frames OPCM's purpose as versioning: it is the mechanism by which
"governance-approved release" becomes something a contract set either is or is
not.<Cite src="op-specs-op-contracts-manager" /> Upgrades move a chain from one version to another as
a unit. A partial or bespoke upgrade is therefore visible as a deviation rather than hidden inside a
directory of individually-deployed contracts.

### What the upgrade call actually does

The specification is worth reading once, because it turns "governance approves an upgrade" from a
phrase into a transaction with a shape you can reason about.

`upgrade` takes an array of `OpChainConfig` structs — a `systemConfigProxy`, a `proxyAdmin` and an
`absolutePrestate` per chain — and is intended to be called via `DELEGATECALL` from the Proxy Admin
Owner Safe. It emits an `Upgraded` event per chain and **reverts if the upgrade is not successful for
any of the chains**.<Cite src="op-specs-op-contracts-manager" /> Internally it upgrades
`SuperchainConfig` and `ProtocolVersions` if not already done, then walks each chain's address list
calling `ProxyAdmin.upgradeAndCall` where new state variables are being set and `ProxyAdmin.upgrade`
otherwise — which requires that any contract receiving new state variables has an upgrade function
that writes them and MUST only be callable once.<Cite src="op-specs-op-contracts-manager" />

Three consequences fall out, and each one is a thing you would otherwise learn during an incident.

**Many chains upgrade in one transaction, and they succeed or fail together.** That is the mechanical
meaning of a Superchain-wide upgrade. It is also a constraint with a ceiling: the spec notes that when
the superchain nears the block gas limit, upgrades may need to be broken into stages so that
components which must be upgraded atomically can be — for example, all `OptimismPortal` contracts in
one transaction followed by all `L1CrossDomainMessenger` contracts in
another.<Cite src="op-specs-op-contracts-manager" /> The number of chains that can be governed as one
unit is bounded by L1 gas.

**Chain-specific values must live in storage, not bytecode.** All contracts used in an OP Chain should
be proxied with a single shared implementation, so values that are not constant across chains should be
held in storage; contracts that do not meet this will need to be deployed by the `upgrade` function
itself, increasing cost and reducing the number of chains that can be atomically
upgraded.<Cite src="op-specs-op-contracts-manager" /> This is the technical reason "we forked one
contract" is expensive rather than merely non-compliant.

**`DELEGATECALL` from a Safe is the risky part, and the docs treat it that way.** Because the Safe
delegate-calls into `upgrade` and `addGameType`, it is critical that no storage writes occur, enforced
by static analysis during development and by simulating and verifying the state changes in the Proxy
Admin Owner Safe prior to execution.<Cite src="op-specs-op-contracts-manager" /> That is exactly the
simulate-and-inspect step `superchain-ops` builds its workflow around, and the reason that workflow is
deliberately manual.

The `addGameType` method exists for the same reason the permissioned-to-permissionless migration
exists: different chains within a Superchain may use different dispute game types and are expected to
move from a permissioned to a permissionless game over time, so the method adds a game type to
multiple chains at once.<Cite src="op-specs-op-contracts-manager" />

## The calendar you have joined

Here is the part no deployment guide frames honestly, because it happens after the guide ends.

There are **two kinds of upgrade**, and the docs separate them precisely: hardforks activate by L2
block timestamp on every chain, while contract upgrades ship as `op-contracts` releases and are
executed on each chain's L1 contracts after governance approval — contract-only upgrades have no
activation timestamp, so they do not get hardfork registry
pages.<Cite src="op-docs-network-upgrades" /> Both exist, they interleave, and a chain has to track
both.

The hardfork side comes with an unforgiving line: failing to upgrade your OP Stack software before the
activation timestamp causes a chain divergence, and you will need to resync the
chain.<Cite src="op-docs-network-upgrades" />

The release history lines up with it: `op-contracts/v7.0.0` was published 25 June 2026 as the release associated with
Upgrade 19, with `v6.0.0` before it on 16 March 2026 for Upgrade 18, and `v8.0.0-rc.3` posted 13 August
2026 as a release candidate for Upgrade 20 — a release the page notes does not include a hard fork, so
L2 predeploy changes will not be deployed.<Cite src="op-docs-op-contracts-releases" />

The governance step in front of all this is public and slow by design. The upgrade process runs devnet,
then testnet, then a mainnet phase containing a Governance Voting Review Period, a Governance Voting
Period, a Veto Period during which the Citizens' House can veto a protocol upgrade approved by the
Token House, a mainnet release cut, and a Mainnet Upgrade Notice Period before
activation.<Cite src="op-docs-network-upgrades" /> "Baking" is the documented term for the interval
where software is live and engineers observe its behaviour on production
networks.<Cite src="op-docs-network-upgrades" />

### The tooling ceiling nobody expects

One concrete trap, published as a warning. The `op-deployer upgrade` command can be used for upgrades
up to `op-contracts/v5.0.0`, and does **not** support upgrading from `v5.0.0` to `v6.0.0`; beyond
v5.0.0 you use `superchain-ops` or interact with OPCM
directly.<Cite src="op-docs-op-deployer-upgrade" /> The supported paths are enumerated and stepwise —
`v1.8.0` to `v2.0.0` on op-deployer `v0.2.x`, `v2.0.0` to `v3.0.0` on `v0.3.x`, and so on — because
each minor version of `op-deployer` supported a single release of the governance-approved
contracts.<Cite src="op-docs-op-deployer-upgrade" />

So the tool that deployed your chain is not the tool that will upgrade it past a certain point.
`superchain-ops` is described as intended primarily for chains managed by the Security Council, chains
with the Foundation or Security Council as signers, and chains requiring a highly secure process; for
chains outside those categories, you interact with OPCM directly using your own
tooling.<Cite src="op-docs-superchain-ops-guide" /> Its workflow is templates and tasks: templates
define a specific upgrade path and are version-specific, tasks apply a template to a chain, and the
process is intentionally manual with thorough verification steps such as EVM state diff
inspection.<Cite src="op-docs-superchain-ops-guide" />

## Every knob costs you a classification

The tooling will not stop you deviating. `op-deployer` can be configured to support L3s, alt-DA and
custom gas token chains,<Cite src="superchain-registry-ops" /> and the registry docs note that
overrides are allowed — an L2 block time of 1 second is an override that remains standard — while
warning that overrides may violate standard specifications.<Cite src="op-docs-superchain-registry" />

What the tooling does not do is tell you what your chain becomes afterwards. Line the answers up:

- **Alt-DA.** Standard Rollups must adhere to the default data availability
  model,<Cite src="op-docs-blockspace-charter" /> and alt-DA's own page states it will always have more
  trust assumptions than posting data to L1 Ethereum, fully trusting the chain operator to make data
  available in its current iteration with generic commitments.<Cite src="op-docs-alt-da-mode" /> This
  is the [rollup-versus-validium](/c/rollup-vs-validium) line, and crossing it changes what external
  classifiers call your chain.
- **Modified system contracts.** Modifications invalidate compliance.<Cite src="op-docs-blockspace-charter" />
- **Beta features.** Not standard until governance approves them post-beta.<Cite src="op-docs-blockspace-charter" />
- **A custom gas token.** Supported as an OP Stack feature<Cite src="op-docs-custom-gas-token" /> and
  visible in the registry as a `gasPayingToken` field.<Cite src="superchain-registry-chainlist" />
- **Keeping permissioned proofs.** Not refused by anything; simply the state you remain in until you
  run the migration.<Cite src="op-docs-migrating-permissionless-current" />

- **Deploying as an L3.** Also supported by the tool,<Cite src="superchain-registry-ops" /> and the
  most far-reaching of the set, because it changes what "L1" means for every claim in this module. Your
  derivation function's input is another rollup's chain, so your data availability, your finality and
  your escape hatch are all now conditional on that chain's, and the registry's own parenting field
  records what a chain hangs off — the mainnet entries in `chainList.json` are parented to `mainnet`,
  while others are parented to `sepolia` or to a devnet.<Cite src="superchain-registry-chainlist" />

The pattern across all six is the same, and it is the reason the concept is called *configurability is
not freedom* rather than *configurability is dangerous*. Nothing on that list is refused. Nothing on
it emits a warning at deploy time. Each one is simply reflected in what the chain is afterwards — in
the registry fields anyone can read, in the charter's own answers, and in how external classifiers
describe you to your users. The deployment decision and the classification decision are one decision,
taken in an afternoon, and only one of them appears in the plan.

Automata Mainnet is the whole argument in one file: `governed_by_optimism = false`,
`data_availability_type = "alt-da"`, a `gas_paying_token` address, an `[alt_da]` block with a challenge
contract and 3,600-block challenge and resolve windows, `seq_window_size = 7200`, and a hardfork table
that stops at `fjord_time`.<Cite src="superchain-registry-automata-config" /> Every one of those is a
legitimate choice somebody made deliberately. Together they are a chain that the charter excludes, that
external stage frameworks will classify on its own terms, and whose upgrade path is its operator's to
maintain.

## Where this pays off

**The final lesson** takes the last configuration decision — joining an interop dependency set — and
shows why it is the one with no undo. Every knob in this lesson can be revisited at some cost; that one
is specified as irreversible.

**The module's reflection prompt** asks you to name a human owner for the batcher, the proposer, the
challenger, the upgrade key, the decision to adopt a release, and the user who cannot withdraw. This
lesson is where those six roles stop being abstractions: four of them are lines in `intent.toml`, one
is a governance calendar, and the last one is what happens when nobody owns the other five.

**Your own evaluation work.** When a vendor offers rollup-as-a-service, the questions that separate
offers are not about deployment. They are: who adopts contract releases and on whose schedule; who
holds the `ProxyAdminOwner`; whether `op-challenger` runs; and what happens on the next hardfork
timestamp if the vendor is having a bad quarter.
