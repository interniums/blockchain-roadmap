The last lesson left you with a claim and no machinery: `op-node` is a derivation engine, and the
rollup chain is a pure function of the L1 chain. The specification even writes the signature.

That is a pure function.<Cite src="op-specs-protocol-overview" /> Everything interesting about an OP
Stack chain follows from taking it literally. This lesson works the function out — what its inputs
are, what the eight stages between input and output do, and what it costs to be a function rather
than a protocol. Then it draws the security conclusion, which is the reason the module opens here
rather than with contracts.

## The unit of input is an L1 block

Start with the domain. Derivation does not consume "L1 data" as an undifferentiated stream; it
consumes L1 blocks one at a time, and each one becomes a named unit.

Each L1 block following L2 chain inception is mapped to a **sequencing epoch** comprising at least
one L2 block. Each L2 block belongs to exactly one epoch, and the corresponding L1 block is its
**L1 origin**. The epoch's number equals that of its L1 origin block.<Cite src="op-specs-derivation" />

To derive the L2 blocks of epoch `E`, the specification lists exactly five inputs:<Cite src="op-specs-derivation" />

1. The L1 blocks in the range `[E, E + SWS)` — the **sequencing window**, of size `SWS`. Note that
   windows overlap.
2. The batcher transactions in those blocks, from which the epoch's sequencer batches are
   reconstructed. An epoch may have no sequencer batches at all.
3. The deposits made in the L1 origin, as events emitted by the deposit contract.
4. The L1 block attributes of the origin, from which the L1 attributes deposited transaction is
   built.
5. The state of the L2 chain after the last L2 block of the previous epoch — or the L2 genesis
   state, if `E` is the first epoch.

Read that list as a function signature and one thing jumps out: the sequencer is not in it. Not as a
parameter, not as an oracle, not as a fallback. Every input is either already on L1 or is the output
of the previous application of the same function. That is what "pure" is doing in the earlier
sentence, and it is the whole security argument in compressed form.

<Aside kind="note">
The specification notes an asymmetry worth holding on to: the L1 origin will never contain data
needed to construct the epoch's sequencer batches, because each batch must contain the L1 origin
hash — you cannot commit to a block from inside it.<Cite src="op-specs-derivation" /> Batches for
epoch `E` therefore arrive in blocks strictly after `E`, which is exactly why the window has to be a
window and not a point.
</Aside>

### Two configuration numbers that are not decoration

`SWS` is a per-chain parameter, and the registry pins it. OP Mainnet records
`seq_window_size = 3600` with `block_time = 2` and `max_sequencer_drift = 600`.<Cite src="superchain-registry-op-config" />
Automata Mainnet, on the same codebase, records `seq_window_size = 7200` and
`max_sequencer_drift = 1800`.<Cite src="superchain-registry-automata-config" /> Same function,
different constants, different chains.

The timestamp rules are equally load-bearing. Every L2 block must satisfy
`block.timestamp = prev_l2_timestamp + l2_block_time`, and
`l1_origin.timestamp <= block.timestamp <= max_l2_timestamp` where
`max_l2_timestamp = max(l1_origin.timestamp + max_sequencer_drift, prev_l2_timestamp + l2_block_time)`.<Cite src="op-specs-derivation" />
The second constraint is the one with teeth: it says an L2 block's timestamp can never precede its L1
origin's, and can never run more than `max_sequencer_drift` ahead of it. While the drift bound is
exceeded, the sequencer must enforce `len(batch.transactions) == 0`.<Cite src="op-specs-derivation" />
A sequencer that loses sight of L1 does not get to keep selling blockspace; it gets to keep producing
empty blocks.

With a 12-second L1 and a 2-second L2, the spec expects each epoch to typically contain `12 / 2 = 6`
L2 blocks, with bigger epochs produced to maintain liveness across a skipped L1 slot or a temporary
loss of connection, and smaller ones afterwards to stop L2 timestamps drifting further
ahead.<Cite src="op-specs-derivation" />

## The eight stages

The architecture decomposes derivation into a pipeline, and a verifier may implement it differently
but must be semantically equivalent so as not to diverge from the L2 chain.<Cite src="op-specs-derivation" />
That sentence is the specification telling you the stages are an implementation convenience and the
*function* is the contract.

The stages, outermost to innermost:<Cite src="op-specs-derivation" />

Data flows from the outer stage inward, but is *processed* in reverse: as many steps as possible are
taken in the innermost stage before any step is taken in its outer stage.<Cite src="op-specs-derivation" />
Each stage keeps an L1 block reference marking where its data came from, which is how the innermost
stage can account for L1 finalisation.<Cite src="op-specs-derivation" />

Three stages deserve a second look because they are where the interesting failures live.

**The Channel Bank is where compression is undone, and where a hostile input would land.** A channel
is a sequence of sequencer batches compressed together, split into frames so it can be spread across
several batcher transactions.<Cite src="op-specs-derivation" /> You met [channel construction from
the batcher's side](/c/batch-compression); here it is the decoder's problem, and decoders that
decompress attacker-supplied bytes need a bound. The spec sets one:
decompression is limited to `MAX_RLP_BYTES_PER_CHANNEL` explicitly to avoid zip-bomb attacks where a
small compressed input expands to a humongous amount of data.<Cite src="op-specs-derivation" /> The
constant moved with a hardfork — Fjord raised `MAX_RLP_BYTES_PER_CHANNEL` from 10,000,000 to
100,000,000 and `MAX_CHANNEL_BANK_SIZE` from 100,000,000 to 1,000,000,000, and the same fork changed
`max_sequencer_drift` from 600 to 1800 and from a chain parameter to a
constant.<Cite src="op-specs-derivation" /> Note what that means for the earlier registry reading:
those pinned `max_sequencer_drift` values are pre-Fjord history for chains that have passed the fork.

**The Batch Queue is where "the sequencer went away" stops being a special case.** Batches are
reordered by timestamp, and if batches are missing for some slots while a valid batch with a higher
timestamp exists, this stage generates empty batches to fill the gaps.<Cite src="op-specs-derivation" />
The validity rules are a list of drop conditions, and one of them is the timeliness rule that the
[forced-inclusion module](/c/sequencing-window) built its argument on: a batch whose epoch is older
than the window relative to its inclusion block is dropped.<Cite src="op-specs-derivation" /> The
others are structural — the batch's parent hash must equal the safe head's hash, the epoch cannot go
backwards, the epoch cannot advance by more than one L1 block per L2 block, and the batch must
reference a canonical L1 origin.<Cite src="op-specs-derivation" />

**The Payload Attributes stage is where deposits get in front of everything else.** For each L2
block, the transaction list is built in a fixed order: one L1 attributes deposited transaction
derived from the L1 origin; then, for the first L2 block in the epoch, zero or more user-deposited
transactions derived from the receipts of the L1 origin; then zero or more network upgrade automation
transactions; then zero or more sequenced transactions from the batch. Transactions must appear in
that order.<Cite src="op-specs-derivation" /> The attributes are then built with `noTxPool` set to
`true`, so the block is constructed from exactly that list.<Cite src="op-specs-derivation" />

**And one stage that looks like plumbing and is not.** In L1 Traversal the node reads the next L1
block header, and on traversal the system configuration copy used by L1 Retrieval is updated, so that
batch-sender authentication is always accurate to the exact L1 block being read.<Cite src="op-specs-derivation" />
The chain's configuration is therefore not a static file consulted at startup; it is a value that
moves as L1 advances, because `SystemConfig` changes are themselves L1 log events consumed by the
pipeline. The Payload Attributes stage keeps its own independent copy, updated when the L1 epoch
referenced by the batch input changes.<Cite src="op-specs-derivation" /> Two copies of the config,
advancing at different points in the pipeline, is not redundancy — it is the difference between "who
was allowed to post this data" and "what rules applied when this block was built".

The same stage carries a small piece of forward-compatibility engineering that tells you how
seriously determinism is taken here. Batcher transaction types come from a fixed allow-list, but
deposit events and `SystemConfig` updates must keep being derivable from receipts of L1 transaction
types that do not exist yet. The spec defines a best-effort process: a first byte in `[0x05, 0x7d]`
marks a future EIP-2718 type, whose receipt must carry the same first byte and decode as
`rlp([status, cumulative_transaction_gas_used, logs_bloom, logs])`, or the receipt is discarded as
invalid.<Cite src="op-specs-derivation" /> The range deliberately excludes `0x7e`, which is the
deposit transaction type and therefore already known.<Cite src="op-specs-derivation" /> A future L1
transaction type must not be able to change what an existing L2 chain derives.

That last flag is small and does a lot of work. A vanilla execution client builds blocks by pulling
from its mempool, which is a non-deterministic source. Derivation cannot tolerate that, so it
switches the mempool off. The specification says it plainly when describing the build sequence:
non-deterministic sources, like the tx-pool, must be disabled to reconstruct the expected
block.<Cite src="op-specs-derivation" />

## Worked example: what one transaction costs on the way back

Take a single L2 transaction and follow it out and back. The subgoals are the point; the numbers are
just the vehicle.

**Subgoal one — establish what the sequencer commits to, and what it does not.** The sequencer builds
an L2 block and, separately, a sequencer batch for it. The difference is not cosmetic: the block
includes an L2 state root, whereas the batch only commits to transactions at a given L2 timestamp,
and a block also references its predecessor.<Cite src="op-specs-derivation" /> The consequence is
stated directly in the spec: even if the sequencer applies a state transition incorrectly, the
transactions in the batch are still part of the canonical L2 chain, and a wrong output root gets
challenged by a fault proof and replaced by a correct one over the *existing*
batches.<Cite src="op-specs-derivation" />

Sit with that. A rollup with an honest data path and a lying sequencer does not get a corrupted
history; it gets a correct history and a wrong claim about it. Those are different incidents with
different fixes, and conflating them is why "the sequencer can steal from you" gets argued past both
sides.

**Subgoal two — locate the boundary where authentication happens.** Batcher transactions are
authenticated by checking that the `to` address matches the batch inbox address and the `from`
address matches the batch-sender address in the system configuration at the time of the L1 block the
data is read from.<Cite src="op-specs-derivation" /> Two addresses and a version byte are the entire
admission check. Everything after it — frames, channels, batches — is untrusted bytes subject to
validity rules, and any frame that fails to parse invalidates all frames in that
transaction.<Cite src="op-specs-derivation" />

**Subgoal three — count what has to survive for the chain to be reconstructible.** Frame overhead is
fixed at `16 + 2 + 4 + 1 = 23` bytes per frame, with `frame_data_length` capped at 1,000,000
bytes.<Cite src="op-specs-derivation" /> A channel is zlib-compressed RLP of concatenated encoded
batches.<Cite src="op-specs-derivation" /> None of that is executed by the EVM. It is written to
Ethereum for one purpose: so that anyone can read it back and run the function.

**Subgoal four — name the moment the sequencer loses control.** When your transaction's batch lands
in an L1 block, the docs mark it: once that data is included in an Ethereum block, the transaction's
ordering no longer depends on the sequencer, and the protocol marks the block
`safe`.<Cite src="op-docs-transaction-finality" /> Before that point you have a promise; after it you
have an input to a function anyone can evaluate. The next lesson is about the gap between those two
states, which is where most product mistakes live.

## Why this is the security model and not a design note

Now the payoff. Three properties fall out of purity, and none of them needs a new mechanism.

**No consensus among L2 nodes, therefore no quorum to attack.** Two honest nodes given the same L1
compute the same L2 chain, so there is nothing to vote on. This is why an OP Stack chain can run with
one sequencer and still be reconstructible by strangers, and why "decentralise the sequencer" and
"decentralise the chain's security" are separate projects with separate justifications.

**History survives the operator.** Everything needed to recompute the chain is either on L1 or is
derived from what is on L1. A dead sequencer threatens new blocks, not old ones. That is not a
policy; it is the type signature.

**L1 finality propagates automatically, and so does its absence.** The spec is precise about the
propagation and about a name collision that trips people up. Post-merge, reorg depth is bounded by
the L1 finality delay, and the derived L2 chain becomes irreversible as the L1 inputs do — but this
form of finalisation only affects *inputs*, and nodes can then subjectively say the chain is
irreversible by reproducing it from those irreversible inputs and the set protocol
rules.<Cite src="op-specs-derivation" /> The spec then adds that this is completely unrelated to the
outputs posted on L1, which require a fault proof or a validity proof, and that optimistic-rollup
withdrawals are only labelled "finalized" after a week without dispute — a name collision with
proof-of-stake finalisation.<Cite src="op-specs-derivation" />

That paragraph resolves an argument you will have with somebody: whether OP Stack transactions "take
seven days to finalise". They do not. The seven days belongs to withdrawals on L1, which is a
statement about outputs, not about the chain's own history.<Cite src="op-docs-transaction-finality" />

### The precondition everyone skips

The function is only as available as its inputs. The components page says the module used for data
availability has a significant impact on the security model, and gives the failure directly: if a
certain piece of data can no longer be retrieved from the DA layer, it may not be possible to sync
the chain.<Cite src="op-docs-components" /> Alt-DA mode's own page states it will always have more
trust assumptions than posting data to L1 Ethereum, and that in its current iteration with generic
commitments it fully trusts the chain operator to make data
available.<Cite src="op-docs-alt-da-mode" />

So "the L2 is a function of L1 data" is a conditional. On a chain with
`data_availability_type = "alt-da"`, part of the argument is a function of *somebody's server*, and
the [rollup versus validium distinction](/c/rollup-vs-validium) is exactly the size of that gap. Same
pipeline, same code, weaker claim.

<Check type="predict" concept="derivation">
An operator runs two `op-node` processes against the same L1 endpoint and the same chain. Node A is
configured with `seq_window_size = 3600`; node B, through a copy-paste error, with
`seq_window_size = 7200`. The chain has been healthy for months. The sequencer then goes dark for
seven hours, comes back, and republishes every missing batch within the next hour.

Predict what each node's `safe` head looks like at the end, and say whether the two nodes are still
on the same chain. Then say which node is right.

<Answer>
**During the outage, both nodes agree.** Neither has batches to process, so neither advances its
`safe` head past the last derived block. The window has not elapsed for either of them, and no empty
batch is generated: the empty-batch rule fires only once the stage has buffered everything readable
up to the L1 block at `epoch.number + sequence_window_size` and the next epoch is
available.<Cite src="op-specs-derivation" />

**On republication, they diverge — permanently.** Seven hours is 2,100 L1 blocks at 12 seconds. For
node A, the window is 3,600 blocks, so the oldest missing epoch is still inside its window: the
late batches pass the timeliness rule, and node A derives the real blocks. For node B, the window is
7,200 blocks — also not elapsed — so B accepts them too. Now change the outage to fourteen hours,
4,200 L1 blocks. Node A drops those batches as untimely and fills the gap with empty batches carrying
only deposits.<Cite src="op-specs-derivation" /> Node B accepts them and derives blocks full of user
transactions. The two nodes now have different L2 state roots for the same L1 data.

**They are not on the same chain, and nothing repairs it.** There is no fork choice among L2 nodes to
appeal to — this is the cost of being a function rather than a protocol. Node B does not get outvoted,
because there is no vote. It computes a different `derive_rollup_chain` and will keep doing so
forever, diverging further with every deposit that lands in a block the other node does not have.

**Node A is right if and only if 3,600 is what the chain's configuration says.** That is the honest
answer, and it is the uncomfortable one. Correctness here is not a property of the software; it is
agreement with the chain's published parameters. OP Mainnet's registry entry records
`seq_window_size = 3600`; Automata Mainnet's records
`7200`.<Cite src="superchain-registry-op-config" /><Cite src="superchain-registry-automata-config" />
Either number is correct — for exactly one chain.

**The operational lesson.** The valuable alert is not "is my node synced" but "does my node's
`safe` head hash match a second, independently configured node's". A config divergence looks
identical to a healthy chain from inside the diverged node, which is why the process holding a few
kilobytes of configuration is the one that needs a review process.
</Answer>
</Check>

## What breaks the function, and how it is put back

Purity does not mean immunity to L1 changing its mind. The pipeline can be **reset**, and the reset
is designed to recover into a state that produces the same outputs as a full derivation from genesis,
but starting from an existing L2 chain traversed back just enough to reconcile with the current L1
chain.<Cite src="op-specs-derivation" />

The same algorithm covers four cases the spec enumerates: starting the pipeline without going back to
zero when a node restarts; recovering when the pipeline becomes inconsistent with the execution
engine; recovering when L1 reorganises; and initialising the pipeline to derive a disputed L2 block
inside a fault-proof program.<Cite src="op-specs-derivation" />

That fourth one is worth pausing on, because it is the seam between this lesson and the proof-systems
module. The fault proof does not run some separate re-execution engine. It runs *this* pipeline, on
the disputed block, with the L1 and L2 history as its inputs. The dispute game you learned to bisect
is a bisection over the execution of the derivation function. Derivation is not merely how nodes
stay in sync; it is the thing the proof system proves.

The spec also notes a practical consequence of resettability: because the pipeline can undo its work
if L1 later disagrees, a node can be configured to eagerly sync L1 data with zero confirmations,
enabling safe low-latency usage.<Cite src="op-specs-derivation" /> Cheap undo buys low latency.

## Where this pays off

**The next lesson** takes the Engine Queue's three references — finalized, safe, unsafe — and turns
them into a product decision. It is the shortest distance between this specification and a bug in
something you ship.

**The Superchain lessons** are about many operators running this same function with contract sets
that must stay compatible. Once you see the chain as a function, "adopting a release" reads correctly:
it is changing the function, on a schedule, in step with everyone who has to compute the same answer.

**The interop lesson** extends the function's domain from one L1 chain to an L1 chain plus every
chain in a dependency set. The safety rule there is the same rule as here, applied across chains, and
it is why verifying a mesh costs what it costs.

**Your own systems.** If you consume an L2 through an RPC provider, you are trusting their `op-node`
configuration as much as their uptime. The cheapest independent check available to you is to compare
the `safe` block hash at a given height across two providers. If they disagree, one of them is running
a different function.
