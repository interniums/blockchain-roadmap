A chain's landing page says it is "part of the Superchain". Your job is to decide whether to put user
funds on it. What, exactly, does that sentence entitle you to assume?

The honest answer requires separating three memberships that the marketing collapses into one:
being **in the registry**, being a **standard chain**, and being in the **interop cluster**. They are
different sets, they are earned differently, and only one of them is a security claim. This lesson is
about telling them apart from primary data, because every chain's own page will tell you the most
flattering of the three.

## Membership one: the registry, which is an index

The Superchain Registry is documented as a repository that shows who is in the registry and each
chain's configuration, plus a step-by-step process new chains can follow to join and validation
checks that standard chains comply with the Standard Rollup Charter while non-standard chains pass
baseline validation.<Cite src="op-docs-superchain-registry" />

Read the second half of that sentence twice. **Non-standard chains join too**, at a lower bar. The
registry is an index of who is in the OP Stack ecosystem and how each chain is configured — its
glossary names the two categories directly: a **standard chain** conforms to the Standard Rollup
Charter, and a **frontier chain** is a non-standard chain with modifications that do not fit the
charter's criteria.<Cite src="superchain-registry-glossary" /> There is a third category too, for the
awkward middle: a **standard chain candidate** has met most of the standard criteria except for the
`ProxyAdminOwner` key handover.<Cite src="superchain-registry-glossary" />

So what does joining buy? The docs are refreshingly unromantic: the main benefit is practical. A
registered chain's genesis and rollup configuration are baked into releases of the canonical OP Stack
node software including `op-node` and `op-reth`, so operators can start a node against a registered
chain by passing its name to the client's network flag, with no hand-distributed configuration
files.<Cite src="op-docs-superchain-registry" /> Registration also lists the chain publicly alongside
its configuration.<Cite src="op-docs-superchain-registry" />

The joining process makes the "index" reading unavoidable. It is a pull request. The chain's ID must
first be registered at `ethereum-lists/chains`, because the validation suite checks against it and
this is a mandatory prerequisite; then you fork the registry, run `just create-config` against the
`state.json` your deployer produced, fill in the fields the tooling cannot infer, and open one PR per
chain.<Cite src="superchain-registry-ops" /><Cite src="op-docs-join-registry" /> Automated checks run
and generate a report describing the chain's level of compliance with the standard blockchain
charter.<Cite src="superchain-registry-ops" />

The converse matters as much. Because joining is an opt-in pull request, **absence from the registry
is not evidence about a chain.** An operator who never raised the PR is not listed, and that is the
entire story. Treat the registry as a source of truth about the chains in it, and as silence about
everything else.

## Membership two: standard, which is a charter

"Standard" has a written definition, and it sits inside a governance framework with three layers.

**Blockspace Charters** are the framework: a type of document that establishes criteria, governing
policies and precommitments for blockspace in the Optimism ecosystem.<Cite src="op-docs-blockspace-charter" />
The **Standard Rollup Charter** is the first such charter, defining the technical and governance
requirements for the highest-security blockspace.<Cite src="op-docs-blockspace-charter" /> The
**registry** then certifies compliance: it validates that chains align with the charter and, once a
chain meets the criteria, promotes it to "Standard" by setting its `superchain_level` value to
`2`.<Cite src="op-docs-blockspace-charter" />

The criteria are grouped into three technical parameters — **version**, validated via commit-hash or
release tag; **configuration**, covering parameter bounds for both static variables like chain ID and
dynamic ones like sequencer roles or upgrade keys; and **solvency**, the verification that all state
transitions in the chain's history are valid and free from invalid withdrawals or outputs that could
undercollateralise the bridge.<Cite src="op-docs-blockspace-charter" />

That third one is easy to skim and is the most interesting. A charter that only checked current
configuration would be satisfiable by a chain that misbehaved last year and tidied up. The **history
integrity** check exists for exactly that, and it is scoped honestly: it identifies discrepancies in
chain history including invalid state transitions, and is only required for chains that have not been
managed by the Optimism Security Council from launch.<Cite src="op-docs-blockspace-charter" />

### What "standard" refuses

The clearest way to understand a standard is to read its rejections. The charter documentation answers
three questions directly:<Cite src="op-docs-blockspace-charter" />

- *Can I modify system smart contracts and remain Standard?* **No** — modifications invalidate
  compliance.
- *Is an alt-DA mode chain Standard?* **No** — Standard Rollups must adhere to the default data
  availability model.
- *Will beta features qualify as Standard?* **No.** Beta features have not been approved by Optimism
  Governance; when they graduate from beta to GA they may be included in the charter.

Two features are named as defining a standard chain in practice: core protocol contracts must use
governance-approved release implementations, and sequencer settings must follow prescribed parameters
for transaction ordering and submission.<Cite src="op-docs-superchain-registry" />

The stated reasons for standardising are worth reading as a description of what deviation costs,
because they are the same three sentences inverted. The docs give interoperability — a standard stack
and security model gives a chain interop with other standard chains by default, including single-block
cross-chain messaging and token transfers with identical trust assumptions; a simplified upgrade path,
reducing the complexity of upgrading to the latest version; and reduced support overhead, minimising
the need for custom support by ensuring uniformity across
deployments.<Cite src="op-docs-superchain-registry" />

Invert those and you have the frontier chain's bill. No interop by default. An upgrade path you
maintain yourself, against contract releases designed for a configuration you are not running. And
support that is yours alone, because nobody else's runbook matches your deployment. None of that makes
the deviation wrong — a chain with a genuine reason to run alt-DA or a custom gas token is trading
deliberately — but it does mean the trade is ongoing rather than a one-time cost at launch, and it
compounds with every release the standard chains adopt and you do not.

And the criteria themselves are governed. Three TOML files referenced in the charter — standard config
params, standard config roles, and standard versions — require a governance vote to alter, while
changes to the code or tools that consume or validate them do not, so long as they do not violate the
semantic interpretation of those files.<Cite src="op-docs-blockspace-charter" /> Everything else about
validation remains at the Optimism Foundation's discretion, including other config checks and RPC
availability.<Cite src="op-docs-blockspace-charter" />

That split is the honest shape of the thing: a governed core of parameters, surrounded by
discretionary checks, with off-chain criteria — unique chain IDs, monitoring of security
configurations, verifying governance authenticity — performed by the Foundation until governance
transitions to fully autonomous control.<Cite src="op-docs-blockspace-charter" />

## Read the data, not the badge

Now do what the badge cannot do for you. The registry publishes machine-readable configuration, and
reading it takes minutes.

As of 26 August 2026, the registry's `superchain/configs/mainnet` directory holds 31 per-chain TOML
files plus a `superchain.toml`,<Cite src="superchain-registry-mainnet-configs" /> and `chainList.json`
lists the same 31 mainnet chains alongside 23 chains parented to Sepolia and two
devnets.<Cite src="superchain-registry-chainlist" /> Across those 31 mainnet entries:

- 21 record `dataAvailabilityType: "eth-da"` and 10 record `"alt-da"`.<Cite src="superchain-registry-chainlist" />
- 7 record `governedByOptimism: true`; 24 record `false`.<Cite src="superchain-registry-chainlist" />
- `faultProofs.status` reads `permissioned` for 20 chains, `none` for 8, and `permissionless` for
  3.<Cite src="superchain-registry-chainlist" />

Those three lines do more work than any summary of the ecosystem. Ten mainnet chains on this stack are
not posting data to Ethereum, which is the [rollup versus validium](/c/rollup-vs-validium) line and
therefore disqualifying under the charter's own alt-DA answer.<Cite src="op-docs-blockspace-charter" />
Eight have no fault proof system recorded at all. Three have a permissionless one.

Take one concrete pair. OP Mainnet: `governed_by_optimism = true`, `data_availability_type = "eth-da"`,
`seq_window_size = 3600`, `batch_inbox_addr = "0xFF00000000000000000000000000000000000010"`, with the
full hardfork table through `karst_time`.<Cite src="superchain-registry-op-config" /> Automata Mainnet:
`governed_by_optimism = false`, `data_availability_type = "alt-da"`, `seq_window_size = 7200`, a
`gas_paying_token` address, an `[alt_da]` section with a challenge contract and 3,600-block challenge
and resolve windows, and a hardfork table that stops at `fjord_time`.<Cite src="superchain-registry-automata-config" />

Both are OP Stack chains. Both are in the Superchain Registry. One of them is a rollup with Ethereum
DA on the current fork line, and the other is not, and no adjective in either chain's marketing will
tell you which.

### The last item on the checklist is a key

The registry's glossary defines "standard chain candidate" as a chain that has met most of the
standard criteria *except for the `ProxyAdminOwner` key handover*, and defines **key handover** as
updating the chain's `ProxyAdminOwner` to fulfil the requirements of the Standard Rollup
Charter.<Cite src="superchain-registry-glossary" />

It is worth sitting with what that costs the operator. Every other criterion is a configuration you
choose and keep. This one is an irreversible transfer of the ability to change your own chain to a
governance process you do not control. From the [upgrade-key](/c/upgrade-key-risk) framing you already
have, this is the whole ballgame: a chain that has done everything else and kept its own admin key has
kept the one power that can undo everything else.

That is also why the category exists as a named waiting room rather than a failure. Operators reach it
and stop, sometimes for a long time, because the last step is a business decision rather than an
engineering one. When you evaluate a chain, "standard chain candidate" is the most informative label
in the vocabulary: it tells you the technical work is done and the governance work is not.

### The shared cadence, made concrete

The other genuinely shared thing is the upgrade schedule, and the mechanism is a single field.

Chains can opt into hard fork activation inheritance by specifying `superchain_time` in their TOML,
after which they activate the network hardforks specified in the superchain-wide `superchain.toml`
files for Sepolia and Mainnet.<Cite src="op-docs-superchain-registry" /> Registered chains also get
their genesis and rollup configuration baked into subsequent `op-node` and `op-geth` releases, so a
node started with `--network` or `--op-network` inherits those activation times automatically instead
of having them set by
hand.<Cite src="op-docs-superchain-registry" />

Look at what that field does to the chains that set it. OP Mainnet records `superchain_time = 0`,
meaning it has inherited superchain-wide activations from the beginning.<Cite src="superchain-registry-op-config" />
Automata Mainnet has no `superchain_time` at all and its hardfork table ends at
`fjord_time`.<Cite src="superchain-registry-automata-config" /> One of those chains upgrades when the
Superchain upgrades; the other upgrades when its operator decides to.

That is the trade the whole Superchain model is built on, stated in one field. You give up the timing
of your own forks and you get an upgrade path somebody else maintains, tests on devnets and testnets,
puts through a governance vote, and ships as a release your node software already knows about. The
hardfork registry publishes the resulting timestamps for every fork, generated from structured
frontmatter and validated against the registry rather than hand-edited.<Cite src="op-docs-network-upgrades" />

## Membership three: the interop cluster

The third membership is the newest and the least settled, and the docs tie it to the second: standard
chains get Superchain interop by default, exchanging cross-chain messages and assets with other
standard chains under identical trust assumptions.<Cite src="op-docs-superchain-registry" />

The reason it is bundled with "standard" rather than with "registry" is the weakest-link problem you
already know from bridge design. Every chain in the Superchain interop cluster shares the same
security model to mitigate the weakest-link risk of cross-chain messaging: as outlined in the Standard
Rollup Charter, these chains share the same L1 `ProxyAdmin` Owner, and any change to the cluster goes
through the standard Protocol Upgrade vote.<Cite src="op-docs-interop-explainer-current" /> The
cluster is being rolled out iteratively, and the docs point at the Superchain Index for which chains
are eligible, looking for chains with a Standard charter.<Cite src="op-docs-interop-explainer-current" />

The last lesson of this module takes the mechanism apart. What matters here is the membership logic:
you cannot let a chain into a shared-security mesh on weaker terms than the mesh, so interop
eligibility is downstream of the charter, not of the index.

## What "shared governance" actually means

The most consequential shared thing in the Superchain is not a contract release or a name. It is a
key, and the docs publish it.

The L1 Proxy Admin is an address that can be used to upgrade most OP Stack chain system contracts, and
its owner is a 2-of-2 multisig whose owners are an Optimism Foundation 5-of-7 multisig and the
Security Council multisig.<Cite src="op-docs-privileged-roles" /> The published risks are stated
without hedging: a compromised L1 Proxy Admin could upgrade contracts to malicious versions, and could
remove or lock ETH or tokens in the Standard Bridge.<Cite src="op-docs-privileged-roles" /> The L2
Proxy Admin is the aliased address of the same L1 owner — nobody has the private key for it, so the
only way it can send transactions is via deposit transactions from the L1
address.<Cite src="op-docs-privileged-roles" />

The other governed roles sit alongside it. The System Config Owner, a 5-of-7 multisig, can change
`SystemConfig` values; a compromise could cause a temporary network outage or cause users to be
overcharged, and the role can be replaced by the L1 Proxy Admin.<Cite src="op-docs-privileged-roles" />
The Guardian can pause several system contracts, disable specific dispute game types or instances from
being used to execute withdrawals, and its published risk is that a compromised guardian could pause
withdrawals for three months, after which withdrawals are automatically
unpaused.<Cite src="op-docs-privileged-roles" />

## What is not shared

Three things are worth naming explicitly, because their absence is where most confident-sounding
claims about the Superchain go wrong.

**Sequencing is not shared.** Each chain's TOML pins its own `batch_inbox_addr`, `block_time`,
`seq_window_size` and `max_sequencer_drift`, and its own `[roles]` block names its own batcher and
proposer.<Cite src="superchain-registry-op-config" /> There is no shared ordering, no cross-chain
mempool, and nothing in the registry that would express one. What interop delivers instead is fast
*messaging* between separately sequenced chains, which is a different thing achieved by a different
mechanism.

**Revenue is a separate agreement.** The registry glossary defines a **Superchain Ecosystem member**
as a chain with an agreement in place to commit sequencer revenue back to the Optimism
Collective.<Cite src="superchain-registry-glossary" /> That is a fourth membership, orthogonal to the
three in this lesson: a commercial arrangement, not a technical classification, and a chain can be one
without being the others.

**Liveness is not shared.** Each chain runs its own batcher, proposer and challenger with its own keys
and its own funding.<Cite src="op-docs-privileged-roles" /> A Superchain-wide contract release does
nothing for a chain whose batcher ran out of L1 ETH last night. Shared governance narrows the range of
*configurations* in the ecosystem; it does not operate anybody's infrastructure.

independent people, or how a stage framework would classify the result — L2BEAT maintains the live
stage assignments and they move, so that is a lookup to do at the time you need it, not a fact to
memorise.<Cite src="l2beat-stages" /> Configuration is necessary and not sufficient, and the registry
is scrupulous about only claiming the part it can check.

## Where this pays off

**The next lesson** turns the charter from a document you read into a deployment you produce. Once
"standard" is a set of parameter bounds and a governance-approved release, the tooling that emits
exactly those bounds stops looking like convenience and starts looking like the only way to be
checkable.

**The interop lesson** shows why the cluster demands the charter rather than the index: a mesh cannot
be safer than its weakest member, so the membership rule has to be the security rule.

**Your own risk work.** The registry census is a script you write once and re-run. Name, DA type,
fault-proof status, governance flag, gas token, hardfork tail — six fields, one table, and most of the
disagreements about "is this chain safe" resolve into disagreements about which row you were looking
at.
