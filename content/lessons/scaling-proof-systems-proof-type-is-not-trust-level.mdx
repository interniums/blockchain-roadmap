On 26 August 2026 the largest rollup by value secured was Base, at $12.52B, and L2BEAT's summary
listed it under **Optimistic** with a proof system named **SP1**.<Cite src="l2beat-summary" />

Open the project page and the row resolves into something the first five lessons of this module did
not prepare you for. Base's state validation runs through a dispute game of type **621**, an
`AggregateVerifier` that accepts *either* an AWS Nitro TEE attestation *or* an SP1 ZK proof; the
risk row describes the result as "Fraud proofs (1R, ZK)", single-round, with no bisection
anywhere.<Cite src="l2beat-base-project" />

Which family is that? A fraud proof with no interactive bisection, settled by a validity proof, on a
chain whose alternative proof path is a piece of hardware in a data centre. The question stopped
having an answer, and this lesson is about what to ask instead.

## Proof type is a `uint32` in a registry

Every OP Stack dispute game is created through the `DisputeGameFactory` with a `GameType` — a
`uint32` selecting which registered implementation the factory
clones.<Cite src="op-specs-dispute-game-interface" /> The canonical list is not a taxonomy of two
families. It is a lookup table:<Cite src="op-docs-fault-proofs-reference" />

| Value | Name | What it is |
|---|---|---|
| 0 | `CANNON` | Fault dispute game on the Cannon VM |
| 1 | `PERMISSIONED_CANNON` | Same game, only the designated PROPOSER and CHALLENGER may play |
| 2 / 3 | `ASTERISC` / `ASTERISC_KONA` | A different fault-proof VM, with and without the Kona program |
| 6 | `OP_SUCCINCT` | Dispute game using OP Succinct — validity proving |
| 8 | `CANNON_KONA` | Cannon VM running `kona-client` |
| 10 | `ZK_DISPUTE_GAME` | "Optimistic + ZK proofs for dispute resolution" |
| 1337 | `KAILUA` | Dispute game using RISC Zero's Kailua |

Read entry 10 twice. The canonical registry contains a game type whose one-line description is
*both families at once*, and it sits beside a pure validity option at 6 and a pure
[bisection](/c/interactive-bisection) option at 8.

Three mechanics make this decisive rather than decorative:<Cite src="op-docs-fault-proofs-reference" />

- A game type is playable on a chain only after the factory owner registers an implementation with
  `setImplementation` and sets its creation bond with `setInitBond`.
- The **respected** game type — the one whose results the system accepts for withdrawals and anchor
  state updates — lives in the `AnchorStateRegistry` and is changed by the Guardian with
  `setRespectedGameType`.
- `op-deployer` ships every new standard chain on type `1`, the permissioned game.

And Base's `621` is not in that canonical list at all. A chain registered its own game type, and the
proof family it belongs to became a per-chain deployment decision rather than a property of the
stack it was built from.

## What the largest rollup actually runs

Base is worth working through in full, because every axis this module built breaks on it at once.
All of the following is L2BEAT's record, read on 26 August 2026.<Cite src="l2beat-base-project" />

**Proposal.** State roots are proposed by calling `DisputeGameFactory.create` with the
`AggregateVerifier` game type, posting a bond of **0.05 ETH**. Each proposal covers 600 L2 blocks
split into sub-ranges of 30, and must carry an initial proof — a TEE attestation or a ZK proof.

**Resolution.** With a single proof the game resolves after **5 days**. If *both* proof arms commit,
the window collapses to **1 day**.

**Challenge.** Any party producing a valid ZK proof of an incorrect intermediate root calls
`AggregateVerifier.challenge`, contradicting a TEE-only proposal. The proof is verified on-chain
through the SP1 verifier gateway; if the challenge stands to the end of the resolution window the
proposer's bond goes to the challenger and the game resolves `CHALLENGER_WINS`.

**Self-detection.** A soundness contradiction *within* one arm is caught by
`AggregateVerifier.nullify`, which permanently disables that arm's verifier contract for all games.

Now take the three consequences in order.

**Subgoal: notice that the window is a function of proof count, not proof family.** Five days with
one arm, one day with two. The [challenge window](/c/challenge-window) you learned to read as a
censorship budget is here a *redundancy* budget: the more independent systems that have committed to
the same root, the less time anyone needs to object. Nothing about optimistic-versus-validity
predicts either number.

**Subgoal: notice that "fraud proof" no longer implies bisection.** L2BEAT's own risk row reads
"Fraud proofs (1R, ZK)" — single round, resolved in one transaction. The 73-deep tree, the chess
clocks, the exponential bond curve, the [fault-proof VM](/c/fault-proof-vm) executing one MIPS
instruction: none of it is running here. The bond is 0.05 ETH rather than a path summing to hundreds
of ETH, because there is no path.

**Subgoal: notice the third category.** One of the two arms is an AWS Nitro TEE attestation. That is
neither a fraud proof nor a validity proof; it is a hardware trust assumption, with its prover
allowlist held in a `TEEProverRegistry` managed by the Base Coordinator Multisig and a separate
Manager EOA able to register and deregister enclave signers. The binary this module opened with has
a third member, and it arrived inside the chain with the most value at stake.

<Aside kind="note">
**Redundancy is the direction of travel, not an oddity.** The Ethereum Foundation's own plan for an
L1 zkEVM is explicitly multi-proof: validators statelessly verifying several proofs — say three —
generated by different zkVMs proving different EVM implementations, on the stated reasoning that
this applies the same defence in depth as existing client
diversity.<Cite src="ef-realtime-proving" /> Base's two arms and that plan are the same idea. Once a
chain runs more than one proof system, "which proof type is this chain" has no single answer by
construction.
</Aside>

## Registered is not respected, and respected is not permanent

You already know from [permissionless challenging](/c/permissionless-challenging) that a proof
system can be fully specified and switched off. The registry makes the point sharper. Three
different states hide behind "this chain has fault proofs":

/>

Only the third is what people mean, and all three are readable. The configurability spec is explicit
that the respected type may be moved *to* `PERMISSIONED_CANNON` as a fallback in the event of a
failure in the fault proof system, and the explainer names the corresponding trust assumption
plainly: the Guardian can pause withdrawals, blacklist games, or revert to a permissioned system, so
the assumption is that the Guardian does not act to
intervene.<Cite src="op-specs-configurability" /><Cite src="op-docs-fault-proofs-explainer" />

On Base the same capability is recorded concretely: the Base Governance Multisig can swap the
`AggregateVerifier` implementation, change the respected game type, blacklist individual games, or
retire all in-flight games through the `AnchorStateRegistry`.<Cite src="l2beat-base-project" />

Note what changing the *program* does not change. When the Karst upgrade promoted `CANNON_KONA` to
the respected game type, the fault proof program running on the VM changed language and
implementation while the tree, the moves, the step, the bonds and the trust model stayed
put.<Cite src="op-docs-karst-hardfork" /> Game-type indirection lets the proof change without the
trust model changing — and, symmetrically, lets the trust model change without the proof changing.

## The one place proof type genuinely buys something

The honest concession, and it is narrow.

L2BEAT's Stage 2 requirements ask for a fully permissionless proof system, a Security Council
restricted to acting on errors detected on chain, and at least **30 days** for users to exit in case
of unwanted upgrades — with one carve-out: given the existence of an on-chain bug detection system,
*for example two valid contradicting ZK proofs*, instant upgrades are allowed for detected bugs. The
framework names Polygon zkEVM's Emergency Mode, triggered when two different valid proofs can be
submitted over the same batches, as a live example.<Cite src="l2beat-stages" />

That is a real, specific advantage, and it is not about proof strength. A system that can adjudicate
*its own failure* on-chain earns the right to move fast when it fails, because the trigger is
verifiable rather than discretionary. Base's `nullify` is the same idea in different plumbing: a
soundness contradiction inside one arm permanently disables that arm's verifier, without anyone
voting.<Cite src="l2beat-base-project" />

Now notice everything the framework does **not** ask. Stage 0 asks whether the project uses a proper
proof system and whether at least five external actors can submit a fraud proof — a count, not a
family. [Stage 1](/c/l2beat-stage-1) is a single principle about compromising ≥75% of the Security
Council, plus a 7-day exit window for upgrades initiated outside it.
[Stage 2](/c/l2beat-stage-2) asks for permissionlessness and 30 days.<Cite src="l2beat-stages" /> At
no rung does the framework ask which mathematics settles a dispute, because the questions it grades
are about who can act.

## The four questions that replace it

So what actually determines how much you must trust a chain? Four things, each answerable.

1. **Who can change the contracts, and how much notice do I get?** This is the
   [exit window](/c/exit-window), and it dominates. Base's is recorded as *none* — contracts are
   instantly upgradable, with upgrades requiring both the Base Coordinator Multisig and the Base
   Security Council, a nested 2/2 arrangement over a 3/6 and an 8/11; L2BEAT records that Base
   counts this as 9 of 12 entities, or 75%, while the Council Safe alone is
   72.7%.<Cite src="l2beat-base-project" /> The glossary's bar is a council of at least eight
   members with a threshold above 75%, so which of those two readings you accept decides whether the
   bar is met.<Cite src="l2beat-glossary" /> Two independent parties is a real control. Zero seconds
   of notice is still zero seconds of notice.
2. **Is challenging or proving permissionless, and how many parties actually do it?** "Anyone may"
   and "several do" are different claims; the framework's five-external-actor floor exists precisely
   because of the gap.<Cite src="l2beat-stages" />
3. **Is the system live, or configured and dormant?** Read `respectedGameType()`, then check that
   games are being created and resolving.<Cite src="op-docs-fault-proofs-reference" />
4. **Who has to stay alive, and what happens the week they do not?** A challenger who must be
   funded, synced and uncensored, or a prover who must keep producing. Both are people; the failure
   modes differ.

Proof type appears in none of the four. It does determine three real things, all of which you have
now priced: the shape of the withdrawal delay, the cost structure — contingent capital against a
recurring hardware bill — and which of those two liveness dependencies you are carrying. Those are
engineering and treasury facts. They are not a trust ranking.

<Check type="explain" concept="proof-type-is-not-trust-level">
A chain you hold funds on announces: *"Next quarter we migrate from fault proofs to validity proofs.
Withdrawals will finalise in under an hour instead of seven days, and users will no longer need to
rely on anyone watching the chain."*

Say what genuinely improves, what does not change, what new dependency appears, and the one thing
you would check on the day of the migration.

<Answer>
**What genuinely improves.** The withdrawal delay, and it is a real number with real working-capital
value. The window drops from days to proving plus aggregation plus L1 finality, and the second half
of that sentence is the part the announcement omits — a submission cadence of one proof per hour
puts a floor under "under an hour" regardless of prover speed.<Cite src="succinct-op-succinct" />
The [one-honest-challenger assumption](/c/one-honest-challenger-assumption) does also go away, which
is a genuine simplification.

**What does not change.** Who holds upgrade authority, what the exit window is, who sequences,
whether the data was published, and whether the escrow contract still does what it did yesterday.
The stage framework grades those and never asks which family the proof belongs
to.<Cite src="l2beat-stages" /> A migration that leaves an instantly-upgradable contract set behind
has not moved the number that matters most.

**What new dependency appears.** A prover. If it stops, no new state roots are accepted and
withdrawals freeze — the same category of failure as an absent challenger, differently shaped and
differently priced. Ask who runs it, whether more than one party can, and what the fallback is for
the week it is down.

**What I would check on the day.** `respectedGameType()` on the `AnchorStateRegistry`, and who can
call `setRespectedGameType`.<Cite src="op-docs-fault-proofs-reference" /> A migration is a
registration plus a pointer change, and the same role that pointed the chain at validity proving can
point it back at a permissioned game — a documented fallback, not an
abuse.<Cite src="op-specs-configurability" /> I would also re-read the risk rows a week later, since
in-progress withdrawals typically must be re-proven against games created after such a
change.<Cite src="op-docs-migrating-permissionless" />

**The sentence I would send back.** "You are removing a delay and swapping one liveness assumption
for another. Tell us what happens to the exit window, because that is the number our risk disclosure
is actually about."
</Answer>
</Check>

## What this unlocks

**The module closes here**, and the shape it leaves you with is the useful part. Two families that
adjudicate the same predicate; a bisection game whose depth explains its bond curve; a window sized
against censorship rather than computation; an attack that targets the game instead of the state; a
compute bill nobody can quote in comparable units; and a boundary that has dissolved into a registry
entry. None of it sorts chains into the ranking everybody expects.

**The reflection prompt is the work.** For the chain you use most, name the party who would
challenge or prove, the software they run, who funds their bonds or their GPUs, and what breaks in
the week they stop. If you cannot answer, the honest output is a reading list, and L2BEAT's
per-project risk rows are where it starts rather than ends.<Cite src="l2beat-summary" />

**And the transferable habit** is the one this lesson practised on a `uint32`. When a field in your
own system turns out to be a pointer into a registry that someone can re-point, the category it
appears to name is not a fact about the system. It is a fact about the current value, and the
question worth asking is always who can change it and how much warning you get.
