Trail of Bits' Uniswap v4 Core review reports six findings: one Low and five
Informational.<Cite src="tob-uniswap-v4-core-review" /> Six, on a novel singleton exchange holding an
eventual multi-billion-dollar book.

And then, near the back, there is a separate appendix with six more items. Two-step ownership transfer.
A local variable named `state` shadowing a struct named `State`. A hashed slot value computed from
`NonzeroDeltaCount` while the library is named `NonZeroDeltaCount`. Incorrect comments in the `Currency`
type. An OpenZeppelin submodule pinned behind the current release. A documentation page that disagrees
with the `Hooks` library.<Cite src="tob-uniswap-v4-core-review" />

Every one of those is real. Every one is worth the client's time. None of them is in the findings list,
and the appendix states exactly why it exists: it contains findings that do not have immediate or obvious
security implications, but that may facilitate exploit chains targeting other vulnerabilities, become
easily exploitable in future releases, or decrease code
readability.<Cite src="tob-uniswap-v4-core-review" />

That is the whole design. Not a lower severity — **a different document**. This lesson is about why that
separation is load-bearing, and about the two ways a finding can be worth less than nothing.

## The counting problem

A client reads two reports. One has 41 findings; one has six. Which codebase is in worse shape?

You cannot tell, and the Stylus and Uniswap reports are the case in point: 47 engineer-weeks against a
novel Rust and WASM virtual machine produced 2 High, 6 Medium, 10 Low, 21 Informational and 2 Undetermined;
six engineer-weeks against a Solidity exchange produced 1 Low and 5
Informational.<Cite src="tob-arbitrum-stylus-review" /><Cite src="tob-uniswap-v4-core-review" /> The
difference is dominated by effort, scope and subject matter, not by code quality.

Now add the failure this lesson is about. Suppose the six-finding report had instead promoted its code
quality appendix, listed twelve findings, and rated the shadowed variable name as Low. The count doubles,
every number in the executive summary moves, and the report is *less useful* — because the one finding
that actually describes a path to loss now sits in a list where the reader has been trained to skim.

**The count is the only number in a report that looks like a score, so it gets read as one.** Every item
you promote spends credibility from the items that deserved it.

## Where the line actually is

The test is not severity. It is whether an **exploit scenario** can be written: an actor, a capability that
actor holds, an ordering, and something the actor obtains. If you cannot write those four parts
concretely, you do not have a vulnerability — you have an observation, and observations have their own
section.

Both competitive platforms encode versions of this line in rules, and the rules are worth knowing because
they are unusually explicit about what does *not* count.

Sherlock states it is exclusively focused on high and medium-severity findings, and publishes a list of
categories that are not valid at those levels.<Cite src="sherlock-issue-validity" /> Several are
instructive because most reviewers' instincts get them wrong:

- **Incorrect event values.** Incorrectly calculated or wrong values in emitted events are not valid
  medium or high.<Cite src="sherlock-issue-validity" />
- **User input validation.** Validation intended to prevent user mistakes is not a valid issue — *however*,
  if a user input could result in a major protocol malfunction or significant loss of funds for other
  parties, it could be a valid high.<Cite src="sherlock-issue-validity" />
- **Accidental direct token transfers.** Tokens sent directly into in-scope contracts outside expected
  operation, with no recovery path, are a user mistake if the user only hurts themselves — but may be valid
  if it harms the protocol or other users.<Cite src="sherlock-issue-validity" />
- **User blacklisting.** A user blacklisted by a token, harming only themselves, is not a valid
  medium or high.<Cite src="sherlock-issue-validity" />
- **Storage gaps.** Simple contracts with a parent not implementing storage gaps are low or informational —
  *unless* the inheritance is highly complex and branched with gaps inconsistently applied and the
  submission clearly describes the necessity, in which case it can be a valid
  medium.<Cite src="sherlock-issue-validity" />
- **Incorrect values in view functions** are low by default — *unless* the value feeds a larger function
  that loses funds.<Cite src="sherlock-issue-validity" />
- **Loss of airdrops** or rewards not part of the original protocol design is not a valid
  high or medium.<Cite src="sherlock-issue-validity" />
- **Future gas repricing.** Issues assuming future opcode gas repricing are not medium or
  high.<Cite src="sherlock-issue-validity" />

Read the pattern rather than memorising the list. Almost every entry has an **exception clause**, and every
exception has the same shape: *unless it reaches someone other than the person who made the mistake, or
unless it feeds something that loses funds.* That is the line. Self-harm, cosmetics and hypotheticals are
observations; anything that propagates to a third party or into an accounting path is a finding.

Code4rena draws it in the other direction, by defining a bucket rather than a blocklist. `QA` covers Low
risk — assets not at risk: state handling, function incorrect as to spec, issues with comments — plus
Governance and Centralization risk; and informational issues, explicitly including code style, clarity,
syntax, versioning and off-chain monitoring such as events, are
**discouraged**.<Cite src="code4rena-severity-classifications" /> Note that "function incorrect as to
spec" sits in QA. A function that does not match its documentation, with no path to loss, is a
correctness observation, not a vulnerability.

<Aside kind="note">
The received story is that contests reward volume and therefore breed inflation. The incentive is real,
but Code4rena's own awarding page — re-read directly on 26 August 2026, since this curriculum's earlier
research could not confirm its contents from a secondary summary — describes a scheme in which a
finding's shares **decay as more submitters duplicate it**, and in which the single submission selected
for inclusion in the report receives a bonus.<Cite src="code4rena-awarding" /> Under that scheme, adding
one more copy of an obvious issue is worth progressively less, while writing the version good enough to be
published is worth more. Breadth without depth is not actually the winning play even inside the system
that is blamed for teaching it.
</Aside>

## The two costs of a wrong finding

A false positive is not a neutral event that gets filtered out. It has two prices and you pay both.

**The client pays in engineering time.** Someone reads it, disagrees, re-reads the code to be sure, writes
the rebuttal, and attends the call where it is discussed. That is a half-day of a senior engineer during a
launch window, spent on nothing. Do it three times and you have consumed more of their attention than your
real findings will receive.

**You pay in prior.** After two wrong findings, the client's default on your third moves from "probably
right" to "probably not". This is the expensive one, because it is applied to the finding you got right,
and it is applied silently — nobody tells you your credibility dropped.

### The controls that prevent it

**Reproduce anything you would rate High or Medium, before you send it.** This is the same discipline the
proof-of-concept convention encodes, and Sherlock's criteria make it near-mandatory in the categories where
misreading is easiest: non-obvious vulnerabilities and attack paths, non-trivial input constraints,
precision loss, reentrancy, and gas or revert-related attacks. A report without a proof of concept is
considered invalid if the issue cannot be clearly understood without
one.<Cite src="sherlock-issue-validity" />

**Report what you could not reproduce as a question, not as a claim.** "I could not construct a path where
`X` is reachable with `Y` unset — can you confirm the initialiser guarantees this?" costs the client five
minutes and costs you nothing. The same content phrased as "Critical: uninitialised state allows takeover"
costs a half-day and a credibility notch if it turns out the initialiser handles it. **The information
content is identical; only the liability differs.**

**Steelman it before sending.** Write the sentence the engineer will reply with, then answer it in the
description. If you cannot answer it, you have found your own false positive at the cheapest possible
moment.

**Say when a finding is not currently exploitable.** Trail of Bits does this inside findings — noting that
an issue is not currently exploitable, listing the two specific reasons why, and then noting that its
severity would be higher combined with another finding.<Cite src="tob-uniswap-v4-core-review" /> That is
not weakening the finding. It is spending three sentences to buy the reader's trust in the other five
findings.

## Worked example: triaging six observations

End of a review. Six things bother you. Sort them.

**Subgoal: attempt an exploit scenario for each, in one sentence, and let the failures sort themselves.**

1. *`transfer` return value unchecked, on a contract with one hardcoded compliant token.* No actor, no gain
   — the token cannot fail. **Code quality appendix**, with a long-term recommendation.
2. *Missing event on `setFeeRecipient`.* No path to loss. Under Code4rena's rules, off-chain monitoring
   issues such as events are explicitly discouraged as informational.<Cite src="code4rena-severity-classifications" />
   **Informational** — and it is genuine evidence for the Auditing maturity category, which is where it
   will do the most good.
3. *Owner can set fee to 100%.* Actor: owner. Gain: all fees. But the scenario runs entirely through a
   trusted role, and Code4rena's rules put direct misuse of privileges in a QA
   report.<Cite src="code4rena-severity-classifications" /> **Informational in a contest; a
   Decentralization input in a firm report.** Same observation, two homes, depending on what was purchased.
4. *Unbounded loop over a user-extendable array in a `view` function used by the front end.* Actor: any
   user. Gain: the front end breaks for everyone. Third parties are harmed, so the self-harm exception does
   not apply. **A finding** — availability impact, and Sherlock's incorrect-view-function rule has its own
   exception where the value feeds something larger.<Cite src="sherlock-issue-validity" />
5. *Storage gap missing in one parent of a two-level inheritance chain.* Simple inheritance, so low or
   informational by rule.<Cite src="sherlock-issue-validity" /> **Informational**, with the exception noted
   for the client's future refactor.
6. *A rounding direction that favours the caller by 1 wei per operation, callable in a loop.* Actor: anyone.
   Repeatable. Under Sherlock's rule, a small loss replayable indefinitely is treated as a 100%
   loss.<Cite src="sherlock-issue-validity" /> **A finding, and probably the most important one in the
   list** — and the one that would have been buried had the other five been promoted alongside it.

**Subgoal: check what the sort did to the report's shape.** Two findings, four informational or
code-quality items. The client reads two things. Both of them matter. That is the outcome the separation
exists to produce.

**Subgoal: make sure the demoted items still land somewhere useful.** Items 1, 2, 3 and 5 are not
discarded — they are evidence. Item 2 is an Auditing rating. Item 3 is a Decentralization rating. Item 1 is
a Testing and Verification note. The maturity assessment, which is the next lesson but one, is where
observations that are not vulnerabilities become the most useful part of the
report.<Cite src="tob-blockchain-maturity" />

<Check type="recall" concept="informational-vs-finding">
A teammate is about to submit a report with 23 findings, 14 of them rated Low. Skimming, you see entries
for: missing NatSpec on four functions; `uint256` used where `uint128` would pack; a `public` function that
could be `external`; a missing zero-address check on a setter that only the owner calls; and an event
emitted after the state change rather than before. What do you say, and what do you *not* say?

<Answer>
**What I say first, before any critique.** These are real observations and they should ship — just not as
findings. Every one of them belongs in an informational or code-quality section, which exists precisely for
items with no immediate security implication that may still facilitate exploit chains, become exploitable
in future releases, or decrease readability.<Cite src="tob-uniswap-v4-core-review" /> Leading with "cut
these" invites a defence of their value; leading with "these are valuable, and they are in the wrong
section" does not.

**Item by item.**

*Missing NatSpec* — documentation. Code4rena lists issues with comments under QA and discourages
informational submissions of this kind.<Cite src="code4rena-severity-classifications" /> Its real home is
the Documentation maturity category, where four undocumented functions is *evidence*, not noise.

*`uint256` where `uint128` packs* — a gas observation. It has no exploit scenario in either direction, and
it is not free advice either: changing a type changes the storage layout, which for an upgradeable contract
is a hazard rather than an optimisation. Worth saying, worth saying carefully, not a finding.

*`public` that could be `external`* — style, and on modern compilers frequently not even a gas win.

*Missing zero-address check on an owner-only setter* — the interesting one, and still not a Low. The actor
is the owner, the failure mode is a mistake, and Code4rena's rules state that reckless admin mistakes are
invalid and that calls are assumed to be previewed.<Cite src="code4rena-severity-classifications" /> If the
setter were permissionless, or if setting zero bricked the contract irrecoverably for all users, it would
be a different conversation — the harm would reach third parties, which is the exception clause that runs
through every one of these rules.<Cite src="sherlock-issue-validity" />

*Event ordering* — cosmetic on-chain; events are ordered within the transaction receipt regardless. Unless
an off-chain consumer's correctness depends on intra-transaction ordering, which would need to be
demonstrated rather than asserted.

**What I do not say.** I do not say "these are worthless" and I do not say "you inflated the report". The
first is false and the second is an accusation about motive where the actual cause is almost always a habit
imported from a scoring system that counted submissions. The useful framing is structural: the findings
list is a list of things with an exploit scenario; everything else has a home, and moving them there makes
the nine real findings visible.

**And the question I ask instead of arguing.** *"Of these 23, which would you wake someone up for?"* If the
answer is two, the report should make those two impossible to miss. Fourteen Lows around them is
camouflage — and the cost is not abstract: it is the reader's attention, which is the scarce resource the
whole document is competing for.
</Answer>
</Check>

## What this unlocks

**Next**, the second deliverable — the codebase maturity assessment, where every observation you just
demoted becomes evidence for a rating, and where a client with zero criticals finds out whether they were
good or lucky.<Cite src="tob-blockchain-maturity" />

**Then**, reading a report for what the engagement actually bought: scope, commit, effort, and the fix
review that determines whether the document still describes a codebase that exists.

**And a calibration exercise worth doing once.** Take any published report and count how many items sit in
the findings list versus the code-quality and informational
appendices.<Cite src="tob-publications-repo" /> The ratio in professional work is not what contest
scoreboards would lead you to expect, and seeing it once is more persuasive than any argument in this
lesson.
