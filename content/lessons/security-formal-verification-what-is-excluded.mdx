One line of specification, and an entire library leaves the proof:

```text
methods {
    function SomeLibrary._ external => NONDET;
}
```

That is a **catch-all entry**. It applies a single summary to all functions declared in a given
contract — there are no parameter types and no return types, because it refers to every method in that
contract.<Cite src="certora-cvl-methods" /> After that line, calls into `SomeLibrary` are replaced with an
approximation that returns an arbitrary value, and nothing inside `SomeLibrary` is being verified any
more. The rules that used to time out now pass. The report says verified.

Nothing here is misconduct. Catch-all entries exist because the exact behaviour of an external library
contract is often genuinely irrelevant to the property being proved, which is what the documentation says
they are for.<Cite src="certora-cvl-methods" /> The problem is that the line lives in a spec file and the
word "verified" lives in a README, and only one of those two travels.

This lesson is about the distance between them. There are three mechanisms that shrink what a proof
covers — **summaries**, **optimistic assumptions**, and **timeouts** — and reading a verification result
means enumerating all three before looking at a single checkmark.

## Summarization: the vendor's own word for it is "unsound"

A summary replaces calls to a method with something simpler for the prover to reason about. Summaries
allow reasoning about external contracts whose code is unavailable, and are also useful to simplify code
being verified in order to circumvent timeouts.<Cite src="certora-cvl-methods" />

Both halves of that sentence are true and only the first is what people picture. The second — using a
summary because a run would not otherwise finish — is the common case, and it is the one that costs
coverage.

The documentation states the consequence without hedging:

> Summary declarations change the way that some function calls are interpreted, and are therefore
> **unsound** (with the exception of `HAVOC_ALL` summaries which are always sound, and `NONDET` summaries
> which are sound for `view` functions).<Cite src="certora-cvl-methods" />

"Unsound" is a precise word here. It means the proof may hold of the summarized program while failing to
hold of the real one. A passing rule under a summary is a claim about a *different program* than the one
you are going to deploy — one where the summarized function behaves as described rather than as written.

The counter-intuitive ordering is worth internalising: **`HAVOC_ALL` is the sound one.** Assuming a called
function can do anything to storage is pessimistic, so a proof that survives it survives reality. The
summaries that make runs *fast* — `NONDET` on a state-changing function, `CONSTANT`, a hand-written
expression summary — are the ones that assume behaviour, and assumption is what costs soundness.

So when you read a spec file, sort the summaries by optimism, not by count. Twenty `HAVOC_ALL` entries are
less interesting than one `ALWAYS(0)` on a function that computes a fee.

### The check that is standard practice to skip

Certora's architecture document describes summarization as splitting one verification problem into two
subproblems: first, verify the program using the summary in place of the method's definition; second,
check that the summary is a correct approximation of the actual method definition. Then it adds the line
this lesson exists for:

> In practice, it is sometimes useful to omit the second check to give rule writers maximum
> flexibility.<Cite src="certora-gentle-intro" />

Read it twice. With the second check omitted, the summary is never confronted with the function it
replaces. You have written down what you believe `computeFee` does, proved a property of a program in
which `computeFee` does that, and shipped a `computeFee` that does something else. The proof is valid. The
conclusion about the deployed contract does not follow.

### Wildcards make the blast radius bigger than the line

Three entry shapes exist, and they differ in how much they capture:<Cite src="certora-cvl-methods" />

- **Exact** — one method of one contract. Must declare a return type, which the Prover checks against the
  contract.
- **Wildcard** — `_.f(uint) external => NONDET;` matches *any* external `f(uint)` in *any* contract.
  Wildcard entries must not declare a return type, because different matched methods may return different
  types, and their only purpose is summarization, so they must carry a summary.
- **Catch-all** — `SomeLibrary._ external => NONDET;` applies one summary to every method of that
  contract.

A wildcard is a one-line statement about an unbounded set of functions across the whole scene. When you
audit a specification — including a client's — count wildcards and catch-alls before you count rules.

## Optimistic assumptions: a family, not a flag

An optimistic assumption discharges a difficult obligation by assuming it holds. The pattern is uniform
enough to be recognisable: without the flag, the Prover *asserts* the hard condition and fails when it can
be violated; with the flag, the Prover *requires* it and those executions vanish.

| Flag | Without it | With it |
|---|---|---|
| `optimistic_loop` | Appends an assertion that the loop actually finished — the loop unwind condition | Turns that assertion into a requirement, so cases where the loop would run longer are ignored rather than treated as failures<Cite src="certora-cli-options" /> |
| `optimistic_hashing` | Checks whether hashed data can exceed `hashing_length_bound` and reports an assertion violation if it can | Assumes the data's length is bounded by it, excluding longer data from verification<Cite src="certora-cli-options" /> |
| `optimistic_contract_recursion` | Reports an assertion failure when a counterexample exceeds the contract recursion limit — default zero, no recursion allowed | Ignores that counterexample<Cite src="certora-cli-options" /> |
| `optimistic_summary_recursion` | Fails when a summary recurses past the limit | Proceeds<Cite src="certora-cli-options" /> |
| `optimistic_fallback` | Unresolved external calls with an empty input buffer havoc all storage of external contracts in the scene | Dispatches to available `fallback` implementations instead<Cite src="certora-cli-options" /> |
| `auto_dispatcher` | Unresolved callees with a known sighash havoc | Behaves as if `DISPATCHER(optimistic=true)` were declared for every such method<Cite src="certora-cli-options" /> |

Two of those deserve a closer look because they are the ones that surprise people.

**`hashing_length_bound` has a default, and the default is small.** The maximum length of unbounded data
chunks being hashed defaults to 224 bytes — seven EVM machine words.<Cite src="certora-cli-options" />
With `optimistic_hashing` on, longer data is assumed away. A contract that hashes a caller-supplied
`bytes` blob is therefore verified over blobs of at most seven words unless somebody raised the bound, and
the documentation is explicit that raising it helps detect bugs that depend on a hashed array reaching a
certain length.<Cite src="certora-cli-options" />

**`optimistic_fallback` is the interesting inversion.** Its *un*-optimistic default havocs all external
storage, which is sound and produces so many spurious counterexamples that work becomes impossible. So the
flag exists to make the tool usable — and it does so by narrowing the set of things an unknown callee is
allowed to be. This is the general shape: **the sound default is often unusable, and the usable
configuration is often unsound.** That trade is not a defect in the tool, it is the subject matter. Your
job is to know which side of it a given result sits on.

<Aside kind="warn">
The Prover can also summarize **without being asked**. With `nondet_difficult_funcs`, it auto-summarizes
`view` or `pure` internal functions returning a value type that are heuristically difficult, with a
threshold set by `nondet_minimal_difficulty`; the notification in the rule report that contains the applied
summaries presents the threshold used.<Cite src="certora-cli-options" /> That notification is a section of
the report, not a line in your spec file. If you only read the spec, you will not see these summaries at
all.
</Aside>

### Ghosts havoc too

One consequence connects back to the previous lesson and catches people who thought their accounting was
watertight. Ghosts are regarded as part of the state of the contracts: if a call reverts, ghost values
revert to their pre-state, and **if an unresolved call is handled by a havoc, the ghost values havoc as
well**.<Cite src="certora-cvl-ghosts" />

So an unresolved external call does not merely fail to update your running sum. It makes your running sum
arbitrary, and any invariant stated over it becomes unprovable — or, if the surrounding rule has enough
`require` clauses, vacuously provable. Ghosts marked `persistent` are never havoced and never
reverted,<Cite src="certora-cvl-ghosts" /> which is sometimes what you want and is itself an assumption.

## Timeouts: the outcome that is not a result

The third exclusion is the one that does not appear in any spec file.

Certora's default SMT timeout is 300 seconds, and the guidance around raising it is discouraging: usually,
if a rule is not solved in 600 seconds it will not be solved in 2,000 either, and it is better to
concentrate on simplifying the rule, simplifying the source, adding more summaries, or using other
time-saving options.<Cite src="certora-cli-options" /> Halmos ships a 60-second default for solving
assertion-violation conditions.<Cite src="a16z-halmos-config" /> Foundry names the outcome directly and
tells you how to read it: `FAIL: incomplete symbolic execution` or `Incomplete` means Forge could not
complete the search or validate a counterexample, and should be treated as "not established", not as a
proof.<Cite src="foundry-forge-testing" />

Notice the second half of Certora's advice, because it closes the loop of this lesson: **the standard
remedy for a timeout is to add a summary or an optimistic assumption.** Timeouts are not a separate
failure mode from the other two; they are the pressure that produces them. Every exclusion in a real
verification project has a timeout somewhere in its history.

And notice what a timeout is *not*. It is not a weak pass. The solver has not searched the space and
failed to find a violation — it has failed to search the space. There is no probability attached, no
partial coverage, no "most of it was fine".

<Misconception
  belief="If the prover times out on a rule, the property is probably fine — nothing was found."
  reality="A timeout carries no information about the property. The only valid responses are to decompose it, summarize something, tighten a bound, or change the encoding — each of which changes what a subsequent pass would mean."
  why="Timeouts look like flaky infrastructure rather than like an answer, and a re-run that happens to finish feels like confirmation rather than like a different experiment."

## Vacuity: the pass that cannot fail

There is a fourth failure that hides inside the other three. Pile up enough `require` clauses — from
preconditions you added to kill spurious counterexamples, from `optimistic_loop`, from a summary that
constrains a return value — and the rule becomes **vacuously** true: proved because no execution satisfies
its hypotheses.

Certora treats this as a first-class risk, implementing techniques for preventing certain patterns of bad
specification and flagging tautological invariants of the form `x = 5 => x > 0` as potentially
incorrect;<Cite src="certora-gentle-intro" /> and the `optimistic_loop` documentation carries an explicit
caution that the flag could cause vacuous rules.<Cite src="certora-cli-options" />

The practical control is cheap and almost nobody does it: **mutate the contract and confirm the rule goes
red.** Invert a comparison, delete a state update, remove an access check. A rule that stays green against
a deliberately broken contract is not testing anything, and finding that out costs one minute.

## The reading protocol for a verification appendix

You will meet these results as a section inside an ordinary audit report far more often than as a
standalone engagement — Cyfrin's public repository listed 243 reports as of 26 August 2026, of which 20
carry a formal-verification component, some split into separate human and AI verification
documents.<Cite src="cyfrin-audit-reports-repo" /> Here is what to extract, in order, before reading a
single verdict.

**1. The scene.** Which contracts were loaded? Anything not in the scene was not verified, whether or not
it is called.

**2. The summaries.** Every entry in the methods block that carries `=>`. Sort by optimism: expression and
view summaries first, `HAVOC_ALL` last. For each, ask whether the summary-correctness check was performed
or omitted.<Cite src="certora-gentle-intro" />

**3. The wildcards and catch-alls.** One line can remove a library.<Cite src="certora-cvl-methods" />

**4. The optimistic flags and the bounds.** `optimistic_loop`, `optimistic_hashing` with its bound,
`loop_iter`, recursion limits.<Cite src="certora-cli-options" /> In a Halmos or Foundry appendix, the
equivalent is `--loop`, invariant depth and array-length settings.<Cite src="a16z-halmos-config" />

**5. The auto-applied summaries.** The rule report's own notification, not the spec
file.<Cite src="certora-cli-options" />

**6. The rules that did not pass.** Timeouts, `Incomplete` results, and rules that were disabled or
filtered out. A `filtered` block excludes methods from a parametric rule and leaves the result looking
identical.

**7. Only now, the checkmarks.**

If that list is longer than the list of proved properties, the appendix is doing its job. An appendix with
no assumptions section is not a stronger result; it is an incomplete document.

## Worked example: a green proof over an exploitable contract

The exercise that makes this concrete is to build the failure deliberately.

```solidity
contract Vault {
    IOracle public oracle;
    function withdraw(uint256 shares) external {
        uint256 price = oracle.price();          // external call
        uint256 assets = shares * price / 1e18;
        _burn(msg.sender, shares);
        token.transfer(msg.sender, assets);
    }
}
```

Property: **a withdrawal never transfers more assets than the withdrawer's pro-rata share.**

**Subgoal: fail honestly first, so you know what the sound answer looks like.** With `oracle` unresolved,
the default treatment havocs external storage, `price` is arbitrary, and the rule fails with a
counterexample where the price is enormous. That failure is *correct*: an arbitrary oracle can produce an
arbitrary payout, which is the actual risk in this contract.

**Subgoal: apply the summary that makes the run finish, and name what it assumed.**
`function _.price() external => ALWAYS(1000000000000000000);` — one line, and the price is now fixed at
`1e18`. The rule passes in seconds. What was assumed: that the oracle returns exactly one value, always.
Everything the oracle can actually do is now outside the proof, and it is a view summary, so it is not in
the sound exception list.<Cite src="certora-cvl-methods" />

**Subgoal: put the bug in the summarized region and watch the proof stay green.** Make the oracle
manipulable — a spot price from a pool, the [rate oracle](/c/oracle-manipulation) pattern that has done so
much damage. The contract is now exploitable end to end. The rule is still green, because the rule is
about a program in which `price()` returns `1e18`.

**Subgoal: write the two sentences that belong in the report.** Not "verified". Rather: *the withdrawal
proportionality rule holds for all share amounts and all callers, under the assumption that
`oracle.price()` returns a constant `1e18`. The oracle's behaviour is not covered by this proof and is a
trust assumption.* Both sentences are true and only the pair is useful.

**Subgoal: notice which artifact the second sentence belongs in.** It is not a verification finding — it
is a line in the [trust-assumption inventory](/c/trust-assumption-inventory). The summary you wrote to
make the solver finish has produced a threat-model entry. That is the healthiest possible outcome of a
summarization decision, and it only happens if somebody writes it down at the moment the summary is added
rather than at report time.

<Answer>
**1. The library that does the arithmetic is not verified.** `function ShareMath._ external => NONDET;`
is a catch-all entry, which applies one summary to every method of that contract — no parameter or return
types, all of them.<Cite src="certora-cvl-methods" /> `ShareMath` is loaded as a file and then replaced by
"returns an arbitrary value" at every call. Since the question asked was about *accounting*, and share
math is the accounting, this single line removes the subject of the engagement from the proof. It is also
not in the sound exception list — `NONDET` is sound only for `view` functions, and a catch-all covers
state-changing ones too.<Cite src="certora-cvl-methods" /> This is the finding.

**2. `noValueCreation` established nothing, and it is the property that matters most.** A timeout is not a
weak pass; it is the absence of a result.<Cite src="certora-cli-options" /> Worse, it timed out at
`smt_timeout` 1200 seconds — four times the 300-second default — and the vendor's own guidance is that a
rule unsolved at 600 seconds will generally not be solved at 2,000, and that the effort should go into
simplifying the rule or the source
instead.<Cite src="certora-cli-options" /> So this is not "nearly there"; it is a rule that needs to be
decomposed. Any summary of these results as "two of three verified" is a misreport.

**3. The parametric rule's filter removes the emergency path.** `f.selector != sig:emergencyExit()` is a
`filtered` block, an exclusion mechanism that is invisible in the passing
result.<Cite src="certora-cvl-rules" /> `emergencyExit` is exactly the sort of function that moves funds
under unusual conditions and has the least test coverage. It may well be a justified exclusion. It is not
a justified *silence*.

**4. Two optimistic flags are on, and one has a default you probably did not choose.**
`optimistic_loop` converts the loop unwind assertion into a requirement, so executions needing more than
three iterations are ignored rather than failing.<Cite src="certora-cli-options" /> `optimistic_hashing`
assumes hashed data is bounded by `hashing_length_bound`, whose default is 224 bytes — seven
words.<Cite src="certora-cli-options" /> If anything in this vault hashes user-supplied `bytes` longer
than seven words, those cases are outside the result. Neither flag is wrong; both belong in the appendix.

**5. The Prover summarized functions you did not name.** `nondet_difficult_funcs` auto-summarizes `view`
or `pure` internal functions returning a value type that it finds heuristically difficult, and the applied
summaries appear in a notification in the rule report along with the threshold
used.<Cite src="certora-cli-options" /> Ask for that notification. It is a list of functions that left the
proof without appearing in the spec file.

**6. `_.balanceOf(address) => NONDET` is a wildcard, and it is the one I would argue least about.** It
matches any external `balanceOf(address)` in any contract.<Cite src="certora-cvl-methods" /> `balanceOf`
is `view`, and `NONDET` is sound for `view` functions,<Cite src="certora-cvl-methods" /> so this is the
pessimistic choice: balances may be anything. If `solvencyInvariant` passed under it, that pass is worth
something. Say so — a report that flags every summary equally trains the client to discount all of them.

**7. What I would actually say.** *Two properties hold under a configuration in which the share-math
library, the emergency exit path, and an unknown set of auto-summarized internal functions are excluded;
the third property was not established. The strongest true statement available is that no counterexample
exists to the accounting rule for the non-view, non-emergency methods of `Vault`, assuming `ShareMath`
behaves arbitrarily.* Then the question that decides the next step: **can `ShareMath` be verified
separately?** If it is pure arithmetic with no external calls, it is the ideal target for a focused proof,
and the composition would give a result worth the word.
</Answer>
</Check>

## What this unlocks

**The next lesson** turns this into a purchasing decision: which code is worth proving, which is not, and
why a proof about code says nothing about oracles, governance or key custody — the places the largest
recent losses actually happened.

**In the audit-craft module**, this reading protocol becomes a general skill. A verification appendix's
assumptions list, an audit's [scope statement](/c/scope-statement) and a threat model's trust-assumption
inventory are three renderings of the same document: *what we did not look at.* Learning to read one
teaches you all three.

**Practically**, the deliberate-hole exercise above is the fastest way to internalise this. Take a passing
run, add one summary, put a bug inside the summarized function, and watch the checkmark survive. Two
minutes of work, and you will never again read the word "verified" without asking the follow-up
question.<Cite src="certora-gentle-intro" />

**And in the literature**, this is the practical face of what the symbolic-execution survey catalogues as
the technique's structural limits — path explosion, solver cost, and the modelling of code the analysis
cannot see.<Cite src="symbolic-execution-survey-2025" /> Summaries and optimistic flags are the industry's
answers to those limits. Each answer is a trade, and the appendix is where the trades are recorded.
