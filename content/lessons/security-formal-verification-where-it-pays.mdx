In February 2025 an exchange lost more value in one transaction than the entire recorded history of smart
contract exploits in most single years. Reported figures vary by source and by snapshot price — roughly
$1.4 billion, $1.46 billion, and $1.5 billion all circulate, with Trail of Bits' own analysis titled
around the highest of the three — and this curriculum has not picked one.<Cite src="tob-bybit-threat-model" />

What is not in dispute is the mechanism. There was no contract vulnerability. Trail of Bits' analysis
frames the whole incident as a threat-modelling failure rather than a code failure: the compromise lived
in the path between a human signer and the transaction they believed they were
authorising.<Cite src="tob-bybit-threat-model" />

Now the uncomfortable question this module has been building toward. Suppose every contract involved had
carried an unbounded, unsummarized, fully verified specification with no optimistic flags. **How much of
that loss does the proof prevent?**

None of it. Not because the proof was weak, but because the proof was about something else.

## A proof is about the code inside the model

Every technique in this module produces a statement of the form: *for all inputs, this code satisfies this
property, under these assumptions.* The word doing the most work is **this code**.

Here is what sits outside that boundary by construction, and where the failures actually happened:

Read the middle rows against the recent incident record. Losses in 2025 and 2026 concentrated at exactly
these boundaries: an exchange signing flow, a bridge whose verifier configuration was set to a single
attesting party combined with poisoned RPC responses, a protocol whose multisig signers were induced over
months to pre-sign administrative transactions. In each case the contracts did what they said. Reported
loss figures for those incidents also vary between sources — around $290 million and around $292 million
for one, roughly $270 to $285 million for another — and again, no single figure is established here.

The pattern is what matters, and it is uncomfortable for anyone selling assurance by code-quality tier:
**the highest assurance available for code is not the highest assurance available for a protocol.**

## The two questions that replace "should we get verified"

"Should we formally verify" is unanswerable because it has no object. Replace it with two questions that
do.

**Question one: where is the risk?** Not where is the complexity — where is the *risk*. If the honest
answer is "our admin key" or "our price feed" or "whether the multisig signers can read what they are
signing", then a proof about the contract improves the wrong quantity. Spend the money on the
[trust boundary](/c/trust-boundary) instead: fewer capabilities, slower ones, better signing hygiene,
independent monitoring.

**Question two: is there a property here that sampling cannot reach?** Fuzzing samples; proving
quantifies, and the premium is worth paying only where sampling is genuinely insufficient. The properties
where it is share a shape: arithmetic edges, all callers rather than some, or a relationship that must hold
in every reachable state rather than along a path.

## Where proving pays

**Fixed-point and arithmetic libraries.** `mulDiv`, exponent and log approximations, square roots, tick
math. The failure region is often a handful of values out of `2^256`, which is precisely the region a
sampler will never visit and a solver reaches immediately. This is also the cheapest target: pure
functions have no storage, no callers, no external calls, so the model is small and the run terminates.
Start here.

**Rounding direction.** "Rounding always favours the protocol, never the user" is a property over every
input, and every rounding bug is a slow leak that no single test looks wrong next to. Trail of Bits'
maturity rubric puts a systematic approach to arithmetic correctness — including rounding and precision —
at the centre of its arithmetic category, and rates a codebase weak when there is no explicit testing
strategy for it.<Cite src="tob-code-maturity-criteria" />

**Access-control matrices.** "No method other than X may change Y, for any caller." This is where the
parametric rule earns its cost: a rule taking a `method` parameter produces a separate verdict per method,
so a function merged next quarter is inside the rule's scope with nobody remembering to extend
anything.<Cite src="certora-cvl-rules" />

**Standard conformance.** ERC-20, ERC-721, ERC-4626 semantics are fixed, published and stable, so the
specification does not rot with your code and can be reused across deployments — CVL specs live in their
own file precisely so they survive code versions.<Cite src="certora-gentle-intro" /> It is the rare case
where someone else already wrote the hard part.

**Small enumerable state machines.** Auction phases, escrow states, withdrawal queues. When the state set
is small and the transitions are named, "no sequence of calls reaches an unreachable state" is both
expressible and provable — and it is the shape an inductive invariant handles naturally rather than by
unrolling.<Cite src="certora-gentle-intro" />

**Storage-layout safety across upgrades.** After the [ERC-7201 bricking case](/c/erc-7201-namespaced-storage) you
already know how expensive a layout mistake is and how invisible it is to a test suite that only exercises
the current implementation.

**Frozen, high-value code.** Verification is an investment amortised over the time the specification stays
true. Immutable code with large balances is the case where the denominator is longest.

## Where it does not pay

**Code that changes weekly.** Every change is a specification change, and an unmaintained specification is
worse than none because it produces confidence about a contract that no longer exists. Halmos' own
rationale names this maintenance burden explicitly.<Cite src="a16z-halmos-post" />

**Risk concentrated in oracles, governance or key custody.** See the entire first half of this lesson.

**Systems whose failure mode is economic rather than logical.** A liquidation engine can be provably
correct and still fail because the market moved faster than the keepers. "The code did what it said" is
the *precondition* of that class of failure, not a defence against it — and the oracle it depends on would
have to be summarized to make the run finish, putting the actual risk outside the proof by
construction.<Cite src="certora-cvl-methods" />

**Teams that cannot maintain the specification.** If the engagement ends and nobody left can read the spec
file, you bought a one-time result rather than a capability — which changes what to ask for: a smaller spec
the team can own beats a larger one they cannot.

<Aside kind="note">
There is a cheap diagnostic for the maintenance question. Ask the team to write down the ten most
essential invariants of their system; if they cannot, dedicate more time to identifying them before buying
anything.<Cite src="tob-invariant-driven-development" /> A team without ten invariants does not have a
verification problem yet. It has a specification problem, and every assurance technique downstream —
fuzzing, proving, monitoring, manual review — takes the specification as input.
</Aside>

## What it costs, honestly

There is no measured study of specification effort across these tools, and no independent, non-vendor
benchmark comparing them on a common corpus. Every side-by-side that surfaced during this track's research
was authored by a market participant. So the figures below are practitioner folklore. Use the **ordering**,
which is stable, and treat the magnitudes as order-of-magnitude
only.<Cite src="allthingsfuzzy-fv-practice" />

| Move | Order of magnitude | Buy it when |
|---|---|---|
| Bounded symbolic run over your existing tests | Hours to a day | Almost always — the ratio is unmatched |
| Focused spec for one component (a math library, a token, a role matrix) | Days to a couple of weeks | The component is stable and the property is arithmetic |
| Full-protocol specification | Person-weeks to months, plus ongoing maintenance | Code is frozen, value is large, team can maintain it |
| Non-trivial arithmetic in a K-based tool | Highest, lemma authoring dominates | You need the strongest semantic foundation and can staff it |

The first row is the recommendation most teams should act on and the one that gets skipped in favour of a
conversation about vendors. Renaming a few tests, making their inputs symbolic and running them costs an
afternoon and produces genuinely quantified results — at a loop bound of 2, an invariant depth of 2 and
array lengths drawn from `0,1,2` unless you change them.<Cite src="a16z-halmos-config" />

## The stack, not the tool

The sequencing that falls out of everything in this module:

1. **Write the invariants.** Before any tool. They are the input to all of them — fuzzing, verification,
   on-chain post-conditions, monitoring and manual review are five consumers of one
   statement.<Cite src="tob-invariant-driven-development" />
2. **Fuzz.** Cheap, finds the counterexample, and tells you which of your properties are even true. Most
   properties do not survive first contact with a fuzzer, and finding that out costs minutes.
3. **Bound.** Convert the surviving properties to symbolic tests. Record the bounds next to the result.
4. **Prove.** Only for properties that survived steps two and three and sit on code worth the cost.
5. **Monitor.** Because everything above is about the code, and the code is not the whole system.

Trail of Bits' Uniswap v4 Core review is a good picture of what that mix looks like at a real firm on a
real engagement: 100 invariants created, of which eight were formally verified by Halmos, 88 checked by
Medusa and Echidna, and four statically checked by Slither.<Cite src="tob-uniswap-v4-core-review" /> The
proportion is not a compromise. It is the shape of the trade.

## Worked example: triaging one protocol

A lending protocol, six weeks from launch, one engineer-month of security budget left. Four candidate
targets. Walk the decision.

**Subgoal: locate the risk before locating the complexity.** Sketch what an attacker would actually do.
Here: manipulate the collateral price feed; or compromise the multisig that lists new collateral; or find
an accounting error in the interest accrual. Two of those three are outside any proof. That is the first
finding of the exercise, and it should reallocate part of the budget before any tool is chosen.

**Subgoal: score each candidate on stability, model size and sampling adequacy.**

**Subgoal: notice why the third row is not a budget decision.** The liquidation engine is the
highest-value component and the worst verification target: its risk is that the market moves faster than
keepers, and its oracle would have to be summarized to make the run finish. Proving it would produce a
green result about the safest thing in the system.

**Subgoal: turn the fourth row into an artifact instead of dropping it.** "Not code" is not "not our
problem". A listing decision that can admit an unbacked asset is the shape of a recent bad-debt incident
where the protocol's code was never exploited — the listing decision was. The output here is a
[trust-assumption inventory](/c/trust-assumption-inventory) entry and a monitoring alert, not a rule.

**Subgoal: spend the remaining hours on the cheap tier, everywhere.** Whatever the budget, converting the
existing test suite to symbolic tests is an afternoon and covers all four components at shipped bounds. Do
it first, then spend the rest on `InterestMath`.

**Subgoal: write down what the engagement will not have covered.** Not at the end — now. "This proof does
not cover the oracle, the listing procedure, the keeper incentives, or the multisig." That sentence is the
deliverable that survives contact with a board slide, and writing it in week one is what stops "we're
formally verified" from being said in week seven.

<Check type="explain" concept="fv-roi">
A protocol tells you: "We're allocating our whole security budget to formal verification this year. Our
contracts are immutable, we've had two audits with no highs, and we want the strongest guarantee
available." They hold roughly $400 million, run a Chainlink-based price feed with a 1% deviation threshold,
and have a 3-of-5 multisig that can add collateral types and pause the system.

What do you tell them? Include what you would keep from their plan.

<Answer>
**Keep the framing, change the allocation.** They are right that immutable, high-value, stable code is the
best case for verification — it is the case where the specification does not rot and the investment is
amortised over the longest period. That is a genuinely good instinct and I would say so before disagreeing
with anything.

**But the whole budget is the wrong number, because the two largest risks are not in the code.**

*The multisig can add collateral types.* That is the capability that has produced the most spectacular
recent bad-debt events: the code executed a listing exactly as designed, and the listed asset was not worth
what the oracle said. A proof of the lending logic proves nothing about which assets it is pointed at.
Budget here goes to procedure — a timelock on listings, a documented risk-assessment step, a cap on new
collateral exposure, and an alert when a listing transaction is queued.

*The multisig can pause.* Which also means it can *fail to* pause, and a 3-of-5 has a signing path with
humans in it. This is the Bybit-shaped risk, and it is a threat-modelling problem about what a signer sees
before approving, not a contract problem.<Cite src="tob-bybit-threat-model" />

*The oracle's 1% deviation threshold is a design parameter with an attack surface.* It defines how far the
on-chain price may drift from the real one before an update, and a proof of the code that consumes the
price cannot say whether that window is exploitable — the price is an input, and inputs are assumptions.

**What I would actually fund, in order.**

1. **A day converting the existing suite to symbolic tests.** Cheapest quantified assurance available; do
   it before any conversation about vendors.<Cite src="a16z-halmos-post" /> Record the
   bounds.<Cite src="a16z-halmos-config" />
2. **A focused proof of the arithmetic and the role matrix.** Interest accrual, share conversion, rounding
   direction, and a parametric rule over admin capability. This is a couple of weeks, not a year, and it
   is the part of the code where sampling genuinely cannot reach.
3. **Stateful fuzzing with real handlers on the liquidation path.** Where the sequencing bugs live.
4. **Monitoring with a defined response.** They are immutable, so their only lever is the pause — which
   means detection speed *is* their security. An alert nobody owns is a notification, not a
   control.<Cite src="tob-invariant-driven-development" />
5. **A bug bounty, funded properly.** Their "two audits, no highs" reasoning is the belief this deserves
   the most pushback on. Immunefi's five-year data across 593 programs reports that 93.9% of programs
   running five or more years have logged at least one confirmed, paid critical disclosure, with the rate
   climbing monotonically from 61.4% at one year — and of the programs that surfaced a critical, the
   average is 2.7 of them.<Cite src="immunefi-long-running-programs" /> That is vendor research from a
   company that sells bounty programs, and it should be read with that in mind; the monotonic shape of the
   curve is harder to explain away than the headline number.

**The sentence I would want them to leave with.** "No highs in two audits" is not evidence that no highs
exist. It is evidence about how much expert attention was purchased, in what scope, at which commit — which
is exactly what the next module is about. Spending an entire year's budget on proving the part of the
system that already has the most attention, while the collateral-listing procedure has none, optimises the
metric rather than the risk.

**One thing I would not say.** I would not tell them formal verification is overrated. It is not. It is
mis-scoped here, and the correct answer is a smaller, better-targeted proof plus four other line items —
not a smaller opinion of proving.
</Answer>
</Check>

## What this unlocks

**The audit-craft module starts next**, and it opens on the same boundary from the other side. An audit
report's [scope statement](/c/scope-statement) is the same artifact as a verification appendix's
assumptions list: a declaration of what was not examined. Once you can read one, you can read the other,
and both convert a badge into a checkable claim.

**Verification is now a line item you will meet inside audit reports** rather than a separate world.
Cyfrin's public repository listed 243 reports as of 26 August 2026, of which 20 carry a formal-verification
component.<Cite src="cyfrin-audit-reports-repo" /> When you meet one, you already know the questions:
which bounds, which summaries, which optimistic flags, which rules did not
finish.<Cite src="certora-cli-options" />

**And the reflection this module is built around** is worth answering before moving on. Pick one property
in a system you care about. Would you rather have a proof of it under three summarizations you chose
yourself, or a fuzz campaign with no summarizations and no proof? The answer is not the same for every
property, and being able to say *why* for a specific one is the skill this module was for.
