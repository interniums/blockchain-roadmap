Two teams set out to prove the same thing about the same ERC-20: that nothing except `mint` can increase
total supply.

The first team renames three existing Foundry tests, deletes the concrete arguments, and has a result
before lunch. The second team writes eleven lines in a language they had to learn, and has a result three
days later.

The first result is: *`transfer`, `approve` and `burn` do not increase total supply.* The second result
is: *no method of this contract, including ones written next year, increases total supply except `mint`.*

Those are not the same claim, the gap between them is not syntax, and choosing between them is the
central decision of a verification engagement. Everything else — which solver, which flag, which
vendor — is downstream.

## The cost is the specification, and the vendors say so

Start with the sentence the tool-comparison posts skip. Halmos' own design rationale opens on it: one of
the main challenges of formal verification is the overhead of writing and maintaining formal
specifications, a process that often involves manually writing them in a specialized language that many
developers will need to learn first.<Cite src="a16z-halmos-post" /> It continues with the part that bites
after the engagement ends: when developers change the code as it is being verified, they must also update
their existing specifications, leading to extra maintenance efforts.<Cite src="a16z-halmos-post" />

That is a vendor describing the dominant cost of its own category. Take it as the frame for this lesson:

> Running the tool has an install command. Writing a specification that is simultaneously **true of the
> intended system** and **strong enough to be worth proving** does not — and keeping it true as the code
> changes is a recurring cost with no natural end.

The specification is also open-ended in a way tests are not. It is an incremental process, typically
starting with simple properties and verifying them first, then gradually adding more complex properties on
top, with no clear stopping point — one can only add as many properties as possible within the available
time frame.<Cite src="a16z-halmos-post" /> A team that budgets verification as a task with a completion
criterion has mis-modelled it. It is closer to test coverage: a dial, not a checkbox.

## Path A: reuse the tests you already have

The cheap path takes an existing test, replaces its concrete inputs with symbols, and calls the result a
specification. Symbolic testing checks the program for all possible inputs, so a program that passes
symbolic testing can be considered formally verified — and the same test cases serve both
purposes.<Cite src="a16z-halmos-post" />

Mechanically it is barely a change. Halmos discovers functions whose names match `(check|invariant)_` by
default;<Cite src="a16z-halmos-config" /> the convention its guide teaches is
`check_<function-name>_<behavior-description>`,<Cite src="a16z-halmos-getting-started" /> and function
parameters become the symbolic inputs. Foundry's in-tree mode uses `check*` or `prove*` and requires
`--symbolic` to discover them at all.<Cite src="foundry-forge-testing" />

```solidity
// before: one scenario, chosen by whoever already believed the code was right
function test_transferMovesBalance() public {
    token.mint(alice, 100e18);
    vm.prank(alice);
    token.transfer(bob, 40e18);
    assertEq(token.balanceOf(bob), 40e18);
}

// after: the same assertion, quantified
function check_transfer(address sender, address receiver, uint256 amount) public {
    uint256 senderBefore = token.balanceOf(sender);
    uint256 receiverBefore = token.balanceOf(receiver);
    vm.prank(sender);
    token.transfer(receiver, amount);
    assertEq(token.balanceOf(receiver), receiverBefore + amount);
    assertEq(token.balanceOf(sender), senderBefore - amount);
}
```

The a16z guide describes the effect conceptually as running an extensive loop over every possible input
combination — the same test, executed against the whole domain rather than one
point.<Cite src="a16z-halmos-getting-started" />

### What you get, and what you did not get

**What you get is real.** The `sender == receiver` case — the self-transfer that breaks naive
implementations reading both balances into locals before writing either — is now covered, and it was not
before. The `amount == senderBefore` boundary is covered. Every address is covered, including the token
itself and address zero. This is a genuine upgrade for the price of an afternoon, and it is the highest
assurance-per-hour trade in this entire module.

**What you did not get is a system specification.** The properties obtained are exactly as strong as the
assertions the tests already contained, and test assertions are *scenario-shaped*: they say what one
function does to two accounts. They do not say what is true of the contract. No test in the suite above
asserts anything about total supply, so nothing about total supply was proved — and the team can now
truthfully say the token is symbolically verified.

There is a second, quieter limit. Halmos' own guide notes that with an older compiler using the `INVALID`
opcode for assertion violation rather than the `Panic(1)` error code, it will not report
counterexamples.<Cite src="a16z-halmos-getting-started" /> Symbolic testing detects failure by recognising
a specific failure signal in the bytecode. If your harness signals failure some other way, a green result
means the tool saw nothing to look at.

<Aside kind="warn">
The Kontrol trap is worth naming here because it looks identical from the outside. Kontrol also takes
existing Foundry tests as specifications.<Cite src="kontrol-docs" /> But its scalability story is
compositional symbolic execution supported by lemmas, loop invariants and bounded model
checking,<Cite src="kontrol-docs" /> and reaching non-trivial results on real arithmetic generally means
authoring the lemmas and invariants yourself. **Same entry point, different cost curve.** Judge these
tools by what it takes to get a *useful* result, not by what it takes to get a first result.
</Aside>

## Path B: a language whose rules quantify over methods

The expensive path is a separate specification language checked against the contract. Certora's is CVL,
written in its own file — a deliberate design choice, so the specification is usable across different code
versions.<Cite src="certora-gentle-intro" /> The Prover analyses compiled bytecode against that spec,
which is the *verify what you execute* principle: it does not trust the compiler that produced the
bytecode from source.<Cite src="certora-gentle-intro" />

Learning a language is a real cost and not the interesting one. The interesting one is what the language
can express that a test cannot.

### Parametric rules: the property that covers code not yet written

A CVL rule may take a `method` parameter instead of naming a function. Rules containing undefined `method`
variables are called parametric rules, and the Prover generates a separate report — and a separate
counterexample — for each method or combination of methods, indicating which contract methods always
satisfy the rule.<Cite src="certora-cvl-rules" />

```text
rule onlyMintIncreasesSupply(method f, env e, calldataarg args) {
    uint256 before = totalSupply();
    f(e, args);
    uint256 after_ = totalSupply();
    assert after_ > before => f.selector == sig:mint(address,uint256).selector;
}
```

Read what that quantifier does. It is not a claim about `transfer`, `approve` and `burn`. It is a claim
about **the set of external methods**, evaluated per method, one report each. A function merged six months
from now is inside the rule's scope with nobody remembering to extend anything.

That temporal property is the argument for the expensive path, and it is worth more than it sounds. A
hand-written property list is a snapshot; it rots at exactly the rate the codebase grows, and it rots
silently, because nothing fails when a new function escapes coverage. A parametric rule fails loudly:
the new method appears in the report with its own verdict.

Two mechanics you will meet immediately. Rules can carry a `filtered` block of the form `var -> expr` to
exclude methods from verification, which the docs note is less computationally expensive than using a
`require` to ignore counterexamples for a method — and the method must be declared as a rule *parameter*
for the filter to reference it.<Cite src="certora-cvl-rules" /> And the Prover automatically skips any
method carrying a `DELETE` summary.<Cite src="certora-cvl-rules" />

<Aside kind="warn">
Both of those are exclusion mechanisms, and both are invisible in a passing result. A parametric rule
whose filter removes half the contract's methods reports success in the same shape as one that removed
none. When you read someone else's specification — including your own from last quarter — the filters and
the `DELETE` entries are the first thing to enumerate.
</Aside>

### Ghosts and hooks: naming a quantity the contract never computes

Most system-level invariants are about quantities no contract stores. "The sum of all balances equals
total supply" is the canonical one: the sum exists in the specification's world, not in storage.

A **ghost** is specification-level state — additional variables for use during verification, used to
communicate information between rules and hooks.<Cite src="certora-cvl-ghosts" /> A **hook** fires when
the contract performs a matching operation, and hooks are instrumented for every appearance of the
matching instruction in the bytecode.<Cite src="certora-cvl-hooks" /> Together they let a rule refer to
the running sum.

```text
ghost mathint sumOfBalances;

hook Sstore balanceOf[KEY address a] uint256 newValue (uint256 oldValue) {
    sumOfBalances = sumOfBalances - oldValue + newValue;
}

invariant supplyEqualsSum()
    to_mathint(totalSupply()) == sumOfBalances;
```

This is the same idea as the [ghost variable](/c/ghost-variable) you already use in a stateful fuzz
harness, moved into the specification layer — and Trail of Bits' invariant framing puts both downstream of
the same statement, with fuzzing and verification as two consumers of one
property.<Cite src="tob-invariant-driven-development" />

Three sharp edges the documentation states and everybody hits anyway:

**Ghosts are part of the verified state, unless you say otherwise.** If a call reverts, ghost values
revert to their pre-state; if an unresolved call is handled by a havoc, the ghost values havoc as
well.<Cite src="certora-cvl-ghosts" /> That last clause matters enormously in the next lesson: an
unresolved external call does not merely leave the ghost unchanged, it makes it arbitrary. Ghosts marked
`persistent` are never havoced and never reverted.<Cite src="certora-cvl-ghosts" />

**Hooks fire on bytecode, not on your mental model of the source.** The documentation's own example: every
Solidity method call to a non-payable function contains an early call to `CALLVALUE` to check that it is
zero, so a `CALLVALUE` hook triggers on every non-payable Solidity function
invocation.<Cite src="certora-cvl-hooks" /> A hook is placed against what the compiler emitted. This is
the same lesson the [Yul](/c/yul-is-the-middle-layer) module taught from the other direction, and it
is why bytecode-level verification is both stronger and stranger than source-level intuition.

**Hooks are not reentrant.** While a hook is executing, additional hooks are skipped; if a hook calls a
contract function that would normally trigger another hook, the inner hook does not
execute.<Cite src="certora-cvl-hooks" /> A ghost accumulator that assumes it sees every write will
undercount if your hook bodies call back into the contract.

## What each path actually costs

Everything below is **practitioner folklore, not measurement.** No public study quantifies specification
effort across these tools, and no independent benchmark compares them on a common corpus. Treat every
figure as an order of magnitude and, more usefully, treat the *ordering* as the durable part.

The ordering has a corollary about *who pays*. The first row is something a team does for itself. The
last three are usually bought, and the thing being bought is the specification, not the run — which is why
an engagement that ends without the client's engineers able to maintain the spec has bought a
one-time result rather than a capability. One of the few non-vendor side-by-side accounts of running these
tools reaches the same conclusion from experience.<Cite src="allthingsfuzzy-fv-practice" />

<Aside kind="note">
Formal verification has stopped being an exotic separate engagement and become a line item inside ordinary
audits. Cyfrin's public report repository listed 243 reports as of 26 August 2026, of which 20 carry a
formal-verification component — and recent entries distinguish a *human* formal-verification appendix from
an *AI* one as separate documents.<Cite src="cyfrin-audit-reports-repo" /> Trail of Bits' Uniswap v4 Core
review is a concrete picture of the mix: the team created 100 invariants, of which eight were formally
verified by Halmos, 88 checked by Medusa and Echidna, and four statically checked by
Slither.<Cite src="tob-uniswap-v4-core-review" /> Eight out of a hundred is not a failure of ambition. It
is what the economics look like when the specification is the cost.
</Aside>

## Worked example: one requirement, both paths

The requirement, from a real specification document: *only the minter role may create new tokens.*

**Subgoal: make the claim falsifiable before choosing a tool.** As written it is an access-control wish.
The machine-checkable form quantifies over callers and over methods: *for every method `f` and every
caller `c`, if executing `f` from `c` increases `totalSupply`, then `c` holds the minter role.* Now it can
be false, which is the only interesting property a specification can have.

**Subgoal: write the cheap version and note exactly what it covers.** In Halmos, a symbolic test with a
symbolic caller and symbolic amount, calling `mint` and asserting the revert-unless-role behaviour. Ten
minutes. What it covers: `mint`. What it does not cover: every other path that can increase supply —
`mintBatch`, a rebase hook, an `initialize` that mints, a `delegatecall` into a module that writes the
supply slot directly. The claim is about a function; the requirement was about a contract.

**Subgoal: write the version that covers the contract, and count what it cost.** The parametric rule
quantifies over `method f`, so the Prover produces a verdict per method and tells you which methods always
satisfy the rule.<Cite src="certora-cvl-rules" /> A path you forgot appears as a named failing method
rather than as silence. Cost: the language, plus a `methods` block, plus resolving whatever external calls
make the run diverge.

**Subgoal: find the assumption the parametric rule forces you to write down.** Run it and a counterexample
arrives on a method you had not thought about — often `upgradeTo`, or a function that writes storage
through assembly. Either it is a genuine hole, or the rule needs a precondition saying the upgrade
authority is trusted. **Writing that precondition converts an unstated trust assumption into a stated
one**, which is the same artifact the [trust-assumption inventory](/c/trust-assumption-inventory) from the
threat-modelling module asks for, arriving from the other end of the toolchain.

**Subgoal: attach the conservation property, because access control alone is not solvency.** Even a
perfect answer to "who may mint" says nothing about whether the balances add up. That needs the ghost and
the `Sstore` hook above, and it is the property that catches the accounting bug rather than the
authorisation bug.<Cite src="certora-cvl-ghosts" /><Cite src="certora-cvl-hooks" />

**Subgoal: schedule the maintenance, in writing.** Both artifacts now exist and both will rot. The
parametric rule rots more slowly, because new methods enter its scope automatically — but a new *contract*
in the system does not, and neither does a change to what the minter role means. Decide now who re-runs
this on every pull request and who owns the spec when the author leaves. The recommendation to define a
process for keeping specifications aligned with code as requirements change is the third of Trail of Bits'
three design-phase questions,<Cite src="tob-invariant-driven-development" /> and it is the one nobody
answers.

A protocol has a vault with eleven external functions. The team has a green Halmos suite: eight `check_`
tests, one per user-facing function, all passing at default bounds. They are deciding whether to spend
three weeks writing a CVL specification, and they ask you a direct question: "We already verify every
function. What would the expensive tool add?"

Give the strongest honest answer, including the case where the answer is *nothing worth three weeks*. Then
name one property their current setup structurally cannot express, and say why.

<Answer>
**First, correct the premise.** They do not verify every function — they verify eight of eleven, and they
verify each one *in isolation*, at default bounds of loop 2, invariant depth 2, and array lengths drawn
from `0,1,2`.<Cite src="a16z-halmos-config" /> Three functions have no property at all, and nothing in the
setup will tell them when a twelfth function lands. That is not an argument for CVL yet; it is an argument
for knowing what they have.

**What the expensive tool adds, in descending order of value.**

*Coverage that survives growth.* A parametric rule ranges over `method f` and produces a verdict per
method, including methods added later.<Cite src="certora-cvl-rules" /> Their eight tests cover a snapshot;
the vault will have fifteen functions next year and the suite will still say eight green. This is the
single strongest argument, and notice that it is about **time**, not about proof strength.

*Claims about the system rather than about a call.* A `check_` test asserts what one function does. A CVL
invariant asserts what is true of every reachable state, and the induction machinery discharges it across
arbitrary call sequences rather than sequences of length two. Solvency is a statement of this kind; no
per-function test is a weaker version of it, because it is not the same kind of sentence.

*Unbounded loop reasoning.* Where their harness unrolls twice, an invariant covers any iteration
count — at the cost of somebody authoring the invariant, and with the trap that the natural statement is
usually not inductive and needs strengthening.<Cite src="certora-gentle-intro" />

*Bytecode-level checking.* CVL is checked against compiled bytecode rather than source, which is the
*verify what you execute* principle and removes the compiler from the trusted
base.<Cite src="certora-gentle-intro" /> Given the Vyper reentrancy-lock incident on the Solidity track,
where correct source compiled to bypassable bytecode, this is not a theoretical benefit.

**The case where the answer is "nothing worth three weeks", and it is a real case.** If the vault's code
changes weekly, if the team cannot maintain a spec after the engagement, or if the actual risk lives in
the oracle, the admin key or the deployment configuration rather than in the contract logic, then three
weeks of CVL buys a beautifully proved statement about the least dangerous part of the system. The right
advice is then: keep the Halmos suite, raise its bounds until the runs stop terminating and record where
that is, spend the three weeks on stateful fuzzing with real handlers, and revisit verification when the
code freezes. Say this out loud rather than selling the upgrade — the next lesson but one is entirely
about when the answer is no.

**The property they structurally cannot express: conservation of value across the whole contract.**
"The sum of all share balances equals `totalSupply`", or "assets never decrease except through an
accounted withdrawal." Both require a quantity the contract does not store — a running sum over an
unbounded key space. In a fuzz harness you would maintain it in a
[ghost variable](/c/ghost-variable) in the handler; in CVL it is a `ghost` updated by an `Sstore` hook,
which is specification-level state that the prover reasons about
symbolically.<Cite src="certora-cvl-ghosts" /><Cite src="certora-cvl-hooks" /> A `check_` test has no
equivalent: it can assert about the two accounts it touched, and there is no place to accumulate anything
across all writes, because the test *is* the specification and the test has no vantage point above the
call.

**One caveat on that last point, since it is the kind of thing that gets overstated.** A symbolic test
harness can approximate conservation for a *fixed, small* set of accounts — three addresses, sum their
balances before and after. That catches a real class of bug. What it cannot do is quantify over the key
space, which is precisely the case a donation or an unexpected mint exploits.
</Answer>
</Check>

## What this unlocks

**Next**, everything the green result excluded: summaries, optimistic flags and timeouts, and how to read
a verification appendix for its assumptions section rather than its
checkmarks.<Cite src="certora-cvl-methods" /><Cite src="certora-cli-options" />

**Then the decision itself** — which code is worth proving and which is not, and why the highest assurance
tier available for code is not the highest assurance tier available for a protocol.

**Back on the toolchain track**, the [invariant testing](/c/invariant-testing) module's handlers and ghost
variables are now visibly the same artifact one layer down. The statement you wrote for a fuzz campaign is
the statement a prover consumes; only the consumer changed.

**And in an audit context**, a specification is a deliverable a client keeps. A finding is fixed once; a
parametric rule keeps testing the fix and everything written after it. When you get to
[code maturity](/c/code-maturity-assessment), that distinction is what separates a codebase rated
satisfactory on testing and verification from one rated strong.
