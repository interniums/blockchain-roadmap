The same handler, the same three actions, the same 2,000-call budget, the same machine. Once against
a local mock, once against mainnet WETH at a pinned block over a public RPC. Measured on forge
1.7.1:<Cite src="measured-forge-1-7-1" />

```text
# local MiniWeth, deployed in setUp
[PASS] invariant_fullyBacked() (runs: 20, calls: 2000, reverts: 0)
Suite result: ok. finished in 82.94ms

# forked mainnet WETH at block 25,838,569
[PASS] invariant_fullyBacked() (runs: 20, calls: 2000, reverts: 0)
Suite result: ok. finished in 107.97s
```

Eighty-three milliseconds against a hundred and eight seconds. Roughly **1,300 times slower** for
identical work, with the RPC cache already warm — the same 100-call campaign took 3.30 seconds cold
and 3.37 seconds warm, so the gap is not simply fetch latency.<Cite src="measured-forge-1-7-1" />

That is the entire trade of this lesson. Forking buys you a target you did not build, running against
balances and prices and integrating contracts you did not invent. It costs you three orders of
magnitude of throughput, which changes what a campaign can be expected to find.

## What forked state actually gives you

[On-chain fuzzing](/c/onchain-fuzzing) points the campaign at state from a real network at a pinned
block. Echidna added it in version 2.1.0 as state network forking: a campaign can start from an
existing blockchain state provided by an external RPC service, which speeds up setup when the
contracts are already deployed.<Cite src="bsc-echidna-onchain-forking" /><Cite src="tob-onchain-echidna" />

Three things become available that a synthetic fixture cannot give you.

**Real balances and real distributions.** Setup fixtures round everything to `1e18` multiples;
mainnet does not, and rounding bugs live in the remainders.

**Real integrating contracts.** The oracle that actually feeds this market, the token that actually
turns out to have a transfer fee. Every mock is a claim about a dependency; forked state removes the
claim.

**A protocol you did not deploy.** The one that matters for audit and bounty work: you cannot run the
deployment script for a system you are reviewing from the outside, but you can point a fuzzer at its
address.

## Three tools, three configuration surfaces

**Echidna** takes `rpcUrl` and `rpcBlock` in the config file, or `ECHIDNA_RPC_URL` and
`ECHIDNA_RPC_BLOCK` as environment variables.<Cite src="echidna-default-config" /><Cite src="bsc-echidna-onchain-forking" />
One behaviour is easy to get wrong and is stated explicitly in the docs: **only the state at
`ECHIDNA_RPC_BLOCK` is fetched.** If the campaign advances the block number, that advance is simulated
locally, and the state still comes from the originally configured
block.<Cite src="bsc-echidna-onchain-forking" /> A campaign that warps forward a year is not looking
at the chain a year later; it is looking at the same storage with a different `block.number`.

Because of that, the harness must set the environment itself. Trail of Bits' Stax reconstruction puts
`hevm.warp(1665493703)` and `hevm.roll(15725066)` in the constructor so `block.timestamp` and
`block.number` match the fetched state.<Cite src="tob-onchain-echidna" /> The forking docs do the same
with `roll(16771449)` and `warp(1678131671)`, labelled as setting the correct block number and the
expected timestamp for it.<Cite src="bsc-echidna-onchain-forking" /> Forget this and every
time-dependent branch in the target reads a timestamp from a different era than its storage.

**Medusa** puts it under chain configuration: `forkModeEnabled` (default `false`), `rpcUrl`, `rpcBlock`
— with block tags like `LATEST` explicitly not supported yet — and `poolSize`, the size of the client
pool used to query the RPC.<Cite src="medusa-chain-config" /> The recommendation attached to
`poolSize` is worth reading as a description of the constraint rather than as a tuning tip: use 2–3×
the number of workers, but smaller pools may be required to avoid exceeding external RPC query
limits.<Cite src="medusa-chain-config" /> With `workers` defaulting to 10, that is 20–30 concurrent
clients against a provider that is metering you.<Cite src="medusa-fuzzing-config" />

**Foundry** uses the fork cheatcodes you already know — `vm.createSelectFork(url, block)` in `setUp`,
then a normal handler and normal invariants.<Cite src="foundry-fork-testing" /> Two measured facts
about 1.7.1 worth having.

The RPC cache on this machine landed at `~/.foundry/cache/rpc/mainnet/25838569`, and it is a **single
file** of 17,809 bytes rather than a directory.<Cite src="measured-forge-1-7-1" /> Foundry's own
documentation pages disagree with each other about this path — one gives
`~/.foundry/cache/rpc/<chain>/<block>/` and another `$HOME/.foundry/cache/<chain id>/<block number>`
with no `rpc/` segment — so treat the measurement as what this version did here, not as a settled
answer, and check yours before you write a CI cache key against it.

And a warm cache does not make the campaign offline. Pointing `vm.createSelectFork` at an unreachable
endpoint with the block already cached fails in `setUp`:<Cite src="measured-forge-1-7-1" />

```text
[FAIL: vm.createSelectFork: could not instantiate forked environment with provider 127.0.0.1;
 …tcp connect error; Connection refused (os error 61)] setUp()
```

A CI job that forks needs a live provider on every run, whatever it has cached. Budget for the
provider being down as a build failure mode.

## Throughput is the design constraint

The measured 1,300× gap above is one target on one machine over one public endpoint, so treat the
ratio as illustrative. The direction is not in doubt, and there is independent work on one component
of it.

An on-chain fuzzing benchmark ran Echidna in optimization mode against the Stax target from Trail of
Bits' post, comparing a **local node** against a **remote RPC provider**, on the same AWS instance
type, with a test limit of one million and ten repetitions. Its finding: the local node consistently
outperformed the RPC provider across all runs, by between 2× and 10×, and with markedly lower
variance between runs.<Cite src="allthingsfuzzy-onchain-benchmark" /> The author also notes that
initial attempts with two managed providers gave much worse results than expected, leading them to
match node implementations — reth on both sides — before comparing at
all.<Cite src="allthingsfuzzy-onchain-benchmark" />

Two things follow for anyone planning a real campaign.

**Run the node next to the fuzzer if the campaign matters.** The lower variance matters more than
the mean when you are trying to decide whether "we found nothing" means anything.

**Do not compare providers without controlling for the client.** Two endpoints serving the same chain
can differ by a large factor for reasons that have nothing to do with your
harness.<Cite src="allthingsfuzzy-onchain-benchmark" />

The arrangement that follows: keep the fast local campaign as the primary search, and use the fork
for three things — validating that a locally-found sequence is reachable against real state, running
one high-value property against a protocol you did not write, and reproducing a historical incident
at the block before it happened.

## Worked example: the shape of a campaign against someone else's protocol

Trail of Bits reconstructed the 2022 Stax Finance exploit — a missing validation check that cost
321,154 xLP tokens, roughly $2.3 million at the time — using only Echidna, with no prior knowledge of
the attack.<Cite src="tob-onchain-echidna" /> The steps generalise to any protocol you are looking at
from the outside.

**Subgoal: get the interfaces without the source.** They used Slither's code generation utilities to
pull the target's interface and deployment address from Etherscan, along with the other interfaces and
addresses the harness needs — tokens, dependent contracts, user-defined
types.<Cite src="tob-onchain-echidna" /> You are writing a harness against an ABI, not against a
repository.

**Subgoal: put the clock where the storage is.** `hevm.warp` and `hevm.roll` to just before the
incident, matching the fetched block.<Cite src="tob-onchain-echidna" />

**Subgoal: wrap the actions you want the fuzzer to have, and clamp them to what the harness can
afford.** Their `stake` wrapper is one line of clamping — `_amount = (_amount % getBalance()) + 1` —
which is the `%` remapping idiom from lesson two, in a tool with no `bound`
helper.<Cite src="tob-onchain-echidna" />

**Subgoal: make the oracle a quantity, not a boolean.** The whole harness exists to serve one
function:

```solidity
function echidna_optimize_extracted_profit() public returns (int256) {
    return int256(StaxLP.balanceOf(address(this))) - int256(initialAmount);
}
```

with `testMode: optimization` in the config.<Cite src="tob-onchain-echidna" /> Against an unfamiliar
protocol this is the right default oracle, because you do not yet know enough to state a property and
you always know that free money is wrong.

**Subgoal: bound the run and keep what it learns.** `testLimit: 1000000` to prevent an indefinite
runtime if the exploit is not there, and `corpusDir: corpus-stax` to persist
it.<Cite src="tob-onchain-echidna" /> On a forked campaign the corpus does double duty: Echidna saves
the fetched contracts and storage slots into a `cache` subdirectory of the corpus directory —
`block_<N>_fetch_cache_contracts.json` and `block_<N>_fetch_cache_slots.json` — and the docs
recommend using it specifically because the data then does not need to be re-fetched, in particular
for CI.<Cite src="bsc-echidna-onchain-forking" />

The engine's optimizer then generates sequences, evaluates the profit function for each, and at the
end discards the unnecessary and reverting calls, leaving the sequence that maximises the
profit.<Cite src="tob-onchain-echidna" /> No knowledge of the vulnerability was required at any point.

<Aside kind="note">
Echidna's UI exposes a diagnostic worth knowing about: pressing `f` during a forked campaign shows
which contracts and slots are being fetched.<Cite src="bsc-echidna-onchain-forking" /> A campaign
that is still fetching heavily after several minutes is a campaign whose handler keeps touching new
storage — sometimes correct, often a sign that the actor set is wandering into contracts you did not
mean to include.
</Aside>

## What forked state does not give you

Being precise here is what stops a fork campaign from being over-claimed in a report.

**It is a snapshot, not a future.** The state is frozen at the pinned block. Other users' concurrent
behaviour, ordering effects, MEV, and liquidity that arrives tomorrow are all outside it.

**The privileged addresses are still not yours.** Diffusc's Compound example ran into this directly:
in fork mode the Comptroller's admin is an address the fuzzer cannot control, so the harness had to
set the admin to the test contract's own address to proceed.<Cite src="tob-diffusc" /> Every such
substitution is a deviation from reality that belongs in the write-up, because it may be the thing
that made the finding possible.

**Finding the right actor is a separate problem from finding an actor.** Diffusc can discover token
holders automatically in fork mode, and on Compound that was not enough — only holders who had
interacted with specific markets before the upgrade could trigger the bug, and the odds of stumbling
onto one were poor. It reproduced once a known exploiter address was supplied by
hand.<Cite src="tob-diffusc" /> Automatic actor discovery gives you addresses with balances, not
addresses with history.

**Coverage reporting degrades.** From 2.3.1 Echidna tries Sourcify first for the source of executed
on-chain contracts and falls back to Etherscan with an API key; a coverage report needs **both**
source and source mapping, and some verified contracts have source without maps — cETH is their named
example.<Cite src="bsc-echidna-onchain-forking" /> So the number a green campaign entitles you to
talk about is exactly the number a forked campaign is least likely to produce.

You are reviewing a lending protocol that is live on mainnet with $200M deposited. You have four days.
Your colleague proposes running the entire invariant suite against a fork at the current block,
arguing that anything found there is immediately credible.

Give your counter-proposal and the reasoning, in terms of what each campaign can cover.

<Answer>
**Counter-proposal: run the suite locally, and run exactly one or two properties against the fork.**

**The throughput argument decides it.** A forked campaign on the measurement in this lesson ran about
1,300× slower than the identical handler against local state.<Cite src="measured-forge-1-7-1" /> Four
days of forked campaign is worth minutes of local campaign in sequences explored. Whatever the suite
would have found by searching, it will not find on a fork.

**So split the two jobs by what each is good at.**

*Locally*, with a deployment fixture and the full suite: this is where the search happens. Depth,
corpus persistence, many properties, many actors. Everything in lessons three and five applies.

*On the fork*, one property — solvency, or "no actor extracts more than they put in" — and a handler
restricted to the two or three actions that matter. This campaign is not searching; it is checking
that the properties survive contact with the real oracle, the real collateral tokens and the real
balances. The finding you want from it is not a new bug but a *contradiction* with the local suite:
something that holds against your mocks and fails against reality is a mock that lied.

**Three specific things to configure, not defaults.**

Pin the block and record it. Everything about the run — cache reuse, reproducibility, the timestamps
you warp to — depends on the block being fixed, and Medusa does not even accept `LATEST` as a
value.<Cite src="medusa-chain-config" />

Run the node locally if you can get one up inside the four days. The independent benchmark puts a
local node at 2–10× a remote provider with much lower variance, which on a four-day budget is the
difference between one campaign and several.<Cite src="allthingsfuzzy-onchain-benchmark" />

Persist the fetch cache with the corpus, which is what the docs recommend precisely so the state does
not have to be re-fetched on subsequent runs.<Cite src="bsc-echidna-onchain-forking" />

**And what to write in the report.** Not "we fuzzed against mainnet". Rather: the block, the actions
the handler could take, the properties checked, the substitutions made — every admin address you had
to reassign to yourself — and the coverage, with an explicit note if source maps were unavailable for
a dependency and coverage could not be produced for it.<Cite src="bsc-echidna-onchain-forking" />
That paragraph is the difference between a scope statement and a slogan.
</Answer>

## Where this leaves the module

Six lessons, and one claim running through all of them: **the oracle is the part you supply, and it
dominates everything else you can adjust.**

The measurements say it more compactly than the argument does. One campaign, one handler, one budget,
two properties: solvency passed 128,000 calls while a two-call sequence extracted two hundred billion
times its stake.<Cite src="measured-forge-1-7-1" /> One target, one fuzzer, two differential
harnesses four lines apart: one passed 256 runs and the other failed on run
four.<Cite src="measured-forge-1-7-1" /> One contract, two clamps: 128,000 clean calls in eleven
seconds proving nothing, against a counterexample in a tenth of a
second.<Cite src="measured-forge-1-7-1" /> In none of those pairs did the engine change.

So the order of operations, when you sit down in front of an unfamiliar system:

**Write the property in one English sentence** with no "should" in it. If you cannot, you do not yet
understand the system well enough to test it, and that is the finding.

**Build the harness until the campaign can reach the state**, then review the clamps as carefully as
you reviewed the properties, because they are the other half of the same decision.

**Spend the budget on depth and keep the corpus**, and sweep once against a seeded bug rather than
inheriting a default.

**Pick the tool last.** Foundry if the codebase is already there, Medusa if you want parallel workers
and Go tooling, Echidna if you want optimization mode or a forked campaign — and note that the only
published comparison of the last two is by the vendor that maintains both, reporting that they
perform similarly.<Cite src="tob-unleashing-medusa" />

**Formal verification** is next, and it takes the same statements to a different consumer. The
relationship is not competitive: fuzzing gives you a counterexample cheaply and no guarantee, proving
gives you a guarantee expensively and no counterexample, and the sensible sequence is to fuzz until
the properties stop failing and then prove the ones you cannot afford to be wrong about.

**Audit craft** and **contests** are where all of this gets pointed at a deadline. The thing that
carries over is not the tooling. It is the habit of asking, of any green result, *what would have had
to be true for this to fail* — and being able to answer with a coverage number, a list of clamps, and
a sentence about what was never reachable.
