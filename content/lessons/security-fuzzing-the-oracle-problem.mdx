One campaign. One handler. One hundred and twenty-eight thousand calls, zero reverts. Two properties
checked against exactly the same sequences, on forge 1.7.1:<Cite src="measured-forge-1-7-1" />

```text
[PASS] invariant_solvent()      (runs: 256, calls: 128000, reverts: 0)

[FAIL: assertion failed: 998003992015972836924 > 4782598839]
	[Sequence] (original: 6, shrunk: 2)
		deposit(uint256,uint256)  args=[..., 4782598834]
		withdraw(uint256,uint256) args=[..., ...]
 invariant_noFreeMoney()
```

The sequences that the passing property walked through are the same sequences the failing property
walked through. The generator did not get luckier for one of them. The difference is entirely in what
each property was willing to call a failure — and in this case the difference is a two-call sequence
that pays 4,782,598,834 wei and receives 998,003,992,015,972,836,924 wei, a return of roughly two
hundred billion times the stake.<Cite src="measured-forge-1-7-1" />

You already know how to run this. Track 05 built the handler, read the metrics table, and set the
budget. What that track deliberately did not settle is the question this module opens with: **what
makes a campaign capable of failing at all**, and why the answer is almost never the fuzzer.

## The oracle is the only part the tool cannot supply

A fuzzer has two halves. One generates inputs. The other decides whether what happened was wrong.
The generator is the part vendors compete on — mutation strategies, parallel workers, corpus
scheduling — and it is the part that gets benchmarked. The decider is the part you write, and there
is no version of any tool that supplies it for you.

Trail of Bits put a number on the split after several years of doing this commercially: writing good
invariants is 80% of the work, and the tool used to check them is important but
secondary.<Cite src="tob-why-fuzzing" /> That is a vendor talking about its own tools, so read it
with the usual discount — but note which direction the discount runs. A company selling a fuzzer is
telling you the fuzzer is the smaller half.

The claim is testable, and the same post tests it. Two bugs that were widely publicised as formal
verification finds — a violation of DAI's fundamental invariant, discovered by MakerDAO with the
Certora Prover after four years of live code, and a Compound V3 Comet issue where an 8-bit mask over
a 16-bit vector let a fully collateralised account be liquidated — were both re-derived with Echidna
in minutes on an ordinary laptop, once the invariant was written down in
Solidity.<Cite src="tob-why-fuzzing" /> The proof engine was not what found the DAI bug. The sentence
"the sum of all collateral-backed debt and unbacked debt equals the sum of all DAI balances" was.

### What a pass actually asserts

Restate the passing line above precisely. `invariant_solvent()` passed after 128,000 calls. The claim
that licenses is: *across the states this generator reached in this budget, no violation of this
predicate was observed.* Three qualifiers, and all three are load-bearing.

It is not a claim about states the generator did not reach. It is not a claim about predicates you
did not write. And it is not a claim that survives a change to the handler, because the handler
determines which states exist.

This is why [coverage](/c/coverage-guided-fuzzing), not the pass, is the number that carries
information. A green run tells you the search found nothing. Coverage tells you where the search
went. Those are different facts, and only the second one can be argued with.

## Four ways to state an oracle

The two mature standalone fuzzers — Echidna and Medusa, both from Trail of Bits — expose the oracle
as an explicit mode, chosen with `testMode` in the config or `--test-mode` on the command
line.<Cite src="crytic-echidna" /> Foundry does not have modes; it has naming conventions that land
in the same places. Learning the modes is worth doing even if you never leave Foundry, because they
name a distinction Foundry leaves implicit.

### Property mode: a boolean about the state as a whole

The original shape. A function that takes no arguments, returns `bool`, and is evaluated between
generated calls.<Cite src="crytic-echidna" /><Cite src="bsc-echidna-testing-modes" />

```solidity
function echidna_check_balance() public returns (bool) {
    return balance >= 20;
}
```

Three behaviours matter and none of them are obvious from the signature.

**Side effects are discarded.** Whatever the property function does to state is reverted when it
returns.<Cite src="bsc-echidna-testing-modes" /> You can call into the system from inside a property
without corrupting the sequence, which is what makes properties safe to write casually.

**A revert is a failure.** If any call the property makes reverts, the property has failed — the
engine cannot distinguish "the predicate is false" from "computing the predicate blew
up".<Cite src="bsc-echidna-testing-modes" /> A property that sums over an unbounded array is
therefore a property that will eventually report a bug in your test.

**No coverage is collected while a property runs**, and the documentation says so plainly, along with
the consequence: keep property functions simple, and use another mode for anything with a non-trivial
number of branches.<Cite src="bsc-echidna-testing-modes" />

Foundry's `invariant_*` functions occupy this slot. Same shape, same between-calls evaluation, same
inability to see anything that existed only during a call.<Cite src="foundry-invariant-guide" />
Medusa calls the same thing property testing and looks for the `property_` prefix by default, while
noting that adding `echidna_` to the prefix list ports an existing Echidna suite
over unchanged.<Cite src="medusa-testing-config" />

### Assertion mode: a claim about this call

The property moves inside the code path being exercised, which puts the call's own arguments and its
intermediate state in scope.<Cite src="bsc-echidna-testing-modes" /><Cite src="crytic-medusa" />

```solidity
function testStake(uint256 toStake) public {
    uint256 balance = balanceOf(msg.sender);
    toStake = toStake % (balance + 1);
    if (toStake < MINSTAKE) return;              // precondition
    stake(msg.sender, toStake);                  // action
    assert(staked(msg.sender) == toStake);       // postcondition
    assert(balanceOf(msg.sender) == balance - toStake);
}
```

Read the four lines as pre / act / post and you have a Hoare triple with a fuzzer supplying the
inputs. Nothing here is expressible as a between-calls boolean, because `balance` — the value before
the action — does not exist once the call returns.

The trade-offs invert cleanly against property mode.<Cite src="bsc-echidna-testing-modes" /> Side
effects are **preserved**, so an assertion function is also an action in the sequence. Coverage **is**
collected, so assertion functions drive exploration as well as checking it. And the failure condition
is narrower: Echidna reports a violation when an `assert` fails in the first call frame of the target
contract, or when any contract emits an `AssertionFailed` event — the event being the escape hatch
for assertions in nested calls and for older compilers.<Cite src="bsc-echidna-testing-modes" />

One hazard is worth memorising, because it silently disables the mode. If the code under test already
uses `assert` for input validation — `assert(tokens > 0)` at the top of a deposit function — then
every rejected input is reported as a property violation.<Cite src="bsc-echidna-testing-modes" /> The
codebase has to reserve `assert` for "this cannot happen" before assertion mode means anything, which
is the discipline Solidity's own `Panic` versus `Error` split has been pushing since 0.8.

Medusa expresses the same idea as configuration rather than convention: assertion testing is on by
default, and `panicCodeConfig` decides which EVM panics count as failures. Only `assert(false)`
does by default; arithmetic overflow, division by zero, out-of-bounds array access and the rest are
each an opt-in flag.<Cite src="medusa-testing-config" /> That default is the right one and worth
understanding — in a Solidity 0.8 codebase an arithmetic panic is usually the *guard working*, not
the bug.

In Foundry there is no mode to select: assertions inside handler functions are assertion-shaped
checks, and they run as part of the call rather than between calls. The distinction is real even
though nothing in the tool names it.

### Optimization mode: how bad, not whether

The third shape is the one almost nobody uses, and for economic properties it is strictly more
informative than the other two.

Instead of falsifying a boolean, the engine searches for the call sequence that **maximises** a
returned `int256`.<Cite src="bsc-echidna-optimization-mode" /><Cite src="crytic-echidna" /> The
function still takes no arguments; a revert during its evaluation is treated as the minimum possible
value.<Cite src="bsc-echidna-optimization-mode" />

```solidity
function echidna_optimize_extracted_profit() public returns (int256) {
    return int256(token.balanceOf(address(this))) - int256(initialAmount);
}
```

That specific function is not a teaching invention. It is the one Trail of Bits used to reconstruct
the 2022 Stax Finance exploit — a missing validation check that cost 321,154 xLP tokens, worth
roughly $2.3 million at the time — with no prior knowledge of the attack. They wrapped the deployed
contracts, set `testMode: optimization`, pointed the campaign at forked state, and let the engine
find the sequence that made the number go up.<Cite src="tob-onchain-echidna" />

Why this is the better question for anything denominated in money: an assertion that profit is
exactly zero fails the instant rounding gives an attacker one wei, and one wei is not a finding.
Optimization mode reports the largest value it reached, so the same run that discovers the leak also
sizes it. Medusa carries the mode too, with `optimize_` as the default prefix and optimization
testing enabled by default.<Cite src="medusa-testing-config" />

The remaining two Echidna modes are worth knowing by name. `overflow` reports integer over- and
underflow on Solidity 0.8 and later, and `exploration` collects coverage without checking any
property at all — which is what you run when you want to know whether the harness can reach the code
before you have decided what to assert about it.<Cite src="crytic-echidna" />

## Worked example: turning a boolean into a number

Take the failing property from the top of this lesson. The vault mints shares with the rounding
direction pointed the wrong way, and the property was a boolean over two ghost accumulators: total
paid in by the handler's actors, total received back.

**Subgoal: establish that a leak exists at all.** The boolean form is the cheapest thing to write and
the fastest thing to falsify.

```solidity
function invariant_noFreeMoney() public view {
    assertLe(handler.ghost_received(), handler.ghost_paid());
}
```

On this machine that failed inside the default budget, and shrinking reduced the sequence from six
calls to two.<Cite src="measured-forge-1-7-1" /> Total information delivered: *there is a path where
money comes out faster than it goes in.*

**Subgoal: find out whether anyone would bother.** The boolean cannot answer that, because it stops
at the first violation. Restate it as a quantity:

```solidity
// Echidna / Medusa optimization mode
function echidna_opt_extracted() public view returns (int256) {
    return int256(handler.ghost_received()) - int256(handler.ghost_paid());
}
```

Now the campaign's output is a maximum rather than a verdict, and the maximum is the number that
decides severity. On the same target, the deterministic version of the leak pays 1 wei and returns
999,000,999,000,999,000,999 wei — and running it a hundred times in a loop extracts
95,117,369,102,223,887,327,231 of the vault's 10^24 assets, which is 9.5% of the pool for a hundred
wei and gas.<Cite src="measured-forge-1-7-1" />

**Subgoal: notice what the boolean would have concealed in the other direction.** Suppose the vault
had rounded correctly and the only leak were a genuine one-wei dust artefact. The boolean fails
identically. You would triage it, write it up, argue about it, and discover the severity by hand.
The optimization run reports "max value: 1" and you close the tab.

That asymmetry is the whole argument for the mode. A boolean gives you one bit for a run that cost
you minutes; a maximum gives you the bit and the magnitude for the same minutes.

<Aside kind="note">
Optimization mode wants different knobs from a normal campaign. Trail of Bits' own example runs it
with `--seq-len 1` because the target function is stateless, and with `--shrink-limit 50000` — ten
times the default — because in this mode shrinking is doing input *minimisation* against a maximum
rather than sequence reduction against a
predicate.<Cite src="bsc-echidna-optimization-mode" /><Cite src="echidna-default-config" /> Their
documented run reports `max value: 1076841` on one campaign and `1146878` on a second that reloaded
the first campaign's corpus, with the note that a longer campaign will likely yield a larger
value.<Cite src="bsc-echidna-optimization-mode" /> Treat a reported maximum as a lower bound on
severity, never as the severity.
</Aside>

## Where the modes sit relative to each other

Four questions decide the mode, and they are about the property, not the tool.

**Does the check need the call's arguments, or a value that exists only mid-call?** If yes, it has to
be an assertion. Nothing evaluated between calls can see them.

**Does the check need to hold across the whole system rather than one operation?** If yes, it wants
to be a property — a boolean over committed state, evaluated after every call, independent of which
call it was.

**Is the quantity being constrained money?** If yes, ask for the maximum instead of the bound.
"Attacker profit is never positive" and "maximise attacker profit" are the same search with different
reporting, and one of them tells you what to write in the severity field.

**Do you know yet what you are asserting?** If no, run exploration mode, or run any mode with a
trivially true property, and read the coverage. A harness that cannot reach the interesting code is a
harness problem, and finding that out before you have invested in properties saves the invested time.
That is the next lesson.

## The same statement, several consumers

One reason to write oracles carefully rather than conveniently is that the good ones outlive the tool
they were written for.

Trail of Bits' invariant-driven framing makes this explicit: an invariant is a statement about a
program that must always hold regardless of state or execution path, and testing, formal verification
and runtime monitoring are three *consumers* of that statement rather than three
activities.<Cite src="tob-invariant-driven-development" /> The same sentence renders as a Foundry
`invariant_`, an Echidna `echidna_`, a Medusa `property_`, a prover rule, and an alert. What does not
survive the translation is a property phrased in one tool's private vocabulary.

The practical form of that discipline: **write the property in English first, in one sentence, with
no "should" and no "usually" in it.** If the English sentence needs the word "typically", the
property is not a property. If it needs a value that only exists during a call, you have discovered
that it is an assertion. If it needs a quantity rather than a comparison, you have discovered that it
is an optimization target. The mode falls out of the sentence.

<Check type="explain" concept="optimization-mode">
A lending market lets an account be liquidated when its health factor drops below 1. You suspect
liquidation is mispriced: under some sequence the liquidator can seize collateral worth more than the
debt they repay plus the intended bonus.

A colleague proposes the property `assert(seizedValue <= repaidValue * (1 + bonus))` inside the
liquidation call. Say what that catches, what it misses, and what you would run instead.

<Answer>
**It catches the mispricing, and it is the right first thing to write.** The check needs `repaidValue`
and `seizedValue`, both of which exist only during the liquidation call, so it must be an assertion
rather than a between-calls boolean.<Cite src="bsc-echidna-testing-modes" /> A property evaluated
after the call sees only the resulting balances and would have to reconstruct the intent.

**It misses the size of the problem, and size is the whole question here.** Every liquidation
mechanism has rounding somewhere, so the assertion will eventually fail by one wei on some input, and
one wei is not a finding. You will then spend an afternoon deciding whether the failure you got is
the failure you were looking for.

**It also misses the multi-step version.** Written as an assertion inside one call, it constrains one
liquidation. The interesting sequence is usually several: move the price, liquidate partially,
re-enter, liquidate again. An in-call assertion cannot see across those steps.

**What to run instead — both, in this order.** Keep the assertion; it is cheap and it drives
coverage, and unlike a property function it collects coverage while it
runs.<Cite src="bsc-echidna-testing-modes" /> Then add an optimization target over the whole
sequence:

```solidity
function echidna_opt_liquidator_profit() public view returns (int256) {
    return int256(ghost_seizedValue) - int256(ghost_repaidValue);
}
```

Now the campaign reports the largest extractable amount and the sequence that achieves it, which is
what a severity rating and a proof-of-concept both need.<Cite src="bsc-echidna-optimization-mode" />
That is the shape Trail of Bits used against Stax: not "is profit ever positive" but "make profit as
large as you can".<Cite src="tob-onchain-echidna" />

**And the caveat to carry:** a reported maximum is a lower bound. A longer campaign will typically
find a larger one, and the documentation says so about its own
example.<Cite src="bsc-echidna-optimization-mode" /> Report it as "at least X", never as "at most X".
</Answer>
</Check>

<Check type="predict" concept="invariant-testing">
You inherit a suite with one invariant, `invariant_totalSupplyMatchesBalances()`, which sums every
holder's balance and compares it against `totalSupply()`. It has passed nightly for four months at
1,000 runs. The protocol is then drained through the staking module.

Predict what the campaign's output looked like on the night before the drain, and name the two
numbers you would have wanted in the nightly report.

<Answer>
**It looked exactly like every other night: PASS, in green, at 1,000 runs.** Nothing about the drain
would have perturbed it, because the property was true throughout the exploit. A token accounting
identity is preserved by any transfer, including the attacker's. The property was never capable of
failing on this bug — which is the definition of the oracle problem, restated as an incident.

**Number one: coverage of the staking module.** If the handler never called `stake` and `unstake` in
a plausible order, the campaign never entered the region where the bug lives, and a pass says nothing
about it. Coverage is the number that distinguishes "searched and found nothing" from "never went
there", and it is the number nobody puts in the nightly summary.

**Number two: the revert rate, per selector.** A staking action that reverts on every generated call
— because the handler never satisfies its precondition — produces exactly the same green line as one
that executes cleanly. Track 05's metrics table names the selector; four months of nightly runs with
`Handler.stake` at a 100% revert rate is four months of a suite that was never testing staking.

**The structural lesson.** This suite had one property and it was a conservation identity, which is
the cheapest property to write and one of the least discriminating. It cannot see fairness (did A's
action harm B), it cannot see solvency against an external asset, and it cannot see value leaving
through a path that keeps the books balanced. The fix is not a longer campaign; it is more properties
of different families, which is lesson three.
</Answer>
</Check>

## Where this pays off

**The next lesson** takes the other half of the pair. A perfect property against a harness that
cannot reach the state still reports nothing, and the diagnostic that tells you which failure you
have takes about a minute to run.

**Lesson three** is the property catalogue: four families that between them catch most economic bugs,
including the family the vault at the top of this lesson violated.

**Lesson four** removes the need to write the oracle by hand, by making a second implementation the
oracle instead.

**The formal verification module** picks up the same statement and asks a different consumer to
check it. Note what carries across and what does not: the sentence carries, the mode does not, and a
property you had to phrase in one engine's private vocabulary will need rewriting before a prover
can read it.<Cite src="tob-invariant-driven-development" />
