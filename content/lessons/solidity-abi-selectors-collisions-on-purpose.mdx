Two facts, and the distance between them is this lesson.

```text
$ cast sig "transferFrom(address,address,uint256)"
0x23b872dd
$ cast sig "gasprice_bit_ether(int128)"
0x23b872dd
```

The first is the selector every token integration on Ethereum depends
on.<Cite src="eip-20" /> The second is a function nobody has ever
written, produced by searching for a name that lands on the same four
bytes.<Cite src="foundry-cast-abi-encoding" />

And yet: put both declarations in one contract and it will not compile. The collision is real, the
compiler catches it, and almost every place you will meet a selector collision in production is
somewhere the compiler was never looking. Getting the boundary right is the point.

## The arithmetic, done honestly

A selector is four bytes.<Cite src="solidity-abi-spec" /> That is 2³² values — 4,294,967,296 — for
an unbounded space of possible signatures. Two consequences follow, and they are different sizes of
problem.

**Accidental collision.** By the birthday bound, a corpus of `n` random selectors contains a
collision with probability around 50% once `n` is near `sqrt(2 · ln 2 · 2³²)`, which is about
77,000 — call it 2¹⁶. This is arithmetic, not a measurement of deployed contracts; nobody has
published an authoritative count of real-world selector collisions on mainnet, and you should treat
"how often does this happen by accident" as an open empirical question rather than a known
frequency. The pairs above are famous because people went looking, not because a survey found them.

**Deliberate collision.** Finding a name whose selector equals a *chosen* four bytes takes an
expected 2³² trial names. That is hashing work, not cryptanalysis: no property of Keccak is being
attacked, and no stronger hash function changes the number, because the number comes from the
truncation and not from the digest.<Cite src="solidity-abi-spec" />

The existence proof is in production. Seaport has a function whose name was mined so that its
selector is `0x00000000`, placing it earliest in a dispatcher that compares selectors in
order.<Cite src="philogy-selector-switches" /> That is 2³² expected work spent on a gas
optimisation. If it is worth doing for gas, assume it is worth doing for access.

<Aside kind="note">
`0x00000000` and `0xffffffff` are reserved by the ABI specification — but specifically as **error**
selectors, reserved for future use.<Cite src="solidity-abi-spec" /> Nothing in the specification
stops a *function* selector from taking either value, which is why the Seaport case is legal.
Reserved-for-future-use is a promise about what the specification will define, not a validity check
anything performs.
</Aside>

## Inside one contract, the compiler is watching

`checkHashCollisions` takes a single `ContractDefinition`, walks its interface function list,
truncates each signature hash to four bytes, and raises a fatal type error — *Function signature hash
collision for* — the moment two of them agree.<Cite src="solc-contractlevelchecker-source" />

So within a compilation unit, a selector really is a unique identifier, and it is guaranteed by a
check rather than by luck. That guarantee is exactly as wide as the argument to that function: one
contract.

This is why the collision class feels theoretical to most Solidity developers. You have never met
one, because in the only place you routinely look, the compiler removes them before you can.

## Two dispatchers, one byte string

Now put two separately compiled contracts behind one address.

A proxy holds storage and delegates calls to an implementation. It also needs functions of its own —
something like `upgradeTo(address)`. OpenZeppelin's documentation states the problem in its own
words and then generalises it: clashing can happen among functions with different names, because
every function in a contract's public ABI is identified at the bytecode level by a four-byte
identifier, and **the Solidity compiler tracks when this happens within the same contract, but not
when the collision happens across different ones, such as between a proxy and its logic
contract**.<Cite src="oz-proxies-function-clashes" />

Read the failure as a sequence rather than as a fact:

**Step 1 — establish that both dispatchers see the same bytes.** A call arrives at the proxy
address. The proxy's own dispatcher runs first, on the full calldata. If nothing matches, the proxy
delegates the same calldata to the implementation, whose dispatcher runs on it too. One byte string,
two independent searches.

**Step 2 — establish who chooses the names.** The implementation is the upgrade. Whoever writes the
next implementation chooses its function names, and therefore chooses which four bytes it responds
to. Nothing at deploy time compares that set against the proxy's set, because they were never
compiled together.

**Step 3 — establish what a match buys.** If an implementation function's selector equals
`upgradeTo(address)`, then whichever dispatcher runs first wins, permanently, for that call
shape — and the loser's function becomes unreachable through the proxy. A governance function
silently stops existing, or an implementation function silently shadows an admin one. Which of the
two happens is decided by dispatch order, not by intent.

**Step 4 — establish that this can be aimed.** From the arithmetic above, a name colliding with any
chosen selector is 2³² hashes away. An implementation that is malicious rather than unlucky does not
need an accident.

### The two production answers

**Split dispatch by caller.** The transparent proxy pattern decides what to delegate based on
`msg.sender`: if the caller is the proxy's admin, the proxy answers only messages it understands and
delegates nothing; if the caller is anyone else, the proxy always delegates, even when the calldata
matches one of its own functions.<Cite src="oz-proxies-function-clashes" /> The table is worth
memorising, because it is unintuitive in exactly one cell:

| `msg.sender` | `owner()` | `upgradeTo()` | `transfer()` |
|---|---|---|---|
| admin | proxy's `owner()` | proxy's `upgradeTo()` | fails |
| anyone else | implementation's `owner()` | fails | implementation's `transfer()` |

<Cite src="oz-proxies-function-clashes" />

The admin cannot call `transfer()` through the proxy at all. That is not a bug; it is the price of
making "which dispatcher answers" a function of the caller instead of a function of the bytes.
OpenZeppelin's tooling avoids the sharp edge by making a separate `ProxyAdmin` contract the actual
admin of each transparent proxy, so a human account is never in the restricted
row.<Cite src="oz-proxies-function-clashes" />

**Make the mapping explicit.** A diamond replaces the compiler-generated dispatcher with an explicit
selector-to-facet mapping, maintained by a `diamondCut` function that adds, replaces or removes
functions.<Cite src="eip-2535" /> The specification addresses the collision case directly: a
selector clash would have the unintended consequence of replacing an existing function when the
intention was to add a new one, and this is not possible with a properly implemented `diamondCut`
because it prevents adding function selectors that already
exist.<Cite src="eip-2535" />

Notice what changed. The check did not get stronger — four bytes are still four bytes. What changed
is *when* the check runs: at the moment the mapping is edited, on chain, with both sets in front of
it. The transparent proxy avoids the question; the diamond answers it at write time. Neither makes
the selector space larger.

## Four bytes used as a namespace: ERC-165

The selector space also gets reused as an identifier space in its own right, which stretches it
further.

ERC-165 defines an interface as a *set of function selectors* — explicitly a subset of Solidity's
notion of an interface, which also carries return types, mutability and events — and defines the
interface identifier as the **XOR of all function selectors in the
interface**.<Cite src="eip-165" /> `supportsInterface(bytes4)` hashes to `0x01ffc9a7`, which is
therefore ERC-165's own identifier, being the XOR of a one-function
set.<Cite src="eip-165" />

You can reproduce any of them with nothing but `cast sig` and a XOR. ERC-721's nine functions:

which is the identifier ERC-721 states for itself.<Cite src="eip-721" />

Three properties of this construction matter in practice, and none of them are obvious from the word
"id".

**It is not a digest of the interface.** It is a XOR of digests. Reordering the functions changes
nothing, because XOR commutes. Adding a function and then removing it returns the identifier to its
previous value. Two interfaces with the same function *set* have the same identifier no matter what
their return types or state mutability say — those were never in the selectors.

**Solidity's built-in excludes inheritance.** `type(I).interfaceId` is defined as the XOR of all
function selectors defined **within the interface itself, excluding all inherited
functions**.<Cite src="solidity-abi-encoding-functions" /> So an `interface IB is IA` yields an
identifier covering only `IB`'s own declarations. If you want the union, you write
`type(IA).interfaceId ^ type(IB).interfaceId` — which is what most standards' reference
implementations do, and which is only correct because the two sets are disjoint.

**It inherits every four-byte property from the previous sections.** An interface identifier is four
bytes derived from other four-byte values, all of them truncated digests. `supportsInterface` is a
claim a contract makes about itself, checked against no evidence — and ERC-165 says as much by
requiring a conforming contract to answer `false` for `0xffffffff`, a probe whose only purpose is to
catch contracts that answer `true` to everything.<Cite src="eip-165" />

<Check type="explain" concept="abi-selector-collision-risk">
A team is shipping a UUPS-style upgradeable contract. In review, someone proposes a rule: "before
every upgrade, we will run a script that computes the selectors of the new implementation and
compares them against the proxy's own selectors. If there is no overlap, the upgrade is safe from
clashes."

The rule is a genuine improvement. Name the two things it still does not cover, and say what you
would ask for instead.

<Answer>
**Gap one: it checks the wrong pair for the wrong risk.** The script compares implementation
against *proxy*, which is the clash OpenZeppelin describes.<Cite src="oz-proxies-function-clashes" />
It says nothing about implementation *N* against implementation *N+1*. A selector that exists today
and is dropped tomorrow does not clash with anything — it simply stops answering, and every
integrator calling it now reaches whatever the new dispatcher does with unmatched calldata. That is
not a collision, but it is the same review question and the script will pass it.

**Gap two: it verifies bytes, not authorship.** A no-overlap result proves the two selector sets are
disjoint. It proves nothing about whether the implementation was chosen adversarially — and a
malicious implementation does not need an overlap with the proxy to be malicious. The check
addresses the accidental case, which the arithmetic says is rare, and leaves the deliberate case,
which the arithmetic says costs 2³² hashes, exactly where it was.

**What to ask for instead.** Two things, in this order.

*Make the check structural, not procedural.* A script someone remembers to run is a control that
fails silently. The transparent proxy makes overlap impossible to exploit by routing on
`msg.sender` rather than on the calldata;<Cite src="oz-proxies-function-clashes" /> a diamond makes
it impossible to introduce by rejecting a `diamondCut` that adds an already-present
selector.<Cite src="eip-2535" /> Both move the guarantee from a step in a runbook into the contract.

*Then ask what the upgrade key is, and who holds it.* Once the mechanism is structural, the residual
risk is not a hash collision — it is that someone can install any implementation at all. The
selector question is the small one; the answer to it should be a pattern, so that review time can go
to the large one.
</Answer>
</Check>

## Where this pays off

You now have the two halves of the selector story: four bytes are derived from a string you chose,
and four bytes are cheap to aim. Everything the rest of the module does with dispatch, fallbacks and
routers sits on top of that, and so does every proxy pattern you will meet later.

Carry one framing forward. A selector is an **identifier**, in the sense that a filename is an
identifier: unique enough to be useful, chosen by whoever wrote it, and never a statement about
authority. When a design treats four bytes as a permission — "only the admin function has these
bytes" — the design has confused a name with a lock. The next lesson looks at what the contract
actually does with those bytes, and shows that even the search for a match is not the neutral,
constant-time operation it is usually assumed to be.
