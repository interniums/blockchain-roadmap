Here are two functions. In Solidity they have different parameter types, different argument
checking, and different call sites. Put them in one contract and the compiler refuses the file.

```solidity
interface IVault { }

contract Router {
    function route(IVault v) external { }
    function route(address v) external { }
}
```

The error is not about overloading being illegal — overloading by parameter type is exactly what
Solidity allows. The error is that these two overloads stop being distinguishable somewhere between
the source and the wire. The compiler names the place: it is an error if two externally visible
functions differ by their Solidity types but not by their **external**
types.<Cite src="solidity-docs-contracts" />

You already know that a call is four bytes of selector followed by an encoded argument tuple, and
you have decoded that layout by hand. This lesson is about the four bytes specifically, and about
the thing sitting between your declaration and the hash: the **canonical signature**, which is a
lossy projection of what you wrote. Most selector bugs are projection bugs.

## The signature is a projection, not a copy

The specification defines the signature as the canonical expression of the basic prototype without
data location specifier — the function name with the parenthesised list of parameter types, split by
a single comma, no spaces.<Cite src="solidity-abi-spec" /> Then it gives a table mapping Solidity
types that are not ABI types onto the ones that are.<Cite src="solidity-abi-spec" />

| You wrote | The signature says |
|---|---|
| `address payable` | `address` |
| a contract or interface type | `address` |
| an `enum` | `uint8` |
| a user-defined value type | its underlying value type |
| a `struct` | a parenthesised tuple `(...)` |
| `uint`, `int` | `uint256`, `int256` |
| `bool` | `bool` (kept, though it is a restricted `uint8`) |
| `address` | `address` (kept, though it is a `uint160`) |

<Cite src="solidity-abi-spec" />

Read that table as a list of things the wire cannot see. Your `enum Side { Buy, Sell }` is a
`uint8` out there, with no rule that the byte is 0 or 1. Your `type Price is uint128` is a
`uint128`. Your `IVault` is twenty bytes. The type system that made those distinctions meaningful
stops at the contract boundary — which is the same boundary at which
[the encoding stops being self-describing](/c/abi-encoding).

Two of these rows are kept rather than collapsed, and the asymmetry is worth noticing: `bool` and
`address` keep their own spelling in the signature even though the specification defines them in
terms of `uint8` and `uint160`.<Cite src="solidity-abi-spec" /> `enum` does not. There is no
principle you can derive here; there is a table you consult.

### What the compiler checks, and where it stops

Two different checks fire on the `Router` example above, and they are worth telling apart because
they cover different failures.

The first is the overload clash: solc reports *Function overload clash during conversion to
external types for arguments* when two overloads of the same name project onto the same external
parameter types.<Cite src="solc-contractlevelchecker-source" /> That is a name-level check.

The second is broader and fires on functions with entirely different names. `checkHashCollisions`
walks the contract's interface function list, hashes each canonical signature to four bytes, and
raises a fatal type error — *Function signature hash collision for* followed by the signature — the
moment two of them land on the same four bytes.<Cite src="solc-contractlevelchecker-source" />

Note the argument that function takes: one `ContractDefinition`.<Cite src="solc-contractlevelchecker-source" />
The guarantee is per compilation unit, and the next lesson is about what lives outside it.

## Return types are outside, on purpose

The signature contains no return types. The specification states the reason rather than leaving it
to be inferred: in Solidity's function overloading, return types are not considered, and the reason
is to keep function call resolution **context-independent**.<Cite src="solidity-abi-spec" /> The
language documentation says the same thing from the other side — return parameters are not taken
into account for overload resolution.<Cite src="solidity-docs-contracts" />

This is a design choice with a shape you have met before in language design. If return types were
part of resolution, then which function a call site means would depend on what the caller does with
the result, and a call would have no meaning until its context was known. Excluding them means
`f(uint256)` resolves to one thing everywhere, including from a contract compiled years later by a
different team that has only the four bytes.

The direct consequence: two functions differing only in return type have the same canonical
signature, therefore the same selector, therefore cannot coexist. `balanceOf(address)` returning
`uint256` and `balanceOf(address)` returning `uint128` are the same function on the wire. There is
no version of the ABI in which a caller can ask for the second one.

The JSON ABI *does* carry both inputs and outputs.<Cite src="solidity-abi-spec" /> That asymmetry is
the whole reason decoding a return value requires the ABI file and encoding a call does not: the
return type is schema you must bring, because it was never in the bytes.

## Worked derivation: a signature with four projections in it

Take a function that exercises most of the table at once.

```solidity
type Price is uint128;
enum Side { Buy, Sell }
struct Order { address maker; uint256 amount; }

interface IExchange {
    function submit(Order calldata o, Side s, Price p, IERC20 token) external;
}
```

**Subgoal — strip everything that is not a type.** Drop the parameter names `o`, `s`, `p`, `token`.
Drop the data location `calldata`. Drop the return list, which is empty here anyway. What survives
is the name and an ordered list of types.<Cite src="solidity-abi-spec" />

**Subgoal — project each type onto its ABI type.** `Order` is a struct, so it becomes the tuple
`(address,uint256)` — its members in declaration order, each itself projected. `Side` is an enum, so
`uint8`. `Price` is a user-defined value type, so its underlying `uint128`. `IERC20` is a contract
type, so `address`.<Cite src="solidity-abi-spec" />

**Subgoal — assemble with no spaces.** Single commas, no whitespace anywhere:

```text
submit((address,uint256),uint8,uint128,address)
```

**Subgoal — hash and truncate.** Keccak-256 of the ASCII bytes of that string, then take the first
four bytes — the left, high-order bytes in big-endian
order.<Cite src="solidity-abi-spec" /><Cite src="nist-fips-202" />

```text
$ cast sig "submit((address,uint256),uint8,uint128,address)"
0x8f6d7b4b
```

**Subgoal — check what you would have got by guessing.** Nothing about `0x8f6d7b4b` is derivable
from `submit`. Change `Price` from `uint128` to `uint256` — a change invisible at every call site,
because the user-defined value type keeps its name — and the selector moves. Add a third member to
`Order` and it moves again. The selector is a function of the *shape* of your interface, and any
edit to that shape is a wire-breaking change even when the source diff looks cosmetic.

<Aside kind="note">
The tuple spelling has a consequence that bites when you leave Solidity. `cast abi-encode
"foo((uint256)[],uint256)"` encodes a function taking two separate arguments — an array and an
integer — while `cast abi-encode "foo(((uint256)[],uint256))"` encodes a function taking one tuple
argument. Those produce different encodings, and the second is the one that matches Solidity's
`abi.encode(someStruct)`.<Cite src="foundry-cast-abi-encoding" /> When a struct crosses into a
command line, the extra parentheses are the struct.
</Aside>

### The same derivation, three different truncations

The canonical-signature machinery is reused for two other things in the language, and the amount of
hash that survives differs each time. It is worth holding all three together, because the
differences are not arbitrary.

- A **function** is named by the first four bytes of the hash.<Cite src="solidity-abi-spec" />
- An **error** is named the same way: the specification's own example gives
  `InsufficientBalance(uint256,uint256)` the selector `0xcf479181`, and revert data is encoded
  exactly as a call to that "function".<Cite src="solidity-abi-spec" /> Two selectors,
  `0x00000000` and `0xffffffff`, are reserved for future use.<Cite src="solidity-abi-spec" />
- An **event** is named by the *whole* 32-byte hash of its canonical signature, sitting in
  `topics[0]`.<Cite src="solidity-abi-spec" />

The reason for the split is where each identifier lives. A selector is prepended to calldata, and
calldata is paid for per byte, so it is truncated as far as anyone dared. A topic occupies a full
32-byte log slot whether you fill it or not, so there is nothing to save by truncating — and a
32-byte identifier does not collide. Every property in the rest of this module that follows from
"four bytes" simply does not apply to `topics[0]`.

## Four ways to say the same four bytes, and what each one checks

Solidity gives you four ways to produce a call's bytes. They differ only in how much the compiler
verifies, and that difference is the entire practical content of this lesson.

```solidity
// 1. the typed selector
IERC20.transfer.selector                                     // bytes4, checked

// 2. full type-check against the function
abi.encodeCall(IERC20.transfer, (to, amount))

// 3. selector checked, arguments not
abi.encodeWithSelector(IERC20.transfer.selector, to, amount)

// 4. nothing checked
abi.encodeWithSignature("transfer(address,uint256)", to, amount)
```

`abi.encodeCall` takes a function pointer and performs a full type-check, ensuring the types match
the function signature; its result equals `abi.encodeWithSelector(functionPointer.selector, ...)`.
`abi.encodeWithSignature(sig, ...)` is defined as
`abi.encodeWithSelector(bytes4(keccak256(bytes(signature))), ...)` — the string is hashed as
written.<Cite src="solidity-abi-encoding-functions" />

Both of those definitions are worth reading twice. The second one means the signature string is
never parsed, never normalised, never compared to anything. It is bytes fed to a hash.

Here is what that costs, compiled on solc 0.8.36:<Cite src="solidity-0836-release" />

```solidity
// (a) swapped arguments, encodeCall — does not compile
abi.encodeCall(t.transfer, (amt, to));
//  Error (5407): Cannot implicitly convert component at position 0
//                from "uint256" to "address".
//  Error (5407): Cannot implicitly convert component at position 1
//                from "address" to "uint256".

// (b) swapped arguments, encodeWithSelector — compiles, ships, misbehaves on chain
abi.encodeWithSelector(IERC20.transfer.selector, amt, to);

// (c) uint instead of uint256, encodeWithSignature — compiles, wrong selector
abi.encodeWithSignature("transfer(address,uint)", to, amt);
```

Case (c) is the one that surprises people, and it deserves precision, because the tooling and the
language disagree about it. `uint` is a legal Solidity alias, but the specification says that for
computing the function selector, `uint256` has to be used.<Cite src="solidity-abi-spec" />

- `cast sig "transfer(address,uint)"` returns `0xa9059cbb` — the tool normalises the alias for you
  before hashing.<Cite src="foundry-cast-abi-encoding" />
- `abi.encodeWithSignature("transfer(address,uint)", ...)` does not. By its own definition it hashes
  the literal string, and the first four bytes of `keccak256("transfer(address,uint)")` are
  `0x6cb927d8`, not the ERC-20 `transfer` selector.<Cite src="solidity-abi-encoding-functions" /><Cite src="eip-20" />

So the habit of checking a signature with `cast sig` and then pasting the same string into
`encodeWithSignature` verifies nothing: the command-line tool was more forgiving than the compiler
will be. The two disagree exactly where it costs you.

<Check type="predict" concept="abi-canonical-signature">
A team is adding a permissioned withdrawal to a vault. Two proposals are on the table:

```solidity
// proposal A
function withdraw(uint256 shares) external returns (uint256 assets);

// proposal B
enum Asset { Underlying, Wrapped }
function withdraw(uint256 shares, Asset a) external returns (uint256 assets);
```

Three questions, all answerable from the rules and none needing a hash.

1. Someone claims proposal B is backwards compatible with A "because the first argument is the
   same". What is wrong with that?
2. A reviewer asks whether changing A's return type from `uint256` to `uint128` would break
   existing integrators' encoded calls. Would it?
3. If the team later changes `Asset` from an `enum` to `type Asset is uint8`, does B's selector
   change?

<Answer>
**1. B is a different function, not a compatible extension.** The canonical signature is the name
plus the full parameter list, so A is `withdraw(uint256)` and B is `withdraw(uint256,uint8)` — the
enum projecting to `uint8`.<Cite src="solidity-abi-spec" /> Different strings, unrelated digests.
Every existing caller sends A's four bytes; if the team ships only B, those calls no longer match
any function. Backwards compatibility here means keeping both declarations, which is legal
overloading precisely because their external types differ.<Cite src="solidity-docs-contracts" />

**2. No — the encoded call is unchanged.** Return types are not part of the
signature.<Cite src="solidity-abi-spec" /> The calldata an integrator sends is byte-identical
before and after. What breaks is the *decode* on their side: they will read 32 bytes and interpret
them against a stale ABI. Nothing on chain will tell them, because the return type was never in the
bytes — which is why this class of change is invisible to every selector-based tool and shows up as
a wrong number in a client.

**3. No.** A user-defined value type projects to its underlying value type, and an enum projects to
`uint8`.<Cite src="solidity-abi-spec" /> `type Asset is uint8` and `enum Asset` with at most 256
members both land on `uint8`, so the canonical signature is `withdraw(uint256,uint8)` either way and
the selector is unchanged.

What *does* change is the checking. Converting a value that is too big or negative into an enum
type raises panic `0x21`; a user-defined value type over `uint8` has no such
check.<Cite src="solidity-docs-control-structures" /> The wire is identical and the guarantee is
not — a good illustration of how much the projection throws away.
</Answer>
</Check>

  why="The name is the only part of the signature that appears verbatim in the source, so it feels like the identifying part. Every other component is a projection you never see written down, which makes changes to it invisible in review."

## Where this pays off

Three things follow immediately, and the rest of this module unpacks them.

The selector is derived from a string that you can also *choose*. A name is free, the space is
small, and nothing about the derivation is a security boundary — that is the next lesson.

The four bytes have to be turned back into a jump somewhere, and that somewhere is ordinary compiled
code with a shape and a cost, not a runtime lookup table.

And when a call arrives whose four bytes match nothing, something still happens. Both of those are
two lessons away.

The habit to take now is smaller than any of them: `abi.encodeCall` is the only one of the four
encoders whose arguments are checked against a real function signature at compile
time.<Cite src="solidity-abi-encoding-functions" /> Every low-level call you write with
`encodeWithSignature` is a string literal you are asking a reviewer to hash in their head.
