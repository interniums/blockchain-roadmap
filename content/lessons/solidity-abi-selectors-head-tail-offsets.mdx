Three ways to declare the same batch-execution entry point. All three take two addresses and two
byte strings. All three encode the same call.

```solidity
function execute(Call[] calldata calls) external;      // struct Call { address target; bytes data; }
function execute(address[] calldata t, bytes[] calldata d) external;
function execute(address[2] calldata t, bytes[2] calldata d) external;
```

Encoded with the same values — two targets, a four-byte payload and a three-byte payload — they
measure 388, 388 and 292 bytes.<Cite src="foundry-cast-abi-encoding" /> The first two are identical
in size and not remotely identical in structure. The third is 96 bytes smaller for a reason you can
state in one sentence once you know where a length word is required and where it is not.

You decoded a flat argument block by hand in Track 01, and this lesson does not repeat that. It is
about what happens when arguments nest: the recursion that generates the layout, the notion of an
*enclosing block* that offsets are measured against, and the handful of places where a declaration
that looks like a formatting choice changes both the byte count and the number of reads a decoder
must perform.

## The recursion, and the sentence that makes decoding possible

The specification defines the encoding as one mutually recursive pair of functions over an argument
tuple. For a tuple `(T1,...,Tk)`:

```text
enc(X) = head(X(1)) ... head(X(k))  tail(X(1)) ... tail(X(k))

  Ti static:   head(X(i)) = enc(X(i))          tail(X(i)) = ""
  Ti dynamic:  head(X(i)) = the byte offset of tail(X(i))
               tail(X(i)) = enc(X(i))
```

<Cite src="solidity-abi-spec" />

Then it adds the line the whole scheme rests on: in the dynamic case, `head(X(i))` is well defined
**since the lengths of the head parts only depend on the types and not the
values**.<Cite src="solidity-abi-spec" />

That is not a remark. It is the reason a decoder can exist. If head widths depended on values, you
would need to read a value to know where the next value starts, and there would be no fixed point to
start from. Because they depend only on types, a decoder that knows the signature knows the head
size before it has looked at a single byte — and therefore knows the boundary between head and tail,
and therefore knows what an offset is relative to.

The specification lists two design criteria the layout was built to satisfy, and both are worth
holding because they explain choices that otherwise look arbitrary:

- The number of reads necessary to access a value is at most the **depth** of the value inside the
  argument structure — four reads to reach `a_i[k][l][r]`. A previous version of the ABI scaled
  linearly with the total number of dynamic parameters in the worst case.<Cite src="solidity-abi-spec" />
- The data of a variable or an array element is not interleaved with other data and **it is
  relocatable, i.e. it only uses relative addresses**.<Cite src="solidity-abi-spec" />

Relocatability is the property that makes one encoder serve a call, a return value, an event's
non-indexed data and a nested tuple without changing rules. It is also what makes the offsets
confusing, and the two are the same fact.

## Which types are dynamic: a recursive predicate, not a list

The definition has five clauses, and the last two are the ones that catch people.

A type is dynamic if it is `bytes`, `string`, `T[]` for any `T`, `T[k]` for any **dynamic** `T` and
any `k >= 0`, or `(T1,...,Tk)` if `Ti` is dynamic for some `i`. All other types are
static.<Cite src="solidity-abi-spec" />

Run it as a predicate rather than memorising cases. `uint256[2][3]`: is the element type
`uint256[2]` dynamic? Its element type `uint256` is static and it is a fixed-size array, so no.
Therefore `uint256[2][3]` is static — six inline words, no offset, no length. Change the inner
dimension to `uint256[]` and every level above it becomes dynamic at once.

Structs are where this bites in ordinary code, because a struct is a tuple and clause five is
contagious upward. Here are both cases encoded, with the argument block shown from byte zero:

```text
k((uint256,uint256))     struct { uint256 a; uint256 b; }        selector 0xda29a80a
[   0]  ...0001                    a, inline
[  32]  ...0002                    b, inline
                                   64 bytes, no offset anywhere

k2((uint256,string))     struct { uint256 a; string b; }         selector 0x317125c6
[   0]  ...0020    offset -> 32    the whole struct moved to the tail
[  32]  ...0001                    a
[  64]  ...0040    offset -> 96    b, relative to byte 32
[  96]  ...0002                    length of b
[ 128]  6162...                    "ab", right-padded
```

One member changed type. The struct went from being inlined in the head to being a pointer, which
means the *argument* changed category, which means every subsequent argument's head position moved.

that touches it — and, because the struct's canonical spelling also changed, changes the selector
too.

## The `T[k]` asymmetry, in bytes

Put a static fixed array and a dynamic fixed array side by side. Both are written `T[2]`; both hold
exactly two elements.

```text
h(uint256[2],string[2])  with ([7, 8], ["ab", "cde"])      selector 0x1c19bb46

[   0]  ...0007      head: uint256[2] element 0, INLINE
[  32]  ...0008      head: uint256[2] element 1, INLINE
[  64]  ...0060      head: offset for string[2] -> byte 96
                     ^ head ends here: 96 bytes, 3 words, 2 arguments
[  96]  ...0040      string[2] block: offset for element 0 -> 96 + 64 = 160
[ 128]  ...0080      string[2] block: offset for element 1 -> 96 + 128 = 224
[ 160]  ...0002      length 2
[ 192]  6162...      "ab"
[ 224]  ...0003      length 3
[ 256]  636465...    "cde"
```

<Cite src="foundry-cast-abi-encoding" />

**Subgoal — size the head from the signature alone.** Two arguments, but three head words: the
static `uint256[2]` contributes both of its elements, the dynamic `string[2]` contributes one
offset.<Cite src="solidity-abi-spec" /> A decoder computes 96 before reading anything, and the first
offset confirms it.

**Subgoal — notice the length word that is not there.** At byte 96 the `string[2]` block begins with
an *offset*, not a count. `T[k]` is encoded as if it were a tuple with `k` elements; only `T[]`
is prefixed with the number of elements.<Cite src="solidity-abi-spec" /> Both arrays here have
their length in the type, so neither spends a word on it.

**Subgoal — check the frame for the inner offsets.** `0x40` is 64, and the first string's length
word is at byte 160. 160 − 64 = 96, which is where the `string[2]` block starts, not where the
argument block starts. This is the whole of the next section, visible in two words.

## Offsets are relative to the enclosing block

Here is the definition, stated as narrowly as it deserves: an offset counts bytes from the beginning
of the **enclosing encoding block**. The specification puts it as the offset of the beginning of
`tail(X(i))` relative to the start of `enc(X)` — where `enc(X)` is whichever tuple or array you are
currently inside, not the call.<Cite src="solidity-abi-spec" />

For top-level arguments the enclosing block starts at the first byte after the four-byte selector,
which makes "relative to the enclosing block" and "absolute in the argument block" produce the same
number. That coincidence is why nested structures are where hand-decoding goes wrong: the rule you
learned on flat calldata is a special case, and nothing warns you when you leave it.

### Worked decode: three frames in one call

This is the shape you will actually meet — a batch router taking an array of
`struct Call { address target; bytes data; }`. Two calls: `0x1111…` with payload `0xdeadbeef`, and
`0x2222…` with payload `0xaabbcc`.

```text
selector 0xbaae8abf      execute((address,bytes)[])      388 bytes total

[   0]  ...0020    FRAME A: offset of the array -> byte 32
[  32]  ...0002    array length: 2 elements
[  64]  ...0040    FRAME B: offset of element 0 -> 64 + 64 = 128
[  96]  ...00c0    FRAME B: offset of element 1 -> 64 + 192 = 256
[ 128]  ...1111    FRAME C0: element 0 tuple, member 0 (address), inline
[ 160]  ...0040    FRAME C0: offset of member 1 (bytes) -> 128 + 64 = 192
[ 192]  ...0004    length 4
[ 224]  deadbeef.. payload, right-padded
[ 256]  ...2222    FRAME C1: element 1 tuple, member 0 (address), inline
[ 288]  ...0040    FRAME C1: offset of member 1 -> 256 + 64 = 320
[ 320]  ...0003    length 3
[ 352]  aabbcc00.. payload, right-padded
```

<Cite src="foundry-cast-abi-encoding" />

**Subgoal — identify frame A and why the first word is 0x20.** The function has one argument, so the
head is one word, so the tail begins at byte 32. Frame A is the argument block, starting at the byte
after the selector.

**Subgoal — find where frame B starts, and note that it is not where frame A started.** The array's
tail is a length word followed by the encoded elements, as if the elements were a
tuple.<Cite src="solidity-abi-spec" /> The length word is at byte 32; the element block — the tuple
— therefore starts at byte 64. Frame B is byte 64. The length word is *not* part of the tuple, and
that one-word shift is where most hand decodes lose a word.

**Subgoal — resolve element 0 using frame B.** Head word `0x40` = 64, plus frame B at 64, gives byte
128. Confirm against the data: byte 128 holds an address, which is what a `Call` starts with.

**Subgoal — resolve element 1, and derive it rather than reading it.** Element 0's total encoding is
its own head (2 words: address plus offset) plus its tail (length plus one padded word) = 4 words =
128 bytes. So element 1 must begin at 128 + 128 = 256, and its offset from frame B must be
256 − 64 = 192 = `0xc0`. The word at byte 96 says `0xc0`. Prediction confirmed, and note that this
one required reading a value — the payload length — which the first prediction did not.

**Subgoal — open frame C0 and watch the base change again.** Inside element 0, the enclosing block
is the tuple, which starts at byte 128. The `bytes` member's offset is `0x40` = 64, so its length
word is at 128 + 64 = 192. Read that offset as absolute and you land at byte 64 — the middle of
frame B's offset words — and decode garbage that will look plausible, because everything in this
region is a small integer.

**Subgoal — confirm the pattern rather than the numbers.** Element 1's offset word is also `0x40`.
Two different absolute positions, one identical relative value, because each tuple is encoded
without knowing where it will sit. That is relocatability, and it is exactly why the offsets must be
relative.<Cite src="solidity-abi-spec" />

**Subgoal — count the reads.** To reach the fourth byte of the second call's payload you followed:
argument offset, element offset, member offset, then the data. Three pointer reads for a value three
levels deep — the design criterion, holding.<Cite src="solidity-abi-spec" />

### The same discipline on an array of arrays

The specification works through a second shape, `g(uint256[][],string[])` with
`([[1, 2], [3]], ["one", "two", "three"])`, and it is worth checking your frame discipline against
its numbers because the nesting is one deeper.<Cite src="solidity-abi-spec" />

The two root offsets come out as `f = 0x40` and `g = 0x140`: the argument block has a two-word head,
so the first root array's content starts at byte 64, and the second starts 320 bytes in, after the
first array's length word, its two inner offsets and its five words of
content.<Cite src="solidity-abi-spec" />

Inside the first root array, the offsets of `[1, 2]` and `[3]` are `0x40` and `0xa0` — 64 and 160
bytes measured **from the start of that array's element block**, not from the argument
block.<Cite src="solidity-abi-spec" /> And the three string offsets inside the second root array are
`0x60`, `0xa0` and `0xe0`, measured from *its* element block.<Cite src="solidity-abi-spec" />

The specification then makes the point that justifies the whole design: the encodings of the
embedded elements of the root arrays are not dependent on each other, and are the same for a
function with the signature `g(string[],uint256[][])`.<Cite src="solidity-abi-spec" /> Swap the two
arguments and every inner offset is unchanged; only the two root offsets move. That is what
"relocatable" buys, stated as a testable prediction.

<Aside kind="note">
One elementary type in the specification is itself a piece of ABI machinery: `function` is an
address (20 bytes) followed by a function selector (4 bytes), encoded identically to
`bytes24`.<Cite src="solidity-abi-spec" /> An external function pointer travelling across a call
boundary is therefore a static 32-byte word carrying a target and four bytes of truncated hash —
the two halves of this module packed into one value.
</Aside>

## What the tails look like, precisely

Two tail shapes cover everything dynamic:

- **A dynamic array `T[]`** is its element count followed by the encoded elements, exactly as if the
  elements were a fixed-size tuple.<Cite src="solidity-abi-spec" /> If `T` is itself dynamic, that
  tuple's own heads are offsets — relative to the start of the element block, one word past the
  length.
- **`bytes` of length `k`** is `k` encoded as a `uint256`, followed by the bytes, followed by the
  minimum number of zero bytes that makes the total a multiple of 32. `string` is the same thing
  applied to the UTF-8 encoding, and the length counts **bytes, not
  characters**.<Cite src="solidity-abi-spec" />

Nothing in either shape records the type. Two `bytes` values, an address array and a list of
`uint256`s can produce identical bytes; which one you get back is decided entirely by the ABI you
decode against, because the encoding is not self describing and requires a schema in order to
decode.<Cite src="solidity-abi-spec" />

That is the sentence to keep when you read someone else's calldata in a trace. You are not observing
what the arguments were. You are observing what they were *if* the function you think you are
looking at is the function that was called.

## Layout is a price, and you set it

Calldata is charged per byte — the [cost model from Track 03](/c/calldata-cost-model) — so the
declaration choices above are not stylistic. Measured on the same two-call payload:<Cite src="foundry-cast-abi-encoding" />

| Signature | Bytes |
|---|---|
| `execute((address,bytes)[])` | 388 |
| `execute(address[],bytes[])` | 388 |
| `execute(address[2],bytes[2])` | 292 |

The first two tie, which is worth pausing on: an array of two-member structs and two parallel arrays
of the same members encode to the same size. The struct form buys you a type that cannot get out of
sync between the two lists, at no byte cost.

The third saves three words. Count them from the rules rather than the diff: `address[2]` is static,
so it replaces one head offset plus one length word plus two tail elements with two inline
words — two words saved; `bytes[2]` keeps its head offset and its inner offsets but drops its length
word — one word saved.<Cite src="solidity-abi-spec" /> Ninety-six bytes, bought by fixing the batch
size at two, which is usually not a trade you want. The point is that you can now price it before
deciding.

<Check type="predict" concept="abi-offsets-relative">
A protocol defines an order type and a batch entry point:

```solidity
struct Order { address maker; uint256 amount; bytes signature; }
function fill(Order[] calldata orders, uint256 deadline) external;
```

Answer from the rules; no hashing and no encoder required.

1. How many words are in the head of the argument block, and what is in each?
2. A colleague is hand-reading a `fill` call and has found the word holding the offset of
   `orders[1]`. They want the absolute position of `orders[1]`. What do they add it to, and what is
   the most likely mistake?
3. They then find `orders[0].signature`'s offset word and read `0x60`. Where is the signature's
   length word?
4. The team is considering changing `signature` from `bytes` to `bytes32` for compactness. What
   happens to the layout of `Order[]`?

<Answer>
**1. Two words.** `Order[]` is a dynamic array, so its head is one offset word. `uint256` is static,
so its head is its value. Two arguments, two head words, 64 bytes of head — and note the ordering
consequence: `deadline` sits at byte 32 of the argument block, ahead of every byte of order
data.<Cite src="solidity-abi-spec" />

**2. Add it to the start of the element block, which is one word past the array's length word.** If
the array's offset word is `0x40`, the length word is at byte 64 and the element block — the
enclosing frame for the per-element offsets — starts at byte 96. The likely mistake is adding the
element offset to the position of the *length* word instead, which is off by exactly 32 bytes and
lands one word early in a region full of other offsets. Every value you read afterwards will be a
plausible small integer, which is why this error does not announce itself.<Cite src="solidity-abi-spec" />

**3. At `orders[0]`'s own start plus 96 bytes.** The enclosing block for a struct member's offset is
the struct, not the array and not the argument block. `Order`'s head is three words — address
inline, `uint256` inline, `bytes` offset — so 96 is exactly the head size, which is what you expect
for the first (and here only) dynamic member. If `orders[0]` begins at byte 128, the length word is
at 224.

**4. `Order` becomes static, and the whole shape collapses.** `bytes32` is a fixed-width type, so a
struct of `address`, `uint256`, `bytes32` has no dynamic member and is therefore static by clause
five.<Cite src="solidity-abi-spec" /> Consequences, in order:

- Each `Order` is three inline words with no internal offset — one frame disappears.
- `Order[]` is still dynamic (it is `T[]`), so it keeps its own offset and length word, but its
  element block becomes a flat run of three-word records with no per-element offsets — a second
  frame disappears.
- Reaching `orders[1].amount` is now arithmetic rather than a pointer chase.
- The canonical signature changes from `fill((address,uint256,bytes)[],uint256)` to
  `fill((address,uint256,bytes32)[],uint256)`, so the selector changes and every existing caller
  stops matching.

That last bullet is the one to raise in review. The layout change is a genuine improvement in size
and read count; it is also a hard interface break dressed as a field-type tweak.
</Answer>
</Check>

## Where this pays off

You can now read any calldata blob without a tool, by carrying one piece of state that the flat case
let you omit: which block you are currently inside. Open a frame when you enter a tuple or an array
element block, and measure every offset from that frame's first byte.

The same layout appears in three more places you will meet shortly. Return values and event data use
the identical encoding minus the four selector bytes.<Cite src="solidity-abi-spec" /> Revert data is
encoded exactly like a call to an error "function". And a proxy's job is to move one of these blobs
from one frame of execution to another without disturbing a byte of it.

Next: what happens when the bytes do not obey these rules. `abi.decode` runs this entire recursion
backwards and rejects input that violates it — and its sibling `abi.encodePacked` produces bytes
that no decoder can process at all, on purpose. Knowing exactly which checks the decoder performs is
what tells you when you are allowed to skip it.
