A clone's deployment transaction runs about ten bytes of code. Those bytes copy 45 bytes of runtime
into memory and return them. That is the entire creation
transaction.<Cite src="eip-1167" />

Compare that to what you know about [initcode versus runtime code](/c/initcode-vs-runtime-code): for
an ordinary contract, the initcode is your constructor — it runs arbitrary logic, writes storage,
patches values into the runtime bytecode, and only then returns the runtime for deposit. A clone's
initcode does none of that, because a clone's initcode is not derived from your source at all. It is
the same stub for every clone in existence.

So the implementation's constructor did run. Exactly once, at the implementation's own address, in
the implementation's own context. Your thousand clones got nothing from it.

Three consequences follow, and one of them has repeatedly cost real money.

## Consequence one: storage is empty, and `immutable` is not

**Storage.** Every slot in a fresh clone reads zero. The owner is `address(0)`, the token address is
`address(0)`, the fee is zero. Nothing you wrote in a constructor is there.

**`immutable` is the surprise.** Immutables are *not* storage, and a clone does have them — with a
twist. The Solidity documentation states the mechanism: the contract creation code generated by the
compiler modifies the contract's runtime code before returning it, replacing all references to
immutables with the values assigned to them.<Cite src="solidity-docs-contracts" /> Immutables live in
the **code**, and `DELEGATECALL` executes the *implementation's* code. So an immutable read inside a
clone returns the value the implementation's constructor computed, and it returns the same value in
every clone. The same holds for `constant`, whose value the compiler inlines and for which it
reserves no storage slot at all.<Cite src="solidity-docs-contracts" />

That gives you a clean split worth memorising:

| Kind of value | In a clone |
|---|---|
| `constant` | present, inlined in the implementation's code, identical for all clones |
| `immutable` | present, patched into the implementation's runtime, identical for all clones |
| storage | zero until an `initialize` writes it, per clone |
| per-clone immutable data | only via `cloneWithImmutableArgs`, read back with `fetchCloneArgs` |

That last row is the one people reach for when they discover the second row. `Clones` has offered
`cloneWithImmutableArgs` and `cloneDeterministicWithImmutableArgs` since Contracts 5.2.0, appending
per-instance arguments to the clone and reading them back with `fetchCloneArgs(address instance)`,
with a `CloneArgumentsTooLong` error when they do not
fit.<Cite src="oz-changelog" /><Cite src="oz-docs-proxy-api" /> The value sits in the clone's own code
rather than its storage, so reading it costs no `SLOAD` — worth measuring against the storage
alternative, whose first read in a transaction is 2,100 gas
cold.<Cite src="eip-2929" /><Cite src="measured-gas-constants" />

## Consequence two: `initialize` is a constructor you have to protect yourself

Since the constructor cannot set state, an ordinary function must — and it must be callable exactly
once.

OpenZeppelin's `Initializable` supplies the machinery.<Cite src="oz-docs-proxy-api" /> The parts you
need:

- **`initializer`** — a modifier defining a protected initializer that can be invoked at most once.
- **`reinitializer(uint64 version)`** — invoked at most once, and only if the contract has not
  already been initialized to a greater version. Versions are consumed; setting the version to
  `2**64 - 1` prevents any future reinitialization.
- **`onlyInitializing`** — for parent-contract initializers, callable only from within an
  `initializer` or `reinitializer` scope.
- **`_disableInitializers()`** — locks a contract against any future initialization. The docs note it
  cannot be part of an initializer call.
- Errors `InvalidInitialization()` and `NotInitializing()`, and an `Initialized(version)` event.

One warning in the documentation deserves quoting, because inheritance makes it easy to get wrong:
when used with inheritance, manual care must be taken not to invoke a parent initializer twice, or to
ensure all initializers are idempotent — and this is **not** verified automatically as constructors
are by Solidity.<Cite src="oz-docs-proxy-api" /> The compiler linearises base constructors for you.
It does not linearise `initialize` calls, because they are ordinary function calls.

## Consequence three: the implementation is a live contract, and it is uninitialized

This is the one that matters.

Your implementation is deployed at a real address, with real code, and its own storage — which,
because the constructor set nothing that matters or because nobody thought about it, is empty.
`initialize` is a public function on it. Anybody can call it.

OpenZeppelin's own words: avoid leaving a contract uninitialized, because an uninitialized contract
can be taken over by an attacker, and **this applies to both a proxy and its implementation contract,
which may impact the proxy**.<Cite src="oz-docs-proxy-api" /> The prescribed fix is three lines:

```solidity
/// @custom:oz-upgrades-unsafe-allow constructor
constructor() {
    _disableInitializers();
}
```

That constructor runs on the implementation, at the implementation's address, and locks it — which is
precisely the context a clone never enters, so it costs your clones nothing.<Cite src="oz-docs-proxy-api" />

### What taking over an implementation buys an attacker, in 2026

The historical answer was: everything. Own the implementation, find any path that performs an
arbitrary `DELEGATECALL` or a `selfdestruct`, destroy the implementation's code, and every proxy and
clone pointing at it becomes an address whose calls delegate into nothing. That was the Parity
wallet shape, and it bricked contracts permanently.

**That specific chain is largely closed, and you should know why rather than assume it still works.**
EIP-6780 restricts `SELFDESTRUCT` to only delete the account when it is called in the same
transaction in which the contract was created; in any other case it transfers the balance and leaves
the code in place.<Cite src="eip-6780" /> An already-deployed implementation can no longer be deleted
by a later transaction. [The neutered opcode](/c/selfdestruct-neutered) has the details.

What remains, and it is enough:

**Anything the implementation itself can do, an attacker who owns it can do.** If it can hold tokens,
approve spenders, or act as an authority anywhere in your system, ownership of it is ownership of
that — and some designs give the implementation a role in an `AccessControl` or `AccessManager`
configuration without noticing.

**An arbitrary-`DELEGATECALL` path is still fully dangerous within a transaction.** Owning the
implementation and calling such a function executes attacker code in the implementation's context,
rewriting its storage and draining whatever it holds.

**Chains vary, and confusion is itself a cost.** EIP-6780 arrived with Cancun; a chain without those
semantics still has the old behaviour, which matters when you ship the same code across many L2s. And
an implementation owned by a stranger, emitting `OwnershipTransferred` and `Initialized` events, turns
a routine morning into an incident call while you work out whether the clones are affected.

<Aside kind="stop">
`Clones` will happily produce a clone pointing at an address with no code. Every one of its functions
carries the warning: it does not check whether the implementation has code, such a clone cannot be
initialized, and **initialization calls may appear to be successful when in reality they have no
effect** — leaving the clone uninitialized and allowing a third party to initialize it
later.<Cite src="oz-docs-proxy-api" /> That is [delegatecall to empty code succeeding](/c/delegatecall-no-code-succeeds)
turned into a production incident. Validate the implementation address once, in the factory's
constructor, and store it as an immutable.
</Aside>

## Deploy and initialize in the same transaction

The other half of the same problem. If your factory deploys a clone in one transaction and
initializes it in another, anyone can initialize it in between and become its owner. The window is
one block and it is watched.

The correct shape is atomic, and the EIP anticipated it: one of ERC-1167's stated design goals is to
support clone initialization in the creation transaction, through a factory contract
model.<Cite src="eip-1167" />

```solidity
function createVault(address owner) external returns (address vault) {
    vault = Clones.cloneDeterministic(IMPLEMENTATION, bytes32(uint256(uint160(owner))));
    IVault(vault).initialize(owner);          // same transaction, non-negotiable
    emit VaultCreated(owner, vault);
}
```

Two notes on that. `cloneDeterministic` reverts if the same implementation and salt are used twice,
since two contracts cannot occupy one address<Cite src="oz-docs-proxy-api" /> — so salting by the
owner's address gives you a one-vault-per-user constraint for free. And
`predictDeterministicAddress(implementation, salt, deployer)` lets you tell the user the address
before the transaction lands.<Cite src="oz-docs-proxy-api" />

<Aside kind="warn">
OpenZeppelin closed the equivalent hole for proxies, but **not** for clones. Since Contracts 5.6.0,
released 25 February 2026, `ERC1967Proxy` and `TransparentUpgradeableProxy` mandate initialization
during construction: deployment reverts with `ERC1967ProxyUninitialized` if no initialize call is
provided, and the only way back is to override the internal `_unsafeAllowUninitialized` to return
true.<Cite src="oz-changelog" /><Cite src="oz-docs-proxy-api" /> `Clones` has no such check and cannot
have one — the clone's bytecode is fixed by the standard and contains no constructor logic to run.
For clones, atomic initialization is entirely your factory's responsibility.
</Aside>

## A clone is not upgradeable, and this is deliberate

The implementation address is 20 bytes at indices 10 through 29 of the clone's runtime
code.<Cite src="eip-1167" /> Deployed code is immutable. There is no setter, because there is nowhere
to set.

The standard says this is intentional, in its own rationale: the design goal is dependable,
locked-down behaviour, and **this is not designed to handle upgradability, nor should it, as the
representation we are seeking is stronger**.<Cite src="eip-1167" /> A clone is not a
weaker proxy that forgot to include an upgrade function. It is a different product whose selling
point is that it cannot change.

<Misconception
  belief="An EIP-1167 clone is an upgradeable proxy."
  reality="The implementation address is immutable bytecode inside the clone, not a storage slot. It is a cheap-deployment pattern, and the standard explicitly says it is not designed to handle upgradability."
  why="Both patterns forward with delegatecall, so the two get collapsed into one idea. The difference is entirely where the target address lives."
  src="eip-1167"
/>

Three patterns, one distinction, and it is always the same question — where does the implementation
address live?

| Pattern | Where the address lives | Upgrade granularity | Per-call cost |
|---|---|---|---|
| EIP-1167 clone | the clone's own code | none | forwarder dispatch + one `DELEGATECALL` |
| ERC-1967 proxy | a storage slot in the proxy | per instance | the above, plus an `SLOAD` to find the target |
| Beacon proxy | a storage slot in a shared beacon | all instances at once | the above, plus a call to the beacon |

The ERC-1967 slot is the standardised pseudo-random one clients can read with `eth_getStorageAt`
and no ABI — OpenZeppelin's docs print it as
`0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc`.<Cite src="eip-1967" /><Cite src="oz-docs-proxy-api" />
Both proxy rows pay at least one extra storage read per call over the clone, and the beacon row adds
an account access to a second contract — 2,600 gas cold, 100
warm.<Cite src="eip-2929" /><Cite src="measured-gas-constants" />

The choice is not about cost, though. It is about who may change your code:

- **Clone** — nobody, ever. No admin key exists.
- **ERC-1967** — the proxy's admin, per instance, arbitrarily.
- **Beacon** — the beacon's owner, for every instance simultaneously, arbitrarily.

Rows two and three add the most dangerous entry to the authorization table you built two lessons ago.
The 2025 incident review reaches the same conclusion from the data: proxy and upgradeability patterns
allow bug fixes but introduce severe risks if admin keys are compromised or the governance mechanisms
controlling upgrades are subverted.<Cite src="sok-root-cause-losses" /> Choosing a clone is choosing
to have no such row.

<Check type="spot-bug" concept="clone-no-constructor">
A protocol ships this factory and implementation. Both compile; the test suite is green.

```solidity
contract Vault is Ownable, Initializable {
    IERC20 public asset;

    function initialize(address owner_, address asset_) external initializer {
        _transferOwnership(owner_);
        asset = IERC20(asset_);
    }

    function sweep() external onlyOwner { /* moves everything out */ }
}

contract VaultFactory {
    address public immutable implementation;
    constructor(address impl) { implementation = impl; }

    function createVault(address asset_) external returns (address v) {
        v = Clones.clone(implementation);
        emit Created(msg.sender, v);
    }
}

// deploy script:
//   vault = factory.createVault(USDC);
//   Vault(vault).initialize(msg.sender, USDC);
```

Find the problems and rank them.

<Answer>
**One — the deploy script initializes in a second transaction, so any clone can be stolen in the gap.**
`createVault` returns an uninitialized clone with `owner == address(0)`. Between that transaction and
the follow-up, anyone can call `initialize(attacker, USDC)` on the new address, become owner, and
call `sweep()` the moment the user funds it. This is not theoretical: the address is in the event
logs, and one block is plenty. **Fix:** call `initialize` inside `createVault`, in the same
transaction — which the ERC-1167 rationale names as one of its design
goals.<Cite src="eip-1167" />

**Two — the `Vault` implementation has no constructor calling `_disableInitializers()`, so the
implementation itself is claimable.** Anyone can call `initialize` on the implementation address and
become its owner. OpenZeppelin's documentation states directly that an uninitialized contract can be
taken over by an attacker and that this applies to the implementation contract as well as the
proxy.<Cite src="oz-docs-proxy-api" /> What it costs you here is bounded — `Vault` holds nothing and
has no arbitrary-delegatecall path, and `SELFDESTRUCT` can no longer delete a previously deployed
contract after EIP-6780<Cite src="eip-6780" /> — but "bounded today" is not a design. Add the
constructor.

**Three — `Vault` inherits `Ownable`, whose constructor is skipped in a clone and *not* skipped in the
implementation.** OpenZeppelin 5.x `Ownable` requires an `initialOwner` constructor
argument.<Cite src="oz-docs-access-api" /> `Vault` as written provides none, so this does not compile
against 5.x at all — and the version that does compile, by passing something like `msg.sender`, sets
an owner on the *implementation* while every clone starts at `address(0)`. The correct pattern for
clonable contracts is `OwnableUpgradeable` initialized inside `initialize`, never the constructor
form.

**Four — `createVault` ignores its own `asset_` argument.** A dead parameter the caller reasonably
assumes did something; the real configuration happens in the separate `initialize`, which is problem
one wearing a different hat.

**Five, structural — the test suite is green because it only tests the happy path.** Three tests
would have caught everything above: `initialize` reverts on a second call with
`InvalidInitialization`;<Cite src="oz-docs-proxy-api" /> `initialize` on the *implementation address*
reverts; and a clone returned by `createVault` already has the correct owner. That third one is the
whole finding, stated as an assertion.

**The corrected factory:**

```solidity
function createVault(address asset_) external returns (address v) {
    v = Clones.cloneDeterministic(
        implementation,
        keccak256(abi.encode(msg.sender, asset_))
    );
    IVault(v).initialize(msg.sender, asset_);
    emit Created(msg.sender, v);
}
```

plus `constructor() { _disableInitializers(); }` on `Vault`, and a check in the factory's constructor
that `impl.code.length > 0` — because `Clones` does not check, and a clone of an empty address accepts
initialization calls that silently do nothing.<Cite src="oz-docs-proxy-api" />
</Answer>
</Check>

## Where this pays off

**Proxies and upgrades**, next in this track, takes that table's third column seriously: what an
upgrade actually is, why version two's storage layout must be compatible with version one's, and the
2026 case where a live contract was permanently deadlocked by an upgrade between two OpenZeppelin
majors. You now know exactly which address is mutable and which is not.

**Token standards and vault factories** across this track and the DeFi track are almost all this
pattern: one implementation, thousands of clones, an `initialize` per instance. Recognising the shape
tells you where to look before you read any logic.

**Track 06's exploit archaeology** covers the uninitialized-implementation family in its historical
form. Read it knowing that EIP-6780 changed the ending, not the beginning: the takeover still works,
the destruction mostly does not.

**Reading a deployed system.** Given an address, three questions settle its nature in two minutes.
Is the code 45 bytes starting `363d3d37`? Then it is a clone and cannot change. Does
`eth_getStorageAt` on the ERC-1967 implementation slot return non-zero? Then it is an upgradeable
proxy and somebody can change it.<Cite src="eip-1967" /> Neither? It is just a contract. The answer
determines which questions are worth asking next.
