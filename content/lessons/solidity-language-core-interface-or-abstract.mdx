You have an `interface IVault`. You want to add two things to it: a `uint256 public totalAssets` so
callers can read the pool, and a `constructor` so implementers cannot forget to set the asset
address. Both are rejected.

The instinct is to file this as arbitrary strictness — an interface is an abstract contract with the
bodies removed, and Solidity is being fussy about which removals it accepts. It is not. One rule sits
underneath every restriction, and once you have it, the choice between the two constructs stops being
a matter of taste.

## The rule under all five restrictions

Interfaces "cannot have any functions implemented", and then five further restrictions
apply:<Cite src="solidity-docs-contracts" />

- They cannot inherit from other contracts, but they can inherit from other interfaces.
- All declared functions must be `external` in the interface, even if they are `public` in the
  contract.
- They cannot declare a constructor.
- They cannot declare state variables.
- They cannot declare modifiers.

Read the list once and it looks like five unrelated prohibitions. Then read the sentence that
follows it:

> Interfaces are basically limited to what the Contract ABI can represent, and the conversion between
> the ABI and an interface should be possible without any information
> loss.<Cite src="solidity-docs-contracts" />

Now the list collapses into one idea. An interface is **a Solidity spelling of an ABI**, and the
round trip has to be lossless in both directions. So the question for any feature is: does it appear in
an ABI JSON?

**State variables** do not. A `public` state variable produces a getter that appears in the ABI, and
the variable itself — its slot, its packing, its type — does not. Allowing a state variable in an
interface would mean an interface carries information the ABI cannot round-trip, and would also
commit implementers to a storage layout, which is exactly what an interface must not do.

**Constructors** do not. Deployment is not part of a contract's callable surface; nothing on the wire
ever invokes a constructor.

**Modifiers** do not. A modifier is a source-level splice with no wire representation at all, as the
previous lesson made concrete — the deployed function contains the modifier's code inline and the
ABI shows one function.

**Visibility collapses to `external`** because that is the only visibility that exists on the
wire.<Cite src="solidity-abi-spec" /> `internal` and `private` functions are not in the ABI; `public`
and `external` are indistinguishable from outside. The interface picks the one that means "reached by
message call", which is the only kind of reaching an ABI describes.

**Inheriting a contract** would import implementation, state and construction behaviour — everything
the first four bullets just excluded.

## What an interface can still carry

More than the restrictions suggest, and the exceptions are exactly the ABI-expressible ones.

**Types.** Interfaces may declare enums and structs, and "types defined inside interfaces and other
contract-like structures can be accessed from other contracts", as `Token.TokenType` or
`Token.Coin`.<Cite src="solidity-docs-contracts" /> Both are ABI types — an enum encodes as `uint8`
and a struct as a tuple.<Cite src="solidity-abi-spec" /> Enums have been allowed in interfaces since
0.5.0, so the pragma has to permit that version at minimum.<Cite src="solidity-docs-contracts" />

**Inheritance from other interfaces**, with the same rules as normal inheritance — including the
override rules from the previous lesson. The docs' own example has `SubInterface is ParentA, ParentB`
where both parents declare `test()`, and the sub-interface "must redefine `test` in order to assert
that the parent meanings are compatible", spelled `override(ParentA, ParentB)`.<Cite src="solidity-docs-contracts" />

**Implicit virtuality.** "All functions declared in interfaces are implicitly `virtual` and any
functions that override them do not need the `override` keyword."<Cite src="solidity-docs-contracts" />
One caveat: the overriding function can itself be overridden again only "if the overriding function
is marked `virtual`."<Cite src="solidity-docs-contracts" /> Since 0.8.8, `override` is not required
for an interface function at all, except when it is defined in multiple
bases.<Cite src="solidity-docs-contracts" />

**A computed identity.** Because an interface is a closed set of external functions, the compiler can
hand you `type(I).interfaceId` — "a `bytes4` value containing the EIP-165 interface identifier of the
given interface `I`", defined as the XOR of all function selectors "defined within the interface
itself - excluding all inherited functions."<Cite src="solidity-docs-global-vars" /><Cite src="eip-165" />
Note the exclusion: inherited selectors are not in the XOR, so composing interfaces does not compose
their ids.

## What an abstract contract is for

The trigger for `abstract` is mechanical: "Contracts must be marked as `abstract` when at least one of
their functions is not implemented or when they do not provide arguments for all of their base
contract constructors."<Cite src="solidity-docs-contracts" />

Two details around that are the ones people miss.

**You may mark a contract abstract even when it is complete** — "such as when you do not intend for
the contract to be created directly."<Cite src="solidity-docs-contracts" /> And such contracts "can
not be instantiated directly. This is also true, if an abstract contract itself does implement all
defined functions."<Cite src="solidity-docs-contracts" /> `abstract` is therefore also a deployment
guard, not only a completeness signal. Almost every base contract in OpenZeppelin is abstract for
this reason.

**Abstractness travels.** "If a contract inherits from an abstract contract and does not implement
all non-implemented functions by overriding, it needs to be marked as abstract as
well."<Cite src="solidity-docs-contracts" /> And it only travels in one direction: "abstract
contracts cannot override an implemented virtual function with an unimplemented
one."<Cite src="solidity-docs-contracts" /> You can leave a hole for a subclass to fill; you cannot
punch a hole back into something already filled.

## Choosing, in one question

Everything above reduces to a test you can apply in a second.

**Does the thing need to remember something, run at construction, or share behaviour?** If yes, it is
an abstract contract. State, constructors and modifiers are precisely the three features that answer
"yes", and precisely the three an interface forbids.

**Are you describing something you will call rather than something you will be?** Then it is an
interface. You need the selectors and the encoding, nothing else — and a contract you do not control
cannot inherit your abstract base anyway. This is the ERC-20 case: `IERC20` exists so your contract
can encode a call to a token whose source you have never compiled.

The two compose, and OpenZeppelin's layout is the canonical shape: an `IERC20` anyone can compile
against, and an abstract `ERC20` that implements it and that you inherit. The interface is the
promise to the outside; the abstract contract is the shared implementation on the inside.

<Check type="explain" concept="sol-interface-vs-abstract">
A team is designing a plug-in system. Each plug-in must: expose `execute(bytes calldata)` to the
router; keep its own `owner`; refuse calls from anyone but the router; and be constructed with the
router's address.

They propose putting all four requirements in `interface IPlugin`. Say which requirements can live
there, which cannot and why, and what the right split is.

<Answer>
**`execute(bytes calldata)` belongs in the interface, and is the only one of the four that does.** It
is a function the router will call by message call, so it has an ABI representation, and `external`
is the correct visibility.<Cite src="solidity-docs-contracts" />

**`owner` cannot.** Interfaces cannot declare state variables.<Cite src="solidity-docs-contracts" />
What *can* go there is `function owner() external view returns (address);` — a getter declaration,
which is ABI-expressible. That changes the commitment: the interface requires plug-ins to *expose* an
owner and says nothing about how they store one, which is why the restriction is a feature.

**"Refuse calls from anyone but the router" cannot.** That is a modifier or an inline check, and
interfaces cannot declare modifiers.<Cite src="solidity-docs-contracts" /> More fundamentally, it is
behaviour, and an interface has no way to express behaviour — nothing in an ABI says what a function
must reject.

**"Constructed with the router's address" cannot.** Interfaces cannot declare a
constructor.<Cite src="solidity-docs-contracts" /> Deployment is not on the wire.

**The split.** `interface IPlugin` declares `execute` and `owner`. `abstract contract BasePlugin is
IPlugin` holds `address public immutable router`, an `owner` state variable overriding the
interface's external getter, an `onlyRouter` modifier, and a constructor taking the router address —
and leaves `execute` unimplemented, which is what makes it
abstract.<Cite src="solidity-docs-contracts" /> A concrete plug-in inherits `BasePlugin` and
implements `execute`.

**The consequence worth naming:** the router should type its calls as `IPlugin`, not `BasePlugin`.
Requiring `BasePlugin` would restrict it to plug-ins compiled from the team's own source tree, and
allowing third-party implementations is the whole reason to have two constructs. To *verify* rather
than trust, `type(IPlugin).interfaceId` plus an ERC-165 `supportsInterface` check is the mechanism —
and it checks the declared shape, not the
behaviour.<Cite src="solidity-docs-global-vars" /><Cite src="eip-165" />
</Answer>
</Check>

## Where this pays off

**Every token standard you will integrate** ships as an interface, for the reason this lesson gives:
you must be able to call a contract you did not compile. The abstract implementations are a
convenience; the interface is the contract.

**ERC-165 detection** rests on `type(I).interfaceId` and on the exclusion of inherited selectors from
the XOR — a detail that quietly decides whether your `supportsInterface` answers agree with a
counterparty's.<Cite src="eip-165" />

**Upgradeable contracts** lean on abstract bases hard, because the plug-in exercise's constructor
problem has a sharper version behind a proxy: a constructor runs at the implementation's deployment,
not the proxy's, so the shared-initialisation job has to move somewhere else entirely.

**And the module closes here.** Types decide whether a name aliases or copies; visibility decides
which code may reach a name; mutability decides what a call may do once it arrives; modifiers splice
code around a body; linearisation decides which body wins. All five are compile-time decisions with
no runtime representation — which is exactly why reading Solidity well means reading what the
compiler will produce, not what the source appears to say.
