Three functions, all marked `view`, reached three different ways.

Called from outside the contract, the promise is enforced by the EVM: the frame runs under a flag
that makes a state write abort. Called from inside the same contract, there is no frame and no flag —
the promise is whatever the compiler checked. Called as a public library function, the promise is
*also* only what the compiler checked, and the docs say so in a Note that most readers skim.

This lesson is what each annotation promises, who enforces it, and the one case where nobody does.

## Mutability is one slot, so the keywords exclude each other

Before the semantics, a piece of grammar that answers a recurring question. The language's function
grammar has a single **state-mutability** position, and its alternatives are `pure`, `view` and
`payable`; "the default mutability 'non-payable' is assumed if no mutability is
specified."<Cite src="solidity-docs-grammar" />

One slot, three fillers, plus a default. So there is no such thing as a `view payable` function —
not because a rule forbids the combination, but because there is nowhere to write it. Four states
exist: non-payable, `view`, `pure`, `payable`, and every function is exactly one of them. The
keywords do not compose, so `pure` is not "`view` plus something"; it is a different, stricter point
in the same slot.

## What `view` promises

"Functions can be declared `view` in which case they promise not to modify the
state."<Cite src="solidity-docs-contracts" /> The docs then enumerate what counts, and the list is
worth reading in full because two entries are broader than "writing to a variable":<Cite src="solidity-docs-contracts" />

- Writing to state variables — storage **and** transient storage.
- Emitting events.
- Creating other contracts.
- Using `selfdestruct`.
- Sending Ether via calls.
- Calling any function not marked `view` or `pure`.
- Using low-level calls.
- Using inline assembly that contains certain opcodes.

The sixth entry makes `view` contagious upward: your function is `view` only if everything it calls
is `view` or `pure`. The seventh removes the obvious escape: a raw `.call` is disqualifying on sight,
because the compiler cannot see where it lands. Together they are what makes the annotation carry
information — it is a statement about the whole reachable call graph, not about the lines in front
of you.

Note also the first entry's parenthesis. Transient storage counts as state for this
purpose.<Cite src="solidity-docs-contracts" /> A `TSTORE` inside what you thought was a read-only
helper is a mutability violation, which is convenient, because it means the compiler catches a
transient write in a `view` path rather than leaving it to a runtime failure.

One small consequence, easily missed: "Getter methods are automatically marked
`view`."<Cite src="solidity-docs-contracts" /> The functions the compiler wrote for your `public`
state variables are already carrying the annotation, which is why they can be called from other
`view` functions without complaint.

### Who enforces it

Here is the sentence that makes `view` different from an ordinary type-system promise:

> If the compiler's EVM target is Byzantium or newer (default) the opcode `STATICCALL` is used when
> view functions are called, which enforces the state to stay unmodified as part of the EVM
> execution.<Cite src="solidity-docs-contracts" />

You know [`STATICCALL`](/c/four-call-variants) from the machine side: EIP-214 added a call variant
that sets a static flag for the duration of the frame, propagates it to every subcall, and makes
state-modifying operations throw inside it.<Cite src="eip-214" /> Solidity uses it for external
`view` calls, so the compile-time promise becomes a runtime guarantee — and, importantly, one that
holds even if the callee is a contract you have never seen. A `view` call into a hostile address
cannot write your state, cannot write its own, and cannot emit a log, because the flag travels down
the whole subtree.<Cite src="eip-214" />

There is a small historical note attached that explains why the enforcement exists at all: before
0.5.0 the compiler did not use `STATICCALL` for `view` functions, "which enabled state modifications
in view functions through the use of invalid explicit type
conversions."<Cite src="solidity-docs-contracts" /> The static check alone was demonstrably
bypassable. The opcode was the fix.

<Aside kind="note">
Two things `view` does not promise, both of which surprise people. It does not promise the function
is cheap — a `view` function can read ten thousand cold slots. And it does not promise the answer is
stable: a `view` function may read `block.timestamp`, a price oracle, or state that an in-flight
transaction is about to change. `view` constrains writes, not cost and not determinism.
</Aside>

## What `pure` adds, and what nothing enforces

"Functions can be declared `pure` in which case they promise not to read from or modify the
state."<Cite src="solidity-docs-contracts" /> The docs give a sharper criterion than the keyword
does: "it should be possible to evaluate a pure function at compile-time given only its inputs and
`msg.data`, but without any knowledge of the current blockchain state."<Cite src="solidity-docs-contracts" />

On top of the modification list, these count as reading:<Cite src="solidity-docs-contracts" />

- Reading from state variables — storage and transient storage.
- Accessing `address(this).balance` or the `.balance` member of any address.
- Accessing any member of `block`, `tx` or `msg` — **with the exception of `msg.sig` and
  `msg.data`**.
- Calling any function not marked `pure`.
- Using inline assembly that contains certain opcodes.

The `msg.sig` and `msg.data` exception is not an oversight: the calldata is an *input* to the call,
so evaluating the function from its inputs plus `msg.data` is exactly what the criterion permits.
That is why a `pure` selector-inspection helper is legal, and why routers can decode their own
calldata in `pure` code.<Cite src="solidity-docs-contracts" />

The `immutable` case is the other one people get wrong. Immutables are baked into the deployed code
rather than read from storage, which makes them feel like constants — but their values are decided
at deployment, not at compilation, so the docs state the consequence directly: "reading from
immutable variables can be a non-pure operation."<Cite src="solidity-docs-contracts" />

Then the warning that reframes the whole keyword:

> It is not possible to prevent functions from reading the state at the level of the EVM, it is only
> possible to prevent them from writing to the state (i.e. only `view` can be enforced at the EVM
> level, `pure` can not).<Cite src="solidity-docs-contracts" />

`STATICCALL` is used for external `pure` calls too, but it "does not guarantee that the state is not
read, but at least that it is not modified."<Cite src="solidity-docs-contracts" /> So `pure` is a
compiler-checked property with no runtime backstop whatsoever. That does not make it worthless — it
makes it a different kind of claim, one about the source you compiled rather than about the bytecode
you are calling.

### Reverting is not a modification

One clarification closes a common design question. "Pure functions are able to use the `revert()`
and `require()` functions to revert potential state changes when an error
occurs."<Cite src="solidity-docs-contracts" /> Reverting only undoes changes made earlier by code
that was not `view` or `pure` restricted, and the docs call that "in line with the `STATICCALL`
opcode."<Cite src="solidity-docs-contracts" /> So validation helpers can be `pure` and still be the
thing that stops a transaction — you never have to relax a mutability annotation to let a function
fail.

## The library exception

Now the case from the opening. Read the second half of the same Note that introduced `STATICCALL`:

> For library view functions `DELEGATECALL` is used, because there is no combined `DELEGATECALL` and
> `STATICCALL`. This means library view functions do not have run-time checks that prevent state
> modifications. This should not impact security negatively because library code is usually known at
> compile-time and the static checker performs compile-time checks.<Cite src="solidity-docs-contracts" />

Everything about that follows from what a library is. Libraries "are deployed only once at a
specific address and their code is reused using the `DELEGATECALL` feature of the EVM", so library
code "is executed in the context of the calling contract, i.e. `this` points to the calling
contract, and especially the storage from the calling contract can be
accessed."<Cite src="solidity-docs-contracts" /> That is the whole point of a library: it is code
that operates on your state.

And [`DELEGATECALL`](/c/delegatecall-is-the-proxy-primitive) carries no static flag — EIP-7 defines
it as propagating the caller's environment, not as restricting
it.<Cite src="eip-7" /><Cite src="eip-214" /> The EVM offers no opcode that means "borrow this code,
run it against my storage, and forbid writes." So the compiler cannot have both properties at once,
and it keeps the one that makes libraries useful.

**The residue is a real, if narrow, gap.** For an ordinary contract, `view` is a promise plus an
enforcement. For a public or external library function, `view` is a promise and nothing else. The
docs' own justification names its own precondition — "library code is usually known at
compile-time" — and *usually* is doing the work. A library address supplied at link time by a build
you did not audit, or a linked address that differs between your test run and your deployment, is
outside the case the reassurance covers.

  reality="For ordinary contracts, yes: external view calls run under STATICCALL. For public or external library functions, no: they are reached by DELEGATECALL, which carries no static flag, so the only check is the compiler's."
  why="The enforcement story for normal contracts is airtight and gets taught as unconditional. The exception appears once, in a Note, in a paragraph whose second half most readers stop reading after the word STATICCALL — and it is stated as a reassurance rather than as a caveat."
  src="solidity-docs-contracts"
/>

<Aside kind="note">
The distinction is between library functions, not between libraries. An `internal` library function
is inlined into the calling contract's bytecode and reached by a plain `JUMP`; only `public` and
`external` library functions are deployed separately and reached by
`DELEGATECALL`.<Cite src="solidity-docs-contracts" /> An internal library `view` function is
therefore enforced exactly as ordinary contract code is — because it *is* ordinary contract code by
the time it runs.
</Aside>

Two more library facts worth banking. Library functions "can only be called directly (i.e. without
the use of `DELEGATECALL`) if they do not modify the state (i.e. if they are `view` or `pure`
functions), because libraries are assumed to be stateless." And the inheritance analogy breaks here:
`L.f()` on a public library function is an external call, while `A.f()` on a base contract is an
internal one.<Cite src="solidity-docs-contracts" />

## `payable`, the third filler

A function must be marked `payable` to accept Ether. The negative case is listed among the
situations that generate an `Error(string)` exception: "if your contract receives Ether via a public
function without `payable` modifier (including the constructor and the fallback
function)."<Cite src="solidity-docs-control-structures" /> The same list includes receiving Ether via
a public getter — which follows from getters being automatically
`view`.<Cite src="solidity-docs-control-structures" /><Cite src="solidity-docs-contracts" />

Because mutability is one grammar slot, `payable` and `view` cannot coexist, and the same is true of
`payable` and `pure`.<Cite src="solidity-docs-grammar" /> The semantic reason lines up with the
grammatical one: accepting value changes the contract's balance, and a balance is state.

The special functions inherit this. A `receive` function "must have external visibility and
`payable` state mutability", and a fallback "must be marked `payable`" if it is to receive Ether
without a function call.<Cite src="solidity-docs-contracts" />

### Mutability under inheritance is a one-way lattice

When a derived contract overrides a base function, "the mutability may be changed to a more strict
one following the order: non-payable can be overridden by `view` and `pure`; `view` can be
overridden by `pure`. `payable` is an exception and cannot be changed to any other
mutability."<Cite src="solidity-docs-contracts" />

So overrides may tighten and never loosen, with `payable` frozen in place. That asymmetry is a
safety property: a caller who compiled against the base contract's `view` declaration cannot be
surprised by a derived implementation that writes.

```solidity
library Math {
    function scale(uint256 x, uint256 bps) public view returns (uint256) {
        assembly { sstore(0, x) }
        return x * bps / 10_000;
    }
}

contract A {
    uint256 private total;
    function report() external view returns (uint256, bytes4) {
        return (total, msg.sig);
    }
    function audit() external pure returns (bytes4) {
        return msg.sig;
    }
    function fee() external view payable returns (uint256) { return 1; }
}
```

<Answer>
**`Math.scale` does not compile — but for the reason you can see, not the one that matters.** Inline
assembly containing certain opcodes counts as modifying state, and `sstore` is squarely in that
set, so the static checker rejects a `view` function containing
it.<Cite src="solidity-docs-contracts" /> The point of the example is what *would* have happened if
the check had been evaded — through an unusual construct, an older compiler, or a linked library
compiled from source you did not review. A public library function is reached by `DELEGATECALL`,
which carries no static flag, so nothing at runtime would have stopped the
write.<Cite src="solidity-docs-contracts" /><Cite src="eip-7" /> It would have landed in the
*calling contract's* slot 0.

**`A.report` compiles, and the EVM enforces it.** Reading a state variable is permitted in `view`,
and `msg.sig` is permitted everywhere.<Cite src="solidity-docs-contracts" /> Called externally, it
runs under `STATICCALL`, so a write anywhere in its subtree aborts the
frame.<Cite src="solidity-docs-contracts" /><Cite src="eip-214" />

**`A.audit` compiles, and nothing enforces it at runtime.** `msg.sig` is the documented exception to
the "no reading `msg` members" rule, so `pure` is legal.<Cite src="solidity-docs-contracts" /> But
`pure` cannot be enforced at the EVM level at all — only writes can be
prevented.<Cite src="solidity-docs-contracts" /> `STATICCALL` is still used, so it is enforced *as
if it were view*; the extra promise `pure` makes is entirely the compiler's.

**`A.fee` does not compile.** `view` and `payable` are two fillers for one grammar position, so the
declaration is not expressible.<Cite src="solidity-docs-grammar" />

The pattern across the four: the strength of a mutability annotation depends on *how the function is
reached*, and the source text does not tell you. Same keyword, three enforcement stories — EVM-level
for an external contract `view`, compiler-only for `pure`, compiler-only for a public library `view`.
</Answer>
</Check>

## Where this pays off

**Modifiers** are next, and they interact with mutability in a way that catches people: a modifier
that writes state makes every function it decorates non-`view`, no matter how read-only the function
body looks.

**Read-only reentrancy** is the attack class that lives in the gap this lesson opened. `STATICCALL`
stops a callee writing; it does not stop a callee calling back into *your* `view` functions while
your own state is halfway through an update. Everything a `view` function reports during that window
is real and wrong.

**Library design** gets a rule from the last section: put logic that must not write state in
`internal` library functions, where the enforcement is real, and reserve `public` library functions
for code whose write access to your storage is deliberate.
