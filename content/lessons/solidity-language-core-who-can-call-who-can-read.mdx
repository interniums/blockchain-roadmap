A protocol deploys with a fee recipient it does not want announced yet.

```solidity
address private pendingRecipient;
```

Nobody calls the contract. No event is emitted. No getter exists — the variable is `private`, and
the compiler generated nothing for it. An hour after deployment, someone posts the address in a
forum thread.

They did not break anything. They ran one JSON-RPC call against a public node, and it returned the
slot.<Cite src="execution-apis-eth-state" />

Solidity's visibility keywords are borrowed from languages where `private` is an encapsulation
boundary that also happens to be a confidentiality boundary, because in those languages the memory
is yours. On a public chain the memory is not yours. This lesson is what the four keywords do
control, precisely, and what they were never able to control.

## Two kinds of call, therefore four visibilities

Start with the distinction the visibility system is built on, because the four keywords are
derived from it rather than the other way round.

> Solidity knows two kinds of function calls: external ones that do create an actual EVM message
> call and internal ones that do not. Furthermore, internal functions can be made inaccessible to
> derived contracts. This gives rise to four types of visibility for
> functions.<Cite src="solidity-docs-contracts" />

Two axes — message call or jump, visible to derived contracts or not — give four combinations, and
the four keywords are those combinations:<Cite src="solidity-docs-contracts" />

- **`external`** functions are part of the contract interface and can be called from other contracts
  and via transactions. "An external function `f` cannot be called internally (i.e. `f()` does not
  work, but `this.f()` works)."
- **`public`** functions are part of the interface and can be called either internally or via
  message calls.
- **`internal`** functions can be accessed only from the current contract or contracts deriving from
  it, and cannot be accessed externally. Because they are not exposed through the ABI, "they can
  take parameters of internal types like mappings or storage references."
- **`private`** functions are like internal ones but are not visible in derived contracts.

The bracketed note under `external` is the one that produces bugs. `this.f()` is not a syntactic
convenience for calling your own function. It is one of the [four call
variants](/c/four-call-variants) — a genuine `CALL` into your own address, opening a new
[call frame](/c/call-frame). Three things change that you did not ask to change:

**`msg.sender` becomes the contract's own address.** Any authorisation check downstream that reads
`msg.sender` now evaluates the contract against itself rather than against whoever started the
transaction. An `onlyOwner` function reached through `this.f()` therefore fails unless the contract
owns itself — and a contract that *does* own itself has granted owner authority to every code path
that can reach `this.f()`, which is a much larger set than the one it meant to grant.

**It costs an account access.** Reaching your own address through a message call is priced like
reaching any other, and account access under EIP-2929 is 2,600 gas cold and 100 warm — measured on
this toolchain at 2,617 and 117 respectively before subtracting harness
overhead.<Cite src="eip-2929" /><Cite src="measured-gas-constants" /> The internal call it replaced
was a `JUMP`.

**Arguments cross the ABI boundary.** An internal call can pass a storage reference; an external
call cannot, because there is no ABI encoding for "a pointer into my
storage."<Cite src="solidity-abi-spec" /><Cite src="solidity-docs-contracts" /> This is why the
mapping-and-storage-reference sentence sits under `internal` and not under `public` — the constraint
is the ABI's, and visibility only decides whether the ABI is involved.

<Aside kind="note">
The practical reading of `internal` is not "less accessible than public". It is "not on the wire."
An internal function has no selector, appears in no ABI JSON, and can therefore have a signature
that the ABI cannot express. That is a capability, not a restriction, and it is the reason the
storage-reference helpers from the previous lesson have to be internal.
</Aside>

## State variables get three, not four

The keyword set is smaller for state variables, and one member of it does something the other three
do not.<Cite src="solidity-docs-contracts" />

**`public`** — "Public state variables differ from internal ones only in that the compiler
automatically generates getter functions for them, which allows other contracts to read their
values." And, immediately: "Setter functions are not generated so other contracts cannot directly
modify their values."<Cite src="solidity-docs-contracts" />

**`internal`** — accessible from the declaring contract and derived contracts, not externally. "This
is the default visibility level for state variables."<Cite src="solidity-docs-contracts" />

**`private`** — like internal, but "not visible in derived contracts."<Cite src="solidity-docs-contracts" />

`external` is not in the list at all. There is no external state variable, and the reason is
structural: `external` means "reached by message call", and a variable is not something a message
call can reach. Only the generated function is.

### Worked example: deriving a generated getter by hand

`public` on a state variable is a code generator, and what it generates for a compound type is not
obvious. Take the documentation's own example, which is deliberately as awkward as a real storage
declaration gets.<Cite src="solidity-docs-contracts" />

```solidity
contract Complex {
    struct Data {
        uint a;
        bytes3 b;
        mapping(uint => uint) map;
        uint[3] c;
        uint[] d;
        bytes e;
    }
    mapping(uint => mapping(bool => Data[])) public data;
}
```

**Subgoal 1 — turn every lookup step into a parameter.** Reading a value out of `data` requires a
`uint` key, then a `bool` key, then an array index. Each of those becomes a positional argument of
the getter, in the order you would have written the subscripts. Three lookups, three parameters.

**Subgoal 2 — decide what can come back.** The value at the end of that path is a `Data`. Some of
its members cannot be returned: "the mapping and arrays (with the exception of byte arrays) in the
struct are omitted because there is no good way to select individual struct members or provide a key
for the mapping."<Cite src="solidity-docs-contracts" /> So `map` is out — you would need a fourth
key. `c` and `d` are out — they are arrays. `e` survives, because it is a byte array.

**Subgoal 3 — assemble the signature.** Three parameters in, three surviving members out:

```solidity
function data(uint arg1, bool arg2, uint arg3)
    public
    returns (uint a, bytes3 b, bytes memory e)
{
    a = data[arg1][arg2][arg3].a;
    b = data[arg1][arg2][arg3].b;
    e = data[arg1][arg2][arg3].e;
}
```

That is the compiler's own rendering of what it produces.<Cite src="solidity-docs-contracts" />

**Subgoal 4 — check the simpler cases against the same rule.** A plain `uint public data` gets a
getter with no arguments returning a `uint`.<Cite src="solidity-docs-contracts" /> A `uint[] public
myArray` gets `myArray(uint i)` returning one element — "this mechanism exists to avoid high gas
costs when returning an entire array", and if you want the whole thing you write a function
yourself.<Cite src="solidity-docs-contracts" /> A `mapping(address => uint256) public balances` gets
`balances(address)`. In every case: one parameter per lookup step, and no way to enumerate.

**Subgoal 5 — notice which half of the interface you did not get.** You have a reader. You have no
writer, no length accessor for the dynamic array, and no iteration. Anything a consumer needs beyond
"give me the value at this exact key" is a function you still have to write. `public` is not "expose
this variable"; it is "expose this one lookup."

### The getter is a function, and that has consequences

Two details follow from the getter being a real function rather than a special access mode.

"The getter functions have external visibility. If the symbol is accessed internally (i.e. without
`this.`), it evaluates to a state variable. If it is accessed externally (i.e. with `this.`), it
evaluates to a function."<Cite src="solidity-docs-contracts" /> So inside the contract, `data = 3`
writes the variable and `this.data()` performs a message call to read it — the same identifier, two
different mechanisms, chosen by the presence of `this.`.

And because it is a function, it can participate in inheritance: "Public state variables can
override external functions if the parameter and return types of the function matches the getter
function of the variable."<Cite src="solidity-docs-contracts" /> A base contract can declare
`function decimals() external view virtual returns (uint8)` and a derived contract can satisfy it
with `uint8 public override decimals`. The direction is one-way, though — "while public state
variables can override external functions, they themselves cannot be
overridden."<Cite src="solidity-docs-contracts" /> Lesson 6 comes back to this.

## Visibility is not privacy

The Solidity docs print the same warning twice — once under state variable visibility and once under
function visibility — which is the documentation equivalent of raising its voice:

> Making something `private` or `internal` only prevents other contracts from reading or modifying
> the information, but it will still be visible to the whole world outside of the
> blockchain.<Cite src="solidity-docs-contracts" />

Three facts you already have from Track 03 explain why this is not a gap that better tooling could
close.

**Storage is a public key-value map with a known key space.** The account's storage is [a
mapping from slot to word](/c/state-as-keyvalue) committed to in the state root, and every node
holds it. `eth_getStorageAt` "returns the value from a storage position at a given address" and is
part of the standard execution API, not a debug extension.<Cite src="execution-apis-eth-state" />
There is no read path that consults your source code.

**The slot numbers are derivable, and usually published.** State variables are stored contiguously
starting at slot 0, packed where the sizes allow, with documented rules for structs, dynamic arrays
and mappings.<Cite src="solidity-docs-storage-layout" /> The compiler will also tell you outright: the
`storageLayout` output emits a JSON array giving the contract, the label, the slot and the byte
offset for every state variable.<Cite src="solidity-docs-storage-layout" /> Visibility does not
appear in that output, because it is irrelevant to it.

**Nothing is written that is not committed.** A value your contract stored is in the state trie by
definition. Choosing not to generate a getter changes what other *contracts* can reach during
execution; it changes nothing about what the chain holds.

<Misconception
  belief="A private variable is hidden — nobody can see it unless the contract chooses to reveal it."
  reality="Every slot of every contract's storage is world-readable through eth_getStorageAt or by reading the state trie directly. Visibility keywords constrain what other contracts' code can reach at execution time, and nothing else. Storing a secret in a private variable publishes it."
  why="The keyword is imported from languages where private is an access-control mechanism enforced by a runtime that owns the memory. Here the runtime is a public replicated database, and the keyword is enforced only by the compiler's name resolution — it never reaches the bytecode as a guard."
  src="solidity-docs-contracts"
/>

If you genuinely need a value on chain that observers cannot read yet, the primitive is a
[commitment](/c/commitment), not a keyword: publish `keccak256(secret, salt)` now, publish the
preimage later, and let anyone check the two agree. That moves the secrecy into cryptography, where
it can survive being replicated to every node on earth. Visibility never could.

<Check type="explain" concept="sol-visibility-not-privacy">
An auction contract stores each sealed bid as `mapping(address => uint256) private bids;` and a
`uint256 private minBid;`. The team's reasoning: bids are private, so nobody can front-run them, and
`minBid` is private, so nobody can tune their bid to just clear it.

State what an observer can actually do, and then say which of the two problems is fixable with a
different keyword and which is not.

<Answer>
**An observer reads both, immediately, for free.**

`minBid` is a single value type at a fixed slot the compiler will name in its `storageLayout`
output, so one `eth_getStorageAt` returns it.<Cite src="solidity-docs-storage-layout" /><Cite src="execution-apis-eth-state" />

`bids` is barely harder. A mapping's declared slot holds nothing; each value lives at a slot derived
by hashing the key together with the mapping's slot, using rules the documentation
specifies.<Cite src="solidity-docs-storage-layout" /> So an observer who knows a bidder's address
computes the slot and reads that bidder's bid. They do not need to enumerate the mapping — they
already know which addresses they care about, because those addresses had to send transactions to
place the bids, and those transactions are public.

Marking either variable `internal`, or `public`, or leaving it as `private`, changes exactly one
thing: whether *other contracts, during execution*, can reference the name.<Cite src="solidity-docs-contracts" />
It does not change a single byte of what the chain stores or what a node will serve.

**Neither problem is fixable with a keyword. They are fixable with different mechanisms, and they
are different mechanisms.**

`minBid` is a *design* problem, not a secrecy problem. If the contract must compare a bid against a
threshold, the threshold is in state and is therefore public. The fix is to stop needing it secret —
a reserve price that is revealed at settlement can be committed to at the start as a hash, and
checked against the revealed value later.<Cite src="solidity-docs-contracts" />

`bids` is a *protocol* problem. The standard answer is commit-reveal: bidders submit
`keccak256(amount, salt)` during the bidding window and the amounts during a reveal window. Nothing
readable during bidding constrains the outcome, because the amount is not on chain yet — only a
[commitment](/c/commitment) to it is.

The useful generalisation: `private` answers "which code may name this?" On a chain that replicates
every slot to every participant, that question is unrelated to "who may know this?", and no keyword
in the language answers the second one.
</Answer>
</Check>

## Where this pays off

**Mutability is the next question about a function**, and it is a genuinely different one.
Visibility says who may call; `view`, `pure` and `payable` say what the call is permitted to do once
it arrives — and one of those three is enforced by the EVM while another is not.<Cite src="solidity-docs-grammar" />

**Inheritance** reuses everything here. `internal` versus `private` is precisely the line between
"my subclasses can use this" and "they cannot", and public state variables overriding external
functions is a small piece of the override machinery that lesson 6 assembles.

**Proxies and upgrades** turn the storage-layout facts from the last section into a correctness
requirement. Two separately compiled contracts sharing one storage region agree about slot numbers
and nothing else — visibility, names and types are all compile-time fictions from the slot map's
point of view.

**Security review** gets a fixed question from this lesson: for every piece of state, ask what
breaks if an adversary reads it at an arbitrary moment. The answer is never "they cannot", so the
useful version of the question is about timing and about what the protocol does with the value.
