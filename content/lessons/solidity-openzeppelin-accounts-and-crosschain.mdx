Open the 5.7.0 changelog and read only the category headings: Utils, Access, **Account**,
Cryptography, **Cross-chain**, Governance, Structures, Token.<Cite src="oz-changelog" />

Now read what is under Token. Five extensions, two of which are crosschain bridges for ERC-721 and
ERC-1155, one ERC-3009 authorisation extension, one bug fix, and a `SafeERC20` helper that reads
`decimals()` without reverting.<Cite src="oz-changelog" /> That is a mature area receiving
maintenance.

The two directories that did not exist three years ago are where the work is now. This lesson is what
is in them, how to tell how settled each piece is, and — the part that matters most — exactly where
the library stops.

## The account stack

`contracts/account/` holds twelve Solidity files at v5.7.0.<Cite src="oz-contracts-tree-570" />

```text
Account.sol
extensions/draft-AccountERC7579.sol
extensions/draft-AccountERC7579Hooked.sol
extensions/draft-ERC7821.sol
paymaster/Paymaster.sol
paymaster/extensions/PaymasterERC20.sol
paymaster/extensions/PaymasterERC20Guarantor.sol
paymaster/extensions/PaymasterERC721Owner.sol
paymaster/extensions/PaymasterSigner.sol
utils/EIP7702Utils.sol
utils/ERC4337Utils.sol
utils/draft-ERC7579Utils.sol
```

Look at the prefixes before the names. `Account.sol` is not `draft-`; `draft-AccountERC7579.sol` is.
That is not an accident of when they were written — both landed in 5.4.0, in the same pull
request.<Cite src="oz-changelog" /> The difference is the maturity of the standard each one tracks.
ERC-4337 is Final.<Cite src="eip-4337" /> ERC-7579 is Draft.<Cite src="erc-7579" /> The prefix is
the library telling you which of those two contracts can change under you.

`utils/ERC4337Utils.sol` makes the same point in reverse: it carried the prefix until 5.7.0, which
dropped it precisely because ERC-4337 finalised — a rename that broke every import of
it.<Cite src="oz-changelog" />

**What each layer is for.** `Account` is described as a simple ERC-4337 account with minimal logic to
process user operations.<Cite src="oz-changelog" /> `AccountERC7579` extends it with support for
ERC-7579 modules of type executor, validator and fallback handler; `AccountERC7579Hooked` adds hook
modules.<Cite src="oz-changelog" /> `ERC7821` is minimal batch execution, deliberately without
support for additional `opData`.<Cite src="oz-changelog" />

The entrypoint version moved in 5.6.0: `Account`'s default is now ERC-4337 entrypoint
v0.9.<Cite src="oz-changelog" /> That is the kind of default worth checking against whatever bundler
infrastructure you intend to use, because the two have to agree and neither is in your repository.

### The signature check is the pluggable part

`contracts/utils/cryptography/signers/` holds ten files:<Cite src="oz-contracts-tree-570" />

```text
AbstractSigner.sol            SignerECDSA.sol       SignerEIP7702.sol
SignerP256.sol                SignerRSA.sol         SignerWebAuthn.sol
SignerERC7913.sol             MultiSignerERC7913.sol
MultiSignerERC7913Weighted.sol                      draft-ERC7739.sol
```

The design choice there is worth naming. An account is mostly boilerplate — nonces, validation data
packing, execution — and the interesting variation is *what counts as a valid signature*. So the
library factored that out: `AbstractSigner` plus a family of implementations, and an account inherits
one.<Cite src="oz-changelog" /> Want an account controlled by a passkey rather than a secp256k1 key?
Inherit `SignerWebAuthn` instead of `SignerECDSA`; nothing else changes.

`MultiSignerERC7913` and its weighted variant give threshold verification over a set of ERC-7913
signers, which is Final.<Cite src="oz-changelog" /><Cite src="eip-7913" /> ERC-7913's job is to make
a signer an *address plus key material* rather than an address, so verifiers for key types the EVM
has no precompile for can be plugged in.

One rename to know about, because it is exactly the sort of thing that fails a search: `SignerERC7702`
became `SignerEIP7702` in 5.5.0. Imports and inheritance must be updated; behaviour is
unchanged.<Cite src="oz-changelog" />

### A twenty-line library you can read in full

`EIP7702Utils` is the whole of the library's EIP-7702 support, and it is small enough to print:

```solidity
library EIP7702Utils {
    bytes3 internal constant EIP7702_PREFIX = 0xef0100;

    function fetchDelegate(address account) internal view returns (address) {
        bytes23 delegation = bytes23(account.code);
        return bytes3(delegation) == EIP7702_PREFIX ? address(bytes20(delegation << 24)) : address(0);
    }
}
```

That is verbatim from v5.7.0.<Cite src="oz-eip7702utils-v570" /> You already know every byte of it:
a [delegation designator](/c/delegation-designator) is `0xef0100` followed by twenty bytes of
address.<Cite src="eip-7702" /> The function takes the first 23 bytes of the account's code, checks
the three-byte prefix, shifts left by 24 bits to drop it, and returns the remaining twenty as an
address — or `address(0)` when there is no delegation.

Two things are worth extracting from it. First, this is what "the library gives you a helper" actually
means at this layer: it is a correct, named, reviewed encoding of a fact from a spec, not an
abstraction. Second, note what it does **not** do. It tells you an account has a delegation and names
the delegate. It does not tell you whether the delegate is trustworthy, whether it is itself an
upgradeable proxy, or whether the delegation was installed by the account's owner. Those are the
questions that matter, and no library can answer them.

### Two routes to a programmable account, one library

There are two live ways for a user to end up with an account that runs code, and the library covers
both without saying so out loud.

**Deploy a contract account.** `Account` plus a signer module plus, optionally, `AccountERC7579` for
modules. The user gets a new address, and everything they already hold has to move to it. The
infrastructure dependency is a bundler and an entrypoint.

**Delegate an existing EOA.** The user keeps their address and installs a
[delegation designator](/c/delegation-designator) pointing at a wallet implementation. Nothing moves.
The library's piece here is `SignerEIP7702` — added in 5.4.0 as `SignerERC7702` and renamed in
5.5.0 — an `AbstractSigner` implementation for externally owned accounts, described in the changelog
as useful with ERC-7702.<Cite src="oz-changelog" /> Its whole body recovers the signer and compares
it to `address(this)` — which, under a delegation, is the user's own
address.<Cite src="oz-signereip7702-v570" />

The two routes are not alternatives so much as different answers to "who pays for the address
change". And they compose: a delegate contract can inherit `ERC7821` for batch execution and a signer
module for validation, which is most of what a 7702 wallet implementation needs.

What neither route removes is the setup problem you already know: a designator is installed by an
authorization tuple that carries no calldata, so initialisation is a separate call and separate calls
can be front-run.<Cite src="eip-7702" /> `EIP7702Utils.fetchDelegate` will tell a contract that it is
talking to a delegated EOA. It will not tell it whether that EOA's delegate was set up safely.

### Paymasters, added in 5.7.0

`Paymaster` is a simple ERC-4337 paymaster with minimal logic, plus four
extensions:<Cite src="oz-changelog" />

- `PaymasterERC20` — sponsors user operations against payment in ERC-20 tokens.
- `PaymasterERC20Guarantor` — lets a third party prefund gas costs upfront and be repaid on success.
- `PaymasterERC721Owner` — sponsors based on ownership of an NFT.
- `PaymasterSigner` — sponsors based on a signature the paymaster verifies.

Four policies, one mechanism. That is the shape the whole directory has: a minimal base plus
extensions that encode a decision, so the decision is visible in your inheritance list rather than
buried in a config.

## The crosschain directory

`contracts/crosschain/` holds ten files:<Cite src="oz-contracts-tree-570" />

```text
CrosschainLinked.sol            CrosschainRemoteExecutor.sol   ERC7786Recipient.sol
bridges/abstract/BridgeFungible.sol      bridges/BridgeERC20.sol     bridges/BridgeERC7802.sol
bridges/abstract/BridgeNonFungible.sol   bridges/BridgeERC721.sol
bridges/abstract/BridgeMultiToken.sol    bridges/BridgeERC1155.sol
```

Three abstract bases — fungible, non-fungible, multi-token — with concrete bridges on top, plus
`ERC20Crosschain`, `ERC721Crosschain` and `ERC1155Crosschain` living in the token tree as extensions
that embed a bridge directly in the token.<Cite src="oz-changelog" /> `GovernorCrosschain` in the
governance tree lets a governor execute operations on remote chains through
`CrosschainRemoteExecutor` and ERC-7786 gateways.<Cite src="oz-changelog" />

Supporting them are two libraries added in 5.5 and 5.6: `InteroperableAddress`, formatting and
parsing ERC-7930 addresses that carry a chain reference alongside the account; and `TrieProof`, for
verifying Ethereum Merkle-Patricia inclusion proofs on
chain.<Cite src="oz-changelog" /><Cite src="eip-7930" />

`TrieProof` is the one to notice. You have already built the mental model it implements — the
[state trie](/c/merkle-patricia-trie), a proof as a node list, `eth_getProof`. Its arrival in the
library means that verifying "this account had this balance in that block on that chain" is now a
composition of shipped parts rather than a bespoke project. Its first appearance in this module was
in a rescue plan: the maintainer replying to the bricked-proxy report suggested using storage proofs
of the locked token's balances to distribute an equivalent working token to
holders.<Cite src="oz-issue-6362" />

<Aside kind="note">
Maturity varies sharply across this directory. ERC-7786 is Final, and its interface file still
carries the `draft-` prefix, which as lesson 3 showed means the prefix lags rather than
leads.<Cite src="eip-7786" /><Cite src="oz-contracts-tree-570" /> ERC-7930 is at Review — not Final —
so `draft-InteroperableAddress.sol` is prefixed for the ordinary reason.<Cite src="eip-7930" />
ERC-7802 is Draft.<Cite src="eip-7802" /> Check each one; the answers are not uniform and they move.
</Aside>

## Where the library stops

Both directories share a property that is easy to miss when you are reading a file list: everything
in them is the *on-chain half* of a system whose other half is infrastructure the library does not
supply and does not choose.

An ERC-4337 account is inert without a bundler collecting user operations and submitting them, and a
mempool for those operations to sit in. OpenZeppelin ships no bundler. A paymaster needs to be funded
and needs an off-chain policy service deciding what to sponsor; the library gives you the contract
that enforces a policy, not the service that forms one.

The crosschain side is starker. ERC-7786 defines a *gateway interface*.<Cite src="eip-7786" /> A
gateway is a thing somebody operates, with its own validators or attesters or proof system and its own
failure modes. `CrosschainLinked` and the bridges give you a contract that talks to one correctly.
Which gateway you talk to — and therefore whose honesty your users' funds depend on — is a decision
the library deliberately leaves to you, exactly as it leaves who may pause and who may upgrade.

That is not a gap in coverage. It is the same boundary as everywhere else in this module, showing up
in a new place, and it is what the last lesson is about.

<Check type="explain" concept="oz-account-abstraction-modules">
`Account.sol` and `draft-AccountERC7579.sol` shipped in the same release, in the same pull request,
written by the same people. One carries the `draft-` prefix and the other does not.

Explain what determines that, what it predicts about each file's future, and what it does **not**
tell you.

<Answer>
**What determines it: the status of the standard, not the quality of the code.** OpenZeppelin's
backwards-compatibility policy says ERCs that are not Final can change incompatibly, so
implementations that may have to break are published with a `draft-` prefix and carry no backwards
compatibility guarantee at all.<Cite src="oz-docs-backwards-compatibility" /> ERC-4337 is
Final.<Cite src="eip-4337" /> ERC-7579 is Draft.<Cite src="erc-7579" />

**What it predicts.** `Account`'s interface is as stable as anything in the library — it can only
change in a release that says so. `AccountERC7579` can change its interface, its behaviour, or both,
in a minor release, if the ERC does. And if ERC-7579 finalises, the file is renamed and your import
breaks — which is the outcome you want, because the compiler tells you. That is precisely what
happened to `ERC4337Utils` in 5.7.0.<Cite src="oz-changelog" />

**What it does not tell you: anything about correctness.** The prefix is a statement about the
standard's stability, not about whether either contract has bugs, and not about whether it has been
audited. Those are separate axes with separate evidence — the audit index for one, the security
policy for the other.

**The practical move.** If you inherit `AccountERC7579`, put ERC-7579's status page on whatever list
you use for dependency watching, and treat a minor bump as a diff to read rather than a version to
raise. If you inherit `Account`, the changelog is enough.

**One trap.** The prefix undercounts as often as it warns. `draft-IERC7786.sol` tracks a standard that
is already Final; the file has not been renamed yet.<Cite src="eip-7786" /> "Prefixed" means "the
maintainers have not committed to this path", which is not the same claim as "the standard is
unsettled".
</Answer>
</Check>

## Where this pays off

**The last lesson** takes the boundary this one ran into — no bundler, no gateway operator, no policy
— and generalises it into a list, then asks the harder question of what "OpenZeppelin is audited"
does and does not transfer to a contract you assembled.

**Track 07** builds on the account material directly: user operations, bundlers, entrypoints,
paymasters and session keys as a product surface rather than a directory listing.

**A habit worth forming now.** When a library adds a directory, read the file names for prefixes
before you read the code. In this one, the prefixes told you the maturity of eight different standards
in about ten seconds — and if you had checked `community-contracts` as well, you would have found a
fifth tier where things are tried before they arrive here at all.<Cite src="oz-community-contracts" />
