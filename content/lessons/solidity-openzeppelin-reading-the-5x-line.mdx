Ask what version of OpenZeppelin Contracts is current and you get two answers, both correct.

```console
$ npm view @openzeppelin/contracts dist-tags
{ latest: '5.6.1', dev: '5.7.0' }
```

The top of the changelog says `5.7.0 (2026-07-29)`.<Cite src="oz-changelog" /> The git tag `v5.7.0`
exists and was published on the same day.<Cite src="oz-releases" /> And `npm install @openzeppelin/contracts`,
which resolves the `latest` tag, installs 5.6.1 — released on 27 February 2026, five months
earlier.<Cite src="oz-npm-contracts" />

That is not a mistake or a lag in publishing. It is the library telling you something specific, in
the only channel it has, and if you cannot read it you will get the rest of this module's answers
wrong too.

## Three tags, three promises

The README documents the npm tag scheme directly.<Cite src="oz-repo-readme" />

So by the project's own tag scheme, 5.7.0 is finished, tagged, published and shipping — and not yet
audited. The audit index in the repository is consistent with that: the newest per-release report is
`2026-02-v5.6.pdf`, covering v5.6.0, and there is no v5.7 report there at the time of
writing.<Cite src="oz-audits-index" />

Two things follow immediately.

**"I'm on the latest OpenZeppelin" is ambiguous.** It means 5.6.1 if you installed from npm without
a tag, 5.7.0 if you ran `forge install OpenZeppelin/openzeppelin-contracts` and took the newest
release, and something else again if a `forge update` walked your submodule onto `master` — which
the README explicitly warns against, because `master` is a development branch that does not carry
the release process's security measures.<Cite src="oz-repo-readme" />

**Pinning is not optional.** Foundry installs a specific version initially and then subsequent
`forge update` commands move to `master`.<Cite src="oz-repo-readme" /> A `git submodule` that
silently advances is a dependency you are not versioning.

<Aside kind="warn">
The 5.7.0 release was preceded by `v5.7.0-rc.0` on 15 July 2026, two weeks
earlier.<Cite src="oz-releases" /> That window exists on purpose: the bug bounty pays a bonus for
issues found in a release candidate before it reaches a stable release.<Cite src="oz-security-policy" />
If you run on `dev` or `next`, you are part of that process rather than a consumer of its output.
</Aside>

Roughly two to three minors a year. **5.0.0 is still the last major**, and there is no 6.0 — nearly
three years of a single major line.<Cite src="oz-changelog" />

That stability is the thing people over-read. The temptation is to translate "no major since 2023"
into "minor bumps are routine". The changelog disagrees in the most direct way available: 5.5.0,
5.6.0 and 5.7.0 each open with a section headed **Breaking changes**.<Cite src="oz-changelog" />

## What semver actually covers here

The maintainers wrote this down, and it is more precise than the usual reading. Semantic versioning
in this library communicates backwards compatibility of **the API and the storage layout**. Minor and
patch updates always preserve storage layout compatibility; major releases should be assumed
incompatible.<Cite src="oz-docs-backwards-compatibility" />

The same page lists the carve-outs, and each one is a real trap:

- **Security.** A patch or minor may remove or change an API in a breaking way if the previous API is
  considered insecure. Published with an advisory.<Cite src="oz-docs-backwards-compatibility" />
- **Draft or pre-final ERCs.** There is no backwards compatibility guarantee for anything in a file
  prefixed `draft-`.<Cite src="oz-docs-backwards-compatibility" /> Lesson 3 is entirely this.
- **Virtual and overrides.** Almost every function is `virtual`, but only a subset is *designed* to
  be overridden. Override outside that subset and you are depending on internal implementation
  details.<Cite src="oz-docs-backwards-compatibility" />
- **Struct members.** A member with a leading underscore is "private" and may break in a
  minor.<Cite src="oz-docs-backwards-compatibility" />
- **Errors.** The specific error format and the data included with reverts are **not** assumed
  stable.<Cite src="oz-docs-backwards-compatibility" />

That last one deserves a moment, because it cuts against the instinct custom errors encourage. A
typed selector feels like an API. The maintainers are telling you it is not one, unless they say
otherwise for a specific error.

## Four ways a minor bump breaks you

Take the breaking changes from the last three minors and sort them not by contract but by *when you
find out*. That ordering is what matters operationally.

**It fails to compile.** 5.5.0 raised the minimum pragma to 0.8.24 in a named list of contracts
including `EIP712`, `ERC1155`, `ERC4626`, `ERC721Enumerable`, `Strings` and
`Votes`.<Cite src="oz-changelog" /> Against Solidity 0.8.36 that is no constraint at all, but a
project pinned to an older compiler stops building. 5.5.0 also dropped the `draft-` prefix from
`ERC6909` and its extensions, because ERC-6909 reached Final — a pure import-path
break.<Cite src="oz-changelog" /><Cite src="eip-6909" /> 5.7.0 did the same for `ERC4337Utils` and
`IERC4337` once ERC-4337 finalised.<Cite src="oz-changelog" /><Cite src="eip-4337" />

**Your deployment reverts.** 5.6.0 made proxy initialisation mandatory: `ERC1967Proxy` and
`TransparentUpgradeableProxy` now revert with `ERC1967ProxyUninitialized` if constructed without an
initialize call, unless you override `_unsafeAllowUninitialized`.<Cite src="oz-changelog" /> This
closes a genuine footgun, and it also means a deploy script that worked in 5.5 stops working in 5.6.
5.7.0 has a companion case: `EIP712` dropped its storage fallback for long values, so a `name` or
`version` longer than 31 bytes now reverts the constructor with
`ShortStrings.StringTooLong`.<Cite src="oz-changelog" /> Both fail at deploy time, which is the good
outcome.

**Somebody else's contract breaks.** 5.6.0 changed ERC-1155 batch semantics: a batch transfer with
exactly one item now calls `onERC1155BatchReceived` with length-one arrays instead of
`onERC1155Received`.<Cite src="oz-changelog" /> Your token compiles. Your tests pass. The receiver
contract that a partner deployed two years ago and only implemented the single-item hook now rejects
your transfer. Nothing in your build tells you.

**Nothing breaks, and your data is wrong.** This is the 4.x-to-5.x class, and the cleanest example is
in 5.0.0: `ERC20` stopped emitting the `Approval` event that used to fire inside `transferFrom` to
signal partial allowance consumption. The changelog states the consequence in one line — allowances
are no longer reconstructible from events.<Cite src="oz-changelog" /> Every contract still works.
Every indexer that rebuilt allowance state from the log stream is now silently wrong, and you will
find out from a support ticket.

## What the minors actually added

Sorting by breakage tells you what to fear. Sorting by addition tells you where the project is going,
and over the 5.x line the direction is unmistakable.<Cite src="oz-changelog" />

- **5.1.0 / 5.2.0** — utility fill-in. `Bytes`, `CAIP2` and `CAIP10`, `NoncesKeyed`, `Strings.parseUint`
  and friends, and on the proxy side `Clones.cloneWithImmutableArgs` with its
  `fetchCloneArgs` reader.
- **5.3.0** — a first-party `ERC6909`, several Governor extensions, an updatable `MerkleTree`.
- **5.4.0** — the pivot. `Account`, `AccountERC7579`, `AccountERC7579Hooked`, `SignerWebAuthn`, and
  the `Paymaster` family.
- **5.5.0** — `WebAuthn`, ERC-7913 verifiers, `RLP`, `Base58`, `Memory`, `LowLevelCall`,
  `RelayedCall`, ERC-7930 interoperable addresses, `ERC7786Recipient`.
- **5.6.0** — crosschain bridges for ERC-20, `CrosschainLinked`, `ERC20Crosschain`, and a `TrieProof`
  library for Merkle-Patricia inclusion proofs.
- **5.7.0** — `Create3`, `ERC1967Clones`, `BlockHeader`, `SimulateCall`, `RateLimiter`, ERC-721 and
  ERC-1155 bridges, `GovernorCrosschain`.

Read that list backwards and the last eighteen months contain almost no token work. Tokens were
finished. The additions are account abstraction, crosschain messaging, and the low-level plumbing
those two need — `RLP` and `TrieProof` are there because a bridge has to verify another chain's
state, which is a job the library did not previously take on. Lesson 6 goes through both directories.

<Aside kind="warn">
`Clones.cloneWithImmutableArgs` is worth checking yourself rather than taking from any summary,
including this one. This repository's own conflict register records it as landing in 5.4.0 on
17 July 2025, and the changelog places the entry — PR #5109 — under the `5.2.0 (2025-01-08)`
heading.<Cite src="oz-changelog" /> The two disagree by two releases and six months. That matters if
you are writing a pragma floor or a "requires OZ >= x" line in a README. The changelog is the
artifact; read the heading the entry sits under, not a summary of it.
</Aside>

## Pragma floors and the EVM version underneath

Two version numbers move independently and both can bite.

**The library's floor.** 5.0.0 raised the minimum compiler to 0.8.20, and 5.5.0 raised a long list of
individual contracts to 0.8.24 — the release that made transient storage available, which is what
`ReentrancyGuardTransient` needs.<Cite src="oz-changelog" /> Against Solidity 0.8.36 neither floor is
a constraint.

**The target's ceiling.** The floor is about what the compiler understands. What the *chain*
understands is a separate setting. `solc` set its default EVM version to `osaka` in 0.8.31, released
3 December 2025.<Cite src="solidity-changelog" /> So a default build assumes `TSTORE`, `TLOAD`,
`MCOPY` and `BLOBHASH` are all present, and emits them freely.

That default is correct for Ethereum mainnet and wrong for any target that has not caught up. If you
deploy the same source to an L2 or a sidechain running an older fork and do not lower
`evm_version`, you get bytecode containing an opcode the chain does not implement — and the failure
is at execution, not at build. The two settings are unrelated: a contract can require solc 0.8.24 and
still be compiled for `paris`.

## 4.x to 5.x is not a dependency bump

The 5.0.0 changelog is long. Sorted the same way, the migration falls into three piles.

**Deletions that stop the build.** `Counters`, `SafeMath`, `SignedSafeMath`, `ERC20Snapshot`,
`ERC777`, `ERC1820Implementer`, `PaymentSplitter`, `PullPayment`, all the escrow contracts,
`Address.isContract`, and every preset contract — the presets removed explicitly in favour of the
Contracts Wizard.<Cite src="oz-changelog" /> Also gone from `ERC20` itself: the non-standard
`increaseAllowance` and `decreaseAllowance`.<Cite src="oz-changelog" /> They survive only on
`SafeERC20` as `safeIncreaseAllowance` and `safeDecreaseAllowance`, which were refactored in the same
release to work with USDT-shaped tokens.<Cite src="oz-changelog" /> Any tutorial telling you to call
`token.increaseAllowance(...)` is describing a function most tokens on chain do not have.

**Signature changes that stop the build.** `Ownable`'s constructor takes an explicit `initialOwner`
and no longer defaults to `msg.sender`, and passing `address(0)` reverts with
`OwnableInvalidOwner`.<Cite src="oz-changelog" /><Cite src="oz-ownable-source-v570" /> The `ERC20`,
`ERC721` and `ERC1155` hooks `_beforeTokenTransfer` and `_afterTokenTransfer` were **deleted** and
replaced by a single internal `_update` that every extension now overrides.<Cite src="oz-changelog" />
That is not a rename. A mint, a burn and a transfer all flow through one function, so a hook that
used to distinguish the three by checking `from` and `to` has to be rewritten as an override that
does its work around a `super._update(...)` call.

**The one that compiles.** Upgradeable storage moved from reserved gap arrays to ERC-7201
namespaces in the same release.<Cite src="oz-changelog" /> Nothing about that is visible to the
compiler when you bump a dependency, and on a live proxy it is a data-corruption event rather than
an error. Lesson 5 is that mechanism end to end.

## The error vocabulary, and what it is not

5.0.0 replaced revert strings and `require` statements with custom errors across the
library.<Cite src="oz-changelog" /> You already know the machinery: an error's selector is the first
four bytes of keccak-256 of its canonical signature, derived by exactly the same rule as a
[function selector](/c/sol-error-selector). What is new is a vocabulary, and the fact that your test
suite is written against the old one.

The token errors are not OpenZeppelin's invention. They come from ERC-6093, which standardises custom
errors for ERC-20, ERC-721 and ERC-1155, and the library ships them as
`contracts/interfaces/draft-IERC6093.sol`.<Cite src="oz-ierc6093-v570" /><Cite src="eip-6093" />
The access errors are declared where they are used:

```solidity
// contracts/access/Ownable.sol
error OwnableUnauthorizedAccount(address account);
error OwnableInvalidOwner(address owner);

// contracts/access/IAccessControl.sol
error AccessControlUnauthorizedAccount(address account, bytes32 neededRole);
error AccessControlBadConfirmation();

// contracts/utils/Pausable.sol
error EnforcedPause();
error ExpectedPause();
```

Those are the real declarations at v5.7.0.<Cite src="oz-ownable-source-v570" /><Cite src="oz-iaccesscontrol-v570" /><Cite src="oz-pausable-source-v570" />
Their selectors, computed the ordinary way:

```console
$ cast sig "OwnableUnauthorizedAccount(address)"
0x118cdaa7
$ cast sig "AccessControlUnauthorizedAccount(address,bytes32)"
0xe2517d3f
$ cast sig "ERC20InsufficientBalance(address,uint256,uint256)"
0xe450d38c
$ cast sig "EnforcedPause()"
0xd93c0665
```

Nothing surprising — which is the point. There is no OpenZeppelin error encoding. There is
`Error(string)` at `0x08c379a0`, `Panic(uint256)` at `0x4e487b71`, and everything else is a
four-byte selector followed by ABI-encoded arguments.<Cite src="solidity-abi-spec" />

Three practical consequences.

**Your 4.x tests fail on the assertion, not the behaviour.** `vm.expectRevert("Ownable: caller is not the owner")`
matched an `Error(string)` payload. The contract now reverts with `0x118cdaa7` followed by an
address. Rewriting to `vm.expectRevert(abi.encodeWithSelector(Ownable.OwnableUnauthorizedAccount.selector, caller))`
is mechanical, and there is a lot of it.

**The saving is at deployment, reliably; at runtime, only sometimes.** A revert string has to sit in
the deployed bytecode as a literal *and* be ABI-encoded when it fires. A custom error costs four
bytes of data when it fires and no literal at rest.<Cite src="solidity-blog-custom-errors" /> The
unconditional win is deploy size. The runtime win only materialises on the revert path, which is the
path your gas report foregrounds and your users mostly do not take.

**Do not branch product logic on the arguments.** The maintainers say the error format and data are
not assumed stable across releases.<Cite src="oz-docs-backwards-compatibility" /> Matching a selector
to render a message is fine. Reading `neededRole` out of `AccessControlUnauthorizedAccount` and
driving a state machine off it is a dependency on something nobody promised you.

**Your frontend needs a merged error ABI.** You already know that a contract's ABI JSON carries its
own error definitions and not those of contracts it calls, so a
[forwarded revert arrives unnameable](/c/errors-not-in-abi-when-forwarded). Moving to 5.x makes that
sharper rather than softer, because the failures your users hit most — an unauthorised call, an
insufficient balance, a paused contract — are now selectors declared inside the library rather than
strings your contract carried. If your client only holds your own artifact, `0x118cdaa7` renders as
four unknown bytes. Assemble the error ABI deliberately: your contract's errors, plus
`IERC6093`'s, plus the access and pause errors of every OpenZeppelin base you
inherit.<Cite src="oz-ierc6093-v570" />

## Where this pays off

**Reading a changelog entry as a risk class** is the transferable skill here, and it is the one the
next four lessons all lean on. The question is never "is this breaking?" — the changelog already
told you. It is "at which point in my pipeline does this become visible, and is that before or after
users touch it?"

**Which files carry a promise** comes next, and starts from a phrase you have now seen twice: the
`draft-` prefix, and the sentence that says it carries no backwards compatibility guarantee at all.

**Gas** stays out of this lesson deliberately. One number worth carrying forward: measured on
forge 1.7.1 with solc 0.8.36 and the optimizer off, `ReentrancyGuardTransient` added 284 gas to a
guarded call while the storage guard added 3,104 with a warm slot — and the storage guard's cost is
cold- and warm-dependent, ranging from roughly 3,100 to roughly 7,100.<Cite src="measured-gas-constants" />
Every single-number figure in circulation for that comparison is wrong for some configuration.
