Open any Solidity file that does something real and look at line six.

```solidity
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
```

Nothing in the compiler put that there. `solc` has no opinion about that path, no bundled package
for it to resolve, and no complaint if you never write it. The remapping that makes
`@openzeppelin/contracts/` mean anything is a line in your `foundry.toml` or a directory in your
`node_modules` — a choice, made by you, or made for you by whoever set the project up.

Roughly every Solidity project makes the same one. This lesson is about why, and about the precise
shape of what you are importing — because the shape determines what it can and cannot do for you,
and that boundary is the subject of the rest of the module.

## The gap

Solidity ships a language and no library.

That is not a slight. The language gives you a great deal: value types and reference types with
explicit data locations, mappings, dynamic arrays, `using ... for` to attach functions to
types.<Cite src="solidity-docs-types" /> It gives you globals — `msg`, `block`, `tx`, `abi.encode`
and its relatives, `keccak256`, `ecrecover`, `type(T)` — as built-ins with no import at
all.<Cite src="solidity-docs-global-vars" /> It gives you inheritance, interfaces, abstract
contracts, modifiers and events.<Cite src="solidity-docs-contracts" />

What it does not give you is anything above that layer. There is no standard `Ownable`. No standard
`Set` or `EnumerableMap`. No standard way to hold a role, pause a system, verify a Merkle proof,
call an ERC-20 that returns nothing, or clone a contract. Python has `collections`. Go has `net/http`.
Rust has `std`. Solidity has `keccak256` and a hope.

Every language with that gap gets a de facto standard library eventually — one package that arrives
early, is good enough, and becomes the thing everyone already has. This one arrived very early. The
repository was created in August 2016 under an MIT licence, and it had already been audited by March
2017, at version 1.0.4.<Cite src="oz-repo-github" /><Cite src="oz-audits-index" /> At the time of
writing it has been forked 12,406 times and starred 27,234 times.<Cite src="oz-repo-github" /> Forks
are a crude proxy for anything, but 12,406 of them is a fair description of a default.

<Aside kind="note">
This position is social, not technical. Nothing in `solc`, in Foundry, or in any EIP requires
OpenZeppelin. A contract that imports none of it is not less standard-compliant; ERC-20 is a
specification of an interface and an event log, not of an implementation.<Cite src="eip-20" /> The
convention is strong enough that most tooling assumes it — and it is still only a convention.
</Aside>

## What is actually in the box

At tag `v5.7.0` the repository holds 368 Solidity files under `contracts/`. One hundred and twenty
of them live in `contracts/mocks/` and exist only to be compiled by the project's own test
suite.<Cite src="oz-contracts-tree-570" /> The remaining 248 are the library.

They sort into layers you will recognise from the module map you have been building all track:

- **Primitives** — `Address`, `SafeCast`, `Math`, `Strings`, `Bytes`, `Panic`, `Memory`, `RLP`.
- **Cryptography** — `ECDSA`, `EIP712`, `MerkleProof`, `SignatureChecker`, `MessageHashUtils`,
  and since 5.5 a `WebAuthn` library and a family of signer modules.<Cite src="oz-contracts-tree-570" />
- **Access** — `Ownable`, `Ownable2Step`, `AccessControl`, `AccessManager`.
- **Tokens** — `ERC20`, `ERC721`, `ERC1155`, `ERC4626`, `ERC6909`, plus their extensions.
- **Proxies** — `ERC1967Proxy`, `TransparentUpgradeableProxy`, `BeaconProxy`, `Clones`, and as of
  5.7 a `Create3` library and `ERC1967Clones`.<Cite src="oz-contracts-tree-570" />
- **Governance** — `Governor` and a dozen extensions, `TimelockController`, `Votes`.
- **Accounts and crosschain** — the newest two directories, and the subject of lesson 6.

The npm package is a strict subset of the repository. `package.json` publishes
`/contracts/**/*.sol` and explicitly excludes `/contracts/mocks/**/*`.<Cite src="oz-package-json-v570" />
Install with `npm` and the mocks are not there. Install with `forge install`, which adds the whole
git repository as a submodule, and they are. Lesson 3 is about why that distinction matters more
than it sounds.

## A library, not a framework

The word matters, and it is the single most useful thing to hold onto.

A framework inverts control: it owns the entry point, it calls your code, and it decides the shape of
your application. Hardhat and Foundry are frameworks in that sense. So is Next.js. You put your code
in the places the framework reserved for it.

OpenZeppelin Contracts does none of that. It is a set of `abstract contract` declarations and
`library` declarations. It has no entry point. It never runs. It does not deploy, does not upgrade,
does not initialise, does not choose an address for anything. The only way it enters your system is
that you write `is` in front of one of its names, and from that moment the composition is yours:

```solidity
abstract contract ERC20 is Context, IERC20, IERC20Metadata, IERC20Errors {
```

That is the real declaration of `ERC20` at v5.7.0.<Cite src="oz-erc20-source-v570" /> Four bases, one of
which — `IERC20Errors` — is an interface of nothing but custom error declarations, imported from
`contracts/interfaces/draft-IERC6093.sol`.<Cite src="oz-ierc6093-v570" /><Cite src="eip-6093" />
When you write `contract MyToken is ERC20, Ownable, Pausable`, the
[C3 linearisation](/c/sol-c3-linearisation) you already know is what decides the order those
constructors run and which `_update` override wins. The library did not arrange that. The compiler
did, from the order *you* wrote.

The consequence runs through the whole module. Because it makes no decisions, it also takes no
responsibility for them. `Pausable` gives you `whenNotPaused` and an internal `_pause()`; who is
allowed to call `_pause()` is a question it deliberately does not answer.<Cite src="oz-pausable-source-v570" />
That is not an oversight, and lesson 7 is entirely about the boundary it draws.

## Reading it is most of the curriculum

There is a second reason the library matters beyond the code it saves you: for most engineers it is
where idiomatic Solidity is learned. The house style is visible and deliberate, and three of its
choices are worth taking on directly because they postdate a lot of the material you will find
elsewhere.

**Named mapping parameters.** The declaration in `ERC20.sol` reads
`mapping(address account => uint256)` rather than `mapping(address => uint256)`.<Cite src="oz-erc20-source-v570" />
The names are documentation the compiler carries into the ABI-adjacent metadata; on a nested
allowance mapping they are the difference between a line you can read and one you have to decode.

**Explicit imports.** Every import in the library names its symbols —
`import {IERC20} from "./IERC20.sol";` — a switch made in 5.0.<Cite src="oz-changelog" /> A bare
`import "path.sol"` drags every top-level symbol in that file into your namespace, which is how you
end up shadowing a name you never knew existed.

**`abi.encodeCall` over `abi.encodeWithSelector`.** 5.0 replaced the selector-and-arguments forms
with `abi.encodeCall`, and the changelog states the reason: type-checking of the
parameters.<Cite src="oz-changelog" /> You already know why that matters — `abi.encodeWithSelector`
happily encodes a `uint256` where the function wanted an `address`, and you find out on chain. The
same argument applies to your own low-level calls.

## Why you install it rather than copy it

The README carries an instruction that reads like style advice and is not: always use the code
"as-is", and neither copy-paste it from elsewhere nor edit it yourself.<Cite src="oz-repo-readme" />

The reason is that the security guarantees are attached to the *package*, not to the bytes. Security
patches are published as npm releases and as GitHub advisories, and the policy is explicit about
which versions receive them: 5.x gets both critical and non-critical security fixes, 4.9 and 3.4 get
critical fixes only, and 2.5 and below get nothing.<Cite src="oz-security-policy" /> A vendored copy
of `ERC20.sol` sitting in your `src/` directory receives none of that. Dependabot cannot see it, the
advisory does not name it, and the day a fix lands you will not know.

The same README adds the counter-argument to the usual objection about bloat: the library is written
so that only the contracts and functions you actually use end up in the deployed
bytecode.<Cite src="oz-repo-readme" /> Unreferenced internal functions in an inherited abstract
contract are not emitted. Importing a large library does not deploy a large contract.

Two teams ship the same ERC-20. Team A writes `import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";`
and pins the dependency. Team B copies `ERC20.sol` into `src/vendor/ERC20.sol`, deletes three
functions they do not need, and commits it.

Both contracts compile to similar bytecode and pass the same tests. Six months later a security
advisory is published against a contract in the library. Name three things that are now different
between the two teams, and one thing that is *not* different.

<Answer>
**1 — Team B will not be told.** The advisory is published against the npm package and the
repository.<Cite src="oz-security-policy" /> Team A's dependency scanner resolves a version range and
raises an alert. Team B's file is an ordinary source file in their own repository; nothing about it
says where it came from or what version it was.

**2 — Team B cannot apply the fix by bumping.** They have to find the patch, read it, and
reimplement it against a file they have already modified — under time pressure, in the one situation
where a hurried diff is most dangerous.

**3 — Team B's deletions bought less than they think.** The library is written so that only the
contracts and functions you actually use are deployed, which is the maintainers' stated reason for
saying you do not need to worry about the import inflating gas costs.<Cite src="oz-repo-readme" />
Measure before you trade a maintenance liability for a saving you have not confirmed.

**What is not different: whether either contract is safe.** The advisory might not touch the
functions either team uses. And nothing about Team A's import protects the part of the system that
actually loses money — their mint authority, their pause key, their upgrade path. The dependency is
maintained; the composition is not. That distinction is the spine of this module and the whole of
lesson 7.
</Answer>
</Check>

## Where this pays off

**The version line** comes next, and it opens with a fact that surprises most people who have used
this library for years: `npm install @openzeppelin/contracts` today does not give you the version at
the top of the changelog.<Cite src="oz-npm-contracts" />

**Which files carry a promise** turns the 368-versus-248 file count into a working rule, because one
package version covers at least four different levels of guarantee.

**Everything downstream** — the upgradeable package, the storage-layout hazard, the account and
crosschain work — is a consequence of the two facts established here. It is a library, so it
composes into your inheritance graph and inherits your mistakes. And it is one package with one
version number, so the version number is the first thing you have to learn to read precisely.
