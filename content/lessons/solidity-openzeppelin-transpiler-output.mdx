Download `CHANGELOG.md` from `openzeppelin-contracts` and from `openzeppelin-contracts-upgradeable`
and diff them. They are byte-identical: 1,510 lines each, same entries, same PR
numbers.<Cite src="oz-changelog" /><Cite src="oz-upgradeable-changelog" />

That is not sloppiness. It is the clearest available statement of what the second repository is. It
does not have its own changelog because it does not have its own changes. It is generated.

## One package, produced by a program

`@openzeppelin/contracts-upgradeable` is the output of a build step. The tool has a name, a version
and an npm listing that describes it in one line: a Solidity preprocessor used to generate
OpenZeppelin Contracts Upgrade Safe.<Cite src="oz-npm-transpiler" /> The documentation says the same
thing in prose — the upgradeable variant replicates the structure of the main package, with every
file and contract suffixed `Upgradeable`, and it takes `@openzeppelin/contracts` as a **peer
dependency**.<Cite src="oz-docs-upgradeable" />

The `Upgradeable` suffix is a rename, not a rewrite. The strongest evidence is in the file header.
`ERC20Upgradeable.sol` opens with:

```solidity
// SPDX-License-Identifier: MIT
// OpenZeppelin Contracts (last updated v5.5.0) (token/ERC20/ERC20.sol)
```

It names its own source path — `token/ERC20/ERC20.sol` — because the comment was copied from the
input along with everything else.<Cite src="oz-erc20-upgradeable-v570" /><Cite src="oz-erc20-source-v570" />

## The six transformations, read off the diff

Put `ERC20.sol` and `ERC20Upgradeable.sol` side by side. Every difference is one of six mechanical
edits, and naming each one's purpose is worth more than memorising the output.

**Subgoal 1 — make the base list initializable.** The declaration gains `Initializable` at the front
and swaps each transpiled parent for its suffixed form.

```solidity
// main package
abstract contract ERC20 is Context, IERC20, IERC20Metadata, IERC20Errors

// upgradeable package
abstract contract ERC20Upgradeable is Initializable, ContextUpgradeable, IERC20, IERC20Metadata, IERC20Errors
```

`Context` became `ContextUpgradeable`; the three interfaces did not
change.<Cite src="oz-erc20-upgradeable-v570" /> Interfaces and libraries are not transpiled at all
— they are imported from the main package.<Cite src="oz-docs-upgradeable" />

**Subgoal 2 — move every state variable out of the sequential range.** This is the transformation
that exists. Five ordinary state variable declarations become one annotated struct plus a hard-coded
root slot plus a private accessor:

```solidity
/// @custom:storage-location erc7201:openzeppelin.storage.ERC20
struct ERC20Storage {
    mapping(address account => uint256) _balances;
    mapping(address account => mapping(address spender => uint256)) _allowances;
    uint256 _totalSupply;
    string _name;
    string _symbol;
}

// keccak256(abi.encode(uint256(keccak256("openzeppelin.storage.ERC20")) - 1)) & ~bytes32(uint256(0xff))
bytes32 private constant ERC20StorageLocation =
    0x52c63247e1f47db19d5ce0460030c497f067ca4cebf71ba98eeadabe20bace00;

function _getERC20Storage() private pure returns (ERC20Storage storage $) {
    assembly {
        $.slot := ERC20StorageLocation
    }
}
```

That is verbatim from v5.7.0, comment included.<Cite src="oz-erc20-upgradeable-v570" /> The
annotation and the derivation formula are ERC-7201's.<Cite src="eip-7201" /> The next lesson derives
that constant by hand and explains why the formula has two hashes in it; here, notice only that the
contract now declares **no state variables at all**, so the compiler assigns it no sequential slots.

**Subgoal 3 — turn the constructor into a pair of initializers.**

```solidity
// main package
constructor(string memory name_, string memory symbol_) {
    _name = name_;
    _symbol = symbol_;
}

// upgradeable package
function __ERC20_init(string memory name_, string memory symbol_) internal onlyInitializing {
    __ERC20_init_unchained(name_, symbol_);
}

function __ERC20_init_unchained(string memory name_, string memory symbol_) internal onlyInitializing {
    ERC20Storage storage $ = _getERC20Storage();
    $._name = name_;
    $._symbol = symbol_;
}
```

Two functions, not one, and the reason is the whole of the next section.<Cite src="oz-erc20-upgradeable-v570" />

**Subgoal 4 — route every access through the accessor.** Each function that touched a state variable
gains a `ERC20Storage storage $ = _getERC20Storage();` prologue, and every `_name` becomes `$._name`.
Mechanical, and it is why the upgradeable files read slightly worse than the originals.

**Subgoal 5 — rewrite imports across the package boundary.** Relative imports in the main package
become absolute imports of the main package: `import {IERC20} from "./IERC20.sol";` becomes
`import {IERC20} from "@openzeppelin/contracts/token/ERC20/IERC20.sol";`.<Cite src="oz-erc20-upgradeable-v570" />
That single edit is why the two packages must be installed together, and at the same version.

**Subgoal 6 — leave everything else alone.** Logic, modifiers, events, errors, NatSpec, the header
comment: untouched. If `ERC20.transfer` has a bug, `ERC20Upgradeable.transfer` has the same bug, in
the same release.

## Why there are two initializer functions

You already know that Solidity linearises constructors: write `contract C is A, B` and the compiler
calls `A`'s constructor then `B`'s then `C`'s, once each, in
[C3 order](/c/sol-c3-linearisation), whatever the inheritance diamond looks like.

An initializer is not a constructor. It is an ordinary internal function, and the compiler gives it
none of that. The documentation states the consequence directly: initializer functions are not
linearised by the compiler like constructors, so each `__Contract_init` embeds the linearised calls
to all of its parents' initializers — and as a result, calling two of these `init` functions can
initialise the same contract twice.<Cite src="oz-docs-upgradeable" />

That is what the `_unchained` split is for. `__ERC20_init` calls its parents and then does its own
work; `__ERC20_init_unchained` does *only* its own work. In a diamond, calling the `_init` forms of
two siblings runs a shared ancestor's initialiser twice; calling each `_unchained` form exactly once,
in the right order, does not. The documentation adds the honest caveat: doing this manually is not
recommended, and safety checks for it are a hope rather than a feature.<Cite src="oz-docs-upgradeable" />

`ContextUpgradeable` shows the shape at its most stripped-down. `Context` has no storage and does
nothing at construction, and its transpiled form still carries two empty stubs:

```solidity
abstract contract ContextUpgradeable is Initializable {
    function __Context_init() internal onlyInitializing {}
    function __Context_init_unchained() internal onlyInitializing {}
    // ...
}
```

Empty because there is nothing to do; present because a child's generated `_init` has to be able to
call its parents' uniformly.<Cite src="oz-context-upgradeable-v570" />

<Aside kind="warn">
The plugins enforce the initialiser rules you cannot see. They check for a missing initializer when
parent initializers need calling, for a parent initializer that is never called, and for one called
more than once — and they warn when parents are not called in linearised
order.<Cite src="oz-docs-writing-upgradeable" /> Reinitializers are excluded from validation by
default, because the tooling cannot tell whether one is meant for a new deployment.
</Aside>

## What is no longer transpiled, and the test for it

Running a file through the transpiler when it has no state and no constructor produces a copy. 5.5.0
stopped doing that, and the changelog splits the outcome into two categories that behave
differently.

**Removed outright.** `ERC721Holder`, `ERC1155Holder`, `ReentrancyGuard` and
`ReentrancyGuardTransient` were flagged as stateless and are no longer transpiled; the changelog lists
this under *Breaking changes* and tells you to import them from the main
package.<Cite src="oz-changelog" /> The files are simply gone:
`contracts/utils/ReentrancyGuardUpgradeable.sol` does not exist at
v5.7.0.<Cite src="oz-upgradeable-tree-570" />

**Kept as an alias.** `Initializable` and `UUPSUpgradeable` are no longer transpiled either, but the
changelog files them under *Deprecation*: aliases remain in the upgradeable package that redirect to
the main one, and they will be removed in the next major.<Cite src="oz-changelog" /> The alias is
exactly what it sounds like — the whole of `contracts/proxy/utils/Initializable.sol` in the
upgradeable package is a licence line, a pragma and one
import.<Cite src="oz-initializable-alias-v570" />

So the import that a thousand tutorials still show —
`import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol"` — resolves today and is
scheduled to stop.

What makes a contract "stateless" here is narrower than it sounds, and the library marks it
explicitly. `ReentrancyGuard` carries a `@custom:stateless` tag in its NatSpec, and it declares no
state variables: its lock lives at a fixed slot,
`0x9b779b17422d0df92223018b32b4d1fa46e071723d6817e2486d003becc55f00`, reached through `StorageSlot`,
and its other fields are `constant`.<Cite src="oz-reentrancyguard-v570" /> There is nothing for
subgoal 2 to relocate, so transpiling it produced a duplicate.

That test is not "has no storage" in the loose sense — `ReentrancyGuard` obviously uses a storage
slot. It is "declares no Solidity state variables", which is a property of the source text, and the
annotation makes the judgement reviewable instead of inferred.

<Answer>
**Import 1 resolves, and is deprecated.** `Initializable` is no longer transpiled, but an alias file
remains in the upgradeable package that re-exports the main package's
version.<Cite src="oz-changelog" /><Cite src="oz-initializable-alias-v570" /> It compiles today. It is
scheduled for removal in the next major, so this is a silent debt, not an error.

**Import 2 fails.** `ReentrancyGuardUpgradeable.sol` does not exist at v5.7.0 — it was removed in
5.5.0 when `ReentrancyGuard` was flagged stateless, and no alias was left
behind.<Cite src="oz-changelog" /><Cite src="oz-upgradeable-tree-570" /> The fix is a one-line import
change to `@openzeppelin/contracts/utils/ReentrancyGuard.sol`, and the contract inherits
`ReentrancyGuard` instead.

**Import 3 is fine.** `ERC20Upgradeable` has storage and a constructor to convert, so it is still
transpiled.<Cite src="oz-erc20-upgradeable-v570" />

**`__ERC20_init(...)` is correct** and stays.

**`__ReentrancyGuard_init()` disappears with the import.** The main package's `ReentrancyGuard` has no
initializer — it has a *constructor* that writes `NOT_ENTERED` to its fixed
slot.<Cite src="oz-reentrancyguard-v570" /> Behind a proxy that constructor never runs, so the
slot holds zero. That is not a bug: the guard's check asks whether the slot equals `ENTERED`, and
zero is not `ENTERED`, so an uninitialised guard reads as unlocked, which is the correct starting
state.

**The one worth stating out loud.** None of this touches the deployed proxy's storage, because
`ReentrancyGuard`'s slot was already a hard-coded constant in both packages. This is a
compile-and-import migration, not a layout migration — which is exactly the distinction the next
lesson is about, and getting the two confused is how live contracts die.
</Answer>

## What the transpiler does not do for your contracts

The transpiler runs over OpenZeppelin's files. Yours it never sees, and the same rules apply to them
unchanged.

**No constructor.** Move the setup into an `initialize` function guarded by the `initializer`
modifier, and call each parent's initialiser yourself — parents should use `onlyInitializing` rather
than `initializer`, because `initializer` can only fire once across the whole inheritance
chain.<Cite src="oz-docs-writing-upgradeable" />

**No initial values in field declarations.** `uint256 public x = 42;` is compiled as constructor
work, so behind a proxy the field is simply zero. Assign it in the initialiser instead. `constant`
declarations are fine, because the compiler reserves no slot and substitutes the expression at each
use.<Cite src="oz-docs-writing-upgradeable" />

**No `selfdestruct`, no `delegatecall`.** Anyone can call your implementation contract directly.
Normally that is harmless, because its own storage is never the storage your users touch. The
exception is destruction: a direct call that reaches `selfdestruct` leaves every proxy pointing at an
address with no code, and a `delegatecall` into an attacker-supplied contract gets there
indirectly.<Cite src="oz-docs-writing-upgradeable" />

**Disable the implementation's initialisers.** Call `_disableInitializers()` in the implementation's
own constructor — annotated `@custom:oz-upgrades-unsafe-allow constructor`, since a constructor is
otherwise a validation error.<Cite src="oz-docs-writing-upgradeable" /> Leaving it out is the
uninitialised-implementation footgun you have met before with
[clones](/c/clone-no-constructor). 5.6.0 closed the proxy half of it by making `ERC1967Proxy` revert
with `ERC1967ProxyUninitialized` when constructed without an initialize
call.<Cite src="oz-changelog" />

**A contract you `new` inside an upgradeable contract is not upgradeable.** Solidity handles that
creation directly; the plugins are not involved and no proxy is
deployed.<Cite src="oz-docs-writing-upgradeable" /> Inject the dependency as a constructor or
initialiser argument instead.

## Version lockstep, and how Foundry enforces it

Because the transpiler rewrites imports to point at `@openzeppelin/contracts`, an upgradeable project
compiles code from two packages at once. If they drift, you get a contract built against two
different releases' assumptions — and the compiler will not object, because both files are valid
Solidity.

The npm path handles this with a peer dependency and an installation line that names both
packages.<Cite src="oz-docs-upgradeable" /> The Foundry path handles it more bluntly, with remappings
that make the second package unreachable:

```text
@openzeppelin/contracts/=lib/openzeppelin-contracts-upgradeable/lib/openzeppelin-contracts/contracts/
@openzeppelin/contracts-upgradeable/=lib/openzeppelin-contracts-upgradeable/contracts/
```

Both prefixes resolve inside the `openzeppelin-contracts-upgradeable` submodule, using its own
transitive copy of `openzeppelin-contracts` at the same release. The README states the consequence:
any copy of `openzeppelin-contracts` you install separately is **not**
used.<Cite src="oz-foundry-upgrades" /> The remapping is also what makes Etherscan verification work,
because the verifier has to resolve the same paths you compiled against.

That is worth internalising as a pattern rather than a recipe. Two packages that must agree on a
version are a class of bug, and the fix is to make one of them structurally unreachable rather than
to rely on everybody reading the release notes.
