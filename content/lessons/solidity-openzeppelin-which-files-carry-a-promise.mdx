Install the library with Foundry and try this:

```solidity
import {ERC20Mock} from "@openzeppelin/contracts/mocks/token/ERC20Mock.sol";
```

It resolves. It compiles. Nothing warns you. And the file you just pulled into your build is one the
maintainers do not ship to npm at all, do not audit, and do not consider part of the
library.<Cite src="oz-package-json-v570" />

That is the problem this lesson solves. One npm package, one version number, one import prefix — and
underneath it, at least four different levels of promise, distinguishable only by where a file sits
in the tree and which tag you installed.

## Level 1: the audited library

At tag `v5.7.0` there are 368 Solidity files under `contracts/`, of which 248 are outside
`contracts/mocks/`.<Cite src="oz-contracts-tree-570" /> Those 248 are what the guarantees attach to,
and the guarantees are specific.

Semantic versioning here covers the API and the storage layout: minor and patch updates always
preserve storage layout compatibility, and major releases should be assumed
incompatible.<Cite src="oz-docs-backwards-compatibility" />

Security patches follow a published matrix.<Cite src="oz-security-policy" />

| Version | Critical fixes | Other security fixes |
|---|---|---|
| 5.x | yes | yes |
| 4.9 | yes | no |
| 3.4 | yes | no |
| 2.5 and below | no | no |

Two details in that policy do more work than the table. First, fixes land only in the **latest minor
of a given major** — a bug affecting 4.6 through 4.8 is patched in 4.8.1, not in
4.6.1.<Cite src="oz-security-policy" /> Staying on an old minor of a supported major is not the safe
conservative choice it looks like; it is opting out. Second, only *critical* severity fixes are
backported to past majors at all.

And running `npm install` without a tag puts you on `latest`, which is the audited channel and today
means 5.6.1 rather than 5.7.0.<Cite src="oz-repo-readme" /><Cite src="oz-npm-contracts" />

## Level 2: draft-

The maintainers state the rule in one sentence: there is **no** backwards compatibility guarantee for
content in files prefixed `draft`.<Cite src="oz-docs-backwards-compatibility" /> The stated reason is
that ERCs which are not Final can change incompatibly, so implementations that may have to break are
named to make that condition explicit.

At v5.7.0 there are 18 such files under `contracts/`.<Cite src="oz-contracts-tree-570" /> Here is
what several of them track, with the EIP status as published:

| File | Standard | Status |
|---|---|---|
| `interfaces/draft-IERC1822.sol` | ERC-1822 (UUPS) | Stagnant<Cite src="eip-1822" /> |
| `interfaces/draft-IERC6093.sol` | ERC-6093 (token errors) | Final<Cite src="eip-6093" /> |
| `interfaces/draft-IERC7786.sol` | ERC-7786 (crosschain gateway) | Final<Cite src="eip-7786" /> |
| `interfaces/draft-IERC7579.sol` | ERC-7579 (modular accounts) | Draft<Cite src="erc-7579" /> |
| `token/ERC20/extensions/draft-ERC3009.sol` | ERC-3009 | Draft<Cite src="eip-3009" /> |
| `interfaces/draft-IERC7802.sol` | ERC-7802 | Draft<Cite src="eip-7802" /> |
| `utils/draft-InteroperableAddress.sol` | ERC-7930 | Review<Cite src="eip-7930" /> |

Look at rows two and three. ERC-6093 and ERC-7786 are Final, and the files still carry the prefix.
The prefix is maintained by hand and **lags** finalisation, because removing it renames a file and
therefore breaks every import of it — a change that can only ship in a release with a breaking-changes
section. 5.5.0 spent one on `ERC6909` when ERC-6909 finalised; 5.7.0 spent another on `ERC4337Utils`
and `IERC4337`.<Cite src="oz-changelog" /><Cite src="eip-6909" />

Row one is the more interesting one. `draft-IERC1822.sol` is the UUPS interface — the pattern behind
a large fraction of upgradeable contracts in production — and ERC-1822 is **Stagnant**: it never
reached Final and is no longer being progressed.<Cite src="eip-1822" /> The prefix is doing exactly
its job there, and it has been doing it for years.

The rule also runs in the other direction, which is easy to miss. The docs say standards with
widespread adoption and strong community expectations of stability may be treated as de-facto
finalised and published **without** the prefix.<Cite src="oz-docs-backwards-compatibility" /> So the
prefix is neither necessary nor sufficient as a status signal. It is a conservative marker of the
maintainers' own confidence, and the thing to read alongside it is the EIP's status page.

## Level 3: mocks

`package.json` publishes `/contracts/**/*.sol` and explicitly excludes
`/contracts/mocks/**/*`.<Cite src="oz-package-json-v570" /> The 120 files under `contracts/mocks/` exist to
be compiled by the project's own test suite and nothing else.<Cite src="oz-contracts-tree-570" />

The trap is that the two common install paths disagree about whether they exist.

- `npm install @openzeppelin/contracts` — mocks absent. An import of one fails to resolve.
- `forge install OpenZeppelin/openzeppelin-contracts` — adds the whole git repository as a
  submodule. Mocks present, and importable through the same `@openzeppelin/contracts/` remapping as
  everything else.

So a Foundry project can import a mock, compile, test and deploy. The same source handed to a
teammate on a Hardhat toolchain, or to a verification service resolving from npm, does not build.
That is a genuinely confusing failure, because the error is "file not found" for a file that is
plainly there on your disk.

Worth being precise about the risk: mocks are not malicious and they are not backdoored. They are
*test doubles* — deliberately permissive, written to exercise a code path rather than to be safe.
`contracts/mocks/token/ERC20Mock.sol` is fifteen lines, and this is all of the interesting
part:<Cite src="oz-erc20mock-v570" />

```solidity
contract ERC20Mock is ERC20 {
    constructor() ERC20("ERC20Mock", "E20M") {}

    function mint(address account, uint256 amount) external {
        _mint(account, amount);
    }

    function burn(address account, uint256 amount) external {
        _burn(account, amount);
    }
}
```

Both functions are `external` with no authorisation of any kind. Anyone can mint to any address, and
anyone can burn from any address. That is correct for a test fixture and it is a total loss of the
token in production. Shipping one is not a subtle bug.

### The documentation's own examples live there too

There is a subdirectory that catches people who never go near `mocks/` deliberately:
`contracts/mocks/docs/`. It holds the example contracts the documentation site
renders — `MyNFT.sol`, `governance/MyGovernor.sol`, `ERC4626Fees.sol`,
`access-control/AccessControlERC20MintOnlyRole.sol` and about thirty
others.<Cite src="oz-contracts-tree-570" />

They are examples, and they are inside the tree that never ships. One of them is named
`AccessControlERC20MintMissing.sol`, which tells you what kind of examples these are: the file exists
so the access-control guide can show a version with the check **missing** and then show the fixed
one.<Cite src="oz-contracts-tree-570" /> If you lift a snippet from the docs site, you are copying
code whose purpose is pedagogical — sometimes deliberately wrong — from the tier the maintainers
excluded from the package. That is fine, as long as you know that is what you did.

## Level 4: community-contracts

There is a fourth surface most people never see, and its own README is unusually blunt about what it
is: community-curated and experimental code, not audited, and — unless explicitly stated otherwise —
**not** covered by the OpenZeppelin bug bounty.<Cite src="oz-community-contracts" /> The maintainers
say they review submissions enough to keep out obviously malicious code, and that anything taken from
the repository should be audited before production use.<Cite src="oz-community-contracts" />

It is also not on npm at all; you install it from git.<Cite src="oz-community-contracts" /> That is a
useful accident, and the only one of the four tiers where the distribution channel itself signals
the level.

What lives there is worth knowing, because the boundary moves. The repository describes itself as
holding extensions and modules compatible with the main package, alternative implementations of
interfaces defined there, third-party integrations, community-built contracts, and general
prototypes.<Cite src="oz-community-contracts" /> That is a staging area by design: things get tried
there. Using something from it is not reckless — the maintainers' own instruction is to have it
audited before production.<Cite src="oz-community-contracts" /> Using it without knowing it carries
no audit, no compatibility promise and no bounty is.

## The safe defaults, and what the phrase means

Against all of that, there is a working set most systems should stay inside: `ERC20`, `ERC721`,
`ERC1155`; `Ownable` and `Ownable2Step`; `AccessControl`; `Pausable`; `ReentrancyGuard` and
`ReentrancyGuardTransient`; `SafeERC20`; `Clones`; `MerkleProof`; `ECDSA` and `EIP712`; `SafeCast`;
`Address`.<Cite src="oz-docs-access-api" /><Cite src="oz-docs-proxy-api" />

What makes them defaults is not that they are blessed and the rest is dangerous. It is a
conjunction of three properties: they are simple enough to read in one sitting, they have been
deployed enough times that their edge cases have been found by somebody else, and they are hard to
hold wrongly. That is the same argument you would make for any dependency.

The rule that follows is about justification, not prohibition. Reaching outside the set — a Governor
extension, a `draft-` file, a crosschain bridge — is a normal thing to do and should come with a
reason you could say out loud in a review: *why this contract, what changes if it breaks, and who
reads the changelog for it.* The failure mode is not using an unusual contract. It is using one
because the Wizard emitted it or an example used it, and never noticing it sits on a different tier.

<Check type="spot-bug" concept="oz-draft-contracts">
A team ships a token. Their Foundry build is green, their tests pass, `forge coverage` looks fine.
Three things in their repository will cause trouble later. Find them, and say when each one surfaces.

```solidity
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {ERC20Mock} from "@openzeppelin/contracts/mocks/token/ERC20Mock.sol";
import {ERC3009} from "@openzeppelin/contracts/token/ERC20/extensions/draft-ERC3009.sol";

contract Reward is ERC20, ERC3009 { /* ... */ }

contract Bootstrap {
    ERC20Mock public immutable seed = new ERC20Mock();
}
```

Their `foundry.toml` pins nothing: the dependency was added with `forge install` and a `forge update`
runs in CI.

<Answer>
**1 — `ERC20Mock` is in production code, not in `test/`.** It compiles because `forge install` puts
the entire repository on disk, including the 120 files under `contracts/mocks/` that npm never
publishes.<Cite src="oz-package-json-v570" /><Cite src="oz-contracts-tree-570" /> Two failures follow: the
project stops building for anyone resolving from npm, and — much worse — `Bootstrap` deploys a test
double whose mint function exists to make tests convenient. Surfaces the moment a teammate on a
different toolchain builds it, or the moment somebody reads `ERC20Mock`.

**2 — `ERC3009` is a `draft-` file.** ERC-3009 is still Draft, and the docs state there is no
backwards compatibility guarantee for anything in a `draft-` prefixed
file.<Cite src="eip-3009" /><Cite src="oz-docs-backwards-compatibility" /> Two distinct future
events: the ERC changes and the implementation changes with it, or the ERC finalises and the prefix
is removed, which renames the file and breaks the import. The second is the *good* outcome, because
the compiler tells you. Surfaces on a minor bump.

**3 — `forge update` in CI.** Foundry installs a specific version first and then subsequent
`forge update` commands move the submodule to `master`, which the README warns against because
`master` is a development branch outside the release process's security
measures.<Cite src="oz-repo-readme" /> Their build is not reproducible and their dependency is not
versioned. Surfaces as an unexplained CI failure, or never — which is worse, because it means they
shipped whatever was on `master` that morning.

**What is fine.** Inheriting `ERC3009` at all. Composing a draft-tracking extension is a legitimate
choice; it just needs to be a choice somebody made on purpose, with a note about who watches that
ERC.
</Answer>
</Check>

## Where this pays off

**The upgradeable package** is the next lesson, and it is a fifth surface with its own rules: a
separate npm package, generated rather than written, that must move in lockstep with this one.

**Lesson 7** returns to the audit index you saw in passing here and reads it properly — because the
scope column of that table says something about your contract that the word "audited" does not.

**Immediately.** Two greps are worth running against any repository you inherit: one for
`contracts/mocks`, one for `draft-`. Both are seconds of work, both are usually clean, and when they
are not you have found something the build was never going to tell you.
