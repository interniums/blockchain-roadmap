The previous lesson ended on a team who moved their implementation pointer from slot 0 to slot 1 and
changed nothing. Slot 2 would not have helped either, nor slot 1000: an implementation with a
thousand and one state variables reaches it, and an implementation with a `uint256[2000]` array
reaches it on the first element.

Any slot you can name by counting is a slot the compiler can reach by counting. The fix is to stop
counting.

## Three constants

EIP-1967 fixes the proxy's own state at slots derived by hashing a namespaced string and subtracting
one.<Cite src="eip-1967" />

```text
implementation
  bytes32(uint256(keccak256('eip1967.proxy.implementation')) - 1)
  0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc

admin
  bytes32(uint256(keccak256('eip1967.proxy.admin')) - 1)
  0xb53127684a568b3173ae13b9f8a6016e243e63b6e8ee1178d6a717850b5d6103

beacon
  bytes32(uint256(keccak256('eip1967.proxy.beacon')) - 1)
  0xa3f0ad74e5423aebfd80d3ef4346578335a9a72aeaee59ff6cb3582b35133d50
```

These are not magic numbers, and you should never copy them from a blog post. Derive them:

```bash
cast keccak "eip1967.proxy.implementation"
# 0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbd
#                                                                 ^ subtract one
```

The hash ends `bbd`; the constant ends `bbc`. That is the whole derivation. The same three constants
appear verbatim in OpenZeppelin's `ERC1967Utils` as `IMPLEMENTATION_SLOT`, `ADMIN_SLOT` and
`BEACON_SLOT`.<Cite src="oz-src-erc1967utils" />

Because these are raw slot numbers rather than declared variables, the proxy reaches them through
`StorageSlot`, which is a thin `assembly { r.slot := slot }` wrapper — there is no way to declare a
Solidity variable *at* an arbitrary slot in the ordinary syntax, so the standard is implemented in
assembly by everyone who implements it.<Cite src="oz-src-erc1967utils" />

## Why sequential assignment cannot get there

Solidity assigns storage to declared variables starting at slot 0 and running contiguously through
the state variables, in linearized inheritance order, packing where types allow.<Cite
src="solidity-docs-storage-layout" /> The implementation slot is roughly `2.4 × 10^76`. Reaching it
by declaration would require that many preceding variables, which is not a bound anyone needs to
argue about carefully.

The two indirect derivations are the ones worth checking, because they *do* land on large numbers:

- A dynamic array declared at slot `p` puts its elements starting at `keccak256(p)`, running
  contiguously.<Cite src="solidity-docs-storage-layout" />
- A mapping declared at slot `p` puts the value for key `k` at `keccak256(h(k) . p)`, where `h`
  pads value-type keys to 32 bytes and passes byte arrays through
  unpadded.<Cite src="solidity-docs-storage-layout" />

Both compute a slot as `keccak256` of something. So the question is not "can a variable be numbered
that high" but "can anyone *produce* a preimage that hashes into the neighbourhood of these
constants". And that is where the subtraction earns its place.

## What the minus one actually buys

The specification's stated reason is one clause: a `-1` offset is added so the preimage of the hash
cannot be known, further reducing the chances of a possible attack.<Cite src="eip-1967" />

ERC-7201, written four years later and reusing the same trick, puts the same idea more precisely:
the `-1` term targets a location that is unused by Solidity.<Cite src="eip-7201" /> That is the
claim to hold on to. Every slot Solidity itself can assign is either a small integer, or
`keccak256(x)` for some `x` the program produced, or a small offset from one of those. The value
`keccak256(s) - 1` is not the keccak image of anything anyone can exhibit — exhibiting one would be
a preimage attack on keccak256.

Be careful about how much this proves. It does not mean an attacker was ever able to steer a
mapping onto `keccak256('eip1967.proxy.implementation')` had the subtraction been omitted: that
string is 28 bytes, while Solidity's array derivation hashes exactly 32 bytes and its mapping
derivation hashes 64, so the shapes do not line up in the first place. The subtraction is
defence in depth against derivations *outside* Solidity's own rules — hand-written assembly,
another language's layout, a future scheme — not the repair of a specific known break. The
specification says "further reducing the chances", and that hedged phrasing is accurate.

<Aside kind="note">
ERC-1822, the standard that named the UUPS pattern, made the earlier choice: it stores the
implementation at `keccak256("PROXIABLE")` with no subtraction, which is
`0xc5f16f0fcc639fa48a6947836d9850f504798523bf8c9a3a87d5876cf622bcf7`.<Cite src="eip-1822" /> It is
also still marked **Stagnant**, and OpenZeppelin's UUPS implementation does not use its slot — it
keeps ERC-1822's compatibility *check* while pointing at ERC-1967's *slot*.<Cite src="eip-1822" />
That splice is the subject of the next lesson.
</Aside>

## Choosing the slot is half of it; writing it is where the checks live

Putting the pointer somewhere unreachable stops the implementation from clobbering it by accident.
It does nothing about the pointer being set to something wrong on purpose, or by a typo in a deploy
script. Those checks have to be written, and it is worth reading which ones OpenZeppelin considered
worth spending gas on.<Cite src="oz-src-erc1967utils" />

- **`_setImplementation` reverts `ERC1967InvalidImplementation` if the new address has no code.**
  This is the direct guard against the failure mode from the previous lesson, and against the more
  common version of it: an address that is right in the deploy script and wrong on this chain.
  Without it the proxy would silently become a contract that succeeds at everything and does
  nothing.<Cite src="oz-src-erc1967utils" />
- **`_setAdmin` reverts `ERC1967InvalidAdmin` if the new admin is `address(0)`.** Renouncing by
  zeroing the admin slot is a plausible-looking way to make a contract "immutable" and a very
  effective way to make it unadministrable. The library refuses.<Cite src="oz-src-erc1967utils" />
- **`_setBeacon` checks twice.** The beacon address must have code, *and* the implementation the
  beacon returns must have code — because for a beacon proxy the address that actually executes is
  one indirection further away, and a beacon that answers with a dead address brings down every
  proxy pointing at it.<Cite src="oz-src-erc1967utils" />

Notice what none of these check: whether the new implementation's storage layout is compatible with
what is already in the proxy. No on-chain check can, because the layout is compiler metadata that
never reaches the chain. That gap is the subject of the last lesson in this module.

## Reading a proxy from the outside

The practical payoff of standardising the numbers is that a proxy becomes legible without its ABI,
its source, or any cooperation from its author. The implementation address is one `eth_getStorageAt`
away, and OpenZeppelin's own documentation points clients at exactly that
call.<Cite src="oz-src-erc1967utils" />

```bash
cast storage <proxy> \
  0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc
# 0x000000000000000000000000<20-byte implementation address>
```

The slot holds a full 32-byte word with the address right-aligned in the low 20 bytes, because that
is how `address` is stored.<Cite src="solidity-docs-storage-layout" /> Reading it costs the caller
nothing off-chain; on-chain it is a single `SLOAD`, 2,100 gas cold and 100
warm.<Cite src="measured-gas-constants" />

This is why "Read as Proxy" exists on every explorer, why a verification service can overlay the
implementation's ABI onto the proxy's address, and why proxy-detection tooling can classify
contracts at scale without source. It is also why an upgrade is *visible*: the standard specifies
`Upgraded(address indexed implementation)`, `AdminChanged(address previousAdmin, address newAdmin)`
and `BeaconUpgraded(address indexed beacon)`, and says any function that changes one of these slots
SHOULD emit the corresponding event.<Cite src="eip-1967" />

<Aside kind="warn">
"SHOULD emit" is not "does emit", and the slot is the ground truth, not the log. In OpenZeppelin's
v5 line, `TransparentUpgradeableProxy` keeps its admin in an **immutable** and writes the ERC-1967
admin slot once at construction purely for compatibility — the source notes that the implementation
behind the proxy can still overwrite that slot, leaving the recorded admin different from the actual
one.<Cite src="oz-src-transparent-proxy" /> `BeaconProxy` does the same with the beacon
slot.<Cite src="oz-src-beacon-proxy" /> If you are building monitoring, alert on the slot values,
and treat the events as a convenience index rather than as the record.
</Aside>

You are writing a monitoring service that must answer, for an arbitrary address, "is this a proxy,
and what is it pointing at right now?" You decide to read the three ERC-1967 slots on every contract
you index.

For each of the following, say what your service concludes and whether it is right:

1. All three slots are zero.
2. The implementation slot holds an address; the beacon slot is zero.
3. The beacon slot holds an address; the implementation slot is zero.
4. The implementation slot holds `0x000000000000000000000000000000000000000000000000000000000003e8`.

<Answer>
**1 — All zero.** Your service concludes "not an ERC-1967 proxy". Correct as far as it goes, and
insufficient as a conclusion. It is not evidence of immutability. EIP-1167 minimal proxies hard-code
their target in bytecode with no storage at all, ERC-2535 diamonds keep a
selector-to-facet mapping, and anyone is free to write a delegating fallback that reads a slot they
invented. "No ERC-1967 slots" means "not this standard", not "not upgradeable".

**2 — Implementation set, beacon zero.** A transparent or UUPS proxy. Correct. You cannot yet tell
which — that distinction is not in the slots, it is in where the upgrade function lives, and it is
the next lesson's subject.

**3 — Beacon set, implementation zero.** A beacon proxy. Correct, and it changes what you have to
monitor: the address this proxy runs is not in this proxy's storage at all. It is whatever the
beacon returns *right now*. To watch this contract for logic changes you must watch a different
account, and one upgrade there moves every proxy pointing at it at once.

**4 — Implementation is `0x...03e8`.** Your service reports the implementation as address 1000.
Mechanically correct, and it is the signal from the previous lesson: an implementation write has
landed on the pointer. There is no code at that address, so every call now succeeds returning empty
data. A monitoring service that checks `eth_getCode(implementation).length != 0` catches this
instantly; one that only records the address does not. This check is cheap and worth having, because
the same read protects you against a legitimate-looking upgrade to an address that was never
deployed — a mistake OpenZeppelin now rejects on-chain with
`ERC1967InvalidImplementation`.<Cite src="oz-src-erc1967utils" />
</Answer>
</Check>

## The half it does not solve

Here is the sentence to carry out of this lesson, because it is the one that the module's case study
turns on.

<Misconception
  belief="ERC-1967 makes storage collisions impossible."
  reality="It removes collisions between the proxy's own state and the implementation's state. Collisions between one implementation and the next implementation you deploy are untouched, because both of them still number their variables from slot 0 into the same shared storage."
  why="The standard is introduced as the solution to 'the storage collision problem', which is true of one of the two problems. The one it solves is the one that bites on day one; the one it leaves open is the one that bites on release four."
  src="oz-issue-6362"
/>

Two contracts share the proxy's storage across an upgrade, and the compiler cannot compare them
because they are, again, separate compilations — this time separated in time as well as in file.
The upgrade documentation's rules for what you may change are consequently a list of prohibitions
with no enforcement behind them: do not reorder state variables, do not change their types, do not
remove them, do not insert new ones before existing ones. Append at the
end.<Cite src="oz-upgrades-proxy-pattern" />

That discipline has to be maintained by hand, across every base contract in your inheritance tree,
by every engineer who ever touches the repository, forever. Two mechanisms exist to make it
mechanical rather than heroic — reserved gap arrays and ERC-7201 namespaces — and the last lesson in
this module is about what happened to a live contract that moved from one to the other.

## Where this pays off

**Immediately**: three constants you can derive from memory and read off any chain, and a reason to
distrust upgrade events in favour of slot reads.

**Next lesson**: ERC-1967 says where the pointer lives and says nothing about who is allowed to
change it. Transparent, UUPS and beacon are three answers to that question, and they differ in
per-call cost, in blast radius, and in which failures are recoverable.

**Two lessons on**: the `admin` slot's real subject is authorisation, and the moment the upgrade
function moves into the implementation, the ability to upgrade becomes something you have to
re-ship, correctly, every single time.
