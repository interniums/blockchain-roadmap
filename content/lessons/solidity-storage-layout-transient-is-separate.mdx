Six declarations, three of them `transient`, deliberately interleaved:

```solidity
contract Mixed {
    uint256 a;
    bool    transient locked;
    address owner;
    uint96  transient tally;
    uint256 b;
    address transient caller;
}
```

Ask `solc` for both layouts and you get two documents, each numbered from zero:

`a`, `owner` and `b` occupy slots 0, 1 and 2 exactly as though the three `transient` declarations were
not in the file. And the transient variables start their own numbering at 0, pack against each other,
and are entirely unaffected by what the persistent ones are doing.

You already know [what transient storage *is*](/c/transient-storage-middle-tier) — a per-contract
key-value store reached by `TSTORE` and `TLOAD`, discarded at the end of the
transaction.<Cite src="eip-1153" /> This lesson is the narrower question the previous three have
prepared you to ask: given a second slot-numbered address space, what does the *compiler* do with it?

## Two address spaces, one namespace

The documentation is unusually direct. The layout rules described for storage apply to both storage and
transient storage; the layouts are completely independent and do not interfere with each other's
variable locations; storage and transient state variables can therefore be safely interleaved without
any side effects.<Cite src="solidity-docs-storage-layout" /> The language reference says it the other
way round: the order of transient state variables does not affect the layout of storage state
variables and vice versa.<Cite src="solidity-docs-contracts" />

That independence has a limit. Two *layouts*, but **one namespace** — all state variables share it, so
a transient and a persistent variable still need distinct
names.<Cite src="solidity-docs-contracts" /> The separation is in where the bytes go, not in what you
may call them.

One more piece of independence, easy to miss: the `layout at` specifier from the previous lesson moves
every storage variable in an inheritance tree and **does not affect transient state
variables**.<Cite src="solidity-docs-contracts" /> A contract with `layout at 42` has its storage
starting at slot 42 and its transient storage still starting at slot 0.

## The packing rules apply, unchanged

Values in transient storage are packed in the same fashion as those in persistent
storage.<Cite src="solidity-docs-contracts" /> Not "similarly" — the same five rules, the same cursor,
the same lower-order alignment.

The `Mixed` layout above proves all of it in three variables.

**Subgoal — watch the cursor start.** `bool locked` needs 1 byte and lands at transient `(0, 0)`.
Cursor to `(0, 1)`, 31 bytes remaining.

**Subgoal — watch a narrow variable pack.** `uint96 tally` needs 12 bytes and 31 remain, so it packs
into the same slot at `(0, 1)`. Cursor to `(0, 13)`, 19 bytes remaining.

**Subgoal — watch rule 3 fire in the transient space.** `address caller` needs 20 bytes and 19 remain.
It does not fit, so it starts transient slot 1 — leaving 19 bytes at the top of transient slot 0
permanently unused, exactly as they would be in persistent storage.

Which means the declaration-order lesson transfers wholesale, canonical pair and all. Three transient
variables declared `uint128, uint128, uint256` occupy two transient slots; the same three declared
`uint128, uint256, uint128` occupy three.<Cite src="solidity-docs-storage-layout" />

What does not transfer is the size of the prize. A `TSTORE` costs 100 gas flat, with no cold tier and
no 20,000 first-write charge, so a transient slot you save is worth two orders of magnitude less than a
persistent one.<Cite src="measured-gas-constants" /><Cite src="eip-1153" /> Reordering transient
declarations for slot count is real but rarely the highest-value change on the page. The *rules* are
identical; only the stakes have changed.

## One encoding, not four

Here is the part that actually constrains designs.

Only value types are supported for transient storage.<Cite src="solidity-docs-storage-layout" /> The
language reference is more explicit: `transient` as a data location is currently allowed only for
value-typed state variable declarations, and reference types — arrays, mappings and structs — as well
as local and parameter variables are not yet supported.<Cite src="solidity-docs-contracts" /> The
compiler says so plainly:

```text
Error: Transient data location is only supported for value types.
```

Read that against the four encodings from the previous lesson. Persistent storage has `inplace`,
`mapping`, `dynamic_array` and `bytes`.<Cite src="solidity-docs-storage-layout" /> Transient storage,
at the language level, has only the first.

The irony is worth naming. EIP-1153 deliberately gave transient storage a word-addressed,
storage-like interface *because* transaction-scoped state is often needed under arbitrary keys —
its worked example is a temporary approval keyed on an owner-and-spender pair, and it argues that
mappings are difficult to implement over linear memory.<Cite src="eip-1153" /> The address space was
designed for mappings. The language does not yet expose them, so the mapping-shaped uses of transient
storage are written in inline assembly against `tstore` and `tload` directly, deriving the key
yourself — which, after the previous lesson, you can do.

Four further restrictions follow from the lifetime rather than the layout, and each one has bitten
someone.

**No in-place initialization.** A transient variable cannot be assigned at its declaration, because
the value would be cleared at the end of the creation transaction, making the initialization
ineffective.<Cite src="solidity-docs-contracts" /> `uint256 transient z = 5;` is a compile error, not
a warning.

**`constant` and `immutable` conflict with it**, since their values are inlined or stored in
code.<Cite src="solidity-docs-contracts" />

**Mutability enforcement is the same as persistent storage.** Transient storage is part of the EVM
state, so any read of it is not `pure` and any write is not
`view`.<Cite src="solidity-docs-contracts" />

**Libraries can only reach it through inline assembly.** References to transient storage variables are
not supported, so they cannot be passed into library calls — which also means the
[storage-pointer](/c/sol-storage-pointer-hazard) idioms you use for persistent state have no transient
counterpart yet.<Cite src="solidity-docs-contracts" />

## Getting the layout out of the toolchain

`transient` reached the parser in Solidity 0.8.27, along with a `--transient-storage-layout` output on
the command line and a `transientStorageLayout` artifact in Standard JSON; value-typed transient state
variables became fully supported in 0.8.28.<Cite src="solidity-changelog" />

Two gaps to know about before you go looking. In Foundry 1.7.1, `forge inspect` accepts
`storageLayout` and has no transient counterpart — the field is not in its
list.<Cite src="foundry-forge-inspect" /> For transient layouts, go to `solc` directly.

The second gap is more fundamental. `cast storage` and `eth_getStorageAt` read *state*, and transient
storage is discarded at the end of the transaction and never becomes
state.<Cite src="eip-1153" /><Cite src="execution-apis" /> There is nothing to query afterwards. You
observe it *during* execution, with a trace or a test, or not at all — which removes the debugging
technique the last three lessons leaned on.

<Aside kind="stop">
**Pin at least 0.8.34 before shipping any `transient` state variable.** Solidity 0.8.34, released 18
February 2026, lists as an Important Bugfix a Yul IR code generation defect that "could result in
clearing a storage variable instead of a transient storage variable at the same position in the layout
(and vice-versa)."<Cite src="solidity-changelog" /> The compiler's known-bugs list carries it as
SOL-2026-1, `TransientStorageClearingHelperCollision`, rated **high**
severity.<Cite src="solidity-known-bugs" /><Cite src="solidity-transient-clearing-bug" />

Notice that this is a *layout* bug, and the exact bug this lesson's opening rules invite. Two address
spaces numbered independently means slot 0 is a legal address in both, and a code generator that names
its helper functions after positions rather than after positions-plus-space will collide. It was
introduced in 0.8.28 — the release that made transient state variables fully supported — and fixed in
0.8.34.<Cite src="solidity-known-bugs" /><Cite src="solidity-changelog" /> The two independent layouts
are not free; someone had to keep them apart in the generated code, and for six releases they were
not.
</Aside>

Given this contract, answer four questions before compiling.

```solidity
contract Router layout at 1000 {
    address owner;
    bool    transient entered;
    uint256 fee;
    address transient unlocker;
    uint64  transient depth;
}
```

1. What slot does `fee` occupy?
2. What are the transient `(slot, offset)` pairs?
3. `unlocker` and `depth` together need 28 bytes. Do they share a transient slot?
4. Which of these compiles: `mapping(address => bool) transient seen;`,
   `uint256 transient counter = 0;`, `function peek() external view returns (bool) { return entered; }`?

<Answer>
**1 — `fee` is at slot 1001.** `layout at 1000` shifts every storage variable in the tree, so `owner`
takes slot 1000 and `fee` takes 1001.<Cite src="solidity-docs-contracts" /> The `transient entered`
declaration between them consumes no storage slot at all — the persistent cursor never sees it.

**2 — the transient layout starts at 0 regardless.** `layout at` does not affect transient state
variables.<Cite src="solidity-docs-contracts" />

- `entered` — `(0, 0)`, 1 byte. Cursor to `(0, 1)`, 31 remaining.
- `unlocker` — 20 bytes into 31 remaining, so `(0, 1)`. Cursor to `(0, 21)`, 11 remaining.
- `depth` — `uint64`, 8 bytes into 11 remaining, so `(0, 21)`.

All three fit in transient slot 0, with 3 bytes spare.

**3 — yes, and the question is a trap worth having fallen into.** 28 bytes is what `unlocker` and
`depth` need *together*, but the slot already contains `entered`, so the real test is 20 into 31 and
then 8 into 11. Both pass. Had `entered` been a `uint96` instead of a `bool`, `depth` would have had
only 4 bytes to work with and would have started transient slot 1. The packing question is never "do
these two fit in 32 bytes" — it is always "does each one fit in what is left when the cursor reaches
it".

**4 — only the third compiles.**

- `mapping(address => bool) transient seen;` fails: transient data location is only supported for
  value types.<Cite src="solidity-docs-contracts" />
- `uint256 transient counter = 0;` fails: initialization of transient storage state variables is not
  supported, because the value would be cleared at the end of the creation
  transaction.<Cite src="solidity-docs-contracts" />
- The `view` getter compiles. Transient storage is subject to the same mutability rules as persistent
  storage, so *reading* it is not `pure` but is fine in a `view`
  function.<Cite src="solidity-docs-contracts" /> Writing it would not be — and `TSTORE` in a static
  context raises an exception at runtime as well.<Cite src="eip-1153" />
</Answer>
</Check>

## Where this pays off

**Reentrancy guards** are the canonical use, and now you know the shape of the variable that holds
one: a single `bool transient`, at transient slot 0, packing with whatever else you declare beside it.
The measured overhead is about 284 gas against a persistent-storage guard whose cost is
cold/warm-dependent and ranges from roughly 3,100 to 7,100 — a range rather than a number, and
every single figure in circulation for the storage guard is wrong for some slot
state.<Cite src="measured-gas-constants" />

**Proxies and namespaced storage** inherit the two-space problem directly. A `delegatecall` gives
borrowed code your transient storage under the same ownership rules as your persistent
storage,<Cite src="eip-1153" /> so an implementation and a proxy that disagree about transient slot 0
collide exactly the way they would about storage slot 0 — with no `eth_getStorageAt` to catch it after
the fact.

**Flash accounting** in the DeFi track is the largest production use of this address space, and it is
built on the part the language does not expose: arbitrary keys, derived by hand in assembly, using the
derivation from the previous lesson.<Cite src="eip-1153" />

**Version pinning** in the toolchain track stops being hygiene here. `transient` at the language level
dates from 0.8.27 and 0.8.28 and has already produced one high-severity layout
bug.<Cite src="solidity-changelog" /><Cite src="solidity-known-bugs" /> The correct posture is a pinned
`solc` plus a pass over the known-bugs list, not a caret range.
