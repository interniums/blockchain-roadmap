Six state variables:

```solidity
contract VaultA {
    address owner;
    uint64  lastUpdate;
    bool    paused;
    uint256 totalAssets;
    uint128 feeBps;
    uint128 cap;
}
```

You deploy it, ask the node for slot 0 of the deployed address, and get back one word:

```text
0x00000001000000006a8f7e00f39fd6e51aad88f6f4ce6ab8827279cfffb92266
```

Three of those six variables are in there. `owner` is the low twenty bytes, `lastUpdate` sits above
it, `paused` above that. Nothing in the source said this would happen, and nothing in the source
would have to change for it to stop happening.

You already know what storage *is*: a [key-value map from 256-bit slot numbers to 32-byte
words](/c/state-as-keyvalue), where [a slot never written reads as zero and occupies
nothing](/c/zero-slot-is-absent). That is the machine's half. This module is the compiler's half —
which of your names ends up at which number, and why that assignment is a decision with consequences
rather than a bookkeeping detail.

## The compiler is filling in a map, in one pass

The rule is short enough to state in full. Except for dynamically sized arrays and mappings, data is
stored contiguously item after item starting with the first state variable, which is stored in slot
0; for each variable a size in bytes is determined according to its
type.<Cite src="solidity-docs-storage-layout" />

Two phrases in that sentence are doing the work.

**"Starting with the first."** Numbering begins at 0 and walks forward in declaration order. The
compiler does not sort, group or optimise — the next lesson is entirely about that.

**"A size in bytes."** Not a size in slots. A `bool` is one byte, an `address` is twenty, a `uint64`
is eight.<Cite src="solidity-docs-storage-layout" /> That is the opening the packing rules walk
through.

And note what is *not* here: no gap, no header, no allocation table, no allocation step. Nothing on
chain records that your contract has six variables or what they are called. Storage is not memory —
you are not asking for space, you are choosing coordinates in a space that is already, notionally,
all there and all zero.

## Reading the map, from outside and from the artifact

Two commands will check every claim in this module in about four seconds.

**The compiler's answer.** `forge inspect <Contract> storageLayout` prints the layout the compiler
computed; `storageLayout` is one of the artifact fields `forge inspect` accepts in Foundry
1.7.1.<Cite src="foundry-forge-inspect" /> From `solc` directly it is `--storage-layout`, or the
`storageLayout` artifact in Standard JSON.<Cite src="solidity-docs-storage-layout" /> For the vault
above:

```text
| Name        | Type    | Slot | Offset | Bytes |
| owner       | address | 0    | 0      | 20    |
| lastUpdate  | uint64  | 0    | 20     | 8     |
| paused      | bool    | 0    | 28     | 1     |
| totalAssets | uint256 | 1    | 0      | 32    |
| feeBps      | uint128 | 2    | 0      | 16    |
| cap         | uint128 | 2    | 16     | 16    |
```

**The chain's answer.** `cast storage <address> <slot>` returns the raw word at that slot on a live
chain; omit the slot and it prints the whole layout with values filled
in.<Cite src="foundry-cast-storage" /> Underneath it is `eth_getStorageAt`, which any node answers
for any address.<Cite src="execution-apis" />

Two fields deserve naming. **`slot`** is the 256-bit key. **`offset`** is the position in bytes
*within* that slot, counted from the low-order end — the right-hand end of the word as printed in
hex.<Cite src="solidity-docs-storage-layout" /> The pair `(slot, offset)` is a variable's full
address, and neither half appears in your source.

The JSON carries more: each entry has `astId`, `contract`, `label`, `offset`, `slot` and `type`, and
the `types` table gives each type an `encoding` of `inplace`, `mapping`, `dynamic_array` or `bytes`
plus a `numberOfBytes`.<Cite src="solidity-docs-storage-layout" /> Those four encodings are the whole
taxonomy of this module: `inplace` is this lesson and the next, the other three are the lesson after
that. One caution the documentation states about its own output — the JSON storage-layout format is
still considered experimental and subject to change in non-breaking releases of
Solidity.<Cite src="solidity-docs-storage-layout" />

<Aside kind="warn">
That everything above works against *any* deployed address, with no cooperation from the contract,
is the point. Slot contents are public regardless of whether the variable was declared `private` —
[a visibility keyword constrains other contracts, not
observers](/c/sol-visibility-not-privacy).<Cite src="solidity-docs-contracts" />
</Aside>

## The five packing rules

Multiple contiguous items that need fewer than 32 bytes are packed into a single storage slot if
possible, according to five rules the documentation states as a
list:<Cite src="solidity-docs-storage-layout" />

1. The first item in a storage slot is stored lower-order aligned.
2. Value types use only as many bytes as are necessary to store them.
3. If a value type does not fit the remaining part of a storage slot, it is stored in the next
   storage slot.
4. Structs and array data always start a new slot and their items are packed tightly according to
   these rules.
5. Items following struct or array data always start a new storage slot.<Cite src="solidity-docs-storage-layout" />

Rules 4 and 5 are the subject of the next lesson. Rules 1 to 3 are a running total: keep a cursor at
`(slot, offset)`, add each variable's byte width, and start a new slot whenever the next variable
would not fit in the 32 minus offset bytes remaining.

### Working the vault, byte by byte

**Subgoal — establish where the cursor starts.** Slot 0, offset 0. `address owner` needs 20
bytes.<Cite src="solidity-docs-storage-layout" /> It lands at `(0, 0)` and the cursor moves to
`(0, 20)`, leaving 12 bytes in the slot.

**Subgoal — test the next variable against the remainder.** `uint64 lastUpdate` needs 8 bytes and 12
remain, so it fits: `(0, 20)`, cursor to `(0, 28)`, 4 bytes left.

**Subgoal — keep going until something does not fit.** `bool paused` needs 1 byte of the 4
remaining. It lands at `(0, 28)`, cursor to `(0, 29)`, 3 bytes left. `uint256 totalAssets` needs 32
and 3 remain, so rule 3 fires: it starts slot 1, and slot 0 keeps three permanently unused bytes at
its high end.

**Subgoal — confirm against the machine rather than against your arithmetic.** Deployed with
`owner = 0xf39F…2266`, `lastUpdate = 1787788800`, `paused = true`, the node returns for slot 0:

Read right to left and the declaration order is intact: `owner` at the low-order end, `lastUpdate`
above it, `paused` above that, three zero bytes of slack at the top. Slot 2 works the same way and is
worth checking yourself: `feeBps` and `cap` are 16 bytes each, exactly filling one slot at offsets 0
and 16.

The alignment rule is one you met on the wire, arriving from the other direction. In ABI encoding a
narrow number [right-aligns inside its own 32-byte word](/c/byte-word-32) because integers are
big-endian.<Cite src="solidity-abi-spec" /> Here several narrow values *share* a word, and
"lower-order aligned" puts the first one at that same right-hand end. A packed slot is not a sequence
of independently encoded values — it is one 256-bit integer you have agreed to read in named
bit-ranges.

## Packing is a trade, and the documentation says so three ways

**The EVM operates on 32 bytes at a time**, so an element smaller than that forces the machine to use
more operations to reduce the size of the element from 32 bytes to the desired
size.<Cite src="solidity-docs-storage-layout" /> Every read of a packed field is a whole-slot load
plus a shift plus a mask. Every write is worse: when one value is written to a multi-value storage
slot, the slot has to be read first and then combined with the new value so that other data in the
same slot is not destroyed.<Cite src="solidity-docs-storage-layout" />

**It is a storage mechanism only.** For function arguments and memory values there is no inherent
benefit, because the compiler does not pack those.<Cite src="solidity-docs-storage-layout" />

**And it is conditional on your access pattern.** Reduced-size types are beneficial when the compiler
can combine multiple reads or writes into a single slot operation; if you are not reading or writing
all the values in a slot at the same time, this can have the opposite
effect.<Cite src="solidity-docs-storage-layout" />

<Misconception
  belief="Packing always saves gas, so declare the narrowest type that fits."
  reality="Packing saves slot accesses, which is a large saving, and costs masking arithmetic plus a read-modify-write on every partial write, which is a small cost paid on every call forever. It pays when the fields in a slot are touched together and can lose when they are touched independently."
  why="The slot count is visible at compile time and the access pattern is not. A layout you can compare in the artifact feels like a decision you have already validated, and the runtime half of the trade never appears in the diff."
  src="solidity-docs-storage-layout"
/>

The two sides are not the same size. A cold `SLOAD` is 2,100 gas and a warm one is 100; a first write
to a slot, taking it from zero to non-zero, is 20,000 on top of that cold
2,100.<Cite src="measured-gas-constants" /><Cite src="eip-2929" /> Against those, the shifts and
masks are ordinary arithmetic opcodes costing single-digit gas each. So removing one slot is worth
two to three orders of magnitude more than the masking it adds — which is why the trade only tips the
other way when the packing buys you no slot at all. Hold that asymmetry; the next lesson spends it.

### The masking has a second edge

The compiler cleans the unused high-order bits of a narrow value before any operation that could be
affected, including before storing it, because otherwise the garbled value can be
observed.<Cite src="solidity-variable-cleanup" /> That is what keeps `uint128 cap` from ever
scribbling into `uint128 feeBps` next door.

It stops at the assembly boundary. Access via inline assembly is not considered such an operation:
if you use inline assembly to read Solidity variables shorter than 256 bits, the compiler does not
guarantee that the value is properly cleaned up.<Cite src="solidity-variable-cleanup" /> So an
`assembly` block that loads a packed field and uses it without masking is reading whatever its
neighbours left in the rest of the word. Nothing warns you, because at that level there is only a
word.

## The layout is an interface, not an implementation detail

One note in the documentation reframes everything above. The layout of state variables in storage is
considered to be part of the external interface of Solidity, because storage pointers can be passed to
libraries; any change to the layout rules is therefore a breaking change of the language, and would
ship with a compatibility mode generating bytecode for the old
layout.<Cite src="solidity-docs-storage-layout" />

Read that as a promise about the compiler, then again as a warning about your own contract. The slot
number is the only name that survives compilation. It is what a `delegatecall` matches on — borrowed
code writes *your* slot 3, not a variable called `totalAssets`. It is what a raw `eth_getStorageAt`
addresses.<Cite src="execution-apis" /> It is what a proxy standard has to negotiate, which is why
EIP-1967 places a proxy's implementation address at a deliberately pseudo-random slot rather than at
slot 0 where a sequentially numbered variable would land.<Cite src="eip-1967" />

<Misconception
  belief="Storage slots are an implementation detail of the compiler, like register allocation."
  reality="They are the contract's only durable identity for its own state. Every off-chain reader, every proxy, and every delegatecall addresses state by slot number, and the compiler treats the assignment rules as a language-level interface it cannot change without a compatibility mode."
  why="In every other toolchain, where a field lands is genuinely private to the compiler and nothing outside the process can observe it. Here the process boundary is the chain, and the chain sees the numbers."
  src="solidity-docs-storage-layout"
/>

Take this contract and, before reading further, write out `(slot, offset)` for every variable and
say how many slots it occupies.

```solidity
contract Escrow {
    bool    settled;
    address buyer;
    address seller;
    uint96  amount;
    uint8   decimals;
}
```

Then answer a second question: the node returns
`0x0000000000000000000000d8da6e5f0e2b2f0b8f1c3d4e5f60718293a4b5c601` for slot 0. What are `settled`
and `buyer`?

<Answer>
**The map is three slots.**

- `settled` — `(0, 0)`. 1 byte, cursor to `(0, 1)`, 31 bytes remaining.
- `buyer` — `(0, 1)`. 20 bytes fit in the 31 remaining. Cursor to `(0, 21)`, 11 bytes remaining.
- `seller` — needs 20, only 11 remain, so rule 3 fires. `(1, 0)`. Cursor to `(1, 20)`, 12 remaining.
- `amount` — `uint96` is 12 bytes, exactly the 12 remaining. `(1, 20)`. Slot 1 is now full.
- `decimals` — 1 byte, no room in slot 1. `(2, 0)`.

**Three slots**, with 11 wasted bytes at the top of slot 0 and 31 at the top of slot 2.

Two slots are achievable, and the reordering that gets you there is not the obvious one. Moving
`settled` down next to `decimals` does *not* help — slot 1 is already exactly full at 20 plus 12, so
the two one-byte values still start a third slot. What works is pairing each address with something
that fits beside it: `address buyer; uint96 amount; address seller; bool settled; uint8 decimals;`
puts `buyer` and `amount` in slot 0 at offsets 0 and 20, and the remaining three in slot 1 at offsets
0, 20 and 21. That is the next lesson in one example.

**Reading the word.** Offsets count from the low-order end, so read from the right:

- `settled` is byte 0 — the last two hex characters, `01`. It is `true`.
- `buyer` is bytes 1 through 20 — the next 40 hex characters to the left,
  `0xd8da6e5f0e2b2f0b8f1c3d4e5f60718293a4b5c6`.
- The remaining leading zeros are the 11 unused bytes at the top of the slot.

The instructive part is what the word does *not* tell you. Those same 32 bytes are also a perfectly
valid `uint256`, and nothing on chain says which reading is intended. The layout artifact is the only
place that knowledge lives — which is why an indexer decoding raw slots is coupled to one compilation
of one source file.
</Answer>
</Check>

## Where this pays off

**Declaration order** is next, and it is the same rules read as a design decision rather than as a
derivation: `uint128, uint128, uint256` occupies two slots and `uint128, uint256, uint128` occupies
three, and nothing in the source hints at it.<Cite src="solidity-docs-storage-layout" />

**Mappings and dynamic arrays** are the three encodings this lesson deferred. They cannot be sized at
compile time, so they cannot participate in the running-total rule at all, and the way out is a
keccak-derived address.

**Proxies and upgrades** are this lesson with a second contract attached. A `delegatecall` gives
borrowed code your storage, and the only thing that lines up the two contracts' state is that they
happen to assign the same names to the same numbers. Every storage-collision bug is a layout
mismatch, and now you can read the layouts.

**Gas profiling** in the toolchain track measures what this lesson only bounded. Which of the two
costs dominates is a property of your access pattern, and the module's practice exercise makes you
produce the number for your own contract rather than inherit one.
