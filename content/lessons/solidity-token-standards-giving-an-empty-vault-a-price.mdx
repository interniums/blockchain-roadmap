The defect in one sentence: an empty vault has no exchange rate, so the first depositor gets to
invent one.

Every mitigation in the previous lesson is a way of deciding that rate in advance instead. A seed
deposit decides it with real capital. Dead shares decide it with capital nobody can withdraw. This
lesson is the two mitigations that decide it with arithmetic — and the price each one charges,
because both charge something.

## Virtual shares and virtual assets

OpenZeppelin's conversion, verbatim from the current source:<Cite src="oz-erc4626-source" />

```solidity
function _convertToShares(uint256 assets, Math.Rounding rounding) internal view virtual returns (uint256) {
    return assets.mulDiv(totalSupply() + 10 ** _decimalsOffset(), totalAssets() + 1, rounding);
}

function _convertToAssets(uint256 shares, Math.Rounding rounding) internal view virtual returns (uint256) {
    return shares.mulDiv(totalAssets() + 1, totalSupply() + 10 ** _decimalsOffset(), rounding);
}

function _decimalsOffset() internal view virtual returns (uint8) {
    return 0;
}
```

Two added terms, doing two different jobs.

**`totalAssets() + 1` — the virtual asset.** The denominator can never be zero, so there is no
division to special-case and no `supply == 0` branch anywhere. An empty vault has a defined rate:
`10 ** offset` shares per asset. OpenZeppelin's own description is that the virtual assets *enforce*
the conversion rate when the vault is empty.<Cite src="oz-erc4626-docs" />

**`totalSupply() + 10 ** offset` — the virtual shares.** The vault behaves as though it holds shares
of its own that nobody can redeem. Every donation is therefore diluted across a supply that includes
them, so part of any donation is captured and never comes back. That is the article's stated
purpose: virtual assets and shares capture part of the donation, making the attack
unprofitable.<Cite src="oz-erc4626-inflation-defense" />

This is dead shares without the dead capital. The comparison OpenZeppelin draws is exactly that —
YieldBox's virtual quantities mirror the behaviour of creating dead shares without having to burn
any tokens to mint them.<Cite src="oz-erc4626-inflation-defense" />

The offset also moves `decimals()`: the vault reports its underlying asset's decimals *plus* the
offset, so shares are represented with more decimal places than assets.<Cite src="oz-erc4626-source" />
That is deliberate — more precision in the share representation means a smaller rounding error when
computing shares.<Cite src="oz-erc4626-docs" />

## Worked example: replay the attack against the formula

Same setup as the previous lesson. Empty vault, 18-decimal asset, attacker deposits 1 wei, donates
`100e18`, victim then deposits `100e18`. The only change is the conversion.

Everything below is arithmetic on the formula above — reproducible with integer division, not a
measurement. Run it yourself before quoting it.

**Subgoal: see what the attacker gets for 1 wei now.**

```text
offset 0:  shares = 1 * (0 + 1) / (0 + 1) = 1
offset 3:  shares = 1 * (0 + 1000) / (0 + 1) = 1000
```

The virtual shares mean the first depositor no longer buys 100% of a supply of one. They buy a
fixed number of real shares against a fixed number of virtual ones.

**Subgoal: see whether the victim still rounds to zero.** After the `100e18` donation:

```text
offset 0:  shares = 100e18 * (1 + 1) / (100e18 + 1 + 1)
                  = 200e18 / (100e18 + 2)  ->  1

offset 3:  shares = 100e18 * (1000 + 1000) / (100e18 + 1 + 1)
                  = 200e21 / (100e18 + 2)  ->  1999
```

Not zero, in either case. The rounding-to-zero failure is gone, and it is gone because the numerator
now carries the virtual shares.

**Subgoal: settle the attacker's position.** The attacker redeems their shares, then the victim
redeems theirs:

```text
offset 0
  attacker spent   100e18 + 1 wei      received  66.666…e18      net  -33.33e18
  victim   spent   100e18              received  66.666…e18      net  -33.33e18
  remaining in the vault (captured by the virtual shares)        66.666…e18

offset 3
  attacker spent   100e18 + 1 wei      received  50.0125…e18     net  -49.99e18
  victim   spent   100e18              received  99.9749…e18     net   -0.025e18
```

Read the offset-0 row first. **The attack is already unprofitable at the default.** The attacker
loses roughly a third of their donation. The victim also loses a third — so this is a mitigation that
makes the attack pointless rather than one that makes the victim whole. That is a meaningful
distinction and it is the reason to consider a non-zero offset.

Now the offset-3 row. The attacker's loss rises to about half the donation while the victim's loss
falls to about 0.025% of their deposit. The published relationship is the general form: the
attacker's loss is at least `10 ** offset` times the value that could be taken from the
user.<Cite src="oz-erc4626-docs" /> OpenZeppelin's own summary of the two cases: with an offset of
zero the attacker's loss is at least equal to the user's deposit, and with an offset greater than
zero the attacker must suffer losses orders of magnitude bigger than what could hypothetically be
stolen.<Cite src="oz-erc4626-docs" />

The source states the same conclusion from the other end: even if an attacker can capture value from
multiple user deposits, the default offset of zero makes the attack non-profitable because the value
captured by the virtual shares matches the attacker's expected gains — and with a larger offset the
attack becomes orders of magnitude more expensive than it is
profitable.<Cite src="oz-erc4626-source" />

## What the offset costs

The implementation is candid about the drawbacks, and they are the kind that show up as support
tickets rather than as exploits.<Cite src="oz-erc4626-source" />

**The virtual shares capture a small part of accruing value.** They hold a permanent claim on the
pool, so a fraction of every unit of yield goes to nobody. Small, and not zero.

**Losses are redistributed across exit order.** If the vault experiences losses and users exit, the
virtual shares and assets cause the **first** user to exit to experience reduced losses at the
expense of the **last**.<Cite src="oz-erc4626-source" /> That is a fairness property, it is the
opposite direction from the one people assume, and it is worth telling a product owner about before
they find out during a drawdown.

**`decimals()` is no longer the asset's.** Every front end, integrator, accounting export and
subgraph reading your vault's decimals gets `underlying + offset`.<Cite src="oz-erc4626-source" />
The standard already recommends mirroring the underlying token's decimals where possible to reduce
confusion, so an offset is a deliberate departure from that
guidance.<Cite src="eip-4626" />

**Reverting is possible and is a decision.** Developers who want the pre-virtual-offset behaviour
need only override `_convertToShares` and `_convertToAssets`.<Cite src="oz-erc4626-source" /> If you
find a vault that has done so, that is a finding, not a style choice.

## Internal accounting: refuse to look

The other structural fix does not adjust the arithmetic. It changes what the arithmetic reads.

```solidity
uint256 private _managedAssets;

function totalAssets() public view override returns (uint256) {
    return _managedAssets;      // never balanceOf(address(this))
}
```

`_managedAssets` is updated only by the vault's own deposit and withdrawal paths. A plain transfer to
the vault's address increases the *token's* record of the vault's balance and changes nothing the
vault reads. OpenZeppelin's assessment of this option is the strongest thing they say about any of
them: it removes the inflation risk completely, and the logic is easy to
understand.<Cite src="oz-erc4626-inflation-defense" />

Since 5.6.0 (25 February 2026) the reference implementation exposes the seam for it. `_transferIn`
and `_transferOut` are internal virtual functions that the deposit and withdrawal paths route
through, so a subclass can hook the movement of underlying assets without reimplementing the
workflow.<Cite src="oz-changelog" /><Cite src="oz-erc4626-source" />

### The cost, named precisely

**The vault's view of its holdings can diverge from its actual balance.** That is not a bug; it is
the mechanism. But it means anything that genuinely arrives outside the deposit path is invisible:

- Yield that a strategy pays as a plain transfer.
- An airdrop to the vault's address.
- A router refund, a rebate, a fee share.
- A rebase, if the asset is a rebasing token.<Cite src="lido-tokens-integration-guide" />

Recognising any of those requires an explicit entry point that adds to `_managedAssets`. And **that
entry point is a privilege**: whoever can call it chooses the moment the share price jumps, which is
a front-runnable event. You have not removed the manipulation surface; you have replaced an open one
with a permissioned one, and moved the question from "who holds the asset" to "who holds the key".

**Second cost: reconciliation becomes your job.** With `balanceOf` accounting, the vault's records
and the token's records agree by construction. With internal accounting they drift, and the drift is
real value sitting in the contract belonging to nobody. Somebody has to decide whether it can be
swept, by whom, and to where.

## Choosing, and the relationship to the delta pattern

Set this next to lesson five and the pair becomes clear, because they are answers to different
questions:

- **The balance-delta pattern** asks *how much did this transfer actually move*, and answers it by
  measuring. It is the right tool at a boundary where an amount is uncertain — fee-on-transfer
  tokens, `type(uint256).max` special cases.<Cite src="weird-erc20" />
- **Internal accounting** asks *what is allowed to move my exchange rate*, and answers by refusing
  to read anything an outsider can write.

They compose. A vault holding a fee-on-transfer asset should measure the delta on the way in *and*
credit that measured delta to its internal counter — the delta gets the amount right, the counter
keeps a donation from mattering.

A decision table for the three realistic cases:

| Situation | Choice | Why |
|---|---|---|
| New vault, ordinary ERC-20 asset | Virtual offset, default or small non-zero | It is the default, it costs nothing to adopt, and it is already sufficient to make the attack unprofitable<Cite src="oz-erc4626-source" /> |
| Asset is fee-on-transfer or rebasing | Internal accounting plus measured deltas at the boundary | The rate must not be movable, and the amount in must be measured rather than assumed<Cite src="weird-erc20" /><Cite src="lido-tokens-integration-guide" /> |
| Integrating someone else's vault | Read its `totalAssets()` and find out which it is | That one function tells you whether a donation can move the price you are about to depend on<Cite src="eip-4626" /> |

The third row is the one that turns this lesson into a habit. `totalAssets()` is a public view
function on every 4626 vault. Reading its implementation takes a minute and answers the only
question that matters about the vault's arithmetic.

<Check type="explain" concept="internal-accounting-vs-balanceof">
You are reviewing a lending market that accepts a third-party ERC-4626 vault token as collateral. It
values a position as `vault.convertToAssets(userShares) * assetPriceFromOracle`.

The vault's `totalAssets()` is the OpenZeppelin default. Its `_decimalsOffset()` returns 0. It
currently holds `1e24` assets against `1e24` shares.

Say whether the collateral valuation is manipulable, and what you would require before listing it.

<Answer>
**Manipulable in principle, and not cheaply in this state.** `convertToAssets` reads `totalAssets()`,
which is `balanceOf(address(this))` on the underlying, so anyone can raise it with a
transfer.<Cite src="oz-erc4626-source" /> Raising the price per share raises every borrower's
collateral value, which is the direction an attacker wants.

**Price the attack rather than asserting it.** With `1e24` shares outstanding, a donation of `D`
raises the price per share by roughly `D / 1e24` and lifts the value of a position holding `s` shares
by roughly `D * s / 1e24`. To gain, the attacker must control a large fraction of the supply — the
same arithmetic as the previous lesson's seeded vault. Against a vault this size the donation is not
economic. Against the same vault after a large redemption, it is.

**Which is the actual finding.** The market's safety depends on a quantity — the vault's share
supply — that the market does not control, does not monitor, and that can fall at any time. A
listing that is safe today can become unsafe without anything happening in the market's own code.

**Also flag the function choice.** `convertToAssets` is the right family here: the spec permits the
convert methods to be inexact and names them as the ones that may be implemented as robust price
oracles, unlike the preview methods, which it warns are manipulable by altering on-chain conditions
and not always safe as price oracles.<Cite src="eip-4626" /> This integration got that part right —
but the specification's permission is that a vault *may* implement `convertToAssets` as a TWAP, and
the OpenZeppelin default does not. Reading the interface tells you which function to call; reading
the implementation tells you what it does.

**What to require before listing.** A vault with either a non-zero decimals offset or internal
accounting, so the rate is not writable by transfer.<Cite src="oz-erc4626-source" /><Cite src="oz-erc4626-inflation-defense" />
A supply floor below which the collateral is disabled, monitored on chain rather than at review time.
And a cap on total exposure to this vault that is small relative to the donation cost at the supply
floor — because that product, not the current supply, is the number the market's solvency actually
rests on.
</Answer>
</Check>

## Where this pays off

**The module's practice exercises** are the place to make this concrete: implement the naive vault,
execute the attack until the victim receives zero, then add the offset and re-run the same test with
the residual loss quantified rather than asserted.

**Invariant testing** on the Foundry track has its best property here — no sequence of deposits,
donations and withdrawals should let any user extract more than they put in plus their share of
yield. Include plain transfers to the vault among the handler's actions, or the campaign never
generates the interesting case.

**The DeFi track** meets vault share prices as an oracle input in lending markets, leveraged
strategies and looping products. Everything above is the question of whether that input is a number
somebody else can write, and lending markets have lost money to the answer.

**And the general form, worth carrying out of this module entirely:** a contract that computes
anything important from `balanceOf(address(this))` has published a write interface to it. Tokens,
vaults, reward distributors, fee splitters — the shape is the same, and the two fixes are always the
same two. Make the value defined when the pool is empty, or stop reading a number that other people
control.
