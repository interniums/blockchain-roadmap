There is a line in ERC-777 that explains an entire era of exploits, and it is only twelve words
long.

> The token contract MUST call the `tokensToSend` hook before updating the state.<Cite src="eip-777" />

Before updating the state. A finalised Ethereum standard, in normative language, requires that a
token hand execution to the sender's chosen code while its own balances still show the pre-transfer
world. A `balanceOf` call inside `tokensToSend` returns the balance *before* the send, and the
specification says so explicitly.<Cite src="eip-777" />

That is interactions-before-effects, mandated. This lesson is about what the ecosystem learned from
it, and about the standard that took the conclusion furthest: ERC-6909, whose rationale section
headings read like a list of things the previous two lessons were about.

## ERC-777 and the shape of the mistake

ERC-777 gives a fungible token two hooks, registered through the ERC-1820 registry rather than
implemented directly, so an *existing* address can acquire a hook without changing its
code:<Cite src="eip-777" />

- **`tokensToSend`** on the holder, called if the holder registered an implementation — **before**
  the state update.<Cite src="eip-777" />
- **`tokensReceived`** on the recipient, called if the recipient registered one — **after** the state
  update.<Cite src="eip-777" />

The ordering is deliberate and documented: `tokensToSend` first, then the state change, then
`tokensReceived`.<Cite src="eip-777" /> The motivation was legitimate — `tokensReceived` lets you
send tokens to a contract and notify it in one transaction, which is the problem ERC-20 genuinely
has.<Cite src="eip-777" /> The sender hook was for symmetry and for veto: the transfer reverts if
either hook reverts.<Cite src="eip-777" />

What it produced is a fungible token where **every transfer is an external call to two addresses
neither party's contract chose**. The weird-ERC-20 catalogue lists this first, under "Reentrant
Calls", and records that it has been exploited in the wild on multiple occasions, naming the drained
imBTC Uniswap pool and Lendf.me.<Cite src="weird-erc20" /> The loss totals for those incidents vary
across secondary retellings and this repository has not verified one, so take the mechanism and
leave the number.

Note the compounding factor that makes ERC-777 worse than the NFT hooks. With ERC-721 you can see the
hazard: the function is called `safeTransferFrom` and the callback is part of the standard's stated
behaviour. With ERC-777, an integration that calls plain `transfer` on what it believes is an ERC-20
gets the hooks anyway, because ERC-777 is backwards compatible with the ERC-20
interface.<Cite src="eip-777" /> The hazard is invisible at the call site.

## The opt-in alternative

ERC-1363 solves the same "notify on receipt" problem with the decision moved to the
caller.<Cite src="eip-1363" /> `transferAndCall` and `approveAndCall` are separate functions; plain
`transfer` and `approve` behave exactly as ERC-20 says. A caller who wants the notification asks for
it by name; a caller who does not, never triggers one.

That is the whole design difference and it is worth stating as a principle, because it generalises
well beyond tokens: **make the dangerous behaviour a different function, not a mode of the safe
one.** Same capability, different failure surface — an integration cannot receive the hazard by
accident.

OpenZeppelin exposes this through `SafeERC20`, with the fallback behaviour spelled out:
`transferAndCallRelaxed` performs the ERC-1363 call when the target has code and falls back to a
plain `safeTransfer` when it does not.<Cite src="oz-safe-erc20-source" /><Cite src="eip-1363" />

## ERC-6909: the interface with the callbacks removed

ERC-6909 is a multi-token interface specified as a simplified alternative to ERC-1155, with
callbacks and batching removed and a hybrid operator-allowance permission
scheme.<Cite src="eip-6909" />

**On its status**, because you will find contradictory claims. The canonical EIP index lists
ERC-6909 as **Final**, verified there on 26 August 2026.<Cite src="eip-6909" /> OpenZeppelin's
changelog agrees and acts on it: in 5.5.0 (31 October 2025) the `ERC6909` contracts stopped being
marked as draft, with the stated reason that the EIP is now final, and the import paths
changed.<Cite src="oz-changelog" /> A good deal of material written between 2023 and early 2026
describes it as Draft, and this repository's own research notes left the question open. Two primary
sources now agree; check the EIP page yourself before repeating either claim, because that is the
only source that settles it.

### The interface

Six functions and three events.<Cite src="eip-6909" />

```solidity
function balanceOf(address owner, uint256 id) external view returns (uint256);
function allowance(address owner, address spender, uint256 id) external view returns (uint256);
function isOperator(address owner, address spender) external view returns (bool);

function transfer(address receiver, uint256 id, uint256 amount) external returns (bool);
function transferFrom(address sender, address receiver, uint256 id, uint256 amount)
    external returns (bool);
function approve(address spender, uint256 id, uint256 amount) external returns (bool);
function setOperator(address spender, bool approved) external returns (bool);

event Transfer(address caller, address indexed sender, address indexed receiver,
               uint256 indexed id, uint256 amount);
event OperatorSet(address indexed owner, address indexed spender, bool approved);
event Approval(address indexed owner, address indexed spender, uint256 indexed id, uint256 amount);
```

The interface identifier is `0x0f632fb3`, and a compliant contract must implement ERC-165 in addition
to the above.<Cite src="eip-6909" /><Cite src="eip-165" /> Note that `transfer`, `transferFrom`,
`approve` and `setOperator` all MUST return `True` — the standard closes the return-value hole from
lesson four by requiring the value rather than merely declaring it.<Cite src="eip-6909" />

### What it removed, in the specification's own words

The rationale has four headings, and each one is an argument this module has already made.

**Granular Approvals.** ERC-1155's operator model gives full permission over every id; ERC-20's
allowance model gives an explicit amount. ERC-6909 requires **both**, with the token id added to the
allowance key — so a holder can grant a specific amount for a specific id, an infinite amount for a
specific id, or infinite permission across all ids.<Cite src="eip-6909" /> That is the exact gap the
previous lesson ended on.

**Removal of Batching.** Batching is useful and its place is not in the standard, so implementations
can make their own tradeoffs about calldata layout — the rationale calls out roll-ups that commit
calldata to global storage as a case where a different encoding pays.<Cite src="eip-6909" /> If you
have worked through what [data actually costs on a rollup](/c/blob-not-in-evm), that is not an
abstract consideration; it is the dominant cost term for many L2 applications.

**Removal of Required Callbacks.** Requiring callbacks "unnecessarily encumbers implementors that
either have no particular use case for callbacks or prefer a bespoke callback mechanism", and
removing the requirement saves contract size, gas and complexity.<Cite src="eip-6909" /> The
motivation section is sharper still: ERC-1155 requires a callback on every transfer to a contract
account, and unlike ERC-721 — which has both `transferFrom` and `safeTransferFrom` — **there is no
option to opt out**.<Cite src="eip-6909" />

**Removal of "Safe" Naming.** This is the paragraph to remember:

> The `safeTransfer` and `safeTransferFrom` naming conventions are misleading, especially in the
> context of the ERC-1155 and ERC-721 standards, as they require external calls to receiver accounts
> with code, passing the execution flow to an arbitrary contract, provided the receiver contract
> returns a specific value. The combination of removing mandatory callbacks and removing the word
> "safe" from all method names improves the safety of the control flow by
> default.<Cite src="eip-6909" />

An EIP saying, in its rationale, that a word in two earlier EIPs was misleading. That is as close as
this ecosystem gets to a retraction.

### The bug the standard ships as a warning

ERC-6909's security considerations contain a worked example of an implementation mistake, and it is a
good one because it is the kind that compiles and passes a happy-path test.

The hybrid permission model means `transferFrom` must check *either* a sufficient allowance *or*
operator status. An implementation that decrements the allowance before establishing which of the two
applies panics on arithmetic underflow when the allowance is insufficient — **even when the caller is
a valid operator** and should have been permitted.<Cite src="eip-6909" /> The standard's own
normative text anticipates it: `transferFrom` MUST NOT decrease the caller's allowance if the caller
is an operator, and MUST NOT decrease it when the allowance is infinite.<Cite src="eip-6909" />

Precedence between two authority sources is the class of bug. It is not specific to this standard,
and it is what makes hybrid permission models more expensive to implement correctly than either half
alone.

### Where it is used, and what it is not

ERC-6909 is the interface Uniswap documents for token accounting in v4.<Cite src="uniswap-v4-erc6909-docs" />
That is where its weight comes from — a large protocol shipping it, rather than a migration away from
ERC-1155.

And it is explicitly **not** a drop-in replacement: the standard states that it is not backwards
compatible with ERC-1155 because some methods are removed, and notes that wrappers can be
implemented for ERC-20, ERC-721 and ERC-1155.<Cite src="eip-6909" /> An existing ERC-1155 integration
does not "upgrade" to it.

## The rule underneath all of it

Line the standards up by where attacker-chosen code can run inside your transaction.

| Standard | Callback | Who decides | Ordering relative to effects |
|---|---|---|---|
| ERC-777 | `tokensToSend`, `tokensReceived` | neither party at the call site | send hook runs **before** the state update<Cite src="eip-777" /> |
| ERC-721 | `onERC721Received` | the caller, by choosing `safeTransferFrom` | after the transfer completes<Cite src="eip-721" /> |
| ERC-1155 | `onERC1155Received`, `onERC1155BatchReceived` | mandatory on the transfer functions | after balances are updated and events emitted<Cite src="eip-1155" /> |
| ERC-1363 | `onTransferReceived` | the caller, by calling `transferAndCall` | opt-in, separate function<Cite src="eip-1363" /> |
| ERC-6909 | none | not applicable | not applicable<Cite src="eip-6909" /> |

Two conclusions, and the second is the one that changes how you write code.

**If you choose the token standard, choosing one without callbacks removes a bug class rather than
guarding against it.** That is a strictly better position than any amount of correct ordering,
because correct ordering is a property somebody has to maintain across every future change to the
contract.

**If you do not choose the token standard — which is most of the time — treat any transfer that can
call out as an interaction in the Checks-Effects-Interactions sense.** Not "a transfer, which is
usually fine". An interaction: the last thing the function does, after every piece of state the
function's own checks depend on is committed, and behind a guard if the invariant spans more than
one function.

That rule costs nothing when the token turns out to be inert, and it is the only thing standing
between you and the previous two lessons when it is not.

A team is designing an internal accounting layer for a protocol that holds many asset types in one
contract. They are choosing between ERC-1155 and ERC-6909 for the claim tokens they issue to users.

Make the argument for ERC-6909, and then make the honest argument against it — the thing they give
up that they may not have noticed.

<Answer>
**For.** No receiver callbacks, so issuing or moving a claim token never passes execution to the
holder's code — the reentrancy surface from the last two lessons does not exist on this
path.<Cite src="eip-6909" /> Per-`(id, spender)` allowances, so a user can authorise a market for
one asset instead of all of them, which ERC-1155 cannot express at
all.<Cite src="eip-6909" /><Cite src="eip-1155" /> Smaller interface, smaller contracts, and no
batch semantics baked in — so the protocol can define whatever batch encoding suits its own
calldata profile, which on a rollup is a real cost decision.<Cite src="eip-6909" />

**Against.** They lose the notification, and with it every integration pattern that depends on it. A
recipient contract can no longer be told that tokens arrived, so anything that used to work by
transferring into a contract and letting its hook do the accounting now needs an explicit second
call — the two-transaction problem from lesson three, reappearing.

**They also lose the stranding protection.** ERC-1155 reverts when a recipient contract does not
implement the receiver interface, which prevents tokens being sent somewhere they can never leave.
With no callbacks, a transfer to a contract that has no code path to move the token succeeds and the
claim is dead. For an internal claim layer that is usually acceptable — the counterparties are
protocol contracts — and for a token users hold directly it is a real regression.

**And they lose ecosystem support.** Wallets, marketplaces, indexers and explorers have a decade of
ERC-1155 handling and much less for ERC-6909. The standard anticipates this and points at
wrappers.<Cite src="eip-6909" />

The decision therefore turns on who holds the token. For an internal accounting layer between
contracts the protocol controls — which is exactly the Uniswap v4 use
case<Cite src="uniswap-v4-erc6909-docs" /> — ERC-6909 is the better fit. For a user-facing asset,
the missing callback and the thinner tooling are costs paid by people who did not choose them.
</Answer>
</Check>

## Where this pays off

**The next three lessons** move from "who can run code inside my transfer" to "what number does my
contract compute from its balance" — ERC-4626, share accounting, and an arithmetic failure that
needs no callback at all.

**The security track** takes the callback table as a threat-modelling input: for every external
token your contract touches, the question is which row it sits in, and that is a per-token answer.

**Uniswap v4's architecture** on the DeFi track uses the claim-token layer discussed here to make
flash accounting possible, which is where the "no callbacks, no batching" tradeoff pays for itself.
