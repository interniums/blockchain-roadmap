A pull request lands on a token contract you maintain. One line changes, inside `_update`. You need
to answer a question that sounds easy: what does this function do now?

`_update` is `virtual`, so you check for overrides — two files up the inheritance chain, one exists.
It calls `super._update`, so the answer depends on the linearisation, which depends on the order the
bases were listed in a declaration on line 12. One of those bases attaches a modifier,
`whenNotPaused`, whose body you have not read. Another declares a state variable you have not seen,
in a slot you did not choose.

You have opened five files, and none of them is the one the pull request touched.

That experience is the argument of this module. Vyper's designers took it as the problem statement
and removed features until it stopped happening.

## The goal is written down, and it is unusual

Vyper's documentation states three principles: security, simplicity of both the language and the
compiler implementation, and auditability, defined as code being maximally
human-readable.<Cite src="vyper-docs-index" /> The third carries a clause that does the real work.
The aim is not only that code be readable but that it should be maximally difficult to write
*misleading* code, with simplicity for the reader taking priority over simplicity for the writer —
and specifically for readers with little prior experience of Vyper, or of programming at
all.<Cite src="vyper-docs-index" />

Read that as an engineering constraint and notice how strong it is.

**"Misleading" is a different target from "buggy".** A feature can be sound, fully specified, and
still a candidate for removal, because the objection is not that it computes the wrong thing — it is
that a reader who does not open a second file will believe the wrong thing. Modifiers are sound.
Inheritance is sound. Both are absent.<Cite src="vyper-docs-index" />

**The reader is assumed to be unfamiliar.** Not a maintainer with the codebase in their head; a
stranger arriving with an hour and a diff. Any feature whose benefit accrues to the person who
already knows the code, at a cost to the person who does not, loses that trade by construction.

**The compiler is in scope.** "Language and compiler simplicity" makes the implementation itself a
design goal.<Cite src="vyper-docs-index" /> That reads as housekeeping. Lesson five is about the July
2023 incident in which it was not.

## Pythonic, and not Python

Vyper's syntax is Python's: significant indentation, `def`, decorators, `self`. Its compiler is
written in Python and installs from PyPI.<Cite src="vyper-pypi-json" /> The similarity is a
recruiting device and a trap in equal measure: the semantics underneath belong to a statically typed,
non-recursive, bounded language that emits EVM bytecode.

Here is a complete contract. Read it once for shape, then follow the labelled pass underneath.

```python
# pragma version ==0.4.3
# pragma evm-version prague

event Deposit:
    depositor: indexed(address)
    amount: uint256

owner: public(address)
balances: public(HashMap[address, uint256])

@deploy
def __init__():
    self.owner = msg.sender

@external
@payable
@nonreentrant
def deposit():
    self.balances[msg.sender] += msg.value
    log Deposit(depositor=msg.sender, amount=msg.value)

@external
@nonreentrant
def withdraw(amount: uint256):
    assert self.balances[msg.sender] >= amount, "insufficient"
    self.balances[msg.sender] -= amount
    send(msg.sender, amount, gas=2300)
```

**Subgoal: pin the toolchain before anything else runs.** The two pragmas are compiler directives,
not comments. `#pragma version` refuses to compile under any other compiler version — from 0.4.0
onward the string is a PEP 440 specifier rather than the npm-style range used
earlier.<Cite src="vyper-docs-structure" /> `#pragma evm-version` fixes the target
ruleset.<Cite src="vyper-docs-compiling" /> Both live in the source, so the pin travels with the code
rather than with whoever last configured the build. It becomes the whole of lesson five.

**Subgoal: declare storage, and know the layout is finished.** State variables are reached through
`self`, and `public(...)` generates a getter. The compiler allocates the slots, and because there is
no inheritance there is no second source of state variables to interleave with these — the
[layout](/c/storage-slot) of this contract is decided by this file and nothing else.

**Subgoal: mark the constructor as a distinct kind of function.** `@deploy` is not a naming
convention. It is a decorator saying this code runs once at deployment and is absent from the runtime
code; only `__init__` may carry it.<Cite src="vyper-docs-control-structures" />

**Subgoal: state every capability the function has.** `@external` puts `deposit` in the selector
table. `@payable` permits it to receive ether and read `msg.value`. `@nonreentrant` takes a
contract-wide lock.<Cite src="vyper-docs-control-structures" /> None of the three is inferable from
the body. All three are on the same screen as the body.

**Subgoal: notice the arithmetic that is not written down.** `+=` on a `uint256` is checked, so is
`-=`, and so is every array index in the language.<Cite src="vyper-docs-index" /> There is no
`unchecked` block wrapping a region; opting out is per-expression, through a builtin whose name
starts with `unsafe_`.<Cite src="vyper-docs-builtins" />

**Subgoal: read the assertion as a revert, and the transfer as a gas decision.** `assert cond,
"reason"` compiles to `REVERT` carrying that string, up to 1024 bytes; `raise "reason"` is the
unconditional form.<Cite src="vyper-docs-control-structures" /> And `send(to, value, gas=...)` takes
the forwarded gas as an explicit argument, which defaults to zero when
omitted.<Cite src="vyper-docs-builtins" /> The forwarding decision is a parameter you can see rather
than a property of which helper you happened to pick.

The part that matters for reading the file: all of it is on one screen. No `super`, no base contract,
no library with `using for`, no modifier defined elsewhere. The language's claim is that this is the
whole story for these two functions — a claim it can keep only because the features that would break
it do not exist.

## The interop is free, because the ABI is the same

The usual practical worry about Vyper is that adopting it fragments a system. It does not, and you
already know enough to check the reason rather than take it.

Vyper compiles to ordinary EVM bytecode against the same [contract ABI](/c/abi-canonical-signature)
Solidity uses. A [selector](/c/abi-function-selector) is the first four bytes of the hash of the
canonical signature under the same rules, so `transfer(address,uint256)` dispatches identically
whichever compiler produced the contract.<Cite src="solidity-abi-spec" /> Calldata layout and return
encoding are identical. Nothing about a call crosses a language boundary, because after the
deployment transaction there is no language — only bytecode and an ABI.

Two details make that concrete rather than assumed.

**Bounds do not appear in the ABI.** A Vyper `DynArray[int128, 3]` is `int128[]` on the ABI level;
`DynArray[DynArray[int128, 3], 3]` is `int128[][]`.<Cite src="vyper-docs-types" /> The maximum is a
fact about the Vyper side only. A Solidity caller passing a longer array produces perfectly valid
calldata, and the Vyper contract reverts at decode time.<Cite src="vyper-docs-types" /> The ABI is the
interface; the bound is an invariant *behind* it, enforced at runtime and invisible to the caller's
type checker.

**Default arguments multiply selectors.** An external function with N defaulted parameters generates
N+1 selectors, one per arity, and the ABI signature omits the optional arguments when their defaults
are used.<Cite src="vyper-docs-control-structures" /> One `def` can therefore occupy several entries
in the dispatch table — the nearest thing Vyper has to overloading, and deliberately narrow, since
every generated signature comes from one body.

Calls *out* diverge in syntax, in the direction the design goal predicts. Since 0.4.0 an external
call carries an explicit keyword: `extcall` for a state-changing call, `staticcall` for a
read.<Cite src="vyper-docs-control-structures" /> Finding every point where control leaves the
contract is a grep for two words; in Solidity it requires knowing which identifiers are contract
types.

<Check type="explain" concept="vyper-design-goal">
A colleague proposes adding function modifiers to Vyper: "A modifier is a function call the compiler
inlines. Anything a modifier does, inline code can do, so removing them cannot remove a class of
bug — it only makes people type more."

The argument is coherent. Say where it misses the design goal, and what a modifier can do that its
inline equivalent cannot.

<Answer>
**Right about expressiveness, wrong about the target.** Nothing is computable with modifiers that is
not computable without them; that was never the claim. The claim is about what a reader believes
after reading the body, against a goal of making misleading code maximally hard to
write.<Cite src="vyper-docs-index" />

**What a modifier can do that inline code cannot: be invisible at the site where it acts.** The
documentation's own objection is that a modifier name looks too innocuous for something that can add
arbitrary pre-conditions, post-conditions or state changes, and that it makes execution jump around
the file.<Cite src="vyper-docs-index" /> Inline code cannot hide, because it is the code. The
difference is not capability, it is locality of evidence.

**The bug class removed is a reviewing bug, not a computing bug** — the part the argument has no slot
for. A reviewer who reads a body and forms a belief about it is performing an inference, and a
modifier is a premise that was never on screen.

**Where the trade genuinely costs.** Duplicated guards. Ten functions needing an owner check means
ten copies, and a diff adding an eleventh can omit it. Vyper's answer is that the omission is visible
in the body, whereas a missing modifier is also an absence — but of a token nobody was scanning for.
Which failure is likelier is arguable; that the designs put the risk in different places is not.
</Answer>
</Check>

## Where this pays off

**The next lesson takes the removals one at a time.** Inheritance, modifiers, overloading, inline
assembly: for each, the documentation names the reading failure that motivated it, and each maps onto
a Solidity bug class you have already met.

**Bounded loops and bounded types** are not a style choice. The principles list "decidability" —
computing a precise upper bound on the gas consumption of any Vyper function call — as something the
language provides.<Cite src="vyper-docs-index" /> That is a liveness property, and lesson three is
about why an unbounded Solidity loop is the same bug with the guarantee removed.

**The module system** replaces inheritance with explicit `initializes`, `uses` and `exports`
declarations, checked by the compiler rather than agreed by
convention.<Cite src="vyper-docs-modules" />

**And the reason this module exists at all** is lesson five: in July 2023 three Vyper releases turned
correct source into bytecode with a reentrancy hole. A language built on the claim that the body is
the whole story is the sharpest possible setting for the lesson that the body is only the whole story
if the compiler agrees.
