A three-line diff adds a subtraction to an existing function. The reviewer checks the arithmetic —
the operands are `uint256`, the subtraction could underflow, but Solidity has reverted on underflow
since 0.8.0, so this is fine.<Cite src="solidity-docs-control-structures" />

The line was added inside an `unchecked` block that starts eleven lines earlier, opened by somebody
else for a loop counter. The setting applies to every statement syntactically inside the
block.<Cite src="solidity-docs-control-structures" /> The subtraction wraps.

Nothing here is a language defect. `unchecked` is precisely specified, and the specification says
what it did. The failure is that the diff and the property it depends on are not in the same place —
which is the same failure the last two lessons were about, arriving now in arithmetic.

This lesson is about how Vyper positions defaults and escape hatches, and about being accurate rather
than triumphant on what that actually gains.

## Vyper has defaults. Both of them are the restrictive option.

The claim you will read most often is that Vyper has no defaults and requires every decorator. That
is not true, and the true version is more useful.

Vyper functions carry decorators in two independent dimensions, and each dimension has a
default:<Cite src="vyper-docs-control-structures" />

| Dimension | Options | Default |
|---|---|---|
| Visibility | `@external`, `@internal`, `@deploy` | `@internal` |
| Mutability | `@pure`, `@view`, `@nonpayable`, `@payable` | `@nonpayable` |

Since 0.4.0 the `@internal` decorator is optional; a function with no visibility decorator is
internal.<Cite src="vyper-docs-control-structures" /> A function with no mutability decorator is
non-payable.<Cite src="vyper-docs-control-structures" />

So the rule is not "everything is written down". The rule is: **the default is always the least
capable option, and every capability is a token you have to type.** A function that can be called
from outside says `@external`. A function that can take money says `@payable`. A function that can
run once at deployment and never again says `@deploy`, and only `__init__` may carry
it.<Cite src="vyper-docs-control-structures" />

<Aside kind="note">
This is a narrower contrast with Solidity than the marketing suggests, and worth being precise about.
Solidity has required explicit function visibility since 0.5.0 and also defaults to non-payable. On
the *function header*, the two languages are close to equivalent. The differences that survive are
elsewhere — at call sites, at state access, and at the escape hatches — and that is where the rest
of this lesson looks.
</Aside>

### Where the explicitness actually differs

**State access is prefixed.** Every state variable read and every internal call goes through `self`:
`self.balances[msg.sender]`, `self._check_owner()`.<Cite src="vyper-docs-control-structures" /> A bare
identifier in a Vyper function body is a local, always. In Solidity a bare identifier may be a local,
a state variable of this contract, a state variable of a base you did not open, a free function, or a
function attached by `using for`.

**External calls are keyworded.** Since 0.4.0 a call out is written `extcall f(...)` when it may
change state, `staticcall f(...)` when it may not.<Cite src="vyper-docs-control-structures" /> The
set of points where control leaves your contract is a grep for two words.

**Unsafe arithmetic is named per expression.** Not per block.

## The escape hatch is at the expression, not around it

Vyper's checks — overflow, underflow, array bounds, division by zero — are on
permanently.<Cite src="vyper-docs-index" /> Opting out means calling a builtin whose name says so:

```python
c: uint256 = unsafe_add(a, b)      # wraps
d: uint256 = unsafe_sub(a, b)      # wraps
e: uint256 = unsafe_mul(a, b)      # wraps
f: uint256 = unsafe_div(a, b)      # b == 0 yields 0, per EVM semantics
```

**Subgoal: notice that the exemption cannot travel.** `unsafe_add(a, b)` exempts that expression. The
next line is checked. A line added later inside the same function is checked. There is no region for
a future diff to fall into, which is exactly the failure at the top of this page.

**Subgoal: notice that this is not a purity argument.** For the EVM's native word types `uint256` and
`int256`, `unsafe_add` compiles to a single `ADD` instruction, because the EVM already wraps at 256
bits.<Cite src="vyper-docs-builtins" /> The unsafe builtins are genuinely cheaper and there are
genuine reasons to reach for them. The design question was never whether to allow wrapping — it was
where the reader finds out that wrapping is what happens here.

**Subgoal: notice where Vyper's escape hatch reaches further than Solidity's.** Solidity's `unchecked`
cannot disable the division-by-zero or modulo-by-zero check at
all.<Cite src="solidity-docs-control-structures" /> `unsafe_div` can: the result of dividing by zero
is zero, following EVM semantics.<Cite src="vyper-docs-builtins" /> That is a sharper knife, handed
over with a longer name. Both halves of that sentence are the design.

## Failure is one mechanism with an explicit opt-out

Vyper has `assert` and `raise`, and both revert.<Cite src="vyper-docs-control-structures" />

```python
assert self.balances[msg.sender] >= amount, "insufficient"
raise "unreachable state"
```

The reason string is optional and limited to 1024
bytes.<Cite src="vyper-docs-control-structures" /> `assert cond, "msg"` is defined as equivalent to
`if not cond: raise "msg"`.<Cite src="vyper-docs-control-structures" />

You have met Solidity's split, where `require` produces `Error(string)` and `assert` produces
[`Panic(uint256)`](/c/sol-panic-codes) with a code identifying the class of internal failure. Vyper
does not split them, which means it does not give you the *free* signal that a failure was a compiler
invariant rather than an input problem.

What it gives instead is an explicit opt-in to the harsher form. If the reason string is exactly
`UNREACHABLE`, the compiler emits the `INVALID` opcode `0xFE` rather than `REVERT`, and calls that
revert this way get no gas refund. The documentation states plainly that this is not recommended for
general usage and exists for interoperability with tools that use `INVALID` for dynamic
analysis.<Cite src="vyper-docs-control-structures" />

That is the pattern of this whole lesson in miniature: the aggressive behaviour exists, it is
reachable, and reaching it requires typing a word that means it.

## The reentrancy guard is a language feature, and it moved

`@nonreentrant` is the most instructive decorator, partly because of what it does and mostly because
of lesson five.

**What it is.** A global lock. One per contract, shared by every protected function. An external
attempt to call back into any `@nonreentrant` function reverts.<Cite src="vyper-docs-control-structures" />
Prior to 0.4.0 the decorator took a key argument for finer-grained control; since 0.4.0 only the
global lock exists.<Cite src="vyper-docs-control-structures" />

**Where it lives.** In a storage slot the compiler allocates — slot 0 unless overridden — visible with
`vyper -f layout`.<Cite src="vyper-docs-control-structures" /> The locked value is 2 and the unlocked
value is 3, both non-zero deliberately to take advantage of net gas metering; the documentation puts
the net cost of using the lock at 2,300 gas as of the Berlin
fork.<Cite src="vyper-docs-control-structures" />

**Where it moved.** From the `cancun` EVM target onwards, the compiler protects `@nonreentrant`
functions with `TLOAD` and `TSTORE` instead of `SLOAD` and
`SSTORE`.<Cite src="vyper-docs-compiling" /><Cite src="eip-1153" /> Since 0.4.3's default EVM version
is `prague`, which is later than cancun, a Vyper contract compiled with defaults today gets a
[transient](/c/transient-reentrancy-guard) guard with no opt-in, no import and no
decision.<Cite src="vyper-release-notes" />

That is a large difference in ergonomics, and the magnitude is worth having in mind even though the
measurement below comes from the other language. On forge 1.7.1 and solc 0.8.36 with the optimizer
off, a transient-storage guard adds a flat overhead of about 284 gas, while a storage guard's
overhead is cold/warm dependent and ranges from roughly 3,100 to roughly 7,100 — the low end measured
directly at 3,104 on an already-warm slot.<Cite src="measured-gas-constants" /> The widely repeated
"7,100 versus 200" pairing overstates the ratio, because it silently compares a cold storage slot
against transient storage.<Cite src="measured-gas-constants" /> The architectural point survives the
correction: the same guard, on a later EVM target, costs about an order of magnitude less.

**What it refuses.** Since 0.4.2 it is an error to call a `@nonreentrant` function from another
`@nonreentrant` function, because the lock is global and would already be
held.<Cite src="vyper-release-notes" /><Cite src="vyper-docs-control-structures" /> A constraint that
would be a runtime revert elsewhere is a compile error here.

### Inverting the default entirely

0.4.2 added `#pragma nonreentrancy on`, which makes every external function and every public getter in
the file nonreentrant, except getters for constants and immutables — whose values cannot change, so
there is nothing to protect.<Cite src="vyper-docs-control-structures" /> The opt-out is `@reentrant`
on a function, or `reentrant(...)` wrapped around a public variable's type:

```python
# pragma nonreentrancy on

x: public(uint256)              # getter is protected from read-only reentrancy
y: public(reentrant(uint256))   # getter is not

@external
def make_a_call(addr: address):
    ...                          # protected

@external
@reentrant
def callback(addr: address):
    ...                          # deliberately re-enterable
```

Two details make this more than a convenience. First, external `view` functions are protected too —
they check the lock on entry without changing it, which is exactly the defence against read-only
reentrancy, where a getter is queried mid-callback while an invariant is temporarily
broken.<Cite src="vyper-docs-control-structures" /> Second, the documentation says the pragma is
preparation for a future release, probably in the 0.5.x line, where nonreentrant locks become the
language-wide default.<Cite src="vyper-docs-control-structures" />

The scoping is worth noting because it is the kind of thing that surprises people: the pragma applies
to the current file only. Import a module written without it and that module's functions behave as its
author intended — reentrant unless marked otherwise.<Cite src="vyper-docs-control-structures" />

<Check type="spot-bug" concept="vyper-safety-by-default">
A Vyper contract tracks per-user shares and reports a price:

```python
# pragma nonreentrancy on

total_assets: public(reentrant(uint256))
total_shares: public(reentrant(uint256))

@external
@view
def price_per_share() -> uint256:
    return self.total_assets // self.total_shares

@external
def withdraw(shares: uint256):
    amount: uint256 = self.total_assets * shares // self.total_shares
    send(msg.sender, amount, gas=50000)
    self.total_shares -= shares
    self.total_assets -= amount
```

The author enabled the file-wide pragma and considers reentrancy handled. Name every problem, in
order of severity.

<Answer>
**1. The state updates come after the external call.** `send` transfers value to `msg.sender`, which
may be a contract, and the two subtractions happen afterwards. During the callback,
`self.total_shares` and `self.total_assets` still hold their pre-withdrawal values. This is a
checks-effects-interactions violation and it is the root cause; everything below is about which
defences catch it.

**2. `withdraw` cannot be re-entered, and that part does work.** Under `#pragma nonreentrancy on`,
`withdraw` is protected without a decorator, so a callback that calls `withdraw` again
reverts.<Cite src="vyper-docs-control-structures" /> The direct reentrancy is closed.

**3. `price_per_share` has been deliberately un-protected, and this is the bug the pragma existed to
prevent.** Under the pragma an external `view` function checks the lock on
entry.<Cite src="vyper-docs-control-structures" /> But the two state variables were declared
`reentrant(uint256)`, and it is worth being exact about what that does: it un-protects *their
generated getters*. `price_per_share` is a separate `@view` function and is still protected by the
pragma — so a callback calling it directly reverts, while a callback reading `total_assets()` and
`total_shares()` through the un-protected getters sees the stale pair and can compute the same wrong
price itself.

The honest reading is therefore: the author disabled precisely the protection that read-only
reentrancy needs, on precisely the two variables that define the price, and left the derived function
guarded. An integrator quoting off the getters is exposed; one quoting off `price_per_share` is not.
Two paths to the same number, one defended.

**4. `send(..., gas=50000)` forwards a substantial budget** — enough for a callback that reads state
and calls another contract, which is what makes item 3 exploitable rather than theoretical.

**5. The division can revert.** A `total_shares` of zero makes `price_per_share` revert; checked
division is on and there is no `unsafe_div` here.<Cite src="vyper-docs-index" /> A `view` function
that reverts on an empty vault is an integration hazard whether or not you call it a bug.

**The fix, in order.** Move both subtractions above the `send`. Remove the `reentrant(...)` wrappers
unless there is a written reason for them. Then reconsider the gas argument. The reordering alone
closes the hole; the other two remove the need to reason about it again next quarter.
</Answer>
</Check>

## Where this pays off

**Lesson five is the one this has been building to.** The `@nonreentrant` decorator you just read
about — a language feature, a compiler-allocated slot, a lock you never see — is the exact feature
that three Vyper releases in 2021 compiled incorrectly, and the exploit landed in July 2023. Every
property in this lesson is a property of what the compiler *says* it does.

**On the security track**, read-only reentrancy is usually taught as a pattern you must remember to
defend. It is worth knowing that a language can make it the default, and worth asking of your own
stack which defences are defaults and which are things somebody has to remember.

**And in Solidity tomorrow**, the transferable habit is to treat scope as a property of a safety
mechanism. `unchecked` has a block scope. A modifier has a function scope. A reentrancy guard has a
contract scope, sometimes a slot scope. When you add a line to existing code, the question "what
region did I just land inside" is not paranoia — it is the whole of the diff at the top of this page.
