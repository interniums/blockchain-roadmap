Suppose the previous five lessons landed and someone on your team proposes writing the next vault in
Vyper. What is the honest answer?

Not "Vyper is safer" — lesson five disposed of that. Not "Vyper is minimal" — minimal is not a
property anyone deploys. The answer has to be a ledger, and this lesson is that ledger: what the
project is currently building, what the omissions cost in practice, and — separately, because it is
the part most readers will actually use — what reading Vyper does for you whether or not you ship a
line of it.

## Venom, and what a new backend means after lesson five

Venom is Vyper's newer intermediate representation and optimiser pipeline, an SSA-form design
inspired by LLVM IR, progressively replacing the original code generator.<Cite src="vyper-docs-compiling" />

**Its status in the current stable release is opt-in.** In 0.4.3 you activate it with a source
directive, `#pragma experimental-codegen` — aliased as `venom-experimental` — or the CLI flag
`--experimental-codegen`.<Cite src="vyper-docs-structure" /><Cite src="vyper-docs-compiling" /> The
0.4.2 release notes record the CLI flag being renamed from `--venom` to `--venom-experimental`, which
is a small change that says what the maintainers want you to
conclude.<Cite src="vyper-release-notes" />

**Most of the 0.4.x line's engineering went into it.** The 0.4.2 release alone lists common
subexpression elimination, dead-store elimination, a new calling convention, memory SSA analysis, a
function inliner and an assert optimiser, and reports benchmark contracts coming out about 5%
smaller.<Cite src="vyper-release-notes" /> The 0.5.0 alpha line adds a direct-to-Venom
pipeline.<Cite src="vyper-releases-gh" />

Now put that next to the previous lesson. A code generator is the component that decides where values
live, and where values live is where compiler bugs land. Rewriting one is the highest-leverage place
in the whole project for exactly the class of defect that drained those pools — and it is not a Vyper
peculiarity, since Solidity's own SSA CFG code generator is experimental in 0.8.36 for the same
reason.<Cite src="solidity-0836-release" />

Two things follow, and they pull in opposite directions.

**Against.** Vyper's bug bounty explicitly excludes experimental features, naming
`--experimental-codegen`, on the grounds that they are not intended for production and are unlikely
to affect production code.<Cite src="vyper-security-policy" /> That is a reasonable scoping decision
and it is also a statement about what you are on your own for if you enable the flag.

**For.** The response to 2023 was partly a testing programme, and it is visible in the changelog: the
0.4.2 notes include adding tests through an hevm harness and basic semantic-check machinery for
Venom.<Cite src="vyper-release-notes" /> That is the maintainers acting on their own post-mortem,
which listed comparing compiler output against a language specification and using formal verification
for bytecode verification among the concrete steps to
take.<Cite src="vyper-postmortem" /> A backend built with an equivalence-checking harness from the
start is a different proposition from one built without.

The practical reading for 2026: Venom is where the performance is going and it is not where your
production bytecode should come from yet. Both halves of that are in the flag's name.

### There is no OpenZeppelin

This is the largest single cost and it is worth being precise about the shape of it.

Vyper ships **interfaces** for the common standards — `from ethereum.ercs import IERC20`, and an
`implements: IERC20` declaration that fails compilation if any interface function is
missing.<Cite src="vyper-docs-interfaces" /> It has begun moving standard-library functionality into
Vyper itself; 0.4.2 moved `sqrt` into a pure Vyper math module as part of a refactor intended to
enable more of the same.<Cite src="vyper-release-notes" />

Interfaces are not implementations. There is no Vyper equivalent of the body of audited, adversarially
reviewed, widely deployed code that [OpenZeppelin functions as](/c/oz-is-the-stdlib) on the Solidity
side. Writing an access-control system in Vyper means writing an access-control system, with the
review budget that implies, rather than importing one whose failure modes are documented in a decade
of issues.

Weigh that honestly in both directions. You lose enormous reuse. You also lose the risk that comes
with importing a large dependency you did not read — which is a real risk, and one that the
upgradeable-proxy material on this track illustrates at length.

### Some patterns needed the language to grow features

Because there is no inline assembly, anything requiring raw EVM behaviour must arrive as a builtin on
the maintainers' schedule. The gap was real. It is now substantially closed:

- `create_minimal_proxy_to` deploys an [ERC-1167](/c/clone-eip1167) forwarder — cheap to create,
  paying one `DELEGATECALL` on every call, with no constructor and no code check at the
  target.<Cite src="vyper-docs-builtins" /><Cite src="eip-1167" />
- `create_copy_of` makes a byte-for-byte copy of the runtime code at a target, cheap to call and
  expensive to create at 200 gas per deployed byte.<Cite src="vyper-docs-builtins" />
- `create_from_blueprint` deploys from initcode stored on chain and *does* invoke a
  constructor.<Cite src="vyper-docs-builtins" />
- `raw_create`, added in 0.4.2, is the low-level form: arbitrary initcode plus ABI-encoded
  constructor arguments, with an optional salt selecting `CREATE2` over
  `CREATE`.<Cite src="vyper-docs-builtins" /><Cite src="vyper-release-notes" />
- `@raw_return`, added in 0.4.3, lets an external function return bytes with no ABI-encoding, which
  is what a forwarding proxy needs in order not to double-wrap its callee's
  output.<Cite src="vyper-release-notes" /><Cite src="vyper-docs-control-structures" />

### The type system has a documented rough edge in the stable release

Worth naming because it is the sort of thing a mature ecosystem files down early.

Vyper's stable documentation states that for interface functions returning a bounded type, the upper
bound declared in the interface acts as a *lower* bound on the implementation: an interface promising
`String[1]` is satisfied by an implementation returning something longer. The documentation adds that
this behaviour might change in future.<Cite src="vyper-docs-interfaces" />

The 0.5.0 pull request that fixes it says what it is plainly — the check was inverted, deliberately,
with a note, because there was no other way to express "any length" in an interface; the fix
introduces the `T[...]` wildcard so the workaround is no longer
needed.<Cite src="vyper-pr-unbounded-types" /> A known variance unsoundness, worked around in the
shipping release and repaired in an alpha, is a small-team signal. It is not a scandal; it is a cost
line.

### Release cadence and target lag

State these as dates rather than as a verdict.

The latest published stable release is 0.4.3, dated 19 June 2025 in the release
notes.<Cite src="vyper-release-notes" /><Cite src="vyper-pypi-json" /> The 0.5.0 alpha line opened in
May 2026, with three alphas released between May and June
2026.<Cite src="vyper-releases-gh" /> So as of 26 August 2026 the stable line has been unchanged for
fourteen months while a breaking major matures in the open.

There is a consequence you have to handle at compile time. 0.4.3's default EVM target is `prague`,
set as a breaking change in that release.<Cite src="vyper-release-notes" /> Against a 2026 mainnet
that is a lagging default, so set `--evm-version` or `#pragma evm-version`
explicitly.<Cite src="vyper-docs-compiling" /> The compiler team maintains an informal policy of
supporting three years of hard-fork rulesets, which is the window you are working
inside.<Cite src="vyper-docs-compiling" />

### Concentration

Vyper's production footprint is concentrated, with Curve as the flagship and a set of protocols
around it.<Cite src="curvefi-contracts" /> One vivid indicator of how tight that coupling is: the
compiler's own test suite carries Curve example contracts, and was expanded with more of them during
the 0.5.0 alpha line.<Cite src="vyper-releases-gh" />

Read that both ways, because both are true. Having your largest user's contracts inside the
compiler's regression suite is an unusually direct feedback loop, and it is the loop whose absence the
2023 post-mortem identified as a contributing factor.<Cite src="vyper-postmortem" /> It is also
evidence that the language's fate and one protocol's fate are entangled, which is a legitimate input
to a procurement decision and not a criticism of anybody's engineering.

<Aside kind="note">
Two numbers deliberately absent from this lesson: Vyper's share of deployed contracts, and the size
of the auditor pool. Both circulate, neither is sourced in a way that survives checking, and a
decision made on an unsourced adoption percentage is worse than one made on the qualitative statement
that the ecosystem is much smaller — which is not in dispute.
</Aside>

## What transfers, whether or not you ship it

Here is the part that pays for the module regardless of what you decide.

**One: name what a function body does not tell you.** Vyper's whole argument is that a reader should
finish a function body knowing what it does.<Cite src="vyper-docs-index" /> Turn that into a question
you ask of Solidity: *what did I have to open?* Every base contract, every modifier, every overload,
every assembly block, every `using for` on the list is a place your belief about the code came from
somewhere other than the code. That list is your review checklist, and it is different for every
contract.

**Two: treat an unbounded loop as a liveness bug.** Not a gas item. The procedure is two lines — find
the ceiling on the iteration count, multiply by the worst case cost of one iteration — and if either
factor is unknown, the loop is unbounded no matter how it reads.

**Three: put the compiler on the ledger.** Pin it, record it, check the pin against advisories on a
schedule, and reproduce the deployed bytecode from source with a second pair of hands. Lesson five is
the argument; the runbook is the artefact.

**Four, which the module earned along the way: scope is a property of every safety mechanism.**
`unchecked` has block scope. A modifier has function scope. A reentrancy guard has contract scope, or
slot scope, or — under Vyper's `#pragma nonreentrancy on` — file scope. When you add a line to
existing code, "which region did I just land in" is a question with an answer, and the answer is
rarely written next to the line.

<Check type="explain" concept="vyper-ecosystem-cost">
Your team is building a stablecoin AMM. Two engineers know Vyper well; the rest know Solidity. The
protocol will be immutable once deployed, will hold significant value, and will be audited before
launch.

Make the call, and defend it. Then say what would change your answer.

<Answer>
There is no universally right answer here, so what follows is a defensible one with its reasoning
exposed — which is the actual skill.

**Arguments for Vyper in this specific case.** The contract is immutable, so the strongest
counter-argument to Vyper — that its ecosystem gives you less to lean on over years of maintenance —
is weakest here; there is no maintenance. It is an AMM, which is the single domain where Vyper has
the deepest production track record and the largest body of comparable code to read against.<Cite
src="curvefi-contracts" /> And a contract designed to be audited benefits directly from a language
whose stated goal is that an auditor can read a function top to
bottom.<Cite src="vyper-docs-index" />

**Arguments against.** Two engineers out of a team is a bus factor, and it is also a review factor —
most of your team cannot review the code that holds the money. The auditor pool is smaller, which
shows up as scheduling and as price. And you inherit a compiler whose stable line has not moved since
June 2025, so a fix you need may only exist in a breaking major that is still in
alpha.<Cite src="vyper-releases-gh" /><Cite src="vyper-pypi-json" />

**The decisive question is not the language.** It is: who reviews this, and can they? A contract in
the language your reviewers read fluently, with a bounded loop written by hand and a compiler pinned
and re-checked quarterly, is safer than one in the theoretically clearer language that three people
can read. The lesson of this module is not that clarity is a language feature. It is that clarity is
a property of the pairing of the code with its readers.

**What would change the answer.** Toward Vyper: if the audit firm you have retained does Vyper work
routinely; if the design is close enough to an existing Curve pool that you are reading production
code rather than inventing; if a stable 0.5.0 has shipped with an audit against it, since the
versioning policy attaches the audit promise to x.0.0
releases.<Cite src="vyper-security-policy" /> Away from Vyper: if the protocol turns out to need
upgradeability, which pulls in proxy patterns where the Solidity ecosystem's accumulated failure
knowledge is a genuine asset; if the two Vyper engineers are also the two people who would be on call.

**And the answer that is always wrong** is the one that cites the 2023 incident as a reason not to use
Vyper. That incident is a reason to pin your compiler, check advisories, and reproduce your bytecode
— in either language.<Cite src="vyper-postmortem" /> Reasoning about it as a fact about Vyper rather
than a fact about compilers is how you end up making the same mistake with a different toolchain.
</Answer>
</Check>

## Where this pays off

**The reflection prompt closes the module**, and it is a writing exercise rather than a reading one:
produce the compiler-risk section of a deployment runbook, then find the line your last project would
have failed. Most people find it in the last two rows.

**Track 05 makes the runbook executable.** Version pinning, reproducible builds, bytecode
verification and CI checks stop being a list of good intentions once they are a workflow with a
failing job attached.

**Track 06 takes the incident apart again from the attacker's side.** You have the mechanism; what
that track adds is the economics — why those specific pools, why that specific ordering, and how the
same reasoning finds the next one.

**And the habit worth keeping** is the one this module has been drilling under different names. For
any claim about how a contract behaves, ask where the claim comes from: the code in front of you, a
file you have not opened, a language default, or a compiler that promised. Only the first of those is
evidence you have actually examined.
