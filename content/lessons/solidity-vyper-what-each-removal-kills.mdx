"Vyper removes features" is the sentence everybody repeats, and on its own it teaches nothing. A
language that removes features is not thereby better; it is smaller. The interesting claim is
narrower and checkable: for each removal, there is a specific way a reader forms a false belief about
a program, and the removal makes that way unavailable.

So work removal by removal. For each one: what the documentation says the reading failure is, which
Solidity bug class inherits from it, what Vyper offers instead, and — the part that keeps this
honest — where the substitute is worse.

## No inheritance

The documentation's objection to class inheritance is that it requires readers to jump between
multiple files, and to understand precedence rules to answer which class's version of a function
actually runs.<Cite src="vyper-docs-index" />

You have already met the machinery it is objecting to. [C3 linearisation](/c/sol-c3-linearisation)
gives a deterministic answer to that question, and determinism is not the issue — the issue is that
the answer is not derivable from the function body, or from the file, or from any one place. It is a
property of a declaration order elsewhere.

Three Solidity bug classes descend from that.

**Which implementation runs.** The [`virtual` and `override`](/c/sol-override-virtual) machinery
means a call inside a base contract can dispatch into a derived contract written later by someone
else. Reading the base tells you what the author intended, not what executes.

**Who owns the slot.** Every base contributes state variables to one flat layout, so a
[storage slot](/c/storage-slot) is assigned by the sum of all bases in linearisation order. Insert a
variable into a base and every slot after it moves. This is the mechanism behind
[storage collisions](/c/storage-collision) in upgradeable systems.

**What ended up exposed.** Inheriting a contract inherits its `external` and `public` functions into
your ABI. The dispatch table of a deployed contract is the union of everything up the chain, which is
not a list anybody wrote down.

### The replacement: modules that declare their relationship

Vyper's answer since 0.4.0 is a module system.<Cite src="vyper-release-notes" /> Any `.vy` file is a
valid module, and importing one gives you nothing by default — the documentation states that modules
are opt-in by design, and that any operation involving state or exposing external functions must be
explicitly opted into with `exports`, `uses` or `initializes`.<Cite src="vyper-docs-structure" />

Walk one through, naming what each declaration buys.

```python
# ownable.vy  — a module, and also a perfectly valid contract
owner: address

@deploy
def __init__():
    self.owner = msg.sender

def _check_owner():
    assert self.owner == msg.sender

@external
def update_owner(new_owner: address):
    self._check_owner()
    self.owner = new_owner
```

**Subgoal: use a helper that touches no state, and owe nothing.** A pure helper from an imported
module can be called immediately, with no declaration, because it has no state to place.<Cite
src="vyper-docs-modules" /> That is the cheap case, and it is the majority of real code reuse.

**Subgoal: declare where the module's state lives before touching it.** To use `owner`, the importing
contract must write `initializes: ownable`. That declaration does two jobs: it fixes the module's
position in the storage layout, and it creates an obligation to call the module's `__init__`.
Invoking that `__init__` more than once is a compile-time error.<Cite src="vyper-docs-modules" />

**Subgoal: separate "I use this state" from "I own this state".** A library that manipulates another
module's state but wants its consumer to initialise it writes `uses: ownable` instead. Such a file is
a valid module and *not* a valid contract — it cannot produce bytecode until somebody
initialises what it uses.<Cite src="vyper-docs-modules" />

**Subgoal: make dependency wiring explicit at the top level.** When the consumer initialises a module
that itself uses another, it writes the dependency out:

```python
import ownable
import ownable_2step

initializes: ownable
initializes: ownable_2step[ownable := ownable]

@deploy
def __init__():
    ownable.__init__()
    ownable_2step.__init__()

exports: ownable_2step.__interface__
```

**Subgoal: choose what appears in the ABI, one line at a time.** External functions from a module are
not exposed in the importing contract unless exported. The documentation calls this a safety feature:
externally facing functionality must be explicitly stated at the top level of the compilation
target.<Cite src="vyper-docs-modules" /> `exports` accepts a single function, a tuple of them, an
interface, or `module.__interface__` for everything.<Cite src="vyper-docs-modules" />

That is the bug class from three paragraphs ago, closed. The deployed dispatch table is a list
somebody wrote down.

The rules behind this are stated as a type-system discipline rather than a convention: a module must
be used or initialised before its state can be accessed, may be used many times, and — if its state
is touched — must be initialised exactly once. The documentation credits Rust's borrow checker as
inspiration and describes initialisation as an affine constraint promoted to a linear
one.<Cite src="vyper-docs-modules" />

<Aside kind="warn">
The substitute is not free of sharp edges. The documentation warns that constructors should be
called in dependency order and that you can get unexpected behaviour otherwise, noting the compiler
*may* enforce this in future.<Cite src="vyper-docs-modules" /> So "explicit" here means the
dependency is written down and checked, while the *ordering* of the `__init__` calls is still yours
to get right. Compare Solidity, where [base constructor order](/c/sol-constructor-order) is decided
for you by the linearisation and is therefore not yours to get wrong — a genuine point in
Solidity's favour on this one axis.
</Aside>

### The bug class did not stop being real

Solidity 0.8.36, released 9 July 2026, fixed a compiler bug in which the code emitting a warning
about a contract's storage base slot could accidentally reverse the annotation describing the
contract's inheritance linearisation.<Cite src="solidity-0836-release" /> The release notes give the
consequences: it affects analysis and code generation, most notably the initialisation order of state
variables and the invocation order of constructors and virtual
functions.<Cite src="solidity-0836-release" />

Sit with that. The precedence rule Vyper removed because readers cannot follow it is complex enough
that the compiler got it backwards, in a shipping release, this year. That is not an argument that
Solidity is unsafe — the bug is found and fixed. It is an argument that "which base runs" is
genuinely hard, and that the difficulty is not only in your head.

## No modifiers

The documentation's objection is specific and worth reading as a review heuristic rather than a
language opinion: a modifier name looks too innocuous for something that can add arbitrary
pre-conditions, post-conditions or state changes, and it encourages code where execution jumps around
the file, which harms auditability. Its recommendation for the usual case — a single check before the
body — is to inline the check as an assertion.<Cite src="vyper-docs-index" />

The Solidity bug classes are the ones you already know by name.

**The placeholder can appear anywhere, or twice, or not at all.** Where
[`_;` sits](/c/sol-modifier-placeholder) decides whether the modifier's code is a pre-condition, a
post-condition, or both; a modifier with no placeholder means the body never
runs.<Cite src="solidity-docs-contracts" />

**Order is semantics.** [Modifier order](/c/sol-modifier-order) changes behaviour, and the ordering
lives on the function signature line rather than anywhere the effects are visible.

**Modifiers can write state.** Reentrancy guards do, pausability flags do, accounting modifiers do.
A reader who treats a modifier as "a check" is reading a category, not the code.

Vyper's version of the owner check is the check:

```python
@external
def update_owner(new_owner: address):
    assert self.owner == msg.sender
    self.owner = new_owner
```

The cost is exactly what it looks like: repetition, and the possibility of forgetting. Vyper's
position is that a missing line in a body is visible to someone reading the body, while a missing
modifier is an absent token on a signature line that nobody was scanning. Both are absences. They
differ in where a reviewer's eye is.

### The exception that proves the rule

`@nonreentrant` is a decorator that injects code before and after the body — which is, structurally,
a modifier.<Cite src="vyper-docs-control-structures" /> So is `@payable`, in the sense that it
changes what the prologue checks.

The distinction Vyper draws is not "no injected code" but "no *user-defined* injected code". The
decorator set is closed and documented: `@external`, `@internal`, `@deploy`, `@pure`, `@view`,
`@payable`, `@nonreentrant`, `@raw_return`.<Cite src="vyper-docs-control-structures" /> Every one has
compiler-defined semantics you can look up once and know forever. What you cannot do is add a ninth
one whose meaning lives in your repository.

Say that out loud, because it is the actual design principle and it generalises: the objection was
never to abstraction. It was to abstraction whose definition ships with the codebase rather than with
the language.

## No overloading, of functions or operators

Function overloading is refused because it causes confusion about which function is called, making it
easier to write misleading code — the documentation's example is a `foo("hello")` that logs and a
`foo("hello", "world")` that steals your funds — and because it makes code harder to search, since
you must track which call reaches which definition.<Cite src="vyper-docs-index" />

The searchability argument is the one that survives contact with a real codebase. Grep for a function
name in Vyper and you have found the definition. In a language with overloading, grep gives you
candidates and you resolve by arity and type, by hand, at every call site.

There is a selector-space consequence too. One name maps to one signature, which shrinks the space in
which a [selector collision](/c/abi-selector-collision-risk) can be engineered and removes the case
where a diff changes which overload a call reaches without changing the call.

The honest complication, from the previous lesson: default arguments still generate N+1 selectors for
N defaults, so one `def` can occupy several rows of the dispatch
table.<Cite src="vyper-docs-control-structures" /> The difference from overloading is that every one
of those rows runs the same body.

### Where the stated rationale over-reaches

Operator overloading is refused on the grounds that `+` could be made to execute commands invisible
at first glance, such as sending funds the user did not intend to send.<Cite src="vyper-docs-index" />

That rationale does not transfer cleanly to modern Solidity, and it is worth being precise about why
rather than repeating it.

Solidity's `using {f as +} for T` attaches an operator to a type, but the type must be a user-defined
value type, the function must be `pure`, and the operator definition must be
global.<Cite src="solidity-docs-contracts" /> A `pure` function cannot read or write state and cannot
call a non-`pure` function, so it cannot send funds. The specific horror in the rationale is not
constructible there.

What remains true is milder and still worth something: a `+` on a user-defined type is a call to a
function whose name is `+`, and grep does not find it. That is the searchability argument again, and
it is the one Vyper's design is actually built on.

<Aside kind="note">
Notice the shape of that correction, because you will need it constantly. A design rationale is
evidence about *why a choice was made*, at the time it was made. It is not evidence about the current
state of the alternative. Quoting a 2018-era objection at a 2026 language feature is how confident,
wrong comparisons get written.
</Aside>

## No inline assembly

The rationale here is the sharpest of the four, and it is not the one people assume. Vyper's stated
objection to inline assembly is that adding it would make it no longer possible to search for a
variable name in order to find all the places where that variable is read or
modified.<Cite src="vyper-docs-index" />

That is a claim about *grep*, not about safety. And it is exactly right: an assembly block can
`sstore` to a slot number, so the set of writers to a variable stops being the set of textual
occurrences of its name. The reader loses the ability to enumerate.

The safety consequence follows from it rather than standing alone. Because there is no assembly, the
compiler knows the full semantics of every instruction it emits, so no hand-written opcode can
violate the language's invariants about bounds, arithmetic or memory. You have seen the Solidity side
of this: assembly [removes the safety net](/c/assembly-removes-the-safety-net), and the
[`memory-safe` annotation](/c/memory-safe-annotation) is a
[promise the compiler does not verify](/c/annotation-is-unverified).

The cost is real and Vyper pays it in a specific currency: every pattern that needs raw EVM behaviour
must arrive as a dedicated builtin, on the maintainers' schedule rather than yours. The current menu
covers most of what assembly is used for in Solidity:

- `raw_call(to, data, max_outsize=..., value=..., is_delegate_call=..., is_static_call=...,
  revert_on_failure=...)` for arbitrary calls, returning `Bytes[max_outsize]`.<Cite src="vyper-docs-builtins" />
- `create_minimal_proxy_to` for an ERC-1167 forwarder, `create_copy_of` for a byte-for-byte runtime
  copy, `create_from_blueprint` to deploy from stored initcode with a constructor, and `raw_create`
  for low-level `CREATE` and `CREATE2` with arbitrary initcode.<Cite src="vyper-docs-builtins" />
- `@raw_return`, added in 0.4.3, to return bytes without ABI-encoding, which is what a forwarding
  proxy needs.<Cite src="vyper-release-notes" />

Look closely at `raw_call`'s signature, because it shows what "the compiler knows the semantics"
buys. The return is `Bytes[max_outsize]` — a bounded type, with the bound supplied at the call
site.<Cite src="vyper-docs-builtins" /> A callee returning more data than that has its output
truncated rather than copied wholesale into your memory. The returndata-bomb surface that Solidity
callers must think about explicitly is closed by the type of the expression.

<Check type="spot-bug" concept="vyper-no-inheritance">
A team is porting a Solidity contract to Vyper. Their Solidity version inherits from an internal
`Pausable` base and an internal `Accounting` base, and one function carries `whenNotPaused`.

Their Vyper port imports two modules, declares `initializes: pausable` and `initializes: accounting`,
calls both `__init__` functions in its own constructor, replaces the modifier with an inline
`assert not pausable.paused`, and exports the module functions it wants.

It compiles. A reviewer says the port has changed the deployed ABI and may have changed behaviour on
upgrade. Name the two things that changed, and say which one the compiler could have caught.

<Answer>
**The ABI changed, and the change is the point.** In Solidity, inheriting `Pausable` and `Accounting`
pulled every one of their `external` and `public` functions into the deployed dispatch table
automatically. In Vyper nothing is exposed unless it appears in an `exports`
declaration.<Cite src="vyper-docs-modules" /> So the port's ABI is exactly the functions the team
listed — which is almost certainly a strict subset of what the Solidity version deployed.

That is a genuine behaviour change for integrators, and it is the deliberate one. The right response
is not to re-add the missing functions reflexively but to look at the Solidity contract's actual
selector list, decide which entries were intended, and export those. Most teams discover at this
point that they were exposing functions nobody meant to expose. The
[surface a contract presents](/c/sol-state-var-visibility) is supposed to be a decision.

**The storage layout changed, and this is the one to be careful about.** Solidity laid out
`Pausable`'s and `Accounting`'s variables in linearisation order, interleaved with the derived
contract's own. Vyper lays out modules according to the `initializes` declarations. There is no
reason the two orders agree, and no reason the slot counts agree. For a fresh deployment this is
harmless. Behind a proxy holding live state it is a
[storage collision](/c/storage-collision) waiting on the next write.

**Which one the compiler could have caught: neither, and that is the honest answer.** The Vyper
compiler checked everything it was asked to check — that each module whose state is touched is
initialised exactly once, that the exports exist, that the assertion type-checks.<Cite
src="vyper-docs-modules" /> It has no knowledge of the Solidity contract this is replacing. Neither
change is a compile error in either language; both are only visible by diffing the two artefacts.

**What would have caught them.** Compare the two dispatch tables — Vyper emits selector data through
its `-f method_identifiers` output, and Solidity through its own.<Cite src="vyper-docs-compiling" />
Then compare the two storage layouts: `vyper -f layout` prints Vyper's, and Solidity's layout output
prints the other.<Cite src="vyper-docs-compiling" /> Two diffs, both mechanical, both the sort of
thing worth wiring into CI once rather than remembering.

**The under-discussed third item.** The inline `assert not pausable.paused` is a *pre*-condition,
placed at the top of the body. If the original modifier's `_;` was positioned so that some code ran
before the check, or if a second modifier ran ahead of it, the port has silently changed the order of
effects.<Cite src="solidity-docs-contracts" /> Porting away from modifiers means re-deriving the
order, not just the checks — and this is precisely the information that was never visible from the
Solidity function body either.
</Answer>
</Check>

## Where this pays off

**Bounded loops and bounded types**, next, are the fifth and sixth removals, and they are the ones
with a formal payoff attached: the design principles claim decidability, meaning a precise upper
bound on the gas any Vyper function call can consume.<Cite src="vyper-docs-index" /> That turns a
style rule into a liveness guarantee.

**The `-f layout` output** you just met in passing is the tool at the centre of lesson five. The July
2023 incident is a story about a compiler that put two things in different storage slots when they
should have shared one — and about the fact that its own layout output made that invisible.

**Reading Solidity afterwards.** The transferable skill is not a preference. It is a question you can
now ask of any function: *what do I have to open to know what this does?* Every base contract,
modifier, overload and assembly block on that list is a place your belief about the code is being
supplied by something other than the code in front of you.
