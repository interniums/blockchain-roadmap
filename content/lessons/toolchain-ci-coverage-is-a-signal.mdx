Two functions, one test, and a number that should end the argument about whether the code is tested.

```solidity
contract Counter {
    uint256 public number;
    function setNumber(uint256 newNumber) public { number = newNumber; }
    function increment() public { number += 2; }   // seeded bug: should be number++
}
```

```solidity
contract EmptyTest is Test {
    Counter c;
    function setUp() public { c = new Counter(); }

    // Calls everything. Asserts nothing.
    function test_TouchesEverything() public {
        c.setNumber(1);
        c.increment();
    }
}
```

```console
$ forge test
[PASS] test_TouchesEverything() (gas: 29072)
Suite result: ok. 1 passed; 0 failed; 0 skipped

$ forge coverage
| File            | % Lines       | % Statements  | % Branches    | % Funcs       |
| src/Counter.sol | 100.00% (4/4) | 100.00% (2/2) | 100.00% (0/0) | 100.00% (2/2) |
```

Green suite. One hundred percent on every column. A counter that increments by two.<Cite src="measured-forge-1-7-1" />

Nothing here is a trick. The test calls both functions, so both are covered; every line executes, so
every line is covered. Coverage answered its question correctly. The question is just not the one
anyone thinks they are asking.

## What the number is

`forge coverage` runs your test suite with instrumentation and reports, per file, which lines,
statements, branches and functions were reached.<Cite src="forge-coverage-reference" /> Reached.
Not checked. There is no column for "an assertion constrained the result", because there is no way
for the instrumentation to know that a `assertEq` two frames up was about the value this line
produced.

That gives coverage exactly one direction of validity:

- **Low coverage is real information.** A file at zero percent has never executed under test. That is
  a fact about your suite and it is worth finding.
- **High coverage is not.** It is consistent with a thorough suite and equally consistent with the
  one above.

Everything else in this lesson follows from holding that asymmetry firmly.

  belief="High line coverage means the code is well tested."
  reality="Coverage measures execution, not assertion. A test that calls every function and asserts nothing scores perfectly, and a seeded bug in a covered line changes neither the number nor the suite result."
  why="It is the only testing metric that produces a single comparable number, and single comparable numbers get treated as summaries of the thing they were extracted from."

## Reading a report without being misled by it

**Subgoal 1 — pick the format the downstream tool wants.** On forge 1.7.1, `--report` takes
`summary` (default), `lcov`, `debug` or `bytecode`, and the flag may be given more than
once.<Cite src="measured-forge-1-7-1" /><Cite src="forge-coverage-reference" /> LCOV is the one
every coverage service and every renderer understands:

```console
$ forge coverage --report lcov --report-file lcov.info
```

`--lcov-version <MAJOR[.MINOR]>` selects the tracefile format, defaulting to `1`; `2.0` adds line-end
numbers for functions and `2.2` changes the format of functions.<Cite src="measured-forge-1-7-1" />
If a coverage service rejects your file, this flag is the first thing to check and almost nobody
knows it exists.

**Subgoal 2 — notice what is dragging the number down before you report it anywhere.** Here is the
same tiny project's default summary in full:<Cite src="measured-forge-1-7-1" />

```text
| File                 | % Lines       | % Statements  | % Branches    | % Funcs       |
| script/Counter.s.sol | 0.00% (0/5)   | 0.00% (0/3)   | 100.00% (0/0) | 0.00% (0/2)   |
| src/Counter.sol      | 100.00% (4/4) | 100.00% (2/2) | 100.00% (0/0) | 100.00% (2/2) |
| Total                | 44.44% (4/9)  | 40.00% (2/5)  | 100.00% (0/0) | 50.00% (2/4)  |
```

The contract is at 100%. The headline is 44.44%. The difference is entirely a deploy script that
nobody tests and nobody should — and on 1.7.1 the default report already excludes `test/` while
including `script/`, so the standard advice to "drop test and script" is half stale.<Cite src="measured-forge-1-7-1" />

Foundry's coverage guide gives the config key, with a caveat that matters:<Cite src="foundry-coverage-guide" />

```toml
skip_files = ["script/**", "src/mocks/**"]
```

The guide notes that skipping a file "does not prevent its code from executing" — you are removing it
from the report, not from the run.<Cite src="foundry-coverage-guide" /> Opinionated templates do the
same job downstream by filtering the LCOV file with the `lcov` CLI before rendering, and pair it with
a threshold gate.<Cite src="scopelift-foundry-template" />

**Subgoal 3 — read the columns you did not ask for.** Look at the branch column: `100.00% (0/0)`.
There are no branches in `Counter.sol`, so the denominator is zero and the ratio is reported as
perfect.<Cite src="measured-forge-1-7-1" /> Every branch-coverage number you ever see needs the
parenthesised counts read alongside it, because "100% of nothing" and "100% of forty" render
identically and mean nothing alike.

<Aside kind="note">
The four columns are not redundant, and the one that carries the most information is usually
**functions**. A file at 100% lines and 60% functions is a file where a few functions do all the work
and the rest have never been called at all — which is a much more actionable sentence than any
percentage. If you only look at one column in a review, look at that one.
</Aside>

## The build being measured is not the build you ship

This is the part that turns coverage from "an imperfect metric" into "a metric computed against
different bytecode", and Foundry's own guide states it without hedging.

> "For accurate source maps, `forge coverage` disables optimizer settings and `viaIR` by default."
> "The coverage build can therefore differ from the production build in bytecode shape, gas use, and
> inlining."<Cite src="foundry-coverage-guide" />

That trade is deliberate and defensible: an optimised, inlined build has source maps too coarse to
attribute execution to source lines, so coverage turns the optimiser off in order to be able to point
at anything at all. But it means the artifact under measurement is not the artifact under review, and
on a project that *requires* the IR pipeline to compile, the difference is not a nuance — it is a
compile failure.

The failure is a stack-too-deep error raised during the coverage build on code that `forge test`
compiles fine, and it has been reported from both sides of the toolchain: as a Foundry issue about
`forge coverage` failing with `--ir-minimum`,<Cite src="foundry-issue-3357" /> as a Foundry issue
about coverage not using the project's via-IR and optimizer settings,<Cite src="foundry-issue-6592" />
and as a compiler-side issue describing coverage failing with stack-too-deep under `--via-ir` while
`forge test` succeeds.<Cite src="solidity-issue-15775" /> All three are long-lived.

The documented workaround is a flag whose own help text tells you the price:<Cite src="measured-forge-1-7-1" />

```text
--ir-minimum
    Enable viaIR with minimum optimization

    This can fix most of the "stack too deep" errors while resulting a relatively accurate
    source map.
```

"Most" and "relatively accurate" are the honest words there, and they are the tool's own. A report
produced this way is an approximation of an approximation: coverage of a differently-compiled
artifact, attributed through source maps the tool describes as *relatively* accurate.

<Aside kind="stop">
**Do not conclude that stack-too-deep has been solved.** Solidity 0.8.36's release announcement
reports that the SSA-form code generator gained stack-to-memory spilling, "which effectively solves
stack-too-deep on that backend" — and then states the constraint in the same section: "It remains
experimental, enabled with `--experimental --via-ssa-cfg`, and is not yet the default for
`--via-ir`."<Cite src="solidity-0836-release" /> Stabilising it is named as a priority for the
following six months, which is a roadmap, not a shipped default.<Cite src="solidity-0836-release" />
Meanwhile Foundry's own resolved default on 1.7.1 is `via_ir = false`, so the ordinary project is
compiling through legacy codegen and the ordinary coverage run is compiling through something
different again.<Cite src="measured-forge-1-7-1" />
</Aside>

## Why there is no number to gate on

Every coverage threshold in circulation — 80, 90, 100 — is folklore. No source in this curriculum's
research links a coverage percentage to a defect rate in smart contracts, and the metric's structural
problem makes it unlikely one could: the cheapest way to raise the number is to add tests that
execute code without constraining it, which is precisely what the opening example does.

That is a real dynamic, not a hypothetical. A threshold gate creates pressure to make a number go up.
The lowest-effort way to make this particular number go up is the one that adds no information. A gate
that is easiest to satisfy by defeating its own purpose is a gate that will be satisfied that way,
eventually, by someone under deadline.

So the useful shape is a comment, not a gate:

```yaml
      - name: Coverage
        run: forge coverage --report lcov --report-file lcov.info
```

…rendered as a pull-request comment showing which files moved. The signal a reviewer can act on is
never "we are at 87%". It is "this new file is at 0%" or "this file dropped 40 points", and both of
those survive perfectly well without a threshold attached.

<Aside kind="warn">
Coverage in the pipeline is also a *cost* decision that gets skipped. It requires a separate,
differently-configured compilation of the whole project plus a full instrumented test
run.<Cite src="foundry-coverage-guide" /> On a large repository that is frequently the slowest job in
the workflow, and it is producing the signal with the weakest claim on a merge decision. If something
has to move to a nightly schedule, this is the first candidate — not the fuzzing.
</Aside>

## What actually covers the gap

The reason to be precise about coverage's limits is that the alternative is concrete rather than
aspirational. Coverage asks whether a line ran. An invariant asks whether a property survived an
arbitrary sequence of calls, which is a question about *behaviour* rather than about
*reach*.<Cite src="foundry-invariant-testing" />

Run the two against the opening example. Coverage reports 100% and says nothing. A solvency-style
invariant — the counter never advances by more than one per `increment` call — falls over on the
first generated sequence, because the property is stated independently of the implementation and the
implementation violates it.

That is not an argument for deleting coverage. It is an argument about what each instrument is for:
coverage finds code nobody looked at, and properties find code that does the wrong thing. A pipeline
that gates on the first and skips the second has its budget allocated backwards, and the
[last lesson in this module](/c/campaign-tiering) is about spending it the other way round.

<Check type="spot-bug" concept="coverage-is-not-correctness">
A team requires 90% line coverage to merge. A pull request adds a withdrawal path and lands at 88%.
The author adds this and the gate goes green:

```solidity
function test_CoverWithdrawPaths() public {
    vault.deposit(1 ether);
    vault.withdraw(0.5 ether);
    vm.expectRevert();
    vault.withdraw(100 ether);
    vault.emergencyWithdraw();
}
```

Say what this test proves, what the gate now certifies, and what you would ask for in review.

<Answer>
**What it proves.** That four calls did not revert unexpectedly, and that one call reverted for *some*
reason.

`vm.expectRevert()` with no argument matches any revert.<Cite src="foundry-cheatcode-expect-revert" />
The third call could
be reverting because the amount exceeds the balance — the intended check — or because the vault is
paused, or because of an arithmetic panic in unrelated code, or because `withdraw` is broken and
reverts on every input. All four produce the same green.

The other three calls assert nothing at all. `deposit` could mint the wrong number of shares.
`withdraw` could transfer the wrong amount, or transfer to the wrong address, or transfer nothing.
`emergencyWithdraw` could drain the vault to `address(0)`. Every one of those executes the same
lines and moves the number the same way.

**What the gate now certifies.** That 90% of lines executed. It certified that before this test too;
the test changed which lines, not what was verified. The gate's guarantee was never stronger than
"was reached", and the pull request satisfied it exactly as specified.

**What to ask for in review.** Not "add assertions" — that invites the same test with `assertTrue`
sprinkled on it. Ask for the *properties*, one per call:

- After `deposit(x)`, the caller's share balance rose and total assets rose by `x`.
- After `withdraw(y)`, the caller received exactly `y` and the vault's accounting fell by `y`.
- The over-withdrawal reverts **with a named error** — `vm.expectRevert(Vault.InsufficientBalance.selector)` —
  so the test fails if the revert reason changes to something else.
- After `emergencyWithdraw`, funds landed at a specific address the test names.

**And the structural fix.** The 88% is not the problem; the threshold is. Replace it with a coverage
*comment* that reports per-file deltas, and put the merge-blocking budget on a property or invariant
that states the vault's solvency independently of the implementation.<Cite src="foundry-invariant-testing" />
Then a reviewer sees that the withdrawal path is newly covered — useful — without anyone being
obliged to manufacture a number.
</Answer>
</Check>

## Where this pays off

**The last lesson in this module** spends the budget you just freed. Fuzzing and invariant campaigns
are searches whose value grows with time, which makes them the opposite kind of check from everything
so far: expensive, probabilistic, and worth a great deal when they are given somewhere to run that is
not the critical path.

**The security track** leans on this distinction constantly. Every write-up of a lost-funds incident
describes a code path that was covered by tests and wrong anyway, and the useful question after
reading one is never "was this line executed" but "what property would have failed".

**The transferable rule** is about proxy metrics generally: *a metric that is cheap to satisfy
without doing the underlying work will eventually be satisfied that way.* Coverage is unusually clean
as an illustration because the cheap path — call it, do not check it — takes about thirty seconds and
looks like diligence in a diff.
