Here is a complete pull request. It adds one test file. It changes no contract, no library, no
compiler setting, no dependency.

```console
$ forge snapshot --check
Ran 2 test suites in 4.90ms: 3 tests passed, 0 failed, 0 skipped
No matching snapshot entry found for "ExtraTest::test_SetOnce()" in snapshot file
$ echo $?
1
```

Required check: red.<Cite src="measured-forge-1-7-1" /> The reviewer has nothing to review, the
author has nothing to fix, and the only available move is to regenerate `.gas-snapshot` and push
again. Do that four or five times and the team has learned a durable lesson: when the gas check is
red, regenerate and re-push without reading it.

That is the failure this lesson is about, and the reason gas belongs in a pull request as *feedback*
rather than as a *wall*.

## Two commands that look like variants of each other

`forge snapshot` writes one line per test into `.gas-snapshot`, a committed text file:<Cite src="foundry-gas-tracking" />

```text
CounterTest:testFuzz_SetNumber(uint256) (runs: 256, μ: 27345, ~: 29289)
CounterTest:test_Increment() (gas: 28783)
```

Two flags read it back, and the documentation's own descriptions separate them precisely:<Cite src="forge-snapshot-reference" />

- `--diff [<SNAPSHOT_FILE>]` — "Output a diff against a pre-existing gas snapshot."
- `--check [<SNAPSHOT_FILE>]` — "Compare against a pre-existing gas snapshot, **exiting with code 1
  if they do not match.** Outputs a diff if the gas snapshots do not match."

That exit code is the entire difference, and it separates information from enforcement. `--diff` tells
you something. `--check` stops you.

The official Foundry CI workflow includes `forge snapshot --check` as a step, a reasonable default for
a repository with a small frozen gas suite.<Cite src="foundry-ci" /> Whether it is reasonable for
*yours* depends on how often the numbers move for reasons unrelated to the change under review.

## Reproducing the false positive, and then failing to fix it

**Subgoal 1 — establish a clean baseline, so any later red is unambiguous.**

```console
$ forge snapshot
$ cat .gas-snapshot
CounterTest:testFuzz_SetNumber(uint256) (runs: 256, μ: 27345, ~: 29289)
CounterTest:test_Increment() (gas: 28783)
$ forge snapshot --check ; echo $?
0
```

**Subgoal 2 — make the one change every growing repository makes: add a test.** A new file,
`test/Extra.t.sol`, with one test that calls an existing function. No production source is touched.

```console
$ forge snapshot --check ; echo $?
No matching snapshot entry found for "ExtraTest::test_SetOnce()" in snapshot file
1
```

Red.<Cite src="measured-forge-1-7-1" /> Note what the message says: not *a number moved* but *a name
is absent*. The snapshot file is keyed by test identity. Adding a test adds a key. Renaming a test
changes a key. Deleting one removes a key. None of these are gas events, and all of them turn the
gate red.

**Subgoal 3 — reach for the flag that is supposed to soften this, and watch it not help.** The
reference documents `--tolerance <SNAPSHOT_THRESHOLD>` — "Tolerates gas deviations up to the
specified percentage".<Cite src="forge-snapshot-reference" /> On forge 1.7.1 it behaves exactly as
advertised against a *numeric* change. Against a real regression of roughly four percent:<Cite src="measured-forge-1-7-1" />

```console
$ forge snapshot --check --tolerance 1 ; echo $?
Diff in "CounterTest::testFuzz_SetNumber(uint256)": consumed "(runs: 256, μ: 28533, ~: 30477)" gas,
  expected "(runs: 256, μ: 27345, ~: 29289)" gas
1

$ forge snapshot --check --tolerance 10 ; echo $?
0
```

Now the same flag against the added test:

```console
$ forge snapshot --check --tolerance 50 ; echo $?
No matching snapshot entry found for "ExtraTest::test_SetOnce()" in snapshot file
1
```

**Fifty percent tolerance, still red.**<Cite src="measured-forge-1-7-1" /> Tolerance is a percentage
band around a number, and a missing entry has no number to band. The flag softens the case people
rarely hit and does nothing for the case they hit constantly.

<Aside kind="note">
Everything above is downstream of a fact you already met: a gas report describes *your test suite's*
call distribution, not production.<Cite src="foundry-gas-tracking" /> A fuzz entry stores `runs`, a
mean and a median — statistics over 256 draws.<Cite src="measured-forge-1-7-1" /> Add one cheap test
call to a function and its average moves without a single opcode changing. The snapshot is an
honest record of a measurement; the mistake is reading it as a measurement of the contract alone.
</Aside>

## When the gate is right

`--check` is not wrong, it is narrow. It works when three things hold at once:

- **The gas suite is separate.** A dedicated `test/gas/` directory whose tests exist only to be
  measured, filtered with `--match-path`, so the general suite can grow without touching it.<Cite src="forge-test-reference" />
- **The gas suite is frozen.** Adding a test to it is a deliberate act that comes with regenerating
  the file in the same commit, and reviewers know that.
- **The numbers are pinned.** Compiler, EVM version, optimizer settings and Foundry build are all
  fixed, or the numbers move for reasons the [previous lesson](/c/foundry-version-pinning) covers.

Under those conditions a red `--check` genuinely means "this change moved gas". The moment the gas
suite and the functional suite are the same suite, the gate produces false positives at the rate the
suite grows.

## Gas as a comment instead

The alternative puts the same information in front of a reviewer without blocking anyone: a job that
measures gas on the base branch and on the head, and posts the delta as a pull-request comment.

The de-facto action for this consumes the human-readable report rather than a snapshot
file:<Cite src="rubilmax-gas-diff" />

```yaml
      - name: Run tests with a gas report
        run: forge test --gas-report > gasreport.ansi

      - name: Compare gas reports
        uses: Rubilmax/foundry-gas-diff@v3
        with:
          summaryQuantile: 0.9
          sortCriteria: avg,max
```

It reads a report file (default `gasreport.ansi`), fetches the stored report artifact from the base
branch, computes per-function deltas and emits markdown for a sticky comment.<Cite src="rubilmax-gas-diff" />
Two of its inputs decide whether the comment gets read: `ignore` and `match` restrict which contract
paths appear, and `summaryQuantile` (default 0.8) sets the threshold below which a diff is not shown
at all.<Cite src="rubilmax-gas-diff" /> An unfiltered gas comment on a repository full of mocks is a
wall of noise, which is functionally the same as no comment.

Two operational details are easy to get wrong. The job needs `pull-requests: write` and only that
job should have it, since posting a comment is a repository write and the guidance is to keep the
default token read-only and raise permissions per job.<Cite src="github-actions-security-hardening" />
And the base measurement has to exist: the action fetches an artifact uploaded by a run on the base
branch, so a comment that appears blank on the first pull requests after you add it is usually that
and not a bug.<Cite src="rubilmax-gas-diff" />

## The constraint that shapes the job

There is one hard fact about `forge test` that decides how this job is written, and it does not
appear in the flag documentation. On forge 1.7.1, the machine-readable output flags are mutually
exclusive with each other and with the gas report:<Cite src="measured-forge-1-7-1" />

```console
$ forge test --junit --gas-report
error: the argument '--junit' cannot be used with '--gas-report'

$ forge test --junit --json
error: the argument '--junit' cannot be used with '--json'
```

The reference lists `--json`, `--junit` and `--gas-report` side by side under display options and
says nothing about them conflicting; the binary rejects the combination
outright.<Cite src="forge-test-reference" /><Cite src="measured-forge-1-7-1" />

So a pipeline that wants both structured test results and a gas report must invoke `forge test`
twice. And now the thread from the previous lesson pulls tight: **two invocations of a suite
containing unseeded fuzz tests produce two different sets of gas numbers**, because the fuzzer draws
different inputs and the stored mean and median are statistics over those draws.<Cite src="measured-forge-1-7-1" />
If a gas diff is going to mean anything, the run that produces it needs `--fuzz-seed` — the same
mechanism you already needed to make the fork cache hit.<Cite src="forge-test-reference" />

<Check type="predict" concept="snapshot-check-gate">
A team runs `forge snapshot --check` as a required merge check on their full suite. Over one week,
five pull requests turn it red. For each, predict whether the red is a true positive, and say what the
reviewer should do:

1. Adds a `require` to a hot function.
2. Renames `test_Withdraw` to `test_Withdraw_RevertsWhenPaused`.
3. Bumps the Foundry version in the workflow from `stable` to `v1.7.1`.
4. Adds three tests to an existing test contract, touching no source.
5. Changes `optimizer_runs` from 200 to 10000.

<Answer>
**1 — true positive.** A `require` adds a comparison, a jump and, if it carries a string, calldata and
revert data. The diff shows which functions moved and by how much; the reviewer decides whether the
check is worth its price. This is the case the gate exists for, and it is one case out of five.

**2 — false positive.** The snapshot is keyed on test identity, so the rename removes one key and adds
another: `No matching snapshot entry found`.<Cite src="measured-forge-1-7-1" /> Gas did not
change. `--tolerance` will not help at any value, because there is no number to compare.

**3 — indeterminate, and that is worse than either.** Moving from a floating channel to a pin changes
which binary measures the gas.<Cite src="measured-forge-1-7-1" /> The numbers may move, and if they
do, nothing in the diff distinguishes "the tool changed" from "the contract changed". Regenerate the
snapshot in the same commit as the pin and say so in the message — this is the one red where the
commit message is the deliverable.

**4 — false positive, and the common one.** Three added keys, three `No matching snapshot entry`
lines, no production change.<Cite src="measured-forge-1-7-1" /> Worse, if any of the three call a
function the fuzz entries also exercise, the *existing* averages may move too, so the reviewer sees
both a missing-entry error and real-looking numeric deltas on a pull request that touched no source.

**5 — true positive, and the largest.** `optimizer_runs` trades deployment size against runtime cost;
raising it to 10000 typically makes deployment more expensive and calls cheaper. The snapshot is
exactly the right instrument. Regenerate, and treat the diff as the reason the change is justified
rather than as an obstacle.

**The tally is the argument.** Two of five reds carry information about the contract, one is
ambiguous, two are pure noise — and the two noisy ones come from the most routine activity a healthy
repository does. That ratio is what trains a team to regenerate without reading, at which point the
gate has negative value: it costs runner time, it costs a round trip, and it has stopped being read.

**What to do instead.** Move `--check` to a small frozen `test/gas/` suite selected with
`--match-path`, and put the full-suite number in a diff comment that informs without
blocking.<Cite src="forge-test-reference" /><Cite src="rubilmax-gas-diff" /> The reviewer still sees
every regression. Nobody is stopped by a rename.
</Answer>
</Check>

## Where this pays off

**The next lesson** applies the same test to coverage, and coverage fails it harder: the number is
not only noisy, it can be high while asserting nothing at all.

**The last lesson** takes the `--junit` constraint above and builds the rest of the pipeline around
it, because once anything is parsing results programmatically, "which flags can coexist" stops being
trivia and becomes the shape of the job.

**The transferable rule** generalises past gas: *before making a measurement a gate, count how often
it moves for reasons unrelated to the change.* If the answer is "often", you are not adding a check.
You are adding a ritual — and rituals get performed without being read.
