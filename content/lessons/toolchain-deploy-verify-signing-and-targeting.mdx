There are two ways to lose a deployment that have nothing to do with your Solidity. You can hand the
signing key to something that keeps it, or you can send a correct transaction to the wrong network.
Both are decided by flags on the same command line, and neither is caught by any test you can write.

This lesson is about those two flags.

## Four ways to sign, listed in the order the docs list them

Foundry's scripting page presents the signer options as a labelled set, and the labels are the
recommendation:<Cite src="foundry-deploying" />

```bash
# Keystore (recommended)
forge script script/Deploy.s.sol --broadcast --rpc-url $RPC_URL --account deployer

# Hardware wallet
forge script script/Deploy.s.sol --broadcast --rpc-url $RPC_URL --ledger

# Browser wallet
forge script script/Deploy.s.sol --broadcast --rpc-url $RPC_URL --browser

# Raw key (not recommended)
forge script script/Deploy.s.sol --broadcast --rpc-url $RPC_URL --private-key $PRIVATE_KEY
```

Note that the docs themselves annotate the first as recommended and the last as not
recommended.<Cite src="foundry-deploying" /> That is a vendor telling you which of its own options is
a mistake, which is rarer than it should be and worth taking seriously.

### Why the raw key is the wrong default even on a testnet

`--private-key $PRIVATE_KEY` works. That is the problem.

A value passed as a command-line argument is not private on the machine it runs on. It is in the
process argument list, readable by any process running as you. It is in your shell history and in your
terminal scrollback. If a CI job runs with tracing on, it is in the build log, and build logs outlive
the pipelines that wrote them. None of that is exotic; it is the ordinary behaviour of tools you
already use.

The counterargument is always "it's a testnet key". The reply is that habits do not know which chain
they are on. The command you type a hundred times on Sepolia is the one your fingers reach for when it
matters, and the only difference between the two invocations is a value in an environment variable
that also does not know which chain it is on.

### The keystore flow, once

`cast wallet` is the wallet-management surface, and `cast wallet import` "imports a private key into
an encrypted keystore".<Cite src="foundry-cast-wallet" /> You do that once per key. Afterwards
`cast wallet list` "lists all the accounts in the keystore default directory", and
`--account <name>` selects one at deployment time.<Cite src="foundry-cast-wallet" /><Cite src="foundry-deploying" />

```bash
cast wallet import deployer --interactive   # prompts for the key, then for a password
cast wallet list                            # confirm it is there under the name you expect
forge script script/Deploy.s.sol --rpc-url $RPC_URL --broadcast --account deployer
```

What this changes: the secret is an encrypted file plus a password you type at signing time, and the
thing on your command line is a *name*. A name in shell history is not a credential. The same
`cast wallet` surface also carries `change-password` and `decrypt-keystore` for the operations you
will eventually need.<Cite src="foundry-cast-wallet" />

`--sender` is the companion flag: "the address which will be executing tests/scripts".<Cite src="forge-script-reference" />
Scripts often need to know the deployer's address during simulation — to predict a `CREATE` address,
to assert an owner — before any signing happens.

### Hardware and browser signers, and what they actually protect

`--ledger` moves the key into a device that will not export it.<Cite src="foundry-deploying" /> A
real improvement, and a narrow one: it protects the *key*, not the *decision*. A script's transactions
arrive at the device as calldata blobs, and approving them is closer to blind signing than to reading
a transfer. The device stops an attacker holding your laptop. It does not stop you broadcasting a
script whose fourth transaction hands ownership to the wrong address.

`--browser` connects to an injected browser wallet instead of loading a key into the
CLI.<Cite src="foundry-deploying" /><Cite src="foundry-browser-wallet" /> Foundry's own guide carries
a warning worth reproducing rather than paraphrasing: browser wallet support "is still in early
development", you should "review every request and use it cautiously", and for high-value production
operations you should "prefer a well-tested hardware wallet or organizational signer
policy".<Cite src="foundry-browser-wallet" />

A fourth shape exists for teams running their own node: `--unlocked` sends "via
`eth_sendTransaction` using the `--sender` argument as sender".<Cite src="forge-script-reference" />
The key lives in the node, and the security question becomes who can reach that node's RPC.

## The flag that does not do what it is named after

Now the second way to lose a deployment.

Foundry's scripting page states it as plainly as it can be stated: "`--chain` only sets the EVM
`block.chainid`. It does not select an RPC endpoint. Use `--rpc-url` (with a URL or an alias from
`[rpc_endpoints]`) to choose the network."<Cite src="foundry-deploying" />

The naming invites precisely the wrong inference. `--chain base` reads like a destination. It is a
value your contract sees, not an address the packet goes to.

### What goes wrong, concretely

The failure is not usually "transaction lands on the wrong chain because of `--chain`" — `--rpc-url`
decides that, and if you got the endpoint right, the transaction goes where you meant. The failure is
subtler and it is about **rehearsal lying to you**.

Suppose your deployment script guards itself, which it should:

```solidity
function run() public {
    require(block.chainid == 8453, "wrong chain");   // Base mainnet
    // ...
}
```

Run that with `--chain base` against an endpoint that points at somewhere else, and the guard passes
during the local phase, because `--chain` supplied the value the guard is reading. The rehearsal is
green. The real execution on the real chain reads the real chain id — and now your guard reverts
after you have paid for a transaction, or worse, a constructor that branches on chain id takes the
other branch on chain than it took in simulation.

The same mechanism affects anything that reads chain id at construction time: an EIP-712 domain
separator cached in an immutable, a chain-specific config lookup, a bridge endpoint id chosen by a
`if (block.chainid == ...)` ladder. Every one of those is a value your simulation can be made to get
wrong by a single flag.

### The defence is to stop typing endpoints

Foundry lets you name networks once, in `foundry.toml`, and refer to them by
alias:<Cite src="foundry-deploying" /><Cite src="foundry-config-overview" />

```toml
[rpc_endpoints]
sepolia  = "${SEPOLIA_RPC_URL}"
base     = "${BASE_RPC_URL}"
mainnet  = "${MAINNET_RPC_URL}"
```

```bash
forge script script/Deploy.s.sol --broadcast --rpc-url base --account deployer
```

Now the word `base` on the command line means the endpoint, once, defined in a file that is reviewed
like code. There is one place where "base" is defined and one place to get it wrong, instead of a URL
retyped per invocation.

Layer three checks on top, in increasing order of how much they save you:

1. **Never pass `--chain` unless you have a specific reason.** The default — letting the endpoint
   report its own chain id — is the honest configuration. A flag that can only make a rehearsal
   diverge from reality has a narrow legitimate use.
2. **Guard inside `run()`.** `require(block.chainid == expected)` is one line and it turns a
   wrong-network run into a failed simulation. Derive `expected` from the config you loaded, not from
   a literal, so the guard and the deployment parameters cannot disagree.
3. **Key your config by chain id.** If the treasury address, the fee, and the bridge endpoint all
   come from `config[block.chainid]`, then a wrong network cannot silently deploy right-looking
   contracts with the wrong parameters — the lookup has no entry.

<Check type="spot-bug" concept="chain-flag-trap">
A team's deployment runbook has this line, copied between engineers for a year:

```bash
forge script script/Deploy.s.sol \
  --chain mainnet \
  --rpc-url $RPC_URL \
  --private-key $DEPLOYER_KEY \
  --broadcast
```

`$RPC_URL` is exported by whichever `.env` file was sourced last. Name every defect and rank them.

<Answer>
**1. The raw key, and it is the worst one.** `--private-key $DEPLOYER_KEY` puts a live mainnet key
into the process argument list, the shell history, and any CI log that traces commands. Foundry's own
docs mark this form "not recommended" and the keystore form
"recommended".<Cite src="foundry-deploying" /> Fix: `cast wallet import` once, then `--account
deployer`.<Cite src="foundry-cast-wallet" />

**2. The destination is an ambient variable, and `--chain` disguises that.** `$RPC_URL` is whatever
was exported last, which is a property of the shell, not of the runbook. Meanwhile `--chain mainnet`
looks like it pins the destination and does not: it only sets `block.chainid` inside the
EVM.<Cite src="foundry-deploying" /> The two together are the dangerous combination — a reader
believes the destination is stated when it is not.

Fix: define `mainnet` under `[rpc_endpoints]` in `foundry.toml` and pass `--rpc-url mainnet`, so the
endpoint is named in a reviewed file.<Cite src="foundry-deploying" /><Cite src="foundry-config-overview" />

**3. `--chain` is not merely useless here, it is actively harmful.** It makes the simulation report a
chain id that the endpoint did not supply, so any `require(block.chainid == ...)` guard or chain-id
branch is rehearsed against a value you asserted rather than a value you observed. Drop it.

**4. No dry run in the runbook.** The same command without `--broadcast` simulates against live chain
state and shows what would happen.<Cite src="foundry-deploying" /> A runbook that goes straight to the
irreversible form has removed its own last checkpoint. Split it into two steps and make the first one
mandatory.

**5. Nothing serialises the sends.** For a one-time mainnet deployment, `--slow` — send each
transaction only after the previous one has been confirmed and succeeded — is almost always the right
trade.<Cite src="forge-script-reference" />

**The corrected line:**

```bash
forge script script/Deploy.s.sol --rpc-url mainnet --account deployer --slow            # rehearse
forge script script/Deploy.s.sol --rpc-url mainnet --account deployer --slow --broadcast
```
</Answer>
</Check>

## Where this pays off

**Immediately next:** with the signer and the destination settled, the remaining question about a
deployment is *where the contract lands* — and the answer turns out to depend on four inputs, all of
which are easy to change by accident.

**In multi-chain work:** the alias table in `foundry.toml` is the first artifact of taking "N
independent deployments" seriously. Every chain gets a name, and the runbook refers to names.

**In your threat model:** the signing question does not end at the deployment. Whatever key deploys
the system usually owns it for a few minutes afterwards, and the handover to a multisig or a timelock
is a step with its own failure modes — including being forgotten entirely. The last lesson in this
module comes back to checking that on chain, per chain.
