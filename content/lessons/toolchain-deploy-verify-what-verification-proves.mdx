A user opens two explorer tabs. Same address, `0xC0FFEE…`, on two different chains. Both pages show a
green check and a `Contract` tab full of readable Solidity. Both show the same contract name. The
source on both pages is, line for line, identical.

On one chain their withdrawal works. On the other it reverts.

Nothing here is a bug in an explorer and nothing here is a lie. Everything on both pages is true. The
gap is between what verification actually certifies and what a green check reads like, and this lesson
is about that gap — first the mechanism, then the two service families you will use, then the
per-chain checks that catch what the badge cannot.

## Verification is a recompile and a comparison

Strip away the interface and the operation is three steps. The explorer takes your source and your
declared compiler settings, recompiles, and compares the output against the bytecode already on chain.

The Solidity documentation describes exactly this, and describes what it proves: with the metadata's
information "it is then possible to verify the source code of a contract by reproducing the
compilation, and comparing the bytecode from the compilation with the bytecode of the deployed
contract".<Cite src="solidity-docs-metadata" />

That sentence is the whole claim. Correspondence between a published source and a deployed artifact.
It contains no assertion about whether the artifact is correct, safe, or acting in your interest.

## The tail on the end of your bytecode

What makes that comparison precise is a block of bytes the compiler adds without being asked.

<Figure

  alt="The end of a deployed runtime bytecode: the executable code, then a CBOR-encoded metadata block holding the IPFS hash of the metadata file and the compiler version, then two bytes giving the length of that block."
>

The Solidity compiler generates a metadata JSON file carrying two kinds of information: how to
interact with the contract — ABI and NatSpec — and how to reproduce the compilation and verify a
deployed contract, meaning the compiler version, the settings, and the source files
used.<Cite src="solidity-docs-metadata" /> Sourcify's summary of the same file is shorter: "the
compiler settings, contract ABI, NatSpec contract documentation, and used source files and their
hashes".<Cite src="sourcify-metadata" />

Then it appends a pointer to that file:

- **By default, the IPFS hash (in CID v0) of the canonical metadata file, plus the compiler version,
  goes on the end of the bytecode.**<Cite src="solidity-docs-metadata" />
- **It is appended to the runtime bytecode — "not necessarily the creation
  bytecode".**<Cite src="solidity-docs-metadata" /> Since the runtime code is what the creation code
  returns, the tail still ends up inside the initcode, which is why the previous lesson's addresses
  moved when the compiler did.
- **It is CBOR-encoded, and "the last two bytes in the bytecode indicate the length of the CBOR encoded
  information".**<Cite src="solidity-docs-metadata" /> Read the last two bytes, step back that far,
  decode.
- **Release builds encode the version as three bytes** — one each for major, minor and patch — while
  pre-release builds use a complete version string including the commit hash and build
  date.<Cite src="solidity-docs-metadata" />
- **Swarm and "no tail at all" are the alternatives.**<Cite src="solidity-docs-metadata" />

<Aside kind="warn">
The docs include a note that is aimed straight at anyone writing tooling: the CBOR mapping can contain
other keys, so decode properly by reading the length from the last two bytes, and "do not rely on it
starting with `0xa264` or `0xa2 0x64 'i' 'p' 'f' 's'`".<Cite src="solidity-docs-metadata" /> Every
hand-rolled "strip the metadata" regex is that assumption written down.
</Aside>

### Why the tail makes verification strong

Sourcify draws the causal chain in one line:<Cite src="sourcify-exact-vs-match" />

That is a chain of hashes, so it does not merely usually hold. The Solidity docs make the same point
from the other end: reproducing the compilation "automatically verifies the metadata since its hash is
part of the bytecode, as well as the source codes, because their hashes are part of the metadata",
and "any change in the files or settings would result in a different metadata
hash".<Cite src="solidity-docs-metadata" />

So the tail is a fingerprint of the whole compilation.<Cite src="sourcify-exact-vs-match" /> Matching
it means you are reading the exact sources, with the exact settings, that produced this deployment.

## Two strengths of match, and a naming problem

Which sets up the distinction that matters.

A verifier can find that the **executable** part of the deployed bytecode matches a recompilation
while the metadata tail does not. The contract behaves identically — the tail is data, not code — but
a differing tail means some compilation input differed: a comment, a file path, a NatSpec string, a
setting.

Or it can find that **everything matches, tail included**, which pins the sources exactly.

Sourcify's docs define both. The stronger outcome is where "the bytecode of the deployed contract is
byte-by-byte the same (excluding libraries and immutables)"; the weaker is where the deployed bytecode
matches a recompilation from the metadata and the source files "except the metadata
hash".<Cite src="sourcify-exact-vs-match" />

<Aside kind="note">
Note the parenthesis in that definition: **excluding libraries and immutables**.<Cite src="sourcify-exact-vs-match" />
Immutable values are written into the runtime bytecode during construction, so the code on chain
differs from a fresh compile at exactly those positions, by design. A verifier has to know where they
are and mask them out. This is why "byte-by-byte identical" is a slightly loose description of even
the strongest match, and why comparing two deployments by raw code hash can report a difference that
is only a different constructor argument.
</Aside>

**Now the naming.** Sourcify itself has renamed these outcomes: it defines "Exact Matches (prev. called
'perfect match')" and "Matches (prev. called 'partial match')".<Cite src="sourcify-exact-vs-match" />
Other services use their own vocabulary, and the terms have moved over time across the ecosystem. Do
not carry a remembered label between services. Read the definition the service in front of you gives,
and map it onto the mechanism: *did the tail match, or only the executable part?* That question is
stable; the words are not.

  reality="If the executable portion matches, the runtime behaviour is the code you are reading. What may differ is compilation input that does not affect execution — comments, file paths, NatSpec, some settings — which is a provenance gap, not a behaviour gap."
  why="The older label for the weaker outcome contained the word partial, which reads as partially verified rather than as verified without a pinned fingerprint."

## Doing it

Two entry points. During a deployment:<Cite src="etherscan-verify-with-foundry" /><Cite src="forge-script-reference" />

```bash
forge script script/Deploy.s.sol \
  --broadcast --rpc-url $RPC_URL \
  --verify --etherscan-api-key $ETHERSCAN_API_KEY
```

`--verify` "verifies all the contracts found in the receipts of a script, if
any".<Cite src="forge-script-reference" /> It works off the broadcast record, which is one more reason
that directory matters.

After the fact, or for anything not deployed by a script:<Cite src="etherscan-verify-with-foundry" />

```bash
forge verify-contract --watch --chain sepolia \
  0x324eca20b358b18e48f2611f7452560ce3b3c1bb \
  src/ContractFile.sol:ContractName \
  --verifier etherscan --etherscan-api-key $ETHERSCAN_API_KEY
```

The arguments are the address and "the contract identifier in the form
`<path>:<contractname>`".<Cite src="forge-verify-contract-reference" />

### Constructor arguments, the usual failure

The recompiled creation code has to include your constructor arguments, and Foundry cannot infer them
from the source. Three options:<Cite src="forge-verify-contract-reference" />

- `--constructor-args` takes the ABI-encoded arguments, and the reference notes it is "only for
  Etherscan".
- `--constructor-args-path` reads them from a file, which is the form to prefer once the arguments are
  long enough to mangle in a shell.
- `--guess-constructor-args` will "try to extract constructor arguments from on-chain creation code" —
  useful when you are verifying someone else's deployment, or your own from a machine that no longer
  has the deployment record.

The other settings must line up too: `--compiler-version` selects "the `solc` version to use to build
the smart contract" and `--num-of-optimizations` (alias `--optimizer-runs`) "the number of optimization
runs used to build".<Cite src="forge-verify-contract-reference" /> Both come from your
`foundry.toml`,<Cite src="foundry-solc-config" /> and a verification failing with no useful message is
very often one of these disagreeing with the build that shipped.

When the automated path is exhausted, `--show-standard-json-input` "prints the standard json compiler
input".<Cite src="forge-verify-contract-reference" /> That output is what an explorer's manual
verification form wants, and it is the escape hatch that always works.

### The race nobody expects the first time

Your transaction confirmed. Verification says the explorer cannot find the deployment. Nothing is
wrong.

Broadcast and indexing are asynchronous. The receipt exists the moment the transaction is included;
the explorer's own database learns about it some time later. Foundry issue #2435 is the long-running
record of this exact confusion — verification failing with a message about the deployment not being
detected — and it is why the retry machinery exists.<Cite src="foundry-issue-2435" />

The flags are built for it: `--watch` waits "for verification result after submission",
`--retries` defaults to 5, and `--delay` is an "optional delay to apply in between verification
attempts, in seconds", defaulting to 5.<Cite src="forge-verify-contract-reference" />

  belief="Verification failed, so the deployment must have failed."
  reality="The usual cause is that the explorer has not indexed the transaction yet. The contract is deployed; the verifier cannot see it yet, which is why --watch, --retries and --delay exist."
  why="Broadcast and indexing are asynchronous, and the error message describes the symptom the verifier observes rather than the cause."
  src="foundry-issue-2435"

## One Etherscan key, not twelve

The single most common piece of stale advice in this area is "collect an API key for each explorer".

Etherscan's own API documentation states the current arrangement in one line: "All 60+ EVM chains
under one key. Set `chainid` to choose one."<Cite src="etherscan-v2-api" /> One key covers Etherscan,
Arbiscan, Basescan, Polygonscan and the rest of the family. The migration to that consolidated
endpoint was tracked inside Foundry itself.<Cite src="foundry-issue-9196" />

For a chain Foundry does not know natively, pass the endpoint explicitly. Etherscan's Foundry guide
gives the form, with the V2 base path and the chain id as a query
parameter:<Cite src="etherscan-verify-with-foundry" />

```bash
forge verify-contract 0x324eca20b358b18e48f2611f7452560ce3b3c1bb \
  src/ContractFile.sol:ContractName \
  --verifier etherscan \
  --verifier-url "https://api.etherscan.io/v2/api?chainid=2201"
```

`--verifier-url` is documented as "the verifier URL, if using a custom provider", and reads
`VERIFIER_URL` from the environment.<Cite src="forge-verify-contract-reference" />

<Aside kind="note">
**No sunset date here, deliberately.** Secondary sources place the V2 consolidation somewhere in
2024-2025 and describe single-key configuration as the 2026 norm, but the date on which the V1 API
stops answering was not established from a primary source. If you are migrating a pipeline, get that
date from Etherscan directly rather than from any tutorial, including this one.
</Aside>

## Etherscan is one option among several

`forge verify-contract` takes a `--verifier`, described as "the contract verification provider to use",
with values `etherscan`, `sourcify`, `blockscout`, `oklink` and `custom` — the last documented as a
"custom verification provider, requires compatibility with the Etherscan
API".<Cite src="forge-verify-contract-reference" />

**Sourcify** is open and chain-agnostic, and its model is different in a way that matters: it works
from the metadata file itself, which contains the compiler settings and the source hashes, and it
keeps that material.<Cite src="sourcify-metadata" /><Cite src="sourcify-exact-vs-match" /> The
practical consequence is that a Sourcify record is a full compilation input, not a rendering of your
source in someone's web interface.

**Blockscout** is common on L2s and app-chains, and is often the only explorer a new chain has on day
one.

Verifying to more than one service costs one extra command:

```bash
forge verify-contract $ADDR src/Token.sol:Token --verifier etherscan --etherscan-api-key $KEY --watch
forge verify-contract $ADDR src/Token.sol:Token --verifier sourcify --watch
```

The argument for doing it is not redundancy for its own sake. It is that the record of what you
deployed should not be a single company's database row, and that different consumers reach for
different services.

## Same address is not the same contract

Now back to the two tabs.

An address is a hash of deployment inputs.<Cite src="eip-1014" /> It is not a certificate, it carries
no signature, and nothing about it is checked against anything on another chain. Two chains can
absolutely hold different code at the same address, and there are three distinct routes there.

**Route one: CREATE3, working as designed.** The whole point of putting the real deployment behind an
intermediate proxy is that the final address "solely depends on `salt`", independent of the
initcode.<Cite src="solady-create3" /> That is a feature, and it means identical addresses across
chains no longer imply identical code. The property you relied on under CREATE2 is gone by
construction.

**Route two: a proxy.** The address is the proxy's. The code that runs is the implementation's. Two
chains can point the same proxy address at completely different implementations, and both proxies
verify perfectly, because a proxy's own source really is what is at that address. Verifying a proxy
tells you nothing about the logic behind it.

**Route three: you never deployed there.** Nobody reserved your address on a chain you have not
launched on. If the deployer, salt and initcode are public — and they are, since the deployment is on
chain elsewhere — anyone can deploy *your exact initcode* at *your exact address* on a new chain, and
it will verify. Whether that is a friendly mirror or a trap is not a question an explorer can answer.

  belief="Deploy once, then repeat the same script per chain, and you are done."
  reality="Chain-specific constructor arguments break address determinism, CREATE3 breaks the address-implies-code link on purpose, and every chain needs its own verification, its own configuration review and its own ownership check."
  why="The script is the same file and the commit hash is the same, so the outcome feels like it must be the same."
  src="layerzero-uniform-address"

### The per-chain checks that actually settle it

Verification is one line in a longer list. Run all of these against every chain, from your machine,
not from a dashboard.

**1. Compare the runtime code hash across chains.** `cast code` on each chain, hashed, or read
`extcodehash` directly. Two chains agreeing here is strong evidence of the same runtime code — much
stronger than two green badges. Remember the caveat from earlier: immutables live in the runtime code,
so a legitimate per-chain constructor argument shows up as a
difference.<Cite src="sourcify-exact-vs-match" />

**2. Read the constructor arguments each explorer decoded.** They are per-chain configuration, and they
are the input most likely to be wrong. A verified page will show them; compare them against your
config file, not against your memory.

**3. For a proxy, read the implementation slot and repeat everything for the implementation.** The
proxy's verification is not the interesting one.

**4. Check ownership and roles on chain, per chain.** Who owns it now, and is that the multisig you
intended or the hot key that deployed it? This is the step that gets skipped, because the deployment
succeeded and the deployment is what everyone was watching. A protocol whose mainnet ownership sits
with a multisig and whose fourth-chain ownership sits with a deployer EOA is one compromised laptop
away from an incident, and everything about it looks verified.

**5. Confirm the factory you used, per chain.** If one chain fell back to a different CREATE2
deployer, its addresses differ for a reason you should be able to
state.<Cite src="foundry-create2-guide" />

**6. Do not use code length as an identity check.** Since EIP-7702 an EOA can carry a
[delegation designator](/c/delegation-designator) and report non-zero code
length.<Cite src="eip-7702" /> `code.length > 0` means "something is here", which is a liveness check.
The hash comparison in step 1 is the identity check.

## What verification cannot do for you

Worth stating flatly, because the checkmark is doing a lot of persuasive work it did not earn.

**It does not review the code.** A contract with an owner-only drain function verifies, and the drain
function is right there in the source that verified.

**It does not mean anyone read it.** Verification is automated. Audit is not. They get confused because
both produce a badge on the same page.

**It does not cover what the code does at runtime.** A verified contract that delegates to an
upgradeable implementation, reads a mutable oracle address, or calls an unverified helper is verified
about the part you are looking at and silent about the parts that matter.

**It does not travel between chains.** Every deployment is its own verification, its own configuration,
and its own ownership question.

What it *does* give you is the precondition for all of the above: a reliable statement that the source
you are about to read is the source that runs. That is genuinely valuable, and it is the floor, not the
ceiling.

<Check type="explain" concept="same-address-not-same-contract">
Your protocol is live on four chains at the same address, `0xC0FFEE…`, deployed through a CREATE3
deployer so that each chain could take its own constructor arguments. All four are verified on
Etherscan-family explorers and show the same contract name and the same source.

A large integrator asks you to sign a statement that "the deployed code is identical on all four
chains".

Work out whether you can sign it, what you would check first, and what you would offer instead if you
cannot.

<Answer>
**Start by noticing that the setup makes the claim unlikely to be true.** CREATE3 makes the final
address depend on the salt alone, independently of the deployed
bytecode.<Cite src="solady-create3" /> It was chosen here precisely so the constructor arguments could
differ per chain. The identical address is therefore evidence of an identical *salt*, and of nothing
else. Under CREATE2 the address would have implied identical initcode;<Cite src="eip-1014" /> that
implication is what CREATE3 trades away.

**Four green checkmarks do not close the gap either.** Verification establishes that each published
source recompiles to the bytecode deployed on *that* chain.<Cite src="solidity-docs-metadata" /> Four
independent correspondence proofs are not one cross-chain equality proof. Nothing in any of them
compares chain A to chain B.

**What to actually check, in order.**

*Compare runtime code hashes.* `extcodehash` on each of the four. Equal hashes across all four would be
strong evidence — but expect them not to be equal, because immutables are written into runtime code at
construction and a verifier explicitly excludes them from a byte-by-byte
comparison.<Cite src="sourcify-exact-vs-match" /> A difference here is a signal to investigate, not a
verdict.

*Compare the decoded constructor arguments.* This is where the intended differences live, and where an
unintended one hides among them.

*Compare compiler version and optimizer settings per chain.* Different settings produce different code
from identical sources.<Cite src="foundry-solc-config" /> If one chain was deployed from a different
branch or a different CI image, the metadata tail on that chain differs and the strength of its match
will say so.<Cite src="sourcify-exact-vs-match" />

*Check ownership and roles on all four.* Not part of the claim as written, and the thing most likely to
be actually wrong.

**What you can honestly sign.** Not "the code is identical". Instead, something true and more useful:

- the same source at the same commit was used for all four deployments, and each chain's verification
  demonstrates that source produced that chain's bytecode;<Cite src="solidity-docs-metadata" />
- the constructor arguments differ per chain, enumerated here, with a reason for each;
- the compiler version and optimizer settings were identical across all four, evidenced by the strength
  of each verification match;
- the runtime code hashes are equal / differ only at these immutable positions, with the measured
  hashes attached;
- ownership on each chain is held by these addresses.

**Why the integrator should prefer that.** "Identical" is not the property they need; they need to know
which differences exist and that each is intentional. A per-chain table answers the question they
actually have. A blanket claim would be either false or unverifiable, and if a mismatch surfaced later
it would be your signature on it.<Cite src="layerzero-uniform-address" />
</Answer>
</Check>

## Where this pays off

**In the security track:** "verified" is one of the words that does the most damage when taken at face
value. You now have the precise version — a recompile matched a deployment — and the list of questions
it leaves open. Almost every one of those questions is a security question.

**In CI:** verification belongs in the deployment pipeline, not a follow-up ticket. The commands are
short and they take a `--watch`; the alternative is a contract that stays unverified for three days
because the person who deployed it went on holiday.

**In incident response:** the per-chain checklist is the first thing you run when someone reports one
chain behaving differently. Code hash, constructor arguments, implementation slot, owner. Four
commands, and they usually name the wrong chain before anyone has finished reading the support thread.

**In your runbook, and in the reflection prompt for this module:** address strategy, signer custody per
step, per-chain verification, and the ownership handover — including how the handover is checked on
chain afterwards. That last item is the one this module has now mentioned three times, because it is
the one teams reliably forget.
