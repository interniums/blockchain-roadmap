At 03:14 the nightly build went red. Three tests failed, all of them in `test/fork/`, all of them with
assertion failures on numbers that were correct yesterday. The last commit to that repository was
eleven days ago.

Nobody changed anything. The *chain* changed. A rate curve moved, a pool rebalanced, and three
assertions that had been written against last month's liquidity stopped being true. The suite was not
pinned, so every run had been silently testing a different world, and the only reason it had been
green until now was that the drift had not yet crossed a threshold.

The obvious lesson is that unpinned fork tests are not reproducible. That is true and it is the small
half. The larger half is that the block number is also the **cache key**, so an unpinned suite is
paying full price, in requests and in seconds, on every single run — and has been all along.

## "Latest" is not a block

Without `--fork-block-number` (or `fork_block_number`, or the second argument to a create
cheatcode), a fork tracks the chain's latest block.<Cite src="foundry-fork-testing" /><Cite src="foundry-cheatcode-create-select-fork" />

That sounds like "current" and behaves like "arbitrary". Mainnet produces a block roughly every twelve
seconds, so two runs a minute apart are two different states. Your commit is fixed; the thing you are
testing it against is not. When it fails you cannot ask "what changed", because the answer is "the
world, by some unknown amount, since the last time this passed".

Pinning converts an observation into a test. An observation tells you something was true when you
looked. A test tells you something is true of your code, and to say that at all you need to hold
everything else still.

## The cache, measured

Every state read a fork issues is scoped to a block, so what comes back can be filed under that block
and reused. Watch it happen on forge 1.7.1.<Cite src="measured-forge-1-7-1" />

Start empty, run one pinned test that reads one contract's `totalSupply()`:

```bash
$ forge cache clean all
$ forge test --fork-url https://ethereum.reth.rs/rpc --fork-block-number 21000000
Suite result: ok. 1 passed; 0 failed; 0 skipped; finished in 689.14ms

$ forge cache ls
- mainnet (10.4 kB)
	- Block Explorer (0.0 B)

	- Block 21000000 (10.4 kB)
```

Run the identical command again:

```bash
Suite result: ok. 1 passed; 0 failed; 0 skipped; finished in 491.29µs
```

**689 milliseconds to 491 microseconds** — and the second run touched no network at
all.<Cite src="measured-fork-cache-1-7-1" /> Nothing about the test changed. What changed is that the
state it needs was already filed under `mainnet` / `21000000`.

Now drop the pin and run twice:

```bash
$ forge test --fork-url https://ethereum.reth.rs/rpc
$ forge cache ls
- mainnet (20.8 kB)
	- Block Explorer (0.0 B)

	- Block 25838556 (10.4 kB)
	- Block 21000000 (10.4 kB)
```

A second entry, keyed on whatever the head was at that
moment.<Cite src="measured-fork-cache-1-7-1" /><Cite src="forge-cache-reference" /> Come back in a
minute and there will be a third. The cache is not failing; it is working exactly as designed. You are
simply asking it a different question every time.

That is the whole economic argument in one paragraph. **A pinned fork collapses onto one key and is
served locally from the second run onwards. An unpinned fork produces a new key every time the chain
advances, so it can essentially never hit cache**, and every run pays the full cold cost in requests,
in latency and — in CI, where "the machine" is a fresh container — in whatever your provider charges.

Foundry says this in its own troubleshooting page, under the heading "Fork tests are slow": forked
state is cached to disk by default, but the cache is only reused when the fork block is
pinned.<Cite src="foundry-troubleshooting" /> That single sentence is the load-bearing one in this
module, and it is filed under a symptom rather than under caching, which is why almost nobody has read
it.

<Aside kind="note">
Notice which direction the incentives point. The version of the suite that is easiest to write
(`vm.createSelectFork("mainnet")`, no second argument) is the version that is non-reproducible *and*
maximally expensive. The version that costs one more argument is deterministic *and* nearly free after
the first run. There is no trade-off to weigh here; the pin is strictly better, and the only reason
suites go unpinned is that the argument is optional.
</Aside>

## Where the cache lives, and why you should look rather than trust

This is the one place in this module where the documentation cannot be taken at face value, and it
matters because CI cache configuration is written against a path.

**Four live pages on Foundry's own site describe this, and they do not all agree.**

Three give the same shape. The config overview's directory table lists the global RPC cache at
`~/.foundry/cache/rpc/` and marks it "not configurable"; the fork-testing guide describes fork data as
cached at `~/.foundry/cache/rpc/<chain>/<block>/`; the troubleshooting page says the cache is stored in
`~/.foundry/cache/rpc/`.<Cite src="foundry-config-overview" /><Cite src="foundry-fork-testing" /><Cite src="foundry-troubleshooting" />

The fourth does not. The testing config reference, under `no_storage_caching`, says the data is cached
to `$HOME/.foundry/cache/<chain id>/<block number>` — no `rpc/` segment, and a chain **id** rather
than a chain name.<Cite src="foundry-testing-config" />

All four were fetched and read on 2026-08-26. They are all current, no source consulted for this
lesson says which supersedes which, and the majority is not evidence — a stale sentence can be
repeated on three pages as easily as one. Do not carry either layout as a fact.

**What forge 1.7.1 actually produced on the machine this lesson was written on** is a third layout,
close to the majority form but not identical to it:

```text
~/.foundry/cache/rpc/mainnet/21000000
```

The `rpc/` segment is present. The chain component is the chain **name**, `mainnet`, not the id `1`.
And `21000000` is not a directory containing files — it *is* the file, 10,362 bytes of Zstandard-
compressed data.<Cite src="measured-fork-cache-1-7-1" /><Cite src="forge-cache-reference" /> Both
documented forms show the block as a directory with a trailing slash; on this version it is a leaf.

### The operational rules that survive the disagreement

Three things are stable enough to build on.

**Cache the root, not a path you constructed.** `~/.foundry/cache` is the directory the ecosystem
agrees on: Foundry's own GitHub Action documents caching all RPC responses, Etherscan queries and
other data in exactly that directory.<Cite src="foundry-toolchain-action" /> A CI step that caches the
root is correct under every layout above. A step that caches
`~/.foundry/cache/rpc/1/21000000/` is correct under none of them.

**Put the block number in the cache *key*, not in the cached *path*.** Your CI cache key is a string
you choose; it can include the pinned block without making any claim about the directory structure.
That is the version of "keyed on the pinned block" that cannot break when Foundry moves a directory.

**Read the layout off your own machine before depending on it.** One pinned run followed by
`forge cache ls` tells you what your version does, in about a second, and `forge cache ls` is a
documented command rather than a filesystem guess.<Cite src="forge-cache-reference" />

There is a fourth wrinkle for anyone building CI images. The `.foundry` root is not fixed either:
`FOUNDRY_DIR` overrides it outright, and if `FOUNDRY_DIR` is unset while `XDG_CONFIG_HOME` is set,
`foundryup` installs to `$XDG_CONFIG_HOME/.foundry/` instead.<Cite src="foundry-config-overview" /> A
container that sets `XDG_CONFIG_HOME` — many do — has moved the cache out from under a hard-coded
`~/.foundry` path, and the symptom is a cache step that reports success while caching nothing.

## Controlling what gets cached

Three knobs, and each exists for a different reason.

**`no_storage_caching`** is a boolean, default `false`. Set it to `true` and block data from RPC
endpoints in tests is not cached at all.<Cite src="foundry-testing-config" /><Cite src="foundry-default-config" />
Environment overrides are `FOUNDRY_NO_STORAGE_CACHING` and `DAPP_NO_STORAGE_CACHING`.<Cite src="foundry-testing-config" />

**`--no-storage-caching`** is the command-line equivalent, and the reference is precise about its
scope: it explicitly disables the use of RPC caching, all storage slots are read entirely from the
endpoint, and **it overrides the project's configuration
file**.<Cite src="forge-test-reference" /> That override is the point. It lets you answer "is this
failure cache-related?" without editing the repository's config, which is exactly the question you
want to answer without changing anything else.

Measured on forge 1.7.1: the same one-assertion suite that runs in under a millisecond warm takes
585 ms with `--no-storage-caching`, right back at cold speed, because it is cold by
construction.<Cite src="measured-fork-cache-1-7-1" />

**`[rpc_storage_caching]`** narrows caching rather than switching it
off.<Cite src="foundry-testing-config" />

```toml
[rpc_storage_caching]
chains    = ["mainnet", "optimism"]
endpoints = "remote"
```

- `chains` — a string or array of chain names, default **all**. `"all"` or a list such as
  `["optimism", "mainnet"]`.<Cite src="foundry-testing-config" />
- `endpoints` — a string or array of regex patterns matching URLs, default **remote**, so by default
  only remote endpoints are cached. Valid values are `all`, `remote`, or a list of patterns such as
  `["localhost"]`.<Cite src="foundry-testing-config" />

That `remote` default is the interesting one, and it is a correctness decision rather than a
performance one. A local endpoint is usually an [anvil](/c/anvil-role) instance or a devnet whose
state you are deliberately mutating between runs. Caching block data from a chain you are actively
rewriting would serve you a stale answer with no way to notice. So the default excludes exactly the
endpoints whose state is not stable, and caches the ones that are — a remote chain's block 21,000,000
is immutable, which is the property the whole cache rests on.

## When the cache is the bug

Caching is invisible until it is wrong, and then it produces the least helpful failure in this module:
a test that behaves in a way the code cannot explain.

The documented first move is to clear it. The fork-testing guide gives the blunt form,
`rm -rf ~/.foundry/cache/rpc`, and the troubleshooting page carries the same general
advice.<Cite src="foundry-fork-testing" /><Cite src="foundry-troubleshooting" />

**But be careful which "clean" you reach for, because one of them does nothing here.** The
fork-testing guide's stale-cache section suggests `forge clean` followed by a re-run. Measured on
forge 1.7.1: `forge clean` removes the project's `out/` and `cache/` directories and leaves
`~/.foundry/cache/rpc/mainnet/*` completely
untouched.<Cite src="measured-fork-cache-1-7-1" /><Cite src="foundry-fork-testing" /> That is
consistent with the config overview, which lists the project build cache at `<project_root>/cache/` and
the global RPC cache separately.<Cite src="foundry-config-overview" /> `forge clean` is the right tool
for a stale *build*. It is not the tool for a stale *fork*, and reaching for it will convince you the
cache is not the problem.

The precise tool is `forge cache`, which has two subcommands:

```bash
$ forge cache ls                        # what is cached, by chain and block, with sizes
$ forge cache clean                     # all chains (the default)
$ forge cache clean mainnet -b 21000000 # one chain, one block
$ forge cache clean --etherscan         # the Etherscan cache specifically
```

`clean` takes chains as positional arguments — defaulting to `all` — plus `-b, --blocks` and an
`--etherscan` switch, and `ls` shows cached data from the global Foundry
directory.<Cite src="forge-cache-reference" /><Cite src="measured-fork-cache-1-7-1" /> Scoped
invalidation is what you want during an investigation: drop the one block you suspect, keep the twenty
you already paid for, and re-run.

<Aside kind="warn">
`forge cache clean` with no arguments cleans **all** chains, because `all` is the documented
default.<Cite src="forge-cache-reference" /> On a machine with a warm multi-chain cache that is a
meaningful amount of re-fetching, and on a metered endpoint it is a bill. Name the chain and the block
unless you mean it.
</Aside>

## Choosing which block to pin

A pin is a number somebody has to pick, and there are only a few real considerations.

**Old enough to be settled.** Pin to a block deep enough that no reorganisation will ever touch it.
Anything more than a few dozen blocks back is comfortably beyond that in practice, and the assertion
you are writing does not care about recency.

**Young enough to be served.** This is the constraint people miss, and it is the subject of the next
lesson. A full node only caches recent state — ethereum.org gives the state associated with the last
128 blocks as its example figure — and prunes older state, which historical queries must then
regenerate or an archive node must supply.<Cite src="eth-archive-nodes" /> Pinning to a block from
2021 is a decision about which providers you may use.

**Chosen for the state you need, and written down.** If a test depends on a pool having a particular
depth or an account holding a particular balance, the block is part of the test's meaning. Put it in a
named constant with a comment saying what was true then. The number `21_000_000` in a diff is
unreviewable; `FORK_BLOCK` with "USDC/WETH pool depth ≈ 40M at this block" is a claim someone can
check.

**One per suite, unless there is a reason.** Every distinct block is a distinct cache key and a
distinct cold-fetch path. Ten tests sharing one pin share one warm cache; ten tests with ten pins are
ten first runs. That is not a rule against multiple pins — a test that needs the state before an
upgrade needs its own block — but each additional one has a price, and it should be buying something.

<Check type="explain" concept="fork-cache-keying">
A team has a forked integration suite of forty tests. It is pinned, it runs in CI on every pull
request, and their RPC bill is roughly what they expected.

Someone adds a fuzz test to that suite. It forks at the same pinned block as everything else, and it
runs the default 256 fuzz cases<Cite src="foundry-testing-config" /> against a lending market, each
case picking a random borrower address from a large set and reading that borrower's position.

The RPC bill quadruples, and CI gets much slower — but only for the first run after each merge to
`main`. Within a branch, repeated pushes are fast.

Explain every part of that pattern: why the bill rose despite the pin, why the first run after a merge
is the slow one, and what two changes would fix it.

<Answer>
**The pin is doing its job. The problem is that the suite now touches vastly more distinct state, and
that the CI cache key changes on every commit.**

**Why the bill rose.** Cost tracks distinct state touched, not test count. Forty hand-written tests
read a bounded, repeated set of accounts and slots. A fuzz test that picks a random borrower per case
reads a *different* position each time — a different hashed mapping slot, a different account — so
256 cases can mean hundreds of items that no previous run had ever requested. Pinning made all of them
cacheable; it did not make them free the first time. The pin controls *which* block you fetch from, not
*how much* of that block you ask for.

**Why the first run after a merge is the slow one.** The `foundry-toolchain` action's default cache key
is `${{ github.job }}-${{ github.sha }}`, with restore keys `[${{ github.job }}-]`.<Cite src="foundry-toolchain-action" />
So the key is unique per commit and never hits exactly; what actually produces a hit is the *prefix
restore key*, which loads the most recent cache saved under the same job. Within a branch that works
well. After a merge the runner may start from a cache saved before the new tests existed, so the new
state is fetched once and saved under the new key — one expensive run, then cheap ones. The suite is
behaving correctly; the cost is concentrated rather than eliminated.

**There is a second, sharper reason the cache can miss entirely, and it is specific to fuzzing.**
Foundry's own action documents it: if you are fuzzing in your fork tests, the caching strategy will not
work unless you set a fuzz seed.<Cite src="foundry-toolchain-action" /> Without a fixed seed each run
picks *different* borrowers, so each run requests state the previous run never fetched. The cache is
warm for state nobody is asking for and cold for everything being asked. That alone can account for a
sustained fourfold bill rather than a one-off spike.

**Two changes that fix it.**

1. **Pin the fuzz seed** for the forked suite, so the same runs request the same state and the cache
   is actually reachable.<Cite src="foundry-toolchain-action" /> The cost is that the fuzzer explores
   the same inputs every run — which is why the honest shape is a seeded fork suite on pull requests
   plus an unseeded campaign on a schedule, where paying for fresh state is the point.
2. **Bound the state the fuzzer can reach.** Fuzz over a fixed set of borrower addresses supplied as a
   fixture rather than over the whole address space. This is the same
   [prefer bound over assume](/c/bound-preferred-over-assume) instinct you already apply to numeric
   inputs, applied to *state breadth* instead of value range — and on a fork, state breadth is the
   dimension with a price on it.

**The general principle.** On a local suite, "fuzz more widely" costs CPU, which is nearly free. On a
forked suite it costs requests, which are not. Fuzzing and forking are both good ideas whose costs
multiply, and the combination deserves an explicit decision rather than inheritance from whichever
directory the test file landed in.
</Answer>
</Check>

## What this unlocks

**Immediately next, and last in this module:** everything here assumed the endpoint answers. The final
lesson is about when it does not — old blocks that need an archive node, rate limits that arrive as a
429, and the CI configuration that turns a per-run RPC bill into a nearly offline run. The pinned block
is what makes that CI cache key stable, so this lesson is its precondition.

**In your own repositories, this week:** run `forge cache ls`. If it lists more than a handful of
blocks per chain, your suite is either unpinned somewhere or rolling more than you realised, and the
list tells you exactly which blocks to go and look for in the source.

**And the review habit worth forming:** treat a `createFork` or `createSelectFork` call with no second
argument the way you would treat a missing `require`. It compiles, it runs, it passes — and it has
quietly made the test unrepeatable and the suite expensive, in a way no failure will ever point at.
