A new engineer clones the repository, runs `forge test`, and gets this:

```text
Error: could not instantiate forked environment

Context:
- Internal transport error: ...
```

That is forge 1.7.1's actual wording when `eth_rpc_url` resolves to something it cannot talk to —
here, an environment variable that was never set, so the literal `${MAINNET_RPC_URL}` survived into
the transport layer.<Cite src="measured-fork-cache-1-7-1" /> Nothing in it mentions forks, tests or
configuration.

There are 240 tests in that suite. Six of them integrate with a live protocol. The other 234 are pure
unit tests of the project's own contracts and have no interest in mainnet whatsoever. All 240 are
unrunnable, for everyone, until somebody has an API key — because a single line in `foundry.toml` put
the *whole run* on a fork.

That is not a configuration mistake so much as a mode mistake. Foundry has two ways to put a test on a
fork, and they are not two syntaxes for the same thing. One is a property of the run; the other is a
property of a test. This lesson is about which question each one answers.

## Mode one: the run is forked

The command-line form puts every test in the invocation on one fork:

```bash
$ forge test --fork-url https://ethereum.reth.rs/rpc --fork-block-number 21000000
```

`--fork-url` is worth a second look. In forge 1.7.1 the canonical flag is `-r, --rpc-url <URL>`, and
`--fork-url` is registered as an alias for it.<Cite src="forge-test-reference" /><Cite src="measured-forge-1-7-1" />
That naming is a hint about the model: you are not asking for a "fork object", you are telling the
test runner which endpoint the EVM may consult when it does not have something.
`--fork-block-number <BLOCK>` then fixes *which* block those consultations refer to — the reference
describes it as
fetching state from a specific block number over a remote endpoint.<Cite src="forge-test-reference" />

The same thing lives in configuration, which is where it belongs for a suite that is always forked:

```toml
[profile.default]
eth_rpc_url = "https://ethereum.reth.rs/rpc"
fork_block_number = 21000000
```

The docs present exactly this pair as the way to set a default fork for all
tests.<Cite src="foundry-fork-testing" /> `eth_rpc_url` is the general "which endpoint should RPC
calls use" key, with `FOUNDRY_ETH_RPC_URL` and `DAPP_ETH_RPC_URL` as its environment
overrides.<Cite src="foundry-testing-config" />

The opening error came from putting that pair under `[profile.default]` in a repository where most
tests are local. The fix is one word: put it under a profile that only the integration job selects,
and let `default` stay offline. You already know how [profiles](/c/foundry-profiles) and
[precedence](/c/config-precedence) resolve; the judgement call is that **"is this run forked" is a
property worth attaching to a profile, not to the project.**

  belief="Setting eth_rpc_url in foundry.toml is harmless — it only matters for tests that actually reach out."
  reality="Under [profile.default] with fork_block_number, it forks the entire run. Every test, including the 234 that never touch a live contract, now needs a working endpoint before it can execute."
  why="The key is named after a URL rather than after a mode, so it reads like a connection string sitting idle until something uses it."

## Mode two: the test is forked

The cheatcode API moves the decision inside the test contract, where it can differ test by test. Four
calls carry almost all of it:

```solidity
function createFork(string calldata urlOrAlias) external returns (uint256 forkId);
function createFork(string calldata urlOrAlias, uint256 blockNumber) external returns (uint256 forkId);
function createFork(string calldata urlOrAlias, bytes32 txHash) external returns (uint256 forkId);

function selectFork(uint256 forkId) external;
function createSelectFork(string calldata urlOrAlias) external returns (uint256 forkId);
function activeFork() external view returns (uint256 forkId);
```

Read them as one idea in four pieces.<Cite src="foundry-cheatcode-create-fork" /><Cite src="foundry-cheatcode-select-fork" /><Cite src="foundry-cheatcode-create-select-fork" /><Cite src="foundry-cheatcode-active-fork" />

**`createFork` builds a fork and hands you a numeric id, without activating it.** The reference is
explicit that the fork is *not* automatically selected.<Cite src="foundry-cheatcode-create-fork" />
This separation is the whole reason the API has four calls instead of one: setup can create every
fork a test might need, and the test decides when to enter one.

**`selectFork(id)` makes one of them the active state.**<Cite src="foundry-cheatcode-select-fork" />

**`createSelectFork` does both, and is documented as equivalent to `createFork` followed by
`selectFork`.**<Cite src="foundry-cheatcode-create-select-fork" /> Convenient, and the source of a
specific trap that the next lesson spends real time on.

**`activeFork()` reports the current id — and reverts when there is no fork active.**<Cite src="foundry-cheatcode-active-fork" />
That revert is not hypothetical. Called in a non-forked run on forge 1.7.1 it fails the test with
`vm.activeFork: no active fork`, which is a usefully unambiguous message the first time you see
it.<Cite src="measured-fork-cache-1-7-1" />

All three creators take an optional second argument, and the *block* and *transaction-hash* overloads
are the same shape: `createFork(url, 21000000)` pins by number, `createFork(url, txHash)` forks at
that transaction's block and replays the transactions before
it.<Cite src="foundry-cheatcode-create-fork" /> The second form is the subject of this module's fourth
lesson; note now only that pinning is available in both modes, and that it is a positional argument
you can forget.

<Aside kind="note">
These arrive through the same mechanism as every other cheatcode: a call to the `Vm` address that the
executor intercepts rather than executes.<Cite src="foundry-cheatcodes-overview" /> In practice you
inherit `forge-std`'s `Test`, which declares the interface and the address for
you.<Cite src="forge-std-repo" /> Nothing about forking is a separate subsystem you have to configure;
it is the same [cheatcode mechanism](/c/vm-cheatcode-mechanism) you already use for `prank` and `warp`.
</Aside>

## The two modes in one run

They compose, and the composition is under-documented, so here is what forge 1.7.1 actually does
rather than what you might assume.

Run a test under `--fork-url` and call `vm.activeFork()` in it: it returns **0**. The
command-line fork is a real fork with the ordinary fork id 0. A subsequent `vm.createFork(...)` in the
same test returns a *different* id and does not change the active one, exactly as the reference
describes; `vm.selectFork` then moves between
them.<Cite src="measured-fork-cache-1-7-1" /><Cite src="foundry-cheatcode-create-fork" />

That behaviour is coherent and convenient, and it is not in the documentation. Treat it as an
observation on one version, not a contract — a suite that depends on "the CLI fork is id 0" is
depending on something nobody has promised. If a test needs a specific fork, create it and hold its
id.

## Naming the endpoints instead of embedding them

Both modes take a URL, and a URL with a provider key in it is a secret. `[rpc_endpoints]` is the
answer, and it has two properties worth knowing precisely.

```toml
[rpc_endpoints]
mainnet  = "${RPC_MAINNET}"
optimism = "https://optimism.example.com/v2/..."
```

**It lives outside profiles.** The config reference states this directly: the section defines a table
where the key is the endpoint's name and the value is the endpoint
itself.<Cite src="foundry-testing-config" /> So the alias table is shared across `default`, `ci` and
anything else you define — one place, not one place per profile.

**The value may be a reference to an environment variable, wrapped in `${}`.**<Cite src="foundry-testing-config" />
That is what keeps the keyed URL out of source control while leaving the *name* in it, which is the
part your tests and your workflow files should be reading.

Anywhere a cheatcode takes `urlOrAlias`, the alias works.<Cite src="foundry-cheatcode-create-fork" />
And the aliases are readable from inside a test through the RPC cheatcodes — `vm.rpcUrl("mainnet")`
resolves one, `vm.rpcUrls()` returns every configured `[alias, url]` pair, and
`vm.rpc(method, params)` issues a raw JSON-RPC call against the active fork's
endpoint.<Cite src="foundry-cheatcode-rpc" />

  belief="Aliases like `mainnet` are chain names Foundry recognises, so a createFork call naming one works out of the box."
  reality="They are keys you define in [rpc_endpoints]. An unconfigured alias is not a known network; it is a missing entry, and the test fails at the point of the call."
  why="`mainnet` and `optimism` appear in every example, which makes them look built in rather than conventional."
  src="foundry-testing-config"

## Worked example: pulling a suite off the fork

Here is the opening repository, repaired. The purpose of each step matters more than the edit.

**Subgoal — separate the tests that need a network from the tests that do not.** Move the six
integration tests into `test/fork/` and leave everything else where it is. This is a filesystem
change, not a semantic one, but it is what makes every later step expressible as a path.

**Subgoal — make the default profile offline again.** Delete `eth_rpc_url` and `fork_block_number`
from `[profile.default]`. `forge test` now runs 234 tests with no endpoint, no key and no network, for
anyone who clones the repository.

**Subgoal — give the forked tests a name for the endpoint rather than the endpoint.**

```toml
[rpc_endpoints]
mainnet = "${MAINNET_RPC_URL}"
```

The alias table sits outside profiles, so it is visible to whichever profile ends up
running.<Cite src="foundry-testing-config" />

**Subgoal — put the fork decision where the test can see it.** Each integration test declares its own
fork and its own pin:

```solidity
contract VaultIntegrationTest is Test {
    uint256 mainnetFork;

    function setUp() public {
        mainnetFork = vm.createSelectFork("mainnet", 21_000_000);
    }
}
```

Now the block number is in the test file, next to the assertions that depend on it, and it is
reviewable in a diff.

**Subgoal — make the expensive suite opt-in.** The integration tests run under their own invocation:

```bash
$ forge test --match-path 'test/fork/**'
```

which is the same [test filtering](/c/test-filtering) you already use, now doing load-bearing work:
it is the boundary between the suite that runs on every save and the suite that costs money.

**Subgoal — check the result against the original complaint.** A fresh clone runs `forge test`
successfully with no secrets. A contributor without an endpoint can change the vault's rounding logic
and see 234 tests confirm it. The six that need mainnet fail loudly and specifically when invoked, and
are never invoked by accident.

## Choosing between them

The decision is not about style.

**Use the run-level flag when the entire invocation is an integration run.** A dedicated fork job in
CI, a repository that exists only to test against a live protocol, or a one-off local run where you
want the whole suite on a fork for an afternoon. It is one flag and there is nothing to get wrong in
Solidity.

**Use the cheatcodes when forking is a property of some tests and not others** — which is the common
case — **or when a test needs more than one chain, or a specific block per test, or needs to move
between blocks.** None of those are expressible with a flag, because a flag applies to the run.

**Use both when it helps.** A run-level `--fork-url` for the default chain plus per-test
`createFork` for the second one is a legitimate shape; just do not let the run-level default leak into
the profile the rest of the team uses.

<Check type="spot-bug" concept="rpc-endpoints-aliases">
A team is preparing a repository for external contributors. Their `foundry.toml`:

```toml
[profile.default]
src = "src"
eth_rpc_url = "https://eth-mainnet.example.com/v2/9f4c1e8a2b7d"
fork_block_number = 21000000
verbosity = 2

[profile.ci]
fuzz = { runs = 10000 }

[rpc_endpoints]
mainnet = "https://eth-mainnet.example.com/v2/9f4c1e8a2b7d"
```

And a representative integration test:

```solidity
contract PriceTest is Test {
    function setUp() public {
        vm.createSelectFork("mainnet");
    }

    function test_OracleIsFresh() public view {
        assertGt(oracle.latestAnswer(), 0);
    }
}
```

Name every distinct problem here, say what each one costs, and give the smallest correct fix for
each. There are four.

<Answer>
**1 — The whole suite is forked, and the profile is the wrong place for that.** `eth_rpc_url` plus
`fork_block_number` under `[profile.default]` is documented as setting a default fork for all
tests.<Cite src="foundry-fork-testing" /> Cost: no test in the repository runs without a working
endpoint, including tests with no interest in one. Fix: remove both keys from `default` and let the
forked tests declare their own forks, or move the pair to a profile only the integration job selects.

**2 — The provider key is committed, twice.** It is in `eth_rpc_url` and again in the `[rpc_endpoints]`
table, so the alias indirection is buying nothing. Cost: a secret in git history, retrievable by
anyone who ever clones the repository, and rotating it means a commit. Fix: the documented
`${ENV_VAR}` form — `mainnet = "${MAINNET_RPC_URL}"` — which is exactly what the alias table exists
to support.<Cite src="foundry-testing-config" />

**3 — `vm.createSelectFork("mainnet")` has no block argument, so it tracks latest.** The
`fork_block_number` in the config does not rescue it: the cheatcode is creating its own fork, and the
block is the argument you did not pass.<Cite src="foundry-cheatcode-create-select-fork" /> Cost:
`test_OracleIsFresh` runs against different state every hour, and cannot hit the cache — which the
fifth lesson in this module shows is the expensive half of that sentence. Fix:
`vm.createSelectFork("mainnet", 21_000_000)`.

**4 — The pin, if it had worked, is in the wrong place to be reviewed.** A block number in
`foundry.toml` applies to every test at once, so changing it to fix one test silently re-dates all of
them. Cost: an invisible blast radius on a one-line change. Fix: keep per-test pins next to the
assertions that depend on them, as a named constant in the test file.

**The pattern underneath all four.** Three of these are the same error wearing different clothes: a
decision that belongs to *one test* has been written somewhere that applies to *the whole project*.
The endpoint, the pin, and the fork mode are all per-test facts in this repository, and all three were
stored globally. The remaining one — the committed key — is what the alias table exists to prevent and
what it cannot prevent if you paste the URL in anyway.
</Answer>
</Check>

## What this unlocks

**Immediately next:** once forks are values with ids, a test can hold several. That opens cross-chain
testing and closes off an intuition you have earned everywhere else in programming — that the objects
you created a moment ago are still there.

**Two lessons on:** the block argument you have been passing positionally becomes the subject. Moving
a fork between blocks is a different operation from moving `block.number`, and the two cheatcodes for
them differ by four characters.

**Later in this module:** `[rpc_endpoints]` is also the seam your CI configuration attaches to. A
workflow that sets one environment variable, and a `foundry.toml` that names it, is the difference
between a fork suite that runs in CI and one that only ever ran on the author's
laptop.<Cite src="foundry-config-overview" /><Cite src="foundry-default-config" />
