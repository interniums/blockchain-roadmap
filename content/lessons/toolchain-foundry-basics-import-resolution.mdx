`import {Test} from "forge-std/Test.sol";` is in every test file you will write, and it is not a path.
There is no directory called `forge-std` next to your test. The string does not begin with `./` or
`../`, so the compiler is not going to resolve it relative to anything. Something rewrote it before
the filesystem was ever consulted.

That something is a **remapping**, and the rule it applies is trivial: a rule of the form
`prefix/=path/` replaces the prefix with the path.<Cite src="foundry-solc-config" /> In this case:

The mechanism is one line long. The reason this lesson is fourteen minutes long is that the *set* of
rules in force comes from four independent places at once, they merge rather than replace, and the
merged result is not written down in any file you can read. If you ever work in a repository that
runs Foundry and Hardhat side by side, this is also where the two toolchains
[stop meaning the same thing by the same string](/c/remapping-vs-node-resolution).

It is worth being clear about what the indirection is *for*, because the same import string has to
survive several different vendoring decisions. A library — [OpenZeppelin](/c/oz-is-the-stdlib) being
the one every project has — might arrive as a git submodule under
`lib/`, as an npm package under `node_modules/`, as a Soldeer download, or as a checked-in fork you
patched. Under any of those, `import "@openzeppelin/contracts/token/ERC20/ERC20.sol"` is the line
people write, and the line every tutorial shows. The remapping is the seam that lets the source stay
constant while the layout underneath it changes — which is exactly why the seam is also where two
machines quietly disagree about what they compiled.

## The four sources, measured

Here is a project with `lib/forge-std`, `lib/solmate` and `lib/openzeppelin-contracts` on disk, and
nothing else configured. `forge remappings` prints the resolved set:

```console
$ forge remappings
forge-std/=lib/forge-std/src/
openzeppelin-contracts/=lib/openzeppelin-contracts/contracts/
solmate/=lib/solmate/src/
```

Nobody wrote those. `auto_detect_remappings` defaults to `true`, and forge derives a rule per
directory under `libs`, pointing at whichever of `src/` or `contracts/` that dependency actually
uses.<Cite src="foundry-solc-config" /><Cite src="measured-foundry-basics-1-7-1" /> That is source
one, and it is why a freshly cloned Foundry repository compiles with no remapping configuration at
all.

**Source two** is `remappings.txt`, one rule per line — the inheritance from dapptools, and still
what most editor plugins and language servers read. Adding one line:

```text
@oz/=lib/openzeppelin-contracts/contracts/
```

```console
$ forge remappings
@oz/=lib/openzeppelin-contracts/contracts/
forge-std/=lib/forge-std/src/
openzeppelin-contracts/=lib/openzeppelin-contracts/contracts/
solmate/=lib/solmate/src/
```

Four rules, not one. The file **added** to the set.<Cite src="measured-foundry-basics-1-7-1" />

**Source three** is the `remappings` key in `foundry.toml`.<Cite src="foundry-solc-config" /> Adding
`remappings = ["@toml/=lib/solmate/src/"]` gives five rules — again additive, not replacing.

**Source four** is the environment. `FOUNDRY_REMAPPINGS` and `DAPP_REMAPPINGS` are listed in the
configuration reference as *exceptions* to the ordinary environment-variable
override.<Cite src="foundry-config-overview" /> Measured, the exception means they append:

```console
$ FOUNDRY_REMAPPINGS="@env/=lib/solmate/src/" forge remappings
@env/=lib/solmate/src/
@oz/=lib/openzeppelin-contracts/contracts/
forge-std/=lib/forge-std/src/
openzeppelin-contracts/=lib/openzeppelin-contracts/contracts/
solmate/=lib/solmate/src/
```

Six rules from four sources, and no single file in the repository contains more than
one-quarter of them.<Cite src="measured-foundry-basics-1-7-1" />

## What happens when two sources claim the same prefix

Merging is fine until two sources define the same prefix differently. That is the case worth learning
properly, because it is the one that produces a build which compiles cleanly against the wrong file.

The experiment: `remappings.txt` says `@oz/` means OpenZeppelin. `foundry.toml` says `@oz/` means
solmate.

```console
$ cat remappings.txt
@oz/=lib/openzeppelin-contracts/contracts/

$ grep remappings foundry.toml
remappings = ["@oz/=lib/solmate/src/"]

$ forge remappings
@oz/=lib/openzeppelin-contracts/contracts/
forge-std/=lib/forge-std/src/
openzeppelin-contracts/=lib/openzeppelin-contracts/contracts/
solmate/=lib/solmate/src/
```

The TOML entry is gone — not merged, not renamed, gone. `remappings.txt` won, and a build confirms
it resolves to `lib/openzeppelin-contracts/contracts/token/ERC20/ERC20.sol`.<Cite src="measured-foundry-basics-1-7-1" />
Delete `remappings.txt` and the same import silently starts resolving into solmate instead. This
precise tension — that a `remappings.txt` sitting in the repository quietly overrides what
`foundry.toml` says — is the subject of a long-running open issue.<Cite src="foundry-issue-5258" />

Both of the non-obvious steps were checked directly: an environment rule overrode a `foundry.toml`
rule with the same prefix, and a `foundry.toml` rule overrode an auto-detected rule with the same
prefix.<Cite src="measured-foundry-basics-1-7-1" /> The practical reading is that auto-detection is a
floor, not a default you have to fight: anything you write explicitly displaces it.

## Overlapping prefixes resolve by order, not by specificity

There is a second collision case, and it is nastier because both rules survive into the resolved set.
Two prefixes can overlap without being equal — `@oz/` and `@oz/token/` — and then the question is
which one an import matching both gets.

The intuition almost everyone brings is *the more specific one*. Measured on forge 1.7.1, that is
wrong: the **first** matching rule in the resolved order wins, regardless of length.

**Subgoal — set up an unambiguous probe.** Two rules, general one first, and a file present at both
targets:

```toml
remappings = [
  "@oz/=lib/openzeppelin-contracts/contracts/",
  "@oz/token/=lib/patched/token/",
]
```

```solidity
import "@oz/token/ERC20/ERC20.sol";
```

**Subgoal — ask the toolchain, not yourself.** `forge tree` prints the resolved import graph, so it
answers the question without any interpretation on your part:

```console
$ forge tree
src/P.sol ^0.8.36
└── lib/openzeppelin-contracts/contracts/token/ERC20/ERC20.sol
```

The general rule fired. `@oz/token/` never had a chance, despite being an exact and more specific
match.<Cite src="measured-foundry-basics-1-7-1" />

**Subgoal — isolate the variable.** Swap the two lines and change nothing else:

```toml
remappings = [
  "@oz/token/=lib/patched/token/",
  "@oz/=lib/openzeppelin-contracts/contracts/",
]
```

```console
$ forge tree
src/P.sol ^0.8.36
└── lib/patched/token/ERC20/ERC20.sol
```

Same source file, same import string, different file compiled. The only thing that changed was line
order.<Cite src="measured-foundry-basics-1-7-1" />

**Subgoal — check it is the order and not the file.** The same experiment run from `remappings.txt`
instead of `foundry.toml`, with the specific rule first, gives the same result — the patched
file.<Cite src="measured-foundry-basics-1-7-1" /> So the behaviour belongs to the position of a rule
in the merged set, not to which file it came from.

The operational rule that falls out: **write the most specific prefix first**, and never assume a
narrower rule will override a broader one just because it is narrower. This one is worth verifying
against whatever version you are on rather than trusting this paragraph — it is exactly the kind of
resolution detail that can change between releases, and `forge tree` settles it in one command.

## Turning auto-detection off, and what goes with it

`auto_detect_remappings = false` is the switch people reach for when they want the configuration to
be self-describing. It does exactly what it says, and the collateral damage is instructive:

```console
$ forge remappings
@oz/=lib/openzeppelin-contracts/contracts/
@toml/=lib/solmate/src/
```

Two rules left — the two that were written down. `forge-std/` is gone, and with it every test file in
the project, because `import {Test} from "forge-std/Test.sol"` no longer resolves to
anything.<Cite src="measured-foundry-basics-1-7-1" /> If you turn detection off, you own the whole
set, forge-std included.

That is a defensible choice; it is how you make a repository's import graph legible from one file.
It is not a choice you make by accident, and the failure mode is loud, which is the good kind.

<Aside kind="note">
`forge remappings --help` describes the command as printing "the automatically inferred remappings
for the project", which undersells it: as every output above shows, it prints the fully merged set
including everything you wrote by hand.<Cite src="measured-foundry-basics-1-7-1" /> Treat it the way
you will shortly treat `forge config` — as the resolved answer, not as an echo of any one input.
`--pretty` groups the output by context, which matters once a dependency carries remappings of its
own.
</Aside>

## Where the files came from: submodules, a lockfile, and Soldeer

Remappings point at `lib/`. What put anything there?

`forge install` vendors a dependency as a **git submodule**.<Cite src="foundry-dependencies" /> A
fresh `forge init` in a git repository produces both halves of that record:

```console
$ cat .gitmodules
[submodule "lib/forge-std"]
	path = lib/forge-std
	url = https://github.com/foundry-rs/forge-std

$ cat foundry.lock
{
  "lib/forge-std": {
    "tag": {
      "name": "v1.16.2",
      "rev": "bf647bd6046f2f7da30d0c2bf435e5c76a780c1b"
    }
  }
}
```

Both are real output.<Cite src="measured-foundry-basics-1-7-1" /> `.gitmodules` records *where the
code comes from*; `foundry.lock` records *which revision was chosen and why* — here, a tag, resolved
to a specific commit. `forge update` moves the submodule checkout and the lockfile entry together,
and the documented rule for what moves is worth memorising: a plain `forge update` fetches the latest
commit for every **branch-based** dependency, while dependencies installed from a tag or a commit
stay pinned until you name a new ref explicitly.<Cite src="foundry-dependencies" />

```console
$ forge update openzeppelin/openzeppelin-contracts@tag=v5.1.0
```

Review and commit both the changed dependency path and `foundry.lock` after an
update.<Cite src="foundry-dependencies" />

The submodule choice has one consequence that will bite you or a contributor within a month: **a
clone without submodules has an empty `lib/`**, so every import fails and the error is a
source-not-found, not a "you forgot to install dependencies". The fix is `--recurse-submodules` on
clone, `git submodule update --init --recursive` afterwards, and
[`submodules: recursive`](/c/submodule-checkout) on the checkout step in CI — which is why every
official Foundry CI example carries that line.<Cite src="foundry-ci" />

Two alternatives ship in the same binary. **Soldeer** is a registry-based package manager exposed as
`forge soldeer`, with `init`, `install`, `update`, `push` and `login`
subcommands.<Cite src="measured-foundry-basics-1-7-1" /> And plain npm packages work if you add
`node_modules` to `libs`:

```toml
[profile.default]
libs = ["lib", "node_modules"]
remappings = ["@openzeppelin/=node_modules/@openzeppelin/"]
```

The documentation attaches a warning to that path — npm packages may not be designed for Foundry, and
git submodules remain the preferred route for Solidity libraries.<Cite src="foundry-dependencies" />
Submodules are also what almost every public contract repository uses, which matters when you are
reading someone else's code rather than writing your own. Whichever route you take, the dependency
is code you will compile and ship, so the choice sits inside your
[trust boundary](/c/toolchain-trust) rather than beside it.

## Reading an unfamiliar repository

Put the pieces together into a procedure, because this is what you will actually do:

**Step 1 — get the truth, not the configuration.** Run `forge remappings`. Whatever it prints is what
the compiler will use. Do not start from `remappings.txt`.

**Step 2 — account for every line.** For each rule, decide which of the four sources produced it.
A rule whose prefix equals a directory name under `lib/` and whose target is that directory's `src/`
or `contracts/` is almost certainly auto-detected. Anything else was written by someone, and the
question is where.

**Step 3 — check for the shadowed entry.** If `remappings.txt` exists *and* `foundry.toml` has a
`remappings` key, any prefix in both is being served by the `.txt` file, and the TOML line is dead
text that reads as if it were live.

**Step 4 — check the environment.** `env | grep -i foundry` before you conclude anything. A shell
profile or a CI image can add rules with no trace in the repository.

**Step 5 — look for overlapping prefixes.** If two rules share a leading segment, the one printed
first is the one that fires, and the other is dead for every import they both match. This is the
failure you will not spot by reading, because both lines look live.

**Step 6 — resolve one import by hand and confirm.** Take the import you care about, apply the first
matching prefix, and check the file exists. `forge tree` will show you the resolved import graph if
you would rather have the tool do it, and it is the fastest way to settle any argument about which
file a line of source actually pulled in.<Cite src="measured-foundry-basics-1-7-1" />

<Check type="spot-bug" concept="remapping-resolution-order">
A repository has been building fine for a year. Its `foundry.toml` contains:

```toml
[profile.default]
libs = ["lib"]
remappings = ["@openzeppelin/=lib/openzeppelin-contracts-v4/contracts/"]
```

It also has a `remappings.txt`, added eighteen months ago and untouched since:

```text
@openzeppelin/=lib/openzeppelin-contracts/contracts/
```

Both directories exist under `lib/`. A new engineer reads `foundry.toml`, concludes the project is on
OpenZeppelin v4, and writes code against the v4 API. It does not compile, and the errors point at
contracts they did not touch.

What is happening, what will `forge remappings` print, and what is the fix?

<Answer>
**`remappings.txt` is winning.** On a prefix collision, `remappings.txt` overrides the `remappings`
key in `foundry.toml`, so `@openzeppelin/` resolves into `lib/openzeppelin-contracts/`, and the
`foundry.toml` line is inert.<Cite src="measured-foundry-basics-1-7-1" /><Cite src="foundry-issue-5258" />
`forge remappings` will print exactly one `@openzeppelin/` rule, pointing at
`lib/openzeppelin-contracts/contracts/`, plus whatever auto-detection contributes for the other
directory — likely a second rule with the prefix `openzeppelin-contracts-v4/`.

**Why the errors look unrelated.** The new engineer's code is not the only thing importing that
prefix. Every existing file resolving `@openzeppelin/` was already getting the other library, so the
compile errors surface wherever the two APIs differ, not where the new code was written. That is the
signature of a resolution problem rather than a code problem: the errors are in files nobody edited.

**The fix, in order of preference.** Delete `remappings.txt` and keep one source of truth in
`foundry.toml`. If an editor or language server in your team's setup needs the `.txt` file, keep it
and delete the `remappings` key instead — but do not keep both, because the one that loses is
invisible.

**The trap underneath.** Two versions of the same library, distinguished only by a directory name, is
a configuration where a one-character mistake changes which contracts you inherit and nothing warns
you. If the situation is deliberate, the documented pattern is to install each under an explicit
alias and give each its own unambiguous prefix, so that no import string is ever ambiguous about
which version it means.<Cite src="foundry-dependencies" />
</Answer>
</Check>

## Where this pays off

Import resolution is the first of the three ways two machines compile the same commit differently,
and it is the one with the most sources: four inputs, merged, with a precedence order you cannot see
from any single file. `forge remappings` collapses all of it into one answer, and building the reflex
to run it before you theorise is most of the value of this lesson.

The next lesson is the same shape applied to everything else. Configuration also arrives from several
layers, also merges rather than replaces, and also has one command that prints the resolved
truth — with the added twist that a profile you never mentioned may be selecting a different set of
values entirely.

One caution to carry forward, and it applies to the entire rest of this track: the published CLI
reference pages are generated from a nightly build, and the site says so on the page that lists which
binaries generated them.<Cite src="foundry-versions-reference" /> The `forge remappings` reference
documents a `--profile` flag that forge 1.7.1 rejects
outright.<Cite src="forge-remappings-reference" /><Cite src="measured-foundry-basics-1-7-1" /> When a
documented flag does not work, run `--help` on your own binary before assuming you typed it wrong.
