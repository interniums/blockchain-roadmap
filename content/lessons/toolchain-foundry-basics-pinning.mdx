Three version numbers decide what bytecode comes out of `forge build`, and they move independently:
the **compiler** that ran, the **hardfork ruleset** it targeted, and the **build of forge** that
chose the other two. Pin none of them and you have a build that is reproducible only by coincidence.
Pin two and you have found out the hard way which one you forgot.

This lesson closes each of the three, in the order they bite.

## The compiler

`auto_detect_solc` defaults to `true`, and it is a per-file decision: forge reads each source file's
pragma and selects a compiler that satisfies it, downloading one if
needed.<Cite src="foundry-solc-config" /><Cite src="measured-foundry-basics-1-7-1" /> Compilers land
in `~/.svm/` if that directory already exists, and otherwise in the platform data directory — on
macOS, `~/Library/Application Support/svm/`.<Cite src="foundry-config-overview" />

Auto-detection is not wrong; it is *underdetermined*. `pragma solidity ^0.8.13` is satisfied by
0.8.13 and by 0.8.36 and by everything between. Which one you get depends on what forge decides to
resolve to on the day, on that machine — and two different compilers produce different bytecode and
different gas for the same source. That is the whole problem.

Pinning is one line:

```toml
[profile.default]
solc = "0.8.36"
```

`solc_version` is the same key under a different spelling; both are accepted and both surface as
`solc` in `forge config`.<Cite src="measured-foundry-basics-1-7-1" /><Cite src="foundry-config-landing" />
There is also `FOUNDRY_SOLC_VERSION` for the environment layer, with the precedence you now expect.

<Aside kind="warn">
Here is a trap worth carrying: after setting `solc = "0.8.36"`, `forge config` still prints
`auto_detect_solc = true`.<Cite src="measured-foundry-basics-1-7-1" /> The flag is not the evidence.
The behaviour is, and it is easy to check — pin a version that cannot satisfy a file's pragma and
forge refuses to compile rather than quietly finding a compatible compiler:

```console
$ grep solc foundry.toml
solc = "0.8.13"

$ forge build --force
Error: Encountered invalid solc version in src/Needs36.sol: No solc version exists that matches
the version requirement: ^0.8.36
```

Under auto-detection that file would have compiled, with a different compiler than everything around
it.<Cite src="measured-foundry-basics-1-7-1" /> The pin turned a silent divergence into a build
failure, which is exactly the trade you want.
</Aside>

The artifact records which compiler ran — `"compiler": { "version": "0.8.36+commit.8a079791" }` — and
that string is what a block explorer needs to reproduce your bytecode later.<Cite src="measured-foundry-basics-1-7-1" />
The deploy-and-verify module makes that concrete; the point here is that the pin and the verification
requirement are the same fact seen from two ends.

## The ruleset

`evm_version` selects which hardfork's opcode set and gas schedule the compiler targets and the test
EVM enforces. On forge 1.7.1 with solc 0.8.36, the resolved default is
`osaka`.<Cite src="measured-foundry-basics-1-7-1" /> That is not Foundry's choice — solc set its own
default EVM version to `osaka` in 0.8.31, released 3 December 2025, and `solc --help` on 0.8.36 still
reports `--evm-version version (=osaka)`.<Cite src="solidity-changelog" /><Cite src="measured-foundry-basics-1-7-1" />

The setting is not cosmetic, and the cleanest demonstration is the smallest one. Compile the
generated `Counter.sol` twice, changing nothing but this line:

**Subgoal — establish that the source is identical.** Same file, same compiler 0.8.36, same optimizer
setting. Only `evm_version` differs.

**Subgoal — compare the first instruction bytes.**

```text
osaka   6080604052348015600e57 5f 5f fd 5b50...
paris   6080604052348015600f57 6000 6000 fd 5b50...
```

**Subgoal — name the difference.** `5f` is `PUSH0`, introduced by EIP-3855 in
Shanghai.<Cite src="eip-3855" /> Targeting `paris` — which predates it — the compiler cannot use the
one-byte instruction and emits `6000`, a two-byte `PUSH1 0x00`, instead. Every zero-push in the
contract pays one extra byte.

**Subgoal — measure the total.** Runtime bytecode: **481 bytes under `osaka`, 498 under `paris`**, for
a contract with two functions.<Cite src="measured-foundry-basics-1-7-1" />

Now invert the scenario. Compile for `osaka`, deploy to a chain whose EVM stops at `paris`, and the
bytecode contains an opcode that chain does not implement. Nothing catches it at build time. Nothing
catches it at deploy time either, if the offending instruction is on a path the constructor does not
take. It surfaces the first time a user hits that path.

Which is why this pin is not optional when you deploy anywhere other than Ethereum mainnet. Many L2s
and sidechains run behind mainnet's fork schedule, and `evm_version` is how you tell the compiler so.

Two guardrails worth knowing. An unknown value is rejected when the configuration loads, not later:

```console
$ forge config
Error: failed to extract foundry config:
foundry config error: Unknown evm version: bogusfork for setting `evm_version`
```

And the accepted set is not the same on both sides of the toolchain. solc 0.8.36 lists
`amsterdam (experimental)` and `@future (experimental)` among its EVM versions, and 0.8.36's release
notes record "Support for the EVM version 'Amsterdam'" as a
feature.<Cite src="measured-foundry-basics-1-7-1" /><Cite src="solidity-0836-release" /> forge 1.7.1
rejects `evm_version = "amsterdam"` outright.<Cite src="measured-foundry-basics-1-7-1" /> The
compiler can target a ruleset the build tool will not let you select — a small thing, and a precise
illustration of why these are three version numbers rather than one.

<Aside kind="stop">
A claim you will meet in 2026 material, and should not repeat: that stack-too-deep is solved in
0.8.36. What the release announcement actually reports is narrower on three counts. The SSA-form code
generator introduced in 0.8.35 gained stack-to-memory spilling; that generator is still experimental
and has to be switched on with `--experimental --via-ssa-cfg`; and it is not the default even for
`--via-ir`.<Cite src="solidity-0836-release" /> Meanwhile `via_ir` itself defaults to `false` on
forge 1.7.1, so a default build is not on the IR pipeline at all.<Cite src="measured-foundry-basics-1-7-1" />
Three gates, all closed, before that fix reaches your build.
[Stack-too-deep](/c/stack-too-deep) is a thing you still design around, and
[the IR pipeline](/c/via-ir-pipeline) is still something you opt into.
</Aside>

## The toolchain itself

The third number is `forge`, and it is the one people forget because it does not appear in
`foundry.toml` at all.

`foundryup` with no arguments installs the latest **stable** release of all four
binaries.<Cite src="foundry-installation" /> Everything else is explicit:

```console
$ foundryup --install nightly
$ foundryup --install 1.0.0
$ foundryup --install nightly-abc1234
$ foundryup --branch master
```

Those four forms are documented, and `foundryup --help` on this machine lists the same shape:
`--install` takes `latest`, `nightly`, `nightly-<SHA>` or a version, with `--branch`, `--commit`,
`--PR` and `--path` building from source.<Cite src="foundry-installation" /><Cite src="measured-foundry-basics-1-7-1" />
Two more flags matter for pinning: `--list` shows what is installed, and `--use` switches between
installed toolchains, which are stored side by side under `~/.foundry/versions/`.<Cite src="measured-foundry-basics-1-7-1" />

That last pair is the piece most people do not know exists. `~/.foundry/versions/` is a store, not a
single slot, so keeping two toolchains and switching between them is a supported workflow rather than
a reinstall:

```console
$ foundryup --list
foundryup: v1.7.1
foundryup: - forge 1.7.1 (4072e48705 2026-05-08T07:54:31.470926000Z)
foundryup: - cast 1.7.1 (4072e48705 2026-05-08T07:54:31.470926000Z)
foundryup: - anvil 1.7.1 (4072e48705 2026-05-08T07:54:31.470926000Z)
foundryup: - chisel 1.7.1 (4072e48705 2026-05-08T07:54:31.470926000Z)
```

Real output, and note that it lists all four binaries under one heading, because switching versions
switches the set.<Cite src="measured-foundry-basics-1-7-1" /> What Foundry does *not* have — at least
not on the installation page as read on 2026-08-26 — is a per-project toolchain file, the way some
language ecosystems pin a runtime version in the repository.<Cite src="foundry-installation" /> The
honest advice is therefore: pin explicitly in CI, and write the version down in the README so a human
switching between two projects knows which toolchain each one expects.

One more habit that costs nothing: `foundryup` verifies downloaded binary hashes against GitHub
artifact attestations, and you can re-check an installed binary yourself with
`gh attestation verify --owner foundry-rs $(which forge)`.<Cite src="foundry-installation" /> Worth
knowing mainly because `foundryup --force` skips that verification, so it is not a flag to reach for
reflexively when an install misbehaves.<Cite src="foundry-installation" />

### Why the toolchain version is a behavioural pin, not a cosmetic one

Foundry's own v1.0 migration guide is the argument. Between the pre-1.0 line and v1.0: the optimizer
became **disabled** by default, `testFail`-prefixed tests stopped being supported, `vm.expectRevert`
stopped applying to internal calls by default, and conflicting remappings between root and
dependencies became an **error** rather than something forge resolved
silently.<Cite src="foundry-v1-migration" />

Read that list as a thought experiment. Every one of those changes alters the result of running an
unchanged repository. A pipeline that installs "latest" is a pipeline whose pass/fail behaviour
changes on a day you did not commit anything, and whose gas numbers change on a day you did not
commit anything. That is not a hypothetical risk; it is the documented history of this specific tool.

### The version question the web cannot answer

Try to establish Foundry's current stable version from search results and you will get a mess. One
widely repeated figure is a "v1.5.1" that the releases and tags pages do not corroborate; the other
is "1.8.0-nightly", dated 2026-08-04. Neither is the stable version of the toolchain on the machine
this module was written on, which is 1.7.1, built 2026-05-08.<Cite src="measured-foundry-basics-1-7-1" />

The site explains it, on a page most people never open. Foundry's CLI reference pages carry a note
that they are generated from a specific set of installed binaries, and the versions page shows which:
forge, cast, anvil and chisel at **1.8.0-nightly**, commit `fa8b5fc2`, built
2026-08-04.<Cite src="foundry-versions-reference" /> The page states its own purpose plainly: it
exists so a reader can tell documentation drift apart from a genuine behavioural difference between
one release and another.<Cite src="foundry-versions-reference" /> So the 1.8.0-nightly figure
circulating on the web is the version the *documentation* was generated from, not a release anybody
is running.

Meanwhile `getfoundry.sh/releases/stable/` — the URL you would go to for an authoritative stable
number — returns 404.<Cite src="measured-foundry-basics-1-7-1" /> There is no stable version table to
read.

The drift is not theoretical either. The published `forge remappings` reference documents a
`--profile <PROFILE>` option; forge 1.7.1 rejects it with `error: unexpected argument '--profile'
found`, and `forge remappings --help` on the installed binary does not list
it.<Cite src="forge-remappings-reference" /><Cite src="measured-foundry-basics-1-7-1" />

**So do not learn a version number. Learn the method.**

```console
$ forge --version          # what am I actually running
$ foundryup --list         # what else is installed on this machine
$ forge <cmd> --help       # what does this binary actually accept
```

Those three commands are authoritative for your machine and take a second. Every version claim in
this module — including the ones in this lesson — was produced that way, and any of them may be stale
by the time you read it.

## Making CI agree with you

The `foundry-rs/foundry-toolchain` action takes a `version` input, documented as being passed
straight to `foundryup --install <version>`, with a default of `"stable"` and `nightly` or a specific
version like `v1.3.6` as the alternatives.<Cite src="foundry-toolchain-action-yml" /><Cite src="foundry-toolchain-action" />

That default is the problem. Every official CI example — and the `.github/workflows/test.yml` that
`forge init` generates — uses `foundry-rs/foundry-toolchain@v1` with no `version:` line at
all.<Cite src="foundry-ci" /><Cite src="measured-foundry-basics-1-7-1" /> That is a moving target by
construction. Interestingly, the generated template does one thing right: it runs `forge --version`
as an explicit step, so at least the log records what you got.<Cite src="measured-foundry-basics-1-7-1" />

A pinned job says what it means:

```yaml
- uses: actions/checkout@v6
  with:
    submodules: recursive        # lib/ is submodules; without this, nothing compiles
- uses: foundry-rs/foundry-toolchain@v1
  with:
    version: "1.7.1"             # not "stable"
- run: forge --version           # record it in the log regardless
- run: FOUNDRY_PROFILE=ci forge test -vvv
```

Three habits are worth adopting alongside it.

**Record the triple in the repository.** The forge version, the solc pin and the `evm_version` belong
somewhere a human reads — the README, or a comment in `foundry.toml`. Two of the three are already in
`foundry.toml`; the third is not, and a year from now the only artifact that remembers it is a CI log
that has been rotated away.

**Pin actions by commit SHA, not by tag.** Tags are mutable. `@v1` is a name someone can repoint, and
[the CI supply chain](/c/action-supply-chain) is a module in this track for a reason. The Foundry action is no
different from any other in this respect.

**Make machine-readable results actually machine-readable.** When CI needs to parse test results
rather than print them, [`--junit` is the reliable path](/c/junit-machine-output): `forge test --json` still writes non-JSON
diagnostics to stdout alongside the JSON, an issue that remains
open.<Cite src="foundry-issue-3001" /><Cite src="forge-test-reference" /> And a constraint that
shapes the job layout — `--junit` **cannot** be combined with `--gas-report`:

```console
$ forge test --junit --gas-report
error: the argument '--junit' cannot be used with '--gas-report'
```

Measured on 1.7.1.<Cite src="measured-foundry-basics-1-7-1" /> Structured results and a gas report are
two runs, not one. The CI module builds on this properly.

<Answer>
**Closed by `foundry.toml`.**

1. *Which compiler.* `auto_detect_solc` picks per file from a pragma range; two machines can
   legitimately resolve differently. Closed by `solc = "0.8.36"`.<Cite src="foundry-solc-config" />
2. *Which ruleset.* `evm_version` defaults to `osaka` on this toolchain, and the default is a property
   of the compiler, so it moves when the compiler moves. Closed by pinning it
   explicitly.<Cite src="measured-foundry-basics-1-7-1" /><Cite src="solidity-changelog" />
3. *Optimizer settings.* Including the side effect from the previous lesson — setting `optimizer_runs`
   in a profile turns the optimizer on — and `via_ir`, and `bytecode_hash`.

**Closed by configuration, but only if you are careful.**

4. *Which profile.* `FOUNDRY_PROFILE` is an environment variable, and selecting one that does not
   exist warns and continues.<Cite src="measured-foundry-basics-1-7-1" /> The file cannot force it;
   the pipeline has to set it and, ideally, assert it.
5. *Which files the imports resolved to.* Four merging sources, one of them the environment. A
   `foundry.toml` closes it only if `auto_detect_remappings = false` and the full set is written down.
6. *Which dependency revisions.* `foundry.lock` and `.gitmodules` pin these — and a clone without
   `--recurse-submodules` has no dependencies at all, which fails loudly rather than
   quietly.<Cite src="foundry-ci" />

**Not closable by `foundry.toml` at all.**

7. *Which forge.* The build tool's own version is nowhere in the project's configuration, and it
   changes defaults and cheatcode semantics between releases — the v1.0 migration list is the
   evidence.<Cite src="foundry-v1-migration" /> This one is closed in CI with an explicit `version:`
   input, and on a laptop with `foundryup --install` plus a documented version in the README.
8. *Environment variables.* Anything `FOUNDRY_*` or `DAPP_*` in a shell profile, a `.envrc` or a
   container image beats the file, and leaves no trace in the repository.<Cite src="foundry-config-overview" />
9. *Where you ran the command from.* The `foundry.toml` walk-up means a build launched from the wrong
   directory can use a different file or none.<Cite src="measured-foundry-basics-1-7-1" />

The honest summary: `foundry.toml` closes the compiler-shaped divergences. The toolchain version and
the environment are outside its reach, and they are the two that produce the most confusing bug
reports, because nothing in the repository records that they were ever different.
</Answer>
</Check>

## Where this pays off

Everything downstream of this module assumes the three pins are in place, and quietly breaks when
they are not.

**Gas profiling** compares numbers across time. A number produced by a different compiler, a
different ruleset or a different forge is not comparable to yesterday's, and a snapshot check that
fires on an unpinned toolchain is a flaky gate rather than a signal.

**Deploy and verify** is [bytecode matching](/c/verification-is-bytecode-matching). An explorer reproduces your deployment by recompiling
your source with the settings you declare; the compiler version, the EVM version, the optimizer
configuration and the remapping set have to match exactly, which is precisely the list the artifact
records and this module taught you to control.

**Security work** inherits [the whole compiler as part of its trust boundary](/c/compiler-is-part-of-tcb). A finding is about a
specific build of specific bytecode. "Which compiler produced the thing we audited" is a question
with an answer only if somebody pinned it.

The module's own closing exercise is question 7 above, applied to a repository you actually own. Run
`forge config` and `forge remappings` in it, list which of the nine mechanisms are closed, and find
out how many of the open ones you knew about.
