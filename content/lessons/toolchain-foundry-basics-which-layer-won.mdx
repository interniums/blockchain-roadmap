A colleague reports that `forge test` passes on their machine. It fails on yours. Same commit, same
branch, no uncommitted changes on either side. Before you read a line of Solidity, there are five
places a value could have come from, and only one command that tells you which value you actually
got.

```console
$ forge config
```

This lesson is about reading that output correctly — including the one thing it deliberately does not
tell you.

## Finding the file at all

`foundry.toml` is the project's configuration file, and forge locates it by walking **up** from the
current working directory until it finds one or reaches the filesystem
root.<Cite src="foundry-config-overview" /> The global `~/.foundry/foundry.toml` is also consulted,
and `FOUNDRY_CONFIG` replaces the search with a path you name.<Cite src="foundry-config-overview" />

The walk-up is easy to state and easy to forget. With `optimizer_runs = 333` in a project's
`foundry.toml`:

```console
$ cd project        && forge config | grep optimizer_runs
optimizer_runs = 333
$ cd project/src/a/b/c && forge config | grep optimizer_runs
optimizer_runs = 333
$ cd ..             && forge config | grep optimizer_runs   # one level above the project
optimizer_runs = 200
```

Three directories deep still finds it; one directory above the project root gets the built-in default
of 200 instead.<Cite src="measured-foundry-basics-1-7-1" /> Nothing errors. You just silently get a
different build. The scenario where this actually happens is a monorepo: run `forge build` from the
repository root when the Foundry project lives two directories down, and you have compiled with
whatever the root `foundry.toml` says, or with nothing at all.

There is a second file most people never create and some people inherit: `~/.foundry/foundry.toml`,
a global configuration consulted alongside the project's.<Cite src="foundry-config-overview" /> It is
a reasonable place for machine-specific things — a keystore path, an RPC alias — and an unreasonable
place for anything that affects bytecode, because it applies to every project you touch and appears
in none of them. If you are diagnosing a difference between two developers' builds, this file is
worth checking early precisely because neither developer will think to mention it. On the authoring
machine it does not exist, which is the normal state.<Cite src="measured-foundry-basics-1-7-1" />

`FOUNDRY_CONFIG` overrides the search outright:

```console
$ FOUNDRY_CONFIG=/elsewhere/other.toml forge config | grep optimizer_runs
optimizer_runs = 12345
```

Measured, and worth knowing precisely because it is invisible in the repository: a value set nowhere
in your project can be the value in force.<Cite src="measured-foundry-basics-1-7-1" />

## The waterfall, measured end to end

The documentation gives the precedence in three steps: default values, then `foundry.toml` (or the
file named by `FOUNDRY_CONFIG`), then environment variables prefixed `FOUNDRY_` or
`DAPP_`.<Cite src="foundry-config-overview" /> That is correct and incomplete, because two more
layers sit inside the middle step: the `extends` key, and the selected profile.

Resolved on forge 1.7.1, lowest priority first:

1. **Built-in defaults.** `optimizer = false`, `optimizer_runs = 200`, `evm_version = "osaka"`,
   `via_ir = false`, `auto_detect_solc = true`, `auto_detect_remappings = true`, `isolate = false`,
   `[fuzz] runs = 256`, `[invariant] runs = 256, depth = 500`.<Cite src="measured-foundry-basics-1-7-1" />
2. **The base file named by `extends`**, if the profile being resolved declares one.<Cite src="foundry-project-config-reference" />
3. **`[profile.default]`** in the discovered `foundry.toml`.
4. **`[profile.<selected>]`** in the same file, selected by `FOUNDRY_PROFILE`.<Cite src="foundry-config-overview" />
5. **`FOUNDRY_*` / `DAPP_*` environment variables.**<Cite src="foundry-config-overview" />

Each of the four non-default steps was checked directly. A profile-selected value beats the file's
default block; an environment variable beats the profile, in both the default and the `ci` profile;
and `DAPP_OPTIMIZER_RUNS` works exactly like its `FOUNDRY_` twin.<Cite src="measured-foundry-basics-1-7-1" />

### The exceptions worth knowing

A handful of variables are documented as exceptions to the ordinary override rule — among them
`FOUNDRY_PROFILE`, `FOUNDRY_FFI`, `FOUNDRY_REMAPPINGS`, `FOUNDRY_LIBRARIES` and
`FOUNDRY_FS_PERMISSIONS`, each with a `DAPP_` counterpart.<Cite src="foundry-config-overview" /> Two
of those you have already met the consequences of. `FOUNDRY_PROFILE` does not override a key at all —
it selects which table gets read. And `FOUNDRY_REMAPPINGS` **appends** to the remapping set rather
than replacing it, which is why the previous lesson counted four merging sources rather than one
winner.<Cite src="measured-foundry-basics-1-7-1" />

The pattern: anything that is a *set* merges; anything that is a *scalar* overrides. Keep that
distinction and the exception list stops looking arbitrary.

## Profiles inherit, and the inheritance is total

Every key in `foundry.toml` lives under a profile table. `[profile.default]` is the base, every other
profile inherits from it, and the active one is chosen with
`FOUNDRY_PROFILE`.<Cite src="foundry-config-overview" /><Cite src="foundry-profiles-docs" />

```toml
[profile.default]
src = "src"
out = "out"
libs = ["lib"]
optimizer = true
optimizer_runs = 200

[profile.ci]
optimizer_runs = 1000000
fuzz = { runs = 10000 }
verbosity = 3
```

```console
$ forge config | grep -E '^(src|optimizer|optimizer_runs|verbosity) '
src = "src"
optimizer = true
optimizer_runs = 200
verbosity = 0

$ FOUNDRY_PROFILE=ci forge config | grep -E '^(src|optimizer|optimizer_runs|verbosity) '
src = "src"
optimizer = true
optimizer_runs = 1000000
verbosity = 3
```

`[profile.ci]` never mentions `src`, `out`, `libs` or `optimizer`, and gets all four from
`default`.<Cite src="measured-foundry-basics-1-7-1" /> That is the feature: a CI profile is a diff,
not a copy. It is also the hazard, because a change to `[profile.default]` six months from now
silently changes CI too, and nothing in the `[profile.ci]` block records that it depended on the
value you just edited.

<Misconception
  belief="A profile is a self-contained configuration block — what you see in [profile.ci] is what CI runs with."
  reality="Non-default profiles inherit every key of [profile.default] that they do not restate. Reading [profile.ci] alone tells you the deltas, not the configuration."
  why="TOML tables look visually independent — a heading, a blank line, another heading. Nothing in the syntax suggests one reads the other."
  src="foundry-config-overview"
/>

<Aside kind="warn">
Select a profile that does not exist and forge tells you, then carries on:

```console
$ FOUNDRY_PROFILE=nope forge config | grep optimizer_runs
Warning: Selected profile `nope` does not exist; falling back to the default profile.
optimizer_runs = 4242
```

A warning, not an error, and a zero exit.<Cite src="measured-foundry-basics-1-7-1" /> In CI that
warning scrolls past in the log and the job goes green having run the wrong profile. If your pipeline
depends on a profile, assert it — echo the value you expect to differ and check it, rather than
trusting that the variable was spelled correctly three files away.
</Aside>

## The side effect that changes your bytecode

Look again at that `[profile.ci]` block. It never says `optimizer = true`. Now put the optimizer on
its default footing and re-run:

```console
$ forge config | grep -E '^(optimizer|optimizer_runs) '
optimizer = false
optimizer_runs = 200

$ FOUNDRY_PROFILE=ci forge config | grep -E '^(optimizer|optimizer_runs) '
optimizer = true
optimizer_runs = 1000000
```

Setting `optimizer_runs` turned the optimizer **on**, in a profile that never asked for
it.<Cite src="measured-foundry-basics-1-7-1" /> That is not a cosmetic difference. The same
`Counter.sol` compiled under both profiles:

Both measured on this machine, same source, same compiler, same
commit.<Cite src="measured-foundry-basics-1-7-1" /> Two conclusions follow, and both are load-bearing
for the rest of this track.

**A gas number is only comparable to another gas number from the same profile.** The
[gas report](/c/gas-report) module builds a whole practice on this; the seed of it is here. If your local `forge test --gas-report`
and your CI gas snapshot disagree by a few hundred gas on every function, check `FOUNDRY_PROFILE`
before you check your code.<Cite src="foundry-gas-tracking" />

**The artifact in `out/` is profile-shaped.** You already saw that the artifact records
`settings.optimizer` and `settings.evmVersion` alongside the bytecode. Those settings are the
resolved ones for whichever profile built it, which is why a contract
[verified from a locally built artifact](/c/verification-is-bytecode-matching) can fail to match a
chain deployment produced by a CI build.

## What profiles are actually for

The documented patterns are three, and they map onto three different jobs.<Cite src="foundry-profiles-docs" />

**`default` is the inner loop.** Optimizer off, low fuzz budget, low verbosity. Everything you run
fifty times an hour. On the generated project, the default 256 fuzz runs finish in 5.79 ms; the same
suite at 10,000 runs takes 30.17 ms.<Cite src="measured-foundry-basics-1-7-1" /><Cite src="foundry-testing-config" />
Those numbers are trivially small on a toy contract and are not trivially small on a real one, which
is the entire reason the split exists.

**[`ci` is the gate](/c/ci-profile).** Raised fuzz and invariant budgets, higher verbosity so a
failure is diagnosable from the log alone, and the compiler settings you actually ship. The official CI guidance pairs
`FOUNDRY_PROFILE: ci` with a profile like `fuzz = { runs = 10000 }` and
`invariant = { runs = 1000 }`, alongside `forge fmt --check` and `forge lint --deny warnings` as
cheap gates that run first.<Cite src="foundry-ci" />

**`production` is the build you ship.** Maximum optimizer runs, `via_ir` on if you use it,
`bytecode_hash = "none"` if you want deterministic bytecode across machines.<Cite src="foundry-profiles-docs" />
This is a separate profile from `ci` on purpose: what you gate on and what you deploy are allowed to
differ, and pretending otherwise means either a slow gate or an unverified deployment.

The allocation rule that makes the split maintainable: **anything that makes a local run painful
belongs in `ci`; anything CI must not be able to skip belongs in `default`.** A lint rule that catches
a real bug belongs in `default`, because if it only runs in CI you find out twenty minutes later. A
ten-thousand-run invariant campaign belongs in `ci`, because nobody will wait for it.

Two smaller habits are worth adopting at the same time. **Name profiles after the job, not the
speed.** `ci` and `production` tell a reader when the block applies; `fast` and `slow` tell them
nothing about who selects it. And **keep the number of profiles small.** Each one is a distinct set
of compiler settings, which means a distinct set of artifacts, a distinct set of gas numbers and a
distinct answer to "is this the bytecode we deployed". Three profiles is a design. Seven is a
configuration surface nobody can hold in their head, and the one you will forget is the one CI is
actually running.

<Aside kind="note">
Foundry also supports per-test configuration through a `forge-config` NatSpec comment above a test
function.<Cite src="foundry-inline-test-config" /> Those comments name the profile they apply
to — `/// forge-config: default.fuzz.runs = 10000` sets a value for the `default` profile and does
nothing at all when CI runs with `FOUNDRY_PROFILE=ci`. The unit-testing module takes this apart. Note
now only that inline configuration is a fourth thing profiles interact with, and the one most likely
to be silently inert.
</Aside>

## `extends`, and the trap inside it

Newer than the profile mechanism, and increasingly common in monorepos: a profile can inherit from a
whole other TOML file.<Cite src="foundry-project-config-reference" />

```toml
# base.toml, shared across packages
[profile.default]
via_ir = true
bytecode_hash = "none"
optimizer_runs = 777
```

```toml
# packages/token/foundry.toml
[profile.default]
extends = "../../base.toml"
src = "src"
evm_version = "osaka"

[profile.ci]
optimizer_runs = 1000000
```

Under the default profile this works exactly as you would hope: `via_ir` and `bytecode_hash` come
from the base, `evm_version` stays `osaka` because the local file wins over the base, and `src` is
local.<Cite src="measured-foundry-basics-1-7-1" />

Now select `ci`:

```console
$ FOUNDRY_PROFILE=ci forge config | grep -E '^(via_ir|bytecode_hash|optimizer_runs) '
optimizer_runs = 1000000
via_ir = false
bytecode_hash = "ipfs"
```

`via_ir` collapsed to the built-in `false` and `bytecode_hash` to the built-in
`ipfs`.<Cite src="measured-foundry-basics-1-7-1" /> **`extends` is per-profile.** A profile that does
not declare it does not inherit the base — and adding `[profile.ci]` to the *base* file does not help
either; that was checked and changes nothing.<Cite src="measured-foundry-basics-1-7-1" /> The fix is
to repeat the key:

```toml
[profile.ci]
extends = "../../base.toml"
optimizer_runs = 1000000
```

With that line, `ci` gets `via_ir = true` and `bytecode_hash = "none"` from the base, plus `src` and
`evm_version` from the local `[profile.default]`.<Cite src="measured-foundry-basics-1-7-1" /> Note
what the failure looks like without it: a monorepo where the shared build settings apply to every
developer's machine and to none of the CI jobs. Nothing errors. The artifacts just differ.

## What `forge config` will not tell you

One limitation, and it is the reason this lesson is a procedure rather than a fact. `forge config`
prints the **resolved** configuration. It does not annotate any line with where the value came from.
There is no `--explain`, no provenance column, no indication that `optimizer_runs = 1000000` arrived
from a profile rather than the default block.

So the technique is differencing, and it is worth doing deliberately rather than by squinting.

**Subgoal — establish the baseline you believe in.** Capture the configuration you think the project
has, from the project root, with a clean environment:

```console
$ env -i PATH="$PATH" HOME="$HOME" forge config > /tmp/clean
```

Stripping the environment is the point. Anything that differs between this and a plain `forge config`
came from your shell, not from the repository.

**Subgoal — attribute the profile.** Capture the same thing under the profile CI uses and diff:

```console
$ FOUNDRY_PROFILE=ci forge config > /tmp/ci
$ diff /tmp/clean /tmp/ci
```

Every changed line is a line `[profile.ci]` is responsible for, directly or through a side effect
like `optimizer_runs` enabling the optimizer. Lines that do not appear in the diff are inherited, and
inherited lines are the ones that will change under you later.

**Subgoal — attribute the environment.** Diff a plain run against the clean one. If they differ,
something outside the repository is configuring your builds, and `env | grep -iE 'foundry|dapp'`
names it.

**Subgoal — attribute the file.** If a value still has no explanation, check that you are reading the
`foundry.toml` forge found. `FOUNDRY_CONFIG` and the walk-up both make that a real question, and a
monorepo makes it a likely one.

Four diffs, and the layer is located by bisection rather than by reading.

One genuinely helpful behaviour to know about, because most configuration systems do not have it: a
misspelled key is reported.

```console
$ forge config | head -1
Warning: Found unknown `optimiser_runs` config for profile `default` defined in foundry.toml.
```

That is forge telling you the British spelling did nothing.<Cite src="measured-foundry-basics-1-7-1" />
It is still a warning rather than an error, so it will scroll past in CI, but it is there.

<Answer>
**Locally:** `optimizer_runs = 200`, `optimizer = true`, `evm_version = "cancun"`, fuzz `runs = 256`.
The default profile applies; the fuzz budget is the built-in default because `[profile.default]`
does not set one.<Cite src="measured-foundry-basics-1-7-1" />

**In CI:** `optimizer_runs = 500`, `optimizer = true`, `evm_version = "cancun"`, fuzz `runs = 10000`.

The one to get right is `optimizer_runs`. The `ci` profile asks for 1,000,000 and does not get it: an

total, not selective.

## Where this pays off

Two commands now cover the whole configuration surface: `forge remappings` for which files, and
`forge config` for which settings. Both print resolved answers, neither prints provenance, and
differencing is how you recover the provenance in both cases.

That leaves one question this module opened with and has not yet answered: the settings are resolved,
but resolved *by what*. Which compiler binary ran, which hardfork ruleset it targeted, and which
build of forge did the resolving — three more version numbers, each capable of changing your bytecode
on its own, and none of them determined by anything you have looked at so far.
