```text
[PASS] testFuzz_FeeAndNetAreConserved(uint256) (runs: 256, μ: 9810, ~: 9394)
```

Three numbers. In my experience roughly one engineer in five reads all three correctly the first
time, and the two that get misread are misread in opposite directions — one is treated as far
stronger evidence than it is, and the other two are treated as evidence at all when they are not.

This lesson takes the line apart, and then shows the mechanism that makes the first number mean far
more than the arithmetic suggests — and that can be switched off without you noticing.

## `runs: 256`

`[fuzz] runs` defaults to 256. You can confirm it on your own machine rather than taking it from a
page: `forge config` prints the resolved configuration, and on forge 1.7.1 the `[fuzz]` table opens
with `runs = 256`.<Cite src="foundry-testing-config" /><Cite src="measured-forge-1-7-1" />

Now do the naive arithmetic, because everyone does it and it is worth having the correct reaction to
the answer. A `uint256` parameter has 2^256 possible values. Two hundred and fifty-six samples over
2^256 points covers a fraction of the domain so small there is no useful way to write it. If draws
were independent and uniform, a bug occupying a fraction `p` of the input space would be missed with
probability `(1 - p)^256`:

That table is a model, not a measurement — it assumes independent uniform draws, and the rest of this
lesson is about why that assumption is wrong in a way that matters enormously. But the shape of it
holds: **a passing fuzz test is a statement about your search, not about your
contract.**<Cite src="foundry-testing-config" />

### What raising `runs` buys, and what it costs

The cost is linear: a hundred times the runs is roughly a hundred times the execution. What you get
for it is best stated in terms of *rarity* rather than confidence. Under the same uniform model, the
miss probability is about `e^(-pN)`, so the smallest region you can reliably reach shrinks in
proportion to the run count: ten times the runs finds bugs ten times rarer, and no rarer than that.

Put concretely, for a bug occupying 1 in 1,000 of the input domain, 256 runs miss it about 77% of the
time and 2,560 runs miss it about 7.7% of the time. To get the same 7.7% against a bug occupying 1 in
a million, you need 2.56 million runs. Rarity spans many orders of magnitude and your CI budget spans
about two, which is why raising `runs` is a real but narrow instrument: it moves the threshold, it
does not remove it.

The practical shape that falls out: a low `runs` for the inner loop, a raised `runs` for the gate,
which is what [profiles](/c/profile-use-cases) are for, and a much larger unattended campaign
somewhere that nobody waits on. The fifth lesson in this module covers the per-test override that
lets one expensive property run long without slowing the other three hundred.

## `μ` and `~`

These are gas statistics, and they carry no correctness information at all. `μ` is the mean gas
across the runs and `~` is the median.<Cite src="foundry-forge-testing" />

You do not have to take that on faith either. `forge test --json` emits the same result structurally,
and on forge 1.7.1 the fuzz result object contains the fields under their full
names:<Cite src="forge-test-reference" /><Cite src="measured-fuzz-probe-1-7-1" />

```json
"kind": { "Fuzz": { "first_case": { "gas": 21702, "stipend": 21204 },
                    "runs": 1000, "mean_gas": 570, "median_gas": 498 } }
```

### The one thing they are genuinely good for

The *gap* between them is a free distribution signal, and it is worth training yourself to glance at.
Mean and median diverge when a minority of runs take a very different execution path from the
majority.

Here is a test that does nothing but exercise that. It writes a storage slot only when the fuzzed
value is small:

```solidity
function testFuzz_SmallShare(uint256 x) public {
    if (x < 1e6) counter += 1;
    assertLt(counter, 20);
}
```

On forge 1.7.1 it reports `runs: 256, μ: 11356, ~: 2629`.<Cite src="measured-fuzz-probe-1-7-1" /> The
median run costs about 2,600 gas — it took the cheap branch. The mean is more than four times that,
because a handful of runs paid for an `SSTORE` and dragged the average up. You have learned, from one
line of output and no instrumentation, that a branch in your function is being reached by a minority
of inputs.

Read it in both directions:

- **Mean far above median** — an expensive path exists and is rarely taken. Either the fuzzer is
  barely reaching an important branch, or an input class is doing something you did not expect.
- **Mean and median nearly equal** — every run took essentially the same path. For a function with
  real branching, that is a warning that your constraints have collapsed the domain onto one branch.
  Lesson four is about how easily that happens.

## The fuzzer does not sample uniformly

This is the part that changes how you think about the first number, and it is the reason the 1-in-2^256
arithmetic above is a floor rather than an estimate.

Foundry mixes a **dictionary** of interesting values into the input stream. On forge 1.7.1 the
defaults are `dictionary_weight = 40`, `include_storage = true` and
`include_push_bytes = true`.<Cite src="foundry-testing-config" /><Cite src="measured-forge-1-7-1" />
That last one is the interesting one: `PUSH` bytes are how the EVM gets constants into a program, so
scraping them recovers the literal values compiled into the contract under test. Storage scraping
does the analogous thing for values the contract is currently holding.

The effect is not subtle. Take a contract whose only bug is at one exact value:

```solidity
contract Magic {
    uint256 public constant THRESHOLD = 1234567890123456789;

    function classify(uint256 x) public pure returns (uint256) {
        if (x == THRESHOLD) return 0;   // the bug: one input out of 2^256 returns nonsense
        return 1;
    }
}

function testFuzz_AlwaysOne(uint256 x) public view {
    assertEq(m.classify(x), 1);
}
```

**Subgoal 1 — establish the uniform-sampling baseline.** One value out of 2^256 triggers the bug. A
uniform sampler finds it after about 2^255 draws, which is to say never, in this universe, at any
budget you or anyone else will ever be granted.

**Subgoal 2 — run it as shipped and record how long it took.** On forge 1.7.1 with solc 0.8.36 it
fails on run 61:<Cite src="measured-fuzz-probe-1-7-1" />

```text
[FAIL: assertion failed: 0 != 1; counterexample:
  calldata=0x37cf121b000000000000000000000000000000000000000000000000112210f47de98115
  args=[1234567890123456789 [1.234e18]]] testFuzz_AlwaysOne(uint256) (runs: 61, μ: 6429, ~: 6429)
```

Sixty-one runs, against a uniform-sampling expectation of 2^255. The constant is in the deployed
bytecode as a `PUSH` operand; the fuzzer read it out and tried it.

**Subgoal 3 — remove the mechanism and confirm it was the mechanism.** Run the identical contract and
the identical test with the dictionary disabled — `dictionary_weight = 0`, `include_push_bytes` and
`include_storage` both false:

```text
[PASS] testFuzz_AlwaysOne(uint256) (runs: 256, μ: 6429, ~: 6429)
```

Same bug, same test, same seed budget. Green.<Cite src="measured-fuzz-probe-1-7-1" /> The dictionary
was doing all of the work, and none of it was visible in the passing output.

**Subgoal 4 — name the general consequence.** The fuzzer is far better than random at finding values
your code already mentions, and no better than random at finding values it does not. Which produces
the failure mode that catches people:

<Aside kind="warn">
The uncomfortable corollary: **refactoring can silently stop a bug from being found.** Move a
threshold out of the contract and behind an interface, replace a literal with a value computed at
runtime, or delete a now-unused constant, and the value leaves the bytecode the fuzzer is scraping.
The contract's behaviour at that value is unchanged. Your fuzz test's odds of ever trying it collapse
back to the uniform baseline, and the test goes on printing `runs: 256` and PASS.

The defence is not to preserve constants for the fuzzer's benefit. It is to stop relying on the
dictionary for values you already know matter — which is what fixtures are for, in lesson four.
</Aside>

## The rest of the `[fuzz]` table, briefly

Worth knowing exists, because two of these will come up in the next three lessons. On forge 1.7.1
`forge config` resolves `[fuzz]` to, among
others:<Cite src="foundry-testing-config" /><Cite src="measured-forge-1-7-1" />

| key | default | what it governs |
|---|---|---|
| `runs` | 256 | samples per fuzz test |
| `max_test_rejects` | 65536 | how many `vm.assume` rejections before the test fails — lesson three |
| `dictionary_weight` | 40 | how heavily dictionary values are favoured over raw random |
| `include_storage` | true | scrape values out of contract storage into the dictionary |
| `include_push_bytes` | true | scrape constants out of contract bytecode into the dictionary |
| `failure_persist_dir` | `cache/fuzz` | where a counterexample is written — lesson five |
| `show_logs` | false | whether `console.log` from fuzz runs is displayed |
| `seed` | unset | pin it and the campaign becomes reproducible — lesson five |

Two more are worth a sentence because they change what "runs" means. `corpus_dir` and
`show_edge_coverage` turn on a coverage-guided workflow, where inputs that reached new code are kept
and mutated rather than discarded, and `forge fuzz cmin` and `forge fuzz tmin` minimise the corpus
that results.<Cite src="foundry-fuzz-corpus-guide" /> That is a different and more powerful search
than the one this module describes, and it is off by default; the numbers above are all for the
default configuration.

A colleague reports that a fuzz test caught a real bug on their machine last week, and that on the
CI runner the same test on the same commit has been green for six days. They suspect a Foundry
version difference.

Before you go looking at versions, name three explanations that are more likely, and say what single
piece of output you would ask them for to distinguish them.

<Answer>
**Ask for the last line of the failing local run.** Forge prints
`Fuzz seed: 0x… (use --fuzz-seed to reproduce)` at the end of a run, and that one line separates most
of the candidate explanations from each other.<Cite src="measured-fuzz-probe-1-7-1" />

**Explanation one — different seed, same everything else.** Without a pinned `[fuzz] seed`, every run
draws a fresh sequence. The bug occupies some small share of the input space, the local run happened
to hit it, and six CI runs at 256 runs each did not. This is by far the most likely answer and it is
not a CI problem at all; it is the miss-probability table at the top of this lesson doing exactly
what it says. Lesson five is about how to live with it.

**Explanation two — different `runs`.** If CI runs under a different profile, `[fuzz] runs` may be
lower there, not higher. Profiles inherit from `[profile.default]` and people usually remember to
raise CI budgets in the profile and forget when the value came from somewhere
else.<Cite src="foundry-testing-config" /> `forge config` under the CI profile settles it in one
command.

**Explanation three — the dictionary lost the value.** If the branch guard was recently moved into a
constructor argument, an immutable set from config, or a separate contract, the constant may no
longer be scraped into the dictionary for that test, and the discovery rate falls from "61 runs" to
"never".<Cite src="measured-fuzz-probe-1-7-1" /> This one is invisible in a diff review because the
change is a refactor with no behavioural difference.

**Why the version hypothesis is last.** It is testable in one second with `forge --version` on both
machines, so check it, but a version difference that changes fuzzing outcomes would also change them
locally, and the local machine is the one finding the bug.

**What to actually do.** Take the counterexample from the local failure — forge persists it to
`cache/fuzz` and prints it — and promote it to a named unit test. That converts a probabilistic
finding into a deterministic one, which is the subject of lesson five, and it makes the entire
question moot.
</Answer>
</Check>

## What to carry forward

The first number is a search budget, not a proof. The other two are gas, and their *difference* is
the only signal in them. And the search itself is far better than uniform at values your code
mentions and no better than uniform at values it does not — which means the fuzzer's effectiveness
depends on properties of your source that no one is watching.

## Where this pays off

**The next lesson** is about the other thing that determines what the fuzzer actually tries: your
constraints. You have just seen that 256 runs can amount to 61 useful draws or to none, depending on
a setting you did not set. Lesson three shows the same variance arising from a single line you *did*
write, and measures it.

**When you tune a suite.** The temptation on a slow suite is to lower `runs` uniformly. The better
move is almost always to raise it on the two or three properties that guard real money and lower it
everywhere else, which needs the per-test override in lesson five.

**When you read a gas report.** `gas_report_samples` also defaults to 256, and the μ figure you have
just learned to ignore for correctness is the one you will use for gas
work.<Cite src="foundry-testing-config" /> The gas-profiling module builds directly on this line.
