Here is a contract small enough to hold in your head, and the report Foundry printed for it.

```solidity
contract Ledger {
    mapping(address => uint256) public balanceOf;
    uint256 public total;

    event Credited(address indexed to, uint256 amount);

    function credit(address to, uint256 amount) external {
        balanceOf[to] += amount;
        total += amount;
        emit Credited(to, amount);
    }
    ...
}
```

Four tests exercise it, plus a `setUp` that deploys it and credits one holder. Then:

```bash
forge test --gas-report
```

## What the columns are

Each contract gets a header row and a body. The header carries **deployment cost** and **deployed
size**; the body carries one row per function with **min, avg, median, max** and **number of
calls**.<Cite src="foundry-gas-tracking" /> That shape is the whole documented contract of the feature, and the rest of this
lesson is about what it does *not* say.

Deployment cost, 312,681,<Cite src="measured-gas-profiling-1-7-1" /> is what it costs to put this contract on a chain — the intrinsic
charge, the initcode, and the per-byte charge for the runtime code the constructor returns.
Deployment size, 1,232 bytes, is the runtime code length, which is the number that has to stay under
the deployed-code limit. It is also the number that moves when you change compiler settings, which
the last lesson in this module makes concrete.

Those two header figures are worth separating in your head, because they move together but mean
different things. Deployment cost is paid once, by whoever deploys, and is dominated by the per-byte
charge for the code being written to state. Deployed size is a hard ceiling: cross it and the
deployment reverts rather than costing more. A contract can be comfortably affordable to deploy and
still be one feature away from being undeployable, and only the size column tells you that.

The per-function columns are the ones people act on. And that is where the accounting gets
interesting.

## Trap one: `--gas-report` changes the numbers

Run the same suite twice, once with the flag and once without, and read the per-test figures `forge
test` prints on the left-hand side:

```
$ forge test --match-path test/Ledger.t.sol
[PASS] test_creditExistingHolder() (gas: 20540)
[PASS] test_creditManyExisting()   (gas: 37708)
[PASS] test_debit()                (gas: 18678)

$ forge test --match-path test/Ledger.t.sol --gas-report
[PASS] test_creditExistingHolder() (gas: 41908)
[PASS] test_creditManyExisting()   (gas: 182948)
[PASS] test_debit()                (gas: 40046)
```

The same test, the same commit, the same machine, twice the gas. `test_creditManyExisting` — a loop
of five calls — reports 37,708 plain and 182,948 under the flag.<Cite src="measured-gas-profiling-1-7-1" />

The explanation is one line, and it resolves a documentation ambiguity that has cost people
afternoons. `forge test --isolate` on the same suite prints **exactly** the `--gas-report` numbers,
digit for digit.<Cite src="measured-gas-profiling-1-7-1" /> On forge 1.7.1, asking for a gas report turns on isolation: every top-level
external call the test makes is metered as its own transaction rather than as one frame inside a
long-running test. `forge config` still reports `isolate = false`, because it is describing the
configured default, not what this particular invocation does.<Cite src="measured-gas-profiling-1-7-1" /><Cite src="foundry-config-overview" />

You already know what changes when a call becomes a transaction: it pays the intrinsic charge, and
its access list starts empty, so [cold and warm accounting](/c/cold-vs-warm-access) restarts. Both
effects push the figure up. The next lesson but two takes that apart with the arithmetic; here the
consequence is procedural.

<Aside kind="warn">
The `(gas: N)` figure beside a test name and the number in the gas-report table are not the same
measurement, and neither is the number `forge snapshot` writes to `.gas-snapshot`. On this suite
`test_debit` reads 18,678 plain, 40,046 under `--gas-report`, and 18,678 in the snapshot file.<Cite src="measured-gas-profiling-1-7-1" />
Before you compare a gas number with anyone — including yourself last month — say which of the three
it is and which flags were set.
</Aside>

## Trap two: the report describes your test suite

Look again at `credit`: min 34,112, median 34,112, max 68,312, avg 48,580, over **13 calls**.<Cite src="measured-gas-profiling-1-7-1" />

Where do thirteen calls come from, in a file with four tests?

**Subgoal — account for every call, because the statistics are computed over exactly this set.**
[`setUp` runs before each test](/c/setup-runs-per-test), not once per contract, and this `setUp`
credits one holder. Five tests, so five `credit` calls from `setUp` alone. The tests then contribute
one, one, five (a loop), and one. Five plus eight is thirteen.

So **five of the thirteen samples are fixture code**. They are the expensive ones — each writes a
holder's balance from zero to non-zero, the tier that costs 20,000 rather than 2,900<Cite src="measured-forge-1-7-1" /> — which
is why the maximum is 68,312 while both the minimum and the median sit at 34,112. The mean is
dragged to 48,580 by calls that no user of this contract will ever make.

<Misconception
  belief="The avg column in the gas report is roughly what a user will pay for that function."
  reality="It is the arithmetic mean over the calls your own suite made, fixture code included. On this suite five of thirteen credit samples came from setUp, and they are the expensive ones; the mean sits 14,468 gas above the median as a result."
  why="The column is labelled avg, which sounds like a property of the function rather than of the sample."
  src="measured-gas-profiling-1-7-1" />

The practical reading order is therefore: **median first, then the min/max spread, then the call
count, and the mean last if at all.** The median tells you what the typical sampled call cost. The
spread tells you the shape — here a 2× range, which is the signature of a
first-write-versus-later-write split rather than of a branch. The call count tells you how much to
trust any of it. A row with `# Calls` of 1 has no distribution at all: min, avg, median and max are
the same number four times, which is what the `debit` row is showing you.

<Aside kind="note">
This is not a defect to be worked around. It is what "aggregate over observed calls" means, and it
is the only thing the tool could compute — Foundry has no way to know your production call mix. The
error is entirely in the reading. The one repair worth making is to keep a small, deliberate gas
suite whose call distribution you *chose*, and to read the report for that suite rather than for the
functional suite. The next lesson builds that suite.
</Aside>

## Trap three: the table is full of contracts you do not ship

On forge 1.7.1 the resolved defaults are `gas_reports = ["*"]` and `gas_reports_ignore = []`.<Cite src="measured-gas-profiling-1-7-1" />
Everything that compiled gets a row: your contracts, your mocks, forge-std's helpers, the test
contracts themselves. On a real repository that is dozens of tables, and the three you care about
are somewhere in the middle.

Two keys in `foundry.toml` fix it:<Cite src="foundry-gas-tracking" />

```toml
[profile.default]
gas_reports = ["Ledger", "Token"]
gas_reports_ignore = ["Test", "Script"]
```

`gas_reports` restricts the report to the named contracts; `gas_reports_ignore` removes named ones
from whatever survives. Since both are opt-in, a repository that has never set them is producing a
report nobody reads, which is functionally the same as not having one.

Because these live under a profile, they inherit like everything else in
[`foundry.toml`](/c/foundry-toml): a `[profile.ci]` block that does not restate `gas_reports` gets
whatever `[profile.default]` says.<Cite src="foundry-config-overview" /> That is usually what you want. It is worth knowing when
CI's table looks different from yours and the diff is in a file neither of you edited.

<Check type="explain" concept="gas-report-is-test-shaped">
A colleague opens a pull request that adds one test:

```solidity
function test_creditZeroAmount() public {
    l.credit(alice, 0);
}
```

No production code changes. They report that `credit`'s avg in the gas report dropped by about 3,400
gas and ask whether the change should be advertised in the release notes.

What actually happened, and what — if anything — should be said about it?

<Answer>
**What happened is arithmetic, not optimisation.** The new test adds two `credit` samples, not one:
`setUp` runs before it, contributing another fixture call, and the test itself contributes a cheap
one. The mean is recomputed over a larger and differently-shaped sample. The bytecode is
byte-for-byte identical; the deployment cost and deployed size rows will not have moved at all,
which is the tell.

**The median is the check.** Both the median and the minimum sit at 34,112 before the change. Adding
one cheap sample and one expensive one to a thirteen-sample set moves the median at most one
position in the sorted order — and here it does not move at all, because 34,112 is already the modal
value. A change that moved the mean while leaving the median, the min, the max, the deployment cost
and the deployed size all fixed is not a change to the contract.

**What to say.** Nothing in the release notes. Internally, this is the moment to notice that the avg
column is being read as a user-facing figure and to stop. If the team wants a number to track, it
should be the median of a fixed gas suite, or better, a named region measured with the snapshot
cheatcodes — both of which the next two lessons set up.

**The general rule.** Any gas movement that is not accompanied by a movement in deployment size is
either a change in the suite, a change in compiler settings, or a change in the state the call ran
against. Check those three before you believe you optimised anything.

</Answer>
</Check>

## Trap four: you cannot have the report and machine-readable results at once

The obvious next step is to feed the report to CI. On forge 1.7.1 that runs into a hard wall:

```
$ forge test --junit --gas-report
error: the argument '--junit' cannot be used with '--gas-report'
```

Not a warning, not a silent precedence rule — the argument parser rejects the combination.<Cite src="measured-gas-profiling-1-7-1" /> And
`--junit` is the output format you actually need, because `forge test --json` writes compiler
diagnostics and other non-JSON to stdout alongside the JSON, a defect that is long-standing and
still open.<Cite src="foundry-issue-3001" /><Cite src="forge-test-reference" />

So a pipeline that wants both structured test results and a gas report runs `forge test` twice: once
with `--junit` for results, once with `--gas-report` for gas. That is not a workaround to be
apologised for. The two runs measure different things anyway — remember that `--gas-report` changes
the accounting — and separating them makes the gas job's flags explicit instead of inherited. The CI
module wires this up properly; what matters here is that you find out now rather than from a red
build.

<Aside kind="stop">
Do not solve this by parsing the gas-report table. It is drawn with box characters for humans, its
column widths float with the data, and nothing promises it is stable across releases. `forge
snapshot` exists precisely so that there is a machine-readable artefact, and it is the subject of
the next lesson.
</Aside>

## When the table is too coarse

The report stops at the function boundary.<Cite src="foundry-gas-tracking" /> If `credit` costs 34,112 and you want to know which
of its three statements owns that, the table cannot tell you — every internal call has been folded
into the external one that contained it.

`forge test` carries three flags for going a level down, all documented in its own help on
1.7.1:<Cite src="measured-gas-profiling-1-7-1" /><Cite src="forge-test-reference" />

- `--decode-internal` identifies internal functions in traces, so a `-vvvv` trace stops being a flat
  list of external calls.
- `--flamegraph` renders a single test as a flame graph — which functions consume the most gas
  overall, sorted. It implies `--decode-internal`.
- `--flamechart` renders the same test as a flame *chart*: gas over time, in execution order, so you
  can see when each function is called rather than only how much it totals.

Both flame options are documented as operating on a single test, so pair them with `--match-test`.
The distinction between the two is worth keeping straight, because the names are one letter apart
and answer different questions: the graph answers "where did the gas go", the chart answers "in what
order".

One more configuration key belongs here. `fuzz.gas_report_samples` resolves to 256 on forge
1.7.1.<Cite src="measured-gas-profiling-1-7-1" /> A fuzz test does not contribute one call per run to the report without bound; it
contributes at most that many samples. So the `# Calls` column on a row fed by fuzzing is a sampling
artefact as well as a suite artefact, and the min and max on such a row are the extremes of whatever
the fuzzer happened to draw.

## What a gas report is actually good for

Three jobs, and it is very good at all of them:

**Finding the outlier.** Sort your attention by the max column. A function whose max is several
times its median has a branch or a first-write path that costs real money, and that is where a
design change pays.

**Watching deployed size.** The one row on the page that is a pure property of the artefact, with no
dependence on your tests, on state, or on flags: the deployed size. It is the number to watch when a
contract is creeping toward the code-size limit, and it is the number that proves a "gas
optimisation" changed the bytecode at all.

**Comparing two versions of the same thing under identical conditions.** Same suite, same flags,
same compiler, one change between them. Every caveat in this lesson is about *absolute* numbers; a
controlled difference is much better behaved, which is exactly why the next lesson is about turning
gas into a diff rather than into a figure.

## Where this goes

**Next**, `forge snapshot` turns these numbers into a committed text file, and the delta between two
of those files into something a reviewer can read next to the code change that caused it — with the
one flaw that fuzz tests make the file move on their own.

**After that**, the snapshot cheatcodes let you measure a *region* rather than a whole test, which
removes the fixture calls that skewed the mean above — and introduces a trap where the probe
measures nothing at all.

**And two lessons on**, the isolation behaviour discovered here gets its arithmetic: the [intrinsic
charge](/c/intrinsic-gas) and the calldata bytes that `--gas-report` puts into the number and plain
`forge test` leaves out, and why the residual bias still runs in one direction.
