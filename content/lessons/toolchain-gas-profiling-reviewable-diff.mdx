A gas report is a photograph. What review needs is a diff — a thing that appears in a pull request,
next to the change that caused it, in a form a reviewer can read in four seconds.

Foundry's answer is deliberately unambitious: a text file.

```
$ forge snapshot
$ cat .gas-snapshot
LedgerTest:test_creditExistingHolder() (gas: 20540)
LedgerTest:test_creditManyExisting() (gas: 37708)
LedgerTest:test_creditNewHolder() (gas: 37595)
LedgerTest:test_debit() (gas: 18678)
LedgerTest:test_snapshotRegion() (gas: 24086)
```

One line per test, sorted, committed to the repository.<Cite src="foundry-gas-tracking" /> No service, no bot, no database. When
gas moves, `git diff` shows it moving, and the reviewer reading your storage change is looking at
its price on the next screen.

Note the numbers. They are the plain `forge test` figures, not the `--gas-report` ones —
`test_debit` reads 18,678 here and 40,046 under `--gas-report`, because that flag switches on
isolation.<Cite src="measured-gas-profiling-1-7-1" /> The snapshot file and the gas report are two different measurements of the same
suite, and a repository can easily end up quoting both.

## Fuzz tests get a different line shape

Not every line is `(gas: N)`. A fuzzed test records a distribution:

```
FuzzyTest:testFuzz_credit(address,uint96) (runs: 256, μ: 55163, ~: 56096)
```

Runs, mean, median.<Cite src="foundry-gas-tracking" /><Cite src="measured-gas-profiling-1-7-1" /> That is more honest than a single number and considerably worse to
diff, for reasons this lesson gets to.

## What one line actually contains

The figure is the gas the **test function** consumed — not `setUp`. On this suite `setUp` deploys
the contract, which costs 312,681 on its own, and no snapshot line is anywhere near that.<Cite src="measured-gas-profiling-1-7-1" /> That
is the right boundary, and it is also why the line is not the cost of anything a user does: it
includes the test contract's own work — encoding arguments, making the call, running assertions, any
cheatcode calls — wrapped around the one call you care about.

So a snapshot line is a **controlled quantity**, not a price. Its value is that it moves when the
thing you are measuring moves and stays put otherwise. Treating it as "what `credit` costs" imports
every problem from the previous lesson and adds test-harness overhead on top.

<Aside kind="warn">
`forge snapshot` runs your tests, which means it inherits the active profile — `FOUNDRY_PROFILE`
selects it, and non-default profiles inherit `[profile.default]`, so a `ci` profile carries every
key you did not restate.<Cite src="foundry-testing-config" /> A file generated locally under `default` (optimizer off on forge
1.7.1) and checked in CI under a profile with the optimizer on will mismatch on every line, and the
diff will look like a catastrophic regression.<Cite src="measured-forge-1-7-1" /> Generate and check the snapshot under the
*same* profile, and say which one in the CI job's name.
</Aside>

## `--diff` informs; `--check` gates

Two flags, and the difference between them is the difference between a comment and a blocker.

`forge snapshot --diff` compares the current run against the committed file and prints the deltas.
Against a snapshot where one line had been edited to 18,000:

```bash
forge snapshot --diff
```

Absolute delta and percentage per test, arrows for direction, and a total. **Exit code 0**.<Cite src="measured-gas-profiling-1-7-1" /> It
is a report, not a judgement.

`forge snapshot --check` runs the same comparison and exits **1** when the numbers do not
match.<Cite src="forge-snapshot-reference" /> Verified on that same 3.767% deviation: `--check` exits 1.<Cite src="measured-gas-profiling-1-7-1" /> That non-zero exit is
the entire mechanism by which gas becomes a required check in CI.

Both take an optional path, so you can diff against a file other than `.gas-snapshot` — useful when
you keep a frozen baseline separate from a rolling one.<Cite src="forge-snapshot-reference" /> And `--snap FILE` writes somewhere
other than the default.

<Aside kind="note">
`--diff-sort` orders the diff output: by percentage change ascending (the default), by percentage
descending, or by absolute change in either direction.<Cite src="forge-snapshot-reference" /><Cite src="measured-gas-profiling-1-7-1" /> On a suite with a hundred tests,
`--diff-sort absolute-desc` is what puts the change that costs real money at the top instead of the
change that moved a cheap test by nine percent.
</Aside>

## `--tolerance` is a percentage, and it exists

The Chainpath research pass could not confirm whether `forge snapshot --check` still accepted a
tolerance flag in the 1.x line, and flagged it as unresolved before anyone designed a gate around
it. It is resolved now, in both directions that matter. The reference documents `--tolerance` as
tolerating "gas deviations up to the specified percentage", and the installed binary
agrees.<Cite src="forge-snapshot-reference" /><Cite src="measured-gas-profiling-1-7-1" />

Behaviour, measured against that same 3.767% deviation:<Cite src="measured-gas-profiling-1-7-1" />

| Command | Exit |
|---|---|
| `forge snapshot --check` | 1 |
| `forge snapshot --check --tolerance 1` | 1 |
| `forge snapshot --check --tolerance 5` | 0 |

The load-bearing detail is that it is a **percentage, not a gas amount**.<Cite src="forge-snapshot-reference" /> `--tolerance 5` on a
test that uses 18,000 gas permits a 900-gas movement; the same flag on a test that uses 2,000,000
permits 100,000. If your suite's tests span two orders of magnitude — and most do, because a
deployment test and a getter test live in the same file — one percentage cannot be right for both.
That is an argument for a small dedicated gas suite with tests of comparable size, which is the same
conclusion the previous lesson reached from the other direction.

## The false positive that trains people to ignore the gate

Here is the failure mode, and it is not hypothetical:

**Subgoal — reproduce the false positive, because reviewers need to recognise it on sight.** Add one
test to an existing suite. Change no production code. Run `forge snapshot --check`.

It fails. The snapshot file keys off test names, so a new test is a new line, and a missing line is
a mismatch. Worse, as the previous lesson showed, adding a test that calls a function also changes
the gas-report statistics for that function even though nothing about the contract moved.

The consequence is behavioural. A gate that goes red for reasons unrelated to the diff teaches
reviewers to regenerate the file without reading it, and once that reflex exists the gate has
negative value — it is now a rubber stamp with a red icon.<Cite src="rubilmax-gas-diff" />

<Misconception
  belief="A red gas diff in CI means the pull request made the contract more expensive."
  reality="Adding, renaming or reordering a test moves the file with no production change at all, because the snapshot keys off test names and the report's statistics are computed over whatever calls the suite made."
  why="The diff is presented as a property of the code, and the file lives next to the code, so it reads as one."
  src="rubilmax-gas-diff" />

Three arrangements survive contact with a real team, in increasing order of discipline:

**Diff comment, no gate.** Run the report on base and on head, post the delta as a pull-request
comment, never block the merge.<Cite src="rubilmax-gas-diff" /> The reviewer sees the economic consequence at the moment they
are reading the code, and a false positive costs nobody anything. This is the
highest-value-per-unit-of-pain option and the right default.

**Gate on a frozen gas suite.** A separate directory of tests that exist only to be measured,
changed about as often as the contract's public interface. `forge snapshot --check --snap
.gas-snapshot.gas --match-path test/gas/*` as a required check. Because the suite does not churn,
the gate does not go red for suite reasons, and when it does go red it means something.

**Gate with a tolerance.** `--tolerance` on a suite of comparable-sized tests, sized so that
ordinary compiler noise passes and a real regression does not. Reach for this only when you have a
number in mind and can say what it protects.

<Aside kind="warn">
A gate on the functional suite, with no tolerance, in a repository where tests are added weekly, is
the arrangement that produces the reflex. If your repository has one, the fix is not a better
tolerance — it is moving the gate onto a suite that does not move.

## Fuzz tests, and how noisy they actually are

The received wisdom is that fuzzed tests make snapshots unusable because the numbers move every run.
Measured, it is subtler than that, and the subtlety is the dangerous part.

On forge 1.7.1 the resolved default is `fuzz.seed = null` — no pinned seed.<Cite src="measured-gas-profiling-1-7-1" /><Cite src="foundry-testing-config" /> Three
consecutive unseeded snapshot runs of the same fuzz test produced **identical** lines: `(runs: 256,
μ: 55163, ~: 56096)` every time. And yet the seed demonstrably matters — `--fuzz-seed 2` moved the
mean to 55,474 while leaving the median at 56,096.<Cite src="measured-gas-profiling-1-7-1" />

So the honest description is not "fuzz gas is random noise". It is:

- The **mean** is input-dependent and can move by hundreds of gas on a test this simple.
- The **median** was stable across every seed tried here, because it is a robust statistic and the
  distribution is dominated by one modal path.
- Unseeded runs are **not guaranteed** to differ, which is worse than guaranteed to differ. A gate
  that is red one run in twenty is harder to diagnose and easier to rationalise than one that is red
  every run.

The two workable answers are the ones the ecosystem converged on independently. [Pin the
seed](/c/fuzz-seed-reproducibility) in the profile the snapshot runs under, which makes the run
reproducible;<Cite src="foundry-testing-config" /> or keep the snapshot on a non-fuzz gas suite and let the fuzz campaign live
somewhere the snapshot does not see.<Cite src="rubilmax-gas-diff" /><Cite src="foundry-ci" />

Pinning has a cost you should say out loud: a fixed seed searches the same points every run, so the
fuzzer stops being a search and becomes a fixed set of test vectors. Pin it in the profile that
produces gas numbers, and run an unseeded campaign elsewhere.<Cite src="foundry-testing-config" />

<Check type="predict" concept="fuzz-seed-determinism">
A repository has `forge snapshot --check` as a required status check on every pull request. The
snapshot covers the whole `test/` directory, which contains 40 unit tests and 6 fuzz tests. There is
no `[fuzz] seed` in `foundry.toml`.

Over one month, three things happen. Predict which of them turns the check red, and say whether each
red is a true or a false positive.

1. A pull request adds a storage variable to a hot struct, pushing a field into a second slot.
2. A pull request adds three unit tests for an existing untested branch, touching no `src/` file.
3. A pull request changes a comment, and CI is re-run twice on the same commit.

<Answer>
**1 — red, and a true positive.** This is the one case the gate exists for. Splitting a struct
across a second slot adds a distinct slot to every function that writes it, which is the single
largest lever on cost. Expect the movement to be in the thousands on first-write paths and around a
hundred on warm ones. The right response is to read it, decide it is worth it or not, and regenerate
the file in the same commit.

**2 — red, and a false positive.** Three new tests are three new lines that the committed file does
not have. Nothing in `src/` changed, so the deployed size is identical, which is how the reviewer
confirms it in five seconds. The gate has just spent a reviewer's attention on nothing.

**3 — possibly red, and if so, a pure false positive on a comment change.** With `fuzz.seed = null`
the six fuzz tests draw fresh inputs, and each contributes a `μ` that is input-dependent. Measured
here, an unseeded fuzz test was stable across three consecutive runs but moved by 311 gas across
seeds<Cite src="measured-gas-profiling-1-7-1" /> — so this may be red on one re-run and green on the next, on a byte-identical commit.
That is the worst failure mode available: intermittent, unexplainable from the diff, and it teaches
the team that the gate lies.

**The repair, in order.** Pin `[fuzz] seed` so case 3 stops. Move the gate off the functional suite
so case 2 stops. What remains is case 1, which is the only thing anyone wanted to catch, and now a
red build means it.

</Answer>
</Check>

## What to commit, and what to say in the pull request

Commit `.gas-snapshot`. It is small, it is text, and its diffs are the point.

When you regenerate it, do so **in the same commit as the change that moved it**, never as a
separate "update snapshot" commit. A snapshot update on its own is unreviewable: the reviewer sees
numbers move with no code beside them and has nothing to check the movement against. The paired
commit is self-documenting.

Do not add `.gas-snapshot` to `.gitignore` to stop the noise. That is the failure this whole
mechanism exists to prevent, and it is the outcome of every gate that goes red for the wrong reason
often enough. If the file is annoying, the suite it covers is wrong; fix the suite.

And write one line in the pull request saying which direction and why. "Splitting the struct costs
~2,900 on `settle`'s warm path and buys us the upgrade slot" is a design decision recorded at the
moment it was made. Six months later that sentence is the only thing that will explain the number.
