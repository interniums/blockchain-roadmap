Two files, both named `hardhat.config`, both described by their documentation as "the config".

```js
// The shape Hardhat 2 material describes.
require("@nomicfoundation/hardhat-toolbox");

module.exports = {
  solidity: "0.8.19",
  networks: {
    sepolia: { url: process.env.SEPOLIA_RPC_URL, accounts: [process.env.PK] },
  },
};
```

```ts
// Hardhat 3.
import { defineConfig, configVariable } from "hardhat/config";
import hardhatToolboxMochaEthers from "@nomicfoundation/hardhat-toolbox-mocha-ethers";

export default defineConfig({
  plugins: [hardhatToolboxMochaEthers],
  solidity: { version: "0.8.36" },
  networks: {
    sepolia: {
      type: "http",
      chainType: "l1",
      url: configVariable("SEPOLIA_RPC_URL"),
      accounts: [configVariable("SEPOLIA_PRIVATE_KEY")],
    },
  },
});
```

Almost nothing survives the transition. The module system changed, the plugin registration model
changed, the network object changed, and the mechanism by which a plugin extends the tool at all was
replaced. That is why a Hardhat 2 tutorial is not "a bit out of date" — it describes a program whose
extension points no longer exist.

This lesson walks the four changes that matter when you are reading or reviewing, then states the one
thing about Hardhat 2's future that is now settled and citable.

## Change one: the config must be an ES module

The migration guide's wording is direct: your Hardhat config must be an ES module.<Cite src="hardhat-migrate-from-2" />
The what's-new page adds the boundary: configuration files must now use ESM, although CommonJS
modules are still supported in scripts and tests.<Cite src="hardhat3-whats-new" />

Concretely, that means `"type": "module"` in `package.json` — which is what the published `hardhat`
package itself declares<Cite src="npm-hardhat-registry" /> — `import` rather than `require`, and
`export default` rather than `module.exports`. Node.js v22.13.0 or later is required, and support
follows subsequent even-numbered majors for as long as the Node team maintains
them.<Cite src="hardhat-getting-started" /><Cite src="hardhat-nodejs-support" />

Both halves of that are worth holding at once, because they are in genuine tension in practice. The
documented requirement is narrow. The reported experience is that it spreads, and secondary
practitioner write-ups treat ESM as the single most disruptive change in the
release.<Cite src="gembait-hardhat-esm" /> The mechanism behind the spread is not mysterious: setting
`"type": "module"` changes how Node interprets every `.js` file in the package, so a project whose
deploy scripts, fixtures and helper modules are CommonJS `.js` files either converts them or renames
them to `.cjs`. A project whose scripts were already TypeScript with ESM-compatible settings barely
notices.

For a reviewer, the useful diagnostic is therefore not "is this project ESM" but "how many `.js`
files does this project have outside `node_modules`". That number predicts the cost.

Nomic's own framing of *why* connects the change to the ecosystem rather than to taste: Hardhat 3 and
its plugin system were redesigned to be ESM native to support the changing Node.js
ecosystem.<Cite src="hardhat-2-eol" /> Which, as the last section of this lesson shows, is also the
stated reason Hardhat 2 has an end date at all.

## Change two: plugins are registered, not imported for effect

In Hardhat 2, importing a plugin was how you installed it. The `require` line at the top of the old
config above is not decoration — it is the registration. Hardhat 3's migration guide names the change
precisely: plugins, tasks and other extensions are configured explicitly in your config instead of
being registered by side effects, and a plugin must now be both imported *and* added to the `plugins`
array.<Cite src="hardhat-migrate-from-2" /> The release notes put it as a design goal: Hardhat 3
configuration is now fully declarative, in contrast to Hardhat 2, where part of the configuration
came from the side effects of importing plugins or calling functions such as
`task`.<Cite src="hardhat3-whats-new" />

If you are inheriting a repository, this is the change that improves your life most, and it is worth
being explicit about why.

**Subgoal — state the old failure mode.** Under side-effect registration, the set of behaviours a
project has is the union of everything reachable through its imports. A plugin imported in a helper
file that is imported by a task that is imported by the config is active, and nothing in the config
says so. Answering "what does this project do on `npx hardhat test`" meant tracing the import graph.

**Subgoal — state what replaced it.** The `plugins` array is a closed list. What is in it is active;
what is not in it is not. One file, one array, one answer.

**Subgoal — name the cost, because there is one.** Explicitness means a longer config and a second
place to forget. The migration guide flags exactly this as the common mistake: unlike Hardhat 2, it
is not enough to import the plugin.<Cite src="hardhat-migrate-from-2" /> A plugin that is installed
and imported but absent from the array is inert, and the failure looks like the plugin being broken.

One consequence of the same design is that the test runner itself became a plugin. Hardhat 2 always
ran JavaScript tests with a bundled Mocha; in Hardhat 3 the test runner is a plugin you choose, with
official options for Mocha and for Node.js's built-in test runner, the latter being the recommended
one on grounds of speed and having no external dependencies.<Cite src="hardhat3-whats-new" /> So
"Hardhat uses Mocha" is now a statement about a particular repository's `plugins` array rather than
about the tool. There is a dedicated guide for moving an existing Mocha suite
across.<Cite src="hardhat-migrate-mocha" />

## Change three: hooks replaced monkey-patching

Hardhat 2 plugins extended the tool by patching it. Two mechanisms carried most of that weight:
`extendConfig`, which let a plugin mutate the resolved configuration, and subtask overriding, which
let a plugin replace a step inside a built-in task. Both are gone, replaced by a hooks
system.<Cite src="hardhat-migrate-from-2" /> The release notes describe it as a new hook system that
enables easy extension of core functionality and allows plugin authors to add their own extensibility
points.<Cite src="hardhat3-whats-new" /> A third mechanism went with them: adding new fields to the
Hardhat Runtime Environment with `extendEnvironment` is no longer possible.<Cite src="hardhat-migrate-from-2" />

The distinction is between *interception* and *declaration*. Interception means a plugin reaches into
something it does not own and changes it; whether two plugins can coexist then depends on the order
they were loaded and on whether their patches happen to compose. Declaration means the tool publishes
the points at which behaviour can be attached, and a plugin attaches there.

This is why the ecosystem port took real time, and why "wait for the plugins" was a rational
migration posture rather than inertia. A Hardhat 2 plugin was not recompiled for Hardhat 3; the
mechanism it was written against no longer existed, so it was rewritten against a different one.

OpenZeppelin's upgrades plugin is the worked case, and the shape of its breaking changes tells you
exactly which mechanism it had been relying on. Its migration notes list: no automatic `hre.upgrades`
— you must call a factory function explicitly; factory functions are asynchronous and require a
network connection; imports changed, because you now import the factory functions rather than just
the plugin; and its peer dependency ranges were updated for Hardhat 3.<Cite src="oz-migrate-from-hardhat2" />
The page also states the prerequisite plainly: migrate your Hardhat project to Hardhat 3
first.<Cite src="oz-migrate-from-hardhat2" />

Read that list against the two mechanisms. "No automatic `hre.upgrades`" is `extendEnvironment` being
gone. "Factory functions are async and require a network connection" is the next change.

<Aside kind="warn">
When you see a Hardhat plugin in a repository, check what it is a plugin *for* before assuming the
version. A tutorial that installs `hardhat-gas-reporter` or `solidity-coverage` is Hardhat 2
material: Hardhat 3 ships gas statistics and Solidity code coverage as first-party features, reached
with `--gas-stats` and `--coverage` respectively.<Cite src="hardhat3-whats-new" /> The presence of
those two packages in a `package.json` is a reliable fingerprint of a project that has not moved.
</Aside>

## Change four: there is no ambient network

In Hardhat 2, a task had access to a single fixed connection for its entire duration, reachable as
`hre.network`. In Hardhat 3, connections are managed explicitly and tasks can create and use multiple
connections simultaneously.<Cite src="hardhat3-whats-new" /> The migration guide states the
consequence for existing code: you create and manage network connections yourself, which means
`hre.network` no longer represents a single network connection that is immediately
available.<Cite src="hardhat-migrate-from-2" />

`hre.network` still exists — but it is now a `NetworkManager`, a factory, not a connection. Its
documented methods are three:<Cite src="hardhat-network-manager" />

```ts
import { network } from "hardhat";

// A fresh connection. With no arguments, it uses the "default" Network Config,
// which is an edr-simulated network, so this creates a new simulated chain.
const connection = await network.create();

// Same, but reuses an existing connection with that name and chain type if one exists.
const reused = await network.getOrCreate({ network: "hardhatOp", chainType: "op" });

// A simulated chain exposed over HTTP JSON-RPC — a wrapper around create().
const server = await network.createServer();
```

Two details that a reviewer should not have to discover the hard way. First, every connection is
independent of every other, and an in-process EDR-simulated connection and an HTTP connection to a
real node expose the same API, so code can be moved between them.<Cite src="hardhat-network-manager" />
Second, `network.connect()` is deprecated and slated for removal; `create()` or `getOrCreate()` are
the current forms.<Cite src="hardhat-network-manager" /> Material written early in the Hardhat 3 line
uses `connect()`, so seeing it is a dating signal rather than an error.

This is also the change with the widest blast radius across a repository's *own* code, as opposed to
its dependencies. Every script, task and test written against the ambient singleton needs rewriting,
because the object it reached for now returns a factory. The migration guide's own smallest example
of the new form is a single line — `const { provider } = await hre.network.create();` — but the
number of call sites is whatever your repository's script directory happens to
contain.<Cite src="hardhat-migrate-from-2" />

### Reading the four changes as one design

Put them side by side and they are the same decision applied four times: replace ambient, implicit,
global state with explicit objects that something has to ask for. The module system change makes
imports statically analysable. The plugins array makes the active feature set enumerable. Hooks make
extension points declared rather than intercepted. The network manager makes connections values
rather than context.

That is a coherent design, and naming it as one decision rather than four is what lets you predict
the rest of the surface instead of memorising it. When you meet a Hardhat 3 API you have not seen,
the useful prior is "it is probably something you construct and pass, not something that is already
there".

## Hardhat 2 has a published end date now

The research this curriculum was built from could not establish an end-of-life date for Hardhat 2 and
recorded it as unknown. That is no longer the state of the world, and the policy page is worth quoting
carefully because it has two triggers rather than one.

Hardhat 2 will be upgraded to support the Glamsterdam hardfork and will continue to receive bug fixes
and security fixes until its end of life, which is the earlier of two events: the activation of the
Hegota hardfork on Ethereum mainnet, or the 1st of June 2027 if Hegota is delayed. It will not be
upgraded to Hegota or any of its EIPs, and after that date no further releases should be expected,
including for security fixes.<Cite src="hardhat-2-eol" /> The stated motivation is the Node.js
ecosystem moving beyond the CommonJS system Hardhat 2 uses.<Cite src="hardhat-2-eol" />

Three things follow that are easy to get wrong.

**The date is conditional, and one of its conditions is a hardfork with no published mainnet date.**
"The earlier of X or 1 June 2027" is a ceiling, not a schedule. If Hegota activates before that
ceiling, Hardhat 2 ends earlier. Any plan that treats June 2027 as the deadline is planning against
the *latest* possible date.

**"No further releases including for security fixes" is the part that matters for a production
repository.** This is not a deprecation warning in a changelog; it is an announced end to the
security-patch stream for a build tool that runs with your keys in its environment.

**Hardhat 2 is still being released today.** The npm registry carries a separate `hh2` distribution
tag, at 2.29.1 as of 26 August 2026, alongside `latest` at 3.14.0.<Cite src="npm-hardhat-registry" />
So "Hardhat 2 is EOL" is wrong in the present tense and correct as a direction. A repository on
Hardhat 2 today is supported; a repository on Hardhat 2 in two years is not.

On the other side of the line, Nomic now describes Hardhat 3 as stable and production
ready.<Cite src="hardhat-2-eol" /> The path there is unusual enough to be worth recording, because it
explains a lot of confused writing about this release. The 3.0.0 tag, published on 13 August 2025,
was titled "Hardhat 3 is now in beta, and ready for production use" — beta and production-ready in
the same sentence.<Cite src="hardhat-300-release" /><Cite src="npm-hardhat-registry" /> The
end-of-life page later characterises that period as nine months in beta spent stabilising the API,
closing bugs and removing migration friction.<Cite src="hardhat-2-eol" /> No separate general-availability
announcement was located for this module, so no GA date is published here — what is citable is the
tag date, the vendor's own "nine months" characterisation, and the current stable
description.<Cite src="hardhat-2-eol" />

Meanwhile the line moves quickly: 3.0.0 in August 2025, 3.3.0 at the end of March 2026, and 3.14.0 on
20 August 2026.<Cite src="npm-hardhat-registry" /><Cite src="hardhat-330-release" /> Read that
alongside the stability policy — semver is not followed strictly and breaking changes may land in
minor versions<Cite src="hardhat-stability-guarantees" /> — and the operational conclusion for a
Foundry user is that a Hardhat dependency needs a committed lockfile and a deliberate upgrade cadence,
not a pin-and-forget.

<Answer>
**1 — The plugins are inert.** Converting `require("@nomicfoundation/hardhat-toolbox")` into an

a green compile job is not evidence of a completed migration. Evidence: an `import` of a plugin

**2 — Every script and test that touches the network.** `hre.network` is now a `NetworkManager`, so

the repository for `hre.network` and `network.connect` — call sites that are not followed by
`create()` or `getOrCreate()` are the list of things to fix. This is usually the largest part of the
work by line count, and it lives in `scripts/` and `test/`, neither of which a compile job exercises.

**3 — Any plugin that extended the environment or a subtask.** If the project used a plugin that
added a field to the HRE — OpenZeppelin's upgrades plugin adding `hre.upgrades` is the canonical case
— that mechanism is gone, and the plugin's own major version has a different API that must be adopted
deliberately.<Cite src="oz-migrate-from-hardhat2" /><Cite src="hardhat-migrate-from-2" /> Evidence:
`extendConfig`, `extendEnvironment` or subtask overriding anywhere in the repository's own code, and
plugin dependency ranges in `package.json` that were not bumped.

`solidity-coverage` are still in `devDependencies`, the project is carrying plugins whose features are
now first-party.<Cite src="hardhat3-whats-new" />

The reviewable rule underneath all of this: a Hardhat 2 to 3 migration cannot be verified by a build
job, because the four things that changed — module system, plugin registration, extension mechanism,
network access — are only two-thirds exercised by compiling. The gate that means something is the
test and script surface actually running.

## What this unlocks

You can now read a Hardhat repository and date it. A `require` in the config, a bare
`hre.network.provider`, `extendConfig` in a local plugin, `solidity-coverage` in the dependency list —
each of those places the project on one side of the version line, and together they tell you whether
you are reviewing current material or archaeology.

The next lesson turns from what changed to what Hardhat 3 *does* that forge does not: Solidity tests
as a first-class runner with a documented compatibility boundary, chain-type simulation, build
profiles, and Ignition's declarative deployment model against the imperative one you know from
[forge script](/c/forge-script) and its [broadcast artifacts](/c/broadcast-artifacts). Three of those
four rest directly on the network-connection change you just read.<Cite src="hardhat-home" />
