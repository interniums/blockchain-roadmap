Here is what `npx hardhat --init` produces, with the annotations the getting-started page attaches to
each entry:<Cite src="hardhat-getting-started" />

```text
hardhat-example/
  package.json          npm package file; Hardhat and its plugins are installed here
  hardhat.config.ts     the project's main configuration file
  contracts/
    Counter.sol         Solidity contracts
    Counter.t.sol       Solidity test files may also live here, with the .t.sol extension
  test/
    Counter.ts          TypeScript and Solidity tests; Solidity here may be .sol or .t.sol
  ignition/
    modules/
      Counter.ts        Ignition deployment modules
  scripts/
    send-op-tx.ts       custom scripts with full access to the runtime
```

Most of a Hardhat repository becomes legible the moment you have the mapping. This lesson is that
mapping, plus the one place where the two toolchains genuinely disagree rather than merely differ —
import resolution, which is where the interesting failures live.

## The mapping

| Foundry | Hardhat 3 | Notes |
|---|---|---|
| `src/` | `contracts/` | both configurable; the Hardhat default is `./contracts`<Cite src="hardhat-config-reference" /> |
| `test/*.t.sol` | `test/*.sol`, `test/*.t.sol`, or `contracts/*.t.sol` | discovery rules differ, see below<Cite src="hardhat-solidity-tests-guide" /> |
| `script/*.s.sol` | `ignition/modules/*.ts` and `scripts/*.ts` | two mechanisms, not one<Cite src="hardhat-getting-started" /> |
| `out/` | `artifacts/` | Hardhat default `./artifacts`<Cite src="hardhat-config-reference" /> |
| `cache/` | `cache/` | same name, different contents — see below<Cite src="hardhat-config-reference" /> |
| `broadcast/` | `ignition/deployments/chain-<id>/` | both recommended for commit<Cite src="hardhat-ignition-guide" /><Cite src="foundry-deploying" /> |
| `lib/` (git submodules) | `node_modules/` (npm) — and `lib/` still works | both supported in Hardhat 3<Cite src="hardhat-dependencies-guide" /> |
| `foundry.toml` | `hardhat.config.ts` | table versus program |
| `remappings.txt` | `remappings.txt` | same file, different scoping rules |

Four rows in that table are more interesting than a mapping.

**`cache/` is not the same thing.** Hardhat 3 builds contracts and tests as separate build processes,
and it does not expose the test build artifacts — they are considered internal and part of
`cache/`.<Cite src="hardhat-foundry-compatibility" /> So a Hardhat `artifacts/` directory is the ABIs
and bytecode of *shipped* contracts, where Foundry's `out/` contains everything it compiled including
your test contracts. If you have ever grepped `out/` for a test helper's ABI, the equivalent grep
finds nothing.

**npm dependencies do not emit artifacts by default.** Hardhat treats files coming from npm as
dependencies rather than as part of your project, so they produce no artifacts unless you ask for
them.<Cite src="hardhat-dependencies-guide" /> This is the direct analogue of a question you have
already met on the Foundry side — whether `lib/` contents show up in your build output — and it has
practical consequences for anything that reads artifacts to find a deployed dependency's ABI.

**There are two deployment mechanisms, not one.** `ignition/modules/` holds declarative deployment
modules; `scripts/` holds ordinary programs with full access to the runtime that can use plugins,
connect to networks and deploy contracts.<Cite src="hardhat-getting-started" /> A repository that
uses only `scripts/` for deployment is doing something closer to `forge script` in spirit, and a
repository with a populated `ignition/deployments/` has real deployment history in version control.

**Test discovery is a superset, and the overlap bites.** In Foundry, a Solidity test is
`test/*.t.sol`. In Hardhat, it is any `.sol` inside `test/`, or any `.t.sol` inside
`contracts/`.<Cite src="hardhat-solidity-tests-guide" /> The consequence in a coexistence repository
is asymmetric: a Solidity file dropped into `test/` without the `.t.sol` suffix is a test to Hardhat
and an ordinary compilation unit to forge. Shared helper contracts placed in `test/` are exactly the
files that trip this.

<Aside kind="note">
Hardhat's own Foundry-migration guide suggests configuring `src/` as the sources directory when you
want the two layouts to line up, and explicitly recommends leaving `foundry.toml`, `remappings.txt`
and `lib/` in place during a migration.<Cite src="hardhat-foundry-compatibility" /><Cite src="hardhat-migrate-from-foundry" />
That is a vendor's migration advice rather than neutral guidance, but the underlying observation is
sound and it is the same one the coexistence lesson lands on: aligning `paths.sources` is the cheapest
way to stop two toolchains from arguing about where the code is.
</Aside>

## The part that is not a mapping

Now the resolver. This is the one place where knowing the translation table is not enough, because
the same import string can name a different file under each tool.

### What you already know: Foundry

Foundry rewrites an import prefix through a remapping and then hits the filesystem. The set of
remappings is assembled from up to three places at once — automatic detection of `lib/` contents,
an optional `remappings.txt`, and the `remappings` key in `foundry.toml` — and they *merge* rather
than replace, so the set that actually applies is frequently written down
nowhere.<Cite src="foundry-solc-config" /><Cite src="foundry-issue-5258" /> `forge remappings`
prints the resolved set, and it is the only reliable answer to "why did this import land
there".<Cite src="foundry-solc-config" /> Auto-detection of `lib/` is on by default, confirmed on
forge 1.7.1.<Cite src="measured-forge-1-7-1" /> Dependencies are git submodules under `lib/` by
default, which is why `lib/`-shaped remappings are the norm.<Cite src="foundry-dependencies" />

The mental model: one global, merged, flat namespace of prefix rewrites.

### What is actually true of Hardhat 3

The received wisdom is that Hardhat resolves imports through Node module resolution over
`node_modules`, full stop. That was a fair description of Hardhat 2 and it is now incomplete in a way
that matters.

Hardhat 3 has built-in support for user-defined Solidity remappings and loads them from *every*
`remappings.txt` it finds — anywhere in your project including inside a git submodule, with
`node_modules` folders as the only exception, plus all the `remappings.txt` files inside an npm
package the first time that package is imported.<Cite src="hardhat-remappings-guide" /> The file
format carries a third component that Foundry's does not:<Cite src="hardhat-remappings-guide" />

```text
context/:prefix/=target/
```

The `context/:` part controls *which files* a remapping affects: a file's source name must start with
`context/` for the remapping to apply.<Cite src="hardhat-remappings-guide" /> And you are advised not
to write it yourself, because Hardhat generates it for you from where the `remappings.txt` sits.

That generation is the whole design. Each `remappings.txt` only affects files in its own directory
and that directory's subdirectories, so remappings cannot clash across a project; where two seem to
clash, Hardhat chooses the more specific one — the one defined
closest.<Cite src="hardhat-remappings-guide" />

The mental model: many scoped rewrite sets, resolved by proximity — not one merged flat set.

On top of that sits npm resolution proper, with properties Hardhat calls out explicitly: transitive
dependencies work natively even when two dependencies need incompatible versions of the same library;
monorepos are supported natively; and npm dependencies need no remappings after installation because
Hardhat handles them automatically. Library authors can also customise which files they export using
`package.json#exports`, so an import of `lib/Foo.sol` can be made to resolve to
`lib/src/Foo.sol`.<Cite src="hardhat-dependencies-guide" />

### The same string, two answers

**Subgoal — set up the ambiguity with real files.** A repository has both toolchains. `lib/` holds
`openzeppelin-contracts` as a git submodule at one tag; `node_modules/@openzeppelin/contracts` holds
a different published version, because some npm dependency needed it. One Solidity file contains:

```solidity
import { ERC20 } from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
```

**Subgoal — resolve it the Foundry way.** Auto-detection of `lib/` produces a remapping for the
submodule; if `remappings.txt` or `foundry.toml` also declares one, all of them merge. The prefix is
rewritten and the file under `lib/` is compiled.<Cite src="foundry-solc-config" /><Cite src="measured-forge-1-7-1" />

**Subgoal — resolve it the Hardhat way.** If a `remappings.txt` is in scope for this file's
directory and declares that prefix, it applies — with the more specific one winning if several could.
If none is in scope, the import is an npm package import and resolves through
`node_modules`.<Cite src="hardhat-remappings-guide" /><Cite src="hardhat-dependencies-guide" />

**Subgoal — notice that both succeeded.** Neither tool errors. Both compile. Two different `ERC20.sol`
files, potentially two different versions, produce two different bytecodes for the same source
file — and your tests pass under both, because each is testing what it compiled.

**Subgoal — name the check.** Run `forge remappings` to get Foundry's resolved set, and compare it
against what `remappings.txt` files exist and where, since their location is what scopes them in
Hardhat.<Cite src="foundry-solc-config" /><Cite src="hardhat-remappings-guide" /> The decisive
evidence is not the config: it is comparing the compiled bytecode, or the version string, of the same
contract from each toolchain's artifacts.

One escape hatch worth knowing, because it appears in real configs: some Foundry projects have no
`remappings.txt` at all and rely on forge to generate remappings from `lib/`. For those,
Hardhat ships `@nomicfoundation/hardhat-foundry`, added to the `plugins` array like any other
plugin.<Cite src="hardhat-foundry-compatibility" /> Seeing it in a config tells you the project's
Foundry side relies on auto-detection rather than a committed file.

<Check type="spot-bug" concept="remapping-vs-node-resolution">
A repository runs both toolchains over the same contracts. CI has two jobs: `forge test` and
`hardhat test`. Both are green. A reviewer notices that the deployed bytecode from the Ignition
deployment does not match what the Foundry gas snapshot implies for the same contract, and no one can
reproduce the discrepancy locally.

What is the most likely cause, and what is the smallest experiment that confirms or eliminates it?

<Answer>
**Most likely cause: the two toolchains are compiling different dependency source.** The candidates,
in order of how often they are the answer:

*Different files for the same import.* An `@openzeppelin/...` import resolving to a `lib/` submodule
under forge and to `node_modules` under Hardhat gives you two different implementations of the same
base contract, which changes the bytecode of everything that inherits from
it.<Cite src="foundry-solc-config" /><Cite src="hardhat-dependencies-guide" /> The scoping rules make
this easy to create accidentally: a `remappings.txt` in a subdirectory affects only that subtree in
Hardhat, while forge merges every remapping it finds into one set.<Cite src="hardhat-remappings-guide" />

*Different compiler settings.* Two configuration files each pin a solc version and optimizer
settings, and nothing keeps them in sync. Ignition compounds this by building with the `production`
build profile automatically, which has the optimizer and isolated builds enabled by
default — so the deployment is not even built the same way as the Hardhat test
run.<Cite src="hardhat-ignition-guide" /><Cite src="hardhat-build-profiles" />

**Smallest confirming experiment: compile one contract with each toolchain and diff the artifacts.**
Not the sources, not the configs — the artifacts, which carry the compiler version and settings
alongside the bytecode.<Cite src="foundry-installation" /> If the metadata differs, it is settings. If
the settings match and the bytecode differs, it is resolution, and `forge remappings` plus an
inventory of every `remappings.txt` in the tree tells you where the fork in the path
is.<Cite src="foundry-solc-config" /><Cite src="hardhat-remappings-guide" />

**Why "both jobs are green" was never evidence.** Each job compiled its own view of the project and
tested that view. Two green suites over two different bytecodes is exactly the state this
configuration produces, and it is the reason the last lesson insists a coexistence setup needs one
declared source of truth for compiler settings and for dependencies rather than two configurations
that happen to agree today.
</Answer>
</Check>

## What this unlocks

You can now open an unfamiliar Hardhat repository and answer, in a couple of minutes: where the
contracts are, which files are tests and to which runner, where deployment history lives, where
dependencies come from, and — the one that takes deliberate checking — which file a given import
actually names.

That last skill is what makes the final lesson possible. Running both toolchains over one `src/` is a
supported and common arrangement; the cost that decides whether it is worth paying is the one you just
learned to measure.
