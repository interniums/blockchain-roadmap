You clone a protocol you have been asked to review. The tree looks close enough to familiar:

```text
package.json
hardhat.config.ts
contracts/
test/
ignition/modules/
scripts/
```

You run `forge test`, because that is what your hands do. It finds no `foundry.toml`, guesses a
project root, compiles nothing you recognise, and produces an error about an import it cannot
resolve. Nothing is broken. You are simply holding the other toolchain, and every reflex you built
over the last four tracks is pointed at the wrong binary.

This module is about reading that repository. Not migrating it, not arguing about it — reading it,
well enough to review a pull request, answer "what will this actually deploy", and decide whether the
second toolchain in your own project is earning its keep. This first lesson establishes what the two
programs are, why one of them is *configured* and the other is *programmed*, and what is actually
executing EVM bytecode inside each.

## Two programs, one language

The Solidity in `contracts/` is the same Solidity that would be in `src/`. Same compiler, same
[storage layout rules](/c/storage-slot), same [delegatecall semantics](/c/sol-delegatecall-context).
The divergence is entirely above the language.

**Foundry** you already know: four Rust binaries — forge, cast, anvil, chisel — installed and
version-managed together by foundryup, with tests written as Solidity contracts executed by an EVM
inside the forge process.<Cite src="foundry-installation" /><Cite src="foundry-writing-tests" /> The
project is described by a declarative TOML file that forge finds by walking up from the working
directory, and `forge config` prints the fully merged result.<Cite src="foundry-config-overview" />
This curriculum pins forge 1.7.1 and solc 0.8.36, both verified on the authoring
machine.<Cite src="measured-forge-1-7-1" />

**Hardhat** is an npm package. The current published version is 3.14.0, released on 20 August
2026, and its `package.json` declares `"type": "module"`.<Cite src="npm-hardhat-registry" /> You
invoke it through your package runner — `npx hardhat test`, `npx hardhat compile` — and it requires
Node.js v22.13.0 or later, with a stated policy of supporting subsequent even-numbered majors for as
long as the Node team maintains them.<Cite src="hardhat-getting-started" /><Cite src="hardhat-nodejs-support" />
The project is described by `hardhat.config.ts`, and that file is not read as data. It is imported
and executed.

That last sentence is the whole difference, and it is worth sitting with before it gets buried under
API details. A Foundry project is *configured*. A Hardhat project is *programmed*. Everything
downstream — how you audit an unfamiliar repo, why plugins were historically hard to trace, what
"multichain" can even mean — follows from it.

## What a Hardhat 3 config looks like

Here is the shape the configuration reference documents, with the standard options that exist before
any plugin is installed.<Cite src="hardhat-config-reference" />

```ts
import { defineConfig, configVariable } from "hardhat/config";
import hardhatFoundry from "@nomicfoundation/hardhat-foundry";

export default defineConfig({
  plugins: [hardhatFoundry],
  paths: {
    sources: "./contracts",
    tests: "./test",
    cache: "./cache",
    artifacts: "./artifacts",
  },
  solidity: {
    version: "0.8.36",
    settings: {
      /* solc settings */
    },
  },
  networks: {
    hardhatMainnet: { type: "edr-simulated", chainType: "l1" },
    hardhatOp: { type: "edr-simulated", chainType: "op" },
    sepolia: {
      type: "http",
      chainType: "l1",
      url: configVariable("SEPOLIA_RPC_URL"),
      accounts: [configVariable("SEPOLIA_PRIVATE_KEY")],
    },
  },
});
```

Hardhat searches for the closest `hardhat.config.ts` starting from the current working directory —
the same walk-up behaviour that makes `foundry.toml` resolution depend on where you ran the command
from.<Cite src="hardhat-config-reference" /><Cite src="foundry-config-overview" /> An empty config is
enough for Hardhat to run.<Cite src="hardhat-config-reference" />

### Reading one in the order that pays off

When you open an unfamiliar Hardhat config, resist reading it top to bottom. Five questions, in this
order, get you to a working mental model faster.

**Subgoal — establish which code is even active.** Look at `plugins`. In Hardhat 3 every plugin,
task and extension is registered explicitly here; nothing installs itself as a side effect of being
imported.<Cite src="hardhat-migrate-from-2" /><Cite src="hardhat3-whats-new" /> This array is the
answer to "what is this project capable of doing", and it did not exist as a single readable answer
in the previous major version.

**Subgoal — find the source of truth for compilation.** Look at `solidity`. It accepts a bare version
string, an array of versions, or an object with `version` and `settings` carrying the same schema as
solc's own settings.<Cite src="hardhat-config-reference" /> This is the equivalent of `solc`,
`optimizer` and `evm_version` in `foundry.toml`, and in a repository that runs both toolchains it is
the first place the two configurations drift apart.

**Subgoal — find where files are expected to be.** Look at `paths`. The defaults are `./contracts`,
`./test`, `./cache` and `./artifacts`, each resolved relative to the config file.<Cite src="hardhat-config-reference" />
If the repository has moved `sources` to `./src`, someone has deliberately aligned it with a Foundry
layout, which is a strong hint that both toolchains are in play.

**Subgoal — find what the tests will run against.** Look at `networks`. Each entry declares a `type`
— `edr-simulated` for an in-process simulated chain, `http` for a real JSON-RPC endpoint — and a
`chainType`.<Cite src="hardhat-config-reference" /> The presence of two simulated networks with
different chain types tells you the project cares about behaviour that differs between chains, which
is the subject of the third lesson in this module.

**Subgoal — notice what is deliberately *not* in the file.** `configVariable("SEPOLIA_RPC_URL")` does
not read an environment variable at parse time. It declares a configuration variable, a value loaded
only when something needs it, sourced from environment variables by default and redirectable by a
plugin — Hardhat ships an official one that stores them encrypted on disk.<Cite src="hardhat3-whats-new" />
So a secret's absence from the file is not evidence it is absent from the run.

## The consequence: reading is not the same as knowing

Because `hardhat.config.ts` is a TypeScript module, any value in it can be computed. It can import
another module, branch on `process.env`, read a file, or assemble a network list from a JSON manifest.
That is not a criticism of any particular repository — it is a property of the mechanism, and it is
also the reason the mechanism is powerful enough that half the ecosystem's tooling lives there.

The operational consequence for a reviewer is specific: for a Foundry project, `forge config` gives
you a guaranteed static answer to "what settings apply here".<Cite src="foundry-config-overview" />
For a Hardhat project, the guaranteed answer comes from *running* the tool, not from reading the file
— because the file's output is the result of executing a program.

Hardhat 3 has narrowed this gap deliberately rather than accidentally. Its own release notes state
that configuration is now fully declarative, in contrast to Hardhat 2, where part of the
configuration came from the side effects of importing plugins or calling functions such as
`task`.<Cite src="hardhat3-whats-new" /> The *shape* is now declarative. The *mechanism* is still a
program. Both facts matter, and confusing them is how people end up surprised.

<Aside kind="note">
One more property that has no Foundry analogue: Hardhat states plainly that it does not follow semver
strictly and may introduce breaking changes in minor versions, naming two categories in advance —
changes to the default config, and dropping support for unmaintained Node.js
versions.<Cite src="hardhat-stability-guarantees" /> Their recommendation is to commit your lockfile
and upgrade often rather than pin, on the grounds that a frozen toolchain eventually stops matching
the chain it was built for. That is a defensible position and a real operational difference from a
project where you pin the toolchain version in CI and leave it.
</Aside>

## What is actually executing the EVM

Now the part that most Foundry users have wrong, usually because they learned it correctly several
years ago.

The component of Hardhat that executes EVM bytecode is EDR — the Ethereum Development Runtime — a
Rust implementation that replaced the original JavaScript simulation layer. It first shipped in
Hardhat v2.21.0, published on 4 March 2024, and Nomic Foundation described it as the rewriting of
Hardhat's largest and most complex component in a new language.<Cite src="nomic-rust-hardhat" /><Cite src="npm-hardhat-registry" />
The JavaScript that remains is orchestration: task dispatch, plugin wiring, artifact management, the
TypeScript test runner. The interpreter loop is not JavaScript and has not been since early 2024.

That correction immediately invites the next question, and this is where the curriculum stops and
declines to give you a number.

**No speed multiplier is published in these lessons.** Nomic's own EDR announcement, secondary
toolchain comparisons, and the Hardhat 3 launch material each quote different figures, and none of
the ones surveyed for this module published a methodology you could inspect or reproduce.<Cite src="nomic-rust-hardhat" />
A multiplier with no method attached is not a measurement; it is a claim about someone's laptop and
someone's test suite.

There is also a structural reason to distrust any single ratio. The two toolchains do not do the same
work per invocation. Compilation caching, artifact emission, test discovery, whether TypeScript needs
transpiling, and whether the suite fuzzes at all move the number more than the interpreter does. A
suite dominated by fuzz campaigns is measuring the fuzzer; a suite of twelve unit tests is measuring
process startup.

The honest form of the question is one you can answer in an afternoon on your own repository, and the
module's practice asks exactly that: run the same suite under both, report the numbers *with* the
suite's shape, and then name what differs beyond wall-clock time.

## Triage in twenty seconds

A useful habit when a repository lands in front of you.

- `foundry.toml` at the root, `src/`, `lib/` as git submodules, `*.t.sol` under `test/` — Foundry
  project.<Cite src="foundry-installation" />
- `package.json` plus `hardhat.config.ts`, `contracts/`, `ignition/`, dependencies under
  `node_modules` — Hardhat project.<Cite src="hardhat-getting-started" />
- Both files present — a deliberate coexistence setup, and the two things to check first are which
  compiler version each config pins and whether the two agree about where a given import resolves.
  That is the fourth lesson, and it is the single most common source of "it passes here and fails
  there".

The third case is more common than newcomers expect and is not a sign of a mess. It is a division of
labour, and the last lesson in this module is about when the division is worth its cost.

<Check type="explain" concept="hardhat-config-is-code">
A colleague sends you a Hardhat repository and asks: "Which solc version does this build with, and
which networks can it deploy to?" You open `hardhat.config.ts` and read it end to end. Why is your
answer necessarily less certain than the equivalent answer for a `foundry.toml`, and what would you
do to raise the certainty?

<Answer>
Because `hardhat.config.ts` is an ES module that Hardhat imports and executes, not a table it
parses.<Cite src="hardhat-config-reference" /> Anything you read in it may be a computed value: the
`solidity.version` could come from a constant imported from another file, the `networks` object could
be spread from a manifest, and any branch could depend on `process.env`. Reading the file tells you
what the program *says*; it does not tell you what the program *returns* on the machine and in the
environment where it will actually run.

`foundry.toml` cannot do any of that, which is exactly why `forge config` can print a merged, static
answer.<Cite src="foundry-config-overview" /> Note the important caveat you already know from the
Foundry side: static does not mean environment-independent — `FOUNDRY_*` variables still override the
file, and the walk-up search means the file that applies depends on your working directory. The
difference is that the set of things that can vary is enumerable in one case and unbounded in the
other.

To raise certainty, execute rather than read. Run the tool in the same environment the answer is
about — the same directory, the same `.env`, the same CI runner — and have it report what it resolved
rather than trusting the source. The generalisable rule: for any configuration mechanism that is a
program, "what does the file say" and "what will the run do" are two different questions, and only
the second one is the one anyone was asking.

There is a second, subtler part to the answer. Even a perfectly static reading would not tell you
what the deploy targets are, because `configVariable` values are loaded lazily from the environment
or from a plugin-provided store.<Cite src="hardhat3-whats-new" /> An RPC URL that is not in the file
is not an RPC URL that does not exist.
</Answer>
</Check>

## What this sets up

Three things follow from here.

**The next lesson** takes the claim that Hardhat 3 is a different program rather than a version bump
and makes it concrete: the module system, the plugin registration model, the extension mechanism and
the network API all changed at once, which is why porting a Hardhat 2 plugin was rewriting rather than
recompiling.<Cite src="hardhat-migrate-from-2" />

**The third lesson** covers the four capabilities Hardhat has that forge does not, including what its
"multichain" actually means — and it is not the [multi-fork testing](/c/multi-fork-testing) you
already know.

**The fourth and fifth** are the practical payoff: translating a Hardhat tree into the layout you
think in, and the conditions under which a second toolchain is worth maintaining. The word
"conditions" is load-bearing there — the module ends in a decision procedure, not a preference.
