Strip out everything Hardhat does that forge also does — compile, run tests, report gas, check
coverage, deploy, verify — and four things are left. They are the honest answer to "what would I
actually get". Each of them is also routinely described wrongly, including by people advocating for
the tool, so each section here pairs the capability with its boundary.

## One: Solidity tests, with a documented compatibility edge

Hardhat has built-in support for Solidity tests and no plugin is needed to use
them.<Cite src="hardhat-solidity-tests-guide" /> The discovery rules are worth memorising because they
differ from Foundry's in a way that shows up the first time you copy a file across.

A Solidity file is a test file if it is inside the `test/` directory, or inside the `contracts/`
directory and ending in `.t.sol`. Both directories are configurable. A contract in a test file with
at least one function whose name starts with `test` is a test contract; the runner deploys every test
contract and calls each of its test functions, and a revert means
failure.<Cite src="hardhat-solidity-tests-guide" /> Fuzz tests are the same thing with parameters:
a test function that takes arguments is called repeatedly with random
values.<Cite src="hardhat-solidity-tests-guide" />

```solidity
contract CounterTest {
    function testInc() public {
        Counter counter = new Counter();
        counter.inc();
        require(counter.count() == 1, "count should be 1");
    }

    function testIncBy(uint by) public {
        Counter counter = new Counter();
        counter.incBy(by);
        require(counter.count() == by, "count should match the 'by' value");
    }
}
```

Note what is absent: no `is Test`, no import. The base contract is optional, and the docs recommend
an assertion library for better failure messages — their example installs `forge-std` from GitHub,
pinned, and extends `Test` so that `assertEq` can show the mismatched
values.<Cite src="hardhat-solidity-tests-guide" /><Cite src="forge-std-repo" /> Which is to say the
recommended way to write Solidity tests in Hardhat is with Foundry's standard library.

The compatibility claim is explicit on the Foundry-compatibility page: Hardhat 3 can run Solidity
tests by default, including those previously built for Foundry, and it supports `remappings.txt`
files by default.<Cite src="hardhat-foundry-compatibility" /> Tests are built as a separate build
process from contracts, and their artifacts are not exposed — they are considered internal and part
of `cache/`.<Cite src="hardhat-foundry-compatibility" />

### The boundary, named

Compatibility claims are only useful with an edge attached, and Hardhat publishes one: a reference
page of cheatcodes that are currently not supported.<Cite src="hardhat-unsupported-cheatcodes" /> The
groups on it are more informative than the individual names.

- **The broadcast family** — `broadcast`, `startBroadcast`, `stopBroadcast`,
  `broadcastRawTransaction`, `getBroadcast`, `getBroadcasts`, `getDeployment`, `getDeployments`,
  `deployCode`, `attachBlob`, and the artifact-path lookups.<Cite src="hardhat-unsupported-cheatcodes" />
  This is not a gap so much as a different answer to the same question: broadcasting is what
  [forge script](/c/forge-script) does, and Hardhat's answer to deployment is Ignition, further down
  this lesson.
- **EIP-7702 cheatcodes** — `attachDelegation`, `signDelegation`,
  `signAndAttachDelegation`.<Cite src="hardhat-unsupported-cheatcodes" /> If you are testing
  [delegation designator](/c/delegation-designator) behaviour, that work stays in forge today.
- **Key management** — `createWallet`, `deriveKey`, `getWallets`, `rememberKey`,
  `rememberKeys`.<Cite src="hardhat-unsupported-cheatcodes" />
- **Foundry version introspection and `breakpoint`.**<Cite src="hardhat-unsupported-cheatcodes" />

The practical consequence of that misconception being dead is that toolchain choice can no longer be
decided on the test-language axis. If someone in your team argues for Hardhat because the team knows
TypeScript, the argument does not survive contact with the current tool — and the last lesson in this
module is about which arguments do.

Two smaller first-party features round this out, both with direct Foundry analogues.
`--gas-stats` prints a per-contract table of min, average, median, max and call count per
function<Cite src="hardhat-gas-statistics" /> — the same shape as `forge test --gas-report`, and it
inherits the same caveat you already know, that the numbers describe your test suite's call
distribution rather than production.<Cite src="foundry-gas-tracking" /> `--snapshot` writes gas
snapshots and `--snapshot-check` compares against them and exits non-zero on a
change<Cite src="hardhat-gas-snapshots" />, which is `forge snapshot --check` under a different
flag.<Cite src="forge-snapshot-reference" /> One detail specific to Hardhat: function gas snapshots
are only written when all tests pass, while snapshot-cheatcode values are written even if some tests
fail.<Cite src="hardhat-gas-snapshots" />

## Two: chain types, which are not forks

This is the capability most often described incorrectly, so start from the documentation's own
framing. Hardhat 2's development network always behaved like Ethereum Mainnet; Hardhat 3 removes that
limitation and lets you choose which kind of chain to simulate, and configure several simulated
networks each with its own chain type.<Cite src="hardhat3-whats-new" />

A **Chain Type** classifies blockchains by behaviour: two chains have the same chain type if they
behave exactly the same. Ethereum mainnet and its testnets share one; Ethereum mainnet and Polygon
PoS do not.<Cite src="hardhat-multichain-support" /> Three are currently supported: `l1` for Ethereum
mainnet and its testnets, `op` for OP Stack chains, and `generic`, a permissive approximation
described as equivalent to how Hardhat 2 and other tools work.<Cite src="hardhat-multichain-support" />

What changes when EDR runs under a chain type is specific, and it is a list worth reading closely,
because it is the list of things a generic EVM simulator gets wrong: gas costs of certain opcodes,
new opcodes, new precompiles, predeployed contracts, how gas and L1 gas are handled, how some
JSON-RPC methods such as `eth_estimateGas` work, and the response formats of some JSON-RPC
methods.<Cite src="hardhat-multichain-support" />

You select one when creating a connection, or when running Solidity
tests:<Cite src="hardhat-multichain-support" />

```ts
import { network } from "hardhat";

const { viem } = await network.create({ network: "hardhatOp", chainType: "op" });
const publicClient = await viem.getPublicClient();
```

### Set this against multi-fork testing

You already know Foundry's answer to "does this work somewhere else": create a fork of a real chain
at a real block, and run against the state that was actually there, fetched lazily over
RPC.<Cite src="foundry-fork-testing" /> One fork is active at a time, and
[selecting between them](/c/multi-fork-testing) switches which state the EVM sees.<Cite src="foundry-cheatcode-create-select-fork" />

These are different tools for different questions, and neither subsumes the other.

**Subgoal — name what a fork gives you that a chain type does not.** Real state. The actual token
balances, the actual oracle price, the actual proxy implementation address at that block. If your
question is "does my integration with this specific deployed contract work", only a fork answers it.

**Subgoal — name what a chain type gives you that a fork does not.** Rule fidelity without a network.
A fork gives you an L2's *state*, but the EVM executing against it is still your local simulator with
its own opcode pricing and its own `eth_estimateGas`. If your question is "does my contract behave
correctly under this chain's rules", the chain type is what encodes the rules — including the
predeploys and the L1 gas handling that a plain fork will not model.

**Subgoal — notice the concurrency difference.** Foundry's forks are one-active-at-a-time within a
test. Hardhat's connections are independent objects, and a task can hold several
simultaneously.<Cite src="hardhat-network-manager" /><Cite src="hardhat3-whats-new" /> A test that
must observe two chains at once — a message sent on one and received on the other — is a
different shape of program, and that shape is what "multichain testing" actually refers to here.

## Three: build profiles

Hardhat 3 supports named build profiles that define different compilation settings for different
workflows.<Cite src="hardhat3-whats-new" /> They live under `solidity.profiles`, each profile taking
a normal Solidity configuration:<Cite src="hardhat-build-profiles" />

```ts
solidity: {
  profiles: {
    myProfile: {
      // normal Solidity config here
    },
  },
}
```

Two are predefined. `default` is used by most tasks when none is specified, with settings optimised
for development speed and experience; `production` is recommended for deployments, with the optimizer
and isolated builds enabled by default.<Cite src="hardhat-build-profiles" /> You select one with
`--build-profile`, as in `hardhat test --build-profile production`, and certain tasks pick one for
you — Ignition deployments use `production` automatically.<Cite src="hardhat-build-profiles" /><Cite src="hardhat-ignition-guide" />

The idea maps onto [Foundry profiles](/c/foundry-profiles), and the mapping is close enough to be
useful and different enough to be a trap.

<Cite src="foundry-config-overview" /><Cite src="hardhat-build-profiles" />

The consequential difference is the first row. A Foundry profile can change fuzz runs, RPC endpoints,
verbosity and remappings, because [every key belongs to a profile](/c/foundry-profiles). A Hardhat
build profile changes how the contracts are *built*. Fuzz settings, for example, live elsewhere —
under `test.solidity` in the configuration.<Cite src="hardhat-config-reference" /> If you are
translating a `[profile.ci]` block from a `foundry.toml`, expect it to land in more than one place.

The second row matters for CI design. An environment variable is set once for a whole job and applies
to everything in it; a flag is per-invocation. Neither is better, but a CI pipeline translated from
one to the other by pattern-matching will silently apply the wrong settings to some steps.

## Four: Ignition, and why it is not forge script

Ignition is a declarative system for deploying smart contracts. You define the contract instances you
want deployed along with operations to perform on them, grouped into Ignition Modules, which are then
analysed and executed — including sending independent transactions in parallel, recovering from
errors, and resuming interrupted deployments.<Cite src="hardhat-ignition-guide" /> The API is
unchanged from Hardhat 2, where it already existed.<Cite src="hardhat-ignition-guide" />

```ts
import { buildModule } from "@nomicfoundation/hardhat-ignition/modules";

export default buildModule("CounterModule", (m) => {
  const counter = m.contract("Counter");
  m.call(counter, "incBy", [5n]);
  return { counter };
});
```

Defining a module does not run the deployment — it declares how the deployment should look, and
Ignition creates a plan to execute every action in the right order.<Cite src="hardhat-ignition-guide" />
Results are stored under `ignition/deployments/chain-<id>`, and the documentation recommends
committing those directories so deployments are versioned and
reproducible.<Cite src="hardhat-ignition-guide" />

### The reconciliation walk-through

This is the part that makes the model click, and it is a three-step worked example.

**Subgoal — establish the baseline.** Run `hardhat ignition deploy ignition/modules/Counter.ts
--network sepolia`. Ignition deploys `Counter` and sends the `incBy(5)` call, recording what happened
under `ignition/deployments/chain-11155111`.<Cite src="hardhat-ignition-guide" />

**Subgoal — change the description, not the procedure.** Add one line to the module —
`m.call(counter, "inc")` — and run the exact same command again.

**Subgoal — observe what it does *not* do.** It does not redeploy `Counter` and does not re-send
`incBy(5)`. It compares the described desired state against the recorded deployment and executes only
the single missing transaction.<Cite src="hardhat-ignition-guide" />

Now hold that against the model you know. `forge script` is an imperative Solidity program: it runs
top to bottom in a simulation, then broadcasts the transactions it
collected.<Cite src="forge-script-reference" /><Cite src="foundry-deploying" /> Its record of what
happened is the [broadcast artifacts](/c/broadcast-artifacts) it writes on the way, and its recovery
mechanism is `--resume`, which continues from those artifacts. Re-running the same script without
`--resume` runs the program again, from the top, doing whatever the program says — because the script
is a procedure, not a description.

<Misconception
  belief="Ignition is forge script with different syntax."
  reality="forge script is an imperative program that recovers by replaying broadcast artifacts. Ignition is a declaration of desired state that is reconciled against what is already deployed, so re-running it converges rather than repeats."
  why="Both are 'the deployment thing' in their toolchain, and both produce on-disk records that get committed. The similarity of the artefacts hides a difference in execution model — and therefore a difference in failure modes."
  src="hardhat-ignition-guide"
/>

The failure modes differ in the way the execution models predict. An imperative script that dies
halfway has sent some transactions and not others, and recovery means telling the tool to continue
from its own log. A declarative module that dies halfway has a partially satisfied description, and
recovery means running the same command again and letting it work out what is missing. The
imperative model gives you exact control over ordering and arbitrary computation between steps; the
declarative model gives you idempotence and parallelism across independent branches. Ignition's
documentation lists what falls out of that: recovering from several classes of network error, bumping
gas for stuck transactions, detecting dropped transactions, and recovering from nonce
issues.<Cite src="hardhat-ignition-guide" />

Neither is strictly better. The question they answer differently is "what happens when I run this
twice", and knowing which model you are looking at is the difference between an idempotent operation
and a duplicate deployment.

<Check type="explain" concept="hardhat3-multichain">
Your protocol will be deployed to Ethereum mainnet and to an OP Stack rollup. Two things worry you:
that a gas-sensitive code path behaves differently under the rollup's rules, and that your integration
with an already-deployed lending market on the rollup breaks. Which tool answers which worry, and
what would you be fooling yourself about if you used only one?

<Answer>
**The chain-type simulation answers the first worry.** Running the Solidity tests against an
`op` chain type makes EDR mimic that chain's behaviour — including opcode gas costs, added opcodes and
precompiles, predeployed contracts, and how L1 gas is handled.<Cite src="hardhat-multichain-support" />
A gas-sensitive path that assumes mainnet pricing shows up here. It would not show up under a generic
EVM simulation, which is exactly what `generic` is documented as being: a permissive approximation
equivalent to how Hardhat 2 and other tools work.<Cite src="hardhat-multichain-support" />

**A fork answers the second worry.** The lending market's real state — its current parameters,
balances, implementation address, oracle readings — exists only on the chain, and fork testing pulls
that state lazily at a pinned block.<Cite src="foundry-fork-testing" /> No amount of rule fidelity
substitutes for it, because a simulator with perfect rules and empty state has nothing to integrate
with.

**What each one alone would let you fool yourself about.** Chain type only: you would have correct
rules over invented state, so every integration assumption you wrote into a mock stays unfalsified —
the classic failure where the mock is a restatement of your beliefs about the counterparty. Fork
only: you would have real state executed under the wrong rules, so a path that is affordable in your
simulator can be priced differently on the target chain, and estimates derived from the fork can
disagree with the chain's own `eth_estimateGas`.<Cite src="hardhat-multichain-support" />

The generalisable point, and the reason this pair is worth internalising: a simulation has two
independent axes of fidelity — the rules and the state — and every EVM testing tool is strong on one
of them. Ask which axis your specific worry lives on before choosing where to write the test.
</Answer>
</Check>

## What this unlocks

You now have the capability map, which is what the last two lessons stand on. The fourth lesson makes
you fluent in the layout — where the files are, and the specific way the two toolchains can disagree
about which file an import names. The fifth turns this list into conditions: three of the four
capabilities here are things a Foundry project can live without, and one of them — the TypeScript
integration surface that these connections and this test runner exist to serve — is where the
justification for a second toolchain actually comes from.<Cite src="hardhat-home" />

Two forward-looking notes. Hardhat tracks upcoming forks quickly, and recent 3.x releases carry
experimental support for the Amsterdam EVM version.<Cite src="hardhat-330-release" /><Cite src="npm-hardhat-registry" />
And the sample project the initializer produces already contains all four capabilities in miniature —
`contracts/Counter.t.sol`, `test/Counter.ts`, `ignition/modules/Counter.ts` and a script that sends an
OP transaction — which makes `npx hardhat --init` the fastest way to see this lesson as running
code.<Cite src="hardhat-getting-started" />
