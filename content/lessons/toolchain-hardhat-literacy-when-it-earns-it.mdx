Someone on your team says: "Should we add Hardhat?" What follows is usually a conversation about
preferences — which language people like, which tool feels faster, what the last place they worked
used. It does not converge, because none of the statements in it are checkable.

The version that converges asks something else: **what would have to be true of this project for a
second toolchain to be worth its maintenance cost?** That is answerable, the answers are few, and each
leaves evidence in the repository. This lesson is that list, the reasons that do not qualify, and —
where the answer is yes — how the two are divided and what the arrangement costs to keep honest.

## Four conditions, each with its evidence

Hardhat is justified by **coupling**, not by preference. The coupling is always between the contract
system and TypeScript, and it takes four recognisable shapes.

**Condition one: types are shared between contracts and an application.** Hardhat 3 generates
TypeScript declarations so artifacts are typed by default, and plugins can derive contract type
information from them.<Cite src="hardhat3-whats-new" /> If a frontend or backend consumes ABIs and
you want a compile error when a function signature changes rather than a runtime failure in
production, that pipeline lives naturally in the same repository as the contracts. *Evidence it
applies:* a `packages/` directory with a web app that imports generated types; a build step that
copies ABIs somewhere and casts them.

**Condition two: integration tests must drive application code and contracts together.** The
documentation's own division is TypeScript for integration tests that need a full network, or custom
scripts in a full-featured language, with Solidity for fast unit
tests.<Cite src="hardhat-migrate-from-foundry" /> A test that has to exercise your indexer, your API's
signature-verification path, and a contract call in one flow cannot be a Solidity test, because
[Solidity tests run inside the EVM](/c/tests-in-solidity) and your application does not. *Evidence it
applies:* tests today that mock the contract layer, in order to test the part that talks to it.

**Condition three: the project lives inside an existing TypeScript monorepo.** Hardhat 3 states
native monorepo support and full npm support, including transitive dependencies at incompatible
versions handled automatically.<Cite src="hardhat-dependencies-guide" /> A contracts package that is
one workspace among fifteen, sharing a lockfile, a CI pipeline and a release process, pays a real
tax for being the one package that resolves dependencies through git submodules instead. *Evidence it
applies:* a workspace manifest at the root that already lists the contracts directory.

**Condition four: a required plugin exists only for Hardhat.** OpenZeppelin's upgrades plugin is the
standard example — a maintained tool for validating storage-layout compatibility across an upgrade,
distributed as a Hardhat plugin with its own Hardhat 3 major
version.<Cite src="oz-migrate-from-hardhat2" /> If your governance process depends on a specific
tool's output, the tool's packaging constrains your toolchain. *Evidence it applies:* name the plugin,
then check for a Foundry equivalent — for this particular case one exists, which is why "a plugin
requires it" must be checked rather than assumed.

Any one of these makes the second dependency tree worth its cost. The useful property of all four is
that they are *observable*: you can look at a repository and say whether they hold, which is exactly
what a preference cannot do.

## Three reasons that do not qualify

**"The team knows JavaScript, not Solidity."** This was decisive for Hardhat 2 and is dead for
Hardhat 3, which runs Solidity tests as a built-in feature needing no plugin, and whose own
documentation recommends writing fast Solidity unit tests for contract logic.<Cite src="hardhat-solidity-tests-guide" /><Cite src="hardhat-migrate-from-foundry" />
Choosing a toolchain on the test-language axis is choosing on an axis that no longer separates the
two tools. It also does not survive its own logic: whoever writes the contracts is writing Solidity
regardless, and untested Solidity written by people who avoid Solidity is a worse outcome than either
toolchain.

**"Hardhat is faster now" or "Foundry is much faster".** No multiplier is publishable here. The
simulation layer is Rust and has been since EDR shipped in Hardhat
v2.21.0<Cite src="nomic-rust-hardhat" />, which kills the old reputation-based argument — but the
replacement figures circulating in vendor posts and comparison articles disagree with each other and
none of the ones surveyed for this module published an inspectable methodology. The measurable form of
the question is your suite on your hardware, and even then the number is dominated by suite shape
rather than by the interpreter. A toolchain decision resting on an unsourced ratio is resting on
nothing.

**"Ignition is a better deployment model."** It is a *different* model — declarative reconciliation
against recorded state, against `forge script`'s imperative program plus broadcast
artifacts.<Cite src="hardhat-ignition-guide" /><Cite src="forge-script-reference" /> Preferring
idempotence over procedural control is legitimate, but it is a preference about one subsystem, and it
does not by itself pay for a second dependency tree, configuration language, artifact directory and
resolver.

## Absent the coupling, Foundry is the default

Not because it is better in the abstract, but because of what a second toolchain costs and what the
first one already covers.

Solidity tests execute inside the EVM in the forge process, with no serialisation boundary between
the assertion and the code under test, which is what makes them fast enough to fuzz and what lets
them reach EVM-level state directly.<Cite src="foundry-writing-tests" /> Fuzzing and
[invariant testing](/c/invariant) are in the box.<Cite src="foundry-invariant-testing" /> The
cheatcode surface reaches storage, revert data and gas accounting
directly.<Cite src="foundry-cheatcodes-overview" /> And parts of that surface have no Hardhat
equivalent today: the entire broadcast family, the EIP-7702 delegation cheatcodes, and the key
management cheatcodes are on Hardhat's published unsupported
list.<Cite src="hardhat-unsupported-cheatcodes" />

Against that, a second toolchain is an ongoing obligation, not a one-time setup: a Node runtime whose
support policy tracks Node's own release cadence<Cite src="hardhat-nodejs-support" />, a dependency
tree with a lockfile and a vulnerability feed, a configuration file that is a program, and a stability
policy that explicitly does not follow semver strictly and permits breaking changes in minor
versions.<Cite src="hardhat-stability-guarantees" /> Every one of those is paid by everyone who joins
the project.

## Running both, deliberately

The division that works is by strength, and it is close to what Hardhat's own material proposes:
Solidity tests for contract logic, TypeScript for integration against a full network and for custom
scripting.<Cite src="hardhat-migrate-from-foundry" /> In practice:

- **Foundry** — unit tests, fuzz campaigns, invariant campaigns, gas snapshots, and anything using a
  cheatcode Hardhat does not support.<Cite src="foundry-invariant-testing" /><Cite src="hardhat-unsupported-cheatcodes" />
- **Hardhat** — TypeScript integration tests, typed artifacts consumed by an application, Ignition
  deployments if you want reconciliation, and plugins with no Foundry
  equivalent.<Cite src="hardhat3-whats-new" /><Cite src="hardhat-ignition-guide" />

This is a supported arrangement, not a workaround. Hardhat 3 supports `remappings.txt` by default,
loading them from the project and from npm packages; it can run Solidity tests previously built for
Foundry; and it supports git submodule dependencies alongside
npm.<Cite src="hardhat-foundry-compatibility" /><Cite src="hardhat-dependencies-guide" />

### Four guardrails, because the costs are specific

**One source of truth for the compiler.** Two configuration files each pin a solc version and
optimizer settings, and nothing keeps them in sync. Ignition sharpens this by building deployments
with the `production` build profile automatically, which enables the optimizer and isolated builds by
default — so the artifact you deploy may not be built the way the artifact you tested
was.<Cite src="hardhat-build-profiles" /><Cite src="hardhat-ignition-guide" /> Pick one file as
authoritative, derive or manually mirror the other, and put a CI check on the pair.

**One source of truth for dependencies.** The previous lesson's failure mode — the same import string
resolving to a `lib/` submodule under forge and to `node_modules` under Hardhat — is created by having
two. Choose npm or submodules for the shared dependencies and make the other toolchain read the same
files.<Cite src="hardhat-remappings-guide" /><Cite src="hardhat-dependencies-guide" />

**A CI job that compares artifacts, not just a CI job per toolchain.** Two green suites over two
different bytecodes is a state this arrangement produces naturally. The check that catches it
compiles one shipped contract under each toolchain and diffs the compiler settings and the
bytecode.<Cite src="foundry-ci" />

**A written division, in the repository.** Not a preference; a rule of the form "contract-level
behaviour is tested in Solidity under forge, application-level flows in TypeScript under Hardhat".
Without it, both suites slowly grow copies of the same tests, and the cost doubles while the benefit
stays flat.

<Aside kind="warn">
Read vendor comparisons as vendor comparisons. Hardhat's migration guide opens by describing Hardhat 3
as a full replacement for Foundry.<Cite src="hardhat-migrate-from-foundry" /> The compatibility work
behind that sentence is real and documented — Solidity tests, `remappings.txt`, Foundry-shaped
layouts.<Cite src="hardhat-foundry-compatibility" /> The counter-evidence is published by the same
project on a different page: a list of cheatcodes that are not supported, including the whole
broadcast family and the EIP-7702 cheatcodes.<Cite src="hardhat-unsupported-cheatcodes" /> Both pages
are accurate; only one is a headline. The habit worth keeping is to look for the compatibility
project's own exceptions page before quoting its summary.
</Aside>

## The decision, as a procedure

1. Name a coupling condition that holds today, with the evidence in the repository. If you cannot
   name one, the answer is Foundry alone, and revisit when one appears.
2. If one holds, decide what moves and what does not. The default division above is a starting point,
   not a law.
3. Write down the two guardrails that cost nothing to set up and everything to retrofit: one
   authoritative compiler configuration, one dependency source.
4. Set a review date. Coupling conditions expire — a monorepo splits, a plugin gains a Foundry
   equivalent. A toolchain kept for a reason that no longer holds is pure cost.

## Where this leaves you

You can read a Hardhat repository, date it, translate its layout, predict where its resolver and
Foundry's will disagree, and make the adoption decision on conditions instead of preferences. That is
literacy in the sense this module meant it: the ability to review work done with the tool.

One durable caveat. This module's most useful facts are also its most volatile: version numbers, the
chain-type list, the end-of-life policy for Hardhat
2.<Cite src="hardhat-2-eol" /><Cite src="hardhat-stability-guarantees" /> Everything with a number
attached carries a verification date for that reason. The stable part is the shape — one toolchain is
configured and one is programmed, one merges remappings globally and one scopes them by directory, one
deployment model is imperative and one reconciles. Shapes are what let you read the next release's
notes in ten minutes instead of relearning the tool.

The module's reflection prompt asks for the memo a team would need to decide. Write it with conditions
in it; conditions outlive versions. The security track picks up next, where both toolchains reappear —
as the thing that runs your fuzzers, and as one more dependency tree with a supply chain of its
own.<Cite src="measured-forge-1-7-1" />
