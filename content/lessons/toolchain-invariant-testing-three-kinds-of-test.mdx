Three tests, all green:

```text
Ran 3 tests for test/Unit.t.sol:UnitTest
[PASS] testFuzz_depositThenWithdrawAllIsWhole(uint256) (runs: 256, μ: 78427, ~: 77931)
[PASS] test_depositMintsSharesAtPar() (gas: 93653)
[PASS] test_depositThenWithdrawAllIsWhole() (gas: 78667)

```

Two example-based tests and one property test at 256 randomised runs, the default on forge
1.7.1.<Cite src="measured-forge-1-7-1" /><Cite src="foundry-testing-config" /> The contract under
test is a share-based vault. It can be emptied in two calls, and the second of those two calls is
`withdraw`, which is the function the fuzz test just exercised 256 times.

This lesson is about why that happens, and about the third engine — the one that finds it in 1.3
seconds.<Cite src="measured-forge-1-7-1" />

<Aside kind="note">
Read the fuzz line carefully, because it invites a wrong inference. `runs: 256` is the sample count,
the default for `[fuzz]` on forge 1.7.1.<Cite src="measured-forge-1-7-1" /><Cite src="foundry-testing-config" />
`μ` and `~` are the **mean and median gas** across those runs. Neither is a confidence measure. The
line contains no information about how much of the input space was covered, and none at all about
how much of the *state* space was.
</Aside>

## The contract

Nothing exotic. Deposit assets, receive shares; burn shares, receive assets back pro rata. You have
seen this shape in [ERC-4626](/c/erc-4626-vault).

```solidity
function withdraw(uint256 s) external returns (uint256 a) {
    require(s > 0 && shares[msg.sender] >= s, "SHARES");
    shares[msg.sender] -= s;
    totalShares -= s;                                     // burned first
    a = totalShares == 0 ? totalAssets() : s * totalAssets() / totalShares;
    asset.transfer(msg.sender, a);
}
```

The payout is computed **after** the burn. `totalShares` in the denominator is already the
post-burn number, so the rate the withdrawer is paid at is not the rate the vault was holding when
they asked. Redeem half the outstanding shares and you are paid `s * A / (S - s)` instead of
`s * A / S` — for `s = S/2`, that is the entire pool.

Now look again at the three tests and ask what each one could have seen.

**`test_depositMintsSharesAtPar`** never calls `withdraw`. It cannot see this.

**`test_depositThenWithdrawAllIsWhole`** deposits and then withdraws *everything*. With every share
burned, `totalShares` hits zero, the ternary takes its other branch, and the withdrawer is paid
`totalAssets()`. Which is correct. The one sequence a person naturally writes down is the one
sequence in which the bug is invisible.

**`testFuzz_depositThenWithdrawAllIsWhole`** is the same sequence with the amount randomised 256
times. Randomising the *amount* does not help, because the defect is not in the amount. It is in the
relationship between two calls, and that relationship was fixed by the author before the fuzzer ever
ran.

## Three shapes, not three intensities

It helps to think of the thing being searched as a space with two axes: the *state* the contract is
in, and the *input* to the next call.

**A unit test is a point.** One starting state, fixed by `setUp` and by whatever the test body does
first; one input; one path. Everything about it is chosen by the author. Its value is that it is
exact, cheap, and readable as documentation — and its ceiling is that it can only ever confirm what
somebody already suspected.

**A stateless fuzz test is a line.** The starting state is still fixed — every run begins from the
post-`setUp` state, because `setUp()` runs before each test<Cite src="foundry-forge-testing" /> —
and the author still fixes the call sequence. What varies is the arguments, drawn 256 times by
default from a weighted dictionary rather than uniformly.<Cite src="foundry-testing-config" /> You
have seen this engine in [stateless fuzzing](/c/stateless-fuzzing) and
[property-vs-example testing](/c/property-vs-example-testing).

**An invariant test is a region.** The author fixes neither the state nor the sequence. Forge
generates a random sequence of calls, executing them one after another against state that carries
over, and re-evaluates the property after each call.<Cite src="foundry-invariant-guide" /> The bug
above lives at a coordinate no line through the author's chosen sequence passes through, which is
exactly why two engines missed it and one did not.

That is the whole argument for the technique. It is not that invariant testing tries harder. It is
that it searches a differently-shaped set.

## What "stateful" buys, mechanically

The Foundry documentation's own one-line description is precise: invariant testing verifies
properties that should always hold regardless of the sequence of actions taken, by running random
sequences of function calls and checking invariants after each call.<Cite src="foundry-invariant-guide" />
Unpack the three commitments in that sentence.

**State carries over inside a run.** Call three sees whatever calls one and two did. A run is
therefore a walk away from the post-`setUp` state, and depth-N states are reachable only by walking
there. This is the property the concept [stateful fuzzing](/c/stateful-fuzzing) names, and it is the
entire difference from the stateless engine.

**Each run starts fresh.** Runs are independent; the walk restarts from post-`setUp` state each
time. Two runs do not compose into a longer sequence.

**The property is checked after every call, not at the end.** So a violation is reported *with the
call sequence that produced it*, not merely as a final assertion failure — which is what makes the
output actionable. Forge also shrinks that sequence before reporting it, within `shrink_run_limit`,
5000 by default on 1.7.1.<Cite src="measured-forge-1-7-1" /><Cite src="foundry-testing-config" />

There is a second hook for the cases where per-call checking is wasteful. `afterInvariant()` runs
once against the final state of a run, after the per-call invariant checks pass; it must have exactly
that signature, a test contract may define only one, and state changes it makes are not
persisted.<Cite src="foundry-invariant-guide" /> Use `invariant_*` for what must hold throughout a
sequence and `afterInvariant()` for aggregate end-of-run checks that would be expensive to evaluate
500 times.<Cite src="foundry-invariant-guide" />

## The budget is two numbers, and only one of them was the problem

A campaign is bounded by `runs` — how many independent sequences — and `depth` — how many calls
inside each one. On forge 1.7.1, `forge config` reports `[invariant] runs = 256` and
`depth = 500`.<Cite src="measured-forge-1-7-1" /> Multiply them and you get the call budget: 128,000
calls per invariant function, which is exactly the number the campaign reports on its result line.

Both keys live under `[invariant]` in `foundry.toml`, separately from the `[fuzz]` block that
configures the stateless engine, and both are overridable per profile or by environment variable —
`FOUNDRY_INVARIANT_RUNS`, `FOUNDRY_INVARIANT_DEPTH`.<Cite src="foundry-testing-config" /><Cite src="rareskills-invariant-testing" />
That the two engines have separate `runs` keys with the same name and the same default of 256 is a
reliable source of confusion in code review.<Cite src="measured-forge-1-7-1" />

Here is the same buggy vault under two budgets that cost about the same wall-clock second, measured
on forge 1.7.1 with solc 0.8.36:<Cite src="measured-forge-1-7-1" /><Cite src="solidity-0836-release" />

```text
runs = 10000, depth = 1
[PASS] invariant_assetsCoverShares() (runs: 10000, calls: 10000, reverts: 0)
finished in 2.29s

runs = 10, depth = 500
[FAIL: assertion failed: 29758432588712463233747 < 43293230703712199788668]
	[Sequence] (original: 2, shrunk: 2)
finished in 1.33s
```

Ten thousand sequences found nothing. Ten found the bug. The reason is structural: at depth 1 every
sequence is a single call from an empty vault, and there is no single call from an empty vault that
breaks this property. No number of runs reaches a state that requires two calls to construct.

Two things follow, and both are worth internalising before you ever tune a campaign.

**`runs` and `depth` are not interchangeable, and `runs` is the one people raise.** It is the number
printed on the pass line, it appears in every published CI snippet, and raising it makes the run
take visibly longer — which feels like more thoroughness.

**Depth is what reaches states.** Runs vary the *path* to a state; depth determines which states are
reachable at all. A bug that needs a fifty-call setup is invisible at depth ten no matter what you
spend on runs.

## What each engine can and cannot reach

Lay the four engines out by what each one varies and what it therefore cannot reach.

| Engine | Varies | Cannot reach |
|---|---|---|
| Unit test | nothing | anything you did not already suspect |
| Stateless fuzz | arguments of a fixed sequence | any bug requiring a sequence you did not write |
| Invariant campaign | the sequence, the arguments and the caller | anything outside `runs × depth`, and anything your handler cannot construct |
| Symbolic (`check*`/`prove*`) | inputs symbolically, within configured bounds | anything outside the modelled EVM surface and the bounds |

The fourth row is there so the third does not read as the top of a ladder. Forge ships a symbolic
path in-tree: `check*` and `prove*` functions, discovered only when symbolic mode is enabled, and
under `--symbolic` your `invariant*` and `statefulFuzz*` functions are explored as bounded symbolic
call sequences instead of by the fuzzer.<Cite src="foundry-forge-testing" /> The documentation
describes symbolic testing as an MVP whose modelled EVM surface, configuration and reporting are
still expected to evolve.<Cite src="foundry-forge-testing" /> Treat it as an additional engine with
its own bounds, not as a proof machine that retires the campaign.

<Misconception
  belief="A passing invariant campaign proves the property holds."
  reality="It failed to find a counterexample inside runs × depth, from one seed, restricted to whatever calls your handler can make. That is evidence at a budget."
  why="The pass line is typographically identical to a unit test's pass line, and carries no confidence qualifier."
  src="foundry-testing-config"
/>

That misconception is the one worth carrying out of this lesson, because the failure mode it
produces is silent. The campaign above passed at ten thousand runs against a vault that can be
drained. Nothing in the output said so.

## Naming and discovery

Forge finds tests by function-name prefix, not by annotation. For this engine the prefixes are
`invariant*` and `statefulFuzz*`;<Cite src="foundry-forge-testing" /> the two are interchangeable,
and `statefulFuzz` is the more honest name for what actually runs. Targets are declared in `setUp`
with `targetContract(address)`.<Cite src="foundry-invariant-guide" /><Cite src="foundry-invariant-testing" />

The invariant function itself is an ordinary Solidity function, usually `view`, holding one
assertion:

```solidity
function invariant_assetsCoverShares() public view {
    assertGe(vault.totalAssets(), vault.totalShares());
}
```

That is the whole interface. Everything hard about this technique is on the other side of it: what
you assert, and what calls the campaign is able to make. Those are the next two lessons.

One operational note before you run one. Campaigns are slow relative to unit tests — a default-budget
campaign against a trivial vault took between one and twenty-seven seconds in the measurements above,
depending entirely on how much work the calls actually did — so you will want to run them
selectively. `--match-contract` and the other `--match-*` filters are the ordinary way to do
that,<Cite src="forge-test-reference" /><Cite src="foundry-forge-testing" /> and the same filters are
what a CI job uses to split a fast pull-request gate from a long scheduled run. That split is a
Track 05 CI topic; what matters here is that the campaign's cost is a function of how much of the
budget it spends on real execution, which is the subject of lesson three.

<Check type="predict" concept="unit-vs-fuzz-vs-invariant">
A team has 340 unit tests at 96% line coverage and a dozen `testFuzz_` tests at 10,000 runs each. An
auditor reports a bug that requires `borrow` → oracle price move → `liquidate` → `repay`, in that
order, with the repay amount just under a rounding boundary.

Their engineering lead argues the fuzz suite should have found it, since 10,000 runs over the repay
amount would certainly have hit the boundary. Say precisely why that reasoning fails, and what the
smallest change to the suite would be.

<Answer>
**The fuzzer would have hit the boundary value. It would never have been in the state where the
boundary matters.**

Separate the two things the lead is conflating. The rounding boundary lives in the *input* space, and
10,000 draws over a bounded amount will very likely hit it — the fuzzer's dictionary is weighted
toward boundary values, not uniform.<Cite src="foundry-testing-config" /> The four-call ordering
lives in the *state* space, and a stateless fuzz test starts every run from the same post-`setUp`
state.<Cite src="foundry-forge-testing" /> Unless somebody wrote out that exact four-call sequence in
a test body, no draw over the repay amount was ever evaluated against a position that had been
borrowed against, revalued, and partially liquidated.

**Coverage does not rescue this either.** 96% line coverage says every line of `repay` executed. It
says nothing about which *states* it executed from, and this bug is a property of the state, not of
the line.

**The smallest change is one invariant function and one handler**, not a new suite. The invariant
would be a per-position solvency statement — debt owed never exceeds collateral value plus the
protocol's tolerated bad debt — and the handler would expose `borrow`, `liquidate`, `repay` and an
oracle move as four callable actions. The campaign then constructs the ordering itself. Note the
budget it needs: this bug is at depth 4, so it is reachable at the default `depth = 500`, and would
have been invisible at `depth = 2` no matter how many runs were bought.<Cite src="measured-forge-1-7-1" />

**One honest caveat.** Adding those four actions to a handler does not guarantee discovery. It makes
discovery possible. Whether the campaign finds it depends on the seed, the bounds the handler
imposes, and whether the oracle action can actually produce the price move the exploit needs —
which is the subject of lesson three.
</Answer>
</Check>

## Where this pays off

**The next lesson** is about the assertion, not the engine. Writing the property is the part teams
get wrong first: they either restate what the code does, in which case the campaign tests the
compiler, or they write something so weak it cannot fail. Solvency — assets held are at least
liabilities owed — is the first invariant worth writing for anything that custodies value, and it is
also the one that maps most directly onto what an attacker is trying to achieve.

**The lesson after that** is about the calls. A campaign pointed at a raw contract spends its entire
budget on calls that revert on unmet preconditions, passes, and tells you nothing — and the numbers
that would have revealed it are printed right next to the pass line, where nobody reads them.

**Security work in Track 06** treats invariants as the artefact that outlives the test run: the same
predicate becomes an on-chain monitor, an audit's scope statement, and the specification a formal
verification tool is pointed at. Writing them down is not a testing chore. It is the first time most
teams state what their system actually guarantees.
