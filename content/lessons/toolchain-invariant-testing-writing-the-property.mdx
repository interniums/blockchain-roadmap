A team is asked, in a design review, what must always be true of their lending market. The
whiteboard fills up:

1. `borrow` reverts if the position would end up under-collateralised.
2. Only the timelock can change the interest rate model.
3. Liquidators receive a 5% bonus.
4. The sum of all `debt[user]` equals `totalDebt`.
5. No position with a health factor above 1 can be liquidated.

Five sentences, all true of the code, and only two of them are invariants. This lesson is about
telling those two apart from the rest, and about which one to write first.

## An invariant is a claim about state, not about a call

Sort the list by asking one question of each line: *is this a property of the system's state, or a
description of what a function does?*

Lines 1, 3 and 5 describe **function behaviour**. They are unit-test material. Each names a specific
entry point and says what happens when you call it. You cannot check "borrow reverts under X" by
looking at storage; you have to make a call and observe the outcome.

Lines 2 and 4 are different. Line 4 — the sum of all `debt[user]` equals `totalDebt` — is a
predicate you can evaluate against the contract's storage at any moment, without calling anything.
Line 2, restated as a state property, becomes "the address holding the rate-setter role is the
timelock", which is also evaluable from storage alone.

That is the working definition. An invariant is a predicate over contract state that must be true
after every valid operation, no matter what came before.<Cite src="foundry-invariant-guide" /> Forge
re-evaluates each `invariant*` function after each call in a sequence, so it is checked against
storage, not against a return value.<Cite src="foundry-invariant-guide" /><Cite src="foundry-invariant-testing" />
Sequences are generated at the campaign's configured budget — 256 runs of 500 calls by default on
forge 1.7.1 — so each invariant function is evaluated 128,000 times in a default
run.<Cite src="measured-forge-1-7-1" /><Cite src="foundry-testing-config" />

Cyfrin's framing is the same and gives three examples worth having as calibration: the number of
votes cast must not exceed the number of registered voters; a user should never be able to withdraw
more money than they deposited; there can only be one winner of the fair
lottery.<Cite src="cyfrin-fuzz-guide" /> Notice what those share. Each is a sentence about the world
the contract models, not about the contract's API. Each would still be a sensible requirement if you
rewrote the implementation from scratch.

## The three questions

Before writing one, put a candidate through three filters.

**Is it evaluable from state alone?** If checking it requires making a call, it is a test, not an
invariant. "The withdrawal fee is 30 basis points" passes; "withdrawing charges 30 basis points"
does not.

**Does it hold after every valid operation, in every order?** Not "usually", not "once initialised".
If there is a legitimate window in which it is false — mid-migration, before the first deposit, while
a batch is processing — then either the invariant needs that exception written into it, or the design
has a state nobody has thought about. The second discovery is the more valuable one.

**Would an attacker want it false?** This filter separates useful invariants from merely true ones.
`totalSupply >= 0` on a `uint256` holds after every operation and is worth nothing. A property whose
violation is the attacker's goal is a property whose violation is worth searching for.

RareSkills draws the same line against unit tests: unit tests verify specific behaviour, while
invariants say something about the system as a whole.<Cite src="rareskills-invariant-testing" /> Their
worked example is the ERC-20 one everybody reaches for — the sum of all balances equals total
supply<Cite src="rareskills-invariant-testing" /> — which is a *conservation* statement, one of six
recognisable families.

## Six families, and where each one bites

Foundry's guide lists the families directly. They are worth memorising, because most real invariants
are an instance of one of them wearing domain clothes.<Cite src="foundry-invariant-guide" />

Line 4 from the whiteboard is state consistency. Line 2 is access control. Neither is solvency, and
that is the gap worth closing first.<Cite src="foundry-invariant-guide" />

## Why solvency is the first one to write

`assets >= liabilities`, or equivalently "total claimable never exceeds total held", is the
highest-value first invariant for anything that custodies value. Three reasons, in order of how much
they matter.

**It is what the attacker is trying to break.** Every drain and every rounding exploit ends in the
same place: somebody's claim exceeds what backs it. The mechanisms differ enormously; the terminal
state does not. A property sitting on the terminal state is mechanism-agnostic, which is what you
want from an automated search — you are not required to have anticipated the attack.

**Both sides are usually already tracked.** A vault knows `totalAssets()` and `totalShares`; a
lending market knows its reserves and `totalDebt`. You are rarely inventing accounting to state
solvency, only writing down a relationship between two numbers the contract already maintains.

**It catches arithmetic no per-function test will.** A unit test of `withdraw` asserts that
`withdraw` behaves. Solvency asserts that the *set* of deposits, withdrawals, transfers and fee
accruals composes into a consistent ledger — a claim about interactions, and therefore unreachable
from any single-function test.

Foundry's own basic example is a solvency check —
`assertGe(address(vault).balance, vault.totalDeposits())` — and it is the first invariant in the
guide for the same reason it should be the first in your repo.<Cite src="foundry-invariant-guide" />

## Worked example: deriving the invariant for a share-based vault

Take the vault from the previous lesson: deposit assets, receive shares; burn shares, receive assets.
The naive first attempt is to write `assertEq` between what the vault says it holds and what it
actually holds, which turns out to assert nothing. Here is the derivation that produces something
better.

**Subgoal: name the liability precisely.** What does the vault owe, and to whom? Not "the deposits" —
depositors hold shares, and a share is a claim on a fraction of the pool, not on a fixed amount. The
liability is `totalShares` claims, each worth `totalAssets() / totalShares` of the asset. Writing this
down is already useful: it says the vault cannot become insolvent by the pool shrinking, because the
claims shrink with it. Whatever breaks solvency here has to break the *relationship*, not the level.

**Subgoal: name the asset side, and notice who can move it.** `totalAssets()` in this vault reads
`asset.balanceOf(address(this))`, which means anyone holding the asset can change it with a plain
transfer — the donation surface you met in the
[inflation attack](/c/inflation-first-depositor-attack).<Cite src="oz-erc4626-inflation-defense" />
For the invariant, that matters in a specific way: the asset side can be increased by an outsider at
any time, so any invariant of the form "assets equal exactly X" is falsifiable by a stranger with a
dollar. The inequality has to be one-sided.

**Subgoal: find the unit both sides share.** Assets and shares are different units, so `assets >=
liabilities` needs a conversion, and a conversion needs a rate — which is the thing under
test.<Cite src="eip-4626" /> That circularity is the trap. Break it by finding a rate-independent
statement instead.

**Subgoal: establish a floor that the correct implementation cannot cross.** The first deposit into
an empty vault mints one share per asset, so the rate starts at exactly 1. Every subsequent operation
rounds in the vault's favour: `deposit` mints `assets * S / A` shares with floor division, and
`withdraw` pays out `s * A / S` assets with floor division.<Cite src="oz-erc4626-docs" /> Both floors
leave the remainder in the pool, so assets per share is non-decreasing across every valid operation,
and a donation can only raise it further.<Cite src="oz-erc4626-inflation-defense" /> Therefore, on a
correct implementation:

```solidity
function invariant_assetsCoverShares() public view {
    assertGe(vault.totalAssets(), vault.totalShares());
}
```

**Subgoal: check it is not vacuous.** Does anything the contract does bring the two numbers close
together? Yes — `withdraw` removes assets and burns shares in a fixed ratio, so the two sides track
each other and the margin stays thin. That is what you want. An invariant with an enormous slack term
passes for reasons unrelated to correctness.

Against the buggy vault from the previous lesson — the one that burns shares before reading the rate
— this property fails, and forge reports the shrunk two-call sequence that produced
it.<Cite src="measured-forge-1-7-1" /> Against the corrected vault it holds across all 128,000 calls
of a default-budget campaign.<Cite src="measured-forge-1-7-1" /><Cite src="foundry-testing-config" />

<Aside kind="warn">
Note what the derivation depended on: the vault mints one share per asset at par into an empty
vault, and rounds down in both directions. Those are facts about *this* implementation. Change the
rounding direction on one side and the invariant is no longer valid — it will fail on correct code,
which is worse than useless because it trains the team to ignore red. Every invariant carries
assumptions; write them in a comment above the function.
</Aside>

## The two ways this goes wrong

**Restating the code.** The most common failure is an invariant that recomputes what the contract
computes:

```solidity
// worthless
assertEq(vault.totalShares(), vault.totalShares());
// almost as worthless
assertEq(vault.convertToAssets(vault.totalShares()), vault.totalAssets());
```

The second one looks like real work. It is not: `convertToAssets` is defined in terms of
`totalAssets()` and `totalShares`, so the assertion is an algebraic identity that holds whatever
those numbers are, including when they are wrong. If the contract's own bookkeeping is the thing that
is broken, an invariant phrased in terms of that bookkeeping cannot see it. The fix is to compare
against a model computed independently of the contract — which is what ghost variables are for, and
the next lesson's subject.<Cite src="foundry-invariant-guide" />

**Too weak to fail.** The other direction is an invariant that no reachable state violates.
`assertGe(vault.totalAssets(), 0)` is the caricature, but the realistic version is subtler: a bound
so generous that only an absurd state breaks it, or a conservation statement over a quantity nothing
in the system modifies. These pass forever and generate a green check that a reviewer reads as
coverage.

There is a cheap test for both failure modes, and it is the only reliable one: **break the contract
on purpose and confirm the invariant goes red.** Change a rounding direction, remove a bounds check,
flip an operator. If the campaign still passes, the invariant is decoration. Foundry's own best-practice
list points at the same habit from the other end — start with simple properties and add complexity,
and log call counts to confirm every function is being
exercised<Cite src="foundry-invariant-guide" /> — because both are ways of checking that the campaign
is doing work rather than reporting that it did.<Cite src="rareskills-invariant-testing" />

## What solvency does not catch

This is the part most write-ups skip, and it matters for calibration.

The [ERC-4626 inflation attack](/c/inflation-first-depositor-attack) — attacker deposits 1 wei,
donates a large amount directly to the vault, victim's deposit rounds down to zero shares — does not
violate `totalAssets() >= totalShares`.<Cite src="eip-4626" /><Cite src="oz-erc4626-inflation-defense" />
It does not violate any solvency statement at all. Throughout the entire attack the vault holds more
than enough to cover every outstanding claim. The victim was not defrauded by an insolvent vault;
they were defrauded by an exchange rate, and every share that exists remains fully backed.

To catch that you need a different family: a **fairness** property, per user rather than in
aggregate. Something of the shape "no actor's realised proceeds exceed what they contributed plus
their pro-rata share of yield" — which is close to Cyfrin's "a user should never be able to withdraw
more money than they deposited", stated per actor.<Cite src="cyfrin-fuzz-guide" /> Stating it requires
the test to remember, independently of the contract, what each actor contributed — again, ghost
variables.<Cite src="foundry-invariant-guide" />

<Check type="spot-bug" concept="solvency-invariant">
A staking contract lets users stake a token, accrue rewards from a funded reward pool, and unstake.
A team writes this invariant and reports the campaign green:

```solidity
function invariant_solvent() public view {
    assertGe(
        token.balanceOf(address(staking)),
        staking.totalStaked()
    );
}
```

Name what this misses, and give the corrected property.

<Answer>
**It ignores the reward liability entirely.** `totalStaked` is only one of the two things the
contract owes. The other is accrued-but-unclaimed rewards, and every accrual increases what users can
withdraw without increasing `totalStaked` at all. A contract that has promised more rewards than its
pool can pay passes this check right up to the moment the last user tries to claim and the transfer
reverts.

**The corrected property adds the second liability:**

```solidity
assertGe(
    token.balanceOf(address(staking)),
    staking.totalStaked() + staking.totalPendingRewards()
);
```

**Two things to check before trusting even that.**

Whether `totalPendingRewards()` is independently computed or read from the same accumulator the
payout path uses. If it is the same accumulator, the invariant restates the code and cannot see a bug
in the accrual arithmetic. A ghost that sums what the handler observed being credited is the
independent version.

And whether the stake token and the reward token are the same. If they differ, one `balanceOf` check
compares unrelated quantities and needs splitting into two invariants. If they are the same token,
reward funding and staked principal share one pool and a mis-accounted reward silently spends
principal — which is exactly what this invariant catches.

**And what it still will not catch:** the aggregate can be sound while one user's share is computed
wrongly at another's expense. That needs a per-actor fairness invariant.<Cite src="oz-erc4626-inflation-defense" />
</Answer>
</Check>

## Where this pays off

**The next lesson** closes the two gaps this one opened. Ghost variables give the invariant an
independent model to compare against, so it stops restating the contract's own arithmetic. And the
handler gives the campaign the ability to reach the states where these properties are interesting at
all — because a correct invariant checked against a state space the campaign never enters is
still worth nothing.

**Audits** are where the wording pays off directly. A findings report argues from a property that was
violated, and a scope section is a list of properties in scope. Teams that arrive with five precise
invariants get a different engagement, because the reviewer's first day is not spent reconstructing
what the system is supposed to guarantee.

**Monitoring** reuses the artefact unchanged: the predicate runs against mainnet state on a timer,
and a violation is an alert rather than a red build. The invariant is the durable object here; the
campaign is one of several engines you can point at it.
