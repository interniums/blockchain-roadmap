A test that passes, on forge 1.7.1, against the wrong contract entirely:

```solidity
vm.expectEmit(true, true, true, true);
emit Target.Ping(alice, 100);
decoy.ping(alice, 100);          // Decoy is a different contract; Target is never called
```

`Decoy` and `Target` are unrelated. They happen to declare an event with the same name and the same
parameter types. Four `true`s — every checkable box ticked — and the assertion is satisfied by a log
from a contract that is not under test.<Cite src="measured-forge-cli-1-7-1" />

That is not a bug in the cheatcode. It is what `expectEmit(bool, bool, bool, bool)` is documented to
do, and the gap between what it does and what "all true" implies is the reason this lesson exists.

## The three-statement idiom, and what the middle line is for

The pattern is fixed: call `expectEmit`, emit the event you expect in your test, then make the call
that should emit it.<Cite src="foundry-cheatcode-expect-emit" />

```solidity
vm.expectEmit(true, true, false, true, address(vault));
emit Vault.Deposit(alice, 100e18);           // <- not an assertion
vault.deposit(100e18);                       // <- the call under test
```

The middle line trips people because it looks like the test is emitting an event, which is a strange
thing for a test to do. It is not asserting anything and it is not the thing being checked. It is a
**value carrier**: emitting the event is how you hand the cheatcode a fully-formed log — signature,
topics, data — to compare the real one against. Solidity has no literal syntax for "a log record", so
`emit` is the syntax.

Which means the order is not stylistic. `expectEmit` must be placed immediately before the call you
want to assert on.<Cite src="forge-std-vm-1-16-2" /> Register, supply the expected value, then call.

## The four booleans check less than they look like they check

You already know the shape of a log: up to four topics and a data body, with topic0 the hash of the
event signature and the indexed parameters occupying the remaining
topics.<Cite src="solidity-abi-events" /> Map the booleans onto that and the gap becomes obvious.

The four booleans control checking of the first indexed parameter, the second indexed parameter, the
third indexed parameter, and the non-indexed event data.<Cite src="foundry-cheatcode-expect-emit" />
That is topics 1, 2, 3 and the body. Two things are conspicuously not in that list:

**Topic 0 is always checked, automatically, and is not one of the
booleans.**<Cite src="foundry-cheatcode-expect-emit" /> This is the part that does work for you.
Because [topic0 is the signature hash](/c/topic0-is-the-signature), an event with a different name or
different parameter *types* can never satisfy your expectation — you cannot accidentally match
`Deposit(address,uint256)` against `Withdraw(address,uint256)`. But the same fact explains the
opening example: two contracts declaring the identical event declare the identical topic0, because
the hash is over the signature and nothing else.<Cite src="solidity-abi-spec" />

**The emitting address is checked only by the overloads that take one.** The `address emitter`
parameter specifies the expected address that emits the event, and it is checked only when explicitly
provided.<Cite src="foundry-cheatcode-expect-emit" /> `expectEmit(true, true, true, true)` does not
take an emitter, so it does not check one, so any contract reached during the call may satisfy it.

The correction is one argument. forge-std v1.16.2 declares
`expectEmit(bool checkTopic1, bool checkTopic2, bool checkTopic3, bool checkData, address emitter)`,
alongside a bare `expectEmit(address emitter)` that checks everything and pins the
source.<Cite src="forge-std-vm-1-16-2" />

**Default to naming the emitter.** In a test that calls a vault which calls a token which calls a
hook, the log stream contains events from all four, and an expectation without an emitter is a claim
about the union.

<Aside kind="note">
Two smaller edges worth knowing before they surprise you.

**Extra booleans have nothing to check.** An event with one indexed parameter has topics 1 and no
more; `checkTopic2` and `checkTopic3` are about positions that do not exist. Writing four `true`s out
of habit on such an event is not stricter than writing `(true, false, false, true)` — it is the same
assertion with two decorative arguments, which is worse only in that it reads as deliberate.

**An indexed dynamic value is compared as a hash.** A `string` or `bytes` parameter marked `indexed`
is stored as the hash of its contents, not the contents — so a topic check on one compares
hashes.<Cite src="solidity-abi-events" /> You know this as
[indexed dynamic types are hashed](/c/indexed-dynamic-is-hashed); the consequence here is that
`checkData` on the non-indexed body is where a readable string comparison actually happens.
</Aside>

## Ordering is enforced; skipping is not

When several expectations are outstanding, the actual log stream must contain them in the same
relative order. The documentation puts it plainly: multiple events must be in order, but you can skip
events.<Cite src="foundry-cheatcode-expect-emit" />

So a call that emits `A`, `X`, `B` satisfies expectations for `A` then `B` — the unmatched `X` is
skipped. Expectations for `B` then `A` do not match, and forge 1.7.1 reports
`[FAIL: log != expected log]`.<Cite src="measured-forge-cli-1-7-1" />

This surprises people because assertions normally commute: three `assertEq` calls can be written in
any order. Here they cannot, and the failure message does not say "wrong order" — it says the log did
not match, which sends people looking at values.

### The expectation that outlives the call it was for

The nastiest interaction is documented in `Vm.sol` and is easy to build by accident: if the next call
reverts and the revert is caught by the caller — a low-level call, or a `try`/`catch` — the
expectation **remains active and may be satisfied by a log emitted from a later
call**.<Cite src="forge-std-vm-1-16-2" />

Measured on forge 1.7.1: register an expectation, make a low-level call that reverts (the boolean
comes back `false`, so the revert is caught), then make a completely different call that emits the
expected event. The test passes.<Cite src="measured-forge-cli-1-7-1" />

Read what that produces in a real suite. You assert that `vault.deposit()` emits `Deposit`. The
deposit reverts, your test catches it and carries on, a later line emits `Deposit` from somewhere
else, and the assertion is satisfied by that. The function you were testing failed, and the test is
green.

The documentation's own remedy is a sequencing rule: perform calls whose reverts you intend to catch
*before* registering expectations.<Cite src="foundry-cheatcode-expect-emit" /> The broader habit is
the one from the previous lesson — the statement after a registration should contain exactly one
call, and you should be able to say what happens to the registration if that call fails.

<Check type="predict" concept="expect-emit-topic-flags">
An ERC-20 wrapper's `deposit` transfers the underlying token in and mints wrapper shares out, so a
successful call emits `Transfer` from the underlying token *and* `Transfer` from the wrapper. The
test:

```solidity
function test_DepositEmitsTransfer() public {
    vm.expectEmit(true, true, true, true);
    emit IERC20.Transfer(address(0), alice, 100e18);   // the mint
    wrapper.deposit(100e18);
}
```

1. What would make this pass while the mint is broken?
2. Would `vm.expectEmit(true, true, true, true, address(wrapper))` fix it?
3. The author adds a second expectation for the underlying token's `Transfer(alice, wrapper, 100e18)`
   *after* the mint expectation. What happens?

<Answer>
**1 — a `Transfer` with those exact values from any other contract in the call tree.** The booleans
cover topics 1-3 and the data; the emitter is not among them, so any `Transfer(address,uint256)`
matching `(address(0), alice, 100e18)` satisfies it, whoever emitted
it.<Cite src="foundry-cheatcode-expect-emit" /> In this specific contract that is a narrow escape —
the underlying token's transfer has different topic values — but the moment the wrapper starts
routing through a hook, a fee module or a rebasing adapter that mints or burns on the same values,
the assertion becomes ambiguous. And it is ambiguous *silently*: the test does not report which
contract satisfied it.

**2 — yes, for that failure, and it is the correct default.** The five-argument overload checks the
supplied address against the emitting contract.<Cite src="forge-std-vm-1-16-2" /> It does not fix
the caught-revert leak, and it does not fix ordering; it fixes exactly the "wrong contract" class.

**3 — the test fails, and the reason is ordering, not values.** The mint happens after the underlying
transfer in the actual log stream, so registering the mint first and the underlying transfer second
asks for an order the contract does not produce. Expected events must appear in the actual relative
order.<Cite src="foundry-cheatcode-expect-emit" /> Forge reports `log != expected log`, which reads
as a value mismatch and sends the author looking at amounts.<Cite src="measured-forge-cli-1-7-1" />
The fix is to register in emission order.

**The thing worth noticing across all three.** Every one of these failures is a mismatch between what
the test *says* and what the harness *checks*, and none of them is visible in the test's own text. The
only way to see the difference is to read the actual log stream — which `-vvvv` prints, and which is
the first thing to look at when an event assertion behaves strangely.
</Answer>
</Check>

## What this unlocks

**Immediately:** re-read your own suite's event assertions. The specific thing to grep for is
`expectEmit(true, true, true, true)` with no address, in any test whose call passes through more than
one contract. That combination is not always wrong, but it is never *checked*, and it is common
enough that it is worth a pass.

**In the fuzzing and invariant modules:** events become the observation channel for properties that
are awkward to state about storage. Knowing that an expectation can be satisfied by the wrong emitter,
or can survive a caught revert, matters more there than here, because a campaign makes thousands of
calls and you will never read the traces.

**In the app-layer track:** the same log stream is what an indexer consumes. An event assertion in a
test and a subgraph handler are two readers of one wire format, and a test that does not pin the
emitter is asserting something weaker than what your indexer will actually filter on.

**And the module's closing question.** Every mechanism in these six lessons — a rename that
un-registers a test, a prank left running in a fixture, an expectation bound to an argument
evaluation, four booleans that do not check the emitter — produces a green test over a broken
contract. Pick the test in your own suite you would be least surprised to learn passes for the wrong
reason, write down the specific mechanism by which it could, and then go and check whether it does.
The tools to check are the ones you now have: `--match-test` to isolate it, `-vvvv` to see what
actually ran, and a deliberate break in the contract to confirm the test notices — all pinned to
forge 1.7.1 and forge-std v1.16.2, because that is the only honest way to state any of
it.<Cite src="measured-forge-1-7-1" /><Cite src="forge-std-repo" />
