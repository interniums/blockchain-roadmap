A pull request titled "test naming cleanup" renames forty-one functions in a suite. Most of the
renames are cosmetic — `testWithdraw` becomes `test_Withdraw`, `testTransferFrom` becomes
`test_TransferFrom`. Three are not. `testOwnerCanPause` becomes `verifyOwnerCanPause`, because the
author decided "verify" read better for an access-control assertion.

CI goes green. It stays green. Those three functions are never executed again, and nothing reports
that the suite got smaller — the summary line prints a count, and nobody had memorised the old one.

This is not a defect. It is the direct consequence of the first decision the runner makes, and the
whole module rests on it: **forge decides what a test is by looking at the name of the function.**
Everything downstream — which engine runs the function, what state it starts from, whether it can be
filtered — follows from a string comparison you can break with a rename.

## Discovery is a prefix match, not an annotation

You have used runners that discover by decorator (`@Test`), by callback registration (`it(...)`), or
by file convention plus a config block. Foundry uses none of those. Test files end in `.t.sol`, and
inside them, functions whose names begin with `test_` or `test` are the
cases.<Cite src="foundry-writing-tests" />

There is no registry, no annotation, and no place to opt a function in. A `.t.sol` file compiles like
any other Solidity file; a helper function named `mintTo` and a case named `test_Mint` differ to the
runner only in their first four characters.

Two consequences worth carrying:

**A rename is a semantic change.** In a codebase where renaming a private helper is a zero-risk
refactor, renaming a test function can delete a test. The failure is silent by construction: there is
nothing to warn about, because a function that does not match a prefix is simply a function.

**Where forge looks is configuration; what it runs is not.** The directory searched comes from the
`test` key, which `forge config` reports as `test = "test"` on a default
project.<Cite src="foundry-config-overview" /><Cite src="measured-forge-cli-1-7-1" /> You can point
that somewhere else. You cannot change the prefix rule from config.

## The prefix chooses the engine, not just the label

This is the part that makes the naming rule more than a convention. Different prefixes hand the
function to different execution strategies:

- **`test`** / **`test_`** — a single deterministic run.<Cite src="foundry-writing-tests" />
- **`testFuzz_`** — parameters are supplied by the fuzzer across many
  runs.<Cite src="foundry-writing-tests" />
- **`invariant*`** and **`statefulFuzz*`** — a stateful campaign that drives sequences of calls
  rather than one call.<Cite src="foundry-writing-tests" />
- **`table*`** — data-driven cases.<Cite src="foundry-writing-tests" />
- **`check*`** and **`prove*`** — symbolic execution, and they run only under
  `--symbolic`.<Cite src="foundry-writing-tests" />

Read the last one again, because it is the trap in the list. A function named `check_NoOverflow` in a
normal `forge test` run is not a failing test and not a skipped test. It is not a test at all in that
run, and the output says nothing about it. If you have written symbolic properties and never passed
`--symbolic`, your evidence is that a command you did not run did not fail.

### `testFail` is not on the list

If you learned this toolchain from material written before Foundry's stable line, you are carrying a
prefix that is no longer in the documented set. `testFail` does not appear on the writing-tests page
at all.<Cite src="foundry-writing-tests" />

Its removal is worth understanding rather than just absorbing, because it is this module's thesis in
miniature. A `testFail_Withdraw` passed if the body reverted — for any reason. A typo'd address with
no code, an arithmetic panic in the test's own setup arithmetic, a call to a function that does not
exist on the target: all of them are reverts, all of them made the test green, and none of them was
the revert the author meant to assert.

The replacement idiom names the condition and pins the error:
`test_RevertWhen_<Condition>` plus an explicit `vm.expectRevert` naming the specific error you
expect.<Cite src="foundry-cheatcode-expect-revert" /> That test fails when the contract starts
reverting with a *different* error. The old one could not tell the difference, which is exactly the
property that made it feel reliable.

### The antidote is one command

Since discovery is mechanical, you can ask forge what it found. `forge test --list` prints the
discovered set as a tree — file, then contract, then case names — without running
anything:<Cite src="forge-test-reference" />

```
$ forge test --list --match-path "test/Vault.t.sol"
test/Vault.t.sol
  VaultTest
    test_DepositCreditsShares
    test_RevertWhen_WithdrawExceedsBalance
```

<Cite src="measured-forge-cli-1-7-1" /> That output is the ground truth about what your suite is. It
takes a second, it is diffable, and it is the one artefact that would have caught the rename in the
opening scene — because a function that stopped being a test simply stops appearing in it.

The habit worth building is not to run it constantly. It is to know the number. A suite that reported
412 tests yesterday and 409 today has lost three, and no other signal in a green run will tell you.

## The contract is the fixture, and it is also the caller

A Foundry test file declares a contract, conventionally inheriting `Test` from
forge-std.<Cite src="foundry-writing-tests" /><Cite src="forge-std-repo" /> That inheritance is doing
real work, and it is worth knowing what it supplies rather than treating it as boilerplate:

```solidity
contract VaultTest is Test {
    Vault vault;              // fixture
    MockToken token;          // fixture
    address alice = makeAddr("alice");   // utility from forge-std

    function setUp() public { ... }

    function test_DepositCreditsShares() public { ... }   // a case
}
```

The state variables are the fixture. The prefix-matching public or external functions are the
cases.<Cite src="foundry-writing-tests" /> There is no separate runner configuration file, no
`describe` block, no fixture-injection container: the contract *is* the configuration.

The `vm` handle you will spend the rest of this module using comes from the same inheritance. In
forge-std it is a constant — `Vm internal constant vm = Vm(VM_ADDRESS)`, where `VM_ADDRESS` is
`0x7109709ECfa91a80626fF3989D68f67F5b1DD12D`.<Cite src="forge-std-base-1-16-2" /> That is the whole
mechanism, and the next lesson but one takes it apart.

One structural fact that catches people later: the test contract is not a neutral observer. It is a
deployed contract with an address, and by default it is the `msg.sender` for the calls your test
makes — `vm.stopPrank()` is documented as resetting subsequent calls' `msg.sender` to be
`address(this)`, and `address(this)` is the test contract.<Cite src="forge-std-vm-1-16-2" /> If your
contract under test has an `onlyOwner` modifier and the test deployed it, the test *is* the owner,
and every access-control assertion you write is being made from the privileged seat unless you
deliberately move.

## Filtering is the inner loop

The reflex when a test fails is to re-run with more verbosity. On a suite of any size that is the
slow path: you get traces for hundreds of passing tests you do not care about, and the one you do
care about is somewhere in a wall of output.

Invert it. Narrow first, then raise verbosity:

**Subgoal — reduce the run to the failing case.** `--match-test`, `--match-contract` and
`--match-path` restrict which tests execute, and they combine; each has a `--no-match-*` inverse for
exclusion.<Cite src="foundry-writing-tests" /><Cite src="forge-test-reference" />

```bash
forge test --match-contract VaultTest --match-test test_DepositCreditsShares
```

**Subgoal — add exactly the verbosity that answers your question.** The levels are not
interchangeable. On forge 1.7.1 the CLI documents them as: `-vv` prints logs for all tests, `-vvv`
prints execution traces for failing tests, `-vvvv` prints execution traces for all tests plus setup
traces for failing tests, and `-vvvvv` adds storage changes and backtraces with line
numbers.<Cite src="measured-forge-cli-1-7-1" /><Cite src="foundry-writing-tests" /> If your question
is "what was the caller", `-vvvv` answers it; `-vvvvv` mostly buys you noise until your question is
"which slot changed".

**Subgoal — keep the narrowed command, not the wide one.** The filter that reproduced the failure is
the filter a colleague needs in the bug report, and it is the same mechanism a grading harness uses
to run exactly the file an exercise is scored on.

<Aside kind="note">
Two flags matter if anything downstream is going to read the results rather than a human. On forge
1.7.1, `--junit` is described as "Output test results as JUnit XML report", while `--json` sits among
the display options next to `--md` and formats *log messages* — they are not two spellings of the
same thing.<Cite src="measured-forge-cli-1-7-1" /><Cite src="forge-test-reference" />

And `--junit` will not combine with a gas report: forge 1.7.1 rejects the pair outright with
`error: the argument '--junit' cannot be used with '--gas-report'`, before running
anything.<Cite src="measured-forge-cli-1-7-1" /> If your CI job is meant to produce both machine-readable
results and gas numbers, that is two invocations, not one.
</Aside>

<Check type="predict" concept="test-discovery-by-prefix">
A colleague opens a PR with these four changes. For each, say what forge does after the change, and
whether anything in the output would tell you.

1. `function testFuzz_Deposit(uint256 amount)` renamed to `function test_Deposit(uint256 amount)`.
2. `function test_Solvency()` renamed to `function invariant_Solvency()`.
3. `function test_Withdraw()` changed from `public` to `internal`.
4. A new `function check_NeverNegative(uint256 x)` added, and `forge test` run normally.

<Answer>
**1 — it is still fuzzed.** The parameter list is what makes forge supply inputs; the `testFuzz_`
prefix is the human-facing convention on top of that. Declaring
`function test_PlainWithParam(uint256 x)` on forge 1.7.1 and running the suite reports
`[PASS] test_PlainWithParam(uint256) (runs: 256, ...)` — a plain `test_` name, fuzzed
anyway.<Cite src="measured-forge-cli-1-7-1" /> So the rename does not convert a fuzz test into a
unit test. The run-count in the output line is your tell. The real cost is to the reader: nothing in
the name now warns that `amount` is adversarial.

**2 — it stops being a unit test and becomes a stateful campaign.** `invariant*` hands the function
to a different engine, one that drives sequences of calls against the contract rather than executing
your body once.<Cite src="foundry-writing-tests" /> A function written as a single deterministic
assertion, run under the invariant engine, is at best a very slow unit test and at worst passes
because the campaign never reached the state the original test set up by hand.

**3 — it stops running.** The cases are the contract's public or external prefix-matching
functions.<Cite src="foundry-writing-tests" /> An `internal` function with a perfect `test_` prefix
is a helper. The suite gets one shorter and nothing says so, which is change one from the opening of
this lesson wearing a different hat.

**4 — nothing happens, and the output is silent about it.** `check*` runs only under
`--symbolic`.<Cite src="foundry-writing-tests" /> Under a plain `forge test` it is neither run nor
reported as skipped. The dangerous version of this is a team that adds symbolic properties, never
wires `--symbolic` into CI, and treats the green suite as covering them.

**The pattern across all four:** three of the four changes alter what executes, and none of the four
produces a diagnostic. The only defence is to know the rule, and to notice the test count.
</Answer>
</Check>

## What this unlocks

**Immediately next:** what a test starts from. Discovery tells you which functions run; the next
lesson tells you what state each one runs against, and why "each test starts clean" is a description
that will mislead you in one specific and expensive way.

**Two lessons on:** the `vm` constant introduced above, taken apart. Knowing that a cheatcode is an
ordinary call to a fixed address explains why the interface is typed, why forge-std's `Vm.sol` is the
list worth reading, and why a fuzzer that generates addresses can generate *that* one.

**And for the rest of the track:** the filter flags are how you will run fuzz campaigns, invariant
campaigns and fork suites separately, because those three cost minutes rather than milliseconds and
you will not want them in the loop you run on every save. The suite you can slice is the suite you
will actually run — pinned, in this module's examples, to forge 1.7.1 and solc
0.8.36.<Cite src="measured-forge-1-7-1" /><Cite src="solidity-0836-release" />
