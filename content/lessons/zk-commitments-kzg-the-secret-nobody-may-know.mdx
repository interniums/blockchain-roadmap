In the `ethereum/kzg-ceremony` repository there is a file called `transcript.json`. It is stored as a
Git LFS object, and the pointer records its size: **253,714,449 bytes** — roughly 254 MB of other
people's randomness, kept in public so that anyone who wants to can recheck every contribution that
went into it.<Cite src="kzg-ceremony-repo" />

That file exists because of a single scalar that the previous lesson showed you how to abuse. A
prover who knows the setup secret can produce valid openings for values the polynomial does not take,
and the ceremony's own FAQ states the consequence without softening it: an attacker who extracted the
secret could make arbitrary claims about the data.<Cite src="kzg-ceremony-faq" />

This lesson is about how a number that must exist in the mathematics was arranged to exist in nobody's
memory — and about what that arrangement actually assumes, which is both narrower and stranger than
"trust the Ethereum Foundation".

## What the reference string is

KZG's public parameters are not random bytes. They are **encrypted powers of a secret scalar**:

```text
[1]G,  [tau]G,  [tau^2]G,  [tau^3]G,  ...,  [tau^(d)]G
```

Each entry is a curve point, and the discrete logarithm problem means that publishing `[tau]G` does
not publish `tau`. Committing to a polynomial is then a linear combination of those points weighted
by the polynomial's coefficients — or, in the Lagrange basis Ethereum actually ships, weighted by its
evaluations.<Cite src="consensus-specs-deneb-polynomial-commitments" />

The **degree bound is a hard parameter**. You cannot commit to a polynomial of higher degree than the
string has powers for, because there is no point to multiply the extra coefficient by. This makes an
SRS unlike a hash function in a way that matters operationally: it has a size, and enlarging it means
running a ceremony again.

Ethereum's ceremony therefore produced not one string but **four**, with different maximum powers and
— importantly — **four independent secrets**. The specification writes them out: sets with G1 powers
up to `2^12 - 1`, `2^13 - 1`, `2^14 - 1` and `2^15 - 1`, each accompanied by G2 powers up to
`tau^64`.<Cite src="kzg-ceremony-specs" />

The first of those four is the one blobs use. `2^12` is 4,096, the same number as
`FIELD_ELEMENTS_PER_BLOB`, because they are the same constraint: the string must be long enough to
commit to a degree-4,095 polynomial and there is no reason to make it
longer.<Cite src="eip-4844" /> The shipped mainnet file matches — 4,096 G1 points in the Lagrange
basis, 4,096 in the monomial basis, and 65 G2
points.<Cite src="consensus-specs-trusted-setup-4096" /> The 65 is `tau^0` through `tau^64`, and the
verifier needs only the second of them, `[tau]_2`, for the pairing check you read last
lesson.<Cite src="consensus-specs-deneb-polynomial-commitments" />

<Aside kind="note">
**Why four sets rather than one big one.** Larger degree bounds serve larger future data structures,
and each set is independent so a problem with one does not implicate the others. The ceremony was
explicitly framed as providing the cryptographic foundation for Ethereum's scaling work rather than
for EIP-4844 alone.<Cite src="kzg-ceremony-repo" />
</Aside>

## Scope the damage before you price the defence

It is worth being exact about what a leaked `tau` would and would not do, because the fear it
generates is usually aimed at the wrong target.

**What it breaks.** Binding, everywhere the string is used. The holder could produce a valid opening
for any value at any point, for any commitment, without touching the underlying
data.<Cite src="kzg-ceremony-faq" /> Concretely: a claim about a blob's contents checked through the
on-chain precompile would pass while being false; a rollup bridging its blob commitment to its
proof system's commitment could be lied to about which data was actually published; and a sampler
could be handed cells that verify individually but reconstruct nothing.

**What it does not break.** It does not reveal a blob — blobs are broadcast, and nothing was ever
hidden.<Cite src="eip-4844" /> It does not forge an ECDSA signature, move anyone's funds directly, or
alter consensus. It is not a key to the chain. It is a key to *statements about committed data*.

**Why that scoping still leaves it catastrophic.** Two properties make it worse than its narrow
surface suggests.

First, it is **silent**. A forged opening is a valid curve point satisfying a valid pairing equation.
There is no signature that fails to match, no hash that comes out wrong, no invariant that trips. It
is indistinguishable from an honest opening to every party and every piece of software, forever.
Compare that with a double-spend, which announces itself the moment two conflicting histories meet.

Second, it is **retroactive and unbounded**. The secret does not expire. Every commitment ever made
under that string, past and future, becomes openable to anything. There is no rotation you can
perform after the fact, because the commitments are already published and already relied upon.

That combination — undetectable, permanent, retroactive — is why the defence is structural rather
than operational. You do not monitor for this, and you do not respond to it. You arrange for the
secret never to have existed, and the arrangement has to be right the first time.

## How a secret is made not to exist

The construction is a **sequential multi-party computation**, and it is simple enough to state in
four lines.

Participant `k` receives the running string. They generate a secret `x_k` known only to them. They
multiply it in — raising every power appropriately, so that the string that comes out is the string
for a new secret. They publish the result together with evidence that they transformed it correctly.
Then they destroy `x_k`.

After `n` participants:

```text
tau = x_1 * x_2 * x_3 * ... * x_n
```

To learn `tau` you need every factor. One participant who generated real randomness and genuinely
destroyed it makes the product unknowable, no matter what everyone else did. This is the **1-of-N**
trust assumption, and the FAQ states it in the operational form that matters: only a single
participant needs to have kept their secret input for the result to be secure, which means an
attacker would have to compromise the contribution software of every participant *and* collude with
all of them.<Cite src="kzg-ceremony-faq" />

### Two roles, and only one of them is a safety risk

The ceremony runs between **participants** and a **sequencer**. Participants contribute randomness;
the sequencer acts as the common point of interaction and verifies each contribution as the ceremony
progresses.<Cite src="kzg-ceremony-specs" />

The specification is unusually direct about what that role can and cannot do: the sequencer should be
a *semi-trusted* entity, because it has the power to **censor participants** — but it **cannot affect
the safety of the setup**.<Cite src="kzg-ceremony-specs-sequencer" />

That sentence is a separation of powers written into a protocol, and it should look familiar from the
consensus track. A coordinator who can decide who participates is a liveness and
censorship-resistance concern. A coordinator who can decide what the output *is* would be a safety
concern, and this design gives nobody that power — because the sequencer never holds a secret, it
only checks other people's arithmetic.

## What gets checked, concretely

A contribution is not taken on trust. The specification lists the checks the sequencer MUST perform on
each one, and the list is worth reading because every entry defends against a specific
attack:<Cite src="kzg-ceremony-specs-sequencer" />

**Schema check.** The submitted `contribution.json` must match the published JSON schema.

**Parameter check.** The number of G1 and G2 powers must equal what the transcript expects, and must
equal the number of points actually present. A contribution that quietly shortens the string is
rejected before anything cryptographic happens.

**Subgroup checks.** Every G1 power, every G2 power, and the contributor's public key must be
elements of the **prime-order subgroup**. A curve point that looks valid but lives in a small
subgroup is the classic vehicle for leaking information about a secret it gets multiplied against.

**Non-zero check.** The contributor's public key must not be the point at infinity. Without this, a
participant could contribute the secret `0`, collapsing the entire string to a known value.

**Pairing check — the one that proves the contribution was honest.** Each `Contribution` carries a
`pot_pubkey`, a G2 point.<Cite src="kzg-ceremony-specs-contribution" /> That point is the
contributor's secret `x_k` carried in G2 — a public commitment to a value they never reveal. The
sequencer then verifies that the new string really is the old one transformed by that secret:

```text
e( [tau_(k-1)]_1 , [x_k]_2 )  ==  e( [tau_k]_1 , [1]_2 )
```

Both sides evaluate to the same pairing target exactly when `tau_k = tau_(k-1) * x_k`. The
specification notes these checks SHOULD be batched via a random linear combination, reducing the
number of final exponentiations to two — the same batching idea you met in the previous
lesson.<Cite src="kzg-ceremony-specs-sequencer" />

Notice what this achieves. A participant proves they multiplied in *some* secret without revealing
which, and without anyone being able to check whether they actually deleted it. **Deletion is not
verifiable and never can be.** The protocol verifies the transformation; the honesty is the part that
cannot be checked, which is precisely why it only needs to be true once.

The transcript then records, per contribution, the running product, the `pot_pubkey`, a signature,
and a `participant_id` derived from the contributor's Ethereum address or GitHub
handle.<Cite src="kzg-ceremony-specs-sequencer" /> That is why the 254 MB file is worth keeping:
every link in the chain can be re-verified by anyone, years later, without asking permission.

## What the ceremony actually assumes

Write the assumption out in full, because most summaries get it wrong in both directions.

**It assumes:** at least one participant, out of everyone who contributed, generated genuine
randomness and destroyed it afterwards.

**It does not assume:** that the Ethereum Foundation is honest. That the sequencer is honest — it can
censor, not corrupt.<Cite src="kzg-ceremony-specs-sequencer" /> That a majority of participants are
honest. That most contributions were made competently.

And the realistic failure mode is not the one the assumption is phrased against. The FAQ is candid
about this: the more plausible danger is not mass collusion but a **common bug** leaking randomness
across many contributions at once — which is the argument for multiple independent implementations
rather than one heavily audited one.<Cite src="kzg-ceremony-faq" /> The repository's client list is
that argument made real: independent contribution clients in Java, Go, C++, JavaScript, C# and more,
built against several different BLS libraries, plus browser interfaces from separate
teams.<Cite src="kzg-ceremony-repo" />

The ceremony was also audited twice, at the two places where a systemic bug would have been most
damaging: a specification and implementation audit by SECBIT in August 2022, and a sequencer audit by
Sigma Prime in January 2023.<Cite src="kzg-ceremony-repo" />

<Aside kind="note">
**The Special Contribution period is the part worth knowing about.** Between 1 and 16 April 2023 the
ceremony accepted contributions that were not possible through the ordinary web interface. The
repository's own framing of why is precise: while the ceremony only needs a single honest participant
for a secure output, these contributions provide **additional assurances** — computing over the
entropy on an airgapped machine that is then wiped and physically destroyed, generating entropy from a
physical process (the README's example is measuring an explosion), and involving large groups of
people, because a contribution made by many people at once is harder to
fake.<Cite src="kzg-ceremony-repo" />

Read that as engineering rather than theatre. Each variant attacks a *different* common-mode failure:
a compromised host, a compromised random number generator, and a fabricated participant. The 1-of-N
assumption is only as good as the independence of the contributions, and independence is what those
contributions were buying.
</Aside>

### The contributor count, handled honestly

You will see a number attached to this ceremony — typically "over 140,000 contributors". Treat it
carefully. This project's own conflict register records that the figure comes from secondary
write-ups rather than from a count taken off the transcript, and neither the ceremony repository's
README nor the specification states a
total.<Cite src="chainpath-conflict-register" /><Cite src="kzg-ceremony-repo" />

It is countable — the transcript stores one `participant_id` and one `pot_pubkey` per
contribution.<Cite src="kzg-ceremony-specs-sequencer" /> It is countable from a 254 MB Git LFS
object, by you, and it was not counted here.

More importantly, the number is not the security argument. **1-of-N does not improve with N the way
people assume.** Going from 100 participants to 140,000 does not multiply your safety margin by
1,400; the assumption was already satisfied at 100 if any one of those hundred was honest. What
breadth actually buys is *diversity*: the more varied the participants, the machines, the client
implementations and the entropy sources, the less plausible it becomes that one systemic flaw
touched all of them. Breadth is a hedge against correlated failure, not a multiplier on an
uncorrelated one.

On what comes after, be careful about what is known. The 2023 output is still what ships in the

roadmap's stated long-run direction is toward post-quantum, hash-based assumptions, which points away
from pairing-based schemes with structured setups
generally.<Cite src="ethereum-org-quantum-resistance" /> What that implies for KZG specifically — a
replacement rather than a re-ceremony — is a reasonable reading of the direction and not a scheduled
event. There is no date to print, and this lesson does not print one.

Your team needs a structured reference string for a proving system in a product you are shipping. An
engineer proposes: "We'll run our own ceremony. Five of us each contribute on our laptops and delete

Say what is correct in that reasoning, and list what you would require before signing off.

<Answer>
**The 1-of-N claim is correct as stated, and it is the wrong thing to be reassured by.** A single
honest participant does make the product unknowable.<Cite src="kzg-ceremony-faq" /> The problem is
that "honest" is not the failure mode you should be worried about.

**1. Common-mode failure defeats 1-of-N directly.** Five colleagues on five similar laptops, running
the same contribution binary, drawing from the same operating system's random number generator, is
close to one contribution repeated five times. The ceremony FAQ names exactly this as the more
realistic danger — a common bug leaking randomness across contributions — and the answer it gives is
multiple independent implementations.<Cite src="kzg-ceremony-faq" /> Five people with one
implementation have the *form* of 1-of-N without its substance. If you run it, run it on different
hardware, with different clients, with at least one contribution from outside the team.

**2. Nobody outside can check it.** Ethereum's ceremony publishes a transcript with a running
product, a public key and an identity per contribution, so any stranger can re-verify the whole chain
years later.<Cite src="kzg-ceremony-specs-sequencer" /><Cite src="kzg-ceremony-repo" /> If your five
contributions are not published in a re-verifiable form, your users are not relying on 1-of-N — they
are relying on your word that a ceremony happened. Those are different products.

**3. Who verifies each contribution, and what exactly do they check?** The sequencer's list is not
optional: schema, parameter counts, prime-order subgroup membership on every point, a non-zero public
key, and the pairing check that the new string is the old one times the contributor's
secret.<Cite src="kzg-ceremony-specs-sequencer" /> Skipping the non-zero check alone lets a
participant contribute zero and collapse the string. This is where a hand-rolled ceremony most often
goes wrong, because the checks are unglamorous and the happy path passes without them.

**4. Is this setup universal or circuit-specific?** Some proof systems need a fresh ceremony **per
circuit**, which turns this from a launch task into a recurring obligation every time you change the
relation being proved — a distinction the next module treats
properly.<Cite src="chainpath-conflict-register" /> Establish which kind you are signing up for
before, not after.

**5. What is the degree bound, and what happens when you outgrow it?** The string is sized. Ethereum
ran four sets at four different bounds precisely so that later, larger uses would not need a new
ceremony.<Cite src="kzg-ceremony-specs" /> Pick your bound with room, because raising it later means
doing all of this again.

**The recommendation I would actually make.** Before running anything, check whether the proof system
can use an **existing** universal reference string that has already been produced by a large, public,
independently verifiable ceremony. Inheriting somebody else's 1-of-N over tens of thousands of
diverse participants is a strictly better trust assumption than manufacturing your own over five
colleagues on matching laptops — and it is free.
</Answer>
</Check>

## What this unlocks

You can now state what a trusted setup costs with precision: not "trust the organisers", but *at
least one of these specific contributions was honest*, with a public transcript that lets anyone
re-verify every transformation and nobody verify any deletion. You know why breadth matters — for
independence, not for arithmetic — and why a ceremony's degree bound is a design constraint that
outlives the event.

The next lesson takes all of this on-chain. A contract cannot read a blob; it can call a precompile
at `0x0A` with exactly 192 bytes and learn one fact about data it is structurally unable to
see.<Cite src="eip-4844" /> That precompile is the pairing check you read in the previous lesson,
against the reference string this one produced, priced at a fixed gas cost — and the pattern built on
top of it lets a rollup prove that the data it published is the data its proof was about.
