Those numbers are from the Noir profiler's own documentation, profiling a small program that zeroes
an array past a dynamic index.<Cite src="noir-docs-profiler" /> An engineer reading the first figure
concludes the comparison is the bottleneck and spends a day on it. An engineer reading the second
concludes it is noise and looks elsewhere. **Both read a real number correctly. One of them is
optimising the thing that costs money.**

This lesson is short and mechanical, and it is the one that makes every optimisation in this module
measurable rather than plausible.

## Three counters, and what each one counts

Your circuit is measured at three different layers, and the tooling reports all three.

**ACIR opcodes** — the count in the backend-agnostic intermediate representation `nargo` emits. This
is the compiler's view of your circuit, before any backend has seen it.

**Brillig opcodes** — the count in the unconstrained portion, the code that runs during witness
generation and contributes no constraints.<Cite src="noir-docs-unconstrained" /> Executed, never
proved. A separate currency entirely.

**Backend gates** — the constraints the prover actually processes, after the backend has expanded
black-box functions and lowered ACIR into its own gate types.

`nargo info` reports the first and the third: its documented output per circuit is the number of ACIR
opcodes and the count of the final number of gates in the circuit used by a
backend.<Cite src="noir-docs-nargo-commands" /> Its printed table also carries the Brillig column, so
a program using an unconstrained helper shows all three at once:<Cite src="noir-docs-unconstrained" />

```text
+---------+-----------+--------------+-----------------+
| Package | Function  | ACIR Opcodes | Brillig Opcodes |
+=========+===========+==============+=================+
| short   | main      | 33           | 114             |
+---------+-----------+--------------+-----------------+
| short   | u64_to_u8 | N/A          | 114             |
+---------+-----------+--------------+-----------------+
```

The backend can also be asked directly. `bb gates` constructs a circuit from the given bytecode — in
particular expanding black-box functions — and returns the gate-count information, with an
`--include_gates_per_opcode` option that reports the mapping rather than only the
total.<Cite src="bb-docs-cli-reference" /> No proof is generated. The number is available from a
compiled artifact, which is the property that makes it usable in a build.

<Aside kind="note">
**`--scheme` applies here too.** `bb gates` takes the same `--scheme` and `--oracle_hash` options as
`bb prove`.<Cite src="bb-docs-cli-reference" /> A gate count is a count *for a proving configuration*,
not a property of your source alone. Record the flags next to the number, or you will compare two
figures that were never comparable.
</Aside>

## Why the two counts diverge

They measure different layers, so nothing forces them to move together. The profiler documentation
states the relationship as an approximation and says why: execution speeds depend on the constrained
execution trace compiled from ACIR opcodes, and proving speeds depend on how the proving backend of
choice interprets those opcodes.<Cite src="noir-docs-profiler" /> Every proving backend interprets
ACIR opcodes differently, which is why the docs tell you to profile backend gates to get the full
picture of proving performance.<Cite src="noir-docs-profiler" />

Two mechanisms produce most of the divergence.

**Some ACIR opcodes are enormously more expensive than others.** A black-box function is one ACIR
opcode and an entire sub-circuit after expansion — which is precisely what `bb gates` does before
counting.<Cite src="bb-docs-cli-reference" /> Counting opcodes treats a hash and an addition as one
each.

**Some backend gates carry fixed setup costs.** In the profiler's example, `blackbox::range`
contributes the majority of the backend gates, and the documentation explains why: Barretenberg's
UltraHonk uses lookup tables for its range gates, which come with a considerable but **fixed** setup
cost in proving gates.<Cite src="noir-docs-profiler" /> Fixed costs do not scale with your program,
so their share depends entirely on how big the rest of it is.

  belief="Fewer ACIR opcodes means a faster proof."
  reality="ACIR opcode count and backend gate count are different measurements at different layers, and they can move in opposite directions. Proving cost tracks gates."

/>

You have already seen this misfire with real numbers. Aztec's three versions of a `u8`-array
conversion went 91 opcodes at 3,619 gates, then 75 at 3,143, then **78 at 2,902** — the third
version's opcode count rose while its gate count fell, and the post's own explanation is that the
extra opcodes are ones the backend finds easier to prove.<Cite src="aztec-unconstrained-blog" />
Optimising the first column would have rejected the best version.

## A worked measurement, end to end

The profiler docs run the same program through every layer, which makes it a good template for your
own work.<Cite src="noir-docs-profiler" />

**The program.** Zero out an array past a dynamic index — `array[i] = 0` inside `if i > ptr`, over a
fixed 32-element array, where `ptr` is a public input.

**Step 1 — get the ACIR flamegraph.**

```text
noir-profiler opcodes --artifact-path ./target/program.json --output ./target/
```

The command maps ACIR opcode counts back to source locations. The program totals **387 ACIR
opcodes**, with the majority coming from the write to `array[i]`.<Cite src="noir-docs-profiler" />

**Step 2 — act on what it shows.** The write is expensive because the index is dynamic. Rewriting so
that the array is produced by an unconstrained helper and then asserted element by element against
the original leaves only reads at compile-time-constant indices. Total: **284 ACIR
opcodes**.<Cite src="noir-docs-profiler" />

The confirmation is nicer than the number. Searching the flamegraph for `memory::op` finds matches
before the change and **none after**, because the optimisation removed the dynamic array — the
program now reads two arrays at known constant indices, and the memory operations became simple
arithmetic.<Cite src="noir-docs-profiler" /> That is the ROM-versus-RAM rule from two lessons ago
appearing as a diff you can see: an index not known at compile time converts read-only memory into
random-access memory and expands the gate count.<Cite src="noir-docs-thinking-in-circuits" />

**Step 3 — get the gate flamegraph, which is the one that matters.**

```text
noir-profiler gates --artifact-path ./target/program.json \
  --backend-path bb --output ./target -- --include_gates_per_opcode
```

The optimised program is **3,062 proving backend gates**.<Cite src="noir-docs-profiler" /> And here
the two views separate: the `i > ptr` call stack that accounted for 43.3% of ACIR opcodes contributes
**3.8%** of backend gates.<Cite src="noir-docs-profiler" />

**Step 4 — profile at the size you will ship.** With the array at 32 elements, `blackbox::range`
dominates the gate flamegraph. With the same program at **2,048** elements, range contributes a
considerably smaller portion of the total, because the setup cost is fixed and everything else
grew.<Cite src="noir-docs-profiler" />

That step is the one teams skip, and it inverts conclusions. A profile taken on a toy input tells you
about your fixed costs. A profile taken at production size tells you about your variable ones. Which
of those you were measuring determines whether the hot spot you found is worth a sprint.

<Aside kind="note">
**Two smaller instruments, both worth knowing.** `nargo info --print-acir` displays the ACIR for the
compiled circuit including the Brillig bytecode,<Cite src="noir-docs-nargo-commands" /> and the docs
suggest reading it alongside the backend's gate count to spot opportunities to reorder arithmetic and
reduce constraints.<Cite src="noir-docs-thinking-in-circuits" /> Separately,
`nargo info --profile-execution` compiles and executes in the Brillig VM and reports Brillig opcodes
executed at *runtime* rather than the static count — it implies `--force-brillig`, because a
constrained circuit has fully flattened control flow and execution profiling is only meaningful for
unconstrained code.<Cite src="noir-docs-nargo-commands" /> That sentence is the whole module in a
tooling footnote: there is nothing to execution-profile in a circuit, because the circuit does not
execute.
</Aside>

## What the gate count actually predicts

Be careful here, because this is where sourced fact runs out and estimation begins.

**What the documentation claims.** Gate count is the significant cost, and *depending on the proving
system* it is linearly proportionate to proof size and proving time, so from a product point of view
it should be kept as low as possible.<Cite src="noir-docs-thinking-in-circuits" /> Note the
conditional. It is a statement about a class of systems, with the qualifier attached.

**What follows reliably.** Gate count is an excellent **relative** instrument. Two versions of your
circuit, same backend, same scheme, same oracle hash: the one with fewer gates is the cheaper one to
prove, and the comparison costs a compile rather than a proving run. Every optimisation claim in this
module is settled this way.

**What does not follow.** A gate count does not give you seconds, gigabytes or dollars. Proving time
depends on the backend, the scheme, the hardware and the parallelism available — and in a browser,
on how many threads the page is allowed. It also does not give you on-chain verification gas. This
module searched for a published gas benchmark for UltraHonk verifiers and **found none**; the widely
circulated per-proof gas models are for Groth16 and FFLONK, and they come from a single 2024
community analysis rather than a specification.<Cite src="orbiter-verifier-gas" /> Do not
back-calculate a verifier's gas from a gate count. Deploy the generated contract and measure it.

The practical consequence: **treat gate count the way you treat a gas estimate from a static
analyser.** Authoritative for comparing two implementations, indicative for capacity planning, and no
substitute for running the thing on the hardware you will run it on.

There is one absolute threshold it does speak to. A circuit small enough to be verified *inside*
another circuit is the precondition for recursion and proof aggregation, and Barretenberg lists
recursive proof verification — verifying proofs within proofs — as a first-class
capability.<Cite src="barretenberg-docs" /> Whether your circuit fits inside a recursive step is a
question about its size, so the gate count is the number you check before designing an aggregation
scheme around it.

<Check type="explain" concept="acir-opcodes-vs-backend-gates">
A teammate posts this in the pull request and asks for approval:

```text
Refactored the range checks in the membership circuit.

nargo info before:  1,204 ACIR opcodes
nargo info after:     870 ACIR opcodes

28% reduction. Proving should get meaningfully faster.
```

Write the review comment. What is missing, what could be true, and what would you ask them to run?

<Answer>
**The claim is unsupported in the direction that matters, and it might be backwards.**

**1. The wrong column is quoted.** ACIR opcodes and backend gates measure different layers, and
proving cost tracks gates.<Cite src="noir-docs-nargo-commands" /> `nargo info` reports both — its
documented output is the ACIR opcode count *and* the final backend gate count — so the second number
was available and was not pasted.<Cite src="noir-docs-nargo-commands" />

**2. The change is specifically the kind where the columns diverge.** This is a refactor of *range
checks*, and range gates are the documented case of a backend cost that does not track opcode count:
UltraHonk implements them with lookup tables carrying a considerable fixed setup
cost.<Cite src="noir-docs-profiler" /> Fewer range-check opcodes may leave the lookup-table setup
entirely in place, in which case a 28% opcode reduction buys close to nothing. Or the refactor
introduced a differently shaped check that the backend prices worse, and gates went *up* — which is
exactly what happened in Aztec's worked example, where the version with **more** ACIR opcodes had
**fewer** gates.<Cite src="aztec-unconstrained-blog" />

**3. No configuration is recorded.** A gate count is a count for a scheme and an oracle hash, both of
which `bb gates` takes as options.<Cite src="bb-docs-cli-reference" /> Two numbers from two
configurations are not a comparison.

**4. No circuit size is stated.** If this was measured on a small test fixture, the fixed setup cost
dominates and the result will not survive contact with production dimensions — the profiler docs show
the same program's range share collapsing when the array goes from 32 to 2,048
elements.<Cite src="noir-docs-profiler" />

**What to ask for.** Re-run `nargo info` and paste the backend gate column for both branches, at
production dimensions, with the scheme and oracle-hash flags recorded. If the gate delta is small or
negative, the refactor may still be worth merging for readability — but the performance claim comes
out of the description. And add the gate count to CI, so the next change of this kind produces a diff
rather than a discussion.

**If the gate count did drop and you want to know why**, run
`noir-profiler gates --artifact-path ... --backend-path bb -- --include_gates_per_opcode` on both
branches and compare where the gates sit.<Cite src="noir-docs-profiler" /> "It got smaller" is a
result. "The range gates moved out of the inner loop" is an explanation you can generalise to the
next circuit.
</Answer>
</Check>

## Make it a build artifact

The habit worth installing, in three lines.

**Record the gate count in CI on every change.** A number that only appears when someone thinks to
ask for it is a number that regresses silently. It comes from a compile, not a proving
run,<Cite src="noir-docs-nargo-commands" /> so this is cheap enough to run on every commit.

**Record the configuration next to it** — compiler version, backend version, scheme, oracle hash.
Pre-1.0 tools change what they emit between releases,<Cite src="noir-docs-quickstart" /> and an
unexplained jump in gate count is much less alarming when the version line next to it also changed.

**Profile at production dimensions, not fixture dimensions.** The one instruction from this lesson
that most often changes a team's conclusions.<Cite src="noir-docs-profiler" />

## What this unlocks

**The last lesson of this module** takes your compiled circuit to two destinations: a Solidity
verifier on an EVM chain, and a browser proving locally through WebAssembly. The gate count you now
know how to read is what determines whether the second of those is a product or a spinner — in a
browser, circuit size stops being a backend concern and becomes something a user waits through.

**And in the practice exercise**, you will implement one operation three ways — naive constrained,
constrained but restructured, and unconstrained hint plus check — and produce a three-row table of
ACIR opcodes and backend gates. Expect at least one row where the two columns disagree about which
version won. That row is the lesson.
