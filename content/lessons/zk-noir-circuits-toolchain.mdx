The first hour with Noir usually ends the same way. You install the compiler, write a five-line
circuit, and then hit a wall that has nothing to do with cryptography: the proving command fails with
an error about the artifact, and nothing in the error mentions versions.

The reason is structural, and it is worth understanding before it happens to you. **There is no
single Noir toolchain.** There are two programs, from two repositories, installed by two different
installers, released on two different cadences, meeting at one file format. This lesson is about that
seam — what crosses it, why it exists, and what the portability it promises is actually worth in
2026.

## Two binaries, one file

Follow the artifacts rather than the commands. The documented flow is four steps:<Cite src="noir-docs-quickstart" />

```text
nargo new hello_world     # scaffold: Nargo.toml + src/main.nr
nargo check               # generate Prover.toml, the input file
nargo execute             # compile to target/hello_world.json  (ACIR)
                          # and execute to target/hello_world.gz (witness)
bb prove -b ./target/hello_world.json \
         -w ./target/hello_world.gz --write_vk -o target
bb verify -p ./target/proof -k ./target/vk
```

The seam is visible in the argument list. `bb` is handed two files and knows nothing else about your
project: the compiled circuit and the witness.<Cite src="noir-docs-quickstart" /><Cite src="bb-docs-getting-started" />
It has never seen your `main.nr`. It does not know your variable names. Everything it needs was
serialised by `nargo` into that JSON, and that serialisation is ACIR.

Two things follow immediately.

**Your circuit's source and your circuit's cost live on opposite sides of a wall.** `nargo` can tell
you how many ACIR opcodes it emitted; only the backend can tell you how many gates those become. The
`nargo info` command bridges the gap by reporting both — its documented output per circuit is the
number of ACIR opcodes and the final number of gates a backend uses.<Cite src="noir-docs-nargo-commands" />
That is a lesson of its own, three lessons from here.

**The witness is a separate artifact from the proof, and only one of them is secret.** `nargo execute`
produces the witness from your inputs; `bb prove` consumes it. To verify, the docs point out, you do
not need the witness — as they put it, that would defeat the purpose.<Cite src="bb-docs-getting-started" />
The witness file on disk is the private data. Treat it like a key.

<Aside kind="note">
**Where the public inputs go.** Barretenberg proofs usually append the public inputs to the beginning
of the proof, and the guides provide commands to split the proof and the public inputs when
needed.<Cite src="bb-docs-getting-started" /> The Solidity verifier takes them as a separate
argument — its entry point is `verify(bytes calldata _proof, bytes32[] calldata _publicInputs)` —
and `bb` writes `proof` and `public_inputs` as separate binary files, each splittable into 32-byte
field-element chunks.<Cite src="bb-docs-solidity-verifier" /> One concept, two layouts. That gap is
the subject of the last lesson in this module, and it is a common source of rejected proofs.
</Aside>

## ACIR, and what "backend-agnostic" is worth

ACIR is the Abstract Circuit Intermediate Representation: a description of constraints that does not
commit to a proving backend. The Noir documentation states the design goal plainly — Noir is designed
to be proving-backend agnostic, which means you can choose different backends to prove and verify
your programs, and the corresponding workflows could differ — then uses Barretenberg as its
example.<Cite src="noir-docs-quickstart" /> Barretenberg describes the handshake from its own side:
Noir programs compile into ACIR, Barretenberg takes the ACIR instructions and converts them into a
circuit representation, computes a witness from actual input values, generates the proof, and
verifies it — including on-chain via Solidity verifiers.<Cite src="barretenberg-docs" />

Now hold that claim at arm's length, because the honest statement is narrower than the marketing
version.

**What is established:** ACIR exists, it is the documented interface, and the two sides describe it
identically. The separation is real, and it is why a Noir circuit is not textually coupled to a
proving scheme.

**What is not established:** that swapping backends is a thing anyone does in production. This module
found no evidence either way about whether non-Barretenberg ACIR backends are production-viable in
2026, and the documentation for both halves treats Barretenberg as the path. Treat portability as a
**design property rather than a demonstrated one**, and do not plan a migration around it.

The tooling itself hints at how tight the coupling is in practice. `bbup` is described as a
versioning tool that installs arbitrary versions of Barretenberg **as well as versions compatible
with installed Nargo versions**.<Cite src="barretenberg-docs" /> An interface that needed a
compatibility lookup between the two sides is an interface that is still moving.

## Barretenberg: what is actually proving your circuit

Barretenberg, invoked as `bb`, is a C++ library implementing zk-SNARK proof systems, cryptographic
primitives and supporting infrastructure; its own getting-started page describes it as an optimised
elliptic-curve library for the bn128 curve and a PLONK SNARK prover, standalone but designed to be
used with Noir.<Cite src="barretenberg-docs" /><Cite src="bb-docs-getting-started" />

Its primitives are worth skimming once, because they tell you which operations are cheap. Elliptic
curve operations over BN254, Grumpkin and secp256k1; Blake2s, Blake3s and Keccak/SHA-3; Schnorr and
ECDSA signatures; Pedersen commitments; KZG and IPA polynomial commitment schemes; the sumcheck
protocol with and without zero-knowledge; ROM and RAM memory operations; Plookup lookup tables; and
efficient multi-scalar multiplication.<Cite src="barretenberg-docs" /> Anything on that list is a
primitive the backend has already specialised. Anything not on it, you will be building out of field
arithmetic.

### The proving schemes, and their names

This is the part where 2023-era tutorials will actively mislead you.

The documentation lists three: **UltraPlonk**, described as a legacy version of PLONK; **UltraHonk**,
a newer and more efficient PLONKish proving system offering faster proving, smaller proofs, reduced
memory use and better recursive proving; and **ClientIVC**, a scheme optimised for Aztec client-side
smart contract execution.<Cite src="barretenberg-docs" /> The JavaScript library's page frames the
same set slightly differently, naming UltraHonk as the current recommended proof system with various
hash-function options, MegaHonk as an alternative Honk implementation, and ClientIVC for
Aztec-specific client-side proving.<Cite src="bb-docs-browser" />

So: if a tutorial tells you to pass a `plonk` backend flag, it is describing a world two naming
generations back. **UltraHonk is the general-purpose scheme for standalone Noir circuits.**

<Aside kind="warn">
**Names are still moving, and this module will not pretend otherwise.** The auto-generated CLI
reference read on 26 August 2026 — stamped as generated on 13 January 2026 — lists the `--scheme`
options for `bb gates`, `bb prove`, `bb check` and `bb write_solidity_verifier` as
`chonk`, `avm` and `ultra_honk`.<Cite src="bb-docs-cli-reference" /> "Chonk" does not appear in the
prose documentation's proof-system section, which names UltraPlonk, UltraHonk and
ClientIVC.<Cite src="barretenberg-docs" /> The reference does mention it in passing — `bb check`
notes that for Chonk it checks the verification keys in the folding stack, which is accumulation-scheme
language.<Cite src="bb-docs-cli-reference" /> This module does not have a source that reconciles the
two lists, so it does not claim one. **Read `bb --help` on the version you installed.** That is the
only statement about scheme names that will still be true when you read this.
</Aside>

### The oracle hash is a deployment decision

One flag deserves its own paragraph because getting it wrong produces a working proof that the wrong
verifier rejects. `--oracle_hash` selects the hash function standing in for the verifier's challenge
generation, with three documented options and a stated purpose for each: **Poseidon2** for proofs
intended to be verified inside another circuit; **Keccak**, optimised for verification in an Ethereum
smart contract, where it has a privileged position because of the EVM precompile; and **Starknet**,
for verification in a Starknet contract via the Garaga library.<Cite src="bb-docs-cli-reference" />

The Solidity verifier guide makes the consequence concrete: you must pass `--oracle_hash keccak` when
generating the verification key **and** when proving, to instruct `bb` to use Keccak, which is more
optimal in Solidity.<Cite src="bb-docs-solidity-verifier" /> Two commands, same flag, and a mismatch
between them is a proof and a verifier that were built for different challenge derivations.

Read it as a target-environment choice made at proving time — the same category of decision as
picking an ABI encoding, and about as forgiving.

## Maturity: what "1.0.0-beta" means for your repository

Noir has not shipped a stable 1.0.

Read on **26 August 2026**, the documentation's version selector shows `v1.0.0-beta.26` as the
current versioned release, with `v1.0.0-beta.25`, `v1.0.0-beta.24` and `v1.0.0-beta.23` still
selectable alongside a `dev` build.<Cite src="noir-docs-quickstart" /> The GitHub release feed on the
same day is a run of dated `nightly-YYYY-MM-DD` pre-releases.<Cite src="noir-releases" /> Reports of
the exact current beta number have disagreed across sources, so read it from the releases page or
your own `noirup` rather than from any lesson text — including this one. No stable 1.0 date is
committed anywhere this module could find. Do not plan against one.

### The pinning discipline, and a live example of why

`noirup` is the endorsed installer, and it takes an explicit version: `noirup --version <version>` for
a specific release, `noirup --version nightly` for the latest nightly, plus options to build from a
branch, a fork, a pull request, a commit or a local path.<Cite src="noir-docs-installation" /> `bbup`
does the same job for the backend.<Cite src="barretenberg-docs" /> **Pin both.** They version
independently, and a mismatch fails in ways that do not name versions.

The clearest evidence that this is not theoretical is in the documentation itself. The NoirJS web-app
tutorial — served on the `v1.0.0-beta.26` docs site — tells you that you will need `nargo` version
`1.0.0-beta.20`, and has you install `@noir-lang/noir_js@1.0.0-beta.20` alongside
`@aztec/bb.js@3.0.0-nightly.20251104`, with an explicit note that these versions work together and
that you can also try older or later ones.<Cite src="noir-docs-noirjs" /> A tutorial published under
one compiler version, pinned to another, against a backend package on an entirely different version
line — the C++ CLI documentation carried a `v0.87.0` badge the same day.<Cite src="bb-docs-cli-reference" />

That is not sloppiness. It is what a pre-1.0 ecosystem looks like from the inside, and the correct
response is a repository where a fresh clone builds without guesswork: exact `nargo` version, exact
`bb` version, exact npm package versions, recorded together, changed together, with a note about what
broke last time.

<Aside kind="note">
**One platform caveat, cheap to hit and cheap to avoid.** The default backend does not ship Windows
binaries, so Noir cannot be installed natively on Windows; the documented path is Windows Subsystem
for Linux.<Cite src="noir-docs-installation" /> Worth knowing before you write onboarding docs for a
mixed team.
</Aside>

### What pre-1.0 means for correctness, not just convenience

Version churn is an inconvenience. The maturity question that matters is different: how much
attack surface has been examined, and what happens when the answer turns out to be "not enough".

The ecosystem provided its own data point during the month this lesson was written. On 7 August 2026
Aztec disclosed a critical vulnerability in its V5 Alpha proving system, found on 27 July 2026
through internal AI-assisted auditing, in which an attacker might construct a proof that passes
verification for a transaction the network should reject.<Cite src="aztec-v5-proving-vulnerability" />
The disclosure states that internal and external human audits had completed, that contributors
continue AI-assisted auditing, and that Alpha is the period for identifying faults before production
deployment.<Cite src="aztec-v5-proving-vulnerability" />

That is Aztec's network-level proving system rather than the standalone Noir-plus-Barretenberg path
you are learning, and the distinction is real — do not carry the finding across as a claim about
`bb prove` on your own circuit. Carry the *posture* instead. Audited, actively maintained,
first-party proving code shipped a soundness bug, and the disclosure is candid that historical chain
activity cannot establish whether it was exploited.<Cite src="aztec-v5-proving-vulnerability" />
Software at this maturity level earns a defensive review budget, and the parts of your system that
would fail silently deserve most of it.

<Check type="explain" concept="barretenberg-backend">
A colleague opens a pull request adding a Noir circuit to your repository. The README says:

```text
Install: `noirup` && `bbup`
Prove:   `nargo execute && bb prove -b target/circuit.json -w target/circuit.gz`
Verify:  deploy Verifier.sol from `bb write_solidity_verifier`
```

Name three things that will go wrong for the next engineer who clones this, and the one-line fix for
each.

<Answer>
**1. Neither tool is pinned, so the next clone gets whatever is current.** `noirup` and `bbup` with
no arguments install the latest; the documented mechanism for reproducibility is
`noirup --version <version>` and the equivalent for `bbup`, which also offers to select a Barretenberg
version compatible with the installed Nargo.<Cite src="noir-docs-installation" /><Cite src="barretenberg-docs" />
*Fix:* record both exact versions in the README and in CI, and install with the explicit version
flags.

**2. The proof and the verifier will be built for different challenge hashes.** The Solidity verifier
path requires `--oracle_hash keccak` on **both** the verification-key generation and the proving
step, because Keccak is the option optimised for verification in an Ethereum smart
contract.<Cite src="bb-docs-solidity-verifier" /><Cite src="bb-docs-cli-reference" /> The `bb prove`
line above passes no such flag, so it will produce a proof against the default oracle hash while the
contract expects the Keccak variant. *Fix:* add `--oracle_hash keccak` to both commands, and write
the verification key explicitly rather than relying on a default.

**3. `bb write_solidity_verifier` needs a verification key, and this README never produces one as a
separate artifact.** The documented sequence is `bb write_vk -b ./target/<name>.json -o ./target
--oracle_hash keccak` followed by `bb write_solidity_verifier -k ./target/vk -o ./target/Verifier.sol`.<Cite src="bb-docs-solidity-verifier" />
*Fix:* make the verification key a named build artifact, because it is the thing the deployed contract
is derived from and therefore the thing that must not drift.

**A fourth, if you want the pull request to be genuinely reproducible:** nothing here records a gate
count. Add `nargo info` output to CI, so a change that quietly triples the circuit shows up as a diff
rather than as a support ticket.<Cite src="noir-docs-nargo-commands" />
</Answer>
</Check>

## What this unlocks

**Next lesson** takes the one decision this pipeline makes that has no compile-time safety net: which
inputs the verifier gets to see. Everything in this lesson was mechanical — files, flags, versions,
all of it failing loudly when wrong. Input visibility fails quietly, and the failure is a published
secret.

**Two lessons on**, the seam you just learned becomes the reason gate counts confuse people. `nargo`
reports one number, the backend reports another, they measure different layers, and an optimisation
can move them in opposite directions. You now know why: they are on different sides of ACIR.

**And in the repository you build**, the transferable practice is the one this ecosystem forces
early. Two independently versioned tools meeting at a serialised interface is not a ZK-specific
shape — it is every compiler-plus-runtime split you have worked with. What is unusual here is only
that the interface is young enough that the compatibility matrix is still published as prose in a
tutorial rather than enforced by a lockfile. Write the lockfile yourself.
