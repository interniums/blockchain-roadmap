The Noir documentation's own web-app tutorial ships this circuit, and it is a good one to think
about because it is almost right:<Cite src="noir-docs-noirjs" />

```rust
fn main(age: u8) {
    assert(age > 18);
}
```

One input, private by default — all primitive types in Noir are private unless marked
otherwise.<Cite src="noir-docs-data-types" /> No public inputs at all. It proves, it verifies, and the
tutorial is correct that it demonstrates the mechanism: the verifier confirms the prover's claim
without knowing the prover's private inputs.<Cite src="noir-docs-quickstart" />

Now put it in a product. A contract receives this proof and grants access. What has it learned?

**That somebody, somewhere, knows a number greater than 18.** Not that *this caller* does. Not that
the number came from a credential anyone issued. Not that it has not been used before. The proof is
true and completely unbound — anyone who obtains the bytes can submit them, because nothing in the
statement mentions who is submitting.

That is the shape of the mistake this lesson is about, and it runs in both directions. Publish too
much and you have leaked a secret with no warning from any tool. Publish too little and you have a
valid proof of a statement nobody needed proved.

## The mechanics, in one page

Every value in a Noir circuit is one of two things. **Private** means known only to the prover and
used to satisfy constraints — the documentation also calls private values *witnesses*. **Public**
means known by both prover and verifier.<Cite src="noir-docs-data-types" /> A public value travels
with the proof and forms part of the statement the verifier attests to; Barretenberg proofs usually
append the public inputs to the beginning of the proof itself.<Cite src="bb-docs-getting-started" />

The rules are short:

- **Everything is private by default.** All primitive types, including individual fields of compound
  types, are private unless marked otherwise; mark a value private when it should be known only to
  the prover.<Cite src="noir-docs-data-types" />
- **`pub` opts a value into visibility**, and visibility is handled **per variable**, so one input
  can be private and the next public in the same signature.<Cite src="noir-docs-data-types" /> Every
  value in Noir is fundamentally composed of field elements, so the split is about disclosure, not
  representation.<Cite src="noir-docs-fields" />
- **Public types can only be declared through parameters on `main`.**<Cite src="noir-docs-data-types" />
  There is no way to mark something public deeper in the call graph; the boundary is the entry point,
  which is exactly where you want it to be reviewable.
- **The return value is public too.** `main`'s return must be `pub`,<Cite src="noir-docs-quickstart" />
  and it reaches the verifier as a public input — a circuit has no notion of a return value, so
  Barretenberg documents the return as syntactic sugar that is passed as an input to the circuit and
  checked at the end of the program.<Cite src="bb-docs-solidity-verifier" /> Barretenberg is the side
  that turns ACIR into a circuit representation and produces the proof, so its layout rules are the
  ones a deployed verifier obeys.<Cite src="barretenberg-docs" />

```rust
fn main(x: u32, y: pub u32) -> pub u32 {
    x + y
}
```

In that signature `x` is private while `y` and the returned `x + y` are public.<Cite src="noir-docs-data-types" />
Two of the three values in a three-value program are published, and nothing about the code's
appearance signals it more loudly than a three-letter keyword.

<Aside kind="warn">
**One keyword, two unrelated meanings.** The documentation flags this directly: `pub` applied to a
type, as in `pub Field`, is a visibility modifier telling the *prover* whether a value should be made
known to the verifier. `pub` applied to a function, as in `pub fn foo()`, is the ordinary
module-visibility modifier telling the *compiler* whether the function is reachable from other Noir
programs.<Cite src="noir-docs-data-types" /> Same token, different subsystems, no relationship. In a
code review, `pub` on a parameter is a privacy decision and `pub` on a function is not, and reading
them at the same speed is how the first kind slips through.
</Aside>

### Two subtleties that decide how you review a diff

**Visibility is part of the circuit; values are not.** Changing the value of a public type does not
change the circuit — and the same is true for private types.<Cite src="noir-docs-data-types" /> So
the interface a verifier is compiled against is fixed by the *signature*, and a diff that changes only
`pub` markers is a diff that changes the deployed verifier, even though it changes no logic. Review
signature changes the way you review a storage-layout change in an upgradeable contract.

**Public values are treated no differently while proving.** The documentation is explicit that public
data types are handled just like private ones apart from the fact that their values are revealed in
the proofs generated.<Cite src="noir-docs-data-types" /> There is no separate code path, no extra
check, no warning. The word "public" does nothing at compile time except record where the value ends
up.

And where it ends up is unambiguous. The docs' own note: for public values in programs paired with
smart-contract verifiers, once proofs are verified on-chain the values can be considered known to
everyone with access to that blockchain.<Cite src="noir-docs-data-types" /> The Solidity verifier's
entry point takes them as a plain array — `verify(bytes calldata _proof, bytes32[] calldata _publicInputs)` —
so they arrive as calldata, permanently, in the clear.<Cite src="bb-docs-solidity-verifier" />
`bb write_solidity_verifier` derives that contract from the verification key, and `bb` also writes
the public inputs as their own `public_inputs` file next to the proof, in a fields-compatible
binary format splittable into 32-byte chunks — one chunk per field
element.<Cite src="bb-docs-solidity-verifier" />

## Choosing the split: a worked signature

Take the age check and make it something a product could deploy. The requirement: prove that the
caller holds a credential, issued by a known issuer, whose birthdate implies an age over a threshold,
and that this credential has not been used for this action before.

**Subgoal: list every value the relation mentions, before deciding anything.** Birthdate. Issuer
signature. Issuer public key. Merkle path and leaf, if membership is by tree. The tree root. Today's
date. The threshold. A nullifier. The address that will act on the result.

**Subgoal: for each value, ask what the verifier must be able to *compare it against*.** That is the
whole test. A public input earns its place only if some party — the contract, the chain, the caller —
already holds the value it must agree with.

| Value | Visibility | Why |
|---|---|---|
| Birthdate | private | The secret, and a witness in the proof-system sense.<Cite src="noir-docs-data-types" /> |
| Issuer signature | private | Reveals which credential; nothing checks it externally. |
| Issuer public key or credential root | **public** | The contract holds the trusted issuer set; the proof must be bound to it, not to an issuer the prover chose. |
| Today's date, or a block reference | **public** | The contract must confirm the freshness claim against something it can see. A prover-chosen "today" is not a date. |
| Threshold | **public** | Policy, not secret. Making it private lets the prover pick the policy. |
| Nullifier | **public** | The contract stores and checks it. A private nullifier prevents nobody from anything. |
| Caller address | **public** | Binds the proof to this actor. Without it, the proof is bearer paper. |

One typing note while you are here: a birthdate compared against a threshold is a comparison, and
comparison operators require the upper bound to have a known bit size, which is why this value wants
a sized integer type rather than a bare `Field`.<Cite src="noir-docs-fields" />

**Subgoal: re-read the private column as an attack surface.** Every value on the private side is a
value the prover supplies and the circuit must constrain. That is the next lesson's subject, and the
two lists are the same list seen from two angles: what leaks, and what must be pinned down.

Now revisit the opening circuit. `fn main(age: u8)` has an empty public column. Nothing to compare
against, nothing bound, so the proof means "a valid `age` exists" and any holder of the bytes can
present it. Adding a public issuer root and a public caller address turns the same private
computation into a statement about a specific person under a specific policy — without revealing the
birthdate, which was the requirement all along.

<Aside kind="note">
**The ordering is part of the contract, and it is easy to get wrong.** The verifier expects the
public-input array in exactly the layout the circuit derived, and Barretenberg documents two rules
that surprise people. First, the return value is appended: a `main` with two public inputs and a
public return expects an array of **length three**, ordered `[in1, in2, return]`, and passing only
two produces an error such as `PUBLIC_INPUT_COUNT_INVALID(3, 2)`.<Cite src="bb-docs-solidity-verifier" />
Second, structs are flattened into a one-dimensional array, so a public `Nested` containing a
`Type1` and a `bool`, sitting between two public `Field`s, arrives as
`[x, nested.t1.val1, nested.t1.val2, nested.is_true, y]`.<Cite src="bb-docs-solidity-verifier" />
A count mismatch is the good failure — it reverts. A *reordering* that still type-checks as
`bytes32[]` is the bad one, and the last lesson in this module deals with it.
</Aside>

## The circuit boundary is not the privacy boundary

This is the correction that matters most, because the `pub` keyword looks like the whole story and
is not.

A circuit's visibility split decides what appears in the proof's public inputs. It decides nothing
about what your *application* publishes. Work through what an observer sees even when every sensitive
value is correctly marked private:

- **The nullifier.** Public by necessity — it is what prevents reuse. Its value is a pseudonym, and
  two actions carrying the same nullifier are linked forever.
- **Amounts and timing.** If the surrounding transaction moves value, the amount is on-chain. If the
  proof is submitted seconds after a deposit, the correlation is free.
- **Who submitted it.** The transaction's sender is public. A privacy design that hides the witness
  and publishes the submitter has hidden the wrong half — which is why relaying exists, and why
  [relayers](/c/relayer) carry their own trust and metadata questions.
- **How many people could have produced it.** A proof over a set of five is a proof about five
  people. The [anonymity set](/c/anonymity-set) is a property of your data, not of your cryptography.

The Aztec model is a useful contrast to hold in mind: private state expressed as notes and nullifiers,
with the privacy properties designed at the protocol and application layer rather than falling out of
a keyword.<Cite src="aztec-docs" /> Whatever system you build, the same division applies. **The
circuit gives you confidentiality of the witness. Everything else about unlinkability, set size and
metadata is application design**, and none of it is checked by the compiler.

  reality="The circuit hides the witness. Nullifiers, amounts, timing, the submitting address and the size of the anonymity set all leak at the application layer, and the proof's own public inputs are permanent calldata."
  why="The visibility keyword is the only privacy control the language exposes, so it reads as the complete set of privacy controls."
  src="noir-docs-data-types"

<Check type="spot-bug" concept="private-vs-public-inputs">
A team ships a private voting circuit. Review the signature.

```rust
fn main(
    voter_secret: Field,          // the voter's key
    merkle_path: [Field; 20],     // membership in the electoral roll
    leaf_index: Field,
    proposal_id: Field,
    vote: Field,                  // 0 = against, 1 = for
    roll_root: pub Field,
    nullifier: pub Field,
) { /* ... */ }
```

Two things are wrong with this split. Name both, and say what an attacker does with each.

<Answer>
**Bug 1: `proposal_id` is private.** The contract must know which proposal a vote is being cast on,
and here it does not — the verifier attests to a statement in which the proposal is a value the
prover chose. An attacker produces one proof and replays it against every proposal, or produces a
proof for the proposal they like while the contract counts it toward another, because nothing in the
public inputs pins the two together. A public input earns its place when some party already holds the
value it must agree with, and the contract holds the proposal it is tallying. *Fix:* `proposal_id: pub Field`.

**Bug 2: `vote` is private.** This one looks like good privacy hygiene and is a correctness failure.
The contract's job is to increment a tally, and it cannot increment a number it cannot see. Left
private, the circuit proves "the voter cast a legal vote" and hands the contract nothing to count. It
also removes the only place a range check would be visible: with `vote` public, the contract can
reject anything outside `0` or `1`; with it private, that constraint has to exist inside the circuit
and its absence is invisible from outside. *Fix:* make the vote public — the confidentiality that
matters is the link between voter and vote, and that is supplied by hiding `voter_secret`,
`merkle_path` and `leaf_index`, not by hiding the ballot's content.

**What is right about the rest.** `roll_root` public is correct — the contract holds the roll and the
proof must bind to it. `nullifier` public is correct and necessary; the contract stores it to prevent
double voting, and a private nullifier prevents nothing.

**The follow-on question this signature does not answer**, and the reason the next lesson exists:
which of `voter_secret`, `merkle_path` and `leaf_index` are actually *constrained* inside the body?
Marking them private hides them. It does not stop the prover from choosing them. If the circuit
computes the nullifier from `voter_secret` but never proves that `voter_secret` corresponds to the
leaf at `leaf_index`, every private value in this signature is free for the taking and the roll
membership means nothing.
</Answer>
</Check>

## What this unlocks

**Next lesson** is the other half of this one. Here you decided what the verifier gets to *see*;
there you decide what the circuit gets to *trust*. The same private inputs that protect a user's
secret are values an adversarial prover picks, and the pattern that makes circuits fast — compute
outside, check inside — is the pattern that makes them unsound when the check is forgotten.

**In the last lesson of this module**, the public-input list you just designed becomes an ordered
array in Solidity calldata, and the contract calling the verifier has to build it in exactly the
right order from values it holds itself rather than from values the caller supplies. Getting that
wrong turns a correct circuit into a replayable one.

**And in any system with a confidentiality requirement**, the transferable move is the one in the
worked example: enumerate every value the relation mentions, and for each, name the party that
already holds the thing it must agree with. Values with such a party are public; values without one
are private; and a value you cannot place is a requirement you have not finished writing down.
