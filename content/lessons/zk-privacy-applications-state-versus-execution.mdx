Two systems describe themselves as private. In the first, you deposit into a pool, your balance is
hidden, and anyone can read the pool contract's source and see exactly what a withdrawal does. In
the second, a contract function runs on your laptop, and the chain learns only that *something*
happened and what its public consequences were.

Both claims are honest. They are claims about different things, and the gap between them determines
what you can build, how you write the contract, and who can integrate with it. Concealment comes in
layers, and the word "private" does not say which layer.

**Layer 1 and layer 2 come together in the note model**, and you already built them. Notes hide the
amounts; the append-only tree plus an unlinkable nullifier hides which record moved. A shielded pool
or a shielded-balance middleware delivers both, and the contract's own logic stays entirely
public — anyone can read the withdrawal circuit's signal list and the Entrypoint's
functions.<Cite src="privacy-pools-docs-core-concepts" /><Cite src="railgun-docs-privacy-system" />

**Layer 3 is a different system.** It requires that the code itself run somewhere the chain cannot
see, which means on the user's device, which means the chain receives a proof instead of an
execution.

## What layer 3 actually looks like

Read the architecture from the documentation of a system that implements it, because the components
make the trade concrete.

**Two state trees, not one.** Public and private data live in separate structures: a public data
tree and a note hashes tree, both storing state for every account directly as leaves — unlike an
account-trie model where a state trie contains per-account tries. Storage is *siloed* to each
contract, by slightly different mechanisms on each
side.<Cite src="aztec-docs-state-management" /> Public state works like any other chain's, stored and
updated by the sequencer.<Cite src="aztec-docs-state-management" /> Private state is the encrypted,
append-only note model of the last two lessons.

**Two execution environments.** Private functions execute and are proved **on the user's device**;
public functions execute in the network's public virtual machine when visibility is
needed.<Cite src="aztec-docs" /> The client-side half is a library — it runs in Node, in wallet
software or in a browser — and it generates the proofs of private function execution, then sends
those proofs along with any public function execution requests to the sequencer. **Private inputs
never leave the client.**<Cite src="aztec-docs-pxe" />

**A client that is a database.** That environment stores secrets and notes, orchestrates circuit
execution and proof generation, syncs the user's relevant network state from a node, and isolates
multiple accounts from each other.<Cite src="aztec-docs-pxe" /> It holds decrypted notes,
authorisation witnesses that let contracts act on the user's behalf, per-contract local storage, and
an address book of known senders so it can find logs addressed to the
user.<Cite src="aztec-docs-pxe" />

**And a chain that is not the EVM.** The system is explicitly not EVM compatible; it extends the
ecosystem with a new privacy-preserving virtual machine.<Cite src="aztec-docs" /> That is not a
detail. It is the reason layer 3 is a migration rather than an integration.

### The programming model changes, visibly

The clearest evidence that this is not a configuration flag is that the contract source looks
different. Storage declarations name the note structure and the owner explicitly, in a form like
`balance: Owned<PrivateSet<UintNote, Context>, Context>` — a collection of notes, wrapped in an
ownership type that binds them to an owner so nullifier computation and access control work
correctly.<Cite src="aztec-docs-state-management" /> Note types are a first-class concept, with
built-in kinds for a set of notes, a single replaceable note, and an immutable one, plus macros for
custom notes that need their own hash or nullifier
computation.<Cite src="aztec-docs-state-management" />

Functions carry visibility that determines *where they run*, not merely who may call them. A private
function executes on the client; a public one executes in the network VM; composing them is a
supported operation with its own semantics.<Cite src="aztec-docs" />

You have written client-side proving before — the [NoirJS](/c/noirjs) path, generating a proof in a
browser and handing it to a contract. Layer 3 takes that from a technique to an **execution model**:
it is not one clever feature of an application, it is where the application runs.

<Aside kind="note">
**Keys stop being one key.** A layer-3 account carries several specialised key pairs with distinct
purposes: nullifier keys for spending private state, incoming viewing keys for decrypting received
notes, and a signing key for authorisation that is entirely abstracted to the account contract. The
protocol keys cannot be changed once the account exists; the signing key
can.<Cite src="aztec-docs-keys" /> The documentation lists the reasons for the separation, and two of
them are product features rather than cryptographic ones: **selective disclosure** — sharing viewing
access without spending ability — and **damage limitation** when one key is
compromised.<Cite src="aztec-docs-keys" /> The next lesson is built on that first one.
</Aside>

### The cost nobody budgets: every interaction is a proving job

At layer 1–2 a user proves once, when they withdraw. At layer 3 a user proves **every time they touch
private state** — and on their own hardware, because that is what "private inputs never leave the
client" means.<Cite src="aztec-docs-pxe" />

That reshapes the performance conversation. The relevant latency is not the network's block time; it
is how long a phone takes to generate a proof for the function the user just tapped. The relevant
capacity limit is not throughput; it is what the weakest supported device can do. And the relevant
optimisation target moves from gas into constraint count, because constraints are now paid by users
rather than by an operator — which is why layer-3 documentation carries guidance on writing
contracts that are efficient for *proving* as a distinct concern from execution
cost.<Cite src="aztec-docs" />

Design consequence: a private function that would be a trivial loop in Solidity may be the thing that
makes your application unusable on a mid-range handset, and you will not discover it from a gas
report.

## What remains public at layer 3

Concealing execution does not conceal everything, and the residue is worth listing because product
teams routinely assume it is empty.

| Still visible | Why |
|---|---|
| That a transaction occurred, and when | It is in a block |
| Its fee, and who paid it | Fees are settled publicly |
| How many note hashes and nullifiers it produced | Those are appended to public trees |
| The entire public half of a hybrid call | Public functions run in the public VM by design |
| Everything settled to L1 | The rollup publishes to Ethereum |
| What your client asked the node for | The node learns which data you are interested in |

That last row is the vendor's own documented trade-off, recorded as a known limitation with running
your own node as the mitigation.<Cite src="aztec-docs-pxe" /> It is the honest version of a fact that
applies to every layer: **hiding execution from the chain does not hide it from the infrastructure
you use to reach the chain.**

## Choosing between the layers

The layers are not a maturity ladder. They are different products with different costs, and the
right one depends on what must be hidden from whom.

The decision usually comes down to one question: **is the confidential thing the amounts, or the
logic?** A payroll product hides amounts and recipients; the fact that it is a payroll contract is
not a secret, and layer 1–2 is sufficient. A sealed-bid auction, a private order book, or a game with
hidden state needs the *logic's inputs* concealed while it runs, and no amount of value-hiding
provides that.

<Check type="explain" concept="private-execution-vs-private-state">
Three product requirements land in the same planning session. For each, say which layer it needs and
what the team is signing up for.

```text
A. A treasury wants its stablecoin holdings and payments hidden from competitors.
B. A sealed-bid auction where bids stay secret until reveal, with no auctioneer
   able to peek.
C. A lending market where positions are private but liquidations still work.
```

<Answer>
**A needs layer 1–2, and is the easy one.**

What must be hidden is amounts and counterparties, not the fact that a treasury moves money. A
shielded-balance system over the chains they already use delivers that with no VM
migration.<Cite src="railgun-docs-privacy-system" /> What they are signing up for: a stateful wallet
that tracks notes, a relayer or sponsored-gas path so withdrawal addresses are not funded from
identified ones, and the anonymity-set analysis from the previous lesson — because a treasury's
amounts are large and therefore distinguishable, which is the case where the funnel is narrowest.

**B needs layer 3, or a commitment scheme, depending on one detail.**

The classic answer is commit–reveal: publish a commitment to your bid, reveal later. That needs no
private execution at all, and it is the right answer if every bidder can be relied on to show up for
the reveal. The failure mode is a bidder who does not reveal — you cannot force them, so the
mechanism needs bonds or a fallback.

If the auction must *settle without a reveal phase* — the winner determined while every losing bid
stays secret forever — then the comparison logic itself has to run on hidden inputs, which is layer 3
territory: contract logic executed on the client with only a proof and the public effects
published.<Cite src="aztec-docs-pxe" /> Signing up for: a different chain, a different language, and
proving on user devices for every bid.

**C is the hard one, and the honest answer is that the requirement is partly self-contradictory.**

Liquidation requires *somebody* to be able to determine that a position is unhealthy, and to act on
it before it becomes insolvent. If positions are fully private, either the owner must prove their own
health periodically — and a defaulting owner simply stops proving, at exactly the moment you need
them to — or some party must hold viewing access, which reintroduces a trusted observer.

Workable shapes exist, and each concedes something: a health proof required on a schedule with a
liquidation-on-timeout rule; over-collateralisation deep enough that stale information is tolerable;
or a designated keeper set with viewing keys and a bond. Each moves the privacy boundary rather than
holding it. The useful answer in the planning session is to say which concession the product can
live with, because "private positions and permissionless liquidation" is asking one system to both
hide and reveal the same fact.

**The general move all three share.** Write down what is hidden *from whom*, then check whether any
required participant is on the wrong side of that line. Layer 3 lets you hide execution from the
chain; it does not let you hide a fact from a party whose job depends on knowing it.
</Answer>
</Check>

## What this unlocks

**Next lesson** takes up the thread the key architecture opened: separating the ability to read from
the ability to spend is what makes voluntary disclosure possible, and voluntary disclosure is the
whole of the compliance story these systems actually offer. You will see two deployed shapes of it,
the argument behind them, and why that argument is about incentives rather than cryptography.

**In architecture reviews**, the layer question is the first one to ask and it is usually skipped.
"Private" without a layer is a mood. Naming the layer immediately settles whether you are adding a
path to an existing product or starting a different one.

**And the general lesson is about what a word hides.** Two teams can agree completely that a system
should be private, mean different layers, and discover the disagreement only after one of them has
committed to a VM. The cheap fix is a table like the one above, written before the decision rather
than after.
