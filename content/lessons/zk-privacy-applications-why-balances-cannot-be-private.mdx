treasury address. What has just been published?

Every salary at that company is now a permanent public fact, joined to a stable identifier for each
employee, in an archive nobody can edit. Anyone who learns one employee's address — from an ENS
name, an NFT, a donation, a single conversation — learns their salary, their raise history, and by
subtraction everyone else's relative standing.

The reflex is to reach for encryption. This lesson is about why that reflex fails, and what the
systems that succeed do instead. The short version: **the leak is in the data model, not in the
interface**, so nothing you add above the data model repairs it.

Note what a working private system claims to conceal, because it is a list of four items rather than
one. Railgun's documentation states its scope as privatising sender, recipient, token type and
amount.<Cite src="railgun-docs-privacy-system" /> Encryption of the payload addresses exactly one of
those four.

## Four attempts to encrypt a balance, and how each one dies

Take the reflex seriously and push it. You know [accounts](/c/account) and storage slots cold, so
these are quick.

**Attempt one: encrypt the calldata.** Send the transfer with the recipient and amount encrypted.
The contract cannot execute it — it needs the plaintext to decrement one slot and increment
another. Whoever decrypts it in order to act on it now knows everything. You have moved the leak to
a party, which is a custodian, which is the thing you were avoiding.

**Attempt two: encrypt the balances themselves and prove the transfer with a circuit.** Now
`balanceOf` holds ciphertexts, and a proof asserts "the new ciphertexts are the old ones adjusted by
some amount, and the sender's balance did not go negative". This is genuinely constructible. It also
fails, for two reasons that have nothing to do with cryptography:

- **Concurrency.** A proof is generated against a specific current ciphertext. Two transfers to the
  same account, generated at the same time, both prove against the same starting value; only one can
  land, and the other is stale. A named mutable cell is a shared resource, and shared resources
  serialise. Your recipient's balance becomes a lock.
- **Access patterns.** Even with every value encrypted, the transaction *writes two storage slots*,
  and slot identity is public. An observer learns that account A and account B interacted, at this
  time, for some amount. Sender, recipient and timing — three of the four things you wanted hidden —
  survive perfect encryption of the fourth. The systems that solve this abandon per-account storage
  entirely: private state is stored as leaves of one tree covering every account, rather than as a
  state trie containing a smaller trie per account.<Cite src="aztec-docs-state-management" />

**Attempt three: hide the access pattern by touching every slot.** Read and write the entire balance
table on every transfer so no slot stands out. This works and it costs the gas of the whole table
per transfer. It is not a design; it is a proof that the problem is real.

**Attempt four: give up on named cells.** Stop representing value as "a number stored at the
location belonging to Alice". This is the one that works, and it is not a feature you add. It is a
different state model.

<Aside kind="note">
**This is not a hypothetical threat model.** Published academic work profiled and deanonymised
Ethereum users precisely by exploiting the account model's properties, using ENS identifiers as
ground truth and quasi-identifiers — patterns characterising only a small set of users — to link
addresses.<Cite src="arxiv-ethereum-deanonymization" /> The paper's framing is worth carrying: the
account-based model is *inferior to an unspent-output model from a privacy
perspective*.<Cite src="arxiv-ethereum-deanonymization" /> The next section is that observation
turned into a design.
</Aside>

## Notes: value as objects rather than as a counter

Replace the balance with a set of discrete **notes**. Each note is an object holding an amount and
an owner, and it is spent whole. If you know [UTXOs](/c/utxo-model) from the ledgers track, the
resemblance is exact and intentional.

Aztec's documentation gives the mechanics and the reason in two sentences. Private state "is
encrypted and owned by users who hold the decryption keys", and it uses an **append-only** data
structure, "since updating records directly would leak information about the transaction
graph".<Cite src="aztec-docs-state-management" /> To delete private state you do not overwrite it;
you add an entry to a nullifier set. Modifying state means nullifying the old record and creating a
new one, which gives private state an intrinsic unspent-output
structure.<Cite src="aztec-docs-state-management" />

Append-only is the whole trick. **Nothing is ever updated in place, so there is no slot whose change
identifies a participant.** Every transaction looks like the same operation: some entries appended
here, some appended there.

The analogy Aztec uses is cash, and it is the right one. To spend a five-dollar note on a
three-fifty purchase you destroy the five and create two new notes, one for one-fifty to yourself and
one for three-fifty to the recipient — and only you and the recipient know about the
three-fifty.<Cite src="aztec-docs-state-management" />

### What actually goes on chain

Notes are not published. **Commitments** to notes are — hashes of the note, appended as leaves to a
public [Merkle tree](/c/merkle-tree), with users proving they know the note's preimage when they
update private state.<Cite src="aztec-docs-state-management" /> Anyone can see that the tree grew and
by how much. Nobody can see what any leaf says.

Frameworks then hide the leaf-level bookkeeping behind ordinary-looking declarations: a collection of
notes standing in for a balance, a single replaceable note, or a note fixed at
initialisation.<Cite src="aztec-docs-state-management" /> The programming model does not require the
developer to think in leaves, which is exactly why it is easy to forget which properties the leaves
were providing.

You already know why a commitment needs more than a hash of its contents: without a salt, anyone can
guess a plausible value and check. A production commitment shows exactly what that salt turns into
when it also has to do other jobs. Privacy Pools defines its note as four fields, and a two-layer
hash over them:<Cite src="privacy-pools-docs-core-concepts" />

**Subgoal: account for each field.** `value` is the payload — and note that the same design supports
partial withdrawals and multiple asset types, so a note is not restricted to a fixed
denomination.<Cite src="privacy-pools-docs-core-concepts" /> `label` is a unique identifier derived
from a pool scope and a nonce, binding the note to a particular pool and deposit so it cannot be
replayed into a different context.<Cite src="privacy-pools-docs-core-concepts" /> `nullifier` is a secret that will
later be revealed in hashed form to mark this note spent — the mechanism of the next lesson. And
`secret` exists solely so that the nullifier is not derivable from anything public.

That is the salt, doing double duty: it hides the commitment's contents *and* it separates the
spend-marker from the commitment. Two properties from one extra field, and the second one is the
non-obvious one.

<Aside kind="warn">
**One structural detail worth stealing.** Aztec includes the contract address when computing note
hashes, so two different contracts cannot produce identical commitments even for identical
contents.<Cite src="aztec-docs-state-management" /> This is domain separation, and it is the same
discipline as a typed-data domain separator in signature schemes: without it, a commitment valid in
one context is valid in another, and a note from a worthless token contract can be spent as a note
in a valuable one.
</Aside>

### Proving ownership without naming the note

Given a public tree of commitments, how do you spend one?

By proving a statement of the form: *I know an index `i` and a note preimage such that hashing that
preimage yields the leaf at index `i`, and the Merkle path from that leaf reaches this published
root.* The index and the preimage are private inputs; the root is public.

Notice that this is a statement in the exact shape circuits are good at — hashing and a fixed number
of comparisons up a path — and that its hidden variable is *which leaf*. That single hidden variable
is the entire product. Everything else in this module is about how large the set of leaves it could
have been actually is.

### The bill for append-only: your wallet has to find its own money

There is a consequence of never naming an owner in state that hits product teams harder than the
cryptography does. If a note's contents are hidden and its commitment is an opaque leaf, **how does
the recipient learn they were paid?**

Nothing tells them. There is no `balanceOf` to call, because there is no cell with their name on it.
The systems that ship solve this three ways, and Aztec documents all three
plainly:<Cite src="aztec-docs-state-management" />

- **On-chain encrypted logs.** The standard route: the sender emits the note data encrypted to the
  recipient as part of the transaction, and the recipient finds it through a note-discovery
  mechanism. The data is public, the plaintext is not, and it costs data to publish.
- **Off-chain.** If you can reach the recipient directly, hand them the note data and let them store
  it. No on-chain cost at all, and a delivery guarantee you now own.
- **Self-created notes.** Change you pay yourself needs no broadcasting; you already have it.

Whichever route, the recipient's client is now **stateful**. Aztec's Private Execution Environment
stores notes locally after discovering and decrypting them, alongside the secrets needed to spend
them.<Cite src="aztec-docs-pxe" /> That is a genuine architectural change, and it produces
requirements no public-ledger wallet has: local storage that must be backed up, a sync process that
must not miss a note, and a recovery story in which losing your device can mean losing the ability to
prove you own money that is provably in the tree.

Railgun arrives at the same shape from the middleware side: its transaction system uses unspent
outputs implemented as a Merkle tree accumulator held inside the smart contract, with users holding a
private address alongside their public one.<Cite src="railgun-docs-privacy-system" /> Two addresses,
two sets of state, one user — and every integration has to know which is which.

**The design rule.** In an account model the chain remembers your balance for you. In a note model
*you* remember it, and the chain only lets you prove you are right. Budget for that in the client,
not in the contract.

## What is still public, and it is more than you think

The note model does not make a transaction invisible. It makes a specific link invisible. Enumerate

**The pool boundary is the privacy boundary.** Inside it, transfers are invisible. Crossing it in
either direction is a public event with an amount and a timestamp attached. A system that only ever
sees you deposit and withdraw has an easier problem than it looks, and the third lesson of this
module is about how much easier.

Bring that back to the payroll run. Moving it into a note-based system genuinely deletes the salary
table: twelve identical-looking appends, no amounts, no recipient addresses in state. What it does
not delete is the treasury's **deposit** — one public transfer of the month's total payroll into the
pool, on the same day each month — and each employee's **withdrawal** when they want to spend. The
sum going in is public. The sums coming out are public. If eleven employees leave their money inside
and one withdraws the day after payday, that withdrawal has a very small set of plausible sources.

Which reframes the design question. You have not bought "privacy"; you have bought *unlinkability
between a specific deposit and a specific withdrawal*, and its strength depends on how many other
deposits and withdrawals it is hiding among. That is a quantity, it varies by the hour, and it is
the subject of the third lesson in this module.

Railgun's own documentation states the resulting property honestly rather than marketing around it:
the level of privacy is a **function of** the number of unique shield interactions and users, the
value locked, and the volume of private activity.<Cite src="railgun-docs-privacy-system" /> That is a
vendor conceding that its cryptography is necessary and not sufficient, which is the correct thing to
concede.

<Check type="explain" concept="account-model-leaks-everything">
A product manager proposes: "Let's ship confidential payroll. We keep the same ERC-20, but the
contract stores each balance encrypted with the account owner's public key, and transfers carry a
zero-knowledge proof that the sender had enough. Same contract, same addresses, same integrations —
just encrypted numbers."

Explain what this does and does not achieve, and what would have to change to actually deliver the
product.

<Answer>
**What it achieves: amount confidentiality, and only against passive readers of state.**

The stored numbers are hidden. That is real, and for some use cases — a treasury not wanting its
holdings legible — it is most of the value.

**What it does not achieve: any of the other three fields.**

1. *Sender and recipient stay public.* The transfer writes two storage slots, and slot identity is
   derived from the address. An observer sees "the slot belonging to the treasury changed and the
   slot belonging to `0xabc…` changed, in this transaction". They have the payroll graph without
   decrypting anything. For salaries, the graph plus the *frequency* is already most of the harm.
2. *Timing stays public*, because the block does. Twelve transfers on the last working day of each
   month, from one address, is a pattern that identifies a payroll run without any amounts at all —
   and the academic profiling work uses exactly this class of signal, time-of-day and periodic
   activity, as a quasi-identifier.<Cite src="arxiv-ethereum-deanonymization" />
3. *Concurrency breaks.* Two payments into the same encrypted balance, proved against the same
   starting ciphertext, cannot both apply. Payroll is a burst of writes; several will be stale by the
   time they land, and the retry pattern is itself observable.

**What would have to change: the state model, not the storage.**

Stop keeping a named mutable cell per account. Represent value as notes committed to an append-only
tree, so every transaction is the same operation — append some leaves — and no slot identifies a
participant.<Cite src="aztec-docs-state-management" /> That is not a modification to the ERC-20; it is
a different contract with a different interface, different wallet requirements (the recipient must
discover and store their notes), and a different integration story for every downstream system that
currently calls `balanceOf`.

**The sentence to give the product manager.** "Same contract, just encrypted numbers" cannot work,
because the thing being leaked is not the numbers. Privacy on a public ledger arrives as a different
state model, and the cost of it is paid in integration surface, not in cryptography.

**And the honest caveat.** Even after the change, deposits into and withdrawals out of the private
system are public events with amounts and timestamps.<Cite src="railgun-docs-privacy-system" /> The
payroll product's real privacy question is what happens when twelve employees each withdraw their
salary to an exchange within a day of each other — which is the subject of two lessons from now.
</Answer>
</Check>

## What this unlocks

**Next lesson** answers the question this one left open. If notes are never revealed, the contract
cannot mark one as spent — it does not know which one you used. The mechanism that solves this is a
single published value, and it carries two independent requirements that are easy to state and
famously easy to get half-right. Getting the second one wrong leaves the double-spend protection
perfectly intact while destroying the only property the system exists for.

**In design work**, the transferable question is the one that killed attempt two: *what does this
operation touch, and is that observable?* Access patterns leak in databases, in caches, in
file systems and in encrypted search, for exactly the reason they leak here. A system that hides
values while revealing which record was read has hidden the easier half.

**And when a stakeholder asks for privacy**, the useful first move is not to discuss cryptography. It
is to write the four fields — sender, recipient, amount, timing — and ask which of them must be
hidden, from whom, and for how long. Different answers lead to genuinely different systems, and three
of the four cannot be delivered by encryption at all.
