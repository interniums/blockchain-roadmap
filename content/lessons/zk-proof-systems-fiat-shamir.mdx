On 13 April 2022, Trail of Bits published a coordinated disclosure of soundness-breaking
vulnerabilities in seven zero-knowledge proof implementations at once: ZenGo's `zk-paillier`, ING
Bank's `zkrp`, SECBIT Labs' `ckb-zkp`, Adjoint's `bulletproofs`, Dusk Network's `plonk`, Iden3's
`SnarkJS`, and ConsenSys' `gnark`.<Cite src="trailofbits-frozen-heart" /> They named the class
**Frozen Heart** — FoRging Of ZEro kNowledge proofs — and reported that the vulnerabilities let a
malicious user forge proofs for statements they could not
satisfy.<Cite src="trailofbits-frozen-heart" />

Not one of those was a break of the underlying mathematics. Every one was the same implementation
mistake in the same step: the transformation that removes the interactive verifier from the
protocol.

That step is the subject of this lesson, and it is the shortest piece of machinery in the whole
stack with the largest ratio of consequence to line count.

## Why an interactive protocol has a verifier at all

Almost every proof system in use has, underneath the polynomial machinery, the same three-move
shape.<Cite src="zkdocs-fiat-shamir" />

1. The prover sends a **commitment** derived from fresh randomness.
2. The verifier replies with a **challenge** drawn uniformly at random.
3. The prover sends a **response** computed from the commitment, the challenge and the witness.

The verifier's only creative act is step 2, and everything rests on it. Soundness comes from the
prover having had to commit *before* learning the challenge, so that a prover without a witness can
satisfy the verification equation only by getting lucky — one chance in the size of the challenge
space.<Cite src="zkdocs-fiat-shamir" />

Modern systems are the same structure repeated: the prover commits to polynomials, the verifier
sends an evaluation point, the prover opens there, and so on for several rounds. Formalised, this is
an interactive oracle proof, and the general fact is the same — the prover must be pinned down
before the randomness arrives.<Cite src="iop-paper" />

### The forgery, in five lines

Work the smallest concrete case: Schnorr's proof of knowledge of a discrete logarithm. Public group
generator `g`, public value `A = g^a`, and the prover claims to know `a`.

Honest protocol: prover picks random `v`, sends `V = g^v`; verifier sends challenge `c`; prover
sends `r = v - a*c`; verifier accepts if `V == g^r * A^c`.<Cite src="rfc-8235" />

Now suppose the prover learns `c` **before** choosing `V`. They do not need `a` at all.

```text
pick r  at random
pick c  at random          (or read it, if it does not depend on V)
set  V := g^r * A^c        (rearrange the verification equation)
publish (V, c, r)
```

The verifier checks `V == g^r * A^c` and it holds by construction. The forger never touched the
witness. There was never a moment at which they were committed to anything.

**That single rearrangement is the whole attack surface of this lesson.** Every Frozen Heart
variant is a version of it: find a value the verification equation depends on that the prover can
still choose after the challenge is fixed, and solve backwards.

## Fiat–Shamir: the prover computes the challenge

The transform is one sentence. Wherever the verifier would have sent fresh randomness, the prover
instead derives the challenge by hashing the transcript so far, and a hash function modelled as a
random oracle stands in for an honest verifier.<Cite src="zkdocs-fiat-shamir" /><Cite src="sok-zk-snarks-arxiv" />

Applied to Schnorr, RFC 8235 fixes it exactly: the challenge is redefined as
`c = H(g || V || A || UserID || OtherInfo)`, where `UserID` is a unique identifier for the prover and
`OtherInfo` is optional contextual data; the resulting proof is
`{UserID, OtherInfo, V = g^v mod p, r = v - a*c mod q}`.<Cite src="rfc-8235" />

Read that hash input against the forgery above. `V` is in it. The forger's move required choosing
`V` after `c` was known, and now `c` is a function of `V`, so choosing `V` re-randomises `c` and
destroys the construction. The prover can grind — try many `V` values hoping for a favourable `c` —
but that is a brute-force search over the challenge space, which is the security level.

## The rule, and the reasons people break it

Trail of Bits states the rule as a single sentence: the Fiat–Shamir hash computation must include
all public values from the zero-knowledge proof statement and all public values computed in the
proof — that is, all the random commitment values.<Cite src="trailofbits-frozen-heart" /> For the
Schnorr example they spell out that `h`, `g` and `q` from the statement all belong in the hash, and
so does the commitment `u`; a Frozen Heart vulnerability appears if the statement value or the
commitment is missing.<Cite src="trailofbits-frozen-heart" />

Their diagnosis of *why* it goes wrong so often is the part worth internalising, because it is a
documentation failure rather than a competence failure.

**Papers say "hash the transcript" without defining the transcript.** Trail of Bits singles out
PLONK: the authors do not explicitly explain how to compute the Fiat–Shamir transformation, but
instruct implementers to hash "the transcript", which is described elsewhere but never explicitly —
and several implementations got the computation wrong because of that
ambiguity.<Cite src="trailofbits-frozen-heart" /><Cite src="plonk-paper" /> They add that PLONK's
description is better than most.<Cite src="trailofbits-frozen-heart" />

**Sometimes the paper specifies something insecure.** The Bulletproofs vulnerabilities stem from a
mistake in the original academic paper, which recommended an insecure Fiat–Shamir generation; the
authors were contacted and updated that section.<Cite src="trailofbits-frozen-heart" />

**There are no test vectors.** Trail of Bits notes that these issues would be largely eradicated if
test vectors were widely available, because an implementation with a wrong transform would fail
against vectors from a correct one — and that producing them for all these systems seems
unlikely.<Cite src="trailofbits-frozen-heart" />

The disclosure timeline is itself instructive: reported to all affected parties on 18 March 2022,
with ZenGo, Dusk Network, Iden3 and ConsenSys patched and ING Bank's repository deleted by 12 April
2022, one day before publication.<Cite src="trailofbits-frozen-heart" />

<Aside kind="warn">
Notice which repositories are on that list. `SnarkJS` and `gnark` are not obscure — they are
mainstream tooling that a great deal of production circuitry passed through. If your instinct is
that this is a beginner's mistake, the evidence says otherwise. It is a specification-gap mistake,
and the people who avoided it mostly did so by having had the code audited.<Cite src="trailofbits-frozen-heart" />
</Aside>

## Boundaries, replay, and the rest of the transcript

Two further requirements are easy to skip because they are not about the proof system at all.

**Unambiguous encoding.** RFC 8235 requires a clear boundary between any two concatenated items
inside the hash, and recommends prepending each item with a 4-byte integer giving its byte
length.<Cite src="rfc-8235" /> Without that, two different transcripts can serialise to the same
byte string — `("ab", "c")` and `("a", "bc")` — and a value moved across the boundary is a value the
prover controls without changing the challenge. This is [domain-separated hashing](/c/domain-separated-hashing)
in a new setting, and the failure mode is the same one you have already met.

**Context, so the proof is not portable.** `UserID` is in RFC 8235's challenge specifically so that
one prover's proof cannot be replayed as another's, and `OtherInfo` exists so that protocols can
bind further contextual information — a protocol name, a timestamp — into the challenge, with the
format required to be fixed and explicitly defined by the protocol
specification.<Cite src="rfc-8235" />

This is the same discipline as the first lesson's public-input analysis, arriving through a
different door. Whether a value binds the proof to its context depends on it being *in the hashed
transcript*, and in a non-interactive proof the hashed transcript is where the public statement
lives. Chain id, verifying contract, epoch, nonce: if they are not in there, the proof is portable
to wherever those differ.

## What the transform assumes, stated honestly

Two limits, because overclaiming here is common and the second one is live research.

**Fiat–Shamir's soundness is proved in the random oracle model.** The argument treats `H` as a
perfectly random function that both prover and adversary can only query. Real hash functions are not
random oracles, and there exist contrived protocols that are sound interactively yet insecure once
Fiat–Shamir is instantiated with any concrete hash. So the transform is a heuristic with a proof in
an idealised model, not a theorem about SHA-256.<Cite src="sok-zk-snarks-arxiv" /> In practice it is
relied on everywhere; the honest framing is that it is a well-tested assumption rather than a
derivation.

**Multi-round protocols need their own analysis.** The five-line Schnorr case has one challenge.
A STARK has many rounds, and the low-degree test at its core is itself
interactive.<Cite src="stark-paper" /><Cite src="ethstark-documentation" /> Collapsing a many-round
protocol with Fiat–Shamir is not a simple repetition of the single-round argument: the adversary can
abandon a partial transcript and restart from any round, which is why the modern analyses are stated
round by round rather than in aggregate.<Cite src="ethstark-documentation" />

That is not a footnote in 2026. It is exactly where the security-bit numbers from the first lesson
came from and where they moved. The Ethereum Foundation's programme requires proof systems to be
measured with `soundcalc` against current bounds and known attacks, and asks separately for a
compact description of each team's recursion architecture with a sketch of its soundness, then a
formal security argument for it.<Cite src="ef-zkevm-security-foundations" /> The reason recursion
gets called out by name is that each recursive layer applies Fiat–Shamir again, inside a circuit,
and the transcripts have to be right at every level.

<Aside kind="note">
Grinding is the deliberate, benign cousin of the forgery above. A system can require the prover to
find a nonce making the challenge hash start with `k` zero bits, which costs the prover `2^k` work
per attempt and therefore multiplies the cost of *searching* for a favourable challenge by the same
factor — buying security bits at a price paid in prover time. The Foundation names grinding as one
of the techniques on the path to its security and proof-size targets.<Cite src="ef-zkevm-security-foundations" />
The mechanism only works because the challenge genuinely depends on everything the prover chose. It
is the same property, used offensively by an attacker and defensively by a designer.
</Aside>

<Check type="spot-bug" concept="non-interactivity-fiat-shamir">
A team implements a non-interactive proof of knowledge of a discrete log for a login flow. Their
challenge derivation is:

```text
c = sha256(A)          // A is the user's public value, g^a
```

The proof they publish is `(V, r)` and the server checks `V == g^r * A^c`.

Name the break, show the forgery concretely, and give the corrected derivation with a justification
for each added term.

<Answer>
**The break: the commitment `V` is not in the hash.** The challenge depends only on `A`, which is
known before the prover picks anything. So `c` is fully determined and public in advance, and the
prover retains complete freedom over `V`.

**The forgery.** Take any `A` for which you do not know the discrete log — a public key you found
on-chain, say. Compute `c = sha256(A)`. Pick `r` at random. Set `V = g^r * A^c`. Publish `(V, r)`.
The server's check `V == g^r * A^c` holds by construction. You have just logged in as someone whose
private key you have never seen. This is precisely the Frozen Heart pattern: a prover-chosen value
missing from the hash.<Cite src="trailofbits-frozen-heart" />

**The corrected derivation.**

```text
c = H( len(g)||g || len(V)||V || len(A)||A || len(UserID)||UserID || len(ctx)||ctx )
```

- **`V`** — mandatory. It is the commitment, and its absence is the entire bug. With it in the hash,
choosing `V` re-randomises `c` and the equation can no longer be solved backwards.<Cite src="rfc-8235" />
- **`A` and `g`** — the public values of the statement. Their absence lets a forger reuse one
transcript against a different statement or a different group.<Cite src="trailofbits-frozen-heart" />
- **`UserID`** — binds the proof to a prover, which is how RFC 8235 prevents replay of one user's
proof as another's.<Cite src="rfc-8235" />
- **`ctx`** — the session identifier, server name, or nonce for this login. Without it, a proof
captured from one login is valid for the next one and for a different service using the same scheme.
RFC 8235 provides `OtherInfo` for exactly this and requires the protocol to fix its format
explicitly.<Cite src="rfc-8235" />
- **The length prefixes** — RFC 8235 requires a clear boundary between concatenated items and
recommends a 4-byte length prefix on each.<Cite src="rfc-8235" /> Without them, two different
transcripts can hash identically, which restores a slice of the prover's freedom.

**What is not a fix.** Replacing `sha256` with a stronger or longer hash. The hash function was
never the weak point; the missing input was. This is the single most common wrong instinct when the
bug is first explained.
</Answer>
</Check>

## What this unlocks

**The practice exercise for this module** is exactly the forgery above, built and then fixed: a toy
sigma protocol with a deliberately weak transform, a forger that gets the verifier to accept a false
statement, and then the same forger failing against a transform that hashes the full transcript. Do
it. Reading the rearrangement and typing it are different amounts of understanding.

**Next lesson**: where the public parameters come from. Fiat–Shamir removed the verifier's
randomness from the protocol; the setup question is about a *different* piece of randomness, one
generated before any proof exists, and whose secrecy some systems depend on
forever.<Cite src="groth16-paper" />

**And in review**: you now have a second question to add to the public-input question. For any
non-interactive proof, ask what the challenge is a hash of, and check that list against two others —
everything the prover chose, and everything about the deployment context that must not be portable.
Anything on either list and missing from the hash is a finding.<Cite src="zkdocs-fiat-shamir" />
