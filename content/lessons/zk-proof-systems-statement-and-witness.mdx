Here is the only part of a verifier contract that decides whether your feature is secure.

```solidity
function verifyProof(
    uint256[8]  calldata proof,
    uint256[3]  calldata publicSignals
) external view returns (bool);
```

Three numbers. That array is the entire interface between what the chain believes and what the
prover claimed. Everything the prover was free to choose but that does *not* appear in
`publicSignals` is, from the contract's point of view, unconstrained — the prover picked it, and the
proof is perfectly happy about that. Most ZK bugs that reach production are not breaks of the
cryptography. They are a value that ended up on the wrong side of that array.

You have already made a proof and had a contract accept it in
[the previous module](/c/onchain-verification). This lesson is about what that acceptance means. Not
"the computation was correct" — that phrase is doing at least three jobs and each of them fails
differently.

## Every proof system is a claim about a relation

Fix the vocabulary first, because the rest of the track leans on it.

A proof system is defined over a **relation** `R`. A relation is a set of pairs, nothing more. One element of
the pair is the **statement** `x`, which is public: the verifier holds it, or can recompute it, or
finds it already committed on-chain. The other is the **witness** `w`, which the prover holds and
never sends. The prover's claim is exactly:

> I know a `w` such that `R(x, w)` holds.

That is the whole content of a proof. Not more. The system is characterised by three properties,
and it is worth writing them out because the differences between them are where the interesting
failures live.<Cite src="sok-zk-snarks-arxiv" />

- **Completeness.** If `R(x, w)` really holds and the prover follows the protocol, the verifier
  accepts. This is the property your tests exercise, and it is the one that almost never breaks
  silently — a completeness bug shows up as "my honest proof was rejected", which you notice.<Cite src="sok-zk-snarks-arxiv" />
- **Soundness.** If no `w` exists with `R(x, w)`, no prover can make the verifier accept, except
  with negligible probability.<Cite src="sok-zk-snarks-arxiv" /> This is the property your tests
  *cannot* exercise, because you would have to be the attacker to write the test.
- **Knowledge soundness.** Stronger than soundness: any prover that convinces the verifier must
  actually *know* a witness, in the formal sense that a witness can be extracted from it by an
  algorithm with the prover's code and the ability to rewind it.<Cite src="sok-zk-snarks-arxiv" />

Zero-knowledge is deliberately absent from that list. It is a fourth, separate property — Groth's
construction, for instance, states it as an additional feature of the scheme rather than as part of
what makes it a succinct argument<Cite src="groth16-paper" /> — and the next lesson is about the
damage caused by welding it onto the other three.

### Why "of knowledge" is not academic decoration

Take a relation that is trivially satisfied and see what plain soundness buys you.

`R(x, w)`: `sha256(w) == x`, where `x` is a 32-byte digest you are holding. For essentially every
`x` you will ever see, a witness *exists* — the hash function's output space is smaller than its
input space, so preimages exist in abundance. A proof of mere existence is therefore worthless: it
asserts something that is true whether or not the prover has any idea what the preimage is.

What you actually want is a proof that the prover **knows** one.<Cite src="sok-zk-snarks-arxiv" /> Knowledge soundness is the property
that turns "this statement is true" into "this party holds the secret", and that second thing is
what your feature is authorising on. You have already relied on this shape without the vocabulary:
an ECDSA signature is, in effect, a proof of knowledge of the private key for a given message. A
signature that only proved "some private key exists for this public key" would authorise nothing.

The formal device behind knowledge soundness is the **extractor**: an algorithm that, given
black-box access to a successful prover and the ability to rewind and re-run it with fresh
randomness, recovers the witness.<Cite src="sok-zk-snarks-arxiv" /> Nothing extracts anything at
runtime. The extractor is a proof technique, not a component you deploy. Its existence is what
licenses you to reason as though the prover held the witness.

## Drawing the line: which values are `x` and which are `w`

This is the first design decision in any ZK feature, it is made in about ten minutes, and it decides
what an attacker can do for the lifetime of the system. Work an example properly.

**The feature.** A gated mint. A user may mint exactly once if they are in an allowlist, and the
contract must not learn which allowlist entry they are.

**Subgoal: name the claim in English before naming any variable.** "I know an allowlist entry, and
its inclusion path into the allowlist that this contract already committed to, and I have not minted
against it before." Three clauses. Every clause is going to need a value on one side of the line.

**Subgoal: put on the public side everything the verifier must pin down itself.** The allowlist
root, because it is the thing the contract already knows and has committed to. The nullifier, which
is a deterministic function of the entry, published so that a second mint against the same entry
collides with a stored value. The recipient address, so that the proof is bound to *this* mint. That
is `x` — three field elements, which is what that `uint256[3]` was.<Cite src="zkdocs-fiat-shamir" />

**Subgoal: put on the private side only what the prover legitimately chooses.** The allowlist entry
itself, its index, and the sibling hashes along its
[Merkle path](/c/merkle-inclusion-proof). That is `w`.

**Subgoal: now attack your own line.** For each value in `x`, ask what happens if you move it to
`w`.

- Move the **root** to `w`. The circuit still proves "there exists a tree containing my leaf". The
  prover builds a tree of their own with themselves in it, proves membership, and the verifier
  accepts because the relation, as written, is satisfied. The proof is valid. The feature is gone.
- Move the **recipient** to `w`. The proof is now a bearer token. Anyone who sees it in the mempool
  can lift it and submit it with their own recipient, because nothing in the statement binds the
  proof to a destination. You have already met the shape of this bug: it is signature replay, and
  the fix is the same — bind the context into what is being attested. RFC 8235's non-interactive
  Schnorr proof does precisely this, fixing a unique prover identifier and further contextual data
  into the challenge specifically to prevent replay.<Cite src="rfc-8235" />
- Move the **nullifier** to `w`. Double-minting becomes free, because the contract has nothing to
  store and compare.

Each of those is a total break, and none of them is a break of the proof system. In all three cases
the cryptography did exactly what it promised. The relation was wrong.

<Aside kind="warn">
The reason this failure mode is so persistent is that all three broken designs pass every test you
would naturally write. The honest path still verifies; the wrong path is one that only an attacker
would take. Reviewing a ZK feature therefore starts at the public-input list and asks, value by
value, "what would the prover do with this if it were private?" — not at the circuit body.
</Aside>

## The word "proof" is a courtesy

Now the second half of the concept, and the part the industry's vocabulary actively works against.

Almost every deployed system is an **argument**, not a proof. The distinction is about who the
soundness guarantee holds against:

- A **proof** in the information-theoretic sense is sound against a computationally unbounded
  prover. No amount of computation forges one.
- An **argument** is sound only against a prover bounded by some computational budget. Given enough
  work, an argument *can* be forged — the security claim is that the work required is
  infeasible.<Cite src="sok-zk-snarks-arxiv" /> Both the pairing-based and the hash-based families
  are stated this way by their own authors.<Cite src="groth16-paper" /><Cite src="stark-paper" />

Both SNARKs and STARKs are arguments. The "AR" in each acronym is literally "argument". A
pairing-based SNARK's soundness rests on assumptions about a specific elliptic curve
group;<Cite src="groth16-paper" /> a STARK's rests on the security of a hash function modelled as a
random oracle, plus soundness bounds for the low-degree test at its
core.<Cite src="stark-paper" /><Cite src="ethstark-documentation" /> Neither is unconditional.

The practical translation is: **every deployed system has a security level in bits, those levels
differ between systems, and the number is a modelling result rather than a measurement.** That last
clause is where 2026 got uncomfortable.

### The 2026 turn: conjectured versus provable bits

Until recently, a security level quoted for a STARK-based system was often *conjectured*: derived
under a mathematical conjecture about the soundness of the underlying low-degree test rather than
from a bound anyone had proved. That was normal practice and it was disclosed in papers, if not in
marketing.

Then some of those conjectures were disproved. The Ethereum Foundation's December 2025 write-up puts
the consequence plainly: foundational conjectures have been mathematically disproven by researchers,
and each conjecture that falls takes bits of security with it — what was advertised as 100 bits
might actually be 80.<Cite src="ef-zkevm-security-foundations" />

The Foundation's response was to make the number auditable rather than asserted. It published
`soundcalc`, a tool that estimates a zkVM's security from its proof-system components and
parameters against current bounds and known attacks, <Cite src="ef-zkevm-security-foundations" /> and set milestones for the teams working on an
L1 zkEVM: integrate every proof-system component and every circuit with `soundcalc` by the end of
February 2026; reach 100-bit *provable* security with a final proof size of 600 KiB or less, plus a
compact description of the recursion architecture and a sketch of its soundness, by the end of May
2026; reach 128-bit provable security with proofs of 300 KiB or less, plus a formal security
argument for the recursion architecture, by the end of 2026.<Cite src="ef-zkevm-security-foundations" />

Two cautions about those milestones, because both are easy to misread.

**They are programme deadlines for prover teams, not protocol activation dates.**<Cite src="ef-zkevm-security-foundations" /> The Foundation
named its second milestone after the Glamsterdam upgrade, but Glamsterdam has not shipped. Nothing
in that milestone list tells you when any fork activates, and no lesson in this track will print a
date for one.

**"Provable" is not "proved correct".** It means the bit count follows from a bound someone has
proved, rather than from a conjecture. The implementation can still be wrong, the circuit can still
be under-constrained, and the model can still be the wrong model. It raises the floor under the number; it does not verify the system — which is why the same
milestone list separately asks for formal verification of the recursion architecture rather than
treating the bit count as sufficient.<Cite src="ef-zkevm-security-foundations" />

### What the number is denominated in

One more piece of hygiene, because "128-bit security" gets compared across incomparable things.

Security bits for a proof system say roughly: an adversary must do about `2^128` units of work to
forge a proof for a false statement — 128 bits being the level the Foundation calls the right
long-term target for Ethereum L1, with 100 bits accepted only in the initial months of
deployment.<Cite src="ef-realtime-proving" /> That is a different quantity from the security level of the
curve underneath a pairing-based verifier, which is about the difficulty of a discrete logarithm.
The curve numbers are themselves contested: BLS12-381 was originally designed for around 128 bits,
but later analysis put it lower — one report cited by the eth2 book gives roughly 117 to 120 bits
while the IETF draft cites 126 — and BN254, the curve behind Ethereum's alt_bn128 precompiles, sits
at roughly 100 bits.<Cite src="eth2book-bls12-381" /> Sources genuinely disagree on the exact
figures; the direction of travel is not in dispute.

Hold that BN254 figure. In the sixth lesson it collides head-on with the Foundation's 128-bit
provable-security target, and the collision is the reason L1-facing verification is drifting away
from pairing-based wrappers.<Cite src="ef-realtime-proving" />

## What the verifier actually checks

Strip the abstraction and say what happens when your contract returns `true`.

The verifier ran a fixed sequence of arithmetic over the numbers in `proof` and `publicSignals`, and
every equation it checked came out right. For a Groth16 verifier that sequence is short: the proof
is three group elements, and verification is a single pairing product equation using three pairings
in total, plus a linear combination over the public inputs.<Cite src="groth16-paper" /> It did not
run your program. It did not look at the witness. It has no notion of "your program" at all — that notion lives in the constraint system, which the
third lesson takes apart.<Cite src="sok-zk-snarks-arxiv" />

So the honest reading of a `true` is:

> There exists an assignment to this constraint system's variables that satisfies every constraint
> and matches these public inputs, and whoever produced this proof knows one — assuming the
> soundness bound holds at the claimed number of bits, the setup was honest if the system needs one,
> and the constraint system says what its author thought it said.

Four clauses, three of which are assumptions. The whole rest of the module works through them: the
soundness assumption in this lesson and the fourth, the setup assumption in the fifth, the
constraint system in the third.<Cite src="ethereum-org-zkevm-roadmap" />

<Check type="explain" concept="proof-system-relation">
A team is building an age-gated feature. A user holds a credential signed by an issuer, containing
their date of birth. They want to prove to a contract that they are over 18 without revealing the
date of birth.

The team's first draft has these public signals: `[minimumAgeInYears, currentTimestamp]`. Everything
else — the date of birth, the issuer's public key, the issuer's signature — is witness.

State the relation the circuit is proving as written, name the break, and give the corrected public
signal list with a reason for each entry.

<Answer>
**The relation as written.** "I know a date of birth, a public key and a signature valid under that
key over that date of birth, such that the date of birth is at least `minimumAgeInYears` before
`currentTimestamp`."

**The break: the issuer's public key is a witness.** The prover chooses it. They generate their own
keypair, sign whatever date of birth they like, and prove the statement honestly — the signature
really does verify under the key they chose, and the arithmetic really does show the age. The proof
is valid and the feature is worthless. This is the same failure as putting a Merkle root on the
private side: the prover manufactured the authority they were supposed to be borrowing.

**A second break: nothing binds the proof to a user.** With only `minimumAgeInYears` and
`currentTimestamp` public, one valid proof is reusable by anyone who observes it. It is a bearer
token for adulthood.

**A third break, subtler: `currentTimestamp` is prover-supplied.** The contract must not accept a
timestamp from the proof; it must compare against its own notion of time, or the prover simply
claims it is 2085.

**Corrected public signals.**

1. `issuerKeyCommitment` — a commitment to, or hash of, the accepted issuer key set. Public because
the verifier must pin down whose authority is being borrowed. The contract compares it against a
value it stores.
2. `minimumAgeInYears` — public because the policy is the verifier's, not the prover's.
3. `currentTimestamp` — still public, but the contract must additionally check it against
`block.timestamp` within a tolerance. Public inputs are not validated by being public; being public
only makes them *checkable*, and someone has to write the check.
4. `subjectBinding` — the address, session identifier or nullifier that ties this proof to this
actor and this use. Without it, replay is free.

**What stays private.** The date of birth, the signature, and which issuer within the accepted set
signed it.

**The general rule this example produces.** A value belongs in the public statement when the
verifier's security depends on it not being the prover's choice. Everything else can be witness. The
question is never "is this data sensitive" — it is "who would benefit from choosing it".
</Answer>
</Check>

## What this unlocks

**Immediately next**: the two properties the word "ZK" welds together. You now have the vocabulary
to see that succinctness is a statement about how the verifier's cost scales, while zero-knowledge
is a statement about what the proof leaks about `w` — and that a system can have either without the
other. Production validity rollups have exactly one of them, and the industry named them after the
one they do not use.<Cite src="l2beat-glossary" />

**Two lessons on**: arithmetization, which is where the relation `R` stops being English and becomes
polynomial constraints. Everything in this lesson about "the relation was wrong" becomes, in
practice, "the constraint system permitted an assignment the author did not intend". Same bug, one
layer down.<Cite src="ethereum-org-zkevm-roadmap" />

**And in review**: you now have a first question to ask of any proof-consuming contract, whether it
uses a zkVM<Cite src="succinct-sp1-docs" /><Cite src="risc0-zkvm-docs" /> or a hand-written circuit.
Not "which proof system" and not "how much gas". Read the public inputs, then say out loud, for each
one, which attack it is there to prevent. If a value has no answer, it should not be there. If an
attack has no value, the feature is already broken.
