02 What 2026 changes

Most published curricula describe a 2022–2023 machine. Six shifts invalidate parts of nearly every roadmap I read — and each one is a direct instruction to the content plan.

1. The account model changed underneath everyone

EIP-7702 (Pectra, May 2025) lets a plain EOA temporarily execute contract code. Ethereum's own 2026 guidance is to build against wallet capabilities rather than raw EOAs — batching, gas sponsorship, session keys, passkeys — pairing EIP-7702 with ERC-4337, and treating delegation targets as wallet infrastructure rather than app-controlled code. ERC-5792 (wallet_sendCalls) is the batching interface.

Instruction: the accounts module in Track 03 is written around delegation from lesson one. "EOA vs contract account" appears only as a supersedes historical note. Research sharpened the teaching point: EXTCODESIZE observes the 23-byte delegation indicator while CODESIZE observes the target code, so a delegated account's external and internal views of itself disagree — and msg.sender == tx.origin no longer implies "not a contract".

2. Mainnet stopped being "too expensive"

Fusaka (Dec 2025) shipped PeerDAS and raised the L1 gas limit 30M → 60M (EIP-7935), capping single transactions near 16.78M gas (EIP-7825). Blob throughput went 3/6 → 6/9 under Pectra and higher under Fusaka, cutting L2 data-posting fees by as much as 90%. EIP-7951 added native secp256r1 (P-256) verification, making passkey signatures cheap on-chain.

Instruction: the gas and fee-market module teaches cost as something you measure, with a live-numbers exercise — never as a memorized constant.

3. L2 consolidated; the long tail is dead weight

50+ rollups exist; Base, Arbitrum and Optimism handle roughly 90% of L2 transactions, and Base + Arbitrum alone secure over 68% of L2 TVL. With blob costs collapsed, the competitive axis moved from gas savings to distribution, liquidity and tooling. Arbitrum's Stylus (Rust/C++ alongside the EVM) is the one genuinely different execution story.

Instruction: Track 09 teaches the mechanism — sequencing, DA, proving, forced inclusion, bridges — and exactly three deployment targets. No chain survey.

The finding that reframes the whole L2 track

As of mid-2026 there are no major Stage 2 rollups. Arbitrum One, Base, OP Mainnet, Starknet and Scroll sit at Stage 1 — and zkSync Era and Linea remain Stage 0 despite shipping validity proofs, because upgrade keys stay centralised. A validity proof constrains execution; it says nothing about who can replace the contracts. Track 09 is therefore organised around trust structure, not proof type.

4. ZK moved from circuits to zkVMs

The 2022 path was Circom/Halo2 — hand-written arithmetic circuits. In 2026 the mainstream path is a zkVM (SP1, RISC Zero, Jolt, Nexus): write ordinary Rust, get a proof, no DSL. Noir remains the accessible circuit DSL when you genuinely need a circuit.

Instruction: Track 10 opens with "prove a Rust program ran" and descends into commitments and constraint systems only when you ask why the proof is small.

5. Foundry is the default; Solidity itself moved

Foundry (Rust, Solidity-native tests, built-in fuzzing, 5–10× faster) is the default for security work, protocol engineering and serious DeFi. Hardhat 3 is the reasonable second when contracts are tightly coupled to a TypeScript app. On the language, 0.8.36 (9 July 2026) is current: 0.8.24+ brought transient storage (EIP-1153, TSTORE/TLOAD); custom errors and user-defined value types are baseline; and 0.8.36 added stack-to-memory spilling to the SSA-form code generator. Correction from the research sweep: that backend is experimental (--experimental --via-ssa-cfg), --via-ir is still not the default pipeline, and legacy codegen remains the compiler default — so stack-too-deep is not solved for ordinary projects and must not be taught as fixed. 0.8.36 also removed the experimental EOF backend (EOF was rejected for Fusaka) and added "Amsterdam" EVM support. The default solc EVM version has been osaka since 0.8.31, so MCOPY/TSTORE/TLOAD/BLOBHASH are assumed present unless a target is lowered for an older L2. Note also that the Solidity repository moved to argotorg/solidity, so older issue and contribution links resolve to the wrong org.

Front-end: viem + wagmi is the default pairing for new EVM apps; ethers.js is maintained legacy. Batching goes through viem's sendCalls / wagmi's useSendCalls (ERC-5792), with a fallback to sequential sends when the wallet lacks support. Pin viem 2.x and wagmi 3.x — wagmi 3 renamed hooks, so every v2-era tutorial is wrong on naming. Session keys are not an ERC-4337 feature: the spec does not define them, they are implemented wallet-by-wallet, and the adjacent standards (ERC-7715, ERC-7710) are still drafts. On data: The Graph fully retired its free hosted service in 2026 — every pre-2026 indexing tutorial is dead on arrival, and Track 13 teaches the decentralised network or an alternative from the start.

6. Security is a thread, not a chapter

Every serious 2026 path says this and it's worth taking literally. The ladder is Ethernaut → Damn Vulnerable DeFi → reading real audit reports → competitive contests (Code4rena / Sherlock / CodeHawks), and the only respected credential is a public leaderboard, not a certificate.

Instruction: Track 06 exists, but security checks are injected into Tracks 04, 05, 08 and 09 as spot-bug items from the first contract lesson onward.

Why concepts are flat and everything else nests

A lesson lives in exactly one module. A concept does not — delegatecall is taught in Solidity, exploited in Security, and relied on by 7702 in the App track. Nesting it under one parent would force a lie about where it belongs, and would break the cross-track connections that make this a graph instead of an outline.

Scale, stated honestly

635 lessons is the built figure across all thirteen tracks — roughly 950 hours of authoring at 90 minutes each. The core six tracks are 288 lessons / ~430 hours, and that is what "v1 complete" means; electives fill in as you reach them. If the number is unacceptable, the lever is track count, not lesson depth — cutting depth defeats the entire brief.

Practice coverage target

  • Every module in Tracks 03–13 ships ≥1 practice. Track 01–02 modules ship practice where code is possible and a written exercise where it isn't (F4's distributed-systems module is analysis, not code — and that's honest).
  • Every track ends with a project, not a quiz. The project is the track's actual exit condition.
  • Practice types: implement (build to spec, tested) · break (exploit a given contract) · fix (given a failing test, repair) · read (answer questions about real production code) · measure (gas/cost profiling, report the number) · write (analysis, self-graded against a rubric).

The cost, stated plainly

This contract means 635 lesson pages, 104 module pages, 236 practices and 13 projects. Concept pages are generated, so they're free. The authoring load is real and it is the project's dominant cost — larger than building the app. §15 sequences around this; §16 names it as the top risk.

08 Navigation

Specified as a system, because with 430 lessons across a graph, navigation is the product. Four mechanisms, each with a distinct job, none overlapping.

1 · Position — where am I?

  • Breadcrumb, always present, always the full ladder: Roadmap › EVM › Execution › The stack. Every segment is a link up a level.
  • Left rail = the current track's tree, expanded to your position, with sibling modules and lessons visible. It shows one track at a time, not all thirteen — showing everything is how a sidebar becomes unusable.
  • Track switcher pinned at the rail's top. One click to any other track, one more to the roadmap.
  • Position strip on lesson pages: two short lists — what this needs, and what needs this — each linking across tracks. Lists, not a mini-graph; at this scale a list is faster to read and impossible to get lost in.

2 · Motion — how do I move?

  • Down: click anything. One level, every time, to a real URL.
  • Up: Esc or the breadcrumb. Returns to the parent with your position highlighted, never to the top of it.
  • Sideways: J / K for next/previous sibling. Wraps at module boundaries with a visible marker, never silently.
  • Forward: one "Next" button, always in the same place, always meaning "the next thing in reading order."
  • Across: cross-track links open in place with a return chip — "← back to Solidity / delegatecall" — so following a prerequisite into another track never loses your thread.

3 · Search — I know what I want

  • Command palette (⌘K) over everything: tracks, modules, lessons, concepts, glossary terms, sources, your own questions and notes. Typed results, grouped by kind.
  • Concept results show mastery state inline, so search doubles as a self-check.
  • Full-text over lesson bodies, ranked with your current track boosted.

4 · Recovery — I've been away three weeks

  • Today is the front door, not the roadmap. It answers "where was I" before asking you to choose.
  • Recent trail — the last five things touched, resumable directly.
  • Resume marker — scroll position and last inline check are restored per lesson.
  • The roadmap is one click away for when you want to survey. It is never the thing you're forced through.

Deliberately excluded

No mega-menu. No hamburger. No nested accordions more than two deep. No "related content" carousel. No infinite scroll — every page has an end, and the end says what comes next.

Why static beats a canvas here

A pan/zoom canvas has no "you are here" — every visit begins with re-orienting, and the camera position is state nobody remembers. Scroll position is memory, browsers restore it for free, and a fixed layout means the map you learned last month is the same map today. It also prints, screenshots, and deep-links, none of which a canvas does well.

Self-grading is fine, and the research supports it

Single-user means no grader, and that isn't a compromise. Free-recall-then-compare is exactly the retrieval-plus-feedback loop that produces the effect; the rubric appears only after you commit. Confidence is captured separately from correctness so the scheduler can catch the dangerous case — confident and wrong.

11 Mastery & review

Three mechanics, all from systems with real evidence behind them, adapted for one adult expert with no deadline.

Readiness, not locks

Hard locking is wrong for you — you can judge when to jump ahead, and a locked node reads as an insult. Every lesson computes a readiness score from the mastery of its requires and recommends concepts.

  • ≥ 0.8 — Ready. Normal presentation.
  • 0.4–0.8 — Reachable. Names the weak prerequisites, one click each.
  • < 0.4 — Ahead of you. Dimmed; opens with "you'll be missing A, B, C — continue anyway?" Never blocked.

Spaced repetition with prerequisite credit

FSRS (ts-fsrs, FSRS-6) schedules each concept, not each card — cards are draws from the concept's item pool, so you don't memorize phrasing.

The key addition is Math Academy's fractional implicit repetition: a successful review of an advanced concept gives its requires and deepens ancestors a discounted credit that pushes their next review out. With 1,490 concepts this is what keeps the daily queue survivable — advanced work is review of the foundations.

onReview(concept C, grade g):
  fsrs.update(C, g)
  for A in ancestors(C, via requires|deepens, maxDepth 2):
    credit = g * decay^depth(A)        # decay ≈ 0.5
    fsrs.updatePartial(A, credit)      # advances stability, never a full rep

Interleaving by default

The daily queue deliberately mixes concepts across tracks rather than blocking by module — interleaved practice produces better retention and transfer, at the cost of feeling harder in the moment. The queue caps itself: a queue you dread is a queue you abandon.

Explicitly not included

Streaks. Daily goals. XP. Leaderboards. Hearts. Each converts a no-deadline project into a source of guilt, and guilt is the main reason self-directed curricula die. Progress is shown as coverage and durability — what you know and how well it's holding — never as a chain you can break.

12 Content currency

"Verified and matching current market state" has to be machine-enforced or it decays within a year. Four mechanisms, all failing the build rather than relying on discipline.

1 · Source tiers and citation

  • tier: spec — EIPs, yellow paper, client specs. tier: canonical-docs — soliditylang, ethereum.org, Foundry Book, Solana docs. tier: primary-analysis — audit reports, post-mortems, papers. tier: secondary — blogs, comparisons.
  • Every concept needs ≥1 source at spec or canonical-docs. Secondary sources may support, never carry.
  • Any assertion with a number, a version, or a named EIP must be wrapped in <Cite src="eip-7702" />. The linter fails when a digit or EIP-\d+ appears with no citation in scope.

2 · Version pinning

Every lesson declares the stack version its code was written and verified against. Rendered as a visible badge, and checked against the canonical stack file.

---
stack:
  solidity: "0.8.35"
  foundry:  "2026-06"
  viem:     "2.x"
  chain:    "mainnet post-Fusaka"
verifiedAt: 2026-08-20
volatility: evolving
---

3 · Market-state markers

Because "what exists" and "what is actually used in production" are different questions, and only the second one is useful to you.

  • status: current — the 2026 default. Foundry, viem/wagmi, subgraphs, Anchor.
  • status: literacy — you'll meet it in real codebases, learn to read it, don't reach for it. Hardhat, ethers.js, Truffle-era patterns.
  • status: superseded — actively wrong to build on now. Circom-first ZK, pre-7702 account assumptions.
  • status: emerging — real but not yet default. Stylus, Pinocchio, zkVM-in-production.
  • A single Stack Currency page lists the canonical current stack in one place. Lessons that disagree with it fail the linter.

4 · Expiry and the re-verify queue

  • volatility: stable → 365 days · evolving → 120 · hot → 45.
  • Past verifiedAt + window, the lesson renders a staleness badge and appears on the Freshness board. It never fails the build — see §17.
  • Conflicted numbers are blocked, not guessed. Where sources disagree, the claim goes in docs/research/CONFLICTS.md and the linter refuses any lesson citing it until it is resolved. The sweep produced 120 such conflicts — gas constants, loss totals, builder market share, proving costs — each one a place the curriculum would otherwise have stated a confident, unsupported number.
  • Re-verify flow: open the cited source → confirm or amend → stamp verifiedAt. Content rot becomes a queue you can work, not a slow silent failure.
  • authorship: authored | adapted | generated renders visibly. Generated prose may never be the sole support for a factual claim.

Why this is section-sized rather than a footnote

Three of the six findings in §02 happened within the last 14 months. In a domain where wrong code loses money irreversibly, confidently-stale content is worse than no content. This is the mechanism that keeps the tool from becoming exactly what it was built to replace.

16 Risks & open calls

Risks

  • Content volume is the whole project. 635 lessons fully built, 288 for the core. At 90 focused minutes each, the core alone is ~430 hours of authoring, the full tree ~950 — several times the cost of building the app. Read every decision above as "does this raise or lower authoring cost?"
  • Building the tool becomes the procrastination. The likeliest failure is a beautiful engine holding 12 lessons. P3 exists to force the content question early, and its exit condition is deliberately "you learned something," not "the code works."
  • Freshness debt compounds. Without the re-verify queue actually worked, the tool becomes confidently wrong — the worst outcome in this domain.
  • Graph over-modeling. Six edge types is ambitious. If authoring an edge takes real deliberation, we cut to requires / recommends / supersedes and demote the rest to prose.
  • 1,490 concepts — the estimate was 1,050. The graph came out 42% denser than planned. P1 turns it into a real number before anything depends on it — which is exactly why P1 is first.

Resolved

  • Fundamentals scope — blockchain-necessary only. Track 01 unchanged at 34 lessons.
  • Authoring loop — I draft from primary sources with citations; you review and correct.
  • Roadmap rendering — static and scrolled, authored coordinates, no graph library.
  • Deployment — dual-mode. Full locally, read-only on the web, capabilities from one flag (§14).
  • Gas constants and versions — settled by measurement, not sourcing. Foundry 1.7.1, solc 0.8.36, COLD_SLOAD_COST 2100. See docs/research/MEASURED.md.

Open calls — yours

  1. Thirteen tracks, or fewer to start? P1 authors the graph for all thirteen regardless (structure is cheap); the question is only whether electives 11–13 get lessons this decade. My take: keep all thirteen on the map — an unreachable region you can see is motivating; a region that doesn't exist is a gap you don't know about.
  2. Name. "Chainpath" is a placeholder.

17 Edge cases & failure modes

Eight things revision 3 did not handle, each now with a decision — so P1 doesn't discover them the expensive way. Several were found by reviewing this document against itself.

Content changes under existing progress

You will edit lessons you already completed, constantly, because §12 forces re-verification. Silently invalidating mastery would be maddening; silently keeping it would be wrong.

  • Every content commit classifies its lesson edits: cosmetic · clarifying · corrective.
  • corrective resets that lesson's concepts to unproven and pushes them to the front of the review queue, with a note saying what changed.
  • cosmetic and clarifying touch nothing.
  • Nothing ever changes your state without telling you why.

Concept identity is the join key

IDs bind git content to SQLite state. Renames and splits silently orphan years of progress.

  • IDs are immutable once authored. A rename is a formerIds[] entry, never an edit.
  • Splitting writes splitInto[] — state migrates to every child at the parent's mastery.
  • Merging writes mergedFrom[] — state takes the maximum.
  • content:lint refuses to build if any state row points at an unknown id.

Practice checks are arbitrary code execution

The site shells out to forge test in your repo from a browser-triggered action. Even bound to localhost, any page in any other tab can POST to 127.0.0.1. This needs handling before P5, not after.

  • Bind to 127.0.0.1 only — never 0.0.0.0.
  • Require a per-session token in a custom request header; a cross-origin form post cannot set one.
  • Strict Origin allowlist on every action that touches the filesystem.
  • The command is never composed from user input. Repo path and test filter come from the practice YAML, and the filter is validated against a strict pattern before it goes anywhere near a process.
  • Spawn with an argument array, never a shell string. No shell: true.
  • Timeout and output cap on every run — a runaway fuzz campaign must not hang the app.
  • Parse --junit, not --json. Research finding: forge test --json still writes compiler diagnostics to stdout alongside the JSON (foundry issue #3001, open), so the stream is not reliably parseable. --junit emits standard JUnit XML with per-testcase results. Capture stderr separately, so "failed to compile" is a distinct state from "test failed".

Review queue growth after an absence

1,490 concepts with no cap generates a queue that guarantees abandonment — the precise failure this design exists to avoid.

  • New concepts are rate-limited into the SRS: a daily ceiling, regardless of how much you read.
  • The queue is capped by time, not count. Overdue items are ordered by retrievability × prerequisite fan-out, so foundations resurface before leaves.
  • Returning after two months shows a normal capped session and a quiet "you're N behind" line. No backlog dump, no guilt.

Freshness must never break the build

Revision 3 had expired verifiedAt failing content:lint. That is a bug: it means taking a two-month break bricks the tool, punishing you for exactly the thing the design promised to survive. Expiry renders a badge and populates the Freshness board. It is never a build error.

Readiness defaults

Mastery is 0 for anything never reviewed, so a fresh install reads every lesson as "ahead of you." Track 01's first module is seeded ready. Beyond that it's cosmetic — readiness gates presentation, never access.

State backup

state.db holds years of reflections, answered questions and mastery history, and is deliberately not in git — which makes it the one irreplaceable artifact with no redundancy.

  • chainpath backup exports state to timestamped JSON in the repo, and that export is committed.
  • It runs automatically on every content build, so the backup can never be much staler than the content.

Roadmap accessibility

SVG connectors are decorative and aria-hidden. The structural truth lives in DOM order and in each node's aria-describedby, which names its prerequisites in text. The roadmap stays fully usable with connectors never rendered — which is also the fallback if the static layout ever misbehaves.
