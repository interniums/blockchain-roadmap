## F5b — MPT path encoding: hex-prefix/compact encoding and node RLP structures

### Concepts
- mpt-four-node-types — A Merkle Patricia Trie node is exactly one of NULL, branch (17 items), extension (2 items) or leaf (2 items); there is no fifth kind. | requires: [rlp-encoding, merkle-tree] | contrasts: [binary-merkle-tree]
- mpt-nibble-path — Keys are traversed as 4-bit nibbles, not bytes, so a 32-byte key is a 64-step path and each branch node fans out 16 ways. | requires: [mpt-four-node-types] | contrasts: [binary-tree-bit-path]
- mpt-branch-node — A branch is `[v0, v1, ... v15, value]`: sixteen child slots indexed by the next nibble plus a 17th slot holding the value of a key that terminates exactly here. | requires: [mpt-nibble-path, rlp-encoding] | contrasts: [mpt-extension-node]
- mpt-extension-node — An extension is `[compactEncode(sharedNibbles, false), childRef]` and exists only to compress a run of nibbles that every key below it shares. | requires: [hex-prefix-encoding, mpt-child-reference-rule] | contrasts: [mpt-leaf-node]
- mpt-leaf-node — A leaf is `[compactEncode(remainingNibbles, true), value]`; the terminator flag in the first nibble is the ONLY thing distinguishing it from an extension on the wire. | requires: [hex-prefix-encoding] | contrasts: [mpt-extension-node]
- mpt-null-node — The empty node is the empty string, RLP `0x80`; the empty trie root is therefore `keccak256(0x80)` = `0x56e81f171bcc55a6ff8345e692c0f86e5b48e01b996cadc001622fb5e363b421`. | requires: [rlp-encoding, keccak256] | contrasts: [mpt-branch-node]
- hex-prefix-encoding — Compact (hex-prefix) encoding packs an odd-or-even nibble path back into whole bytes by prepending a flag nibble, and optionally a zero padding nibble. | requires: [mpt-nibble-path] | contrasts: [rlp-encoding]
- hp-flag-nibble-table — The first nibble is 0 = extension/even, 1 = extension/odd, 2 = leaf/even, 3 = leaf/odd; equivalently `flag = 2*isLeaf + isOdd`. | requires: [hex-prefix-encoding] | contrasts: [mpt-leaf-node]
- hp-even-padding — When the nibble count is even (flags 0 and 2) a second zero nibble is appended to the flag so the payload stays byte-aligned; odd paths (flags 1 and 3) put the first real nibble in that slot instead. | requires: [hp-flag-nibble-table] | contrasts: [hex-prefix-encoding]
- mpt-child-reference-rule — A child is referenced by `keccak256(rlp(child))` only when `len(rlp(child)) >= 32`; shorter children are inlined verbatim inside the parent's RLP. | requires: [rlp-encoding, keccak256] | contrasts: [merkle-tree]
- mpt-secure-trie — State and storage tries are "secure": the path is `keccak256(key)`, not the key, which fixes path length at 64 nibbles and stops an attacker choosing addresses that deepen the trie. | requires: [keccak256, mpt-nibble-path] | contrasts: [mpt-index-keyed-tries]
- mpt-index-keyed-tries — Transaction, receipt and withdrawal tries key by `rlp(index)` and are NOT hashed, so they are shallow, ordered, and rebuilt per block rather than persisted. | requires: [mpt-secure-trie, rlp-encoding] | contrasts: [state-root]
- mpt-canonical-root — Because every structural choice is forced (no free ordering, no optional compression), two clients with the same key/value set must produce byte-identical nodes and the same root hash. | requires: [mpt-four-node-types, hex-prefix-encoding] | contrasts: [merkle-tree]
- mpt-proof-is-node-list — A Merkle proof is the ordered list of RLP-encoded nodes from root to leaf; the verifier re-hashes each and checks it matches the reference held by its parent. | requires: [mpt-child-reference-rule, mpt-canonical-root] | contrasts: [state-root]

### Primary sources
- [Merkle Patricia Trie — ethereum.org developer docs](https://ethereum.org/en/developers/docs/data-structures-and-encoding/patricia-merkle-trie/) — tier: canonical-docs — published: continuously updated — carries the exact hex-char/bits/node-type/path-length table, the four worked compact-encoding examples, the 17-item branch layout, and the `>= 32` inline rule verbatim.
- [Ethereum Yellow Paper, Appendix C (RLP) and Appendix D (Modified Merkle Patricia Tree)](https://ethereum.github.io/yellowpaper/paper.pdf) — tier: spec — published: rolling (Berlin+ revisions) — the normative definition of HP(x, t) and of the trie function; the source everything else paraphrases.
- [ethereum/execution-specs — trie.py](https://github.com/ethereum/execution-specs) — tier: spec — published: rolling — executable Python spec: `nibble_list_to_compact_bytes`, `encode_internal_node`, `LeafNode/ExtensionNode/BranchNode` dataclasses. Best oracle to diff a from-scratch implementation against.
- [go-ethereum trie package](https://pkg.go.dev/github.com/ethereum/go-ethereum/trie) — tier: canonical-docs — published: rolling — production implementation; `shortNode`/`fullNode` naming shows extension and leaf are the same Go type distinguished only by the HP flag.
- [EIP-7864: Ethereum state using a unified binary tree](https://eips.ethereum.org/EIPS/eip-7864) — tier: spec — published: 2025-01 (Draft) — the intended successor: binary tree, unified account+storage+code, 31-byte stems, InternalNode/StemNode/LeafNode/EmptyNode.
- [Towards Stateless Clients: Benchmarking Verkle Trees and Binary Merkle Trees with SNARKs (arXiv 2504.14069)](https://arxiv.org/pdf/2504.14069) — tier: primary-analysis — published: 2025-04 — quantitative case for binary-over-Verkle; useful for "why replace MPT" framing.

### Current state (Aug 2026)
- The hexary MPT with keccak256 is still the live mainnet state commitment as of Aug 2026. Nothing in Pectra (May 2025) or Fusaka (3 Dec 2025) changed the trie format.
- **Verkle trees are dead as the successor.** This is the single biggest thing that is now wrong in most 2023-2024 teaching material. The replacement direction is EIP-7864, a *binary* tree, which merges the account trie, storage tries and contract code into one tree with prefix-free keys (1 byte storage-type + stem + 1 byte subindex; stem is 31 bytes).
- EIP-7864 is still **Draft** and is **not** scheduled for a named fork. It was not in Fusaka and is not among the Glamsterdam headline EIPs (EIP-7732 ePBS, EIP-7928 BALs). Teach it as direction of travel, not as a shipping date.
- EIP-7864's hash function is explicitly **TBD**. The current spec text uses BLAKE3 "to reduce friction for EL clients experimenting"; Keccak and Poseidon2 remain candidates. Do not teach "the binary tree uses Poseidon" as settled.
- Migration model in the draft follows EIP-7612: freeze the existing MPT and start a new empty tree beside it, rather than a stop-the-world conversion.
- Motivation has shifted from "stateless clients / witness size" (the Verkle framing) to "proving cost" — shorter Merkle branches and a SNARK-friendlier hash, in the same programme as the RISC-V execution-layer proposals Vitalik outlined in early 2026.

### Misconceptions
- Belief: A leaf node and an extension node are different data structures. | Reality: Both are 2-item RLP lists `[encodedPath, x]`. Only the hex-prefix flag nibble (0/1 vs 2/3) tells them apart, and it also tells you whether item 2 is a value or a child reference. | Why: Diagrams draw them as different shapes; go-ethereum calls both `shortNode`. | Source: https://ethereum.org/en/developers/docs/data-structures-and-encoding/patricia-merkle-trie/
- Belief: Every child in the trie is a 32-byte hash. | Reality: If `rlp(child)` is under 32 bytes the child is embedded literally inside the parent node. | Why: The "Merkle" framing implies hash-linking everywhere; this optimisation is a classic source of failing from-scratch implementations. | Source: https://ethereum.org/en/developers/docs/data-structures-and-encoding/patricia-merkle-trie/
- Belief: The trie path is the address / the storage slot. | Reality: For state and storage tries the path is `keccak256(address)` / `keccak256(slot)`. The preimage is not recoverable from the trie, which is exactly why "iterate all storage slots of a contract" is not an RPC you get for free. | Why: Tutorials draw `0xabc...` at the root of the path. | Source: https://ethereum.org/en/developers/docs/data-structures-and-encoding/patricia-merkle-trie/
- Belief: Hex-prefix encoding and RLP are the same layer. | Reality: HP encodes a nibble path into bytes; RLP then encodes the resulting byte string as one item of the node list. Two independent codecs, applied in that order. | Why: They only ever appear together. | Source: Yellow Paper Appendices C and D
- Belief: The trie is a Merkle tree with a nice key lookup bolted on. | Reality: It is a radix trie whose edges are hash-linked; the root commits to the *set of key-value pairs*, and any two clients must reach the identical root because no structural freedom exists. | Why: "Merkle" is the loud word in the name. | Source: Yellow Paper Appendix D
- Belief: Verkle trees are coming to replace the MPT. | Reality: As of Aug 2026 the successor work is EIP-7864, a binary Merkle tree; Verkle has effectively been dropped. | Why: Three years of roadmap posts said Verkle. | Source: https://eips.ethereum.org/EIPS/eip-7864

## F6b — Cost of attack: 51%, finality reversal, and the slashing arithmetic

### Concepts
- security-is-a-price — Blockchain security is not a proof that an attack is impossible; it is a claim that an attack costs more than it earns, denominated in a volatile asset. | requires: [proof-of-stake] | contrasts: [cryptographic-guarantee]
- accountable-safety — Casper FFG is designed so that if two conflicting checkpoints both finalize, at least 1/3 of the total stake must have signed a provably contradictory message and can be slashed by anyone. | requires: [casper-ffg, slashing-conditions] | contrasts: [nakamoto-probabilistic-finality]
- slashing-conditions — There are exactly two slashable consensus offences: a double vote (two different attestations for the same target epoch) and a surround vote (one attestation's source/target span strictly surrounds another's). | requires: [attestation, casper-ffg] | contrasts: [inactivity-penalty]
- attack-threshold-one-third — 1/3 of stake is the safety threshold: below it you cannot finalize conflicting checkpoints; at or above it you can, and the protocol makes you pay for it. | requires: [accountable-safety] | contrasts: [attack-threshold-one-half]
- attack-threshold-one-half — >1/2 of stake buys censorship, reorgs of unfinalized blocks and control of the fork choice, but NOT a finality reversal; these are different attacks with different price tags. | requires: [fork-choice-lmd-ghost] | contrasts: [attack-threshold-one-third]
- finality-reversal-cost-model — Cost of reverting a finalized checkpoint ≈ 1/3 of total staked ETH destroyed, because the correlation penalty at that participation level takes the attacker's entire effective balance. | requires: [accountable-safety, slashing-correlation-penalty] | contrasts: [pow-51-rental-cost]
- slashing-initial-penalty — On being slashed a validator immediately loses `effective_balance / MIN_SLASHING_PENALTY_QUOTIENT`; the quotient was 32 pre-Electra and 4096 post-Electra, so a 32 ETH validator went from ~1 ETH to ~0.0078 ETH. | requires: [slashing-conditions, eip-7251] | contrasts: [slashing-correlation-penalty]
- slashing-correlation-penalty — Roughly 18 days (4096 epochs) after being slashed, the validator is charged `3 * EB * SB / TB` where SB is the balance slashed in the surrounding window; at SB = TB/3 this equals EB and the validator loses everything. | requires: [slashing-initial-penalty] | contrasts: [slashing-initial-penalty]
- slashing-is-anti-correlation-not-anti-error — The two-tier design means a lone fat-fingered operator pays almost nothing while a coordinated 1/3 pays 100%; slashing prices *correlation*, not mistakes. | requires: [slashing-initial-penalty, slashing-correlation-penalty] | contrasts: [security-is-a-price]
- inactivity-leak — If a chain fails to finalize for 4+ epochs, non-participating validators bleed balance quadratically until the participating set again exceeds 2/3 — this is how a >1/3 liveness attack is made to end. | requires: [attack-threshold-one-third] | contrasts: [slashing-conditions]
- cost-of-corruption-vs-cost-of-capital — Acquiring 1/3 of stake and destroying 1/3 of stake are different numbers; the honest framing is cost-of-corruption (burned), not market cap of the acquisition, and it ignores the slippage of actually buying that much ETH. | requires: [finality-reversal-cost-model] | contrasts: [security-is-a-price]
- attack-cost-is-not-attack-profit — A security budget only binds if attacker profit is bounded; a large enough short position, a bridge drain, or an L2 exit window can make an expensive attack rational. | requires: [security-is-a-price] | contrasts: [finality-reversal-cost-model]
- pow-vs-pos-cost-asymmetry — PoW 51% cost is *rental* (hashpower for an hour, recoverable hardware); PoS attack cost is *burn* (stake destroyed and non-recoverable), which is why the two numbers are not comparable. | requires: [security-is-a-price] | contrasts: [finality-reversal-cost-model]
- social-layer-recovery — Against a >1/3 or >1/2 attacker the last line of defence is out-of-band: minority-fork coordination that slashes the attacker's stake on the surviving chain, which is a governance act, not a protocol one. | requires: [accountable-safety] | contrasts: [security-is-a-price]
- cheap-reorgs-exist — Short unfinalized reorgs (ex-ante/ex-post, MEV-driven) are achievable well under 1/3 stake and cost nothing in slashing, which is why "finalized" and "included" are different safety claims for a product. | requires: [attack-threshold-one-half, fork-choice-lmd-ghost] | contrasts: [finality-reversal-cost-model]

### Current state (Aug 2026)
- **Staked ETH ≈ 41.4M, ~34% of supply** (41.41M / 33.98% reported as of 4 Aug 2026) across roughly 897,000 active validators. This is an all-time high; the ratio was ~29% at the start of 2026.
- Therefore the finality-reversal cost anchor is **≈ 13.8M ETH destroyed** (1/3 of 41.4M). Teach the *quantity in ETH*; convert to fiat at lesson time, never bake a dollar number into the material.
- **Native staking APR has compressed to ~2.7-2.8%** (7-day APR ~2.66%, down from a 5.06% peak in June 2023), plus roughly 0.5-1% from MEV. Any curriculum quoting 4-5% staking yield is out of date.
- Because issuance falls as the validator set grows, the *marginal* security purchased per new validator is shrinking — this is the live debate behind EIP-8361 (tapered validator rewards), which is a **proposal**, not shipped.
- **Post-Pectra slashing is much softer for the honest-mistake case**: initial penalty quotient 32 → 4096. A slashed 32 ETH validator loses ~0.0078 ETH up front instead of ~1 ETH; a consolidated 2048 ETH validator loses ~0.5 ETH. Ejection and the ~36-day exit still apply.
- MaxEB is 2048 ETH (EIP-7251), so "one validator = 32 ETH" is no longer a safe unit of account. Validator *count* and *stake* have decoupled; always reason in ETH.
- Entry and exit queues are at multi-year highs, which means "the attacker exits and re-enters" is slower and more visible than the naive model assumes.
- Fusaka (Dec 2025) and Glamsterdam do not change the slashing arithmetic. Glamsterdam's EIP-7732 (ePBS) changes *who builds* blocks, not the cost of attacking consensus.

### Misconceptions
- Belief: A 51% attack lets you reverse finalized transactions. | Reality: 51% buys censorship, fork-choice control and reorgs of *unfinalized* blocks. Reversing a finalized checkpoint requires conflicting finality, which is what costs 1/3 of stake. | Why: The PoW mental model, where 51% is the only number. | Source: https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/attack-and-defense/
- Belief: The cost of attacking Ethereum is the market price of 1/3 of the stake. | Reality: That is the cost of *acquisition*; the cost of *corruption* is the stake destroyed, and acquiring 13.8M ETH on the open market would move the price violently against you long before you got there. | Why: Headline numbers quote market cap. | Source: https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/attack-and-defense/
- Belief: Getting slashed means losing your whole stake. | Reality: Post-Electra a lone slashed validator loses `EB/4096` plus small correlation and ejection costs — a fraction of a percent. Total loss happens only when ~1/3 of all stake is slashed in the same 8192-epoch window. | Why: Pre-2023 material, and conflating slashing with the inactivity leak. | Source: https://notes.ethereum.org/@mikeneuder/slashings-eip-7251
- Belief: Slashing punishes downtime. | Reality: Downtime is an *inactivity penalty* (roughly symmetric to the reward you would have earned); slashing requires a signed, provable contradiction — double vote or surround vote. | Why: Staking providers market "no slashing" as an uptime claim. | Source: https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/rewards-and-penalties/
- Belief: One validator = 32 ETH, so 897k validators = 28.7M ETH. | Reality: Post-EIP-7251 effective balances range from 32 to 2048 ETH; the numbers do not multiply. | Why: The 32 ETH figure is the most-repeated fact about Ethereum staking. | Source: https://eips.ethereum.org/EIPS/eip-7251
- Belief: If the attack costs more than it earns, the chain is safe. | Reality: Profit is unbounded when the attacker also holds a short position, controls a bridge with a large TVL, or can force an L2 exit; security budget only binds relative to *the largest extractable prize*. | Why: The cost side is easy to measure, the profit side is not. | Source: https://arxiv.org/pdf/2102.02247
- Belief: Finalized means irreversible. | Reality: It means reversible only at a known, very large, publicly attributable price — and the community can still coordinate a minority fork afterwards. It is an economic claim, not a mathematical one. | Why: "Finality" is an absolute-sounding word. | Source: https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/

## 02.2 — The account model

### Concepts
- account-four-fields — An Ethereum account is exactly four fields, RLP-encoded as `[nonce, balance, storageRoot, codeHash]`; everything else you think of as "the account" is derived. | requires: [rlp-encoding, mpt-secure-trie] | contrasts: [utxo-model]
- account-address-not-stored — The address is not a field of the account; it is the *key* under which the account sits in the state trie (path = `keccak256(address)`). | requires: [account-four-fields, mpt-secure-trie] | contrasts: [account-four-fields]
- account-nonce-eoa — For an EOA the nonce is the count of transactions it has sent, and a transaction is valid only if its nonce exactly equals the account's current nonce. | requires: [account-four-fields] | contrasts: [account-nonce-contract]
- account-nonce-contract — For a contract account the nonce counts contracts *created* by it, starting at 1 (EIP-161), because `CREATE` derives the child address from `keccak256(rlp([sender, nonce]))`. | requires: [account-nonce-eoa, keccak256] | contrasts: [create2-address-derivation]
- create2-address-derivation — `CREATE2` derives the address from `0xff ++ sender ++ salt ++ keccak256(initcode)`, deliberately removing the nonce so the address is knowable before deployment. | requires: [account-nonce-contract] | contrasts: [account-nonce-contract]
- account-balance-wei — Balance is an integer count of wei (1e18 wei = 1 ETH) stored in the account itself, not as a token balance in some ledger contract; ETH is the only asset the protocol knows about. | requires: [account-four-fields] | contrasts: [erc20-balance-mapping]
- account-storage-root — Each account owns a private storage trie of 32-byte-key → 32-byte-value, committed by a single 32-byte root inside the account; this is what makes a contract *stateful*. | requires: [account-four-fields, mpt-secure-trie] | contrasts: [utxo-model]
- account-code-hash — `codeHash` is `keccak256(bytecode)`; the bytecode itself lives outside the account record and is fetched by hash, so identical contracts share one code entry. | requires: [account-four-fields, keccak256] | contrasts: [account-storage-root]
- accounts-enable-stateful-contracts — Because storage is addressed by a persistent account identity rather than consumed and recreated, a contract can hold mutable state that many independent callers mutate in place. | requires: [account-storage-root, account-address-not-stored] | contrasts: [utxo-model]
- nonce-replay-protection — Strict sequential nonces make every transaction single-use on a given chain: re-broadcasting a signed transaction after it lands is a no-op because the nonce is already consumed. | requires: [account-nonce-eoa] | contrasts: [eip-155-chain-id-replay]
- nonce-total-ordering — The nonce also forces a total order on one sender's transactions: nonce N cannot execute before N-1, which is the root cause of nonce gaps, stuck transactions and the need for replacement-by-fee. | requires: [account-nonce-eoa] | contrasts: [mempool-pending-is-not-a-queue]
- eip-155-chain-id-replay — The nonce alone does not stop *cross-chain* replay; EIP-155 folds the chain id into the signed payload so a mainnet transaction is invalid on any other chain. | requires: [nonce-replay-protection] | contrasts: [nonce-replay-protection]
- utxo-model — In UTXO (Bitcoin) there are no accounts: the state is a set of unspent outputs, a transaction consumes some and creates others, and "balance" is a wallet-side sum the protocol never computes. | requires: [ledger-state] | contrasts: [account-four-fields, accounts-enable-stateful-contracts]
- utxo-vs-account-tradeoff — UTXO gives natural parallelism (disjoint inputs = independent transactions) and no replay problem by construction; accounts give shared mutable state and therefore ordering dependence, contention and MEV. | requires: [utxo-model, accounts-enable-stateful-contracts] | contrasts: [solana-account-model]
- empty-account-clearing — EIP-161 defines an "empty" account (nonce 0, balance 0, no code) and deletes it from state on touch, which is why sending 0 wei to a fresh address can leave no trace. | requires: [account-four-fields] | contrasts: [accounts-enable-stateful-contracts]
- eoa-contract-line-is-blurred — Post-EIP-7702 an EOA can carry a non-empty `codeHash` (the 23-byte `0xef0100 || address` designator), so "has code" no longer implies "is a contract" and `msg.sender == tx.origin` no longer implies "not a contract". | requires: [account-code-hash, eip-7702] | contrasts: [account-four-fields]

### Primary sources
- [Ethereum accounts — ethereum.org developer docs](https://ethereum.org/en/developers/docs/accounts/) — tier: canonical-docs — published: rolling — the four fields with their normative definitions; explicitly states EOA `codeHash` is the hash of the empty string and `storageRoot` is empty by default. Does NOT yet mention EIP-7702 (as of this read) — a real gap in the canonical docs.
- [Ethereum Yellow Paper §4.1 "World State"](https://ethereum.github.io/yellowpaper/paper.pdf) — tier: spec — published: rolling — normative `σ[a] = (nonce, balance, storageRoot, codeHash)` and the address-derivation functions.
- [EIP-161: State trie clearing](https://eips.ethereum.org/EIPS/eip-161) — tier: spec — published: 2016-10 — defines the empty account, touch-and-delete, and contract nonce starting at 1.
- [EIP-155: Simple replay attack protection](https://eips.ethereum.org/EIPS/eip-155) — tier: spec — published: 2016-10 — chain id in the signature; the other half of replay protection that nonces do not cover.
- [EIP-7702: Set EOA account code](https://eips.ethereum.org/EIPS/eip-7702) — tier: spec — published: shipped Pectra 2025-05 — authorization tuple `[chain_id, address, nonce, y_parity, r, s]`; the authority's nonce is incremented during execution; `chain_id == 0` means valid on every EIP-7702 chain.
- [eip7702.io — overview and delegation registry](https://eip7702.io/) — tier: canonical-docs — published: rolling 2025-2026 — practical reference for what delegations are live and which wallets set them.
- [EIP-7702 Phishing Attack (arXiv 2512.12174)](https://arxiv.org/pdf/2512.12174) — tier: primary-analysis — published: 2025-12 — empirical study of malicious delegations; the concrete reason the EOA/contract blur matters to a product engineer.
- [In-Depth Discussion on EIP-7702 and Best Practices — SlowMist](https://slowmist.medium.com/in-depth-discussion-on-eip-7702-and-best-practices-968b6f57c0d5) — tier: primary-analysis — published: 2025 — security-firm treatment of the `chain_id = 0` wildcard and nonce-binding pitfalls.

### Current state (Aug 2026)
- The four-field account record is unchanged since Frontier and is still exactly what the state trie stores in Aug 2026. Nothing in Pectra, Fusaka or Glamsterdam alters it.
- **What changed is the meaning of `codeHash` on an EOA.** Since Pectra (May 2025), EIP-7702 lets an EOA's code field hold the 23-byte delegation designator `0xef0100 || address`. Consequences to teach: `EXTCODESIZE` on a delegated EOA returns 23; `CODESIZE` *during delegated execution* reflects the target's code; delegation chains are not followed; setting the target to `address(0)` clears it. The account is still an EOA — it can still originate transactions.
- **`msg.sender == tx.origin` is dead as an EOA check.** Any curriculum or codebase using it as an anti-contract guard is now wrong. This is the single most important 2026 correction in this module.
- Replay protection now has three layers to teach, not one: nonce (per-account, per-chain), EIP-155 chain id (cross-chain, transaction level), and the EIP-7702 authorization's own `chain_id` + `nonce` (cross-chain, delegation level — and `chain_id = 0` deliberately opts *out* of cross-chain protection).
- ERC-4337 (EntryPoint v0.7 in production; v0.8/v0.9 exist) sits entirely *above* the account model: it gives smart-contract accounts their own userop nonce space (a 2D nonce: 192-bit key + 64-bit sequence) that has nothing to do with the protocol account nonce. Teach these as two separate counters.
- EIP-7864's binary tree would merge account fields, storage and code into one unified tree with 31-byte stems — i.e. `storageRoot` and `codeHash` as separate committed sub-structures would disappear. Draft only; no fork.
- Practical note for tooling: `eth_getTransactionCount(addr, "pending")` and `"latest"` diverge whenever a sender has in-flight transactions, and after Pectra a 7702 authorization also bumps the nonce — wallets that assumed only transactions move the nonce have shipped bugs.

### Misconceptions
- Belief: The account stores its own address. | Reality: The address is the trie key; the stored record is only the four fields. This is why you cannot enumerate all accounts from a state root without the keccak preimages. | Why: Every database table has an id column. | Source: Yellow Paper §4.1
- Belief: EOAs have no code, contracts have code — that is the whole distinction. | Reality: Post-EIP-7702 an EOA can have a code hash. The real distinction is: only an EOA can be the `tx.origin` of a transaction (it has a private key). | Why: True from 2015 to May 2025. | Source: https://eips.ethereum.org/EIPS/eip-7702
- Belief: The nonce prevents replay attacks. | Reality: It prevents replay *on the same chain*. Cross-chain replay is prevented by EIP-155's chain id, and an EIP-7702 authorization signed with `chain_id = 0` is deliberately replayable on every EIP-7702 chain. | Why: "Replay protection" is taught as one idea. | Source: https://eips.ethereum.org/EIPS/eip-155
- Belief: Your ETH balance is a token balance like USDC's. | Reality: ETH lives in the protocol's `balance` field; ERC-20 balances live in a contract's storage mapping. This asymmetry is exactly why WETH exists and why `transfer` semantics differ. | Why: Wallets render them in one list. | Source: https://ethereum.org/en/developers/docs/accounts/
- Belief: A contract's nonce is always 0 / irrelevant. | Reality: It starts at 1 (EIP-161) and increments on every `CREATE`, which is why factory-deployed addresses are predictable and why `CREATE2` was introduced to escape that dependence. | Why: Nonce is taught only as "transaction counter". | Source: https://eips.ethereum.org/EIPS/eip-161
- Belief: UTXO vs accounts is a Bitcoin-vs-Ethereum trivia question. | Reality: It is the architectural fork that decides whether transactions can execute in parallel. Solana's response was to keep the account model but externalise state into per-item accounts with declared access lists, recovering parallelism. Ethereum's response is EIP-7928 block-level access lists in Glamsterdam. | Why: Taught as history, not as a live design axis. | Source: https://eips.ethereum.org/EIPS/eip-7928
- Belief: Contract storage is stored inside the account record. | Reality: The account holds only a 32-byte `storageRoot`; the storage is a whole separate trie, which is why an `SSTORE` is a state-trie write cascading to the world state root. | Why: "The contract has storage" reads as containment. | Source: Yellow Paper §4.1

## 02.3 — Blocks and chains

### Concepts
- block-header-is-the-block — The header is the only thing hashed and linked; the body (transactions, withdrawals) is committed to *by root hashes inside the header*, so verifying a chain means verifying headers. | requires: [keccak256, mpt-canonical-root] | contrasts: [block-body]
- block-hash-is-header-hash — `blockHash = keccak256(rlp(header))`; nothing in the body is hashed directly into it. | requires: [block-header-is-the-block, rlp-encoding] | contrasts: [transactions-root]
- parent-hash-chain — Each header commits to its parent's hash, which is the only thing making this a *chain*; everything else about ordering is consensus policy layered on top. | requires: [block-hash-is-header-hash] | contrasts: [fork-choice-lmd-ghost]
- state-root-commits-to-all-accounts — `stateRoot` is the root of the account trie *after* executing the block, so it is an outcome, not an input; a wrong execution produces a wrong root and the block is rejected. | requires: [mpt-secure-trie, account-four-fields] | contrasts: [transactions-root]
- transactions-root — Root of an index-keyed trie over the block's transactions, committing to *what was included and in what order* — an input to execution, unlike stateRoot. | requires: [mpt-index-keyed-tries] | contrasts: [state-root-commits-to-all-accounts]
- receipts-root — Root of an index-keyed trie over receipts (status, cumulative gas, logs, bloom), which is what makes event logs provable to an off-chain verifier. | requires: [mpt-index-keyed-tries] | contrasts: [transactions-root]
- logs-bloom — A 2048-bit filter over every log address and topic in the block, letting a client cheaply rule out "no matching events here" without downloading receipts; false positives are expected, false negatives are not. | requires: [receipts-root] | contrasts: [receipts-root]
- withdrawals-root — Shanghai (EIP-4895) added a fourth root for validator withdrawals, which are *system-level balance credits*, not transactions: no gas, no receipt, no sender, not in the transactions trie. | requires: [block-header-is-the-block] | contrasts: [transactions-root]
- requests-hash — Pectra (EIP-7685) replaced per-type request lists with one `requestsHash`, a SHA256 (not keccak) accumulator over typed execution-layer requests — deposits, withdrawal requests, consolidations — flowing EL → CL. | requires: [block-header-is-the-block] | contrasts: [withdrawals-root]
- post-merge-fossil-fields — `difficulty` = 0, `nonce` = 0x00..00, `ommersHash` = the constant hash of an empty list: three header fields kept purely so the RLP layout never changed. | requires: [block-header-is-the-block] | contrasts: [prev-randao]
- ommers-are-historical — Ommers (uncles) rewarded near-miss PoW blocks to reduce mining centralisation; with a single scheduled proposer per slot the concept is meaningless and the list is always empty. | requires: [post-merge-fossil-fields] | contrasts: [slot-vs-block]
- prev-randao — Under PoS the old `mixHash` slot carries `prevRandao`, the beacon chain's RANDAO output; it is biasable by the proposer (who can decline to propose) and is therefore not safe randomness. | requires: [post-merge-fossil-fields] | contrasts: [post-merge-fossil-fields]
- slot-vs-block — Slots are a fixed 12-second heartbeat with one assigned proposer; a block is what a proposer *may* produce. Missed slots mean block numbers stay contiguous while slot numbers do not, so `blockNumber` is not a clock. | requires: [proof-of-stake] | contrasts: [block-time-average]
- epoch-and-finality-timing — 32 slots = 1 epoch = 6.4 minutes; Casper FFG justifies then finalises checkpoints, so finality lands roughly 2 epochs (~12.8 min) behind the head. | requires: [slot-vs-block, accountable-safety] | contrasts: [slot-vs-block]
- parent-beacon-block-root — EIP-4788 puts the previous beacon block root in the EL header and exposes it in a ring-buffer contract, letting EVM contracts verify consensus-layer state (staking, restaking, light clients) without an oracle. | requires: [block-header-is-the-block, slot-vs-block] | contrasts: [state-root-commits-to-all-accounts]
- gas-limit-vs-gas-used — `gasLimit` is a validator-adjustable ceiling (±1/1024 per block) and `gasUsed` is the realised total; `baseFeePerGas` is derived from the parent's gasUsed relative to target, which is the whole EIP-1559 feedback loop. | requires: [block-header-is-the-block] | contrasts: [blob-gas-fields]
- blob-gas-fields — `blobGasUsed` and `excessBlobGas` run a *second, independent* EIP-1559 market for blob space, which is why blob fees and calldata fees move separately. | requires: [gas-limit-vs-gas-used, blob-basics] | contrasts: [gas-limit-vs-gas-used]

### Current state (Aug 2026)
- The execution header is **21 fields** as of Prague/Pectra, in RLP order: `parentHash, ommersHash, beneficiary, stateRoot, transactionsRoot, receiptsRoot, logsBloom, difficulty, number, gasLimit, gasUsed, timestamp, extraData, prevRandao(mixHash slot), nonce, baseFeePerGas, withdrawalsRoot, blobGasUsed, excessBlobGas, parentBeaconBlockRoot, requestsHash`.
- **Fusaka (3 Dec 2025) added no new execution header field.** PeerDAS (EIP-7594) changed how blob data is distributed (128 columns) at the consensus/networking layer; the EL header's blob accounting fields are unchanged.
- **Gas limit is now 60M** (EIP-7935 default, Fusaka), doubled from 30M. Any material quoting a 30M block gas limit or ~15M target is out of date. There is also a per-transaction cap of ~16.78M gas (EIP-7825), which is new and frequently missed — a single transaction can no longer consume a whole block.
- **Slot time is still 12 seconds.** EIP-7782 (6-second slots) was **declined for Glamsterdam** — reportedly because it would squeeze real-time ZK proving, force timing recalibration, and had no complete client implementation. It is expected to be reconsidered for Hegota. Do not teach 6s slots as coming.
- Glamsterdam is unshipped (final devnet mid-June 2026, targeted H2 2026, no mainnet date). Its headline EIPs — EIP-7732 (ePBS) and EIP-7928 (block-level access lists) — both change block *structure and semantics*: ePBS splits the block into a consensus part and a separately-revealed execution payload, and BALs add a declared read/write set to enable parallel execution. Expect the header/payload split to be a teaching point once it lands, but it has not landed.
- Withdrawals have been live and boring since Shanghai; they remain the cleanest example of "a state change that is not a transaction". Post-Pectra there are now *two* withdrawal paths to distinguish: the automatic sweep (EIP-4895, `withdrawalsRoot`) and EL-triggered withdrawal requests (EIP-7002, surfaced through `requestsHash`).
- `blockNumber` and `block.timestamp` are still commonly abused as clocks. Timestamps are proposer-set with only loose bounds; block numbers skip no values but slots do.

### Misconceptions
- Belief: A block is produced every 12 seconds. | Reality: A *slot* occurs every 12 seconds; if the assigned proposer misses it there is no block. Average block time is slightly above 12s and varies. | Why: Pre-Merge Ethereum had probabilistic ~13s block times and the number stuck. | Source: https://ethereum.org/en/developers/docs/consensus-mechanisms/pos/
- Belief: `blockNumber * 12` gives you elapsed time. | Reality: Missed slots break the mapping; block numbers are contiguous, slot numbers are not. Use timestamps, and even then treat them as proposer-influenced. | Why: The two counters look interchangeable. | Source: Yellow Paper §4.3
- Belief: `stateRoot` in a header is the state the block started from. | Reality: It is the post-execution state root. This is why you cannot validate a block without executing it. | Why: "The block contains the state" reads as a snapshot taken at the top. | Source: Yellow Paper §4.3
- Belief: Withdrawals are transactions from the deposit contract. | Reality: They are system-level operations with their own trie and root — no sender, no gas, no receipt, invisible to `eth_getTransactionByHash`. Indexers that only read transactions silently miss validator income. | Why: Every balance change you have ever seen was a transaction. | Source: https://eips.ethereum.org/EIPS/eip-4895
- Belief: Uncles/ommers still exist, they are just rare. | Reality: The list is always empty post-Merge and `ommersHash` is a fixed constant. The field exists so the RLP layout did not have to change. | Why: The field is still in every header you print. | Source: Yellow Paper §4.3 + EIP-3675
- Belief: `block.prevrandao` is on-chain randomness. | Reality: It is RANDAO output, and the slot proposer can bias it by choosing not to propose — a one-bit grind per slot they control, worth more than the block reward for a large enough prize. | Why: It replaced `difficulty` and looks random. | Source: https://eips.ethereum.org/EIPS/eip-4399
- Belief: Blob fees and gas fees are the same market. | Reality: `excessBlobGas` drives an independent EIP-1559 curve; blob prices sat near zero for long stretches while L1 gas was expensive. | Why: Both are called "gas". | Source: https://eips.ethereum.org/EIPS/eip-4844
- Belief: The block gas limit is 30M. | Reality: 60M since Fusaka (EIP-7935), with a ~16.78M per-transaction cap (EIP-7825). | Why: 30M was true from 2021 to late 2025. | Source: https://eips.ethereum.org/EIPS/eip-7935
- Belief: `requestsHash` is another Merkle Patricia root. | Reality: It is a SHA256 accumulator over the typed request byte arrays, not an MPT root — different hash function, different structure. | Why: Every other root in the header is an MPT root. | Source: https://eips.ethereum.org/EIPS/eip-7685

## 02.4 — The mempool

### Concepts
- mempool-is-not-global — There is no "the mempool". Every node keeps its own pool, filled by gossip, with its own limits and eviction policy, so two nodes legitimately disagree about what is pending. | requires: [p2p-gossip] | contrasts: [mempool-pending-is-not-a-queue]
- mempool-view-is-node-local — `txpool_content`, `eth_getTransactionByHash` on an unmined hash and pending-transaction subscriptions all answer *for the node you asked*, which is why two RPC providers give different answers to the same question. | requires: [mempool-is-not-global] | contrasts: [state-root-commits-to-all-accounts]
- pending-vs-queued — Geth splits the pool: *pending* transactions are executable now (nonce contiguous from the account's current nonce); *queued* transactions are parked behind a nonce gap and are not gossiped or mined. | requires: [nonce-total-ordering, mempool-is-not-global] | contrasts: [mempool-pending-is-not-a-queue]
- nonce-gap — Sending nonce N+1 before N leaves N+1 queued indefinitely; it is not "slow", it is structurally ineligible until N lands. Most "stuck transaction" incidents are this. | requires: [pending-vs-queued, account-nonce-eoa] | contrasts: [transaction-replacement]
- transaction-replacement — There is no cancel and no edit. Replacing means broadcasting a *different* transaction with the *same* sender and nonce; whichever one gets mined invalidates the other. | requires: [account-nonce-eoa] | contrasts: [nonce-gap]
- price-bump-rule — Nodes reject a replacement unless its fees beat the incumbent's by a policy margin — geth's default is 10% on both `maxFeePerGas` and `maxPriorityFeePerGas`. This is anti-DoS policy, not consensus. | requires: [transaction-replacement, eip-1559-fee-fields] | contrasts: [blob-pool-different-rules]
- cancellation-is-a-replacement — "Cancelling" is sending a 0-ETH self-transfer at the same nonce with bumped fees; it can lose the race, and it costs gas when it wins. | requires: [transaction-replacement, price-bump-rule] | contrasts: [nonce-gap]
- blob-pool-different-rules — Blob transactions live in a separate pool with stricter rules: 100% fee bump to replace (not 10%), a minimum fee floor, and **nonce-gapped blob transactions are disallowed outright**. | requires: [price-bump-rule, blob-basics] | contrasts: [price-bump-rule]
- eip-1559-fee-fields — `maxFeePerGas` is what you will tolerate; `maxPriorityFeePerGas` is what the block producer keeps. Inclusion depends on the tip relative to competitors, refunds happen automatically, and a too-low `maxFeePerGas` makes a transaction ineligible whenever base fee rises above it. | requires: [gas-limit-vs-gas-used] | contrasts: [price-bump-rule]
- mempool-pending-is-not-a-queue — Pending is a *set*, priced and re-sorted every block; a builder picks the most profitable ordering, so arrival time confers no position. FIFO intuition is the single most damaging mental model here. | requires: [pending-vs-queued, mev-boost] | contrasts: [pending-vs-queued]
- mempool-is-a-public-broadcast — Anything in the public pool is a signed, readable statement of intent to every node, which is what makes frontrunning and sandwiching possible; the mempool is an adversarial channel, not a staging area. | requires: [mempool-is-not-global] | contrasts: [private-orderflow]
- private-orderflow — Users and apps increasingly submit through private RPCs straight to builders, skipping the public pool entirely, in exchange for MEV protection and sometimes a rebate. | requires: [mempool-is-a-public-broadcast, mev-boost] | contrasts: [mempool-is-a-public-broadcast]
- order-flow-auctions — OFAs (MEV Blocker, MEV-Share-style systems) auction the right to backrun a user's transaction and return part of the proceeds to the user, turning orderflow into a monetised asset. | requires: [private-orderflow] | contrasts: [mempool-is-a-public-broadcast]
- private-orderflow-centralises-building — Exclusive orderflow is the main input to builder market share; a builder others cannot see cannot be outbid, which is the structural driver behind the top-2 builder concentration. | requires: [private-orderflow, mev-boost] | contrasts: [mempool-is-not-global]
- pool-limits-and-eviction — Pools are bounded (per-account and global slot caps, plus a lifetime after which stale transactions are dropped); a transaction can silently disappear from every pool and simply never be mined. | requires: [mempool-is-not-global] | contrasts: [transaction-replacement]
- inclusion-lists-are-not-live — FOCIL (EIP-7805) would force proposers to include eligible public-mempool transactions, restoring censorship resistance; it was **declined for Glamsterdam** and deferred, so today there is no protocol-level inclusion guarantee. | requires: [private-orderflow-centralises-building] | contrasts: [mempool-pending-is-not-a-queue]

### Primary sources

### Current state (Aug 2026)
- **The public mempool is no longer the main path to inclusion.** Somewhere between "most" and "the large majority" of value-bearing orderflow now reaches builders privately. Teach the *direction* as settled and the *percentage* as contested (see Gaps).
- MEV-Boost still builds ~90% of blocks; top 2 builders (Titan, Quasar) ~73% share, top 4 >95%. Exclusive private orderflow is the causal mechanism, not a side effect — this is the link between 02.4 and any MEV module.
- **FOCIL (EIP-7805) was declined for Glamsterdam** and deferred to Hegota. So as of Aug 2026 there is still no protocol mechanism forcing a proposer to include a public-mempool transaction. Any material claiming inclusion lists are coming in the next fork is wrong.
- **EIP-7732 (ePBS)** is a Glamsterdam headline EIP and would restructure the proposer/builder relationship in-protocol, but it is unshipped and has no mainnet date.
- Fusaka's gas-limit doubling (30M → 60M) roughly doubled per-block capacity, which changes mempool dynamics: less persistent backlog at the same demand, and the ~16.78M per-transaction cap (EIP-7825) means a single huge transaction can no longer monopolise a block.
- PeerDAS (EIP-7594) changed blob *distribution*, not blob mempool admission; the blobpool's 100% replacement bump and no-nonce-gap rules still apply.
- EIP-7702 delegations added a new mempool consideration: a pending 7702 authorization consumes the authority's nonce, so wallets tracking only transactions can compute a wrong next nonce and produce a gap. Also, delegated EOAs mean an address's behaviour can change between the time a transaction is simulated and the time it is included.
- `eth_sendRawTransaction` against a private RPC is now the default for consumer wallets in practice; a product engineer should assume their user's transaction may never appear in any public pool, and should not build UX that depends on seeing it there.

### Misconceptions
- Belief: There is a global mempool. | Reality: Each node has its own pool with its own limits; the union is not observable and no node holds it. "Is my transaction in the mempool?" is only answerable per-node. | Why: Block explorers present one "pending" list. | Source: https://github.com/ethereum/go-ethereum/blob/master/core/txpool/
- Belief: Pending transactions are a queue and mine is in line. | Reality: Pending is a re-priced set; builders order by profit each block. A transaction submitted an hour ago has no priority over one submitted 200ms ago with a higher tip. | Why: Every other system with a "pending" state is FIFO. | Source: https://arxiv.org/html/2410.12352
- Belief: I can cancel a transaction. | Reality: You can only *race* it with a replacement at the same nonce and higher fees, and you may lose. Wallet "cancel" buttons are exactly this. | Why: The UI says Cancel. | Source: geth txpool
- Belief: Any higher gas price replaces a pending transaction. | Reality: Geth requires ≥10% higher on both `maxFeePerGas` and `maxPriorityFeePerGas`; +1 wei is rejected with "replacement transaction underpriced". For blob transactions it is **100%**. | Why: The rule is client policy, not in any EIP, so it is rarely taught. | Source: geth `core/txpool`, `blobpool.PriceBump = 100`
- Belief: Blob transactions behave like normal transactions with extra data. | Reality: Separate pool, 100% replacement bump, a fee floor, and nonce gaps forbidden entirely. L2 batcher tooling that assumes normal-pool semantics breaks here. | Why: They look like type-3 transactions in an explorer. | Source: https://github.com/ethereum/go-ethereum/blob/master/core/txpool/blobpool/blobpool.go
- Belief: A transaction with a low `maxFeePerGas` will eventually be mined. | Reality: It is ineligible in any block whose base fee exceeds it, and pools evict on lifetime and slot pressure, so it can simply vanish from every node. | Why: "It's still pending" implies it is still alive somewhere. | Source: https://eips.ethereum.org/EIPS/eip-1559
- Belief: Raising `maxPriorityFeePerGas` gets you in faster. | Reality: It helps only relative to competitors for the same block, and it does nothing at all if your transaction was routed privately or is stuck behind a nonce gap. | Why: "Tip" sounds like a speed dial. | Source: https://eips.ethereum.org/EIPS/eip-1559
- Belief: Watching the public mempool tells you what is about to happen on-chain. | Reality: A large and growing share of value-bearing flow is private; mempool-based analytics and liquidation bots see a systematically biased sample. | Why: This was true in 2020. | Source: https://arxiv.org/html/2410.12352
- Belief: Private RPCs are strictly better for users. | Reality: They trade public frontrunning risk for trust in the operator and, sometimes, slower inclusion; they also concentrate builder power. It is a tradeoff with measured costs. | Why: "MEV protection" is marketed as free. | Source: https://arxiv.org/html/2505.19708v1
