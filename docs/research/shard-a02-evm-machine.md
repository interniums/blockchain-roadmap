## 03.2 — State & tries: how Ethereum commits to "everything that exists"

### Concepts
- state-as-keyvalue — Ethereum's world state is one global key→value map from 20-byte address to an account record, not a set of transactions; the chain of blocks is only the log of edits to it. | requires: [] | contrasts: [utxo-model, solana-account-model]
- account-record-four-fields — Every account (EOA or contract) is exactly four fields: nonce, balance, storageRoot, codeHash, RLP-encoded as the trie leaf value. | requires: [state-as-keyvalue] | contrasts: [account-arbitrary-struct]
- eoa-vs-contract-same-record — EOAs and contracts share the identical record shape; an EOA is just an account whose codeHash is the hash of the empty string, which is why EIP-7702 can turn an EOA into a code-bearing account with a single field write. | requires: [account-record-four-fields] | contrasts: [eoa-separate-type]
- merkle-patricia-trie — The state is stored in a hexary (16-way) Merkle Patricia Trie: a radix trie whose every node is identified by the keccak256 of its RLP encoding, so one 32-byte root commits to the whole map. | requires: [account-record-four-fields, keccak256] | contrasts: [binary-merkle-tree, sparse-merkle-tree]
- trie-node-kinds — The MPT has three node kinds — leaf, extension (path compression for a shared prefix), and branch (17 slots: 16 nibbles plus a value) — and the compression is what keeps proofs short on a sparse key space. | requires: [merkle-patricia-trie] | contrasts: []
- secure-trie-hashed-keys — Trie keys are keccak256(address) and keccak256(slot), not the raw values; hashing spreads keys uniformly so an attacker cannot grind adjacent keys to build a pathologically deep, expensive subtree. | requires: [merkle-patricia-trie] | contrasts: [raw-key-trie]
- per-account-storage-trie — Each contract has its own separate storage trie keyed by keccak256(32-byte slot number); its root is the storageRoot field inside that account's leaf, so state is a trie of tries. | requires: [account-record-four-fields, merkle-patricia-trie] | contrasts: [flat-storage-map]
- zero-slot-is-absent — Writing zero to a storage slot deletes the key from the storage trie rather than storing a zero, which is why clearing a slot earns a gas refund and why "never written" and "written to zero" are indistinguishable on-chain. | requires: [per-account-storage-trie] | contrasts: [null-vs-zero]
- state-root-is-post-execution — The header's stateRoot is the root *after* executing every transaction in the block plus withdrawals; it is the block's claim about the resulting world, and every validating node recomputes it independently. | requires: [merkle-patricia-trie] | contrasts: [state-root-pre-execution]
- three-block-tries — A block header carries three separate trie commitments: stateRoot (world after), transactionsRoot (what was submitted), receiptsRoot (what execution produced), plus withdrawalsRoot since Shanghai. | requires: [state-root-is-post-execution] | contrasts: []
- tx-and-receipt-tries-are-index-keyed — The transactions and receipts tries are keyed by RLP(index-in-block), not by hash, and exist only for that one block; they are throwaway commitment structures, not queryable global databases. | requires: [three-block-tries] | contrasts: [per-account-storage-trie]
- receipt-contents — A receipt is [status, cumulativeGasUsed, logsBloom, logs]; since Byzantium (EIP-658) the first field is a 1/0 success flag, replacing the intermediate state root that older tutorials still describe. | requires: [three-block-tries] | contrasts: [receipt-post-state-root]
- eth-getproof — eth_getProof (EIP-1186) returns the RLP-encoded node path from stateRoot down to an account leaf, plus per-slot paths from that account's storageRoot, letting anyone who trusts only the 32-byte state root verify a balance or storage slot offline. | requires: [merkle-patricia-trie, state-root-is-post-execution] | contrasts: [trusted-rpc-read]
- proof-vs-trust — A Merkle proof proves "this value is under this root"; it does not prove the root is canonical, so light clients and bridges still need a separate mechanism (consensus light client, committee signature) to trust the root itself. | requires: [eth-getproof] | contrasts: [proof-proves-truth]
- state-growth-problem — The MPT's depth and keccak-hashed keys make random state access disk-bound, and state size growth is the main reason clients moved to path-based/flat storage layouts and why binary-tree replacements are being designed. | requires: [merkle-patricia-trie] | contrasts: []

### Primary sources
- [EIP-1186: RPC-Method to get Merkle Proofs — eth_getProof](https://eips.ethereum.org/EIPS/eip-1186) — tier: spec — published: 2018-06 — normative definition of accountProof/storageProof shape; still the exact response format clients return in 2026.
- [EIP-658: Embedding transaction status code in receipts](https://eips.ethereum.org/EIPS/eip-658) — tier: spec — published: 2017-06 — the change that replaced the receipt's post-state root with a status byte; kills a common stale explanation.
- [EIP-2718: Typed Transaction Envelope](https://eips.ethereum.org/EIPS/eip-2718) — tier: spec — published: 2020-06 — why transaction and receipt trie *values* are now `type-byte || payload` rather than plain RLP.
- [EIP-7685: General purpose execution layer requests](https://eips.ethereum.org/EIPS/eip-7685) — tier: spec — published: 2024-04 — added the header's requestsHash in Pectra; a header commitment that is deliberately NOT an MPT root.
- [EIP-4895: Beacon chain push withdrawals as operations](https://eips.ethereum.org/EIPS/eip-4895) — tier: spec — published: 2022-03 — added withdrawalsRoot to the header; state changes that are not transactions.
- [EIP-7864: Ethereum state using a unified binary tree](https://eips.ethereum.org/EIPS/eip-7864) — tier: spec — published: 2024-12 — the live proposal to replace the hexary MPT with a unified binary tree; supersedes Verkle as the direction of travel.
- [Ethereum Execution Layer Specification (EELS / execution-specs)](https://github.com/ethereum/execution-specs) — tier: spec — published: 2026 — the executable Python spec; `trie.py` is the authoritative MPT implementation to read.
- [Ethereum Execution APIs — eth_getProof / block object schema](https://ethereum.github.io/execution-apis/) — tier: spec — published: 2026 — current JSON-RPC schemas including the post-Pectra header fields.
- [Ethereum stateless book — Binary Tree](https://stateless.fyi/trees/binary-tree.html) — tier: primary-analysis — published: 2025 — the clearest maintained write-up of the binary-tree migration design and why MPT is being frozen rather than converted.
- [Chainstack: Deep dive into Merkle proofs and eth_getProof](https://docs.chainstack.com/docs/deep-dive-into-merkle-proofs-and-eth-getproof-ethereum-rpc-method) — tier: vendor — published: 2024 — vendor, but has runnable proof-verification walkthroughs.

### Current state (Aug 2026)
- The hexary Merkle Patricia Trie is still the production state commitment on mainnet. Nothing has replaced it.
- **Verkle is dead as the migration path.** After years of being the assumed answer, Verkle trees were dropped in favour of EIP-7864's unified binary tree. Curricula that teach "Verkle is coming next" are out of date. The binary tree's hash function is still undecided between BLAKE3 and a Poseidon variant.
- EIP-7864's design freezes the existing MPT and starts a new empty binary tree that absorbs new writes, rather than doing a big-bang conversion. Treat any claimed shipping date as speculation — it is not in Glamsterdam's headline set (EIP-7732 ePBS and EIP-7928 block-level access lists are).
- Post-Merge header fields are dead constants that still confuse readers: difficulty is 0, nonce is 0, ommersHash is the hash of an empty list, and mixHash now carries prevRandao.
- Header commitments added since 2023: withdrawalsRoot (Shanghai), blobGasUsed + excessBlobGas + parentBeaconBlockRoot (Cancun), requestsHash (Pectra). requestsHash is a flat SHA-256 commitment, not a Merkle Patricia root — the first header field to break the "everything is an MPT root" pattern.
- Client storage layouts have diverged from the textbook: Geth's path-based state scheme, Erigon's flat state, and Reth's separate flat-table + trie design all mean the on-disk representation is no longer "the trie". The trie is a commitment; the database is flat. This is invisible over JSON-RPC but explains why archive-node sizes and sync strategies differ so wildly between clients.
- EIP-7928 (block-level access lists), a Glamsterdam headline EIP, would put a per-block list of touched accounts/slots in the block, which is effectively a pre-declared read/write set for parallel execution. Not shipped.

### Misconceptions
- Belief: The blockchain stores balances directly in blocks. | Reality: Blocks store transactions and a single 32-byte root; the balance lives in a trie whose nodes clients maintain separately. | Why: "Ledger" framing from Bitcoin and from accounting analogies. | Source: https://github.com/ethereum/execution-specs
- Belief: Contract storage is a big flat mapping you can enumerate. | Reality: It is a per-contract trie keyed by keccak256(slot); there is no supported way to list "all non-zero slots" over standard JSON-RPC. | Why: Solidity's `mapping` syntax hides the hashing. | Source: https://eips.ethereum.org/EIPS/eip-1186
- Belief: A receipt contains the state root after that transaction. | Reality: Since Byzantium it contains a 1/0 status byte instead. | Why: Pre-2017 tutorials and old diagrams are still widely copied. | Source: https://eips.ethereum.org/EIPS/eip-658
- Belief: eth_getProof proves data is true. | Reality: It proves data is committed under a given root; you must obtain and trust that root independently. | Why: "Merkle proof" sounds self-sufficient. | Source: https://eips.ethereum.org/EIPS/eip-1186
- Belief: Verkle trees are Ethereum's next state format. | Reality: Verkle was superseded by EIP-7864's unified binary tree; Verkle is not on the roadmap as the migration target any more. | Why: Verkle was heavily promoted 2021-2024 and dominates older explainer content. | Source: https://eips.ethereum.org/EIPS/eip-7864
- Belief: Every block header root is a Merkle Patricia root. | Reality: requestsHash (Pectra) is a plain SHA-256 commitment over concatenated request hashes. | Why: Pattern-matching on the other four roots. | Source: https://eips.ethereum.org/EIPS/eip-7685
- Belief: Setting a storage slot to zero leaves a zero in the trie. | Reality: It removes the key entirely, which is precisely why clearing storage is refundable. | Why: Mental model imported from ordinary databases. | Source: https://github.com/ethereum/execution-specs
- Belief: The transactions trie is how you look up a transaction by hash. | Reality: It is keyed by index within one block; hash→transaction lookup is a client-side index, not a protocol structure. | Why: Etherscan makes hash lookup feel native. | Source: https://github.com/ethereum/execution-specs

### Practice ideas
- kind: implement — Write a standalone `verifyAccountProof(stateRoot, address, proof)` in TypeScript or Rust: walk the RLP node list, re-keccak each node, check it matches the hash referenced by its parent, consume nibbles of keccak256(address), and return the decoded [nonce, balance, storageRoot, codeHash]. Feed it live output from `eth_getProof` on a public RPC. — acceptance: verifies a real mainnet account against a root fetched from a *different* provider, and rejects the proof when any single byte of any node is flipped.
- kind: measure — For a deployed ERC-20, compute the storage slot for a holder's balance as keccak256(abi.encode(holder, mappingSlot)), fetch it with `eth_getStorageAt`, and compare to the value from `balanceOf`. — acceptance: the two agree for three different holders, and the learner can state the slot formula without looking it up.
- kind: read — Open `trie.py` in ethereum/execution-specs and identify the three node kinds and the exact point where keys are hashed. — acceptance: learner can explain in one sentence why the trie hashes keys and what attack it prevents.
- kind: break — Take a valid `eth_getProof` response, delete the final leaf node from `accountProof`, and re-run the verifier. Then try substituting a leaf from a *different* account. — acceptance: the verifier rejects both, and the learner can say which invariant caught each case.
- kind: measure — Use Foundry's `vm.load`/`vm.store` cheatcodes to zero a non-zero slot in a fork test and record `gasleft()` deltas versus writing a fresh non-zero value. — acceptance: learner produces the three-way gas comparison (zero→non-zero, non-zero→non-zero, non-zero→zero) with numbers from their own run, not from a table.
- kind: write — Write a 200-word explanation of why `stateRoot` lets a phone verify a balance without downloading Ethereum, aimed at a product manager. — acceptance: mentions the root, the proof path, and explicitly names the trust assumption that remains.

### Visual opportunities
- **Trie of tries**: one diagram showing header → stateRoot → account leaf (four fields highlighted) → storageRoot → storage trie. This single picture explains more than any prose; the recursion is the whole idea.
- **A proof is a path, not a tree**: overlay the returned `accountProof` node list on a drawn trie, showing that a proof is the sibling-hash path, and that its length is the trie depth.
- **Header field anatomy, annotated by era**: colour-code header fields by the fork that introduced them (Frontier / Byzantium / Merge-dead-constants / Shanghai / Cancun / Pectra). Makes "why are there dead fields" self-answering.
- **Hexary vs binary branching**: side-by-side node fan-out showing why 16-way nodes make proofs wide (many sibling hashes per level) and why binary trees trade depth for narrower proofs.
- **Same key, four hashings**: address → keccak → trie path; slot number → keccak → storage path; mapping key → keccak(key ‖ slot) → slot number. Learners routinely conflate these three keccaks.

### Gaps & uncertainties
- **requestsHash exact construction**: I did not open the final Pectra text of EIP-7685 to confirm the precise nesting (whether it is `sha256(sha256(req_0) ‖ sha256(req_1) ‖ …)` and whether empty request types are skipped). The claim that it is SHA-256-based and not an MPT root is confident; the exact formula must be re-checked against the EIP before publishing.
- **EIP-7864 hash function**: BLAKE3 vs Poseidon2 is genuinely undecided as of Aug 2026. Do not teach a winner.
- **EIP-7864 performance numbers**: search results carried claims of ~4x shorter branches, ~3x faster proving with BLAKE3, and "up to 100x" with Poseidon variants. These came from secondary summaries, not from the EIP or a benchmark I read. Do not publish these figures without reading the EIP's own analysis.
- **Empty-value constants**: the well-known empty-trie root and empty-code hash constants were not re-verified this session. If a lesson prints literal hex for `keccak256("")` or the empty MPT root, re-derive them locally first.
- **Fusaka/Glamsterdam impact on state format**: none found, but I did not exhaustively check whether any Fusaka EIP altered trie semantics. Assume unchanged, verify before asserting.
- **Client on-disk layouts**: the Geth path-based / Erigon flat / Reth split-table characterisations are from general knowledge, not re-verified against client docs this session. Directionally right; specific claims need a client-docs citation.

## 03.5 — EVM execution: the loop, call frames, creation, and the three ways to fail

### Concepts
- evm-execution-loop — Execution is a plain interpreter loop over a byte array: fetch the opcode at the program counter, check stack depth, charge gas, mutate stack/memory/state, advance PC — repeat until a halting instruction or an exception. | requires: [] | contrasts: [jit-execution]
- gas-is-a-countdown — Gas is a single decrementing counter charged *before* each operation; running it to zero is not an error condition the code can observe, it is an immediate exceptional halt. | requires: [evm-execution-loop] | contrasts: [gas-as-fee]
- deterministic-single-threaded — One transaction executes alone, in order, with no concurrency, no clock, no I/O and no randomness beyond block values; every node must reach byte-identical results, which is why every "environment" opcode is a fixed block or tx field. | requires: [evm-execution-loop] | contrasts: [parallel-execution, solana-sealevel]
- call-frame — Every CALL-family instruction opens a new frame with its own stack, memory, PC and gas allowance; only storage, balances and logs are shared through to the outer world state. | requires: [evm-execution-loop] | contrasts: [function-call-same-frame]
- memory-is-per-frame — A frame's memory is fresh and zeroed and dies with the frame; nothing is inherited from the caller except the explicitly copied calldata region. | requires: [call-frame] | contrasts: [shared-heap]
- four-call-variants — CALL runs the callee's code in the callee's storage; DELEGATECALL runs the callee's code in the *caller's* storage while preserving msg.sender and msg.value; STATICCALL is CALL with all state mutation banned; CALLCODE is a deprecated ancestor of DELEGATECALL. | requires: [call-frame] | contrasts: []
- delegatecall-is-the-proxy-primitive — DELEGATECALL is the entire basis of upgradeable proxies and of EIP-7702 delegation: borrowed code, your storage, your identity — and therefore the entire basis of storage-collision bugs. | requires: [four-call-variants, per-account-storage-trie] | contrasts: [call-isolated-storage]
- sixty-three-sixty-fourths — EIP-150 forbids forwarding all remaining gas: a caller can pass at most 63/64 of what it holds, so the caller always survives a callee that burns everything and can react. | requires: [call-frame, gas-is-a-countdown] | contrasts: [forward-all-gas]
- depth-limit-1024 — Call depth is hard-capped at 1024 frames; exceeding it makes the call return failure rather than throwing, which historically made "check the return value" a security requirement. | requires: [call-frame] | contrasts: []
- call-returns-a-boolean — A low-level CALL pushes 1 or 0 onto the stack; a failed inner call does NOT automatically abort the caller, so ignoring that boolean silently swallows failures. | requires: [call-frame] | contrasts: [exceptions-propagate]
- returndata-buffer — RETURNDATASIZE/RETURNDATACOPY read a single buffer that is overwritten by every sub-call — including failed ones, where it holds the revert payload — and RETURNDATACOPY reverts on out-of-bounds reads instead of zero-padding like CALLDATACOPY. | requires: [call-frame] | contrasts: [calldata-zero-pads]
- three-failure-modes — REVERT undoes state, returns data, and refunds unused gas; an exceptional halt (invalid opcode, stack under/overflow, static-context violation) undoes state, returns nothing, and burns all gas in the frame; out-of-gas is a special case of the latter. | requires: [gas-is-a-countdown, call-frame] | contrasts: [single-error-type]
- revert-data-encoding — Revert payloads are ABI-encoded like calls: Error(string) = 0x08c379a0, Panic(uint256) = 0x4e487b71, and custom errors are the 4-byte selector of their signature — which is why unknown reverts look like opaque hex. | requires: [three-failure-modes, returndata-buffer] | contrasts: [plain-string-error]
- create-address-from-nonce — CREATE derives the new address as the last 20 bytes of keccak256(rlp([sender, sender_nonce])), so the address depends on deployment order and cannot be known before the deployer's nonce is fixed. | requires: [call-frame, account-record-four-fields] | contrasts: [create2-address]
- create2-address — CREATE2 derives the address from keccak256(0xff ‖ sender ‖ salt ‖ keccak256(initcode))[12:], making it fully predictable from the initcode and salt — the basis of counterfactual deployment, deterministic multichain addresses and smart-account factories. | requires: [create-address-from-nonce] | contrasts: [create-address-from-nonce]
- initcode-vs-runtime-code — Deployment runs the initcode, and whatever bytes it RETURNs become the account's permanent code; constructor arguments and constructor logic exist only during that one execution and are not part of the deployed contract. | requires: [create-address-from-nonce] | contrasts: [code-is-what-you-wrote]
- code-deposit-and-size-limits — Storing the returned code costs 200 gas per byte, contract code is capped at 24,576 bytes (EIP-170), initcode at 49,152 bytes (EIP-3860), and code may not begin with 0xEF (EIP-3541) — the reserved prefix EIP-7702 later used for delegation designators. | requires: [initcode-vs-runtime-code] | contrasts: []
- selfdestruct-neutered — Since EIP-6780 (Cancun), SELFDESTRUCT only erases code and storage if the contract was created in the *same transaction*; otherwise it merely sweeps the balance and the contract keeps living. | requires: [initcode-vs-runtime-code] | contrasts: [selfdestruct-deletes-contract]
- warm-cold-access — EIP-2929 makes the first touch of an address or storage slot in a transaction expensive (cold) and every later touch cheap (warm), so identical code costs wildly different gas depending on what ran before it. | requires: [gas-is-a-countdown] | contrasts: [flat-opcode-cost]

### Current state (Aug 2026)
- **EOF did not ship.** It was rejected for Fusaka, and Solidity 0.8.36 removed its experimental EOF backend entirely. Any material that teaches EOF sections, EOF's separate code/data areas, or EOF's replacement call instructions (EXTCALL/EXTDELEGATECALL/EXTSTATICCALL) as current reality is wrong. Teach the legacy CALL family.
- Consequently EIP-7830's larger EOF code-size limits are also not live. EIP-170's 24,576 and EIP-3860's 49,152 remain the real ceilings. EIP-7903 (remove the initcode cap) is a draft.
- **EIP-7702 (Pectra, May 2025) changed what a "contract call" means.** Calling a delegated EOA runs the delegate's code with the EOA as the storage and identity context. Concretely: `msg.sender == tx.origin` no longer implies the caller has no code, and EXTCODESIZE on a delegated EOA returns 23 (the `0xef0100 ‖ address` designator) while CODESIZE inside the delegated execution reports the delegate's real code size. Delegation chains are not followed.
- **EIP-7825 (Fusaka, Dec 2025) caps a single transaction at ~16.78M gas** even though the block limit rose to 60M (EIP-7935). A single monolithic deployment or batch can now hit a per-transaction ceiling that did not exist before, while the block has room. This is new and under-taught.
- New precompiles are live: BLS12-381 (EIP-2537, Pectra) and secp256r1/P-256 at address 0x100 costing 6900 gas (EIP-7951, Fusaka). The P-256 precompile is what makes passkey-signed smart accounts cheap; it belongs in any 2026 account-abstraction lesson.
- EIP-1153 transient storage is live: TSTORE/TLOAD at 100 gas, cleared at end of transaction, and — critically — **reverted along with everything else when a frame reverts**. Solidity 0.8.34 shipped a high-severity fix for incorrect transient-storage clearing, so pin ≥0.8.34 if a lesson uses it.
- SELFDESTRUCT is effectively vestigial: on 2025 data, essentially all remaining uses are the same-transaction create-and-destroy pattern that EIP-6780 still permits.
- Glamsterdam's EIP-7928 (block-level access lists) would pre-declare each block's read/write sets, which is the groundwork for parallel execution. Not shipped, no mainnet date.

### Misconceptions
- Belief: A failed inner call aborts the whole transaction. | Reality: A low-level CALL just pushes 0; only Solidity's high-level call syntax inserts an automatic bubble-up. Raw assembly and `.call{}` do not. | Why: Every mainstream language propagates exceptions by default. | Source: https://eips.ethereum.org/EIPS/eip-140
- Belief: `assert` compiles to the INVALID opcode and burns all gas. | Reality: Since Solidity 0.8.0 `assert` reverts with `Panic(uint256)` and refunds unused gas; the burn-everything behaviour is pre-0.8 history. | Why: The old behaviour was heavily taught and the docs' phrasing about "Panic" is easy to miss. | Source: https://docs.soliditylang.org/en/latest/control-structures.html
- Belief: SELFDESTRUCT deletes a contract. | Reality: Since Cancun it only does so if the contract was created in the same transaction; otherwise the code and storage survive and only ETH moves. | Why: EIP-6780 is recent and pre-2024 material dominates search results. | Source: https://eips.ethereum.org/EIPS/eip-6780
- Belief: `send`/`transfer`'s 2300-gas stipend is the safe way to send ETH. | Reality: The stipend is a fixed number against opcode costs that have repeatedly been repriced; the current guidance is `call` with an explicit reentrancy guard. | Why: A 2017-era security rule that outlived its assumptions. | Source: https://eips.ethereum.org/EIPS/eip-2929
- Belief: You can forward all your remaining gas to a callee. | Reality: EIP-150 caps forwarding at 63/64 of what you hold, so the caller always retains a slice. | Why: `call{gas: gasleft()}` reads as if it forwards everything. | Source: https://eips.ethereum.org/EIPS/eip-150
- Belief: The return data buffer holds the last *successful* call's output. | Reality: It holds the last call's output whatever the outcome, and a revert payload lands there too — which is exactly how revert reasons are read. | Why: The name "return data" implies success. | Source: https://eips.ethereum.org/EIPS/eip-211
- Belief: RETURNDATACOPY zero-pads past the end, like CALLDATACOPY. | Reality: It reverts. The asymmetry has produced real bugs in hand-written assembly. | Why: The two opcodes look symmetric. | Source: https://eips.ethereum.org/EIPS/eip-211
- Belief: A CREATE2 address is fixed by the contract's source. | Reality: It is fixed by keccak256 of the *initcode*, which includes constructor arguments — change an argument and the address changes. | Why: "Deterministic deployment" is usually explained without mentioning constructor args. | Source: https://eips.ethereum.org/EIPS/eip-1014
- Belief: Constructor code lives in the deployed contract. | Reality: The constructor runs once during initcode and is not part of the deployed runtime bytecode; `extcodesize` during construction is 0. | Why: The source file shows one contract, so it feels like one artefact. | Source: https://github.com/ethereum/execution-specs
- Belief: EOF is how the EVM works now. | Reality: EOF was rejected for Fusaka and its Solidity backend was removed in 0.8.36. | Why: EOF was extensively pre-announced through 2024-2025. | Source: https://eips.ethereum.org/EIPS/eip-7830
- Belief: Gas costs per opcode are constants you can memorise. | Reality: EIP-2929 makes the same SLOAD cost 2100 cold or 100 warm depending on transaction history, and access lists shift the boundary. | Why: Opcode gas tables in tutorials print one number. | Source: https://eips.ethereum.org/EIPS/eip-2929

### Practice ideas
- kind: implement — Write a Solidity contract with a `deploy(bytes32 salt, bytes memory initcode)` CREATE2 factory plus a pure `predict(bytes32 salt, bytes32 initcodeHash)` function implementing the 0xff formula by hand in assembly. — acceptance: `predict` matches the deployed address in a Foundry test for three different salts, and the test also proves that changing a constructor argument changes the address.
- kind: break — Write `A` that low-level-calls `B`, where `B` always reverts, and A ignores the returned boolean. Assert in a Foundry test that A's transaction *succeeds* and A's state changed anyway. — acceptance: learner produces a passing test that demonstrates the silent-failure bug, then a second test showing the fixed version reverts.
- kind: measure — Instrument a contract that calls itself recursively and record the exact depth at which the call starts returning 0. Then, separately, measure how few frames it takes for the 63/64 rule to starve the innermost frame of gas. — acceptance: learner reports both numbers from their own run and explains why the two limits bite at different depths.
- kind: fix — Take a proxy whose implementation declares its own state variable in slot 0, colliding with the proxy's admin slot. Demonstrate the corruption, then fix it using an ERC-1967 style hashed storage slot. — acceptance: a test that fails before and passes after, plus a one-line explanation of why DELEGATECALL made the collision possible.
- kind: read — Decode three real failed mainnet transactions' revert data by hand: one `Error(string)`, one `Panic(uint256)`, one custom error. — acceptance: learner identifies each selector and states the panic code's meaning without a decoder tool.
- kind: implement — Build a minimal EVM interpreter in TypeScript or Rust supporting roughly 25 opcodes (arithmetic, PUSH, DUP, SWAP, MSTORE/MLOAD, JUMP/JUMPI with a jumpdest table, SSTORE/SLOAD against a HashMap, RETURN, REVERT). — acceptance: runs a hand-assembled bytecode program that loops and returns a computed value, and correctly distinguishes REVERT from an invalid jump.
- kind: measure — Call the same view function twice in one transaction and log `gasleft()` deltas to observe the cold-then-warm price difference; repeat with an EIP-2930 access list attached. — acceptance: learner produces three numbers and can name which EIP caused each.

### Visual opportunities
- **Frame stack with context columns**: a vertical stack of frames, each annotated with `address(this)`, `msg.sender`, `msg.value`, and "whose storage". Run CALL, DELEGATECALL and STATICCALL through it side by side. This one diagram prevents most proxy confusion.
- **Gas as a funnel**: caller holds G, forwards at most 63/64·G, callee forwards 63/64 of that. Shows visually why deep call chains starve.
- **Three exits from a frame**: a decision diagram with REVERT / exceptional halt / normal RETURN, each labelled with three outcomes (state? gas? return data?). Learners conflate these constantly.

- **EIP-7702 seen from outside vs inside**: same EOA, two observers — EXTCODESIZE sees 23 bytes of designator, CODESIZE inside execution sees the delegate. Best done as a split panel.

## 03.6b — Opcodes & the memory model: four places bytes can live

### Concepts
- word-is-256-bits — Every stack item is exactly 32 bytes; the EVM has no smaller native word, which is why `uint8` arithmetic is *more* expensive than `uint256` (it needs masking) and why 256 bits was chosen — keccak256 and elliptic-curve field arithmetic both want that width. | requires: [evm-execution-loop] | contrasts: [byte-addressable-cpu]
- stack-depth-1024 — The operand stack holds at most 1024 items; overflowing or underflowing it is an exceptional halt, not a recoverable error. | requires: [word-is-256-bits] | contrasts: [unbounded-stack]
- stack-reach-16 — DUP and SWAP come in variants 1-16 only, so code can address just the top 16 stack slots; anything deeper is unreachable without shuffling. | requires: [stack-depth-1024] | contrasts: [random-access-registers]
- stack-too-deep — "Stack too deep" is the compiler hitting the 16-slot reach with too many live local variables — a machine limitation surfacing as a language error, historically worked around with structs, scopes and fewer locals. | requires: [stack-reach-16] | contrasts: []
- memory-is-a-flat-byte-array — Memory is a zero-initialised, byte-addressable array that grows on demand, is private to one call frame, and vanishes when the frame ends. | requires: [memory-is-per-frame] | contrasts: [storage-persists]
- memory-word-granularity — MLOAD and MSTORE always move 32 bytes at a time (MSTORE8 is the single-byte exception), so "the byte at offset 5" means loading a word at offset 5 and masking. | requires: [memory-is-a-flat-byte-array, word-is-256-bits] | contrasts: []
- memory-expansion-quadratic — Expanding memory to `a` 32-byte words costs 3·a + floor(a²/512) gas total, charged as the delta from the previous high-water mark; the linear term dominates for small buffers and the quadratic term makes multi-megabyte buffers effectively unaffordable. | requires: [memory-is-a-flat-byte-array, gas-is-a-countdown] | contrasts: [flat-allocation-cost]
- memory-highwater-never-shrinks — You are charged for the highest byte offset ever touched in a frame; writing at offset 1,000,000 once and then working at offset 32 does not refund anything, and there is no free(). | requires: [memory-expansion-quadratic] | contrasts: [malloc-free]
- solidity-free-memory-pointer — Solidity's convention reserves 0x00-0x3f as scratch, 0x40 as the free-memory pointer, 0x60 as a permanently-zero slot, and starts allocations at 0x80; assembly that ignores this convention corrupts the allocator. | requires: [memory-is-a-flat-byte-array] | contrasts: []
- calldata-is-read-only — Calldata is the immutable input byte array of the current frame; it can be read (CALLDATALOAD/CALLDATACOPY) but never written, and reads past its end return zeros rather than reverting. | requires: [call-frame] | contrasts: [returndata-buffer, memory-is-a-flat-byte-array]
- calldata-priced-at-the-edge — Calldata's real cost is paid once when the transaction enters the block (per byte, at the transaction level), not per read; inside execution a CALLDATALOAD is as cheap as a memory load. | requires: [calldata-is-read-only, gas-is-a-countdown] | contrasts: [memory-expansion-quadratic]
- four-data-locations — Stack, memory, calldata and storage are genuinely different machines with different lifetimes and prices; returndata and code are two more read-only regions, making six places bytes can be. | requires: [memory-is-a-flat-byte-array, calldata-is-read-only, per-account-storage-trie] | contrasts: []
- storage-is-the-expensive-one — Storage is the only location that survives the transaction, and it is priced two to three orders of magnitude above memory precisely because every write mutates the global trie every node must keep. | requires: [per-account-storage-trie, four-data-locations] | contrasts: [memory-expansion-quadratic]
- packing-helps-storage-only — Packing several small values into one 32-byte slot saves real money in storage and saves nothing in memory or on the stack, where everything occupies a full word regardless. | requires: [storage-is-the-expensive-one, word-is-256-bits] | contrasts: [struct-packing-universal]
- transient-storage-middle-tier — TSTORE/TLOAD (EIP-1153) give a transaction-scoped, revert-aware key/value store at 100 gas, filling the gap between per-frame memory and permanent storage. | requires: [four-data-locations] | contrasts: [storage-is-the-expensive-one]
- copy-costs-are-per-word — Every bulk copy opcode (CALLDATACOPY, CODECOPY, RETURNDATACOPY, MCOPY, and the keccak256 hash) charges a small base plus 3 gas per 32-byte word plus any memory expansion, so "just hash the whole thing" scales with length. | requires: [memory-expansion-quadratic] | contrasts: []

### Primary sources
- [EIP-5656: MCOPY — memory copying instruction](https://eips.ethereum.org/EIPS/eip-5656) — tier: spec — published: 2022-09 — adds 0x5E in Cancun; before this, memory-to-memory copies were loops of MLOAD/MSTORE.
- [EIP-3855: PUSH0 instruction](https://eips.ethereum.org/EIPS/eip-3855) — tier: spec — published: 2021-02 — the 2-gas zero push; why Shanghai-era compiler output looks different, and why some L2s lagged.

- [EIP-7623: Increase calldata cost](https://eips.ethereum.org/EIPS/eip-7623) — tier: spec — published: 2024-02 — Final, live since Pectra; introduces the 10/40 floor for data-heavy transactions.
- [EIP-7976: Increase calldata floor cost](https://eips.ethereum.org/EIPS/eip-7976) — tier: spec — published: 2025 — draft/peer review; would raise the floor to 64 gas per calldata byte. NOT shipped.

- [LearnEVM — Working with Memory](https://learnevm.com/chapters/evm/memory) — tier: primary-analysis — published: 2024 — one of the few maintained deep treatments of the memory model aimed at practitioners.

### Current state (Aug 2026)
- **Stack-too-deep is solved only on an experimental backend.** Solidity 0.8.36 (9 July 2026) added stack-to-memory spilling to the SSA CFG code generator, but that backend is enabled with `--experimental --via-ssa-cfg`, is NOT the default for `--via-ir`, and `--via-ir` is itself still not the default pipeline. For ordinary projects on legacy codegen, stack-too-deep is still real and the classic workarounds (block scopes, structs, fewer live locals) still apply. See module 03.9 for the correction. Teach the 16-slot reach as the *reason* either way.
- **EOF is not coming**, so the promised EOF stack-validation and its removal of dynamic jumps are not the future of this topic. JUMPDEST analysis and dynamic jumps remain how the EVM works.
- **Calldata is no longer uniformly cheap.** EIP-7623 (Pectra, live) imposes a floor of 10 gas per zero byte and 40 per non-zero byte for transactions whose gas is dominated by calldata rather than execution. Ordinary application transactions still pay the old 4/16 because they are execution-heavy. Any lesson that says "calldata costs 16 gas per non-zero byte" is now conditionally wrong.
- EIP-7976 would raise that floor to a flat 64 gas per byte. It is in peer review and not scheduled to a named fork as far as I could confirm. Do not teach it as coming.
- MCOPY (0x5E) has been live since Cancun; hand-written memory-copy loops in assembly are now legacy. Solidity emits MCOPY when the target EVM version allows it.
- Transient storage is live and cheap (100 gas), making the transient reentrancy guard (~200 gas round trip) the modern default over the ~7,100-gas storage version.
- The Fusaka block gas limit rise to 60M with a ~16.78M per-transaction cap (EIP-7825) interacts with the quadratic memory formula: the per-transaction cap now sets a practical ceiling on how much memory one transaction can ever allocate.
- EIP-7686 (linear memory limits) exists as a proposal but has not shipped; quadratic expansion is still the live pricing.

### Misconceptions
- Belief: Using `uint8` instead of `uint256` saves gas. | Reality: On the stack and in memory it costs *more* (masking instructions); it only saves gas when several small values share one storage slot. | Why: Direct transfer of C-style "smaller type, less memory". | Source: https://docs.soliditylang.org/en/latest/internals/layout_in_storage.html
- Belief: Memory is free because it is not persisted. | Reality: It is charged 3 gas per word plus a quadratic term, and the high-water mark never resets within a frame. | Why: "RAM is free" intuition from ordinary programming. | Source: https://eips.ethereum.org/EIPS/eip-5656
- Belief: You can free memory when done with it. | Reality: There is no deallocation; Solidity's allocator only moves the free-memory pointer forward, so loops that allocate per iteration grow memory monotonically. | Why: Every mainstream runtime has GC or free(). | Source: https://docs.soliditylang.org/en/latest/internals/layout_in_memory.html
- Belief: Calldata costs 16 gas per non-zero byte. | Reality: Since Pectra, data-heavy transactions pay a 40-gas floor per non-zero byte under EIP-7623. | Why: EIP-2028's numbers are in every gas table written before 2025. | Source: https://eips.ethereum.org/EIPS/eip-7623
- Belief: Reading calldata inside a function costs gas per byte read. | Reality: The per-byte charge happens once, at transaction intrinsic-gas time; CALLDATALOAD itself is 3 gas like any cheap opcode. | Why: The two charges are usually taught together. | Source: https://eips.ethereum.org/EIPS/eip-2028
- Belief: Declaring parameters `memory` instead of `calldata` is a style choice. | Reality: `memory` forces a copy of the whole array, paying copy and expansion gas; `calldata` reads in place. For large arrays this is a large, easily measured difference. | Why: The keywords read as type annotations rather than as machine locations. | Source: https://docs.soliditylang.org/en/latest/internals/layout_in_memory.html
- Belief: Stack too deep means you exceeded 1024 stack items. | Reality: It means the compiler could not reach a value within DUP16/SWAP16's 16-slot window; 1024 is a completely different limit. | Why: Both are "stack limits". | Source: https://eips.ethereum.org/EIPS/eip-3855
- Belief: Reading past the end of calldata reverts. | Reality: It returns zeros — which is precisely why a call with a short payload can silently decode as zero arguments rather than failing. | Why: Symmetry with RETURNDATACOPY, which does revert. | Source: https://eips.ethereum.org/EIPS/eip-211
- Belief: Clearing storage refunds most of what you paid. | Reality: EIP-3529 cut the refund and capped total refunds at a fifth of gas used; gas-token schemes died with it. | Why: Pre-London gas guides. | Source: https://eips.ethereum.org/EIPS/eip-3529
- Belief: PUSH0 has always existed. | Reality: It arrived in Shanghai (EIP-3855); compiling with a newer EVM target and deploying to a chain that has not adopted it produces invalid bytecode. This is still a live L2 footgun. | Why: It looks like a primitive. | Source: https://eips.ethereum.org/EIPS/eip-3855

### Practice ideas
- kind: measure — Write a Foundry test that MSTOREs at increasing offsets (1 KiB, 64 KiB, 1 MiB) and records gas used. Plot it and fit the curve. — acceptance: the measured costs match 3·words + words²/512 within rounding, and the learner can state at roughly what size the quadratic term overtakes the linear one.
- kind: measure — Write the same function twice, once taking `bytes calldata` and once `bytes memory`, and compare gas for a 32-byte, 1 KiB and 32 KiB input. — acceptance: learner produces a three-row table and explains which term (copy cost vs expansion) dominates at each size.
- kind: implement — Write a Yul/assembly function that concatenates two byte arrays in memory using MCOPY, correctly reading and advancing the free-memory pointer at 0x40. — acceptance: passes a fuzz test against a plain-Solidity reference implementation for random lengths including 0 and non-multiples of 32.
- kind: break — Deliberately write to memory below 0x80 (say, MSTORE at 0x40) inside inline assembly, then allocate a new array afterwards, and observe the corruption. — acceptance: learner produces a failing test and can name which reserved region they clobbered.
- kind: measure — Benchmark a reentrancy guard three ways: storage-based, transient-storage-based, and none. — acceptance: numbers from the learner's own run, roughly matching the ~7,100 vs ~200 gas gap, with an explanation of why the storage version is so much worse.
- kind: implement — Compute, by hand and then verify on a fork, the storage slot for `mapping(address => mapping(uint256 => uint256))` at declaration slot 3, and read it with `eth_getStorageAt`. — acceptance: matches the value returned by the contract's own getter.
- kind: measure — Take a struct with five `uint32` fields, deploy it once as-declared and once padded so each field occupies its own slot, and compare deployment-plus-write gas. — acceptance: learner quantifies the packing saving and confirms it disappears when the same struct lives in memory.

## 03.7 — Logs & bloom filters: the write-only side channel

### Concepts
- logs-are-write-only — LOG0-LOG4 append records to the transaction's receipt; no opcode anywhere in the EVM can read a log, so logs are a one-way channel out of the chain to off-chain consumers. | requires: [evm-execution-loop, receipt-contents] | contrasts: [per-account-storage-trie]
- log-record-shape — Every log is (emitting address, 0-4 topics of exactly 32 bytes each, arbitrary-length data blob); the digit in LOG0..LOG4 is just how many topics you are supplying. | requires: [logs-are-write-only] | contrasts: []
- topic0-is-the-signature — For a normal Solidity event, topic0 is keccak256 of the canonical event signature (e.g. "Transfer(address,address,uint256)"), which is how indexers know which event they are looking at. | requires: [log-record-shape] | contrasts: [anonymous-event]
- anonymous-event — Declaring an event `anonymous` omits topic0, freeing that slot for a fourth indexed parameter — at the cost of no longer being identifiable by signature. | requires: [topic0-is-the-signature] | contrasts: [topic0-is-the-signature]
- indexed-means-searchable — `indexed` parameters become topics and are therefore filterable by exact value in eth_getLogs; non-indexed parameters are ABI-encoded into the data blob and can only be read after you have already found the log. | requires: [log-record-shape] | contrasts: []
- indexed-dynamic-is-hashed — An indexed string, bytes, array or struct is stored as keccak256 of its value, not the value itself, so you can filter for an exact known string but can never recover the original from the log. | requires: [indexed-means-searchable] | contrasts: [indexed-value-preserved]
- logs-are-cheap — A log costs a small base plus a per-topic charge plus a per-byte charge on the data — roughly two orders of magnitude less per byte than storage — because nodes never have to keep logs in the state trie or serve them to the EVM. | requires: [logs-are-write-only, storage-is-the-expensive-one] | contrasts: [storage-is-the-expensive-one]
- logs-still-committed — Logs are not free-floating metadata: they are inside receipts, receipts are hashed into the receiptsRoot, and the receiptsRoot is in the header — so a log is as provably-part-of-the-chain as a transaction is. | requires: [three-block-tries, log-record-shape] | contrasts: [logs-are-offchain]
- logs-revert-with-the-frame — Logs emitted in a frame that later reverts are discarded, so an event in a receipt is evidence that its code path actually completed. | requires: [three-failure-modes, logs-are-write-only] | contrasts: []
- bloom-filter-idea — A Bloom filter is a fixed-size bit array where each item sets a few bits; if any of an item's bits is unset the item is definitely absent, and if all are set it is probably present — false positives are possible, false negatives are not. | requires: [] | contrasts: [exact-index]
- ethereum-bloom-parameters — Ethereum's log bloom is 2048 bits (256 bytes) and sets up to 3 bits per item, taken as the low 11 bits of each of the first three byte-pairs of keccak256(item); the items entered are the emitting address and every topic. | requires: [bloom-filter-idea, log-record-shape] | contrasts: []
- block-bloom-is-a-union — Each receipt carries its own bloom, and the header's logsBloom is the bitwise OR of every receipt bloom in the block, so a node can reject an irrelevant block by reading 256 bytes of header instead of downloading its receipts. | requires: [ethereum-bloom-parameters, receipt-contents] | contrasts: []
- bloom-saturation — As blocks fill with more logs, more of the 2048 bits get set, the false-positive rate climbs, and the filter's usefulness degrades — a fixed-size filter against a growing workload. | requires: [block-bloom-is-a-union] | contrasts: []
- getlogs-topic-semantics — eth_getLogs matches topics positionally: position i must match one of the values given for position i, null is a wildcard, and the list is an AND across positions with an OR inside each position. | requires: [indexed-means-searchable] | contrasts: [full-text-search]
- events-are-an-api-contract — Because indexers, subgraphs, wallets and analytics all key off topic0, changing an event signature is a breaking API change with no compiler to catch it downstream. | requires: [topic0-is-the-signature] | contrasts: []

### Primary sources
- [Ethereum Yellow Paper](https://ethereum.github.io/yellowpaper/paper.pdf) — tier: spec — published: ongoing — Appendix defines M₃:₂₀₄₈, the exact three-bits-from-11-bit-slices bloom construction. The only normative source for it.
- [EIP-7668: Remove bloom filters](https://eips.ethereum.org/EIPS/eip-7668) — tier: spec — published: 2024-03 — Vitalik's proposal to force the header and receipt blooms empty; Draft, proposed for Glamsterdam.
- [EIP-7745: Trustless log and transaction index](https://eips.ethereum.org/EIPS/eip-7745) — tier: spec — published: 2024-07 — the proposed replacement: an adaptive two-dimensional filter-map structure hashed into a Merkle tree, so log queries can be *proved*, not just filtered. Draft, proposed for Glamsterdam.
- [EIP-7773: Hardfork Meta — Glamsterdam](https://eips.ethereum.org/EIPS/eip-7773) — tier: spec — published: 2024-09 — the authoritative list of what is proposed vs included for Glamsterdam; check this before claiming any EIP ships.
- [EIP-7919: Pureth Meta](https://eips.ethereum.org/EIPS/eip-7919) — tier: spec — published: 2025 — the umbrella effort to make RPC responses, including log queries, independently verifiable.
- [Ethereum Execution APIs — eth_getLogs](https://ethereum.github.io/execution-apis/) — tier: spec — published: 2026 — normative filter-object and topic-matching semantics.
- [Solidity docs — Events / Contract ABI: events](https://docs.soliditylang.org/en/latest/abi-spec.html#events) — tier: canonical-docs — published: 2026 — normative rule that indexed dynamic types are stored hashed, and the 3-vs-4 indexed-parameter limit.
- [Pureth guide — Bloom filters](https://pureth.guide/logs-bloom/) — tier: primary-analysis — published: 2025 — clearest current explanation of why the fixed 2048-bit filter is failing and what replaces it.
- [man bytes gnu — Making sense of Ethereum log bloom filters](https://manbytesgnu.org/eth-log-bloom.html) — tier: primary-analysis — published: 2022 — worked byte-level example; good source for building an implementation exercise.

### Current state (Aug 2026)
- **The 2048-bit bloom filter is on death row.** EIP-7668 (empty the blooms) and EIP-7745 (replace them with a provable, adaptive log index) are both Draft and both proposed for Glamsterdam. Glamsterdam has NOT shipped — final devnet was mid-June 2026, targeting H2 2026, no mainnet date — and the confirmed headline EIPs are EIP-7732 (ePBS) and EIP-7928 (block-level access lists). Treat 7668/7745 as proposed, not scheduled.
- The reason is bloom saturation: at current log volumes the fixed-size filter produces so many false positives that clients scan large numbers of irrelevant blocks anyway, so it costs header bytes without saving work.
- Practically, almost nobody consumes blooms directly any more. Applications use `eth_getLogs` against a provider, or an indexing layer. This is worth being blunt about: the bloom is a protocol artefact that most engineers will never touch, but it explains why log queries are shaped the way they are.
- **The indexing layer changed hard in 2026.** The Graph fully retired its free hosted service. Envio HyperIndex is the speed leader; Ponder's team joined Monad in Feb 2026; SQD/Subsquid was acquired and is mid-rebrand. Any lesson pointing at "deploy a subgraph to the hosted service" is dead.
- EIP-7919 (Pureth) is the broader push to make log queries verifiable rather than trusted — the honest framing for 2026 is that `eth_getLogs` results today are a trusted RPC read, and making them provable is active work, not shipped.
- Nothing about LOG0-LOG4 semantics or pricing changed in Pectra or Fusaka as far as I could establish.

### Misconceptions
- Belief: Contracts can read their own past events. | Reality: There is no log-reading opcode at all. If contract logic needs a value, it must be in storage; events are exclusively for off-chain consumers. | Why: In ordinary systems, an event log is just another queryable table. | Source: https://ethereum.github.io/yellowpaper/paper.pdf
- Belief: Events are off-chain and therefore untrustworthy. | Reality: Logs live in receipts, receipts hash into receiptsRoot, receiptsRoot is in the header — a log is Merkle-provable against the chain. | Why: "Off-chain consumers" gets compressed into "off-chain data". | Source: https://eips.ethereum.org/EIPS/eip-658
- Belief: `indexed` on a string lets you read the string from the log. | Reality: It stores keccak256 of the string; the value is unrecoverable. You can filter for a string you already know, and nothing else. | Why: "Indexed" implies "included". | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#events
- Belief: You can index as many event parameters as you like. | Reality: Three for a normal event, four for an anonymous one — a hard consequence of four topic slots and topic0 being the signature. | Why: The compiler error is rarely hit until late. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#events
- Belief: A bloom hit means the block contains your event. | Reality: Blooms have false positives by construction; a hit means "maybe", and the client must fetch and check receipts. | Why: Probabilistic data structures are unfamiliar. | Source: https://ethereum.github.io/yellowpaper/paper.pdf
- Belief: Emitting an event is basically free. | Reality: It is cheap relative to storage but not free — there is a per-topic charge and a per-byte data charge, so logging a large blob every call is a real cost. | Why: The contrast with SSTORE is so large it reads as zero. | Source: https://ethereum.github.io/yellowpaper/paper.pdf
- Belief: Events emitted before a revert still appear. | Reality: They are discarded with the rest of the frame's effects. | Why: In ordinary systems logging is a side effect outside the transaction. | Source: https://eips.ethereum.org/EIPS/eip-140
- Belief: `eth_getLogs` searches event *names*. | Reality: It matches raw 32-byte topic values positionally; the name→topic0 mapping is done client-side by your ABI. | Why: Libraries like viem and ethers hide the hashing. | Source: https://ethereum.github.io/execution-apis/
- Belief: Bloom filters are how modern apps find events. | Reality: Almost all real traffic goes through eth_getLogs on a provider or a dedicated indexer; blooms are a protocol-level pre-filter now considered failed and slated for replacement. | Why: They are prominent in the Yellow Paper and in every architecture diagram. | Source: https://eips.ethereum.org/EIPS/eip-7745

### Practice ideas
- kind: implement — Implement Ethereum's bloom construction in TypeScript or Rust: for an address and each topic, keccak256 it, take the low 11 bits of each of the first three byte-pairs, and set those bits in a 2048-bit array. OR the results together. — acceptance: reproduces the exact `logsBloom` field of a real mainnet receipt fetched over RPC, byte for byte.
- kind: measure — Construct a deliberate false positive: find (or brute-force) a topic value whose three bits are all already set in some real block's bloom, then show that the block contains no such log. — acceptance: learner exhibits a concrete address/topic that the bloom says "maybe" to and the receipts say no.
- kind: implement — Write a Foundry test that emits the same payload three ways: fully indexed, fully non-indexed, and as one SSTORE. Record gas for each. — acceptance: learner reports three numbers and can explain the per-topic versus per-byte versus per-slot pricing that produced them.
- kind: break — Emit an event with an `indexed string`, then try to reconstruct the string from `eth_getLogs` output. Then show that filtering for the exact known string does work. — acceptance: learner demonstrates both the failure and the working filter, and can state the rule in one sentence.
- kind: implement — Build a minimal ERC-20 Transfer indexer: poll `eth_getLogs` in block ranges for topic0 = keccak256("Transfer(address,address,uint256)") with topic1 pinned to one holder, and reconcile the resulting balance against `balanceOf`. — acceptance: the reconstructed balance matches the on-chain getter, and the learner handles the reorg / block-range-limit cases their provider imposes.
- kind: read — Take a real transaction receipt, decode one log by hand (topic0 → signature, topics 1-3 → indexed args, data → ABI-decoded remainder) without a library. — acceptance: matches what Etherscan shows.
- kind: write — Document an event-schema change (adding a field, changing a type) as a breaking-API RFC for downstream indexer consumers. — acceptance: correctly identifies that changing the signature changes topic0 and silently breaks every existing filter.

### Gaps & uncertainties
- **Log gas constants**: I did not verify the base cost, per-topic cost, or per-byte data cost this session. My recollection is 375 base, 375 per topic, 8 per data byte, plus memory expansion — treat all three as unverified and check the Yellow Paper or execution-specs before publishing.

## 03.9 — Yul & inline assembly: when to drop below the language

### Concepts
- yul-is-the-middle-layer — Yul is a small typed-by-convention intermediate language (one type, u256; `let`, `if`, `switch`, `for`, functions) that sits between Solidity and raw bytecode and is what inline `assembly` blocks are written in. | requires: [evm-execution-loop] | contrasts: [raw-bytecode]
- assembly-removes-the-safety-net — Inside an assembly block there are no overflow checks, no type checks, no bounds checks, no automatic revert bubbling and no ABI decoding — every guarantee Solidity 0.8 gives you is off. | requires: [yul-is-the-middle-layer] | contrasts: [solidity-checked-arithmetic]
- solidity-memory-model-is-a-contract — Solidity's memory conventions (0x00-0x3f scratch, 0x40 free-memory pointer, 0x60 permanently zero, allocations from 0x80 upward) are an implicit contract that the compiler's own generated code relies on; assembly that breaks it corrupts unrelated code. | requires: [solidity-free-memory-pointer, assembly-removes-the-safety-net] | contrasts: []
- memory-safe-annotation — `assembly ("memory-safe") { ... }` is a promise to the optimizer, not a check: it asserts your block only touches memory you allocated, memory Solidity allocated and you legitimately reference, the 0x00-0x3f scratch space, or scratch beyond the free-memory pointer that you do not leave depended-upon. | requires: [solidity-memory-model-is-a-contract] | contrasts: [compiler-verified-safety]
- unannotated-assembly-disables-optimizations — Any assembly block that touches memory or assigns to a memory variable *globally* disables stack-to-memory movement and other memory optimizations, so one unannotated block degrades the whole compilation unit. | requires: [memory-safe-annotation] | contrasts: []
- annotation-is-unverified — If you annotate a block memory-safe and the claim is false, the result is undefined behaviour that typically does not show up in tests, because the optimizer's choices depend on unrelated code changes. | requires: [memory-safe-annotation] | contrasts: [type-system-guarantee]
- assembly-storage-access — Solidity storage variables are not directly addressable in assembly; you reach them through `x.slot` and `x.offset`, and calldata arrays through `x.offset` and `x.length` — a common early confusion. | requires: [assembly-removes-the-safety-net, per-account-storage-trie] | contrasts: []
- dirty-upper-bits — Values narrower than 32 bytes may carry non-zero garbage in their unused high bits; Solidity cleans them at defined points, assembly does not, so comparisons and hashes on an unmasked `address` can silently differ. | requires: [word-is-256-bits, assembly-removes-the-safety-net] | contrasts: []
- signed-vs-unsigned-opcodes — Yul exposes separate signed and unsigned instructions (div/sdiv, mod/smod, lt/slt, gt/sgt, shr/sar); choosing the wrong one is a silent correctness bug, not a compile error. | requires: [assembly-removes-the-safety-net] | contrasts: [solidity-typed-operators]
- raw-call-no-existence-check — In assembly, a `call` to an address with no code returns success; Solidity's high-level calls insert an EXTCODESIZE check, and dropping to assembly drops that check. | requires: [call-returns-a-boolean, assembly-removes-the-safety-net] | contrasts: []
- when-assembly-is-justified — The defensible cases are narrow: custom storage slots (ERC-1967, ERC-7201), proxy fallbacks that must forward arbitrary calldata and return arbitrary returndata, hot loops in widely reused libraries, and expressing things Solidity cannot express — not shaving gas off ordinary application logic. | requires: [assembly-removes-the-safety-net] | contrasts: [assembly-for-gas-golf]
- assembly-cost-is-review-cost — Assembly's real price is paid in audit hours and in the reviewers who can no longer read the contract; measured against 2025's loss data, where access control dominates, micro-optimising with assembly is usually optimising the wrong risk. | requires: [when-assembly-is-justified] | contrasts: []
- via-ir-pipeline — `--via-ir` compiles Solidity to Yul, optimises the Yul, then emits bytecode; it usually produces better runtime gas, compiles much slower, and can change observable details, which is why it is opt-in rather than default. | requires: [yul-is-the-middle-layer] | contrasts: [legacy-codegen]
- verbatim-escape-hatch — Yul's `verbatim` lets you inject literal bytecode the compiler will not touch, the last resort below assembly; it is opaque to every analysis tool. | requires: [yul-is-the-middle-layer] | contrasts: []

### Current state (Aug 2026)
- **Correction to the shared baseline.** Solidity 0.8.36's stack-to-memory spilling lives on the **experimental SSA CFG code generator**, enabled with `--experimental --via-ssa-cfg`. It is **not** the default for `--via-ir`, and `--via-ir` is itself **still not the default pipeline** — legacy codegen remains the default as of 0.8.36 (July 2026). So "stack-too-deep is solved" is true only on an experimental backend that most projects are not using. Stabilising the SSA CFG codegen is stated as the maintainers' main priority for the following six months.
- **Solidity's repository moved to `argotorg/solidity`** and the Argot Collective now publishes the roadmap. Issue links and contribution instructions in older material point at the wrong org.
- The experimental **EOF backend was removed in 0.8.36** after EOF was rejected for Fusaka. Any assembly or Yul material referencing EOF instructions is dead.
- 0.8.34 patched a **high-severity transient-storage clearing bug**. If a lesson uses `transient` state variables or TSTORE from assembly, pin ≥ 0.8.34.
- Current stable release line at the time of writing is 0.8.36 (9 July 2026), with 0.8.37 in development.
- Foundry's exact current stable version is unresolved: v1.5.1 is referenced as stable supporting solc 0.8.31, with nightly 1.8.0-nightly dated 2026-08-04. - The economic argument against assembly has strengthened: 2025 saw 122 incidents and $905.4M lost, with access control the dominant category. Gas micro-optimisation via assembly addresses none of the categories that actually lose money.

### Misconceptions
- Belief: `("memory-safe")` makes the compiler check your assembly. | Reality: It is an unchecked assertion; violating it produces undefined behaviour that can appear only after unrelated code changes shift the optimizer's decisions. | Why: The syntax looks like a safety modifier. | Source: https://docs.soliditylang.org/en/latest/assembly.html
- Belief: Omitting the annotation is the safe default. | Reality: Omitting it is safe for correctness but disables stack-to-memory movement and memory optimizations across the *entire* compilation unit, so one lazy block taxes everything. | Why: "Not asserting anything" feels conservative. | Source: https://docs.soliditylang.org/en/latest/assembly.html
- Belief: All inline assembly needs the annotation. | Reality: A block that neither touches memory nor assigns to memory variables is automatically memory-safe and needs no annotation. | Why: The rule is stated once and easy to miss. | Source: https://docs.soliditylang.org/en/latest/assembly.html
- Belief: Assembly is always faster than Solidity. | Reality: With the optimizer on — especially via-IR — hand-written assembly frequently matches or loses to generated code, and the gap has narrowed every release. Measure before claiming a win. | Why: Folk knowledge from 2018-2020, when codegen was much worse. | Source: https://www.soliditylang.org/blog/2024/07/12/a-closer-look-at-via-ir/
- Belief: via-IR is the default now. | Reality: As of 0.8.36 legacy codegen is still the default; via-IR is opt-in. | Why: It has been "about to become default" since the 2023 Solidity Summit. | Source: https://www.soliditylang.org/blog/2026/07/09/solidity-0.8.36-release-announcement/
- Belief: Stack-too-deep is fixed in 0.8.36. | Reality: Fixed only on the experimental SSA CFG backend, behind `--experimental --via-ssa-cfg`. | Why: Release-note headlines compress the qualifier away. | Source: https://www.soliditylang.org/blog/2026/07/09/solidity-0.8.36-release-announcement/
- Belief: via-IR only changes gas, not behaviour. | Reality: The compiler maintains a dedicated "IR-based Codegen Changes" page precisely because observable behaviour can differ. Re-run the full test suite when switching. | Why: "Optimizer" implies semantics-preserving. | Source: https://docs.soliditylang.org/en/latest/ir-breaking-changes.html
- Belief: You can read a storage variable in assembly by naming it. | Reality: You need `x.slot` (and `x.offset` for packed variables); naming it directly is a compile error or means something else. | Why: Assembly looks like it shares the enclosing scope. | Source: https://docs.soliditylang.org/en/latest/assembly.html
- Belief: `call` in assembly behaves like a Solidity external call. | Reality: It performs no code-existence check, does not decode returndata, and does not bubble reverts — you must do all three yourself. | Why: The name is the same. | Source: https://docs.soliditylang.org/en/latest/assembly.html
- Belief: Arithmetic in assembly is checked because the file says `pragma solidity ^0.8`. | Reality: 0.8's overflow checks are inserted by codegen and do not exist inside assembly; `add` wraps silently. | Why: The pragma feels global. | Source: https://docs.soliditylang.org/en/latest/assembly.html

### Practice ideas
- kind: implement — Write a minimal ERC-1967-style proxy fallback in assembly: copy all calldata to memory, `delegatecall`, `returndatacopy`, then `return` or `revert` on the result. - kind: measure — Take a small library function (e.g. a Merkle proof verifier), write it in plain Solidity and in assembly, and benchmark both under legacy codegen, `--via-ir`, and `--via-ir` with high optimizer runs. — acceptance: a 6-cell gas table produced by the learner, plus a written conclusion about whether the assembly version was worth it.
- kind: fix — Take an assembly snippet that compares an `address` without masking the high bits and demonstrate a case where a dirty value makes the comparison fail. Fix it with the correct mask. — acceptance: a failing test before and passing after, with the mask value derived rather than copied.
- kind: implement — Implement ERC-7201 namespaced storage for a small upgradeable contract: derive the namespace slot, access it with `.slot` in assembly, and prove no collision with a second namespace. — acceptance: two independent namespaces coexist in one contract and a test proves writes to one do not disturb the other.
- kind: read — Read one Solady library file end to end and annotate every assembly block with which memory region it touches and why the memory-safe claim holds (or does not appear). — acceptance: learner correctly classifies each block against the four permitted regions.
