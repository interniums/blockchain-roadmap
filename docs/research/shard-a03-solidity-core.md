## 04.1 — Language core: types, data locations, visibility, inheritance, modifiers

### Concepts
- sol-value-type — Value types (uint/int, bool, address, address payable, bytesN, enum, contract, user-defined value types, function types) are always copied on assignment and carry no data-location annotation because they live on the stack. | requires: [] | contrasts: [sol-reference-type]
- sol-reference-type — Reference types (structs, arrays incl. bytes/string, mappings) are accessed through a name that points at data elsewhere, so two names can alias the same data. | requires: [sol-value-type] | contrasts: [sol-value-type]
- sol-data-location — Every reference-type variable must be annotated `storage`, `memory` or `calldata`; there is no default since 0.5.0, and `transient` is NOT yet a valid data location for reference types. | requires: [sol-reference-type] | contrasts: [evm-storage-slot, evm-memory-model]
- sol-assignment-copy-rules — storage<->memory and calldata->anything always deep-copy; memory->memory and storage->local-storage-variable only alias; every other assignment *to* storage copies. | requires: [sol-data-location] | contrasts: [sol-value-type]
- sol-calldata-immutable — `calldata` is the non-modifiable, non-persistent region holding the raw arguments of the current external call; using it avoids the copy that `memory` forces, and calldata structs/arrays can be returned but never allocated. | requires: [sol-data-location] | contrasts: [sol-memory-scratch]
- sol-storage-pointer-hazard — A local `T storage p` is a slot pointer, not data: reassigning `p` retargets the pointer while `p.field = x` writes through it into contract state. | requires: [sol-assignment-copy-rules] | contrasts: [sol-calldata-immutable]
- sol-state-var-visibility — State variables are `public` (compiler auto-generates a getter, no setter), `internal` (default, self + derived), or `private` (self only); `external` is not allowed on state variables. | requires: [] | contrasts: [sol-function-visibility]
- sol-function-visibility — Functions are `external` (message-call only, `f()` fails, `this.f()` works), `public` (both), `internal` (self + derived, can take mappings/storage refs as params), `private` (self only, invisible to derived). | requires: [sol-state-var-visibility] | contrasts: [sol-state-var-visibility]
- sol-visibility-not-privacy — `private`/`internal` restrict which *contracts* can read or write, never which *humans* can read; all contract state is world-readable off-chain. | requires: [sol-state-var-visibility] | contrasts: [sol-function-visibility]
- sol-view-pure — `view` promises no state modification (enforced at runtime by STATICCALL since Byzantium); `pure` additionally promises no state reads, so it may not touch storage, balances, or most block/tx/msg members (msg.sig and msg.data excepted). | requires: [sol-function-visibility] | contrasts: [sol-payable]
- sol-payable — A function must be marked `payable` to accept Ether; unmarked functions reject value-bearing calls, and `payable` is incompatible with `view`/`pure`. | requires: [sol-view-pure] | contrasts: [sol-view-pure]
- sol-library-view-not-enforced — Library `view` functions are invoked with DELEGATECALL, not STATICCALL, so their "no state change" promise is compile-time only with no EVM-level runtime guard. | requires: [sol-view-pure] | contrasts: [sol-delegatecall-context]
- sol-modifier-placeholder — A modifier's body wraps the function; `_;` marks where the function body is spliced in, so code before `_;` is a precondition, code after is a postcondition, and omitting `_;` on a path silently skips the function and returns default values. | requires: [sol-function-visibility] | contrasts: [sol-custom-error]
- sol-modifier-order — Multiple modifiers execute left-to-right as written in the declaration, nesting each inside the previous; the function body only runs when every modifier reaches its `_;`. | requires: [sol-modifier-placeholder] | contrasts: [sol-c3-linearisation]
- sol-c3-linearisation — Solidity resolves multiple inheritance with C3 linearisation; direct bases are listed "most base-like to most derived" (the reverse of Python), and lookup searches bases right-to-left depth-first, skipping already-searched bases. | requires: [sol-function-visibility] | contrasts: [sol-modifier-order]
- sol-constructor-order — Base constructors always run in linearised order, regardless of the order their arguments are supplied in the derived constructor's inheritance list. | requires: [sol-c3-linearisation] | contrasts: [sol-modifier-order]
- sol-override-virtual — A function inherited from multiple bases without a unique override MUST be explicitly overridden with `override(A, B)`; overridable functions must be `virtual`, and interface functions are implicitly virtual. | requires: [sol-c3-linearisation] | contrasts: [sol-interface-vs-abstract]
- sol-interface-vs-abstract — An `interface` may contain no implementations, no state variables, no constructor, no modifiers, and all functions must be `external`; an `abstract contract` may have state, constructors, modifiers and partial implementations but cannot be deployed directly. | requires: [sol-override-virtual] | contrasts: [sol-override-virtual]

### Current state (Aug 2026)
- Current stable is **0.8.36 (9 July 2026)**. 0.8.37 is unreleased at the time of writing; its dev branch removes `pragma experimental ABIEncoderV2` and adds `block.slotnum` / Yul `slotnum()` (EIP-7843) for the "Amsterdam" EVM version.
- **Default EVM version is `osaka`** since 0.8.31 (3 Dec 2025) — i.e. Fusaka-era targets by default. 0.8.36 added `amsterdam` as a selectable EVM version.
- **Deprecation wave in 0.8.31** that most existing tutorials predate: `send` and `transfer` on `address` now emit deprecation warnings; **`virtual` modifiers are deprecated**; ABI coder v1 is deprecated; comparisons between contract-typed variables are deprecated; the `memory-safe-assembly` special comment is deprecated in favour of the `assembly ("memory-safe")` dialect string.
- 0.8.35 warns about identifiers reserved for future keyword promotion: `at`, `error`, `layout`, `leave`, `super`, `transient`, `this` (Solidity) and `basefee`, `blobbasefee`, `blobhash`, `clz`, `leave`, `memoryguard`, `mcopy`, `prevrandao`, `tload`, `tstore` (Yul). Existing code using these as variable names will start warning.
- **Stack-too-deep**: 0.8.36's SSA CFG codegen can spill stack values to memory, which effectively removes the classic "stack too deep" wall — but it is **experimental** and gated behind the `--experimental` CLI flag / `settings.experimental` in Standard JSON (both introduced in 0.8.35). Do not teach it as the default behaviour of `solc 0.8.36`.
- **0.8.36 fixed a real inheritance bug**: `linearizedBaseContracts` was being unintentionally reversed when emitting a storage-layout warning, which "would affect analysis and code generation dependent on the inheritance order." Relevant for anyone on 0.8.31–0.8.35 using custom storage layout.
- Custom storage layout (`layout at <expr>`) is now a language feature and, with the `erc7201` builtin (0.8.35), is the sanctioned way to place a contract's storage at a namespaced base slot.
- EOF is gone from the toolchain: the experimental EOF backend was removed in 0.8.36, consistent with EOF being rejected for Fusaka.

### Misconceptions
- Belief: `memory` vs `storage` is a performance hint. | Reality: It changes assignment semantics — `storage` assignment aliases, `memory` copies — so it changes program meaning, not just gas. | Why: Learners map it onto stack/heap intuition from C. | Source: https://docs.soliditylang.org/en/latest/types.html#data-location-and-assignment-behavior
- Belief: `private` means the data is hidden. | Reality: All contract storage is publicly readable off-chain via `eth_getStorageAt`; visibility only constrains other contracts' code. | Why: The keyword is borrowed from languages where private is an encapsulation boundary, not a security boundary. | Source: https://docs.soliditylang.org/en/latest/contracts.html#state-variable-visibility
- Belief: `view` functions cannot change state, full stop. | Reality: Library `view` functions are reached by DELEGATECALL, not STATICCALL, so the EVM does not enforce it at runtime — only the compiler's static check does. | Why: Docs mention this only in a Note. | Source: https://docs.soliditylang.org/en/latest/contracts.html#view-functions
- Belief: `pure` means "reads nothing external". | Reality: `pure` may still read `msg.sig` and `msg.data`; and reading an `immutable` variable can be a non-pure operation. | Why: The mathematical sense of "pure" over-generalises. | Source: https://docs.soliditylang.org/en/latest/contracts.html#pure-functions
- Belief: `external` is always cheaper than `public`, so mark everything external. | Reality: Since 0.6.9 both `memory` and `calldata` are allowed on parameters at any visibility, so a `public` function with `calldata` parameters gets the same argument-handling; the old gas gap was about forced memory copies. | Why: Pre-0.6.9 advice was never retired. | Source: https://docs.soliditylang.org/en/latest/types.html#data-location
- Belief: You list base contracts in `is A, B` in any order. | Reality: Order is semantic — most base-like first, most derived last, the reverse of Python — and a wrong order produces "Linearization of inheritance graph impossible". | Why: Most languages treat the base list as unordered. | Source: https://docs.soliditylang.org/en/latest/contracts.html#multiple-inheritance-and-linearization
- Belief: Base constructors run in the order you pass their arguments. | Reality: They always run in linearised order regardless of argument order. | Why: The argument list looks like a call sequence. | Source: https://docs.soliditylang.org/en/latest/contracts.html#multiple-inheritance-and-linearization
- Belief: An interface is just an abstract contract with no bodies. | Reality: Interfaces additionally cannot declare state variables, constructors or modifiers, cannot inherit from contracts (only other interfaces), and every function must be `external`. | Why: The Java/TypeScript analogy is close but not exact. | Source: https://docs.soliditylang.org/en/latest/contracts.html#interfaces
- Belief: `virtual` modifiers are the way to make modifiers overridable. | Reality: Virtual modifiers are deprecated as of 0.8.31 and warn; prefer composing internal functions. | Why: The docs page still documents "Modifier Overriding". | Source: https://github.com/ethereum/solidity/blob/develop/Changelog.md
- Belief: A modifier that fails just reverts. | Reality: A modifier that reaches its end without hitting `_;` (e.g. `if (cond) { _; }`) silently skips the function body and returns zero-values — no revert. | Why: The docs' own `costs(uint price)` example does exactly this. | Source: https://docs.soliditylang.org/en/latest/contracts.html#function-modifiers
- Belief: `transient` is a data location you can put on a struct or array. | Reality: EIP-1153 transient storage is available for value-typed state variables only; `transient` is explicitly not yet supported as a data location for reference types. | Why: TSTORE/TLOAD are taught as "storage but cheap". | Source: https://docs.soliditylang.org/en/latest/types.html#data-location

### Practice ideas
- kind: break — Write a contract with `uint[] x;` and a function that takes `uint[] memory a`, does `uint[] storage y = x; y = a;` (should not compile) then `x = a;` and observe the deep copy. Measure gas of the copy for 1, 10, 100 elements with `forge test --gas-report`. | acceptance: learner can state, before running, which of the four assignment rules each line hits, and the gas curve is linear in element count.
- kind: measure — Same external function implemented three ways: `(uint[] memory)`, `(uint[] calldata)`, and `(uint[] calldata)` that only reads `a[0]`. Compare gas across input sizes. | acceptance: learner produces a table showing memory-parameter cost growing with input length while the calldata read-only version is roughly flat.
- kind: implement — Build a 4-contract diamond (`X`, `A is X`, `B is X`, `C is A, B`) where each contract's constructor emits an event and each overrides `foo()` calling `super.foo()`. Predict the emitted order and the `foo()` resolution before running. | acceptance: predicted order matches the actual event log; learner can then explain why `contract C is B, A` changes the answer and why `contract C is A, X` fails to compile.
- kind: fix — Give a contract whose `onlyWhitelisted` modifier wraps `_;` in an `if` instead of a `require`, plus a test that a non-whitelisted caller "succeeds". Fix so the call reverts. | acceptance: the test asserting silent success now fails, and a `vm.expectRevert` test passes.
- kind: read — Read OpenZeppelin's `Ownable`/`AccessControl` and identify (a) every use of `virtual`, (b) where storage is namespaced with ERC-7201, (c) why upgradeable variants use an internal `__X_init` instead of a constructor. | acceptance: learner can explain why constructors don't work behind a proxy without being told.
- kind: write — Given a public state variable `mapping(address => uint256) public balances;`, write out by hand the exact signature of the auto-generated getter and confirm it with `forge inspect <C> abi`. | acceptance: hand-written signature matches the ABI output exactly, including for a nested mapping and for an array (index parameter).

### Gaps & uncertainties
- I did not verify against a running compiler whether the 0.8.36 SSA-CFG memory spilling is *only* reachable via `--experimental`; the Changelog places SSA CFG codegen under the experimental-mode restriction introduced in 0.8.35, and 0.8.36 describes it as "the experimental SSA CFG codegen". Treat "0.8.36 solves stack-too-deep by default" as **not confirmed** — the baseline's phrasing overstates it.

## 04.3 — ABI & selectors: derivation, collisions, dispatch, decoding, calldata layout

### Concepts
- abi-function-selector — The first four bytes of calldata are the function selector: the high-order 4 bytes of `keccak256` of the canonical signature. | requires: [sol-function-visibility] | contrasts: [abi-head-tail]
- abi-canonical-signature — The canonical signature is `name(type1,type2,...)` with no spaces, no parameter names, no data-location keywords, and no return types; `uint`->`uint256`, enum->`uint8`, contract->`address`, struct->tuple `(...)`, user-defined value type->its underlying type. | requires: [abi-function-selector] | contrasts: [abi-function-selector]
- abi-return-type-not-in-selector — Return types are deliberately excluded so call resolution is context-independent; two functions differing only in return type therefore cannot be overloaded. | requires: [abi-canonical-signature] | contrasts: [abi-canonical-signature]
- abi-selector-space — Selectors live in a 2^32 space, so by the birthday bound a random corpus of roughly 2^16 signatures already contains a collision, and any target selector can be brute-forced by mining function names. | requires: [abi-function-selector] | contrasts: [abi-selector-collision-risk]
- abi-selector-collision-risk — A selector collision is only dangerous where two *different* dispatch surfaces overlap — classically a proxy's own admin function colliding with an implementation function — not inside a single contract, where the compiler rejects duplicate selectors. | requires: [abi-selector-space] | contrasts: [abi-dispatch]
- abi-dispatch — solc's legacy codegen builds the dispatcher as a binary search over selectors sorted as integers: it emits `DUP1, PUSH4 pivot, GT, JUMPI` splits recursively, falling back to a linear `EQ`/`JUMPI` chain for four or fewer selectors and whenever `--optimize-runs` is too low to justify the extra deploy bytes. | requires: [abi-function-selector] | contrasts: [abi-fallback-receive]
- abi-dispatch-gas-not-uniform — Because dispatch is a search, the gas to reach a function depends on where its selector sorts, so two identical functions in the same contract do not cost the same to call. | requires: [abi-dispatch] | contrasts: [abi-dispatch]
- abi-fallback-receive — If no selector matches, execution falls to `fallback()`; a call with empty calldata and value goes to `receive()` if defined, else `fallback() payable`, else it reverts. | requires: [abi-dispatch] | contrasts: [abi-dispatch]
- abi-static-vs-dynamic — A type is dynamic if it is `bytes`, `string`, `T[]`, `T[k]` with dynamic `T`, or a tuple with any dynamic member; everything else is static and encodes in place. | requires: [abi-function-selector] | contrasts: [abi-head-tail]
- abi-head-tail — Encoding is `head(X1)..head(Xk) tail(X1)..tail(Xk)`: static arguments put their value directly in the head, dynamic arguments put a 32-byte byte-offset in the head and their content in the tail. | requires: [abi-static-vs-dynamic] | contrasts: [abi-static-vs-dynamic]
- abi-offsets-relative — Offsets are counted in bytes from the start of the enclosing encoding block — for top-level arguments that is the byte after the 4-byte selector, and for nested dynamic types it is the start of the nested block, not the start of calldata. | requires: [abi-head-tail] | contrasts: [abi-head-tail]
- abi-dynamic-array-layout — A dynamic array's tail is `[length][element0][element1]...`; `bytes`/`string` tails are `[length][raw bytes right-padded to a 32-byte multiple]`. | requires: [abi-head-tail] | contrasts: [abi-packed-encoding]
- abi-decode-validates — `abi.decode` re-runs the encoding rules in reverse and reverts on malformed input (out-of-range offsets, lengths past the end of data, dirty high bits, `bool` outside {0,1}), which is why raw `returndata` should be decoded rather than read with assembly. | requires: [abi-head-tail] | contrasts: [abi-strict-mode-not-enforced]
- abi-strict-mode-not-enforced — Strict encoding requires offsets to be minimal and gap-free; Solidity's *encoder* always emits strict encoding but its *decoder* does not enforce it, so more than one byte string can decode to the same values. | requires: [abi-decode-validates] | contrasts: [abi-decode-validates]
- abi-packed-encoding — `abi.encodePacked` concatenates without padding and drops array lengths, so two different argument tuples can produce identical bytes; it must never feed a hash used as an identity or signature digest when more than one dynamic argument is present. | requires: [abi-dynamic-array-layout] | contrasts: [abi-head-tail]
- abi-msg-data-msg-sig — `msg.data` is the full calldata byte array and `msg.sig` is its first four bytes; both are readable from `pure` functions and are what generic forwarders/multicall routers inspect. | requires: [abi-function-selector] | contrasts: [sol-calldata-immutable]

### Current state (Aug 2026)
- **The canonical Solidity repository is now `github.com/argotorg/solidity`** — requests to `ethereum/solidity` resolve to `argotorg/solidity` via the GitHub API. Links in older curricula still work but the org name in file paths and issue references has changed. Worth a one-line note so learners are not confused.
- `pragma experimental ABIEncoderV2` support is removed on the 0.8.37 development branch; `pragma abicoder v2` is the only spelling. ABI coder v1 has warned as deprecated since 0.8.31.
- ABI coder v2 has been the default since 0.8.0, so the "you must opt in to encode structs" caveat in older material is dead.
- Error selectors `0x00000000` and `0xffffffff` are reserved by the spec for future use.
- Nothing in the ABI encoding rules themselves has changed in the last 18 months; the churn is all in tooling. `cast sig`, `cast 4byte`, `cast calldata` and `cast --calldata-decode` remain the fastest way to work selectors by hand; viem's `toFunctionSelector` / `decodeFunctionData` are the TS equivalents.
- Calldata cost, not encoding, is what changed: L2s charge for calldata bytes, so calldata layout (and packed alternatives) has real economic weight that pre-2023 material treats as negligible.

### Misconceptions
- Belief: The selector is a hash of the function *name*. | Reality: It hashes the full canonical signature including parameter types, which is what makes overloading work. | Why: `cast sig "transfer"` looks like it should work. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#function-selector
- Belief: `uint` and `uint256` produce different selectors. | Reality: `uint` is an alias; the canonical signature always uses `uint256`, and hashing `"f(uint)"` gives the wrong selector. | Why: The alias is legal Solidity, so people paste it into hashing tools. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#function-selector
- Belief: Two functions with the same selector cannot exist. | Reality: The compiler rejects them within one contract, but a proxy and its implementation are separate compilations, so nothing prevents the clash — and selectors can be deliberately mined to collide. | Why: The compiler error creates false confidence. | Source: https://medium.com/nomic-foundation-blog/malicious-backdoors-in-ethereum-proxies-62629adf3357
- Belief: Function dispatch is a jump table, so all functions cost the same to reach. | Reality: solc's legacy dispatcher is a binary search over sorted selectors (linear chain for <=4 functions), so per-call dispatch gas depends on selector value and function count. | Why: "switch statement" implies O(1). | Source: https://github.com/argotorg/solidity/blob/develop/libsolidity/codegen/ContractCompiler.cpp
- Belief: Offsets in calldata are absolute positions in `msg.data`. | Reality: They are relative to the start of the enclosing block — the byte after the selector for top-level args, and the start of the nested array/tuple for nested dynamic types. | Why: The top-level case makes the two look the same until you nest. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#formal-specification-of-the-encoding
- Belief: `uint256[3]` is encoded like `uint256[]`. | Reality: A fixed-size array of a static type is itself static and is inlined in the head with no offset and no length word. | Why: Both "look like arrays". | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#formal-specification-of-the-encoding
- Belief: If `abi.decode` succeeds the bytes were canonically encoded. | Reality: Solidity's decoder does not enforce strict mode, so non-minimal offsets and gaps can decode successfully; only the encoder is strict. | Why: The spec defines a single encoding, so people assume it is the only accepted one. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#strict-encoding-mode
- Belief: `abi.encodePacked` is just a cheaper `abi.encode`. | Reality: It drops padding and array lengths, so `("a","bc")` and `("ab","c")` hash identically — a real signature/commitment forgery class. | Why: The names suggest a pure size optimisation. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#non-standard-packed-mode
- Belief: A call with unknown calldata reverts. | Reality: It hits `fallback()` if one exists, which is exactly how proxies and generic routers work. | Why: Typed-language intuition about missing methods. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html
- Belief: An interface id is the hash of the interface. | Reality: ERC-165 interface ids are the XOR of all the interface's function selectors, so they inherit the same 4-byte collision properties. | Why: "id" suggests a digest. | Source: https://eips.ethereum.org/EIPS/eip-165

### Practice ideas
- kind: implement — Write a pure-TypeScript (or Rust) encoder for `f(uint256,uint32[],bytes10,bytes)` from the spec alone, then diff its output byte-for-byte against `cast calldata "f(uint256,uint32[],bytes10,bytes)" 0x123 "[0x456,0x789]" 0x31323334353637383930 0x48656c6c6f2c20776f726c6421`. | acceptance: byte-identical output, and the learner can point at each 32-byte word and say head/tail/offset/length.
- kind: implement — Implement `selectorOf(sig)` = `keccak256(sig)[0:4]` yourself and reproduce three known selectors: `transfer(address,uint256)` = 0xa9059cbb, `withdraw(uint256)` = 0x2e1a7d4d, `InsufficientBalance(uint256,uint256)` = 0xcf479181. | acceptance: all three match; then show that `"transfer(address,uint)"` and `"transfer (address,uint256)"` both give the wrong answer.
- kind: break — Brute-force a function name (e.g. `attack_<n>()`) whose selector equals a chosen 4 bytes, then deploy a minimal proxy whose `upgradeTo(address)` selector is shadowed by that implementation function. Show an admin call reaching the wrong code. | acceptance: a Foundry test where calling the implementation function through the proxy as admin changes the implementation slot.
- kind: measure — Deploy contracts with 4, 5, 16 and 64 identical-body external functions at `--optimize-runs 1` and `--optimize-runs 10000`. Record dispatch gas for the lowest-, median- and highest-sorted selector. | acceptance: the learner reproduces the linear-vs-binary split and can predict the crossover from `_runs * 6 * (n - 4) > 17 * 200`.
- kind: break — Write `keccak256(abi.encodePacked(a, b))` over two `string` arguments and produce two distinct `(a,b)` pairs with the same hash; then fix it with `abi.encode` and show the collision disappears. | acceptance: a passing test asserting equal hashes before the fix and unequal after.
- kind: fix — Given a contract that reads a returned `uint256` with `assembly { r := mload(add(data, 32)) }` and a mock returning 8 bytes, replace with `abi.decode(data, (uint256))` and show the mock now reverts instead of returning garbage. | acceptance: the truncated-return test reverts after the fix.
- kind: read — Take a real mainnet transaction's `input` via a public RPC `eth_getTransactionByHash`, look the selector up in a 4-byte database, and hand-decode the arguments before checking against `cast --calldata-decode`. | acceptance: hand decode matches the tool for at least one transaction containing a nested dynamic type.

### Visual opportunities

### Gaps & uncertainties
- I verified the **legacy** codegen dispatcher (`ContractCompiler::appendInternalSelector`) directly from source: binary split with pivot `GT`, never split for <=4 ids, split condition `_runs * 6 * (_ids.size() - 4) > 17 * GasCosts::createDataGas`. I did **not** verify how the **via-IR** pipeline lowers its Yul `switch selector`; `IRGenerator::dispatchRoutine` only emits the switch. Do not claim the two pipelines produce the same dispatcher shape without measuring.
- `createDataGas` is **confirmed 200** (`libevmasm/GasMeter.h`, `GAS_CODE_DEPOSIT`), so the "always split" branch triggers at `--optimize-runs > 566` (integer division of 3400/6). Verified from source, not measured on a real compile.
- The birthday-bound figure (~2^16 signatures for a likely collision) is a standard derivation, not a measured statistic about deployed contracts. I found no authoritative count of real-world selector collisions on mainnet.
- The Philogy dispatcher article is from 2022 and describes Solidity's dispatcher as linear if-else; the current source shows binary search. Sources conflict; I trust the source tree over the blog post and have flagged this rather than reconciling it.
- I did not confirm which selectors, if any, solc actively refuses to emit besides duplicates within one contract — in particular whether it guards against emitting the spec-reserved `0x00000000` / `0xffffffff`.
- ERC-165 interface-id semantics for interfaces that inherit other interfaces (whether inherited selectors are included in the XOR) is a common exam question; I did not verify the current compiler behaviour of `type(I).interfaceId` under inheritance.

## 04.4 — Calls, delegatecall & staticcall: whose context are you in?

### Concepts
- evm-message-call — Every contract-to-contract interaction is a *message call*: a new execution frame with its own gas budget, its own `address(this)`, and its own storage; there is no shared address space and no direct function call across contracts. | requires: [abi-function-selector] | contrasts: [sol-delegatecall-context]
- evm-call-context — Under `CALL`, `address(this)` is the callee, `msg.sender` is the caller contract, `msg.value` is the value attached to this call, and storage writes hit the callee's storage. | requires: [evm-message-call] | contrasts: [sol-delegatecall-context]
- sol-delegatecall-context — Under `DELEGATECALL`, only the *code* comes from the target: `address(this)`, storage, balance, `msg.sender` and `msg.value` are all those of the calling contract, propagated unchanged from the parent scope. | requires: [evm-call-context] | contrasts: [evm-call-context]
- delegatecall-storage-is-the-risk — Delegatecall matches storage by slot *position*, never by variable name, so a layout mismatch between proxy and implementation silently writes the wrong variable; this — not reentrancy — is the whole reason delegatecall is dangerous. | requires: [sol-delegatecall-context] | contrasts: [sol-data-location]
- delegatecall-no-code-succeeds — The EVM treats a call to an address with no code as a success returning empty data, so a proxy pointing at `address(0)` or an EOA makes every call "succeed" while doing nothing; low-level `.call`/`.delegatecall` skip the `EXTCODESIZE` check that Solidity inserts for typed calls. | requires: [sol-delegatecall-context] | contrasts: [evm-message-call]
- staticcall-context — `STATICCALL` is `CALL` with `value` forced to zero plus a STATIC flag that propagates into every subcall; `SSTORE`, `TSTORE`, `LOG0`–`LOG4`, `CREATE`, `CREATE2`, `SELFDESTRUCT` and any `CALL` with non-zero value throw inside it. | requires: [evm-call-context] | contrasts: [sol-view-pure]
- staticcall-is-the-enforcement — Solidity compiles `view` calls to `STATICCALL`, which is what turns a compile-time promise into a runtime guarantee — and is why a `view` function on an untrusted contract cannot reenter and write. | requires: [staticcall-context] | contrasts: [sol-view-pure]
- low-level-call-returns-bool — `.call`, `.delegatecall` and `.staticcall` return `(bool success, bytes memory returndata)`; an unchecked `success` is a silent-failure bug, and since 0.8 the compiler warns but does not stop you. | requires: [evm-message-call] | contrasts: [sol-custom-error]
- revert-bubbling — Re-throwing a failed subcall's reason requires manually re-reverting the raw returndata (`assembly { revert(add(r, 32), mload(r)) }`); otherwise the caller loses the callee's error entirely. | requires: [low-level-call-returns-bool] | contrasts: [abi-decode-validates]
- eip150-63-64-rule — A subcall can be given at most all-but-one-64th of the remaining gas, so the parent always survives a child's out-of-gas; conversely, a caller cannot guarantee a child receives a specific amount of gas. | requires: [evm-message-call] | contrasts: [low-level-call-returns-bool]
- returndata-bomb — Solidity's high-level and `.call` forms copy the entire returndata into memory, so a hostile callee can return megabytes and burn the caller's gas on memory expansion; the defence is an assembly call with `out_size = 0` plus a bounded `RETURNDATACOPY`. | requires: [eip150-63-64-rule] | contrasts: [revert-bubbling]
- this-dot-f-is-external — `this.f()` is a real `CALL` back into the same contract, which makes `msg.sender` become `address(this)` and defeats `msg.sender`-based authorisation. | requires: [evm-call-context] | contrasts: [sol-function-visibility]
- library-linking — A `library`'s `internal` functions are inlined into the caller's bytecode with a plain `JUMP`, while `public`/`external` library functions are deployed separately and reached by `DELEGATECALL`, requiring link-time address substitution. | requires: [sol-delegatecall-context] | contrasts: [sol-library-view-not-enforced]
- proxy-storage-slots — Because slot 0 collisions are otherwise inevitable, proxies keep their own state at pseudorandom slots (EIP-1967 `keccak256("eip1967.proxy.implementation") - 1`) or in ERC-7201 namespaces rather than in ordinary declared variables. | requires: [delegatecall-storage-is-the-risk] | contrasts: [proxy-storage-slots]
- tx-origin-not-eoa — Since EIP-7702, `msg.sender == tx.origin` no longer proves the caller is a plain EOA, because a delegated EOA runs contract code in its own top-level frame. | requires: [evm-call-context] | contrasts: [delegatecall-no-code-succeeds]
- try-catch-external-only — `try`/`catch` works only on external calls and contract creation, and splits into `catch Error(string)`, `catch Panic(uint)` and `catch (bytes)`; it cannot catch an out-of-gas in the caller's own frame. | requires: [low-level-call-returns-bool] | contrasts: [sol-custom-error]

### Primary sources
- [EIP-7: DELEGATECALL](https://eips.ethereum.org/EIPS/eip-7) — tier: spec — published: 2015-11 (Homestead) — the definitive one-liner: "CALLER and VALUE behave exactly in the callee's environment as they do in the caller's environment." No gas stipend is given.
- [EIP-214: New opcode STATICCALL](https://eips.ethereum.org/EIPS/eip-214) — tier: spec — published: 2017-02 — the STATIC flag, its propagation to subcalls, and the exact list of throwing opcodes.
- [EIP-150: Gas cost changes for IO-heavy operations](https://eips.ethereum.org/EIPS/eip-150) — tier: spec — published: 2016-09 — defines "all but one 64th" and thus why gas forwarding is never exact.
- [EIP-211: New opcodes RETURNDATASIZE and RETURNDATACOPY](https://eips.ethereum.org/EIPS/eip-211) — tier: spec — published: 2017-02 — why return data is a buffer the caller must copy, which is the mechanism the return bomb abuses.
- [Solidity docs — Units and Globally Available Variables: Members of Address Types](https://docs.soliditylang.org/en/latest/units-and-global-variables.html) — tier: canonical-docs — published: 2026-08 — states that low-level calls skip the `extcodesize` existence check and that delegatecall requires aligned storage layouts.
- [EIP-1967: Standard Proxy Storage Slots](https://eips.ethereum.org/EIPS/eip-1967) — tier: spec — published: 2019-04 — the implementation/admin/beacon slot constants every proxy and every block explorer uses.
- [EIP-7702: Set Code for EOAs](https://eips.ethereum.org/EIPS/eip-7702) — tier: spec — published: 2024 (shipped Pectra, May 2025) — why `tx.origin == msg.sender` is no longer an EOA test.
- [EIP-6780: SELFDESTRUCT only in same transaction](https://eips.ethereum.org/EIPS/eip-6780) — tier: spec — published: 2023-03 (Dencun) — the Parity-multisig "kill the library" attack no longer works the way it is still taught.
- [nomad-xyz/ExcessivelySafeCall](https://github.com/nomad-xyz/ExcessivelySafeCall) — tier: primary-analysis — published: 2021 — the reference implementation of a returndata-bounded low-level call.
- [OpenZeppelin — Proxy Upgrade Pattern / storage gaps](https://docs.openzeppelin.com/upgrades-plugins/proxies) — tier: vendor — published: 2024 onward — vendor doc, but the de facto standard treatment of layout compatibility across upgrades.

### Current state (Aug 2026)
- **`send` and `transfer` are formally deprecated** as of solc 0.8.31 (Dec 2025) and warn; the docs say they are "scheduled for removal". The 2300-gas stipend advice that dominates older tutorials is now actively wrong guidance. `call{value: x}("")` with a checked return is the current answer.
- **EIP-7702 has changed the shape of the "is it a contract?" question.** `EXTCODESIZE` on a delegated EOA returns 23 (the `0xef0100 || address` designator), so `code.length > 0` now says "has code", not "is a contract", and `msg.sender == tx.origin` no longer says "is an EOA". Any curriculum that still teaches the `extcodesize == 0` EOA check must be corrected.
- **`SELFDESTRUCT` is effectively neutered** since EIP-6780 (Dencun, March 2024): it only sends the balance unless called in the same transaction the contract was created in. The Parity multisig story is still worth telling as history, but "an attacker can selfdestruct your library and brick your proxy" is no longer the live threat it was.
- **Transient storage changes the reentrancy-guard calculus.** `TSTORE`/`TLOAD` (EIP-1153) cost 100 gas each, making a transient reentrancy guard roughly 200 gas versus roughly 7100 with cold storage. `TSTORE` is also forbidden inside a static context, so the guard composes correctly with `STATICCALL`. Note solc 0.8.34 patched a high-severity bug where a storage variable could be cleared instead of the transient variable at the same layout position — pin >= 0.8.34 before teaching transient storage.
- **Access control, not reentrancy, is where the money goes.** 2025 loss data: 122 incidents, $905.4M total, with access-control failures dominating and reentrancy fourth by value at $35.7M. Delegatecall/proxy-admin mistakes sit squarely in the access-control bucket, which argues for teaching this module before the reentrancy module.
- Default EVM target in solc is `osaka` since 0.8.31, so `MCOPY`, `TSTORE`/`TLOAD`, `BLOBHASH` and the Fusaka additions are all assumed available unless the target is lowered for an older L2.
- Fusaka raised the L1 gas limit to 60M with a ~16.78M single-transaction cap (EIP-7825). Deep call chains that previously fit in one transaction can now hit a per-transaction ceiling that did not exist before.

### Misconceptions
- Belief: `delegatecall` is dangerous because the callee can steal Ether. | Reality: The callee runs *as* the caller, so it writes the caller's storage — including the implementation-address slot and the owner slot. The storage context is the entire risk; the Ether follows from owning the storage. | Why: "call" framing makes people think about value transfer. | Source: https://eips.ethereum.org/EIPS/eip-7
- Belief: Storage variables are matched by name across a delegatecall. | Reality: They are matched by slot number. Renaming is free; reordering, inserting, or changing a type's packing silently corrupts state. | Why: Solidity source makes them look like named fields. | Source: https://docs.soliditylang.org/en/latest/units-and-global-variables.html
- Belief: A failed low-level call reverts the transaction. | Reality: `.call` returns `false`; execution continues. Only an unhandled revert in the *current* frame reverts. | Why: High-level typed calls do auto-revert, so the two behave differently and look the same. | Source: https://docs.soliditylang.org/en/latest/units-and-global-variables.html
- Belief: Calling a nonexistent contract reverts. | Reality: The EVM treats it as success with empty return data. Solidity inserts an `extcodesize` check for typed calls, but `.call`/`.delegatecall`/`.staticcall` do not have it. | Why: The compiler's hidden check masks the EVM behaviour until you drop to low level. | Source: https://docs.soliditylang.org/en/latest/units-and-global-variables.html
- Belief: `msg.sender` inside a delegatecalled implementation is the proxy. | Reality: It is whoever called the proxy — the original caller — because DELEGATECALL propagates CALLER unchanged. | Why: Every other kind of call changes msg.sender to the immediate caller. | Source: https://eips.ethereum.org/EIPS/eip-7
- Belief: `address(this)` inside a delegatecalled implementation is the implementation. | Reality: It is the proxy. So is `address(this).balance`, and so is the address that appears in emitted logs. | Why: `this` reads as "the code I am in". | Source: https://eips.ethereum.org/EIPS/eip-7
- Belief: `this.f()` is a cheap internal call. | Reality: It is a full external CALL costing 2600+ gas and resetting `msg.sender` to the contract's own address. | Why: The `this.` prefix reads like Java. | Source: https://docs.soliditylang.org/en/latest/contracts.html#function-visibility
- Belief: `gas: g` guarantees the callee receives `g` gas. | Reality: EIP-150 caps a subcall at all-but-one-64th of remaining gas, so requesting more silently gives less; you cannot force a callee to OOG at a chosen point, nor guarantee it has enough. | Why: The syntax looks like an exact allocation. | Source: https://eips.ethereum.org/EIPS/eip-150
- Belief: `staticcall` prevents reentrancy generally. | Reality: It prevents *state-changing* reentrancy in that subtree; a read-only reentrancy (calling back into a view function that reports stale intermediate state) is still possible and has been exploited against price oracles. | Why: "static" sounds total. | Source: https://eips.ethereum.org/EIPS/eip-214
- Belief: `require(success)` after a low-level call gives the user a useful error. | Reality: It replaces the callee's revert reason with a bare failure; you must re-revert the raw returndata to preserve it. | Why: The reason bytes are sitting in a variable people ignore. | Source: https://eips.ethereum.org/EIPS/eip-211
- Belief: Checking `addr.code.length == 0` proves the caller is an EOA. | Reality: Post-EIP-7702 a delegated EOA has 23 bytes of code; and any contract in its constructor still has zero code length. Both directions of the check are broken. | Why: The check was standard advice for years. | Source: https://eips.ethereum.org/EIPS/eip-7702
- Belief: An attacker can brick your proxy by selfdestructing the implementation. | Reality: Since EIP-6780 (Dencun), `SELFDESTRUCT` only removes code when executed in the same transaction as the contract's creation. | Why: The 2017 Parity incident is still the standard teaching example. | Source: https://eips.ethereum.org/EIPS/eip-6780

### Practice ideas
- kind: implement — Build `Caller` and `Target` where `Target.probe()` emits `(address(this), msg.sender, msg.value, address(this).balance)`. Invoke it four ways from `Caller`: typed call, `.call`, `.delegatecall`, `.staticcall`. Tabulate the four fields for each. | acceptance: learner produces a 4x4 table and can predict every cell before running; the staticcall row fails to emit at all (LOG is forbidden), which is itself the lesson.
- kind: break — Write a proxy whose slot 0 is `address implementation` and an implementation whose slot 0 is `uint256 totalSupply`. Call a function that sets `totalSupply = 1`, then show the proxy now points at `address(0x01)` and every subsequent call silently "succeeds" doing nothing. | acceptance: a test asserting the implementation slot changed, plus a second assertion that a later call returns `success == true` with empty returndata.
- kind: fix — Take the same proxy and move its state to the EIP-1967 slot with inline assembly (or to an ERC-7201 namespace using solc 0.8.35's `erc7201` builtin). Re-run the breaking test. | acceptance: the state-corruption test now fails to corrupt anything, and `cast storage <proxy> 0x360894...` returns the implementation address.
- kind: break — Implement a hostile callee whose fallback does `assembly { return(0, 0xffffff) }` and show a naive `(bool ok, bytes memory r) = t.call(data)` in the caller consuming an order of magnitude more gas than with a benign callee. Then swap in an ExcessivelySafeCall-style assembly call with `out_size = 0`. | acceptance: measured gas drops back to roughly the benign baseline.
- kind: measure — Compare a storage-based `nonReentrant` modifier against a TSTORE/TLOAD one on solc >= 0.8.34 with `--evm-version cancun` or later. | acceptance: learner's own numbers land near the ~7100 vs ~200 gas ballpark and they can explain the difference from the SSTORE cold/warm schedule.
- kind: write — Write a `bubbleRevert(bytes memory ret)` helper and a test proving that a custom error thrown three frames deep still reaches the top-level caller with its selector and arguments intact. | acceptance: `vm.expectRevert(abi.encodeWithSelector(MyError.selector, 1, 2))` passes across the whole chain.
- kind: read — On a public RPC, read slot `0x360894a13ba1a3210667c828492db98dca3e2076cc3735a920a3ca505d382bbc` of any live OpenZeppelin proxy and confirm it holds the implementation address that the block explorer shows. | acceptance: the raw slot value matches the explorer's "implementation" link.

### Gaps & uncertainties
- The transient-guard figures (~200 gas vs ~7100 gas) come from the shared baseline, not from a measurement I made; they depend on whether the storage slot is cold or warm and on the optimiser. Publish them as an order-of-magnitude claim, not an exact number, or have learners measure their own.
- I did not independently verify that `TSTORE` throws under the STATIC flag from the EIP-1153 text — EIP-214's enumerated list predates transient storage. It is the near-certain design, but confirm against EIP-1153 before asserting it in a lesson.
- Exact current gas costs of `CALL`/`DELEGATECALL`/`STATICCALL` under the `osaka` and `amsterdam` EVM revisions were not checked; EIP-150's 700 and EIP-2929's cold/warm 2600/100 both apply in layers and I did not confirm no later repricing landed in Fusaka.
- The 2025 security figures ($905.4M / 122 incidents, access control dominating, reentrancy $35.7M) come from the shared baseline; the baseline itself flags the access-control total's period as unclear. Do not present the access-control number as directly comparable to the others.
- I did not find a 2025-2026 primary incident report specifically attributing a large loss to a delegatecall storage-layout mismatch. The teaching example should probably be constructed rather than sourced, or use a documented older case, until one is verified.
- Whether the via-IR pipeline still emits the `extcodesize` existence check for typed external calls in all cases (it can be elided when the return data size is known) was not verified.

## 04.5 — Custom errors & events: cost, selectors, indexing, and how they reach clients

### Concepts
- sol-custom-error — A custom error is declared like an event (`error Unauthorized();`) and thrown with `revert Unauthorized();`; its revert data is the ABI encoding of a call to a function of the same signature. | requires: [abi-canonical-signature] | contrasts: [sol-revert-string]
- sol-error-selector — An error's selector is derived exactly like a function selector — first 4 bytes of `keccak256` of the canonical signature — so `Unauthorized()` is `0x82b42900` and `InsufficientBalance(uint256,uint256)` is `0xcf479181`. | requires: [sol-custom-error, abi-function-selector] | contrasts: [abi-function-selector]
- sol-builtin-error-selectors — Two selectors are built in: `Error(string)` = `0x08c379a0` (from `require(cond, "msg")` and `revert("msg")`) and `Panic(uint256)` = `0x4e487b71` (from `assert` and compiler-inserted checks). | requires: [sol-error-selector] | contrasts: [sol-custom-error]
- sol-panic-codes — Panic codes classify compiler-detected bugs: 0x01 assert, 0x11 arithmetic over/underflow, 0x12 division or modulo by zero, 0x21 bad enum conversion, 0x22 malformed storage byte array, 0x31 pop on empty array, 0x32 index out of bounds, 0x41 allocation too large, 0x51 uninitialised internal function pointer. | requires: [sol-builtin-error-selectors] | contrasts: [sol-custom-error]
- sol-revert-string — A revert string costs 4 bytes of selector plus a full ABI-encoded `string` — the compiler's own example needs 100 bytes of revert data for `"Unauthorized"` against 4 bytes for `revert Unauthorized()` — and the literal must also be stored in deployed bytecode. | requires: [sol-custom-error] | contrasts: [sol-custom-error]
- sol-require-no-data — `require(bool)` with no second argument reverts with *no data at all* — not even a selector — which is why bare requires produce unhelpful client errors. | requires: [sol-builtin-error-selectors] | contrasts: [sol-revert-string]
- sol-require-with-error — Since 0.8.26 (via-IR) and 0.8.27 (legacy pipeline), `require(cond, CustomError(args))` is a supported overload, so the old "custom errors force you to write if/revert" advice is obsolete. | requires: [sol-custom-error] | contrasts: [sol-revert-string]
- sol-require-args-eager — `require`'s second argument is evaluated unconditionally, so `require(cond, CustomError(f()))` calls `f()` even when `cond` is true. | requires: [sol-require-with-error] | contrasts: [sol-modifier-placeholder]
- error-data-untrusted — Error data bubbles up through the whole call chain and any contract can fabricate any error by returning matching bytes, so a decoded error name is evidence about the bytes, never about which contract failed. | requires: [sol-error-selector] | contrasts: [revert-bubbling]
- sol-event-topics — A non-anonymous event's `topics[0]` is `keccak256` of the event's canonical signature; up to three further parameters may be `indexed` and become `topics[1..3]`. Anonymous events omit `topics[0]` and may index four. | requires: [abi-canonical-signature] | contrasts: [sol-error-selector]
- event-indexed-reference-types — An indexed `string`, `bytes`, array or struct stores the *Keccak hash* of the value in the topic, not the value, so it is searchable but not recoverable — the standard fix is to emit the same value twice, once indexed and once not. | requires: [sol-event-topics] | contrasts: [sol-event-data]
- sol-event-data — Non-indexed parameters are ABI-encoded (head/tail, same rules as a function call) into the log's `data` field, where they are readable but not filterable. | requires: [sol-event-topics, abi-head-tail] | contrasts: [event-indexed-reference-types]
- log-gas-model — A `LOG` costs 375 base + 375 per topic + 8 per byte of data (plus memory expansion), so indexing is roughly 375 gas per field and moving a field from data to a topic is not free. | requires: [sol-event-topics] | contrasts: [sol-revert-string]
- events-are-not-readable-onchain — Logs are written to the receipt, not to state; no contract, including the emitting one, can read a log back. They exist for off-chain consumers only. | requires: [sol-event-data] | contrasts: [evm-storage-slot]
- error-client-surfacing — Clients receive revert data as raw bytes on the JSON-RPC error and must match the selector against an ABI to name it; viem raises `ContractFunctionRevertedError` carrying decoded `data`/`errorName`/`args`, special-cases `Error` and `Panic`, and when the selector is absent from the ABI reports only the raw signature. | requires: [sol-error-selector] | contrasts: [abi-decode-validates]
- errors-not-in-abi-when-forwarded — The compiler lists a contract's own errors in its ABI JSON but *not* errors forwarded from external calls, so a frontend holding only the entrypoint's ABI will fail to decode errors thrown deeper in the stack. | requires: [error-client-surfacing] | contrasts: [error-data-untrusted]

### Current state (Aug 2026)
- **`require(cond, CustomError())` is supported.** Introduced in 0.8.26 (via-IR only, May 2024) and available in the legacy pipeline from 0.8.27 (Sep 2024). Virtually all custom-error tutorials predate this and still teach `if (!cond) revert CustomError();` as mandatory. 0.8.35 preserves the custom-error argument even under `--revert-strings strip`, and 0.8.37-develop fixes an ICE on parenthesised custom-error construction inside `require`.
- 0.8.26 also added "cheaper code for reverting with errors of a small static encoding size" in the Yul IR generator, which widened the custom-error gas advantage in via-IR builds.
- 0.8.32 fixed error and event selectors not being treated as compile-time constants — relevant if you teach `MyError.selector` in constant expressions; pin >= 0.8.32.
- 0.8.36 disallows `@return` in event NatSpec (previously accepted, now an error) — a small break for anyone with older documented events.
- LOG gas constants are unchanged in the Fusaka/`osaka` fork: 375 base, 375 per topic, 8 per data byte. Nothing in the last 18 months repriced logs.
- **The indexing ecosystem shifted underneath events.** The Graph fully retired its free hosted service in 2026; Envio HyperIndex is the current speed leader, Ponder's team joined Monad in Feb 2026, and SQD/Subsquid is mid-rebrand after an acquisition. Any lesson that says "deploy a subgraph to the hosted service" is dead. Event design should be taught as "design for whatever indexer you run", with `topics[0]` stability as the contract you must not break.
- The 4-byte directory that clients point at for unknown selectors is now `4byte.sourcify.dev` (viem's own error message links there), not the older standalone 4byte.directory UI.
- Custom errors are the default in modern libraries: OpenZeppelin moved wholesale to custom errors in v5, so revert strings now mostly appear in legacy code and in learners' own contracts.

### Misconceptions
- Belief: Custom errors save gas at runtime, so they always save gas. | Reality: The runtime saving only materialises when the revert actually fires; the reliable, unconditional saving is in *deploy* cost, because revert string literals live in the deployed bytecode. | Why: Gas reports show the revert path. | Source: https://soliditylang.org/blog/2021/04/21/custom-errors/
- Belief: You cannot use `require` with a custom error. | Reality: `require(bool, error)` has existed since 0.8.26/0.8.27. | Why: The canonical 2021 blog post says so and has never been amended. | Source: https://github.com/argotorg/solidity/blob/develop/Changelog.md
- Belief: `require(cond, CustomError(compute()))` only calls `compute()` on failure. | Reality: `require` arguments are evaluated unconditionally — `compute()` runs on the happy path too, costing gas and possibly causing side effects. | Why: Short-circuit intuition from `&&`. | Source: https://docs.soliditylang.org/en/latest/control-structures.html
- Belief: `require(cond)` gives the client a generic "execution reverted" message. | Reality: It reverts with *zero bytes* of data, so there is nothing to decode at all — strictly worse for debugging than any alternative. | Why: Clients print a generic string that looks like a message. | Source: https://docs.soliditylang.org/en/latest/control-structures.html
- Belief: `assert` and `require` are two flavours of the same thing. | Reality: `assert` produces `Panic(uint256)` and signals a bug in your own code; `require` produces `Error(string)` or your custom error and signals bad input. Since 0.8.0 `assert` no longer consumes all gas, which removed the old cost argument but not the semantic one. | Why: Both take a boolean. | Source: https://docs.soliditylang.org/en/latest/control-structures.html
- Belief: Receiving a `Panic(0x11)` means the contract has an overflow guard working correctly. | Reality: A Panic means the compiler caught a condition that "properly functioning code should never create" — it is an internal-bug signal, and reaching one from valid external input is itself the bug. | Why: The 0.8 checked-arithmetic revert is taught as a safety feature. | Source: https://docs.soliditylang.org/en/latest/control-structures.html
- Belief: Decoding an error name tells you which contract reverted. | Reality: Error data bubbles up unlabelled and any contract can return bytes matching any error signature; the name is a claim, not provenance. | Why: The client shows a tidy `MyError(1, 2)` with no address. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#errors
- Belief: Index everything so it can all be filtered. | Reality: Each topic costs 375 gas, only three are available on non-anonymous events, and indexing a `string`/`bytes`/array replaces the value with its hash so you can no longer read it back. | Why: "indexed" reads like a database index with no downside. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#events
- Belief: An indexed string can be read from the log. | Reality: You get `keccak256(value)`. You can test "is it equal to X?" but you can never recover X. Emit it twice — once indexed, once not — if you need both. | Why: The ABI shows the parameter as `string`. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#events
- Belief: A contract can read its own past events. | Reality: Logs go to the receipt trie, never to state; no opcode reads them back. Anything a contract needs later must be in storage. | Why: "emitting an event" sounds like writing a record. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#events
- Belief: Renaming an event parameter is a harmless refactor. | Reality: Parameter *names* are not in the signature, so renaming is safe; but reordering, retyping, or adding a parameter changes `topics[0]` and silently breaks every deployed indexer and filter. | Why: The two edits look equally cosmetic in a diff. | Source: https://docs.soliditylang.org/en/latest/abi-spec.html#events
- Belief: The frontend will decode any revert my system produces. | Reality: The ABI JSON contains only the contract's *own* errors, not errors forwarded from contracts it calls, so multi-contract systems need a merged error ABI on the client. | Why: One-contract tutorials never hit this. | Source: https://soliditylang.org/blog/2021/04/21/custom-errors/

### Practice ideas
- kind: measure — Build three contracts identical except for the failure path: `require(cond, "Insufficient balance for this transfer")`, `revert InsufficientBalance(a, b)`, and `require(cond, InsufficientBalance(a, b))`. Record deploy bytecode size, deploy gas, happy-path gas and revert-path gas, both with and without `--via-ir`. | acceptance: a 3x4 table; learner can explain why deploy cost differs even though the happy path barely does, and why via-IR changes the picture.
- kind: implement — Compute the selector for your own error by hand (`cast sig "InsufficientBalance(uint256,uint256)"`) and confirm it equals the first four bytes of the raw revert data captured with `vm.expectRevert` / a low-level call. | acceptance: hand-computed selector equals the on-chain bytes, and the learner reproduces `0xcf479181` from the docs example.
- kind: break — Deploy an "impostor" contract that does `revert InsufficientBalance(0, 0)` for an error it does not own, call it through a wrapper, and show the client naming the wrong failure. | acceptance: a test proving that error name alone cannot identify the failing contract.
- kind: measure — Emit the same four-field event with 0, 1, 2 and 3 indexed parameters and record gas for each. | acceptance: measured deltas land near 375 gas per topic and the learner can decompose total cost into base + topics + 8/byte.
- kind: break — Emit an event with an `indexed string`, then try to reconstruct the original string from `eth_getLogs`. Fail. Fix by emitting it twice (indexed + non-indexed) and show both filtering and reading working. | acceptance: the first attempt yields only a hash; the second yields a filterable *and* readable value.
- kind: fix — Take a contract using bare `require(cond)` throughout, convert to custom errors with arguments carrying the offending values, and show a viem or ethers script printing a specific, actionable failure where it previously printed a bare "execution reverted". | acceptance: the client script prints the error name and both arguments.
- kind: write — Write a Panic-code lookup table by triggering each of 0x01, 0x11, 0x12, 0x32 and 0x41 deliberately in Foundry tests and asserting `vm.expectRevert(abi.encodeWithSignature("Panic(uint256)", 0x11))` etc. | acceptance: at least five distinct panic codes triggered and asserted.
- kind: read — Point a local indexer (Envio HyperIndex or Ponder) at a live ERC-20's `Transfer(address,address,uint256)` on a public RPC and confirm the filter works by `topics[0]`; then change one parameter type in a local copy and show `topics[0]` changing. | acceptance: learner can compute `keccak256("Transfer(address,address,uint256)")` by hand and see it as the literal `topics[0]` in raw log output.

### Visual opportunities
- Revert-data anatomy, three side-by-side byte strips at the same scale: `require(cond)` (0 bytes), `revert Unauthorized()` (4 bytes), `revert("Unauthorized")` (100 bytes). The visual size difference *is* the argument and needs no numbers.
- A single log entry drawn as its real structure: `address`, `topics[0..3]`, `data`. Overlay one event declaration on top, with arrows from each parameter to where it lands, and a hash symbol on the indexed dynamic parameter.
- Gas decomposition bar for one emit: 375 base, +375 per topic, +8/byte data, plus a memory-expansion tail — stacked so learners see indexing is a per-field purchase.
- The error journey end to end: `revert MyError(a,b)` -> 4-byte selector + ABI args -> bubbles up through N frames unchanged -> JSON-RPC error `data` field -> client matches selector against ABI -> `MyError(1, 2)` in the UI. Mark the one step where a hostile contract can inject a fake.
- A decision flowchart for "indexed or not?": do I need to filter on it (yes -> indexed) / do I need to read the value back (yes -> not indexed, or emit twice) / is it dynamic (warn: hashed) / am I already at three?

### Gaps & uncertainties
- The "4 bytes vs 100 bytes" comparison is exactly what the Solidity blog's Yul listings show, and it is a *revert-data-size* comparison, not a gas figure. I found **no authoritative published gas number** for custom errors vs revert strings — the widely circulated numbers are blog-post benchmarks with unstated optimiser settings. Do not publish a gas figure; make learners measure it.
- The claim that custom errors save more on deploy than at runtime is directionally supported by the compiler blog ("decrease both deploy and runtime gas costs") but I could not find a quantified breakdown from a primary source.
- I did not verify whether `0.8.26`'s "cheaper code for reverting with errors of a small static encoding size" applies to the legacy pipeline as well as via-IR; the changelog entry is filed under Yul IR Code Generation, which suggests via-IR only.
- I did not verify current viem/ethers version numbers or their exact error class names beyond reading viem's `main`-branch `contract.ts`; the class `ContractFunctionRevertedError` and its `data`/`reason`/`signature` fields are confirmed from source, but API surface may have shifted in a release I did not check.
- Panic code `0x00` ("generic compiler inserted panics") is listed in the docs without explanation of when it fires; I could not find a concrete trigger.
- The indexer landscape claims (Graph hosted service retired, Envio fastest, Ponder team at Monad, SQD rebranding) come from the shared baseline, not from sources I verified in this shard. "Fastest" in particular is a benchmark claim that should be attributed, not stated flatly.
- I did not confirm whether anonymous events are still worth teaching; they save the `topics[0]` slot (375 gas) at the cost of undecodability without out-of-band knowledge, and I found no current guidance on real-world usage.
