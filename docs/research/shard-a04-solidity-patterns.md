## 04.6 — Contract patterns: CEI, pull-over-push, access control, pausability, factories & clones

### Concepts
- cei-order — Checks-Effects-Interactions orders a function as validate inputs, write all state, then call outside contracts last, so a re-entrant call always sees final state. | requires: [evm-external-call, storage-vs-memory] | contrasts: [reentrancy-guard, cei-insufficient]
- cei-insufficient — CEI protects the function it is applied to but not cross-function or cross-contract reentrancy, and not read-only reentrancy where a `view` getter is queried mid-callback while an invariant is temporarily broken. | requires: [cei-order] | contrasts: [reentrancy-guard]
- reentrancy-guard — A mutex flag (OpenZeppelin `nonReentrant`) blocks re-entry into any guarded function of the same contract, and is the belt to CEI's braces; it does nothing for a *different* contract reading your state. | requires: [cei-order] | contrasts: [reentrancy-guard-transient, cei-insufficient]
- reentrancy-guard-transient — `ReentrancyGuardTransient` stores the mutex in EIP-1153 transient storage (TSTORE/TLOAD), cutting the guard from roughly 5,000-7,100 gas to roughly 200 gas because it never touches the state trie and dodges the EIP-2929 cold-access penalty. | requires: [reentrancy-guard, eip-1153-transient-storage] | contrasts: [reentrancy-guard]
- pattern-pull-payments — Pull-over-push records a credit balance and lets the recipient call `withdraw()` later, instead of the contract pushing ETH out during its own logic. | requires: [evm-external-call] | contrasts: [push-payment-dos]
- push-payment-dos — Pushing funds inside a loop lets one recipient that reverts, consumes all gas, or is a contract without a payable fallback permanently brick the whole distribution for everyone else. | requires: [pattern-pull-payments] | contrasts: [pattern-pull-payments]
- transfer-stipend-obsolete — `address.transfer` / `.send` forward a fixed 2300 gas stipend; since EIP-1884 repriced SLOAD this breaks legitimate smart-contract wallets, so the current guidance is `call{value: x}("")` plus a reentrancy guard and a checked return value. | requires: [pattern-pull-payments] | contrasts: [cei-order]
- access-ownable — `Ownable` is a single-address privilege bit; OZ 5.x requires the initial owner as a constructor argument (no implicit `msg.sender`) and reverts with `OwnableUnauthorizedAccount`. | requires: [msg-sender] | contrasts: [access-ownable2step, access-roles]
- access-ownable2step — `Ownable2Step` splits transfer into `transferOwnership` (pending) plus `acceptOwnership` by the new owner, which makes a typo'd address non-fatal. | requires: [access-ownable] | contrasts: [access-ownable]
- access-roles — `AccessControl` gives per-contract `bytes32` roles with an admin role per role; `DEFAULT_ADMIN_ROLE` administers itself, so it is the root key and should be a multisig or timelock, not an EOA. | requires: [access-ownable] | contrasts: [access-manager]
- access-manager — `AccessManager` (added in OZ 5.0) centralises permissions for a whole protocol in one contract: roles are granted per (target contract, function selector) and can carry per-role execution delays, giving timelocks without a separate timelock contract. | requires: [access-roles] | contrasts: [access-roles]
- access-control-is-top-loss — Access-control failures, not reentrancy, are the largest category of on-chain loss by value; the bug is usually a missing modifier, an unprotected initializer, or a compromised owner key rather than an exotic reentrancy. | requires: [access-roles] | contrasts: [cei-order]
- pausability — `Pausable` supplies `whenNotPaused` / `whenPaused` modifiers and internal `_pause` / `_unpause`; it deliberately ships with *no* access control, so forgetting to gate the pause entry point is the classic bug. | requires: [access-roles] | contrasts: [access-manager]
- pause-is-centralisation — A pause switch is a live centralisation vector and a trust assumption a user must be told about; auditors expect it behind a multisig, with an explicit unpause path and a rule about which functions (usually not withdrawals) stay open. | requires: [pausability] | contrasts: [pausability]
- factory-create-vs-create2 — `CREATE` derives the address from (deployer, nonce) so it is path-dependent; `CREATE2` derives it from (0xff, deployer, salt, keccak256(initcode)) so the address is known before deployment but changes if the constructor arguments or bytecode change. | requires: [evm-address-derivation] | contrasts: [clone-eip1167]
- clone-eip1167 — An EIP-1167 minimal proxy is a fixed 45-byte runtime (55 bytes of creation code) that `delegatecall`s every call to one hard-coded implementation address, turning a multi-thousand-byte deployment into a tiny one. | requires: [delegatecall, factory-create-vs-create2] | contrasts: [proxy-upgradeable]
- clone-tradeoff — Clones trade a large one-time deployment saving for a permanent extra `delegatecall` on every call, so they pay off for many instances of the same contract and lose for a singleton. | requires: [clone-eip1167] | contrasts: [clone-eip1167]
- clone-no-constructor — A clone runs no constructor, so state must be set by an `initialize()` function that is callable exactly once; the implementation contract itself must call `_disableInitializers()` in its own constructor or it can be initialised and, if it self-destructs or delegatecalls, take every clone with it. | requires: [clone-eip1167] | contrasts: [factory-create-vs-create2]
- clone-not-upgradeable — The implementation address is baked into the clone's immutable bytecode, so clones are cheap but frozen; upgradeable-per-instance needs ERC-1967 proxies, and upgrade-all-at-once needs a beacon proxy. | requires: [clone-eip1167] | contrasts: [proxy-upgradeable]

### Current state (Aug 2026)
- OpenZeppelin Contracts 5.x is the baseline for every pattern here. Pre-5.0 teaching material is wrong in specific ways: `Ownable()` no longer defaults to `msg.sender` (it takes `initialOwner`), `require` strings were replaced by custom errors (`OwnableUnauthorizedAccount`, `AccessControlUnauthorizedAccount`, `EnforcedPause`, `ExpectedPause`), and `Counters`/`ERC20 hooks` were removed.
- `ReentrancyGuardTransient` (EIP-1153 backed) is available and is the default choice on chains that have Cancun-or-later semantics. Note it is transaction-scoped, not call-scoped — that is the point, but it also means a guard set in one call frame is visible to the whole transaction.
- **EIP-7702 breaks a load-bearing assumption of these patterns.** A delegated EOA has 23 bytes of code (`0xef0100 || address`), so `address.code.length == 0` and `msg.sender == tx.origin` no longer prove "this is a plain EOA". Any pull-payment, airdrop, or anti-contract guard written before May 2025 that uses those checks is now unsound, and pushing ETH to an "EOA" can now execute arbitrary code.
- Fusaka (Dec 2025) raised the L1 gas limit to 60M but capped a single transaction at ~16.78M gas (EIP-7825). That cap is a hard argument for pull-over-push: a batch-push distribution that grew past ~16.78M gas is now *unlandable*, not merely expensive.
- CREATE2-based factories remain the standard for deterministic addresses. CREATE3 (address independent of initcode, via an intermediate CREATE2-deployed deployer) is widely used by Solady/Solmate-style stacks for cross-chain same-address deployments — verify the specific library version before teaching it.
- Commonly taught and now wrong: "use `transfer()` to send ETH because the 2300 gas stipend prevents reentrancy". It has been wrong since EIP-1884 (Istanbul, 2019) and it breaks smart-contract wallets and now EIP-7702 delegated EOAs.

### Misconceptions
- Belief: CEI alone makes a contract reentrancy-safe. | Reality: it protects that one function; cross-function, cross-contract, and read-only reentrancy all survive CEI. | Why: tutorials demo the single-function withdraw bug and stop there. | Source: https://www.cyfrin.io/blog/solodit-checklist-explained-8-reentrancy-attack
- Belief: `.transfer()`'s 2300 gas stipend is a reentrancy defence. | Reality: gas costs are repriced by hard forks, so a fixed stipend is a compatibility bug, not a security control; it bricks multisig and account-abstraction wallets. | Why: it was correct advice pre-2019 and the advice outlived the pricing. | Source: https://docs.soliditylang.org/en/latest/security-considerations.html
- Belief: reentrancy is the top cause of smart-contract loss. | Reality: access-control failure dominates by value; reentrancy was 4th in 2025 (~$35.7M vs access control at the top). | Why: reentrancy is the most *teachable* bug, so it dominates curricula, not incidents. | Source: https://arxiv.org/pdf/2507.20175
- Belief: an EIP-1167 clone is an upgradeable proxy. | Reality: the implementation address is immutable bytecode in the clone; it is a *cheap deployment* pattern, not an upgrade pattern. | Why: both use `delegatecall`, so people collapse the two. | Source: https://eips.ethereum.org/EIPS/eip-1167
- Belief: clones are strictly cheaper. | Reality: cheaper to deploy, permanently more expensive to call (one extra delegatecall plus the proxy's own dispatch on every call). | Why: benchmarks quote deployment gas only. | Source: https://docs.openzeppelin.com/contracts/5.x/api/proxy
- Belief: `Pausable` protects the pause function. | Reality: OZ ships `_pause`/`_unpause` as internal with no authorization; you must add it, and forgetting to is a real audit finding. | Why: the module name implies a complete feature. | Source: https://docs.openzeppelin.com/contracts/5.x/api/utils#Pausable
- Belief: `msg.sender == tx.origin` means the caller is a human's EOA. | Reality: since EIP-7702 an EOA can execute delegated contract code within its own transaction. | Why: the check was reliable for a decade. | Source: https://eips.ethereum.org/EIPS/eip-7702
- Belief: an uninitialized implementation contract behind clones is harmless because "nobody uses it". | Reality: anyone can call `initialize()` on the implementation and become its owner; historically that has been chained into `selfdestruct`/delegatecall to brick every clone. | Why: the implementation feels like an abstract class. | Source: https://docs.openzeppelin.com/contracts/5.x/api/proxy

### Practice ideas
- kind: break — In Foundry, write a `VulnerableBank` with the interaction before the effect, and an attacker contract whose `receive()` re-enters `withdraw`. | Acceptance: `forge test` shows attacker balance > its deposit, and the same test fails to drain after reordering to CEI.
- kind: break — Extend the above into read-only reentrancy: a second contract prices shares via `bank.totalAssets()`; the attacker calls it from inside the callback. | Acceptance: the CEI-fixed, `nonReentrant`-guarded bank still returns a wrong price to the observer, proving the guard's scope.
- kind: fix — Take a `distribute(address[] recipients)` that pushes ETH in a loop and convert it to pull payments with a `credits` mapping. | Acceptance: a recipient whose `receive()` always reverts can no longer block any other recipient's payout; add a test with a gas-burning recipient too.
- kind: measure — Benchmark three guards on the same function: no guard, `ReentrancyGuard`, `ReentrancyGuardTransient`. | Acceptance: a `forge test --gas-report` table showing the storage guard costing thousands of gas and the transient one on the order of a few hundred.
- kind: measure — Deploy one full implementation and 50 EIP-1167 clones vs 50 full deployments; also measure the per-call delta on an identical function. | Acceptance: a break-even instance count computed from your own numbers, plus the measured per-call delegatecall overhead.
- kind: implement — Build a `Factory` using `Clones.cloneDeterministic` and `predictDeterministicAddress`, with an `initialize` guarded by `Initializable` and `_disableInitializers()` in the implementation constructor. | Acceptance: predicted address equals deployed address; a test proving `initialize` reverts on the second call and on the implementation itself.
- kind: implement — Wire the same protocol two ways: `AccessControl` roles per contract, then a single `AccessManager` with a delayed admin role. | Acceptance: a test showing a delayed role cannot execute until the delay elapses, and a written comparison of how many transactions each design needs to rotate one operator.
- kind: read — Read `Clones.sol` and `Pausable.sol` from `openzeppelin-contracts` and write down every place authorization is assumed but not enforced. | Acceptance: a list naming at least `_pause`, `_unpause`, and the clone `initialize` pattern.
- kind: break — Write a guard `require(msg.sender == tx.origin)` and defeat it on a fork with an EIP-7702 delegated EOA (or simulate by `vm.etch`ing a `0xef0100||impl` designator). | Acceptance: the "EOA-only" function executes contract logic.

### Gaps & uncertainties
- The "~5,000 vs ~200 gas" figure for storage vs transient reentrancy guards comes from secondary sources; the shared baseline says ~7,100 vs ~200. These disagree because the storage figure depends on whether the slot is cold/warm and whether the refund applies. Do NOT publish a single number — have learners measure it.
- EIP-1167 deployment-gas savings are quoted very differently across sources (they depend on the implementation's bytecode size). No canonical number exists; treat this as a measurement exercise only.
- RESOLVED while researching 04.9: `Clones.cloneWithImmutableArgs` landed in **OpenZeppelin Contracts 5.4.0 (2025-07-17)**, not 5.2. The exact ABI of `fetchCloneArgs` is still unverified.
- RESOLVED while researching 04.9: OZ **5.7.0 (2026-07-29)** ships a first-party `Create3` library, so CREATE3 is no longer only a third-party pattern.
- ERC-7511 ("minimal proxy with PUSH0", a shorter variant) — I recall this as a draft EIP but did not confirm its status or byte length. Do not state a byte count without checking.
- CREATE3 is a community pattern, not an EIP; library implementations differ (Solady vs Solmate vs 0age's original). Unverified which is dominant in 2026.
- Whether `AccessManager` has meaningful production adoption versus `AccessControl` in Aug 2026 is unverified — the OZ docs recommend it, which is a vendor position, not evidence of adoption.

## 04.8b — Token standards ERC-20 / ERC-721 / ERC-1155 and how integrations break

### Concepts
- erc20-is-a-ledger — An ERC-20 token is not an object a user holds; it is one contract holding a `balanceOf` mapping, so "sending a token" is that contract editing two numbers, and a user's wallet holds no token state at all. | requires: [contract-storage] | contrasts: [erc721-ownership]
- erc20-allowance-model — Spending someone else's tokens requires a two-transaction dance: the holder calls `approve(spender, amount)` on the token, then the spender calls `transferFrom`; the token contract, not the dapp, is the source of truth. | requires: [erc20-is-a-ledger] | contrasts: [erc2612-permit]
- erc20-approve-race — Changing a non-zero allowance to another non-zero value is front-runnable: the spender can watch the mempool, spend the old allowance first, then spend the new one, extracting old+new. | requires: [erc20-allowance-model] | contrasts: [erc20-approve-race-mitigations]
- erc20-approve-race-mitigations — Mitigations are approve-to-zero-then-set (which USDT *enforces*), `safeIncreaseAllowance`/`safeDecreaseAllowance`, `forceApprove`, or avoiding standing allowances entirely with signature-based approvals. | requires: [erc20-approve-race] | contrasts: [erc2612-permit]
- erc20-approve-race-is-overrated — The race requires the victim to already have granted a non-zero allowance to a spender willing to steal from them; auditors treat it as low severity relative to infinite-approval phishing, which is where users actually lose funds. | requires: [erc20-approve-race] | contrasts: [erc20-approve-race-mitigations]
- erc2612-permit — EIP-2612 `permit` lets a holder sign an EIP-712 allowance off-chain and lets the spender submit it, collapsing approve+transferFrom into one transaction — but only for tokens that implement it, and replay-protected by a per-owner nonce and a domain separator bound to chain id. | requires: [erc20-allowance-model, eip-712] | contrasts: [permit2]
- permit2 — Permit2 is a single canonical contract that adds signature-based, expiring, per-spender allowances on top of *any* ERC-20: the user grants Permit2 one infinite approval, then signs short-lived permits per protocol. | requires: [erc2612-permit] | contrasts: [erc2612-permit]
- erc20-missing-return — The ERC-20 ABI says `transfer` returns `bool`, but major tokens (USDT, BNB, OMG) return nothing; a Solidity call declared to return `bool` reverts on the empty returndata, so naive integrations simply do not work with those tokens. | requires: [erc20-is-a-ledger, abi-decoding] | contrasts: [safe-erc20]
- safe-erc20 — `SafeERC20` wraps the calls in low-level `call` and treats "no returndata plus code at the address" as success, and reverts on `false`; using it is the difference between supporting USDT and not. | requires: [erc20-missing-return] | contrasts: [erc20-missing-return]
- fee-on-transfer-tokens — Some tokens burn or tax a percentage on transfer, so the amount received is less than the amount sent; any contract that credits the *requested* amount rather than the *measured* delta becomes insolvent one deposit at a time. | requires: [erc20-is-a-ledger] | contrasts: [balance-delta-pattern]
- balance-delta-pattern — The fix for fee-on-transfer is to record `balanceOf(address(this))` before and after the transfer and credit the difference; this also silently handles tokens with transfer hooks. | requires: [fee-on-transfer-tokens] | contrasts: [rebasing-tokens]
- rebasing-tokens — Rebasing tokens (stETH, AMPL-style) change every holder's balance without any transfer event, so a contract that stored "user deposited 100" is wrong the next day; the fix is to store shares, not amounts, or to use the wrapped non-rebasing version (wstETH). | requires: [erc20-is-a-ledger] | contrasts: [balance-delta-pattern]
- weird-erc20-taxonomy — "ERC-20 compliant" is a spectrum: missing returns, fee-on-transfer, rebasing, blocklists, pausable transfers, upgradeable implementations, non-18 decimals, zero-value transfer reverts, and multiple entry points to one balance (proxied tokens) each break a different integration assumption. | requires: [erc20-missing-return, fee-on-transfer-tokens, rebasing-tokens] | contrasts: [safe-erc20]
- erc721-ownership — ERC-721 tracks a unique `tokenId -> owner` mapping plus per-token and per-operator approvals, so ownership is per-item and approvals come in three flavours: single-token, `setApprovalForAll`, and (in practice) marketplace operator contracts. | requires: [erc20-is-a-ledger] | contrasts: [erc1155-semantics]
- erc721-safe-transfer-callback — `safeTransferFrom` calls `onERC721Received` on a recipient *contract* and requires the magic selector back; the purpose is to stop tokens being stranded in contracts that cannot move them. | requires: [erc721-ownership] | contrasts: [erc721-callback-reentrancy]
- erc721-callback-reentrancy — That callback hands arbitrary code execution to the recipient in the middle of your mint or transfer, so `_safeMint` before updating `minted[msg.sender]` lets an attacker recurse and mint past the per-wallet cap; this is the single most common NFT exploit. | requires: [erc721-safe-transfer-callback, cei-order] | contrasts: [erc721-safe-transfer-callback]
- erc1155-semantics — ERC-1155 puts many token ids in one contract with `balanceOf(account, id)`, so it expresses fungible, semi-fungible, and non-fungible in one interface and one deployment. | requires: [erc721-ownership] | contrasts: [erc6909]
- erc1155-batch-atomicity — `safeBatchTransferFrom(from, to, ids[], amounts[], data)` is all-or-nothing: array lengths must match, the whole call reverts if any single transfer fails, and it emits one `TransferBatch` rather than N `TransferSingle` events — indexers that only handle `TransferSingle` silently miss batch activity. | requires: [erc1155-semantics] | contrasts: [erc1155-callback]
- erc1155-callback — ERC-1155 has the same receiver-hook hazard as ERC-721, with two hooks (`onERC1155Received`, `onERC1155BatchReceived`) and an operator-approval model that is all-ids-or-nothing. | requires: [erc1155-semantics, erc721-callback-reentrancy] | contrasts: [erc6909]
- erc6909 — ERC-6909 is a stripped-down multi-token interface: no receiver callbacks, no mandatory batching, and per-(id, spender) allowances plus a global operator flag; Uniswap v4 uses it as its internal claim-token layer. | requires: [erc1155-semantics] | contrasts: [erc1155-callback]
- token-callbacks-are-the-vector — Every "safety" callback in the token standards (ERC-777 `tokensToSend`, ERC-721 `onERC721Received`, ERC-1155 receivers) is an attacker-controlled code-execution point inside your transaction; the historical Uniswap-v1/imBTC and Lendf.me losses came from exactly this. | requires: [erc721-callback-reentrancy, erc1155-callback] | contrasts: [erc6909]

### Current state (Aug 2026)
- OpenZeppelin 5.x **removed `increaseAllowance` / `decreaseAllowance` from `ERC20` itself.** They were never in the standard, they encouraged a false sense of safety, and they broke tokens that follow USDT's approve-from-zero rule. The equivalents survive only in `SafeERC20` as `safeIncreaseAllowance` / `safeDecreaseAllowance`, and `forceApprove` was added for USDT-shaped tokens. Any tutorial telling learners to call `token.increaseAllowance(...)` is now wrong against current OZ.
- The practical approval story in 2026 is signature-based: EIP-2612 `permit` where the token supports it, Permit2 where it does not. Standing infinite approvals are the dominant real-world user-loss vector (phishing signatures), which is a different problem from the classic approve race.
- ERC-6909 has real production weight because Uniswap v4 went live on mainnet 30 Jan 2026 and has overtaken v3 as the default deployment target — but the EIP is still **Draft**, not Final. Teach it as "the standard the biggest AMM ships", not "the successor to ERC-1155".
- ERC-777 is effectively dead as a design; its send-hooks caused the Uniswap-v1/imBTC and Lendf.me incidents and it is the canonical example of "callbacks in a fungible token were a mistake". ERC-1363 (`transferAndCall`) exists as the opt-in alternative.
- EIP-7702 interacts here too: a token contract's `isContract`-style check, or a receiver-hook decision based on `code.length == 0`, now behaves differently for delegated EOAs. Airdrop and claim contracts that branch on "EOA vs contract" need review.
- ERC-721A-style batch-mint optimisations remain common for NFT drops but shift cost from mint to first transfer; that trade is a design decision, not a free win.

### Misconceptions
- Belief: `approve` then `transferFrom` is the token moving itself. | Reality: the token contract only edits its own mappings; the "approval" is a number in the token's storage that the spender later spends. | Why: wallet UIs say "give permission to access your tokens", which sounds like file permissions. | Source: https://eips.ethereum.org/EIPS/eip-20
- Belief: use `increaseAllowance` to avoid the approve race — it's the OpenZeppelin way. | Reality: OZ removed it from `ERC20` in 5.0; it is non-standard and most tokens on chain do not have it. | Why: it was the OZ 4.x recommendation for years. | Source: https://docs.openzeppelin.com/contracts/5.x/changelog
- Belief: `IERC20(token).transfer(...)` works for every ERC-20. | Reality: USDT and others return no data, so the ABI decode reverts; you need `SafeERC20`. | Why: the interface file compiles, so the bug only shows up on mainnet with a specific token. | Source: https://github.com/d-xo/weird-erc20
- Belief: after `transferFrom(user, address(this), amount)` succeeds, the contract received `amount`. | Reality: fee-on-transfer tokens deliver less; you must measure the balance delta. | Why: the boolean return says "success", not "how much". | Source: https://github.com/d-xo/weird-erc20
- Belief: a user's stETH balance only changes when they transfer. | Reality: rebasing tokens change balances with no transfer and no `Transfer` event, so stored amounts and event-derived indexes both drift. | Why: every other token teaches balance-changes-imply-events. | Source: https://eips.ethereum.org/EIPS/eip-20
- Belief: `safeTransferFrom` is the safe version, so prefer it. | Reality: it is safe for the *recipient* (it prevents stranding) and dangerous for the *sender's contract* (it yields execution to the recipient); it must be the last thing you do, behind CEI and a guard. | Why: the word "safe" is in the name. | Source: https://ackee.xyz/blog/reentrancy-attack-in-erc-721/
- Belief: an NFT mint cap enforced by a `require(minted[msg.sender] < CAP)` before `_safeMint` is enforced. | Reality: if the counter is written after the mint, the receiver's callback re-enters and mints again with the counter still stale. | Why: the check *is* first — the effect isn't. | Source: https://blocksecteam.medium.com/when-safemint-becomes-unsafe-lessons-from-the-hypebears-security-incident-2965209bda2a
- Belief: ERC-1155 batch transfers can partially succeed. | Reality: the whole call reverts if any leg fails; arrays must be equal length. | Why: "batch" suggests independent items in most non-blockchain APIs. | Source: https://eips.ethereum.org/EIPS/eip-1155
- Belief: an indexer that handles `TransferSingle` covers ERC-1155. | Reality: batch transfers emit only `TransferBatch`, so single-event indexers silently lose data. | Why: the single-transfer path is what tutorials demo. | Source: https://eips.ethereum.org/EIPS/eip-1155
- Belief: ERC-6909 is a finalized replacement for ERC-1155. | Reality: it is still a Draft EIP; its weight comes from Uniswap v4 shipping it, not from standardization. | Why: production usage reads as endorsement. | Source: https://eips.ethereum.org/EIPS/eip-6909

### Practice ideas
- kind: break — On a mainnet fork in Foundry, write a vault that does `IERC20(usdt).transfer(...)` with the standard `IERC20` interface and deposit USDT into it. | Acceptance: the call reverts; swapping in `SafeERC20.safeTransfer` makes the identical test pass.
- kind: break — Implement a fee-on-transfer mock (2% burn) from `weird-erc20`, deposit into a vault that credits the requested amount, and have three users deposit and withdraw in sequence. | Acceptance: the last withdrawal reverts for insufficient balance; the balance-delta version does not.
- kind: break — Write an NFT with a per-wallet cap that calls `_safeMint` before incrementing the counter, plus an attacker contract whose `onERC721Received` re-enters `mint`. | Acceptance: the attacker holds more than the cap; reordering to CEI (or adding `nonReentrant`) reduces it to exactly the cap.
- kind: implement — Write a rebasing mock and a share-based vault (ERC-4626-shaped). | Acceptance: after a +10% rebase, every depositor's redeemable amount grows proportionally and no depositor can withdraw another's gain.
- kind: fix — Take a naive `Distributor` that emits/handles only `TransferSingle` and extend it to `TransferBatch`. | Acceptance: an off-chain script (viem `parseEventLogs`) reconstructs correct balances after a mixed sequence of single and batch transfers.
- kind: implement — Build the approve-race demo end to end: victim approves 100, then submits approve(50); attacker front-runs with `transferFrom(100)` then follows with `transferFrom(50)`. | Acceptance: attacker nets 150; then show approve-to-zero and `forceApprove` each preventing it, and write one paragraph on why auditors still rate this low severity.
- kind: read — Read `SafeERC20.sol` line by line and write down exactly how it distinguishes "returned nothing" from "returned false" from "address has no code". | Acceptance: a three-line explanation naming `returndatasize`, the `bool` decode, and the code-length check.
- kind: measure — Deploy comparable ERC-1155 and ERC-6909 implementations and measure deploy cost, single transfer, and transfer-to-a-contract. | Acceptance: a gas table showing where the receiver-hook check costs ERC-1155, with your own numbers.
- kind: write — Given a list of ten real mainnet tokens (USDT, USDC, stETH, DAI, BNB, PAXG, cUSDCv3, AMPL, TUSD, WETH), classify each against the weird-erc20 taxonomy. | Acceptance: each classification cites the on-chain source or a spec, not a blog post.

## 04.9 — OpenZeppelin: the de facto standard library

### Concepts
- oz-is-the-stdlib — Solidity ships no standard library, so OpenZeppelin Contracts fills that role by convention: it is the most-audited, most-deployed, most-forked Solidity code and reading it is how most engineers learn idiomatic patterns. | requires: [solidity-inheritance] | contrasts: [oz-not-a-framework]
- oz-not-a-framework — OZ Contracts is a library of base contracts and libraries you inherit and compose, not a framework that runs your contract; it makes no deployment, upgrade, or governance decisions for you. | requires: [oz-is-the-stdlib] | contrasts: [oz-nonprovision]
- oz-v5-line — The current line is 5.x; **5.7.0 shipped 2026-07-29**, following 5.6.x (Feb 2026), 5.5.0 (Oct 2025), 5.4.0 (Jul 2025), 5.3.0 (Apr 2025), 5.2.0 (Jan 2025). 5.0 (Oct 2023) was the last breaking major. | requires: [oz-is-the-stdlib] | contrasts: [oz-v4-differences]
- oz-v4-differences — Migrating 4.x to 5.x is not mechanical: `require` strings became custom errors, `Ownable` takes `initialOwner`, ERC-20 hooks collapsed into `_update`, `Counters` and `increaseAllowance`/`decreaseAllowance` were deleted, and upgradeable storage moved from gaps to namespaces. | requires: [oz-v5-line] | contrasts: [oz-v5-line]
- oz-safe-defaults — The contracts treated as safe defaults are the ones that are simple, widely deployed, and hard to misuse: `ERC20`, `ERC721`, `ERC1155`, `Ownable`/`Ownable2Step`, `AccessControl`, `Pausable`, `ReentrancyGuard(Transient)`, `SafeERC20`, `Clones`, `MerkleProof`, `ECDSA`/`EIP712`, `SafeCast`, `Address`. | requires: [oz-is-the-stdlib] | contrasts: [oz-draft-contracts]
- oz-draft-contracts — Files under `contracts/mocks`, anything with a `draft-` prefix, and anything tracking an EIP that is not Final carry a weaker stability and audit promise; the `draft-` prefix is removed only when the underlying EIP finalizes. | requires: [oz-safe-defaults] | contrasts: [oz-safe-defaults]
- oz-custom-errors — 5.x replaced revert strings with typed custom errors (`OwnableUnauthorizedAccount`, `ERC20InsufficientBalance`, `EnforcedPause`), which are cheaper to deploy and give clients a decodable selector instead of a string to regex. | requires: [oz-v4-differences] | contrasts: [oz-v5-line]
- oz-upgradeable-package — `@openzeppelin/contracts-upgradeable` is not a separate codebase: it is machine-transpiled from the main package, replacing constructors with `__Contract_init` initializers. You must use both packages together and at the same version. | requires: [oz-v5-line, proxy-upgradeable] | contrasts: [oz-namespaced-storage]
- oz-namespaced-storage — Since 5.0 the upgradeable variants use ERC-7201 namespaced storage: each contract's state lives in a struct at a hashed slot annotated `@custom:storage-location erc7201:<id>`, instead of the old `uint256[50] __gap` reservation. | requires: [oz-upgradeable-package] | contrasts: [oz-storage-gaps]
- oz-storage-gaps — The pre-5.0 approach reserved trailing slots with `__gap` arrays so new variables could be added without shifting children; it worked but broke the moment anyone miscounted, and it made 4.x-to-5.x upgrades of *live* proxies storage-incompatible. | requires: [oz-namespaced-storage] | contrasts: [oz-namespaced-storage]
- oz-upgrade-unsafe-across-majors — Upgrading a deployed proxy from OZ 4.x implementations to 5.x implementations is unsafe by default because the storage layout changed from gaps to namespaces; this is a data-corruption class of bug, not a compile error. | requires: [oz-storage-gaps, oz-namespaced-storage] | contrasts: [oz-upgradeable-package]
- oz-upgrades-plugins — The `@openzeppelin/upgrades-core` Hardhat/Foundry plugins are the enforcement layer: they diff storage layouts between versions and refuse an upgrade that would corrupt state, and they flag constructors, `selfdestruct`, `delegatecall`, and immutable variables in implementations. | requires: [oz-upgradeable-package] | contrasts: [oz-namespaced-storage]
- oz-stateless-not-transpiled — From 5.5.0, contracts with no storage (`ReentrancyGuard`, `ReentrancyGuardTransient`, `ERC721Holder`, `ERC1155Holder`, and since then `Initializable` and `UUPSUpgradeable`) are no longer transpiled; import them from the *main* package even in upgradeable projects. | requires: [oz-upgradeable-package] | contrasts: [oz-upgradeable-package]
- oz-account-abstraction-modules — 5.4-5.5 added a first-party account-abstraction stack: `Account`, `AccountERC7579`, `SignerECDSA`/`SignerP256`/`SignerRSA`/`SignerWebAuthn`, ERC-7913 multi-signer verification, and (in 5.7) paymasters — OZ now competes with bespoke ERC-4337 stacks. | requires: [oz-v5-line, erc-4337] | contrasts: [oz-nonprovision]
- oz-crosschain-modules — 5.6-5.7 added crosschain primitives: ERC-7786 messaging gateway interfaces, ERC-20/721/1155 bridge contracts, `CrosschainLinked`, `GovernorCrosschain`, ERC-7930 interoperable addresses, and a `TrieProof` library. | requires: [oz-v5-line] | contrasts: [oz-nonprovision]
- oz-nonprovision — OZ deliberately does not provide: a DEX/AMM, oracles or price feeds, a stablecoin, keepers/automation, off-chain infrastructure, opinionated deployment scripts, or a testing framework; and it does not decide your access-control policy, your pause authority, or your upgrade governance. | requires: [oz-not-a-framework] | contrasts: [oz-account-abstraction-modules]
- oz-audit-is-not-your-audit — OZ's code being audited says nothing about *your composition* of it; the overwhelming majority of exploits in OZ-based systems are in the application logic and in how privileges were assigned, not in the library. | requires: [oz-is-the-stdlib, access-control-is-top-loss] | contrasts: [oz-safe-defaults]
- oz-wizard — The Contracts Wizard generates a compiling starting point from checkboxes (token type, mintable, pausable, votes, upgradeable) and is the fastest way to see idiomatic composition — but it generates *scaffolding*, and every privileged role it emits is a decision you still have to make. | requires: [oz-safe-defaults] | contrasts: [oz-audit-is-not-your-audit]

### Current state (Aug 2026)
- **Pin: OpenZeppelin Contracts 5.7.0, released 2026-07-29.** Release cadence in the 5.x line has been roughly quarterly: 5.2.0 (2025-01-08), 5.3.0 (2025-04-09), 5.4.0 (2025-07-17), 5.5.0 (2025-10-31), 5.6.0 (2026-02-25), 5.6.1 (2026-02-27), 5.7.0 (2026-07-29). There has been **no 6.0**; 5.0 (Oct 2023) remains the last breaking major.
- What actually changed in the last 18 months, by release:
  - **5.3.0 (Apr 2025)** — first-party `ERC6909` implementation with metadata/URI extensions; several Governor extensions (`GovernorCountingOverridable`, `GovernorProposalGuardian`, `GovernorSuperQuorum`, `GovernorSequentialProposalId`); updatable `MerkleTree`.
  - **5.4.0 (Jul 2025)** — `Account` / `AccountERC7579` (ERC-4337), `SignerERC7913` / `MultiSignerERC7913`, `ERC20Bridgeable` (ERC-7802), and **`Clones.cloneWithImmutableArgs`**.
  - **5.5.0 (Oct 2025)** — WebAuthn/passkey signers (`SignerWebAuthn`, P256 fallback), ERC-7913, `Memory` and Base58 libraries, ERC-7930 interoperable addresses, `ERC7786Recipient`. Minimum pragma raised to **0.8.24** for many contracts. `ERC6909` lost its `draft-` prefix (import paths changed). `SignerERC7702` renamed `SignerEIP7702`. Stateless contracts stopped being transpiled.
  - **5.6.0 (Feb 2026)** — crosschain bridges for ERC-20, `CrosschainLinked`, `ERC20Crosschain`, `TrieProof`, richer `ERC4337Utils`. Breaking: **`ERC1967Proxy` now reverts with `ERC1967ProxyUninitialized` if deployed without an initializer**; a single-item ERC-1155 batch transfer now calls `onERC1155BatchReceived` instead of `onERC1155Received`; `Strings.escapeJSON` escapes all control chars.
  - **5.7.0 (Jul 2026)** — `Create3`, `BlockHeader`, `SimulateCall`, a `RateLimiter` library (token bucket + sliding window), ERC-721/1155 crosschain bridges, `GovernorCrosschain`, and paymaster implementations (ERC-20 payment, NFT-sponsored). Breaking: EIP-712 dropped the storage fallback so name/version **must fit in 31 bytes**; `ERC2771ForwarderFailureInAtomicBatch` renamed to `ERC2771ForwarderNoRefundReceiver`; Governor queueing errors restructured. ECDSA signature-malleability protection was partly deprecated in the 5.5 timeframe.
- The 5.x direction of travel is unmistakable: OZ has moved from "token + access control + proxies" into **account abstraction** and **crosschain messaging**. Both are areas where it previously provided nothing.
- Commonly taught and now wrong: `import "@openzeppelin/contracts-upgradeable/proxy/utils/Initializable.sol"` and the upgradeable `ReentrancyGuardUpgradeable`. Since 5.5 these are aliases or gone — import from the main package.
- Commonly taught and now wrong: "add `uint256[50] private __gap;` to your upgradeable contract". That is the 4.x idiom; 5.x uses ERC-7201 namespaces, and mixing the two on one live proxy is how you corrupt state.
- Solidity pragma floor matters now: much of 5.5+ requires **0.8.24 or later** (transient storage, MCOPY-era features). Against current Solidity 0.8.36 this is not a constraint, but it does break projects pinned to older compilers.

### Misconceptions
- Belief: OpenZeppelin is audited, so a contract built on it is safe. | Reality: the library is audited in isolation; your composition, your privileged roles, and your business logic are not, and that is where nearly all losses occur. | Why: the audit badge transfers emotionally but not technically. | Source: https://arxiv.org/pdf/2507.20175
- Belief: `contracts-upgradeable` is a hand-maintained alternate library. | Reality: it is transpiled from the main package; the two must be used at the same version, and stateless contracts are no longer transpiled at all. | Why: two npm packages look like two projects. | Source: https://docs.openzeppelin.com/contracts/5.x/upgradeable
- Belief: you can bump a deployed proxy's implementation from OZ 4.x to 5.x. | Reality: the storage model changed from `__gap` reservations to ERC-7201 namespaces, so the layouts are incompatible and the upgrade silently corrupts state. | Why: it compiles, and semver "4 to 5" reads like a routine dependency bump. | Source: https://medium.com/51nodes/why-upgrading-openzeppelin-smart-contracts-from-version-4-to-version-5-is-unsafe-e08be30efd8a
- Belief: storage gaps are still the recommended upgradeable pattern. | Reality: ERC-7201 namespaced storage replaced them in 5.0 and removes the whole class of gap-miscount bugs. | Why: gaps dominated tutorials for five years. | Source: https://github.com/OpenZeppelin/openzeppelin-contracts/pull/4534
- Belief: everything in the repo carries the same guarantee. | Reality: `draft-` prefixed files track non-Final EIPs and can change; `mocks/` is test scaffolding and must never ship. | Why: it is all one npm package. | Source: https://github.com/OpenZeppelin/openzeppelin-contracts/releases
- Belief: OZ provides an oracle / price feed / AMM you can inherit. | Reality: it deliberately does not; those require off-chain infrastructure or market design, which a library cannot supply. Chainlink, Pyth, Uniswap are separate. | Why: OZ covers so much that people assume it covers everything. | Source: https://docs.openzeppelin.com/contracts/5.x/
- Belief: OZ has nothing for account abstraction, so you need a bespoke ERC-4337 stack. | Reality: since 5.4/5.5 it ships `Account`, `AccountERC7579`, multiple signer modules including WebAuthn/passkeys, and paymasters as of 5.7. | Why: this is genuinely new and post-dates most tutorials. | Source: https://raw.githubusercontent.com/OpenZeppelin/openzeppelin-contracts/master/CHANGELOG.md
- Belief: `require(cond, "Not owner")` is the OZ style. | Reality: 5.x is custom errors throughout; string reverts are the 4.x style and cost more deploy gas. | Why: the string form is what every older tutorial shows. | Source: https://www.openzeppelin.com/news/introducing-openzeppelin-contracts-5.0

## 04.10 — Vyper: what a language leaves out on purpose

### Concepts
- vyper-design-goal — Vyper optimizes for the *reader* — specifically a human auditor — not for the writer; every feature that makes control flow harder to follow by reading top to bottom is a candidate for removal. | requires: [solidity-basics] | contrasts: [solidity-expressiveness]
- vyper-python-syntax — Vyper is Pythonic in syntax and is implemented in Python, but it is not Python: no classes, no runtime, no dynamic typing, and it compiles to EVM bytecode with the same ABI as Solidity, so Vyper and Solidity contracts interoperate freely. | requires: [vyper-design-goal] | contrasts: [vyper-omissions]
- vyper-no-inheritance — Vyper has no contract inheritance, so there is no C3 linearization and no "which `super` runs first" question; a function's body is the whole story. Since 0.4.0 code reuse is done with an explicit **module** system (`import`, `initializes:`, `uses:`, `exports:`). | requires: [vyper-design-goal] | contrasts: [solidity-inheritance]
- vyper-no-modifiers — Vyper has no Solidity-style function modifiers, because a modifier can inject arbitrary code — including state changes — at a call site that shows only a keyword; the guard has to be written inline where you can see it. | requires: [vyper-design-goal] | contrasts: [solidity-modifiers]
- vyper-no-inline-assembly — There is no inline assembly and no Yul equivalent, so the compiler always knows the full semantics of every instruction it emits and no hand-written opcode can violate the language's invariants. | requires: [vyper-design-goal] | contrasts: [solidity-yul]
- vyper-bounded-loops — Every loop must have a compile-time bound (`for i: uint256 in range(n, bound=MAX)`), and there is no recursion and no unbounded dynamic array, which together give every function a static upper bound on gas. | requires: [vyper-design-goal] | contrasts: [push-payment-dos]
- vyper-bounded-types — Dynamic types carry their maximum size in the type: `DynArray[uint256, 100]`, `String[64]`, `Bytes[1024]`. There is no unbounded `bytes`/`string`/array, which is why gas is boundable and why storage layout is fully known at compile time. | requires: [vyper-bounded-loops] | contrasts: [vyper-bounded-loops]
- vyper-no-overloading — No function overloading and no operator overloading: one name means one function, so a selector clash or a surprising `+` cannot hide in a diff. | requires: [vyper-design-goal] | contrasts: [solidity-expressiveness]
- vyper-explicit-visibility — Decorators are mandatory and explicit: `@external`, `@internal`, `@deploy` (constructor), `@payable`, `@view`, `@pure`, `@nonreentrant`. There is no default that a reader has to remember. | requires: [vyper-python-syntax] | contrasts: [vyper-no-modifiers]
- vyper-safety-by-default — Overflow/underflow checks, array bounds checks, and division-by-zero checks are always on, with explicit `unsafe_add`/`unsafe_sub`/`unsafe_mul`/`unsafe_div` builtins as the escape hatch — the opposite of Solidity's `unchecked` block only in that the unsafe path is named at each call site. | requires: [vyper-design-goal] | contrasts: [solidity-unchecked]
- vyper-compiler-was-the-bug — In July 2023 Vyper 0.2.15/0.2.16/0.3.0 mis-assigned storage slots for `@nonreentrant` locks, so different functions got different lock slots and the guard could be bypassed cross-function; correct source code compiled to vulnerable bytecode and several Curve pools were drained. | requires: [vyper-explicit-visibility, reentrancy-guard] | contrasts: [vyper-safety-by-default]
- compiler-is-part-of-tcb — That incident is the general lesson, not a Vyper lesson: the compiler is inside your trusted computing base, so the compiler version is a security-relevant deployment parameter and must be pinned, recorded, and cross-checked against known-bad ranges. | requires: [vyper-compiler-was-the-bug] | contrasts: [oz-audit-is-not-your-audit]
- vyper-audit-policy — Vyper's stated policy is that major (x.0.0) releases get an external audit before release and reported moderate/severe findings are addressed; point releases do not carry that guarantee, which is why version choice is a risk decision. | requires: [compiler-is-part-of-tcb] | contrasts: [vyper-compiler-was-the-bug]
- venom-backend — Venom is Vyper's newer SSA-based IR and optimizer pipeline, progressively replacing the old codegen; 0.4.x releases are largely about maturing it, and 0.5.0 alphas compile direct-to-Venom. | requires: [vyper-design-goal] | contrasts: [vyper-python-syntax]
- vyper-transferable-lessons — Reading Vyper teaches a Solidity developer three things concretely: how much control flow inheritance and modifiers hide, that unbounded loops are a liveness bug not a gas optimization, and that "the compiler is correct" is an assumption, not a fact. | requires: [vyper-no-inheritance, vyper-no-modifiers, vyper-bounded-loops, compiler-is-part-of-tcb] | contrasts: [vyper-design-goal]
- vyper-ecosystem-cost — The omissions have a real price: a far smaller library ecosystem (no OpenZeppelin equivalent), fewer auditors, fewer tools, and patterns like proxies and generic factories needing dedicated builtins (`raw_create()` in 0.4.2, `@raw_return` in 0.4.3) rather than assembly. | requires: [vyper-no-inline-assembly] | contrasts: [oz-is-the-stdlib]

### Current state (Aug 2026)
- **Latest published stable per PyPI on 2026-08-25 is 0.4.3 ("Buttermilk Racer"), released 2025-06-18.** A 0.5.0 alpha line has existed since May 2025 (0.5.0a1 2025-05-07, a2 2025-05-29, a3 2025-06-14) but I found no evidence of a stable 0.5.0. See gaps — this is a long stable gap and worth re-verifying.
- The 0.4.x line's headline items: 0.4.0 (2024-06-20) was the breaking major that introduced the **module system** (`import` / `initializes:` / `uses:` / `exports:`), `@deploy` for constructors, and `flag` in place of `enum`. 0.4.1 was a polish/bugfix release with heavy Venom work. 0.4.2 (2025-05-31) added **`raw_create()`** for generic factories and moved `sqrt()` into pure Vyper. 0.4.3 (2025-06-18) added **`@raw_return`** (return raw bytes with no ABI encoding, enabling proxy patterns) and set the default EVM version to **prague**.
- The 0.5.0 alphas advertise **custom errors**, a direct-to-Venom pipeline, stack spilling, and unbounded types — note that "unbounded types" would be a meaningful softening of one of Vyper's signature constraints, so do not teach the bounded-types rule as absolute for 0.5.x without checking.
- Ecosystem context: 0.4.3's default EVM target is `prague`, which pre-dates Fusaka (Dec 2025). Against a 2026 mainnet you should set the EVM version explicitly rather than relying on the default.
- Commonly taught and now wrong: `@nonreentrant("my_lock")` with a named key. Since 0.4.0 the lock is unnamed — a single global reentrancy lock per contract — which is a direct simplification response to the 2023 bug class. Verify the exact syntax against 0.4.x docs before writing lesson code.
- Commonly taught and now wrong: "Vyper has no way to write a factory or a proxy without leaving the language". `raw_create()` (0.4.2) and `@raw_return` (0.4.3) exist specifically to close that gap.
- Vyper's real-world footprint remains concentrated: Curve is the flagship, plus a set of DeFi protocols around it. It is a minority language by deployment count and by auditor supply, and that is a legitimate input to a "should we use it" decision.

### Misconceptions
- Belief: Vyper is safer than Solidity. | Reality: Vyper narrows the space of *source-level* mistakes; it does not make the toolchain safer, and its worst incident was caused by the compiler itself producing wrong bytecode from correct source. | Why: "fewer features" is conflated with "fewer bugs". | Source: https://hackmd.io/@vyperlang/HJUgNMhs2
- Belief: Vyper is Python, so I already know it. | Reality: no classes, no inheritance, no recursion, no dynamic typing, no unbounded collections, and everything is bounded at compile time; the syntax is familiar and the semantics are not. | Why: indentation and decorators look identical. | Source: https://docs.vyperlang.org/en/stable/
- Belief: no inheritance means no code reuse. | Reality: 0.4.0 added a module system with explicit `initializes:` / `uses:` / `exports:` declarations — reuse without an implicit method-resolution order. | Why: OOP conflates reuse with inheritance. | Source: https://docs.vyperlang.org/en/stable/release-notes.html
- Belief: bounded loops are just a gas optimization. | Reality: they are a liveness guarantee — an unbounded loop can make a function permanently uncallable once the collection grows, and since EIP-7825 a single L1 transaction is also hard-capped at ~16.78M gas. | Why: gas is taught as cost, not as a correctness constraint. | Source: https://docs.vyperlang.org/en/stable/
- Belief: the Curve exploit was a Curve bug. | Reality: Curve's Vyper source was correct; three specific compiler versions emitted a broken reentrancy guard. | Why: incidents get named after the protocol that lost money. | Source: https://blocksec.com/blog/curve-incident-compiler-error-produces-faulty-bytecode-from-innocent-source-code
- Belief: pinning a compiler version is a reproducibility nicety. | Reality: it is a security control; the affected Vyper range (0.2.15, 0.2.16, 0.3.0) is exactly the kind of thing a version pin plus an advisory check catches. | Why: in web development, compiler versions rarely have security semantics. | Source: https://hackmd.io/@vyperlang/HJUgNMhs2
- Belief: Vyper contracts cannot call or be called by Solidity contracts. | Reality: both emit standard EVM bytecode with the same ABI encoding, so they interoperate with no special handling. | Why: "different language" implies a different platform. | Source: https://docs.vyperlang.org/en/stable/
- Belief: every Vyper release is audited. | Reality: the policy covers major (x.0.0) releases; point releases do not carry that guarantee. | Why: "Vyper is audited" gets repeated without the qualifier. | Source: https://docs.vyperlang.org/en/stable/versioning.html

### Practice ideas
- kind: read — Read a Curve stableswap pool's verified Vyper source alongside a Solidity AMM of similar function. | Acceptance: a written list of every place the Solidity version's behaviour depends on an inherited function or a modifier that you cannot see from the function body, and the Vyper equivalent that is inline.
- kind: implement — Write the same ERC-20 twice: once in Vyper 0.4.3, once in Solidity 0.8.36 with OpenZeppelin. | Acceptance: both deploy to a local Anvil, pass the same Foundry test suite driven through the ABI, and you can state the deployed bytecode size difference.
- kind: break — Install Vyper 0.3.0 in a venv, compile a contract with two `@nonreentrant` functions, and inspect the emitted storage slots for the locks; then compile the same source with 0.4.3. | Acceptance: you can point at the differing slot assignment in the 0.3.0 output and explain why cross-function reentrancy became possible.
- kind: fix — Take a Vyper contract with `for i in range(len(self.recipients))`-shaped intent and rewrite it under the `bound=` requirement, then add pull-payment withdrawal instead. | Acceptance: the contract compiles, and a test proves gas is bounded regardless of how many recipients are registered.
- kind: measure — Compile one non-trivial Vyper contract with and without the Venom pipeline (where the version exposes the flag) and compare bytecode size and runtime gas on identical calls. | Acceptance: a small table with your own numbers, plus a note on which version's flags you used.
- kind: implement — Use `raw_create()` (0.4.2+) to build a clone/factory in Vyper, and `@raw_return` (0.4.3+) for a forwarding contract. | Acceptance: the factory deploys instances at predictable addresses and the forwarder returns raw bytes that a Solidity caller decodes correctly.
- kind: write — Produce a compiler-risk checklist for a deployment: which compiler and version, where it is pinned, which advisories were checked, whether the deployed bytecode was reproduced from source independently. | Acceptance: every row cites where the answer lives in the repo (lockfile, foundry.toml/vyper config, CI job).
- kind: read — Read the Vyper post-mortem and write a three-paragraph incident summary a non-engineer PM could act on. | Acceptance: it names the mechanism (per-function lock slots), the affected version range, and the process change (pin + advisory monitoring) without naming a loss figure you cannot source.

### Gaps & uncertainties
- **Version confidence is moderate, not high.** PyPI `info.version` read 0.4.3 on 2026-08-25 and search agrees, but a 14-month gap since the last stable while 0.5.0 alphas sat open is unusual. A 0.5.0 or 0.4.4 may have shipped and not be reflected in what I could fetch. Re-verify against https://pypi.org/project/vyper/ and the GitHub releases page before pinning in a lesson.
- **Loss figures for the July 2023 Curve/Vyper incident conflict badly across sources**: $52M (MetaTrust), ~$61M, ~$70M (several), ~$73M elsewhere, and a large fraction was later returned by white-hats and one attacker. Do NOT publish a single number. State the mechanism and say the total is disputed.
- I did not verify the exact `@nonreentrant` syntax in 0.4.x (unnamed global lock vs named keys). I am fairly confident 0.4.0 removed named keys, but confirm against the docs before writing lesson code.
- I did not confirm which firms audited which Vyper releases (ChainSecurity, OpenZeppelin, Statemind have all been associated with Vyper or Curve work at various times). Do not attribute an audit without a report link.
- The 0.5.0a "unbounded types" feature was surfaced in a release summary and not investigated. If it means what it sounds like, it materially changes the "everything is bounded" teaching point. Verify before writing.
- Whether Venom is the default pipeline in 0.4.3 or still opt-in behind a flag was not confirmed.
- I did not verify current Vyper adoption numbers (share of deployed contracts, number of protocols). Do not publish an adoption percentage.
- Vyper's default EVM version being `prague` in 0.4.3 is from a release-notes summary, not read directly from the docs; confirm before telling learners to override it.
