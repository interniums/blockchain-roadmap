## 07.1 — viem: clients, transports, actions, type inference, typed errors, simulate-before-send

### Concepts
- viem-client-vs-transport — A viem Client is a bundle of actions bound to a chain and an account; a Transport is only the wire protocol that carries JSON-RPC, so the same actions work over HTTP, WebSocket or an injected wallet. | requires: [json-rpc-basics] | contrasts: [ethers-provider-signer]
- viem-public-client — `createPublicClient` exposes read-only actions (`readContract`, `getBalance`, `estimateGas`, `call`, `getLogs`) and never holds a key. | requires: [viem-client-vs-transport] | contrasts: [viem-wallet-client]
- viem-wallet-client — `createWalletClient` exposes signing and sending actions and is backed either by a local account (private key in process) or a JSON-RPC account (the wallet holds the key and viem only asks). | requires: [viem-client-vs-transport] | contrasts: [viem-public-client]
- viem-account-kinds — A Local Account signs in your runtime and viem submits raw bytes; a JSON-RPC Account delegates signing to the wallet via `eth_sendTransaction`, so viem cannot see or pre-compute the signature. | requires: [viem-wallet-client] | contrasts: [viem-public-client]
- viem-transport-fallback — `fallback([http(a), http(b)])` ranks and fails over between RPC endpoints; `http()` also batches eligible requests into a single JSON-RPC array by default. | requires: [viem-client-vs-transport] | contrasts: [single-rpc-endpoint]
- viem-actions-are-functions — Every action is a standalone tree-shakable function; clients are thin, and `client.extend()` grafts extra action sets (public/wallet/test) onto one client. | requires: [viem-client-vs-transport] | contrasts: [monolithic-provider-object]
- viem-abi-const-inference — Typing comes from the ABI value itself: an ABI declared `as const` (or generated by wagmi CLI) lets TypeScript infer valid function names, argument tuples and return types with no codegen step. | requires: [abi-encoding] | contrasts: [typechain-codegen]
- viem-bigint-boundary — All EVM integers cross into JS as `bigint`, never `number`; `parseEther`/`parseUnits`/`formatUnits` are the only sanctioned conversions and float math on token amounts is always a bug. | requires: [evm-uint256] | contrasts: [js-number-precision]
- viem-simulate-before-send — `simulateContract` runs the call as `eth_call` against pending state, returns `{ result, request }`, and `request` is handed straight to `writeContract`; failures surface as a thrown error before the user is asked to sign. | requires: [viem-public-client, eth-call] | contrasts: [viem-write-without-simulate]
- viem-simulation-is-not-a-guarantee — Simulation runs against one node's view of pending state at one moment; between simulation and inclusion the state can change, so a successful simulation lowers but does not remove revert risk. | requires: [viem-simulate-before-send] | contrasts: [viem-simulate-before-send]
- viem-error-hierarchy — Every viem error extends `BaseError` and wraps a `cause` chain; `error.walk(fn)` climbs that chain to find the specific error class instead of string-matching messages. | requires: [viem-actions-are-functions] | contrasts: [string-matching-revert-reasons]
- viem-typed-revert — `ContractFunctionRevertedError` exposes `data.errorName` and `data.args` when the reverting custom error is present in the ABI you passed; if it is absent you only get raw hex. | requires: [viem-error-hierarchy, solidity-custom-errors] | contrasts: [require-string-revert]
- viem-multicall-batching — `multicall` aggregates many `readContract` calls into one Multicall3 call, cutting RPC round-trips; `allowFailure: true` returns per-call status instead of failing the batch. | requires: [viem-public-client] | contrasts: [n-plus-one-rpc-reads]
- viem-sync-send — `sendTransactionSync` / `writeContractSync` use EIP-7966 `eth_sendRawTransactionSync` to block until a receipt, and are only appropriate on fast-block chains, not L1 mainnet. | requires: [viem-wallet-client, tx-lifecycle] | contrasts: [wait-for-transaction-receipt-polling]

### Current state (Aug 2026)
- npm `viem@latest` = **2.55.19**; `viem@next` = **3.0.0-next.10** (checked via `npm view viem` on 2026-08-25). viem 3 is in prerelease, not the default install — teach 2.x, mention 3 exists.
- viem 2.x is still the single default EVM client library; ethers v6 remains widely deployed in older codebases but new tutorials, wagmi, and most SDKs assume viem.
- New in the last ~18 months and commonly missing from older tutorials: `sendTransactionSync`/`writeContractSync` (EIP-7966), EIP-7702 authorization support (`signAuthorization`, `authorizationList` on tx type 0x4), EIP-5792 `sendCalls`/`getCallsStatus` batching, and simulation actions built on `eth_simulateV1`.
- Commonly taught but now wrong: "use ethers Provider/Signer" as the default mental model; "ABIs need TypeChain codegen" (viem infers from a `as const` ABI); "revert reasons are strings" (custom errors dominate post-0.8.4 Solidity); "numbers are `number`" (everything is `bigint`).
- `estimateContractGas` and `simulateContract` are different calls with different failure surfaces — do not treat gas estimation as simulation.

### Misconceptions
- Belief: `writeContract` will fail fast if the contract would revert. | Reality: it just signs and broadcasts; a reverting tx is still mined and still burns gas. | Why: the name reads like an assertion, and ethers' `contract.fn()` estimated gas implicitly, which caught many reverts. | Source: https://viem.sh/docs/contract/writeContract
- Belief: a successful `simulateContract` means the transaction will succeed. | Reality: it only means it would have succeeded against one node's pending state at that instant; MEV, other users' txs, and oracle updates can invalidate it. | Why: "simulate" implies determinism. | Source: https://viem.sh/docs/contract/simulateContract
- Belief: you can read a revert reason from `error.message`. | Reality: the useful data is in the `cause` chain — you must `error.walk(e => e instanceof ContractFunctionRevertedError)` and read `data.errorName`/`data.args`. | Why: most examples log the error. | Source: https://github.com/wevm/viem/discussions/1789
- Belief: viem decodes any custom error it encounters. | Reality: decoding only works if that error's definition is in the ABI you supplied; an error thrown by an inner contract you did not pass an ABI for comes back as undecoded hex. | Why: people assume a global 4-byte registry is consulted. | Source: https://viem.sh/docs/glossary/errors
- Belief: TypeScript inference works from an imported JSON ABI. | Reality: it needs a literal type — `as const` on an inline ABI, or `import abi from './abi.json' with { type: 'json' }` widened away — otherwise you get `string`/`unknown[]` and no autocomplete. | Why: JSON imports are the natural habit. | Source: https://viem.sh/docs/typescript
- Belief: `writeContractSync` is a strictly better `writeContract`. | Reality: it depends on the RPC provider implementing EIP-7966 and is documented as unsuitable for chains with slow finality such as mainnet. | Why: sync APIs feel simpler. | Source: https://viem.sh/docs/contract/writeContractSync

### Practice ideas
- kind: implement — Build a two-client script: a `publicClient` over `http()` reading an ERC-20 `balanceOf` + `decimals` via `multicall`, and a `walletClient` from a local private key on Anvil doing `simulateContract` → `writeContract` → `waitForTransactionReceipt`. | acceptance: the script prints a human-formatted balance before and after, and never calls `writeContract` without a preceding successful simulate.
- kind: break — Deploy a contract with `error InsufficientBalance(uint256 available, uint256 required)`, trigger it, and catch the failure two ways: once passing the full ABI, once passing an ABI with the error stripped. | acceptance: learner can show the first yields `errorName === 'InsufficientBalance'` with typed args and the second yields raw hex, and can explain why.
- kind: fix — Give the learner a file where an ABI is imported from JSON and every `readContract` call has `args: any`. | acceptance: after converting to `as const`, TypeScript rejects a wrong argument count and a wrong argument type at compile time with no runtime change.
- kind: measure — Time 20 sequential `readContract` calls vs one `multicall` against a public RPC. | acceptance: learner reports both wall-clock numbers and the RPC request count, and explains the difference in round-trips rather than in compute.
- kind: read — Read the viem errors glossary and write the `cause`-chain walk for a failing `estimateGas`. | acceptance: learner produces a `mapError()` helper that distinguishes `ContractFunctionRevertedError`, `InsufficientFundsError` and a transport/network error without matching on message strings.

## 07.2 — wagmi: hooks architecture, connectors, query caching, SSR in Next.js, state pitfalls

### Concepts
- wagmi-is-viem-plus-query — wagmi is a thin React layer: viem does the chain I/O, TanStack Query v5 does caching/dedupe/retry, and wagmi supplies connectors, chain switching and a persisted config store. | requires: [viem-client-vs-transport, tanstack-query-basics] | contrasts: [wagmi-as-rpc-library]
- wagmi-config-object — `createConfig({ chains, connectors, transports, storage })` is the single source of truth; `WagmiProvider` puts it in context and everything (including vanilla `@wagmi/core` actions) reads from it. | requires: [wagmi-is-viem-plus-query] | contrasts: [per-component-client]
- wagmi-read-hooks-are-queries — `useReadContract`, `useBalance` etc. return TanStack Query results (`data`, `isPending`, `isFetching`, `error`, `refetch`) and are cached by a structured `queryKey`, so two components asking the same question fire one RPC call. | requires: [wagmi-config-object] | contrasts: [useeffect-fetch-pattern]
- wagmi-write-hooks-are-mutations — `useWriteContract`, `useSendTransaction`, `useSignMessage` are TanStack mutations; in v3 their custom mutate names were normalised to `mutate`/`mutateAsync`. | requires: [wagmi-read-hooks-are-queries] | contrasts: [wagmi-read-hooks-are-queries]
- wagmi-no-auto-invalidation — Chain state changes on its own; wagmi does NOT know when your balance moved. Freshness is your job: `watch: true`, or `useBlockNumber({watch:true})` plus `queryClient.invalidateQueries({ queryKey })` in an effect. | requires: [wagmi-read-hooks-are-queries] | contrasts: [rest-api-cache-invalidation]
- wagmi-querykey-shape — Query keys are produced by exported `get<X>QueryOptions(config, args)`, so you can build the exact key to invalidate from outside React; ad-hoc string keys will silently miss. | requires: [wagmi-no-auto-invalidation] | contrasts: [manual-string-query-keys]
- wagmi-bigint-serialization — BigInt is not JSON-serialisable, so wagmi ships a custom `hashFn` from `@wagmi/core/query` for query-key hashing and DevTools; forgetting it breaks devtools and any naive key stringification. | requires: [viem-bigint-boundary, wagmi-querykey-shape] | contrasts: [json-stringify-query-keys]
- wagmi-connector-abstraction — A Connector is an adapter from a wallet's transport (EIP-1193 provider, WalletConnect relay, Safe app bridge, SDK) to a uniform connect/disconnect/getAccounts/switchChain interface. | requires: [wagmi-config-object] | contrasts: [window-ethereum-directly]
- wagmi-eip6963-discovery — Injected wallets are discovered via EIP-6963 (multi-injected provider discovery) rather than a single `window.ethereum`, which is what makes multiple browser wallets coexist. | requires: [wagmi-connector-abstraction] | contrasts: [window-ethereum-directly]
- wagmi-connection-not-authentication — A connected wallet only proves the wallet told the page an address; proving control requires a signature (SIWE / EIP-4361). | requires: [wagmi-connector-abstraction] | contrasts: [siwe-auth]
- wagmi-ssr-hydration-mismatch — wagmi's connection state lives in `localStorage` and in EIP-6963 discovery, both client-only; server HTML therefore cannot know it, and rendering it directly causes React hydration mismatches. | requires: [nextjs-ssr] | contrasts: [wagmi-cookie-storage]
- wagmi-cookie-storage — Setting `ssr: true` plus `storage: createStorage({ storage: cookieStorage })` lets the server read connection state from the cookie header and pass `cookieToInitialState(config, cookie)` into `WagmiProvider`, removing the disconnected-then-connected flash. | requires: [wagmi-ssr-hydration-mismatch] | contrasts: [wagmi-ssr-hydration-mismatch]
- wagmi-provider-is-client-component — `WagmiProvider` and `QueryClientProvider` must sit in a `"use client"` component; the `QueryClient` must be created per request/per mount, never as a module-level singleton in an SSR app. | requires: [wagmi-cookie-storage] | contrasts: [module-singleton-queryclient]
- wagmi-chain-mismatch — The connected wallet's chain is independent of the chain your hook targets; reads silently hit the wrong chain unless you pass `chainId`, and writes must be gated on `useSwitchChain`. | requires: [wagmi-config-object] | contrasts: [single-chain-assumption]

### Current state (Aug 2026)
- npm `wagmi@latest` = **3.7.6** (checked 2026-08-25). **wagmi v3 is out and shipped a rename that breaks every tutorial written before it.** Correct the shared baseline accordingly.
- v3 breaking changes confirmed from the official migration guide: `useAccount` → `useConnection`, `useAccountEffect` → `useConnectionEffect`, `useSwitchAccount` → `useSwitchConnection`; `.connectors` removed from `useConnect`/`useReconnect`/`useDisconnect`/`useSwitchConnection` (use `useConnectors()` / `useConnections()`); `.chains` removed from `useSwitchChain` (use `useChains()`); custom mutate names normalised to `mutate`/`mutateAsync`.
- v3 made **all connector dependencies optional peer deps** — you now install the wallet SDK yourself: `baseAccount`→`@base-org/account`, `coinbaseWallet`→`@coinbase/wallet-sdk`, `metaMask`→`@metamask/connect-evm`, `safe`→`@safe-global/safe-apps-provider` + `@safe-global/safe-apps-sdk`, `walletConnect`→`@walletconnect/ethereum-provider`. A v2 app that "just worked" will fail at connect time after upgrade.
- wagmi states the v3-and-after policy is additive: new functionality opt-in, old functionality deprecated alongside — so future majors should be less disruptive than v1→v2 and v2→v3.
- Also current: EIP-5792 batching hooks (`useSendCalls`/`useCallsStatus`) with `experimental_fallback` for wallets that do not support it; EIP-7702-aware flows.
- Commonly taught but now wrong: `const { address, isConnected } = useAccount()` (renamed in v3); `useConnect().connectors` (removed); `useContractRead` (v1 name, long gone — it is `useReadContract`); assuming `npm i wagmi` gives you WalletConnect (it does not, in v3).

### Misconceptions
- Belief: wagmi hooks re-render when on-chain state changes. | Reality: they are plain cached queries; without `watch` or explicit invalidation they will happily serve a stale balance forever. | Why: the hook name reads like a subscription. | Source: https://wagmi.sh/react/guides/tanstack-query
- Belief: `isConnected` means the user is authenticated. | Reality: it means a wallet exposed an address to the page; anyone can spoof a claim of ownership without a signature — use SIWE for auth. | Why: connect buttons look like login buttons. | Source: https://eips.ethereum.org/EIPS/eip-4361
- Belief: `ssr: true` alone fixes Next.js hydration. | Reality: it removes the hydration warning by deferring client-store reads, but you still get a disconnected-state flash unless you add `cookieStorage` + `cookieToInitialState`. | Why: the flag name suggests completeness. | Source: https://wagmi.sh/react/guides/ssr
- Belief: create the `QueryClient` once at module scope. | Reality: in SSR that shares cache across requests and leaks one user's data into another's render; create it inside the client provider (e.g. `useState(() => new QueryClient())`). | Why: the TanStack quickstart is a client-only SPA example. | Source: https://wagmi.sh/react/guides/ssr
- Belief: the wallet's selected chain is the chain your reads use. | Reality: reads use the config's transports and the `chainId` you pass (defaulting to the connection's chain); mixing them silently produces cross-chain-wrong data. | Why: MetaMask's network dropdown feels global. | Source: https://wagmi.sh/react/api/hooks/useReadContract
- Belief: upgrading wagmi v2→v3 is a version bump. | Reality: connector SDKs became optional peer deps, so connectors that used to be bundled now throw at runtime until you install them. | Why: semver majors are usually type-level in this ecosystem. | Source: https://wagmi.sh/react/guides/migrate-from-v2-to-v3

## 07.6 — Session keys: scoping, expiry, revocation, and the cost of not re-prompting

### Concepts
- session-key-definition — A session key is a secondary keypair the user's account authorises to act on their behalf under a policy, so the app can submit transactions without the user signing each one. | requires: [smart-account-basics] | contrasts: [eoa-single-key]
- session-key-needs-programmable-account — A plain EOA cannot scope its own key: authority is all-or-nothing. Session keys require either an ERC-4337 smart account or an EOA that has delegated to smart-account code via EIP-7702. | requires: [session-key-definition, eip-7702-delegation] | contrasts: [eoa-single-key]
- session-key-policy-dimensions — Useful policies constrain: target address(es), function selector(s), argument values, per-call and cumulative value caps, call-rate limits, gas budget, chain id, and a `validAfter`/`validUntil` window. | requires: [session-key-definition] | contrasts: [unscoped-approval]
- session-key-enforced-on-chain — A policy is only real if the account's validation logic enforces it on-chain; a client-side check of the same rules is decoration, because whoever holds the key can bypass the client. | requires: [session-key-policy-dimensions] | contrasts: [client-side-policy-check]
- erc-7579-validator-vs-executor — In a modular (ERC-7579) account, a validator module decides whether a signature/permission authorises a call and an executor module performs calls; conflating the two module types is a known privilege-escalation class. | requires: [session-key-enforced-on-chain] | contrasts: [monolithic-smart-account]
- erc-7715-grant-permissions — ERC-7715 defines `wallet_grantPermissions`, a JSON-RPC method where the dapp asks the wallet for a scoped, time-bounded permission; the wallet renders one human-readable consent screen and returns a signed permissions context. | requires: [session-key-definition] | contrasts: [per-transaction-prompt]
- erc-7710-delegation-manager — ERC-7710 is the on-chain half: a delegation-manager interface the app calls with the permissions context each time it exercises the granted authority. | requires: [erc-7715-grant-permissions] | contrasts: [erc-7715-grant-permissions]
- session-key-expiry-is-free — Expiry (`validUntil`) needs no transaction: authority simply stops being valid at a timestamp, which is why short-lived keys are the cheap default. | requires: [session-key-policy-dimensions] | contrasts: [session-key-revocation-costs-gas]
- session-key-revocation-costs-gas — Early revocation is a state change: it needs an on-chain transaction (uninstall the module, bump a session nonce, or flip a registry bit) that costs gas, needs a signer available, and is not instant. | requires: [session-key-expiry-is-free] | contrasts: [session-key-expiry-is-free]
- session-key-revocation-race — Between the user pressing "revoke" and the revocation transaction being mined, the session key is still valid; a compromised key can front-run the revocation. | requires: [session-key-revocation-costs-gas, mempool-visibility] | contrasts: [session-key-expiry-is-free]
- session-key-material-location — Where the session private key lives (page memory, IndexedDB, a service worker, a device enclave, or a server-side signer) determines the actual attack surface, and is usually a bigger risk than the policy design. | requires: [session-key-definition] | contrasts: [session-key-policy-dimensions]
- session-key-blast-radius — The security argument is not "this key is safe" but "if this key leaks, the loss is bounded by the policy" — so the policy must be sized to what you can afford to lose. | requires: [session-key-policy-dimensions] | contrasts: [unscoped-approval]
- session-key-consent-moves-not-disappears — Removing the per-transaction prompt does not remove consent; it relocates all of it into one grant-time screen the user reads once, under time pressure, with less context. | requires: [erc-7715-grant-permissions] | contrasts: [per-transaction-prompt]
- session-key-4337-validation-limits — ERC-4337's validation-phase storage/opcode restrictions limit what a policy can inspect during validation, which is why some checks are pushed into the execution phase or a post-op hook. | requires: [erc-4337-entrypoint, session-key-enforced-on-chain] | contrasts: [arbitrary-policy-logic]
- session-key-vs-token-approval — An unlimited ERC-20 `approve` is the pre-existing, worse version of a session key: unbounded amount, no expiry, revocation also costs a transaction. | requires: [session-key-blast-radius] | contrasts: [session-key-policy-dimensions]

### Current state (Aug 2026)
- Session keys are **in production but not standardised end-to-end**. The ERC-4337 documentation says these patterns "are not yet standardized and are implemented wallet-by-wallet" — that sentence should shape how this is taught.
- ERC-7715 (`wallet_grantPermissions`) + ERC-7710 (delegation manager) are the convergence point, but both are **draft ERCs**, and MetaMask's implementation is shipped under an `experimental` namespace in its Delegation Toolkit.
- EIP-7702 (live since Pectra, May 2025) materially changed the story: session keys no longer require moving assets to a new smart-account address. An EOA can delegate to ERC-7579-style code, keep its address, and use the same validator modules — then clear the delegation with `address(0)`.
- ERC-7579 has effectively won as the modular-account interface for permission modules; "Smart Sessions"-style reusable policy modules are the common building block.
- Commonly taught but now wrong: "session keys need an ERC-4337 smart account" (7702 removes that); "session keys are an ERC-4337 feature" (4337 does not define them — the account's validation logic does); "revoking is instant" (it is a transaction).
- ERC-4337 EntryPoint v0.7 is the production version per the shared baseline; v0.8/v0.9 exist. Session-key modules are usually written against a specific EntryPoint version.

### Misconceptions
- Belief: a session key is safe because it is "temporary". | Reality: safety comes from the policy bound to it, not its lifetime; a 1-hour key with unlimited transfer authority can drain everything in that hour. | Why: "session" borrows web-session intuitions where the server holds the authority. | Source: https://docs.erc4337.io/smart-accounts/session-keys-and-delegation.html
- Belief: the app can enforce the spending limit. | Reality: the app holds the key; only the account's on-chain validation can enforce anything. Client-side limits stop bugs, not attackers. | Why: engineers map this onto API rate limits. | Source: https://eips.ethereum.org/EIPS/eip-7710
- Belief: revoking a session key takes effect immediately when the user clicks revoke. | Reality: it is a transaction — it costs gas, needs inclusion, and the key stays valid (and can front-run) until it lands. | Why: web sessions are revoked by deleting a server-side row. | Source: https://eips.ethereum.org/EIPS/eip-7715
- Belief: session keys remove the need for user consent. | Reality: consent is compressed into one grant screen; if that screen does not clearly state contract, cap and expiry, you have made consent worse, not lighter. | Why: the UX win is measured in prompts removed. | Source: https://metamask.io/news/introducing-advanced-permissions
- Belief: ERC-7715 is a finished standard you can rely on. | Reality: it is a draft, implemented experimentally by a small number of wallets; assume per-wallet divergence and feature-detect. | Why: it has an ERC number. | Source: https://eips.ethereum.org/EIPS/eip-7715
- Belief: a session key is a new idea. | Reality: an unlimited `approve()` to a router is a session key with the worst possible policy — unbounded, no expiry, revocation costs gas. Session keys are that pattern made explicit and constrained. | Why: the two are taught in different chapters. | Source: https://eips.ethereum.org/EIPS/eip-7710

## 07.7 — Passkeys: WebAuthn flow, on-chain secp256r1 after EIP-7951, recovery, device loss

### Concepts
- passkey-definition — A passkey is a WebAuthn credential: a P-256 (secp256r1) keypair generated and held in device secure hardware (Secure Enclave, Android Keystore, security key), unlocked by biometric or PIN, with the private key non-exportable. | requires: [public-key-crypto] | contrasts: [seed-phrase-wallet]
- passkey-curve-mismatch — Ethereum EOAs sign on secp256k1; passkeys sign on secp256r1 (P-256). These are different curves, so a passkey can never be an EOA private key and can never sign a raw Ethereum transaction. | requires: [passkey-definition, ecdsa-secp256k1] | contrasts: [eoa-single-key]
- passkey-needs-smart-account — Because of the curve mismatch, a passkey can only control funds through a contract that verifies P-256 — an ERC-4337 smart account, an ERC-1271 signer, or an EOA delegated via EIP-7702. | requires: [passkey-curve-mismatch, eip-7702-delegation] | contrasts: [eoa-single-key]
- webauthn-signed-payload — WebAuthn does not sign your message. It signs `authenticatorData || SHA-256(clientDataJSON)`, and your message appears only as the `challenge` field inside `clientDataJSON`. | requires: [passkey-definition] | contrasts: [eth-sign-personal-message]
- webauthn-challenge-binding — The challenge must commit to the full transaction semantics — account address, chain id, nonce, calldata, EntryPoint — usually by setting it to the `userOpHash`; a challenge that commits to less is a replay hole. | requires: [webauthn-signed-payload, erc-4337-userop] | contrasts: [webauthn-signed-payload]
- webauthn-onchain-reconstruction — On-chain verification means rebuilding the exact signed bytes: hash `clientDataJSON`, concatenate after `authenticatorData`, hash again, and pass that digest to the P-256 verifier. | requires: [webauthn-signed-payload] | contrasts: [ecrecover-flow]
- webauthn-clientdata-checks — A correct verifier also checks `type == "webauthn.get"`, that the embedded challenge is the expected value at the expected offset, the origin/RP-ID binding, and the `UP` (and optionally `UV`) flag bits in `authenticatorData`. | requires: [webauthn-onchain-reconstruction] | contrasts: [signature-check-only]
- eip-7951-precompile — EIP-7951 (Fusaka, Dec 2025) puts a secp256r1 verifier at address `0x100`: 160 bytes of input (`h ‖ r ‖ s ‖ qx ‖ qy`, 32 bytes each), 6900 gas flat, returns 32-byte `0x...01` on success and empty bytes on failure. | requires: [webauthn-onchain-reconstruction] | contrasts: [solidity-p256-verifier]
- eip-7951-no-low-s — EIP-7951 deliberately does **not** enforce low-s, because NIST FIPS 186-5 does not require non-malleable ECDSA. Every P-256 signature therefore has a second valid form, and the account must normalise or handle it. | requires: [eip-7951-precompile, signature-malleability] | contrasts: [secp256k1-eip2-low-s]
- p256-precompile-vs-solidity — Before the precompile, P-256 verification in Solidity cost on the order of hundreds of thousands of gas; 6900 gas changes passkey accounts from a subsidised curiosity to a default. | requires: [eip-7951-precompile] | contrasts: [solidity-p256-verifier]
- passkey-rp-id-binding — A passkey is bound to a Relying Party ID (an eTLD+1 domain). Lose or change the domain and the credential is unusable; this makes your DNS name part of the custody model. | requires: [passkey-definition] | contrasts: [seed-phrase-wallet]
- passkey-sync-vs-device-bound — Platform passkeys synced through iCloud Keychain / Google Password Manager survive device loss but move custody into the OS account; device-bound (hardware-key) passkeys do not sync and are permanently lost with the device. | requires: [passkey-definition] | contrasts: [passkey-recovery-is-mandatory]
- passkey-recovery-is-mandatory — A passkey account with exactly one credential and no recovery path is a single point of failure; production designs register a second credential and/or guardians at account-creation time, not later. | requires: [passkey-needs-smart-account] | contrasts: [seed-phrase-wallet]
- passkey-recovery-mechanisms — Practical options: multiple registered passkeys across devices, an EOA/hardware-wallet co-owner, social recovery guardians with a timelock, or a custodial fallback — each with a different trust and phishing profile. | requires: [passkey-recovery-is-mandatory] | contrasts: [passkey-recovery-is-mandatory]
- passkey-pubkey-must-be-registered — The account contract must know the credential's public key (and usually credential id) on-chain; registering a new device is itself a transaction, so a user with zero working credentials cannot add one. | requires: [passkey-needs-smart-account] | contrasts: [passkey-recovery-mechanisms]
- passkey-ux-win — The UX gain is real: no seed phrase, no extension, biometric confirmation per action, and phishing resistance from the RP-ID binding that seed phrases and signature prompts do not have. | requires: [passkey-definition] | contrasts: [seed-phrase-wallet]

### Primary sources
- [EIP-7951: Precompile for secp256r1 Curve Support](https://eips.ethereum.org/EIPS/eip-7951) — tier: spec — published: 2024, activated Fusaka 2025-12 — address `0x100`, 160-byte input layout, 6900 gas, explicit "no low-s requirement" rationale.
- [W3C Web Authentication Level 2/3 — §7.2 Verifying an Authentication Assertion](https://www.w3.org/TR/webauthn-2/) — tier: spec — published: 2021 (L2) — normative source for `authenticatorData ‖ SHA-256(clientDataJSON)` and the flag/type checks.
- [base/webauthn-sol](https://github.com/base/webauthn-sol) — tier: canonical-docs — published: 2024-2026 — the widely used Solidity WebAuthn verifier; read its low-s handling and clientDataJSON offset checks.
- [CertiK — Security Considerations for Passkey-Based Web3 Wallets](https://www.certik.com/blog/security-considerations-for-passkey-based-web3-wallets) — tier: primary-analysis — published: 2025-2026 — enumerates the concrete audit checks: challenge binding to chain id/nonce/calldata, flag checks, low-S, key-to-account binding.
- [MojoAuth — How to Verify a WebAuthn Assertion Signature, Step by Step](https://mojoauth.com/blog/how-to-verify-a-webauthn-assertion-signature-step-by-step) — tier: secondary — published: 2025-2026 — clear byte-level walkthrough of the assertion; good for the reconstruct-the-payload lesson.

- [Yubico — WebAuthn Client Authentication](https://developers.yubico.com/WebAuthn/WebAuthn_Developer_Guide/WebAuthn_Client_Authentication.html) — tier: canonical-docs — published: ongoing — authoritative on ceremony mechanics, RP ID, UP/UV flags.

### Current state (Aug 2026)
- **EIP-7951 is live on L1 since Fusaka (3 Dec 2025)**: precompile `0x100`, 6900 gas. This is the single biggest change — passkey signature verification stopped being a gas-cost objection on mainnet.
- Confirmed input layout, 160 bytes exactly: `h(32) ‖ r(32) ‖ s(32) ‖ qx(32) ‖ qy(32)`. Success returns 32 bytes of `1`; failure returns **empty** output, not a revert and not a 32-byte zero. Charged 6900 gas either way.
- Confirmed rationale text targets "Apple Secure Enclave, Android Keystore, and FIDO2/WebAuthn devices".
- L2s (via RIP-7212) have had the same precompile at `0x100` since 2024, at a lower gas price — see gaps below.
- Passkey-backed smart accounts (Coinbase Smart Wallet / Base Account, and 7702-delegated EOAs) are mainstream consumer onboarding in 2026, not experimental.
- Commonly taught but now wrong: "P-256 verification is too expensive on Ethereum" (6900 gas since Dec 2025); "passkeys replace seed phrases with no trade-off" (they move custody to the OS/cloud account or require guardians); "ecrecover works for passkeys" (wrong curve entirely).

### Misconceptions
- Belief: a passkey signs your transaction hash. | Reality: it signs `authenticatorData ‖ SHA-256(clientDataJSON)`; your hash is only the `challenge` string inside that JSON, so the contract must reconstruct and re-hash before verifying. | Why: every other signing flow in Ethereum signs the digest directly. | Source: https://www.w3.org/TR/webauthn-2/
- Belief: EIP-7951 rejects malleable signatures like Ethereum's secp256k1 rules do. | Reality: the spec explicitly imposes no low-s requirement, because FIPS 186-5 does not require it — so `(r, s)` and `(r, n-s)` both verify. | Why: EIP-2 trained everyone to expect low-s enforcement. | Source: https://eips.ethereum.org/EIPS/eip-7951
- Belief: verifying the P-256 signature is the whole check. | Reality: you must also check `type == "webauthn.get"`, the challenge value and its position in `clientDataJSON`, the RP-ID hash, and the UP/UV flags — otherwise a signature over some other ceremony can be replayed. | Why: the precompile returns a satisfying boolean. | Source: https://www.certik.com/blog/security-considerations-for-passkey-based-web3-wallets
- Belief: passkeys eliminate the "lose your key, lose your money" problem. | Reality: they relocate it. Synced passkeys make your Apple/Google account the recovery authority; device-bound passkeys are gone with the device; either way you need a second credential or guardian set up in advance. | Why: "backed up by iCloud" is marketed as recovery. | Source: https://eco.com/support/en/articles/15039720-passkey-wallets-explained
- Belief: after losing a device you can just register a new passkey. | Reality: registering a new credential is an on-chain transaction that must be authorised by an existing credential or guardian; with zero working credentials the account is bricked. | Why: web services let support re-enrol you. | Source: https://www.certik.com/blog/security-considerations-for-passkey-based-web3-wallets
- Belief: the passkey works anywhere the user goes. | Reality: it is bound to the RP ID (your domain). A domain change, a subdomain migration, or an embedded cross-origin context can make the credential unusable. | Why: wallets feel domain-independent. | Source: https://developers.yubico.com/WebAuthn/WebAuthn_Developer_Guide/WebAuthn_Client_Authentication.html
- Belief: the precompile reverts on a bad signature. | Reality: it returns empty output and still charges 6900 gas; a caller that checks only "did the call succeed" treats an invalid signature as valid. | Why: Solidity's `require(success)` idiom. | Source: https://eips.ethereum.org/EIPS/eip-7951

## 07.8 — Transaction UX: the full lifecycle, pending/replaced/dropped, simulation, and reorgs

### Concepts
- tx-lifecycle-states — A transaction passes through: constructed → simulated → signed → broadcast → pending in mempool → included in a block → N confirmations → finalized. Off that happy path it can also be **replaced**, **dropped**, or **included-and-reverted**. | requires: [mempool-basics] | contrasts: [http-request-response]
- tx-is-not-request-response — There is no 200/500. Sending returns only a hash; success, failure, and "never happened" are all discovered later by polling, and the three are distinct outcomes your UI must model separately. | requires: [tx-lifecycle-states] | contrasts: [http-request-response]
- tx-receipt-status-zero — A receipt with `status: 'reverted'` (0x0) means the transaction was mined, did nothing useful, and still consumed gas. "Mined" is not "succeeded". | requires: [tx-lifecycle-states] | contrasts: [tx-dropped]
- tx-nonce-is-a-sequence — Each account's transactions execute in strict nonce order; a pending transaction at nonce N blocks every later nonce, so one stuck transaction stalls the whole account. | requires: [tx-lifecycle-states] | contrasts: [parallel-request-queue]
- tx-replacement-same-nonce — You cannot edit or delete a pending transaction. You can only broadcast a *different* transaction with the *same nonce* and a higher fee; nodes typically require a meaningful bump (commonly ~10-12.5%) to accept it. | requires: [tx-nonce-is-a-sequence] | contrasts: [tx-cancel-is-deletion]
- tx-cancel-is-a-replacement — "Cancel" is a replacement that does nothing: a 0-value self-send at the same nonce. It costs gas, it can lose the race, and the original may still land. | requires: [tx-replacement-same-nonce] | contrasts: [tx-cancel-is-deletion]
- tx-replacement-changes-the-hash — A replaced transaction has a new hash, so any UI, database row, or webhook keyed on the original hash silently orphans; viem's `onReplaced` exists precisely to re-key. | requires: [tx-replacement-same-nonce] | contrasts: [tx-hash-as-primary-key]
- tx-replacement-reasons — viem classifies replacements as `repriced` (same value/data, higher fee), `cancelled` (value → 0), or `replaced` (different value or data) — three distinct things to tell the user. | requires: [tx-replacement-changes-the-hash] | contrasts: [tx-replacement-same-nonce]
- tx-dropped — A transaction can be evicted from mempools (low fee, long wait, node restarts) and simply never mined. There is no event: you observe it as "no receipt, and the nonce is free again". | requires: [tx-lifecycle-states] | contrasts: [tx-receipt-status-zero]
- tx-stuck-from-fee-cap — Under EIP-1559 a transaction is unminable while the block base fee exceeds its `maxFeePerGas`; it is not dropped, just parked, and becomes minable again if base fee falls. | requires: [eip-1559-fee-market, tx-dropped] | contrasts: [tx-dropped]
- tx-simulate-before-send — Simulating (`eth_call` / `simulateContract` at pending state) before asking for a signature converts most reverts into a pre-signature error message, which is the single highest-leverage UX improvement in the whole flow. | requires: [viem-simulate-before-send] | contrasts: [tx-receipt-status-zero]
- tx-confirmations-vs-finality — Confirmations are a probabilistic heuristic (block depth); Ethereum finality is a separate, deterministic property reached after two epochs (~12.8 minutes ideal). Below finality, a reorg can undo an included transaction. | requires: [tx-lifecycle-states, casper-ffg-finality] | contrasts: [tx-receipt-status-zero]
- tx-reorg-effects — In a reorg an included transaction can return to pending, be re-executed with different results, or vanish; emitted logs are re-delivered with `removed: true`, so any indexer or UI that appends on log receipt must be able to un-append. | requires: [tx-confirmations-vs-finality] | contrasts: [append-only-event-log]
- tx-confirmation-policy-is-a-product-decision — How many confirmations to wait for is a value-at-risk decision, not a technical constant: 1 for a UI toast, more for crediting an account, finality for irreversible off-chain actions. | requires: [tx-confirmations-vs-finality] | contrasts: [fixed-12-confirmations]
- tx-l2-confirmation-tiers — On rollups, "confirmed" has at least three meanings — sequencer soft confirmation (sub-second), data posted to L1, and proven/challenge-window-passed — and only the last is as strong as L1 finality. | requires: [tx-confirmations-vs-finality, rollup-basics] | contrasts: [tx-confirmations-vs-finality]
- tx-one-intent-many-transactions — A single user intent (approve then swap, bridge then act) is often several transactions; EIP-5792 `wallet_sendCalls` + `wallet_getCallsStatus` lets a wallet report one batched status instead of N. | requires: [tx-lifecycle-states, erc-5792-batching] | contrasts: [tx-is-not-request-response]
- tx-optimistic-ui-boundary — Optimistic UI is safe for reversible display state and unsafe for anything that triggers an irreversible off-chain effect (shipping, crediting, emailing) before the confirmation policy is met. | requires: [tx-confirmation-policy-is-a-product-decision] | contrasts: [tx-reorg-effects]

### Current state (Aug 2026)
- Ethereum finality is still ~2 epochs. Ideal case ~12.8 minutes (64 slots × 12s). **Single-slot finality has not shipped** and had no confirmed deployment timeline as of mid-2026; EIP-7251 (Pectra, May 2025) validator consolidation is a stepping stone, not SSF itself.
- viem `waitForTransactionReceipt` defaults as of 2.55.x: `confirmations: 1`, `timeout: 180_000`ms, `retryCount: 6`, exponential `retryDelay`. Replacement detection works by scanning new blocks for a transaction from the same sender at the same nonce.
- EIP-7966 sync sends (`eth_sendRawTransactionSync`) collapse broadcast+wait into one call on fast chains — a genuinely new UX primitive since 2025, and one that hides the pending state rather than removing it.
- EIP-5792 batching is now the mainstream way to kill the "approve then swap" double prompt, and EIP-7702 lets plain EOAs participate.
- Fusaka (Dec 2025) raised the L1 gas limit 30M → 60M and capped a single transaction at ~16.78M gas (EIP-7825) — a new hard failure mode for very large transactions that older material does not mention.
- Commonly taught but now wrong: "wait 12 confirmations" as a universal rule (post-Merge, finality is the meaningful boundary and 12 is a proof-of-work holdover); "cancel a transaction" as if it were a delete; "the transaction hash identifies the user's action" (replacement breaks it); "gas price" as a single number (it is base fee + priority fee with a cap).

### Misconceptions
- Belief: if the transaction was mined, it worked. | Reality: `status: 'reverted'` receipts are mined, failed, and fully charged; the UI must read `receipt.status`, not the existence of a receipt. | Why: HTTP conflates delivery with success. | Source: https://viem.sh/docs/actions/public/waitForTransactionReceipt
- Belief: you can cancel a pending transaction. | Reality: you can only race it with a same-nonce replacement that costs gas and may lose; wallets label this "Cancel" for familiarity. | Why: every other queue in software supports cancel. | Source: https://eips.ethereum.org/EIPS/eip-1559
- Belief: the transaction hash is a stable identifier for the user's action. | Reality: speeding up or cancelling produces a new hash for the same nonce; key your records on `(address, chainId, nonce)` and treat the hash as mutable. | Why: hashes look like UUIDs. | Source: https://viem.sh/docs/actions/public/waitForTransactionReceipt
- Belief: a transaction that has not been mined for an hour has failed. | Reality: it may be parked because base fee exceeds its `maxFeePerGas` and can still be mined much later; it may also have been dropped. These need different UI. | Why: timeouts mean failure everywhere else. | Source: https://eips.ethereum.org/EIPS/eip-1559
- Belief: one confirmation is enough because Ethereum is proof-of-stake. | Reality: PoS gives *finality* after ~2 epochs, not instant irreversibility; below finality, reorgs of unfinalized blocks remain possible. | Why: "PoS has finality" gets compressed into "PoS is instant". | Source: https://ethereum.org/roadmap/single-slot-finality/
- Belief: an L2 transaction confirmed by the sequencer is final. | Reality: that is a sequencer promise; the data still has to reach L1 and (for optimistic rollups) survive a challenge window before it inherits L1 security. | Why: L2 UIs show a green check in under a second. | Source: https://l2beat.com
- Belief: event logs are append-only. | Reality: reorged logs are re-delivered with `removed: true`; indexers and UIs that only handle additions will show phantom state. | Why: log streams look like Kafka. | Source: https://viem.sh/docs/actions/public/watchContractEvent

## 07.9 — Error surfaces: decoding custom errors, revert reasons, estimateGas failures, human messages

### Concepts
- revert-data-is-abi-encoded — A revert returns raw `bytes`. The EVM attaches no meaning to them; all "error messages" are an application-level ABI convention layered on top. | requires: [abi-encoding, evm-call-semantics] | contrasts: [http-status-codes]
- four-revert-shapes — Revert data comes in exactly four shapes: **empty** (0 bytes), `Error(string)` (selector `0x08c379a0`), `Panic(uint256)` (selector `0x4e487b71`), or a **custom error** (any other 4-byte selector + ABI-encoded args). | requires: [revert-data-is-abi-encoded] | contrasts: [revert-data-is-abi-encoded]
- error-string-legacy — `require(cond, "msg")` and `revert("msg")` produce `Error(string)`; it is the pre-0.8.4 default, costs a full string in bytecode and calldata, and is now the legacy path. | requires: [four-revert-shapes] | contrasts: [solidity-custom-errors]
- solidity-custom-errors — `error Foo(uint256 a)` encodes as `keccak256("Foo(uint256)")[0:4] ‖ abi.encode(a)`, which is far cheaper than a string and carries structured, typed data the client can render. | requires: [four-revert-shapes] | contrasts: [error-string-legacy]
- panic-codes — `Panic(uint256)` signals a language-level invariant break, not a business rule: `0x01` failed `assert`, `0x11` over/underflow, `0x12` division or modulo by zero, `0x21` bad enum conversion, `0x22` bad storage byte-array encoding, `0x31` `.pop()` on empty array, `0x32` array index out of bounds, `0x41` allocated too much memory / array too large, `0x51` called a zero-initialised internal function pointer. | requires: [four-revert-shapes] | contrasts: [solidity-custom-errors]
- panic-means-bug — A Panic is almost always a contract bug or a client passing impossible input; it should never be surfaced to a user as a business message. | requires: [panic-codes] | contrasts: [solidity-custom-errors]
- empty-revert-data — Zero-length revert data has many causes with no way to distinguish them from the data alone: bare `revert()`, out of gas, `INVALID` opcode, calling an address with no code, a proxy pointing at nothing, or a precompile/ABI mismatch. | requires: [four-revert-shapes] | contrasts: [solidity-custom-errors]
- selector-only-4-bytes — A custom-error selector is 4 bytes with no on-chain registry; decoding requires you to already hold a matching ABI, and different signatures can collide on the same selector. | requires: [solidity-custom-errors] | contrasts: [json-error-codes]
- decode-needs-the-right-abi — The reverting contract is often not the one you called (a token inside a router, a library, an implementation behind a proxy); you must supply that contract's error definitions or you get undecodable hex. | requires: [selector-only-4-bytes] | contrasts: [selector-only-4-bytes]
- viem-decode-error-result — viem's `decodeErrorResult({ abi, data })` turns revert bytes into `{ errorName, args }`; `BaseError.walk()` finds the `ContractFunctionRevertedError` in the cause chain that carries them. | requires: [viem-error-hierarchy, decode-needs-the-right-abi] | contrasts: [string-matching-revert-reasons]
- estimategas-is-a-search — `eth_estimateGas` is not one call: clients dry-run and then binary-search the gas limit for the smallest value at which the call succeeds, so it costs several executions and can be slow. | requires: [gas-basics] | contrasts: [eth-call-simple]
- estimategas-nonmonotonic — The binary search assumes success is monotone in gas limit. Contracts with gas-dependent branches (`gasleft()` checks, gas-forwarding to callbacks, refund interactions) break that assumption and can produce a wrong estimate. | requires: [estimategas-is-a-search] | contrasts: [estimategas-is-a-search]
- estimategas-63-64 — EIP-150 retains 1/64 of remaining gas at each call frame, so a transaction can pass estimation yet fail in production when a deep sub-call receives less gas than it needs; adding headroom is not paranoia. | requires: [estimategas-is-a-search] | contrasts: [exact-gas-limit]
- estimategas-failure-modes — Estimation fails for at least four different reasons — the call reverts, the sender lacks funds for value+gas, the estimate exceeds the block/allowance cap, or state changed — and providers collapse several of them into one opaque "gas required exceeds allowance" or "execution reverted" string. | requires: [estimategas-is-a-search] | contrasts: [tx-receipt-status-zero]
- estimategas-is-not-simulation — Estimation tells you a number or throws; simulation (`eth_call`) tells you the return value and the revert data. Use `eth_call`/`simulateContract` to explain a failure, and `estimateGas` only to size the limit. | requires: [estimategas-failure-modes, viem-simulate-before-send] | contrasts: [estimategas-failure-modes]
- provider-error-shape-drift — RPC providers wrap and truncate errors differently; some strip revert data entirely from `eth_estimateGas` failures, so the same contract failure looks different across Alchemy, Infura, a public node and Anvil. | requires: [estimategas-failure-modes] | contrasts: [revert-data-is-abi-encoded]
- error-triage-taxonomy — Every chain error belongs to one of four buckets, each with a different UI: **user can fix** (insufficient balance, needs approval, wrong chain), **app bug** (Panic, decode failure, bad args), **transient chain/wallet state** (nonce race, RPC timeout, fee too low), **user declined**. | requires: [four-revert-shapes, estimategas-failure-modes] | contrasts: [generic-error-toast]
- error-message-must-name-the-next-action — A usable message states what failed, why, and the one thing the user should do; raw hex, selectors and "execution reverted" fail all three tests. | requires: [error-triage-taxonomy] | contrasts: [generic-error-toast]

### Misconceptions
- Belief: reverts carry a human-readable reason. | Reality: they carry ABI-encoded bytes; the "reason" only exists if the client holds a matching ABI and decodes it. Custom errors have no string at all. | Why: pre-0.8.4 `require("...")` trained everyone. | Source: https://blog.soliditylang.org/2021/04/21/custom-errors/
- Belief: `execution reverted` with no data means the require failed. | Reality: empty revert data is also produced by out-of-gas, `INVALID`, calling an address with no code, and a proxy with no implementation — a wrong-address bug looks identical to a business-rule failure. | Why: the message names the most common cause. | Source: https://docs.soliditylang.org/en/latest/control-structures.html
- Belief: a Panic is a validation error to show the user. | Reality: Panics are language-invariant breaks — a contract bug or impossible input. Showing "arithmetic overflow" to a user is an admission of a bug, not a hint. | Why: it arrives on the same channel as business errors. | Source: https://github.com/OpenZeppelin/openzeppelin-contracts/blob/master/contracts/utils/Panic.sol
- Belief: if `eth_estimateGas` throws, the transaction would revert. | Reality: it also throws when the sender cannot cover value + gas, when the estimate exceeds the allowance/block cap, or when the node's state moved — geth's "gas required exceeds allowance" is a balance check, not a revert. | Why: wallets surface all of them as "transaction will fail". | Source: https://github.com/ethereum/go-ethereum/issues/21311
- Belief: use the estimate as the gas limit. | Reality: EIP-150's 63/64 rule means a deep sub-call may get less gas than it needs even when the top-level total is correct; and state can change before inclusion. Add headroom. | Why: the number is called an estimate but read as an answer. | Source: https://eips.ethereum.org/EIPS/eip-150
- Belief: a 4-byte selector uniquely identifies an error. | Reality: 4 bytes is 2^32 of space with no registry; collisions exist, and lookup services return multiple candidate signatures for one selector. | Why: selectors look like unique IDs. | Source: https://viem.sh/docs/contract/decodeErrorResult
- Belief: you can decode any revert with the ABI of the contract you called. | Reality: the error may be defined in a library, a token, or the implementation behind a proxy; you need that contract's ABI, and viem will hand you raw hex otherwise. | Why: one call feels like one contract. | Source: https://viem.sh/docs/glossary/errors
- Belief: errors look the same everywhere. | Reality: RPC providers wrap, truncate, and sometimes strip revert data, so an error that decodes on Anvil may be opaque on a hosted provider — always test error paths against the provider you ship on. | Why: local development uses Anvil. | Source: https://github.com/ethers-io/ethers.js/discussions/1944
