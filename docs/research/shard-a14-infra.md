## 13.1 — Running nodes: EL+CL pairing, hardware, sync modes, archive cost

### Concepts
- node-two-process-model — Since the Merge an "Ethereum node" is two processes: an execution client (EVM, state, JSON-RPC) and a consensus client (fork choice, attestations, blocks), and you must run both. | requires: [] | contrasts: [node-single-binary-myth]
- engine-api-jwt — EL and CL talk over the Engine API on port 8551 authenticated by a shared 32-byte hex JWT secret file; a mismatched or missing jwtsecret is the single most common "node won't sync" failure. | requires: [node-two-process-model] | contrasts: [json-rpc-public-port]
- client-diversity-risk — If one EL or CL client exceeds ~33% of the network, a consensus bug in it can prevent finality, and above ~66% it can finalise an invalid chain, so choosing a minority client is a network-level safety act, not a preference. | requires: [node-two-process-model] | contrasts: []
- el-client-landscape — Production EL clients are Geth (Go), Nethermind (.NET), Besu (Java), Erigon (Go) and Reth (Rust); Erigon and Reth are the "staged sync / flat-state" designs optimised for archive and high-throughput reads. | requires: [node-two-process-model] | contrasts: []
- cl-client-landscape — Production CL clients are Lighthouse (Rust), Prysm (Go), Teku (Java), Nimbus (Nim) and Lodestar (TS); any CL pairs with any EL because the Engine API is the only contract between them. | requires: [engine-api-jwt] | contrasts: []
- sync-mode-snap — Snap sync downloads a recent state snapshot plus headers and then replays only recent blocks, so it reaches tip in hours instead of days but has no historical state before the snapshot point. | requires: [node-two-process-model] | contrasts: [sync-mode-full-exec, sync-mode-archive]
- sync-mode-full-exec — A "full node" in the strict sense re-executes every block from genesis to verify the chain itself, and after syncing keeps only recent state (typically 128 blocks of history) plus all blocks and receipts. | requires: [sync-mode-snap] | contrasts: [sync-mode-archive]
- sync-mode-archive — An archive node retains every historical intermediate state root and trie node so `eth_call`/`eth_getBalance` at an arbitrary past block works, which is what costs the extra terabytes — not the block data. | requires: [sync-mode-full-exec] | contrasts: [sync-mode-snap]
- archive-cost-is-state-not-blocks — Block bodies and receipts for all of Ethereum are a few hundred GB; the archive premium comes from historical state, and how big that premium is depends entirely on the client's state layout (hash-based trie vs path-based vs flat KV). | requires: [sync-mode-archive] | contrasts: []
- checkpoint-sync — A consensus client normally starts from a trusted finalised checkpoint (a weak-subjectivity state fetched over HTTP from a public endpoint or a friend's node), taking CL sync from days to minutes; the trust assumption is one-time and bounded. | requires: [cl-client-landscape] | contrasts: [sync-mode-full-exec]
- history-expiry-4444 — Since May 2025 execution clients may drop pre-Merge block bodies and receipts (EIP-4444 partial history expiry), saving on the order of 300-500 GB; pre-Merge headers are still served, and full historical block data moves to e2store files and the Portal Network. | requires: [sync-mode-full-exec] | contrasts: [sync-mode-archive]
- blob-storage-is-separate — Blobs live on the consensus layer with ~18-day retention and are stored by the CL, not the EL, so blob throughput increases (PeerDAS BPO forks) change CL disk and bandwidth, not EL state size. | requires: [cl-client-landscape] | contrasts: [archive-cost-is-state-not-blocks]
- peerdas-node-impact — Under PeerDAS a node samples a subset of the 128 blob columns rather than downloading every blob, so blob capacity can rise without every home node's bandwidth rising proportionally. | requires: [blob-storage-is-separate] | contrasts: []
- disk-is-the-bottleneck — Node performance is dominated by random-read IOPS on the state database, so a consumer NVMe SSD is the requirement and network-attached or SATA/QLC storage will cause a node to fall behind head. | requires: [sync-mode-snap] | contrasts: []
- offline-pruning-treadmill — Geth-style hash-based state grows continuously (roughly ~14 GB/week per its own docs) and must be periodically pruned offline, which means a node on a 1 TB disk is a recurring maintenance chore rather than a one-time setup. | requires: [disk-is-the-bottleneck] | contrasts: [sync-mode-archive]

### Primary sources
- [Spin up your own Ethereum node](https://ethereum.org/developers/docs/nodes-and-clients/run-a-node/) — tier: canonical-docs — published: 2026-continuously-updated — the baseline "what is a node, what do I need" reference; states the 2 TB SSD / 16 GB RAM / 25 Mbit baseline.
- [go-ethereum: Hardware requirements](https://geth.ethereum.org/docs/getting-started/hardware-requirements) — tier: canonical-docs — published: 2026-continuously-updated — the only first-party number I could confirm for growth rate: snap-synced full node >650 GB growing ~14 GB/week; archive "more than 12TB".
- [go-ethereum: Database pruning](https://geth.ethereum.org/docs/fundamentals/dbpruning) — tier: canonical-docs — published: 2026 — explains why offline pruning exists and how the state trie accumulates.
- [Nethermind docs: Sync](https://docs.nethermind.io/fundamentals/sync/) — tier: canonical-docs — published: 2026 — client-specific sync mode taxonomy (snap, fast, full, archive) and its own hardware baselines.
- [Ethereum Archive Node](https://ethereum.org/developers/docs/nodes-and-clients/archive-nodes/) — tier: canonical-docs — published: 2026 — definition of archive node and why the state history is the expensive part.
- [EIP-4444: Bound Historical Data in Execution Clients](https://eips.ethereum.org/EIPS/eip-4444) — tier: spec — published: 2021-11 (still Stagnant/Draft status, partially implemented) — the actual spec text for history expiry.
- [EIP-7927: History Expiry Meta](https://eips.ethereum.org/EIPS/eip-7927) — tier: spec — published: 2025 — the meta-EIP tracking the rollout phases; use this rather than 4444 alone to describe current status.
- [Partial history expiry announcement (Ethereum Foundation blog)](https://blog.ethereum.org/2025/07/08/partial-history-exp) — tier: canonical-docs — published: 2025-07 — announces that all EL clients support partial history expiry and quantifies the 300-500 GB saving.
- [eth-docker: Client Resource Usage](https://ethdocker.com/Usage/ResourceUsage/) — tier: primary-analysis — published: 2026 — practitioner-maintained per-client disk/RAM table; the most credible non-vendor comparative numbers.
- [Running a Reth Archive Node (Degen Code)](https://www.degencode.com/p/running-a-reth-archive-node) — tier: primary-analysis — published: 2024-2025 — hands-on account of archive node build, useful for the "what actually goes wrong" narrative.

### Current state (Aug 2026)
- Post-Fusaka (3 Dec 2025) the L1 gas limit is 60M, so EL state and receipt growth per block is materially higher than pre-Fusaka teaching material assumes. Any disk-growth figure sourced before Dec 2025 is an underestimate.
- Blob parameter-only (BPO) forks stepped blob target/max upward after Fusaka; search results cite BPO2 on 7 Jan 2026 moving target/max to 14/21. This affects CL disk and bandwidth, not EL state. UNVERIFIED against a primary spec source — flag before teaching the exact numbers.
- Partial history expiry (pre-Merge bodies + receipts droppable) has been live in all EL clients since ~May-July 2025. Rolling-window history expiry (the full EIP-4444 vision, where nodes keep only ~1 year of history) was still not shipped as a hard fork as of Aug 2026.
- Geth added a path-based archive mode that reportedly brings archive from the classic ~12 TB down to roughly 2 TB. Geth's own hardware page still quotes ">12TB", so the docs and the release notes disagree — treat this as unresolved.
- Reth reached 1.0 and is now a mainstream archive choice; the commonly quoted figures are ~1.2 TB full / ~2.8 TB archive. Erigon archive is commonly quoted at ~1.8-2.2 TB. Neither number was confirmable from a first-party doc in this session.
- Commonly taught and now wrong: "an archive node is 12+ TB and only Erigon makes it feasible" — path-based Geth, Reth and Erigon 3 all land in the low single-digit TB range now. Also wrong: "a full node stores all historical state" — it does not, and never did.
- Commonly taught and now wrong: "just run Geth" — Geth's supermajority share is itself the risk the client-diversity argument is about.

### Misconceptions
- Belief: You run "an Ethereum node" as one program. | Reality: You run two processes, EL + CL, joined by the authenticated Engine API. | Why: Pre-Merge documentation and most tutorials predate the split. | Source: https://ethereum.org/developers/docs/nodes-and-clients/run-a-node/
- Belief: A full node keeps the whole history of the chain's state. | Reality: A full node keeps all blocks but only recent state; querying balances at an old block needs an archive node. | Why: "Full" implies completeness in ordinary English. | Source: https://ethereum.org/developers/docs/nodes-and-clients/archive-nodes/
- Belief: Archive nodes are big because they store all the transactions. | Reality: Blocks and receipts are a small fraction; historical *state* (every intermediate trie node) is the cost. | Why: People reason by analogy to a database of transactions. | Source: https://ethereum.org/developers/docs/nodes-and-clients/archive-nodes/
- Belief: Snap sync is a trust-minimised way to get history. | Reality: Snap sync starts from a state snapshot; you have no verified pre-snapshot state and no historical state at all. | Why: The word "sync" suggests eventual completeness. | Source: https://docs.nethermind.io/fundamentals/sync/
- Belief: More blobs means my node needs proportionally more bandwidth. | Reality: Under PeerDAS a node samples a subset of the 128 columns, decoupling per-node bandwidth from total blob capacity. | Why: Pre-Fusaka every node downloaded every blob, which is what old material describes. | Source: https://eips.ethereum.org/EIPS/eip-7594
- Belief: You can run a node on cloud network-attached storage if it's SSD-class. | Reality: Random-read IOPS and latency, not throughput, decide whether you keep up with head; NAS/EBS-style volumes commonly cause a node to fall behind. | Why: Cloud dashboards advertise MB/s, which is the wrong metric. | Source: https://geth.ethereum.org/docs/getting-started/hardware-requirements

## 13.2 — RPC economics: providers, pricing models, rate limits, archive queries, build vs buy

### Concepts
- rpc-is-the-only-door — Every wallet, frontend, indexer and bot reaches the chain through JSON-RPC; the RPC endpoint is therefore both the hard dependency and the single most common production outage source for an on-chain product. | requires: [node-two-process-model] | contrasts: []
- credit-unit-pricing — Providers do not bill per request; they bill per internal unit (Alchemy "compute units", QuickNode "API credits", Infura "credits"), and each provider sets its own multiplier per method, so headline $/million-units numbers are not comparable across providers. | requires: [rpc-is-the-only-door] | contrasts: [flat-request-pricing]
- method-cost-asymmetry — Method costs differ by an order of magnitude within one provider: on Alchemy `eth_getBalance`/`eth_getBlockByNumber` are 20 CU, `eth_call` 26 CU, `eth_getLogs` 60 CU, tracing methods 40 CU, and `eth_getBlockReceipts` carries a 500-CU throughput charge. | requires: [credit-unit-pricing] | contrasts: []
- flat-request-pricing — A second pricing family (dRPC, Chainstack, Dwellir and similar) charges a flat rate per million requests regardless of method, which makes trace- and log-heavy workloads dramatically cheaper and cost forecasting possible. | requires: [credit-unit-pricing] | contrasts: [credit-unit-pricing]
- rate-limit-two-axes — Providers enforce two independent limits: a throughput limit (units or requests per second, which causes 429s under burst) and a volume cap (units per month or per day, which causes hard cutoff), and an app can be well under quota and still be throttled. | requires: [credit-unit-pricing] | contrasts: []
- getlogs-is-the-cost-driver — Almost every surprise RPC bill traces to `eth_getLogs` over wide block ranges or `eth_call` in a loop; providers additionally cap the block range and result size of `eth_getLogs`, so wide scans must be chunked and the chunking interacts directly with cost. | requires: [method-cost-asymmetry] | contrasts: []
- archive-query-definition — An "archive query" is any call carrying a historical block tag older than the ~128 blocks a full node retains (`eth_call`, `eth_getBalance`, `eth_getStorageAt`, `debug_traceTransaction` at an old block); it is a different backend, not a different price line, for most providers. | requires: [sync-mode-archive, rpc-is-the-only-door] | contrasts: []
- trace-vs-debug-namespace — `trace_*` (Erigon/OpenEthereum style) and `debug_*` (Geth style) are separate non-standard namespaces with different semantics and different provider availability; code written against one will not run against the other. | requires: [archive-query-definition] | contrasts: []
- provider-failover-pattern — Production apps run at least two providers behind a client-side or gateway-level fallback, because provider outages are correlated with exactly the moments you need the chain (congestion, depegs, exploits). | requires: [rpc-is-the-only-door] | contrasts: []
- rpc-consistency-hazard — Load-balanced provider fleets can serve two consecutive requests from nodes at different heights, so a read-after-read can go backwards in block number; correctness-sensitive code must pin a block number rather than repeatedly using `latest`. | requires: [provider-failover-pattern] | contrasts: []
- self-host-tco — The build-vs-buy line is set by engineering time, not hardware: the machine is a few hundred dollars a month, but on-call, upgrade forks, disk pruning and resync after corruption are the real cost, so self-hosting wins only at sustained high volume or when you need methods/latency nobody sells. | requires: [offline-pruning-treadmill, credit-unit-pricing] | contrasts: []
- self-host-does-not-remove-provider — Even self-hosters keep a commercial provider as failover and for chains they do not run, so self-hosting is usually additive infrastructure rather than a replacement. | requires: [self-host-tco, provider-failover-pattern] | contrasts: []
- privacy-of-rpc — Your RPC provider sees every address you query and every transaction you broadcast, which is a real deanonymisation surface for wallets and a real business-intelligence leak for protocols. | requires: [rpc-is-the-only-door] | contrasts: []
- enhanced-apis-lock-in — Provider "enhanced" endpoints (token balances, NFT APIs, transfer history, webhooks, `alchemy_*`/`qn_*` namespaces) are not standard JSON-RPC; using them is a portability decision that makes provider migration a code change rather than a URL change. | requires: [rpc-is-the-only-door] | contrasts: [flat-request-pricing]
- websocket-vs-poll — `eth_subscribe` over WebSocket avoids polling cost but adds reconnection, missed-event-on-reconnect and per-connection limits; many providers bill or cap subscriptions separately from HTTP requests. | requires: [rate-limit-two-axes] | contrasts: []

### Current state (Aug 2026)
- Infura did NOT shut down. It rebranded into MetaMask Developer under Consensys and in 2026 moved from monthly request quotas to a daily credit cap plus a credits-per-second throughput limit. Search results state free = 3M credits/day at 500 credits/sec, Developer = 15M/day, Team = 75M/day; I could not fetch the pricing page to confirm (both doc URLs 404'd), so treat these as UNVERIFIED.
- Infura also runs DIN (Decentralized Infrastructure Network), routing some traffic to third-party operators for failover — relevant to the "your provider is a single point of failure" framing.
- The pricing market has bifurcated: opaque credit-multiplier pricing (Alchemy, QuickNode, Infura, Ankr) vs flat per-million-request pricing (dRPC, Chainstack, Dwellir). This bifurcation is the single most teachable 2024→2026 change.
- Archive data has largely stopped being a premium SKU at the top providers — Alchemy advertises free archive access on all chains. Teaching "archive costs 10x" is now wrong for many providers, though it remains true for some.
- L2 RPC is now the majority of most products' traffic; provider chain coverage (Base, Arbitrum, OP, Linea, Solana, Starknet) is a bigger selection factor than mainnet performance.
- Commonly taught and now wrong: "use Infura, it's the standard." The default free tier a 2022 tutorial hands you now has different semantics (daily credits, per-second caps) and the ecosystem default has shifted.

### Misconceptions
- Belief: A "10 million requests/month" plan means 10 million RPC calls. | Reality: It means 10 million internal units; at 26 CU per `eth_call` that is closer to 380k calls. | Why: Marketing pages headline the unit count, not the method multiplier. | Source: https://www.alchemy.com/docs/reference/compute-unit-costs
- Belief: All providers charge roughly the same per call. | Reality: The same `eth_call` reportedly costs 1 unit on one provider and 200 on another; the unit price is meaningless without the multiplier. | Why: People compare $/million-units across providers. | Source: https://www.dwellir.com/blog/best-rpc-node-providers-2026
- Belief: I am under my monthly quota, so I will not be rate limited. | Reality: Throughput limits (units or requests per second) are enforced independently and produce 429s during bursts. | Why: Dashboards foreground the monthly number. | Source: https://www.alchemy.com/docs/reference/compute-unit-costs
- Belief: Archive nodes are only for analytics. | Reality: Any `eth_call` with a historical block tag — including a routine "what was this user's balance at the snapshot block" — is an archive query. | Why: "Archive" sounds like cold storage. | Source: https://www.quicknode.com/guides/infrastructure/node-setup/ethereum-full-node-vs-archive-node
- Belief: Running my own node saves money. | Reality: Hardware is a few hundred dollars a month; the dominant cost is engineering time for forks, pruning, corruption recovery and on-call, and you still pay a provider for failover. | Why: The hardware line item is the only visible one. | Source: https://chainstack.com/self-hosted-blockchain-nodes-myths-2026/
- Belief: Calling `latest` twice gives non-decreasing block numbers. | Reality: A load-balanced provider fleet can answer from nodes at different heights, so height can appear to go backwards. | Why: Developers assume one server behind the URL. | Source: https://ethereum.github.io/execution-apis/api-documentation/
- Belief: Switching providers is a URL change. | Reality: Only if you stayed on standard JSON-RPC; enhanced APIs, `trace_*` vs `debug_*`, and per-provider `eth_getLogs` range caps all break on migration. | Why: The base URL really is the only config most tutorials show. | Source: https://ethereum.github.io/execution-apis/api-documentation/

## 13.4 — Envio / Ponder / alternatives: status, migration effort, selection criteria

### Concepts
- indexer-why — Contracts emit logs but the chain has no query engine; an indexer replays historical logs into a queryable database so a product can ask "all positions for this user, sorted by size" without scanning the chain. | requires: [rpc-is-the-only-door] | contrasts: []
- indexer-is-a-deterministic-fold — An indexer is a deterministic fold over an ordered event stream into a database; every design decision (reorgs, backfill, schema migration) follows from the fact that the input stream can be rewritten. | requires: [indexer-why] | contrasts: []
- subgraph-model — The Graph's subgraph is the legacy default: a YAML manifest, a GraphQL schema and AssemblyScript mappings, deployed to a decentralised network of indexers who are paid in GRT and queried through gateways. | requires: [indexer-why] | contrasts: [ponder-model, envio-model]
- graph-hosted-service-retired — The Graph's free hosted service is fully retired as of 2026, so every legacy subgraph has been forced onto either The Graph's decentralised network (paid, GRT) or a third-party host, which is the event that reshuffled the whole indexer market. | requires: [subgraph-model] | contrasts: []
- graph-compatible-hosts — Goldsky, Alchemy Subgraphs and Ormi host subgraphs with the same manifest/schema/mapping format, so migrating off the hosted service to one of them is a deploy-target change, not a rewrite. | requires: [graph-hosted-service-retired] | contrasts: [rewrite-cost-to-ponder]
- ponder-model — Ponder is a self-hosted open-source TypeScript framework: you write handlers in plain TS against a Postgres-backed schema and get GraphQL and SQL over the result, with local dev and hot reload as first-class. | requires: [indexer-why] | contrasts: [subgraph-model]

## 13.5 — Event pipelines: indexed data into a product database, backfill vs live tail, idempotency, reorgs

### Concepts
- pipeline-two-regimes — Every event pipeline has two distinct regimes with different failure modes: bounded historical backfill (throughput-bound, deterministic, restartable) and unbounded live tail (latency-bound, non-deterministic because the tip can be rewritten). | requires: [indexer-is-a-deterministic-fold] | contrasts: []
- log-natural-key — The natural primary key for an on-chain event is (chainId, blockNumber, transactionIndex, logIndex) — or equivalently (chainId, blockHash, logIndex); using transactionHash alone is wrong because one tx emits many logs and a hash can appear on two forks. | requires: [pipeline-two-regimes] | contrasts: []
- idempotency-via-upsert — Idempotent ingestion means writing with `INSERT ... ON CONFLICT (natural key) DO NOTHING/UPDATE`, so replaying the same block range produces the same table; without it, any retry or restart double-counts. | requires: [log-natural-key] | contrasts: []
- at-least-once-is-the-default — Every real transport (webhooks, queues, WebSocket resubscribe, cursor checkpoints) delivers at-least-once; exactly-once is achieved downstream through idempotent writes keyed on the natural key, never by the transport promising it. | requires: [idempotency-via-upsert] | contrasts: []
- cursor-checkpointing — The pipeline persists a cursor (last fully-processed block) in the same transaction as the rows it wrote, so a crash resumes exactly where it stopped; a cursor written in a separate transaction is the classic source of silent gaps. | requires: [idempotency-via-upsert] | contrasts: []
- reorg-definition — A reorg replaces recently-canonical blocks with a different branch, so events you already ingested can cease to exist or reappear at a different block number and log index. | requires: [pipeline-two-regimes] | contrasts: []
- finality-vs-confirmations — On Ethereum L1 the correct safety boundary is the CL's finalized checkpoint (roughly two epochs, ~13 minutes), not a fixed "12 confirmations" count; on L2s the equivalent boundary is L1 finality of the batch, which is minutes to hours later than the L2's own "confirmed". | requires: [reorg-definition] | contrasts: []
- reorg-depth-reality — Post-Merge L1 reorgs are almost always 1-2 blocks and are common enough to hit weekly; deep reorgs are rare. This makes "handle 1-2 block rewrites correctly, always" the practical requirement rather than "survive a 50-block reorg". | requires: [reorg-definition] | contrasts: []
- indexer-handles-reorgs-your-db-does-not — Modern frameworks roll their own store back automatically (Envio keeps entity state history for unfinalized blocks and reverts on reorg; Ponder keeps a trigger-based transaction log and rolls back to the common ancestor), but that guarantee stops at the indexer's database — anything you copied downstream is your problem. | requires: [reorg-definition, idempotency-via-upsert] | contrasts: []
- side-effects-are-unrollbackable — Emails, push notifications, Slack alerts, fiat payouts and third-party API calls cannot be undone by a reorg rollback, so all irreversible side effects must be gated on finality even when the read model updates optimistically. | requires: [indexer-handles-reorgs-your-db-does-not, finality-vs-confirmations] | contrasts: []
- two-tier-read-model — The standard product pattern is a fast optimistic view (tip data, may be revised, labelled "pending" in the UI) plus a finalized table that only advances on finality and is what accounting, exports and payouts read. | requires: [side-effects-are-unrollbackable] | contrasts: []
- backfill-chunking — Backfill is chunked by block range with the chunk size tuned against the provider's `eth_getLogs` range and result-size caps; chunks must be independently retryable and idempotent so parallel workers and restarts are safe. | requires: [getlogs-is-the-cost-driver, idempotency-via-upsert] | contrasts: []
- ordering-guarantee — Downstream consumers need events in (block, txIndex, logIndex) order for state machines to be correct; parallel backfill workers therefore write rows out of order but must not emit derived events until the range is contiguous. | requires: [backfill-chunking, log-natural-key] | contrasts: []
- schema-change-means-rebackfill — Changing derived logic or adding a field usually requires re-running the whole backfill because the fold is not incremental over logic changes; this makes backfill duration a first-class product constraint, and is the main practical reason indexer speed matters. | requires: [pipeline-two-regimes] | contrasts: [benchmark-is-workload-shaped]
- gap-detection-monitoring — The pipeline must continuously assert two invariants: no missing block numbers in the ingested range, and cursor lag behind chain head under a threshold; both failures are silent otherwise. | requires: [cursor-checkpointing] | contrasts: []
- multichain-clock-skew — With multiple chains there is no global ordering, each chain has its own head, finality rule and reorg behaviour, so a cross-chain read model must either key everything by chain or define an explicit, documented merge rule. | requires: [ordering-guarantee] | contrasts: []

- [Envio: Chain Reorganization Support](https://docs.envio.dev/docs/HyperIndex/reorgs-support) — tier: canonical-docs (vendor) — published: 2026 — documents entity state history for unfinalized blocks, automatic rollback, and the `rollback_on_reorg` config flag.

- [Alchemy: What is a blockchain indexer?](https://www.alchemy.com/overviews/blockchain-indexer) — tier: secondary (vendor) — published: 2026 — landscape framing only.

### Current state (Aug 2026)
- Both major TS frameworks now ship automatic reorg handling by default (Envio via unfinalized entity-state history with a `rollback_on_reorg` flag; Ponder via a trigger-based DB transaction log rolled back to the common ancestor). Writing manual reorg logic inside handlers is no longer normal and is now an anti-pattern.
- Because reorg handling moved into the framework, the teachable risk moved downstream: the failure that still bites teams in 2026 is a side effect (notification, payout, export) fired on unfinalized data.
- Post-Fusaka the L1 gas limit is 60M, so a single block can carry roughly double the logs of 2024 blocks. `eth_getLogs` chunk sizes and result-size caps tuned before Dec 2025 will now fail more often — a concrete, current reason to re-tune backfill chunking.
- Provider-side "streams"/finality-ordered delivery products have matured (exactly-once framing, monotonic sequence numbers, delivery in finality order). Useful, but the guarantee is only end-to-end if your writes are idempotent anyway.
- Commonly taught and now wrong: "wait 12 confirmations". On post-Merge Ethereum the meaningful boundary is the finalized checkpoint, and on L2s neither number is the right one — L2 soft confirmation is not finality.
- Commonly taught and now wrong: "use the transaction hash as the primary key". It is not unique per log and not stable across forks.

### Misconceptions
- Belief: Once my indexer handles reorgs, my pipeline handles reorgs. | Reality: The rollback covers the indexer's own tables; anything replicated downstream or any side effect already fired is not rolled back. | Why: The framework docs say "automatic" and people stop reading there. | Source: https://docs.envio.dev/docs/HyperIndex/reorgs-support
- Belief: transactionHash is a unique key for an event. | Reality: One transaction emits many logs, and the same logical event can exist on two competing branches; the key is (chainId, blockNumber, txIndex, logIndex). | Why: Explorers display events keyed by tx. | Source: https://ponder.sh/docs/indexing/overview
- Belief: 12 confirmations means finalized. | Reality: Post-Merge Ethereum has explicit finality after roughly two epochs (~13 min); confirmation counting is a pre-Merge PoW heuristic. | Why: Exchange deposit UIs still show confirmation counts. | Source: https://ethereum.org/developers/docs/consensus-mechanisms/pos/
- Belief: An L2 transaction is final when the L2 explorer shows it confirmed. | Reality: The sequencer's confirmation is a promise; real finality arrives when the batch is finalized on L1, which is much later. | Why: L2 UX deliberately hides the gap. | Source: https://www.quicknode.com/answers/what-is-a-blockchain-reorg
- Belief: Exactly-once delivery from a streaming API removes the need for idempotent writes. | Reality: Exactly-once is achieved by your idempotent write on a natural key; the transport can always redeliver after a crash. | Why: "Exactly-once" is a strong-sounding marketing claim. | Source: https://docs.envio.dev/docs/HyperIndex/reorgs-support
- Belief: Adding one field to my schema is a small change. | Reality: Derived-state changes usually require a full re-backfill because the fold is not incremental over logic changes. | Why: Normal application migrations are incremental. | Source: https://ponder.sh/docs/indexing/overview
- Belief: If the indexer is running, data is arriving. | Reality: A stalled cursor, a silently dropped block range, or a subscription that reconnected past a gap all look like "running". You must assert contiguity and lag explicitly. | Why: Process liveness is the default health check. | Source: https://bilinearlabs.io/blog/indexing-blockchain-events/

### Practice ideas
- kind: implement — Build a minimal TypeScript ingester: chunked `eth_getLogs` backfill → Postgres with `ON CONFLICT (chain_id, block_number, log_index) DO NOTHING`, cursor row updated in the SAME transaction as the inserts. Acceptance: killing the process with SIGKILL at random points and restarting yields byte-identical table contents to an uninterrupted run.
- kind: break — Move the cursor update into a second transaction, then kill the process between the two. Acceptance: you demonstrate and can name the resulting failure (duplicate rows or a permanent gap) and explain why the single-transaction version is immune.
- kind: implement — Add a reorg simulator: a local Anvil chain where you mine blocks, snapshot, revert, and mine a different branch. Point the ingester at it. Acceptance: after the induced reorg, your table matches the canonical branch exactly, with no orphaned rows from the abandoned branch.
- kind: implement — Add a two-tier read model: a `pending` view fed from tip and a `finalized` table that only advances when the CL `finalized` block passes the row's block. Acceptance: a notification job reads only from `finalized` and provably never fires for an event that was later reorged out.
- kind: measure — Instrument backfill to record rows/second and provider calls per 1000 blocks at three different chunk sizes across a post-Fusaka range. Acceptance: you produce a chunk-size recommendation and identify the provider cap that bounds it.
- kind: fix — Take a pipeline that keys on transactionHash and migrate it to the composite natural key, including a query that finds the rows the old key had silently collapsed. Acceptance: the count of previously-lost logs is reported.
- kind: write — Write the two SQL invariant queries a pipeline should run on a schedule: (1) missing block numbers within the ingested range, (2) cursor lag vs chain head. Acceptance: both produce zero rows on a healthy pipeline and fire on an injected gap.

## 13.6 — Monitoring a deployed protocol: what to alert on, services, invariants in production, detection

### Concepts
- monitoring-is-not-auditing — An audit is a point-in-time check of code; monitoring is a continuous check of state and behaviour, and it catches the categories audits structurally cannot (oracle manipulation, economic drift, key compromise, dependency changes). | requires: [] | contrasts: []
- three-signal-layers — Protocol monitoring has three distinct layers: transaction-level (a specific call pattern), state-level (an invariant over contract storage), and economic-level (TVL, price, flow anomalies); each has different latency, different false-positive rates, and needs different tooling. | requires: [monitoring-is-not-auditing] | contrasts: []
- invariant-monitoring — The highest-signal alert is a protocol-specific invariant evaluated on-chain state every block (e.g. total shares vs total assets, sum of user balances vs contract balance, AMM pool invariant); when it breaks, something is wrong by construction, not by heuristic. | requires: [three-signal-layers] | contrasts: [anomaly-heuristics]
- invariants-are-the-same-artifact-as-fuzzing — The invariants you assert in Foundry invariant tests are the same predicates you should evaluate against mainnet state, so production monitoring should be a deployment target for test artifacts rather than a separate hand-written system. | requires: [invariant-monitoring] | contrasts: []
- anomaly-heuristics — Threshold and statistical alerts (TVL drop % per block, mint volume vs baseline, price deviation from a reference oracle, large single-address flows) catch things no invariant covers but generate false positives, so they belong on a lower-severity channel than invariant breaks. | requires: [three-signal-layers] | contrasts: [invariant-monitoring]
- false-positive-budget — An alerting system's real constraint is human attention: a channel that fires daily on noise is a channel nobody reads during an actual incident, so severity tiering and precision are safety properties, not polish. | requires: [anomaly-heuristics] | contrasts: []
- admin-action-alerting — Every privileged event must alert unconditionally regardless of amount: role grants/revokes, ownership transfer, proxy `Upgraded`, timelock queue/execute, pause/unpause, oracle source change, fee parameter change. These are both the exploit path and the insider path. | requires: [three-signal-layers] | contrasts: []
- timelock-queue-is-the-alert — For a timelocked system the actionable alert is the *queue* event, not the execute: the delay exists precisely to give humans time, and that time is only usable if queueing pages someone. | requires: [admin-action-alerting] | contrasts: []
- offchain-liveness-signals — Half of real protocol incidents are liveness, not theft: a keeper that stopped, an oracle that went stale, a relayer wallet out of gas, a sequencer stalled, a bridge message stuck. These need their own alerts and are commonly missing. | requires: [monitoring-is-not-auditing] | contrasts: [invariant-monitoring]
- detect-to-respond-pipeline — The standard production shape is detect → alert → decide → act, where the act step is an automated or semi-automated privileged transaction; the pipeline is only as fast as its slowest human step, which is why pre-authorised response paths exist. | requires: [invariant-monitoring, admin-action-alerting] | contrasts: []
- automated-response-risk — Auto-pausing on a detector is itself an attack surface and a liveness risk: a false positive halts a live protocol, and the automation's key is a new privileged key to protect; most teams gate automation behind multi-signal confirmation or restrict it to reversible actions. | requires: [detect-to-respond-pipeline] | contrasts: []
- mempool-vs-onchain-detection — Detecting an exploit in the mempool gives you seconds of lead time but is unreliable (private orderflow, builder-only bundles, blind bundles), so mempool detection is an optimisation and post-inclusion state monitoring must be the backstop. | requires: [detect-to-respond-pipeline] | contrasts: []
- monitoring-the-monitor — The monitoring stack has its own failure modes — indexer lag, RPC outage, a bot process that exited — so it needs heartbeat/dead-man's-switch alerts; a silent monitor is indistinguishable from a healthy protocol. | requires: [gap-detection-monitoring] | contrasts: []
- dependency-monitoring — A protocol's risk surface includes contracts it does not control: oracle feeds, an underlying vault/LST, a bridge, a DEX pool it prices against. Their upgrades, pauses and depegs must be monitored as if they were your own. | requires: [admin-action-alerting] | contrasts: []
- alert-enrichment — An alert that arrives with the decoded trace, the balance deltas per address, the attacker's funding path and the affected TVL turns a 20-minute triage into a 2-minute decision; enrichment is the difference between an alert and a page worth waking up for. | requires: [detect-to-respond-pipeline] | contrasts: []

### Current state (Aug 2026)
- The 2026 vendor landscape splits into: detection networks (Forta), integrated dev+ops platforms (Tenderly, OpenZeppelin Defender), commercial threat-detection with pre-emptive claims (Hypernative), and DIY (your own bot reading state each block). Most serious protocols run at least two, because a single detector is a single point of failure.
- Invariant monitoring — evaluating the protocol's own mathematical invariants against live state every block — is now the mainstream recommended practice rather than a niche one, and is explicitly marketed as the mitigation for the Balancer-class exploit of late 2025.
- Pre-authorised automated response (detector → Sentinel → Autotask → Relayer calls `pause()`) is a documented standard pattern, no longer exotic.
- Academic work has moved from "can we detect exploits at all" to "can we detect them in real time with a tolerable false-positive rate" — HOUSTON (NDSS 2026) is the current reference point.
- Consistent with the shared baseline's 2025 loss data (122 incidents, $905.4M, access-control-dominant), the alerting priority ordering should be: privileged/admin actions first, invariant breaks second, economic anomalies third. Most curricula invert this.
- Commonly taught and now wrong: "monitor for reentrancy patterns". Reentrancy was 4th by value in 2025; access control dominated. Monitoring effort should follow the loss distribution.
- Commonly taught and now wrong: "an audit is your security". Audits are point-in-time; the loss data is dominated by categories (key compromise, access control, dependency failure) that continuous monitoring addresses and audits do not.

### Misconceptions
- Belief: If it passed an audit, monitoring is optional. | Reality: Audits cannot cover key compromise, oracle failure, dependency upgrades or economic drift, which is where the losses are. | Why: Audits are the visible, purchasable security artifact. | Source: https://dl.acm.org/doi/10.1145/3660786
- Belief: Monitor for large withdrawals. | Reality: Large withdrawals are a lagging, low-precision signal; a broken protocol invariant is a leading, high-precision one. | Why: Withdrawals are easy to instrument. | Source: https://tenderly.co/blog/how-to-mitigate-balancer-like-exploits-with-invariant-monitoring
- Belief: More alerts means more safety. | Reality: A noisy channel is an ignored channel; false-positive rate is a safety property. | Why: Coverage feels like the goal. | Source: https://www.ndss-symposium.org/wp-content/uploads/2026-f1534-paper.pdf
- Belief: I should alert when the timelock executes. | Reality: By execution the delay is spent; the queue event is the alert that preserves your response window. | Why: Execution is the state change that matters on chain. | Source: https://docs.openzeppelin.com/defender/
- Belief: Auto-pause on detection is strictly safer. | Reality: It adds a privileged automated key and a false-positive-driven liveness risk; it is a tradeoff, not a free win. | Why: Speed of response is the obvious metric. | Source: https://docs.openzeppelin.com/defender/
- Belief: Watching the mempool catches attacks before they land. | Reality: Private orderflow and builder bundles mean a large share of attack transactions never appear in the public mempool. | Why: Historical MEV-bot lore predates private orderflow dominance. | Source: (see MEV-Boost/private-orderflow material; not re-verified this session)
- Belief: My monitoring is working because I haven't seen alerts. | Reality: Silence is ambiguous between healthy and dead; a heartbeat/dead-man's-switch is required to distinguish. | Why: Alerting systems only speak when things are bad. | Source: https://docs.forta.network/

### Practice ideas
- kind: implement — Write a Foundry invariant test for a simple vault (totalAssets >= sum of user shares priced at current rate), then write a TS script that evaluates the SAME predicate against a live fork every block via multicall. ## 13.7 — Simulation: pre-send simulation, forked state, upgrade and governance rehearsal

### Concepts
- simulation-definition — Simulation is executing a transaction against a chosen chain state without broadcasting it, to learn its outcome (revert reason, gas, state diff, emitted logs, balance changes) before committing.
 | requires: [rpc-is-the-only-door] | contrasts: []
- eth-call-is-the-primitive — `eth_call` is the base simulation primitive: it runs a message against a block's state and discards the result; everything richer (overrides, bundles, traces) is a superset of it. | requires: [simulation-definition] | contrasts: []
- estimategas-is-a-simulation — `eth_estimateGas` binary-searches over repeated simulated executions to find a gas limit that succeeds, which is why it is slow, why it can be wrong for state-dependent gas, and why it fails loudly when the transaction would revert. | requires: [eth-call-is-the-primitive] | contrasts: []
- eth-simulatev1 — `eth_simulateV1` is the standardised multi-transaction, multi-block simulation method in the Ethereum execution APIs: it takes block-level and state-level overrides, executes a sequence of calls, and returns per-call results and logs. It is the standards-track replacement for vendor-specific bundle simulation. | requires: [eth-call-is-the-primitive] | contrasts: [tenderly-simulation-api]
- state-overrides — Simulation lets you override balances, nonces, code and individual storage slots before execution, which is what makes "what if this user had 1000 USDC" or "what if this contract were the new implementation" answerable without deploying anything. | requires: [eth-simulatev1] | contrasts: []
- bundle-simulation — Simulating a sequence where each transaction sees the previous one's state is required for anything realistic (approve → swap, flashloan → exploit, queue → warp → execute) and is not expressible with a single `eth_call`. | requires: [eth-simulatev1] | contrasts: [eth-call-is-the-primitive]
- pre-send-ux — Wallets simulate before signing to show asset diffs and warnings; this is the main defence against blind-signing drainer approvals, and it is a product feature, not just a debugging tool. | requires: [simulation-definition] | contrasts: []
- simulation-is-not-a-guarantee — A simulation is against a specific state; by inclusion time the state has moved (price, nonce, allowance, another transaction ahead of yours), so simulation reduces uncertainty but does not remove it — this gap is exactly where sandwiching and stale-approval failures live. | requires: [pre-send-ux] | contrasts: [simulation-definition]
- fork-testing-foundry — Foundry fork testing (`vm.createSelectFork`, `--fork-url`, `--fork-block-number`) runs your test suite against real mainnet state, which is the cheapest way to test an integration against live protocols; pinning the fork block is required for determinism and for cache reuse. | requires: [simulation-definition] | contrasts: [tenderly-virtual-testnets]
- cheatcodes-for-rehearsal — `vm.prank`/`startPrank`, `vm.warp`, `vm.roll`, `vm.store`, `vm.deal` let a fork test impersonate a multisig or timelock and fast-forward through delays, which is what makes a full governance rehearsal expressible as a unit test. | requires: [fork-testing-foundry] | contrasts: []
- tenderly-virtual-testnets — Tenderly Virtual TestNets are hosted, persistent forks of mainnet state with a real RPC URL, so frontends, backends, bots and Safe UIs can all point at the same rehearsal environment — something a local Anvil fork cannot easily provide to a whole team. | requires: [fork-testing-foundry] | contrasts: [fork-testing-foundry]
- anvil-fork — `anvil --fork-url ... --fork-block-number ...` gives a local persistent forked node with impersonation and time control, and is the free equivalent of a hosted virtual testnet for a single developer or CI job. | requires: [fork-testing-foundry] | contrasts: [tenderly-virtual-testnets]
- upgrade-rehearsal — The correct rehearsal for a proxy upgrade is: fork at head, impersonate the admin, execute the real upgrade calldata, then run the existing integration suite plus a storage-layout diff against the fork. Passing means "the upgrade does not break live state", which unit tests on a fresh deployment cannot tell you. | requires: [cheatcodes-for-rehearsal, state-overrides] | contrasts: []
- governance-rehearsal — A governance action must be simulated end to end — propose, reach quorum (override voting-power storage or impersonate whales), queue, warp past the timelock, execute — because most governance failures are in the encoding of the payload or the permissions of the executor, not in the intent. | requires: [upgrade-rehearsal, timelock-queue-is-the-alert] | contrasts: []
- calldata-verification — The artifact a governance voter actually needs is a human-readable diff of what the proposal's calldata does when executed against current state; simulation is the only way to produce it, and publishing it is now an expected part of a serious proposal. | requires: [governance-rehearsal] | contrasts: []
- simulation-in-ci — Running the fork-based upgrade/governance rehearsal in CI on every PR, pinned to a recent block, converts "we simulated it once" into a standing regression check. | requires: [upgrade-rehearsal] | contrasts: []
- simulation-for-incident-triage — During an incident, simulating the attacker's transaction with a decoded trace is the fastest route to understanding the mechanism, and simulating your candidate response (pause, parameter change) before sending it prevents the classic second incident caused by the fix. | requires: [bundle-simulation, detect-to-respond-pipeline] | contrasts: []

### Current state (Aug 2026)
- The biggest change since 2024: `eth_simulateV1` is a standardised execution-API method, so multi-transaction simulation with state and block overrides is no longer a vendor feature. Teaching simulation as "you need Tenderly" is now wrong as a default; Tenderly's value is decoding, persistence, sharing and UI, not the ability to simulate.
- Tenderly's product line consolidated around Virtual TestNets (hosted, persistent, real RPC URL, forkable, CI-integrable). Older material about "Tenderly Forks" describes the predecessor product — check which one the docs describe before writing lesson steps.
- Tenderly's public API is v2 (`https://api.tenderly.co/api/v2/`). Tutorials referencing v1 paths are stale.
- Wallet-side pre-send simulation with asset-diff display is now table stakes rather than a differentiator, which shifts the teaching emphasis from "how to simulate" to "what simulation cannot tell you" (the state-drift gap).
- EIP-7702 (Pectra) makes pre-send simulation harder to reason about: an EOA can carry a delegation designator, so simulating "a transfer from this EOA" may execute contract code. Simulation UIs and any code branching on `EXTCODESIZE` must account for this.
- Fusaka's per-transaction gas cap (~16.78M) means a rehearsal bundle that executes fine in a fork can be unsendable as a single mainnet transaction. Governance payload size is now a real constraint to check in simulation.
- Commonly taught and now wrong: "simulate with `eth_call` and you know what will happen". `eth_call` cannot express a sequence, cannot override state on most public endpoints, and gives no decoded trace.

### Misconceptions
- Belief: A successful simulation means the transaction will succeed. | Reality: It succeeded against one historical state; price moves, nonce changes, front-running and allowance changes can all flip the outcome by inclusion time. | Why: The tool returns a binary success/failure. | Source: https://ethereum.github.io/execution-apis/api/methods/eth_simulateV1/
- Belief: `eth_estimateGas` returns the gas the transaction will use. | Reality: It binary-searches for a limit that succeeds at current state; actual usage differs, and state-dependent branches (cold/warm slots, first-time storage writes) move it. | Why: The name says "estimate gas". | Source: https://geth.ethereum.org/docs/interacting-with-geth/rpc/ns-eth
- Belief: Simulation requires a paid service. | Reality: `eth_simulateV1` is a standard method, and `anvil --fork-url` gives a full local forked chain for free. | Why: Vendor tooling dominates search results and tutorials. | Source: https://ethereum.github.io/execution-apis/api/methods/eth_simulateV1/
- Belief: Testing the new implementation contract's unit tests is enough for an upgrade. | Reality: Upgrades fail on live storage layout and live state, which only a fork rehearsal at head exercises. | Why: Unit tests run against a fresh deployment with empty storage. | Source: https://www.getfoundry.sh/guides/fork-testing
- Belief: If the governance proposal's intent is right, the proposal is right. | Reality: Most governance failures are encoding and permission failures in the payload — wrong target, wrong selector, executor lacks the role, value not forwarded. | Why: Voters read the description, not the calldata. | Source: https://getrecon.substack.com/p/automate-your-security-operations
- Belief: Forking without pinning a block is fine. | Reality: An unpinned fork is non-deterministic and defeats Foundry's RPC cache, making tests flaky and slow. | Why: Omitting the flag is easier and works once. | Source: https://www.getfoundry.sh/guides/fork-testing
- Belief: Simulating an EOA-originated transfer cannot execute contract code. | Reality: Post-EIP-7702 an EOA can carry a delegation designator and run the delegate's code. | Why: The EOA/contract distinction was absolute before Pectra. | Source: https://eips.ethereum.org/EIPS/eip-7702

## 13.8 — Incident response: live exploit, pause mechanisms, war-room practice, post-mortems

### Concepts
- irreversibility-changes-everything — On-chain incident response has no rollback, no WAF rule and no "revoke the session"; once a transaction is included the funds are gone, so response is about stopping the *next* transaction, not undoing the last one. | requires: [monitoring-is-not-auditing] | contrasts: []
- clock-is-the-adversary — Exploits execute in seconds to minutes while human decision-making takes minutes to hours, so every response capability must be pre-decided, pre-authorised and pre-rehearsed; the first 30-60 minutes determine the loss. | requires: [irreversibility-changes-everything, detect-to-respond-pipeline] | contrasts: []
- war-room-roles — A functioning war room separates three roles that otherwise collide: an ops/incident lead who decides and sequences, a security analyst who reverse-engineers the exploit, and a comms lead who owns external messaging — one person cannot do two of these under pressure. | requires: [clock-is-the-adversary] | contrasts: []
- parallel-not-serial — Forensics, containment decisions and communications must run concurrently from minute one; teams that finish the analysis before deciding whether to pause lose the window. | requires: [war-room-roles] | contrasts: []
- containment-ladder — Pause is not the only lever; the ladder runs from full pause → disable specific entry points → cap or rate-limit flows → raise fees/parameters to make the attack unprofitable → blacklist → do nothing and let the exploit run out of profitable surface. The right rung depends on how much of TVL is still exposed. | requires: [parallel-not-serial] | contrasts: []
- pause-is-a-two-sided-risk — A pause guardian that can stop an exploit can also freeze user funds arbitrarily; it is simultaneously a security control and a centralisation vector, and both sides must be presented when it is designed. | requires: [containment-ladder] | contrasts: []
- pause-design-patterns — Mitigations that keep pause useful without making it a permanent censorship power: a low-threshold guardian multisig that can pause but a high-threshold/governance path to unpause, an automatic forced expiry of the pause after a deadline, and a cooldown preventing immediate re-pause. | requires: [pause-is-a-two-sided-risk] | contrasts: []
- pause-efficacy-declines — Pause is a race against an automated attacker, and its effectiveness declines as attackers get faster and more automated; treating pause as the answer rather than as one bounded tool is a strategic error. | requires: [containment-ladder] | contrasts: [pause-design-patterns]
- guardian-key-operational-readiness — A pause capability is only real if the signers can be reached and can sign at 3am on a Sunday: signer geographic spread, an out-of-band contact channel, pre-built and pre-simulated pause calldata, and a rehearsed signing flow are the actual capability. | requires: [pause-design-patterns, simulation-for-incident-triage] | contrasts: []
- exploit-triage-questions — The first analysis loop answers four questions in order: what is the attack transaction, what is the mechanism, is the remaining TVL still exposed to the same mechanism, and does the same mechanism exist in our other deployments/chains. | requires: [parallel-not-serial, simulation-for-incident-triage] | contrasts: []
- copycat-window — Once an exploit is public, copycats replay it against forks and sibling deployments within minutes, so notifying similar protocols and checking your own other chains is part of containment, not aftercare. | requires: [exploit-triage-questions] | contrasts: []
- seal-911 — SEAL 911 (Security Alliance) is a free 24/7 emergency hotline connecting a team under active attack to vetted security responders; having the contact path saved before you need it is itself a preparedness item. | requires: [clock-is-the-adversary] | contrasts: []
- whitehat-safe-harbor — SEAL's Whitehat Safe Harbor Agreement is a pre-adopted legal framework letting a protocol authorise good-faith fund rescue in advance; adopting it before an incident converts an ambiguous legal situation into a defined one during the rescue. | requires: [seal-911] | contrasts: []
- negotiation-and-bounty — Public on-chain negotiation with an attacker (a bounty offer, typically a percentage, communicated via an on-chain message) is a real and sometimes effective recovery path, and it has legal and precedent-setting consequences that should be pre-discussed with counsel, not improvised. | requires: [containment-ladder] | contrasts: []
- comms-during-incident — Communication policy is a security decision: too early and you tip off copycats and cause a bank run, too late and you destroy trust; the workable pattern is early acknowledgement without mechanism details, a fixed update cadence, and a single authoritative channel. | requires: [war-room-roles] | contrasts: []
- wargames-rehearsal — Incident response is a skill that decays; scheduled tabletop and live-fire exercises (SEAL Wargames, internal drills against a forked mainnet) are what convert a written runbook into a capability. | requires: [guardian-key-operational-readiness, upgrade-rehearsal] | contrasts: []
- postmortem-purpose — A post-mortem is written for three audiences with different needs — users (am I affected, what do I do), the ecosystem (what was the bug class so we can check ourselves), and the team (which control failed) — and a document that serves only PR fails all three. | requires: [comms-during-incident] | contrasts: []
- postmortem-content — A credible post-mortem contains: a timeline with block numbers and timestamps, the root cause at code level, the exact loss and affected users, why detection took as long as it did, why the response took as long as it did, remediation with dates, and what is being changed in the process rather than only in the code. | requires: [postmortem-purpose] | contrasts: []
- blameless-but-specific — The post-mortem norm is blameless about people and ruthlessly specific about controls: "the invariant that would have caught this did not exist" is useful; "an engineer made a mistake" is not. | requires: [postmortem-content] | contrasts: []

### Current state (Aug 2026)
- SEAL (Security Alliance) is now the ecosystem's de facto incident-response institution: SEAL 911 hotline, a crypto-native ISAC, SEAL Intel threat reports (a 2Q 2026 threat summary exists), SEAL Frameworks, SEAL Wargames, the Whitehat Safe Harbor Agreement and the Security Research Legal Defense Fund. Any 2026 incident-response lesson that does not mention SEAL 911 is incomplete.
- Automated response (detector → pre-authorised pause transaction) has moved from exotic to marketed-as-standard, which sharpens rather than removes the centralisation debate.
- The Resolv USR incident (22 March 2026) is cited as the current canonical example of *good* response: detection of unauthorised minting, rapid pause, coordinated recovery within minutes. UNVERIFIED beyond a single secondary source — verify before using as the worked example.
- Consistent with the shared baseline's 2025 data (122 incidents, $905.4M, access control dominant), the response playbook should be weighted toward key-compromise and privileged-action incidents, not only clever-Solidity-bug incidents. A key-compromise incident has a completely different response (you cannot trust your own admin path) and most curricula never cover it.
- Commonly taught and now wrong: "have a pause function and you're covered". Trail of Bits' position — pause efficacy declines as attackers automate, and key-centric controls are the thing to mature past — is the current state of the art.
- Commonly taught and now wrong: "post-mortems are optional / a PR exercise". The ecosystem norm in 2026 is a technical post-mortem with a block-level timeline, and its absence is read as a signal.

### Misconceptions
- Belief: If we get hacked we can pause and fix it. | Reality: Pause races an automated attacker who may finish in one transaction, and it does nothing about funds already taken. | Why: Web2 incident response usually has a rollback or a kill switch that works. | Source: https://blog.trailofbits.com/2025/06/25/maturing-your-smart-contracts-beyond-private-key-risk/
- Belief: The pause guardian is a pure safety feature. | Reality: The same key can freeze honest users indefinitely; it is a centralisation vector that must be bounded by expiry, cooldown and a separate unpause path. | Why: The feature is named for its benign use. | Source: https://arxiv.org/pdf/2107.10979
- Belief: We should understand the exploit fully before deciding to pause. | Reality: Analysis, containment and comms must run in parallel; serialising them spends the window. | Why: Engineers are trained to diagnose before acting. | Source: https://immunefi.com/blog/security-guides/how-to-run-a-war-room-a-playbook-for-crypto-protocols/
- Belief: Staying silent protects us. | Reality: Silence erodes trust hour by hour and does not stop copycats who are reading the chain, not your Twitter. | Why: Opsec instincts say say nothing. | Source: https://immunefi.com/blog/security-guides/how-to-run-a-war-room-a-playbook-for-crypto-protocols/
- Belief: The incident is over when the contract is paused. | Reality: Sibling deployments on other chains, forks of your code, and the same bug class in dependent protocols are still live. | Why: The dashboard stops showing losses. | Source: https://securityalliance.org/our-work/seal-911
- Belief: We'll figure out who to call when it happens. | Reality: SEAL 911 exists precisely because that improvisation costs the first critical minutes; the contact path and the safe-harbor adoption belong in the runbook beforehand. | Why: Nobody plans for the thing that has not happened. | Source: https://securityalliance.org/our-work/seal-911
- Belief: A written runbook means we are prepared. | Reality: Untested runbooks fail on the unglamorous parts — a signer unreachable, calldata that reverts, nobody with the Twitter password. Only drills reveal these. | Why: The document is the visible artifact. | Source: https://securityalliance.org/our-work
- Belief: A post-mortem should protect the team. | Reality: It should be blameless about people and specific about which control failed; vagueness is what destroys credibility. | Why: Legal and PR instincts pull toward vagueness. | Source: https://immunefi.com/blog/security-guides/how-to-run-a-war-room-a-playbook-for-crypto-protocols/

### Practice ideas
- kind: implement — Write a `Pausable` vault with the mature pattern: a 2-of-N guardian multisig can pause, only governance can unpause, the pause auto-expires after 7 days, and re-pause is blocked for 24 hours after expiry. Acceptance: Foundry tests prove all four properties, including that a guardian cannot keep funds frozen indefinitely.
- kind: break — On a forked mainnet, run a red-team drill: one participant executes a scripted drain against a deployed test protocol while the other must detect it and get a pause transaction signed and included. Acceptance: you record wall-clock time from first malicious transaction to pause inclusion, and the percentage of TVL that left in that window.
- kind: fix — Take the drill above and pre-build the pause calldata, pre-simulate it (13.7), and put it in a Safe transaction ready to sign. Re-run the drill. Acceptance: response time improves measurably and you can state which step was the bottleneck before and after.
- kind: write — Write the protocol's incident runbook: the three war-room roles with named people, the containment ladder with the criteria for each rung, the SEAL 911 contact path, the comms templates for T+15min and T+2h, and the signer contact list with an out-of-band channel. Acceptance: a person who was not in the room could execute the first 15 minutes from the document alone.
- kind: read — Read two real post-mortems of 2025-2026 incidents and score them against the postmortem-content checklist (timeline with blocks, root cause at code level, exact loss, detection delay, response delay, remediation dates, process change). Acceptance: you can name at least one item each one omits.
- kind: write — Write a post-mortem for the drill you ran, including honest detection and response delays. Acceptance: it contains a block-level timeline and at least one process change that is not "add a test".
- kind: implement — Add the copycat check to the runbook as a script: given a bug signature, enumerate your protocol's deployments across every chain and report which ones share the vulnerable code hash. Acceptance: it correctly identifies a deliberately-planted vulnerable sibling deployment.
